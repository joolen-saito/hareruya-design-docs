A15-01 ログイン ／ API デッキビルダー — ログイン

<!-- リバース詳細設計書（API・機能単位）。deck-api が提供する会員ログインAPI。 -->

概要

デッキビルダーアプリの利用者が会員のメールアドレスとパスワードでログインし、以降のAPI呼び出しに使うアクセストークンを取得するためのAPIである。deck-api（デッキビルダー用のAPIアプリケーション）が提供するJSON APIで、受け取ったメールアドレスとパスワードを会員データと照合し、認証成功時にアクセストークンとセッションIDを返す。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。既存実装のふるまい、参照するデータ、判定境界、副作用を確認し、仕様の確からしさを把握することを目的とする。確認値はdeck-apiのログイン処理、入力フォーム定義、トークン生成処理、ルート定義（config/routes.yaml）、照合先の会員データを正とする。

本機能のカスタマイズ区分は現行踏襲であり、挙動はデッキビルダー用APIの現行実装（deck-api）を、DB関連はec-cube-enterpriseの実装を正とする。

対象はJSON APIエンドポイントであり、ブラウザ向けの画面を持たない。本文ではフレームワークのコントローラ型名やメソッド名を主説明としない。「利用者視点の入口」にHTTPメソッドとパスパターンを書く。

本書で扱うこと

  • メールアドレスとパスワードによる会員ログインの判定
  • 入力検証（必須・形式）と認証照合の境界
  • 認証成功時に発行するアクセストークンとセッションID、およびトークンの以降の用途
  • 認証失敗時・入力不正時の応答

本書で扱わないこと

以下は本書では仕様確定せず、実装または別APIの設計を正とする。

  • 発行したトークンを用いる各デッキビルダーAPIの認可（各APIの設計を正とする）
  • 会員データの登録・編集（会員管理機能を正とする）
  • ログアウト（A15-02 ログアウトの設計を正とする）
  • パスワードハッシュ方式・ソルトの詳細仕様（会員認証の共通仕様を正とする）

DB関連の記述はec-cube-enterpriseの実装を正とする。挙動は現行のデッキビルダー用API（deck-api）を正とする。現行と移行先で会員テーブルの主キー列名・会員ステータスの持ち方が異なる。

利用者視点の入口

入口URLエンドポイント期待されるふるまい

応答形式はJSON。呼び出し元はデッキビルダーアプリ。

認証・認可

観点内容
本APIの認証本APIはトークン取得の入口であり、jwt-tokenヘッダを要求しない。未認証のクライアントが呼び出せる。
照合先メールアドレスで会員を引き、入力パスワードを会員のソルトでハッシュ化した値と保存値を突合する。会員は有効状態（ステータスが本会員）かつ未削除のものに限る。
トークン発行認証成功時、署名付きJWTを発行する。ペイロードは発行者・利用者ID（会員ID＝aud）・発行時刻を持つ。署名方式はHS256。
以降の認可呼び出し元は受け取ったアクセストークンを以降のdeck-apiのjwt-tokenヘッダに付与する。各APIはトークンのaud（会員ID）からプレイヤーを引いて認可する（各APIの設計を正とする）。
認証失敗時該当会員が無い、またはパスワードが一致しない場合は認証拒否（HTTP 401）とする。

トークン原値・署名シークレット・パスワードは本書に記載しない。

処理フロー

会員ログインを行う（POST /user/login）

  1. リクエストボディからid（メールアドレス）とpasswordを受け取る。
  2. 入力をログインフォームへ投入し検証する。必須・形式の検証に失敗した場合は入力不正（HTTP 400）のJSONを返す。
  3. メールアドレス・有効状態（本会員）・未削除の条件で会員を引く。該当が無い場合は認証拒否（HTTP 401）のJSONを返す。
  4. 入力パスワードを会員のソルトでハッシュ化し、会員の保存パスワードと突合する。一致しない場合は認証拒否（HTTP 401）のJSONを返す。
  5. 一致した場合、会員IDを利用者IDとするアクセストークンを発行する。
  6. トークンを有効期限付きのCookieに設定し、セッションを開始する。
  7. コード200・成功メッセージ・アクセストークン・セッションIDのJSONを返す。

集計条件

本APIは一覧・検索・件数を返さない。集計を行わない。

副作用

アクセストークンを有効期限付きのCookieに設定する。Cookie名は設定キーcookie_nameとtoken_nameを結合した名称とし、有効期限は設定キーjwt_expire_daysの日数に基づく。セッションを開始する。会員・プレイヤー等の業務データは更新しない。

応答はJSON応答整形を経て返す。プロパティはcamelCase、日時はISO8601、serialize_nullは有効とする。

業務ルール・計算

  • 認証判定は既存のID、パスワード、会員・管理者状態、利用可否フラグを正とし、認証成功時のみセッションまたはトークンを発行・更新する。
  • 認証失敗、退会・停止・権限不足の場合は業務データを更新せず、既存のエラー形式で返す。
  • ログイン時に金額・ポイント・在庫などの業務値は計算しない。

  2. 値が指定された条件のみを検索条件に積む。カード名・テキストは空白・カンマで語分割し、語ごとに日英の名称／テキストに対して部分一致を取り、条件の論理（AND／OR／NOT）で結合する。

一意化カード識別子で集約し、種別・色は集約値を数値配列へ展開する。総件数はカード識別子の重複排除で数える。
除外除外色・除外マナ総量・除外パワー・除外タフネス・除外ロイヤルティを満たす行を除外する。フォーマット指定時は使用可（必要に応じて禁止を含む）区分に限定する。
並び順sort（色順・マナ総量・パワー・タフネス）をorder（昇順／降順）で並べ、続いて英語名で整える。完全一致優先時はカード名完全一致を最優先する。
ページングpageとper_pageで算出する。1ページ件数は上限100に丸める。

処理フロー

デッキ情報を新規登録する（POST /deck）

  1. jwt-tokenヘッダのトークンを検証し、プレイヤーを特定する。検証できない場合は認証拒否（HTTP 401）とし、{code, message}を返す。
  2. リクエストボディの全パラメータを受領し、新規デッキを生成する。
  3. 採用カードを受け取り、ボード区分ごとに採用カード・メイビー・アトラクション・ステッカーとして組み立てる。各カードの整合性を検証し、不正な場合は入力不正（HTTP 400）とする。
  4. フォーマット・アーキタイプ・公開範囲・代表カード画像・キャンペーンタグを解決し、デッキ本体に設定する。設定済み内容からレギュレーション違反を判定する。
  5. デッキ本体の整合性を検証し、不正な場合は入力不正（HTTP 400）とする。
  6. デッキ本体と採用カードを保存する。限定公開トークン未設定の場合は、発番したデッキIDから閲覧用トークンを生成して保存する。一連の保存は1件のトランザクションで行い、例外時はロールバックする。
  7. 成功時はコード200・メッセージ・デッキIDを返す。公開範囲が限定公開の場合は閲覧用トークンも返す。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。確認値はdeck-apiのデッキ削除処理、ルート定義（config/routes.yaml）、デッキ削除処理（デッキ保存サービス）、デッキを扱うエンティティ、共通の認証処理を正とする。

本機能のカスタマイズ区分は現行踏襲とする。挙動はdeck-api（デッキビルダー用APIアプリケーション）の実装を確認値とし、DB関連の記述（テーブル名・列名・永続化先）はec-cube-enterpriseの実装を正とする。

対象はJSON APIエンドポイントであり、ブラウザ向けの画面を持たない。本文ではフレームワークのコントローラ型名やメソッド名を主説明としない。「利用者視点の入口」にHTTPメソッドとパスパターンを書く。

本書で扱うこと

  • 認証したプレイヤーによる自身のデッキの削除と所有者チェック
  • 論理削除（削除日時の設定）とRedis一時保存の削除
  • 認証失敗・対象なし・他人デッキ・処理失敗時の応答

本書で扱わないこと

以下は本書では仕様確定せず、実装または別APIの設計を正とする。

  • デッキの新規登録・更新・参照（デッキ情報登録・デッキ情報更新・デッキ情報参照の各APIの設計を正とする）
  • 採用カード・関連テーブルの物理削除（本APIはデッキ本体の論理削除のみを行う）
  • トークンの発行（デッキビルダー用ログインの設計を正とする）

デッキ情報を削除する（DELETE /deck/{id}）

  3. 対象デッキの所有者が認証したプレイヤーと一致しない場合は認証拒否（HTTP 401、「Authentication failed」）とする。
  4. 対象デッキに削除日時を設定して論理削除し、当該デッキのRedis一時保存があれば削除する。一連の処理は1件のトランザクションで行い、例外時はロールバックして処理失敗（HTTP 500）とする。
  5. 成功時はコード200・メッセージ（「Deck delete success」）を返す。

処理フロー

デッキ情報を参照する（GET /deck/{id}）

  1. クエリの限定公開トークン（display_token）を受領する。
  2. デッキIDに対応するRedis一時保存（下書き）を取得する。
  3. 下書きがある場合は公開範囲を判定する。公開デッキはそのまま返す。非公開デッキはトークン検証で所有者本人と確認できる場合のみ返す。限定公開デッキは限定公開トークン一致、または所有者本人の場合のみ返す。可否を満たす場合はコード200・メッセージを付与して返す。満たさない場合は該当なし（HTTP 404）とする。
  4. 下書きが無い場合はデータベースからデッキIDの情報を取得する。
  5. データベースのデッキについても同じ公開範囲判定を行う。可否を満たす場合はコード200・メッセージを付与して返す。満たさない、または該当が無い場合は該当なし（HTTP 404、「Deck is not found」）とする。

処理フロー

デッキ情報を検索する（GET /decks）

  1. クエリパラメータを既定値とともに受領する。
  2. モードが自分のデッキ検索（private）の場合はjwt-tokenヘッダのトークンを検証し、プレイヤーを特定する。検証できない場合は認証拒否（HTTP 401）とする。公開検索（public）の場合は認証を行わない。
  3. 検索条件でデッキを絞り込む。公開検索は公開デッキ、自分のデッキ検索は認証プレイヤー所有デッキを対象とする。デッキ種別フラグがいずれも対象外の場合は空の一覧と総件数0を返す。

  5. デッキタグ・キャンペーンタグを各デッキに整形して付与し、総件数とともにコード200・メッセージで返す。
