詳細設計書

A05-01 注文印刷_印刷情報をプリンタへ送信 / API 受注管理 — 注文印刷（印刷情報送信・印刷済み更新）

概要

店頭のスタック用紙プリンタ（印刷クライアント）が、印刷対象の受注からスタック用紙の印刷情報を取得し、印刷完了後に該当受注のステータスを印刷済み相当へ更新するためのAPIである。pf-api（受注・買取連携用のAPIアプリケーション）が提供するエンドポイントで、リクエストパラメータConnectionTypeの値によって動作が2系統に分岐する。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。確認値はpf-apiの注文印刷処理、ルート定義（config/routes.yaml）、受注の印刷情報取得処理、店頭注文番号の参照、受注ステータスのマスタ定義を正とする。

本機能のカスタマイズ区分はカスタマイズで、挙動の参照リポはpf-api、DB関連の記述はec-cube-enterpriseを正とする。

本エンドポイントの応答はJSONではなく、印刷情報を表すXML（GetRequest系）または空応答（SetResponse系）である。本文ではフレームワークのコントローラ型名やメソッド名を主説明としない。「利用者視点の入口」にHTTPメソッドとパスパターンを書く。

本書は次の2つの機能を1つのエンドポイントとして扱う。

  • A05-01 注文印刷_印刷情報をプリンタへ送信（ConnectionTypeがGetRequestの分岐）
  • A05-02 注文印刷_該当受注のステータスを印刷済みに変更（ConnectionTypeがSetResponseの分岐）

本書で扱うこと

  • 印刷対象受注の抽出と、スタック用紙の印刷情報（XML）の生成・送信（GetRequest）
  • 印刷完了後の該当受注のステータス更新（SetResponse）
  • 印刷情報のXMLログファイルへの書き出しという副作用
  • 本エンドポイントの認証有無

本書で扱わないこと

以下は本書では仕様確定せず、実装または別APIの設計を正とする。

  • 印刷クライアント側の通信制御・再送・プリンタ機種仕様（呼び出し元クライアントの仕様を正とする）
  • 店頭注文番号そのものの採番・参照API（A05-03 店頭注文番号取得の設計を正とする）
  • 受注ステータスの遷移ルール全般（受注管理の各設計を正とする）
  • まとめ買取・買取受注に関する各API（ネット買取・店頭買取の各設計を正とする）

認証・認可

観点内容
認証方式本エンドポイントは認証処理を行わない。jwt-tokenヘッダの検証も管理ログインのプロキシも経由しない。pf-apiの他の管理系APIが用いる共通の認証処理を呼び出さず、未認証で実行できる。

未認証で実行できる点は本書の確認値である。トークン原値・署名シークレットは本書に記載しない。

処理フロー

印刷情報を送信する（GET /order/print/direct、ConnectionTypeがGetRequest）

  1. リクエストのConnectionTypeを読み、値がGetRequestであることを判定する。
  2. 印刷対象の受注一覧を取得する。店頭受取で注文受領の受注、スムーズ店頭受取で所定の支払方法かつ未確定・未出荷・未取消・未受領・店頭予約日なし・スマレジコードありの受注、ブラウザ印刷フラグが立つ受注を対象とし、最大10件を取得する。
  3. 受注ごとに、注文日・合計金額・店頭注文番号・スマレジコード・問い合わせ有無・注文詳細URLを組み立て、1受注分の印刷情報（ePOSPrint要素）を生成する。配送がスムーズ店頭受取の場合は合計金額欄を「スムーズ店頭受取」とする。
  4. 全受注分を束ねたスタック用紙の印刷情報XMLを生成する。対象受注が無い場合はXMLを生成せず空文字とする。
  5. 生成した印刷情報が空でない場合、印刷不具合検証のため印刷情報のXMLをログファイルへ書き出す（副作用）。
  6. 印刷情報XMLを応答本体としてストリーム送信する。応答のContent-Typeはapplication/octet-streamとする。

印刷済みステータスへ更新する（POST /order/print/direct、ConnectionTypeがSetResponse）

  1. リクエストのConnectionTypeを読み、値がSetResponseであることを判定する。
  2. POSTで受け取ったResponseFileのXMLを解析する。解析に失敗した場合は内容とエラーを記録して更新を行わずに戻る。
  3. XMLの直接印刷結果が偽、または印刷結果要素が1件も無い場合は内容を記録して更新を行わずに戻る。
  4. 印刷結果要素ごとに、印刷ジョブIDの先頭部分から受注IDを取り出し、対象受注を特定する。受注が見つからない場合はエラーを記録して次の要素へ進む。
  5. 対象受注の補助情報のブラウザ印刷フラグが立っている場合は、そのフラグを倒すだけに留める。立っていない場合は受注のステータスをピック中へ更新し、補助情報の確定日時に現在時刻を設定する。
  6. 各受注の更新を反映する。
  7. 空の本文（HTTP 200、text/xml）を返す。

業務ルール・計算

項目内容
更新対象リクエストで指定されたID・入力値に対応する業務データを対象にする。対象特定、入力不正、認証・認可の判定順序は処理フローとバリデーションの各節を正とする。
更新方法入力値を対象データへ上書きまたは追加登録する。履歴登録や関連データ更新がある場合は入出力の副作用およびDBカラムの節を正とする。
計算処理本APIでは金額・税・ポイント・在庫数量の再計算や丸めを行わない。ステータスやコメント等の更新は、実装で定義された遷移・存在確認・担当者判定に従う。
応答値成功時は処理結果コードまたは更新後に取得した値を返す。レスポンス値は本API内で独自集計せず、保存結果または取得結果をJSON応答へ整形する。

副作用

本エンドポイントは参照のみではなく、次の副作用を持つ。

  • 印刷ログファイルの書き出し（GetRequest）。生成した印刷情報が空でない場合、印刷情報のXMLをログ保存ディレクトリ（var/log/print_logs/配下）にタイムスタンプと一意名を付けたファイルとして書き出す。ディレクトリが存在しない場合は作成する。
  • 受注ステータスの更新（SetResponse）。印刷結果に含まれる受注について、ブラウザ印刷フラグが立つ場合はフラグを倒し、立たない場合は受注のステータスをピック中へ更新し、補助情報の確定日時に現在時刻を設定する。これらはデータベースへの更新である。

応答はXMLまたは空応答であり、JSON応答整形・camelCaseのプロパティ命名は適用しない。

本エンドポイントはフォーム型やマスタ存在チェックによる入力検証を行わない。ConnectionTypeが想定値（GetRequest・SetResponse）に一致しない場合は処理を行わず応答を組み立てない。SetResponseではResponseFileのXML解析に失敗した場合と直接印刷結果が偽・印刷結果要素なしの場合に更新を行わずログに記録して戻る。

処理フロー

印刷情報を送信する（GET /order/print/direct、ConnectionTypeがGetRequest）

  1. リクエストのConnectionTypeを読み、値がGetRequestであることを判定する。
  2. 印刷対象の受注一覧を取得する。店頭受取で注文受領の受注、スムーズ店頭受取で所定の支払方法かつ未確定・未出荷・未取消・未受領・店頭予約日なし・スマレジコードありの受注、ブラウザ印刷フラグが立つ受注を対象とし、最大10件を取得する。
  3. 受注ごとに、注文日・合計金額・店頭注文番号・スマレジコード・問い合わせ有無・注文詳細URLを組み立て、1受注分の印刷情報（ePOSPrint要素）を生成する。配送がスムーズ店頭受取の場合は合計金額欄を「スムーズ店頭受取」とする。
  4. 全受注分を束ねたスタック用紙の印刷情報XMLを生成する。対象受注が無い場合はXMLを生成せず空文字とする。
  5. 生成した印刷情報が空でない場合、印刷不具合検証のため印刷情報のXMLをログファイルへ書き出す（副作用）。
  6. 印刷情報XMLを応答本体としてストリーム送信する。応答のContent-Typeはapplication/octet-streamとする。

印刷済みステータスへ更新する（POST /order/print/direct、ConnectionTypeがSetResponse）

  1. リクエストのConnectionTypeを読み、値がSetResponseであることを判定する。
  2. POSTで受け取ったResponseFileのXMLを解析する。解析に失敗した場合は内容とエラーを記録して更新を行わずに戻る。
  3. XMLの直接印刷結果が偽、または印刷結果要素が1件も無い場合は内容を記録して更新を行わずに戻る。
  4. 印刷結果要素ごとに、印刷ジョブIDの先頭部分から受注IDを取り出し、対象受注を特定する。受注が見つからない場合はエラーを記録して次の要素へ進む。
  5. 対象受注の補助情報のブラウザ印刷フラグが立っている場合は、そのフラグを倒すだけに留める。立っていない場合は受注のステータスをピック中へ更新し、補助情報の確定日時に現在時刻を設定する。
  6. 各受注の更新を反映する。
  7. 空の本文（HTTP 200、text/xml）を返す。

概要

スマレジが送信する取引情報の通知を受け取り、対象会員のポイントとポイント履歴を更新するためのAPIである。pf-eccube3のHareruyaEcプラグインが提供するJSON APIで、通知の区分（通常・取消・打消）に応じて会員ポイントの加減算、ポイント履歴の登録または取消、店頭注文の出荷完了反映を行い、支店コードの明細は支店システムのスマレジ受信APIへ転送する。取消・打消の処理では取引IDからポイント履歴を取得して巻き戻す。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。確認値はHareruyaEcプラグインのスマレジ取引取込処理、フロントのルート登録（ControllerProvider）、ポイント履歴テーブル・会員（プレイヤー）・注文サブ・オプションマスタ・ポイント区分マスタを正とする。

本機能のカスタマイズ区分はカスタマイズで、挙動の参照リポはpf-eccube3（HareruyaEcプラグイン）とする。DB関連の記述（テーブル名・列名・永続化先）はec-cube-enterpriseを正とする。

対象はJSON APIエンドポイントであり、ブラウザ向けの画面を持たない。本文ではフレームワークのコントローラ型名やメソッド名を主説明としない。「利用者視点の入口」にHTTPメソッドとパスパターンを書く。

本書で扱うこと

  • スマレジ取引通知の受信と、取引区分（通常・取消・打消）の判定
  • 会員ポイントの加減算とポイント履歴の登録・取消
  • 取消・打消時の、取引IDによるポイント履歴の取得と巻き戻し
  • 対象店舗の明細による店頭注文の出荷完了反映
  • 支店コードの明細の、支店システムのスマレジ受信APIへの転送と更新件数の合算

本書で扱わないこと

以下は本書では仕様確定せず、実装または別機能の設計を正とする。

  • スマレジ側の取引登録・通知送信そのもの（外部システムの仕様を正とする）
  • 出荷完了反映後の付与ポイントのスマレジ連携（スマレジ連携サービスの設計を正とする）
  • 支店システム側のスマレジ受信API本体（支店システムの設計を正とする）
  • ポイント履歴の閲覧画面（管理画面・フロントのポイント履歴の設計を正とする）

認証・認可

観点内容
認証方式本APIは認証トークンを要求しない。フロントのファイアウォールは匿名アクセスを許可し、本パスにはログイン必須のアクセス制御を設定していない。
連携用ヘッダ支店システムへの転送時に、受信したリクエストのX_contract_id・X_access_tokenヘッダを転送先へ引き継ぐ。これらは本APIの呼び出し元認証ではなく、転送先のスマレジ受信APIに渡す資格情報として用いる。
認証失敗時認証判定を行わないため、未認証でも処理を実行する。
認可呼び出し元はスマレジおよび転送経路。利用者の資格情報による絞り込みは行わない。

連携用ヘッダの値は本書に記載しない。

処理フロー

スマレジ取引通知を取り込む（POST /{_locale}/smaregi/transaction）

  1. リクエストボディのparamsをJSONとして解釈し、data配下のうち取引ヘッダと取引明細を抽出する。
  2. オプションマスタからスマレジ店舗IDを取得し、3桁ゼロ埋めの店舗コードに整形する。
  3. 取引区分を判定する。
  • 取消の場合は、会員ポイントを取消方向に補正し、取引IDに一致するポイント履歴を取得して削除する。
  • 打消レコードの場合は、付与・利用ポイントの正負を反転したうえで取消と同様に補正し、対象履歴を削除する。
  • 通常取引の場合は、会員ポイントを加減算し、付与・利用それぞれのポイント履歴を登録する。続いて取引明細の各行を処理し、商品コードの店舗コードが自店舗と一致する行は対象注文を出荷完了に反映する。一致しない行は支店分として記録する。
  1. 支店分の明細がある場合は、受信ヘッダの連携用ヘッダを引き継ぎ、支店システムのスマレジ受信APIへ明細を転送する。転送結果に更新件数が含まれる場合は合算し、含まれない場合は転送エラーをログに記録する。
  2. 取引ヘッダの更新件数を合算した値を、更新件数として応答に組み立てて返す（HTTP 200）。

業務ルール・計算

項目内容
更新対象リクエストで指定されたID・入力値に対応する業務データを対象にする。対象特定、入力不正、認証・認可の判定順序は処理フローとバリデーションの各節を正とする。
更新方法入力値を対象データへ上書きまたは追加登録する。履歴登録や関連データ更新がある場合は入出力の副作用およびDBカラムの節を正とする。
計算処理本APIでは金額・税・ポイント・在庫数量の再計算や丸めを行わない。ステータスやコメント等の更新は、実装で定義された遷移・存在確認・担当者判定に従う。
応答値成功時は処理結果コードまたは更新後に取得した値を返す。レスポンス値は本API内で独自集計せず、保存結果または取得結果をJSON応答へ整形する。

副作用

会員（プレイヤー）の保有ポイントの更新。ポイント履歴の登録（通常取引）または削除（取消・打消）。対象注文の出荷完了反映（受注ステータス・出荷確定日・コミット日・注文サブの出荷日・担当者の更新、ポイント付与処理）。支店システムのスマレジ受信APIへの明細転送。これらはデータベースへ反映する。

応答はJSON応答整形を経て返す。result配列を持つ連想配列を返し、Content-Typeにapplication/json;charset=UTF-8、キャッシュ抑止とAccess-Control-Allow-Origin: *を明示する。

項目内容

データ整合性

観点内容
更新の有無本APIは参照だけでなく、会員ポイント・ポイント履歴・受注を更新する。
ポイントと履歴通常取引では会員ポイントの加減算とポイント履歴の登録を同一処理内で行う。取消・打消では取引IDに一致するポイント履歴を取得して削除し、会員ポイントを逆方向へ補正する。会員または対象履歴が無い場合は更新しない。
出荷完了反映自店舗の明細に対し、注文サブを商品コードで特定して出荷完了へ反映する。対象注文が無い場合は反映しない。
支店転送自店舗以外の明細は支店システムへ転送し、結果件数を更新件数に合算する。転送に件数が含まれない場合はログに記録し、件数は合算しない。

排他制御・トランザクション

本APIは会員ポイント・ポイント履歴・受注を更新する。各処理の末尾で永続化を確定する。明示的な悲観ロック・楽観ロックの取得は行わない。同一取引の重複受信時の整合は、取消・打消が取引IDを基準にポイント履歴を特定して巻き戻す前提に依存する。
