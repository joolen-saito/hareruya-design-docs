詳細設計書

M11-01 メンバー管理一覧 / メンバー管理一覧（システム情報設定／設定）

概要

管理画面の「システム情報設定」配下において、管理ログイン用の管理者アカウント（メンバー）を一覧表示し、各行から登録・編集・削除・表示順の入れ替えへ誘導する一覧機能である。ページタイトルブロックは「システム設定」、サブタイトルおよび一覧ボックス見出しは「メンバー管理」として表示される。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。対象は pf-eccube3 のメンバー一覧（index）と、一覧から実行する削除・上へ・下への各操作とする。一覧（index）はコア実装のままで、HareruyaEcプラグインによる一覧の上書きはない。登録・編集フォームの詳細は「メンバー管理」（M11-02）を正とする。

挙動・画面・処理フローの参照ソースツリーは pf-eccube3 を正とする。ただしDB関連の記述（テーブル名・列名・型・制約・関連・永続化先、DBカラム節、データ整合性のDB部分、副作用のDB更新）は、リニューアル後システムである ec-cube-enterprise の実装を正とする。両者でスキーマが食い違う点は「リニューアル移行時の扱い」に明記する。URLエンドポイントは管理画面コントローラのルート定義（AdminControllerProvider）で確認した利用者視点の入口として記載する。管理画面プレフィックスは ADMIN_ROUTE（path.yml の admin_route）で決まる。本書ではコントローラクラス名・ルートbind名は本文に置かない。

本書で扱うこと

  • メンバー一覧の表示項目、並び順、件数・ページングの有無
  • 一覧から新規登録・編集・削除・上へ・下へへ向かう利用者視点の導線と結果メッセージ
  • 削除時の表示順繰り下げ、上へ・下へによる隣接行との表示順入れ替え
  • ログイン中メンバー自身の行に対する削除リンクの非表示、先頭・末尾行での上へ・下へリンクの非表示
  • 一覧初期化イベントおよび削除前後イベントによる拡張点（名称はコード内の EccubeEvents 定数を参照）

本書で扱わないこと

以下は本書では仕様確定せず、実装または別機能の設計を正とする。

  • メンバーの登録・編集フォームの項目、検証、パスワード・ソルトの扱い、保存処理（「メンバー管理」M11-02 を正とする）
  • 管理画面へのログイン、セッション、CSRF の名称形式、Remember Me、パスワードポリシー全般の詳細
  • 権限マスタ（mtb_authority）の各行が拒否するパスの対応関係（「権限管理」画面および権限制御の実装を正とする）
  • 管理画面 IP 制限やファイアウォールの判定順序の詳細
  • ログイン認証時に参照する「稼働」マスタ値と非稼働メンバーの扱いの網羅（ログイン処理の実装を正とする）
  • 本機能以外が dtb_member を更新する経路（バッチ、他画面、直接SQL）の一覧

リニューアル移行時の扱い

  • 基本設計の機能仕様（同シート上部）に記載される、所属・権限による絞り込み・ソート、および表示リストへの項目追加（デフォルト検索表示店舗、編集可能店舗、自動ログアウト、二段階認証など）は、リニューアル後の追加仕様である。現行の pf-eccube3 のコア一覧には実装されていない。pf-eccube3 の一覧は名前・所属・権限・稼働の4列と操作メニューのみで構成し、検索フォーム・絞り込みセレクト・ソートリンク・追加列は持たない。
  • DB関連の記述は ec-cube-enterprise を正とする。挙動説明・画面構成は現行（pf-eccube3）の確認値だが、DBスキーマは移行先（ec-cube-enterprise）に合わせる。現行と移行先の主な差は次のとおり。
  • 表示順キー: 現行は dtb_member.rank、移行先は dtb_member.sort_no。いずれも降順で並べる。本書のDB記述は sort_no を正とする。
  • 削除方式: 現行は dtb_member.del_flg を立てる論理削除、移行先は del_flg 列を持たず物理削除である。本書のDB記述は物理削除（del_flg なし）を正とする。
  • 所属: 現行は dtb_member.department のテキスト、移行先は dtb_member.department_id（mtb_department 参照）のマスタFKである。一覧の「所属」列は移行先ではマスタ名称を表示する。
  • メールアドレス・所属店舗・デフォルト検索表示店舗・二段階認証・自動ログアウトは、移行先では dtb_member 本体の列（email、base_info_id、default_search_base_info_id、two_factor_auth_enabled、is_auto_logout）として存在する。編集可能店舗は移行先の結合表 dtb_member_base_info に保持する。現行ではこれらの列・表は存在しない（所属店舗・スマレジは現行プラグインの補助表 dtb_member_sub で代替）。これらは一覧の追加列・絞り込みの裏付けとなる。
  • 移行時は、本書の現行挙動・画面と機能仕様（マトリックスでない一覧の追加列・絞り込み）、および現行↔移行先のスキーマ差分を移行設計で吸収する。

フロント挙動

観点内容
表示要素一覧テーブルの列は、名前、所属、権限（マスタ名称）、稼働（マスタ名称）、操作メニュー。各行の操作メニューはドロップダウンで、編集・削除・上へ・下へを表示する。画面下部に新規登録ボタンを置く。検索フォーム・絞り込みセレクト・ソートリンクは持たない。
表示条件付き要素削除は、行のメンバーがログイン中メンバー自身の場合はリンクにせず文言のみとし、それ以外はトークン付きの削除リンクとする。上へは先頭行で出さず、下へは末尾行で出さない。
JS 挙動一覧テンプレートに changeAction 関数が定義されているが、当該テンプレート内で呼び出しはなく、本機能の主操作には使われない確認値である。削除・上へ・下へは共通スクリプトにより、data-method とトークン用属性を付与した疑似フォーム送信で DELETE または PUT を行う。削除リンクは共通スクリプトの既定の確認ダイアログに従い、上へ・下へは data-confirm="false" を付けて確認ダイアログを出さない。
CSS・レイアウト管理画面標準の Bootstrap 系テーブル・ドロップダウンメニューを用いる。
モーダル・ポップアップBootstrap モーダルは用いず、削除確認はブラウザの確認ダイアログに依存する。
入力項目一覧画面は検索・絞り込みの入力項目を持たない。登録・編集フォームの入力項目は本機能では扱わない。

処理フロー

一覧を開く（GET）

  1. 管理画面の認証・認可・ネットワーク制限などの前置処理を通過する（詳細は管理画面基盤の実装を正とする）。
  2. dtb_member を sort_no 降順のみの条件で取得する。削除済みの行は取得対象から除外する（移行先は物理削除のため対象行自体が存在しない。現行 pf-eccube3 は del_flg フィルタで除外）。稼働状態による絞り込みは行わない。
  3. 空のフォームビルダを生成し、一覧向け初期化イベントをディスパッチする。プラグイン等がビルダや一覧に干渉し得る。コアの一覧テンプレートはフォーム行を描画しないため、ビルダへ項目を足しても画面に出ない限り利用者視界には効かない。
  4. テンプレートにフォームビュー（コアでは実質空に近い）とメンバー配列を渡して描画する。件数集計・ページング処理は行わない。

上へ（PUT）

  1. トークンを検証する。無効ならアクセス拒否となる。
  2. 対象メンバーを取得する。無ければ 404 とする。
  3. PUT のとき、上へ処理を呼ぶ。自身の sort_no より 1 大きい行と sort_no を交換する。隣が存在しないなどで処理できない場合は失敗とする。
  4. 成否に応じて成功またはエラーメッセージを積み、一覧へリダイレクトする。

下へ（PUT）

上へと同様に、自身の sort_no より 1 小さい行と sort_no を交換する。先頭・末尾などで隣接行が無い場合は失敗とし、エラーメッセージを積む。

削除（DELETE）

  1. トークンを検証する。無効ならアクセス拒否となる。
  2. 対象メンバーを取得する。見つからない場合は削除警告メッセージを積み、一覧へリダイレクトする（404 にはしない）。
  3. 見つかった場合は削除前イベントをディスパッチし、削除処理を呼ぶ。削除対象より大きい sort_no の全行を 1 つ繰り下げたうえで、対象メンバーを物理削除する（移行先は del_flg を持たない。現行 pf-eccube3 は del_flg を立て rank を 0 にする論理削除）。
  4. 成功時は削除完了イベントをディスパッチし、成功メッセージを積む。失敗時はエラーメッセージを積む。
  5. 一覧へリダイレクトする。

集計条件

指標集計の要点
一覧の並びdtb_member を sort_no 降順で並べ替える。件数表示やページングは行わない。
一覧の対象削除されていないメンバーを対象とする（移行先は物理削除のため削除済み行は存在しない）。稼働・非稼働の区別による絞り込みはしない。
削除時の繰り下げ削除対象より大きい sort_no の全行を 1 つ繰り下げる。
上へ・下への入れ替え対象行の sort_no と、隣接する sort_no（上へは +1、下へは -1）の行とで sort_no を交換する。

管理画面システム情報設定配下のログイン履歴一覧で、管理画面ログインの試行記録を検索・閲覧する機能。

概要

ログイン履歴は、管理画面へのログイン試行で記録された行を、ログインID・IPアドレス・ログイン試行日時・成功失敗区分とともに一覧で閲覧し、期間や成功失敗などの条件で絞り込むための参照機能である。記録の発生源は認証処理側であり、本機能はその記録を読み取って表示する。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。 既存実装のふるまい、参照するデータ、検索条件、表示列、副作用を確認し、仕様の確からしさを把握することを目的とする。

本機能のカスタマイズ区分は標準であり、挙動・DB関連ともにリニューアル後（ec-cube-enterprise）の標準実装を正とする。

対象はブラウザ経由の管理画面のログイン履歴一覧である。履歴を生成する認証成功・失敗の判定そのものは別機能とし、本書では確認できる範囲で記録の発生源を整理する。

管理画面プレフィックスは環境変数ECCUBE_ADMIN_ROUTEをeccube.yamlのeccube_admin_routeへ束ねた値で決まる。本書では%eccube_admin_route%で示し、ホスト名やクエリを含む具体URLは書かない。Symfonyのルートname、Controllerの構成は本文の主題としない。

処理フロー

一覧表示

  1. 利用者がログイン履歴一覧を開く。
  2. 表示件数はセッションキーeccube.admin.login_history.search.page_countから取得し、未保存ならアプリ既定の表示件数を用いる。リクエストに有効なpage_countがあり、かつ表示件数マスタに一致する場合はその値を採用し、同セッションキーへ保存する。
  3. ページ番号付きURLまたはresumeでの再表示では、保存済みの検索条件eccube.admin.login_history.searchと保存済みページ番号を読み出して絞り込む。
  4. ページ番号も再表示指定もない初回表示では、検索条件を空にしてセッションへ保存し、1ページ目を全件対象で表示する。
  5. 絞り込み結果を作成日時の降順、同一日時内はID降順で並べ、ページ送りして一覧表に表示する。

検索実行

  1. 利用者が検索条件を入力して検索ボタンを押す。
  2. 入力値の検証に成功した場合、検索条件をセッションeccube.admin.login_history.searchへ保存し、ページ番号を1へ初期化してセッションへ保存する。
  3. 保存した条件で絞り込み、1ページ目を表示する。検索結果件数を画面に表示する。
  4. 入力値の検証に失敗した場合は一覧を出さず、詳細検索ブロックを開いた状態で再描画し、条件の見直しを促す表示にする。この場合は検索条件をセッションへ保存しない。

ページ送り・表示件数変更

  1. ページャのリンクまたは表示件数プルダウンで遷移する。
  2. ページ番号はURLの値をセッションeccube.admin.login_history.search.page_noへ保存する。表示件数は前述の判定でセッションへ保存する。
  3. 保存済みの検索条件のまま、指定ページ・指定件数で一覧を表示する。

処理フロー

マスタ選択フォーム組み立て（マスタ管理画面の初期表示および再入）

  1. マスタ選択用フォームビルダを生成する。
  2. 拡張イベントを dispatch し、リスナーがビルダを変更し得る。
  3. マスタ選択が POST され検証に成功した場合、完了イベントを dispatch する。リスナーがレスポンスを設定した場合はそれを返し終了する。
  4. リスナーがレスポンスを返さなければ、一覧表示用の入口へリダイレクトする。リダイレクト先のパス引数には、3の直前に送信されたマスタキーが載る。
  5. 入口にマスタキーのパス引数があり、かつマスタ選択フォーム上そのキーが有効なら、当該エンティティのリポジトリで sort_no 昇順の findBy を実行する。
  6. 各行について、配列データに主キー・名称を格納する。主キーは行キーにも用いる。
  7. 配列末尾に、ID・名称が空の1行を追加する。
  8. メタデータ解釈に失敗した場合（マッピング例外）は、6のデータ読込を行わず、編集テーブル用データを空に近い状態にする。
  9. 編集用フォームビルダを、7または8で得たデータを初期値として生成する。
  10. 別の拡張イベントで編集フォームビルダを改変し得る。
  11. 2つのフォームのビューを返し、テンプレートを描画する。

保存（編集テーブル送信）

  1. 編集用フォームのみリクエストから組み立て、拡張イベントで初期化し得る。
  2. POST なら handleRequest 後、検証する。
  3. 検証失敗なら、マスタ選択フォームを別イベントで初期化し、リクエストボディと編集フォーム内 hidden のマスタ名を merge した値でマスタ選択フォームを submit し、2つのフォームビューを返す（同一画面でエラー再表示）。
  4. 検証成功なら、隠しフィールドのマスタキーからクラス名を復元する。
  5. 送信データの各行について、非 null の ID と非 null の名称が両方ある行は、主キーで既存を検索し、無ければ新規インスタンスを生成する。setId・setName のあと、ループの 0 始まり連番で setSortNo する。persist する。
  6. ID と名称が両方そろわない行のうち、行キーが「他行で使われている ID 一覧」に含まれないものは削除候補とし、行キーを主キーとして find した結果があれば remove する。
  7. flush を試みる。成功時は保存完了イベントを dispatch し、成功フラッシュに admin.common.save_complete を積む。失敗時（コメント上は外部キー制約など）は例外を握り潰し、エラーフラッシュに admin.common.save_error を積む。
  8. 選択中マスタの一覧表示入口へリダイレクトする。

編集入口への GET のみ

  1. 編集用フォームを空のデフォルトで生成し、初期化イベントを dispatch する。
  2. マスタ選択フォームを生成し、別イベントで初期化したあと、リクエストの POST パラメータ全体と、編集フォーム hidden のマスタ名を merge して submit する。GET では POST パラメータは空に近い。
  3. 2つのフォームビューを返す。編集データが空ならテンプレートは編集テーブルを出さない。

システム情報画面の表示

  1. 利用者がシステム情報の画面表示を要求する。
  2. 認証・認可により許可された場合、コントローラは情報行の配列を組み立てる。先頭から順に、EC-CUBEバージョン定数、php_uname の結果、データベース接続経由のバージョン文字列、SERVER_SOFTWARE サーバ変数、PHPバージョン文字列にカンマ区切りで拡張名一覧を括弧付きで連結した値、User-Agentヘッダ値を並べる。各見出しは翻訳キー由来のラベルとする。
  3. テンプレートへ情報配列と、環境由来のPHP情報有効フラグを渡し、HTMLを応答する。要求クエリの有無やキーは上記の組み立てに使われない。

PHP情報（iframe内）

  1. eccube_phpinfo_enabled が偽の場合、PHP情報カード自体を出力しない。真の場合のみiframeのsrcにphpinfo用の別GETを設定する。
  2. そのGETが許可された場合、標準のphpinfo出力をバッファに取り、そのHTMLをそのまま応答ボディとする。管理画面の共通フレームTwigは通さない。

権限拒否時

  1. ログイン中メンバーの権限に紐付く各行の拒否URLが、現在の要求パス（パス情報のみ、クエリは含めない）と、設定された管理ルート接頭辞付きで先頭一致するかを検査する。
  2. 一致する拒否が一つでもあればアクセス拒否となり、画面本文の描画に至る前に403応答となる。システム情報の本体と、より長いパスを持つphpinfo側のGETは同一の拒否パターン先頭により両方拒否され得る。

集計・判定・計算

本機能は台帳件数の集計や業務判定を行わない。画面に出すのは実行時に取得した文字列の表示のみである。

M11-02 メンバー管理 / メンバー管理（システム情報設定／設定）

概要

管理画面の「システム情報設定」配下において、管理ログイン用の管理者アカウント（メンバー）を新規登録・編集する機能である。ページタイトルブロックは「システム設定」、サブタイトルは「メンバー管理」、登録・編集ボックスの見出しは「メンバー登録・編集」として表示される。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。対象は pf-eccube3 のメンバー登録・編集（new／edit）とその保存処理とする。一覧表示・削除・表示順の入れ替えは「メンバー管理一覧」（M11-01）を正とする。

挙動・画面・処理フローの参照ソースツリーは pf-eccube3 を正とする。メンバー登録・編集は現行では HareruyaEcプラグインがコア実装を上書きしており、保存時に補助テーブル dtb_member_sub（所属店舗・スマレジ用アカウント）を併せて更新する。ただしDB関連の記述（テーブル名・列名・型・制約・関連・永続化先、入力項目の保存先、DBカラム節、データ整合性のDB部分、副作用のDB更新）は、リニューアル後システムである ec-cube-enterprise の実装を正とする。ec-cube-enterprise では所属店舗・スマレジ用アカウント・メールアドレス等は dtb_member 本体の列、編集可能店舗は結合表 dtb_member_base_info に保持し、現行プラグインの補助表 dtb_member_sub は持たない。現行と移行先のスキーマ差は「リニューアル移行時の扱い」に明記する。URLエンドポイントは管理画面コントローラのルート定義（AdminControllerProvider）で確認した利用者視点の入口として記載する。管理画面プレフィックスは ADMIN_ROUTE（path.yml の admin_route）で決まる。

  • 編集時のパスワード・ソルトの扱い（未変更時の既存ハッシュ維持、変更時のソルト生成と再ハッシュ）
  • 所属店舗とスマレジ用アカウントの保存（DB保存先は ec-cube-enterprise を正とし dtb_member.base_info_id / dtb_member.smaregi_member_flg。現行は HareruyaEcプラグインが補助表 dtb_member_sub の shop_id / smaregi_member_flg に保存）
  • スマレジ用アカウントの一意制約（自身以外に有効な行が存在する場合のエラー）
  • 保存成功・失敗時の結果メッセージと遷移先（プラグインは編集画面へ戻す）
  • 編集画面表示時のセキュリティトークン上のユーザー復元

リニューアル移行時の扱い

  • 画面挙動・処理フローは現行（pf-eccube3）の確認値、DBスキーマは移行先（ec-cube-enterprise）を正とする。実装済み・未実装を取り違えず、現行と移行先を対比で示す。
  • 永続化モデルの差: 現行は所属店舗・スマレジ用アカウントを補助表 dtb_member_sub（shop_id / smaregi_member_flg、メンバーと1対1）へ手動保存する。移行先は補助表を持たず、これらを dtb_member 本体の列（base_info_id / smaregi_member_flg）に保存する。本書のDB記述は移行先（dtb_member 本体）を正とする。
  • 列対応（現行 → 移行先）:
  • 所属: dtb_member.department（テキスト） → dtb_member.department_id（mtb_department 参照のマスタFK）
  • 所属店舗: dtb_member_sub.shop_id（mtb_shop 参照） → dtb_member.base_info_id（dtb_base_info 参照）
  • スマレジ用アカウント: dtb_member_sub.smaregi_member_flg → dtb_member.smaregi_member_flg
  • 表示順: dtb_member.rank → dtb_member.sort_no（一覧 M11-01 と共通）
  • 主キー: dtb_member.member_id → dtb_member.id
  • 移行先のみに存在する列・表: メールアドレス（dtb_member.email、非NULL）、デフォルト検索表示店舗（dtb_member.default_search_base_info_id）、二段階認証（dtb_member.two_factor_auth_enabled / two_factor_auth_key）、自動ログアウト設定（dtb_member.is_auto_logout）、編集可能店舗（結合表 dtb_member_base_info の member_id / base_info_id）。現行画面にはこれらの入力項目がなく、現行 dtb_member にも相当列がない。基本設計の機能仕様の追加項目はこれらに対応する。
  • 所属店舗のマスタ差: 現行は専用マスタ mtb_shop、移行先は店舗（拠点）マスタ dtb_base_info。移行時はマスタ対応と、単一選択（所属店舗）と複数選択（編集可能店舗）の保持先の差を移行設計で吸収する。
  • 保存成功時の遷移先は、コアでは一覧、現行の HareruyaEcプラグイン適用後は編集画面である。現行挙動は編集画面への遷移を正とする。

処理フロー

新規登録・編集を開く（GET）

  1. 管理画面の認証・認可・ネットワーク制限などの前置処理を通過する（詳細は管理画面基盤の実装を正とする）。
  2. 編集で ID 指定がある場合、該当メンバーと補助メンバー情報を取得する。どちらも無ければ 404 とする。あれば退避用に暗号化済みパスワードを保持し、エンティティのパスワードにプレースホルダ値を代入してフォーム表示用にする。新規の場合は空のメンバーと空の補助メンバー情報を生成する。
  3. ログイン中メンバーをクローンし、永続化コンテキストから切り離す（セッション上のユーザー実体と編集対象の混在を避けるための確認値）。
  4. 管理者メンバー用フォームをメンバーに紐づけて生成し、編集向け初期化イベントをディスパッチする。フォームには標準項目に加え、所属店舗とスマレジ用アカウントをプラグイン拡張で表示する。
  5. フォームを描画する前に、セキュリティトークンのユーザーへクローンしたログイン中メンバーを戻す。
  6. テンプレートにフォームビュー、メンバー、補助メンバー情報を渡して描画する。所属店舗・スマレジ用アカウントの初期表示は補助メンバー情報の現行値を用いる。

登録ボタン押下（POST、検証成功）

  1. フォームをリクエストで処理する。
  2. 検証成功時、編集かつ入力パスワードがプレースホルダのままなら退避していた暗号化パスワードを戻す。それ以外はソルト未設定ならランダムソルト（5文字）を生成し、エンコーダでパスワードをハッシュ化してセットする。
  3. メンバーを保存する。
  4. 保存に成功した場合、フォームの所属店舗が選択されていれば所属店舗を設定し、未選択なら空にする（現行は補助メンバー情報の shop_id へ保存。移行先は dtb_member.base_info_id を正とする）。
  5. スマレジ用アカウントが有効で、かつ自身以外に有効なスマレジ用アカウントが存在する場合は、エラーメッセージを積み、編集画面へ遷移する（スマレジ用フラグは反映しない）。
  6. 競合がなければ、スマレジ用フラグを設定して保存する（現行は補助メンバー情報の smaregi_member_flg、移行先は dtb_member.smaregi_member_flg を正とする）。
  7. 編集完了イベントをディスパッチし、成功メッセージを積み、登録時は作成したメンバーの編集画面へ、編集時は同じ編集画面へ遷移する。
  8. メンバー保存が失敗した場合はエラーメッセージを積み、同一画面を再表示する。

登録ボタン押下（POST、検証失敗）

  1. フォームをリクエストで処理する。
  2. 同一の登録・編集テンプレートを再表示し、項目エラーを表示する。成功メッセージは積まない。
  3. 描画前にセキュリティトークンのユーザーをクローンしたログイン中メンバーへ戻す。

M11-03 権限管理 / 権限管理（システム設定／拒否URL）

概要

管理画面の「システム設定」配下にある「権限管理」は、権限マスタ（管理者の種類）ごとに、管理画面のパス接頭辞を指定してアクセスを拒否するルールを登録する機能である。画面では「権限」と「拒否URL」を行単位で入力し、「登録」で一括保存する。保存内容はデータベースに保持され、同一権限の利用者が該当パスへ遷移しようとしたときにセキュリティ上拒否される。また、左ナビゲーションでは拒否パスに対応するメニュー項目を出さないようにする。

本機能のカスタマイズ区分はカスタマイズであり、現行挙動は pf-eccube3 の実装を、DB関連は ec-cube-enterprise の実装を正とする。

「システム情報」画面（EC-CUBE バージョン・PHP 情報の閲覧）とは別の画面である。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。既存実装のふるまい、参照するデータ、判定境界、副作用、外部プラグイン差し込み点を確認し、仕様の確からしさを把握することを目的とする。

対象はブラウザ経由の管理画面に限定する。

本書では Symfony のルート名、URL パス、コントローラクラス名は扱わない。

本書で扱うこと

  • 権限管理画面の表示内容（表形式、行追加・行削除、説明文、送信ボタン）
  • フォーム検証（権限と拒否URLの片方だけ入力された場合のエラー、両方そろった場合の保存）
  • 保存処理における全件差し替え（既存行の一括削除後、送信内容の再登録）
  • 保存完了メッセージとリダイレクト後の再表示
  • 拒否URLの照合方式（リクエストのパス情報と、管理ルートおよび拒否URLを結合した前方一致・正規表現）
  • 権限用アクセス判定（Voter）によるアクセス拒否と、Twig グローバル AuthorityRoles によるナビ項目の非表示
  • 表示初期化時および保存完了時のイベントによるプラグイン拡張点
  • 永続化先テーブルとマッピング上必須の列の関係

本書で扱わないこと

以下は本書では仕様確定せず、実装または別機能の設計を正とする。

  • 管理画面ログイン、セッション、CSRF、パスワードの詳細
  • 管理者（Member）の作成・編集や、権限マスタ（mtb_authority）自体の編集方法
  • 管理画面 IP 許可リスト（admin_allow_host）の設定形式

  • 基本設計の機能仕様にある権限マトリックスUI等のリニューアル後仕様。pf-eccube3 には未実装であり、差分は「リニューアル移行時の扱い」を参照する

リニューアル移行時の扱い

  • 基本設計の機能仕様（同シート上部）は、権限管理を権限マトリックスのUIで行うリニューアル後仕様として記述する。pf-eccube3 の現行実装は、権限と拒否URLを行単位で入力する一覧フォーム（全件差し替え保存）であり、マトリックスUIは未実装である。実装済みとして書かず、現行の確認値と移行後仕様を対比で示す。
  • 現行（pf-eccube3）の権限制御は、権限ごとに拒否URL（パス接頭辞）を登録し、前方一致でアクセスを拒否する仕組みである。アクセス可否は「拒否ルールに一致するか」の1段階判定であり、可・不可の明示的な2値や「閲覧」列のような権限レベルの概念は持たない。
  • 基本設計が描く次の項目は、リニューアル後（ec-cube-enterprise系）で追加・変更される想定であり、本書の対象実装にはない。
  • 機能（URL）×権限のマトリックス表示と、セル内チェックボックスでの登録・解除
  • アクセス可／アクセス不可の2段階、および閲覧列の追加
  • 上位権限がアクセス可のとき下位権限も自動でアクセス可とし、下位権限を編集不可にする継承
  • 新規追加機能・未設定項目を既定でアクセス不可とする扱い
  • 権限の複製
  • マスターデータ管理によるURLとページ名のマッピング管理、権限レベルの設定
  • 現行はURLとページ名のマッピングをマスタで持たず、拒否URLを直接文字列で入力する。移行時はマスタ化とマトリックス化、判定モデル（拒否ベースから許可・拒否の2値ベースへ）の差を移行設計で吸収する。
  • DB関連の記述は ec-cube-enterprise を正とする。dtb_authority_role のスキーマ差は、主キー列名（現行 authority_role_id → 移行先 id）、deny_url の型（現行 text → 移行先 VARCHAR(4000)）、creator_id の NULL 可否（現行 非NULL → 移行先 NULL 可）、移行先のみの is_modifiable 列である。詳細はDBカラム節を参照する。

処理フロー

画面を開く（GET）

  1. 権限ロールを権限ID昇順、拒否URL昇順で一覧取得する。
  2. フォームビルダに、取得したエンティティ配列を data とした AuthorityRoles コレクションを定義する。
  3. 表示初期化イベントを発火する。プラグイン等がビルダや一覧を変更し得る。
  4. コレクションが0件のとき、空の子フォームを1つ追加する。
  5. POST 以外のため、テンプレートを描画して返す。

「登録」押下（POST、検証成功）

  1. リクエストをフォームに取り込む。検証に成功した場合にのみ保存処理へ進む。
  2. 画面表示時点で取得済みの既存権限ロール行をすべて EntityManager から削除する。続けて送信中の各行について、権限と拒否URLがともに非空ならその行を永続化対象として persist する。権限または拒否URLが欠ける行は、既にIDがある既存行なら削除を試み、新規行なら保持しない。処理のあと flush する。
  3. 保存完了イベントを発火する。引数の AuthorityRoles は当リクエスト開始時に読み込んだ一覧参照であり、保存後の最新一覧ではない点に注意が要る。
  4. 管理者向け成功メッセージ「権限設定を保存しました。」を積む。
  5. 権限管理画面自身へリダイレクトする（GET で再表示）。

「登録」押下（POST、検証失敗）

  1. 同一テンプレートを再描画する。フィールドエラーを表示する。データベースは更新しない。

アクセス拒否の判定（管理画面の他画面へ遷移したとき）

  1. 認可処理の一環として投票者が動く。利用者が Member でない場合は拒否ルールを適用せず許可方向で返す。
  2. Member の場合、当該 Member の権限に紐づく権限ロールをすべて取得する。
  3. 各拒否URLについて、現在リクエストのパス情報（必要に応じてデコード済み）が、「/ ＋ 管理ルート ＋ 登録拒否URL」をエスケープして得たパターンの先頭一致になるかを正規表現で試す。最初のパターン化で例外が出た場合は preg_quote による別パターンで再試行する。いずれかに一致すればアクセス拒否を返す。
  4. いずれにも一致しなければ許可方向で返す。

左ナビの抑制（管理画面の controller イベント）

  1. 管理画面かつログイン済み Member のとき、当該 Member の権限に紐づく権限ロールを取得する。
  2. 各行について、リクエストbaseUrl ＋ / ＋ 管理ルート ＋ 拒否URL を連結した文字列を配列に入れ、Twig グローバル AuthorityRoles として渡す。
  3. ナビテンプレートは、第1階・第2階の項目について、この配列に「baseUrl／管理ルート／ナビid（階層連結）」形式が含まれるとき該当ブロックを出さない。第3階は path(ルート名) 生成URLが配列に含まれるとき項目を出さない（実装はテンプレートの条件分岐）。

概要

管理画面の「システム設定」配下にある「権限管理」は、権限マスタ（管理者の種類）ごとに、管理画面のパス接頭辞を指定してアクセスを拒否するルールを登録する機能である。画面では「権限」と「拒否URL」を行単位で入力し、「登録」で一括保存する。保存内容はデータベースに保持され、同一権限の利用者が該当パスへ遷移しようとしたときにセキュリティ上拒否される。また、左ナビゲーションでは拒否パスに対応するメニュー項目を出さないようにする。

本機能のカスタマイズ区分はカスタマイズであり、現行挙動は pf-eccube3 の実装を、DB関連は ec-cube-enterprise の実装を正とする。

「システム情報」画面（EC-CUBE バージョン・PHP 情報の閲覧）とは別の画面である。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。既存実装のふるまい、参照するデータ、判定境界、副作用、外部プラグイン差し込み点を確認し、仕様の確からしさを把握することを目的とする。

対象はブラウザ経由の管理画面に限定する。

本書では Symfony のルート名、URL パス、コントローラクラス名は扱わない。

本書で扱うこと

  • 権限管理画面の表示内容（表形式、行追加・行削除、説明文、送信ボタン）
  • フォーム検証（権限と拒否URLの片方だけ入力された場合のエラー、両方そろった場合の保存）
  • 保存処理における全件差し替え（既存行の一括削除後、送信内容の再登録）
  • 保存完了メッセージとリダイレクト後の再表示

リニューアル移行時の扱い

  • 基本設計の機能仕様（同シート上部）は、権限管理を権限マトリックスのUIで行うリニューアル後仕様として記述する。pf-eccube3 の現行実装は、権限と拒否URLを行単位で入力する一覧フォーム（全件差し替え保存）であり、マトリックスUIは未実装である。実装済みとして書かず、現行の確認値と移行後仕様を対比で示す。
  • 現行（pf-eccube3）の権限制御は、権限ごとに拒否URL（パス接頭辞）を登録し、前方一致でアクセスを拒否する仕組みである。アクセス可否は「拒否ルールに一致するか」の1段階判定であり、可・不可の明示的な2値や「閲覧」列のような権限レベルの概念は持たない。
  • 基本設計が描く次の項目は、リニューアル後（ec-cube-enterprise系）で追加・変更される想定であり、本書の対象実装にはない。
  • 機能（URL）×権限のマトリックス表示と、セル内チェックボックスでの登録・解除
  • アクセス可／アクセス不可の2段階、および閲覧列の追加
  • 上位権限がアクセス可のとき下位権限も自動でアクセス可とし、下位権限を編集不可にする継承
  • 新規追加機能・未設定項目を既定でアクセス不可とする扱い
  • 権限の複製
  • マスターデータ管理によるURLとページ名のマッピング管理、権限レベルの設定
  • 現行はURLとページ名のマッピングをマスタで持たず、拒否URLを直接文字列で入力する。移行時はマスタ化とマトリックス化、判定モデル（拒否ベースから許可・拒否の2値ベースへ）の差を移行設計で吸収する。
  • DB関連の記述は ec-cube-enterprise を正とする。dtb_authority_role のスキーマ差は、主キー列名（現行 authority_role_id → 移行先 id）、deny_url の型（現行 text → 移行先 VARCHAR(4000)）、creator_id の NULL 可否（現行 非NULL → 移行先 NULL 可）、移行先のみの is_modifiable 列である。詳細はDBカラム節を参照する。

観点内容
表示要素見出し「権限設定」。説明文として、管理ベースURL以降を拒否URLに含めること、拒否URL以降が前方一致でアクセス拒否されること、/setting のように先頭に / を付ける例を表示する。表の列は「権限」「拒否URL」「削除ボタン」。右カラムに「登録」button。
入力項目権限は mtb_authority を参照する単一選択のセレクト。未選択用の空選択肢がある。拒否URLは一行テキスト。
JS 挙動「行追加」はテーブルに保持したプロトタイプ文字列で __name__ をインデックスに置換し、最終trの後ろへ挿入する。「削除」は行trを除去する。削除後に拒否URL入力欄が0個になったら、tbodyへ同プロトタイプから1行入れる。
CSS・レイアウト横並びフォーム用のテーマを適用。表は striped・condensed・with-border。
モーダル・ポップアップ本機能ではモーダル、確認ダイアログ、トースト専用処理は使わない。
拡張フィールドフォーム直下の子のうち、テンプレートの条件に合う追加項目を「extra-form」領域に描画する構造がある（プラグイン由来フィールド用）。

処理フロー

画面を開く（GET）

  1. 権限ロールを権限ID昇順、拒否URL昇順で一覧取得する。
  2. フォームビルダに、取得したエンティティ配列を data とした AuthorityRoles コレクションを定義する。
  3. 表示初期化イベントを発火する。プラグイン等がビルダや一覧を変更し得る。
  4. コレクションが0件のとき、空の子フォームを1つ追加する。
  5. POST 以外のため、テンプレートを描画して返す。

「登録」押下（POST、検証成功）

  1. リクエストをフォームに取り込む。検証に成功した場合にのみ保存処理へ進む。
  2. 画面表示時点で取得済みの既存権限ロール行をすべて EntityManager から削除する。続けて送信中の各行について、権限と拒否URLがともに非空ならその行を永続化対象として persist する。権限または拒否URLが欠ける行は、既にIDがある既存行なら削除を試み、新規行なら保持しない。処理のあと flush する。
  3. 保存完了イベントを発火する。引数の AuthorityRoles は当リクエスト開始時に読み込んだ一覧参照であり、保存後の最新一覧ではない点に注意が要る。
  4. 管理者向け成功メッセージ「権限設定を保存しました。」を積む。
  5. 権限管理画面自身へリダイレクトする（GET で再表示）。

「登録」押下（POST、検証失敗）

  1. 同一テンプレートを再描画する。フィールドエラーを表示する。データベースは更新しない。

アクセス拒否の判定（管理画面の他画面へ遷移したとき）

  1. 認可処理の一環として投票者が動く。利用者が Member でない場合は拒否ルールを適用せず許可方向で返す。
  2. Member の場合、当該 Member の権限に紐づく権限ロールをすべて取得する。
  3. 各拒否URLについて、現在リクエストのパス情報（必要に応じてデコード済み）が、「/ ＋ 管理ルート ＋ 登録拒否URL」をエスケープして得たパターンの先頭一致になるかを正規表現で試す。最初のパターン化で例外が出た場合は preg_quote による別パターンで再試行する。いずれかに一致すればアクセス拒否を返す。
  4. いずれにも一致しなければ許可方向で返す。

左ナビの抑制（管理画面の controller イベント）

  1. 管理画面かつログイン済み Member のとき、当該 Member の権限に紐づく権限ロールを取得する。
  2. 各行について、リクエストbaseUrl ＋ / ＋ 管理ルート ＋ 拒否URL を連結した文字列を配列に入れ、Twig グローバル AuthorityRoles として渡す。
  3. ナビテンプレートは、第1階・第2階の項目について、この配列に「baseUrl／管理ルート／ナビid（階層連結）」形式が含まれるとき該当ブロックを出さない。第3階は path(ルート名) 生成URLが配列に含まれるとき項目を出さない（実装はテンプレートの条件分岐）。

集計・判定・計算

本機能は件数集計や金額計算を行わない。拒否との照合はパターン前方一致（実装は正規表現の先頭アンカー）による。

業務ルール・計算

本機能では金額・税率などの業務計算を行わない。

エッジケース

ケース扱い

データ整合性

観点内容
一覧と保存結果保存成功後は再GETで一覧が読み直される。保存中に他セッションが同テーブルを変えた場合の直列化はアプリケーションレベルでは保証しない。
ナビ非表示と実際の拒否グローバルは「フルURL文字列」、ナビ側の比較は階層id連結や path() 生成URLとの包含判定であり、投票者のパス前方一致とは文字列の作り方が異なる。メニューに出ても直接URLで開ける可能性や、逆に非表示でも境界条件では差が出る余地は実装差として残る。
Creator・日時マッピングでは作成者・作成日時・更新日時は非NULL。標準コントローラは保存時にこれらを直接セットしない。既存行の属性はエンティティに残るが、全件削除後の再登録で新規行のみになる場合、環境やプラグインの事前処理に依存し得る。
