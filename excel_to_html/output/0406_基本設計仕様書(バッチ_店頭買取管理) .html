1. 買取自動入庫バッチ

機能の目的と役割

買取成立した商品に対して自動入庫処理を行う。

入出力仕様

種類内容
入力バッチ起動条件、設定値、DB上の対象データ。
出力CSVファイル、DB更新結果、ログ。
副作用対象データの更新、CSV出力、処理ログの記録。

開始条件、終了条件

種類内容
開始条件バッチ起動時刻または手動起動により処理が開始される。
終了条件対象データの処理と出力、ログ記録が完了する。

判定条件

  • Excel設計書に記載された対象条件、検索条件、CSV出力条件、登録条件を正とする。
  • Excel設計書に未記載のURLエンドポイント、DBカラム、実処理順序は ../ec-cube-enterprise の実装を正とする。
  • 権限、ログイン状態、管理画面プレフィックスなどの共通判定は共通設計および実装側のセキュリティ設定に従う。

プロセスフロー

  1. 利用者または外部システムが対象機能を開始する。
  2. 入力値、検索条件、アップロードファイル、またはリクエスト本文を受け付ける。
  3. Excel設計書に定義された対象データを取得し、実装側の検証・権限・状態条件を適用する。
  4. 登録・更新・出力・連携のいずれかの主処理を実行する。
  5. 成功時は結果画面、CSV/PDF/APIレスポンス、またはバッチ結果を返す。失敗時はエラー内容を返し、更新が必要な処理では不整合が残らないように扱う。

ビジネスロジック

  • **Excel設計優先**: 仕様の目的、対象データ、出力項目、表示項目、業務上の条件は excel_to_html/output の設計書を正とする。
  • **実装補完**: Excel設計に書かれていないURLエンドポイント、DBカラム、トランザクション、サービス分割、非同期処理は ../ec-cube-enterprise の実装を正とする。
  • **対象機能の要点**: 買取成立した商品に対して入庫処理を行う
  • **実装確認値**: BuyOrderAutoStockCommand / BatchAutoStockAction を実装確認値とする。

状態・データ更新

対象内容
主データバッチ対象の在庫・買取・履歴データを参照し、必要に応じて更新する。
履歴・ログ必要に応じてCSV取込履歴、在庫履歴、ステータス履歴、API受信履歴、アプリケーションログを作成・更新する。
DB関連実装確認値対象テーブル: dtb_buy_order_stock, dtb_buy_order_stock_history 明示列: dtb_product_class.stock, dtb_product_stock.stock 列詳細は ../ec-cube-enterprise の Entity / Repository / Migration を正とする。

例外処理

  • **入力不備**: 必須項目、CSVヘッダ、CSV行、APIリクエスト本文、検索条件が不正な場合はエラーとして処理し、登録・更新対象を確定しない。
  • **対象なし**: 検索条件や対象IDに該当するデータがない場合は、空の一覧、空CSV、またはエラーレスポンスとして扱う。扱いの細部は対象画面/API/バッチの実装に従う。
  • **状態不整合**: 既に処理済み、キャンセル済み、承認不可、在庫不足など状態条件に合わない場合は処理対象外またはエラーとする。
  • **外部連携失敗**: スマレジ等の外部連携で失敗した場合は、実装側の再連携・エラーログ・エラーメール・ステータス更新仕様を正とする。

関連設計への接続点

  • 画面項目、CSV列、PDFレイアウト、APIリクエスト/レスポンスの詳細は、参照元Excel設計書の該当シートを正とする。
  • URLエンドポイントとDBカラムは ../ec-cube-enterprise の Controller Route、Entity、Repository、Migration、Service 実装を正とする。

リニューアル移行時の扱い

本機能は新規実装であり、現行（pf-eccube3）に対応するバッチは存在しない。仕様は基本設計仕様書（店頭買取管理 基本設計、機能No B06-01）を正とし、DB関連はec-cube-enterpriseの実装を正とする。

観点現行（pf-eccube3）移行先（ec-cube-enterprise）
自動入庫バッチ対応機能なし（新規実装）。買取自動入庫バッチを新設する（実装確認値: BuyOrderAutoStockCommand / BatchAutoStockAction）。
対象データと判定—入庫待ちの店頭買取（ステータス12）・ネット買取（ステータス16）の買取情報を入庫済みへ更新する。
入庫・在庫履歴の永続化先—ネット買取は dtb_buy_order_stock・dtb_buy_order_stock_history、店頭買取は dtb_otc_buy_order_stock・dtb_otc_buy_order_stock_history。在庫数は dtb_product_class.stock・dtb_product_stock.stock を更新する。

列詳細はec-cube-enterpriseのEntity / Repository / Migrationを正とする。

B06-02 買取集計バッチ / バッチ 買取管理 — 買取集計バッチ

概要

店頭買取の取引データを集計日単位で集計し、店舗・部門ごとの買取金額・売価金額を買取集計テーブルへ登録するバッチである。コマンドライン（コンソールコマンド）から実行する。集計日の店頭買取データを店舗・部門単位で合算し、同じ集計日の既存集計を削除してから当日分を登録し直す。集計対象の中に部門が未設定の商品がある場合は、その一覧を管理者へ通知メールで送る。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。確認値はpf-eccube3（EC-CUBE3系）のHareruyaEcプラグインの買取集計バッチ、店頭買取・買取集計を扱うリポジトリ、通知メール送信処理を正とする。

カスタマイズ区分はカスタマイズであり、挙動はpf-eccube3を参照し、DB関連の記述はec-cube-enterpriseを正とする。

対象はコンソールコマンドであり、ブラウザ経由の画面を持たない。

本文ではフレームワークのコマンド型名やサービス型名を主説明としない。実行はコンソールのバッチコマンドで行う。

本書で扱うこと

  • バッチの起動方法（コンソールコマンド）と集計日引数
  • 集計日の店頭買取データの店舗・部門単位の集計
  • 既存集計の削除と当日分の登録
  • 部門未設定商品がある場合の管理者通知メール
  • 集計中エラー時のロールバックとエラー通知メール

本書で扱わないこと

以下は本書では仕様確定せず、実装または別機能・運用の設計を正とする。

  • 店頭買取の受付・査定・ステータス遷移そのもの（買取管理を正とする）
  • 集計結果を参照する管理画面の買取集計表示（画面側の設計を正とする）
  • 通知メールの宛先設定・本文テンプレート（メール設定・オプション管理を正とする）
  • バッチの起動スケジュール（運用・ジョブ設定を正とする）

リニューアル移行時の扱い

集計・登録の挙動は現行pf-eccube3を踏襲し、DB関連の永続化先はec-cube-enterpriseを正とする。店舗参照キーが現行と移行先で異なる。

観点現行（pf-eccube3）移行先（ec-cube-enterprise）
集計・登録の挙動集計日の店頭買取を店舗・部門単位で集計し、当日分の既存集計を入れ替える。同等の挙動を踏襲する（挙動はpf-eccube3を正とする）。
店舗参照キー独自店舗マスタ参照の shop_id（dtb_otc_buy_order・dtb_otc_buy_order_summary）。base_info_id（店舗基本情報 dtb_base_info 参照）。dtb_otc_buy_order・dtb_otc_buy_order_summary とも shop_id から base_info_id へ変わる。
集計結果の永続化先dtb_otc_buy_order_summary。同名テーブル。店舗参照キーのみ base_info_id へ変わる。
明細・個別入力商品の集計元dtb_otc_buy_order_detail・dtb_otc_buy_order_indivisual_input_product。同名・同等スキーマ（section_id・price・original_quantity／quantity・sell_price 等）。

買取集計店舗・部門・集計日ごとに買取金額・売価金額を合算した結果。買取集計テーブルへ登録する。

利用者視点の入口

入口実行方法期待されるふるまい
コンソールのバッチコマンドotcBuyOrder:batch updateSummary [YYYY-MM-DD]集計日の店頭買取データを店舗・部門単位で集計し、当日分の既存集計を入れ替える。部門未設定商品があれば管理者へ通知メールを送る。

引数に集計日（YYYY-MM-DD形式）を1つ指定できる。引数を省略した場合は前日を集計日とする。本機能はHTTPで届く画面を持たない。コマンド名が一致しない場合は処理を行わずに終了する。

処理フロー

買取集計を実行する（otcBuyOrder:batch updateSummary）

  1. 実行時間制限を解除し、メール送信用の経路を準備し、トランザクションを開始する。
  2. 集計日を決める。引数が指定されていればその日付、無ければ前日を用いる。いずれも当日0時0分0秒を起点とする。
  3. 集計日の店頭買取データを店舗・部門単位で集計し、買取金額・売価金額の合計を得る。
  4. 同じ集計日の既存の買取集計を削除する。
  5. 集計結果を買取集計テーブルへ一括登録する。集計結果が0件の場合は登録を行わない。
  6. 集計日の店頭買取の中から部門未設定商品の一覧を取得する。
  7. 部門未設定商品がある場合は、その一覧を管理者へ通知メールで送る。
  8. トランザクションをコミットする。

集計または登録の途中で例外が発生した場合は、登録をロールバックし、エラー内容を添えた集計エラー通知メールを管理者へ送る。

対象ステータス完了・ダブルチェック済み・入力済みの店頭買取を対象とする。
買取金額明細・個別入力商品それぞれで単価と数量を掛けて算出し合算する。
売価金額明細・個別入力商品それぞれで売価単価と数量を掛けて算出し合算する。

指標集計の要点
対象データ集計区間内に完了日を持つ店頭買取の明細と個別入力商品。

データ整合性

観点内容
多重実行ロックファイル等による多重起動防止は行わない。同じ集計日を同時に実行すると、双方が削除と登録を行い当日分が重複し得る。
途中失敗・再実行削除と登録を1トランザクションで行い、例外時はロールバックする。再実行で同じ集計日の集計を入れ替えるため重複しない。
参照時点実行時点の店頭買取データを集計対象とする。
削除と登録の範囲削除・登録の対象は指定集計日の当日分に限る。他日の集計は変更しない。

排他制御・トランザクション

ロックファイル等による多重起動防止は行わない。集計結果の削除と登録は1トランザクションで囲み、例外時はロールバックする。長時間処理に備えて実行時間制限を解除する。本バッチは楽観ロック・悲観ロックの対象を持たない。
