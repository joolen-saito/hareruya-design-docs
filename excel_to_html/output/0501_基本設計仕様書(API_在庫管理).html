カスタマイズ説明

スマレジの在庫が変動するタイミングで、ECCUBEとスマレジをスマレジプラットフォームAPIを介して連携させる

トリガーとなるポイントに合わせて、APIやWebhookを活用して連携させる

実装時の注意点

API利用時の注意事項一般　https://developers.smaregi.dev/apidoc/common/#section/Webhook

APIのレート制限(スロットリング)　https://developers.smaregi.dev/apidoc/common/#section/%E3%83%AC%E3%83%BC%E3%83%88%E5%88%B6%E9%99%90

※秒間50回が上限になりますが、理論上1秒間にレジ25台(在庫・受注処理で2回として仮定)が同時決済まで対応可能
※レート制限を超えた場合もエラーレスポンスで待機時間が返ってくるのでリトライ処理が可能

機能仕様処理概要（★はカスタマイズ項目）

在庫におけるスマレジとの連携は大きく分けて3つの方式

1スマレジ -> ECCUBE (Webhook方式)スマレジ側で在庫変動があった場合、取引完了や取引キャンセル(全キャンセル)
2ECCUBE -> スマレジ(API個別)CSV登録等の一括処理ではない管理画面でスマレジ側の在庫変動が発生した場合
3ECCUBE -> スマレジ連携(Patch一括)CSV登録等の一括処理でスマレジ側の在庫変動が発生した場合

1.スマレジ -> ECCUBE (Webhook方式) 処理概要（★はカスタマイズ項目）

スマレジ -> ECCUBE (Webhook方式)

★1-1. スマレジで取引完了もしくは取引全キャンセルをhookにwebhook発動

※ 在庫変動履歴情報のIDは商品と店舗の組合せでしかまとめて取得できないので、取引商品種類数分CのAPIを叩く必要がある

★1-2. 取得したスマレジ在庫変更履歴情報をもとにECCUBE上のスマレジ在庫情報を更新

在庫区分が02:売上の時は出庫処理, 12:の時は入庫処理を実施

取得したスマレジ在庫変更履歴情報の在庫区分が02:売上と12:返品のみ、情報更新処理を実施。それ以外は無視する

店頭受取分の商品IDの場合、スマレジ側の在庫は変動しないので無視する

スマレジの在庫変動履歴IDはECCUBE側の在庫変動履歴に紐づけて保存しておく

在庫変動履歴の登録については、「在庫変動時の履歴作成について」シートを参照

3. ECCUBE -> スマレジ連携(Patch一括) 処理概要（★はカスタマイズ項目）

ECCUBE -> スマレジ連携(Patch一括)

ECCUBE側の管理画面でCSVなどで一括で登録するなどして、大量の商品の種類数でスマレジの在庫変動が発生する場合に利用する

主にCSVによる登録を想定

★3-1. 管理画面操作によってスマレジ側の在庫のCSVによる登録処理

コールバックURLは処理結果が返ってきた時に処理ができるようにパラメータを設定する。

CSVファイルはコールバックで返ってきた時に処理に使用するので、S3に保存しておく

登録したCSVは各CSV登録画面で、CSV履歴として表示し処理結果を明示できるようにしておく。100件以上ある場合は、100件毎の小データにCSVを分割してS3に上げて履歴表示する

※「3-2 F. 在庫一括相対値更新API リクエストパラメータのコールバックURLに設定するGETパラメータ」を参照

※ この段階ではスマレジ側の登録の成功/失敗が判別できないので、ECCUBE側の在庫変動処理は行わない。結果がコールバックURLに返ってきた時に処理を行う

★3-2. 在庫一括相対値更新APIによりスマレジの在庫変動を一括登録

※ 在庫一括更新のPatch処理は、在庫変動数ではなく在庫総数を更新する処理のため使用しない

★3-3. 登録した処理結果がリクエストパラメータに登録したURLに非同期で返ってくるので、登録されていれば返ってきたらECCUBE側の在庫データも更新

処理が成功していれば、問合せ用IDやコールバックURLのパラメータに従い処理対象のCSVを特定し、S3よりダウンロードしてECCUBE側の処理を実行

処理結果をCSV処理履歴に登録する

スマレジwebhook連携エラー再連携
概要
スマレジ連携のwebhookで連携エラーになったものを再連携する
処理概要（★はカスタマイズ項目） 処理内容は、スマレジ連携処理と処理概要1-2と同様の処理を実行する

カスタマイズ説明

バッチプログラムの起動方法の変更

サーバ構成が変更になるので、AWS Step Functionsを利用して実装する

APIの仕様が廃止予定のスマレジAPIからプラットフォームAPIに変更

本店・支店の処理を統合

全店舗のデータをともに処理対象とする

スマレジ連携処理でスマレジ -> ECCUBE (Webhook方式)で連携に失敗したものをリトライする

機能仕様処理概要（★はカスタマイズ項目）

★1. APIでバッチ駆動時間から5時間前までの間のスマレジの在庫変動履歴データを取得する

そのデータの中で、在庫変動区分が「02:取引」もしくは「12:返品」でかつ、その在庫変動履歴IDがECCUBE側の在庫変動履歴に保存されているかを検索し、保存されていないIDを抽出

★2. スマレジ在庫と連携されていないデータを再連携処理する

機能仕様処理内容は、スマレジ連携処理と処理概要1-2と同様の処理を実行する

★3. バッチの実行時間を閉店時間などを見て可変的に実行する運用に変更する

取得する期間は可変で実装し、実行タイミング(1時間あたりの実行回数)やバッチの実行時間、APIでのエラー発生率、テスト結果等を踏まえて検討する

全店舗閉店後はスマレジが稼働しないので、バッチ処理は閉店後1回のみとする

念の為、取引のスマレジ再連携バッチと処理時間が被らないように設定する

実行トリガー　スケジュール起動(Step Functions)　実行タイミング　毎時16分

入力データ元　スマレジプラットフォームAPI　出力先(フォーマット)　DB

入力データ詳細

Webhookが何らかの理由で失敗したスマレジ取引情報

スマレジ側のwebhookにはリトライ処理が実装されていないので、在庫変動履歴が連携済みか確認が必要

以下の条件下でwebhookに失敗している場合、再連携処理を実行

・スマレジ在庫変動履歴IDがECCUBE側に登録されているかどうかを検索し、保存されていないIDを抽出
・在庫変動区分が「02:取引」もしくは「12:返品」
・店頭受取のデータではない

項目名　条件　備考

スマレジ在庫変動履歴データ.取引更新時間　バッチ駆動時間(X)からバッチ駆動時間よりY時間前(X-Y hours)の間

実行結果詳細 ※主にDBの登録・更新結果について記載

Webhookに失敗した処理が、スマレジ連携処理と処理概要1-2と同等の処理が完了した状態になる
