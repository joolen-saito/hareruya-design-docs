M02-01 受注状況 ／ m02-01_admin_home_home_order_status（管理画面_トップ受注状況）

管理画面ホームに表示される、受注ステータス別件数の要約と受注一覧への導線。

概要

管理画面ホームの受注状況は、管理者がログイン後に最初に見るダッシュボード上で、マスタに定義された受注ステータスごとの受注件数を一覧表示し、受注一覧へ遷移して同じステータスで絞り込んだ状態から業務を始められるようにする機能である。日本語ロケールではカード見出しが「注文状況」となるが、本書では設計上の呼称として「受注状況」と記す。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。 既存実装のふるまい、参照するデータ、表示ルール、拡張による差し替え可能性を確認し、仕様の確からしさを把握することを目的とする。

対象はブラウザ経由の管理画面ホームの一ブロックである。売上グラフ用の非同期取得やショップ状況ブロック、在庫・商品・会員数の集計は別機能として切り離す。

本書では Symfony の route 名、URL パス、Controller 構成は扱わない。 代わりに、ホーム画面表示、受注状況カード、ステータス行クリック、カード見出しクリックといった利用者視点の入口ごとに期待されるふるまいを記載する。

本機能のカスタマイズ区分は標準であり、挙動・画面とも移行先のec-cube-enterpriseの実装を正とする。DB関連の記述（テーブル名・列名・集計列）もec-cube-enterpriseを正とする。

本書で扱うこと

  • ホーム画面表示時に、既定の除外ルールに従って「表示対象の受注ステータス」と「ステータス別件数」がどのように決まるか
  • 除外対象ステータスを拡張処理が上書きする場合があること
  • 件数がデータベース上のどの情報に基づくか（全件集計であり期間絞り込みが無いこと）
  • 件数が存在しないステータス行をゼロ表示として描画するルール
  • ステータス行またはカード見出しから受注一覧へ遷移したとき、受注一覧の検索条件にどう反映する場合があるか（入口としての役割に限る）
  • 受注ステータスマスタの並びと表示名の扱い
  • 本ブロックに固有の Ajax 取得、永続化の更新、監査ログが無いことの明示
  • 受け入れテストで確認されている表示・件数・遷移の範囲

本書で扱わないこと

以下は本書では仕様確定せず、実装または別機能の設計を正とする。

  • Symfony の route 名、URL パス、Controller クラス名・メソッド名の一覧
  • 管理画面へのアクセス制御、ログイン、二段階認証、権限設定の詳細
  • 受注一覧の検索フォーム全般、ページネーション、一覧のクエリビルド、CSV、一括操作
  • 受注ステータスマスタの管理画面での編集・色・業務ルール
  • display_order_count を他画面でどう使うか（本ホームの一覧ループでは参照しない実装に基づく）
  • プラグインのイベント識別子やフックの直列名の確定表記
  • データベース接続失敗時の HTTP ステータスや例外型の列挙

処理フロー

ホーム画面表示・除外リストの確定

  1. 管理者がホーム画面にアクセスしたとする。
  2. システムは受注状況用の除外ステータス配列を用意する。既定では次の区分が除外に含まれる。キャンセル、出荷完了、決済処理中、購入処理中、返品に相当する識別子。
  3. ホーム表示向けの拡張フックにより、プラグイン等が上記配列を差し替える場合がある。差し替え後の配列が、その後の件数取得とマスタ行の取得の両方に使われる。
  4. 別の拡張フックが、ホームに渡す最終的なコンテキスト（件数マップ、表示用ステータス一覧、ほかダッシュボード他ブロック用の値）をイベント引数として公開する。拡張処理が受注状況に関わる配列を上書きした場合、以降の画面表示は上書き後の値に従う。

ステータス別件数の取得

  1. 確定した除外リストに含まれない受注ステータス識別子のみを対象に、受注台帳をデータベースへ問い合わせて件数を集計する。問い合わせは識別子ごとの件数にグループ化した読み取りである。
  2. 集計結果は「受注ステータス識別子と対になる件数」の対応表として保持される。除外されたステータスに属する受注は件数に含めない。
  3. 期間による絞り込み、会員、宛先、支払方法、店舗などの業務的条件は課さない。台帳に存在する受注行を対象とする。

表示用ステータス一覧の取得と画面への合成

  1. 確定した除外リストに含まれない受注ステータスについて、マスタから一覧を取得する。並びはマスタの表示順の昇順である。
  2. 画面はこの一覧の各行について件数を表示する。件数対応表に当該識別子が無い場合は 0 を表示する。よってマスタに存在し除外されていないステータスは、台帳に一件も無くても行として残る。

カード見出しから受注一覧へ

  1. 利用者が受注状況カードの見出しリンクを押下する。
  2. 受注一覧へ遷移する。本リンク経路ではステータス識別子をクエリに載せる設計にはしない。
  3. 以降の一覧の検索条件の初期化・セッション復元は、受注一覧機能の実装に従う。

ステータス行から受注一覧へ

  1. 利用者が特定のステータス行を押下する。
  2. 受注一覧へ遷移し、そのステータスの識別子がクエリとして付与される。
  3. 受注一覧の初回表示ロードでは、クエリにステータス識別子がある場合、検索条件のステータスにその識別子が含まれる形でフォームが組み立てられ、同条件がセッション上の検索条件として保存される場合がある。以降のページ送りや戻りは受注一覧のセッション復元ルールに従う。

データ整合性

観点内容
参照時点受注状況の件数は、ホーム画面表示時にデータベースから読み取った結果である。表示後に受注が作成・更新されても、表示中の数値は自動更新しない。
件数とマスタ件数集計と表示対象ステータスは同一の除外リストを使う。ただし、受注台帳の読み取りとマスタの読み取りを単一の業務トランザクションで固定する要件は持たない。
一覧との整合性ステータス行から受注一覧へ遷移した後の検索条件、一覧件数、ページング、セッション復元は受注一覧機能の実装に従う。本ブロックの件数と一覧上の件数の完全一致は保証しない。
更新との整合性本ブロックは参照のみであり、受注やステータスマスタを更新しない。受注更新との排他制御や再集計タイミングは各更新機能の設計を正とする。
外部連携との整合性外部連携やバッチにより受注が更新される場合の反映タイミングは、外部連携機能またはバッチ機能の設計を正とする。本ブロックは表示時点の永続化済みデータだけを読む。

処理フロー

ホーム画面表示・売上対象外リストの確定

  1. 管理者がホーム画面にアクセスしたとする。
  2. システムは売上集計用の売上対象外ステータス配列を用意する。既定ではキャンセル、決済処理中、購入処理中、返品を除外する。注文受領、入金待ち、対応中、出荷完了、入金済み、出荷指示、ピック中、店頭予約、ピック完了、引渡し済みは、既定の売上集計対象に含まれる。
  3. 売上向けの拡張フックにより、プラグイン等が上記配列を差し替える場合がある。差し替え後の配列が、その後のサマリ集計とグラフ用データ取得の双方に使われる。
  4. ホーム全体のコンテキストを公開する別の拡張フックにより、売上サマリを含むダッシュボード値が最終的に上書きされる場合がある。拡張処理が値を上書きした場合、画面表示は上書き後の値に従う。

売上サマリの取得

  1. 「今日」について、当日 0 時から翌日 0 時未満の order_date を持つ受注のうち、既定実装では注文受領、入金待ち、対応中、出荷完了、入金済み、出荷指示、ピック中、店頭予約、ピック完了、引渡し済みの受注を対象に、payment_total の合計と件数を求める。
  2. 「昨日」について、前日の日付で同様の境界を用いて合計と件数を求める。
  3. 「今月」について、当月 1 日 0 時から翌月 1 日 0 時未満の order_date を持つ受注のうち、既定実装で売上集計対象となるステータスの受注を対象に、合計と件数を求める。終端日の解釈は実装が用いる相対日付指定に依存し、タイムゾーンは永続化層および実行環境の設定に従う。
  4. 問い合わせ結果が無い場合、実装は空の結果として扱い、画面は 0 を表示する。

売上グラフ用データの取得と変換

  1. ブラウザがホーム画面表示後、グラフ用データを非同期で要求する。
  2. サーバは再度売上対象外リストを拡張フックで確定したうえで、次の三つの区間について、確定後の売上集計対象ステータスの受注を読み取り、日付または年月単位のバケットに売上金額と件数を累積する。
  • 週間相当。当日から見て過去にさかのぼった約一週間の範囲と当日現在までの upper bound を持つ区間。バケットキーは日単位である。
  • 月間相当。当月 1 日から現在までの区間。バケットキーは日単位である。
  • 年間相当。現在から過去にさかのぼった約一年と現在までの区間。バケットキーは年月単位である。
  1. 各区間について、範囲内の各日または各年月キーに対し、売上が無い期間も値が 0 のバケットとして用意される。これによりグラフの横軸ラベルが欠けない。
  2. 返却される JSON は三つのバケット集合からなる配列であり、画面側はこれを順に週間・月間・年間の canvas に対応付けて棒グラフを生成する。

画面への描画

  1. 売上サマリはテンプレートが通貨表示および件数の桁区切りを適用して出力する。
  2. グラフは売上金額のみを縦棒として表示する。ツールチップは通貨記号付きで値を整形する。
  3. 非同期取得が完了すると読み込みインジケータが非表示となる。取得に失敗した場合も読み込み表示は消えるが、グラフは描画されない。

処理フロー

ホーム画面表示・グラフ領域の初期描画

  1. 管理者がホーム画面にアクセスしたとする。
  2. サーバはホーム画面のHTMLを組み立て、売上状況カードに週間・月間・年間のタブと、各タブに対応する空のcanvas、読み込み中インジケータを出力する。この時点ではグラフは未描画である。
  3. ページ読み込み完了後、ブラウザがグラフ用データを非同期で要求する。

売上グラフ用データの取得と変換

  1. ブラウザがグラフ用データを非同期で要求する。要求はXMLHttpRequestであり、管理画面共通のAjax設定によりCSRFトークンが付与される。
  2. サーバはXMLHttpRequestかつCSRFが妥当かを判定する。いずれかを満たさない場合はHTTP400で{"status":"NG"}を返し、以降の集計を行わない。
  3. 条件を満たす場合、サーバは売上対象外ステータスを拡張フックで確定したうえで、次の三つの区間について確定後の売上集計対象の受注を読み取り、バケットに売上金額と件数を累積する。
  • 週間相当。当日0時から現在時刻までの区間。開始は当日から過去へ約一週間さかのぼった日とし、バケットキーは日単位（Y/m/d）である。
  • 月間相当。当月1日0時から現在時刻までの区間。バケットキーは日単位（Y/m/d）である。
  • 年間相当。現在時刻から過去へ約一年さかのぼった月の1日0時から現在時刻までの区間。バケットキーは年月単位（Y/m）である。
  1. 各区間について、開始日から終了日まで1日ずつ進めながらバケットを初期化し、各バケットの売上金額と件数を0で用意する。年間区間ではバケットキーが年月単位のため、同一月内の各日が同一キーへ集約され、結果として月単位のバケットになる。
  2. 範囲内の各受注を、その受注日をバケットキー書式へ変換して該当バケットへ加算する。売上金額はバケットの値へ加算し、件数はバケットの件数を1増やす。
  3. 三つのバケット集合を週間・月間・年間の順に並べた配列をJSONで返す。

画面への描画

  1. ブラウザは返却された配列を順にchart-0・chart-1・chart-2へ対応づける。
  2. 各バケット集合について、キーを横軸ラベル、売上金額を縦棒の値とする棒グラフを生成する。件数はバケットに含まれるが、棒グラフの系列としては使わない。
  3. 縦棒の系列ラベルは売上金額を示す文言とする。
  4. 非同期取得が完了すると読み込み中インジケータを非表示にする。取得に失敗した場合も読み込み表示は消えるが、グラフは描画されない。

処理フロー

ホーム画面表示・ショップ状況用集計

  1. 管理者がホーム画面にアクセスしたとする。
  2. システムはデータベースへ問い合わせ、在庫切れ商品数・取扱商品数・本会員数をそれぞれ集計する。詳細は後述の「集計条件」を参照する。
  3. ホーム表示組み立ての終盤で、ダッシュボード全体向けの拡張イベントが発火し、イベント引数として受注状況・売上サマリに加え、上記の3指標も渡される。
  4. 画面へ渡す最終的なテンプレート変数は、イベント dispatch の直前に保持したローカル変数から組み立てられる。リスナーがイベント引数内の集計値を書き換えても、dispatch 後にその引数から再読込しない限り、画面表示は自動では変わらない。

在庫切れ商品数から商品一覧へ

  1. 利用者が在庫切れ商品数の行を押下する。
  2. システムは商品一覧向けの検索条件セッションに、「在庫なし」に相当する条件だけを格納した連想配列を保存する。既存の検索条件は本処理ではマージせず、当該セッション領域をこの配列で上書きする。
  3. 商品一覧の1ページ目へリダイレクトする。
  4. 以降の一覧の検索UI・件数・ページ送りは商品一覧機能の実装に従う。

  2. 商品一覧へ遷移する。ショップ状況側では検索条件セッションを更新しない。
  3. 以降の一覧の初期状態は商品一覧機能の実装に従う。

処理フロー

ホーム画面表示・おすすめ一覧取得

  1. 管理者がホーム画面にアクセスしたとする。
  2. システムは受注状況、売上状況、ショップ状況を組み立て、ホーム表示組み立て完了時の拡張イベントを発火する。
  3. 拡張イベントの後に、おすすめプラグイン一覧を外部のプラグイン API から取得する。
  4. 外部 API へは、プラグイン認証キー、現在のサイト URL、EC-CUBE バージョンをヘッダとして送信する。認証キー原値は本書では扱わない。
  5. 外部 API のレスポンスを配列として読み込み、各プラグインにインストール状態と対応バージョン判定を付与する。
  6. 取得・加工に成功した場合、テンプレートへおすすめプラグイン配列を渡す。
  7. 外部 API 通信またはレスポンス処理でプラグイン API 例外が発生した場合、例外はホーム表示処理内で握りつぶし、テンプレートへ空配列を渡す。
  8. テンプレートは配列内の各プラグインを一覧表示し、プラグインごとの詳細モーダルを出力する。

インストール状態の付与

  1. システムはローカルに登録済みのプラグインを全件取得する。
  2. 各おすすめプラグインの状態を、初期値として「未インストール・未購入扱い」にする。
  3. ローカルプラグインの取得元 ID が外部 API のプラグイン ID と一致する場合、「インストール済み」にする。
  4. インストール済みで、ローカルのバージョンが外部 API のバージョンより古い場合、「アップデートあり」にする。
  5. 外部 API 上で未購入かつ購入が必要なプラグインの場合、「未購入の有料プラグイン」にする。この判定はインストール済み・アップデートあり判定の後に評価され、条件に一致した場合は表示状態を上書きする。
  6. 現在の EC-CUBE バージョンが外部 API の対応バージョン一覧に含まれるかを判定し、詳細モーダルの警告表示に使う。

詳細モーダル表示

  1. 利用者がプラグイン画像または名称を押下する。
  2. ブラウザは対象プラグイン ID に対応する詳細モーダルを同一画面上で開く。
  3. モーダルには API 取得値とインストール状態に基づく詳細情報、警告、導線を表示する。
  4. 利用者が閉じるボタンまたはキャンセルボタンを押下すると、モーダルを閉じてホーム画面へ戻る。サーバ通信は発生しない。

インストール確認・購入・外部 URL への導線

  1. 無料または入手可能な未インストールプラグインの場合、モーダルの主導線としてインストール確認へのリンクを表示する。
  2. インストール済みで更新が不要なプラグインの場合、モーダルの主導線は「インストール済み」の状態表示になる。
  3. インストール済みで外部 API 上のバージョンが新しいプラグインの場合、モーダルの主導線としてアップデート確認へのリンクを表示する。
  4. 未購入の有料プラグインの場合、モーダルの主導線として外部ストア購入用フォームの送信ボタンを表示する。フォームはプラグイン ID と公開鍵を送信し、外部ストアを別ウィンドウで開く。
  5. 問い合わせ URL またはマニュアル URL がある場合、モーダル内に外部リンクを表示する。押下時は別ウィンドウで開く。

集計条件

本機能では DB レコードの件数集計を行わない。 ただし、おすすめプラグイン配列の各要素に対して、ローカル登録済みプラグイン全件との突き合わせを行い、表示状態を算出する。

指標集計の要点
おすすめプラグイン件数外部 API が返した配列件数をそのまま表示対象件数とする。ホーム画面側で件数表示は行わない。
ローカルプラグイン突き合わせローカルの登録済みプラグイン全件を取得し、外部 API のプラグイン ID とローカルの取得元 ID が一致するかをプラグインごとに確認する。

観点内容

外部 API との整合性推薦対象、並び順、価格、説明、対応バージョンは外部 API の返却値を正とする。ホーム画面側では返却値の内容を業務的に補正しない。
ローカルプラグインとの整合性インストール状態は、ホーム画面表示時点のローカル登録済みプラグインと外部 API 取得値の突き合わせ結果である。インストール確認以降で状態が変わった場合、次回ホーム表示までカード内表示は更新しない。
