M01-01 パスワード認証 ／ m01-01_admin_login_login（管理画面_認証機能）

概要

管理画面ログインは、登録済みの管理者を本人確認し、管理画面を利用できる状態にする機能。

本機能のカスタマイズ区分は標準であり、挙動・DB関連ともec-cube-enterpriseを正とする。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。 既存実装のふるまい、状態、参照するデータ、判定境界、永続化、副作用を確認し、仕様の確からしさを把握することを目的とする。

対象はブラウザ経由の管理画面ログイン。

本書では Symfony の route 名、Controller 構成は扱わない。 URL エンドポイントは利用者視点の入口に限り、実装確認値として記載する。

本書で扱うこと

  • 管理ログイン画面表示時のふるまい
  • ログイン ID・パスワード送信時の認証判定
  • 管理セッション確立時のふるまい
  • 二段階認証が必要な場合の入口制御
  • 未ログイン時の保護画面アクセス制御
  • ログイン成功・失敗時の副作用
  • ログイン履歴、最終ログイン日時、セッション、Cookie に関する確認事項
  • 自動ログアウト、明示ログアウト時のふるまい
  • ログイン画面に表示される正常・エラーメッセージの文言と表示条件

リニューアル移行時の扱い

本機能はリニューアル移行対象である。Cookie 名、セッションキー名、保存形式は現行実装の確認値として記録し、機能仕様として固定しない。

移行時に保証する対象は、名称ではなく次のふるまいである。

  • 管理者ログイン状態をブラウザ単位で保持する。
  • 未ログインで保護された管理画面へアクセスした場合、ログイン画面へ誘導する。
  • 管理者としてログイン済みの場合、保護された管理画面を利用できる。
  • 二段階認証が必要な管理者は、追加認証完了まで保護された管理画面を利用できない。
  • 明示ログアウト時に管理者としての認証状態を終了する。
  • Remember Me が有効な場合、保存済み情報により管理ログイン状態を再確立する。
  • ログイン成功履歴と最終ログイン日時更新が実行される。

次の項目は現行実装の確認値として本書に記録する。名称一致を確認する場合は、設計書ではなくソースコードを確認する。

  • Cookie 名
  • セッションキー名
  • セッション内の保存形式
  • Remember Me トークンのサーバ側保存キー
  • Cookie 値、セッション ID、Remember Me トークンの原値

処理フロー

ログイン画面表示

  1. 利用者が管理ログイン URL にアクセスする。
  2. 既に管理者としてログイン済みなら、ログイン画面を表示せずホーム画面へ遷移する。
  3. 未ログインなら、ログイン ID・パスワード入力画面を表示する。
  4. 未ログインで保護された管理 URL に来た場合も、ログイン画面へ誘導する。

ログイン送信

  1. 利用者がログイン ID・パスワードを送信する。
  2. 入力不足、なりすまし対策トークン不整合、試行制限に該当する場合はログインを成立させず、ログイン画面でエラーまたは制限状態にする。ログイン送信は Symfony Security の form_login が受けるため、入力不足はログインフォームの NotBlank ではなく認証失敗として扱う。
  3. ログイン ID から管理者を特定する。
  4. 管理者が存在しない、停止中、ログイン不可の場合は認証エラーにする。
  5. パスワードを照合する。
  6. パスワード不一致の場合は認証エラーにする。
  7. ID・パスワード認証が成功し、追加認証が不要な場合は、管理セッションを作成し、ホーム画面へ遷移する。
  8. ID・パスワード認証が成功し、二段階認証が必要な場合は、業務画面へ入る前に追加認証へ誘導する。

ログイン後

  1. ログイン成功・失敗はログイン履歴に残る。
  2. 成功時は最終ログイン日時も更新される。
  3. Remember Me Cookie を持つ状態で管理画面へアクセスした場合は、管理ログイン画面へリダイレクトして認証状態を再確立する。
  4. 無操作時間が設定値を超えた場合、自動ログアウト扱いとなり再ログインが必要になる。
  5. 明示ログアウト時は管理セッションを終了し、ログイン画面へ戻る。

業務ルール・計算

項目内容
認証対象管理者として登録され、ログイン可能な状態の管理メンバーだけを認証対象とする。一般フロント会員は管理画面の認証主体ではない。
判定順序入力不足、CSRF、試行制限、管理者存在、有効状態、パスワード照合、追加認証要否の順にログイン成立可否を判定する。
失敗時表示管理者の存在有無、停止状態、ログイン不可状態、パスワード不一致は画面上では詳細に区別しない。表示文言は「表示メッセージ」の認証エラー表を正とする。
成功時副作用管理セッションを確立し、ログイン履歴と最終ログイン日時の更新対象にする。Remember Me が有効な場合は Cookie とサーバ側保存情報により再確立できる。
試行制限固定窓方式でログイン ID と IP アドレス、または IP アドレス単体を単位に送信回数を制御する。
業務計算本機能では金額、件数、在庫などの業務計算を行わない。

項目名必須／任意最大長初期値保存先・扱い

データ整合性

観点内容
管理者状態認証時点で有効な管理者だけがログインできる。認証後に管理者状態が変更された場合の扱いは、以降の認可・セッション検証の実装に従う。
セッションと Cookie管理ログイン状態はブラウザ単位のセッション Cookie とサーバ側セッションに依存する。Remember Me は別の Cookie とサーバ側保存情報によりログイン状態を再確立する。
ログイン履歴ログイン成功・失敗はログイン履歴に保存する。失敗履歴保存に失敗した場合は認証結果そのものとは切り離してサーバログに記録する。
最終ログイン日時成功時は管理者の最終ログイン日時を更新する。成功履歴保存や最終ログイン日時更新に失敗した場合は、明示的に握りつぶさず例外として扱う。
二段階認証との整合性二段階認証が必要な管理者は、ID・パスワード認証後に追加認証へ進む。追加認証の詳細は二段階認証機能の設計を正とする。

API/バッチ結果

種類内容
API本機能はブラウザ経由の管理ログインを対象とし、API ログインは扱わない。
バッチ本機能はバッチを起動しない。管理者状態やパスワードが別処理で変更済みの場合、次回ログイン送信時にその時点の永続化済みデータを読む。

管理画面における二段階認証。

概要

管理画面二段階認証は、管理者としての ID・パスワード認証が成功したあと、登録済みの TOTP 方式のワンタイムトークンで再度本人確認を行い、認証済み状態をブラウザに紐付けて保持する機能である。

本機能のカスタマイズ区分は標準であり、挙動・DB関連ともec-cube-enterpriseを正とする。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。 既存実装のふるまい、状態、参照するデータ、判定境界、永続化、副作用を確認し、仕様の確からしさを把握することを目的とする。

対象はブラウザ経由の管理画面であり、二段階認証の有効化、初回設定、追加認証、本人による再設定を含む。

本書では Symfony の route 名、URL パス、Controller 構成は扱わない。 利用者がたどる境界として、「利用者視点の入口」に HTTP メソッドとサイトルートからのパスパターン（実装確認値）を記載する。

本書で扱うこと

  • システム全体および個別管理者における二段階認証の有効／無効の扱い
  • パスワード認証後、保護された管理画面へ進む前の追加認証としての TOTP 検証
  • 二段階認証が有効な管理者の、秘密鍵未設定時の初回設定。QR の表示およびトークンによる登録
  • 本人による秘密鍵の再設定および既存デバイスへの影響

二段階認証用 Cookie 名、保存 JSON の構造、パラメータ名は現行実装の確認値として記録し、機能仕様として固定しない。

移行時に保証する対象は、名称ではなく次のふるまいである。

  • システムで二段階認証が無効な場合、追加認証を要求しない。
  • 二段階認証が有効な管理者は、パスワード認証後、トークン検証および初回秘密鍵登録のいずれかを完了するまで保護された管理画面を利用できない。
  • トークン検証または秘密鍵登録が成功したあと、一定期間は同一ブラウザで追加認証を省略できる。その範囲は認証済み Cookie が有効な期間による。
  • 管理者の 2 段階認証を OFF にした場合、当該管理者に対する追加認証要求は発生しない。当該管理者の秘密鍵が DB に残るかどうかは実装に従う。

  • 二段階認証用 Cookie 名。既定は環境変数 ECCUBE_2FA_COOKIE_NAME 由来の値となる
  • 認証済み状態の有効日数。環境変数 ECCUBE_2FA_EXPIRE 由来。0 のときはブラウザセッションに近い扱いとなる
  • Cookie の Path、Secure、SameSite。いずれも SSL 強制設定と連動する
  • Cookie 値、TOTP 秘密鍵、6 桁トークンの原値

  1. リクエストが管理画面であること、かつシステム 2FA が有効であることを確認する。いずれかで無ければ何もしない。
  2. 追加認証画面そのものへのリクエストは、ガードによるリダイレクトの対象外とする。
  3. 初回設定画面へのリクエストは、当該管理者の秘密鍵が未設定のときのみガードの対象外とする。秘密鍵が既にある場合は対象とし、これにより初回設定ルートへの安易な迂回を防ぐ。
  4. 現在利用者が管理者であり、個別 2FA が ON であり、認証済み Cookie が有効でない場合、秘密鍵の有無に応じて追加認証画面または初回設定画面へリダイレクトする。それ以外はそのまま後続処理へ進む。

追加認証・秘密鍵が既に設定済みの場合

  1. システム 2FA が無効、または認証済み Cookie が既に有効なら、ホーム画面相当へ送る。
  2. 秘密鍵が未設定なら、初回設定画面へ誘導する。
  3. POST で 6 桁トークンを受け取り、フォーム妥当性のうえで秘密鍵と照合する。
  4. 成功時はホーム画面相当へリダイレクトし、認証済み Cookie を付与する。
  5. 失敗時またはフォーム不正時は、同画面に留まり、再入力を促す文言を表示する。

初回設定・個別 2FA ON かつ秘密鍵未設定の場合

  1. システム 2FA が無効、または認証済み Cookie が既に有効なら、ホーム画面相当へ送る。
  2. 既に秘密鍵が設定済みなら、追加認証画面へ送る。未認証状態での秘密鍵の再設定を防ぐためである。
  3. GET 時は新規秘密鍵候補を生成し、フォームの隠し項目に渡し、QR コード用データとして画面に出す。
  4. POST 時は隠し項目の秘密鍵と入力 6 桁を照合し、成功時に DB に保存し、フラッシュ成功メッセージと認証済み Cookie を付与してホーム画面相当へ送る。
  5. 失敗時はエラーメッセージを表示する。GET 時に既に秘密鍵が DB 上ある場合は警告を出し、再設定に相当することを伝える。

本人による再設定・秘密鍵の付け替え

  1. 認証済み Cookie が無効な場合、ホーム画面相当へ送る。以降のガードにより追加認証へ誘導される想定である。
  2. 初回設定と同様に GET で秘密鍵候補と QR を出し、POST で検証する。画面上の遷移およびレイアウトは管理画面標準フレームを用いる。
  3. 成功時の DB 更新により、従来のデバイスから発行されたトークンは無効化される。新秘密鍵で認証アプリを再登録する必要がある。
