機能

現行ECサイトインポートされたアカウントにパスワードリセットメールを送信

(カスタマイズ後のシステムは厳格なパスワードを設定してもらう想定のため、全会員のパスワードを変更を促す可能性)

機能仕様処理概要（★はカスタマイズ項目）

事前準備

・現行ECサイトから会員情報インポート後、各ユーザーの会員データに「パスワード再設定キーコード(※)」を登録する。

「パスワード再設定キーコード」を登録すると会員データの最終更新日が自動的に更新される。

※パスワード再設定キーコードはパスワード再設定用URLで使われるコードのこと。全ユーザー毎に個別生成され重複しないコード(ユニークコード)が割り振られる。

機能仕様処理内容

・リニューアル時パスワードリセットメール送信バッチを実行する際に日付入力しないとエラーとなる。

引数には「パスワード再設定キーコード登録開始した日時」を入力し実行する。

・リニューアル時パスワードリセットメール送信バッチを実行後、該当者に対してサイトリニューアルの案内およびパスワード再設定URLをメール送信される。

設定言語(日本語・英語)によって、メール本文が切替わる

・メール送信後、データベース内にあるメール送信履歴データ(dtb_user_mail_history)に送信内容が保存される。

送信対象

・会員情報データ最終更新日時がバッチ実行時に指定された日時以降のもの(最終更新日 >= 指定日時)

今回の指定日時は「パスワード再設定キーコード登録開始した日時」を設定

・会員情報データ内にパスワード再設定キーコードが事前に設定されていること

実行トリガー　-　実行タイミング　手動実行

入力データ元　DB　出力先(フォーマット)　メール・DB

入力データ詳細

バッチ実行時に、パスワード再設定コードを登録した日時を入力し実行する。

B08-01 リニューアル時パスワードリセットメール送信 / バッチ 会員管理 — リニューアル時パスワードリセットメール送信

概要

サイトリニューアルに伴い、指定した基準日以降に更新された会員に対し、パスワード再設定を促す案内メールを送信するバッチである。コマンドライン（コンソールコマンド）から、基準日を引数に指定して実行する。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。確認値はpf-eccube3（EC-CUBE3系）のHareruyaEcプラグインの会員バッチ（アカウント移行通知処理）、会員を抽出するリポジトリ、移行通知メール送信処理を正とする。カスタマイズ区分は現行踏襲であり、挙動はpf-eccube3を参照し、DB関連の記述（テーブル名・列名・永続化先）はec-cube-enterpriseを正とする。

対象はコンソールコマンドであり、ブラウザ経由の画面を持たない。

本文ではフレームワークのコマンド型名やサービス型名を主説明としない。実行はコンソールのバッチコマンドで行う。

本書で扱うこと

  • バッチの起動方法（コンソールコマンド・基準日引数）
  • 対象会員の抽出
  • パスワード再設定案内メールの送信
  • 基準日未指定時の挙動

本書で扱わないこと

以下は本書では仕様確定せず、実装または別機能の設計を正とする。

  • パスワード再設定そのもの（パスワード変更機能を正とする）
  • 移行通知メールの本文・件名（メールテンプレート管理を正とする）
  • バッチの起動スケジュール（運用・ジョブ設定を正とする）

リニューアル移行時の扱い

挙動の参照は現行（pf-eccube3）、DB関連の記述は移行先（ec-cube-enterprise）を正とする。

処理フロー

リニューアル時パスワードリセットメールを送信する（customer:batch sendAccountMigration <基準日>）

  1. 引数の基準日を取得する。未指定の場合は日付の指定を促して終了する。
  2. メール用テンプレートとメール送信経路を準備する。
  3. 基準日以降の更新日を持つ会員を抽出する。
  4. 会員ごとに移行通知メールを送信する。
  5. 一定件数ごとに件数とメモリ使用量をコンソールに出力する。

B08-06 スマレジ使用ポイント連携 / バッチ 会員管理 — スマレジ使用ポイント連携

概要

指定した受注で使用したポイントを、スマレジ側の会員ポイントへ反映（減算連携）するバッチである。コマンドライン（コンソールコマンド）から、対象の受注IDを引数に指定して実行する。購入完了処理や購入完了再処理から別プロセスとして呼び出される。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。確認値はpf-eccube3（EC-CUBE3系）のHareruyaEcプラグインのスマレジバッチ（使用ポイント連携処理）、受注サブ・選手情報を扱うリポジトリ、スマレジポイント連携処理を正とする。カスタマイズ区分は現行踏襲であり、挙動はpf-eccube3を参照し、DB関連の記述（テーブル名・列名・永続化先）はec-cube-enterpriseを正とする。

対象はコンソールコマンドであり、ブラウザ経由の画面を持たない。

本文ではフレームワークのコマンド型名やサービス型名を主説明としない。実行はコンソールのバッチコマンドで行う。

本書で扱うこと

  • バッチの起動方法（コンソールコマンド・受注ID引数）
  • 受注の使用ポイントのスマレジへの減算連携
  • 連携失敗時のエラー記録

本書で扱わないこと

リニューアル移行時の扱い

挙動の参照は現行（pf-eccube3）、DB関連の記述は移行先（ec-cube-enterprise）を正とする。最大の差は受注の拡張情報の保持先である。

項目現行（pf-eccube3）移行先（ec-cube-enterprise）
受注の拡張情報（消費ポイント・連携エラー）補助テーブル受注サブdtb_order_subに保持補助表を廃し受注dtb_orderへ統合。spended_points（ポイント使用）・point_error_message（ポイント連携エラーメッセージ）・smaregi_error_flg（スマレジ連携エラーフラグ）

現行は消費ポイントと連携エラー情報を受注サブdtb_order_subに保持するが、移行先ec-cube-enterpriseでは補助表を持たず、これらを受注dtb_orderの列（spended_points・point_error_message・smaregi_error_flg）へ統合している。本文の挙動説明にある「受注サブ」は現行の保持先を指す。

利用者視点の入口

入口実行方法期待されるふるまい
コンソールのバッチコマンドsmaregi:batch updatePoint <受注ID>指定受注の使用ポイントをスマレジ会員ポイントへ減算連携する。失敗時はエラーを記録する。

本機能はHTTPで届く画面を持たない。受注IDが未指定または数値でない場合は処理を行わずに終了する。購入完了処理・購入完了再処理から別プロセスで呼び出される。

処理フロー

スマレジ使用ポイント連携を実行する（smaregi:batch updatePoint <受注ID>）

  1. 引数の受注IDが未指定または数値でない場合は処理を終了する。
  2. 受注IDから受注サブと会員（選手情報）を取得する。
  3. 会員のスマレジIDに対し、受注の消費ポイント分を減算してスマレジへ連携する。
  4. 連携が成功した場合は終了する。
  5. 連携が失敗した場合は受注サブにエラーメッセージを記録し、連携エラーフラグを立てて保存する。

業務ルール・計算

項目内容
連携量受注の消費ポイントを負の値（減算）としてスマレジへ連携する。
失敗時の記録連携失敗時はエラーメッセージとエラーフラグを受注サブに残し、後続の再連携対象とする。
