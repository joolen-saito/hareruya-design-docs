# HTML設計書 再生成 手順書

正本HTML設計書（`excel_to_html/output/*.html`）を作り直すときの手順とゲート。
**この手順を通さない再生成は行わない。**

- 変換の規約は [[function-spec-html-render]] / [[excel-to-html]] / [[output-exclusion-policy]] が正本。
  本書は「どの順で回し、どこで落とすか」を定める。
- 不具合調査（②）は再生成後の正本を読む。**正本が欠けたまま調査すると、その範囲は原理的に検出できない。**

---

## 合意した手順（2026-08-21 利用者と合意）

### 対象 — 現行仕様セクションを出す条件

正本HTMLに埋め込む「現行仕様」は、**Excel設計書を補うためだけに置く**。
Excel が既に定めている仕様を現行仕様にも書くと、**同じ正本の中で二重定義になり矛盾が生まれる**。
②不具合調査はその矛盾を DESIGN_ISSUE として拾い、無駄な指摘を量産する。

#### 出さない条件（どれか1つでも当たれば出さない）

| # | 条件 | 根拠・実測 |
| --- | --- | --- |
| 1 | **カスタマイズ区分が「新規実装」「標準」** | 新規実装の正典は Excel のみでリバースを行わない。標準は生成自体が不要（389本中73本） |
| 2 | **Excel設計書がCSV/TSVの項目定義程度しか書いていないシート** | 見出し（機能について／処理概要／カスタマイズ説明）があっても、中身が項目表とその追加リストだけなら対象。実測: 0203「受注一覧CSV出力」は84行中64行が項目表 |
| 3 | **同一機能Noが複数シートに割り当てられているとき、2枚目以降** | 同じ現行仕様が重複して載る。実測7件（0203 受注情報検索 一覧(検索入力)/(検索結果)、0205 買取商品履歴(検索入力)/(検索結果) ほか） |
| 4 | **フェーズ2で対応する機能のシート** | 実測12件（0302 ナビゲーション5件、0205 買取一覧、0306 マイページ ほか） |
| 5 | 廃止（superseded）・CSV項目のみ台帳に登録済み | 既存の台帳 |

#### 出す場合に書く範囲

**Excel設計書に書かれていないことだけを書く。** Excel と同じ仕様を言い換えて載せない。
Excel が項目・条件・文言を定めているなら、現行仕様側はその話題に触れない。

### 粒度 — I/Oとふるまいに限り、Excelと重ならない範囲だけ

現行仕様セクションに書くのは、次の3条件をすべて満たすものだけ。

1. **I/O とふるまい**であること。画面・応答・ファイルに現れる入出力と、条件と結果。
   内部手順・実装手段・観測できない中間状態は書かない。
2. **Excel設計書が定めていない**こと。Excel が項目・条件・文言を定めているなら触れない
   （二重定義は同じ正本の中で矛盾を作り、②不具合調査が無駄な指摘を量産する）。
3. **正典に根拠がある**こと。正典は区分で決まる（現行踏襲・カスタマイズ＝現行ソース＋ee確認＋Excel）。

**行数や小見出し数を目標にしない。** 手本を決めて他機能を合わせる、という進め方をしない。
2026-08-21 に 0203 受注検索（202行）を手本として他書と比べたが、
0203 自身が上の条件を満たしていなかった（CSV項目だけのシートに現行仕様を出す、
同一機能Noの2シートに重複して出す）。**量ではなく条件で判断する。**

### 作業単位

**1機能＝1単位**。正典が機能ごとに違うため、書（0202等）単位でまとめない。

### 出典（P1/P2/P3で強度を変える）

記述が指すふるまいの重要度で、求める裏取りの強さを変える。

| 重要度 | 定義 | 出典の要求 |
| --- | --- | --- |
| **P1** | 業務が回らず商売が止まる／データ整合性が壊れる／手作業でも代替できない（受注・買取・出荷・商品金額・金額相当・決済・在庫・メール通知・外部連携・認証・認可・セキュリティ・法令要件・登録フォームのバリデーション） | **出典を付ける** |
| **P2** | 迂回すれば回る（CSV一括登録・イベント・デッキ・分析・コンテンツ） | **出典を付ける** |
| **P3** | 業務は回る（見出し・文言・列名・並び順・桁区切り） | 機械が**出典の実在だけ**を見る |

重要度は機能名で機械的に決めず、**影響と迂回可否**で判断する
（受注管理でも文言差は P3、CSV一括登録でも取り込めない＝データ登録不能なら P1）。

#### 書く場所 — 正本Markdownだけ。HTML設計書には出さない

Markdown の末尾に `## 出典` 節を置く。h2 が3種以外なので **HTML には出力されない**。
設計書の読み手にファイルパスや行番号は不要であり、本文に実装用語を書けない制約とも両立する
（2026-08-21 利用者確認: HTML設計書に出典は不要）。

```
## 出典
| 小見出し | 重要度 | 出典 |
| --- | --- | --- |
| 承認と却下 | P1 | pf-eccube3:src/.../StockApprovalController.php:139 |
| 出力する列 | P3 | 0202:sheet-46 |
```

書式は `<リポジトリ>:<パス>[:<行>]`（pf-eccube3 / pf-api / ec-cube / deck-api / ec-cube-enterprise）
または `<書番>:<シートID>`（例 `0202:sheet-46`）。

#### 出典ゲートと「粒度を細かくしない」の両立

両立する。**P1/P2 はふるまい・I/O という粗い記述で、細かい記述の大半は P3** だからである。
P3 に出典を課さないので、ゲートは細かさを増やす方向に働かない。

ただし設計を誤ると両立しない。次の3点を守る（`check_source_citation.py` が実装）:

1. **出典は `###` 小見出し単位**に1つ以上。文単位で要求しない
   （文単位にすると、まとめて書けた挙動をわざわざ分割する動機が生まれる）。
2. **被覆率で評価しない。** 率にすると文を刻んで率を上げられる。P1/P2 の小見出しに
   出典があるか無いかの二値で見る。
3. **機械は出典先の実在だけを見る。** 内容が一致しているかは人の点検の仕事。

**逆向きの失敗は捕まえられない。** 出典の手間を避けて P1/P2 の記述そのものを書かない
（過小報告）は率では検出できないので、`--report` の重要度分布と「出典節を持たない文書」の数を
人が見る。

### 順序

```
1. 台帳を更新（csv-format-only / superseded / phase2）
2. 対象を確定（区分で 316本に絞る）
3. 正典から書く（1機能1単位・I/Oとふるまいに限る・P1/P2は出典付き）
4. ゲート（構造 / 完全性 / 出典）
5. 再生成（convert → integrate → orphan）
6. verify
7. 台帳へ記録してコミット
8. ②不具合調査（全冊の正本が固まってから）
```

| --- | --- | --- |
| 第1段 | 区分による除外（新規実装45・標準28）と、誤って書き直した31本の差し戻し | 済（2026-08-21） |

| 第5段 | 再生成 → verify → 台帳記録 | 未 |

## なぜ手順書が要るか（2026-08-21 の事故）

Markdown正本を「0203の型」（業務ロジック／入出力／表示メッセージの3節）へ書き直す工程で、
**内容が3節へ移されず捨てられた機能設計書が35本**出た。うち22本が 0202（在庫管理）。

| 例 | 変化 | 残ったもの |
| --- | --- | --- |
| m04-12 在庫分割結合検索/一覧 | 274行 → **11行** | 表示メッセージ表だけ |
| m04-22 在庫移動・振替CSV登録 | 330行 → **1行** | タイトルのみ |
| m04-01 在庫検索一覧 | 456行 → 39行 | 業務ロジック・入出力なし |

結果として 0202 は、正本のうち現行仕様由来の要求が **3.8%** しかない（0203は32.2%、0204は33.5%）。
在庫管理の主要11機能について、業務ロジックと入出力の突合が実施できない正本になっていた。

**なぜ止まらなかったか。** 既存ゲート `check_rewrite_quality.py` は
**メッセージIDと画面文言の保存しか見ていない**。捨てられたのは本文で、メッセージ表は残っていたため、
上の3本はいずれも「OK」で通った（実測済み）。`verify.py` は Excel→HTML の忠実性を見る道具で、
Markdown書き直しの欠落は守備範囲外。**守る対象と守っている対象がずれていた。**

同じ日に、`csv-format-only.tsv` のヘッダが参照する `detect_csv_format_only.py` が
**存在しなかった**ことも判明した。そのため台帳の登録が4件で止まり、
CSV項目だけのシート（0206「買取商品一覧CSV出力項目」など）に現行仕様が埋め込まれていた。

## 手順

### 0. 前提の確認

```bash
git status --short functions/ excel_to_html/output/   # 作業ツリーが汚れていないこと
```

再生成は既存の正本を上書きする。**比較元（git HEAD）が正しい状態であること**が全ゲートの前提。
未コミットの変更が残っている状態で始めない。

### 1. 台帳を先に更新する

書き直しも変換も、台帳を見て「出さない」を決める。**台帳が古いまま回すと、出すべきでないものが出る。**

```bash
python3 .cursor/skills/function-spec-html-render/scripts/detect_csv_format_only.py --unregistered
python3 .cursor/skills/function-spec-html-render/scripts/detect_superseded_specs.py
python3 .cursor/skills/function-spec-html-render/scripts/detect_phase2_specs.py
```

| 台帳 | 意味 | 出力への効き方 |
| --- | --- | --- |
| `functions/csv-format-only.tsv` | CSV/TSVの項目定義しか無いシート | 現行仕様を埋め込まない |
| `functions/embed-exclusion.tsv` | 同一機能Noの2枚目以降／機能まるごとPh2のシート | 現行仕様を埋め込まない |
| `functions/superseded_specs.json` | 刷新後は実装不要 | 「刷新後は実装不要」バナー |
| `functions/phase2_specs.json` | フェーズ2対応 | 「フェーズ1では実装不要」バナー |

**Ph2台帳の `scope` を必ず見ること。** `FUNCTION_SCOPE`（機能まるごとPh2）だけが埋め込み除外の対象で、
`ITEM_SCOPE`（項目だけPh2）は現行仕様を出す。2026-08-21、これを混同して 0302 のナビゲーション5件を
誤って除外しかけた。当該シートは正本に「本機能はフェーズ1対象」と明記されている。

**除外が効いたかの検算は埋め込みマーカー `Source:` で行う。** シート本文に「現行仕様」という語が
あるかで見ると、Excel本文にその語を含むだけのシート（0210 sheet-4）を誤検出する。

**候補は機械が出し、登録は人が確認して行う。** 未登録の候補が残っている状態で次へ進まない
（`--unregistered` は未登録があれば終了コード1）。

### 2. Markdown正本を正典から書く

**旧Markdownを要約してはならない。正典を読んで書く。**

2026-08-21、旧Markdown（＝ee実装のリバース）を唯一の入力にして要約させたところ、
32本すべてで捏造が出た。散文を散文へ圧縮する作業には照合先が無く、
「既定は10件」「同一在庫区分間」のように締めた一文が正しいか確かめる相手がいないためである。
実測された捏造: 業務条件の反転（同一店舗**内の**在庫区分間 → 同一在庫区分間）、
画面制御を受理条件にすり替え（ボタンを活性化する → 登録を受け付ける）、
留保を断定に（実装確認値 → 事実として列挙）、存在しない設計書名。

正典は区分で決まる（「合意した手順」の表）。旧Markdownは**論点の抜け漏れチェックリスト**として
だけ使い、記述の根拠にはしない。

書く範囲は **I/O とふるまい**に限る。画面・応答・ファイルに現れる入出力と、条件と結果だけを書く。
内部手順・実装手段・観測できない中間状態は書かない（②不具合調査で無駄な不具合を生む）。

落としてよいのは次だけ:
- 出力除外規約が「設計書に書かない」と決めた定型節（概要・本書で扱うこと・改訂履歴・
  ログ・セッション・Cookie・排他制御・試行制限・権限認可 ほか。正本は [[output-exclusion-policy]]）
- 実装手段の語（クラス名・メソッド名・DB物理名・翻訳キー・定数名）。
  **語を消すのであって、その語が説明していた挙動は残す。**

### 3. 書き直しのゲート（2本とも通すこと）

```bash
python3 .cursor/skills/function-spec-html-render/scripts/check_rewrite_quality.py      --book <書番>
python3 .cursor/skills/function-spec-html-render/scripts/check_rewrite_completeness.py --book <書番>
```

| ゲート | 見るもの | 落ちる条件 |
| --- | --- | --- |
| `check_rewrite_quality` | 捏造・様式 | メッセージIDや画面文言が減った／H2が3節以外／実装手段の語やDB物理名が残っている |
| `check_rewrite_completeness` | **本文の欠落** | 業務ロジックか入出力が無い／本文がほぼ全消し（既定8%未満） |
| `check_source_citation` | **出典** | P1/P2 の小見出しに出典が無い／出典が実在しない／出典の小見出しが本文に無い |

`completeness` は警告も出す（本文15%未満・情報語の保存率20%未満）。
**警告は自動で落とさない。** 較正の記録として: 正しく書き直せた m11-01 は 5,467字→1,225字（22%）で、
消えた語は「エラーフラッシュ」「セレクト」など**規約が意図的に落とす実装用語**だった。
要約は元の7〜8割を捨てるのが正常なので、縮小率だけでは良し悪しを決められない。
警告が出たものは人が抜き取りで中身を見る。

除外台帳（廃止・Ph2・CSV項目のみ）に載る機能は両ゲートとも免除される。
**免除したいなら台帳に登録する。ゲートの閾値をいじって通さない。**

### 4. HTMLを再生成する

```bash
cd excel_to_html && uv run python convert.py                 # Excel → HTML（全書）
python3 .cursor/skills/function-spec-html-render/scripts/integrate_function_docs_into_excel_html.py
python3 .cursor/skills/function-spec-html-render/scripts/build_orphan_group_html.py   # 入力xlsxが無い6冊
```

入力xlsx が無い Markdown起点の6冊（0000 / 0215 / 0216 / 0417 / 0508 / 0515）は
`build_orphan_group_html.py` の系統で作る。

### 5. 再生成のゲート

```bash
cd excel_to_html && uv run python verify.py
```

8種を見る: シート網羅／セル文言網羅／画像／遷移図／引き出し線の相互リンク／出力除外規約／
非表示シート／廃止仕様バナー。**`verify.py` は Excel→HTML の忠実性しか見ない。**
Markdown書き直しの欠落は手順3のゲートで止める。ここで代替できると考えない。

### 6. 台帳へ記録してコミットする

`design_impl_drift_report/html_regen_checklist_state.tsv` の `再生成` と `再生成備考` を更新する。
**備考には実際にやったことだけを書く。** 「書き直し済み」と書くなら手順3のゲートが通っていること
（2026-08-21 の台帳は 0204「40本中11本」「0205 未着手」のまま実態と食い違っていた）。

再生成の成果物は**その場でコミットする**。作業ツリーに置いたままにしない（手順0の前提が崩れる）。

### 7. 不具合調査をやり直す

正本が変わった書は、②不具合調査の判定が陳腐化する。
`design_impl_drift_report/design_audit/<書>/parts/` を破棄して inventory からやり直す。
観点と手順は [AUDIT_SCOPE.md](../design_impl_drift_report/AUDIT_SCOPE.md) /
[AUDIT_JUDGING_RULES.md](../design_impl_drift_report/AUDIT_JUDGING_RULES.md)。

## この手順が守らないもの

- **ゲートは「捨てられた」を捕まえるが、「正典の事実が落ちている」は捕まえられない。**
  必須節があって本文も残っていれば通る。落ちていないかは正典と突き合わせて見るしかない
  （第2段の全数点検がこれに当たる）。
  **行数や小見出し数を判断材料にしない。** 正典が規定する事実の量は機能ごとに違う。
- 台帳への登録判断そのもの（廃止か、Ph2か、CSV項目だけか）。機械は候補を出すだけ。
