M03-17 売上分析タグ登録/編集 / 商品管理 — 売上分析タグ登録/編集
概要
mtb_tag_sales_analysis（売上分析タグマスタ）を管理画面で新規登録・編集し、一覧・ページ送り・表示件数変更を同一画面上に並べて扱う機能である。ナビゲーション上の名称は翻訳キー admin.product.sales_analysis_management（確認値として「売上分析登録/編集」）。
本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。確認値は ec-cube-enterprise における売上分析タグ用ルートおよび対応した管理画面の一覧・編集処理、入力フォーム定義、マスタ本体 mtb_tag_sales_analysis とテンプレート tag_sales_analysis.twig、コントローラ基底での無効フォーム時応答および CSRF 検証、別画面および CSV により商品へタグを紐付ける経路とする。カスタマイズ区分は現行踏襲であり、現行挙動は pf-eccube3 を参照し、DB関連（テーブル名・列名・型・制約・関連）は ec-cube-enterprise を正とする。
対象はブラウザ経由の管理画面に限定する。
コントローラの処理名を本文の中心には置かず、本文ではルートbind名やSymfonyのルートnameの網羅は主説明としない。「利用者視点の入口」にHTTPメソッドとサイトルートからのパスパターンを書く。コード探索でbind名が必要なときだけ「調査補助」へ書く。
リニューアル移行時の扱い
現行（pf-eccube3）と移行先（ec-cube-enterprise）のDBスキーマを比較した結果は次のとおり。相違が判明した場合は ec-cube-enterprise 実装を正とする。
観点現行（pf-eccube3）移行先（ec-cube-enterprise）
売上分析タグ本体 mtb_tag_sales_analysis（id・name・` rank `） 同一スキーマ。name は varchar(64)、` rank ` は符号なし整数。
並び順キー ` rank ` 昇順 同一。sort_no への置き換えは無い。
商品紐付けの補助表 dtb_product_tag_sales_analysis 同一。移行先にも結合表として存在する。
注文明細紐付けの補助表 dtb_order_item_tag_sales_analysis 同一。移行先にも結合表として存在する。
削除方式 商品・注文明細との紐付けが無いとき物理削除 同一。論理削除列は持たない。
利用者視点の入口
入口URLエンドポイント期待されるふるまい
ナビ「売上分析登録/編集」 GET /{admin_route}/product/tag_sales_analysis 新規フォームと一覧が表示される。既定ページは 1、件数はセッションまたは 10。
一覧の ID・名称または「編集」 GET /{admin_route}/product/tag_sales_analysis/{id} 当該行がフォームに載る。ページャは編集モード向けルートに切り替わる。
一覧のページリンク（新規時） GET /{admin_route}/product/tag_sales_analysis/page/{page_no} セッションのページ番号が更新される。
一覧のページリンク（編集時） GET /{admin_route}/product/tag_sales_analysis/{id}/page/{page_no} 同上。パスの id は編集中の主キー。
表示件数セレクト変更 現在ページの GET にクエリ page_count=N を付けて遷移 セッションの件数が更新され、N が選択肢にある場合のみ（テンプレート上は 10, 50, 100, 300, 500, 1000, 2000, 10000, 12000）。
「登録」ボタン POST …/product/tag_sales_analysis/store または …/store/{id} 妥当なら保存し成功メッセージののち一覧 GET へリダイレクト。否なら同画面にエラーが出る。
「削除」（確認モーダル経由の DELETE） DELETE /{admin_route}/product/tag_sales_analysis/{id}/delete 紐付けが無ければ行が消える。あれば削除されず説明フラッシュとなる。
フォーム送信による登録または更新。id がパスにある場合は当該行を更新対象として束ねる。 POST /{admin_route}/product/tag_sales_analysis/store フォーム送信による登録または更新。id がパスにある場合は当該行を更新対象として束ねる。
フロント挙動
観点内容
表示要素 親フレームのタイトルは翻訳キー admin.product.product_management（確認値として「商品管理」）。見出し下は admin.product.tag_sales_analysis（確認値として「売上分析タグ」）。メニューのハイライト配列は product と tag_sales_analysis。上半分カード見出しは編集時「編集」、新規時は新規登録系ラベル。入力は「名称」「並び順」の 2 欄のみ。下半分カードヘッダ右に表示件数セレクト。表は ID（リンク）、名称（リンク）、並び順、編集ボタン、削除ボタン。フッタの変換領域に「登録」ボタン（form="form_tag_sales_analysis" で上半分フォームへ送信）。
JS 挙動 .js-page-count の change で現在 URL に page_count を付け替えフルページ遷移する。削除ボタンはアンカーに data-method="delete" 等があり、共通スクリプトが DELETE と CSRF を送る実装になる。
CSS・レイアウト ページ見出し用の細い見た目調整のみ。一覧は縞模様テーブル。Bootstrap 4 横型フォームテーマ。
モーダル・ポップアップ 削除前に共通の削除確認モーダル文言（admin.common.delete_modal__message。名称が埋め込まれる）。
処理フロー
画面を表示する（GET）
管理画面の共通認証を通過する。ルートによって既存エンティティを読み込むか、読み込めないときは（主キーの無い新規ケースのみ）まっさらな行インスタンスをフォームデータとする。クエリまたはパスの page_no から現在ページ番号を決め、admin.product.tag_sales_analysis.page_no に書き込む。欠けるときはセッション既存または 1。クエリの page_count があれば整数化して admin.product.tag_sales_analysis.page_count に書く。無いときはセッション既存または 10。リポジトリのクエリビルダでエイリアス t とし、rank 昇順の一覧を、アプリケーションのページネータで上記ページ番号・件数に分割する。tag_sales_analysis.twig でフォームの action は新規なら無修飾 store、編集なら同一主キーを付けた store URL とする。
登録または更新する（POST m03-13_admin_product_product_tag_sales_analysis_store）
GET と同様のエンティティの起点でフォームを生成し、handleRequest で POST をとる。送信が無い、または検証に失敗した場合、フラッシュに admin.register.failed を積み（確認値として「登録できませんでした。」）、セッションにあったページ番号と件数で一覧を組みなおして同テンプレートで返す。このとき無効フォームがあるとコントローラ基底の実装により、通常は HTTP ステータス 422 を返す。検証が通ったデータを persist し、flush する。単一トランザクション境界はDoctrineの単位に従う（明示トランザクションは張らない実装）。flush が一意制約違反（永続化層が検知）で終わった場合、フラッシュに admin.error.non_unique を積み（確認値として「値が重複しています。」）、一覧を組みなおした同テンプレートを返す。成功時、admin.register.complete を積み、m03-13_admin_product_product_tag_sales_analysis へ HTTP リダイレクトする。リダイレクトパラメータに保存後主キーを渡すため、生成 URL はクエリ id が付く（パス側の {id} は一覧トップには無く、画面は新規モード側のリスト表示に落ちやすい。実装確認値）。
削除する（DELETE）
CSRF が要件を満たすか共通処理で検証し、無効なら例外でアクセス拒否（HTTP 403）となる。売上分析タグ行にひも付く商品が 1 件でもあるなら、admin.tag.delete.failed で名称を埋めフラッシュして一覧へリダイレクトする（確認値として「商品で使用されているため、当該名称のタグは削除することができません。」）。商品側にひも付きが無くとも、注文明細との結合があるなら、admin.order_tag.delete.failed をフラッシュして一覧へリダイレクトする（確認値として「購入済の商品で使用されているため、当該名称のタグは削除することができません。」）。両方とも結合無しなら削除予約後 flush し、admin.common.delete_complete を積んで GET m03-13_admin_product_product_tag_sales_analysis へリダイレクトする。
集計条件
本機能では一覧総件数の算出以外に業務寄りの独自集計は行わない。ページャライブラリが総件数を求めるのみである。
指標集計の要点
一覧総件数 mtb_tag_sales_analysis 全件を rank 昇順として対象にし、page_count で分割する。
登録・更新時の判定順序
順序判定結果
1 フォームが送信済みか、かつ項目検証が通るか 否ならエラーフラッシュと再描画。
2 persist と flush 一意制約違反ならエラーフラッシュと再描画。
3 上記すべて成功 成功フラッシュと一覧へのリダイレクト（クエリ id 付き）。
業務ルール・計算
項目内容
一覧の並び rank の昇順。一覧上にドラッグ並べ替えの UI は無い。
並び順の意味 rank が小さい行がクエリ順で先頭に来る。
本機能では加算税率や売上集計などの業務計算を行わない。
入力項目
項目名必須／任意最大長初期値保存先・扱い
名称 必須 64（入力 maxlength と検証および列 varchar(64) に一致する実装値） 新規は空欄、編集は mtb_tag_sales_analysis.name mtb_tag_sales_analysis.name。空白不可（NotBlank）。送信キーは tag_sales_analysis[name]。
並び順 必須 整数・1 から 65535（SMALLINT UNSIGNED と Range 検証の実装値） 編集時は現行 DB 値。新規モードでの画面初期はフォームウィジェットの空表示に従う mtb_tag_sales_analysis.rank（Doctrine により列名 ` rank ）。空白不可、Range(min=1,max=65535)。HTML 入力に min/max。送信キーは tag_sales_analysis[rank]`。
エッジケース
ケース扱い
存在しない id で編集 GET ルート引数のマスタ読み込みに失敗し 404 となる。
DELETE の CSRF 不正 アクセス拒否（HTTP 403）。
名称の重複で DB が一意を返す フォーム側の単純検証より後に検知され、admin.error.non_unique と再描画。
商品にだけ紐付き、まだ注文明細に載っていない 削除処理は実行されず admin.tag.delete.failed と一覧へリダイレクトする。マスタ行は残る。
注文明細側の関連のみが残っている 注文明細との結合があると判定されれば admin.order_tag.delete.failed と一覧へリダイレクトする。
データ整合性
観点内容
一覧とフォーム 一覧は全件クエリからのページネーション結果。フォームはルート id の 1 行または新規用の未保存インスタンス。同一画面でもデータ起源が別になる。
商品側の関連 dtb_product_tag_sales_analysis が 1 件でもあれば当該タグを削除しない。一覧の内容と DB は GET 読み込み時点での整合。
注文明細側の関連 dtb_order_item_tag_sales_analysis が 1 件でも連結されていれば削除しない。
同時更新 楽観ロックは持たない。後続の UPDATE が単純に上書きされる。
API/バッチ結果
本機能では外部 API を呼ぶ処理や別バッチによる更新を実行しない。
入出力
種類内容
入力 GET のページや件数、編集主キー。POST のフォームおよび CSRF トークン。DELETE と CSRF。
成功時出力 リダイレクト先の一覧 HTML と成功フラッシュ。または DELETE 後の一覧。
失敗時出力 一覧付きフォーム HTML とエラー表示、またはフラッシュのみのリダイレクト応答。
副作用 mtb_tag_sales_analysis の INSERT/UPDATE または単一行 DELETE（条件付き）。セッションのページ状態変更。フラッシュメッセージ。
DBカラム
本機能が直接読み書きする主な列は次のとおり（インデックスと一意はマイグレーションとスキーマを参照）。

エラー内容処理

試行制限

ログ・監査

セッション
本機能におけるセッション
観点内容
GET 表示時 admin.product.tag_sales_analysis.page_no と admin.product.tag_sales_analysis.page_count を更新する。
POST 側 一覧再構築に同キーを読むのみで、入力値本体はフォームオブジェクト側に載る。

Cookie

排他制御・トランザクション
当画面では明示トランザクションや楽観バージョン列は利用しない。flush がコミット単位となる。並行編集では後続保存が単純上書きしうる。
