# レビュー・チェックリスト（codex用）

レビューは **codex（実ソース読取専用）のみ**で行う（2026-07-21 ユーザー指示。fable5 は使わない）。
以下を **実ソースを根拠に** 検証する。推測で埋めない。根拠が取れないものは確定しない。

> **二段構えが必須**: 監査は「捏造を摘発せよ」の敵対バイアスで走らせるため指摘が過剰に出る。
> 実績で **fabrication 2件中1件 / wrong_en 37件中28件 / wrong_meta 187件中55件が偽陽性**だった。
> 監査結果は**そのまま適用してはならない**。逆バイアス（既定=refuted）の二次検証を必ず挟む。

## A. 捏造ゼロ（最優先）

- [ ] 各行の `メッセージ内容` の固定リテラルは、`根拠(file:line)` の実ソースに逐語で存在するか。
- [ ] ロケール解決した文言は `messages.ja.yaml` / `validators.ja.yaml` の当該キーの値と一致するか。
- [ ] 実ソースに存在しない文言（言い換え・敬体化・要約）が混入していないか。→ あれば削除/是正。
- [ ] **断片になっていないか**。`validate_messages.py` の検証は `grep -F` の**部分一致**なので、
      より長い正しい文言の一部を切り取った断片が PASS してしまう。
      実例: `admin.event.entry.paying_mem`（実キーは `...paying_member_customer_not_registered`）が
      前方部分一致ですり抜けていた。→ `check_literal_strict.py`（境界付き一致）まで通すこと。

## B. 抜け漏れ（網羅性）

- [ ] 当該機能の controller/テンプレの add(Success|Error|Warning|Info|Danger) を全て拾えているか。
- [ ] Form制約 `message` と JS `confirm/alert` を拾えているか。
- [ ] twig 本文の `{{ 'key'|trans }}` 直描画を拾えているか（フロント・管理画面ともこれが主流）。
- [ ] PHP例外 throw / JsonResponse 直書き / twig ハードコード和文（エラー系）を拾えているか。
- [ ] 一覧にあって設計書の表に無いメッセージを、表へ新規行として追記したか。

## C. 未解決の確定

- [ ] `variable`（`$message` `$e->getMessage()` `$res['error']` 等）は、実際に代入され得る文言を
      実ソースで追い、逐語literalが取れる場合のみ確定したか。
- [ ] 実行時可変で一意に絞れない行は、候補を **「候補A ／ 候補B」** で全列挙したか
      （各候補はソース逐語。単一に絞る／散文で説明するのは違反）。
- [ ] `other`（`implode`・連結）は組み立て結果を実ソースで確認したか。
- [ ] `key_unknown`（YAML未在キー）は本当に未定義か確認したか。
      **未定義なら Symfony はキー文字列をそのまま描画する**＝それが表示文言で確定（捏造ではない）。

## D. 列の妥当性

- [ ] `要素`（操作トリガー）は該当ルートを叩く実UI（ボタン/リンク/フォーム）と一致するか。
      到達不能（デッドルート・未参照ハンドラ・オープナー非在のモーダル）なら「該当なし＋根拠」と書く。
- [ ] `トリガー（条件）` は controller の分岐条件と一致するか。
      **多候補行では全候補を覆っているか**（1つの候補しか覆わない条件は誤り）。
- [ ] `種別`・`どこに`・`要素(表示)` はテンプレの実描画（トースト/モーダル/インライン）と一致するか。
      統制語彙は TERMINOLOGY.md。既定値のまま検証されていない行が多いので実テンプレを必ず開く。
- [ ] `後続処理` は `return`（redirect先ルート/render）と一致するか。
- [ ] `メッセージ内容(英語)` は**当該日本語と同じキー**の英語か。
      ja が複数キーに一致する行で**別キーの英語を流用**する事故が起きる（grep ゲートは通ってしまう）。
      実例: `form_error.numeric_only`（正 `Entry must be numbers.`）に
      `admin.setting.shop.delivery.fee.invalid` の `Please enter with numbers.` を充てていた。

## E. 機能紐付け・埋め込み

- [ ] `EE-JS-*` / `EE-<area>-*` の未割当行を、正しい機能へ紐付けたか（テンプレ→ルート→機能）。
- [ ] 埋め込んだ `メッセージID` は一覧に実在し、表の日本語文言と一致するか。
- [ ] 静的ラベル等スコープ外の行に誤ってIDを付けていないか（`—` が正しい）。
- [ ] **API設計書に管理画面のメッセージが紛れていないか**（実例: a02-05 に CSV取込のフラッシュが2件）。
      根拠パスが `Controller/Admin/...` なのに A系IDになっている行は誤割当を疑う。
- [ ] 設計書mdに**退役IDを文字列で書いていないか**。`validate --check-embed` が
      「[D]md埋め込みIDが一覧に無い」で FAIL する（ID正規表現が本文全体を走査するため）。

## F. 二次検証（逆バイアス）— 監査結果を適用する前に必ず

- [ ] **既定は refuted**。実ソースを読んで動かしがたく正しいと確認できた指摘だけ confirmed にしたか。
      判断がつかないものも refuted。
- [ ] confirmed のものだけ、列ごとの是正値を統制語彙に沿って出したか。
- [ ] 以下の**却下ガード**を適用したか（confirmed でも適用しない）:
  - **内部用語の混入** — 「セッションの有効期限が切れているとき」→「CSRFトークンが無効なとき」等。
    設計書は利用者視点で書く規約なので改悪。
    ただし**その語が当該行の文言に実際に出る**なら画面表示語なので許可。
  - **多候補行の条件の狭め** — 列挙を含まない一般化への置換は却下。
  - **文言(ja/en)の変更提案** — 監査対象外の列なので常に却下。

## G. 偽陽性ガード（これらを違反と判定したら誤り）

- [ ] yaml 未定義でも、根拠ソース(.php/.twig/.js/.en.twig)に逐語あれば捏造ではない。
- [ ] `vendor/symfony/*/Resources/translations` の同梱訳も実表示される正当なソース
      （xlf は `<source>`=英語 / `<target>`=日本語 の対で、これも正当な ja/en 対応）。
- [ ] `%name%` `{{ limit }}` `%s` の**保持は正**。実行時値へ置換していたら違反。
- [ ] 「候補A ／ 候補B」の併記は実行時可変行の**規約**。
- [ ] ja/en を切り詰めて判定しない（「途切れ＝捏造」の誤判定になる）。

## H. 実行ゲート（すべて通ること）

```bash
S=.codex/skills/hareruya-message-inventory/scripts
python3 $S/validate_messages.py --check-embed   # 捏造ゼロ(部分一致)＋ID整合
python3 $S/check_literal_strict.py              # 断片でないか(境界付き一致)
python3 $S/check_en_pairing.py                  # 英語が同一キーの対か
python3 $S/check_evidence_anchor.py             # 根拠が指す場所に文言/キーがあるか
```

> 正本 `message_inventory.tsv` は `"\t".join(cells)` の**生タブ区切り**で RFC4180 ではない。
> `csv.DictReader` で読むと `"` 始まりの値の引用符が食われる（実害5セル）。
> 読むときは必ず `lib_messages.read_master_rows()` を使う。
