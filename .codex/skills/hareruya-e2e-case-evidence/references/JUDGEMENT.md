# 切り分け・判定・記録・報告

## 切り分けの手順（不合格・未判定の1件ごと）

```bash
cd e2e
python3 tools/evidence_judgements.py todo <機能ID>     # 判定が要るケース（不合格・未判定・注記のある合格）
```

1. `evidence/<機能ID>/<テストID>/evidence.html` を開き、落ちた場面の画面・確かめた項目・エラー・注記を読む。
2. 落ちた場面のひとつ前の画面で、手順が正本どおりに行われたか（入れた値・押したボタン・開いた画面）を見る。
3. 次の順に疑う。
   1. **E2E の不備か**: セレクタの取り違え・読み込みを待たずに読んだ・シードの画面操作の誤り・決め打ちの値。アプリの実ソースと画面で確かめる。不備なら `e2e/` を直して、そのケースだけ流し直す（`run_evidence.sh <機能ID> <番号>`）。直したことは記録に書く。
   2. **アプリが設計・正本と違うか**: 設計書の写し（`datapattern/units/<機能ID>/design.txt`）の行番号で、期待結果の根拠を確かめる。違えば不合格（実装差異 など）。何も直さない。
   3. **正本の問題か**: 手順が画面で実行できない・期待結果が設計書と食い違う・前提が他のケースのシードと干渉する。手順だけの誤りで設計書が画面と合うなら裁定で直す（RULES.md の4）。それ以外は直さず、判定に書き、判断待ちに挙げる。
   4. **環境か**: 画面が開かない・システムエラー・時間切れ・前回の残りデータ。未判定（環境）。環境が戻ったら流し直す。
4. 合格でも注記があるもの（手順の一部が画面で実行できず DB で確かめた、正本にない値を補った など）は、条件付きかを決める。

## 判定の値

判定の表 `e2e/review/judgements/<機能ID>.tsv`（列: テストID・判定・区分・理由・対象の実施日時・判定日・記録）。`tools/evidence_judgements.py` で書く（手で書くなら列の形を守る。`evidence_check.mjs` が検査する）。

| 判定 | 区分 | 使うとき | 合否の一覧に載るか |
| --- | --- | --- | --- |
| 合格 | （空） | 正本どおりに操作し、期待結果をすべて確かめて通った | 載る（合格） |
| 合格 | 条件付き | 正本の外の補い（シードの一部を画面で確かめるだけにした など）の上で通った | 載らない |
| 不合格 | 実装差異 | アプリの動きが設計書・期待結果と違う | 載る（不合格） |
| 不合格 | 設計と実装の差異 | 設計書が触れていない画面の作り（ブラウザの入力チェックが送信を止める など）で期待結果にならない | 載る |
| 不合格 | 設計書の中の食い違い | 設計書の Excel 由来の部分と現行仕様の節などが食い違い、期待結果がその片方に立つ | 載る |
| 不合格 | 正本の問題 | 手順が画面で実行できない・期待結果の側の誤り（裁定で直せないもの） | 載る |
| 不合格 | 条件付き | 正本の外の補いの上で落ちた（補いが原因かもしれない） | 載らない |
| 未判定 | 環境 | 環境の停止・遅さ・残りデータで、合否が出なかった | 載らない |
| 未判定 | ハーネス不良 | E2E の不備で止まり、まだ直して流し直していない | 載らない |
| 未判定 | 開発用データ | 手元の DB の開発用データのせいで正本の前提が成り立たない | 載らない |
| 未判定 | 正本の問題 | 正本の前提のせいで合否を出せない（判断待ち） | 載らない |
| 未判定 | シード | シードが作れず止まった（原因が E2E・環境のどちらとも決まらない） | 載らない |

- ブラウザの入力チェックで送信が止まるケースの区分は、機能によって「設計と実装の差異」と「正本の問題」が混ざっている（HANDOFF_codex.md 4章の19。依頼者の判断待ち）。新しく判定するときは「設計と実装の差異」にそろえ、判断待ちに挙げる。
- 理由は業務の言葉で1〜2文。詳しい説明・根拠の行番号は記録（MD）に書く。
- 判定は「どの実施への判定か」を実施日時で持つ。流し直すと判定は古くなり、自動判定に戻る。流し直したら判定し直す。
- 判定で自動判定を覆せるのは「未判定」へ下げるときだけ。合格と判定できるのは自動判定が合格の実施、不合格と判定できるのは自動判定が不合格の実施だけ（落ちた実施を「E2E の不備だったから」と合格にしない。直して流し直す）。道具と検査がこれを止める。

## 書き方

```bash
# 注記の無い合格をまとめて判定する（不合格・未判定・注記のある合格は書かない）
python3 tools/evidence_judgements.py accept-clean <機能ID> --record e2e/review/<機能ID>_progress_<日付>.md
# 1件ずつ
python3 tools/evidence_judgements.py set <機能ID> IT-<機能ID>-016 不合格 設計と実装の差異 "名称が空だとブラウザの入力チェックが送信を止め、新規入力欄へ戻らない" --record e2e/review/<機能ID>_progress_<日付>.md
# 検査
node tools/evidence_check.mjs --strict <機能ID>
# 合否の一覧（playwright_cases.tsv）へ
python3 tools/evidence_judgements.py sync <機能ID>            # 差分を見る
python3 tools/evidence_judgements.py sync <機能ID> --apply    # 書き込む
nice -n 19 ionice -c3 python3 ../integration_test/casegen/build_all_test_cases.py
```

- `sync` は既にある行を消さない。いまの判定が載せる条件に当たらない行（前は合格だったが、いまは条件付き など）は注意として出る。消すかは依頼者に聞く。
- `sync` は正本が変わったケースを飛ばす（流し直してから）。

## 記録（MD）の形

`e2e/review/<機能ID>_progress_<日付>.md`。前回の記録は消さずに新しい日付で書く。

```markdown
# <機能ID> <機能名> — <何をしたか>（<日付>）

## 振り分け
| ケース | 実装 | 理由 |
（実装しないケースは理由。DB での準備・外部の試験環境・入力ファイルが決まらない など）

## 結果
合格 n・不合格 n・未判定 n・スキップ n（1件ずつ流した結果の合算／通しの結果、のどちらか）。DB の状態（ダンプに戻した日時など）。

| ケース | 結果 | 区分 | 理由（根拠の設計書の行番号） |

## E2E 側で直したこと
（何を・なぜ。流し直した結果）

## シードでの解釈
（シード表から一意に決まらず、こう解釈した値）

## 再実行の制約
（同じ DB で流せないケースと理由）

## 判断待ち
（依頼者に決めてもらうこと）
```

## 報告の書き方（依頼者へ）

- 最初に結果: 「<機能ID> の n件を流し、合格 a・不合格 b・未判定 c」。通しか分割の合算か。
- 不合格1件ごとに一行: 実装の問題か・正本の問題か・基盤の問題か。
- 正本とシード表を直していないこと。直したら裁定の項目（E01〜）と依頼者の決定。
- 基盤（e2e/）を直したら、何をなぜ直したか。
- 確かめていないことは「未確認」と書く。
- エビデンスの場所: `e2e/evidence/<機能ID>/index.html`、固めたもの（`tools/evidence_pack.sh` の出力のパス）。
