# 流し方とエビデンス

## 流す前に確かめること

1. ほかの Playwright が流れていないか: `pgrep -af "playwright test"`。流れていれば終わるのを待つ（`run_evidence.sh` はロックを待つが、待ちが長いと止まる）。
2. 環境が動いているか: `docker ps`（ec-cube-enterprise-ec-cube-1 が healthy）と、ログイン画面が開くか。`run_evidence.sh` も流す前に確かめ、応答しなければ止まる。
3. DB の状態: `e2e/HANDOFF_codex.md` の「手元環境の注意」の先頭が、いまの DB。ダンプに戻したあとか、空から作ったか、前回の実行のデータが残っているか。
4. 再実行の制約: `e2e/review/<機能ID>_progress_*.md` に「同じDBでは流さない」と書かれたケース（固定の商品コードが残るもの など）は、依頼者の許可なしに流さない。`run_evidence.sh <機能ID> <番号…>` で外して流す。

## 流す

```bash
cd e2e
tools/run_evidence.sh <機能ID> --dry-run           # 流すケースと spec
tools/run_evidence.sh <機能ID>                     # テストのあるケースを全部
tools/run_evidence.sh <機能ID> 003 007             # 番号で
tools/run_evidence.sh <機能ID> --todo              # エビデンスが無いか、正本が変わったケースだけ
tools/run_evidence.sh <機能ID> --failed            # いま合格でないケースだけ
```

- 1件ずつ `tools/pw_run.sh` を呼ぶ（ロック・ログ `.runs/<機能>-<番号>.log`・結果 `.runs/<機能>-<番号>.json`）。1件のエビデンスは終わるたびに書かれるので、途中で止めても流したぶんは残る。`--todo` で続きから。
- 1件に1〜10分かかる（シードを画面から作るため）。担当は `run_evidence.sh` を裏で流し（コマンドの制限時間を超えるため）、終わりの知らせを待つ。見張りのループを回さない。
- 終了コード: 0＝流し終えた（合否は問わない）、1＝エビデンスの検査で誤り、3＝環境が応答しない・ロックが取れずに止めた（残りのケースを出す）、4＝流したのにエビデンスが書かれなかったケースがある（`.runs/<機能>-<番号>.log` を見る）。
- 撮り方の切り替え: `E2E_EVIDENCE=viewport`（見えている範囲だけ）・`off`（撮らない。キャプチャが動きに影響していないかを切り分けるときだけ）。`E2E_EVIDENCE_FORMAT=jpeg` で小さくなる。
- 共有の開発環境で流すのは依頼者の了承があるときだけ（`e2e/README.md` の「環境の切り替え」）。

## エビデンスの中身

`e2e/evidence/`（git の対象外）。

```
evidence/
  index.html・index.md・results.tsv      全機能の一覧
  <機能ID>/
    index.html・index.md・results.tsv    機能の一覧（結果・判定の状態・落ちた場面・正本との一致）
    history.tsv                          実施の履歴（流すたびに1行。消さない）
    <テストID>/
      evidence.html・evidence.md         ケース1件のエビデンス
      result.json                        機械が読む記録
      01_開始時.png・02_手順1.png …        画面
      Playwrightの画面_N.png・trace.zip   落ちたときだけ
```

ケース1件のエビデンスに出るもの:

- テストID（一覧のテストIDが違えば併記）・結果・自動判定・正本との一致・観点ID・実行区分・出典・実施日時・所要・環境・E2E とアプリのコミット・テストコードの位置・使用シード
- 期待結果に対する実際の状態（文）。例: 「期待結果と違う。「登録ボタンを押したあとの応答」は＝ 403を期待したのに対し、実際は302。」「期待結果のとおり。確かめた2項目すべてが期待どおりだった（…）。」。手順や事前準備で止まったときは、どこで止まって期待結果を確かめていないか
- 事前準備の文と、控えた番号（〔…〕の呼び名と値）
- 手順1の前の画面、手順ごとに「正本の手順の文（控えた番号つき）・済／失敗・画面」、期待結果の文・確かめた項目ごとの「期待」「実際の状態」「合否」・画面
- 注記（手順の注記・シード作成時の問題）、スキップの理由、エラー（Playwright の出力）と、落ちたときの画面・操作の記録

自動判定の決め方（`lib/evidence_reporter.ts`）:

| Playwright の結果 | どこで落ちたか | 自動判定 |
| --- | --- | --- |
| 合格 | — | 合格 |
| スキップ | — | スキップ（理由つき。共有環境で DB 確認が無い など） |
| 失敗 | 手順 n・期待結果 | 不合格 |
| 失敗 | 事前準備（シード）・手順1の前（ログインなど）・全手順のあと（基盤の検査） | 未判定 |
| 時間切れ | どこでも | 未判定 |

自動判定は入口にすぎない。不合格・未判定は人が切り分けて判定する（JUDGEMENT.md）。

正本との一致: エビデンスを取ったときのケースの中身（使用シード・事前準備・手順・期待結果・実行区分）の指紋と、いまの `cases/` を比べる。裁定やパイプラインの流し直しでケースが変わると「正本が変わった（要再実行）」になる。同じように、テストの spec ファイルの指紋が変わると「テストコードが変わった（要再実行）」になる。どちらも古いので流し直す（`--todo`）。
画面の部品（`pages/`）・シード（`seeds/`）・基盤（`lib/`）やアプリの変更は指紋に入らない（入れると全ケースが古くなる）。それらを直したら、影響するケースを番号か `--failed` で流し直す。エビデンスには E2E とアプリのコミットが残る。

## 一覧・検査・固め

```bash
node tools/evidence_index.mjs [機能ID…]          # 一覧を作り直す（判定の表を書き足したあとなど）
node tools/evidence_check.mjs [--strict] [機能ID…]  # 誤りで終了コード1。--strict は注意でも1
tools/evidence_pack.sh [機能ID…]                 # evidence/_packs/evidence_<機能>_<日時>.tar.gz（trace は含めない）
```

`evidence_check.mjs` が見るもの: 合格なのに手順・期待結果が済でない／確かめが無い・落ちている、画面が1枚も無い（理由も無い）、判定の表の値と列、正本が変わった、要判定・判定が古い、テストがあるのにエビデンスが無い、合否の一覧と判定の食い違い。

## 片付け

- `.runs/` は実行のたびに `results-<機能>-<番号>/`（trace を含む）がたまり大きくなる（10/26 時点で 12GB）。消すときは依頼者に聞く（過去の実行の手がかりを含む）。
- 殺した実行のブラウザ（chrome-headless-shell）が残っていないか `pgrep -af chrome-headless` で見る。
