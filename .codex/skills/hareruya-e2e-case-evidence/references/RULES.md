# 守ること（依頼者の決定。出どころつき）

迷ったら、ここに無いことは自分で決めずに依頼者に聞く（報告の「判断待ち」に挙げる）。

## 1. テストケースが正（2026-07-23・2026-10-14）

- 正本は `integration_test/casegen/cases/<機能ID>_test_cases.tsv`（11列・1行1ケース）と `<機能ID>_seed_data.tsv`（7列・1行1シード）。`cases/` を直接書き換えない（パイプラインの流し直しで戻る）。
- テストが落ちても、期待結果・確かめ（expect）を実装に合わせて変えない。アプリ（ec-cube-enterprise）も変えない。落ちたこと自体が結果（不具合・仕様の乖離を見つけた）。
- 直してよいのは `e2e/` の中の、正しく観測できていない不備（セレクタの誤り・待ち方・シードの画面操作の誤り）だけ。
  - 見分け方: 「テストが実際の動きの違いを見つけた」なら何も変えず不合格として記録する。「テストの側が正しく見られていない」なら e2e/ を直す。

## 2. 期待結果を弱めない・偽の合格を作らない（2026-10-14・codex R2）

- 手順が画面で実行できないとき（項目が無い・ボタンが押せない など）:
  - 期待結果が DB などで確かめられるなら、手順の注記（`手順の注記`）を残して続けてよい。
  - 期待結果が「遷移すること」「メッセージが出ること」など操作の結果を見るものなら、**不合格**。操作をせずに元の画面を見て合格にしない（2巡目のレビューで、この偽の合格を4件指摘された）。
- 期待結果に確かめる項目が複数あるときは `expect.soft` で全部確かめる（1つ落ちても残りがエビデンスに出る）。
- 「〜が無いこと」「0件であること」を確かめるときは、対象が本当に表示される状態（読み込みが済んだ・検索が流れた）で数える。読み込み前に数えて0件で合格にしない。

## 3. テストデータは画面から作る（2026-10-09・2026-10-23）

- シードはシード表の投入方法のとおりに画面操作で作る。SQL・フィクスチャで入れない。DB は確かめのための参照（`lib/db.ts` が読み取り専用のトランザクションで流す）だけ。
- 画面が振る番号（ID など）は `notes.set("〔…〕", 値)` で控え、ケースでは呼び名で引く。シード表が控えると定めた呼び名だけを控える。
- 共有可のシードは「あれば使い、無ければ作る」。何度流しても同じ状態になるように書く。ケース専用のシードは毎回作る。
- シード表に無い清掃・再利用を勝手に足さない。固定の商品コードなどが前回の実行で残り、シードが止まるときは、流し直してよいか（残りを画面から消してよいか）を依頼者に聞く。
- DB での準備が要るシード（投入方法が「DB」「画面+DB」）を使うケースは、依頼者の指示があるまで着手しない。

## 4. 正本の手順を直してよい唯一の場合（2026-10-16）

- 設計書の写し（`integration_test/casegen/datapattern/units/<機能ID>/design.txt`）の行番号で、**設計書が画面と合っていて、ケースの手順だけが誤っている**と示せるとき、手順を直す。期待結果は直さない。
- 設計書が操作の結果を定めていない・設計書と画面が食い違うときは直さない（不合格のまま報告）。
- 直し方: `integration_test/casegen/datapattern/conflicts/rulings.tsv` に裁定の行（項目は E01 から順。処置「手順」、置換「旧⇒新」、根拠に設計書の行番号）を足し、`apply_rulings.py` → `build_all_test_cases.py` → `precond/gate_precond.py --all`（どれも `nice -n 19 ionice -c3` で1本ずつ）。
- 手順を直して前提（シード）が足りなくなるときは、シードの追加は依頼者の決定を待つ（決まったら `added_seeds.tsv`）。
- 直したら、エビデンスは「正本が変わった（要再実行）」になる。流し直してから判定する。

## 5. 実行の決まり（2026-10-17・2026-10-21・2026-10-22）

- Playwright は全体で1本（`test-results` を取り合うと結果が壊れる）。流すのは `e2e/tools/run_evidence.sh` か `e2e/tools/pw_run.sh`（どちらもロックを取る）。調べるための一時テストも `flock e2e/.runs/playwright.lock npx playwright test …`。
- 担当（サブエージェント）は同時に2人まで（1人が流している間にもう1人が実装する）。ワークフローで多数を並べない。
- 手元のマシンはメモリ・CPU がすぐ上限に届く。パイプラインは `nice -n 19 ionice -c3` で1本ずつ。リポジトリ全体の検索をしない。殺した実行のブラウザ（chrome-headless-shell）を残さない。
- 共有の開発環境（`E2E_ENV=dev` や localhost 以外）では、依頼者の了承なしに流さない。データを消すシードを持つケースは、共有環境では基盤が自動で飛ばす。
- DB をダンプに戻す・アプリのコンテナを起こし直すのは依頼者の判断（自動の許可では止められる。依頼者が `!` で流す）。戻したら、コンテナを起こし直して healthy になってからログインを確かめる（キャッシュに古いマスタが残る）。

## 6. 論理名（2026-08-19〜）

- テスト名・注記・確かめのメッセージ（`expect(x, "ここ")`）・記録・判定の理由は業務の言葉で書く。テーブル名・カラム名・ルート名・翻訳キーを書かない。併記も書かない。
- 物理のままでよいのは、セレクタ・フォーム項目の id/name・HTTP のパス・SQL の中・`file:line` の出典。エビデンスのエラー出力（Playwright の出力）にセレクタや URL が出るのはそのままでよい。

## 7. 記録（2026-07-23・2026-10-20）

- 結果は TSV と MD の両方に残す。TSV＝判定の表 `e2e/review/judgements/<機能ID>.tsv`（1ケース1行・どの実施への判定かを実施日時で持つ）。MD＝`e2e/review/<機能ID>_progress_<日付>.md`（振り分け・判定の理由・判断待ち）。
- 合否の一覧 `integration_test/casegen/playwright_cases.tsv` に載せるのは、条件の付かない合格と、正本の外の補いの上に成り立たない不合格だけ（`evidence_judgements.py sync` がこの条件で選ぶ）。シードで止まった未判定は載せない。
- 一覧（`all_test_cases.tsv`）の検証方法が「Playwright」になるのは合格のケースだけ（`build_all_test_cases.py` が決める）。
- 一覧の末尾の実施者・実施日・実施結果は、`build_all_test_cases.py` が playwright_cases.tsv から埋める（依頼者決定 2026-10-26。実施者「E2E（Playwright）」、実施日は判定の表の対象の実施日時か記録のファイル名の日付）。人が書いた値は上書きしない。備考と、人が書いた行は手で書く。一覧のセルを直接書き換えない（作り直しで決まる）。
