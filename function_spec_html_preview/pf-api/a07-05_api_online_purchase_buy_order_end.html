API ネット買取管理 — ネット買取注文の査定終了処理

概要

買取アプリ（MTGバイヤー）が、ネット買取注文の査定を終え、査定結果（買取明細とステータス）を確定するためのAPIである。pf-api（買取連携用のAPIアプリケーション）が提供するJSON APIで、受注IDで対象を特定し、送られた明細から買取代表カード・個別入力商品を登録・更新・削除し、合計額と買取受注ステータスを更新する。ステータスが変わった場合はステータス履歴も登録する。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。確認値はpf-apiのネット買取注文の査定終了処理、ルート定義（config/routes.yaml）、ネット買取受注を扱うエンティティとリポジトリ、入力検証用のエンティティと制約、共通の認証処理を正とする。本機能のカスタマイズ区分は現行踏襲であり、挙動はpf-apiの実装を参照し、DB関連（テーブル・列）の記述はec-cube-enterpriseを正とする。

対象はJSON APIエンドポイントであり、ブラウザ向けの画面を持たない。本文ではフレームワークのコントローラ型名やメソッド名を主説明としない。「利用者視点の入口」にHTTPメソッドとパスパターンを書く。

本書で扱うこと

  • 受注IDによるネット買取受注の特定と、明細・合計額・ステータスの更新
  • 送られた明細からの買取代表カード・個別入力商品の登録・更新・削除
  • ステータス変更時のステータス履歴登録
  • 認証、対象なし、入力検証、更新処理失敗時の応答

本書で扱わないこと

以下は本書では仕様確定せず、実装または別APIの設計を正とする。

  • ネット買取受注の一覧取得（ネット買取受注一覧取得APIの設計を正とする）
  • ネット買取受注のフリーコメント更新・ステータス単独更新（各ネット買取APIの設計を正とする）
  • 申込時買取価格の算出ロジックそのものの妥当性（買取価格設定の設計を正とする）
  • まとめ買取商品IDの設定値（まとめて買取商品IDの取得APIの設計を正とする）
  • トークンの発行（買取アプリ用ログインの設計を正とする）

観点内容
認証方式jwt-tokenヘッダのJWTを検証し、ペイロードの利用者IDから管理者会員を引く。署名方式はHS256。

トークン原値・署名シークレットは本書に記載しない。

処理フロー

ネット買取注文の査定を終了する（PUT /admin/buyOrder/{id}.json）

  1. jwt-tokenヘッダのトークンを検証し、管理者会員を特定する。検証できない場合は認証拒否（HTTP 401）とする。
  2. パスの受注IDでネット買取受注を1件取得する。該当が無い場合は該当なし（HTTP 404）とする。
  3. ボディのステータス（order_status）と明細配列（order_details）を受け取り、入力検証する。ステータスは選択必須かつ買取受注ステータスマスタに存在すること、明細配列は1件以上必須であること、各明細は商品名必須・数量／単価／商品規格ID／買取カテゴリが整数であることを検証する。検証エラーが1件以上あれば入力不正（HTTP 400）とし、エラーメッセージの配列を返す。
  4. 明細を1件ずつ処理する。商品規格IDが0の明細は個別入力商品として、同名の既存があれば更新し、無ければ新規に作る。それ以外は商品規格から買取代表カードを特定し、同一条件の既存があれば更新し、無ければ新規に作って既存明細から申込時買取価格を引き継ぐ。各明細の単価×数量を合計額に加算する。
  5. 受注に既存登録されているカードのうち、まとめ買取商品は申込時買取価格を削除し、サプライ・パック相当（カード詳細IDが未設定）の明細は合計額に加算して保持する。
  6. 合計額を10円単位で切り上げ、受注にステータス・合計額・買取代表カード・個別入力商品・更新担当者・更新日時を設定する。今回保持しない既存の買取代表カード・個別入力商品とそれに紐づく申込時買取価格を削除する。
  7. 更新前後でステータスが変わった場合は、受注のステータスと更新日時を再設定し、ステータス履歴を1件登録する。
  8. ここまでを1つのトランザクションで確定する。処理中に例外が発生した場合はロールバックし、内部エラー（HTTP 500）とし、エラーメッセージの配列を返す。
  9. 成功時はコード200のJSONを返す。

業務ルール・計算

項目内容
更新対象リクエストで指定されたID・入力値に対応する業務データを対象にする。対象特定、入力不正、認証・認可の判定順序は処理フローとバリデーションの各節を正とする。
更新方法入力値を対象データへ上書きまたは追加登録する。履歴登録や関連データ更新がある場合は入出力の副作用およびDBカラムの節を正とする。
計算処理本APIでは金額・税・ポイント・在庫数量の再計算や丸めを行わない。ステータスやコメント等の更新は、実装で定義された遷移・存在確認・担当者判定に従う。
応答値成功時は処理結果コードまたは更新後に取得した値を返す。レスポンス値は本API内で独自集計せず、保存結果または取得結果をJSON応答へ整形する。

副作用

ネット買取受注を更新する（DB更新）。具体的には次を行う。

  • 受注の買取受注ステータス・合計額・更新担当者・更新日時を更新する。
  • 送られた明細から買取代表カード・個別入力商品を登録・更新する。今回保持しない既存の買取代表カード・個別入力商品と、それに紐づく申込時買取価格を削除する。まとめ買取商品は申込時買取価格のみ削除する。
  • 更新前後でステータスが変わった場合は、ステータス履歴を1件登録する（履歴に受注ID・ステータスID・更新担当者・登録日時を記録する）。

参照のみではない。応答はJSON応答整形を経て返す。プロパティはcamelCase、日時はISO8601、serialize_nullは有効とする。

ログ・監査

更新処理中に例外が発生した場合、例外メッセージをエラーログに出力する。

ログに出してはいけないもの

  • JWTトークンの原値
  • 署名シークレット（auth_magic）
  • Cookie値・セッションIDの完全値

排他制御・トランザクション

本APIは受注の明細・合計額・ステータスの更新とステータス履歴の登録を1つのトランザクションで行う。明細の取得・登録・削除、受注の更新、履歴の登録までを1トランザクションとし、処理中に例外が発生した場合はロールバックして内部エラー（HTTP 500）を返す。楽観ロック・悲観ロックの対象は持たず、同一受注への同時更新は後勝ちとなる。
