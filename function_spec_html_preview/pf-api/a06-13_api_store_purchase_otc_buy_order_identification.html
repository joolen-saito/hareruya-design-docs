API 店頭買取管理 — 本人確認更新

概要

買取アプリ（MTGバイヤー）が店頭買取受注の本人確認情報（提示された証明書の種別）を更新するためのAPIである。pf-api（買取連携用のAPIアプリケーション）が提供するJSON APIで、受注IDで対象を特定し、本人確認証明書マスタに存在する証明書を設定して、更新担当者・更新日時とともに保存する。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。確認値はpf-apiの本人確認更新処理、ルート定義（config/routes.yaml）、店頭買取受注を扱うエンティティ、本人確認証明書マスタ、共通の認証処理を正とする。

カスタマイズ区分は現行踏襲。挙動の参照リポは現行の買取連携API（pf-api）とし、DB関連はec-cube-enterpriseを正とする。現行と移行先で異なる点は「リニューアル移行時の扱い」に集約する。

対象はJSON APIエンドポイントであり、ブラウザ向けの画面を持たない。本文ではフレームワークのコントローラ型名やメソッド名を主説明としない。「利用者視点の入口」にHTTPメソッドとパスパターンを書く。

本書で扱うこと

  • 受注IDによる店頭買取受注の特定と、本人確認証明書・更新担当者・更新日時の保存
  • 証明書IDの妥当性確認（本人確認証明書マスタの存在確認）
  • 認証、対象なし、証明書ID不正時の応答

本書で扱わないこと

以下は本書では仕様確定せず、実装または別APIの設計を正とする。

  • 店頭買取受注そのものの登録・査定・ステータス更新（各店頭買取APIの設計を正とする）
  • 本人確認証明書マスタの登録・編集（マスタ管理の設計を正とする）
  • オンライン本人確認の判定ロジック（本人確認機能の設計を正とする）
  • トークンの発行（買取アプリ用ログインの設計を正とする）

認証・認可

観点内容
認証方式jwt-tokenヘッダのJWTを検証し、ペイロードの利用者IDから管理者会員を引く。署名方式はHS256。
認証失敗時ヘッダ欠落・署名不正・該当する管理者会員なしのいずれも認証拒否（HTTP 401）とする。
認可認証した管理者会員が更新担当者として記録される。呼び出し可能なクライアントは買取アプリ。

トークン原値・署名シークレットは本書に記載しない。

処理フロー

店頭買取受注の本人確認を更新する（PUT /admin/otcBuyOrder/{id}/identification）

  1. jwt-tokenヘッダのトークンを検証し、管理者会員を特定する。検証できない場合は認証拒否（HTTP 401）とする。
  2. パスの受注IDで店頭買取受注を1件取得する。該当が無い場合は該当なし（HTTP 404）とする。
  3. リクエストの証明書IDで本人確認証明書マスタを引く。該当が無い場合は入力不正（HTTP 400）とし、エラーメッセージを返す。
  4. 店頭買取受注に本人確認証明書を設定し、更新担当者に認証した管理者会員を、更新日時に現在時刻を設定して保存する。
  5. コード200のJSONを返す。

業務ルール・計算

項目内容
更新対象リクエストで指定されたID・入力値に対応する業務データを対象にする。対象特定、入力不正、認証・認可の判定順序は処理フローとバリデーションの各節を正とする。
更新方法入力値を対象データへ上書きまたは追加登録する。履歴登録や関連データ更新がある場合は入出力の副作用およびDBカラムの節を正とする。
計算処理本APIでは金額・税・ポイント・在庫数量の再計算や丸めを行わない。ステータスやコメント等の更新は、実装で定義された遷移・存在確認・担当者判定に従う。
応答値成功時は処理結果コードまたは更新後に取得した値を返す。レスポンス値は本API内で独自集計せず、保存結果または取得結果をJSON応答へ整形する。

排他制御・トランザクション

本APIは本人確認証明書・更新担当者・更新日時の更新を行う。楽観ロック・悲観ロックの対象は持たず、同一受注への同時更新は後勝ちとなる。
