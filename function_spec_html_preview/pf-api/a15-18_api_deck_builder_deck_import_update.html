API デッキビルダー — デッキ更新インポート

概要

デッキビルダーアプリが、デッキリストのテキスト（カードリスト）を貼り付けて既存デッキを上書き更新するためのAPIである。deck-api（デッキビルダー用のAPIアプリケーション）が提供するJSON APIで、jwt-tokenヘッダから特定したプレイヤーが所有する既存デッキを対象に、カードリストを解読してデッキ内容を更新し保存する。本書は更新（パスにデッキ識別子を持つPUT）を対象とする。

本機能のカスタマイズ区分は現行踏襲であり、挙動は現行実装（deck-api）を参照し、DB関連はec-cube-enterpriseを正とする。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。確認値はdeck-apiのデッキインポート処理、ルート定義（config/routes.yaml）、デッキ保存サービス・カードリスト解読処理、共通の認証処理を正とする。

対象はJSON APIエンドポイントであり、ブラウザ向けの画面を持たない。本文ではフレームワークのコントローラ型名やメソッド名を主説明としない。「利用者視点の入口」にHTTPメソッドとパスパターンを書く。

本書で扱うこと

  • パスのデッキ識別子による既存デッキの特定と所有者照合
  • カードリストテキストの解読と既存デッキの上書き更新
  • 解読できなかった行（カード名未一致）の扱いと部分成功（HTTP 206）
  • 非公開・限定公開時の表示用トークンの扱い

本書で扱わないこと

以下は本書では仕様確定せず、実装または別APIの設計を正とする。

  • デッキの新規登録インポート（デッキ登録インポートAPI POST /deck/importの設計を正とする）
  • カードリストを用いない通常のデッキ更新（PUT /deck/{id}の設計を正とする）
  • デッキの参照・検索・削除（各デッキAPIの設計を正とする）
  • トークンの発行（デッキビルダー用ログインの設計を正とする）

リニューアル移行時の扱い

現行（deck-api）と移行先（ec-cube-enterprise）でデッキ永続化のスキーマに差がある。DB関連の記述は移行先を正とし、確認できた差を以下に記録する。

ボード外区分メイビー・アトラクション・ステッカー別表 dtb_maybe_card・dtb_attraction_card・dtb_sticker_card（いずれも deck_id・card_id・count）。更新時はこれらを初期化してから作り直す。

利用者視点の入口

入口URLエンドポイント期待されるふるまい
デッキ更新インポートPUT /deck/import/{id}jwt-tokenヘッダから特定したプレイヤーが所有する、パスのidのデッキを対象に、card_listを解読して内容を上書き更新し、デッキ識別子をコード200のJSONで返す。解読できない行があるときはコード206を返す。

応答形式はJSON。呼び出し元はデッキビルダーアプリ。新規登録（POST /deck/import）と同一の処理を共有し、本書はパスにデッキ識別子を持つPUT（更新）のみを扱う。

認証・認可

観点内容
認証方式jwt-tokenヘッダのJWTを検証し、ペイロードのaudの顧客IDから顧客IDに対応するプレイヤーを引く。署名方式はHS256。
認証失敗時ヘッダ欠落・署名不正・該当するプレイヤーなしのいずれも認証拒否（HTTP 401）とし、本文は{code, message}で返す。
認可パスのデッキの所有プレイヤーが認証したプレイヤーと一致する場合のみ更新できる。一致しない場合は認証拒否（HTTP 401）とする。呼び出し可能なクライアントはデッキビルダーアプリ。

トークン原値・署名シークレットは本書に記載しない。

処理フロー

デッキを更新する（PUT /deck/import/{id}）

  1. jwt-tokenヘッダのトークンを検証し、プレイヤーを特定する。検証できない、または該当するプレイヤーがない場合は認証拒否（HTTP 401）とし、{code, message}を返す。
  2. メソッドがPUTでパスのidが指定されているため、idに一致する既存デッキを取得する。該当が無い場合は該当なし（HTTP 404）とし、「The deck does not exist」を返す。
  3. 取得したデッキの所有プレイヤーが認証したプレイヤーと一致しない場合は認証拒否（HTTP 401）とし、「Authentication failed」を返す。
  4. ボディのformat_idからフォーマットを取得し、card_listをフォーマットの統率者使用設定に応じて解読する。解読結果のカード配列をcardsとしてリクエストに組み込む。
  5. 既存デッキ配下の旧カード（デッキカード・メイビー・アトラクション・ステッカー）を初期化したうえで、解読したカードとdeck_name・scope_id・archetype_id等で内容を組み立て直し、検証を通過したらデータベースに保存する。あわせて当該デッキのRedis上の下書きを削除する。検証エラーは入力不正（HTTP 400）とし、その他の例外は処理失敗（HTTP 500）とする。
  6. デッキ識別子（deck_id）を含むコード200のJSONを返す。公開区分が限定公開のときは表示用トークン（display_token）も返す。
  7. カードリストに解読できない行（カード名未一致）がある場合は、コードを206に切り替え、該当行の行番号をerrorsとして返す。

新規登録との分岐

同一処理を新規登録（POST）と共有し、パスのデッキ識別子の有無で動作を分ける。

条件動作
メソッドがPUTかつパスのidが非nullidの既存デッキを取得し、該当なしは404、所有者不一致は401とする。取得できた場合は既存デッキを上書き更新する。
メソッドがPOST（パスにデッキ識別子なし）既存デッキの取得・所有者照合を行わず、新規デッキとして登録する（デッキ登録インポートAPIで扱う）。

更新時のメッセージは「Deck update success by import」、新規登録時は「Deck registration success by import」となる。

業務ルール・計算

項目内容
更新対象リクエストで指定されたID・入力値に対応する業務データを対象にする。対象特定、入力不正、認証・認可の判定順序は処理フローとバリデーションの各節を正とする。
更新方法入力値を対象データへ上書きまたは追加登録する。履歴登録や関連データ更新がある場合は入出力の副作用およびDBカラムの節を正とする。
計算処理本APIでは金額・税・ポイント・在庫数量の再計算や丸めを行わない。ステータスやコメント等の更新は、実装で定義された遷移・存在確認・担当者判定に従う。
応答値成功時は処理結果コードまたは更新後に取得した値を返す。レスポンス値は本API内で独自集計せず、保存結果または取得結果をJSON応答へ整形する。

副作用

既存デッキ配下のカード（デッキカード・メイビー・アトラクション・ステッカー）を初期化したうえで、デッキ内容とカードをデータベースに上書き更新する（DB更新）。あわせて当該デッキのRedis上の下書きを削除する。保存は単一のトランザクション内で行い、例外時はロールバックする。

応答はJSON応答整形を経て返す。本APIは連想配列を組み立てて返すため、JSONキーは実装で記述したsnake_case（code・message・deck_id・display_token・errors）となる。serialize_nullは有効とする。

データ整合性

観点内容
更新の有無既存デッキ配下のカードを初期化してから、解読したカードで作り直して保存する。デッキ本体は同一識別子のまま内容を上書きする。
トランザクションカードの初期化・デッキ本体・カードの保存を1つのトランザクションで行い、検証エラー・例外時はロールバックする。
下書きとの整合保存後に当該デッキのRedis上の下書きを削除し、保存済みデータと下書きの不整合を解消する。

ログ・監査

ログに出してはいけないもの

  • JWTトークンの原値
  • 署名シークレット（auth_magic）
  • パスワード
  • Cookie値・セッションIDの完全値

排他制御・トランザクション

本APIは既存デッキのカード初期化とデッキ・カードの上書き更新を1つのトランザクションで行う。検証エラー・例外時はロールバックする。同一デッキへの同時更新に対する楽観ロック・悲観ロックは持たない。
