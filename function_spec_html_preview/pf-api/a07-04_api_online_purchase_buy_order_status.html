API ネット買取管理 — ネット買取受注ステータス更新

概要

買取アプリ（MTGバイヤー）がネット買取受注のステータスを更新するためのAPIである。pf-api（買取連携用のAPIアプリケーション）が提供するJSON APIで、受注IDで対象を特定し、指定したステータスへ更新するとともに更新担当者とステータス変更履歴を保存する。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。確認値はpf-apiのステータス更新処理、ルート定義（config/routes.yaml）、ネット買取受注・買取ステータスマスタ・買取ステータス履歴を扱うエンティティ、共通の認証処理を正とする。

本機能のカスタマイズ区分は現行踏襲であり、挙動の参照リポはpf-api、DB関連（テーブル名・列名・永続化先）の記述はec-cube-enterpriseを正とする。

対象はJSON APIエンドポイントであり、ブラウザ向けの画面を持たない。本文ではフレームワークのコントローラ型名やメソッド名を主説明としない。「利用者視点の入口」にHTTPメソッドとパスパターンを書く。

本書で扱うこと

  • 受注IDによるネット買取受注の特定と、ステータス・更新担当者・更新日時の保存
  • ステータス変更履歴の登録
  • 認証、対象なし、無効なステータス、査定終了後・査定中の更新可否判定と応答

本書で扱わないこと

以下は本書では仕様確定せず、実装または別APIの設計を正とする。

  • ネット買取受注そのものの登録・査定・コメント更新（ネット買取受注コメント更新APIおよび各買取APIの設計を正とする）
  • 店頭買取受注のステータス更新（店頭買取受注ステータス更新APIの設計を正とする）
  • ステータスごとの業務上の意味づけや画面表示（買取アプリの設計を正とする）
  • トークンの発行（買取アプリ用ログインの設計を正とする）

認証・認可

観点内容
認証方式jwt-tokenヘッダのJWTを検証し、ペイロードの利用者IDから管理者会員を引く。署名方式はHS256。
認証失敗時ヘッダ欠落・署名不正・該当する管理者会員なしのいずれも認証拒否（HTTP 401）とする。
認可認証した管理者会員が更新担当者として記録される。査定中・査定再開の受注を査定開始できるのは、その受注を査定中の担当者本人に限る。呼び出し可能なクライアントは買取アプリ。

処理フロー

ネット買取受注のステータスを更新する（PUT /admin/buyOrder/{id}/status.json）

  1. jwt-tokenヘッダのトークンを検証し、管理者会員を特定する。検証できない場合は認証拒否（HTTP 401）とする。
  2. パスの受注IDでネット買取受注を1件取得する。該当が無い場合は該当なし（HTTP 404）とする。
  3. 更新前のステータスIDを保持する。
  4. リクエストのステータスID（status）で買取ステータスマスタを引く。該当が無い場合は入力不正（HTTP 400）とし「正しい店頭買取ステータスIDを入力してください」を返す。
  5. 更新前ステータスが査定終了に該当する場合は更新不可とし、入力不正（HTTP 400）を返す。指定ステータスが査定中・査定再開のときは「この査定はすでに終了しているため開くことができません。」、それ以外は「この査定はすでに終了しているためステータスの更新に失敗しました。」を返す。
  6. 更新前ステータスが査定中・査定再開で、かつ指定ステータスも査定中・査定再開で、その受注の査定担当者が認証した管理者会員と異なる場合は、入力不正（HTTP 400）とし「この受注は「（査定担当者名）」が査定中です。」を返す。
  7. 更新前ステータスと指定ステータスが異なる場合のみ、受注のステータス・更新担当者・更新日時を更新し、ステータス変更履歴を1件登録する。保存はトランザクション内で行う。更新前後が同じステータスのときは更新も履歴登録も行わない。
  8. コード200のJSONを返す。

業務ルール・計算

項目内容
更新対象リクエストで指定されたID・入力値に対応する業務データを対象にする。対象特定、入力不正、認証・認可の判定順序は処理フローとバリデーションの各節を正とする。
更新方法入力値を対象データへ上書きまたは追加登録する。履歴登録や関連データ更新がある場合は入出力の副作用およびDBカラムの節を正とする。
計算処理本APIでは金額・税・ポイント・在庫数量の再計算や丸めを行わない。ステータスやコメント等の更新は、実装で定義された遷移・存在確認・担当者判定に従う。
応答値成功時は処理結果コードまたは更新後に取得した値を返す。レスポンス値は本API内で独自集計せず、保存結果または取得結果をJSON応答へ整形する。

副作用

更新前後でステータスが異なる場合に、ネット買取受注のステータス・更新担当者・更新日時を更新し（DB更新）、ステータス変更履歴を1件登録する。履歴には受注ID・更新後ステータスID・更新担当者ID・登録日時を記録する。参照のみではない。更新はトランザクション内で確定し、例外時はロールバックする。更新前後が同じステータスのときは更新も履歴登録も行わない。

応答はJSON応答整形を経て返す。プロパティはcamelCase、日時はISO8601、serialize_nullは有効とする。

ログ・監査

ステータス変更の履歴は買取ステータス履歴として永続化する（受注ID・更新後ステータスID・更新担当者ID・登録日時）。アプリケーションログとは別のDB上の業務履歴である。

ログに出してはいけないもの

  • JWTトークンの原値
  • 署名シークレット（auth_magic）
  • Cookie値・セッションIDの完全値

排他制御・トランザクション

本APIはステータス更新と履歴登録を1つのトランザクション内で行い、例外時はロールバックする。楽観ロック・悲観ロックの対象は持たず、同一受注への同時更新は後勝ちとなる。査定中・査定再開の占有は担当者比較による業務判定であり、DBレベルのロックではない。
