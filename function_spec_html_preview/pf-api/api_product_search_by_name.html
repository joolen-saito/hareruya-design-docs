API 店頭買取管理 — 商品名から商品詳細の情報を取得

概要

買取アプリ（MTGバイヤー）が商品名で商品を検索し、該当する商品の詳細情報（カテゴリ・コンディション別の商品規格・画像）を取得するためのAPIである。pf-api（買取連携用のAPIアプリケーション）が提供するJSON APIで、商品名に該当する商品を最大100件まで返す。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。確認値はpf-apiの商品名検索処理、ルート定義（config/routes.yaml）、商品サブクラスを扱うリポジトリを正とする。カスタマイズ区分は現行踏襲で、挙動の参照リポはpf-api、DB関連はec-cube-enterpriseを正とする。

対象はJSON APIエンドポイントであり、ブラウザ向けの画面を持たない。本文ではフレームワークのコントローラ型名やメソッド名を主説明としない。「利用者視点の入口」にHTTPメソッドとパスパターンを書く。

本書で扱うこと

  • 商品名による商品の検索と、商品詳細情報・商品規格・画像の取得
  • 表示するコンディションの絞り込みと最大件数
  • 該当が無い場合の応答

本書で扱わないこと

以下は本書では仕様確定せず、実装または別APIの設計を正とする。

  • 商品IDによる商品詳細取得（商品詳細取得APIの設計を正とする）
  • 買取用商品情報の取得（買取用商品情報取得APIの設計を正とする）
  • 商品の登録・編集（商品管理を正とする）

リニューアル移行時の扱い

DB関連はec-cube-enterpriseを正とする。商品（dtb_product）・商品規格（dtb_product_class）・商品規格画像（dtb_product_class_image）・カード（mtb_card）・カード詳細（mtb_card_detail）はec-cube-enterpriseに同名で実在する。一方、本APIが現行（pf-api）で参照する商品サブクラス（dtb_product_sub_class）のビューと商品サブクラス画像（dtb_product_sub_class_image）は、ec-cube-enterpriseでは商品規格・商品規格画像（dtb_product_class_image）系へ再編されており同名ビューを確認できない。商品名検索・一意化・画像URL生成に用いる該当テーブル・列はec-cube-enterprise実装で要確認とする。挙動（検索条件・コンディション絞り込み・最大100件・該当なし時の応答）は現行（pf-api）を正とする。

処理フロー

商品名で商品詳細を取得する（GET /product/search）

  1. クエリの商品名を受け取る。未指定の場合は該当なし（HTTP 404）とする。
  2. 商品名から対象の商品ID群を取得する。該当が無い場合は該当なし（HTTP 404）とする。
  3. 対象の商品サブクラス情報を取得する。該当が無い場合は該当なし（HTTP 404）とする。
  4. 商品ID・言語・高額商品コードの組み合わせを単位に商品をまとめ、商品ごとにカテゴリ・地域制限・商品名を設定する。カード詳細を持つ商品は商品名の先頭に言語コードを付す。
  5. 各商品規格について、良品（NM）または価格が表示下限以上のものだけを商品規格として加え、画像はファイル名からURLへ変換して並べる。商品の件数が100件に達した時点で打ち切る。
  6. 商品ごとに、その他コンディションの表示可否を判定し、表示しない場合は良品（NM）の規格のみに絞る。
  7. コード200と商品配列をJSONで返す。

集計条件

指標集計の要点
対象商品商品名に該当する商品サブクラスから、商品ID・言語・高額商品コードの組み合わせで一意化する。
表示する商品規格コンディションが良品（NM）の規格、または価格が表示下限（設定値）以上の規格のみを含める。
その他コンディションの抑制商品ごとの表示可否判定で「表示しない」と判定された場合、良品（NM）の規格のみに絞る。
最大件数商品は最大100件で打ち切る。

  • 検索・一覧・取得条件はリクエストパラメータ、ログイン状態、公開状態、店舗・支店条件、既存リポジトリの絞り込み順序を正とする。
