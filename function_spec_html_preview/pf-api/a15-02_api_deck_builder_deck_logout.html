API デッキビルダー — ログアウト

<!-- リバース詳細設計書（API・機能単位）。deck-api が提供する会員ログアウトAPI。 -->

概要

デッキビルダーアプリの利用者がログアウトし、クライアントが保持するアクセストークンのCookieを無効化するためのAPIである。deck-api（デッキビルダー用のAPIアプリケーション）が提供するJSON APIで、jwt-tokenヘッダのトークンを検証して会員に紐づくプレイヤーを引き、認証できた場合にトークンCookieを空に設定して成功応答を返す。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。既存実装のふるまい、参照するデータ、判定境界、副作用を確認し、仕様の確からしさを把握することを目的とする。確認値はdeck-apiのログアウト処理、共通基底のトークン認証処理、ルート定義（config/routes.yaml）、照合先のプレイヤーデータを正とする。

本機能のカスタマイズ区分は現行踏襲であり、挙動はデッキビルダー用APIの現行実装（deck-api）を、DB関連はec-cube-enterpriseの実装を正とする。

対象はJSON APIエンドポイントであり、ブラウザ向けの画面を持たない。本文ではフレームワークのコントローラ型名やメソッド名を主説明としない。「利用者視点の入口」にHTTPメソッドとパスパターンを書く。

本書で扱うこと

  • アクセストークンによる認証判定とログアウトのふるまい
  • ログアウト時のトークンCookieの扱い
  • 認証成功時・認証失敗時の応答

本書で扱わないこと

以下は本書では仕様確定せず、実装または別APIの設計を正とする。

  • アクセストークンの発行（A15-01 ログインの設計を正とする）
  • サーバ側でのトークン失効・ブラックリスト管理（実装には存在しない。後述の副作用を正とする）
  • 各デッキビルダーAPIの認可（各APIの設計を正とする）

リニューアル移行時の扱い

DB関連の記述はec-cube-enterpriseの実装を正とする。挙動は現行のデッキビルダー用API（deck-api）を正とする。現行と移行先でプレイヤーテーブルの主キー列名が異なる。

観点現行（deck-api）移行先（ec-cube-enterprise）
プレイヤーテーブルdtb_playerdtb_player
プレイヤーの主キー列player_idid
会員ID列customer_id（現行はdtb_customer.customer_idを参照）customer_id（移行先はdtb_customer.idを参照）

トークン認証・Cookie操作の挙動は現行と移行先で同じだが、プレイヤーテーブルの主キー列名（現行player_id、移行先id）と会員参照先の主キー列名が異なる。移行に伴うトークン仕様の変更は本書では確定しない。

利用者視点の入口

入口URLエンドポイント期待されるふるまい

認証・認可

観点内容
認証方式jwt-tokenヘッダのJWTを検証する。署名方式はHS256。ペイロードのaud（会員ID）でプレイヤーを引く。
照合先audに対応する会員IDでプレイヤーを引く。プレイヤーが取得できた場合に認証成功とする。
認証失敗時jwt-tokenヘッダが欠落、またはトークンの署名が不正な場合は認証拒否（HTTP 401）とし、メッセージAccess Token is incorrectを返す。該当プレイヤーが無い場合も認証拒否（HTTP 401）とし、メッセージAuthentication failedを返す。
認可ログイン済みのクライアント（有効なトークンを持つ会員）のみがログアウトできる。

トークン原値・署名シークレット・パスワードは本書に記載しない。

処理フロー

会員ログアウトを行う（POST /user/logout）

  1. jwt-tokenヘッダのトークンを検証する。ヘッダが欠落、または署名が不正な場合は認証拒否（HTTP 401）のJSONを返す。
  2. トークンのaud（会員ID）でプレイヤーを引く。該当が無い場合は認証拒否（HTTP 401）のJSONを返す。
  3. 認証できた場合、トークンCookieを空値に設定する。
  4. コード200・メッセージLogout successのJSONを返す。

副作用

トークンCookieを空値に設定する（クライアント側のトークン保持を解除する）。サーバ側ではトークンの失効・ブラックリスト登録は行わず、業務データも更新しない。発行済みトークン自体は有効期限まで署名上有効なままである。

応答はJSON応答整形を経て返す。プロパティはcamelCase、日時はISO8601、serialize_nullは有効とする。

バリデーション

本APIはリクエストボディの入力検証を行わない。認証はjwt-tokenヘッダの検証で行い、未充足時は認証拒否（HTTP 401）となる。

業務ルール・計算

  • ログアウトは現在のセッションまたはトークンの無効化のみを行い、会員・注文・ポイント等の業務データは更新しない。
  • 既に無効なセッションに対する要求は既存の認証エラーまたは冪等な成功応答の実装に従う。
  • 金額・ポイント・在庫などの業務値は計算しない。

データ整合性

観点内容
参照時点照合するプレイヤーデータはログアウト呼び出し時点の値である。
トークンサーバ側ではトークンを保存・失効しないため、ログアウト後も発行済みトークンは有効期限まで署名上有効である。無効化はクライアント側のCookie解除に依存する。
