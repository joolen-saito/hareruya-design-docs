API その他 — PointGranterAPI連携

概要

外部連携先（任意門・PointGranter）からの呼び出しを受けて、スマレジの取引APIへ中継し、取引更新時に会員のポイントを付与してポイント履歴を登録するAPIである。pf-eccube3（EC-CUBE3系）のHareruyaEcプラグインが買取アプリ用APIの一部として提供するJSON APIである。

本機能のカスタマイズ区分は現行踏襲であり、挙動は現行実装（pf-eccube3）を参照し、DB関連はec-cube-enterpriseを正とする。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。確認値はpf-eccube3のPointGranter連携処理、ルート定義（買取アプリ用APIのルート登録）、スマレジ顧客連携サービス、会員ポイント・ポイント履歴を扱うリポジトリを正とする。

対象はJSON APIエンドポイントであり、ブラウザ向けの画面を持たない。本文ではフレームワークのコントローラ型名やメソッド名を主説明としない。「利用者視点の入口」にHTTPメソッドとパスパターンを書く。

本書で扱うこと

  • 連携先からの取引要求のスマレジ取引APIへの中継
  • 取引更新時の会員ポイント付与とポイント履歴の登録
  • ヘッダ・パラメータ不足時、連携結果が不正な場合の応答

本書で扱わないこと

以下は本書では仕様確定せず、実装または別機能の設計を正とする。

  • スマレジ取引APIそのものの仕様・応答構造（スマレジ連携の設計・連携先仕様を正とする）
  • 任意門・PointGranter側の処理仕様
  • ポイントの利用・失効・他経路での付与（ポイント機能・各バッチの設計を正とする）

リニューアル移行時の扱い

現行（pf-eccube3、EC-CUBE3系）と移行先（ec-cube-enterprise、EC-CUBE4系）でポイント関連のスキーマが異なる。DB関連の記述は移行先を正とし、確認できた対応を以下に記録する。

項目移行先（ec-cube-enterprise）メモ
会員ポイント残高dtb_customer.point取引更新時に付与ポイントを加算する。
スマレジ会員IDプレイヤー dtb_player.smaregi_id 由来会員（顧客）に紐づくプレイヤーのスマレジIDから特定する。会員の特定に用いる。
ポイント履歴dtb_point_history付与時に登録する。会員（customer_id）・増減ポイント（point_change）・備考（note）・発行日（issue_date）・作成日（create_date）・ポイント種別（point_type_id）・スマレジ取引ID（transaction_id）を持つ。

現行のポイント残高列・ポイント履歴テーブルの呼称・型は現行（EC-CUBE3系）と移行先で異なる可能性があり、列名・型の最終確定はec-cube-enterprise実装を正とする。

利用者視点の入口

入口URLエンドポイント期待されるふるまい

応答形式はJSON。呼び出し元は外部連携先（任意門・PointGranter）。/admin_apiは買取アプリ用APIのマウントである。

認証・認可

観点内容
認証情報契約ID（X_contract_id）とアクセストークン（X_access_token）をリクエストヘッダで受け取り、スマレジ連携のために中継する。いずれかが欠落する場合は入力不正（HTTP 400）とする。
認可呼び出し元は外部連携先（任意門・PointGranter）。アクセス経路の制御はAPI外（ネットワーク・配置）の範囲とし、本書では仕様確定しない。

契約ID・アクセストークンの原値は本書に記載しない。

処理フロー

PointGranter連携を行う（POST /admin_api/point_granter）

  1. リクエストヘッダの契約ID・アクセストークンと、本文の処理名・パラメータを受け取る。いずれかが欠落する場合は入力不正（HTTP 400）とし、空の本文を返す。
  2. 契約ID・アクセストークンを付与して、スマレジ顧客連携サービスへ処理名とパラメータを渡し、取引APIへ中継する。
  3. 中継結果に結果キーが含まれない場合は入力不正（HTTP 400）とし、結果をそのまま返す。
  4. 処理名が取引更新（transaction_upd）の場合、パラメータの先頭行から会員（スマレジ会員IDで特定）を引く。会員が見つからない場合はポイント付与を行わず、コード200で結果を返す。
  5. 会員が見つかった場合、会員ポイントに付与ポイントを加算し、ポイント履歴（会員・増減ポイント・メモ・発生日時・ポイント種別）を登録して保存する。
  6. 中継結果をコード200で返す。

業務ルール・計算

項目内容
更新対象リクエストで指定されたID・入力値に対応する業務データを対象にする。対象特定、入力不正、認証・認可の判定順序は処理フローとバリデーションの各節を正とする。
更新方法入力値を対象データへ上書きまたは追加登録する。履歴登録や関連データ更新がある場合は入出力の副作用およびDBカラムの節を正とする。
計算処理本APIでは金額・税・ポイント・在庫数量の再計算や丸めを行わない。ステータスやコメント等の更新は、実装で定義された遷移・存在確認・担当者判定に従う。
応答値成功時は処理結果コードまたは更新後に取得した値を返す。レスポンス値は本API内で独自集計せず、保存結果または取得結果をJSON応答へ整形する。

副作用

処理名が取引更新（transaction_upd）で会員が特定できた場合、会員ポイントの加算とポイント履歴の登録を行う（DB更新）。それ以外は中継のみで業務データを更新しない。応答にはCORS許可ヘッダを付与する。

応答はJSON応答整形を経て返す。
