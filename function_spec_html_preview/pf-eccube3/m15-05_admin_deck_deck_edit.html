デッキ管理 — 新規登録・編集・削除・複製

概要

HareruyaEc プラグインが管理画面に提供する「デッキ管理」のうち、dtb_deck および関連するデッキカード行・表示用テキストを、単一画面で新規作成・更新する処理と、複製および削除の HTTP 処理を対象とする。一覧での検索条件・並び順・ページ番号や CSV・一括更新は別範囲とする。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。カスタマイズ区分は「カスタマイズ」。画面・挙動は pf-eccube3 配下 HareruyaEc のソースとプラグイン config.yml の HareruyaEc.const.deck を確認値とし、DB関連（テーブル・列・型・制約・関連）は ec-cube-enterprise の実装を正とする。

対象はブラウザ経由の管理画面に限定する。コントローラの処理名単位の解剖は本文の主題としない。本文ではルートbind名やSymfonyのルートnameの網羅は主説明としない。「利用者視点の入口」にHTTPメソッドとサイトルートからのパスパターンを書く。コード探索でbind名が必要なときだけ「調査補助」へ書く。

リニューアル移行時の扱い

  • 画面・挙動は現行（pf-eccube3 の HareruyaEc プラグイン）の確認値、DBスキーマは移行先（ec-cube-enterprise）を正とする。
  • 主データはデッキ（dtb_deck）と関連するデッキカード行・表示用テキストである。dtb_deck／dtb_deck_card は移行先 ec-cube-enterprise にも存在する。列名・型は移行先の DtbDeck／DtbDeckCard を正とし、現行と異なる場合は移行先名を主として現行名を併記する。
  • 新規登録・編集・削除・複製の管理画面（コントローラ）が ec-cube-enterprise に移植済みかは未確認のため、移植有無とデッキ系テーブルのスキーマ差は ec-cube-enterprise 実装で要確認とする。差が判明した場合は本節とDB節を更新する。

処理フロー

新規入力画面を表示する（GET admin_deck_new）

  1. 管理画面の共通制約を通過する。
  2. モデルとして新規デッキ行を用意し、admin_deck 名前のフォームを生成する。
  3. admin_deck_copy（空データ）、イベント検索用 admin_event_list、カード検索用 admin_search_card を補助フォームとして生成する。
  4. プレイヤー・イベント詳細が未設定でも、モデル側に ID が載っていれば対応する表示名・日時を項目へ補完する。
  5. 管理者会員検索ではソフト削除除外から Member のみ除外し、モデルにある member_id の会員名をサイド情報として渡す場合がある。
  6. deck_detail.twig をレンダする。id は未設定であり、一覧戻りはセッションの admin.deck.search.page_no 既定 1 で組み立てる。

複製入力用の新規画面を表示する（GET admin_deck_duplicate）

  1. 手順は新規画面とほぼ同様であるが、duplicateId で既存デッキを読み込みモデルとして用いる。
  2. Twig には id を渡さないため、画面上は新規同様であり、フォーム送信先も POST の admin_deck_create となる。

既存デッキの編集画面を表示する（GET m15-05_admin_deck_deck_edit）

  1. パス {id} の行を読み込めなければ 404 とする。
  2. モデル読み込み後の処理は「新規表示」と同型。
  3. 代表カードは card_image_id があれば解決済み画像を Twig に渡す。
  4. 削除・アンカー・複製モーダルは id があるときだけ表示するブロックにある。

登録または更新する（POST admin_deck_create または admin_deck_update）

  1. 対応するモデルを用意し（更新で見つからない場合は 404）、admin_deck フォームにリクエストを取り込む。
  2. フォームの CSRF と Symfony の妥当性チェックが FormValidHelper により行われる前に、textMain、textSide、textCommand それぞれをリスト解釈関数へ渡す。戻りが整数のときは、その値を行番号としてフロント用翻訳 front.deckentry.error.invalid を管理画面へエラー表示し、リストエラー状態とする。
  3. Symfony フォームが無効、またはリスト解釈に失敗した場合、同一 Twig を再表示して終える（フラッシュのみ、リダイレクトしない）。
  4. モデル側にプレイヤー ID が入力されていれば関連プレイヤー行へ紐付け直す。
  5. 「編集者」としてログイン済み管理会員 ID を member_id に格納する。
  6. 代表カード ID の扱い: 更新でない新規のみ、ID がセットされていれば代表カード行を名前解決する。ID が空なら、選択中アーキタイプの既定代表カード画像を設定する。
  7. モデルを永続化し flush したあと、deck_cards コレクションの既存要素をすべて remove する。
  8. 解釈済みリストを三ボードごとに子行作成ユーティリティへ渡し、永続化する。管理側では、マスタに存在しない名前は子行へ載せず捨て、設定どおりの「不明参照」の文字列だけはカウント付きで子へ載せられる。
  9. flush 後、モデルの「現行フォーマット」フラグが真かつフォーマットがセットされているとき、リスト整合・フォーマット制限チェックを走らせ、問題があれば警告カテゴリとしてボード単位ごとにメッセージを追加する。この検査はエラーとはせず送信は完了扱いのままとする。
  10. 登録完了の成功フラッシュを積む。
  11. POST が更新なら、その deck_id。新規作成なら採番後の deck_id を付けて GET の m15-05_admin_deck_deck_edit へ HTTP リダイレクトする。

複製保存する（POST admin_deck_copy）

  1. admin_deck_copy フォームへリクエストを投入する。この経路では FormValidHelper（CSRF と Symfony 妥当性）を経由しない。
  2. 「複製」整数が PHP の整数型であり、かつ 1 以上かつ設定 deck.copy_max（既定値 310）以下でなければ、エラー用翻訳 admin.deck.error.copy_count を積み、元の編集画面 URL へそのまま戻す。
  3. 元デッキが取得できない場合は admin.register.failed を積み同様に戻す。
  4. 回数だけループし、元のデッキ行を言語標準の clone で複製、articles は空に設定し、member_id を操作者へ更新して永続化し flush したうえで、元デッキの各デッキカード行についてもクローン生成し親を差し替えて追加保存する。
  5. 完了時は成功フラッシュとして admin.deck.copy 形式文言に回数が埋め込まれ、ステップ 2 と同じ編集画面 URL に戻す。

単体削除する（DELETE admin_deck_delete）

  1. フォーム検証とは別の共通 CSRF 検証のみを明示的に実行する。
  2. 一覧に戻る際に使う page_no をセッションから読むキーは admin.deck.search.page_no とする。
  3. 処理対象 ID リストはパス単体削除では id 一要素のみ。
  4. 各行について、モデル未取得なら 404。
  5. 記事コレクションの件数が 0 でなければ、エラー admin.deck.is_used.article を積み、Referer があればそこへ戻して終える。
  6. デッキカード行をすべて remove したあと、member_id を操作者に更新して一度 flush（更新反映）したうえでデッキ行自体を remove・flushする。
  7. 成功フラッシュ admin.delete.complete のあと、page_no があれば m15-01_admin_deck_deck_search でそのページへ、無ければ admin_deck_list へリダイレクトする。
  8. パス側 id 不在で POST に ID 配列も無いときはフラッシュなく一覧相当へだけ戻す分岐がある（本書の一覧操作は詳細しない）。

集計条件

本機能では検索一覧の総件数集計などはメイン処理としない。編集画面上の一覧枚数サマリーは、各 textarea の行を「先頭の空白区切られたトークンを数」とみなし、それが数値化できた分だけ画面上で合計表示するのみである（送信内容の検証とは独立）。

登録／更新処理におけるリスト解釈の判定順序

順序判定結果
1テキストが空または空白のみ空配列へ扱う。送信はリストエラーにしない。
2非空の各行が 数量 カード名 または拡張正規表現に合う行形式か合わない行があれば、その 1 始まり行番号を整数で返し、エラー文言に載せて送信中止。
3カード名の正規化後、マスタ照合または不明参照許可文字列か未解決なら子生成時は捨て、管理では不明許可のみ子へ残せる。
4同一リスト内での同一カード重複件数だけ合算した一要素へまとめる。

業務ルール・計算

本機能単体での金額・ポイント等の算出はしない。送信後オプションの「現行フォーマット」警告は、getCheckedCardList に基づき、フォーマット別のボードごとの最小・最大枚数、サイドとの合算視点、およびカード合法性情報（公開エントリー向けチェック再利用）によりメッセージを積む。ここでの禁止・制限・レストリクション等の検出順はユーティリティ実装順に依存するが、画面上は警告のみであり保存は済んでいる。

データ整合性

観点内容
モデルテキスト列とデッキカード子行毎送信で子は全削除後にリストから再生成する。整合は保存処理が完了した時点で一致するまで進むが、異常終了すると途中状態の可能性がある（明示的トランザクション境界はシングル処理内の複数 flush に依存）。
画面上のプレイヤー／イベント／代表カードモデルと補助表示が食い違わないように、イベント三項目やプレイヤー名／DCI は ID 側があれば空欄でも補完して表示することがある。
一覧の検索条件削除・更新リダイレクトはページキーを見るのみで、一覧の入力条件ストアは詳細側では更新しない。

本機能では API 呼び出し・バッチ実行を扱わない。
