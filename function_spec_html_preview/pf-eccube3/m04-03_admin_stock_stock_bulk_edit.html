M04-03（在庫一括編集）

商品検索一覧で選択した商品の規格について、増減させる在庫数と在庫変動理由を一括で入力し、まとめて在庫数を更新する画面。

概要

在庫一括編集は、商品検索一覧でチェックした商品の各規格を一覧に並べ、規格ごとに在庫の増減数・在庫変動理由・在庫変動理由区分を入力させ、送信時に各規格の在庫数を増減して更新する機能である。更新時には在庫変更履歴を記録し、在庫が0から増えた規格には入荷通知メールを送る。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。HareruyaEc プラグインの実装を確認値とする。

本機能のカスタマイズ区分はカスタマイズであり、画面・処理フロー・検証などの挙動は現行のpf-eccube3（HareruyaEcプラグイン）を正とし、永続化に関わるDB関連はリニューアル先のec-cube-enterprise実装を正とする。両者でスキーマが異なる箇所は移行先名を主とし現行名を括弧で添える。

対象はブラウザ経由の管理画面に限定する。管理画面プレフィックスは HareruyaEc プラグインの設定キー admin_route（$app['config']['admin_route']）で決まるため、本書では %eccube_admin_route% で示す。

本書の本文ではコントローラのメソッド名・クラス名は主題としない。ルート bind 名は調査補助へ退避する。

本書で扱うこと

  • 商品検索一覧から在庫一括編集画面を開く入口と、選択した商品の規格の並べ方
  • 増減させる在庫数・在庫変動理由・在庫変動理由区分の入力ルールと検証
  • 送信時の在庫数の更新計算、在庫変更履歴の記録、入荷通知メールと支店在庫連携の発火条件
  • 入力エラー時の再表示と、正常終了時の商品検索一覧への戻り

本書で扱わないこと

以下は本書では仕様確定せず、実装または別機能の設計を正とする。

  • 商品検索一覧の検索フォーム・ページング・チェックボックス選択そのものの仕様（別機能 m03-01_admin_product_product_search_list を正とする）
  • 価格一括編集・買取価格一括編集の入力ルール（同一コントローラだが対象が異なる別機能）
  • 在庫変更履歴の検索・一覧・CSV出力（M04-17 / M04-18 を正とする）
  • 入荷通知メールの文面・送信基盤、支店在庫連携の通信仕様
  • 管理画面の認証・ログイン・権限マスタの詳細

リニューアル移行時の扱い

挙動は現行のpf-eccube3を正とし、DB関連はリニューアル先のec-cube-enterpriseを正とする。在庫変更履歴のスキーマは現行と移行先で名称・構成が異なるため、本書のDB記述はec-cube-enterpriseの名称を主とし現行名を括弧で添える。差分は次のとおり。

挙動・画面の正は現行（pf-eccube3）の直接更新型とし、本書の処理フロー・業務ルール・表示メッセージは現行を記述する。一方、永続化の正はリニューアル先（ec-cube-enterprise）であり、DB操作は承認ワークフロー型となる（下記「DB操作」節を正とする）。両者は更新の確定タイミングと対象テーブルが構造的に異なるため、結合試験では参照リポに応じて期待値を読み替える。

フロント挙動

観点内容
表示要素規格ごとに1行を並べる表を表示する。列はID、商品名、言語、状態、在庫数、増減させる在庫数、当日・昨日・3日間・1週間・1ヶ月間の販売総数。増減させる在庫数の列には、在庫変動理由区分の選択、増減数の数値入力、在庫変動理由のテキスト入力を縦に並べる。
JS 挙動画面読込時に各行の増減数入力を監視し、増減数が0以外のとき在庫変動理由の入力欄に required を付け、0のとき外す。サーバ側でも0以外で理由空はエラーにするため、JS は補助的なクライアント検証である。
CSS・レイアウト管理画面共通の表スタイル。増減数入力にはサーバ側で算出した最小値・最大値の属性を付ける（最小は現在庫を0にできる値、最大は在庫上限まで増やせる値）。
モーダル・ポップアップ本機能ではモーダル・トーストを表示しない。エラーは画面上部とフォーム直下に表示する。

処理フロー

在庫一括編集画面を開く

  1. 商品検索一覧で1件以上の商品を選び「在庫一括編集」を押下する。選択IDは productIds として送られる。
  2. productIds が空のときは「商品が選択されていません。」を表示し、商品検索一覧の保持ページへリダイレクトする。
  3. 選択商品の検索条件フォームから言語・状態の選択を読み取り、表示対象の規格を絞り込む補助情報とする。
  4. 選択商品の規格を在庫更新向けに取得し、各規格を1行に展開した一括編集フォームを組み立てて画面を表示する。

在庫一括編集を登録する

  1. 「登録」を押下すると各行の入力が送信される。
  2. フォーム全体を検証する。増減数が0以外で在庫変動理由が空の行、在庫がマイナスになる行、在庫上限を超える行、在庫変動理由が上限を超える行はエラーとする。
  3. 検証エラーがあれば、選択商品の規格を取り直してフォームを再構築し、エラー文言とともに同一画面を再表示する。在庫は更新しない。
  4. 検証を通った行のうち、増減数が0の行は更新対象から除外する。
  5. 各更新対象の規格について、新しい在庫数を現在庫＋増減数で求め、規格在庫と規格本体の在庫数を更新する。更新前在庫が0だった規格は入荷通知の対象として記録する。
  6. 在庫変動理由区分が入荷またはマスタ更新で、かつ増減数が正のときは、規格拡張の入荷集計列（直近期間別の入荷数）に増減数を加算する。
  7. 各更新対象について在庫変更履歴を1件作成する。理由メモが未指定なら既定文言「価格・在庫一括更新による在庫数更新」を用いる。
  8. 支店向けに本店在庫の更新を通知する。入荷通知対象がある場合は入荷通知メールを送る。
  9. 永続化を確定し、「登録が完了しました。」を表示して、商品検索一覧の保持ページへリダイレクトする。

集計条件

指標集計の要点
一覧へ並べる規格選択商品IDの規格を在庫更新向けに取得する。商品検索の言語・状態選択があれば、その条件で表示対象規格を絞る補助に用いる。
販売総数の各列規格拡張に保持する期間別の販売数量（当日・昨日・3日間・1週間・1ヶ月間相当）を表示する。本画面では再集計せず保持値を表示する。

業務ルール・計算

項目内容
新在庫数の計算規格ごとに新在庫数＝現在庫＋増減させる在庫数。負の増減数で減算する。
更新対象の判定増減させる在庫数が0の行は更新しない。0以外の行のみ在庫数を更新し履歴を記録する。
入荷通知の判定更新前在庫が0だった規格を入荷通知対象とする。対象が1件以上あれば入荷通知メールを送る。
入荷集計の加算在庫変動理由区分が入荷またはマスタ更新で、増減数が正のときのみ、規格拡張の入荷集計列に増減数を加算する。
履歴の理由メモ在庫変動理由が入力済みならその値、未指定なら既定文言を履歴メモとする。
上限・下限新在庫数が0未満になる更新は不可。新在庫数が在庫桁数の上限（9桁、最大999999999）を超える更新は不可。

入力項目

項目名必須／任意最大長初期値保存先・扱い
増減させる在庫数必須整数。フォームの最大10桁、HTML 上の最大値属性は999999999。新在庫数の上限は在庫桁数9桁（999999999）0規格在庫 dtb_product_stock.stock と規格 dtb_product_class.stock を新在庫数で更新。フォームキー stock_change。新在庫数が0未満・上限超過はコレクション検証でエラー。
在庫変動理由区分必須—区分マスタの先頭相当在庫変更履歴 dtb_stock_history.stock_change_type_detail_id（現行 stock_change_type_id）。フォームキー stock_change_type_id。区分マスタは移行先 mtb_stock_change_type_detail（現行 mtb_stock_change_type）の単一選択。入荷・マスタ更新かつ増減数が正のとき入荷集計列も加算。
在庫変動理由増減数が0以外のとき必須、0なら任意最大65535文字（設定キー stock_history.memo）空在庫変更履歴 dtb_stock_history.stock_change_reason（現行 memo）。フォームキー stock_change_memo。未入力かつ増減数0以外は行ごとにエラー。未指定で更新成立時は既定文言を保存。

増減数が0以外で在庫変動理由が空のときは、行の送信後処理とコレクション検証の双方で「ID: …の在庫変動理由が入力されていません。」相当のエラーになる。商品規格ID（product_class_id）と現在庫（stock）は隠し項目として送られ、計算と表示にのみ用いる。

エッジケース

ケース扱い
商品未選択で開く「商品が選択されていません。」を表示し商品検索一覧へ戻す。
選択した規格が送信時に削除済み「…：対象の商品は既に削除されています。」を表示しエラー扱いとする。当該行は更新しない。
増減数0の行更新せず履歴も残さない。理由欄は空でもよい。
新在庫数が負になる行「…：在庫がマイナスになる更新はできません。」を表示し全体を更新しない。
新在庫数が上限超過の行「…：在庫の合計が…を超える更新はできせん。」を表示し全体を更新しない。
在庫変動理由が上限超過「ID …：在庫変動理由は最大65535バイト以下で入力してください。」を表示し全体を更新しない。

データ整合性

観点内容
規格在庫と規格本体同一更新で dtb_product_stock.stock と dtb_product_class.stock を同じ新在庫数に揃える。
履歴との整合更新成立した規格ごとに在庫変更履歴を1件作る。変更前在庫と変更後在庫を記録する。
同時更新本画面は表示時点の在庫を現在庫として計算する。送信までに他処理が在庫を変えた場合、その差分は考慮しない。
支店連携永続化確定後に支店へ更新を通知する。連携の到達保証は連携機能側の設計を正とする。

本機能では外部 HTTP API の呼び出しやバッチ実行を扱わない。入荷通知メール送信と支店在庫連携の通知は更新処理内で行う。

DB操作

永続化の正はリニューアル先（ec-cube-enterprise）であり、一括編集は承認ワークフロー型である。テーブル名・操作は ec-cube-enterprise を正典とする。現行（pf-eccube3）の直接更新型との差は「リニューアル移行時の扱い」を参照。

操作種別対象テーブル契機・条件
登録dtb_stock_edit_approval一括編集の登録時に承認単位を1件作成する（approval_status=未承認）。
登録dtb_stock_edit_approval_detail対象規格ごとに編集明細を1件作成する。
登録dtb_stock_approval_list承認対象リストを1件作成する（history_source_type_id=STOCK_BULK_EDIT、未承認）。
更新dtb_product_stock在庫変動区分が廃棄のときのみ、当該規格在庫の stock を即時更新する。入庫・マスタ更新等では即時更新しない（承認後に反映）。
登録dtb_stock_history在庫変動区分が廃棄のときのみ、在庫変更履歴を1件作成する（history_source_type_id=STOCK_EDIT）。

現行（pf-eccube3）では、上記に代えて、登録時に対象規格すべての dtb_product_class.stock と dtb_product_stock.stock を即時更新し、各規格に dtb_stock_history を都度作成する。
