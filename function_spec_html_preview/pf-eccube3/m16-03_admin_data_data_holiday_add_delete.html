データ管理 — 祝日の追加・削除

概要

HareruyaEc プラグインが管理画面「データ管理」配下に提供する「祝日管理」画面において、mtb_holiday に祝日を1件追加したり、一覧から1件削除したりする機能である。同一画面には日本の祝日カレンダーライブラリから期間指定でまとめて登録する処理もあるが、本書では手入力による新規追加と削除を主題とし、一括読込の詳細フローは対象外とする。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。カスタマイズ区分は「現行踏襲」。画面・挙動は pf-eccube3 配下の HareruyaEc プラグインのソースを確認値とし、DB関連（テーブル・列・型・制約・関連）は ec-cube-enterprise の実装を正とする。

対象はブラウザ経由の管理画面に限定する。

本文ではコントローラのメソッド単位の解剖を主題としない。本文ではルートbind名やSymfonyのルートnameの網羅は主説明としない。「利用者視点の入口」にHTTPメソッドとサイトルートからのパスパターンを書く。コード探索でbind名が必要なときだけ「調査補助」へ書く。

リニューアル移行時の扱い

  • 本機能の DB は現行（pf-eccube3 の HareruyaEc プラグイン）と移行先（ec-cube-enterprise コア）で同一スキーマである。mtb_holiday（id / date / name(VARCHAR(64), NULL可)）のテーブル名・列名・型は一致するため、DB記述はそのまま移行先の正とする。
  • 祝日と催事の関連は、両リポとも mtb_holiday から催事テーブルへの直接FKは持たず、dtb_event_detail.holiday_flg（BOOLEAN）で表す。本機能の追加・削除時に同日の催事明細の holiday_flg を更新する副作用も移行先で同等。
  • 画面・挙動は現行（pf-eccube3）の確認値。移行先では祝日管理がコア（管理画面「データ」配下）に存在する。現行はプラグイン提供、移行先はコア提供である。
  • 現行と移行先でスキーマ差は確認されていない。差が生じた場合のみ本節に追記する。

処理フロー

一覧を表示する（GET admin_holiday_list）

  1. 管理画面の認証・共通制約を通過する。
  2. 追加用フォームビルダと一括読込用フォームビルダを名前だけから生成しビューを用意する（一覧描画時点ではリクエストをバインドしない）。
  3. 祝日マスタを日付昇順で全件取得する。
  4. Twig で一覧・両フォームを描画する。

手入力で祝日を追加する（POST admin_holiday_add）

  1. 管理画面の認証・共通制約を通過する。
  2. 追加フォームを生成しリクエストでバインドする。
  3. 共通トレイトにより、フォーム名に対応する CSRF トークンを検証する。成功時はトークンを更新する。
  4. Symfony の検証が失敗した場合、管理画面向けエラー鍵 admin.register.failed を積み、一覧ルートへ HTTP リダイレクトする（同一レスポンス内でのフィールドエラー表示はしない）。
  5. 送信された日付と同一の日付を持つ行を検索し、1件でもあればプラグイン定義メッセージ鍵 hareruyaec.holiday.overlap を積み、一覧へリダイレクトする。保存はしない。
  6. 重複が無ければ新規行を組み立て、日付・名称をセットして永続化し、成功鍵 admin.register.complete を積む。
  7. その日の開始時刻がイベント詳細の開始日時と同日スパンに入る全行について、祝日フラグをオンに更新し、行ごとに永続化処理を呼ぶ実装である。
  8. 一覧ルートへ HTTP リダイレクトする。

一覧から祝日を削除する（POST admin_holiday_delete）

  1. 管理画面の認証・共通制約を通過する。
  2. フォーム無しの経路で共通 CSRF トークンを検証する（フォーム名ではなくアプリケーション共通のトークン鍵）。成功時はトークンを更新する。
  3. URL の数値 ID に対応する行を取得する。無ければアプリケーションエラー応答となる記述がある。
  4. 行を削除してフラッシュし、成功鍵 admin.delete.complete を積む。
  5. 削除した行の日付について、イベント詳細リポジトリが「その暦日に開始する詳細」を検索する条件で該当行を取得し、各行の祝日フラグをオフにして永続化する実装である（詳細は複数回フラッシュされる）。
  6. 一覧ルートへ HTTP リダイレクトする。

業務ルール・計算

本機能では金額計算や複合スコアリングを行わない。

入力項目（手入力による追加のみ）

追加フォームは初期表示では DOM 上非表示でも、一覧 GET 時にトークン付きで生成される。

項目名必須／任意最大長初期値保存先・扱い
祝日名必須64 文字（ウィジェット maxlength および Symfony Length max と一致）空（プレースホルダ「名称」）mtb_holiday.name。NotBlank、最大 64。
日付必須単一行日付入力、yyyy-MM-dd空の単一行フィールドmtb_holiday.date。Symfony の date 型、datetime 入力、single_text。フォームに Symfony の Length は無いが DB は date 型列である。

補足: 日付が同一の行が既に存在する場合、追加は拒否されプラグインの重複メッセージが表示される。

エッジケース

ケース扱い
同一日付が既に登録済み新規追加は保存せず重複エラーで一覧へリダイレクトする。
追加フォームの検証エラー（名称未入力、長さ超過など）admin.register.failed で一覧へリダイレクトする。入力値の再提示はしない。
削除対象 ID が存在しないソース上は一覧更新前にエラー応答となる分岐がある。
同日にイベント詳細が無い祝日フラグ追随ループは対象ゼロであり、イベント詳細テーブルへの書き込みは発生しない。

データ整合性

観点内容
一覧とマスタ一覧は常に mtb_holiday の現在状態を日付昇順で読む。追加・削除の直後はリダイレクト GET で再読込される。
祝日マスタとイベント詳細フラグ追加時は同日開始のイベント詳細へ祝日フラグオンを書き込む。削除時はオフにする。イベント開始日時が別日へ変更済みであれば、その変更結果とフラグの整合は別機能の保存処理に依存する。
トランザクション祝日の flush とイベント詳細の複数 flush が別単位である。途中失敗時の原子性はフレームワーク既定と DB 設定に依存し、本書では個別トランザクション境界までを確認値とする。

API/バッチ結果

本機能では外部 HTTP API の呼び出しやサーバ側バッチの起動を行わない。

試行制限

本機能ではレートリミットや試行回数制限を扱わない。

ログ・監査

本機能専用の監査ログ出力はソース上は主眼としていない。永続化は Doctrine 経由である。

ログに出してはいけないもの

  • パスワード
  • なりすまし対策トークン
  • Cookie 値
  • セッション ID の完全値
  • Remember Me トークンの原値

セッション

本機能は検索条件のセッション保存を行わない。管理画面セッション自体はログイン共通処理に依存する。

セッションへ保存しない情報

祝日フォームの入力値をセッションに退避する処理はない（失敗時は再入力が必要）。

Cookie

本機能独自の Cookie は設けない。セッション Cookie は管理画面共通を正とする。

排他制御・トランザクション

明示的な楽観ロック版本管理は祝日マスタおよび本画面からは行わない。同一日付の同時追加は重複チェックのタイミング次第で競合しうるが、一意制約の有無はスキーマを正とする。
