商品管理 — 購入グループ管理

概要

管理画面「商品管理」配下から到達できる、mtb_sell_group（購入グループ）および関連するmany-to-many（支払方法・配送方法）を維持する機能である。同一テンプレート上に入力フォーム（新規または編集中の一行）と、論理削除対象外の一覧表を並べ表示し、新規作成・更新・論理削除を行う。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。ソースは eccube-enterprise コア（Symfony の管理画面ルート・アプリケーション層およびテンプレート）を確認値とする。

本機能のカスタマイズ区分は現行踏襲である。挙動の参照は現行リポ pf-eccube3 の HareruyaEc プラグイン実装を正とし、DB関連は ec-cube-enterprise を正とする。現行と移行先のスキーマ差は「リニューアル移行時の扱い」へ集約する。

対象はブラウザ経由の管理画面に限定する。

本文ではSymfonyのコントローラ型やメソッド名を主題としない。本文ではルートbind名やSymfonyのルートnameの網羅は主説明としない。「利用者視点の入口」にHTTPメソッドとサイトルートからのパスパターンを書く。コード探索でbind名が必要なときだけ「調査補助」へ書く。

リニューアル移行時の扱い

DB関連の正典は ec-cube-enterprise とする。挙動は現行リポ pf-eccube3 の HareruyaEc プラグインを正とし、移行先との差は本節へ集約する。

処理フロー

一覧と新規フォームを表示する（GET m03-22_admin_product_product_sell_group）

  1. 管理画面の認証状態を経てルートへ到達する。
  2. 削除日時が null の購入グループを主キー昇順で読み込む。
  3. 入力対象となる空の業務モデルへフォーム型をバインドし、画面へ渡す。編集フラグは偽で、編集中の対象参照は渡さない。
  4. Twig で上部フォーム送信先は create ルートとなる。

新規作成する（POST m03-22_admin_product_product_sell_group_create）

  1. 新規モデルへ同型フォームを生成し、handleRequest で束ねる。
  2. SymfonyのフォームCSRFおよび各フィールド制約により妥当性評価を行う。
  3. 妥当なら現在日時を作成・更新両日時へ入れ、ログイン管理者が運用アカウント種別として解釈される場合は、その参照を更新者へ記録して永続レイヤへ保存対象として登録し単一トランザクションへ flush する。成功フラッシュ鍵は admin.common.save_complete。一覧 GET へリダイレクトする。
  4. 妥当でなければ一覧再取得およびエラー状態のフォーム表示で応答コード 200 とする。

編集表示する（GET m03-22_admin_product_product_sell_group_edit）

  1. {id} に該当する永続モデルをパラメータ解決により取得できなければ、フレームワークが 404 とする。
  2. モデルの削除日時が非 null の場合は、「対象が見つからない」趣旨の翻訳メッセージをエラースロットへ積み、一覧へリダイレクトする。
  3. そうでなければモデル結合済みフォームを生成する。一覧は再読込し、現在 ID が編集中であるフラグおよび参照オブジェクトを渡す。送信先 URL は update となる。

更新する（POST m03-22_admin_product_product_sell_group_update）

  1. {id} 解決失敗時は 404 とする。
  2. 削除日時が非 null のモデルへの送信は一覧へリダイレクトし変更はしない。
  3. フォーム処理は新規作成と同型。妥当時は作成日時は触らず更新日時のみ現在時刻、更新者はログイン状態に準じ記録され、flush 後成功フラッシュと一覧リダイレクト。
  4. 失敗時は編集フラグ維持で同一テンプレ再表示。

論理削除する（DELETE m03-22_admin_product_product_sell_group_delete）

  1. アンカー送信に付随するCSRF確認を親抽象で行い、失敗時アクセス拒否（HTTP 403）。
  2. 削除日時が既に設定済みなら削除エラークラスのフラッシュを積んで一覧へ戻す。
  3. モデルから商品側一方参照の集合が空でなければ、名称埋め込みの翻訳メッセージでエラー表示し一覧へ戻す。
  4. ここまで通れば情報ログに削除開始メッセージと主キーを残し、deleted_at を現在時刻で flush、完了ログ、削除完了フラッシュ、一覧へリダイレクトする。

集計条件

指標集計の要点
画面上の一覧行数永続モデル側で削除日時が null のものに限定した件数。その場のソート規則は主キー昇順のみで、名前検索などは無い。

フォーム送信・削除時の判定順序（POST と DELETE に共通する範囲を含む）

順序判定結果
1（DELETE のみ最初）共通CSRF名のトークンが有効か無効なら403。
2（GET 編集・更新）対象モデルが論理削除済みかGET編集およびPOST更新とも削除済みなら一覧リダイレクト（編集開始時は特定のエラーメッセージ、更新時は名称等を変えず）。
3（POST）Symfonyフォームと宣言制約により妥当か否なら同一画面レイアウトと検証結果表示。
4（POST 成功時）日時および更新者の付与、persist と flush の実行後リダイレクトはい。
5（DELETE）商品コレクション空か否ならエラーと一覧へ。
6（DELETE 成功時）論理削除日時のセットとログはい、一覧へ。

業務ルール・計算

項目内容
支払方法の選択肢表示フラグが真である支払のみ。並びキーが大きいものから順に並べ替えクエリにより取得し、チェックボックス一覧にする。未選択許容。送信時選択集合が中間表へ反映される。
配送方法の選択肢同上で配送側のマスタであり、並び順定義および表示フラグ条件はそれぞれのマスタ側の並び項目で降順になるようクエリ側で並べる。未選択許容。
予約商品フラグUIは単一チェック。永続モデル側は整数0または1。フォーム側でモデル変換により双方向へマッピングする。

本機能では金額丸めや集約集計などの別種の業務計算は行わない。

エッジケース

ケース扱い
商品が一つでも紐づく購入グループへの削除要求flush しない。フラッシュへ埋め込み名称付きエラー文案を載せ一覧へリダイレクト。
既に論理削除されたIDを編集URLで開く一覧へリダイレクトし、対象未取得のエラーメッセージをフラッシュへ積む。404にはせずパラメータ変換結果の実体読込は起こり得る。
POST 送信で検証失敗一覧表は送信処理内でも再クエリ済みであり、画面上は常に削除されていない全集を伴う編集状態または新規状態で検証結果を見せる。
一覧に行が無いとき表はヘッダのみの空データ相当で描画される。フォームだけで新規登録は継続可能。
