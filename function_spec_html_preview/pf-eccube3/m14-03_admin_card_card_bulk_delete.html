カード管理 — 一括削除

処理フロー

一括削除を実行する（POST m14-03_admin_card_card_bulk_delete）

  1. 管理画面の認証・共通制約を通過する。
  2. リクエストボディの _token を、コア既定 ID（実装では Constant::TOKEN_NAME と一致する文字列）として CSRF プロバイダで検証する。無効ならアクセス拒否（HTTP 403）となる例外を投げる。成功時は同プロバイダでトークンを更新する。
  3. セッションキー admin.card.search.page_no を読む（互換の別画面パスでは空のときがある）。
  4. ルートパラメータで ID が無い一括経路では、ボディの cardIds を ID 群とみなす。cardIds がリクエストに存在しない（null）とき、フラッシュは付けず、admin.card.search.page_no が空でなければ m14-01_admin_card_card_search の当該ページへ、空なら admin_card_list へリダイレクトして終了する。
  5. cardIds を先頭から順に走査する。要素が空文字相当、またはカードマスタが取得できないとき、HTTP 404 で打ち切る。
  6. 各 ID について、デッキ採用行（deckCards の件数）が 1 件でもある、または「論理未削除の商品がカード詳細経由で存在する」ネイティブ問い合わせの件数が 1 以上のとき、削除ブロックとみなす。翻訳キー admin.card.delete.failed にカードの合成名を埋め込んだエラーメッセージをフラッシュし、この時点までに削除完了した ID だけを支店通知へ渡してから Referer へリダイレクトする。
  7. ブロックされなければ、カード用レポジトリのネイティブ更新で、当該カードにぶら下がるカード詳細に結び付いていた商品規格の card_detail_id を NULL に切り離す（販売商品の親子構造は維持し、印刷版参照だけ外す）。
  8. 汎用ヘルパの再帰削除で、Doctrine 上 oneToMany として子側へマッピングされたコレクションを深さ優先で remove し、最後に当該カードマスタを remove して flush する（ manyToMany はこの再帰の対象外。親エンティティ削除時の ORM の扱いはマッピングに従う）。
  9. ループ内で commit を呼ぶ実装になっている（トランザクション境界は実装を確認値とする）。
  10. すべての ID が成功したら再度 commit を呼び、翻訳キー admin.delete.complete を成功フラッシュする。
  11. 支店連携サービスに、リクエストで受け取った ID 配列（文字列のまま混在し得る）を渡して更新通知を送る。通知結果はログに残し、失敗時は支店連携エラーテーブルへ追記して flush する。
  12. admin.card.search.page_no が空でなければ m14-01_admin_card_card_search の当該ページへ、空なら admin_card_list へリダイレクトする。

論理未削除商品の有無判定（削除ブロックの内訳）

実装の SQL は mtb_card・mtb_card_detail・dtb_product_sub・dtb_product を結合し、dtb_product.del_flg = 0 の行が 1 件でもあれば「削除不可の商品が残っている」と数える。買取系テーブルはこの問い合わせに含まれない（ソース上のコメントと SQL の対応は実装を確認値とする）。

一括削除時の判定順序

順序判定結果
1CSRF トークン無効なら HTTP 403（アクセス拒否）。
2ボディに cardIds キーが存在するか無ければリダイレクトのみ（メッセージなし）。
3各 ID が非空かつ DB にカードが存在するか満たさなければ HTTP 404。
4デッキ採用があるかあればエラーフラッシュ・部分通知・Referer へ。
5論理未削除商品がカード詳細経由で存在するかあれば同上。
6上記を通り抜けた各 ID規格紐付け解除・ORM 削除・flush。

入出力

種類内容
入力POST ボディ: cardIds[]、_token。検索条件は同じフォームの他フィールドも載るが、当ルートでは参照しない。
成功時出力302 で m14-01_admin_card_card_search（ページ番号付き可）または admin_card_list。成功フラッシュ admin.delete.complete。
失敗時出力CSRF 失敗は HTTP 403。カード未存在は HTTP 404。削除ブロックはエラーフラッシュと 302 で Referer。
副作用mtb_card 周辺の物理削除（ORM）、dtb_product_sub の NULL 更新、支店通知、ログ、支店エラー表の追記。

業務ロジック

業務ルール・計算

本機能では数量計算や料金計算は行わない。削除の順序は POST の cardIds 配列の反復順に依存する。

入力項目

項目名必須／任意最大長初期値保存先・扱い
行チェック（一覧）任意（未選択なら送信されない）カード ID の整数表現に準ずる未チェックボディキー cardIds（配列フィールド名 cardIds[]）。未送信時は null 扱いでリダイレクトのみ。
CSRF トークン（隠し）必須実装のトークン長サーバが発行した現行値ボディキー _token。コアの既定トークン ID で検証。成功後にプロバイダが更新。

エッジケース

ケース扱い
cardIds が空配列として送られるループが 0 回になり、成功フラッシュと支店通知（空配列に近いパラメータ組み立て）に至り得る。実装を確認値とする。
複数 ID のうち途中でブロックその時点までに flush 済みの削除は残る。フラッシュは 1 件分のエラーのみ。支店には削除済み ID のみ通知。
支店 API 失敗画面は成功メッセージのままリダイレクトし得る。失敗内容はログと支店連携エラーテーブル側に残る。

データ整合性

観点内容
一覧との関係削除直後はリダイレクトで一覧を再取得する。別タブの古い一覧とは一致しない場合がある。
商品マスタカード削除前に dtb_product_sub.card_detail_id が NULL に更新されるため、商品行は残りカード参照だけ失われる。
支店通知は HTTP クライアントで非同期に近い呼び出しであり、支店側反映と管理 DB 削除の厳密な同一トランザクションは保証しない。

排他制御・トランザクション

楽観ロックや明示のユーザー単位排他はない。ループ内 commit と終盤の commit があり、他セッションとの競合時は先に成功した削除と DB 制約の結果としてエラーが出る可能性がある。詳細は運用再現時の実装ログを正とする。
