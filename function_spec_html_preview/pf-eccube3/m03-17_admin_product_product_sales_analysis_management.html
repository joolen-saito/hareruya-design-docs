商品管理 — 売上分析タグ登録/編集

概要

mtb_tag_sales_analysis（売上分析タグマスタ）を管理画面で新規登録・編集し、一覧・ページ送り・表示件数変更を同一画面上に並べて扱う機能である。ナビゲーション上の名称は翻訳キー admin.product.sales_analysis_management（確認値として「売上分析登録/編集」）。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。確認値は ec-cube-enterprise における売上分析タグ用ルートおよび対応した管理画面の一覧・編集処理、入力フォーム定義、マスタ本体 mtb_tag_sales_analysis とテンプレート tag_sales_analysis.twig、コントローラ基底での無効フォーム時応答および CSRF 検証、別画面および CSV により商品へタグを紐付ける経路とする。カスタマイズ区分は現行踏襲であり、現行挙動は pf-eccube3 を参照し、DB関連（テーブル名・列名・型・制約・関連）は ec-cube-enterprise を正とする。

対象はブラウザ経由の管理画面に限定する。

コントローラの処理名を本文の中心には置かず、本文ではルートbind名やSymfonyのルートnameの網羅は主説明としない。「利用者視点の入口」にHTTPメソッドとサイトルートからのパスパターンを書く。コード探索でbind名が必要なときだけ「調査補助」へ書く。

処理フロー

画面を表示する（GET）

  1. 管理画面の共通認証を通過する。
  2. ルートによって既存エンティティを読み込むか、読み込めないときは（主キーの無い新規ケースのみ）まっさらな行インスタンスをフォームデータとする。
  3. クエリまたはパスの page_no から現在ページ番号を決め、admin.product.tag_sales_analysis.page_no に書き込む。欠けるときはセッション既存または 1。
  4. クエリの page_count があれば整数化して admin.product.tag_sales_analysis.page_count に書く。無いときはセッション既存または 10。
  5. リポジトリのクエリビルダでエイリアス t とし、rank 昇順の一覧を、アプリケーションのページネータで上記ページ番号・件数に分割する。
  6. tag_sales_analysis.twig でフォームの action は新規なら無修飾 store、編集なら同一主キーを付けた store URL とする。

登録または更新する（POST m03-13_admin_product_product_tag_sales_analysis_store）

  1. GET と同様のエンティティの起点でフォームを生成し、handleRequest で POST をとる。
  2. 送信が無い、または検証に失敗した場合、フラッシュに admin.register.failed を積み（確認値として「登録できませんでした。」）、セッションにあったページ番号と件数で一覧を組みなおして同テンプレートで返す。このとき無効フォームがあるとコントローラ基底の実装により、通常は HTTP ステータス 422 を返す。
  3. 検証が通ったデータを persist し、flush する。単一トランザクション境界はDoctrineの単位に従う（明示トランザクションは張らない実装）。
  4. flush が一意制約違反（永続化層が検知）で終わった場合、フラッシュに admin.error.non_unique を積み（確認値として「値が重複しています。」）、一覧を組みなおした同テンプレートを返す。
  5. 成功時、admin.register.complete を積み、m03-13_admin_product_product_tag_sales_analysis へ HTTP リダイレクトする。リダイレクトパラメータに保存後主キーを渡すため、生成 URL はクエリ id が付く（パス側の {id} は一覧トップには無く、画面は新規モード側のリスト表示に落ちやすい。実装確認値）。

削除する（DELETE）

  1. CSRF が要件を満たすか共通処理で検証し、無効なら例外でアクセス拒否（HTTP 403）となる。
  2. 売上分析タグ行にひも付く商品が 1 件でもあるなら、admin.tag.delete.failed で名称を埋めフラッシュして一覧へリダイレクトする（確認値として「商品で使用されているため、当該名称のタグは削除することができません。」）。
  3. 商品側にひも付きが無くとも、注文明細との結合があるなら、admin.order_tag.delete.failed をフラッシュして一覧へリダイレクトする（確認値として「購入済の商品で使用されているため、当該名称のタグは削除することができません。」）。
  4. 両方とも結合無しなら削除予約後 flush し、admin.common.delete_complete を積んで GET m03-13_admin_product_product_tag_sales_analysis へリダイレクトする。

集計条件

本機能では一覧総件数の算出以外に業務寄りの独自集計は行わない。ページャライブラリが総件数を求めるのみである。

指標集計の要点
一覧総件数mtb_tag_sales_analysis 全件を rank 昇順として対象にし、page_count で分割する。

登録・更新時の判定順序

順序判定結果
1フォームが送信済みか、かつ項目検証が通るか否ならエラーフラッシュと再描画。
2persist と flush一意制約違反ならエラーフラッシュと再描画。
3上記すべて成功成功フラッシュと一覧へのリダイレクト（クエリ id 付き）。

業務ルール・計算

項目内容
一覧の並びrank の昇順。一覧上にドラッグ並べ替えの UI は無い。
並び順の意味rank が小さい行がクエリ順で先頭に来る。

本機能では加算税率や売上集計などの業務計算を行わない。

データ整合性

観点内容
一覧とフォーム一覧は全件クエリからのページネーション結果。フォームはルート id の 1 行または新規用の未保存インスタンス。同一画面でもデータ起源が別になる。
商品側の関連dtb_product_tag_sales_analysis が 1 件でもあれば当該タグを削除しない。一覧の内容と DB は GET 読み込み時点での整合。
注文明細側の関連dtb_order_item_tag_sales_analysis が 1 件でも連結されていれば削除しない。
同時更新楽観ロックは持たない。後続の UPDATE が単純に上書きされる。
