デッキ管理 — 一括削除

概要

HareruyaEc プラグインが管理画面「デッキ管理」の検索一覧から、チェックボックスで選んだデッキをまとめて削除する機能である。一覧と同一の HTML フォームにぶら下がる「一括削除」ボタンが、formaction で専用の POST URL に送信を切り替える。単一デッキの削除（別ルートの DELETE 相当のリンク送信）とは HTTP メソッドと CSRF の載せ方が異なるが、サーバ側の削除可否チェックやデッキ内カード削除・デッキ本体の除去の流れは同一の処理分岐として実装されている。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。pf-eccube3 に配置された HareruyaEc プラグインのソースを確認値とする。

本機能のカスタマイズ区分は現行踏襲である。挙動は現行リポ（pf-eccube3 の HareruyaEc プラグイン）を参照し、DB関連は ec-cube-enterprise を正とする。

対象はブラウザ経由の管理画面に限定する。

コントローラのメソッド名は本文の主題としない。本文ではルートbind名やSymfonyのルートnameの網羅は主説明としない。「利用者視点の入口」にHTTPメソッドとサイトルートからのパスパターンを書く。コード探索でbind名が必要なときだけ「調査補助」へ書く。

リニューアル移行時の扱い

  • ec-cube-enterprise にデッキ関連テーブル一式が実装されており、本機能の削除対象は移行先に存在する。
  • デッキ（dtb_deck）の主キー列名が異なる。移行先 ec-cube-enterprise では id、現行 pf-eccube3 では deck_id である。本書が dtb_deck の主キーを deck_id と記す箇所は、移行先では dtb_deck.id に対応する。デッキ内カード（dtb_deck_card）および記事との中間テーブル（dtb_article_deck）の外部キー列は現行・移行先とも deck_id のままである。
  • デッキの削除前に更新する member_id 列、および論理削除列 deleted_at は現行・移行先とも存在する。
  • 削除可否判定で参照する記事とデッキの中間テーブル（dtb_article_deck、列 deck_id、article_id）、および親削除前に除去するデッキ内カード（dtb_deck_card、列 deck_id、card_id、board_id、count）は移行先に存在し同一スキーマである。

処理フロー

一括削除を実行する（POST m15-03_admin_deck_deck_bulk_delete）

  1. 管理画面の認証・共通制約を通過する。
  2. フォームオブジェクト無しで CSRF を検証する。ボディ直下の _token を、コアの既定キーと一致する ID としてトークンプロバイダで検証する。無効ならアクセス拒否（HTTP 403）となる例外を投げる。成功後、プロバイダでトークンを更新する。
  3. セッションキー admin.deck.search.page_no を読む（本文中では実装確認値としてこの文字列で示す）。
  4. 単一削除用のルート引数 $id が無いとき、ボディの deckId を ID の配列とみなす。deckId が null（キー無し相当）なら、フラッシュは付けず、admin.deck.search.page_no が空でないときはルート m15-01_admin_deck_deck_search の当該 page_no へ、空のときは admin_deck_list へリダイレクトして終了する。
  5. 配列を先頭から走査する。各要素について、その主キーでデッキを取得する。取得できない場合は HTTP 404 で終了する（後続 ID は処理されない）。
  6. 当該デッキについて、記事との many-to-many コレクション件数が 0 より大きい場合、フラッシュとして翻訳キー admin.deck.is_used.article を積み、HTTP ステータスのままレスポンスを返せばよい状態で Referer ヘッダの URL にリダイレクトして終了する。この時点までに正常完了した削除は既にフラッシュ済みであり、一覧は再読込されていないので、並び順・残件との表示は一覧側のクエリタイミングに従う。
  7. デッキに紐づくすべてのデッキ内カードを ORM で remove する。
  8. デッキの更新者として、現在ログイン管理アカウントの主キーをデッキの member_id にセットし、persist のうえ一回 flush する。
  9. 続けてデッキ本体を remove し、再度 flush する。
  10. すべての要素で上記ブロックなく完了した場合、フラッシュとして翻訳キー admin.delete.complete を積む。
  11. admin.deck.search.page_no が空でなければ m15-01_admin_deck_deck_search の当該ページへ、空なら admin_deck_list へリダイレクトする。

「記事中」の判定の要点（実装上の入力）

処理はデッキの articles コレクションの count() を参照する。このコレクションが非空なら削除しない。

集計条件

本機能では売上集計や一覧件数の再計算は行わない。

一括削除時の判定順序

順序判定結果
1CSRF トークン無効なら HTTP 403（アクセス拒否）。
2ボディに deckId が存在するか（null でないか）無ければリダイレクトのみ（フラッシュ無し）。
3各要素でデッキが DB から取れるか取れなければ HTTP 404 で打ち切り。
4articles 件数が 0 か0 より大きければエラーフラッシュと Referer へリダイレクト。
5上記を満たす各要素デッキ内カード削除、メンバー ID 書き換え、flush、remove、flush。

同一 POST に重複した ID が含まれ、先行要素で削除が完了済みでも後続要素が同じ主キーを再度たどれば、ステップ 3 で 404 になり得る（実装上の順序依存）。
