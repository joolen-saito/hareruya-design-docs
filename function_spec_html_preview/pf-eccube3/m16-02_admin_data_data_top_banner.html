データ管理 — トップバナー管理

概要

HareruyaEc プラグインが管理画面に提供する「データ管理」配下のトップバナー管理である。画面上部では mtb_top_banner の各スロットについて画像 URL・リンク先・表示タイプ・言語・画像 alt・並び順をまとめて保存する。画面下部（アンカー「画像設定」）ではオブジェクトストレージ上の banner/ 配下へ画像ファイルをアップロードし、一覧・削除・公開 URL のコピーを行う。トップバナーではイベントバナーにある「表示店舗」項目は出さない。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。カスタマイズ区分は「カスタマイズ」。画面・挙動は pf-eccube3 に配置された HareruyaEc プラグインのソースを確認値とし、DB関連は ec-cube-enterprise の実装を正とする。EC-CUBE 3 コア単体では当ルートは存在しないが、移行先 ec-cube-enterprise にはコアの同等機能（トップバナーの画像アップロード・一覧・削除）が存在する。

対象はブラウザ経由の管理画面に限定する。

本文ではフレームワークのコントローラ型名やメソッド名は主説明としない。本文ではルートbind名やSymfonyのルートnameの網羅は主説明としない。「利用者視点の入口」にHTTPメソッドとサイトルートからのパスパターンを書く。コード探索でbind名が必要なときだけ「調査補助」へ書く。

リニューアル移行時の扱い

  • 本機能は画像ファイルをオブジェクトストレージ（banner/ プレフィックス配下、店舗別は banner/{html_class}/）に格納し、DBテーブルを持たない。したがってDBスキーマ上の差分は無い。
  • 画面・挙動は現行（pf-eccube3）の確認値。移行先 ec-cube-enterprise でも同等のアップロード・一覧・削除がコアのアクション（TopBannerUploadAction / TopBannerFileListAction / TopBannerDeleteAction 相当）として提供される。現行はコントローラ内に直書き、移行先はアクションクラスに分離という実装差がある。
  • 店舗別格納の絞り込みキーが異なる。現行はプラグインの mtb_shop.html_class、移行先は店舗（拠点）dtb_base_info の shop_digit を用いる。移行時はこのキー対応を移行設計で吸収する。

フロント挙動

観点内容

モーダル・ポップアップ専用モーダルはない。並び順・重複は alert。削除は共通実装の確認ダイアログに依存する。

処理フロー

画面を表示する（GET m16-01_admin_data_top_banner または m16-01_admin_data_top_banner_narrow）

  1. 管理画面の認証・共通制約を通過する。
  2. mtb_top_banner を主キー昇順で全件取得する。
  3. フォーム型 hareruyaec_banner に一覧データを載せてフォームビューを生成する。トップバナーモードでは表示タイプの選択肢が「非表示」「表示」の2値になる。
  4. 画像アップロード用に別フォームを生成する。ファイル入力、テキスト項目（送信処理では未参照）、店舗エンティティの単一選択がある。店舗絞り込み GET のときは当該店舗が既定選択になる実装である。
  5. ストレージサービスで banner/ または banner/{html_class}/ のオブジェクト一覧を取得する。一覧は PHP の配列ソートで更新日時の降順に並べ替える。
  6. 並べ替え後、先頭から最大 2000 件だけテンプレートへ渡す。
  7. Twig を描画する。

「バナー設定」を送信する（POST、ファイルなし）

  1. CSRF を検証する。失敗時はアクセス拒否（HTTP 403）となる実装である。
  2. hareruyaec_banner をバインドして検証する。
  3. 失敗時は bannerError.message に、プラグイン設定 banner.length（既定 255）を埋め込んだ admin.error.text_over を表示する文言をセットする。画像一覧は実装上ルート直下 banner/ のみ再取得する場合がある（店舗絞り込み表示との不一致リスク）。HTTP 200 で同一テンプレートを返す。
  4. 成功時、各スロットの「並び順」数値で並べ替えた結果に応じて、フォームのどの画像 URL／リンク／表示タイプ／言語／alt がどの mtb_top_banner 行に書き込まれるかを解決する（並べ替えアルゴリズムは後述「並び順と永続化の対応」）。
  5. トップバナーでは店舗との関連更新は行わない。
  6. 言語は複数選択の ID 配列から言語エンティティを取得し、多対多を置き換える。
  7. リンクはフォーム値が欠ける場合は空文字を保存する。
  8. 全行を永続化処理に渡し、一度フラッシュする。
  9. 店舗絞り込みでなければ GET /{admin_route}/banner/top へ、絞り込みなら GET /{admin_route}/banner/top/{html_class} へリダイレクトする（フラッシュメッセージの付与はこの経路では行わない）。

画像をアップロードする（POST、ファイルあり）

  1. アップロード用フォームをバインドする。CSRF は共通ヘルパで検証する。
  2. 検証失敗時は [false, null] を返し、後段でバナー設定失敗と同様にテンプレート描画へ入る。
  3. ファイル未選択なら admin.error.select_no_file を表示用エラーにセットする。
  4. ファイルサイズが 520000 バイト超なら admin.error.size_over をセットする（メッセージに上限値が埋め込まれる）。
  5. exif_imagetype が 1〜3（GIF／JPEG／PNG）のときのみ続行する。それ以外は admin.error.not_image。
  6. 店舗が未選択ならストレージディレクトリは banner/、選択済みなら banner/{htmlClassName}/。
  7. アップロードしたファイルの推定拡張子と本体をストレージへ送る。
  8. 成功時、店舗未選択なら null、選択済みなら htmlClassName を返し、リダイレクト先の絞り込み判定に使う。
  9. GET に #upload_wrap を付けてリダイレクトする。

画像を削除する（DELETE）

  1. CSRF を検証する。
  2. クエリ select_file をサーバー側エンコーディングルールに従って変換する（Windows 環境ではマルチバイトのエンコーディング変換が入る実装である）。
  3. オブジェクトが存在すれば削除する。存在しなくてもエラー画面にはせずリダイレクトする。
  4. GET に #upload_wrap を付けてリダイレクトする。

並び順と永続化の対応

  1. 各スロットごとにフォーム「並び順」の整数値を読む。
  2. 並び順の値をキーとして、当該スロットの画像 URL・リンク・表示タイプ・言語・alt のフォームフィールド名を値とするマップを組み立てる。
  3. キーで昇順ソートする。
  4. ソート後のエントリに 1 から通し番号を振り直す。
  5. その後、主キー id が k である mtb_top_banner 行に、通し番号 k に対応したフォーム値を書き込む。

この対応は「主キーが 1 からの連番で欠番がない」前提で整合する。並び順の重複はクライアント脚本で送信を阻むが、サーバー側では重複検証をしない。

データ整合性

観点内容
DB とストレージアップロードはストレージのみ更新する。バナー設定で画像 URL を手入力しない限り、新規ファイルとスロットは自動連携しない。
一覧の並び表示はストレージの LastModified 降順。バナー設定の並び順とは独立。
同時更新複数利用者が同一スロットを更新した場合、後勝ちでフラッシュされる一般的な ORM 挙動に依存する（楽観ロックは持たない）。

試行制限

本機能では試行制限を扱わない。

ログ・監査

当コントローラが専用の監査ログを出力する記述は見当たらない。オブジェクトストレージや Web サーバ側の標準ログはインフラ設定を正とする。

ログに出してはいけないもの

  • パスワード
  • なりすまし対策トークン
  • Cookie 値
  • セッション ID の完全値
  • Remember Me トークンの原値

セッション

当機能専用のセッションキー読書きは行わない。CSRF トークンの更新は共通ヘルパが行う。

セッションへ保存しない情報

バナー設定の下書きやアップロードファイル本体をセッションに保持する実装はない。

Cookie

管理画面のセッション Cookie に依存するにとどまり、本機能固有の Cookie を新設しない。

排他制御・トランザクション

明示の楽観ロック・悲観ロックはない。Doctrine の単一トランザクションとしてフラッシュされる範囲に依存する。
