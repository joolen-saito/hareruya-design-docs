カード管理 — カード検索（一覧・条件抽出）

概要

HareruyaEc プラグインが管理画面に提供する「カード管理」において、mtb_card を対象にキーワード・属性・マナコスト・フォーマット合法性などの条件で絞り込み、一覧表示・ページ送り・並び替えを行う機能である。検索条件・ページ番号・表示件数・ソートはセッションに保持し、同一セッション内の再表示やページ遷移後の復元に使う。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。pf-eccube3 に配置された HareruyaEc プラグインのソースを確認値とする。コア単体では当ルートは存在しない。本機能のカスタマイズ区分はカスタマイズであり、挙動の確認はpf-eccube3を参照し、永続化先のテーブル・列名などDB関連の記述はec-cube-enterpriseを正とする。

対象はブラウザ経由の管理画面に限定する。カード詳細の編集・削除・CSV 一括処理の業務定義の全部は別範囲とし、本書は検索・一覧表示・ソート・セッション回りを中心に記す。

本書の本文では Symfony のコントローラ型名やメソッド名は主説明としない。本文ではルートbind名やSymfonyのルートnameの網羅は主説明としない。「利用者視点の入口」にHTTPメソッドとサイトルートからのパスパターンを書く。コード探索でbind名が必要なときだけ「調査補助」へ書く。

リニューアル移行時の扱い

本機能は現行（pf-eccube3のHareruyaEcプラグイン）の挙動を踏襲する。DB関連の記述は移行先（ec-cube-enterprise）を正とする。

観点現行（pf-eccube3）移行先（ec-cube-enterprise）
カード本体カード（mtb_card。id・name_jp・name_en・text_jp・text_en・cmc）同名のmtb_cardが存在し、同名の列を持つ。
カード詳細カード詳細（mtb_card_detail。cardset_id・rarity_id・card_layout_id・illustrator_id・promotion_id等）同一スキーマ。同名のmtb_card_detailが存在する。
区分の関連表タイプ・サブタイプ・特殊等（dtb_card_cardtype等）、フォーマット（dtb_card_format。format_id・restriction_id）同名の関連表が存在する。
並び順既定はmtb_cardのid順。フォーマットはランク昇順で選択肢を構成。同一（DB列名に差は無い）。

現行と移行先でカード関連のスキーマは同一であり、移行に伴うテーブル名・列名の読み替えは生じない。本機能は参照専用で画面入力を永続化しない。

利用者視点の入口

入口URLエンドポイント期待されるふるまい
ナビからカード一覧を開くGET /{admin_route}/card検索フォームのみ表示。結果エリアは件数ゼロ相当。セッション上のカード検索状態はクリアされる。

ページリンクから N ページ目へGET /{admin_route}/card/search/{page_no}直前の検索条件とソートをセッションから復元し、N ページ目を表示する。

一覧のカード名リンクGET /{admin_route}/card/{id}カード詳細（編集）画面へ遷移する。

フロント挙動

観点内容
表示要素ページタイトルは「カード管理」。サブタイトル行に新規・CSV 取込・カード名リスト作成バッチのボタンがある。メインは単一の search_form で、上部に複合キーワード用の一行テキスト、その下にアコーディオンで詳細条件（色、マナコスト上下限、レアリティ、レイアウト、タイプ、サブタイプ、特殊、セット、フォーマットとチェック、イラスト、プロモ）。フッタに「検索」ボタン。結果部は件数見出し、CSV 出力・一括削除、表示件数ドロップダウン、ソートドロップダウン、表（チェックボックス・カード ID・カード名リンク・行メニュー）、ページネーション。
JS 挙動共通 function.js の formPropStateSubscriber により、.search-box-inner 内に入力やチェックがあるときだけアコーディオンを開いた状態にする。複合キーワードだけではアコーディオン開閉状態に影響しない。card-search.js でカードタイプ・サブタイプ・特殊・セット・フォーマット・イラスト・プロモの select に select2 を付与。「すべてクリア」で上記 select を空にし change を発火。表頭チェックで全行のチェックを同期。CSV 出力ボタンは短時間ボタン無効化の後に解除。カード名リスト作成は確認後に別 URL へ AJAX POST し、応答メッセージを alert してから全体リロード。sort-method-display.js でソートの二段ドロップダウン表示を切り替え。
CSS・レイアウトselect2 の CDN CSS、eventlist.css を読み込み。Bootstrap 横型フォームテーマで検索フォームを描画。
モーダル・ポップアップ本検索画面専用のモーダルはない。削除・一括削除は確認ダイアログはブラウザの confirm に依存する実装がある。

処理フロー

カード一覧を初期表示する（GET admin_card_list）

  1. 管理画面の認証・共通制約を通過する。
  2. セッションから admin.card.search、admin.card.search.page_no、admin.card.search.page_count を削除する。
  3. 検索用フォーム名 admin_search_card で空データのフォームを生成し、Twig を描画する。ページマスタ・一覧結果・ソートキー一覧は空または既定に近い状態である。

検索・一覧を表示する（GET または POST m14-01_admin_card_card_search）

  1. 管理画面の認証・共通制約を通過する。
  2. カード用レポジトリ参照をセットする。
  3. フォーム admin_search_card を生成する。送信前に「有効」とみなされると空の一覧で返す分岐がトレイト先頭にあるが、未送信の通常表示ではこの分岐は通らない想定である。
  4. リクエストをフォームに取り込む。
  5. クエリパラメータまたはセッションから sort を決める。リクエスト優先、なければセッション、なければ既定値 default。
  6. 同様に order を決める。既定は DESC。
  7. order が正規表現 ^(ASC|DESC|asc|desc)$ に一致しない場合、管理画面エラー文言 admin.error.sort を積み、admin_card_list と同様の初期化処理へ進む（セッション初期表示）。
  8. ページマスタを全件取得し、許容される表示件数の一覧を得る。
  9. 表示件数はセッションの admin.card.search.page_count があればそれを使い、なければ設定 default_page_count。リクエストに page_count があり、かつページマスタの値と一致すればセッションへ上書き保存する。
  10. フォームの送信データが取れない場合、セッション admin.card.search に保存したビューデータから復元する。ビューと検索データの両方が欠ける場合は admin_card_list と同等の初期表示へフォールバックする。
  11. 検索データに sort・order を合成する。
  12. レポジトリが検索データからクエリビルダを構築する。別途同条件の件数を数え、最終ページ削除直後などで現在ページが空になる場合はページ番号を 1 減らす。
  13. セッションへ admin.card.search.page_no、admin.card.search、admin.card.sort、admin.card.order、admin.card.search.page_count を書き込む。
  14. アプリケーションのページネータでクエリビルダをページ分割し、Twig へ渡して描画する。

不正な並び順パラメータを渡した場合

  1. 手順 7 で検出し、エラーメッセージを積んだうえで一覧初期表示へ遷移し、関連セッションは初期表示側の処理でクリアされる。

集計条件

指標集計の要点
一覧の総件数一覧と同じ検索データで組み立てたクエリに対し、count 集約で取得する。件数と一覧は同一レポジトリ経路を使う。
ページ内の行ページネータがクエリビルダと現在ページ・表示件数から切り出す。

検索条件適用時の判定順序（リポジトリ内）

リポジトリ実装における条件の足し込み順は概ね次のとおりである。いずれも「値が空・未選択ならその条件は付けない」形式である。

順序判定結果
1複合キーワードが非空かトークンごとに、和文名・英文名・和文ルールテキスト・英文ルールテキストのいずれかへ部分一致する行を要求し、トークン間は AND となる。
2タイプ・サブタイプ・特殊・セット・レアリティ・レイアウト・フォーマット・イラスト・プロモの各複数選択選択されたマスタ ID ごとに IN 条件として結合する。複数カテゴリ間は AND。
3色の複数選択選んだ色ごとに別結合として要求し、複数色は AND。
4マナコスト下限設定されていれば cmc が下限以上。
5マナコスト上限設定されていれば cmc が上限以下。
6フォーマットが 1 件以上選択されているか選ばれたフォーマット紐付けのうち、制限区分がレガルまたはレストリクションの行に限定する。オプションの合法性チェック用チェックボックスがオンのときはバンの行も許容リストに加える。

並び順は、ソートキーに応じて mtb_card の主エイリアス c に対する列（既定は c.id）へ order を適用する。ソートキー default は c.id ソートに対応する。

業務ルール・計算

本機能は参照専用の検索であり、画面入力をそのまま永続化テーブルへ書き込まない。検索条件はセッションのシリアライズ可能な構造として保持される。

エッジケース

ケース扱い
複合キーワードのみ入力し、アコーディオン内は空一覧はキーワード条件のみ。アコーディオンは閉じた見た目のままになりうる（inner 監視のため）。
ソート用クエリパラメータが許容パターン外エラーメッセージを積み、セッションを初期化した一覧へ戻る。
GET でブックマークした検索 URL にセッションがない検索データが復元できなければ空フォームの一覧へフォールバックする。
フォーマット未選択制限区分による追加フィルタは付かない。合法性チェックの有無も参照されない。

本機能では税額・価格・在庫などの業務計算を行わない。

データ整合性

観点内容
一覧と件数同一検索データで件数取得と一覧クエリを組み立てるため、件数とページング前提の総件数は同じ条件式に整合する。
一覧と詳細一覧の行はマスタ上の ID と名称表示に過ぎず、詳細画面の同時編集との整合は保証しない。
検索条件の再現セッションに保存されたビューデータが失効すると、GET だけでは直前の条件を再現できない。

API/バッチ結果

本機能では外部 HTTP API の呼び出しやサーバ側バッチの成否画面は扱わない。タイトル横の「カード名リスト作成」は別エンドポイントへの AJAX となるが、検索条件の保存とは独立する。
