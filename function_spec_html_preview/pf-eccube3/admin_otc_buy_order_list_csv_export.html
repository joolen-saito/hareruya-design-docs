店頭買取管理 — 買取一覧 CSV ダウンロード（買取商品明細ほか）

概要

HareruyaEc プラグインが管理画面「店頭買取管理」の「買取一覧」検索結果から、チェックした店頭買取を対象に CSV ファイルを返す機能である。画面上のラベルは「CSVダウンロード」であり、用途別に次の 6 種類をドロップダウンで選ぶ。うち在庫連携向けの 5 種類は店頭買取在庫明細（商品コード・数量など）を主とし、古物台帳向けの 1 種類は申込者単位の台帳列を返す。利用者が「買取商品一覧 CSV」と呼ぶ場面は、主に在庫明細を含む出力（EC インポート用・支店系・TC 東京用など）を指すが、画面文言は上記のとおり「CSVダウンロード」とする。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。pf-eccube3 に配置された HareruyaEc プラグインのソースを確認値とする。

対象はブラウザ経由の管理画面に限定する。

コントローラのメソッド名は本文の主題としない。本文ではルートbind名やSymfonyのルートnameの網羅は主説明としない。「利用者視点の入口」にHTTPメソッドとサイトルートからのパスパターンを書く。コード探索でbind名が必要なときだけ「調査補助」へ書く。

処理フロー

POST admin_otc_buy_order_export で CSV を取得する（共通）

  1. 管理画面の認証・共通制約を通過する。
  2. POST パラメータ otcBuyOrderIds を配列として解釈する。空または未設定のとき、フラッシュにメッセージキー admin.csv.error.export.product（日本語文言は環境の翻訳リソースに従い「1つ以上の商品を選択してください」）、管理画面フラッシュ種別は admin を用い、Referer ヘッダの URL へリダイレクトする。
  3. そうでなければ export_type を読み、その値に応じて定義済みヘッダ配列と生成処理をひもづける。
  4. set_time_limit(0) を実行する。Doctrine の SQL ロガーをオフにする。
  5. 店頭買取向け CSV サービスへ渡し、その中から export_type に対応した行生成処理を呼ぶ。処理中は次のような分岐がある（後述）。
  6. 同一オブジェクト経由でストリーム応答を組み立て、CSV サービス側で送信処理まで行われた結果を応答として返す。例外時はエラーメッセージをフラッシュして Referer へリダイレクトする。

古物台帳入力用（old_goods_account）

  1. 在庫系と異なり、export_type ごとのステータス／店舗単一チェックは行わない。
  2. 指定 ID の申込情報をクエリで集約し、1 査定につき次のヘッダに対応する列を並べた行を返す。査定 ID、査定完了日の和暦風フォーマット、買取総額、数量（詳細／個別入力の有無により式で割る集約式）、氏名結合、身分証種別名、住所（国情報により都道府県＋住所の並びが切替）、年齢（申込年月日から生年月日を差し引いた年数、floor）、電話は Excel で文字列扱いとするために先頭に ' と = を付した形式（実装確認値）、職業、適格請求書発行事業者か否、その番号。
  3. CSV の文字コード設定は共通サービス側の既定（branch_store_import 等とは異なる）に従い、ヘッダ行の前に UTF-8 の BOM を付ける。ファイル名は接頭語 old_goods_account_ に現在時刻ベースの接尾。

EC インポート用および在庫系 4 種（ec_import、branch_store_import、tc_tokyo_import、new_branch_store_import、branch_order_import）

  1. 店頭買取 ID 群について、すべてがダブルチェック済み以外のステータスを欠くか確認する（内部定数値 3 以外が 1 件でも混ざると無効）。違反時は例外メッセージに翻訳キー admin.csv.error.export.not_export_status（日本語環境では「出力対象にダブルチェック済以外のステータスが設定されています。」）。
  2. 同じ ID 群について、紐づく店頭買取の店舗 ID が複数種類になる場合は無効とし、admin.csv.error.export.not_export_shop（「出力対象が単一の店舗ではありません。」）。
  3. 在庫取得クエリのパラメータは種別により次のように分岐する。
  • 一般の在庫系（グルーピング無し、needsConditons が偽のパス、ec_import）: カード状態 ID がニアミント（内部定数 1）のみ。同じ商品規格 ID について数量を SUM し、合計が正のグループのみ行を返す。
  • 「条件付き」（needsConditons が真、branch_store_import・tc_tokyo_import・new_branch_store_import）: ニアミント制限無し、数量が正の明細のみ行を構成。
  • 支店伝票（branch_order_import）: priceGrouping 真により、店頭買取 ID と商品規格 ID の組でグループし、販売価格は明細側の売価、数量は在庫行の値を用いる。あとから商品コード単位へ数量を足し込む処理が PHP 側にあり、同一商品コード複数グループが 1 行にまとまることがある。
  1. CSV データ行生成後、dtb_otc_buy_order を接続オブジェクト経由で一括 UPDATE し、otc_buy_order_status_id を入力済み状態（内部定数 4）、data_export_date と update_date に現在、member_id に操作者へ更新する。
  2. flush で永続化を確定する。
  3. ec_import のみ、その前に読み込んだ各行の査定オブジェクトについて、入力済み状態に遷していたものはステータス履歴を追加しない。その他については入力済みへ遷移した旨のステータス履歴を追加するループがある（画面上の状態はクエリ済みオブジェクト参照の順序により、履歴可否判定に用いられる）。

業務ルール・計算

ヘッダと列（データ行側の並び）

  • ECインポート用: 論理項目名として 商品コード・在庫増減数 に相当する値。増減数はクエリ済み整数。
  • 支店インポート用: 商品コード・商品名（中身は実装により 【言語コード】 前置と商品名の sprintf）・在庫数。ファイルは SJIS とみなされるようエクスポート設定を一時的に書き換え、BOM を付けない取り扱い。
  • TC東京インポート用・新支店インポート用: ECインポート用と同様のコードと数量を基本とする。新支店は 3 列目に ピックアップ商品 ラベルの列があり、データは null 固定。
  • 支店伝票インポート用: 商品コード・在庫増減数・販売価格・状態コード。商品コード単位での数量縦積み後に出力される。
  • 古物台帳入力用: 氏名結合には全角空白 　 が間に入る。年齢は YYYYMMDD 整数差を 10000 で割って床関数。電話は先述のExcel向け前置。

本機能には画面によるテキスト入力保存はなく、### 入力項目 は置かない（検索条件は別フォームであり本 CSV 機能の入力ではない）。
