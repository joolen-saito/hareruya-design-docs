イベント管理 — イベント申込検索

刷新後は実装不要本節は現行実装（pf-eccube3）からのリバースです。次の記述は Excel基本設計により廃止されており、刷新後に実装する必要はありません。

  • DCIナンバー（検索条件） は削除（0214 イベント申込一覧(検索入力) 識別ID:3-1）
  • 決済中処理バッチ実行ボタン は削除（0214 イベント申込一覧(検索入力) 識別ID:3-2）

管理画面「イベント管理」のイベント申込一覧で、登録済みの申込を申込者・支払・開催日時などの条件で検索し、申込（または登録デッキ）を一覧表示する機能である。

概要

イベント申込検索は、管理者がイベント申込を絞り込み、一覧から申込の編集・一括編集・CSV出力・デッキ表示などへ進むための入口となる機能である。検索は「イベント申込検索」と「デッキ登録検索」の2モードを持ち、選択したモードにより集計対象（申込プレイヤー単位かデッキ単位か）とソートキーが切り替わる。検索条件・表示件数・ソート条件はセッションに保持し、ページ送りや再表示で復元する。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。既存実装のふるまい、参照するデータ、2モードの分岐、検索条件の保持、ページング、ソートの挙動を確認し、仕様の確からしさを把握することを目的とする。

対象はブラウザ経由の管理画面イベント申込一覧である。本機能は晴れる屋向けプラグインで提供され、EC-CUBE3系のSilexアプリケーション上で動作する。管理画面プレフィックスはアプリケーション設定admin_route（$app['config']['admin_route']）で決まり、ルートはこの値を連結して登録される。確認観点は申込用サービスプロバイダのルート登録とする。

イベント一覧検索はM13-01、イベント編集/削除はM13-02を正とする。申込の新規登録・編集・一括編集・CSV出力・CSV取込・デッキ表示（別ウィンドウ）は本書では扱わない。デッキ表示画面の中身はM13-08を正とする。

本機能のカスタマイズ区分はカスタマイズである。挙動の参照リポはpf-eccube3（HareruyaEcプラグイン）の現行実装とし、DB関連（永続化先のテーブル名・列名、DBカラム節、保存先・扱い、副作用のDB更新）はec-cube-enterpriseを正とする。現行と移行先でスキーマが異なる箇所はリニューアル移行時の扱いに集約する。

本書で扱うこと

  • イベント申込一覧の初期表示と、検索フォーム送信による絞り込みのふるまい
  • 検索モード（イベント申込検索／デッキ登録検索）による集計対象とソートキーの切り替え
  • 検索条件（イベント名・申込状況・支払方法・支払番号・プレイヤー名・DCIナンバー・開催日時・確認済・デッキ登録有無・店舗・イベント詳細ID）の扱い
  • 表示件数・ソート条件・検索条件・ページ番号のセッション保持と復元
  • イベント詳細指定表示（特定日程の申込一覧）の入口
  • 一覧からデッキ表示・申込編集・一括編集・CSV出力への導線（入口としての役割に限る）

本書で扱わないこと

以下は本書では仕様確定せず、実装または別機能の設計を正とする。

  • イベント一覧の検索・編集・削除（M13-01、M13-02を正とする）
  • デッキ表示画面（別ウィンドウ）の表示内容（M13-08を正とする）
  • 申込の新規登録・編集・更新・一括編集の入力ルール
  • 申込CSVの出力項目・取込・ひな型ダウンロード
  • イベント検索モーダル・プレイヤー検索モーダルの内部実装
  • 管理画面へのアクセス制御、ログイン、権限設定の詳細
  • マスタ（申込状況・支払方法・店舗）の管理画面での編集ルール

リニューアル移行時の扱い

検索・集計の挙動は現行（pf-eccube3）を正とし、永続化先の列名は移行先（ec-cube-enterprise）を正とする。検索条件の絞り込みキー・ソートキーは検索条件セッション上の論理キーであり、移行で変わらない。

処理フロー

申込一覧を初期表示する

  1. 管理者が申込一覧を開く。
  2. 検索フォーム（フォーム名admin_entry_list）を生成する。
  3. 検索条件セッション（admin.event_entry.search、admin.event_entry.search.page_no、admin.event_entry.search.page_count）を削除する。
  4. 一覧結果を空、ページ番号1、表示件数を既定として一覧テンプレートを描画する。イベント検索モーダル・一括編集モーダルの呼び出し用フォームも渡す。

検索フォームを送信して絞り込む

  1. 管理者が条件と検索モードを選び、検索ボタンを押す。
  2. 検索フォームを生成し、リクエストを反映する。
  3. ソートキー・並び順を決める。優先順位はリクエスト、セッション、既定の順。並び順がASC／DESC以外なら並び順エラーを表示し初期表示へ戻す。
  4. 表示件数を決める。リクエストのpage_countがマスタに存在すれば採用しセッションへ保存する。
  5. フォームから検索条件を取り出す。空でセッションに条件が残っていれば復元する。条件もセッションも無ければ初期表示へ戻す。
  6. 検索条件にソートキー・並び順を付与し、検索モードに応じてクエリビルダと件数を取得する（後述の集計条件）。
  7. 最終ページのデータ削除等で当該ページに表示対象が無くなった場合、ページ番号を1つ前に補正する。
  8. ページ番号・検索条件・ソートキー・並び順・表示件数をセッションへ保存する。
  9. ページネーターで該当ページを取得し、一覧テンプレートを描画する。検索モードに応じてソートキー候補を切り替える。

イベント詳細指定表示（特定日程の申込一覧）

  1. パスのイベント詳細IDを検索フォームのイベント詳細IDに設定する。
  2. ソート・並び順は既定とする。
  3. 表示件数を決め、検索条件をセッションへ保存する。
  4. 検索モードをentriedEvent（イベント申込検索）に固定し、申込プレイヤーのクエリビルダで該当ページを取得して一覧テンプレートを描画する。

ページ送り・表示件数変更・ソート変更

  1. ページ送り等のリンクは検索処理と同じ処理を呼ぶ。
  2. リクエストにフォーム検索条件が無いため、セッションの検索条件を復元して再検索する。
  3. リクエストのsort・order・page_countがあれば優先して反映する。

集計条件

指標集計の要点
イベント申込検索（entriedEvent）申込プレイヤー（dtb_entry_player）を集計単位とし、申込プレイヤーリポジトリのクエリビルダ・件数取得を用いる。ソートキーがデッキ登録用のキーに該当する場合は申込用の既定キー（default）へ補正する。
デッキ登録検索（registedDeck）デッキ（dtb_deck）を集計単位とし、デッキリポジトリのクエリビルダ・件数取得を用いる。ソートキーが申込用のキーに該当する場合はデッキ用の既定キー（deckDate）へ補正する。
ソートキー候補イベント申込検索では申込用ソートキー（default＝申込ID、entryDate＝申込日時、entryStatus＝申込状況など）、デッキ登録検索ではデッキ用ソートキー（deckDate、deckUpdate、startDateなど）を一覧のソートメニューに出す。

業務ルール・計算

項目内容
検索モード検索モードによって集計対象（申込プレイヤー単位／デッキ単位）と既定ソートキーが切り替わる。モードはフォーム必須項目。
ソートキー補正選んだモードと整合しないソートキー（他モード用のキー）が来た場合、当該モードの既定ソートキーへ補正する。
イベント名検索イベント名の語による絞り込み（申込・デッキの検索クエリ側で処理）。
開催日時開催日時From・Toで日程の開始日時を絞り込む。Fromは初期値として当日0時を持つ。
表示形式件数は整数で表示する。金額計算・税計算・丸めは行わない。

検索フォームの入力項目

項目名必須／任意最大長初期値保存先・扱い
イベント名任意一行テキスト（フォーム上のLengthなし）空検索条件キーmulti。永続化しない。イベント名等への絞り込み。
申込状況任意セレクト（複数）未選択検索条件キーentry_status。申込状況マスタ（MtbEntryStatus）。
支払方法任意セレクト（複数）未選択検索条件キーpayment。支払方法（Payment）の所定ID群、ランク昇順。
支払番号任意64文字（entry.length.payment_no、maxlength属性）空検索条件キーpaymentNo。
プレイヤー名任意255文字（entry.length.name、maxlength属性）空検索条件キーplayer。
DCIナンバー任意複数行入力（textarea）空検索条件キーdci_no。
開催日時From任意日時（single_text、設定の日時書式）当日0時検索条件キーdate.from。日程の開始日時の下限。
開催日時To任意日時（single_text、設定の日時書式）空検索条件キーdate.to。日程の開始日時の上限。
確認済任意複数選択（展開）未選択検索条件キーconfirm_flg。選択肢は確認済（保存値true）・未確認（保存値false）。
デッキ登録有無任意複数選択（展開）未選択検索条件キーdeckEntried。選択肢は登録済（保存値true）・未登録（保存値false）。
店舗任意セレクト（複数）未選択検索条件キーshop。店舗マスタ（MtbShop）。
検索モード必須選択（展開）イベント申込検索検索条件キーsearchMode。選択肢はイベント申込検索（保存値entriedEvent）・デッキ登録検索（保存値registedDeck）。
イベント詳細ID任意整数（10桁以内、Regex）空検索条件キーevent_detail_id。特定日程に絞る。イベント詳細指定表示ではパス値を設定する。

最大長の数値はプラグイン設定（config.ymlのentry.length）の確認値を記載する。運用環境で上書きされている場合はその環境の値が正とする。

データ整合性

観点内容
参照時点一覧の件数と行は検索実行時にデータベースから読み取った値である。表示後の申込・デッキの更新は自動反映しない。
検索条件の保持検索条件・表示件数・ソートキー・並び順・ページ番号はセッション（接頭辞admin.event_entry）に保存し、ページ送り・再表示・デッキ表示・CSV出力で参照する。
デッキ表示・CSVとの整合性デッキ表示（M13-08）とCSV出力は、申込一覧の検索条件セッションを読んで対象を決める。検索後に条件を変えずに開けば同一条件の対象を扱う。
件数と行の整合性件数は検索モードに応じた件数取得で求め、表示行はページネーターが取得する。

API/バッチ結果

本機能ではAPI呼び出し・バッチ実行を扱わない。検索結果の一覧表示のためにデータベースを読み取るのみである。イベント検索モーダル・プレイヤー検索モーダルの非同期取得は本書では扱わない。

入出力

種類内容
入力一覧初期表示・ページ送り・イベント詳細指定表示のGET、検索フォームのPOST（フォーム名admin_entry_list）。
