o01-01_other_mtg_buyer_mtg_buyer_store_purchase（その他_MTGバイヤー_店頭買取）

概要

MTGバイヤーで店頭買取の査定を行う業務を、EC-CUBE側の店頭買取データ、管理画面、pf-api連携から見たリバース詳細設計である。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。確認値は../pf-eccube3のHareruyaEcプラグインにある店頭買取業務資料、店頭買取フロント・管理画面、店頭買取API設計を正とする。本機能のカスタマイズ区分はカスタマイズであり、挙動はpf-eccube3（HareruyaEcプラグイン）の実装を参照し、DB関連（テーブル・列）の記述はec-cube-enterpriseを正とする。

MTGバイヤー本体は本リポジトリ内に実装が無い外部アプリである。本書では外部アプリ内部の画面・UI・ローカル保存仕様は確定せず、EC-CUBE側で確認できる入口、API、DB更新、副作用を扱う。

本書で扱うこと

  • 店頭買取の受付後、MTGバイヤーで査定を開始・入力・確定する業務境界
  • MTGバイヤーが利用する店頭買取APIの役割
  • 査定結果がEC-CUBE側の店頭買取受注、明細、在庫、履歴、ステータスへ反映される範囲
  • リポジトリ内で確認できる管理画面・CSV・集計との整合

本書で扱わないこと

以下は本書では仕様確定せず、外部アプリまたは別機能の設計を正とする。

  • MTGバイヤー本体の画面項目、ローカルDB、オフライン動作、バーコード読取、印刷の内部仕様
  • Backlog、Excelマクロ、スマレジ、店舗作業などリポジトリ外の運用
  • 店頭買取申込フォームの詳細（F08-01〜F08-03を正とする）
  • 店頭買取管理画面の検索・編集・CSV出力の詳細（M06系の各設計を正とする）
  • pf-api各エンドポイントのリクエスト・レスポンス詳細（A06系の各API設計を正とする）

リニューアル移行時の扱い

本機能はカスタマイズであり、挙動の参照は現行のpf-eccube3（HareruyaEcプラグイン）、DB関連の正はec-cube-enterpriseとする。店頭買取の各テーブルは現行と移行先で同名であり、本書が参照する範囲では同一スキーマである。移行先には現行に無い承認者テーブル（dtb_otc_buy_order_approver）が追加されているが、本書が扱う査定確定・ステータス更新・在庫反映の範囲には影響しない。

用語

用語説明
MTGバイヤー店頭買取・ネット買取の査定作業に使う外部アプリ。EC-CUBEとはpf-api経由で連携する。
店頭買取受注店頭で受け付けた買取申込。EC-CUBE側ではdtb_otc_buy_orderを中心に管理する。
査定対象店頭買取ステータスが商品到着、査定中、振込前、保留、査定再開など、MTGバイヤーで扱う対象となる受注。

店頭買取ステータス店頭買取の進行状態。査定前、査定中、買取成立、買取キャンセル、ダブルチェック済、データ出力済などを持つ。

処理フロー

店頭買取を受付する

  1. フロントの店頭買取申込で、会員または非会員が申込情報を入力する。
  2. 申込確定時に店頭買取受注を作成し、査定番号を採番する。
  3. 店頭買取ステータスは査定前として登録される。
  4. 受付時の本人確認、買取品の預かり、身分証コピーなどの実作業は運用で行う。

MTGバイヤーで査定を開始する

  1. MTGバイヤーはログインAPIで認証し、認証トークンを取得する。
  2. 店頭買取受注一覧取得APIで査定対象の受注を取得する。
  3. 店舗に紐づく管理者で認証している場合は、当該店舗の受注だけが一覧に含まれる。
  4. 査定開始時はステータス更新APIにより査定中へ更新する。
  5. EC-CUBE側は受注のステータス、査定担当者、更新日時、ステータス変更履歴を保存する。

MTGバイヤーで査定結果を確定する

  1. MTGバイヤーは商品検索・商品取得APIを使い、査定対象の商品情報を取得する。
  2. 査定明細として商品規格ID、商品名、数量、買取単価、販売価格、部門などを送信する。
  3. EC-CUBE側は受注IDで店頭買取受注を特定する。該当が無い場合は該当なしとして返す。
  4. ステータス、明細配列、明細各項目を検証する。検証エラーがあれば保存せず入力不正を返す。
  5. 既存の受注明細、個別入力商品、在庫、在庫履歴を削除し、送信明細で作り直す。
  6. 商品規格に紐づく明細は商品規格単位で数量を集計し、在庫と在庫履歴を作る。
  7. 明細の買取単価×数量を合計し、買取合計金額を10円単位へ切り上げる。
  8. ステータス、買取合計金額、査定担当者、更新日時、成立日時またはキャンセル日時を保存する。
  9. ステータスが変わった場合はステータス変更履歴を登録する。

査定後の店頭買取業務へ進む

  1. 査定結果を顧客と確認する。
  2. 買取キャンセルの場合はステータスを買取キャンセルへ更新する。
  3. 買取成立の場合はステータスを買取成立へ更新する。
  4. EC-CUBE管理画面では、買取一覧、買取詳細、買取商品履歴、買取集計、古物台帳用CSV、在庫登録用CSVなどで確定済みデータを参照・出力する。
  5. バーコード印刷、Backlog起票、スマレジ、仕入れ作業などはリポジトリ外の運用を正とする。

業務ルール・計算

項目内容
査定対象の抽出店頭買取受注一覧取得APIは、商品到着、査定中、振込前、保留、査定再開の状態にある受注を対象にする。成立、キャンセル、ダブルチェック済、データ出力済などは査定対象一覧から外れる。
店舗絞り込み認証した管理者に所属店舗がある場合は、その店舗に一致する店頭買取受注だけを返す。所属店舗が無い場合は店舗で絞り込まない。
明細の全置換査定結果確定APIは、既存の明細・個別入力商品・在庫・在庫履歴を削除して、送信された明細で作り直す。送信されなかった既存明細は残らない。
個別入力商品の扱い商品規格IDが空の明細は個別入力商品として登録する。商品規格に紐づかないため、商品規格単位の在庫集計には含めない。
買取合計金額送信明細の買取単価×数量を合算し、10円単位へ切り上げる。MTGバイヤー側の表示値ではなく、EC-CUBE側保存処理で再計算した値を保存する。
在庫数量商品規格に紐づく明細を商品規格ごとに集計し、同一商品規格の数量を合算して店頭買取受注在庫と在庫履歴を作成する。
ステータス変更履歴更新前後でステータスが異なる場合に履歴を登録する。同じステータスへの詳細更新では明細・在庫は作り直すが、ステータス変更履歴は追加しない。
外部運用査定表印刷、本人確認の実作業、出金、バーコード印刷、Backlog、スマレジ、仕入れ統合作業はEC-CUBE側で確認できる範囲外の運用を正とする。

入力項目

項目名必須／任意最大長初期値保存先・扱い
認証トークン必須API認証仕様に従うログインAPIの成功結果各APIのjwt-tokenヘッダ。原値は本書に記載しない。
店頭買取受注ID必須整数査定対象一覧から選択店頭買取受注の特定に用いる。該当なしはHTTP 404相当。

フリーコメント任意API設計の上限に従う既存値または空店頭買取受注のフリーコメントへ保存する。
本人確認情報任意API設計の上限に従う既存値店頭買取受注に紐づく本人確認状態を更新する。

エッジケース

ケース扱い
認証不可APIは認証拒否とし、店頭買取データを返さず更新しない。
査定対象が0件店頭買取受注一覧取得APIは空配列を返す。
受注IDが存在しない詳細更新、ステータス更新、コメント更新、本人確認更新は該当なしとして扱う。
明細が空詳細更新APIは入力不正とし、既存明細・在庫を削除しない。
同じステータスで詳細更新明細・個別入力商品・在庫・在庫履歴は送信内容で作り直す。ステータス変更履歴は追加しない。
同時更新専用の楽観ロック・悲観ロックは持たない。後から確定した更新が残る。

データ整合性

観点内容
参照時点MTGバイヤーの一覧取得、商品情報取得、管理画面の一覧・詳細・CSVは、それぞれ実行時点で永続化済みのデータを参照する。
査定結果と管理画面MTGバイヤーで確定した受注明細、個別入力商品、在庫、在庫履歴、ステータス、査定担当者、更新日時は、保存成功後に管理画面の店頭買取詳細・履歴・CSVの参照元になる。
在庫と履歴詳細更新時に商品規格ごとの数量で店頭買取受注在庫を作り直し、対応する在庫履歴を登録する。既存在庫・履歴は削除後に再作成される。
ステータスと集計買取成立、ダブルチェック済、データ出力済など集計対象のステータスへ変わると、店頭買取集計やCSV出力の対象になる。集計処理の詳細はM06系およびバッチ設計を正とする。
外部運用との整合Backlog、スマレジ、Excelマクロ、バーコード印刷は本リポジトリ内で直接整合を保証しない。EC-CUBE側で出力したCSVや確定済みデータを運用で利用する。
同時更新DB行ロックを使った査定占有は確認できない。同一受注を複数の利用者・APIが同時に更新した場合、後から保存された内容が残る。

API/バッチ結果

種類内容
APIMTGバイヤーはpf-apiのA06系APIを利用する。ログイン、店頭買取受注一覧取得、詳細更新、コメント更新、ステータス更新、本人確認更新、商品検索・商品取得が主な接続点である。
成功結果参照APIはJSONで対象データを返す。更新APIは対象データを保存し、成功コードまたは更新結果を返す。
失敗結果認証不可、対象なし、入力不正、保存例外は各API設計のHTTPステータスと本文形式に従う。
バッチ店頭買取集計はotcBuyOrder:batch updateSummaryで実行される。MTGバイヤー本体が直接バッチを起動する仕様は確認できない。
再実行時参照APIは実行時点の最新データを返す。詳細更新APIは明細・在庫を全置換するため、同じ受注に再送すると送信内容で上書きされる。

入出力

種類内容
入力認証トークン、店頭買取受注ID、ステータスID、査定明細、コメント、本人確認情報、商品検索条件など。
成功時出力JSON応答、店頭買取受注の更新、明細・個別入力商品・在庫・在庫履歴の作成、ステータス変更履歴の作成。

副作用DB更新、ステータス変更履歴、在庫履歴、管理画面・CSV・集計への反映。外部運用への直接連携は本書では確認できない。
