デッキ管理 — デッキ検索・一覧

概要

HareruyaEc プラグインが管理画面に提供する「デッキ管理」において、大会用デッキ（dtb_deck のうちデッキ種別が大会用のもの）を多数の条件で絞り込み、一覧・ページ送り・並び替えする機能である。検索条件・ページ番号・表示件数・ソートはセッションに保持し、GET での再表示時に復元する。一覧上から CSV 出力・一括削除・一括編集の導線が接続されているが、それら個別処理の検証や CSRF の例外の列挙は本書の主題としない。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。pf-eccube3 配下の HareruyaEc プラグイン実装を確認値とする。EC-CUBE コア単体では当ルートは存在しない。

本機能のカスタマイズ区分はカスタマイズである。挙動は現行リポ（pf-eccube3 の HareruyaEc プラグイン）を参照し、DB関連は ec-cube-enterprise を正とする。

対象はブラウザ経由の管理画面に限定する。コントローラのメソッド名の列挙は本文の主題としない。本文ではルートbind名やSymfonyのルートnameの網羅は主説明としない。「利用者視点の入口」にHTTPメソッドとサイトルートからのパスパターンを書く。コード探索でbind名が必要なときだけ「調査補助」へ書く。

リニューアル移行時の扱い

  • ec-cube-enterprise にデッキ関連テーブル一式が実装されており、本機能の検索対象は移行先に存在する。
  • デッキ（dtb_deck）の主キー列名が異なる。移行先 ec-cube-enterprise では id、現行 pf-eccube3 では deck_id である。本書が dtb_deck.deck_id（主キー）と記す箇所は、移行先では dtb_deck.id に対応する。中間テーブル（dtb_deck_deck_tag、dtb_article_deck、dtb_deck_campaign_tag）の外部キー列は現行・移行先とも deck_id のままである。
  • デッキのその他の検索対象列（deck_name、format_id、archetype_id、disp_id、private_flg、event_date、ranking、win_count、loss_count、draw_count、result、event_name_jp、event_name_en、player_name、dci_no、member_id、deck_type_id、event_detail_id、old_deck_id ほか）は現行と同一スキーマである。論理削除列 deleted_at を現行・移行先とも持つ。
  • 移行先 dtb_deck には現行に無い追加列（player_id、card_image_id、display_token 等）があるが、本機能の検索条件では参照しない。
  • カード条件で結合するデッキ内カード（dtb_deck_card、列 deck_id、card_id、board_id、count）は移行先に存在し同一スキーマである。

フロント挙動

観点内容
表示要素ページタイトルは「デッキ管理」。サブタイトル行に新規・CSV 取込ボタン。検索は単一フォーム search_form。1 行目付近にデッキ ID・旧デッキ ID・フォーマット・色（チェックボックス横並び）・アーキタイプ（複数選択）。表示／非表示マスタ・プライベートのラジオ群。イベント日 From／To（単一行日付ウィジェットと「日付クリア」ボタン）、大会名テキスト。順位レンジ、戦績テキスト、勝敗引き分けの上下限、デッキ名・DCI・プレイヤー名。デッキタグ・カード名（候補リスト用の ul.cardNameList）。イベント ID・店舗・登録管理者。フッタに「すべてクリア」リンクと「検索」ボタン。結果部は件数見出し、CSV 出力・旧サイト CSV・一括削除・一括編集アコーディオン、表示件数ドロップダウン、ソート二段ドロップダウン、表（チェックボックス・概要リンク・行メニュー）、ページネーション。
JS 挙動select2 をフォーマット・アーキタイプ・デッキタグ（および一括編集内の同名項目）に付与する。ヘッダ全選択チェックで deckId 属性を持つ行チェックを同期する。「すべてクリア」で検索フォーム内の入力を空にし、チェック・ラジオをオフにする（_token 名一致は除外）。「日付クリア」でイベント日 From／To を空にする。フォーマットまたは色変更時、アーキタイプ選択肢をフォーマット ID・色クラスでフィルタし、無効オプションを切り替える。CSV 出力ボタンは未選択時に alert で中断する。一括編集はチェックされた項目だけ入力域を開き、required.js と連動して必須表示を付ける。ソート UI は sort-method-display.js に依存する。カード名欄は deck_card.js（パブリック資産経由）と data-list でカード名候補 URL を参照する構成である。
CSS・レイアウトselect2 CDN、eventlist.css を読み込む。Bootstrap 3 系フォームレイアウト。
モーダル・ポップアップ検索画面専用モーダルはない。一括削除・行削除・一括編集送信はブラウザの confirm に依存する。

処理フロー

デッキ一覧を初期表示する（GET admin_deck_list）

  1. 管理画面の認証・共通制約を通過する。
  2. セッションから admin.deck.search、admin.deck.search.page_no、admin.deck.search.page_count を削除する（admin.deck.sort・admin.deck.order は残りうる）。
  3. フォーム名 admin_search_deck で検索フォームを生成し、deck.twig を描画する。ページネーションは空配列、page_no は 1、page_count は設定 default_page_count。ソートキー一覧はデッキレポジトリから取得する。
  4. イベント日 From はフォーム種別の既定データとして「現在日時から設定 HareruyaEc.const.search_form.default_from_term（確認値 -3 month）だけシフトした日付」が入る。

検索・一覧を表示する（GET または POST m15-01_admin_deck_deck_search）

  1. 管理画面の認証・共通制約を通過する。
  2. デッキ用レポジトリ参照をセットする。
  3. フォーム admin_search_deck を生成する。送信前に「有効」とみなされると空一覧で返す分岐があるが、未送信の通常経路では続行する。
  4. リクエストをフォームに取り込む。
  5. クエリパラメータまたはセッションから sort を決める。優先順はリクエスト、なければセッション、なければ既定値 default。
  6. 同様に order を決める。既定は DESC。
  7. order が正規表現 ^(ASC|DESC|asc|desc)$ に一致しない場合、管理画面エラー admin.error.sort を積み、admin_deck_list と同様の初期化処理へ進む（検索条件・ページ関連セッションのみ削除され、admin.deck.sort と admin.deck.order は削除されない）。
  8. ページマスタを全件取得し、許容される表示件数の一覧を得る。
  9. 表示件数はセッションの admin.deck.search.page_count があればそれを使い、なければ設定 default_page_count（確認値 10）。リクエストに page_count があり、かつページマスタの名前と一致すればセッションへ上書き保存する。
  10. フォームから送信データが得られない場合、セッション admin.deck.search のビューデータから復元する。ビューと検索データの両方が欠ける場合は admin_deck_list と同等の初期表示へフォールバックする。
  11. 検索データに sort・order を合成する。
  12. レポジトリが検索データからクエリビルダを構築する。別メソッドで同一条件の件数を取得する。現在ページが最終ページかつそのページのデータが削除済みなどで件数とページの関係がずれる場合、実装はページ番号を 1 減らして調整する。
  13. セッションへ admin.deck.search.page_no、admin.deck.search、admin.deck.sort、admin.deck.order、admin.deck.search.page_count を書き込む。
  14. アプリケーションのページネータでクエリビルダをページ分割する（デッキ一覧では wrap-queries を有効にするオプションが指定されている）。Twig を描画する。

集計条件

指標集計の要点
一覧の総件数getQueryBuilderBySearchData と同等の結合・絞り込みをしたうえで、dtb_deck 主エイリアスに対する count で取得する。一覧クエリと件数クエリで条件が乖離しない。
一覧の各行dtb_deck エンティティがページネーションされる。テーブルに出す文言はプロパティおよび関連の遅延参照（アーキタイプ名など）に依存する。

検索実行時の判定順序（グローバル除外）

以下は利用者が入力しない前提でもクエリに適用される。

順序判定結果
1イベント詳細との結合条件イベント詳細が無いデッキは残す。イベント詳細がある場合は、その開始日時が現在より前である行だけが結合対象となり、開始が未来のイベントにだけ紐づくデッキは結果から除外される。
2デッキ種別大会用デッキ種別定数に一致する行だけを残す。ユーザー作成デッキ種別などは除外される。

業務ルール・計算

検索フォーム入力はセッションへ保存されるが、dtb_deck を更新しない。送信値からクエリビルダへの対応は次のとおりである。

項目内容
複数トークン検索デッキ名・大会名・戦績文字列・DCI・プレイヤー名は、半角／全角スペースおよびカンマで分割した各トークンについて、対象列へ部分一致条件を付ける。トークン間は論理 AND（いずれかの列への一致でそのトークンは充足）。同一トークン内の複数列は論理 OR。
複数 IDデッキ ID・イベント ID は同様に分割し、数値だけを抽出して IN 検索する。非数値トークンは無視される。
フォーマット・アーキタイプ・表示マスタ・色選択されたマスタ行への IN 一致。色はアーキタイプ経由で色マスタと結合して絞り込む。
プライベートラジオがちょうど 1 選択のときだけ、その真偽値で一致させる。未選択または両方選択のときは条件を付けない。
イベント日From のみ指定ならその日 0 時以上。To のみ指定なればその日 23:59:59 以下。両方あれば範囲。
順位・勝敗引き分けそれぞれ From／To に整数が入っていれば下限・上限を付ける。
デッキタグ選択された各タグについて、dtb_deck とタグの関連がすべて存在する行だけを残す（論理 AND）。
カード名デッキに含まれるカードの日本語名または英語名が、入力文字列と完全一致する行だけを残す（LIKE ではない）。
旧デッキ ID文字列一致（単純等価）。
店舗イベント詳細経由でイベントが店舗マスタと結合され、その店舗が選択値と一致する行だけを残す。イベント詳細が無いデッキはこの条件では基本的に絞り込まれない。
登録管理者dtb_deck.member_id が選択された管理者アカウント ID と一致する行だけを残す。

本機能では業務計算（税・ポイント等）は行わない。

フォーム種別にはフォームキー latest（ラベルは翻訳キー form.deck.latest.*）も定義されているが、一覧テンプレートでは出力しておらず、レポジトリの検索処理でも参照しない。したがって画面からは通常操作できず、クエリにも効かない。

検索フォームは CSRF 保護を無効にしている（プラグインのフォーム種別の既定）。

エッジケース

ケース扱い
ソートキーが不正admin.error.sort を表示し、admin_deck_list と同様に検索条件・ページ関連セッションを削除したうえで一覧初期画面へ戻る（ソート・並び順のセッションキーは削除しない）。
セッションに検索条件がなく GET のみ一覧初期表示へフォールバックする。
ページ番号がルート制約に合わないルートにマッチしないため到達しない（別経路の 404 に依存）。
プライベートを複数選択絞り込みを付けない。
未来開始のイベントにのみ紐づくデッキグローバル結合・WHERE により結果に含まれない。
表示件数パラメータがマスタ外セッションを更新せず、直前の表示件数を使う。

データ整合性

観点内容
一覧と詳細一覧は検索時点の DB 状態を読む。詳細画面で更新後、一覧へ戻ればセッションが残っていれば古い条件のまま再検索されうる。
大会開始時刻「開始が未来のイベントに紐づくデッキは一覧に出ない」ため、一覧と「イベント詳細をそのまま見た期待」とはずれる場合がある。
件数と一覧件数取得と一覧クエリは同一ビルダ経路を踏む設計であり、通常は件数とページ内容が対応する。

API/バッチ結果

本機能では API 呼び出し・バッチ実行を扱わない。

入出力

種類内容
入力HTTP クエリ／フォーム POST の検索条件、sort、order、page_no、page_count。
成功時出力HTML（検索フォーム＋該当時は一覧テーブル・ページネーション）。
失敗時出力不正ソート時はフラッシュエラーと初期画面。レポジトリがクエリビルダ以外を返した場合は HTTP 404（通常の検索経路では発生しない想定）。
副作用セッション更新（検索条件・ページ・ソート・表示件数）。

DB操作
