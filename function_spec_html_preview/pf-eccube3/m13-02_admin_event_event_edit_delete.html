M13-02（イベント編集/削除）

刷新後は実装不要本節は現行実装（pf-eccube3）からのリバースです。次の記述は Excel基本設計により廃止されており、刷新後に実装する必要はありません。

  • チーム人数 は チーム戦フラグ（dtb_event.is_team_battle、真偽） へ変更（0214 イベント編集 識別ID:1-12）これに伴い実装不要: チームメンバーのメールアドレス・席次の入力／メールのみの仮選手（dtb_player）の作成／チームメンバー招待メールの送信／未承認（confirm_flg=UNCONFIRMED）での申込選手登録／招待リンクからのチームプレイヤー認証（events_team_player_activate）

管理画面「イベント管理」で、登録済みイベントの内容を編集・更新し、または不要なイベントを削除する機能である。新規登録の入力フォームと同一のフォームを用いるが、本書では登録済みイベントの編集と削除に範囲を限定する。

概要

イベント編集/削除は、管理者が一覧から特定のイベントを開き、イベント情報を更新したり、条件を満たすイベントを削除したりするための機能である。編集画面には登録済みの開催日程一覧も表示され、日程ごとの申込一覧・編集・削除・複製新規への導線を兼ねる。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。既存実装の入力項目、検証、永続化、削除可否の判定、副作用を確認し、仕様の確からしさを把握することを目的とする。

カスタマイズ区分はカスタマイズであり、挙動の参照リポはpf-eccube3、DB関連の記述はec-cube-enterpriseを正とする。

対象はブラウザ経由の管理画面イベント編集画面である。本機能は晴れる屋向けプラグインで提供され、EC-CUBE3系のSilexアプリケーション上で動作する。管理画面プレフィックスはアプリケーション設定admin_route（$app['config']['admin_route']）で決まり、ルートはこの値を連結して登録される。確認観点はイベント用サービスプロバイダのルート登録とする。

一覧検索はM13-01、複製新規はM13-05、申込検索はM13-06、デッキ表示はM13-08を正とする。日程（イベント詳細）の登録・更新・削除のうち、本書はイベント編集画面からの日程一括削除（チェックした日程削除）に限り触れ、日程の追加・編集・繰返し登録の入力ルールは扱わない。

本書で扱うこと

  • 登録済みイベントの編集画面表示と入力項目
  • イベント更新の検証・永続化・申込済み時の支払方法変更不可の判定
  • イベント削除の確認・可否判定（日程が残っている場合は削除不可）
  • 日程一括削除（チェックした日程削除）の可否判定（デッキ登録済み・申込済みは削除不可）
  • 編集画面に表示される開催日程一覧と、申込一覧・複製新規・戻るへの導線（入口としての役割に限る）

本書で扱わないこと

以下は本書では仕様確定せず、実装または別機能の設計を正とする。

  • イベント一覧の検索・ページング・ソート（M13-01を正とする）
  • 複製新規の複製範囲（M13-05を正とする）
  • イベント申込の検索・登録・編集（M13-06を正とする）
  • デッキ表示（M13-08を正とする）
  • 日程（イベント詳細）の追加・編集・繰返し日程登録の入力ルールと検証
  • 管理画面へのアクセス制御、ログイン、権限設定の詳細
  • マスタ（会場・フォーマット・ルール適用度・店舗・公開状態・支払方法）の管理画面での編集ルール

リニューアル移行時の扱い

現行（pf-eccube3）と移行先（ec-cube-enterprise）の差を記録する。DB関連はec-cube-enterpriseを正とする。入力項目・検証・削除可否の挙動は現行（pf-eccube3）を正とする。

処理フロー

編集画面を表示する（登録済みイベント）

  1. パスのIDでイベントを読む。存在しなければ404とする。
  2. 当該イベントの日程（イベント詳細）を開始日時の降順で読み、イベントに設定する。
  3. 日程ごとの申込人数（参加状態の件数）を集計する。
  4. イベント登録フォーム（フォーム名admin_event_detail）を当該イベントで生成する。
  5. 編集テンプレートを描画する。フォーム、イベント、申込人数配列、IDを渡す。

新規登録画面を表示する

  1. 新しいイベントを用意する。
  2. 支払方法の初期値としてクレジットカードを設定する。
  3. 空のフォームを生成し、編集テンプレートを描画する。IDは渡さない。

イベントを更新する（登録済み）

  1. パスのIDでイベントを読む。すでに削除されている場合は403とする。
  2. 申込人数を集計する。
  3. フォームにリクエストを反映する。
  4. 申込済みの場合の支払方法変更不可を判定する。送信された支払方法が現在の支払方法と差分を持ち、かつ当該イベントの日程のいずれかに申込が1件以上あるとき、支払方法変更不可エラーを表示し、直前画面（referer）へ戻す。
  5. フォーム検証に失敗した場合、登録失敗エラーを表示し編集テンプレートを再描画する。
  6. 登録者IDにログイン中の管理者IDを設定する。
  7. イベントを永続化（更新）してフラッシュする。
  8. 完了メッセージを表示し、編集画面へリダイレクトする。

イベントを新規登録する

  1. 新しいイベントを用意する。
  2. フォームにリクエストを反映し、検証する。失敗時は登録失敗エラーを表示し再描画する。
  3. 登録者IDを設定し、永続化（登録）してフラッシュする。
  4. 完了メッセージを表示し、登録したイベントの編集画面へリダイレクトする。

イベントを削除する

  1. パスのIDでイベントを読む。存在しなければ403とする。
  2. なりすまし対策トークンの妥当性を確認する。
  3. 日程（イベント詳細）が1件以上残っている場合、削除不可エラーを表示し直前画面（referer）へ戻す。
  4. 日程が無い場合、イベントを削除してフラッシュする。
  5. 完了メッセージを表示し、検索結果ページへリダイレクトする。遷移先のページ番号はセッションのページ番号、無ければ1ページ目とする。

チェックした日程を一括削除する

  1. 削除対象の日程IDが空の場合は404とする。
  2. 送信された日程IDをカンマ区切りで分解し、当該イベントの該当日程を読む。該当が無ければ404とする。
  3. なりすまし対策トークンの妥当性を確認する。
  4. 各日程について、デッキ登録が1件以上あればデッキ登録エラーを表示し直前画面へ戻す。申込が1件以上あれば申込エラーを表示し直前画面へ戻す。
  5. いずれにも該当しない日程を削除してフラッシュする。
  6. 日程削除完了メッセージを表示し、編集画面へリダイレクトする。

集計条件

指標集計の要点
日程ごとの申込人数当該イベントの日程ごとに、申込状況が参加状態の申込件数を数える。表示は「申込人数／定員」の形で日程ごとに示す。集計はイベント詳細との結合と申込状況の一致条件で行う。

更新時の判定順序

順序判定結果
1パスIDのイベントが存在するか存在しなければ403。
2申込済みの日程があり、支払方法に差分があるか差分があり申込済みなら支払方法変更不可エラーを表示し直前画面へ戻す。
3フォーム検証失敗なら登録失敗エラーを表示し編集テンプレートを再描画。
4永続化成功なら完了メッセージを表示し編集画面へリダイレクト。

削除時の判定順序（イベント）

順序判定結果
1パスIDのイベントが存在するか存在しなければ403。
2なりすまし対策トークン不正なら共通のアクセス拒否として扱う。
3日程が残っているか残っていれば削除不可エラーを表示し直前画面へ戻す。
4削除実行完了メッセージを表示し検索結果ページへリダイレクト。

削除時の判定順序（チェックした日程）

順序判定結果
1削除対象日程IDが空でないか空なら404。
2当該イベントに該当日程が存在するか無ければ404。
3なりすまし対策トークン不正なら共通のアクセス拒否として扱う。
4各日程にデッキ登録があるかあればデッキ登録エラーを表示し直前画面へ戻す。
5各日程に申込があるかあれば申込エラーを表示し直前画面へ戻す。
6削除実行日程削除完了メッセージを表示し編集画面へリダイレクト。

業務ルール・計算

項目内容
登録者ID新規登録・更新の永続化前に、ログイン中の管理者IDを登録者ID（member_id）に設定する。
支払方法の選択肢支払方法はイベント申込で利用可能な支払方法に絞って表示する（支払方法の所定ID群、ランク昇順）。新規時はクレジットカードを初期選択する。
支払方法変更不可更新時に申込済みの日程があり、送信された支払方法が現在値と差分を持つ場合は変更を許さず直前画面へ戻す。
イベント削除可否日程が1件でも残っているイベントは削除しない。
日程削除可否デッキ登録済み、または申込済みの日程は削除しない。
計算参加費・定員・チーム人数は入力値をそのまま整数として保存する。金額計算・税計算・丸めは行わない。

項目名必須／任意最大長初期値保存先・扱い
