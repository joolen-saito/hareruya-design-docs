F07-04（大会申込～完了）

刷新後は実装不要本節は現行実装（pf-eccube3）からのリバースです。次の記述は Excel基本設計により廃止されており、刷新後に実装する必要はありません。

  • チーム人数 は チーム戦フラグ（dtb_event.is_team_battle、真偽） へ変更（0214 イベント編集 識別ID:1-12）これに伴い実装不要: チームメンバーのメールアドレス・席次の入力／メールのみの仮選手（dtb_player）の作成／チームメンバー招待メールの送信／未承認（confirm_flg=UNCONFIRMED）での申込選手登録／招待リンクからのチームプレイヤー認証（events_team_player_activate）
  • 席順（席次） は削除（0214 イベント申込詳細・編集 識別ID:4-1）これに伴い実装不要: 参加プレイヤー表の席順セレクトと、席順アルファベット一覧による検証／申込選手への席次（seat_order）設定
  • チームメンバー確認済み（承認フラグ） は削除（0214 イベント申込詳細・編集 識別ID:4-3）これに伴い実装不要: 参加プレイヤー表のチームメンバー確認済チェックと、その更新／承認フラグ（dtb_entry_player.confirm_flg）の運用／招待リンクからのチームプレイヤー認証（events_team_player_activate）

ログイン会員が、イベント詳細を申込対象に選び、別日程の同イベントを追加し、支払方法を選び、確認のうえ申込を登録し、無料時または決済完了後に申込完了画面に至るまでの、複数段階のイベント申込機能である。

概要

大会申込～完了は、ログイン会員が選択したイベント詳細について、申込対象の選択（別日程の同イベントの追加を含む）、支払方法・チームメンバー席次とメールアドレスの入力、申込内容の確認、申込の登録、決済への遷移、申込完了画面の表示までを扱う機能である。申込登録は1トランザクションで申込・申込選手・申込履歴を作成し、チーム戦ではメンバー招待メールを送る。参加費が0円なら申込状況をエントリー済みにして完了画面へ進み、有料なら申込状況を決済中にして外部決済へ遷移し、決済完了後に完了画面へ至る。

なお、チームメンバー席次・メールアドレスの入力と招待メールの送信は現行挙動であり、※Excel基本設計 0214 識別ID:1-12 により廃止。刷新後は実装しない（リニューアル移行時の扱いを参照）。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。確認値はpf-eccube3（EC-CUBE3系）のHareruyaEcプラグインのイベント申込・支払方法選択・申込確認・申込登録・決済完了・決済キャンセル処理、申込フォーム種別（event_registration）、テンプレート（Event/entry.twig・Event/select_payment.twig・Event/entry_confirm.twig・Event/payment_complete.twig・Block/js/event_payment.twig）、申込状況マスタを正とする。

本機能のカスタマイズ区分はカスタマイズであり、挙動の参照リポはpf-eccube3、DB関連はec-cube-enterpriseを正とする。

対象はブラウザ経由のフロントに限定する。フロントのルートはロケールを先頭に持つ/{_locale}配下にあり、イベントは/{_locale}/events配下にまとまる。

本文ではフレームワークのコントローラ型名やメソッド名を主説明としない。本文ではルートbind名の網羅は主説明とせず、「利用者視点の入口」にHTTPメソッドとサイトルートからのパスパターンを書く。コード探索でbind名が必要なときだけ「調査補助」へ書く。

本書で扱うこと

  • 申込対象の選択（別日程の同イベント追加）から完了までの段階遷移
  • 支払方法・チームメンバー席次・メールアドレスの入力と検証
  • 申込確認・申込登録（非同期）の判定順序と副作用
  • 無料申込と有料申込（外部決済）の分岐、決済完了・決済キャンセルの扱い
  • 受付期間・定員・重複申込の再判定

本書で扱わないこと

以下は本書では仕様確定せず、実装または別機能の設計を正とする。

  • イベント大会TOP（F07-01）・大会詳細検索（F07-02）・イベント詳細参照（F07-03）
  • 外部リンク決済（SPLINKS決済プラグイン）の内部仕様・暗号化・決済URL生成の詳細
  • チームメンバー招待メールの本文・件名（メールテンプレート管理を正とする）
  • デッキ登録・キャンセル申込・チームメンバー認証（チームメンバー認証は招待メールのリンクから未承認の申込選手を承認する現行機能。Excel基本設計 0214 識別ID:4-3 により廃止のため、刷新後は実装しない）
  • 会員ログイン・選手情報登録の仕組み

リニューアル移行時の扱い

本機能はカスタマイズ区分がカスタマイズである。現行挙動はpf-eccube3のHareruyaEcプラグインを正とし、DBスキーマと移行後の扱いはec-cube-enterpriseを正とする。イベント関連テーブルはec-cube-enterpriseに移行済みであり、現行と移行先で次の差がある。

処理フロー

申込対象を選ぶ（GET /{_locale}/events/{eventDetailId}/entry）

  1. イベント詳細を取得する。無ければページが見つからない（HTTP404）として扱う。
  2. 受付期間外、またはログイン会員が申込済みなら、イベント詳細（F07-03）へリダイレクトする。
  3. ログイン会員の選手情報で、申込可能な別日程の同イベントを取得し、申込可能なものに絞る。
  4. 申込可能な別日程が無ければ、支払方法選択処理へ進む。あれば申込対象選択画面を表示する。

支払方法選択を開く（GET /{_locale}/events/{eventDetailId}/select_payment）

  1. 一括遷移（主IDが0）の場合、追加対象の先頭を主対象に繰り上げる。
  2. 主対象を取得する。無ければページが見つからない（HTTP404）として扱う。
  3. 受付期間外、または申込済みなら、イベント詳細へリダイレクトする。
  4. 追加対象を取得し、すべて同一イベントであること・すべて参加可能であることを確認する。満たさなければ不正要求（HTTP400）として扱う。
  5. 合計参加費を計算する。0円なら支払方法を提示せず、有料ならイベントの支払方法を提示する。
  6. 申込対象・合計・支払方法・チーム入力欄を表示する。前段の検証エラーがあれば各欄に表示する。

申込内容を確認する（POST /{_locale}/events/confirm）

  1. なりすまし対策トークンを検証する。
  2. 主対象を取得する。無ければHTTP404。受付期間外・申込済みならイベント詳細へリダイレクトする。
  3. 追加対象を取得し、同一イベント・参加可能を確認する。満たさなければHTTP400。
  4. チーム戦（チーム人数が1より大きい）なら、メンバーメールと席次を検証する。重複メール・席次不正・ログイン会員と同一メールはエラーとし、支払方法選択へエラー付きで戻す。
  5. 検証を通過したら、申込確認画面を表示する。支払方法があれば確認後の送信をPOST、無料時はGETとする。

申込を登録する（POST /{_locale}/events/registration・非同期）

  1. 非同期要求でなければ不正要求（HTTP400）として扱う。
  2. 申込フォームを検証する。検証不正ならエラーログを記録し不正要求（HTTP400）。
  3. 申込対象（主対象＋追加対象）を取得し、トランザクションを開始する。
  4. 同一イベント・参加可能（定員ロックつき再判定）を満たさなければ不正要求（HTTP400）。
  5. 合計参加費が0円なら申込状況をエントリー済み、正しい支払方法があれば決済中、いずれでもなければ不正要求（HTTP400）とする。
  6. チーム戦なら、メンバーメール数・重複・席次を再検証し、不正なら支払方法選択へエラー付きで戻す。検証通過後、メンバーのメールのみの仮選手を作成する。
  7. 申込対象ごとに、申込・申込選手（ログイン会員と仮選手）を作成し、チーム戦のメンバーには未承認・席次を設定する。チーム戦ではメンバー招待メールを送る。（※Excel基本設計 0214 識別ID:4-3 により廃止。刷新後は実装しない。仮選手の作成・未承認登録・席次設定・招待メール送信はいずれも行わない）
  8. 先頭申込から支払番号（EV＋作成日時＋申込ID）を生成し、申込群に設定する。
  9. 申込履歴を登録する。
  10. トランザクションをコミットする。例外時はロールバックして再送出する。
  11. 無料なら完了画面用パラメータ（対象詳細ID）を、有料なら決済用パラメータ（支払番号・金額）をJSONで返す。

決済後に戻る（GET /{_locale}/events/payment_finish）

  1. 外部決済の結果を復号して取得する。
  2. 結果コードが正常でなければ、決済ログにエラーを記録し、決済キャンセルへリダイレクトする。
  3. 正常なら、支払番号で申込を取得し、決済確認処理で申込状況を確定する。確定に失敗すれば決済ログにエラーを記録する。
  4. 申込完了画面へリダイレクトする。

申込完了を表示する（GET /{_locale}/events/payment_complete）

  1. 対象詳細IDで詳細を取得する。
  2. 完了文言と、デッキ登録可能なときのデッキ登録導線、大会一覧への導線を表示する。

決済キャンセル（GET/POST /{_locale}/events/payment_cancel）

  1. 支払番号で申込を取得する。
  2. 決済確認処理で申込を取消側に整える。
  3. 決済キャンセル画面を表示する。
