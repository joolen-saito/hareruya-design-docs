店頭買取管理 — 買取商品履歴（検索／一覧）

概要

管理画面「店頭買取管理」配下の「買取商品履歴」である。店頭買取の実在庫履歴（1行が1件の在庫増減履歴に相当）を検索し、一覧表示する。検索は画面専用フォームから POST で実行し、条件・ページ番号・表示件数・ソート指定はセッションに保持する。検索後は同一画面上に結果テーブルを出し、選択行または直近の検索条件に基づく CSV を別リクエストで返す。

HareruyaEc プラグイン由来のテンプレートコメントがあるが、現行の確認対象は ec-cube-enterprise の実装とする。

カスタマイズ区分はカスタマイズである。挙動はec-cube-enterpriseの実装を確認値とし、DB関連もec-cube-enterpriseを正とする。現行（pf-eccube3のHareruyaEcプラグイン）との差は「リニューアル移行時の扱い」に記録する。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。対象はブラウザ経由の管理画面に限る。

本文ではコントローラのメソッド単位の解剖を主題としない。本文ではルートbind名やSymfonyのルートnameの網羅は主説明としない。「利用者視点の入口」にHTTPメソッドとサイトルートからのパスパターンを書く。コード探索でbind名が必要なときだけ「調査補助」へ書く。

リニューアル移行時の扱い

買取商品履歴が検索・出力で参照する店頭買取系テーブルは、現行（pf-eccube3のHareruyaEcプラグイン）と移行先（ec-cube-enterprise）でテーブル名・主要列名が一致し、概ね同一スキーマである。dtb_otc_buy_order_stock_historyのbefore_quantity・after_quantity・create_date・member_id・otc_buy_order_stock_id、dtb_otc_buy_order_stock、dtb_otc_buy_orderはいずれも同名である。確認できた差分は次のとおりで、DB関連はec-cube-enterpriseを正とする。

観点現行（pf-eccube3のHareruyaEcプラグイン）移行先（ec-cube-enterprise）
実在庫履歴・実在庫テーブル同名（同一スキーマ）同名（同一スキーマ）
棚戻し列dtb_otc_buy_orderにrestocked_flg・restocked_dateを持たないrestocked_flg・restocked_dateを追加。ただし本履歴の検索・出力列には含まれない

フロント挙動

観点内容
表示要素タイトルは「店頭買取管理」、サブタイトルは「買取商品履歴」。メニューは purchase_store と history。検索欄に査定ID、申込者名、会員ID、ステータス（複数チェック）、買取店舗、査定担当者名、商品コード、商品名、買取日時（開始・終了）、基準価格（開始・終了）、買取価格（開始・終了）、言語（チェック）、状態（NM/SP/MP/HP のチェック）、検索ボタン。結果エリアは件数、表示件数ドロップダウン、CSV ドロップダウン、テーブル（チェック、査定番号、申込者、商品コード、商品名、基準価格、買取価格、買取店舗、作業者、買取数、入庫数、増減数、買取日時、更新日時）。0件時は該当なしメッセージ。
JS 挙動moment と tempusdominus で datetimepicker-input に日時選択（ロケール ja、形式 YYYY-MM-DD HH:mm）。ヘッダの全選択チェックで otcBuyOrderHistoryId 属性の行チェックを一括切替。CSV の各リンクは export_type 隠し項目を埋めて結果フォームを submit。
CSS・レイアウトBootstrap 4 系の水平フォームテーマ。ページャと CSV 用ドロップダウンで display:block !important のワークアラウンドを当てている。
モーダル・ポップアップ本機能専用のモーダルは無い。

補足（一覧テンプレートの二重ループ）: 結果テーブルは、ページングオブジェクトに対する外側の {# for #} と、同じコレクションに対する内側の {# for #} がネストした構造になっている。1ページ N 件のとき、同じ N 行から成る表が最大 N 回繰り返し描画されうる（実装を確認値とする）。

補足（一覧の日付表示）: 「買取日時」列は注文の completeDate が無いとき cancelDate を使う。日付と時刻は2行表示。

処理フロー

初回表示（GET admin_otcbuyorder_history、ページ番号 0）

  1. 管理画面の認証・共通制約を通過する。
  2. 空の検索フォームを生成する（CSRF 保護はフォーム側で無効）。
  3. pagination を空配列、page_count を eccube_default_page_count にし、テンプレートを返す。一覧は出さない。

検索実行（POST admin_otcbuyorder_history）

  1. コントローラがページ番号 1 でトレイトの検索処理を呼ぶ。
  2. フォームがリクエストを取り込み、検索データが得られる。
  3. 表示件数はセッションまたは page_count クエリで上書きし、許可された値だけ mtb_page_max 由来の一覧に合わせて矯正する。
  4. sort と order はクエリまたはセッションから決まるが、不正な order 文字列のときはソートエラーメッセージを出し、初回表示相当へ戻る。
  5. 検索データから専用 DTO を経由して履歴のクエリビルダを組み、ページャで Slice する。
  6. ページ番号・検索条件の表示用データ・ソート・表示件数をセッションキー eccube.admin.otcbuyorder_history.* 系に保存する。
  7. 最終ページで件数が境界に落ちた場合は 1 ページ戻して再ページングする。
  8. フォームのビュー・ページング・表示件数リスト・フィルタ有効フラグ等をテンプレートへ渡す。

ページング表示（GET admin_otcbuyorder_history_page または GET /history に page_no／pageno）

  1. パス上の page_no が正のとき、フォームの handleRequest を経ずにトレイトの検索を呼ぶ（コントローラ実装どおり）。
  2. 検索データがフォームから空のとき、セッションの表示用データを復元して同じ条件で再検索する。
  3. セッションにも検索が無いとき、初回表示相当の配列を返す。

CSV 出力（POST admin_otcbuyorder_history_export）

  1. export_type を読む。check_export でも all_export でも無ければ例外を投げる（本書ではバリデーション失敗時の利用者向け画面挙動を仕様確定しない）。
  2. check_export のとき、POST の otcBuyOrderHistoryIds が空なら管理画面向けエラー文をフラッシュし、eccube.admin.otcbuyorder_history.search.page_no のページへリダイレクトする。
  3. all_export のとき、セッションの eccube.admin.otcbuyorder_history.search が無ければエラー文をフラッシュし、同様にリダイレクトする。
  4. それ以外はストリーム応答で CSV を書き、ファイル名 otc_buy_order_history_YmdHis.csv、ログにファイル名のみ情報ログを残す。

集計条件

一覧・CSV の対象行は、実在庫履歴を起点に実在庫・店頭買取注文・規格・商品・言語・注文ステータス・店舗（左結合）へ結合した結果集合である。検索条件は次節の業務ルールに従い AND で積み上げる。件数表示はページャの総件数である。

指標集計の要点
一覧件数上記集合への条件適用後の履歴行数。重複排除の特別処理は無い。
CSV 全件一覧と同じクエリ条件で Slice せずに全行を読み、行配列に変換する。

一覧・検索時の判定順序（条件の適用）

実装はクエリビルダに条件を順に付与し、最後に固定の ORDER BY を付ける。利用者が指定できるソート列の切替は本クエリでは行わない（セッションの sort/order を読んでも履歴クエリは並びを変えない。実装を確認値とする）。

順序判定結果
1会員IDが非 null注文の会員参照がその ID と一致する一致条件を付与する。空文字列も非 null のため条件に含まれる（実装を確認値とする）。
2申込者名が非 null空白・全角半角カンマで分割した各キーワードについて、姓・名・姓カナ・名カナへの部分一致を OR し、キーワード間は AND とする。
3査定IDが非 null査定IDの完全一致。空文字列も非 null（実装を確認値とする）。
4査定担当者名が非 null注文に紐づく査定担当者名の部分一致。SQL ワイルドカードはエスケープする。
5店舗が非 null注文の BaseInfo がその店舗と一致する条件。
6ステータスが1件以上選択注文ステータスがそのいずれかに合致。
7商品コードが非 null規格コードの完全一致。
8商品名が非 null商品名の部分一致。ワイルドカードはエスケープする。
9買取日時（開始または終了）注文ステータスがキャンセル（ID 2）のときは cancelDate、それ以外は completeDate に対して境界を付与する。
10買取価格下限subtotal >= 下限 * quantity（単価条件の代数変形）。
11買取価格上限subtotal <= 上限 * quantity。上下限は独立に付与しうる。
12基準価格下限／上限規格の standardPrice に不等号。
13言語が1個以上日本語・英語IDは IN、フォーム値「その他言語」（整数 3）は日本語・英語以外の言語を NOT IN で表す分岐を含む複合条件。規格の Language に追加結合する。
14状態が1個以上規格のカード状態IDが選択集合に含まれる。
最後並び注文の completeDate 降順、履歴の createDate 降順に固定する。

項目内容

データ整合性

観点内容
一覧と CSV全件 CSV は直近セッションの検索条件をフォームへ再投入してから同一系のクエリで取り直す。選択 CSV は ID 列の集合で取り直す。
参照時点検索リクエスト処理中のコミット済みデータを読む。リアルタイム一致の保証はトランザクション隔離の一般論に従い、本書では追わない。
店舗名表示注文と店舗が左結合のため、店舗無しの注文では店舗名列は空表示になりうる。
