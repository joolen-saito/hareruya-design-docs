F06-16（大会デッキ登録編集）

概要

ログイン済み会員が、申し込んだ大会（イベント）に登録するデッキを編集・提出する機能である。デッキ登録一覧などからイベント詳細単位の編集画面に入り、フォーマットを選択し、メインボード・サイドボードのカードリスト（半角数字＋半角スペース＋カード名の行）を入力して提出する。提出時にカードリストの書式・カードを検証し、書式に誤りがあれば入力を保持したまま編集画面へ戻す。書式が通れば登録済みデッキを上書き、または新規にデッキを作成し、デッキ確認画面（枚数・カードの確認）へ遷移する。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。確認値はpf-eccube3（EC-CUBE3系）のHareruyaEcプラグインの大会デッキ編集・更新処理、テンプレート（Mypage/deckentry.twig）、カードリスト解析のユーティリティ処理、メッセージ（message.ja.yml）を正とする。

本機能のカスタマイズ区分はカスタマイズである。挙動の参照リポはpf-eccube3とし、DB関連の記述（テーブル名・列名・永続化先・副作用のDB更新）は ec-cube-enterprise を正とする。現行と移行先のスキーマ差は「リニューアル移行時の扱い」に集約する。

対象はブラウザ経由のフロント（会員マイページ）に限定する。フロントのルートは/{_locale}配下にマウントされ、URLは/{_locale}/deckentry/{eventDetailId}/editなどの形をとる。

本文ではフレームワークのコントローラ型名やメソッド名を主説明としない。本文ではルートbind名の網羅は主説明とせず、「利用者視点の入口」にHTTPメソッドとサイトルートからのパスパターンを書く。コード探索でbind名が必要なときだけ「調査補助」へ書く。

本書で扱うこと

  • デッキ編集画面の入口と表示（フォーマット選択・メイン／サイドボードの入力）
  • デッキ提出（更新）時の書式検証・登録（上書き／新規作成）・遷移
  • 入力補助（カード名サジェスト、インポート、マイデッキ取得）のUI
  • デッキ登録可否の判定（イベント詳細の存在・登録可否・締切）
  • 書式エラー時の入力保持と再表示
  • 未ログイン・登録不可イベントの扱い

本書で扱わないこと

以下は本書では仕様確定せず、実装または別機能の設計を正とする。

  • デッキ確認画面（枚数チェック・カードエラー表示・確認～完了）の表示（大会デッキ確認機能を正とする。本書では提出後の遷移先として示す）
  • デッキビルダー本体・デッキ情報取得API・マイデッキの内部仕様（デッキ機能・APIを正とする）
  • イベント申込・決済そのもの（イベント機能を正とする）
  • デッキ登録完了メールの本文・件名（メールテンプレート管理機能を正とする）

処理フロー

デッキ編集画面を表示する（GET /{_locale}/deckentry/{eventDetailId}/edit）

  1. 会員ログインを要求し、ログイン会員に紐づく選手情報を特定する。選手情報が無い場合は存在しない（HTTP404）として処理する。
  2. イベント詳細を取得し、デッキ登録可否を判定する。問題があれば存在しない（HTTP404）として処理する。
  3. 当該選手情報・イベント詳細の登録済みデッキをフォーマット別に取得する。
  4. 書式エラーでのリダイレクト直後は、セッションに退避した入力（メイン・サイド・エラー）を復元し、セッションから削除する。
  5. マイデッキ取得指定（deckId）があれば、デッキ情報取得APIで取得し、本人のデッキであればメイン・サイドの入力をマイデッキの内容で上書きし、選択フォーマットを合わせる。
  6. フォーマット別サジェストファイル・マイデッキ一覧・選択中フォーマット等とともに編集画面を表示する。

デッキを提出する（POST /{_locale}/deckentry/{eventDetailId}/update）

  1. なりすまし対策トークンを検証する。
  2. ログイン会員に紐づく選手情報を特定する。選手情報が無い場合は存在しない（HTTP404）。
  3. 選択フォーマットを確定する。フォーマットが確定できない場合は存在しない（HTTP404）。
  4. デッキ登録可否を判定する。問題があれば存在しない（HTTP404）。
  5. メイン・サイドの入力をアリーナ形式から実カード名へ変換する。
  6. メイン・サイドのカードリストを解析し、書式・カードを検証する。
  7. 書式に誤りがある場合は、入力（メイン・サイド・エラー内容）をセッションへ退避し、編集画面（同一イベント詳細・選択フォーマット）へリダイレクトする。デッキは登録しない。
  8. 書式が通った場合、当該イベント詳細・選手情報・フォーマットに登録済みデッキがあれば上書き（既存カードを除去して再登録）し、無ければ新規にデッキを作成する。
  9. メイン・サイドのカードをデッキに登録し、編集者をクリアして保存する。
  10. デッキ登録完了メールを送信する。
  11. デッキ確認画面（/{_locale}/deckentry/{deckId}/check）へ遷移する。

デッキ提出時の判定順序

順序判定結果
1なりすまし対策トークンが正当か不正ならアクセス拒否（フレームワークの検証による）
2選手情報が特定できるかできないなら存在しない（HTTP404）
3選択フォーマットが確定できるかできないなら存在しない（HTTP404）
4イベント詳細が登録可（存在・登録フラグ有効・締切前）か不可なら存在しない（HTTP404）
5メイン・サイドの書式が正しいか誤りなら入力を保持して編集画面へ戻す（登録しない）
6上記を通過デッキを上書きまたは新規作成し、確認画面へ遷移

カードの枚数（最小／最大）・禁止・制限などの判定はデッキ確認画面で行い、本機能では書式（行形式・カード存在・登録枚数の妥当性）を検証する。

DBカラム

テーブル列メモ
