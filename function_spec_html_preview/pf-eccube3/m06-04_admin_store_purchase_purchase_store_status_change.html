店頭買取管理 — 買取ステータス変更

概要

管理画面「店頭買取管理」において、店頭買取受注（dtb_otc_buy_order）のステータス（mtb_otc_buy_order_status）を変更する機能である。専用の「ステータス変更」画面での任意ステータス選択と保存に加え、詳細画面の「経理払出し済」「入庫済みにする」の固定遷移ボタンから同一の更新処理へ到達する。

詳細画面の明細保存・在庫増減・個別入力商品の実在庫登録は本書の範囲外とする。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。リポジトリ内の店頭買取管理HTTPルートとステータス更新処理を確認値とする。

カスタマイズ区分はカスタマイズである。挙動はec-cube-enterpriseの実装を確認値とし、DB関連もec-cube-enterpriseを正とする。現行（pf-eccube3のHareruyaEcプラグイン）との差は「リニューアル移行時の扱い」に記録する。

対象はブラウザ経由の管理画面に限定する。

本文ではコントローラのメソッド単位の解剖を主題としない。本文ではルートbind名やSymfonyのルートnameの網羅は主説明としない。「利用者視点の入口」にHTTPメソッドとサイトルートからのパスパターンを書く。コード探索でbind名が必要なときだけ「調査補助」へ書く。

リニューアル移行時の扱い

ステータス変更が更新する店頭買取系テーブルは、現行（pf-eccube3のHareruyaEcプラグイン）と移行先（ec-cube-enterprise）でテーブル名・主要列名が一致し、概ね同一スキーマである。dtb_otc_buy_orderのotc_buy_order_status_id・complete_date・cancel_date・update_date、dtb_otc_buy_order_status_history、mtb_otc_buy_order_status（name列長16）はいずれも同名である。確認できた差分は次のとおりで、DB関連はec-cube-enterpriseを正とする。

観点現行（pf-eccube3のHareruyaEcプラグイン）移行先（ec-cube-enterprise）
ステータス・履歴テーブル同名（同一スキーマ）同名（同一スキーマ）
入庫日時列dtb_otc_buy_orderにrestocked_dateを持たないrestocked_date（入庫日時）を追加。入庫済み系遷移時の日時保持に用いる
棚戻し済みフラグrestocked_flgを持たないrestocked_flg（棚戻し済みフラグ）を追加

フロント挙動

観点内容
表示要素ステータス変更画面は menus = ['purchase_store', 'list']。カード見出し「ステータス変更」。査定番号・現在のステータスは参照表示。変更は「変更後のステータス」のセレクト1つと「保存」。左下リンクで詳細へ戻る。
JS挙動詳細画面で「経理払出し済」送信前に confirm('経理払出し済みに変更します。よろしいですか？') を出し、取消なら送信しない。「入庫済みにする」に同様の確認は無い。
CSS・レイアウトステータス変更画面は4系の変換エリア（下部バー）に戻る・保存を配置。
モーダル・ポップアップステータス変更専用モーダルは無い。詳細画面の商品検索モーダルは別用途。

処理フロー

ステータス変更画面を表示する（GET admin_otcbuyorder_status）

  1. 管理画面の認証を通過する（管理用ファイアウォールのパターンに含まれるパス）。
  2. otcBuyOrderId に該当する店頭買取受注が無ければ404応答とする。
  3. 店頭買取ステータス変更用の空フォームを生成する（変更後ステータスに初期選択値は載せない。プレースホルダ「ステータスを選択」）。
  4. テンプレートを表示する。

ステータス変更画面から保存する（POST admin_otcbuyorder_status_update）

  1. 手順2と同様に対象行の存在を確認する。
  2. フォームをバインドし、送信かつ妥当なら「変更後のステータス」エンティティを取り出す。
  3. 共通の更新処理を呼ぶ（後述「共通更新処理」）。
  4. 更新処理が業務拒否用のメッセージ付き例外を投げた場合、管理者向けフラッシュにメッセージを積み、同一店頭買取IDのステータス変更画面へGETリダイレクトする（詳細には戻さない）。
  5. 成功時は保存完了のフラッシュを積み、店頭買取詳細のルートへリダイレクトする。
  6. フォームが未送信または妥当でない場合、200で同一テンプレートを返しフィールドエラーを表示する。

詳細から「経理払出し済」を実行する（POST admin_otcbuyorder_update_status_account_team_paid）

  1. CSRFトークン名 account_team_paid を検証する。不一致ならCSRFエラーフラッシュを積み詳細へリダイレクトする。
  2. ログイン利用者が管理者アカウントでなければ認証例外を投げる。
  3. 店頭買取受注の店舗と、利用者の編集可能店舗が一致しない場合は実行時例外を投げ、利用者向け表現はアプリケーション全体のエラー表示に従う。
  4. 現在ステータスが経理払出し待ちでない場合、エラーフラッシュ「経理払出し待ちステータスの買取ではありません」を積み詳細へリダイレクトする。
  5. 次ステータスを買取成立（ID1）として共通更新処理を呼ぶ。
  6. 成功時は保存完了フラッシュ、失敗時は例外メッセージをフラッシュし、いずれも詳細へリダイレクトする。

詳細から「入庫済みにする」を実行する（POST admin_otcbuyorder_update_status_restocked）

  1. CSRFトークン名 restocked を検証する。不一致ならCSRFエラーフラッシュを積み詳細へリダイレクトする。
  2. ログイン利用者が管理者アカウントでなければ認証例外を投げる。
  3. 店舗一致が取れなければ実行時例外を投げ、利用者向け表現はアプリケーション全体のエラー表示に従う。
  4. 次ステータスを入庫済み（ID11）として共通更新処理を呼ぶ。
  5. 成功時は保存完了フラッシュ、失敗時は例外メッセージをフラッシュし、いずれも詳細へリダイレクトする。

共通更新処理

  1. ログイン利用者の編集可能店舗と、店頭買取受注の店舗が一致しなければ拒否する。
  2. 現在が入庫済みのとき、次が管理者取消でなければ拒否する。
  3. 次が入庫済みのとき、数量が正の明細に未紐付けの商品規格が無いか、個別入力商品に未登録の実在庫（商品規格未紐付け）が無いかを検査し、違反なら拒否する。
  4. トランザクションを開始する。
  5. 次が入庫済みかつDB上が入庫待ちのとき、DQLの一発更新で先行して入庫済みへ更新し、二重入庫抑止に使う（影響行数が処理要不要の判定に使われる）。
  6. 店頭買取受注の update_date を現在時刻に更新する。ステータスに紐づく日付列（買取成立・キャンセル・入庫）のうち、受注側の対応表に載るものだけを、ステータス遷移に応じた日時更新ルールで埋める（同一ステータスへの更新や、買取成立の重複上書きは抑止する実装）。
  7. ステータス本体を更新し、dtb_otc_buy_order_status_history に1件追記する。
  8. 次が買取成立のとき、個別入力商品の有無で「未登録在庫あり」か「入庫待ち」のどちらかを決め、同じトランザクション内でもう一度ステータス更新と履歴追記を行う。
  9. 手順5で入庫処理が要請されたとき、店頭買取実在庫を商品在庫へ反映し在庫履歴を残す（変更種別は店頭買取入庫）。
  10. flushしてコミットする。例外時はロールバックして再送出する。
  11. トランザクション完了後、新旧ステータスが「買取集計データ対象ステータス」集合の内外に跨い且つ買取成立日時が既に入っている場合だけ、買取成立日の日付単位で集計サマリを再計算する。

集計条件

本機能は一覧の件数集計画面を持たない。ステータス更新後に走る再集計は、マスタ定義の買取集計データ対象ステータス（買取成立・入庫済み・未登録在庫あり（ID12）・入庫待ち）への出入りがあり、且つ店頭買取受注に買取成立日時が入っている場合に限定される。

ステータス変更時の判定順序

順序判定結果
1編集可能店舗と買取店舗の一致不一致なら拒否（画面別にリダイレクト先と例外種別が異なる）。
2現在が入庫済みか入庫済みなら次が管理者取消でなければ拒否。
3次が入庫済みか明細・個別入力の商品規格必須チェック。
4次が買取成立か成立なら続けて入庫待ち系の最終ステータスへ2回目の更新を行う。
5入庫待ちから入庫済みか条件を満たせば在庫入庫処理を行う。

項目内容

エッジケース

ケース扱い
DB上の現在ステータスが廃止IDプルダウンに無くても、他IDへの変更は可能（画面は現在名をそのまま表示）。
買取成立へ遷移履歴は最大2件連続で同一操作時刻ベースで残る。買取成立日時は二重設定を避ける実装がある。
入庫済み以外から「入庫済みにする」入庫待ちを前提とした先行更新は0件となり在庫入庫処理は走らない。

データ整合性

観点内容
画面とDB成功後はリダイレクト先で再読込した値が新ステータスと一致する。
履歴各成功遷移で最低1件、買取成立なら2件の履歴が同一トランザクションに乗る。
在庫入庫待ちから入庫済みへ変えるときだけ、受注が入庫待ちであることを条件とした先行更新が1件起きた場合に店頭買取実在庫に基づく入庫が走る。入庫待ち以外から入庫済み化すると先行更新は0件となり在庫入庫処理は呼ばれない。

排他制御・トランザクション

更新処理は単一のDBトランザクションでまとめる。入庫待ちから入庫済みへの遷移では、DQLの条件付き更新で先行して状態を確定し、並行実行での二重入庫を抑止する意図の実装がある。HTTPや行レベルロックのユーザー向け文言は無い。

調査補助（grep向け）

実装の所在を機械検索するときの手掛かりとして、ルート名 admin_otcbuyorder_status、店頭買取ステータス用フォーム種別名、ステータス更新サービス、店頭買取在庫入庫処理、受注リポジトリの入庫待ち条件付き更新メソッドを参照する。
