デッキ管理 — 検索一覧からの一括編集

概要

HareruyaEc プラグインの管理画面「デッキ管理」において、検索結果一覧でチェックした複数デッキに対し、チェックボックスで選択した項目だけを共通値でまとめて更新する機能である。一覧・検索・詳細編集・CSV 入出力とは別ルートで POST され、change_flgs[項目名] でサーバに「どの列を上書きするか」が伝わる。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。カスタマイズ区分は「カスタマイズ」。画面・挙動は pf-eccube3 に配置された HareruyaEc プラグインのソースを確認値とし、DB関連（テーブル・列・型・制約・関連）は ec-cube-enterprise の実装を正とする。

対象はブラウザ経由の管理画面に限定する。

コントローラのメソッド単位の解剖は本文の主題としない。本文ではルートbind名やSymfonyのルートnameの網羅は主説明としない。「利用者視点の入口」にHTTPメソッドとサイトルートからのパスパターンを書く。コード探索でbind名が必要なときだけ「調査補助」へ書く。

リニューアル移行時の扱い

  • 画面・挙動は現行（pf-eccube3 の HareruyaEc プラグイン）の確認値、DBスキーマは移行先（ec-cube-enterprise）を正とする。
  • 一括編集の対象データはデッキ（dtb_deck）および関連するデッキカード（dtb_deck_card）である。これらは移行先 ec-cube-enterprise にも存在する。change_flgs[項目名] で指定された列のみを共通値で更新する点は実装挙動であり、移行先での列名・型は ec-cube-enterprise の DtbDeck／DtbDeckCard を正とする。
  • デッキ管理一括編集の管理画面（コントローラ）が ec-cube-enterprise に移植済みかは未確認のため、移植有無と差分は ec-cube-enterprise 実装で要確認とする。現行と移行先でデッキ系テーブルのスキーマ差が判明した場合は本節とDB節を更新する。

フロント挙動

観点内容
表示要素検索結果が 1 件以上のときのみ、一覧ヘッダ付近に CSV 出力・旧サイト向け出力・一括削除・「一括編集」アコーディオン・ページ件数・ソートがある。テーブル左端は deckId[] のチェックボックス、表頭 #allCheck で [deckId] 属性を持つ行チェックを一括オンオフする。一括編集パネル内は項目ごとに「変更フラグ用チェック」と入力ウィジェットを組み合わせる。初期状態では入力ブロックは display: none。
JS 挙動（一覧共通）Select2 を検索条件のフォーマット・アーキタイプ・タグ、および一括編集のアーキタイプ・フォーマット・デッキタグに適用する。検索側のアーキタイプはフォーマット・カラー選択で選択肢がフィルタされる。
JS 挙動（一括編集）変更フラグのチェックで対応する #bulk_update_form_* を表示切替し、チェック時に子要素の .required に HTML5 required を付与する（チェックオフで除去）。ページ読込時は一括編集の入力から required を剥がし、変更フラグはすべてオフにする。イベント開催日は moment 日本語ロケール付き datetimepicker（YYYY-MM-DD HH:mm）。「一括編集実行」押下時、変更フラグが 1 つも無ければアラート「変更されている項目がありません。」で送信中止。チェック済みデッキが 0 件なら「一括編集するデッキをひとつ以上選択してください。」で中止。通過後、フォームの submit イベントに確認「一括編集の内容を送信しますか？」を紐付ける（送信のたびにハンドラが追加され、同一セッションで複数回実行すると確認が複数回積み上がり得る実装である）。
CSS・レイアウト管理画面共通の Bootstrap 系。一括編集アコーディオンは accordion / toggle / accpanel 構造で、管理テンプレートの function.js によるスライド開閉が前提。
モーダル・ポップアップ専用モーダルは使わない。確認は alert / confirm のみ。

処理フロー

一括編集を実行する（POST m15-04_admin_deck_deck_bulk_update）

  1. 管理画面の認証・共通制約を通過する。
  2. フォーム名 m15-04_admin_deck_deck_bulk_update でリクエストを処理し、CSRF を検証する。失敗時はアクセス拒否（HTTP 403）の扱いになる（共通ヘルパの実装に従う）。
  3. フォーム検証に失敗した場合、エラーメッセージをフラッシュに積み、Referer ヘッダの URL へ HTTP リダイレクトする。
  4. 検証成功時、フォーム項目名とエンティティ更新用セッター名の対応表に従い、各 change_flgs[項目名] が存在する項目だけについて、フォームの値をセッターに渡して各デッキ行を更新する。change_flgs に無い項目は既存値を保持する。
  5. リクエストの deckId を配列として取得し、各要素が非空かつ半角数字のみであることを検査する。1 つでも不一致なら HTTP 404 で打ち切る。
  6. デッキ ID 集合に対応する行をリポジトリから取得する（取得方法は「エッジケース」参照）。
  7. 取得した各行について手順 4 の更新を適用し、最終更新者として操作者の管理者 ID を member_id に記録する。永続化コンテキストへ登録する。
  8. まとめて flush する。
  9. 成功メッセージキー admin.register.complete をフラッシュに積み、Referer へリダイレクトする。

一覧に一括編集フォームを載せる（表示時）

  1. デッキ検索一覧用のコントローラが bulkUpdateForm として空の m15-04_admin_deck_deck_bulk_update フォームビューをテンプレートへ渡す（トークンのみ実体化し、入力は未送信状態）。

エッジケース

ケース扱い
POST された deckId の一部が DB に存在しない取得できたデッキ行だけを更新する。存在しない ID についてエラーにはしない。
サーバ実装でのリポジトリ呼び出しコントローラ側の取得メソッド呼び出し名と、リポジトリに定義された複数 ID 取得メソッド名が一致しないソースがあり得る。その場合は未定義メソッド呼び出しとなる（調査補助でファイルとメソッド名を照合すること）。
変更フラグを 1 つも付けずに送信クライアントの「一括編集実行」でブロックされる。サーバ側は変更フラグが無くても検証が通れば flush だけ行い、実質データ変化はセッターが呼ばれない。
deckId を付けずに POSTクライアントではブロックされない経路があり得る。サーバでは deckId を foreach しており、PHP の版によっては致命的エラーまたは警告となり得る。
Referer が無いリダイレクト先が空や不正 URL になり得る。ブラウザとクライアント実装に依存する。
