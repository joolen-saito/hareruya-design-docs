m05-01_admin_order_order_search_list（受注管理 — 受注情報検索・一覧）

概要

管理画面の「受注管理」において、dtb_order および関連する配送・明細・顧客・店舗情報を検索条件で絞り込み、一覧（配送単位の行）としてページング表示する機能である。検索条件・ページ番号・表示件数・並び替えキーはセッションに保持し、resume クエリや検索パターン適用時に復元する。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。確認値とするソースは src/Eccube/Controller/Admin/Order、src/Eccube/Controller/Admin/Order/SearchOrderController、src/Eccube/Form/Type/Admin/SearchOrderType、src/Eccube/Repository/OrderRepository、src/Eccube/Resource/template/admin/Order/index.twig、共通 JS html/template/admin/assets/js/function.js とする。

本機能のカスタマイズ区分はカスタマイズである。挙動は現行リポpf-eccube3の受注管理実装を参照し、DB関連の記述はec-cube-enterpriseを正とする。

対象はブラウザ経由の管理画面に限定する。受注詳細の編集・メール個別送信・状態機械の業務規則の全部、CSV本体の項目マッピング、一括処理モーダル内部の通信仕様の細部は別範囲とする。

コントローラの公開関数一覧は本文の主題としない。本文ではルートbind名やSymfonyのルートnameの網羅は主説明としない。「利用者視点の入口」にHTTPメソッドとサイトルートからのパスパターンを書く。コード探索でbind名が必要なときだけ「調査補助」へ書く。

リニューアル移行時の扱い

受注検索・一覧が参照する永続化テーブルは、現行（pf-eccube3）と移行先（ec-cube-enterprise）で同一の名称を用いる。受注本体は dtb_order、配送は dtb_shipping、検索パターンは dtb_search_pattern であり、移行先 ec-cube-enterprise にいずれも実在する。本書が条件として参照する受注の列（注文番号 order_number、店頭注文番号 waiting_number、スマレジ取引ID smaregi_receipt_no、店頭予約日時 otc_rsv_date ほか）も移行先に存在し、列名・用途に差は確認されない。

DB関連の記述は ec-cube-enterprise を正とする。検索パターンの保存・適用が用いる列（name・display_key 等）の型・桁・制約の細部は ec-cube-enterprise の Entity / Repository / Migration を正とし、現行と移行先でスキーマが食い違う箇所があれば移行先の名称を主とする。本書時点で現行と移行先のスキーマ差は確認されていない。

処理フロー

通常一覧を表示する（admin_order / admin_order_page）

  1. 管理画面の認証・共通制約を通過する。
  2. ADMIN_ORDER_INDEX_INITIALIZE イベントで検索フォームビルダが差し替えられうる。
  3. 表示件数はリクエストの page_count が mtb_page_max と一致するときのみセッション eccube.admin.order.search.page_count を更新し、それ以外はセッションまたは eccube_default_page_count を使う。
  4. POST のときフォームをバインドし、検証に成功した場合のみ検索ビューデータをセッション eccube.admin.order.search に保存しページ番号を1にする。失敗時は has_errors を真にして詳細検索枠を開いた状態で同一テンプレートを返し、一覧は組み立てない。
  5. GET で page_no または resume があるときはセッションから検索ビューデータを復元してフォームへ流し込む。ページ番号はルートパラメータ優先。
  6. GET でどちらも無く初期表示のときはページ1とし、order_status_id クエリがあればステータス配列初期値のみ載せたビューデータでセッションを初期化する。
  7. 復元済み検索データから一覧用クエリビルダを組み立て、ADMIN_ORDER_INDEX_SEARCH イベントで差し替えられうる。
  8. KNPページネータでページングする。並びキーがマップに存在し order_status でないときは wrap-queries を付ける。
  9. display_key が order の検索パターン一覧などテンプレート変数を渡して描画する。

検索パターンを適用して一覧する（admin_order_search_pattern）

  1. pattern_id のパターンが無いときHTTP404とする。
  2. パターン本体をデシリアライズしてフォームへ投入し、検索データを組み立てる。
  3. セッションの検索ビューデータとページ番号をこの内容で上書きする。
  4. ページは常に1としてページネーションする。
  5. 返却変数セットが通常一覧より少ない点に注意する（後述）。

検索パターンを保存する（admin_order_save_pattern）

  1. POSTされたフォームからビューデータを生成する。
  2. パターン名が空ならエラーメッセージを積み admin_order へ戻る。
  3. tenants キーは保存前にビューデータから除去する。
  4. 既存IDがあれば更新、無ければ新規行を作り、display_key を order にし、会員が紐づく基本情報を書き込む。
  5. 成功メッセージののち、admin_order_search_pattern にリダイレクトする。

検索パターンを削除する（admin_order_delete_pattern）

  1. 対象が無ければエラーで admin_order に戻る。
  2. 削除成功時は成功メッセージののち admin_order に戻る。

検索パターン件数を取得する（admin_order_count_pattern）

  1. パターンをデシリアライズして検索データを組み立てる。
  2. 一覧と同じクエリビルダを複製し、COUNT(DISTINCT o.id) で件数を返す。
  3. パターン無しは実装上例外が投げられる経路がある。

エッジケース

  • 対応状況を1件も選ばないGET初期表示では、キャンセルと引渡し済を除く否定条件が付き、一覧の母集団が狭まる。
  • 日時範囲の開始と終了の両方があるとき、終了が開始より前ならフォームエラーとなり一覧は返らない。
  • 相対日数とカレンダー日時を同時に入れた場合、ヘルパが双方の境界を合成し、意図と異なる狭いレンジになりうる。
  • addDateCondition が常に同名プレースホルダ date_start と date_end を使うため、複数の日時列に同時に境界を掛けるとバインドが上書きされ、後から付与した条件以外が壊れる可能性がある（実装上有害な衝突）。
  • message_flg の厳密比較と文字列選択肢の組み合わせ次第でフィルタが期待通り動かない可能性がある。
  • 顧客グループはフォームとTODOコメントがあるがリポジトリ側フィルタが未実装である。
  • 一覧クエリは Customer を内部結合しており、顧客無し注文は結果から落ちる。
  • shipping_mail、tracking_number、単独の会社名、お届け日 の日付専用フィールドなどはフォームまたはマップにはあるが一覧検索クエリへ未到達である。
  • csrf_token はSymfonyフォームトークンにより検証される。

業務ルール・計算

  • 検索・一覧・取得条件はリクエストパラメータ、ログイン状態、公開状態、店舗・支店条件、既存リポジトリの絞り込み順序を正とする。
  • 件数、ページ番号、表示順は既存実装のデフォルトと上限に従い、取得後に業務値を再計算しない。
  • 金額、ポイント、数量、ステータス、日時はDBまたは連携元の永続化済み値を返却し、レスポンス生成時の丸め・補正は行わない。
  • 条件に一致しない、権限がない、または非公開のデータは空結果または既存のエラー形式で返す。

データ整合性

  • セッションキー eccube.admin.order.search、eccube.admin.order.search.page_no、eccube.admin.order.search.page_count が一覧・ページング・resume の再表示と整合することを狙う。
  • 一覧テーブルは配送単位であり、詳細画面の注文単位表示と行数が一致しない。
  • admin_order_search_pattern のレスポンスでは OrderCsvExtensions や ShippingCsvExtensions、memberId などが通常一覧より欠けるため、kernel.debug が真のTwigでは未定義変数エラーになりうる。
  • 一覧ヘッダの data-sortkey に order_date・order_number・order_commit_date などがあり、リポジトリの並びキーマップのキー集合（order・orderer・payment_method 等）と一致しない。該当キーで並び指示が送られると未定義キー参照になりうる。
  • admin_order_count_pattern は一覧イベントを経由しないため、プラグインが検索クエリへ付けた変更と件数がズレる余地がある。

排他制御・トランザクション

観点内容
トランザクション境界検索・一覧・件数取得は読み取りのみで明示トランザクションを開始しない。検索パターン保存・削除だけがdtb_search_patternを更新し、保存処理のflush単位で確定する。
ロック受注検索、検索パターン保存・削除とも行ロック・悲観ロック・楽観ロック・ロックファイルは使用しない。検索パターンを同時更新した場合は後から保存された内容が残る。
例外時検索・一覧表示中の例外にロールバック対象は無い。検索パターン保存・削除でflush前に例外が起きた場合は未確定、flush後の例外では保存済み内容は戻らない。
