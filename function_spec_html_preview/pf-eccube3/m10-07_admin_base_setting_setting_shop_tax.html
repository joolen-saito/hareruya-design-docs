店舗設定 — 税率設定（共通税率・商品別税率オプション）

概要

管理画面の「店舗設定」配下において、店舗全体の共通税率（税率・課税規則・適用開始日時）を複数件保持し、画面上で一覧・新規登録・編集・論理削除する機能である。また、画面ブロック「個別税率設定」から、商品ごとに個別の税率ルールを設定できるモード（実装上は店舗基本情報のオプション項目）を切り替える。画面ブロックタイトルは「基本情報設定」、サブタイトルは「税率設定」である。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。pf-eccube3コア実装を確認値とする。プラグインがコントローラ・テンプレート・イベントを差し替えている環境では、その環境の実装を正とする。

カスタマイズ区分は現行踏襲であり、挙動の参照リポはpf-eccube3とする。DB関連の記述（テーブル名・列名・型・制約、保存先・扱い、副作用のDB更新）はec-cube-enterpriseを正とする。現行と移行先でスキーマが異なる箇所は「リニューアル移行時の扱い」に集約する。

対象はブラウザ経由の管理画面に限定する。

本書の本文ではルート名の網羅やコントローラ実装の手順は扱わない。ただし「利用者視点の入口」には、HTTP メソッドとサイトルートからの相対パスを {admin_route} を含む形で記載する（ホスト名・絶対 URL は書かない）。

本書で扱うこと

  • 税率設定画面のブロック構成（個別税率設定・共通税率設定・税率一覧）と、同一HTMLフォーム内に2系統の送信先があること
  • 共通税率の入力検証、同一適用日時の重複チェック、保存・削除・適用不能・不存在時のリダイレクトとフラッシュメッセージ
  • tax_rule_id が既定の基本税率（ID固定値1）のときのフォーム差し替え（適用日時フィールド非表示・変更対象外）
  • 税率一覧の抽出条件（商品・規格に紐付かない共通税率のみ）と並び（適用日時の降順）
  • 店舗基本情報への「商品別税率機能」フラグの保存経路（上部「登録」ボタン専用）
  • 新規共通税率行の既定（課税規則マスタID1、税端数調整0、論理削除フラグ0）と、永続化時に付与される作成者・日時
  • イベントディスパッチによるフォーム初期化・保存完了・削除完了・パラメータ保存完了への差し込み点
  • 購入・表示側で税率を解決するときの優先キー設定（設定ファイルの確認値）およびリポジトリ内キャッシュの存在（画面保存とは別経路の確認値として記載）

本書で扱わないこと

以下は本書では仕様確定せず、実装または別機能の設計を正とする。

  • 管理画面ログイン、セッション、CSRFの仕様の詳細（名称や値の環境依存を含む）
  • 商品編集・規格編集画面での個別税率入力や、dtb_tax_rule に商品・規格・地域が付いた行の作成・更新の詳細
  • カート・注文・明細への税額の計上、TaxRuleService を介した金額計算の全呼び出し元と丸めの業務定義の網羅
  • 論理削除済み税率が課税解決クエリでどう扱われるかの意図した仕様（当コアでは課税解決クエリに論理削除条件が無い。実装を正とする）
  • 課税規則マスタ（mtb_taxrule）の名称・件数の運用変更手順
  • 導入プラグインによる差分の完全列挙

リニューアル移行時の扱い

現行（pf-eccube3）と移行先（ec-cube-enterprise）で、共通税率の永続化に関するスキーマが異なる。挙動説明は現行を確認値とするが、DB記述は移行先を主とし、現行名を括弧で添える。

観点現行（pf-eccube3）移行先（ec-cube-enterprise）
主キー列tax_rule_idid（dtb_tax_rule.id）
削除方式del_flg による論理削除。一覧取得では除外しないdel_flg 列が無く物理削除。論理削除の概念自体が無い
課税規則（端数処理）の参照calc_rule（参照先マスタ mtb_taxrule）rounding_type_id（参照先マスタ mtb_rounding_type、丸め種別マスタ）
税率・税端数・適用日時・作成更新・作成者・地域商品キーtax_rate／tax_adjust／apply_date／create_date／update_date／creator_id／country_id／pref_id／product_id／product_class_id同名（dtb_tax_rule 上で一致）
商品別税率機能フラグdtb_base_info.option_product_tax_rule同名（移行先では真偽型、既定偽）

移行先で論理削除が無いため、現行の「一覧取得が論理削除行を除外しない」という挙動は移行先には引き継がれない。削除済み行が一覧に残る現象は現行固有の確認値であり、移行先では物理削除により行自体が消える。

用語

用語説明
共通税率dtb_tax_rule のうち、product_id と product_class_id がともにNULL相当の行。本画面の一覧と編集対象はこの集合に限られる。
基本税率設定tax_rule_id がコア定数で定められた既定値（1）の共通税率行。一覧では適用日時列に固定文言「基本税率設定」と表示し、適用日時入力は出さない。
商品別税率機能店舗基本情報 dtb_base_info.option_product_tax_rule。有効時のみ課税解決で商品・規格を考慮する実装分岐がある（詳細はリポジトリ・サービス実装を正とする）。画面ラベルは「商品別税率機能」。
課税規則dtb_tax_rule.calc_rule が参照するマスタ mtb_taxrule の1件。税額計算時の端数処理種別（四捨五入・切り捨て・切り上げ）に対応するIDがマスタに保持される。
適用日時共通税率が「いつから有効か」の起点として比較される日時。基本税率行では画面上から変更しない。
論理削除del_flg を削除済み値へ更新する。本画面の一覧取得では論理削除を除外しないため、一覧に残りうる（実装確認値）。

利用者視点の入口

入口URLエンドポイント期待されるふるまい
ナビから税率設定を開く（一覧の既定入口）GET /{admin_route}/setting/shop/tax「個別税率設定」「共通税率設定」「税率一覧」が縦に並ぶ。共通税率の入力フォームは新規行用の初期状態で載り、商品別税率機能は現在の店舗基本情報の値が選択状態になる。一覧は共通税率のみが適用日時の新しい順で並ぶ。
一覧から「編集」を選ぶGET /{admin_route}/setting/shop/tax/{id}/edit当該行がフォームに載る。基本税率行なら適用日時欄は出ない。それ以外なら適用日時欄と日時ピッカーが出る。
共通税率で下部「登録」を押すPOST /{admin_route}/setting/shop/tax または POST /{admin_route}/setting/shop/tax/{id}/edit（編集文脈に応じる）検証に通れば当該行が保存され、成功メッセージのあと税率設定画面に戻る。失敗なら同画面でフィールドエラーが付く。
「個別税率設定」ブロックの「登録」を押すPOST /{admin_route}/setting/shop/tax/edit_paramフォームの送信先だけが切り替わり、商品別税率機能の選択だけが店舗基本情報へ保存される想定の経路になる。成功時は成功メッセージのあと税率設定画面に戻る。検証に失敗した選択値は保存されず、その場合も同様に画面へ戻る。
一覧から「削除」（論理削除）を実行するDELETE /{admin_route}/setting/shop/tax/{id}/deleteCSRF付きの削除要求。基本税率行は削除処理を呼ばず一覧へ戻るのみ。それ以外で対象が存在すれば論理削除し成功メッセージ。存在しなければ警告メッセージに差し替えられたうえで一覧へ戻る。
編集対象IDが存在しないGET /{admin_route}/setting/shop/tax/{id}/edit（不存在の {id}）例外によりエラー画面系の応答となる（フレームワークのエラーハンドリングに従う）。
未ログインまたは権限・IP制限で拒否される利用者上記パス（到達前）管理画面の共通ルールに従いアクセスできない（詳細は管理画面認証・認可の実装を正とする）。

フロント挙動

観点内容
表示要素ページ見出しはブロックタイトル「基本情報設定」とサブタイトル「税率設定」。ブロック「個別税率設定」にラベル「商品別税率機能」の展開ラジオ（選択肢は実装上「有効」「無効」）。その直下に中央寄せのボタン「登録」。ブロック「共通税率設定」にラベル「消費税率」の数値入力、ラベル「課税規則」の展開ラジオ（マスタ名称）、編集対象が基本税率でないときのみラベル「適用日時」の単一行テキスト入力とBootstrap datetimepicker。プラグイン等の追加フィールドは名前が plg で始まらない項目を「extra-form」欄にループ描画する実装がある。下部にもう一度中央寄せのボタン「登録」。ブロック「税率一覧」は表でID・消費税率（末尾に%表示）・課税規則・適用日時（基本税率は文言「基本税率設定」、それ以外は日時書式）・操作ドロップダウン。
JS挙動moment と bootstrap-datetimepicker を読み込み、適用日時入力に対してロケール日本語・書式 YYYY-MM-DD HH:mm・当日ジャンプボタンあり・現時刻の自動代入は行わない設定。上部「登録」クリック時にフォームの action を差し替えてそのまま submit する関数がある。
CSS・レイアウトdatetimepicker用CSSとBootstrap横型フォームテーマ。
モーダル・ポップアップ本機能では確認モーダルは使わない。
入力項目必須・任意・検証・保存先の対応は「業務ルール・計算」「バリデーション」を正とする。

処理フロー

一覧画面を開く（GET、一覧用エンドポイント）

  1. 管理画面の認証・権限・IP制限の各ルールを通過する。
  2. 編集対象として新規の共通税率エンティティを組み立てる（課税規則はマスタID1を既定割り当て、税端数調整0、論理削除フラグ0）。
  3. 店舗基本情報を取得し、フォームの「商品別税率機能」に現在値を明示的にセットする（フォーム項目自体はエンティティにマップしない）。
  4. 編集対象が基本税率ならフォームから適用日時項目を取り除く。
  5. イベントでフォームビルダに対する初期化フックを実行する。
  6. 共通税率一覧を取得しテンプレートへ渡す。
  7. テンプレートを描画する。

一覧画面を開く（GET、既存行の編集エンドポイント）

  1. 管理画面の認証・権限・IP制限の各ルールを通過する。
  2. パスに含まれるIDで共通税率を取得する。無ければ例外。
  3. 以降は「一覧を開く」と同様に、店舗基本情報との合成フォームを組み立て、基本税率なら適用日時を除外し、イベント初期化、一覧取得、描画する。

共通税率を保存する（POST、一覧または編集エンドポイント）

  1. フォームをリクエストで処理する。
  2. フォーム全体が有効であり、かつ同一適用日時の別行が存在しないことを確認する（基本税率は適用日時がフォームに無いため、この重複検索は実質ほかの行の適用日時との突き合わせのみになる）。
  3. 対象の共通税率エンティティを永続化しフラッシュする。イベントで完了フックを実行する。
  4. 管理画面向け成功メッセージを積み、税率設定画面（一覧表示）へリダイレクトする。
  5. 検証に失敗した場合は同一テンプレートを再描画し、成功メッセージは積まない。

商品別税率機能だけを保存する（POST、パラメータ用エンドポイント）

  1. tax_rule 名前のフォームビルダをデータ無しで用意し、イベントで初期化フックを実行する。
  2. POSTならリクエストで処理する。
  3. 「商品別税率機能」子フォームだけが有効な場合に限り、店舗基本情報の同一項目を更新しフラッシュする。完了イベントを実行し、成功メッセージを積む。
  4. GETでもPOSTでも最終的に税率設定画面（一覧表示）へリダイレクトする。子フォームが無効な場合は店舗基本情報を更新しない。

共通税率を論理削除する（DELETE）

  1. CSRFトークン検証を行う。
  2. 対象IDで行を取得する。無ければフラッシュをクリアし警告メッセージだけ残して一覧へリダイレクトする。
  3. 基本税率行でなければ論理削除フラグを更新してフラッシュし、完了イベントと成功メッセージを積む。
  4. 基本税率行なら何も更新せず一覧へリダイレクトする。
  5. 一覧へリダイレクトする。

集計条件

本機能では売上集計や税率ごとの件数集計を表示しない。

課税解決時の優先順序（参照のみ）

購入処理など別機能が税率を解決するとき、共通／地域／商品／規格の優先は設定キー tax_rule_priority の並びに基づきランク付けしたうえで、適用日時とランクの組でソートして先頭を選ぶ実装である。既定の確認値は product_id,product_class_id,pref_id,country_id の順である。同一リクエスト内のリポジトリキャッシュにより、キャッシュクリアまで再問い合わせ結果が再利用される。

本節は税率設定画面の保存処理そのものではなく、保存結果が参照される側の実装概要のメモである。

エッジケース

ケース扱い
基本税率行の削除を試みるリクエストは受理されるが論理削除処理は呼ばれず、リダイレクトのみ。
同一適用日時の別行が既に存在する（基本税率以外の編集・新規）フォームエラー文言「既に同じ適用日時で登録されています。」を付与し保存しない。
商品別税率機能へ不正な選択値をPOST店舗基本情報は更新しない。
論理削除済みIDへの削除要求対象無し扱いで警告メッセージに差し替え。

データ整合性

観点内容
一覧と編集フォーム一覧は共通税率の全件を論理削除で除外せず返すため、一覧に残った論理削除行を編集画面へ入れることは技術的に可能である。
商品別税率機能とフォームの上下ボタン画面上は同一フォームだが、店舗基本情報への反映は上部ボタン経路のみ。下部ボタン経路では値を読み取って保存しない。
課税計算側との整合税率設定保存時にリポジトリのメモリキャッシュを自動クリアする処理は当コントローラには無い。別機能が参照する税率はキャッシュ・クエリ条件の実装次第である。

API/バッチ結果

本機能ではAPI呼び出し・バッチ実行を扱わない。
