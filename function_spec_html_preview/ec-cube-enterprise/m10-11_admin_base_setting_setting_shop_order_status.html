店舗設定 — 受注対応状況設定

管理画面の「店舗設定」から辿れる「受注対応状況設定」であり、画面のサブタイトルは日本語ロケールでは翻訳キー admin.setting.basic_info により「基本情報設定」となる（口語の「店舗設定の基本設定」と混同しうるが、表示文言はこのキーに従う）。mtb_order_status と同一キーで紐付くマスタの表示名・色・受注管理画面でのステータス別件数表示の有無をまとめて編集して保存する。

概要

管理者が、mtb_order_status と同一キーで紐付くマイページ向け名称・受注管理向け見た目の色を画面から更新し、display_order_count により受注一覧の検索エリアでのステータス別件数表示のオンオフを切り替える。行の追加削除や並び順の変更はこの画面では行わず、一覧に並ぶステータスの集合は事前に用意されたマスタ行に固定される。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。既存実装のふるまい、参照するデータ、判定境界、副作用を確認し、仕様の確からしさを把握することを目的とする。

カスタマイズ区分は標準であり、挙動・DB関連ともにec-cube-enterpriseの実装を正典とする。DB関連の記述（テーブル名・列名・型・制約、保存先・扱い、副作用のDB更新）もec-cube-enterpriseを正とする。

対象はブラウザ経由の管理画面であり、REST API 経由での同旨の編集やマスタデータの新規インポートは別機能とする。

本書では Symfony の route 名、URL パス、Controller 構成は扱わない。

本書で扱うこと

  • 受注対応状況設定画面で表示される行の並び順と入力項目ごとの入力種別・初期表示の決まり方
  • 送信成功時およびバリデーション失敗時の画面状態とフラッシュメッセージ
  • 送信内容がmtb_order_status、mtb_customer_order_status、mtb_order_status_colorのどの列に反映されるか
  • テナント系の管理権限で本画面が利用できない理由（権限拒否の仕組みと初期データ上の対応）
  • 受注一覧のステータス件数表示機能との論理的つながりの入口（件数算出ロジックの詳細は別機能）

本書で扱わないこと

以下は本書では仕様確定せず、実装または別機能の設計を正とする。

  • 認証済みセッションの確立過程、ログアウト、二段階認証、Remember Me
  • mtb_order_status に行そのものが存在しない初期構築、マスタデータインポート、マスタデータ管理画面からの変更
  • 受注一覧・ホームでの件数算出SQL、タイミング、display_order_countが偽のときのUI詳細は受注一覧・関連FormTypeの実装を正とする
  • Doctrineのセカンドレベルキャッシュの無効化タイミングやマルチテナント環境での接続振り替え詳細

リニューアル移行時の扱い

本機能はカスタマイズ区分が標準であり、ec-cube-enterpriseの標準実装を正典とする。永続化先は mtb_order_status、mtb_customer_order_status、mtb_order_status_color であり、本書のDBカラム節・入力項目の保存先・副作用はこのスキーマに一致する。並び順キーは3テーブルとも sort_no であり、件数表示は mtb_order_status.display_order_count（真偽型）である。マスタ系3テーブルの共通列（id／name／sort_no）は共通の基底定義に従う。

現行システム側の同等機能との列名差は本書では扱わない（標準機能として移行先を正典とするため）。移行先スキーマで確認できた列のみを記述し、未確認の列は推測でスキーマ化しない。

処理フロー

画面表示（GET）

  1. 利用者が受注対応状況設定画面にGETで到達する。
  2. システムはOrderStatusをsort_no昇順で列挙する。
  3. CollectionTypeで各OrderStatusを1行分の子フォームに割り当て、OrderStatusSettingTypeのPOST_SET_DATAで、同じIDのOrderStatusColorとCustomerOrderStatusが存在すれば色・名称(マイページ)の初期表示値をそこから埋める。名称(受注管理)はOrderStatus自身のnameから来る。
  4. テンプレートでテーブル行を描画する。ID列は子フォームのデータ実体からidを表示し、編集不可とする。

登録送信（POST・成功）

  1. 利用者が登録を押下し、同一画面向けにPOSTする。
  2. CSRFトークンが無効なら管理共通の扱いに従い拒否される。
  3. 各子フォームについてバリデーションが通ると、紐付くOrderStatusに名称(受注管理)と件数表示がマッピングされ、永続化対象として積まれる。
  4. 同じIDのCustomerOrderStatusが存在すれば名称(マイページ)を上書きし永続化指示する。存在しなければ名称(マイページ)は保存されない。
  5. 同じIDのOrderStatusColorが存在すれば色文字列を上書きし永続化指示する。存在しなければ色は保存されない。
  6. 一度flushし、addSuccessでキーadmin.common.save_completeを管理フラッシュドメインに積む（日本語ロケールの確認値は「保存しました」）。続けて同一画面の一覧表示へGETするリダイレクト応答を返す。
  7. リダイレクト後のGETで、更新後のマスタを読み直して再表示する。

登録送信（POST・バリデーション失敗）

  1. 手順は成功時と同様にPOSTを受け取るところまで進む。
  2. いずれかの子フィールドがNotBlankまたはLength最大超過に該当すると、フォーム全体は無効となりflushは行われない。
  3. HTTP 200で同一画面を再描画し、該当フィールド下にエラーを表示する。PHPUnitの実装確認では日本語ロケールで未入力に対し「入力されていません。」が画面テキストに含まれる。

セッション

本機能では、画面のためだけに検索条件セッションなど新たなサーバ状態を増やさない。

セッションへ保存しない情報

フラッシュバッグの用途以外に、入力下書きだけをサーバ側に保持する処理はしない。

Cookie

この画面が独自にCookieを増やすことはない。セッション維持は管理画面全体の認証に従う。

排他制御・トランザクション

本機能はエンティティマネージャの既定トランザクション境界でflushするだけであり、行バージョン列や楽観ロックを持たない。同時保存は最後に成功したflushが残る。
