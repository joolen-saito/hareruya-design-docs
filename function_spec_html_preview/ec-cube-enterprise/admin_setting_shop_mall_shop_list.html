admin_setting_shop_mall_shop_list（管理画面_店舗設定_基本情報_店舗一覧）

管理画面の「基本情報」配下にある店舗一覧。モール側が保持する複数テナント店舗を検索・ページネーションして表示し、店舗詳細へ進む。また選択した複数店舗に対して論理削除リクエストを送ることができる。

概要

本機能はモール側管理者が、dtb_base_infoにおいてモールルート以外のテナント店舗レコードを検索して一覧するための機能である。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。 既存実装のふるまい、参照するデータ、判定境界、副作用、拡張による差し替え可能性を確認し、仕様の確からしさを把握することを目的とする。

対象はブラウザ経由の管理画面であり、画面上の親メニューは「設定」、小見出しは「基本情報」、一覧画面のページタイトルはロケールにより「店舗一覧」と表示される構成である。

本書ではSymfonyのroute名、URLパス、Controllerクラス名は扱わない。

本書で扱うこと

  • 一覧の初回表示、検索POST、ページ送りGET、resume付きGETにおける検索条件セッションとページ番号の更新・復元
  • 一覧に載るデータのクエリ基底（モールルートID除外）および検索条件（入力が桁のみのときはID等価、常に店舗名LIKE側も付くOR結合。このうち桁パターンに合う空入力ではID側パラメタも束ねられる）
  • DoctrineのQueryCustomizationフックおよび画面組み立て前後に発火する拡張イベントの呼び出しタイミング
  • 画面上の一覧列・検索欄・一括削除モーダル・表示件数プルダウンのふるまい
  • 単一店舗の論理削除API（選択行からのAjax DELETE）および成功後のフラッシュ・キャッシュクリア・JSON応答の形

本書で扱わないこと

以下は本書では仕様確定せず、実装または別機能の設計を正とする。

  • 管理画面共通のログイン認証、権限チェック、アクセス可否の網羅的な状態表（自動テストではモール側メンバーで当画面への到達を確認しているが、環境側の許可セットは共通設計が正となる）
  • 店舗新規作成・詳細編集画面の入力項目および永続化手順全体
  • テナント初期化処理、店舗向けディレクトリ生成、S3アップロード等のインフラ的副作用詳細（詳細機能の実装側を正とする）
  • メール送信、外部API連携の非同期キュー、knpページャ内部のクエリログ

用語

用語説明
店舗一覧画面「基本情報」配下メニューを開いたときに表示される、テナント店舗の検索結果テーブルを持つページ。ページタイトルの翻訳キーは現行実装においてモール側の「店舗一覧」文言に相当する。
モールルート構成値`eccube_root_base_info_id`で参照されるモール共通のBaseInfo。一覧のクエリ基底から明示的に除外される。
テナント店舗モールルート以外の`dtb_base_info`行。一覧はこの集合を起点とする。
検索条件セッション検索入力の表示復元およびページネーション状態を保持するセッション上の名前空間。キー文字列は実装でのみ固定されており仕様証明には用いず、機能が保存・読み込みする状態の概要としてのみ本書で指す。
論理削除DELETE APIが行う処理のうち、`tenant_status`を「削除」を表すマスタ状態に書き換えてフラッシュすること。一覧クエリ側で自動的に削除済みレコードが除外される保証については本章「データ整合性」を正とする。

利用者視点の入口

入口URLエンドポイント期待されるふるまい
メニューから店舗一覧を開く`GET /%eccube_admin_route%/mall/tenant`検索欄にはフォーム項目「店舗名」相当の入力欄が並ぶ。ラベル翻訳は店舗名だが入力はリポジトリ上「IDまたは店舗名の類似」を条件に読み替える実装となる。一覧はテーブルまたは件数ゼロ用の説明文言が表示される。
「検索」ボタンを押下してPOST送信する`POST /%eccube_admin_route%/mall/tenant`CSRFおよびフォーム項目を含んだ検索送信が処理される。有効なときは検索条件とページ番号1が検索条件セッションに保存される。無効なときはエラー状態でフォームのみ再表示される。
ページリンクや「表示件数」プルダウンで一覧をページ送りする`GET /%eccube_admin_route%/mall/tenant/page/{page_no}`（`{page_no}` はページ番号）GETによりページ番号と表示件数を更新しつつ、`resume`フラグまたはパスパラメタに応じてセッション上の検索条件を復元して再クエリする。
行のチェックボックスを操作する—（同一一覧ページ上）「一括操作」のエリアが表示または非表示に切り替わる。表示ロジックは他画面共通の補助関数に依存する。
「削除」を実行するモーダルで確定して一括処理する`DELETE /%eccube_admin_route%/mall/tenant/{識別子}/delete`（ルートパラメタ名・型は実装を正とする。Ajax）選択された各行に対応する削除URLへDELETEのAjaxリクエストを並列送信する。完了後リロードで画面を再度読み込む。
店舗名リンクを押下する`GET /%eccube_admin_route%/mall/tenant/detail/{id}`店舗詳細編集へ遷移する。当一覧が書き換える検索条件セッションの内容は、この遷移直前には更新しない。
未認証ユーザー`GET /%eccube_admin_route%/mall/tenant`（到達前）管理画面の入口共通の処理により当画面まで到達できない。

フロント挙動

観点内容
表示要素画面上部に検索フォーム。検索後にのみ「検索結果：N件」が表示される。結果テーブルは列ごとに店舗ID、店舗名（詳細へのリンク）、会社名、公開フラグ（公開／非公開の翻訳表示）、開店フラグ（開店／閉店の翻訳表示）が並ぶ。先頭列に行チェックボックス。テーブルの右側に広い空列がテンプレート上残っている。
JS挙動表示件数プルダウン変更でクエリパラメタを付けた同一一覧へブラウザ遷移する。一括削除はモーダル内進捗表示とAjax並列送信、失敗や`success:false`応答ごとにエラーリストへ追記する。チェック状態に応じ一括ツールバー表示。商品規格読み込みモーダル向けのテンプレート断片があるがテナント行には該当ボタンを置いておらず本画面上では機能しない残骸である。また未選択削除への`alert`が残っている。
CSS・レイアウト管理画面共通のカード縦並びおよびテーブルの見た目。
モーダル・ポップアップ論理削除確認モーダル、進捗バー。閉鎖または完了ボタンでリロードが走る経路がある。
入力項目検索用テキスト1項目。ラベルは翻訳上「店舗名」。入力必須ではない。空や未入力に近い値はクエリ側の解釈に委ねられる。詳細検索の折りたたみ枠は共通テンプレートを読み込むが、検索入力が実質一項目のときは一覧表示側に追記される条件は現状ほぼ出ない。

処理フロー

一覧画面の検索フォーム初期化および拡張イベント

  1. リクエストを受ける。
  2. SearchTenantType相当の検索フォームビルダを用意する。
  3. 初期化用の拡張イベントを発火し、プラグイン等が項目追加や束縛変更できるようにしてからフォームオブジェクトを得る。
  4. 検索処理の詳細へ進む。

表示件数のセッション初期値

  1. セッションに保存された表示件数を読む。無ければ構成で定めるデフォルト件数。
  2. リクエストクエリでpage_countが送られ、その値がページ最大件数マスタにある名称と一致するときのみ、セッション上の表示件数をその値へ上書き保存する。一致しない値は無視される。
  3. 以降のページネーションおよびテンプレートの選択状態は、この確定済みの件数で行う。

POST検索（フォーム送信が有効だった場合）

  1. フォームにリクエストを束縛して検証する。
  2. 有効なら検索結果のページ番号を1にセットし、FormUtil::getViewDataで検索入力の復元用文字列セットを検索条件セッションへ保存する。ページ番号1も検索条件セッションへ保存する。
  3. 無効なら一覧部を空応答相当で返す専用配列構成にしてレンダリングし、フラグによりエラー状態のまま視覚要件に合わせた再表示となる。
  4. 有効ならテナント用QueryBuilderへ検索データを適用したうえページネーションを組み立てる。

GETでページパラメタまたはresumeが明示される場合の再表示

  1. page_noまたはresumeのいずれかが入力に含まれるとみなす条件で分岐するとき、セッション上の検索入力を復元してフォームへ再セットする。またパス側のpage_noが優先されセッション上の一覧ページ番号も更新される。
  2. ページネーションを組み立てる。

GETで上記以外の初回到達

  1. ページ番号を1として扱う。
  2. フォーム既定値由来の復元セットを検索条件セッションへ保存して同期する。すなわち前回検索状態は初期表示で上書きリセットされる。
  3. ページネーションを組み立てる。

クエリ適用および検索イベント

  1. テナント集合のQueryBuilderを得る。この時点ですでにモールルートは除外済みという前提のビルダを受け取る。
  2. 検索データに基づき、(A)桁のみからなる長さ制限内の入力はID等価条件のパラメタを束ねる(整数として解釈できない桁あふれは無効としてID側パラメタはnull扱い)、(B)店舗名の部分一致。この二系統を論理ORで付与する。また%と_文字はLIKEにおけるワイルドカードとして機能しないようにエスケープする。入力が桁パターンに合う空文字列のときでもID側パラメタが束ねられる。さらにQueryCustomizationで追加改変がある。
  3. 検索直後にもう一つの拡張イベントが発火し、プラグイン等がクエリおよび検索データを読み書きできる。

ページネーションとテンプレート返却

  1. KNPページネータにQueryBuilderまたは同等のページング対象、ページ番号、表示件数を渡してページ一覧情報を構築する。
  2. 検索フォームのビュー、ページ一覧、ページ最大選択肢、現在のページ件数などをビューレイヤへ渡してHTMLを応答する。

一覧から複数選択して論理削除を確定するとき

  1. 利用者が行チェックおよびモーダル確定により削除開始操作をすると、クライアントは各行の削除URLへDELETEメソッドのAjax送信を並列に行う。
  2. サーバーは各行ごとに対応するテナントBaseInfoを特定し、tenant_statusを「削除」状態のマスタIDへ更新してDBへフラッシュする。
  3. Doctrineキャッシュをクリアするユーティリティを実行する。
  4. フラッシュへ成功文言を載せつつ、success:trueおよび翻訳済み文言をJSONで返す。クライアントは完了後ページ全体を強制リロードしてサーバー側フラッシュおよび更新後リストを読み直す。

集計条件

指標集計の要点
画面上部の総件数KNPページネーションの`totalItemCount`。クエリ適用済みテナント行の件数。
テーブルの行集合モールルートを除いた`dtb_base_info`行であり、クエリ側は初期時点ですべて読み込んですべて表示する。テナントステータスによる除外はクエリ標準組みの条件には含まれない。

一覧クエリ処理時の判定順序（検索条件の適用）

順序判定結果
1基底QueryBuilder生成モールルートIDなど価ではない条件だけを適用済みとして受け取る。
2`id`入力文字列が10桁までの数字のみであるか真なら数値へ解釈を試み、DBMSが32bit整数の範囲外なら検索でのIDパラメタは使わずnull扱いに寄せる。
3上記IDパラメタと店舗名LIKE用パターン`OR`で両方クエリへ束ねる。
4QueryCustomization適用後最終クエリ。

画面上の検索入力ラベルは翻訳上「店舗名」のみだが、この判定は利用者入力を名前ではなく両兼用フィールドとして解釈する。利用者視点でのラベルと実装側の入力意味は一致しない。

項目名必須／任意最大長初期値保存先・扱い

エッジケース

ケース扱い
検索入力が桁のみであり空文字にもマッチするとき店舗ID等価条件が張られる一方で名前LIKE側もセットされる。実データ集合と合成されて論理フィルタとなる。SQL方言および型変換規則の詳細はDBに委ねる。
検索入力に英字を含む桁のみパターンに合致しないためID側パラメタはnull。名前LIKEのみ。
論理削除後の再表示標準の一覧クエリは`tenant_status`で除外しない。削除後も行は一覧に載る。
検索結果ゼロ「検索結果はありません」系の共通メッセージと案内。一括削除UIは構築されない。
Ajax DELETEで一部失敗並列処理の結果配列側で個別文言をリスト表示し、処理完了文言へ至る。全体リロードで再同期。

データ整合性

観点内容
一覧・詳細一覧はクエリ適用済み読み込みであり、詳細画面の入力途中との同時編集競合検知まではしない。
論理削除ステータスのみ更新。物理削除しない。標準の一覧クエリでは除外しないので、削除した行も一覧結果に含まれる。
QueryCustomizationとイベント実行順は固定で拡張は後段でクエリ改変できる。プラグイン導入により一覧集合が変わる。
