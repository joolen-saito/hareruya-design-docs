m10-12_admin_base_setting_setting_shop_calendar（管理画面_店舗設定_定休日カレンダー設定）

管理画面で定休日の「タイトル」と「日付」を登録・一覧表示・行単位編集・削除する機能。一覧は店舗（BaseInfo）に紐付くマスタのみを読み込み、入力した日付はフロントのカレンダーブロックなど別機能のクエリにより参照される。

概要

本機能は運用者が営業日カレンダー表示に載せたい休業日や記念日相当のイベントを名前付きで日単位保存し、一覧で維持するための管理画面機能である。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。 既存実装のふるまい、参照するデータ、判定境界、副作用、拡張による差し替え可能性を確認し、仕様の確からしさを把握することを目的とする。

カスタマイズ区分は標準であり、挙動・DB関連ともにec-cube-enterpriseの実装を正典とする。DB関連の記述（テーブル名・列名・型・制約、保存先・扱い、副作用のDB更新）もec-cube-enterpriseを正とする。

対象はブラウザ経由の管理画面の定休日カレンダー設定画面である。 同一メニューグループ内の「基本設定」そのほか項目の入力保存、フロントのカレンダーブロックレイアウトや土日のみテンプレ側で強調する表示は別機能として切り離す。

本書ではSymfonyのroute名、URLパス、処理クラス構成は扱わない。 代わりに、設定画面を開く、新規追加を送る、行を編集して確定する、削除するなど利用者視点の入口ごとに期待されるふるまいを記載する。

本書で扱うこと

  • 設定画面での新規作成、一覧表示順、行単位インライン編集、削除要求の処理境界
  • 「タイトル」「日付」入力とフレームワークバリデーション、同日・同一店舗内の一意性チェック（フォーム実装による差）
  • 永続先テーブルの列単位での意味と、画面上のフラッシュメッセージ種別
  • 保存成功後の遷移先がホーム画面となること、その時点でのフラッシュ
  • CSRF が無効な削除要求へのふるまい

本書で扱わないこと

以下は本書では仕様確定せず、実装または別機能の設計を正とする。

  • 管理画面ログイン・二段階認証・ロール一覧とURL許可の対応表
  • 「基本設定」とのナビ項目の並びや可視条件のソース外の運用規定
  • フロントのカレンダーブロック表示、テンプレ上の「土曜日」と「日曜日」を追加で休業日表示に見せるコードコメントによる装飾
  • サイト内ブロック経由での定休日取得クエリが店舗を絞らない場合のPostgreSQLポリシーと実データの完全一致
  • create_date と update_date を画面上の処理がどの共通機構またはDB既定で埋めるかのORMスキーマ以下の細部全体
  • 削除成功後に返却される配列のみの応答が、ブラウザにどう表示されるかのHTTP応答タイプ詳細のフレームワーク内部仕様

リニューアル移行時の扱い

本機能はカスタマイズ区分が標準であり、ec-cube-enterpriseの標準実装を正典とする。永続化先は dtb_calendar であり、本書のDBカラム節・入力項目の保存先・副作用はこのスキーマに一致する。主キーは id、タイトルは title、休業日日時は holiday、作成更新は create_date／update_date である。店舗（テナント）への紐付け列 base_info_id は、テナント共通トレイト（BaseInfo への外部キー、NULL不可）により付与され、一覧の絞り込みと保存時の店舗セットに用いる。

現行システム側の同等機能との列名差は本書では扱わない（標準機能として移行先を正典とするため）。移行先スキーマで確認できた列のみを記述し、未確認の列は推測でスキーマ化しない。

モーダル・ポップアップ削除の確認モーダル。削除実行リンクには確認ダイアログ抑止フラグが付いており、アンカーを押した瞬間にはブラウザの confirm は出ない。モーダルは行ごとに個別DOMを持つ。

処理フロー

画面の初回表示

  1. 利用者が定休日カレンダー設定画面へ遷移する。
  2. システムは引数または既定の規則に従って1件の店舗エンティティを取得する。この店舗IDを条件に一覧をクエリする。
  3. 新規登録に用いる空の状態のエンティティにつきフォームビルダを生成し、そのビューと、既存各行につき別個の編集フォームビューをテンプレに渡す。
  4. 画面上部の新規用フォームはCSRFフィールドのみ先行埋め込み、一覧の各行にも各行専用のCSRFおよび隠しパラメータを埋め込む。

新規作成の送信

  1. 画面上部フォームへタイトルと日付を入力し送信する。送信先は新規エイリアスのある同一ハンドラだがクエリ側の名前で区別する設計とは独立に、処理は共通本文で受ける。
  2. インライン編集モード指定が付いていない通常モードとしてフォームが束ねられる。
  3. 送信済みかつ検証済みであるとき、baseInfo へ画面上で解決した店舗をセットし、persist と flush を行う。
  4. 「保存しました」相当のフラッシュを管理向け名前空間に追加し、管理者向けホームへリダイレクトする。このリダイレクト経路にはソース内TODOコメントで一時処置である旨がある。

既存行のインライン更新

  1. 利用者が鉛筆を押して編集状態にし、タイトルや日付を変え、「決定」でPOSTする。このPOSTには編集対象を示すユニークIDとインライン用モード値が埋め込まれる。
  2. 共通ハンドラはモードにより上部の空白用フォームの束ね処理を省略する。
  3. 一覧の各行について、送信メソッドがPOSTであり、モード値が編集モードであり、リクエスト中の対象カレンダー行IDが当該行のIDと文字列一致するときのみ、その行のフォームへリクエストを束ねる。
  4. 当該フォームのみが有効だった場合、エンティティへ店舗を再セットして persist と flush し、成功フラッシュ後に管理者向けホームへリダイレクトする。
  5. 送信が無い行のフォームは束ねず、画面上の入力欄だけが生成される。バリデーションに失敗した行にはエラー個数が数えられ、テンプレに渡されるエラー有無フラグにより当該行は編集表示のまま残る。
  6. 編集フォーム生成時、BaseInfo オプションをフォームタイプへ渡していない。同日チェック処理はフォームオプション内の店舗参照値に依存するため、編集側のクエリでの店舗条件の解釈はORMの規則に従う（新規側では店舗を明示的にオプション渡ししている）。

削除

  1. 利用者がモーダルから削除用アンカーを押す。共通スクリプトがCSRFとメソッド上書きを含む隠しフォームを作りPOSTする。
  2. ハンドラはCSRF検証に通ったあと、リポジトリの delete を呼ぶ。リポジトリ実装は remove のあと即座に flush する。
  3. 削除完了フラッシュを積み、真偽マップのみをPHPの配列として返す。テンプレ指定はなく、この配列のみをレスポンスに載せた場合のブラウザ表示はフレームワークの応答組み立てに依存する。ソース上ホーム転送などを書いておらず、画面上の自動遷移や白画面表示はソース単体からは断定しない。

集計条件

本機能では件数や金額の集計算出を持たない。一覧は「対象店舗に紐付く全行」をID降順で列挙するだけである。

保存処理における検証順序

順序判定結果
1フレームワークの項目必須と長さおよび日付範囲不一致なら送信されたフォームだけが無効扱いとなり一覧にエラー状態が視覚的に残る。
2日付の下限が内部で許容される最小日以降であるか個別チェック（同一キーをPOST_SUBMITで再検証）不一致なら同日重複判定へ進まず打ち切る。
3同一 holiday 値および同一店舗条件でほかに行が残るか数える一致するほか行があれば「同日の定休日が既に存在しているため、設定できません。」文言を日付入力に載せて無効完了とする。更新時は自IDをカウントから除外する。

画面上はHTTPレベルの失敗とCSRF不正を利用者ごとには区別せず、アクセスできない状態として扱う。

業務ルール・計算

項目内容
一覧のソースアクティブな店舗解決結果に対し baseInfo 相等で絞る。絞らないクエリ関数もリポジトリにはあるが、この画面ハンドラの一覧取得だけは絞りを付ける。
日表示画面上の保存済み一覧はフィルタ date_day により日粒度で表示値を決める（内部は日時）。
同一日の禁止POST_SUBMITでの重複カウントが1より大きい場合にエラー項目を増やす（新規と更新共通のロジック骨格だが編集側は店舗オプション未設定）。
成功後遷移新規保存およびインライン更新の成功のみで管理者向けホームへ転送される。画面上のソースTODOは将来の恒久遷移先変更の見込み記述。

入力項目

項目名必須／任意最大長初期値保存先・扱い
タイトルフォーム定義では必須共通設定項 eccube_stext_len の値（環境既定の確認値として255）と一致させる検証がある新規行フォームのみ空文字相当。一覧行フォームでは既存の文字列から開始dtb_calendar.title に保存される。長さ超過は無効。未入力および空白のみはフレームワークの必須検証により無効。
日付必須日単位入力同上dtb_calendar.holiday に日時値として保存。0003年以前は範囲エラー。また同一店舗・同一値の競合があると専用メッセージで無効（新規分岐では店舗をオプションで渡している）。

エッジケース

ケース扱い
インラインPOSTが特定行だけにヒットしない全行とも更新せず一覧を再ビルドするだけ。フラッシュおよびホーム転送も起きない。
CSRF が欠けるまたは不正な削除アクセス拒否例外方針。
論理削除や複数法人のクロス混入Doctrineのグローバル規則とDBポリシーに依存し、ここでは当画面のクエリだけを根拠に書かない。

データ整合性

観点内容
画面上の一覧と永続データGET表示のたび一覧を取り直す。保存成功後はホームへ飛ぶため当画面での即時一覧再クエリでは見えず、フラッシュのみが残る。
店舗切替画面上でどの店舗を対象とするかはハンドラの引数解決および既定の店舗取得規則に依存する。複数モール構成では実データ集合と画面上の単一選択店舗との間に読み替えがある場合がある。この画面の一覧クエリだけが保証するのは、そのとき解決される1店舗に紐付く行だけである。
フロントブロック側サイト側ブロック用のクエリ関数は歴史的に店舗条件をクエリへ含めず、画面上の一覧とサイト表示のセットが一致しない可能性がある。サイト表示のデータ境界はサイト側機能を正とする。

API/バッチ結果

本機能では管理目的のHTTPS以外の公開APIおよび夜間バッチを持たない。削除以外の処理は標準ブラウザ遷移とフォーム送信である。

入出力

種類内容
入力テキスト2種（上部新規セットと各行セットが別々のフォーム名空間になる）、複数種の隠しパラメータ（ID、編集モード、CSRF、メソッド上書き）、日付入力。

DB操作

永続化の正は ec-cube-enterprise（テーブル名・操作は ec-cube-enterprise を正典）。当ドメインは承認ワークフローを介さず persist/flush で直接確定する（承認ワークフローは在庫機能固有）。

操作種別対象テーブル契機・条件
登録/更新dtb_calendar当機能が行う登録・更新で対象テーブルを直接保存する（不要な削除は含まない）。確定は persist/flush による即時反映。DB=ec-cube-enterprise を正典とする。

未ログインまたは管理URL範囲外アクセス自体が拒否またはログインへ誘導され、機能に未到達受理されない
CSRFのみ欠落または不正（該当操作が送信・削除のみ）削除は拒否。フォーム側は共通エラーとなる

詳細対応はロールマトリクス機能の別設計を正とする。

  • Remember Meトークンの原値

セッション

テナント自動補填の共通Doctrineリスナは定休日用エンティティを明示的に除外しており、この画面での persist がセッション上の別店舗へすり替える経路には乗せない設計になっている。本機能におけるセッションでの直接キー読み書きは行わない。

セッションへ保存しない情報

定休日行のドラフト状態はサーバ側セッションに保持せず、未送信の入力はレスポンス再描画でのみ復元される。

Cookie

ブラウザのセッションCookieはフレームワークとインフラの範疇であり、業務入力として読み書きしない。本機能ではCookieを業務状態として変更しない。

排他制御・トランザクション

当画面での保存は単一エンティティに対する flush が中心であり、楽観的ロック用のバージョン列やロック句は明示しない。 同一行への同時POSTの順序競合については、アプリケーション側で順序を保証する記述がなく、データベースの最終書き込み勝ちに依存する。
