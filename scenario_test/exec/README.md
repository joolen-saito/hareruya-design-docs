# シナリオテスト 具体化TSV（結合テストと同形式）

`scenario_test/test_items/all_scenario_test_items.tsv`（11列・1,067行）を、結合テストの具体化TSV
`integration_test/e2e/exec/tsv/m03-*_concretized.tsv`（13列）と同じ列構成・整形規則へ機械変換したもの。
同ディレクトリのF04系4本は `使用シード`・`自動検証` を持たない11列の旧仕様なので参照していない。

揃えたのは列名・列順・セル1行化・期待結果の文末規則。**括弧最小化だけは適用しない**
（結合テスト側は `emit_concretized_tsv.py` の `strip_parens` で括弧書きを除去するが、
シナリオ層では `経路R01（正常代表）`・`DP-N001（正常系 代表）` のように括弧が原典の識別情報を
担っており、除去すると情報が落ちるため）。

- 生成: `python3 scenario_test/tools/emit_scenario_concretized_tsv.py`
- 出力: `scenario_test/exec/tsv/sti-<業務コード>_concretized.tsv`（業務別10本）
- `実行方法` 列を除き、元TSVからの決定的な導出のみで値の新規創作は行っていない。
  `実行方法` だけはプロジェクト事実（シナリオ層に自動実行ハーネスが無い）に基づく（後述）。

## 列構成（14列）

先頭13列は結合テスト具体化TSVと同一。14列目のみシナリオ層固有。

| # | 列 | 結合テストとの差分 |
|---:|---|---|
| 1-6 | 機能名 / テストID / I/FID / テスト観点 / 優先度 / テスト項目名 | 元TSVの値を転記（I/FIDの `-` は `—` に統一） |
| 7 | 前提条件 | 12キーの構造化ブロブを1行に再構成 |
| 8 | 使用シード | **新設**。元は前提条件に内包されていた実値を分離 |
| 9 | 入力データ/リクエスト内容 | 1行化。`分岐ID` は種別と別フィールドとして分離（分岐/異常行34件） |
| 10 | 操作手順/実行方法 | セル内改行を除去し `担当者: X／1. … 2. …` に平坦化 |
| 11 | 期待結果／レスポンス | 文末を「〜こと」で統一 |
| 12 | 自動検証（内部: session/DB/URL） | **新設**。全行 `—`（下記） |
| 13 | 実行方法 | **新設**。プロジェクト事実から全行「手動」の一値（下記） |
| 14 | 確認対象 | シナリオ層固有。結合テスト形式に受け皿が無いため末尾に**逐語**保持（重複要素も出現回数どおり残す） |

## 変換規則

- **前提条件**: 元の12キーのうち、**他列から完全に復元できるものだけ**を落として再構成する。
  - 残す: 元シナリオID / 経路ID・経路種別 / 主アクター / 業務経路条件 /
    前提差分（下記のとおり `追加前提` として出す行がある） / 最終業務状態 / 関連システム
  - 落とす: 業務（機能名の ` — ` 前）・元シナリオの表題（機能名の ` — ` 後）・
    データパターンID/種別（入力データ列へ）・シードデータ（使用シード列へ）。
  - 業務経路条件は全行保持する。前提差分がその後続分になっている1,033行では、全文再掲を避けて
    追加分のみを `追加前提:` として出す（ラベルで形を区別するので逆変換で再結合できる）。
    前方一致しない34行は `前提差分:` として全文を残す。
  - 復元可能性は「主張」ではなくゲートG8が毎回検証する。出力14列から入力11列を逆変換し、
    全1,067行で入力と完全一致することを確認する（許す差はセル内の空白の畳み込みのみ）。
- **使用シード**: 前提条件の「シードデータ:」以降を逐語で転記。結合テスト側の `SEED-*` のような
  ID体系はシナリオ層に存在しないため、実値（`担当者アカウント=st-user-…` 等）をそのまま置く。
- **操作手順**: 先頭の「担当者: X」は**ステップ実施者**で `主アクター`（シナリオ全体の主担当）とは
  別概念のため保持する（909のステップ行のうち168行で両者は異なる）。
  従属行「対象: …」は直前の手順へ併合する。手順の番号と本文は保持。
- **自動検証（内部）**: シナリオ層は業務要件の充足を画面・現物で観測する層で、元データに
  内部状態（session/DB/URL）の観測仕様が存在しない。捏造を避けるため全行 `—` とする。
- **実行方法**: **この列だけは元TSVからの導出ではない**。列の意味は「テストの実行方法」で、
  シナリオ層に自動実行ハーネスが存在しないという事実から全行「手動」とする。
  業務そのものの実行形態ではない点に注意（`※夜間自動実行` と明記された業務ステップが8行あるが、
  テストは人が起動・観測するため「手動」）。

  **確認手段の要約（補記）は一切行わない。** 確認対象から行全体のラベルを導く試みは3度とも
  破綻した。この列に書けるのはプロジェクト事実だけで、確認手段の一次情報は14列目の
  `確認対象` に原文で残る。

  | 試した補記 | 破綻した理由 |
  |---|---|
  | 既定「EC-CUBE画面確認」 | 関連システムにEC-CUBEが無い行にも付き、原典に無い確認先の捏造になった（`STI-DECK-004-003`） |
  | 「EC-CUBE外」 | 更新が無いことと**EC-CUBEを操作しないことは別**。カート画面を操作しつつ更新は発生しない行に誤って付いた（`STI-TSUHAN-EC-001-004`） |
  | 「EC-CUBE更新なし」 | 操作手順が「EC-CUBEに価格変更を反映させる」と明記する行で、同じ行の別の列と矛盾した（`STI-PRICE-002-004` 等3行） |

  根本原因は、確認対象の1要素が `キャンセル状態、在庫戻し、通知結果、操作履歴` のように
  複数の観測先を並記していること。そこから行全体を要約すると、どれが主たる手段かという
  原典に無い判断が混入し、必ず他列と衝突する。

## 生成時のハードゲート

`emit_scenario_concretized_tsv.py` は以下を満たさない場合エラー終了する。

| ゲート | 内容 |
|---|---|
| G1 | 入力TSVのヘッダが想定11列と一致 |
| G2 | `前提条件` の12キーのマーカーが各1回だけ出現し、分解結果を再直列化すると入力と完全一致すること（値中に偽のキー区切りが紛れれば失敗） |
| G3 | 前提条件から落とすキーが、同一出力行の他列から復元できること。業務は機能名と、DPID・種別は入力データ列の**分解値と完全一致**で照合する（部分一致だと `代替系` が `代替系 / 分岐ID=A1` を通してしまう） |
| G4 | 出力パスが業務ごとに一意（衝突すると後勝ちで片方が消えるため） |
| G5 | **書き出したファイルを読み直して**、業務ごとに行の並びまで含めメモリ上の生成結果と完全一致すること。各行が正しい業務ファイルに属すること。加えてID一意性・14列・改行/タブ/CR残存0・想定外の残存TSV無しを照合 |
| G6 | `入力データ` の分解結果を再直列化して入力と完全一致し、各フィールドが1回だけ出現すること |
| G7 | 分岐IDとデータパターンIDの整合。`DP-A`/`DP-E` は必ず対応する分岐IDを持ち（`A2`↔`DP-A002` と番号まで一致・実データ A22/E12）、`DP-N` は持たない（1,033行） |
| G8 | **出力14列から入力11列を逆変換**し、全1,067行で入力と完全一致すること（許す差はセル内の空白の畳み込みのみ）。前提条件から落としたキーの復元可能性を、主張ではなく毎回の実測で担保する |
| G9 | 元TSVに対応の無い2列の検査。`自動検証` が全行 `—`、`実行方法` が全行「手動」であること（G8は入力由来列しか見ないため、この2列はここでしか守れない） |
| G10 | テストIDの業務記号が機能名の業務と対応すること。出力ファイル名は業務名→コードの固定マップで決める（テストIDから後勝ちで決めると、1行のID改変でファイル全体を誤命名できる） |
| G11 | 業務の集合と業務別件数が既知の規模（計1,067行・10業務）と一致すること。入力と出力から**同時に**1行が失われる静かな欠落は、入力自身を基準にした照合では検出できない。正本を意図的に更新したときは定数 `EXPECTED_TOTAL` / `EXPECTED_BY_BIZ` を直す |

G5はメモリ上の集計ではなくディスクの実体を検証する。これが無いと、パス衝突などで
ファイルが失われても集計だけは一致してしまい、取りこぼしを検出できない。

## 一見矛盾して見えるが正しい2点（是正しないこと）

読み手が「不整合」と誤認して直しにいかないよう、根拠を明記しておく。

- **「異常系 #2」の行に `DP-N001（正常系 代表）` が付く**（1,067行中1,033行がDP-N001）。
  `DP-N*` は「その経路を通すための代表データ」を指し、経路そのものの分類ではない。
  経路の分類は `経路種別`（主要代替568/正常代表430/業務異常69）・`目的`・項目名のprefixが担う。
  生成側 `hareruya-scenario-test-cases/scripts/generate_scenarios.py:1874` の仕様で、
  `validate_scenarios.py:84` が全シナリオに `DP-N*` の存在を必須化している。
- **項目名・操作手順の担当者と `主アクター` が食い違う**（経路全体158行を除く909のステップ行中168行）。
  項目名の担当者は業務フローの**ステップ実施者**、`主アクター`は**シナリオ全体の主担当**で、
  別物である。生成側 `hareruya-scenario-test-items/scripts/generate_test_items.py:815` の
  `actor = row.get("担当者") or s.main_actor` がステップの担当者を優先する。
  複数チームが関わる業務（例: トレードチーム主管の業務で一部ステップをITチーム・店舗チームが実施）で
  差が出るのが正しい姿。
