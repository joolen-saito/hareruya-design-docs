# 仕入れ業務の統合仕入れ（社員）の在庫変更CSV登録と戻し（USH-02）

IPA「高信頼化ソフトウェアのための開発手法ガイドブック」(2010) の表6-9〜6-11と同じ手順で作る（FL表→禁則表→2因子間網羅の組み合わせ）。1行が1回ずつ流すテスト1本で、行の中の水準は条件ごとに1つ（2026-11-09 に scenario_list.md の L3 欄で「／」で並べていた値を分けた）。

## 範囲

- 社員が、規定数以上のインポート依頼済みの仕入れストレージを選び、統合仕入れファイルから在庫変更CSVを作って在庫に入れ、承認を受けて、依頼元へ完了を返し、高額品と戻しまで終える
- 在庫変更CSV登録から承認までの条件違い（在庫変動区分の親区分・店舗・在庫区分・承認／却下・登録者本人は承認できない・100点以上の在庫変動で出る確認モーダル）は UZK-02・UZK-01 で通す。このマトリクスは USH-02 固有の条件違いだけを持つ
- 取り込む時刻は運用の時刻でシステムは制御しないので水準にしない（scenario_list.md の USH-02 の行）。同名ファイルは取り込めない（※4）ので、分割したファイルには別の名前を付ける。取り込めない場合は例外 E1 で差し込む

## まとめた水準

なし（どの水準も処理が違う）。主な根拠：問屋仕入と他店仕入は在庫履歴に残る区分が違い、仕入単価0円と1円以上は総原価に足される額が違い、5000行を超えると複数ファイルに分けて1ファイルごとに承認され、戻し先は金庫・戻し棚・キャビネットで担当が違う。

## 外した因子・水準（2026-11-09 依頼者決定：画面の操作の違い）

業務が回るかを確かめるシナリオテストでは、業務の流れが分かれない画面操作の違い（画面かCSVか・作り方・出力形式・確認表示）は組み合わせ表から外し、結合テストに任せる。

- 因子 D「入庫用ファイルの修正の原因」を外した。理由：修正の原因（カードの状態の不一致／打ち込みミス）は違うが、どちらも取り込む前にファイルで直し、後の流れも結果も同じ。前提として残す代表：修正の原因は問わず、取り込む前にファイルで直したものを取り込む。
- 作り直し後：6行（2026-11-09 以前は8行）。rows=6 pair=100.00% (30/30) triple=54.55% (24/44)
- この節より上の文章（範囲・まとめた水準など）に外した因子・水準の名前が残る場合は、上の決定が優先する。
