# 仕入れ業務：シナリオ一覧（L2）

シナリオ1本は「起点の業務イベントから、業務として完了した状態になるまで」とする。担当者が替わっても切らない（遅番→アルバイト→社員→承認者→依頼元へのメール→戻す人）。日をまたぎ、システムの状態が何かを待つもの（在庫変更CSV登録の承認待ち）は、在庫管理のシナリオ（UZK-02）の中で通す。ただし、日をまたぐのがシステムの外の作業だけで、システムの状態が何も待たないとき（前日17:30以降の価格ソート用ファイルの用意、スリーブ入れ、棚への戻しなど）は分けない。条件違いはL3のバリエーションとして書く。この業務は、システムを触るのが「価格ソート用CSVの出力」「在庫変更CSV登録」「在庫移動の戻しリスト出力」の3か所だけで、あとはExcel・スプレッドシート・LINE WORKS・Backlog・メール・現物の作業（システムの外）。システムの外の作業は、各シナリオの中で「システムの外」の行として書く。

| L4 ステップ | 画面操作と確認 | まだ書かない |

※3 ネット買取の買取は「入庫済み」になった時点で自動で在庫に入る（ネット買取のUNK-09）。統合仕入れの在庫変更CSVに同じカードを入れると、二重に増える。設計書（0202 在庫移動・振替登録 編集(振替)）は「買取商品はすぐ棚に戻すように店頭買取と同じ動作とするか、現行踏襲で統合仕入れとするかのどちらかになる」と未決。この行は業務フローのとおり現行踏襲の経路で書いた。**判断待ち**。二重入庫の判断は仕入れ業務（USH-02）の側で決める（通しシナリオ UTH-02 は決めずに、この判断待ちを引き継いでいる）。同じ論点は、業務横断のUXB-10・UXB-11（判断待ち3・※4。買取の入庫だけで在庫に入る経路にして、統合仕入れで同じカードを入れる経路は通さない）、店頭買取のUKA-05・UKA-09（手動入庫を在庫変更CSVで行った買取が入庫待ちのまま残り15時に二重に入庫されるか）、ネット買取のUNK-09（入庫待ちを入庫済みにして在庫へ入れ、仕入れ業務へ渡す）にもある。決まったら、それらと揃えて直す。

※4 同名ファイルは取り込めない。設計書（0202 在庫変更CSV登録の現行仕様）は「直近で取り込んだファイルと同じ名前」、新実装は「過去1か月以内に同じファイル名」。分割したファイルには別の名前を付ける。

※5 業務フロー15の2-3は、仕入れ統合作成ファイル（Excelマクロ）で棚戻しリストのファイルを作り、店頭買取・ネット買取・在庫移動一覧の各チームへ渡すと書く。3-13は現物の戻し作業。どちらにも、システムの戻しリスト出力は書かれていない。そのためUSH-03は15のパターン2・3の工程の代わりとして数えず、マクロでの作成と現物の戻しはUSH-01・USH-02の中に「システムの外」として残した。USH-03は、在庫管理の12 2-18（統合仕入れで棚戻しを行う）に対応する新システムの戻しリスト（0202 M04-33・M04-34）を通す補足で、統合仕入れがこの出力を使うかは判断待ち。
