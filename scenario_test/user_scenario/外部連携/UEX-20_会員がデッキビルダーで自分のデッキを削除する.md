# UEX-20 会員がデッキビルダーで自分のデッキを削除する

| 項目 | 内容 |
|---|---|
| 利用者 | 会員（デッキビルダー。システムの外）→ EC（API） |
| 目的 | 会員が自分のデッキの削除を指示する。削除したデッキは見えなくなり（論理削除）、同じデッキの下書きも消える。もう一度削除しようとすると見つからない（404）で、削除日時は付け直されない。他人のデッキは削除できない |
| 種類 | 正常（1本）＋ L3の具体例（組み合わせ表は無い。1つずつ別のテストにする） |
| マトリクスの行 | なし（組み合わせ表は無い）。L3 は `scenario_list.md` の UEX-20 の L3 欄の項目を1つずつ別のテストにした。削除後に1件の参照・検索で見えない応答は、`matrix_UEX-07/` の例外EX4と同じ応答 |
| もとのシナリオ | なし（業務フローに無い）。設計書 0515 API_デッキビルダー「デッキ情報削除」（A15-11） |

デッキビルダーの画面の見え方は外部サービスなので記録だけにし、合否は EC が返した値（応答の結果・メッセージ）と、EC に残るもの（見えなくなること）で付ける。EC の応答は、デッキビルダーが送るのと同じ要求を、試験担当者が用意する HTTP クライアントで EC に送って読む。会員がデッキビルダーで作ったデッキ（デッキタイプ ユーザー）は、管理画面のデッキ一覧に出ないので、EC 側の確かめは応答で行う。

## 前提

- システムの外で済んでいること：デッキビルダーが EC の会員のメールアドレスとパスワードでログインできる状態
- 用意するデータ（試験用の値。設計書の値ではない）
  - 会員：試験 五郎（UEX-20）（メールアドレス `uex-20@example.test`、パスワード「Uex20Test-2026」、本会員）。試験 六郎（UEX-20）（メールアドレス `uex-20-b@example.test`、パスワード「Uex20Test-2026」、本会員。他人の行用）
  - デッキ（会員がデッキビルダーで作る。システムの外の操作。UEX-07 の登録の手順と同じ）：五郎が、スタンダードのデッキを2件保存する。DK1：デッキ名「シナリオ試験削除デッキDK1 UEX-20」・公開範囲＝公開。DK2：デッキ名「シナリオ試験削除デッキDK2 UEX-20」・公開範囲＝公開。六郎が、スタンダードのデッキ DK3「シナリオ試験削除デッキDK3 UEX-20」（公開範囲＝公開）を1件保存する
  - 下書き（DK1 だけ）：五郎が DK1 を開いて内容を編集し、確定せずに下書きとして保存する（UEX-08）。下書きに入れた内容は、確定の内容と見分けがつく値にする（例：デッキ名を「シナリオ試験削除デッキDK1 下書き UEX-20」にする）
  - 控える値：DK1・DK2・DK3 のデッキID（デッキビルダーの保存の応答）、五郎・六郎の認証用トークン（デッキビルダーのログインの応答）、五郎のデッキユーザーID（デッキビルダーのユーザー情報の応答。UEX-10）
- 画面の名前・文言は新実装の表示で書く。メッセージの文言は設計書の文言（英語）を期待値にし、新実装の文言が違えば不合格として記録する。新実装は要求の言語の指定で英語・日本語の文言を返すので、英語の指定で確かめる

## L3で変わるところ（組み合わせ表は無い。1つずつ別のテストにする）

手順の番号は上の「操作の流れと期待値」。どの行も、行ごとに新しいデッキを使う（前の行で削除したデッキを使い回さない）。

| 行 | 条件（`scenario_list.md` の L3 欄の項目） | 変わるところ |
|---|---|---|
| R1 | 所有者でない（401） | 手順1の代わり：六郎のトークンで、五郎の DK2 を削除する要求を送る。期待値：認証拒否（401）・処理結果メッセージ「Authentication failed」。DK2 は削除されない（五郎の自分のデッキ検索に DK2 が残り、1件の参照も成功する） |
| R2 | 存在しない（404） | 手順1の代わり：存在しないデッキID（例：2147483000）を、五郎のトークンで削除する要求を送る。期待値：該当なし（404）。メッセージは表示メッセージの節の「The deck does not exist」（新実装の文言が違えば不合格として記録）。どのデッキも変わらない |
| R3 | 削除済みの再削除（404） | 代表の行の手順5 |
| R4 | 削除の途中で例外（すべて取り消して500） | 画面の操作では起こせない（EC の保存先の障害が必要）ので、実施不可（流せない）として記録する。起こせるときの期待値：処理失敗（500）で、例外の内容をメッセージに含めて返す。デッキは削除されず、下書きも残る（一連の処理は1つのまとまりで、例外のときはすべて取り消す） |
| R5 | 削除後に1件の参照・検索で見えない（`matrix_UEX-07/` の例外EX4と同じ応答） | 代表の行の手順2〜4 |
| R6 | 認証用トークンが無い・誤っている | 手順1の代わり：認証用トークンを付けずに（または誤った値で）DK2 を削除する要求を送る。期待値：認証拒否（401）・処理結果メッセージ「Access Token is incorrect」。DK2 は削除されない。設計書の判定順（トークンの確認が先、デッキの有無が次、所有者の確認が最後）のとおり、存在しないデッキIDにトークン無しで要求しても401になる |
