# UEX-10 会員がデッキビルダーのニックネーム・プロフィールを決め、デッキユーザーIDで他の人に見せる

| 項目 | 内容 |
|---|---|
| 利用者 | 会員（デッキビルダー。システムの外）→ 他の人 |
| 目的 | 会員がデッキビルダーのユーザー情報で、ニックネームとプロフィールを変える。本人が見ると、ニックネーム・プロフィール・デッキユーザーIDが返る（未設定はnull）。他の人は、デッキユーザーIDだけで（ログインなしで）、その会員のニックネーム・プロフィール・デッキユーザーIDを見られる（0515 A15-03〜A15-05・A15-02） |
| 種類 | 正常（変更→本人の参照→他の人の参照の1本）。ニックネーム未指定・プロフィール未指定・該当する人がいない・アクセストークンなし・ログアウトは「L3で変わるところ」 |
| マトリクスの行 | 組み合わせ表は作らない（因子はユーザー情報の指定だけ）。L3の値は「L3で変わるところ」の V1〜V6 |
| もとのシナリオ | なし（業務フローに無い） |

デッキビルダーのアプリ本体の画面（ユーザー情報の欄・他の人のプロフィール画面）は外部サービス（システムの外）なので、見え方は記録だけにする。この試験では、アプリの役を HTTP の呼び出し（UEX-07 と同じ）で務め、EC が返す値（HTTP の結果・応答の本文）で合否を付ける。ニックネーム・プロフィールを EC の管理画面・フロントで表示する画面は見つからないので、EC 側の値は、ユーザー情報参照の結果で確かめる。

## 前提

- 共通の決まり：`../L4を流すときの共通の決まり.md` を先に読む（試験データの名前にシナリオIDを付ける・共有の設定は元に戻す・バッチの起動・店舗の読み替えなど）
- 用意するデータ（試験用の値。設計書の値ではない）
  - 会員：本人（会員1。メールアドレス `uex-10-self@example.test`）と他の会員（会員2。メールアドレス `uex-10-other@example.test`）。どちらも本会員にする（UMB-01・UMB-02 と同じ操作）。会員を作ると、デッキユーザーIDも一緒に付く（新実装）
  - 変更する値：ニックネーム「シナリオ試験ニック UEX-10」・プロフィール「シナリオ試験プロフィール UEX-10」（流すときは名前の後ろにシナリオIDが付く）。別の値：ニックネーム「シナリオ試験ニック UEX-10 B」
- 応答のメッセージの文言は、設計書の文言（英語）を期待値にする。新実装の文言が違えば、不合格として記録する（UEX-07 と同じ）。HTTPの結果と処理結果コードは、文言とは別に合否を付ける

## L3で変わるところ（組み合わせ表は無い。L3欄の値）

1回ずつ別のテストとして流す。どの行も準備P1を通る。

| 行 | 条件 | 変わるところ |
|---|---|---|
| V1 | ニックネーム未指定（400。更新しない） | 手順2を、ニックネームを指定せず（プロフィールだけ）に呼び出す。HTTP 400・メッセージ「Invalid request parameters」。続けて手順1と同じ参照で、ニックネーム・プロフィールが手順2の前のまま（更新されていない） |
| V2 | プロフィール未指定（nullで保存） | 手順2の後に、ユーザー情報変更を、ニックネーム「シナリオ試験ニック UEX-10 B」だけ（プロフィールを指定しない）で呼び出す。HTTP 200・「Update user information」。続けて手順3と同じ参照で、ニックネームは「…B」、プロフィールは空（null。前の値は引き継がれない）。手順4の他ユーザー情報参照でも、プロフィールは空 |
| V3 | デッキユーザーIDに該当する人がいない（400。404でない） | 手順4を、存在しないデッキユーザーID（例：「ZZZZZZZZ」）で呼び出す。HTTP 400・メッセージ「Invalid request parameters」。HTTP 404にならない（設計書 A15-04：該当が無いときもHTTP 404ではなく入力不正） |
| V4 | 認証用トークンが無い・不正（401。本人の参照・変更） | 手順1を、アクセストークンを付けずに呼び出す：HTTP 401・メッセージ「Access Token is incorrect」または「Authentication failed」。手順2を、アクセストークンを付けずに呼び出す：HTTP 401で、更新されない（続けて会員1の参照で値が変わっていない） |
| V5 | ログアウト後 | 手順6のあとに、会員1の手順1と同じ参照を、同じアクセストークンで呼び出した結果を記録する（設計書 A15-02：ログアウトはトークンのCookieを空にする。すでに無効な状態に対する要求のふるまいは、既存の認証エラーまたは冪等な成功応答の実装に従う）。アクセストークンなしでログアウトを呼び出すと HTTP 401・「Access Token is incorrect」。再ログインすれば新しいアクセストークンが返る |
| V6 | 更新中の例外（500。更新を取り消す） | **実施不可（流せない）**。保存中に例外を起こす操作が画面・呼び出しに無い（通信を書き換える手段は使わない）。設計書どおりの期待値（記録のために残す）：HTTP 500・例外メッセージ。更新は取り消され、値は変わらない |

例外（組み合わせ表が無いので、L3の値として扱う）：なし。
