# デッキビルダーで登録したデッキを、公開範囲に応じて見せる（UEX-07）

IPA「高信頼化ソフトウェアのための開発手法ガイドブック」(2010) の表6-9〜6-11と同じ手順で作る（`通販/matrix/README.md` と同じ）。

1. 因子・水準表（FL表）: `fl_table.tsv`
2. 禁則表: `prohibitions.tsv`
3. マトリクス: `matrix.md` / `matrix.tsv`（`tools/build_matrix.py` が作る。1行が1本のシナリオ＝デッキを登録して、ある人がある入口から見るまで）
4. 例外の差し込み表: `exceptions.tsv`

## 範囲

- デッキビルダー（会員が自分のデッキを作るアプリ。システムの外）が呼ぶデッキの登録・参照・検索のAPI（0515 A15-09・A15-12・A15-13）。会員のログインは EC の会員（A15-01）
- 見え方は、API の応答（デッキの内容・「Deck is not found」などの応答文言・HTTP の結果）と、EC 側の保存結果で確かめる。デッキビルダーの画面の見た目はシステムの外
- 下書き保存・確定保存は UEX-08、削除は UEX-20、テキストのインポートは UEX-09、検索の絞り込み・件数・ページは UEX-19。この表は「公開範囲×見る人×入口」だけを組み合わせる
- ここでの「見る入口」の「公開検索」は、デッキビルダーが呼ぶ検索API。EC のフロントのデッキ検索（0309）は管理画面で登録した大会デッキの閲覧で、UDK-01・03 の終点で確かめる

## 実装と設計書で確かめたこと（2026-11-05）

- 参照できる条件（0515 A15-12 現行仕様節 628行目付近）：公開＝誰でも／非公開＝所有者本人だけ／限定公開＝閲覧用トークンが一致するか所有者本人。判定は下書き・保存済みのどちらでも同じ。参照できないときは「Deck is not found」（404）で、デッキが無いときと区別しない
- 検索（A15-13 653行目付近）：公開検索は認証不要で公開デッキだけ、自分のデッキ検索は認証必須で所有者のデッキだけ。閲覧用トークンは自分のデッキ検索のときだけ応答に含める
- 閲覧用トークンの発行（A15-09 550行目付近）：未設定のときだけ作って保存するが、応答に含めるのは公開範囲が限定公開のときだけ
- 新実装は `src/Eccube/Controller/App/DeckBuilder/DeckController.php`（1件の参照は 214〜262行目。下書きは Redis から先に読む＝224行目、公開範囲の判定は 767行目）にある。検索（262行目以降）は保存済みのデッキを検索し、下書きを見ない。下書きが残っていても検索は実行できるので、下書きの有無と検索の組は禁則にせず、検索結果には保存済みの内容が出る
- デッキビルダー本体のローカルの checkout は 2025-01-16 の古いもの（画面の構成の参考だけに使う）

## まとめた水準

- 見る人の「所有者でない人」は、1件の参照・公開検索では処理が同じなので、まとめず分けると行が増えるだけになる。ただし自分のデッキ検索（C3）だけは、未ログインは認証拒否（401）、ログイン済みの他の会員は自分のデッキの一覧が返る（このデッキは出ない）と処理が違うため、B2（未ログイン）とB4（他の会員）に分けた（codexレビュー1巡目の指摘で、まとめていた水準を分けた）
- 1件の参照で、未ログインと他の会員が同じ判定になる根拠：0515 A15-12「トークンが無い、または有効でないときは所有者扱いにしない」、新実装 `src/Eccube/Controller/App/DeckBuilder/DeckController.php` 767〜790行目（所有者でなければ公開以外は参照できない）
- 限定公開の閲覧用トークンを持つ人（B3）は、トークンの照合が違うので分けた
