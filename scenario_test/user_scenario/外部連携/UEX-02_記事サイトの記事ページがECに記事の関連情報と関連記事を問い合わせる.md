# UEX-02 記事サイトの記事ページが、ECに記事の関連情報と関連記事を問い合わせる

| 項目 | 内容 |
|---|---|
| 利用者 | 記事サイトの読者（WordPress。システムの外）→ EC（API。記事サイトが呼ぶ） |
| 目的 | 読者が記事サイトの記事ページを開くと、記事サイトがその記事のWPの投稿IDでECに問い合わせる。ECは、記事情報（記事ID・WPの投稿ID・WP種別ID・URL・更新日時・作成日時）と、記事に紐づくカード・アーキタイプ・デッキ・イベント詳細を返す（0517 A17-01）。続けて関連記事を問い合わせると、ECは同じデッキ・アーキタイプ・カード・イベント詳細のいずれかを共有する記事を、WPの投稿IDと一致フラグで返す（0517 A17-02）。同じWPの投稿IDは1件にまとまる |
| 種類 | 正常。記事が無いとき・関連記事が無いとき・件数の指定・共有の種類・WP種別の違いは「L3で変わるところ」 |
| マトリクスの行 | 組み合わせ表は作らない（因子は問い合わせの対象の記事だけ）。L3の値は「L3で変わるところ」の V1〜V8 |
| もとのシナリオ | なし（業務フローに無い。今のシナリオ SCN-* に無く、0517 A17-01・A17-02 から足した） |

記事サイトの側（記事ページの見た目・記事サイトが呼び出す仕組み）は外部サービス（システムの外）なので扱わない。この試験では、記事サイトの役を、ブラウザのアドレス欄に設計書の呼び出し先を入れて開くことで務め、ECが返す値（応答の本文とHTTPの結果）で合否を付ける。

- 記事・記事に紐づくカード・アーキタイプ・デッキ・イベント詳細は、登録する手段が無い（0517 は取得だけ。新実装の記事の保存の受け口は、受け取った内容を捨てて整数1を返すだけで、記事の紐付けを作らない）。そのため、開発環境の初期データ（開発環境のダンプ）にある記事を使う。試験では記事を作らず、データも書き換えない
- 用意するデータ（開発環境のダンプ 2026-09-07 の値。設計書の値ではない。流す前に手順1の呼び出しで確かめ、環境の値が違うときは、その環境にある同じ性質の記事に読み替えて控える）

- 呼び出し先（設計書のエンドポイント）：記事情報1件の取得は「開発環境の本店のアドレス」＋ 設計書のエンドポイントのパスにWPの投稿IDを渡す形（0517 A17-01 のリクエストパラメータサンプル）。関連記事の取得は同じアドレスに設計書の関連記事のパスと、記事IDの位置にWPの投稿ID（0517 A17-02 のリクエストパラメータサンプル）。取得件数は設計書の取得件数のとおり指定する。認証は不要（設計書：認証の有無 無）

## L3で変わるところ（組み合わせ表は無い。L3欄の値）

1回ずつ別のテストとして流す。どの行も準備P1を通る。「関連記事の取得」の件数は値の読み替え後に合わせる。

| 行 | 条件 | 変わるところ |
|---|---|---|
| V1 | 記事が無い（記事情報1件の取得で、存在しない投稿ID＝値E） | 記事情報1件の取得を値Eで呼ぶ。結果は該当データなし（404。設計書 0517 A17-01 のステータスコード）。応答の本文は、設計書（表示メッセージの節）では「Not Found」（コードとメッセージの2項目）。**新実装は、コードと、エラーの一覧（「記事が見つかりません」）を返す作りに見える**。文言が違えば不合格として記録する（HTTPの結果が404であることは合格）。食い違いに書く |
| V2 | 削除済みの記事（A17-01：削除日時が入っている記事は検索の対象から外れる／A17-02も関連から外れる） | **実施不可（流せない）**。ダンプに削除済みの記事は無く、記事を削除・登録する画面・APIが無い（試験で書き込みもしない）。設計書どおりの期待値（記録のために残す）：削除済みの記事のWPの投稿IDだけを指定すると、V1と同じ該当データなし（404） |
| V3 | 同じWPの投稿IDの記事が複数あり、1件に絞れない（A17-01） | **実施不可（流せない）**。ダンプに、同じWPの投稿IDの記事は無く、記事を登録する手段が無い。設計書（現行仕様の節。Excel由来の欄に記載なし）は、1件に絞れずエラーになり、正常も該当データなしも返さないと書く。新実装は、複数あっても先頭の1件を返す作りに見える（食い違いに書く） |
| V4 | 関連記事が無い（A17-02：共有する記事が無い） | 関連記事の取得を値D（737）で呼ぶ。結果は該当データなし（404。設計書 0517 A17-02）。応答の本文は、設計書では「Not Found」（関連記事が無いとき）。新実装の応答の形を記録し、違えば不合格として記録する（V1と同じ） |

## 判断待ち

なし。

記録（判断待ちではない。合否は付けず、実際の画面・値を記録する）：
- 記事の紐付けの登録（記事サイトが記事を保存するときにECへ通知する）は、現行も新実装も動いていない（`scenario_list.md` の判断済みの事項）。このシナリオは取得だけを確かめる
- 開発環境のデータはダンプの値から変わっていることがある。値A〜Dは、手順1・V4の呼び出しで性質を確かめてから使い、読み替えを控える
- 応答の中のカード・デッキ・イベント詳細の細かい項目（名称・画像・フォーマットなど）の中身は、設計書の例の形と同じ項目が並んでいるかを記録する（値の合否は付けない）

設計書との食い違い（起票しない）：
- 日時の書式：A17-01 の項目表（Excel 由来）は「日時（YYYY/MM/DD HH:MM）」、同じシートの応答の例は「2018-11-02T15:29:49+09:00」の形。期待値は項目表の書式（決まりの優先順位）。新実装は例の形（ISO）で返す作りに見え、そのとおりなら不合格として記録する
- 該当データなしの応答の本文：設計書は「Not Found」だけ（コードとメッセージの2項目）。新実装は、コードとエラーの一覧（「記事が見つかりません」など）を返す（記事情報1件の取得）。関連記事の取得の404の本文は、画面で確かめて記録する
- 同じWPの投稿IDの記事が複数あるとき：設計書（現行仕様の節）はエラー、新実装は先頭の1件を返す。ダンプには複数ある記事が無く、試験では起こせない
