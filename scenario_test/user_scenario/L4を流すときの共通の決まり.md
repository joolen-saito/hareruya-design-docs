# L4 を流すときの共通の決まり

全部の業務の L4（手順と手順ごとの期待値）に共通する決まり。各 L4 の「前提」より先に読む。

## 試験データの名前（2026-11-27 依頼者「全部おすすめどおりで」）

- 「シナリオ試験カードB」「シナリオ試験サプライZ」などの名前・商品コード・会員のメールアドレスは、その L4 のファイルの中だけの呼び名。ファイルが違えば、同じ名前でも中身（価格・在庫・扱い）は別のもの
- 流すときは、名前の後ろにシナリオID を付けて作る（例：「シナリオ試験カードB」→「シナリオ試験カードB UPM-02」、商品コード「UZK01-T01」はそのまま）。期待値の文に出る名前も、付けた名前に読み替える
- 前提に「〇〇（シナリオID）の終点」を使う続きのシナリオは、前のシナリオで付けた名前のまま使う（例：UPM-06 は UPM-02 で作った「シナリオ試験カードB UPM-02」を使う）
- 同じ開発環境で前に流した試験の商品・会員が残っていたら、名前の後ろの番号で見分ける。残った物を消してよいかは、その環境の決まりに従う

## カードの商品コード（2026-11-27 仕入れ業務の L4 のレビューで分かった事実）

- カード商品CSVには商品コードの列が無い。カードの規格の商品コードは、登録のときに新実装がカードの情報から自動で作る（プロモーションコード・カードセットのコード・Foil の印・カード番号5桁・言語のコード・状態のコード・高額商品コードをつないだもの。src/Eccube/Service/Csv/Importer/Event/ProductCardImportHandler.php）
- そのため、L4 がカードに「商品コード「UZK02-T01」」のように書いた値は、その L4 の中だけの呼び名。流すときは、カード登録CSV→カード商品CSVで登録したあと、商品一覧（または在庫一覧）で実際の商品コードを控え、L4 の呼び名をその値に読み替えて、検索・在庫変更CSV・期待値に使う
- グッズ・サプライ（グッズ商品CSV）は商品コードの列があるので、L4 に書いた商品コードで登録してよい（新規の登録で同じ商品コードが既にあるとエラーになるので、試験データの名前と同じくシナリオIDを付けて重ならないようにする）

## 共有の開発環境の設定を一時的に変えるとき（2026-11-27 依頼者「全部おすすめどおりで」）

- 対象：入荷通知メールの許可（UKA-05・UNK-09）、管理者へのメールの宛先（UNK-14）など、追加システム設定のように全部の試験が使う設定
- 流す前に今の値を確かめて控える。確かめに要る値でないとき（「送らない」・空など）だけ変える。もともと要る値なら変えない
- 確かめ終わったら控えた元の値に戻し、戻ったことを設定の画面で確かめる

## 画面の操作で作れない状態の用意（2026-11-27 依頼者「全部おすすめどおりで」）

- 画面の操作では作れない状態（必須の項目が空の会員、ポイントの履歴と残高のずれ、注文完了メールが送られていない注文、金額の合わない注文など）は、試験で作ったデータ（名前にシナリオID が付いたもの）に限って、開発環境のデータを書き換えて作ってよい。人のデータ・ほかの試験のデータは書き換えない
- 書き換えた項目（論理名）と、書き換える前と後の値を記録に残す
- 対象：会員管理 UMB-24、スマレジ連携 USM-20・21、ポイント UPT-09。ほかに同じ用意が要る L4 も、この決まりで流す

## 外部のシステムから EC への要求（2026-11-27 依頼者「全部おすすめどおりで」）

- デッキビルダー・記事サイト・店舗のプリンタ・ポイントグランター・スマレジの通知・買取端末など、外部のシステムから EC への要求は、本物の機器・外部の試験環境が使えるときはそれで流す
- 使えないときは、試験の担当者が用意する HTTP クライアントで、同じ要求を EC へ代わりに送ってよい。どちらで流したかを記録に残す
- EC が返す応答の本文で合否を付ける L4（外部連携 UEX-07・08・17・19・20 など）は、各 L4 に書いたとおり、HTTP クライアントで同じ要求を送って応答を読む

## 本店の店名を一時的に変える（MTGバイヤーのネット買取。2026-11-27 依頼者「全部おすすめどおりで」）

- MTGバイヤーの端末でネット買取を選べるのは、所属店舗名が「トーナメントセンター 東京」のときだけ。開発環境の本店の店名（基本設定の「店名」）は「Hareruya」なので、ネット買取を流す間だけ「トーナメントセンター 東京」に変えてよい
- 「共有の開発環境の設定を一時的に変えるとき」と同じく、元の店名を控えて変え、終わったら戻して、基本設定の画面で戻ったことを確かめる。店名はメールや画面にも出るので、ほかの試験が走っていない時間に流す
- 対象：UMG-01 の L1、ネット買取を使う UMG-02・03・04・07・08・09・10、ネット買取 UNK-03

## これまでに決まった共通の決まり（各 L4 の書き方の元）

- バッチは時刻を待たず手で起動してよい。起動のしかたは各 L4 の根拠の欄にある（2026-11-26）
- 外部サービス（スマレジ・SPLINKS・ポイントグランター・オンライン本人確認・配送会社など）の画面の見え方は記録だけにし、合否は EC 側の値で付ける（2026-11-26）
  - ただし、店頭受取の連携でスマレジに作る商品の登録・削除（店頭受取受注管理 UOR-01・02・06・07・09・10 と、それを参照する業務周期 UCY-16〜18 など）は、EC 側に見える印が無いので、スマレジに登録された値（商品名・部門・金額・在庫・商品コード）と、スマレジから商品が消えたことで合否を付ける（`判断待ち_L4_店頭受取受注管理.md` の A3 と UOR-09 の決着 2。2026-11-26 依頼者「おすすめどおり」）
- 試験用に日付の古いデータが要るときは、試験で作ったデータに限り開発環境で書き換えて用意してよい（2026-11-26）
- 店舗は新しく作らない。L4 が「支店A」などと書く所は、流す前に既存の店舗から条件に合う店舗を選び、店舗IDと画面に出る名前を控えて読み替える。本店は店舗ID 1（画面によって「Hareruya」「トーナメントセンター 東京」と出る）。本店の 3F・B2F は本店バックヤード、2F は本店
- 画面の操作で起こせない例外は「実施不可（流せない）」として記録する
- 新実装が設計書どおりに動かない見込みの所は、期待値は設計書どおりにし、各 L4 に書いた別の手順で先へ進み、不合格として記録する
- EC からスマレジへの在庫連携は行わない（スマレジ在庫の反映は確かめない）。支店システムは存在しない
