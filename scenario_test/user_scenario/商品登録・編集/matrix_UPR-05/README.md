# 商品登録・編集の入荷した商品の在庫と公開（UPR-05）

IPA「高信頼化ソフトウェアのための開発手法ガイドブック」(2010) の表6-9〜6-11と同じ手順で作る。

2026-11-09：シナリオの本文に「／」で並べていた値を、1回ずつ流すテストに分けるために作った（IPA 6.3.1・6.3.2。依頼者決定）。値と期待値は本文に書いてあったものを水準ごとに分けただけで、新しい期待値は作っていない。

## 範囲

- 登録済みの商品の在庫を入れ、承認を受け、公開して販売を始めるところ（業務フロー09の4-7〜4-9／10の4-6〜4-9）
- 因子：入荷時の商品の公開状態（非公開だった／既に公開されていた）、お客様の検索の確認時点（ユニサーチのフィードを送る前／送って取り込んだあと）
- 例外（★）：承認者が却下する、登録した本人が承認しようとする（承認後のスマレジ連携が失敗する例外E3は2026-11-18に外した）。1つずつ別のテストにした
- 在庫を入れて承認する操作そのものはUZK-01、デッキセットの在庫の結合の承認はUZK-05で見る。1つの商品規格で100件以上増減するときの確認のモーダルは、実装に無い（判断待ち）ので水準にしていない

## 期待結果の決まり

- 商品が非公開だった：商品公開CSVで公開に直す
- 既に公開されていた：商品公開CSVを取り込まず、商品が公開のまま変わらずお客様の画面に出る
- 承認：承認された在庫数が商品の在庫に入り、公開にした商品がお客様の画面に出る
- フィードを送る前：公開にしても、お客様の検索（キーワード・詳細検索・カテゴリ）にはすぐ出ない
- フィードを作って送り、ユニサーチが取り込んだあと：検索に出る

※因子が1〜2つのとき、`tools/build_matrix.py` は網羅率の分母が0になって止まる（2026-11-09時点）。この表は、割り算の前に分母0を100％として扱い、因子が1つのときは水準ごとに1行にする以外は `build_matrix.py` と同じ手順の写しで作った。道具が直れば、下のコマンドで同じ表ができる。

## 外した因子・水準（2026-11-10 codex R1：出し分けだけの違い）

- 因子B「お客様の検索の確認時点（ユニサーチのフィード）」（フィードを送る前／取り込んだあと）：検索・カテゴリに出るかどうかが変わるだけで、公開済みの商品詳細は直接開ける（`ProductRepository.php` 122行）。〇表の N1（ユニサーチの反映状態）も適用外にした
- 因子が A だけになり、`build_matrix.py` が0割りで止まるため、`matrix.md` は同じ形式で手で書いた（UEX-16 と同じ）。例外E3 の差し込む元は T03 から T02 に付け替えた
- 作り直し：テスト 4本 → 2本

## 外した例外（2026-11-18 レビュー指摘：EC-CUBE からスマレジへの在庫連携は行わない）

- 例外E3「承認後のスマレジ連携が失敗する（承認を押し直す）」を外した。EC-CUBE からスマレジへの在庫連携は行わないことになったため、承認後に「スマレジ連携失敗」にならない。例外IDは振り直さず E3 は欠番。
