# 商品登録からサンクスメールまで：通しシナリオ（UTH-01）

バックオフィスで商品を登録し、価格・在庫・公開を整え、ユニサーチ（検索サービス）へ商品のフィードを作って送り、お客様が本店・支店のサイトでサジェストや検索で商品を探し、買い物かごに入れて注文し、注文確認メール（サンクスメール）が届くまでを、1本の通しシナリオにする。今のシナリオ（商品管理から注文確認メールまで UPM、商品登録・編集 UPR、価格管理 UPC、在庫管理 UZK、通販 UTS、ポイント UPT）は消さず、通しの「区間」として参照する。UPM はユニサーチを入れない版で、この通しは UPM に「ユニサーチへのフィード」「ユニサーチの検索・サジェスト」「予約・登録後の改定・スタン落ち」を足した上位版にあたる。

ユニサーチ側（外部サービス）のフィードの取り込み・索引づくりは「システムの外」。ECが作って送るフィードの中身と、ECの画面に返ってくる検索結果を期待値にする。

## 利用者と目的

| 利用者（担当の順） | 目的 |
|---|---|
| トレードチームの担当者（登録担当） | 入荷した商品（カード・グッズ・高額商品、予約か通常か）をCSVで登録し、在庫を入れ、公開する。価格をセールにする・改定する。ユニサーチのフィードを作って送る（管理画面のボタン、または定時のバッチ） |
| 在庫の承認者 | 登録担当が入れた在庫を承認する（登録した本人は承認できない） |
| 顧客戦略チームの担当者 | セール用価格変更CSV・基準価格変更CSVで価格を変える（登録担当と同じ人でもよい） |
| 会員のお客様（本店・支店のサイト） | ヘッダーの検索・サジェスト・詳細検索・カテゴリで商品を探し、並び順を変え、買い物かごに入れて、支払方法・配送方法・ポイントを選んで注文し、注文確認メールを受け取る |

## 起点・終点

- 起点：入荷した商品を、バックオフィスで登録する（商品の画像はS3へ保存済み。予約商品は新弾の発表を受けて登録する）
- 終点：お客様に注文確認メールが届き、商品・数量・金額・支払方法・配送方法・お届け先が、画面で確かめた注文と一致する。途中の「ユニサーチに載ったあとで、検索結果に出る」ことも確かめる
- 待ちの境目（切らずに通す）：①ユニサーチへの反映待ち（フィードを送ってから検索に出るまで。ユニサーチ側の取り込みは外）、②予約商品の発売日待ち（水準B3）。入金を待つ支払方法（郵便振替・銀行振込・コンビニ決済）は、購入完了と注文確認メールまでを終点にし、入金から先は通販のUTS-16・UTS-17

### 設計書との食い違い（設計書の不足。起票はしない）

- フィードの作成と送信：設計書は別のバッチ（作成は毎時15分、送信は5分おき・SCP）。新実装は1つの処理で作成して続けてSFTPで送り、管理画面のボタンも送信までする。このため、管理画面のボタンを押した直後からユニサーチへ届く時間の見込みが、設計書（最長で次の送信の5分後）と新実装（作成が終わり次第）で違う。定期実行の定義は新実装で見つからなかった
- フィードの項目：設計書37項目に対し、新実装は41項目（カテゴリ名（英）・検索ワード・ピックアップが設計書に無い）。先頭の項目名の行、カテゴリの階層の区切り（\x05）、複数カテゴリの区切り（\x01）は設計書に定めが無い（タグ・色などの区切りは^A）
- 在庫の項目：設計書は「在庫数（NM以外も合計）」「支店ID:在庫数の形式で指定可能であれば」と要相談。新実装は在庫のある店舗のIDの一覧
- Foilの項目：設計書は「項目名を変更するかは要相談」。新実装は項目名を変えていない（値は通常・あり・特殊の3通りに対応する）
- 送信先のフォルダに古いファイルを残さない処理：新実装は作成するファイル名の前半を「feed_hareruyamtgecc_」「done_hareruyamtgecc_」にし、送信前の削除には「feed_hareruyamtg_」「done_hareruyamtg_」を渡し、前方一致（`UniSearchSftpService.php` 94〜100行の前方一致）で消す。「feed_hareruyamtg_」は「feed_hareruyamtgecc_…」の前半と一致しないので、この実装が送ったファイルは、この削除では消えない（`UniSearchExportService.php` 94〜95行・118〜125行）。送信先には送るたびに新旧のフィードが残る。設計書は送信先の古いファイルの扱いを書かない。L4の手順7で、送信先に残るファイルを確かめて記録する（送信先はユニサーチ側で、見られないときは記録に留める）
- 作成の失敗・送信の失敗：設計書のエラーハンドリングの欄が空（再送・通知・画面での案内の定めが無い）。新実装は、ログに記録し、処理を異常終了にするだけ
- ユニサーチへの反映までの時間：設計書は、フィード送信後にユニサーチが取り込んで索引ができるまでの目安を書かない。期待値に時間を入れられない（反映前と後で見え方が変わることだけを確かめる）
- ユニサーチの対象外の検索：設計書は、TOPページのタグによる商品検索と商品詳細ページの同名商品検索を対象外とする。新実装はタグ・カードの同名商品の検索もユニサーチを通す。設計書を優先すると、タグの検索はフィードに載る前でも出るはずだが、新実装は載る前は出ない
- 0件の案内の文言：設計書の0303 商品一覧の表示メッセージが、結果領域の「お探しの商品は見つかりませんでした」（MSG-002）と、一覧領域の「ご指定の条件に一致する商品が見つかりませんでした。」の2系統を書く。商品管理から注文確認メールまで（UPM-01）は後者を期待値にしている。新実装のユニサーチの経路は前者。この通しは、どちらかの0件の案内が出ることを合格とし、実際の文言を記録する
- 件数が上限を超えたときの案内：MSG-005・006は「商品一覧を表示したまま」、一覧領域の行は「商品内容を表示しない」と、設計書の中で食い違い、上限の件数も書かない。新実装は上限4,000件で、先頭の4,000件までを出して最後のページに案内を出す（新実装 `html/template/default/assets/hareruya/js/hareruya-unisearch-list-client-core.js` 339〜341行）
- 商品一覧の読み込みに失敗したときの案内：設計書にメッセージが無い（商品詳細の同名商品一覧の「読み込みに失敗しました。」だけ）。新実装は「一覧の読み込みに失敗しました。」

## まとめた水準

マトリクスで代表の1つにまとめた種類の一覧と、流れ・処理が変わらない根拠は `matrix_UTH-01/README.md` の「まとめた水準」に書いた。通しで足したまとめ方：

| 因子 | まとめた種類 | 根拠（要約） |
|---|---|---|
| 商品の種類（高額商品・委託販売） | 高額商品・委託販売商品を1つ（A3） | 業務フロー10 パターン7「高額商品登録と同様の変更」。UPR-07の終点はUPR-06と同じ |

| 公開の仕方（CSV） | 商品公開CSV登録と、カード・グッズ商品CSV登録の公開ステータス列を1つ（D2） | どちらもCSVで公開ステータスを変える（UPR-09） |
| 並び順 | おすすめ順・色順を選び直す／既定のまま（J1） | 選び直しても既定と同じ並びの指定を送る（新実装の並び順の指定） |
