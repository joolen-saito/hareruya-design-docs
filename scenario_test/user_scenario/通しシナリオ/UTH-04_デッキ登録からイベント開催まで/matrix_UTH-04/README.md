# デッキ登録からイベント開催までの通し（UTH-04）

IPA「高信頼化ソフトウェアのための開発手法ガイドブック」(2010) の表6-9〜6-11と同じ手順で作る。1行が「始まりから終わりまで通す1回の試験」（L3）。

1. 因子・水準表（FL表）: `fl_table.tsv`。通し全体で、流れ・処理・表示・期待値を変える分岐・選択・データの違いを因子にし、業務フロー08・18の文と設計書の文を根拠に持つ
2. 禁則表: `prohibitions.tsv`。1行として通せない組み合わせ（申込が無いのにキャンセルする、など）
3. 組み合わせテストマトリクス: `matrix.md` / `matrix.tsv`。`build_matrix.py` が作る
4. 例外の差し込み表: `exceptions.tsv`。エラーや中断（★の手順）は、正常な値と混ぜず、条件に合う行へ1つずつ差し込む

## 範囲

- 業務フロー 18（デッキ登録）と 08（イベント管理）の全パターンを1回の通しにしたもの。顧客戦略チームが外部大会のデッキを登録し（タグ・アーキタイプを必要なら登録）、店舗チームがイベント・日程・バナーを登録して公開し、会員が申込・決済し、参加者がデッキを登録し、キャンセル・返金があり、開催日に受付・実施・参加ポイントの付与・売上登録をして、開催後に入賞者のデッキを公開し、注目の大会をデッキ検索に載せるところまで
- 各区間の細部（例外・境界・入力の水準）は今のシナリオ（UDK-01〜04・UEV-01〜08・UEH-01〜04・UEX-11・UEX-13・USM-23）のマトリクスに任せる。この通しは、区間のつなぎ目で値が引き継がれ、利用者に見えることと、パターンで流れが変わるところを確かめる
- 因子 12、水準は 30。業務フローの分岐に対応する因子：A・B＝18の1-2・1-3（タグ・アーキタイプが無いときだけ登録）、C＝08の1-4（バナー登録有無）、D＝08の2-1と3-2（オンライン受付の有無と参加費）、E＝08の3-4（会員登録有無）、G＝08の2-2・3-6（デッキ登録の時期）、H＝08の3-1（競技イベントの全員分のデッキ出力）、L＝08の3-3（ルールが厳しい場合の登録デッキの確認）。業務フローは二つを別の条件で書いているので別の因子にし、出力だけ・確認だけの組も通す、I＝08の2-3・2-9（キャンセル有無・キャンペーン対象有無）、J＝18の2-2（入賞者のデッキの公開）、K＝18の3-1（直近の大会に該当するか）。F（デッキリストを入れる方法）は、デッキビルダーという別の入口（18の「デッキビルダー」連携）で、入れる前の準備の手順が変わるので分けた。デッキ登録なしのイベントは入れる方法が無いので「該当なし」（F3）とした
- 1行の中の順序：外部大会のデッキの登録（A・B）→イベント登録（C）→申込・決済（D）→参加者のデッキ登録（F・G）→キャンセル・返金（I）→開催日（D・E・G・H）→開催後の入賞者のデッキの更新（J）→直近の大会（K）。日程の開始時刻を過ぎてから開催後の手順（J）を行う（開始時刻の前のデッキは管理画面のデッキ一覧に出ない）
- 禁則の考え方：申込が前提の水準（申込直後・後日のデッキ登録、キャンセル、返金）はオンライン受付なしと組まない。会員登録のない参加者はオンラインで申し込めない。キャンセルした会員は開催日に参加しないので、当日の登録・入賞者にならない。デッキ登録なしのイベントには、入力も取り込みも更新する入賞者のデッキも無い（F3はG4とだけ組む）。当日に新規会員になる参加者は、事前にデッキビルダーでマイデッキを作れない（デッキビルダーの認証は本会員だけ。0515 認証 306行）。キャンセルは申込を期限（前日23時59分）の前に行うので、キャンセルする行は日程の開始を翌日以降にする
- タグの「自動設定」は選んだアーキタイプに紐づくタグを入れる（0212 デッキ編集 (7)）ので、新規に登録したタグを既存アーキタイプのデッキに付けるときは、「自動設定」でなく選択肢から選ぶ（A2×B1）。直近の大会の参加人数は受付した人数なので、キャンセルして不参加の行（I2）は直近の大会を登録する行（K1）と組まない（禁則X19）
- 「デッキ登録の締切後」「イベント終了後」にデッキ登録のボタンが出ないこと、書式の誤り、枚数・禁止カードの警告、決済の中止・離脱、定員到達、二重申込、ポイント付与の失敗、直近の大会の入力不備などは、正常な値と混ぜず例外に入れた
- 因子に入れなかったもの（今のシナリオのマトリクスで確かめる）：まとめて申し込む日程の数（UEH-01・UEV-02）、表示言語・会員の登録住所（メールの言語。UEH-01）、イベント規模・公開状態・参加費の金額・チーム戦（UEV-01）、キャンセル理由・取り消す範囲・店舗チームの申込状況の変え方（UEV-03）、外部大会デッキの登録のしかた（画面で1件ずつ・CSV。UDK-01）、デッキ・デッキリストの公開状態の組み（UDK-01・UDK-03）、デッキリストの入れ方のうち入力欄と貼り付けインポート（まとめた水準）、ポイントの値・複数行（USM-23）、会員登録（仮会員→本会員。UMB-01・UMB-02）
- 通しで代表の値にしたもの：外部大会デッキは公開（デッキ検索に載る）、イベントは「定番イベント」・公開、フォーマットは1つ、ポイントは正の値（50）。この通しは本店のサイトで通す（新実装は申込・デッキ登録を本店専用にしている。判断待ちは scenario_list.md）

## 実装・設計書で確かめたこと（2026-11-05）

- 申込は、ログイン会員の選手情報で行う。会員登録のない参加者はオンライン申込ができない（0307 大会申込～完了 業務ロジック「申込対象ごとに申込と申込選手（ログイン会員と仮選手）を作成する」。新実装 イベント申込の画面の処理が、選手情報の無いログイン会員をイベント詳細へ戻す）。禁則X6・X7の根拠
- オンライン受付のないイベントでは、申込・申込完了画面・マイイベントの申込済みの行が無いので、申込直後・後日のデッキ登録とキャンセルは通らない（禁則X1〜X4。イベント管理のマトリクスUEV-06の禁則X4と同じ線）。当日にイベント詳細からデッキを登録するのは通る（G3。デッキ登録ボタンの条件は申込と無関係で、「デッキ登録あり」・「デッキ登録を終了する」にチェックなし・締切の前の3つだけ。0307 大会詳細 4）
- 開催日の手順は業務フローの順（3-1 リスト出力→3-2 受付→3-3 実施→3-4・3-5 会員登録→3-6 デッキ登録→3-7 ポイント付与→3-8 売上登録）。3-6は実施の後なので、当日登録（G3）の行はデッキ登録締切を実施の後にして通す（UEH-01・UEH-02のR3指摘と同じ）
- 入賞者のデッキの更新（J）は、デッキ管理の「デッキ一覧」で探す。管理画面のデッキ一覧は、イベントに結び付いたデッキを大会開始時刻を過ぎてから出す（0212 デッキ一覧(検索入力)「大会開始時刻前のデッキは検索結果に表示しない」）。会員が提出した直後のデッキは、公開状態「非公開」・デッキリスト非公開・アーキタイプ未設定（デッキ登録のUDK-03）。更新のとき、アーキタイプは必須（0212 デッキ編集 (5)）
- 直近の大会は、開催日・フォーマット・イベント名（日・英）・参加人数を入力して5大会まで登録でき、デッキ検索画面に出る（0212 直近の大会管理 処理概要）。登録できる大会を店舗のイベントに限る定めは無い（判断待ち）
- 参加ポイントの付与は、ポイントグランターの端末販売の内容を新実装が受け、スマレジに中継し、ECの保有ポイントとポイント履歴に反映する（0517 PointGranterAPI連携。イベント管理のUEV-06・スマレジ連携のUSM-23・外部連携のUEX-13と同じ）
- キャンセルの入口はお問い合わせフォーム、店舗チームが管理画面で申込状況を「キャンセル済み」にする。返金はシステムの外（イベント管理のUEV-03）。キャンペーン対象の返金も、システムの状態は変えない（UEV-04）

## まとめた水準

- デッキリストの入れ方：入力欄に入力／MTGアリーナ形式を貼り付けてインポート → 代表は「入力欄に入力」（F1）。インポートは入力欄に自動入力するだけで、提出後の保存・メール・一覧・出力が同じ（0306 大会デッキ登録編集）。マイデッキの取得（F2）は、デッキビルダーという別のシステムで作ったデッキを取り込み、取得できる条件（フォーマットの設定・マイデッキの有無）が増えるので分けたまま
- 外部大会デッキの登録のしかた（画面で1件ずつ／CSV）は、処理が違う（CSVは存在しないタグ名を読み飛ばす、枚数の検証が違う）が、この通しでは区間S1の細部なので、代表は画面入力にして、CSVはUDK-01に任せる（因子から外した。まとめた水準ではなく範囲外の扱い）
