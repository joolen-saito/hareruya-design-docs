# 店頭買取の業務フロー全体（UTH-03）

IPA「高信頼化ソフトウェアのための開発手法ガイドブック」(2010) の表6-9〜6-11と同じ手順で作る（`店頭買取/matrix_UKA-01/` と同じ形）。

1. 因子・水準表: `fl_table.tsv`。お客様と店舗チームの選択、買取品の違い、業務フローの分岐を因子にし、設計書または業務フローの文を根拠に持つ
2. 禁則表: `prohibitions.tsv`。ありえない組み合わせ
3. 組み合わせテストマトリクス: `matrix.md` / `matrix.tsv`。`build_matrix.py` が作る。1行が「お客様の持ち込み・受付から、査定、出金、買取成立、入庫、店頭陳列・棚戻しまで通す1回の試験」になる
4. 例外の差し込み表: `exceptions.tsv`。エラー・中断・全キャンセル（★）は、正常な値と組み合わせず、条件に合う行へ1つずつ差し込む

## 範囲

- 業務フロー06（店頭買取。新フロー）・07（店頭買取 tobe）の全体。お客様の持ち込み・受付 → 本人確認（受付で身分証をコピー、査定端末で身分証をスキャン）→ 査定 → 査定表印刷・ダブルチェック → 査定結果の確認 → 出金（レジの出金と端末取引ID、または経理の払い出し）→ 買取成立 → 未登録在庫の実在庫登録 → 入庫（15時の自動入庫、または手動入庫）→ 店頭商品／通販商品の振り分け → 店頭商品は在庫移動・バーコード・陳列、通販商品は戻し作業（仕入作業）
- 通る買取のステータス：査定前 → 査定中 →（査定中断 → 査定再開）→ 買取成立（または経理払い出し待ち → 買取成立）→ 未登録在庫あり／入庫待ち → 入庫済み。全キャンセルは査定中（査定再開）→ 買取キャンセル
- 待ちの状態は切らない。区間の境目として `../scenario_list.md` の区間の表に書く：経理の振込（経理払い出し待ち）・商品マスターの登録（未登録在庫あり）・15時の入庫（入庫待ち）
- 一部キャンセルはフェーズ2で見送り（`functions/phase2_specs.json` 0205-M06-03・0506-A06-14）。因子に入れない
- 細部（申込画面の入力エラーの全件、査定表の追加方法ごとの結果、買取詳細の権限、戻しリストの全エラーなど）は区間の既存シナリオ（UKA・UMG・USM・UZK・UMB）とそのマトリクスに任せる。この通しは、つなぎ目で値が引き継がれるか、パターンで流れが変わるところを確かめる

## 因子にしなかったもの

| 項目 | 扱い | 理由 |
|---|---|---|
| 全キャンセル（査定結果確認でお客様が全部断る） | 例外EX17 | その時点で買取が終わり、出金・入庫・陳列・戻し作業へ進まない。正常な値と組むと行が成り立たない（全因子の水準を通せなくなる）ので、条件に合う行へ差し込む |
| 一部キャンセル | 対象外 | フェーズ2で見送り |
| 経理対応が必要な理由（高額な場合・レジの金額が足りない場合） | まとめる（H2） | 理由を端末で入力する項目が無く、どちらも「経理払い出し待ち」ボタンを押すだけ（0601 書類確認：経理払い出し待ちの状態ID 10。送る内容は状態と明細で、理由は無い） |
| 申込者の国（Japan／Japan以外） | 因子にしない | 申込画面の入力項目の出し分けだけが違い、査定・出金・入庫以降は変わらない。出し分けは `店頭買取/matrix_UKA-01/` で確かめる。この通しでは国内（Japan）で通す |
| ブラックリストに該当する会員登録 | 因子にしない | 会員が作られず申込だけが登録される分岐は申込の中で閉じる。`店頭買取/matrix_UKA-01/` のA4 |
| ダブルチェック者の入力の有無 | 因子にしない | 入力の有無は買取成立の条件ではなく、買取詳細への表示だけ（0601・0205）。通しでは入力して通し、買取詳細に出ることを確かめる。入力エラーはUMG-08・`店頭買取/matrix_UKA-01/` |
| 買取価格0円の商品 | 因子にしない | 業務フロー06の1-11は「買取情報として残らない」と書くが、設計書にも新実装にも対応する処理が見つからない。判断待ち（`../scenario_list.md`） |
| 管理者取消 | 因子にしない | 業務フロー06・07に無い（設計書0205のステータス変更。UKA-10） |
| 本人確認 | 必須の手順として全行に入れる | 依頼者の指示「買取の場合は本人確認証明が必要」（2026-11-05）。書類の種類は下の「まとめた水準」。証明が無い場合（その受注の両面の画像が端末に無い）は例外EX5・EX6・EX7 |

## まとめた水準（2026-11-05 依頼者決定「種類別のフローや処理が変わらないならまとめて」）

| 因子 | まとめた水準 | 代表 | 根拠（変わらない理由） |
|---|---|---|---|
| 本人確認書類の種類（因子にしない） | 自動車運転免許証・パスポート・健康保険被保険者証・外国人登録証明書・住民基本台帳カード・学生証、会社員証・身体障害者手帳（0601の7種） | 自動車運転免許証 | `店頭買取/matrix_UKA-01/README.md` の「まとめた水準」と同じ。0601「身分証明書種別とID」で、どの種類も同じ身分証スキャン画面・同じ「本人確認更新」。0506 A06-13は証明書IDがマスタに無いときのエラーだけで、種類で処理を分けない |
| G 買取品の売り先（店頭商品） | 買取価格1円〜250円以下のプレイド（ストレージ等）／250円以上（ショーケース品）／サプライ | 店頭商品（G2） | 06の1-11・07の1-9が分けるのは物理の保管先で、システムの処理（買取商品の確認 → 在庫移動・振替 → バーコード → 店頭陳列）は同じ。価格帯・サプライの表の出し分けは `店頭買取/scenario_list.md` のUKA-06。ちょうど250円は設計書にも新実装にも定めが無く判断待ち |
| H 出金の方法（経理の理由） | 高額な場合・レジの金額が足りない場合 | 経理に振込を頼む（H2） | 上の表のとおり、理由を入力する項目が無い |

分けたままにしたもの：
- 買取を行う店舗（E）：流れ・処理は同じだが、合意書・買取証明書の店舗の住所（0506 買取アプリ用ログイン「ログイン者の所属店舗の住所」を査定端末が帳票に設定）、入庫先のEC在庫、戻しリストの棚番号（本店のみ。0205 戻しリストPDF「買取店舗が本店の場合のみ必要」）が変わる。担当者は自分の所属店舗の査定情報しか取得できない（0506 店頭買取情報取得）ので、担当者の所属店舗は買取店舗と同じで、別の因子にはしない
- 買取品の中身（F）：個別入力と金額指定は、買取成立のあとの結果（未登録在庫あり）が同じだが、査定端末の操作・必須項目が違う（個別入力は5項目すべて必須、金額指定は金額の選択と枚数だけ）ので分けた（`店頭買取/matrix_UKA-01/` と同じ）
- 入庫のしかた（J）：15時の自動入庫・入庫済みボタン・在庫変更CSVは、買取のステータスの変わり方が違う（在庫変更CSVは買取のステータスに触れず、入庫待ちのまま15時のバッチの対象に残る）ので分けた

## 禁則（5件）

業務フロー06・07の図で、「戻し作業」へ進むのは通販商品の枝だけであることによる（X1〜X4）。07には手動入庫が無いこと（X5）。いずれも業務フローの文または図の線を根拠に持つ。設計書の画面・APIには、店頭商品と通販商品の組み合わせを制限する記述は無い（振り分けは担当者の判断。システムを触らない）。

## 実装と設計書で確かめたこと

- 新実装・設計書とも、買取成立の更新を受けると、個別入力商品が無ければ入庫待ち、有れば未登録在庫あり（履歴は2件）。経理払い出し待ちを受けると経理チームへ振込依頼のメール（件名「店頭買取振込依頼 【査定ID: XXXXX】」）を送る（0506 店頭買取情報更新。`店頭買取/scenario_list.md` の確かめ済みの事実）
- 端末取引ID（スマレジの取引区分が出金の取引ID）は買取成立のときだけ送る。経理払い出し待ち・買取キャンセルは送らない。EC側は必須にしない（端末が必須にする）。スマレジの出金取引との突き合わせはECに無い（0601・`MTGバイヤー/scenario_list.md` のUMG-05）
- 経理が「経理払い出し済」を押すと、確認ダイアログ「経理払出し済みに変更します。よろしいですか？」のあと、「保存しました」が出て買取成立になり、続けて入庫待ちまたは未登録在庫ありになる（0205 買取詳細 M06-03-MSG-012・MSG-004）
- 15時の自動入庫は入庫待ちだけが対象。入庫済みボタンと15時のバッチは二重に入庫しない（`店頭買取/scenario_list.md` UKA-05・UKA-09）
