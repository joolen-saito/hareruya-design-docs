# フロント注文から出荷まで：通しシナリオ（L2）

お客様がフロントで注文し、通販チームが受注を確認し、入金を確認し、在庫を引き当ててピッキングし、出荷して、お客様に出荷完了メールが届きポイントがつくまで（店頭受取・スムーズ店頭受取・店頭PCは、店舗がスタック用紙でピックし、引き渡すまで）を、1本で通す。通販（UTS）・店頭受取受注管理（UOR）・在庫管理（UZK）・ポイント（UPT）・スマレジ連携（USM）・外部連携（UEX）に分かれている区間を、つなぎ直したもの。今のシナリオは書き換えず、区間として参照する。この一覧の役割は、区間のつなぎ目で値（注文番号・金額・在庫・受注の状態・ポイント）が正しく引き継がれ、お客様の画面・メール・通販チームの画面に出ることと、パターン（支払方法・配送方法・商品の状態・入金の確認・欠品など）で流れが変わるところを確かめること。区間の中の例外・境界の細部は、今のL2とそのマトリクスに任せる。

待ちの状態（入金待ち・入荷待ち・発売日・取り置き期限）があっても切らない。待ちは「区間の境目」として書き、そこで確かめる状態を期待値にする。

## 利用者と目的

- 利用者（担当の順）：お客様（会員）→通販チーム（受注の確認・入金の確認・出荷指示・ピッキング・出荷実績の取り込み）→店舗チーム（店頭受取系のスタック用紙・ピック・引き渡し）→トレードチーム（入荷・入庫の承認。入荷待ちの商品）→SPLINKS（決済）→スマレジ（ポイント）→メール
- 目的：お客様が選んだ支払方法・配送方法・ポイントの注文が、受注として正しく確認され、在庫が引き当てられ、入金が確認され、ピックされて、出荷（引き渡し）され、出荷完了メールとポイントがお客様に届く。途中で入金待ち・入荷待ち・発売日の待ちがあっても、つなぎ目で値が変わらない

## 起点・終点

| 項目 | 内容 |
|---|---|
| 起点 | 会員のお客様が、フロントで商品を探し始める（入荷待ちの行は、在庫0の商品で「入荷時に通知」を押す） |
| 終点（宅配） | 出荷実績の取り込みで受注が「出荷完了」になり、出荷日・送り状No.が入る。お客様に出荷完了メールが届き、マイページの処理状態が「出荷完了」になる。付与額（（小計−使用ポイント）×付与率。0以下は0）が正なら保有ポイントとポイント履歴に出てスマレジの会員ポイントも合う。0（全額ポイント支払いなど）なら履歴は増えない |
| 終点（店頭受取・店頭PC） | 引き渡しで、元の受注が「引き渡し済み」になり、スマレジの取引から新しい受注が「出荷完了」で作られる（スムーズ店頭受取は元の受注が「出荷完了」）。店頭PCは店頭注文番号がモニターから消える |
| 途中で終わる場合（例外） | 入金されないまま期限が過ぎてキャンセル、お客様の依頼で出荷前に取り消して返金、取り置き期限の超過でキャンセル（`matrix_UTH-05/exceptions.tsv`）。出荷完了のあとの返品は範囲外 |
