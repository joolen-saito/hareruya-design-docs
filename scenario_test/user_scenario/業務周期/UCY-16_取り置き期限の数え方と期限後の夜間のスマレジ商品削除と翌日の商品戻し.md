# UCY-16 取り置き期限（注文日を含めて1日・7日・14日）の数え方と、期限後の夜間のスマレジ商品削除（4時）・翌日の商品戻しをつなげて確かめる

| 項目 | 内容 |
|---|---|
| 利用者 | 店舗チーム（期限超過のチェック・キャンセル・引き渡し・商品戻し）→（通販チーム。SPLINKSの請求のキャンセル）→ スマレジ商品削除のバッチ（システム。試験では手で起動する）→ 店舗チーム（スマレジの商品一覧で確かめる）。お客様（注文・来店） |
| 目的 | 取り置き期限を、注文日を1日目として数えて、最終日の分は受け取れ（期限内）、最終日の翌日の分は期限超過になることを、注文日の違う受注で確かめる。期限超過の受注は店舗チームが「キャンセル」にし（日付が変わっただけでは変わらない）、在庫・使用ポイントが戻る。キャンセルした受注・引き渡した受注のスマレジの商品は、夜間（毎日4時）のバッチで削除される。バッチの前にキャンセルした分は削除され、バッチの後にキャンセルした分は次の回まで残る。店頭PCの分の商品は翌日にまとめて戻す |
| 種類 | 正常（代表の1本）。組み合わせ表は作らない（`../scenario_list.md` の L3 の欄にそう書いてある。取り置き期限の日数・支払方法は業務フローの区分で、受注の作り方と期限の日数だけが変わる）。L3で変わるところ7本 |
| マトリクスの行 | 組み合わせ表の無いシナリオ。代表＝V1（店頭受取（本店）・店頭支払・7日間）。V2〜V7 は「L3で変わるところ」 |
| もとのシナリオ | SCN-ORDER-002・004・006・008（区間：UOR-04・UOR-05・UOR-08→UOR-09）。UOR-12（期限の前にお客様が取り消す場合は期限超過ではなく依頼による取り消し）は別 |

## 前提

- 共通の決まり：`../L4を流すときの共通の決まり.md` を先に読む（試験データの名前にシナリオIDを付ける・共有の設定は元に戻す・バッチの起動・店舗の読み替えなど）
- 取り置き期限の数え方（業務フロー05。1-5・2-5・3-5・4-6）：注文日を1日目と数える。期限は店頭受取・店頭受取（支店）7日間、スムーズ店頭受取14日間、店頭PC 1日間。最終日の23:59までは受け取れる。したがって、実行日を基準にして、注文日が「実行日の6日前」の店頭受取は最終日（7日目。期限内）、「実行日の7日前」は期限超過（8日目）。スムーズ店頭受取は、13日前が最終日、14日前が期限超過。店頭PCは、実行日（当日）が最終日、前日が期限超過。「最終日の23:59に来店／翌日0:00に来店」は、時刻を待たず、注文日を変えた受注で確かめる（日付の判定は注文日だけで、時刻は見ない）
- 期限超過のチェックと「キャンセル」への更新は、店舗チームの作業（業務フロー）で、日付が変わっただけでは受注の対応状況は変わらない。新実装の注文画面の案内「期間超過で自動キャンセルとなります」は、キャンセルを行う処理が見当たらず、設計書・業務フローと食い違う（`../scenario_list.md` に記録済み）。この試験は、受注が自動でキャンセルされないことを確かめる
- バッチは時刻を待たず手で起動してよい（定時は毎日4時。起動のしかたは根拠の欄のファイル）。バッチは環境の中の対象を全部処理するので、ほかの試験の受注も一緒に削除される。合否は、この試験の受注のスマレジの商品が消える・残ることで付ける。一度に処理するのは先頭100件まで（古い受注から）なので、この試験の受注が入らなければ、起動を繰り返す。スマレジの商品の削除そのものは別の処理が順に行うので、起動の直後でなく、少し待ってから確かめる（待ち時間の期待値は置かない）
- 試験用の古い日付：取り置き期限を過ぎた受注は、試験で作った受注に限り、開発環境で注文日を書き換えて用意する（共通の決まり）。書き換えるのは、スマレジの商品が登録されたあと（UOR-01 の手順6のあと）にする。スマレジの商品を登録する再連携は、注文日が起動の30分前以降の受注だけを対象にするので、先に書き換えると商品が登録されない
- システムの外で済んでいること：本店と支店にスタック用紙のプリンタ（30秒おき）・タブレットがある。スマレジの店舗が登録済み。お客様のスマレジの会員とECの会員が紐付いている（V1 の最終日の受け取りに使う）。通販チームがSPLINKSの管理画面を使える（V3〜V5）
- 用意するデータ（試験用の値。設計書の値ではない。流すときは名前の後ろにシナリオIDを付ける）
  - 店舗の読み替え：流す前に、開発環境の既存の店舗から、支店の行（V2）で使う店舗を1つ選び、店舗IDと画面に出る名前を控える（以下「支店A」）。店舗は新しく作らない。本店は店舗ID 1（画面によって「Hareruya」「トーナメントセンター 東京」と出る）
  - 会員：試験 十六（メールアドレス `ucy-16@example.test`、国内（東京都）の住所を登録済み、スマレジの会員作成済み）
  - 商品：グッズ「取り置き期限試験グッズ UCY-16」（商品コード「UCY16-G01」、販売価格 1,000円、公開）。グッズ商品CSVで登録する（UPR-04 の手順3〜5と同じ）。本店の EC-CUBE 在庫に 30点、支店Aの EC-CUBE 在庫に 10点を、在庫変更CSVの入庫で入れて承認する（UZK-01 の手順3〜6と同じ）
  - 店舗チームの担当者（管理画面で本店・支店Aの受注を編集できる権限を持つ）。運用の担当者（バッチを手で起動でき、試験で作った受注の注文日を書き換えられる）。通販チームの担当者
- 画面の名前・文言は新実装の表示で書く。設計書の文言と違えば、期待値は設計書の文言にし、新実装の文言が出たら不合格として記録する

## 判断待ち

開いた項目は無い。確かめたこと（記録）：

1. 全額ポイント支払いのスムーズ店頭受取（V5）は、新実装も本店のスムーズ店頭受取でポイント欄を出す（src/Eccube/Resource/template/default/Shopping/index.twig 123行。2026-11-27 に確かめた）ので作れる。`../scenario_list.md` の L3 欄と「決着した論点」の行15にある「作れない」という書き方は古い。業務横断の禁則（UXB-16 の X34・X46）の古い理由は、依頼した側が判断する
2. UOR-04 の前提は「注文日が8日以上前」と書くが、この試験は期限の境目を確かめるので「7日前」を期限超過（8日目）にした。UOR-04 の「8日以上前」も期限超過なので矛盾しない
3. 取り置き期限の「最終日の23:59に来店／翌日0:00に来店」は、受取の画面の操作が時刻で変わらない（日付の判定は店舗の運用）ので、注文日を変えた受注と、受注一覧の注文日の見比べで確かめる。来店の時刻そのものは試験に使えない
4. 店頭PCの注文のスマレジ商品（V6）は、UOR-06 の手順4で登録されるが、設計書に削除の対象としての明示は無い（0405 B05-05 は「スマレジ商品コードが存在する」受注を対象にする）。新実装は、スマレジ商品コードのある受注を状態だけで拾う（店頭PCも含む）

設計書との食い違い（起票しない）：

- 新実装の注文画面の案内「期間超過で自動キャンセルとなります」は、設計書・業務フロー05（店舗の人がキャンセルにする）と食い違う（`../scenario_list.md` に記録済み）
- スマレジ商品削除の対象の状態：設計書の本文は「キャンセル」「引き渡し済み」、検索条件欄は「キャンセル」「出荷完了」。新実装は引き渡し済み・出荷完了・キャンセルの3つ（`../scenario_list.md` に記録済み。UOR-09 の依頼者決定どおり3つを対象にする）
