# UCY-01 店頭PCで夜に注文した番号が0時をまたぎ、翌日に受け取りに来たときの扱いを確かめる

| 項目 | 内容 |
|---|---|
| 利用者 | お客様（店内のPC）→ 店舗チーム（スタック用紙・ピック・管理画面・店頭モニター）→ 店頭注文番号初期化のバッチ（システム。試験では手で起動する）→ 店舗チーム（期限超過のキャンセル） |
| 目的 | 店頭PCの注文がピック完了になり、店頭モニターに店頭注文番号が出たまま0時を迎えたとき、0時のバッチで前日までの店頭注文番号が全件消え、受注は残る（お客様が示す前日の番号から受注は引けない）ことを確かめる。0時にキャンセルになるわけではなく、店舗チームの期限超過チェック（注文日を含めて1日間）で受注の対応状況を「キャンセル」にして初めてキャンセルになり、商品は翌日にまとめて戻される。0時の後に入った店頭PCの注文には1番から振られる |
| 種類 | 正常（代表の1本）。ほかの条件は「L3で変わるところ」（このシナリオには組み合わせ表が無い。scenario_list.md の L3 欄の条件を、表外の具体例として書く） |
| マトリクスの行 | 組み合わせ表は無い（表外の具体例。代表＝本店・注文が23時台・受け取りが0時の後に来ない／来てもスタック用紙の番号から引けない） |
| もとのシナリオ | 区間：UOR-06→UOR-11→UOR-07 または UOR-08（UOR-08 は期限超過のキャンセルまで）。業務フロー05の4-5〜4-9・4-10〜4-14。0405 店頭注文番号初期化 |

## 前提

- 共通の決まり：`../L4を流すときの共通の決まり.md` を先に読む（試験データの名前にシナリオIDを付ける・共有の設定は元に戻す・バッチの起動・店舗の読み替えなど）
- バッチは毎日0時に動く設計（0405 B05-03）だが、時刻は待たず、手で起動する（起動のしかたは「根拠」の欄。2026-11-26 の決まり）。「0時の前」は、バッチを起動する前、「0時の後」は、バッチが終わったあとと読み替える
- バッチは本店・支店の店頭注文番号を全部消すので、ほかの試験の店頭注文番号も一緒に消える（記録）。合否は、この試験の注文の店頭注文番号・受注で付ける。ほかの試験が店頭注文番号を使っている間は流さない（UOR-11 と同じ）
- 起点の注文：UOR-06 の T02 の終点（本店・店内アカウントで「シナリオ試験カードA」を数量2で注文し、スタック用紙でピックして「ピック完了」にし、店頭モニターにTC注文番号が出ている。注文金額合計（税込）・ご注文番号・店頭注文番号を控える。名前の後ろに UCY-01 を付ける）
- 注文日の書き換え：夜に注文した注文にするため、起点の注文の注文日時を、実行日の前日の23:30:00に書き換える（試験で作った注文だけ。開発環境のデータの書き換え。2026-11-26 の決まり）。注文日を含めて1日間の取り置き期限は、注文日の日付で数える（UOR-08 の前提と同じ）。画面の日時で確かめる
- 画面の名前は新実装の表示で書く（受注情報検索・受注情報編集・店頭注文番号札管理・店内注文モニター）
