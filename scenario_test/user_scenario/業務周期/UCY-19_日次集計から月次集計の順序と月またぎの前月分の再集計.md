# UCY-19 日次集計→月次集計の順序と月またぎ（月初の前月分の再集計）を確かめる

| 項目 | 内容 |
|---|---|
| 利用者 | 日次集計・月次集計のバッチ（システム。試験では手で起動する）→ 運用の担当者（バッチを起動する）→ 店舗統括・顧客戦略チーム（分析・集計の日別集計・月別集計の画面） |
| 目的 | 毎日、前日に更新された受注の注文日（過去日を含む）と前日自身が日次集計で洗い替えられ、そのあとで、洗い替えた日が属する月の月次集計が日次の合算で更新されることを確かめる。月次集計は日次集計が先に更新されていないと合わない。前月の受注が前日に更新されたときは、前月の日次・月次が再集計される。日付・月を指定して流し直せる |
| 種類 | 正常（代表の1本）。組み合わせ表は作らない（`../scenario_list.md` の L3 の欄にそう書いてある。順序・月またぎ・取りこぼしの条件は別々で、効き合う組が無い）。L3で変わるところ5本と例外2件 |
| マトリクスの行 | 組み合わせ表の無いシナリオ。代表＝V1（前月の受注が前日に更新され、日次→月次の順に流す）。V2〜V6 と例外 E1・E2 は「L3で変わるところ」 |
| もとのシナリオ | なし（周期の観点で足した。区間：UAN-03・UAN-11）。日次・月次集計のバッチは、バッチ設計書（0402〜0417）に載っていない |

## 前提

- 共通の決まり：`../L4を流すときの共通の決まり.md` を先に読む（試験データの名前にシナリオIDを付ける・共有の設定は元に戻す・バッチの起動・店舗の読み替えなど）
- 日次・月次集計のバッチの実行時刻・順序の定めは、設計書にもリポジトリにも無い（`../scenario_list.md` の決着：記録だけ。順序は「日次→月次」で確定。時刻は設計の不足）。時刻は待たず、手で起動する（起動のしかたは根拠の欄のファイル）。この試験は、日付を付けずに起動する形（毎日の定時の形）と、日付・月を指定して流し直す形を確かめる
- 日付を付けない起動は、前日に更新された受注の注文日と前日自身を洗い替える。試験の受注の更新日時が「前日」になるよう、試験で作った受注に限り、開発環境で更新日時と注文日を書き換えて用意する（UAN-03 の手順3と同じ）
- バッチは環境の中の対象を全部処理する。ほかの試験の受注も一緒に洗い替わる。合否はこの試験の取引由来の値（流す前に控えた値からの増え方）で付け、対象日数・対象月数は記録にする
- 用意するデータ：UAN-03 の前提と同じ（担当者・店舗＝本店・商品「分析試験グッズ UAN-03」の考え方。この試験は名前を変える）
  - 担当者：店舗統括（日別集計・月別集計を使えるメンバー。所属店舗は本店＝店舗ID 1）。通販チームの担当者。登録担当と在庫の承認者。運用の担当者（バッチを起動でき、試験で作った受注の日付を書き換えられる）
  - 店舗：本店（店舗ID 1）。店舗は新しく作らない
  - 商品：グッズ「周期集計試験グッズ UCY-19」（商品コード「UCY19-G01」、NM の1規格、販売価格 15,000円、本店で公開）。在庫変更CSVで 20点、仕入単価 6,000円（UAN-03 の P2 と同じ手順）
  - 会員：「試験 十九」（メールアドレス `ucy-19@example.test`、本会員、国内（東京都）の住所を登録済み）
  - 取引：商品を数量2（商品合計 30,000円・送料0・手数料0。受注時原価 6,000×2＝12,000円）の通販の注文1件。総売上 30,000・原価 12,000・粗利益高 18,000・販売点数 2・取引数 1
  - 試験日（S）：流す日。月の3日以降に流す（日付を書き換える行があるため）。「前月15日」は、試験日の前の月の15日
- 画面の名前・文言は新実装の表示で書く。完了の表示は設計書に無いので新実装の文言（UAN-03 の手順4と同じ）

## L3で変わるところ（組み合わせ表は無い。確かめを5本に分ける。1回ずつ流す）

手順の番号は上の「操作の流れと期待値」。行ごとに別の受注（商品名の末尾「UCY-19 V2」など）を用意する。

| 行 | 条件 | 変わるところ |
|---|---|---|
| V1 | 前日に前月の受注が更新された・日次→月次の順 | 代表の行 |
| V2 | 月中（前日が今月）で、今月の過去日の受注が更新された | P4：注文日を「試験日の2日前」（同じ月）に、更新日時を「前日」に書き換える。手順2：再集計対象日に、注文日（2日前）と前日が含まれる。手順3：日別集計の注文日の行が増える。手順4：再集計対象月は今月だけ（M＝1）で、この試験の受注の分は今月だけで、前月は含まれない（前日が今月なので。ほかの試験の受注の更新で前月が含まれることがあるので、対象月数は記録）。手順5：月別集計の今月の行が増え、前月の行は変わらない。手順6：今月の合計と一致する |
| V3 | 月初（前日が前月の末日）に流す | **実施不可（流せない）**（試験日が毎月1日のときだけ流せる）。試験日が1日のときは、前日（前月の末日）自身が検知日として必ず洗い替えられるので、手順2の再集計対象日に前月の末日が含まれ、手順4の再集計対象月に前月が含まれる（前月分の日次・月次が再集計される）。今日が1日でなければ、時計を動かす手段が無いので流さず、V1（前月の受注が前日に更新された）で前月の再集計を確かめる |
| V4 | 日次が止まったまま月次が動く | 手順2を行わず、手順4（月次）だけを起動する。期待値：月別集計の前月の行は、増えない（月次は日次集計テーブルの合算のため、日次が先に更新されていないと、この試験の受注の分が合算に入らない）。続けて手順2（日次）を起動し、もう一度手順4（月次）を起動すると、手順5と同じ値になる（順序は日次→月次）。月次を先に流しただけでは、エラーにならずに完了の表示が出る（「月次集計テーブル更新が完了しました。対象月数: M」）が、値は合わない |
| V5 | 日付・月を指定して流し直す | 手順2のかわりに、日次を「前月15日（Y-m-d）」を指定して起動する。期待値：「日次集計テーブル更新が完了しました。対象日: 前月15日」（指定日だけ。前日は洗い替えない）。手順3：前月15日の行が増える。手順4のかわりに、月次を「前月（Y-m）」を指定して起動する。期待値：「月次集計テーブル更新が完了しました。対象月: Y-m」。手順5・6：V1と同じ値。この場合は P4 の更新日時の書き換えは要らない |
| V6 | 更新日時が前日より前（取りこぼし） | P4：更新日時を「前々日」にする（前日にしない）。手順2：再集計対象日に前月15日は含まれない（検知は前日1日分だけ）。期待値：手順3・5：前月15日・前月の行は増えない（日付を付けない起動では取りこぼす）。続けて V5 のとおり日付・月を指定して流し直すと、増える（復旧）。バッチが止まっていた期間の変更は、日付指定で復旧する前提（新実装のコメント） |

## 判断待ち

開いた項目は無い。確かめたこと（記録）：

1. 日次・月次集計のバッチは、バッチ設計書（0402〜0417）に載っていない。実行時刻の定めが無く、順序は新実装のコメントだけが根拠（日次→月次。`../scenario_list.md` の決着：記録だけ。依頼者への確認は要らない）
2. 月初の実行で前月が再集計されるのは、前日（検知日）が前月の末日になるため。時刻（暦）を動かさないので、この試験は前月の受注を前日に更新したものとして用意して確かめる（V1）
3. 完了の表示は設計書に無く、新実装の文言を期待値にした（UAN-03 の手順4と同じ）

設計書との食い違い（起票しない）：新しいものは見つからなかった（バッチ設計書に載っていないことは `../scenario_list.md` に記録済み）。
