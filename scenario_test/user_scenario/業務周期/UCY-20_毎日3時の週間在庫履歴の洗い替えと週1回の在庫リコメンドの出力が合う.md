# UCY-20 毎日3時の週間在庫履歴の洗い替えと、週1回の在庫リコメンドの出力が合う

| 項目 | 内容 |
|---|---|
| 利用者 | 週間在庫履歴更新のバッチ（システム。試験では手で起動する）→ 運用の担当者（バッチを起動する）→ トレードチーム・店舗の担当者（在庫一覧の「在庫リコメンドCSV出力」で週1回確かめる） |
| 目的 | 毎日3時のバッチが、1週間前〜11週間前の各時点の在庫数を、商品コード・店舗ごとに、前回の結果を全部消して作り直す（洗い替え）。日が進むと、時点（n週間前）と履歴の位置関係が変わるので、週1回出す在庫リコメンドCSVの一週前〜一月前在庫が、その日のバッチの結果に合う。前回の値は残らない。設計書はEC-CUBEとスマレジの在庫の合算とするが、新実装はスマレジ在庫の取り込みが未実装でEC-CUBE在庫だけ（食い違い。期待値は設計書どおりで、新実装が違えば不合格として記録する） |
| 種類 | 正常（代表の1本）。組み合わせ表は作らない（`../scenario_list.md` の L3 の欄にそう書いてある。因子は在庫区分と時点だけ）。L3で変わるところ3本 |
| マトリクスの行 | 組み合わせ表の無いシナリオ。代表＝V1（日が進む前後の2回、バッチを手で起動して、在庫リコメンドCSVの値の変わり方を見る）。V2〜V4 は「L3で変わるところ」 |
| もとのシナリオ | なし（周期の観点で足した。区間：UZK-06（起点の在庫リコメンド）・UAN-13（バッチの中身）。業務フロー12の2-1・2-2） |

## 前提

- 共通の決まり：`../L4を流すときの共通の決まり.md` を先に読む（試験データの名前にシナリオIDを付ける・共有の設定は元に戻す・バッチの起動・店舗の読み替えなど）
- バッチは時刻を待たず手で起動してよい（定時は毎日3:00。起動のしかたは根拠の欄のファイル）。バッチは環境の中の在庫の全データを扱い（前回の結果を全部削除してから登録し直す）、ほかの試験の在庫も一緒に作り直される。合否はこの試験の商品の行の値で付け、対象数は記録にする
- 日が進むことは、時計を動かす手段が無いので、試験で作った在庫変動履歴の登録日を、2日古い日に書き換えて表す（試験で作った履歴だけ。開発環境のデータの書き換え。UAN-13 の手順5と同じ考え方）。S は流す日（バッチが時点の判定に使うのは、画面の登録日ではなく、履歴の記録上の作成日時で、2つは別の値なので、両方を同じ日時に書き換える）
- 用意するデータ（試験用の値。設計書の値ではない。名前の後ろにシナリオIDを付けて作る）
  - 担当者：登録担当と在庫の承認者（別の担当者）。商品管理・トレードチームの担当者（在庫一覧・在庫リコメンドCSVを使える）。運用の担当者（バッチを起動でき、試験で作った履歴の登録日を書き換えられる）
  - 店舗：本店（店舗ID 1）。店舗は新しく作らない
  - 商品：グッズ「在庫履歴試験グッズ UCY-20」（商品コード「UCY20-G01」、販売価格 3,000円、本店で公開）。グッズ商品CSVで登録する（UPR-04 の手順3〜5と同じ）。在庫は 0 から始める
  - 在庫の履歴（本店。変更後の在庫数を右に書く。S の何日前に書き換えるかを「登録日」に書く）

|---|---|---|---|
| EC-CUBE | 入庫 +20（UZK-01 の手順3〜6。仕入単価 300円） | 20 | 80日前 |
| EC-CUBE | 廃棄 -5（UZK-15 の手順2〜4。廃棄(破損)） | 15 | 13日前 |
| EC-CUBE | 入庫 +3（UZK-01 の手順3〜6） | 18 | 3日前 |
| スマレジ | 入庫 +10（UZK-01 の手順3〜6を、在庫場所「スマレジ」で） | 10 | 50日前 |

  - 履歴の日が、時点の日（7日・14日・21日・28日…前）と同じにならない日にしてある（時点の判定で、境界の日にならないため）。日が2日進んだあと（登録日を2日古くしたあと）は、80→82日前・13→15日前・3→5日前・50→52日前
  - 取得の決まり（0402 B02-07）：在庫ごと（商品コードごと・店舗ごと・在庫区分ごと）に、n週間前（S の 7×n 日前）の時点で最新の在庫変動履歴の在庫数を取得する（n＝1〜11）。EC-CUBE とスマレジの在庫は、店舗ごとに合算して保存する
- 手で数えた期待値（本店。n週間前の時点＝S の 7n 日前より前の最新の履歴の在庫数。在庫リコメンドCSVに出るのは、現在庫・一週前在庫・二週前在庫・三週前在庫・一月前在庫（4週間前）の5列）

| 時点 | 日が進む前（S） | 日が進んだ後（登録日を2日古くしたあと） |
|---|---|---|
| 現在庫 | 28（EC-CUBE 18＋スマレジ 10） | 28（履歴の日付に関係なく変わらない） |
| 一週前在庫（7日前） | EC-CUBE：13日前の履歴＝15、スマレジ：10 → 25 | EC-CUBE：15日前の履歴＝15、スマレジ：10 → 25 |

## L3で変わるところ（組み合わせ表は無い。確かめを3本に分ける。1回ずつ流す）

手順の番号は上の「操作の流れと期待値」。

| 行 | 条件 | 変わるところ |
|---|---|---|
| V1 | 日が進む前後で洗い替えられる | 代表の行 |
| V2 | 在庫リコメンドを3時台（バッチの実行中）に出す | **実施不可（流せない）**：バッチの全件削除と再登録はトランザクションの中で行うので、途中の空の状態は見えない（新実装 src/Eccube/Service/Product/BatchUpdateWeeklyStockHistoryAction.php）。バッチの実行中にCSVを出して途中の状態を作る手段が無い。期待値だけを記録する：実行中にCSVを出しても、前回の完成した結果（または終わったあとの結果）のどちらかが出て、空の行・途中の行は出ない |
| V3 | バッチが失敗した翌日の出力 | **実施不可（流せない）**：バッチを画面の操作で失敗させる方法が無い（UAN-13 のE1と同じ）。期待値だけを記録する：失敗した回は、集計できなかったメールが届く（0402 B02-07「エラーハンドリング」）。翌日の回が成功すれば、その日の履歴で洗い替えられ、リコメンドCSVも新しい値になる（前日の失敗の影響を残さない） |
| V4 | 20,000在庫ごとの処理で全件が入る | **実施不可（流せない）**：バッチは商品コードの順ではなく、在庫の行の番号の範囲を20,000ずつ処理する。在庫の行の番号は画面で見えず、境目（20,000件目・40,000件目）をまたぐ対象の在庫を画面で選べないので、全件が処理されることの確かめは流せない。商品コードの順で最後の商品がCSVにあるかだけで合否を付けない。期待値だけを記録する（0402 B02-07）：20,000在庫ごとにまとめて処理するが、全件が取り込まれ、行が欠けない |

## 判断待ち

開いた項目は無い。確かめたこと（記録）：

1. 週間在庫履歴の取得は、設計書がEC-CUBEとスマレジの在庫の合算とするのに対し、新実装はスマレジ在庫の取り込みが未実装でEC-CUBE在庫のみ（`../scenario_list.md` の食い違い。0402_*在庫*.html:1216-1217／新実装 `src/Eccube/Service/Product/BatchUpdateWeeklyStockHistoryAction.php:41-46`）。期待値は設計書どおり。新実装の値は、手順3・6のとおり記録する
2. 現在庫の列が、EC-CUBE とスマレジの合算か、EC-CUBE 在庫かは設計書の別添資料の例だけでは決まらない（UAN-13 の判断待ち3と同じ）。新実装の値を記録し、合わなければ記録する
3. 日が進むことは時計を動かせないので、履歴の登録日を古くして表した。判定の日付の境目（7の倍数の日）と履歴の日が重ならないよう、日を選んである

設計書との食い違い（起票しない）：週間在庫履歴更新のEC-CUBEとスマレジの合算（上の1。`../scenario_list.md` に記録済み）。
