## 前提

- 共通の決まり：`../L4を流すときの共通の決まり.md` を先に読む（試験データの名前にシナリオIDを付ける・共有の設定は元に戻す・バッチの起動・店舗の読み替えなど）
- システムの外で済んでいること：S3（保存先）・本番DBのスナップショット・一時的なDBの作成と削除・ステージング環境のDBとサーバは、バッチ用の環境（AWS）の機能で、ブラウザの画面の試験では確かめられない。この L4 の手順は、2つのバッチを起動できる環境（本番DBのクラスタの最新スナップショットを使える・S3に書ける権限がある・ステージングのDBとサーバがある・設定が済んでいる）で、運用の担当者が行う。そのような環境が無ければ、この L4 は「実施不可（流せない）」として記録する（環境依存。UAN-14 と同じ）
- 設計書の定時は、月次スナップショットが毎月1日1:00（0416 B16-06）、ステージングDB保守が毎月1日3:00（0416 B16-10）。時刻は待たず、手で起動する（起動のしかたは根拠の欄）。月初でない日に流しても、同じ処理になる。ファイル名の日付は実行した日になる（1日の日付にはならない。確かめるのは「実行した日の日付」）
- 開発環境の日付は動かさない。「本番DBの最新スナップショット」は設計書どおり日本時間04:00の日次のバックアップだが、試験ではその時刻を待たず、試験データを作ったあとにDBのスナップショットを新しく取り、それを最新にする（スナップショットを取る権限が無ければ、試験データが載らないので、この L4 は実施不可として記録する）
- 用意するデータ（試験用の値。設計書の値ではない。名前の後ろにシナリオIDを付けて作る）
  - 担当者：登録担当と在庫の承認者。在庫反映の権限のある人（棚卸の反映）。運用の担当者（2つのバッチの起動とスナップショットの取得ができる）。在庫チェックの担当（S3から取得できる）。開発・検証の担当者（ステージングの管理画面にログインできる管理者のアカウントを持つ。管理者は本番と同じアカウントでステージングにログインできる）
  - 店舗：本店（店舗ID 1。画面によって「Hareruya」「トーナメントセンター 東京」と出る）。在庫区分「EC-CUBE」
  - 商品：グッズ「月次試験グッズ UCY-14」（商品コード「UCY14-G01」、販売価格 3,300円、買取価格 1,000円、公開）。グッズ商品CSVで登録する（UPR-04 の手順3〜5と同じ。商品カテゴリは既存のものを選ぶ）。在庫は在庫変更CSVで本店の EC-CUBE 在庫に 10点（仕入単価 300円）入れる（UZK-01 の手順3〜6と同じ）
  - 会員：試験 十四（メールアドレス `ucy-14-a@example.test`）と試験 十四B（`ucy-14-b@example.test`）。ともに国内（東京都）の住所を登録済み。会員登録は UMB-01・UMB-02 と同じ。メールアドレスの末尾は、マスクしない社内・ベンダーのドメイン（根拠の欄）以外にする
- ステージングの状態の控え：流す前に、ステージングの管理画面の商品一覧で商品コード「UCY14-G01」を探す（無い。今のステージングは、この試験の前の本番の写し）。会員一覧で「試験 十四」を探す（無い）
- 画面の名前・文言は新実装の表示で書く（2つのバッチの完了の表示は、設計書が文言を定めないので新実装の文言）

## L3で変わるところ（組み合わせ表は無い。確かめを4本に分ける。1回ずつ流す）

手順の番号は上の「操作の流れと期待値」。

| 行 | 条件 | 変わるところ |
|---|---|---|
| V1 | 棚卸の反映が済んだあとにスナップショットを取る（代表） | 代表の行 |
| V2 | 棚卸の反映がスナップショットより後 | 準備のP3を、P4（スナップショット）のあとに行い、手順1・2・6・9を流す。期待値：ファイルとステージングの「UCY14-G01」の在庫は、反映の前の 9（スナップショットの時点の値）。本番の在庫は 8。設計書どおり、月初の1:00のファイルが前日の04:00のバックアップの時点なら、前日の04:00より後の棚卸の反映はファイルに入らない。04:00のバックアップの時刻自体は新しいスナップショットを手で取るので試験では確かめない（他層。`../scenario_list.md` の決着） |
| V3 | 保護対象のメールアドレスの会員はマスクしない | 本番相当のDBに、メールアドレスの末尾が「@hareruyamtg.com」「@joolen.com」「@ec-cube.co.jp」「@sai-net.jp」「@tam-tam.co.jp」のいずれかである会員が既にあれば、手順10で、その会員の氏名・メールアドレスはマスクされず本番と同じ。無ければ「実施不可（流せない）」として記録する（社内・ベンダーのアドレスで試験用の会員を新しく作ってメールを送ることはしない） |
| V4 | マスクの実行確認が無い | マスクの実行確認の指定を「yes」以外にして手順6を起動する（環境の設定を変えられる環境のとき）。期待値：マスクを行わずに、データベースの個人情報をダミー値で上書きし元に戻せないこと・ステージング環境であることを確認して確認の指定を付けて再実行することを求めるメッセージ「ERROR:」が出て異常終了する。今のステージングは変わらない（手順9のとおり商品は出ない）。一時リソースは削除される（異常終了時の後片付け）。設定を変えられない環境では「実施不可（流せない）」。流したあとは確認の指定を「yes」に戻して V1 の手順6〜11をやり直す |
| V5 | 1時のバッチの復元の待ち時間が足りない／スナップショットが1件も無い | 待ち時間は処理に固定で入っており画面・環境の操作で変えられず、スナップショットを無くすこともできないので、「実施不可（流せない）」として記録する（UAN-14 の E2 と同じ。新実装は待ちを30秒おき最大60分で確かめ、設計書の月次スナップショットは30分のスリープ。差は食い違いに記録） |
