# UXB-17 店頭受取と店頭PCの受注を、1回の取引でまとめて引き渡し、統合した新しい受注が各集計に出る

| 項目 | 内容 |
|---|---|
| 利用者 | お客様 → 店舗チーム → スマレジ → （バッチ）→ 店舗統括 |
| 目的 | 店頭受取の会員が店頭PCでも注文しており、両方をまとめて受け取ったとき、元の受注がすべて引き渡し済みになり、全ての明細（受注時原価を含む）を統合した新しい受注が1件、出荷完了で作られ、新しい受注の小計・合計がスマレジの取引の小計・合計と合い、日別・月別集計の店舗の行に取引数1・総売上（小計＋送料＋手数料）で載ることを確かめる（J48・J20）。ピック・引き渡し・複数受注の細部は UOR-01・UOR-02・UOR-06・UOR-07 に任せる |
| 種類 | 正常（代表：店頭受取＋店頭PCの2件）。マトリクスに行が無いので、ほかの組は表外の具体例 |
| マトリクスの行 | 該当する行なし（`matrix_UXB-16/` に統合する受注の組・件数の因子が無い）。表外の具体例として扱う |
| もとのシナリオ | 区間：UOR-01（店頭受取の注文・ピック）・UOR-06（店頭PCの注文・ピック）→UOR-02・UOR-07（まとめて引き渡し。UOR-02 のT03・T07）→UAN-01・UAN-04・UPC-08 |

## 前提

- 店舗：本店は店舗ID 1（画面によって「Hareruya」「トーナメントセンター 東京」と出る）。支店の具体例は、流す前に既存の店舗から店舗識別子を持つ支店を1つ選び、店舗ID・画面の名前を控えて読み替える（以下「支店A」）。開発環境では店舗を新しく作らない
- 用意するデータ（試験用の値。名前は流すとき後ろに「UXB-17」を付ける）
  - 会員：試験 十七郎（`uxb-17@example.test`。国内の住所を登録済み。スマレジの会員とECの会員が紐付いている）。店内アカウント：本店の店内のPCで使うログイン（UOR-06 の前提）。店内注文モニター・スタック用紙のプリンタ・タブレットがある
  - 商品：グッズ「シナリオ試験グッズM」（商品コード `UXB17-G01`・販売価格10,000円（税込）・公開・販売制限なし）。在庫は仕入れで10点×仕入単価500円（在庫10・総原価5,000円）
  - 注文：店頭受取（本店・店頭支払）で数量2（20,000円。注文Aとする）と、店頭PC（本店）で数量1（10,000円。注文Bとする）。受注時原価は注文Aが 5,000×2÷10＝1,000円（在庫8・総原価4,000円）、注文Bが 4,000×1÷8＝500円（在庫7・総原価3,500円）。合計の受注時原価1,500円。商品金額合計30,000円。送料・手数料の値は注文画面に出た値を控える（以下「送料S・手数料C」。設計書に値の定めが無ければ実際の表示を記録する）
  - スマレジの取引：2件分の商品（バーコード2つ）を1回の取引でまとめて決済する。ついで買いなし。会員を指定する。取引の小計30,000円・合計（スマレジの取引の値を控える）
  - 注文日：注文Aの注文日を前日の同じ時刻に書き換える（試験で作ったデータに限り、開発環境で書き換えてよい）。注文Bは今日。統合した新しい受注の注文日は、新実装は突合した元の受注のうち最も古い日（前日）。設計書 0505 は「店頭受取注文の注文日（複数なら一番若いもの）」で、この組では店頭受取注文Aの注文日（前日）と一致する
  - 店舗チームの担当者：管理画面とスマレジのレジを使える
- 日別・月別集計・受注売上分析・販売数は、準備で控えた値との差で合否を付ける
- 画面の名前・文言は新実装の表示で書く。設計書の名前と違うときは「（設計書：…）」を添える

## 記録（判断待ちではない）

- 元の受注に移行先の新しい受注を記録する項目が画面に出ない場合は、記録だけにし、元の注文番号で検索して同じ新しい受注が見つかることで確かめる
- 日別・月別集計の総売上は値引き前だが、スマレジ由来の新しい受注の小計は「取引明細の値引き後小計の合計」（0505）。スマレジの明細に値引きが無いこの試験では差が出ない

設計書との食い違い（起票しない）
- 統合した新しい受注の注文日：設計書は店頭受取注文の注文日（複数なら一番若いもの）、新実装は突合した受注すべて（店頭PCを含む）から最も古い日を選ぶ。店頭PCだけを統合するときの注文日は設計書に無い（`scenario_list.md` の※5）
- ついで買い・店頭購入の受注時原価：設計書に定めが無く、新実装は原価を入れない（※2）
