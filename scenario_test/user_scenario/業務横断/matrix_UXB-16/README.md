# 業務をまたぐ通しの組み合わせ（UXB-16）

IPA「高信頼化ソフトウェアのための開発手法ガイドブック」(2010) の表6-9〜6-11と同じ手順で作る。

1. 因子・水準表（FL表）: `fl_table.tsv`
2. 禁則表: `prohibitions.tsv`
3. 組み合わせテストマトリクス: `matrix.md` / `matrix.tsv`。`build_matrix.py` が作る。1行が1本の通しのシナリオになる
4. 例外の差し込み表: `exceptions.tsv`。エラーや中断は正常な値と混ぜず、条件に合う行へ1つずつ差し込む

## 範囲

- 因子は「区間のつなぎ目で、値の引き継ぎ方が変わるもの」だけにした。入口（A）・在庫の入り方（B）・出口（C）・分析の見方（D）・在庫の総原価の按分（E）・注文の日と最後の操作の日（F）・ポイントの使い方（G）
- 各区間の中の細かい組み合わせ（配送方法・支払方法・商品の種類・承認の条件など）は、それぞれの業務のマトリクス（`通販/matrix/`・`店頭受取受注管理/matrix_UOR-01/`・`在庫管理/matrix_UZK-06/` など）に任せ、ここでは重ねない。- 入口Aの店頭PCは本店（A5）と支店（A6）を分ける。支店は店頭注文番号を番号札管理で手動登録・削除する（業務フロー05 4-5・4-8）
- 店頭受取系（A2〜A6）×欠品（C4）の行は、在庫・総原価・受注の数量・金額・各集計だけを期待値にする。スマレジに登録済みの商品の内容・金額がどうなるかは設計書に無いので期待値に入れない（判断待ち）
- 注文の日と最後の操作：F1は注文と同じ日、F2は翌日以降の完了・取り消し・返品、F3は翌日以降の取り置き期限切れの取り消し（店頭受取系だけ。出口C5だけと組む）。店頭PC（A5・A6）×F2（翌日以降の引き渡し・返品）は、0時をまたぐ扱いが設計書に無いので行を作らない（判断待ちの禁則。業務周期 UCY-01）。期限切れのキャンセル（F3）は通す
- 1行は「Bの経路で入った在庫を、Aの入口で注文し、Cの終わり方にして、Dの分析で値を突き合わせる」手順
- 1行の手順（通しの流れ）：①Bの経路で在庫を入れ、商品を公開する ②Aの入口で注文する ③受注の確認・在庫・総原価を確かめる ④Cの終わり方にする ⑤Dの分析を見て、②〜④の値と合うか確かめる。Gは通販の購入のときだけ付ける（G1以外は入口Aが通販の行だけ）
- 区間の中身は、既存の業務のシナリオIDを参照する（`../scenario_list.md` の各シナリオの「区間」の欄）
- 毎行で確かめること：注文完了画面のアクセス解析への受け渡し（`分析・集計` の UAN-09。購入完了画面の表示1回につき1件）。入口が店頭受取系でも新実装は同じ受け渡しを組み立てる（`ShoppingController.php` 675行目）。法令の表示（最終確認画面）は通販・店頭受取のマトリクス側で毎行確かめるので、ここでは重ねない

### 在庫と総原価（つなぎ目：購入→在庫）

- 在庫は購入確定の時点で、受注店舗のEC在庫から注文数だけ減る（出荷や引き渡しの時点ではない）。在庫履歴に「受注による減算 注文番号：… 受注時価格：… 円」が残り、履歴登録元は「フロント注文完了」、操作者は「システム」
- 総原価：在庫の総原価から「総原価 ×（注文数 ÷ 在庫数）を四捨五入した額」を引く。この額が受注の明細の「受注時原価」になる。E1は割り切れる値、E2は四捨五入が入る値、E3は在庫を売り切る（在庫0・総原価0）
- 在庫が入った経路ごとの総原価の足し方：B1は仕入単価×数量（承認の時点）、B2・B3は買取単価×数量（入庫の時点。仕入単価＝買取単価）、B4は出庫元の出庫総原価（入庫承認の時点）。B4に差分があるときは4通り：不足は入庫先に出庫総原価×((移動数−差分数)÷移動数)、過剰で出庫元から差し引けるときは入庫先に出庫総原価＋出庫元の総原価×(差分数÷出庫元の総在庫)、差し引けないときは入庫先は計画時の総原価のまま・出庫元は何もしない（0202 在庫移動・振替登録 編集 (移動)）

### 分析での見え方

| 分析 | C1 完了 | C2 完了前の取り消し（お客様の依頼。通販だけ）／C5 取り置き期限切れの取り消し（店頭受取系だけ。C2と同じ） | C3 完了後の取り消し・返品 | C4 一部欠品 |
|---|---|---|---|---|
| D1 日別・月別集計（毎日のバッチの後に見る） | 出荷完了の受注が、注文日の行に載る。総売上＝商品小計＋送料＋手数料（値引き前）、原価＝受注時原価の合計、粗利益高＝総売上−原価 | 出ない | 取り消したあとのバッチで、注文日の行から外れる | 欠品を引いた数量・金額・原価で載る。欠品の列は受注の欠品減算 |
| D2 受注売上分析 | キャンセル以外の受注が出る（出荷完了に限らない） | キャンセル日で絞ったときだけ出る | キャンセル日で絞ったときだけ出る | 欠品を引いた数量・金額で出る |
| D3 期間別販売数（0時のバッチ） | キャンセル・決済処理中を除く受注が数える（出荷前でも数える） | 数えない | 取り消し後の次のバッチで数えない | 欠品を引いた数量 |

- 店頭受取系：日別・月別集計は新しい受注（出荷完了）を元の注文日（複数まとめたときは最も古い注文日）で数え、元の受注（引き渡し済み）は数えない。受注売上分析・期間別販売数も元の受注を外し、新しい受注を計上する。期間別販売数の計上日は、元の受注から複製された明細はEC受注日、ついで買い分はレジ取引日時
- 新しい受注の受注時原価：元の受注の明細の原価は複製される（`SmaregiOrderFactory.php` 303行目）。ついで買い・店頭購入の明細には原価を入れる処理が無い（設計書0203「スマレジ側からは原価情報を取得しない」）。そのため原価の期待値は複製した明細の分だけにする
- F2・F3（注文の翌日以降に最後の操作）：日別・月別集計は注文日の行に載る（操作の日の行ではない）。受注売上分析は、使用日付（注文日・注文確定日・入金日・出荷日・キャンセル日）によって載る日が違う

## 実装で確かめたこと（2026-11-05）

- 購入確定で在庫を引く：`StockReduceProcessor.php` の在庫引き当て（受注店舗のEC在庫を取り、総原価×注文数÷在庫数を四捨五入して受注の明細の受注時原価にする。在庫が足りなければエラー）。受注店舗はカートの店舗（`OrderHelper.php` 111行目）
- 取り消しで在庫を戻す：`order_state_machine.php` の取り消しの遷移は出荷完了・引き渡し済みを含む（200〜211行目）。取り消しのとき在庫・使用ポイントを戻す（`OrderStateMachine.php` 99〜100行目）
- 欠品の2行の履歴：`StockDiffProcessor.php` 217〜291行目（欠品でもどし＋欠品の減算）
- 買取の入庫：店頭買取は買取を行った店舗の在庫に買取小計を総原価へ足す（`OtcBuyOrderStockInbound.php` 43・79〜80行目）。ネット買取は本店（`Admin/Purchase/BuyOrderStockInbound.php` 43・79〜81行目）
- 日別・月別集計の原価は、出荷完了の受注の明細の受注時原価の合計（`DtbDailySummaryRepository.php` 99・106行目）

## まとめた水準

通販の支払方法（裁定R13の6種類＋全額ポイント・登録済みカード）は、購入直後の受注の状態・入金の確認の経路・カード情報の入力画面の有無が違うので、因子Hとして分け、まとめていない（H1 クレジットカード決済［カード情報を入れる］・H8 登録済みカード［カード情報の入力画面が無い。通販/matrix/README.md 83行］・H2 銀行振込・H3 郵便振替・H4 コンビニ決済・H5 代金引換・H7 全額ポイント）。店頭支払とスムーズ店頭受取のカード決済は通販の入口ではないのでH6にまとめた（違いは店頭受取受注管理のUOR-01）。在庫の引き当てと戻し、日別・月別集計・受注売上分析・期間別販売数の条件は支払方法に依らない（`StockReduceProcessor.php`、0211）が、日別・月別集計の総売上は手数料を含む（0211 日別・月別集計(検索結果-日別) (3)総売上「送料・手数料は含む」）ので、H5 代金引換は手数料330円（通販/matrix/README.md 47行）ぶん総売上が増える。

上記以外はまとめた水準なし（どの水準も処理が違う）。主な根拠：受注の経路（通販・店頭受取本店・支店・スムーズ・店頭PC）や在庫の入り方（仕入れ・店頭買取・ネット買取・移動）、受注の終わり方（完了・取消・返品・欠品・取り置き期限切れ）、集計（日別月別・受注売上分析・期間別販売数）、原価の割り切れる・四捨五入・売り切り、ポイントの使い方は、設計書がそれぞれ別の処理・ステータス・集計対象を定めており、種類違いで処理が同じものは無い。
