# 会員管理の会員情報変更と本人確認ステータス（UMB-11）

IPA「高信頼化ソフトウェアのための開発手法ガイドブック」(2010) の表6-9〜6-11と同じ手順で作る。

1. 因子・水準表（FL表）: `fl_table.tsv`
2. 禁則表: `prohibitions.tsv`
3. 組み合わせテストマトリクス: `matrix.md` / `matrix.tsv`。`build_matrix.py` が作る。1行が1本のシナリオになる
4. 例外の差し込み表: `exceptions.tsv`。エラーや中断（★の手順）は正常な値と混ぜず、条件に合う行へ1つずつ差し込む

## 範囲

- 会員がマイページの「会員情報変更」で登録内容を変え、確認・完了に進む（0306 F06-18）。変えた項目と変える前の本人確認ステータスによって、本人確認ステータスが未確認に戻るかを確かめる
- スマレジの会員情報の更新は USM-13（成功・失敗）。ブラックリストは UMB-23。管理画面の会員編集で同じ判定をするのは UMB-16
- 1行は「本人確認ステータス（A）の会員が、項目（B）を変え、国（C）・パスワード（D）の指定で、会員情報変更を完了する」手順

## 期待結果の決まり（行ごとに当てはめる）

| 変更前（A） | 住所（B1） | 氏名・フリガナ・生年月日（B2） | それ以外だけ（B3） |
|---|---|---|---|
| A1 未確認 | 未確認のまま | 未確認のまま | 未確認のまま |
| A2 確認中 | 確認中のまま | 確認中のまま | 確認中のまま |
| A3 オンライン本人確認済み | 未確認に戻る | 未確認に戻る | オンライン本人確認済みのまま |
| A4 簡易書留確認済み | 未確認に戻る | 簡易書留確認済みのまま | 簡易書留確認済みのまま |

- 住所とは、国・郵便番号（海外用郵便番号）・都道府県・住所1・住所2（0306 F06-18 現行仕様「本人確認ステータスの扱い」）。住所3だけを変えたときは設計書が定めない（`scenario_list.md` の判断待ち#5）。この表の行では住所3を変えない
- 完了画面に「会員登録内容の変更が完了いたしました。」が出る（F06-18-MSG-002）。保存した値は、会員情報と既定のお届け先に反映される
- C2（海外）：郵便番号は海外用郵便番号を変える。国を Japan から変えると画面が読み込み直され、都道府県が消えて住所3が出る
- D1：パスワード欄はマスクの初期値のまま。従前のパスワードでログインできる。D2：新しいパスワードで次回からログインできる（従前のパスワードではログインできない）
- 確認済みのままか戻るかは、変更後のマイページ・オンライン本人確認の画面の本人確認状況（「未確認」「現在、確認中です」「オンラインで本人確認済み」「簡易書留で本人確認済み」）で見る

## 実装で確かめたこと（2026-11-05）

- 住所の変更はオンライン確認済みと簡易書留確認済みで、氏名・フリガナ・生年月日の変更はオンライン確認済みだけで未確認に戻す：`src/Eccube/Controller/Front/Mypage/ChangeController.php` 144〜167行目。0306 F06-18 現行仕様の表と同じ
- 新実装の住所の変更の判定は、国・郵便番号・都道府県・住所1・住所2で、住所3を含まない（同148〜152行目）。管理画面の会員編集は住所3を含む（`src/Eccube/Resource/template/admin/Customer/edit.twig` 64行目）。0306 には住所3の定めが無い
- 本人確認ステータスの名前は開発環境の設定どおり：未確認・確認中・オンライン本人確認済み・簡易書留確認済み（DBダンプ 2026-09-07）

## まとめた水準

- 本人確認に使わない項目（B3）：電話番号・会社名・職業・MTG Campaign 登録名・メールアドレスなどを1つにまとめた。どれを変えても本人確認ステータスは変わらず、同じ完了画面になるため（0306 F06-18 現行仕様の表に、これらの項目は無い）。ただし電話番号・氏名・カナの変更はスマレジにも送られるので、スマレジの確認は USM-13 に任せる
- 住所（B1）の項目（国・郵便番号・都道府県・住所1・住所2）：同じ表の1行にまとまっており、判定が同じなので1水準にした
