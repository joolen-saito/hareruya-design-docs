# 会員管理のログイン（UMB-03）

IPA「高信頼化ソフトウェアのための開発手法ガイドブック」(2010) の表6-9〜6-11と同じ手順で作る。

1. 因子・水準表（FL表）: `fl_table.tsv`
2. 禁則表: `prohibitions.tsv`
3. 組み合わせテストマトリクス: `matrix.md` / `matrix.tsv`。`build_matrix.py` が作る。1行が1本のシナリオになる
4. 例外の差し込み表: `exceptions.tsv`。エラーや中断（★の手順）は正常な値と混ぜず、条件に合う行へ1つずつ差し込む

## 範囲

- お客様が会員ログイン画面でメールアドレスとパスワードを入れてログインする（0306 F06-03）。本店と支店の入口、ログイン状態の保持、ログインのあとの遷移先、失敗が続いたときの制限（5回・30分）まで
- パスワードが今の決まりに合わない会員のログインは UMB-04。通販の購入の途中でログインが要るときの例外（制限・ポリシー違反）は通販のマトリクスの例外E4・E8（UTS-01）。ここではログインそのものを、アカウントの側から確かめる
- 1行は「アカウントの状態（A）に、パスワード（B）で、失敗が続いた状況（C）のとき、入口（D）からログインする。成功するときは保持（E）と遷移先（F）も確かめる」手順

## 期待結果の決まり（行ごとに当てはめる）

| 条件 | 期待 |
|---|---|
| A1 本会員 ＋ B1 正しいパスワード ＋ C1 または C3 | ログインでき、遷移先の指定があればその画面へ、無ければトップ（/）へ進む。保持を選んだ行（E2）は、ブラウザを閉じて開き直してもログイン状態が続く（既定で1年間）。支店の入口（D2）は本店に問い合わせて認証し、支店側のログイン状態になる |
| A1 ＋ B2 誤ったパスワード ＋ C1 | ログイン画面に留まり、「ログインできませんでした。入力内容に誤りがないかご確認ください。」が出る |
| A2 本会員でない（仮会員・退会済み・登録のないメールアドレス）＋ B1／B2 ＋ C1 | 同じエラー（会員の有無・パスワードの違いは画面で区別しない）。パスワードが合っていても認証されない |
| C2 制限中（A・B によらず） | 「ログイン試行回数が多すぎます。{ログイン不可の残り時間}分後に再度お試しください。」（通販の裁定R9）。正しいパスワードでもログインできない |
| C3 30分が過ぎたあと | 制限が解け、A1＋B1ならログインできる（A2・B2のときは通常のエラー） |

- ログインに失敗する行（A2・B2・C2）でも、保持の選択（E）とマイページからの誘導（F）は成り立つ（認証の前に決まる条件。0306 ログイン 機能仕様）。失敗のときは、ログイン状態にならず、保持もされず、ログイン画面に留まる（誘導されていても遷移先へは進まない）
- 制限の数え方は、入力したメールアドレスとIPアドレスの組み合わせごと（別のメールアドレスは制限されない。例外E4）
- C2 の作り方：同じメールアドレスで5回続けて誤ったパスワードを入れる。C3 は、そのあと30分待つ

## 実装で確かめたこと（2026-11-05）

- 5回・30分：`app/config/eccube/packages/eccube.yaml` 322〜324行目、会員の入口の制限 `app/config/eccube/packages/security.yaml` 92〜94行目
- 文言「ログイン試行回数が多すぎます。%minutes%分後に再度お試しください。」：`src/Eccube/Resource/locale/validators.ja.yaml` 26〜27行目。0306 ログインの機能仕様（通販の裁定R9が採る 0306:1678）に合う。0306 表示メッセージ節の F06-03-MSG-001（『しばらく時間をおいてから』）には従わない
- ログイン状態の保持は、開発環境の店舗基本情報で有効（DBダンプ 2026-09-07）。保持の選択欄が出る

## まとめた水準

- A2：仮会員・退会済み・登録のないメールアドレスを1つにまとめた。0306 ログイン 現行仕様「認証の対象」が「退会・削除済みの会員と、本会員でない会員は、メールアドレスとパスワードが合っていても認証が成立しない」、「ログインの判定順序」が「会員の存在有無とパスワード不一致は画面上で区別しない」と定め、どれも同じ画面・同じ文言になるため
- 本人確認ステータスや顧客グループ（通常会員・店内アカウント）ごとの違いは、ログインの流れを変えない（店内アカウントのIP制限は UMB-22）
