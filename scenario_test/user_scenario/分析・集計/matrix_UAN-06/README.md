# 分析・集計の入荷通知依頼（UAN-06）

IPA「高信頼化ソフトウェアのための開発手法ガイドブック」(2010) の表6-9〜6-11と同じ手順で作る。

1. 因子・水準表（FL表）: `fl_table.tsv`
2. 禁則表: `prohibitions.tsv`
3. 組み合わせテストマトリクス: `matrix.md` / `matrix.tsv`。`build_matrix.py` が作る。1行が1本のシナリオになる
4. 例外の差し込み表: `exceptions.tsv`。エラーや中断（★の手順）は正常な値と混ぜず、条件に合う行へ1つずつ差し込む

## 範囲

- 管理画面の「入荷通知依頼」（M12-05）と「入荷通知依頼 CSV出力」（M12-06）で、会員が商品詳細で入れた入荷通知の依頼が、商品ごと・言語ごとの「通知待ち」「削除」の件数に出るか
- 依頼の作り方：会員がログインして商品詳細の「入荷通知」（規格ごと）または「まとめて入荷通知」（商品ごと）を押す（0303 フロント_商品「入荷時通知」）。取り消しは同じボタン。バッチによる取り消しは UAN-07

## 期待結果の決まり（行ごとに当てはめる）

- 1行は商品×言語。通知待ち＝取り消されていない依頼をした会員の数。削除＝取り消した会員の数
- 同じ商品の複数の規格に依頼した1人の会員は1と数える。削除は、その会員のすべての規格と商品の依頼が取り消されているときだけ数える（0211 入荷通知依頼 一覧表示(検索結果) 識別ID 4・5）
- 依頼日（To）は指定した日の当日分まで含める。販売金額の（From）は指定額を含み、（To）は含まない（現行仕様）
- 会員名では検索できない（0211 入荷通知依頼 一覧表示(検索項目)）

## 実装で確かめたこと（2026-11-05）

- 通知待ち＝取り消されていない依頼をした会員の数（重ねて数えない）。削除＝依頼した会員の数−通知待ち（`src/Eccube/Repository/DtbProductRequestRepository.php` getAnalysisSummary）。設計書の「すべての規格が削除されているときだけ削除」と同じ動き
- 入荷通知のメールを送っても、依頼は取り消されず残る（`Service/Stock/RestockNotificationMailSender.php` に依頼を削除する処理が無い）。通知後も通知待ちに数え続ける。設計書は通知済みの扱いを書いていない（`scenario_list.md` の食い違い）
- 古い版の設計書（0211 詳細設計）は「通知済み／削除」と書く。新しい版（0211 基本設計）は「削除」。新しい版に従った（`scenario_list.md` の食い違い）
- バッチで取り消された依頼を画面の「削除」に数えるかは、設計書に無く、新実装は数える（取り消した日時が入るため）。判断待ち（`scenario_list.md`）

## まとめた水準

なし（どの水準も処理が違う）。主な根拠：商品規格への依頼と商品まとめてへの依頼は設計書の別の画面項目（2-14・2-17）で数え方が違い、通知待ち・自分で取り消し・バッチ取り消しは数える列が違う。言語は日本語・英語・その他の言語を指定する絞り込みで、言語ごとに対象の行が違う。1人1規格・複数規格・複数会員は1カウントの決まりが違う。
