# 分析・集計の取引が後から変わったときの集計の更新（UAN-03）

IPA「高信頼化ソフトウェアのための開発手法ガイドブック」(2010) の表6-9〜6-11と同じ手順で作る。

1. 因子・水準表（FL表）: `fl_table.tsv`
2. 禁則表: `prohibitions.tsv`
3. 組み合わせテストマトリクス: `matrix.md` / `matrix.tsv`。`build_matrix.py` が作る。1行が1本のシナリオになる
4. 例外の差し込み表: `exceptions.tsv`。エラーや中断（★の手順）は正常な値と混ぜず、条件に合う行へ1つずつ差し込む

## 範囲

- 「日別・月別集計」は毎日の集計バッチが作った集計の表を読むため、取引が後から変わると、次のバッチが動くまで画面とCSVに出ない。その待ちと、変わったあとの値を確かめる
- 1行は「取引の変化（A）が、注文日と何日離れているか（B）で起き、バッチ（D）が動いたあとに画面（C）で見る」手順。データは通販・店頭受取のシナリオ（UTS-01・UOR-02・UOR-10・UTS-02）の手順で作る

## 期待結果の決まり（行ごとに当てはめる）

| 取引の変化（A） | バッチが動いたあとの集計 |
|---|---|
| A1 出荷完了になる | 注文日の行に、通販の売上・取引数が加わる。出荷完了にした日の行は変わらない |
| A2 店頭受取の引き渡し | 元の注文日の行に、店舗の売上・取引数が加わる。元の受注（引き渡し済み）は数えない |
| A3 返品でキャンセル | 注文日の行から、その売上・取引数が外れる（総合計も減る） |
| A4 出荷前の取り消し | 変わらない（最初から数えていない）。日付指定の再集計（D2）でも変わらないことを確かめる |

- E2（バッチの前にも見る）は途中の確認。変化した日のうちに見ると集計は変化の前のままで、終点はいつもバッチのあとに値が直ること
- 月別（C2）は、日別の集計の合算。月別は別のバッチ（日付指定の実行では対象月を指定して別に流す）で洗い替わる。日別のバッチだけ流して月別を見ると、月別は古いまま
- D2（日付を指定する実行）は、注文日（集計日）を指定する。変化した日ではなく、変化した受注の注文日

## 実装で確かめたこと（2026-11-05）

- 毎日のバッチは「前日に更新された受注・買取・在庫履歴」を探し、それらの集計日（注文日・申込日・履歴の登録日）を洗い替える。前日は必ず洗い替える。受注は更新日時のほか削除した日時でも見つける（`SummaryRecalculateTargetDateResolver.php` 全体、`DtbDailySummaryRepository.php` 148〜200行目）
- 日付を指定してバッチを実行すると、その日の日別だけを洗い替える（`DailySummaryAggregateCommand.php` 84〜95行目）。月別は別のコマンドで、月を指定して流す（`MonthlySummaryAggregateCommand.php` 33〜41行目・86〜96行目）。月別は日別の合算なので日別のあとに流す（`MonthlySummaryAggregateCommand.php` の説明・`BatchAggregateMonthlySummaryAction.php`）
- バッチが止まった間の変化は拾えない。日付を指定して流し直す前提（`SummaryRecalculateTargetDateResolver.php` の説明）
- 設計書に、この日別・月別集計のバッチのシートは無い。実行の時刻もわからない（`scenario_list.md` の食い違い・判断待ち）

## まとめた水準

なし（どの水準も処理が違う）。主な根拠：出荷完了・引き渡し・返品・取消は集計に加わる・外れるが違い、日別バッチと日付指定の再実行は流れが違う。日別・月別は集計の単位が違い、バッチ前後の確認の有無も確認の内容が違う。
