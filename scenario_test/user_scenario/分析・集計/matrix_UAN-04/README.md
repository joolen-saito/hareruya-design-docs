# 分析・集計の受注売上分析（UAN-04）

IPA「高信頼化ソフトウェアのための開発手法ガイドブック」(2010) の表6-9〜6-11と同じ手順で作る。

1. 因子・水準表（FL表）: `fl_table.tsv`
2. 禁則表: `prohibitions.tsv`
3. 組み合わせテストマトリクス: `matrix.md` / `matrix.tsv`。`build_matrix.py` が作る。1行が1本のシナリオになる
4. 例外の差し込み表: `exceptions.tsv`。エラーや中断（★の手順）は正常な値と混ぜず、条件に合う行へ1つずつ差し込む

## 範囲

- 管理画面の「受注売上分析」（M12-03）と「受注売上分析 CSV出力」（M12-04）で、商品別・カテゴリ別の売れ筋が、取引のシナリオで作った受注と合うか。価格管理（UPC-02）の売上確認でも使う画面
- 日別・月別集計と違い、出荷完了の受注だけを数えるのではない。集計日対象項目がキャンセル日以外のときはキャンセル以外のすべての受注を、キャンセル日のときはキャンセルの受注を、その日で数える（下の「実装で確かめたこと」）
- 1行は「通販・店頭受取・店頭の6種類の注文（下表の①〜⑥）を同時に用意し、集計日対象項目（B）などを変えて検索する」手順。注文の種類は因子にせず、各行で6種類を用意して期待値を下の表から決める（種類×日付の30通りの値を、1つのデータで確かめるため）

## 期待結果の決まり（行ごとに当てはめる）

設計書（0211 受注売上分析 集計一覧(検索項目) 画像2）の「基準日」表。表の日付が集計期間の中にある注文だけを数える。

| 集計日対象項目 | ①シンプルEC | ②引渡し前（店頭受取の元の受注） | ③スムーズ店頭受取 | ④統合受注の複製分 | ⑤ついで買い | ⑥シンプル店頭 |
|---|---|---|---|---|---|---|
| 注文日 | EC購入完了日時 | EC購入完了日時 | EC購入完了日時 | 元注文ごとのEC購入完了日時（複数まとめ時は最古に寄る） | レジ取引日時 | レジ取引日時 |
| 注文確定日 | ピック中遷移日時 | ピック中遷移日時 | ピック中遷移日時 | ピック中遷移日時 | レジ取引日時 | レジ取引日時 |
| 入金日 | 入金済み遷移日時 | 決済済みなら決済日時。未決済は－（対象外） | EC決済日時 | レジ取引日時 | レジ取引日時 | レジ取引日時 |
| 出荷日 | 出荷完了遷移日時 | －（対象外） | レジ取引日時 | レジ取引日時 | レジ取引日時 | レジ取引日時 |
| キャンセル日 | キャンセル遷移日時 | キャンセル遷移日時 | キャンセル遷移日時 | 取消日時 | 同左 | 同左 |

- 「－」は、その集計日対象項目で検索しても出ない（対象外）。キャンセル日以外の検索では、キャンセルの受注は出ない。キャンセル日の検索では、キャンセルの受注が出る
- 設計書の画面の集計日対象項目には「売上確定日」もあるが、表の行は全部「－」（対象外）。「売上確定日」で検索すると何も出ないのが設計書どおりで、水準に入れず、シナリオ一覧のL3に1件として置いた。新実装は受注の受領日の列で絞るため、何も出ないとは限らない（`scenario_list.md` の食い違い）
- 通販の支払方法（因子G。①シンプルECの注文に使う）：注文日・注文確定日・出荷日・キャンセル日の基準は支払方法で変わらない。入金日は、入金済みへ遷移した日時（新実装は入金済みへ入るすべての遷移で入金日を登録する：`OrderStateMachine.php` 96〜98・114〜118行）。G1・G2（カード）は購入完了の日時、G3 銀行振込・G4 郵便振替は入金を確認して入金済みにした日時、G5 コンビニ決済は入金通知で入金済みになった日時。G6 代金引換・G7 全額ポイントは、入金済みを通らないまま出荷完了にした受注には入金日が入らず、入金日の期間検索に出ない（期間は入金日の列で絞る：`OrderItemRepository.php` 248〜255行）。設計書の基準日表は①の入金日を「入金済み遷移日時」とだけ書き、入金済みを通らない場合を書かない（`../scenario_list.md` の判断待ち7）
- 店頭受取の引き渡しで元の受注が置き換わった分は、二重に数えない（0211 受注売上分析 集計一覧(検索項目)「スマレジの受注は、引き渡し済みの元EC受注を集計対象から外し、スマレジ由来受注1件を計上元とする」）
- 集計の値：数量＝明細の数量の合計。合計＝単価×数量の合計。平均単価＝合計÷数量（小数点以下切り捨て）。件数＝受注の数（同じ受注を重ねて数えない）。商品は受注時の商品名・商品コードでまとめ、カテゴリは1つの商品が複数のカテゴリに入ると重ねて数える（0211 受注売上分析 集計一覧(検索項目)の現行仕様「集計のまとめ方」）
- 通販と店舗の行を選んだときは、選んだ店舗の数値を合算する（0211 受注売上分析 集計一覧(検索結果-集計単位 商品)「集計データについて」）
- 表示件数（F2）：打ち切った分は出ない。合計行は表示中の行だけの合計。CSV（G2）は打ち切らず全件

## 実装で確かめたこと（2026-11-05）

- 新実装は、キャンセルを除く全受注を数える（`src/Eccube/Repository/OrderItemRepository.php` 46行目・241〜244行目）。置き換わった元の受注（移行先の受注が決まっているもの）は除く（232行目）
- 集計日対象項目は、注文日・注文確定日・入金日・出荷日・「売上確定日」（受注の受領日の列で絞る）・キャンセル日（`Form/Type/Admin/Analysis/SalesType.php` 44〜51行目）。キャンセル日で検索するとキャンセルの受注だけが出る（`OrderItemRepository.php` 237〜240行目）
- スマレジ由来の受注の日付の読み替え（注文日・注文確定日・出荷日）は新実装にある（`OrderItemRepository.php` 345〜400行目）。入金日・キャンセル日の読み替えは新実装に見当たらない。設計書の表の期待値と合うかは、実行して確かめる
- 検索せずにCSVを開くとエラー「検索条件がありません。先に検索を実行してください。」（`SalesAnalysisController.php` 123〜130行目）。設計書の表示メッセージ M12-04-MSG-001 と同じ

## まとめた水準

通販の支払方法は、購入直後の状態・入金の経路・カード情報の入力画面の有無が違い、入金日の基準が変わるので、まとめていない（因子G：G1〜G7）。

上記以外はまとめた水準なし（どの水準も処理が違う）。主な根拠：注文日・注文確定日・入金日・出荷日・キャンセル日は、設計書が受注の種類ごとに別の日時（EC購入完了日時・ピック中遷移日時・レジ取引日時など）を定めており集計日が違う。商品とカテゴリの集計単位、絞り込みの種類（明細に効く・集計後の行に効く）、表示件数による打ち切りも結果が違う。
