# 分析・集計の購入完了の売上と会員IDのアクセス解析への連携（UAN-09）

IPA「高信頼化ソフトウェアのための開発手法ガイドブック」(2010) の表6-9〜6-11と同じ手順で作る。

1. 因子・水準表（FL表）: `fl_table.tsv`
2. 禁則表: `prohibitions.tsv`
3. 組み合わせテストマトリクス: `matrix.md` / `matrix.tsv`。`build_matrix.py` が作る。1行が1本のシナリオになる
4. 例外の差し込み表: `exceptions.tsv`。エラーや中断（★の手順）は正常な値と混ぜず、条件に合う行へ1つずつ差し込む

## 範囲

- 会員が購入して注文完了画面が出たとき、ページに積まれるアクセス解析用の値（購入完了の売上連携 F10-02、会員IDの連携 F10-01）が、購入した受注の値と合うか
- 見るのは、ブラウザの開発者ツールで見るページ内の受け渡し領域の中身（画面に文言は出ない）。タグの管理サービス（GTM）とアクセス解析（GA）の側の設定は、ここでは作っていない（結合テストのGA連携の観点でも「GTM設定待ち」）。受け渡し領域までを確かめる
- 購入は、通販のシナリオ（UTS-01）の手順。非会員は買えない（通販の範囲）。お届け先が複数になる購入は、設計書が1件目だけを積むと定めている（0310 F10-02）。開発環境の設定では本店の複数配送オプションが無効（DBダンプ 2026-09-07 の店舗の表 option_multiple_shipping 列が偽）で購入画面から作れないため、水準に入れず例外E4に置いた

## 期待結果の決まり（行ごとに当てはめる）

積まれる値（0310 F10-02 の表）。1つの要素にまとめて積む。

| 項目 | 値 |
|---|---|
| transactionId | 受注ID。8桁に満たないときは左を0で埋める |
| transactionAffiliation | 1件目のお届け先の配送方法の名称 |
| transactionTotal | 商品小計（税込単価×数量の合計）。送料・ポイント・値引きを反映しない |
| transactionTax | 常に0 |
| transactionShipping | 送料合計（0円のときは0） |
| transactionMailaddress | 注文完了画面を表示した時点でログインしている会員のメールアドレス |
| transactionProducts | 明細1行につき1件。商品コード・商品名・カテゴリ（常に空）・税抜の単価・数量 |

- 会員ID（F10-01）：ログインしているとき、会員IDを数値のまま1項目（uid）だけ積む。氏名・メールアドレスは積まない
- 税抜の単価×数量の合計は、消費税がかかる注文では transactionTotal（税込）と一致しない
- 期待値は、購入時に控えた受注の画面（金額・明細・配送方法）から手で決める。積まれた値を期待値にしない

## 実装で確かめたこと（2026-11-05）

- 0310 は専用のExcelシートが無く、現行ソース（pf-eccube3）からの機能仕様書がそのままの正本（0310 の説明）。新実装との照合は、実行して確かめる

## まとめた水準

なし（どの水準も処理が違う）。主な根拠：0310 F10-02 の transactionAffiliation は「配送方法の名称」で、配送方法ごとに期待値（送る名称）が変わる。0304 注文 1573行は「選択肢：ゆうパケット、ゆうパック、店頭受取、スムーズ店頭受取、EMS、Small packet、同梱」と別の選択肢を列挙する。ポイントの使い方（決済の流れが違う）・送料・明細の行数・サイトの言語も積む値や流れが違う。
