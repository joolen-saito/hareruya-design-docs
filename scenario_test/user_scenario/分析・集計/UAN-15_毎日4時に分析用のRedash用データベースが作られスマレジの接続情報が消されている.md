| 項目 | 内容 |
|---|---|
| 利用者 | 運用の担当者（バッチを手で起動。バッチ用の環境で行う）→ 顧客戦略（Redash で分析する。Redash の画面はシステムの外で対象外）。DB の中の値の確認は運用の担当者が DB の確認用の道具で行う |
| 目的 | 毎日4時のバッチが、本番のデータベースのスナップショットから、分析用の Redash 用データベースを作り、Redash 用データベースの中で、スマレジ用の接続IDとアクセストークンが消え、取り消し・発送済みの注文のスマレジ削除フラグが ON になることを確かめる。本番のデータベースは変わらない |
| 種類 | 正常（代表の1本）。組み合わせ表は作らない（`../scenario_list.md` の L3 の欄にそう書いてある）。例外1件 |
| マトリクスの行 | 組み合わせ表の無いシナリオ。代表のみ。例外 E1 は「L3で変わるところ」 |
| もとのシナリオ | なし（今のシナリオ SCN-* に無い。0416 B16-07 から起こした） |

## 前提

- 共通の決まり：`../L4を流すときの共通の決まり.md` を先に読む（試験データの名前にシナリオIDを付ける・共有の設定は元に戻す・バッチの起動・店舗の読み替えなど）
- システムの外で済んでいること：Redash の画面・データベースの作成の仕組みは、ブラウザの画面の試験では確かめられない（他層：Redash・DB。決着した論点 #5）。この L4 は、バッチ用の環境（AWS）でバッチを起動でき、Redash 用データベースの中を DB の確認用の道具で見られる運用の担当者が行う。そのような環境・権限が無ければ、この L4 は「実施不可（流せない）」として記録する
- 新実装には、Redash 用データベース作成のバッチが見つからない（確かめた場所：`script/ops/` の月次商品情報スナップショット・ステージングデータベース保守・DB初期化・データ移行の各処理。ステージングデータベース保守（B16-10）は別のバッチで、Redash 用ではない）。バッチを起動できなければ、手順1以降は先へ進めないので、「未実装の見込み」として不合格に記録する（期待値は設計書どおり）。起動のしかた（ファイルの場所）は、実装が見つかったら根拠の欄に足す
- 注文のステータス名の読み替え：設計書は「注文ステータスが「注文取消し」「発送済み」」と書く。これは現行のステータス名で、新システムの名前（キャンセル・出荷完了・引き渡し済み）との対応が設計書に無い。この L4 は、「注文取消し」＝新システムの「キャンセル」、「発送済み」＝新システムの「出荷完了」（引き渡し済みを含むかは確かめて記録）と読んで確かめる。読み替えは設計書に無い推測として記録する（決着した論点 #5）
- 用意するデータ（試験用の値。設計書の値ではない。名前の後ろにシナリオIDを付けて作る）
  - 担当者：通販チームの担当者。運用の担当者（バッチの起動・DB の確認用の道具を使える。本番のデータは書き換えない）。経理・運用で、スマレジ連携の設定を見られるメンバー
  - 会員：「試験 十三郎」（メールアドレス `uan-15@example.test`、本会員、国内（東京都）の住所を登録済み）
  - 商品：グッズ「分析試験グッズ UAN-15」（商品コード「UAN15-G01」、販売価格 3,300円、公開）。在庫は在庫変更CSVで 20点（UZK-01 の手順3〜6と同じ）
  - 注文（本番のデータベースに試験の注文として入れる）：注文 X（通常。出荷完了まで進める。UTS-01 の手順1〜9・16〜20と同じ流れ）、注文 Y（出荷前に取り消してキャンセルにする。UTS-02 の手順）、注文 Z（通常。注文受領のまま止める）
  - スマレジの設定：管理画面の設定＞店舗設定のスマレジ連携の設定（接続ID・アクセストークン）が入っていること。入っていなければ、この試験では「接続情報が消える」ことの確かめが成り立たないので、記録する。流す前に今の値の有無だけを確かめる（値そのものは成果物・返答に書かない）
- 認証情報（スマレジの接続ID・アクセストークン）は、成果物にも返答にも書かない。消えている・残っていることだけを確かめる
