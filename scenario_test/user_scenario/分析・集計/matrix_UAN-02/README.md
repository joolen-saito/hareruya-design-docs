# 分析・集計の日別・月別集計の買取・廃棄・欠品（UAN-02）

IPA「高信頼化ソフトウェアのための開発手法ガイドブック」(2010) の表6-9〜6-11と同じ手順で作る。

1. 因子・水準表（FL表）: `fl_table.tsv`
2. 禁則表: `prohibitions.tsv`
3. 組み合わせテストマトリクス: `matrix.md` / `matrix.tsv`。`build_matrix.py` が作る。1行が1本のシナリオになる
4. 例外の差し込み表: `exceptions.tsv`。エラーや中断（★の手順）は正常な値と混ぜず、条件に合う行へ1つずつ差し込む

## 範囲

- 「日別・月別集計」の買取件数・買取金額・廃棄・欠品の4列が、買取・在庫のシナリオで作ったデータと合うか。売上の列は `matrix_UAN-01/`
- 1行は「集計の元（A）のデータを、状態・区分（B）、在庫の区分・店舗（C）で用意して見る」手順。データは店頭買取（UKA-01・UKA-10）、ネット買取（UNK-04・UNK-05）、廃棄（UZK-15）、欠品（UTS-03・UZK-11・UZK-12）の手順で作る。期待値は作ったデータから手で計算する

## 期待結果の決まり（行ごとに当てはめる）

| 元（A） | 数える行 | 数えるとき | 値 | 集計日 |
|---|---|---|---|---|
| A1 店頭買取 | 買取をした店舗の行 | 買取成立日が入っている。管理者取消は数えない | 件数：1件、金額：査定金額合計 | 買取申込日 |
| A2 ネット買取 | 通販の行 | 査定承諾日が入っている。キャンセルは数えない | 件数：1件、金額：査定承諾金額の合計（査定金額の合計ではない。送料は含まない） | 買取申込日 |
| A3 廃棄 | 通販はEC在庫の行、店舗は在庫の区分に応じた行 | 区分が「廃棄」。ただし廃棄(イベント商品)・廃棄(他事業移動)は数えない | 廃棄コスト合計（プラスで表示） | 在庫履歴の登録日 |
| A4 欠品 | 同上 | 詳細区分が欠品減算（受注）・欠品減算（移動）・欠品減算（結合） | 欠品コスト合計（プラスで表示） | 在庫履歴の登録日 |

- 在庫の行の決め方：通販＝TC東京のEC在庫。店舗＝TC東京はスマレジ在庫のみ、ほかの店舗はEC在庫とスマレジ在庫の両方（0211 日別・月別集計 集計一覧(検索結果-日別) (11)(12)）
- 廃棄のうち、廃棄(破損)・廃棄(その他)・廃棄(欠品)・廃棄(棚卸ロス)・廃棄(却下)（却下したときの戻し）は数える。却下の戻しは符号が逆なので、廃棄コストが相殺される
- 欠品：UTS-03の欠品登録は「欠品減算（受注）」と「欠品加算（受注）」の2行を残す。数えるのは減算の行だけで、加算（戻す側）は数えない
- 集計日は申込日・登録日。成立・承諾・承認が別の日でも、申込日・登録日の行に載る（D2）

## 実装で確かめたこと（2026-11-05）

- 買取：ネット買取は査定内容承諾の履歴があり現在のステータスがキャンセルでないもの、店頭買取は買取成立日が入り現在のステータスが管理者取消でないもの。ネット買取は本店（通販）の行、店頭買取は店舗の行（`DtbDailySummaryRepository.php` 209〜222行目の説明と集計）
- 廃棄：区分「廃棄」のうち、詳細区分がイベント商品・他事業移動を除く（`DtbDailySummaryRepository.php` 332〜350行目）。廃棄の区分には、廃棄(破損)・(他事業移動)・(イベント商品)・(その他)・(欠品)・(棚卸ロス)・(却下) がある（開発環境の設定 2026-09-07）
- 欠品：詳細区分が欠品減算（受注）・（移動）・（結合）の履歴。欠品加算は含めない。値は総原価の減少分（`DtbDailySummaryRepository.php` 372〜402行目）
- 設計書内の食い違い：同じシートが「買取関連の集計は買取ステータスが「買取成立」のみ計上」と、(9)で「買取成立日が入っているもの」（買取成立のあと入庫待ちなどに進んでも数える）を並べて書く。新実装は後者。後者に従った（`scenario_list.md` の食い違い）

## まとめた水準

なし（どの水準も処理が違う）。主な根拠：買取・廃棄・欠品は集計の元データと数える条件が違い、在庫の区分（EC在庫・スマレジ在庫）は元データの作り方が違う（TC東京はスマレジ在庫のみ集計）。確定・未確定・取消の状態、集計に入る区分・入らない区分も数える・数えないが違う。
