| 項目 | 内容 |
|---|---|
| 利用者 | 取引の変化は通販チーム・店舗チーム・お客様（この L4 の準備と手順で行う）→ 運用の担当者（集計バッチを手で起動）→ 店舗統括（日別集計・月別集計・CSV） |
| 目的 | 出荷完了・店頭受取の引き渡し・返品などで取引が後から変わったとき、集計バッチを流す前の日別集計・月別集計は変化の前のままで、バッチを流したあとに、出荷完了は注文日の行に加わり、返品は注文日の行から外れ、出荷前の取り消しは変わらないことを確かめる。月別も合う |

## 前提

- 共通の決まり：`../L4を流すときの共通の決まり.md` を先に読む（試験データの名前にシナリオIDを付ける・共有の設定は元に戻す・バッチの起動・店舗の読み替えなど）
- システムの外で済んでいること：なし（取引はこの L4 の準備と手順で作る）
- 日別・月別集計は、毎日のバッチが作った集計の表を読む。バッチの時刻は設計書にもリポジトリにも無い（決着した論点 #1）ので、時刻は待たず手で起動し、バッチのあとの確認は「日付を指定して流し直す」ことで行う。毎日のバッチ（日付を付けない起動）は、前日に更新された受注の注文日の分を洗い替えるので、試験で作った受注の更新日時を前日に書き換えて用意する（試験で作った受注だけ。開発環境のデータの書き換え）
- バッチは環境の中の対象を全部処理する。共有の開発環境ではほかの試験の受注も一緒に洗い替わる。合否はこの試験の取引由来の値（流す前に控えた値からの増え方）で付け、バッチの対象日数は記録にする
- 用意するデータ（試験用の値。設計書の値ではない。名前の後ろにシナリオIDを付けて作る）
  - 担当者：店舗統括（日別集計・月別集計を使えるメンバー。所属店舗は本店＝店舗ID 1）。通販チームの担当者。店舗チームの担当者。在庫の登録担当と承認者。運用の担当者（バッチを起動できる）
  - 店舗：本店（店舗ID 1）。店舗は新しく作らない
  - 商品：グッズ「分析試験グッズ UAN-03」（商品コード「UAN03-G01」、NM の1規格、販売価格 15,000円、本店で公開）。在庫変更CSVで 20点、仕入単価 6,000円（UAN-01 の P2・P3 と同じ手順）
  - 会員：「試験 三郎」（メールアドレス `uan-03@example.test`、本会員、国内（東京都）の住所を登録済み）
  - 取引：商品を数量2（商品合計 30,000円・送料0・手数料0。受注時原価 6,000×2＝12,000円）の注文1件。総売上 30,000・原価 12,000・粗利益高 18,000・販売点数 2・取引数 1
  - 試験日（S）：流す日。月の3日以降に流す（注文日を同じ月の2日前に書き換える行があるため）
- 取引の変化ごとの手で計算した、バッチのあとの集計（注文日の行。行は通販の取引なら「通販」、店頭受取なら「本店」）

| 取引の変化 | バッチのあとの集計 |
|---|---|
| A1 通販の注文が出荷完了になる | 注文日の行に、通販の総売上 +30,000・原価 +12,000・粗利益高 +18,000・販売点数 +2・取引数 +1 が加わる。出荷完了にした日の行は（注文日と違うとき）変わらない |
| A2 店頭受取が引き渡され、スマレジの取引から新しい受注が出荷完了で作られる | 元の注文日の行に、本店の総売上 +30,000・原価 +12,000・粗利益高 +18,000・販売点数 +2・取引数 +1 が加わる。元の受注（引き渡し済み）は数えない。通販の行は変わらない |
| A3 出荷完了のあとで返品され、受注がキャンセルになる | 先に A2 の値が加わった状態（控える）から、注文日の行のその売上・取引数が外れ、返品前の値に戻る（総合計も減る） |
| A4 出荷前に注文が取り消される | 変わらない（最初から数えていない）。日付指定の再集計でも変わらない |
