# 分析・集計の日別・月別集計の売上（UAN-01）

IPA「高信頼化ソフトウェアのための開発手法ガイドブック」(2010) の表6-9〜6-11と同じ手順で作る。

1. 因子・水準表（FL表）: `fl_table.tsv`
2. 禁則表: `prohibitions.tsv`
3. 組み合わせテストマトリクス: `matrix.md` / `matrix.tsv`。`build_matrix.py` が作る。1行が1本のシナリオになる
4. 例外の差し込み表: `exceptions.tsv`。エラーや中断（★の手順）は正常な値と混ぜず、条件に合う行へ1つずつ差し込む

## 範囲

- 管理画面の「日別・月別集計」（M12-01）と「日別・月別集計 CSV出力」（M12-02）で、売上の列（総売上・原価・粗利益高・販売点数・取引数・取引単価(平均)）と総合計行が、取引のシナリオで作った受注と合うか
- 買取・廃棄・欠品の列は `matrix_UAN-02/`、取引が後から変わる場合は `matrix_UAN-03/` で扱う
- 1行は「取引の種類（C）の受注を1件以上用意し、集計対象（B）・集計タイプ（A）で見る」手順。取引のデータは通販・店頭受取のシナリオ（UTS-01・UOR-02・UOR-03・UOR-07）の手順で作り、期待値は作った受注の金額から手で計算する（集計の画面の値を期待値にしない）

## 期待結果の決まり（行ごとに当てはめる）

| 取引の種類（C） | 数える行 | 数えるとき | 注意 |
|---|---|---|---|
| C1・C2・C8〜C12 通販 | 通販の行 | 出荷完了になったとき | 支払方法（裁定R13の6種類・登録済みカード・全額ポイント）は関係しない（集計の条件に無い）。配送方法が店頭受取系・なし以外 |
| C3・C4 店頭受取 | 店舗の行 | 引き渡しで作られたスマレジ由来の新しい受注が出荷完了のとき | 元の受注（引き渡し済み）は数えない。売上の日付は元の注文日（複数まとめたときは最も古い注文日） |
| C5 スムーズ店頭受取 | 店舗の行 | 元の受注が出荷完了になったとき | 新しい受注は作られない |
| C6 店頭PC購入 | 店舗の行 | 新しい受注が出荷完了のとき | 元の店頭PCの受注（引き渡し済み）は数えない |
| C7 スマレジだけの店頭購入 | 店舗の行 | 取引を受信して新規登録された受注が出荷完了のとき | 取引した日が注文日。購入前にEC受注は無い |

- 総売上：商品合計金額。送料・手数料を含み、ポイント・クーポンの値引きは考慮しない（値引き前）。原価：受注時の原価の合計。粗利益高：総売上−原価。販売点数：注文明細の数量の合計。取引数：注文件数。取引単価(平均)：総売上÷取引数（小数点第一位を切り上げ）。総合計：各列の合計（0211 日別・月別集計 集計一覧(検索結果-日別) (3)〜(8)・識別ID 14）
- 並び：集計日の昇順、同じ日の中は店舗の表示順の昇順（同シート「店舗の並び順は店舗の表示順の昇順」）。月別は集計日の代わりに集計月
- 集計対象で選んだ行だけが出る。通販だけを選んだときは店舗の取引は出ない
- 日付は注文日の行に載る。出荷完了の日の行ではない（D2・D3では、出荷完了の日の行は増えない）
- CSV（G2）は画面（G1）と同じ内容。最終行に総合計

## 実装で確かめたこと（2026-11-05）

- 新実装の日別・月別集計は、毎日の集計バッチが作った集計の表を読む。集計の元は「出荷完了」の受注だけ。注文日が集計日。総売上は商品小計＋送料＋手数料。取引数は受注の件数。販売点数は商品明細の数量だけ（`src/Eccube/Repository/DtbDailySummaryRepository.php` 56〜143行目）。取引単価は切り上げ（`BatchAggregateDailySummaryAction.php` 116行目）
- 通販の行を持つのはTC東京（本店）だけ。支店は配送方法によらず店舗の行に入る（`DtbDailySummaryRepository.php` 66〜74行目、`BatchAggregateDailySummaryAction.php` 175〜179行目）
- 店頭受取の新しい受注の注文日は、元の店頭受取の注文のうち最も古い注文日（`EccubeOtcPatternHandler.php` 60行目・157〜164行目。設計書 0505 スマレジ受信処理の同じ記述）
- 設計書との食い違い：設計書の画像（検索項目・検索結果）は店舗の一覧と結果の行に「その他」を持つが、新実装の集計には「その他」の行が無い（`scenario_list.md` の食い違い）
- 集計の表は毎日のバッチで更新される。出荷完了にした当日のうちには出ない。この待ちは `matrix_UAN-03/` で確かめる。この表の行は、バッチが動いたあとに見る

## まとめた水準

通販の支払方法は、購入直後の状態・出荷完了までの経路・カード情報の入力画面の有無が違うので、まとめていない（C1 クレジットカード決済［カード情報を入れる］・C12 登録済みカード・C2 全額ポイント・C8 銀行振込・C9 郵便振替・C10 コンビニ決済・C11 代金引換）。根拠：通販/scenario_list.md 37行 ※1、31・32行（UTS-16・UTS-17）、通販/matrix/README.md 83行。出荷完了になれば、どの支払方法でも通販の行の同じ注文日の行に載る（0211 日別・月別集計 集計一覧(検索項目-日別)の集計条件に支払方法が無い）。ただし総売上は商品小計＋送料＋手数料（0211 日別・月別集計(検索結果-日別) (3)総売上「送料・手数料は含む」）なので、代金引換（C11）は手数料330円（通販/matrix/README.md 47行）ぶん増える。値は各受注の手数料を含めて手で計算する。

上記以外はまとめた水準なし（どの水準も処理が違う）。主な根拠：集計日の同日・同月翌日以降・翌月以降は計上日の決まりが違い、通販・各店舗・元の受注が引き渡し済みになる店頭受取・スマレジだけの購入は、受注の作られ方と集計の行が違う。
