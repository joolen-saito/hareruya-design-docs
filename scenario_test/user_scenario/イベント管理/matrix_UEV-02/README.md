# イベント管理のオンライン申込（UEV-02）

IPA「高信頼化ソフトウェアのための開発手法ガイドブック」(2010) の表6-9〜6-11と同じ手順で作る。

1. 因子・水準表（FL表）: `fl_table.tsv`。利用者が画面で選ぶもの・変わるものを因子にし、設計書の文を根拠に持つ
2. 禁則表: `prohibitions.tsv`。ありえない組み合わせ
3. 組み合わせテストマトリクス: `matrix.md` / `matrix.tsv`。`build_matrix.py` が作る。1行が1本のシナリオになる
4. 例外の差し込み表: `exceptions.tsv`。エラーや中断（★の手順）は、正常な値と混ぜず、条件に合う行へ1つずつ差し込む

## 範囲

- ログイン会員が、イベント詳細から申し込み、クレジットカード決済（有料のとき）をして、デッキを登録するところまで（業務フロー2-1・2-2）。決済の外部画面はSPLINKSのリンクタイプ（ソニーペイメント）
- 支払方法はクレジットカード決済だけ（0307 大会申込「お支払方法はクレジットカード決済のみとさせていただきます」・0214 イベント編集でコンビニ決済を削除）。決済が通らないときは例外に入れた
- 各行の期待値：申込完了画面「イベント申込が完了いたしました。」が出る。有料は決済が成立して申込状況が「決済中」から「申込済み」になり、クレジット決済完了メールが届く。無料はそのまま「申込済み」。マイイベント・デッキ登録の一覧に申込が載り、デッキを登録した行は「デッキ登録済み」と出る。定員の数に入る
- チーム戦の他メンバーの入力は廃止（0307 大会申込「チームの他メンバーに関する入力情報は削除とする」）なので、チーム戦は因子に入れない
- 申込後に日をまたいでデッキ未登録のまま待つ登録（マイイベント・デッキ登録の一覧から）は、UEV-07に分けた（R1指摘）
- 因子に入れなかったもの：参加費の金額（0円か1円以上かだけで流れが決まる）、受付期間・定員・申込済みの再申込（正常な行は受付期間内で空きがある。外れるときは例外に入れた）

## 実装・設計書で確かめたこと（2026-11-03）

- 設計書の「エントリー済み」は、開発環境の申込状況マスタの「申込済み」にあたる（新実装は無料の申込を申込済みで作る）。有料は「決済中」で作り、決済の戻りか決済処理中チェックバッチ（UEV-05）の取引照会で成立したときに申込済みへ更新し、クレジット決済完了メールを送る
- デッキ登録ボタンは、申込とは別に、デッキ登録の条件（デッキ登録あり・締切前・終了にチェックなし）だけで出る（新実装 EventDetailButtonStateResolver）。受付期間が終わっていても出る

## まとめた水準

なし（どの水準も処理が違う）。主な根拠：別日程の同時申込は選択画面の表示が違い、有料と無料は支払方法の提示有無が違う。デッキ登録あり・なしはボタンの出る出ないが違い、日本語・英語は表示項目の出し分けが違う。
