# イベント管理の開催日の受付〜ポイント付与（UEV-06）

IPA「高信頼化ソフトウェアのための開発手法ガイドブック」(2010) の表6-9〜6-11と同じ手順で作る。

1. 因子・水準表（FL表）: `fl_table.tsv`。利用者が画面で選ぶもの・変わるものを因子にし、設計書の文を根拠に持つ
2. 禁則表: `prohibitions.tsv`。ありえない組み合わせ
3. 組み合わせテストマトリクス: `matrix.md` / `matrix.tsv`。`build_matrix.py` が作る。1行が1本のシナリオになる
4. 例外の差し込み表: `exceptions.tsv`。エラーや中断（★の手順）は、正常な値と混ぜず、条件に合う行へ1つずつ差し込む

## 範囲

- 開催日に店舗チームが申込一覧をCSV出力して受付し、イベントを実施し、参加者に会員登録とデッキ登録をしてもらい、ポイントグランターでポイントを付与し、スマレジに売上を登録するところまで（業務フロー3-1〜3-8）
- 各行の期待値：参加者の保有ポイントが付与分増え、ポイント履歴が残る。新規登録した会員は会員として登録される。デッキを登録した参加者は、マイイベント・デッキ登録の一覧で「デッキ登録済み」になる。当日のイベント金額はスマレジの売上に登録される（スマレジは外部システム）
- オンライン受付の行は、申込一覧のCSV（event_entry_YmdHis.csv）に参加者が載る。競技イベント（ルールが厳しい行）は、デッキ表示（デッキ表示の「印刷」ボタン）で全員分のデッキを出し、登録デッキを確認する
- 当日受付（オンライン受付でない）の参加費の徴収は、業務フローにも設計書にもシステムの記述が無いので、システムの外とした
- 会員が登録を断る場合は終点が変わる（ポイントなどの受取拒否として終了）ので、行に入れず例外に入れた

## 実装・設計書で確かめたこと（2026-11-03）

- ポイント付与：ポイントグランターの端末販売の内容を新実装が受け取り、スマレジのポイント加算に中継し、ECの保有ポイントとポイント履歴に反映する（0517 PointGranterAPI連携、新実装 PointGranterRelayService）。設計書はプレイヤーを特定できないとき何も登録せず正常（200）を返す。新実装は先にスマレジへ加算し、ECへの反映だけを省く
- 業務フローの「PDFで出力」は、設計書ではデッキ表示の「印刷」ボタン（0214 デッキ表示 識別ID:1）
- 当日の参加者がデッキを登録するときは、イベント詳細のデッキ登録ボタンを使う（デッキ登録の条件を満たす間は、受付期間が終わっていても出る）

## まとめた水準

なし（どの水準も処理が違う）。主な根拠：オンライン受付と当日受付は参加費の徴収の流れが違い、会員登録済み・新規は会員登録を促す手順が違う。ルールの厳しさ・デッキ登録の時期（申込時・当日・なし）も確認の流れが違う。
