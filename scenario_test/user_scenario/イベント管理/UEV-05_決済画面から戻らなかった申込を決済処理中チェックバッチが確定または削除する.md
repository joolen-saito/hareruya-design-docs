# UEV-05 決済画面から戻らなかった申込を、決済処理中チェックバッチが確定または削除する

| 項目 | 内容 |
|---|---|
| 利用者 | お客様（決済画面から戻らなかった会員）→ バッチ（10分ごとの定期起動。試験では手で起動する）→ SPLINKS（取引照会。外部）→ メール |
| 目的 | 決済画面を閉じる・通信障害などで申込完了画面へ戻れず、決済中のまま30分以上たった申込を、決済処理中チェックバッチが取引照会して、成立なら申込済み（クレジット決済完了メール）に、不成立・取引が無いなら削除（枠が戻る）にすることを確かめる。照会がエラーのときは決済中のまま保留になる |
| 種類 | 正常（組み合わせ表の1行）＋例外1件。このうち、取引照会がエラーを返す行と、バッチ自体のエラーは、画面・設定の操作で起こせないので実施不可（流せない） |
| マトリクスの行 | `matrix_UEV-05/matrix.md` のT01（取引照会の結果＝取引が成立している・取引照会の対象にする申込の数＝1件）。ほかの5行（T02〜T06）と例外1件は「L3で変わるところ」 |
| もとのシナリオ | なし（今のシナリオ SCN-EVENT-* に無く、0413 バッチ_イベントの「決済処理中チェックバッチ」から足した。業務フロー08のシート「イベント受付(オンライン受付)」＃2-1の決済の離脱を片付けるバッチで、業務フローに無い） |

## 前提

- 共通の決まり：`../L4を流すときの共通の決まり.md` を先に読む（試験データの名前にシナリオIDを付ける・共有の設定は元に戻す・バッチの起動・店舗の読み替えなど）
- システムの外で済んでいること：参加者が使うクレジットカード（試験環境ではSPLINKSの試験決済画面で決済できるもの）
- バッチは時刻を待たず手で起動してよい（起動のしかたは「根拠」の欄のファイル）。対象は、申込状況が決済中・支払番号あり・作成日時が起動時刻の30分以上前の申込なので、30分は待たず、試験で作った申込に限って、作成日時を31分以上前に書き換えて用意する（開発環境のデータの書き換え。ほかの人の申込は触らない）
- バッチは環境の中の対象を全部処理する。ほかの試験の決済中の申込も同時に処理されるので、合否はこの試験の申込（支払番号・申込一覧・マイイベント・メール）で付け、バッチの完了表示の件数や、ほかの人の申込の行は記録だけにする
- 定期起動（10分ごと）が先に処理してしまった場合は、手で起動した完了表示が変わる（対象が無い旨が出る）。その場合も、申込状況の結果で合否を付ける
- 日程の日時は、実行日の1日の中で通せるように決める（試験用）。順序は、オンライン受付の開始＜申込を行う時刻＜オンライン受付の終了＜日程の開始
- 用意するデータ（試験用の値。設計書の値ではない）
  - 店舗の読み替え：流す前に、開発環境の既存の店舗から、イベントの開催店舗にでき、店舗チームの担当者に編集権限を付けられる店舗を1つ選び、店舗IDと画面に出る名前を控える。店舗は新しく作らない（本店は店舗ID 1で、画面によって「Hareruya」「トーナメントセンター 東京」と出る）。以下の「店舗A」は、控えた名前に読み替える
  - 店舗チームの担当者（開催店舗「店舗A」の編集権限がある）
  - 会員：試験 三郎（本会員、メールアドレス `uev-05@example.test`、国内（東京都）の住所を登録済み、選手情報あり）。複数件の行（T02・T04・T06）では、もう1人、試験 四郎（メールアドレス `uev-05-b@example.test`、同じ条件）を使う
  - イベント「シナリオ試験 スタンダード大会（有料）」（英語名 Scenario Test Standard Tournament）：店舗＝店舗A、フォーマット＝スタンダード、ルール適用度＝競技、イベント規模＝定番イベント、公開状態＝公開、定員＝8、チーム戦＝オフ、支払方法＝クレジットカード決済、参加費＝1,000円
  - 日程1：開始＝実行日20:00、受付あり（受付時間 19:30〜19:50）、デッキ登録あり・デッキ登録締切＝実行日19:00、オンライン受付あり（開始＝実行日0:00、終了＝実行日19:00）、定員8・参加費1,000円・公開状態は親イベントを引き継ぐ
