# イベント管理のキャンセル申込と返金（UEV-03）

IPA「高信頼化ソフトウェアのための開発手法ガイドブック」(2010) の表6-9〜6-11と同じ手順で作る。

1. 因子・水準表（FL表）: `fl_table.tsv`。お客様と店舗チームが画面で選ぶもの・変わるものを因子にし、設計書の文を根拠に持つ
2. 禁則表: `prohibitions.tsv`。ありえない組み合わせは無い（空）
3. 組み合わせテストマトリクス: `matrix.md` / `matrix.tsv`。`build_matrix.py` が作る。1行が1本のシナリオになる
4. 例外の差し込み表: `exceptions.tsv`。エラーや中断は、正常な値と混ぜず、条件に合う行へ1つずつ差し込む

## 範囲

- お客様の都合によるキャンセル。申し出（お問い合わせ）から、店舗チームが申込状況を「キャンセル済み」にし、返金を依頼・処理し、お客様にキャンセル完了を知らせるまで（業務フロー2-3〜2-8）。キャンセルの期限はイベント前日23時59分まで
- 前提（2026-11-05）：期限（前日23時59分）の前に申し出るので、申し出る日程の開始はあらかじめ翌日以降にしておく（開始が当日または過去の日程は、期限を過ぎていて申し出の前提を満たさない。通しシナリオ UTH-04 の指摘）。全行に共通
- 返金（2-6 返金依頼・2-7 返金処理）はシステムの外。まとめて決済した一部の日程だけを取り消すときの返金額・方法は、設計書・業務フローに無く判断待ち。新実装のイベント決済の処理は、決済画面への転送・結果の復号・取引照会だけで、SPLINKSの請求の取消・減額を呼ぶ処理が無い（新実装 EventSlnLinkPaymentService）。キャンセル完了の連絡（2-8）も、新実装にイベントのキャンセルメールが無く、店舗チームが手でメールを送る
- イベントの支払方法はクレジットカード決済だけ（0307 大会申込「お支払方法はクレジットカード決済のみ」・0214 イベント編集 (1-13)）。全額ポイント支払い・登録済みカードの選択肢はイベントに無いので、因子にしない
- 各行の期待値：申込状況が「キャンセル済み」になり、変更した申込ごとに申込履歴が1件増える（取り消す範囲が複数日程なら、その日程の申込の数だけ増える）。キャンセル済みは定員に数えず、空きが戻る（開発環境の申込状況マスタで、数えない設定は「キャンセル済み」だけ）。マイイベント・デッキ登録の一覧は、デッキ未登録なら申込が消え、デッキ登録済みなら「デッキを登録したイベント」として残る。同じ日程にもう一度申し込める（0307 大会詳細「申込済みの判定は…取消以外の申込に含まれること」）。参加ポイントは開催日にポイントグランターで付与するので、キャンセルで戻すポイントは無い。有料の行は返金のあと、お客様にキャンセル完了のメールが届く。無料の行は返金が無く、キャンセル完了の連絡だけ
- キャンセル待ちの仕組みは、設計書・新実装に無い
- 範囲外（`../scenario_list.md`）：キャンペーン対象の返金（UEV-04）、店舗の都合による中止（UEV-08。日程の削除の失敗もそちら）、決済前の中止・決済の離脱（UEV-02 の例外・UEV-05）

## まとめた水準

- キャンセル理由：「都合が悪くなったため」「他のイベントに参加するため」「体調不良のため」「同種の予選等を既に通過したため」の4種は、同じ入力・同じ送信で、店舗チームの申込状況の変更と返金は変わらないので、1つの水準（F1）にまとめた（新実装 お問い合わせ画面のスクリプト。理由は店舗への情報）。「その他」は追加の理由欄の入力と、空のときの送信停止があるので別の水準（F2）にした
- 期限の前後：期限（前日23時59分）をお問い合わせフォームが確かめる処理は新実装に無い。期限の後の申し出をどう扱うかは設計書・業務フローに無く、判断待ち（`../scenario_list.md`）。この表の行はすべて期限の前

## 実装・設計書で確かめたこと（2026-11-05）

- キャンセル申込みの導線は、エントリーフラグが真で、事前予約期間内で、定員未満のときだけ出る。キャンセルの期限は前日23時59分（お問い合わせフォームの文言「イベントのキャンセル期限はイベント開催日の前日23時59分までになります。」）。オンライン受付が前日より前に終わる日程では、受付終了から前日23時59分のあいだ、詳細画面の入口が出ない（A2）
- 新実装の申込状況の更新（管理画面）は、申込履歴を1件記録し、返金やメール送信の処理を持たない（新実装 EntryUpdateAction）
