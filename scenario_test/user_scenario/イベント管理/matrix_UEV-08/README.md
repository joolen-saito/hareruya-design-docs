# イベント管理の店舗都合の中止（UEV-08）

IPA「高信頼化ソフトウェアのための開発手法ガイドブック」(2010) の表6-9〜6-11と同じ手順で作る。

1. 因子・水準表（FL表）: `fl_table.tsv`
2. 禁則表: `prohibitions.tsv`（ありえない組み合わせは無い）
3. 組み合わせテストマトリクス: `matrix.md` / `matrix.tsv`。`build_matrix.py` が作る
4. 例外の差し込み表: `exceptions.tsv`

## 範囲

- 店舗チームの都合で日程を中止する。業務フロー・設計書に店舗都合の中止の手順が無く、設計書にある道具（日程の公開状態・申込一覧の一括編集・申込詳細編集）から組み立てた（判断待ち。`../scenario_list.md`）
- 手順（システムの内）：日程を「非公開」にして新規の申込を止める → 申込一覧で対象の申込をキャンセル済みにする（申込のある日程は削除できないので、削除は選べない） 。お客様への中止の連絡と、有料の申込の返金は、業務フロー08の連絡・返金（2-6〜2-8）がお客様の「キャンセル申込」を起点とする工程で、店舗都合の中止の対応は設計書・新実装に定めが無いので、判断待ちとし、期待値に入れない（新実装の一括更新は状態と履歴を更新するだけで、連絡・返金を持たない）。日程を非公開にするのは、公開のままだとキャンセルで空きが戻り、受付期間内なら新たに申し込めてしまうため（0307 大会詳細「エントリーフラグが真で、現在日時が事前予約期間の開始日時以上かつ終了日時以下で、定員が申込済み人数より多いときだけ（申込の導線を）表示する」。非公開の日程は詳細・申込画面に出ない）
- 各行の期待値：日程がイベント大会TOP・詳細・申込に出なくなる。対象の申込が「キャンセル済み」になり、変更した申込ごとに申込履歴が1件増える。デッキ未登録のお客様は、マイイベント・デッキ登録の一覧から消える。デッキ登録済みなら「デッキを登録したイベント」として残る。連絡・返金は判断待ち（システムの状態の期待値に入れない）
- 決済中の申込は含めない：一括編集は申込状況と履歴を変えるだけで取引の照会をしない。決済の結果の確認（戻りの処理・決済処理中チェックバッチ。UEV-05）は決済中の申込だけが対象で、先にキャンセル済みにすると成否を確かめられない。決済が確定してから扱う（判断待ち）
- 申込を1日程ずつ・まとめてのどちらで決済したかは因子にしない（まとめ決済の一部取り消しの返金は判断待ち。UEV-03）

## 実装・設計書で確かめたこと（2026-11-05）

- 一括更新（新実装 EntryStatusBulkUpdateAction）は、選んだ申込ごとに状態を書き換え、申込ごとに履歴を1件記録する。返金やメールの処理は持たない
- 日程の削除は、申込やデッキ登録がある日程にはできない（0214 イベント編集。新実装は日程に紐づく申込があれば削除させない）
