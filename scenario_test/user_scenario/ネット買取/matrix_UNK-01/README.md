# ネット買取のお客様の申込（UNK-01）

IPA「高信頼化ソフトウェアのための開発手法ガイドブック」(2010) の表6-9〜6-11と同じ手順で作る。

1. 因子・水準表（FL表）: `fl_table.tsv`。お客様が申込の画面で選ぶもの・変わるものを因子にし、設計書の文を根拠に持つ
2. 禁則表: `prohibitions.tsv`
3. 組み合わせテストマトリクス: `matrix.md` / `matrix.tsv`。`build_matrix.py` が作る。1行が1本のシナリオになる
4. 例外の差し込み表: `exceptions.tsv`。エラーや中断は、マトリクスの行に1つずつ差し込んで別のシナリオにする

エラーになる値は、正常な値と混ぜて組み合わせない。混ぜると、先にエラーになった値に隠れてほかの値が確かめられないため。

## 範囲

- 本店のネット買取で、会員がカートに商品を入れ、買取依頼内容を記入して申し込み、買取依頼完了画面と買取受付メールが出るところまで。非会員は申し込めない（0305「買取カートに商品があり、会員としてログイン済みであることを…前提とする」）
- 郵送（システムの外）以降は UNK-03 以降で扱う。本人確認は UNK-02、簡易書留は UNK-06・UNK-07
- 買取価格が500円未満の商品はカートに入れられない（0305）ので、用意する商品は500円以上にする。まとめて買取の商品は専用の1商品で、価格表示は「システム都合」（実際の査定金額とは関係ない）

- 申込は、会員の本人確認の状態に関わらず通る（因子K）。確定の判定は買取カート・ログイン・入力の妥当性だけで、本人確認の状態を見ない（0305「確定時の判定順序」）。本人確認の証明が要るのは、あとで振込依頼済みにするとき（UNK-04）。完了画面に「オンライン本人確認について」の案内がある（0305「買取依頼完了」(3)）

## まとめた水準

| 因子 | まとめた種類 | 代表 | 根拠 |
|---|---|---|---|
| 口座種別（G） | 普通・当座・貯蓄 | 普通 | 0305 (15)「選択肢：普通、当座、貯蓄」の選択肢が違うだけで、入力検査・登録・画面の表示に種類ごとの分岐の記載が無い。新実装の申込フォームも口座種別を選択肢として保存するだけ |
| 会員の本人確認の状態（K） | 未確認・確認中・オンライン本人確認済み・簡易書留確認済み | 未確認 | 0305「確定時の判定順序」は、カート・ログイン・入力の妥当性だけで、本人確認の状態を見ない。申込の流れ・画面・期待値が変わらない（本人確認の状態が効くのは振込依頼済みのとき：UNK-04） |

分けたままにしたもの：探し方（B）・カートに入れる画面（C）・商品の選び方（D）・職業と生年月日（E）・振込口座（F）・箱数（H）・承諾方法（I）・適格請求書（J）。画面・入力欄・保存する内容のどれかが違うため。

## 実装で確かめたこと（2026-11-03）

- 箱数：新実装の設定は最小1・最大20・警告基準3。警告は申込みを妨げない（H2）
- 職業・生年月日の入力欄：新実装は、会員情報の職業が空のときは職業欄、生年月日が空のときは生年月日欄をそれぞれ出し、どちらも入力必須。両方が空なら両方出る。水準E2は両方が未登録、E3は職業だけ、E4は生年月日だけが未登録のとき（0305(11)(12)は各欄を未登録のときに別々に出し、出た欄は入力必須）
- 承諾方法：選んだ内容は買取受注の自動承諾の印として保存されるだけで、申込の時点で状態は変わらない（新実装・現行 pf-eccube3 とも）。承諾方法に応じた後の動きは UNK-04 で扱う
- 申込の確定で、買取受注は状態「注文」で登録される（0305 業務ロジック「買取受注は状態「注文」で登録し」）
