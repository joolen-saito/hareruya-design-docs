# ネット買取のオンライン本人確認（UNK-02）

IPA「高信頼化ソフトウェアのための開発手法ガイドブック」(2010) の表6-9〜6-11と同じ手順で作る。手順と表の役割は `../matrix_UNK-01/README.md` と同じ。

## 範囲

- 会員がマイページのオンライン本人確認で身分証を申請し（本人確認ステータス：未確認→確認中）、店舗チームが会員編集のオンライン本人確認で確かめて「オンライン本人確認済み」にし、お客様に完了メールが届くところまで
- 問題ありの場合（水準C2。身分証そのものの問題も、身分証と登録情報が合わない場合も含む）は、手動メール通知で再申請を依頼し、お客様に本人確認失敗メールが届くところで終わる。そのあと、システムは「確認中」のままお客様の再申請を待つので、再申請以降は別のシナリオ UNK-10 にする（R2指摘）
- 禁則は無い（端末・身分証の種類・確認結果はどの組み合わせも成り立つ）。禁則表は見出しだけ

- 本人確認の証明（身分証）は、買取の振込依頼済みの条件になる（UNK-04・UNK-07）。申請の提出が無い（撮影しない・同意しない）ときは申請が確定せず、ステータスは変わらない（例外E1・E2）
- 身分証と登録情報が合っているかは、システムが照合せず店舗チームが画面で確かめる（業務フロー1-8「その内容と登録情報を確認する」）。身分証有効期限が過去の日付でも確認済みにできるかは、設計書に決まりが無い（scenario_list.md に記録）

## まとめた水準

| 因子 | まとめた種類 | 代表 | 根拠 |
|---|---|---|---|
| 身分証の種類（B） | 自動車運転免許証・パスポート・外国人登録証明書・学生証社員証・身体障害者手帳 | 自動車運転免許証 | 0306 (3-4)〜(3-6) は表・裏・斜めの撮影を種類によらず求め、種類で分けるのはマイナンバーカードだけ（(3-5)を非表示）。新実装も画面と検査で種類を分けるのはマイナンバーカードだけ（`MtbIdentification::MY_NUMBER_CARD` の判定）。開発環境の身分証の種類のマスタで、この5種類は同じく表示される（住民基本台帳・健康保険被保険者証は表示なし。0306 は「住民基本台帳カード…除外」） |
| 店舗チームの確認結果の問題あり（C） | 身分証そのものの問題・登録情報と合わない | 問題あり | 業務フロー14は「身分証問題ないか」の1つの判断で、問題ありの先は手動メール通知で再申請を依頼する同じ流れ（1-9・1-10）。システムの処理も画面も同じ |

分けたままにしたもの：端末（A。PCはQRコード、スマートフォンは直接で画面が違う）・マイナンバーカード（裏面の撮影が無い）・確認結果の問題なしと問題あり（終点が違う）。

## 実装で確かめたこと（2026-11-03）

- 申請の確定で、本人確認ステータスは「確認中」になり、本人確認申請完了メールが会員に届く（0306 業務ロジック「本人確認ステータスを確認中へ変更して保存する。そのうえで本人確認申請完了メールを送信する」）
- 確認済みの会員が氏名・カナ・住所・生年月日を変えると、本人確認ステータスは「未確認」に戻る（0306 会員情報変更「住所系または氏名・カナ・生年月日を変更し、変更前のステータスが該当するとき。本人確認ステータスを未確認へ戻す」）。確認中のままのときは戻らない。再申請（UNK-10）で情報を直すのは確認中のときなので、ステータスは確認中のまま
- 業務フロー1-8「お客様に通知したメールと同じメールがネット買取に届く」：新実装・現行とも、申請完了メールの返信先とBccは買取専用メールアドレス（0306 業務ロジック「返信先と Bcc には、買取専用メールアドレスに設定した宛先を用いる」）
