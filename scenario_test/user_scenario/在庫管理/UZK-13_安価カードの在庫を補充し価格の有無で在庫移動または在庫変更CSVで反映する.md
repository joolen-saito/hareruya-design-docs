# UZK-13 安価カードの在庫を補充し、価格の有無で在庫移動または在庫変更CSVで反映する

| 項目 | 内容 |
|---|---|
| 利用者 | 商品管理チームの担当者（補充の作業）→ 価格が付くカードは出庫・入庫の担当者、価格が付かないカードはインポート担当者 → 在庫の承認者 |
| 目的 | 安価カードの在庫を補充するとき、現在庫データをダウンロードして補充用ファイルを更新し、補充するカードと枚数を決めてピックする。補充するカードに価格が付く（在庫管理されている）なら、地下2F在庫（本店バックヤードのB2F）から通販・店舗へ在庫移動して入庫完了にし、価格が付かないなら、在庫変更CSVを承認して在庫に反映する。最後に補充用ファイルを更新する |
| 種類 | 正常（3つの経路。この2経路は排他） |
| マトリクスの行 | `matrix_UZK-13/matrix.md` のT01（補充するカードの価格＝価格が付く（地下2F在庫から通販・店舗へ在庫移動し、入庫完了が終点））。T02・T03は「L3で変わるところ」 |
| もとのシナリオ | SCN-ZAIKO-014・015・034 |

## 前提

- 共通の決まり：`../L4を流すときの共通の決まり.md` を先に読む（試験データの名前にシナリオIDを付ける・共有の設定は元に戻す・バッチの起動・店舗の読み替えなど）
- システムの外で済んでいること：補充用ファイル（別途用意してある、補充するカードの一覧とバックヤード状況のファイル）、並び順ファイル、バックヤード残数ファイル
- 用意するデータ（試験用の値。設計書の値ではない。行ごとに別の商品を使う）
  - T01：カード「シナリオ試験カードN01」（商品コード「UZK13-T01」、安価カードで価格が付く）。本店バックヤード（B2F）のEC-CUBE在庫10・原価単価50円（総原価500円）。本店（2F通販在庫）のEC-CUBE在庫2・原価単価50円（総原価100円）
  - T02：カード「シナリオ試験カードN02」（商品コード「UZK13-T02」、価格が付かない。本店のEC-CUBE在庫2）
  - T03：カード「シナリオ試験カードN03」（商品コード「UZK13-T03」、価格が付かない。本店バックヤードのEC-CUBE在庫0、本店のEC-CUBE在庫2）
  - 担当者：商品管理チームの担当者、出庫・入庫の担当者、インポート担当者、在庫の承認者（別の担当者。承認通知先に入る）
- 出力項目設定「通常作業用」は UZK-02・UZK-14 と同じ内容（商品コードと「在庫(通販+TC東京)」の列を含む）にしておく
- 補充する枚数：5。補充用ファイルのパターンは2通り（パターン1：ダウンロードしたデータを補充用ファイルに反映／パターン2：並び順ファイルとバックヤード残数ファイルを使う）。ファイルの作業はシステムの外

## 操作の流れと期待値

| # | 操作する人と操作 | 期待値（画面で見えること） |
|---|---|---|
| 1 | 商品管理チームの担当者：管理画面の商品管理＞商品マスター（商品一覧）で、補充範囲に応じて言語や状態を絞り込んで検索し、「カスタムデータCSVダウンロード」で出力項目設定「通常作業用」を選んでダウンロードする（業務フロー12の8-1。ダウンロードするファイルをなるべく軽くする） | 絞り込んだ商品のCSVがダウンロードされる。「UZK13-T01」の行が入っている |
| 2 | 商品管理チームの担当者：補充用ファイルを更新する（システムの外の作業。8-2）。パターン1：ダウンロードしたデータで、在庫数・販売/買取価格・各期間の販売数を、別途用意してある補充用ファイルに反映させる（並び順ファイルとバックヤード残数ファイルは使わない）。パターン2：ダウンロードした在庫データに並び順ファイルの並び順を充て、バックヤード残数ファイルから各カードのバックヤード残数を補充用ファイルに反映する | 画面の変化は無い |
| 3 | 商品管理チームの担当者：各種補充用のフィルター条件で、補充するカードと枚数を決めてピックする。別の担当者がピックしたカードの種類・枚数をダブルチェックする（システムの外の作業。8-3・8-4） | 画面の変化は無い。補充するカード「UZK13-T01」を5枚と決まる |
| 4 | 出庫・入庫の担当者：管理画面の在庫管理＞在庫一覧で「UZK13-T01」を検索し、店舗「本店バックヤード」・在庫区分EC-CUBEの行にチェックを入れ、「在庫移動登録」を押す。入庫先店舗「本店」・入庫先在庫区分「EC-CUBE」を選び、移動点数に5を入れて「登録」を押す。確認の画面で「登録」を押す（8-5「補充するカードに価格が付く（在庫管理されている）場合は、地下2F在庫から通販または店舗に在庫移動を行う」。発送を伴わない移動処理。UZK-08のT03と同じ操作） | 「ピック・出庫承認申請」の画面が開き、ステータスが「新規登録」。本店バックヤードの在庫が10から5に減り、総原価が250円になる |
| 5 | 出庫・入庫の担当者：「店舗内入庫確定」を押し、確認の画面で「店舗内入庫確定」を押す（本店と本店バックヤードの間の移動は、同じ本店の中の店舗内移動として扱い、出庫承認・入庫承認を通らず店舗内入庫確定で入庫完了になる：依頼者の決定 2026-11-06。**新実装は同じ店舗のときだけ店舗内にするので、本店バックヤードから本店への移動では「店舗内入庫確定」が出ず「承認申請」が出て「出庫承認待ち」になる見込み。そのときは、この手順を不合格として記録し（食い違い。UZK-08の判断待ち1と同じ）、先へ進む別の手順として、UZK-06の手順4〜10とUZK-07の手順2〜6のとおり、出庫承認→移動指示→送り状No.の登録→入庫確認→入庫承認で「入庫済み」にする**） | ステータスが「入庫済み」（設計書の「入庫完了」）になる |
| 6 | 出庫・入庫の担当者：在庫一覧で「UZK13-T01」の本店バックヤードと本店の在庫・原価を確かめる。在庫移動振替一覧で、同じ移動をチェックして「在庫移動振替CSV出力」を押す | 本店バックヤードの在庫5（総原価250円）、本店の在庫が2から7になり、総原価が350円（100円＋出庫総原価250円）、原価単価50円。在庫履歴に、本店バックヤードの「在庫移動(減算)」と本店の「在庫移動(加算)」が残る。CSVに、出庫元店舗「本店バックヤード」・入庫先店舗「本店」・移動点数5・ステータス「入庫済み」が出る。移動中を通らないので、移動指示・送り状・在庫移動実績インポートは使わない |
| 7 | 商品管理チームの担当者：補充内容から、補充用ファイルのバックヤード状況等を更新し、指定されたフォルダに保存する（システムの外の作業。8-8） | 画面の変化は無い |

| T02 | 価格が付かない（在庫変更依頼を作り、在庫変更CSVが承認されて在庫に反映される） | 手順4・5は行わない（在庫移動を通らない）。手順4'：商品管理チームの担当者が、補充するカードと枚数を纏めた在庫変更依頼用のファイルを作り、インポート担当者に共有する（8-6。残すデータは「商品コード」「在庫変動数（補充する枚数）」「商品名」「略称タグ」「在庫数」「販売価格」「言語」。システムの外）。手順5'：インポート担当者が、在庫管理＞在庫変更CSV登録で、店舗「本店」・在庫場所「EC-CUBE」・在庫変動区分「入庫/GOOD抜き」（T03と同じ）・在庫変動理由「安価カード補充」を選び、承認通知先に承認者を選んで、在庫増減数5・仕入単価0のCSVを「一括登録を実行」する（8-7）。手順6'：承認者が在庫編集承認一覧で一括承認する（UZK-01の手順6と同じ）。承認状態が「承認済」になり、本店の在庫が2から7になる（総原価は変わらず、原価単価は下がる）。手順7は代表と同じ |
| T03 | 価格が付かない補充分を仕入単価0円（GOOD抜き）で入庫し、そのあと在庫移動で2F通販在庫へ移す | 手順4・5は行わない。手順4'：T02の手順4'と同じく、在庫変更依頼用のファイルを作ってインポート担当者に共有し、在庫変更CSV（商品コード「UZK13-T03」・在庫増減数5・仕入単価0）を作る（8-6。システムの外）。手順5'：インポート担当者が在庫管理＞在庫変更CSV登録で、店舗「本店バックヤード」・在庫場所「EC-CUBE」・在庫変動区分「入庫/GOOD抜き」・在庫変動理由「安価カード補充」を選び、承認通知先（所属・メンバー）に承認者を選んで、CSVを「一括登録を実行」する。登録だけでは未承認で、本店バックヤードの在庫は0のまま（在庫編集承認一覧に承認状態「未承認」で出る）。手順6'：承認者が在庫編集承認一覧で、登録した行にチェックを入れ、「一括承認」を押し、確認の画面で「承認する」を押し、最後の確認「本当に承認してもよろしいですか？」で「OK」を押す。承認状態が「承認済」になり、本店バックヤードの在庫が0から5になり、総原価は0円のまま（仕入単価0円×数量5＝0円を総原価に足す。在庫数だけ増える）。続けて、手順4・5のとおり本店バックヤードから本店（2F通販在庫）へ5点を在庫移動する。移動時点の原価（総原価0円）の移動分が出庫元から引かれて入庫先に足される。本店の在庫が2から7になり、総原価は変わらない（0円が足される）。手順5は代表と同じ扱い（店舗内入庫確定。出ないときは不合格として記録し、別の手順で先へ進む） |
