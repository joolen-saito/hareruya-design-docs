# 在庫管理の店舗間の在庫移動：登録から出庫承認・移動中まで（UZK-06）

IPA「高信頼化ソフトウェアのための開発手法ガイドブック」(2010) の表6-9〜6-11と同じ手順で作る（FL表→禁則表→2因子間網羅の組み合わせ）。例外（エラー・中断）は正常な値と混ぜず、`exceptions.tsv` で条件に合う行へ1つずつ差し込む。

## 範囲

- 店舗間の在庫移動を、出庫元が登録し、出庫を承認され、移動指示に送り状No.を登録して「移動中」になるまで（終点）。入庫側は UZK-07
- 本店内（本店種別の店舗どうし）と同一店舗内の移動は UZK-08。出庫承認で却下された場合の終点は「却下」（`exceptions.tsv` E6・E7）
- 在庫区分がスマレジ（水準C2）のときの、承認後のスマレジ在庫への反映は、スマレジ連携のUSM-03で確かめる。このマトリクスは移動の登録から移動中までを通し、スマレジ側の在庫数は期待値に入れない
- 起点の業務イベント（在庫リコメンド・成田倉庫への間引き・支店からの依頼・成田倉庫からの戻し・棚卸後の余剰分の配送・別部署からの発送依頼）は、画面上は同じ登録画面なので因子Bの出庫元→入庫先で表す

## 実装・設計書で確かめたこと（2026-11-03）

- 移動指示から出す帳票（因子G。2026-11-05追加）：送り状CSV出力（M04-28）は在庫移動指示検索で指示を選んで出し、項目は設計書に定めがある。ピッキングリスト印刷（M04-26）と在庫移動実績入力用CSV出力（M04-27）は、0202 の目次が「不要となった」「廃止」としながら、シートと在庫移動指示検索の3-2が残る（設計書の中で決まらない。adjudication-ledger.tsv ADJ-049・ADJ-050・ADJ-086）。新実装は、実績入力用CSVを在庫移動指示検索から出し（列は「移動指示ID」「送り状No.」）、ピッキングリストは出庫承認依頼の画面から出す。出力する操作は業務フローの工程なので手順に入れる（G2・G3・三帳票をそろえるG4）。目次の不要・廃止と、シート・ボタンが残る矛盾の扱い（出力結果の合否の期待値）は判断待ちとして残し、期待値は設計書のシートの記述の範囲に限る

- 在庫移動の状態（開発環境のDBダンプ 2026-09-07）：新規登録・出庫承認待ち・却下・出庫承認済み・移動中・入庫承認待ち・入庫済み・振替承認待ちの8つ。設計書は最後を「入庫完了」と書く（扱いは同じ）。別添資料の状態遷移概要（2025-09-18）にある「差し戻し」「差し戻し承認済み」「棄却」は、あとの改訂（0202 在庫移動・振替登録 編集 (移動) 2026-02-06）の「入庫承認待ち」「入庫再確認」に置き換わっていて、開発環境にも無い
- 店舗間の移動は在庫区分を変えられない（EC-CUBE↔スマレジは禁止）。店舗内だけ別区分を選べる（0202 在庫移動・振替登録 編集(振替)）
- 成田店は開発環境の店舗設定で本店扱いではない。本店扱いは本店と本店バックヤードの2店
- 欠品CSVは、欠品点数が移動点数を超えるときだけ取込エラーにする（新実装の欠品CSV取込の処理）。移動1点・欠品1点は取込できるので、欠品CSV（E3）は移動点数1点とも組み合わせる。画面の欠品登録ボタンは「移動点数より少ない」ので1点とは組み合わせない（禁則X1）
- 新実装も、送り状No.を登録すると移動中になり、出庫承認の却下でステータスが却下になる（在庫移動指示の送り状登録・出庫承認却下の処理）

## まとめた水準

なし（どの水準も処理が違う）。主な根拠：画面登録とCSV登録は入口が違い、移動の方向（支店→本店のトレードチーム宛は3Fに入庫・本店→支店の依頼・本店→成田の間引き・成田→本店の戻し）は業務の目的が違う。EC-CUBE在庫とスマレジ在庫は区分をまたげない決まりがあり、欠品点数・送り状Noの登録方法も画面・CSVで処理が違う。
