# UKA-05 15時の自動入庫で、入庫待ちの買取がEC在庫に入り、入庫済みになる

| 項目 | 内容 |
|---|---|
| 利用者 | システム（毎日15時の買取自動入庫バッチ）→ 店舗チーム（結果を管理画面で確かめる）→ 入荷通知メールを受け取る会員 |
| 目的 | 毎日15時に、入庫待ちの買取が、買取を行った店舗のEC在庫に買取数だけ入り、ステータスが「入庫済み」になる。在庫履歴が残り、本店のEC在庫が0から1以上になった商品は、入荷通知を依頼した本会員に入荷通知メールが届く |
| 種類 | 正常（組み合わせ表の2行）＋例外2件 |
| マトリクスの行 | `matrix_UKA-05/matrix.md` のT01（買取を行った店舗＝本店（TC）・15時の時点の買取＝入庫待ちの買取・自動入庫のバッチ＝毎日15時に動く）。T02（支店）は「L3で変わるところ」 |
| もとのシナリオ | SCN-KAITORI-001・004（後段）。業務フロー06の1-10（買取商品自動入庫バッチ） |

## 前提

- 共通の決まり：`../L4を流すときの共通の決まり.md` を先に読む（試験データの名前にシナリオIDを付ける・共有の設定は元に戻す・バッチの起動・店舗の読み替えなど）
- 起点の買取（15時の時点で入庫待ち）
  - T01：UKA-02 の T01 の終点（UKA-01 の T04 の終点を、経理が経理払い出し済みにした買取）。本店（店舗ID 1。画面によって「Hareruya」「トーナメントセンター 東京」と出る）・ステータス「入庫待ち」・買取金額1,900円・数量5（「店頭買取試験カードA」×2＝800円・「店頭買取試験カードB」×3＝100円）。この試験専用に1件作る
  - T02：UKA-01 の T03 の終点（会員でログインして申込・出金＝レジ・買取品＝登録済みの商品だけ・支店・住民基本台帳カード）。流す前に既存の店舗から店舗識別子を持つ支店を1つ選び、店舗ID・画面の名前を控えて、以降の「支店」を読み替える。ステータス「入庫待ち」・買取金額1,900円・数量5。この試験専用に1件作る
- バッチは毎日15時に動く設計（0406 B06-01）だが、時刻は待たず、手で起動する（2026-11-26 決定）。買取自動入庫バッチは、店頭買取とネット買取の入庫待ちの両方を処理する1本のため、共有の開発環境にある他の入庫待ちの買取も同時に入庫される（記録。記録欄）
- 入荷通知（T01で確かめる）
  - 入荷通知メールの許可：設定＞店舗設定＞追加システム設定の「入荷通知メールの許可」。流す前に今の値を確かめて控え、「送らない」のときだけ「送る」にする（初期データは「送らない」）。確かめ終わったら元の値に戻す（手順8）。T02だけを流すときは、この設定を変えない
  - 試験用の本会員M：「店頭買取試験 通知会員」（`uka05-notify@example.test`）。「店頭買取試験カードA」（日本語・NMの規格。公開の商品）の入荷通知をフロントで依頼済み（商品が在庫切れのとき出る「入荷通知」を押し、確認「入荷通知依頼を行いますか?」で進み、「入荷通知を設定しました」が出る）。商品Aの本店のEC在庫は0にしてから流す（試験で作った商品に限り、在庫変更CSV登録などで0にしてよい）
- 手順の前に控える値：「店頭買取試験カードA」「店頭買取試験カードB」の買取店舗のEC在庫・総原価・原価単価、買取詳細の入庫日時（空）・最終更新者・ステータス変更履歴の行数
- 画面の名前は新実装の表示で書く

| # | 操作する人と操作 | 期待値（画面で見えること） |

| 3 | 店舗チーム：買取一覧と買取詳細で、手順1の買取を見る | ステータスが「入庫済み」になる。買取詳細の入庫日時が入る（0205 買取詳細「データが入るタイミングは入庫済みステータスに変更したタイミング」）。最終更新者は変わらない（0406「店頭買取情報の最終更新者は更新しない」）。買取金額・明細は手順1のまま。棚戻し済みは「未」のまま |

| 5 | 店舗チーム：在庫管理＞在庫履歴一覧で、AとBの商品コードを検索する | 買取店舗・在庫場所「EC-CUBE」の行が、AとBに1行ずつ増える。在庫変動数はA＝2・B＝3、変更前在庫・変更後在庫の差がAは2・Bは3（バッチは環境の入庫待ちを順に処理し、処理の時点の在庫を履歴に残すので、同じ商品の別の買取があると、変更前・変更後の値は手順1・4の値と合わない。合否は差で付け、手順1・4の総数との一致は求めない）、在庫変動理由「買取/店頭買取」（画面は「区分/内訳」の形。初期データは区分「買取」・内訳「店頭買取」）、在庫変動理由の文言「店頭買取による入庫 査定ID：（査定番号）」、仕入単価はA＝800円・B＝100円（買取単価）。登録元は「買取自動入庫バッチ」。登録元IDは査定ID（設計書）。変更前総原価・変更後総原価がA・Bとも小計の分だけ増える |
| 6 | 会員M（T01のみ）：入荷通知の依頼に使ったメールの受け口を開く | 手順2のバッチのあと、商品A（本店のEC在庫が0から1以上になった公開の商品）の入荷通知メールが届く（件名「ご希望いただいていた商品が入荷いたしました」）。Bは依頼が無いので誰にも届かない。入荷通知メールの許可が「送らない」のときは届かない |

## 記録（判断待ちではない。合否は付けず、実際の画面・値を記録する）

- （見たもの：0406 B06-01 は店頭買取とネット買取の両方を1つのバッチで処理すると書く。共有の開発環境には他の試験の入庫待ちの買取がある）手で起動すると、この試験の買取以外の入庫待ちの買取も入庫される。おすすめ：記録で済む。流す前に他の入庫待ちの買取を確かめ、この試験の買取のAとBの増えた分（2・3）だけを期待値にする（他の試験の買取に同じ商品が含まれていないことを前提にする）

設計書との食い違い（起票しない）
- 0406 B06-01 の「登録元IDは査定ID」。査定番号は「年月日-店舗ID-連番」の文字列で、新実装は在庫履歴の登録元IDを数値に変換して保存するので、日付の数字（例：20261126）になる見込み（読んだコードからの推定で実機未確認）。そのとき手順5の登録元IDは不合格として記録し、先へ進む
- 0406 B06-01 は、店頭買取の入庫済みへの更新で入庫日時・ステータス変更履歴を残すとは書かない一方、0205 買取詳細は入庫日時を入庫済みへ変えたときに入れると書く。新実装のバッチは状態の更新だけを行う見込み（上の「終わったあとに確かめること」）
- 0406 B06-01 のステータス番号の誤記は `scenario_list.md` に記録済み
