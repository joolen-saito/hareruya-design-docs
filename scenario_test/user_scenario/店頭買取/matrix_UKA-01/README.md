# 店頭買取の申込から買取成立まで（UKA-01）

IPA「高信頼化ソフトウェアのための開発手法ガイドブック」(2010) の表6-9〜6-11と同じ手順で作る。

1. 因子・水準表（FL表）: `fl_table.tsv`。お客様と店舗チームが画面で選ぶもの・変わるものを因子にし、設計書の文を根拠に持つ
2. 禁則表: `prohibitions.tsv`。ありえない組み合わせ（今回は無い。下記）
3. 組み合わせテストマトリクス: `matrix.md` / `matrix.tsv`。`build_matrix.py` が作る。1行が1本のシナリオになる
4. 例外の差し込み表: `exceptions.tsv`。エラーや中断（★の手順）は、マトリクスの行に1つずつ差し込んで別のシナリオにする

## 範囲

- お客様が店頭買取の査定を申し込み、買取端末（MTGバイヤー）で査定・承諾し、出金して、買取成立または経理払い出し待ちになるまで（通る状態：査定前→査定中→（経理払い出し待ち）→買取成立→入庫待ち／未登録在庫あり）
- 全品キャンセル（UKA-03）、経理が振り込んで買取成立にする部分（UKA-02）、未登録在庫の実在庫登録（UKA-04）、自動入庫（UKA-05）は別のシナリオ
- 一部キャンセルはフェーズ2で見送り（`functions/phase2_specs.json` 0205-M06-03・0506-A06-14）。因子に入れない

- 買取品の中身：金額指定（「1円」「2円」「5円」「10円」で追加）の行も、個別入力と同じく商品規格IDを持たず個別入力商品になり、買取成立のあと未登録在庫ありになる（0601・0506）。水準G3として、個別入力（G2）と別にテスト行へ入れた

## 本人確認（2026-11-05 追加）

- 因子J：査定端末の身分証スキャン画面で選ぶ書類の種類（0601の7種）。流れ・処理・期待値が変わらないので、代表の1つにまとめた（下の「まとめた水準」）
- 身分証の画像が端末に無いまま査定開始する（E23）・種類を記録できない（E24）は、正常な値と混ぜずに例外で扱う。E23は、その受注の両面の画像が端末に残っていれば成り立たない（査定端末は画像ファイルの有無で判定する）。停止するとき買取のステータスは、受注を選んだ時点で査定中（再開した受注は査定再開）になっている
- 査定開始前に、身分証スキャン画面が「スキャンした身分証と住所登録を照合してください。」と表示する（査定端末のソース `IdentificationScan.xaml` 105〜106行）。照合の結果はシステムが判定も記録もしない。期限切れ・氏名の不一致・住所の不一致のときの扱い・未成年の保護者同意書は、設計書・実装に確認が無いので因子にも例外にもしていない（`../scenario_list.md` の食い違いに判断待ちとして記録）

分けたままにしたもの：
- 受付のお客様（A）・年齢（B）・言語（C）・国（D）・適格請求書発行事業者（E）・出金の方法（F）・ダブルチェック者（I）：流れまたは画面の表示・期待値が変わる
- 買取品の中身（G）：金額指定（G3）は、個別入力（G2）と買取成立のあとの結果（未登録在庫あり）は同じだが、査定端末の操作・必須項目が違う（個別入力は5項目すべて必須、金額指定は金額の選択と枚数だけ）ので分けた
- 開発環境の身分証マスターで表示しない種類（健康保険被保険者証・住民基本台帳カード）：表示の設定は、新実装のフロントの身分証の選択欄（表示する種類だけを出す）で使われ、店頭買取の査定端末の一覧（7種固定）と本人確認更新の処理には使われない。扱いが変わらないのでまとめた。マイナンバーカード（開発環境のマスタにあり、新実装のほかの画面では特別扱い）は、査定端末の一覧に無く選べないので水準に入れない（食い違いに記録）

## 禁則が無い理由

水準どうしを突き合わせて確かめた。10因子のうち、受付・年齢・言語・国・買取店舗は申込画面の入力で、本人確認書類の種類・適格請求書発行事業者・出金の方法・買取品の中身・ダブルチェック者は査定端末の操作で決まる。設計書にも、現行ソース（pf-eccube3）・新実装（ec-cube-enterprise）・査定端末のソースにも、一方の水準が他方を選べなくする記述は見つからなかった。

- 出金の方法F2（経理払い出し待ち）でも、印刷済みと登録番号の確認は買取成立と同じ条件で確かめる（0601）。端末取引IDだけがF1（買取成立）の条件
- ダブルチェック者の入力は買取成立の条件ではない。査定端末のソースでも買取成立・経理払い出し待ちの確認にダブルチェック者を見ていない
- 国がJapan以外でも言語はJPのまま申込める（0308に組み合わせの制限なし）

## 実装で確かめたこと（2026-11-03）

- 買取成立のあとのステータス：新実装は、買取成立を受け取ると続けて「個別入力商品が無ければ入庫待ち、有れば未登録在庫あり」にし、履歴を2件残す。経理払い出し待ちのときは経理チームへ振込依頼のメールを送る（新実装 UpdateOtcBuyOrderAction）。設計書 0506 と一致
- 査定端末（MTGBuyer の checkout は2026-09-08の版で古い可能性がある）：書類確認画面で、登録番号が未確認、印刷済みでない、端末取引IDが未入力・整数でないときに中止する文言がメッセージ設定にある。ダブルチェック者の更新は空・数値でない場合に文言があり、買取成立の条件には入っていない
- 申込の入口：新実装の店頭買取申込（フロント）は「/otcbuy/{店舗識別子}」。開発環境の店舗の設定（新実装リポジトリのDBダンプ 2026-09-07）で、識別子 tc は本店のTC（Hareruya Tournament Center Tokyo）、札幌・大阪・福岡などは支店。ブラックリストに該当する会員登録は、新実装でも会員を作らず申込だけを登録する
- 未成年：現行ソース pf-eccube3 の申込画面に「年齢が未成年ですが正しいですか？」のモーダルがあり、「はい」で次へ進む。会員でログインした申込にも同じモーダルがある
