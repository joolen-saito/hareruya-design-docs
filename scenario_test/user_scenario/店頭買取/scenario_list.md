# 店頭買取：シナリオ一覧（L2）

シナリオ1本は「起点の業務イベントから、業務として完了した状態になるまで」とする。担当者が替わっても切らない（お客様→店舗チーム→買取端末→経理→スマレジ）。日をまたいで、買取のステータスが何かを待つもの（経理の振込、15時の自動入庫、商品マスターの登録待ち）は別の1本にする。ただし、日をまたぐのがシステムの外の作業だけのとき（棚戻しの価格ソート・スリーブ入れ、店頭陳列など）は分けない。条件違いはL3のバリエーションとして、組み合わせテストマトリクス（ペアワイズ）で絞る。

業務フローは06と07（tobe版）。06は「tobeではなくこちらを新フローとして記載しています。」（06の索引表R3）と明記する新フローで、07は図の中に asis と tobe の区間を持つ。両者が食い違うときは、設計書（Excel由来の部分）に合う方を採り、扱いを下の「設計書との食い違い」に書いた。フェーズ2で見送る「一部キャンセル」はシナリオに入れない。

※1 買取成立のあとの「入庫待ち／未登録在庫あり」は、買取成立を受け取ったシステムが続けて自動で付ける（新実装で確認。履歴は2件残る）。経理に頼む場合は、査定端末が経理払い出し待ちにするだけで、買取成立はUKA-02で経理が付ける。

※6 業務フロー06・07の「買取履歴一覧」（06 の#33・#34、07 の#56・#57）は、在庫移動・振替（#35）の前、店頭商品の振り分け（1-11）のあとに置かれた定義済み処理で、同名の画面は設計書に無い。近い機能は、買取商品履歴（検索入力・検索結果・CSV出力。0205 のM06-05〜07。「実在庫情報変更履歴の検索」）と、買取一覧のダウンロード「買取商品一覧CSV」（M06-12）。0205の買取商品履歴(検索入力)のカスタマイズ説明は「実際に買取を行った商品についての情報がほしいため、買取一覧に実装する」と書く一方、同じ0205に基準価格・買取価格・申込者を出す買取商品履歴の画面とCSVの仕様が残り、設計書の中で決まらない。そのため、買取商品履歴の画面での確認（UKA-06）と買取商品一覧CSVの出力（UTH-03 手順25）の両方を試験に入れる。どちらを指すかは判断待ち。
※4 業務フロー06の1-11「※買取価格が0円商品の場合は、買取情報として残らない」。設計書0205の買取商品一覧CSVの対象は「チェック済みの買取情報に紐づく商品」「キャンセル済みでないもの」「部分キャンセルがされていないもの」で、価格0円を除かない。新実装のCSV抽出も価格で除かず、買取成立の処理は価格0の明細も数量のとおり実在庫にする。在庫移動の対象に0円が入るかは、設計書（0406・0506）にも見つからない。CSVに載ることは設計書・実装どおりと読めるが、業務フローの「残らない」との食い違いは決められない。
※3 設計書0205は、入庫済みボタンを押せる買取のステータスを書かない（実在庫情報の登録は「入庫待ちまたは未登録在庫あり」のときだけ）。新実装は、入庫済みへの変更を元のステータスで限らず、商品マスターに無い商品や実在庫登録の無い個別入力商品が残るとエラーにする。

### 設計書との食い違い（設計書の不足。起票はしない）

- 本人確認（06の1-4「受付時にコピーした身分証で本人確認を実施する」）のうち、住所の照合は査定端末の画面が指示するだけで（照合結果は判定も記録もされない）、氏名の一致・有効期限・期限切れのときの扱いの確認項目が設計書に無い。確認できなかったときに買取を止める処理も、設計書にも新実装・現行にも無い（本人確認が無くても、サーバ側は買取成立・経理払い出し待ちにできる）。システムで止まるのは、身分証の画像が両面そろわないと査定を始められない点だけ。判断待ち
- 未成年の買取に保護者同意書が必須か、同意書をシステムで確かめるかが設計書に無い。判断待ち
- 身分証の種類：0601の査定端末の一覧は7種（健康保険被保険者証・住民基本台帳カードを含み、マイナンバーカードが無い）。開発環境のマスターはマイナンバーカードを表示し、健康保険被保険者証と住民基本台帳カードを表示しない設定。査定端末は7種を固定で持つので、マイナンバーカードは選べない。マトリクスは査定端末の7種から、処理が変わらないので代表1つ（自動車運転免許証）にまとめた
- 身分証の画像はECCUBEに残らない（端末のみ・32日で削除）。店頭買取の本人確認の記録をどこに何日残すかが設計書に無い
- 0205の買取詳細に、身分証の種類を表示する記述が見つからない（古物台帳入力用CSVには出る）

- 0406 買取自動入庫バッチは対象を「店頭買取情報のステータス 12: 入庫待ち」と書くが、0506 のステータス一覧は 12 が未登録在庫あり、13 が入庫待ち。新実装は13が入庫待ち。数字の誤記と見て、名前（入庫待ち）で扱った。出どころは別だが同種の設計書の誤記として、MTGバイヤー側では 0601 の機能No欄が M06-01（正しくは O01-01）と誤記されている（MTGバイヤー/review/dispositions_R3.md）ことも並べて記録する
- 業務フロー06の手動入庫3-3・3-4は在庫変更CSVで入庫と書くが、0205 買取詳細は入庫済みボタンで入庫と書く。07版には手動入庫（パターン3・4）が無い。設計書（入庫済みボタン）に従った。CSVで入庫した買取が入庫待ちのまま残り、15時のバッチの対象になる。新実装は先のCSVを調べずに買取数量を加えるので、同じ商品の数量をCSVに入れていれば在庫は二重に増える。これを意図した仕様と認めるかは設計書に無い
- 業務フロー06の3-2は棚戻し業務用CSVの出力、3-5は「3-2で出力した」棚戻し業務用PDFと書く
- 07版の「出金方法」は銀行振込と店頭出金の両方からMTGバイヤーの買取成立へ進む線を引くが、設計書は経理払い出し待ち→経理が買取成立
- 0506 API_店頭買取管理「店頭買取情報ステータス更新」は、成功時出力で「更新前後が同じステータスでも成功（HTTP 200）」（0506:1567）と書く一方、表示メッセージ表（0506:1572）は「査定中・査定再開の受注を、査定担当者本人以外が査定中・査定再開へ更新しようとしたとき」にエラーとする。同じ状態を指定する場合（別の査定者が査定中の受注を選ぶ。端末は査定中を送る）はどちらにも読める。新実装は同じ状態なら何もせず成功を返し（OtcBuyOrder/UpdateStatusAction.php:75〜77）、更新前が査定再開で査定中へ更新するときだけエラーにする（同:95〜102）。MTGバイヤー（0507 ネット買取の同じ矛盾。dispositions_R1.md #9）の判定と同じ。期待値は例外E9（査定中＝成功）とE25（査定再開＝エラー）
- 店頭の「この受注は…が査定中です」の文言：設計書は「この受注は「（査定担当者名）」が査定中です。」、新実装は「この受注は{査定担当者名}が査定中です」（括弧と句点なし）
- 買取成立後の管理者取消で、入庫済みのEC在庫・スマレジの在庫や出金を戻すかが設計書に無い
- 業務フロー06の1-11「買取価格が0円商品の場合は、買取情報として残らない」に当たる処理が、設計書にも新実装にも見つからない（買取商品一覧CSVは0円を除かない）
- 入庫済みボタンを押せる買取のステータスが0205に無い。新実装は元のステータスを限らず、未登録の商品が残るときだけエラーにする
- 0205 買取一覧の戻しリストは、本店だけ棚番号を出し、支店は棚番のソートをしないとあるが、支店で買取をしたときの棚戻し先（支店の棚）の扱いは書かれていない

### 判断待ち（何を見ても決まらなかったもの）

- 業務フローの「買取履歴一覧」が買取商品履歴（M06-05）か買取一覧（買取商品一覧CSV）か：設計書0205の中で決まらない（※6）。UKA-06 は両方を試験に入れた。どちらかに決まったら、指さない側の手順を外す（2026-11-05 作業一覧2-1）
- 手動入庫（在庫変更CSV）の買取を15時のバッチが入庫して在庫が二重に増える動作（新実装のコードで確認）を、意図した仕様と認めるか（UKA-09。通しシナリオ UTH-03 と同じ判断待ち）。戻しリストPDFは、3-2のCSVで棚戻し済みになった買取にも出せる（0205・新実装で確認。判断待ちから外した）
- 買取価格ちょうど250円の棚：業務フロー06は「1円〜250円以下」はストレージ等、「250円以上」はショーケース品扱いと書き、250円ちょうどが両方に入る（※2）。設計書にも新実装にも250円の記述が無い
- 買取価格0円の商品が在庫移動（UKA-06）の対象か：業務フロー06の1-11は「買取情報として残らない」、設計書・新実装の買取商品一覧CSVは0円を除かない（※4）。在庫移動の対象は設計書（0406・0506）に見つからない
- 本人確認の確認項目（氏名の一致・有効期限）と、確認できなかったときに買取を止める処理：設計書にも新実装・現行にも無い（食い違いの1項目目）
- 未成年の買取の保護者同意書が必須か、システムで確かめるか：設計書に無い
- 0601 の「PH2で対応」の対象：どの機能・項目を指すか未判定（`phase2_specs.json` 0601 needs-triage）。一部キャンセル（0506 A06-14）はフェーズ2で見送りと判定済みだが、0601 の「PH2で対応」がそれと同じかは決まらない。MTGバイヤー側でも未判定として揃えて書いている

### 本人確認の見直し（2026-11-05）

依頼者の指示「買取の場合は本人確認証明が必要」を受け、本人確認を「システムの外」の1行から、買取の必須の確認として扱い直した。

- UKA-01・UKA-03：L3に本人確認の手順を足し、システムで確かめる部分（査定端末の身分証スキャンと書類の種類の記録）とシステムの外の部分（受付での身分証のコピー、査定後の照合）を分けた
- `matrix_UKA-01/`：因子J「本人確認書類の種類」（7種）を足したが、流れ・処理が変わらないので代表1つにまとめた（R4。店舗の本店・支店も同様にまとめ、12テストのまま）。例外E23（身分証を両面ともスキャンしない）・E24（種類の記録に失敗）を足した。E8は片面だけの場合として残した
- 証明が無い場合（その受注の両面の画像が端末に無い）は、査定端末で査定に進めず、査定中のまま止まる（E23）。身分証を持参していなくても、以前の画像が端末に残っていれば進める。期限切れ・氏名や住所の不一致のときの扱いは設計書・実装に確認が無いので、例外にせず判断待ちとして上の食い違いに記録した
- 他のシナリオへの影響：業務横断のUXB-10は区間にUKA-01を使うので、UKA-01の手順に本人確認の必須の確認が増える。ほかにUKA-01またはUKA-02を使うシナリオ（`業務横断/scenario_list.md` の買取の区間）も同じ。そちらのシナリオ・マトリクスは書き換えていない

### MTGバイヤー（2026-11-05）との関係

- UKA-01 のE9：別の査定者が査定中の受注を選んだときは何も更新せず成功する（0506:1567・新実装 OtcBuyOrder/UpdateStatusAction.php:75〜77。MTGバイヤー dispositions_R1.md #9・R3.md）。査定再開の受注を査定中にしようとしたときだけエラーで、E25に分けた。E9の文言は新実装と食い違う（括弧と句点が無い。上の食い違い）
- 買取成立・買取キャンセルのEC側の結果（端末取引ID・合計金額・実在庫・ダブルチェック者・査定担当者）は UMG-05 が確かめる。UKA-01・UKA-03 はその終点を参照する
- UKA-01 の「買取店舗」の因子：ログインした担当者の所属店舗は、合意書・買取証明書の店舗の住所が変わるだけでなく、査定端末の受注一覧の絞り込みにも効く（店頭は所属店舗の査定前・査定中・査定中断・査定再開の受注だけが出る。UMG-02）
- レジ出金（スマレジ連携 USM の対象外「出金取引そのものの取り込み」）：UKA-01 は端末取引IDの登録（F1。入れないとき E15、整数でないとき E16）と、端末取引IDがあるとき出金コードをECに連携する動き（F1・UMG-05）まで確かめている。出金取引そのものをECへ取り込む処理は設計書に無く、確かめない
- 本人確認（E23・E24）：査定開始は身分証の両面の画像が端末に無いと進めない。UMG-02 は 0506 A06-13（本人確認更新）の行を UKA-01・UKA-03 に任せている。UMG-02 の前提に身分証の画像が入ること（査定端末で両面を撮る）は UKA-01 のE23を参照する
