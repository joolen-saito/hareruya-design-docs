# ユーザー目線のシナリオテスト（見本）

シナリオテストは、利用者が画面を操作して目的を果たせるかを確かめるテストとする。
1本のシナリオには次の3つを書く。

1. **利用者と目的**：誰が、何のためにシステムを使うか（例：会員のお客様が、欲しいカードを探して買う）
2. **操作の流れ**：利用者が画面で行う操作を順に並べる
3. **期待値**：手順ごとに、画面に何が見えれば合格かを書く。エラーが起きず、データが正しく処理されたかも確かめる

## シナリオの単位

- シナリオ1本は「起点の業務イベントから、業務として完了した状態になるまで」。担当者が替わっても切らない。日をまたぐものは分ける
- L1 業務領域 → L2 シナリオ → L3 バリエーション（組み合わせテストマトリクスで絞る）→ L4 ステップ（画面操作と確認）
- 通販の一覧は [通販/scenario_list.md](通販/scenario_list.md)、UTS-01のL3は [通販/matrix/](通販/matrix/README.md)

## 範囲外

非機能（性能・障害回復・運用・セキュリティ・使用性）、データ移行、現行との比較はシナリオテストに入れない（2026-11-05 依頼者決定）。観点の体系（`scenario_test/シナリオテスト観点.md`）では SV-11〜SV-15・SV-17・SV-18 にあたる。

## 書き方の決まり

- 期待値には、設計書に書かれている文言・項目・状態だけを書く。設計書に無い値は書かない。
- 設計書の中で食い違いがあり、依頼者の裁定があるものは裁定に従う（通販は `scenario_test/coverage/viewpoint_application/review/通販受注管理/rulings.md`）。決まっていないものは「判断待ち」と書く。
- システムを触らない作業（ピッキング・梱包・集荷など）は「システムの外」として1行で書き、期待値は書かない。
- 物理名（テーブル名・内部の識別子）は使わない。画面の名前と画面の文言で書く。
- 根拠は末尾の表にまとめる。設計書の行番号は再生成でずれるため、設計書名・シート名と引用した文で示す。
- 試験用の値（会員名・商品名・在庫数など）は、シナリオを動かすために決めた値であり、設計書の値ではない。
