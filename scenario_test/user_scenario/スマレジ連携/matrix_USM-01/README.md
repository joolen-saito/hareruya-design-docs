# スマレジ連携のレジの取引を購入パターンに応じて受注に反映する（USM-01）

IPA「高信頼化ソフトウェアのための開発手法ガイドブック」(2010) の表6-9〜6-11と同じ手順で作る（`通販/matrix/README.md` と同じ）。

1. 因子・水準表（FL表）: `fl_table.tsv`
2. 禁則表: `prohibitions.tsv`
3. マトリクス: `matrix.md` / `matrix.tsv`（`tools/build_matrix.py` が作る。1行が1本のシナリオ＝レジで取引が完了し、受注に反映されるまで）
4. 例外の差し込み表: `exceptions.tsv`

## 範囲

- 0505 スマレジ受信処理の購入パターン1〜9と複数受注購入パターンの、取引の完了（created）の取り込み。返品（取消・打消）は USM-02、取り込みが失敗したときの再連携は USM-05
- 因子Aは、取引の種類・ついで買い・会員状態の組が設計書の購入パターンの番号に1対1で決まるので、番号を水準にした（番号ごとに通すことを確かめるため）。パターン2と3（ついで買い）、4〜7（店頭PC・会員状態・ついで買い）は処理が違うので分けたまま
- ポイント専用の取引（取引区分6・7）は範囲外（設計書に処理の定めが無い。`scenario_list.md` の食い違い）
- 店頭受取・店頭PCの注文からピック完了までは UOR-01・UOR-06 を区間として使う（A1〜A3の行の前提）
- 各行の期待値（共通）：取り込んだ取引の支払方法は「店頭支払」（0505「スマレジで取り込んだ取引情報の支払方法はすべて店頭支払とする」）、会員状態は取引のとおり、受注の担当者はスマレジ用アカウント、受注情報編集画面で編集できない（0203 受注情報編集「スマレジから連携されてきたデータについては更新不可」）

## 期待値が決まらない行（判断待ち）

- パターン1（スムーズ店頭受取）×複数件（T01）、水準A10「スムーズ店頭受取＋ついで買い」（T03・T04）：成り立つ組で、禁則にしていない。0505 の購入パターン表はスムーズ店頭受取のついで買いを「-」とし、複数受注購入パターンは配送方法を店頭受取として統合する定めだけで、これらの組の期待値が設計書に無い。新実装は受取方法がスムーズ店頭受取ならついで買いの有無を見ずパターン1（既存の受注だけを出荷完了にする）に決める。期待値は実行時に確かめて記録する（`scenario_list.md` の判断待ちに書いた）

## 購入パターンと実行行の対応（レビュー2巡目で因子を購入パターンの番号に変えた）

設計書の購入パターン1〜9のどれも、店舗・持ち込む受注の数を変えて2行以上で通る。

| 購入パターン | 実行行 |
|---|---|
| 1 | T01（複数件）・T02（1件） |
| 2 | T05・T06 |
| 3 | T07・T08 |
| 4 | T09・T10 |
| 5 | T11・T12 |
| 6 | T13・T14 |
| 7 | T15・T16 |
| 8 | T17・T18 |
| 9 | T19・T20 |
| （パターン無し・判断待ち）スムーズ店頭受取＋ついで買い | T03・T04 |

## まとめた水準

- スマレジでの支払いの種類（現金・クレジットカード・電子マネーなど）：まとめて水準にしない。0505「スマレジの詳細な支払方法を取得することはできないため、…支払方法はすべて「店頭支払」とする」ので、どの種類でも流れ・処理・表示が変わらない。0304 ご注文方法指定の「表示名称はスマレジで決済した方法」との食い違いは `scenario_list.md` に記録
- 取引する商品の種類（シングルカード・グッズなど）：水準にしない。0505 は「スマレジの商品IDで検索」するだけで、商品の種類で処理を分けていない
- パターン2・3（店頭受取）とパターン4〜7（店頭PC）は、新実装でも連携の処理は同じ（コードの注記「連携方法が同一」）が、元の注文の流れ（店頭注文番号の削除・マイページの表示）と引き渡し後の確認の流れが違うので、まとめず分けた（迷ったので分けたまま）
- 会員／非会員、ついで買いのあり／なしは、受注の会員状態・明細の数が変わるので分けた（水準Aの番号に含まれる）

## 実装で確かめたこと（2026-11-05）

- パターンの決まり方（新実装の購入パターンの判定処理）：既存の受注が突合できれば、その受注が店頭PC（購入グループが店頭用）か店頭受取かで分け、スムーズ店頭受取ならパターン1。突合できなければ会員状態でパターン8・9。設計書の購入パターン表と一致
- 因子Aは、取引の種類・ついで買い・会員状態の組が設計書の購入パターンの番号に1対1で決まるので、番号を水準にした（番号ごとに通すことを確かめるため）。パターン2と3（ついで買い）、4〜7（店頭PC・会員状態・ついで買い）は処理が違うので分けたまま
- ポイント専用の取引（取引区分6・7）は受注を作らず、会員のポイントだけを増減する。設計書にこの処理の定めは無い
- 取消・打消が作成より先に届いたときの救済は未実装（コードの注記 TODO）
