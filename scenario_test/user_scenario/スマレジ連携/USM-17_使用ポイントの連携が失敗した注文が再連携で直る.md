# USM-17 使用ポイントのスマレジ連携が失敗した注文が、再連携で直る

| 項目 | 内容 |
|---|---|
| 利用者 | 再連携のバッチ（システム。5分ごと）→ スマレジ（試験環境。システムの外）→ 通販チーム（管理画面で注文を確かめる） |
| 目的 | USM-16 で使用ポイントのスマレジ連携が失敗し、注文にエラー内容と連携エラーの印が残っているとき、再連携のバッチがその会員のポイントをスマレジへ絶対値（ECの残高）で送り直し、印が消える。スマレジの会員のポイントがECの保有ポイントと一致する。会員情報・プレイヤー情報が無い受注は対象にならず、印が残る。再連携が失敗すると、スマレジからの応答をエラー内容に保存する |
| 種類 | 代替（外部連携の失敗と回復。代表の1本）＋ L3の2件（組み合わせ表は無い） |
| マトリクスの行 | なし（組み合わせ表は無い。`matrix_USM-17/` は作っていない）。L3 は `scenario_list.md` の USM-17 の L3 欄の項目（再連携の失敗・対象外の受注）を1つずつ別のテストにした（R1・R2） |
| もとのシナリオ | なし（業務フローには無い。設計書 0405 B05-08 による）。同じ再連携に合流する出荷後の付与の失敗は UTS-14、注文完了メールが送られなかった注文の再処理は USM-21 |

スマレジの試験環境の画面の見え方は外部サービスなので記録だけにし、合否は EC 側の値（受注編集の「ポイントエラーメッセージ」と「要再収束」の印・保有ポイント・バッチの完了の表示）で付ける。

## 前提

- 共通の決まり：`../L4を流すときの共通の決まり.md` を先に読む（試験データの名前にシナリオIDを付ける・共有の設定は元に戻す・バッチの起動・店舗の読み替えなど）
- システムの外で済んでいること：スマレジの試験環境に接続できる。スマレジの試験環境の管理画面で会員のポイントを見られること。スマレジへの接続を失敗する状態にして、元に戻す作業を、試験環境の担当者に頼めること（システムの外。UTS-14 の手順2・7と同じ扱い）
- 再連携は5分ごとの定期起動（0405 B05-08）だが、時刻は待たずに手で起動する（2026-11-26 決定）。再連携は、依頼を積む処理と、積まれた依頼を実行する処理に分かれているので、手で起動したあと、実行が終わるのを待つ（手順4）。実行する処理が動いていること（ジョブ一覧のステータスが進むこと）を確かめる
- 用意するデータ（試験用の値。設計書の値ではない）
  - 会員：お名前「試験 会員USM17」、メールアドレス `usm17-t01@example.test`、パスワード「Usm17Test-2026」の本会員。国内の住所を登録済み。スマレジの会員が作られている（UMB-01 の手順1〜7と UMB-02 の手順1〜2、USM-12 の手順で、この試験専用に作る）。保有ポイントは USM-15 の代表の手順（増減量 3000・備考「USM-17 付与」）で 3,000 にしておく。スマレジの会員のポイントも 3,000（記録）
  - 連携エラーの印が付いた注文（起点の用意）：USM-16 の手順1〜3と同じ流れで、この会員が「シナリオ試験ポイントグッズ USM16」（USM-16 の前提の商品。名前の後ろは USM-17 に読み替える）を数量2・お支払い方法「銀行振込」・使用ポイント1,000で買う。購入の前に、試験環境の担当者が、スマレジへの接続を失敗する状態にしておく（USM-16 の R1 と同じ）。購入のあと、会員の保有ポイントは 3,000 から 2,000、スマレジの会員のポイントは 3,000 のまま（食い違った状態）。注文番号を控える（以下「控えた注文番号」）
  - 試験環境の担当者が接続を失敗する状態にできないとき：受注情報編集の「ポイントエラーメッセージ」の欄の「現在のECポイント残高で再収束を依頼」のボタンで、同じ印（要再収束）を付けて用意してよい（通販チームが、この注文の受注情報編集で押す。押したあと、「スマレジポイント残高の再収束を依頼しました。」が出る）。その場合は、印の出どころが管理者の依頼になり、エラー内容も失敗の応答でなく依頼の記録になるので、手順1・R1の「エラー内容」は確かめず、用意の方法を記録する
  - 通販チームの担当者：管理画面にログインでき、受注管理（受注情報検索・受注情報編集）・会員管理を使えるアカウント
  - 手順の前に控える値：会員の保有ポイント（2,000）、スマレジの会員のポイント（3,000。記録）、ジョブ一覧の先頭の行（番号）
- 画面の名前・文言は新実装の表示で書く。設計書の名前と違うときは「（設計書：…）」を添える
- 再連携のバッチは、環境の中の依頼が積まれた会員を全部処理する作り。合否はこの会員・この注文の値で付け、バッチの完了の表示の件数は記録にする

## 記録（判断待ちではない。合否は設計書の期待値で付け、新実装の動きは記録する）

- 設計書は注文ごとの再連携（注文のスマレジ連携エラーフラグ）を5分ごとに動かすと定める。新実装は会員ごとの「ポイント残高の再収束」の依頼を積んで実行する作りで、会員単位・ECの履歴の合計を絶対値でスマレジへ送る（UTS-14 と同じ。シナリオ一覧の言い方は設計書のもの）
- 再連携のバッチを手で起動するときの「対象(会員)」の件数・「投入」の件数は、環境の中の依頼の数で変わる。この会員の値で合否を付け、件数は記録する
- 再連携が失敗したあとの依頼の状態の表示（再試行の待ち・手動確認・結果不明）は設計書に定めが無く、新実装の表示を記録する（R1）
- 手順5：再連携に成功したあとのエラー内容の残り方は、設計書の現行仕様と新実装で違う見込み。合否は付けない
- スマレジの会員のポイントの見え方は外部サービスの見え方（記録だけ）

設計書との食い違い（起票しない）
- 再連携の単位と画面の名前：設計書は注文ごとの再連携と「ポイント連携エラー」、新実装は会員ごとの再収束と「ポイントエラーメッセージ」＋「要再収束」の印（UTS-14 の食い違い②③と同じ）
- 再連携に成功したあとのエラー内容：現行仕様は残す、新実装は消す（UTS-14 の食い違い④と同じ）
