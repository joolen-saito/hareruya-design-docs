# USM-18 有効期限が近いポイントを持つ会員に、期限前の通知が届く

| 項目 | 内容 |
|---|---|
| 利用者 | ポイント有効期限通知のバッチ（システム。毎日0:05）→ お客様（メール）→ 店舗チーム（管理画面で送信履歴を確かめる） |
| 目的 | 有効期限の30日前・7日前に、その日に獲得して残っているポイントがある会員に、期限前の通知のメールが届く。通知の対象は、スマレジの会員IDがあり、ポイント残高が1以上の会員だけ。残高が0の会員には通知しない |
| 種類 | 正常（代表の1本）＋ L3の3件（組み合わせ表は無い） |
| マトリクスの行 | なし（組み合わせ表は無い。`matrix_USM-18/` は作っていない）。L3 は `scenario_list.md` の USM-18 の L3 欄の項目（通知の時期：30日前／7日前・スマレジ会員IDの有無・残高が0）を1つずつ別のテストにした（代表が30日前、R1〜R3） |
| もとのシナリオ | なし（業務フローには無い。設計書 0408 B08-03 による）。失効のバッチは USM-19、残高と履歴の差分は USM-20、夜間のバッチの前後関係は UCY-04・UCY-05 が受け持つ |

メールは試験用の受け口で読んだ件名・本文・届くかで合否を付ける。スマレジの画面の見え方は、このシナリオでは使わない（通知はスマレジを呼ばない。設計書：「本バッチでは、いずれの場合も他のAPIを呼び出さない」）。

## 前提

- 共通の決まり：`../L4を流すときの共通の決まり.md` を先に読む（試験データの名前にシナリオIDを付ける・共有の設定は元に戻す・バッチの起動・店舗の読み替えなど）
- システムの外で済んでいること：なし
- バッチは毎日0:05に動く設計だが、時刻は待たずに手で起動する（2026-11-26 決定。起動のしかたは根拠の欄）。バッチは環境の中の対象の会員を全部処理する作り。合否はこの試験の会員の値（届くメール・送信履歴）で付け、ほかの会員に送った通数は記録にする
- 用意するデータ（試験用の値。設計書の値ではない）
  - 会員：どれも本会員（UMB-01 の手順1〜7と UMB-02 の手順1〜2、USM-12 の手順で、この試験専用に作る。スマレジの会員が作られている）。メールアドレス・お名前（名）：代表 `usm18-t01@example.test`・「会員USM18」、R1 `usm18-r1@example.test`、R2 `usm18-r2@example.test`、R3 `usm18-r3@example.test`。住所は国内（UMB-01 の入力値。住所の都道府県が「日本国外」の会員は英語のメールになるが、このシナリオでは使わない）
  - 店舗チームの担当者：管理画面の会員管理（会員編集・ポイント管理）を使えるアカウント
  - ポイントの用意（会員ごと。UMB-10 の準備1〜3と同じ操作：会員編集の「ポイント管理・履歴一覧」＞「ポイント履歴追加（キャンペーン、特別対応）」で、備考は「キャンペーン」、保存して「保存しました」を確かめる）。バッチを起動する日を「実行日」と呼ぶ
    - 代表（30日前）：増減量 200・ポイント発行日は実行日の153日前（有効期限は発行日の183日後なので、実行日の30日後）。備考のメモ欄は無いので、履歴の行の発行日で見分ける。保有ポイント 200
    - R1（7日前）：増減量 150・ポイント発行日は実行日の176日前（有効期限は実行日の7日後）。保有ポイント 150
    - R3（残高0）：増減量 200・発行日は実行日の153日前で付与したあと、続けて増減量 -200・発行日は実行日で減算する（保有ポイントが 0 になる。残高0）
    - 発行日を過去にできないときは、そのエラーを記録し、試験で作った会員の履歴に限り、開発環境で発行日を書き換えて用意してよい（共通の決まり）
  - 手順の前に控える値：各会員の保有ポイント、管理画面の会員編集の「送信履歴」の行数、メール受け口の各メールアドレスの件数
- 画面の名前・文言は新実装の表示で書く。設計書の名前と違うときは「（設計書：…）」を添える

## L3で変わるところ（組み合わせ表は無い。1つずつ別のテストにする）

手順の番号は上の「操作の流れと期待値」。どの行も、代表の会員 `usm18-t01@example.test` に手順3のメールが届いたのを見てから、各行の会員が「届く／届かない」を判定する（届かないことは、同じ処理で届くはずの別の会員に届いたのを見てから判定する）。

| 行 | 条件 | 変わるところ |
|---|---|---|
| R1 | 通知の時期：7日前 | 会員 `usm18-r1@example.test`（保有 150・発行日は実行日の176日前）を使う。手順3：件名は同じ「※重要【晴れる屋】ポイント有効期限のお知らせ」のメールが1通届き、本文の区切り線の間は「150ポイント　有効期限　〇〇〇〇/〇〇/〇〇」（日付は実行日の7日後）。手順4：送信履歴が1件増える。手順5：残高 150 のまま。代表の手順2のバッチで、30日前の会員（t01）と7日前の会員（r1）の両方に1通ずつ届く（同じ起動で2つの通知の時期が処理される） |
| R2 | スマレジ会員IDが無い会員（通知しない） | **実施不可（流せない）**：画面の操作で作る本会員にはスマレジの会員IDが必ず付く（本会員になるときにスマレジの会員が作られる。USM-12）。スマレジの会員IDが無い本会員は画面から作れない。用意の手段（試験で作った会員に限り、開発環境でスマレジの会員IDを空にする）が決まったときの期待値：その会員（`usm18-r2@example.test`・代表と同じポイントを用意）に、通知のメールは届かない。送信履歴は増えない。保有ポイントは変わらない（設計書 0408 B08-03 現行仕様「スマレジ会員IDが設定されており、かつポイント残高が1以上の会員だけを通知の対象とする」） |
| R3 | 残高が0（通知しない） | 会員 `usm18-r3@example.test`（付与 200＋減算 -200 で保有 0）を使う。手順1：ポイント残高が 0。履歴が2行（+200・-200）。手順3：通知のメールは届かない（件数は手順の前のまま）。手順4：送信履歴は増えない。手順5：残高 0 のまま、履歴は2行のまま |

## 記録（判断待ちではない。合否は設計書の期待値で付け、新実装の動きは記録する）

- 設計書は、有効期限の日付の数え方に1日ずれる例を載せる（バッチ実行日 2025/9/30 の有効期限切れ日を 2025/4/1 とするが、183日前は 3/31）。183日（設計書・新実装）で数え、日付は期待値を183日で書いた（業務周期 UCY-05 と同じ）
- 設計書の通知のひな形には有効期限間近ポイント数と日付を書く箇所が無く「追記した」とある。新実装は区切り線の間に「〇ポイント　有効期限　〇〇〇〇/〇〇/〇〇」を出す
- 通知の送信を防ぐ定め（同じ日に2回起動したときの二重送信）は設計書に無い。確かめるだけで合否は付けない
- 仮会員・退会済み会員が対象外になることは設計書が定める（★カスタマイズ項目）が、`scenario_list.md` の L3 欄に項目が無いので、このシナリオでは行にしていない（シナリオ一覧は変えていない）
- メールの問い合わせ先のリンクは本番のドメインに決め打ち（メールのひな形の固定の文）。このシナリオは問い合わせ先の画面を確かめないので、開発環境の画面は開かない

設計書との食い違い（起票しない）
- `scenario_list.md` に記録済みのもの以外に新しいものは無い（有効期限の日付の数え方の例の1日のずれは業務周期の一覧に記録済み）
