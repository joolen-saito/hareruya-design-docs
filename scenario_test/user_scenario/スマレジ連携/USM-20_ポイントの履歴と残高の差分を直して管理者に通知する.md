# USM-20 ポイント履歴と残高の差分を検知して残高を直し、管理者に通知する

| 項目 | 内容 |
|---|---|
| 利用者 | ポイント差分発生通知のバッチ（システム。毎日3:30）→ 管理者（メール）→ 店舗チーム（スマレジの手動更新。システムの外） |
| 目的 | 会員ごとのポイント履歴の増減量の合計と、会員の保有ポイント（残高）が違うとき、バッチが残高を履歴の合計に直し、差分の一覧（会員ID・履歴合計値・現在のポイント・差分）を管理者へメールで送る。スマレジの会員のポイントは自動では直らず、手動で更新する。差分が無いときは、メールを送らない |
| 種類 | 正常（代表の1本）＋ L3の1件（組み合わせ表は無い） |
| マトリクスの行 | なし（組み合わせ表は無い。`matrix_USM-20/` は作っていない）。L3 は `scenario_list.md` の USM-20 の L3 欄の項目（差分がある／無い・スマレジへの反映は行わない）のうち、無いほうを別のテストにした（R1）。スマレジへの反映を行わないことは代表の手順で確かめる |
| もとのシナリオ | なし（業務フローには無い。設計書 0408 B08-05 による）。夜間のバッチの前後関係は UCY-04、失効は USM-19、二重登録の通知は UTS-15 |

スマレジの試験環境の画面の見え方は外部サービスなので記録だけにし、合否は EC 側の値（バッチの完了の表示・保有ポイント・管理者へ届いたメール）で付ける。

## 前提

- 共通の決まり：`../L4を流すときの共通の決まり.md` を先に読む（試験データの名前にシナリオIDを付ける・共有の設定は元に戻す・バッチの起動・店舗の読み替えなど）
- システムの外で済んでいること：スマレジの試験環境の管理画面で会員のポイントを見られること。スマレジの会員のポイントを手動で更新する作業は店舗チームがスマレジで行う（システムの外。本書は行わない）
- バッチは毎日3:30に動く設計だが、時刻は待たずに手で起動する（2026-11-26 決定。起動のしかたは根拠の欄）。バッチは環境の中の全会員を調べる作りで、ほかの会員に差分があれば、その会員の残高も直り、メールの本文に載る。合否はこの試験の会員の値（残高・メールの該当の行）で付け、ほかの会員の件数は記録にする
- 共有の設定を一時的に確かめる：追加システム設定の「ポイント差分発生通知メールアドレス」（設定＞基本情報設定＞追加システム設定。`app/config/eccube/packages/eccube_nav.yaml`）。**流す前に今の値を確かめて控える**。値が入っていれば変えない（もともと要る値。その宛先の受信箱で通知を読む。読めないときは、メールを確かめる手順を実施不可（流せない）として記録し、残高が直ることだけで合否を付ける）。空のときだけ、試験用の受信箱（`usm20-admin@example.test`）を入れて確かめ、**終わったら空に戻し、戻ったことを追加システム設定の画面で確かめる**（`../L4を流すときの共通の決まり.md`）。空のときは通知しない（設計書 0408 B08-05 現行仕様）
- 用意するデータ（試験用の値。設計書の値ではない）
  - 会員：どれも本会員（UMB-01 の手順1〜7と UMB-02 の手順1〜2、USM-12 の手順で、この試験専用に作る。スマレジの会員が作られている）。代表 `usm20-t01@example.test`（お名前（名）「会員USM20」）、R1 `usm20-r1@example.test`
  - 店舗チームの担当者：管理画面の会員管理（会員一覧・会員編集・ポイント管理）を使えるアカウント
  - ポイントの用意（代表の会員）：USM-15 の代表の手順（ポイント履歴追加（キャンペーン、特別対応）で増減量 500・発行日は今日・備考「キャンペーン」）で付与する。履歴の合計 500・保有ポイント 500・スマレジの会員のポイント 500（記録）
  - 差分の用意（代表の会員）：画面の操作では、履歴と残高をずらす手段が無い（付与・減算は履歴と残高を同時に変える）。試験で作ったこの会員に限り、開発環境で保有ポイントを 470 に書き換えて用意してよい（UMB-24 の空欄の会員の用意と同じ扱い。履歴は変えない）。書き換えたあと、管理画面の会員編集の「ポイント確認」で、ポイント残高が 470・履歴の増減量の合計が 500 であることを確かめる。差分（現在のポイント − 履歴合計値）は -30
  - R1の会員：付与 300 だけ（履歴の合計 300・保有ポイント 300）で、差分なし（書き換えない）
  - 手順の前に控える値：代表の会員の会員ID（会員一覧の「会員ID」の列。以下「控えた会員ID」）・保有ポイント（470）、管理者の受信箱の通数
- 画面の名前・文言は新実装の表示で書く。設計書の名前と違うときは「（設計書：…）」を添える

## 操作の流れと期待値（起点：毎日3:30にバッチが動く。代表：差分がある）

| # | 操作する人と操作 | 期待値（画面で見えること） |
|---|---|---|
| 1 | 店舗チーム：管理画面の会員管理＞会員一覧で `usm20-t01@example.test` を検索し、会員ID（控える）を見てから、会員編集を開き、「ポイント確認」を押す | ポイント残高が 470。履歴が1行（増減量「500」）。履歴の合計 500 と残高 470 が違う（差分 -30） |
| 2 | 運用担当：ポイント差分発生通知のバッチを手で起動し、終わるまで待つ（時刻は待たない。起動のしかたは根拠の欄） | 「ポイント差分発生通知バッチ開始」のあと、「ポイント差分発生通知処理が完了しました。」が出る |
| 3 | 店舗チーム：会員編集の「ポイント確認」を開き直す | ポイント残高が 500 に変わっている（履歴の合計に上書きされた。設計書：「会員データの現在のポイントに履歴合計値を上書きを行い」）。履歴は1行のまま（行を足さない・消さない） |
| 4 | お客様：`usm20-t01@example.test` でログインし、マイページを開く | 「現在のポイント」が 500（管理画面と同じ） |
| 5 | 管理者：追加システム設定の「ポイント差分発生通知メールアドレス」の受信箱を開く | 件名「ポイント差分発生通知メール」のメールが1通届く（手順の前から1通増える）。本文は「以下のポイント差分が発生したため自動調整されました。」「会員ID, 履歴合計値, 現在のポイント, 差分」の見出しのあと、1会員1行で並ぶ。この会員の行：「（控えた会員ID）, 500, 470, -30」（設計書の例は「11111,5340,5310,-30」。区切りの後ろの空白の有無は新実装の表示を記録する）。差分は「現在のポイント − 履歴合計値」で、-30。ほかの会員に差分があれば、その会員の行も並ぶ（件数は記録）。差出人は店舗基本情報のメールアドレス |
| 6 | 店舗チーム（スマレジの試験環境。システムの外）：スマレジの管理画面で、この会員のポイントを見る | 記録のみ（合否は付けない。外部サービスの画面の見え方は記録にとどめる：2026-11-26 決定）：スマレジの会員のポイントは 500 のまま変わらない（バッチはスマレジへ連携しない。設計書：「ポイントのスマレジ連動処理は行っていないため、手動でスマレジポイントの更新が必要」）。EC の残高の補正は 470 → 500 で、スマレジとは元から同じ 500 なので、このシナリオでは食い違いは生じない。差分の分だけスマレジが食い違う場合の手動の更新は、システムの外 |

## 終わったあとに確かめること

| 確かめる場所 | 期待値 |

## 記録（判断待ちではない。合否は設計書の期待値で付け、新実装の動きは記録する）

- 履歴と残高をずらす手段は画面に無いので、代表の差分は、試験で作った会員の保有ポイントを開発環境で書き換えて用意する（共通の決まり「画面の操作で作れない状態の用意」。2026-11-27 決定。UMB-24 の会員の用意と同じ扱い。シナリオ一覧が「差分がある」を条件にしており、ほかに作る手段が見つからなかった）
- 通知先が未設定のときの扱い（補正は行い、通知はしない。設計書の現行仕様）は、`scenario_list.md` の L3 欄に項目が無いので、行にしていない（シナリオ一覧は変えていない）。追加システム設定が空のときの記録として、手順5で受信箱が無いときは、通知のメールが無いこと・残高が直ることを記録する
- 設計書の例は「11111,5340,5310,-30」と区切りの後ろに空白が無い。新実装は「,」の後ろに空白を入れる見込み。会員IDの桁・空白の有無は設計書に定めが無く、行の中身（会員ID・履歴合計値・現在のポイント・差分）で合否を付ける
- バッチは環境の中の全会員を処理する。ほかの会員の差分の件数は記録する
- スマレジの会員のポイントの見え方は外部サービスの見え方（記録だけ）

設計書との食い違い（起票しない）
- `scenario_list.md` に記録済みのもの以外に新しいものは無い（スマレジのポイントを手動で直す範囲の線引きが設計書に無い点は、シナリオ一覧の食い違いの節に記録済み）
