# USM-19 期限を過ぎたポイントが失効し、スマレジのポイントも差し引かれる

| 項目 | 内容 |
|---|---|
| 利用者 | ポイント失効のバッチ（システム。毎日0:00）→ スマレジ（試験環境。システムの外）→ お客様・店舗チーム（保有ポイントと履歴で確かめる） |
| 目的 | 有効期限（発行日の183日後）を過ぎたポイントが失効し、ECの保有ポイントと履歴（「有効期限切れによる失効」の行）が失効分だけ減り、スマレジの会員のポイントも失効分だけ減って一致する。スマレジの会員IDが無い会員は対象外。スマレジへの連携に失敗した会員は、その会員の失効を行わず次の会員へ進む |
| 種類 | 正常（代表の1本）＋ L3の2件（組み合わせ表は無い） |
| マトリクスの行 | なし（組み合わせ表は無い。`matrix_USM-19/` は作っていない）。L3 は `scenario_list.md` の USM-19 の L3 欄の項目（スマレジ会員IDの有無・スマレジへの連携の失敗）を1つずつ別のテストにした（R1・R2）。失効額の決まり（残高−期限内の付与の累計。使用後の残高との差）の細部は UPT-08 が確かめる |
| もとのシナリオ | なし（業務フローには無い。設計書 0408 B08-02 による）。履歴の見え方は UMB-10、期限前の通知は USM-18、残高と履歴の差分は USM-20、夜間のバッチの前後関係は UCY-04 |

スマレジの試験環境の画面の見え方は外部サービスなので記録だけにし、合否は EC 側の値（バッチの完了の表示・保有ポイント・ポイント履歴・マイページの履歴・ジョブ一覧）で付ける。

## 前提

- 共通の決まり：`../L4を流すときの共通の決まり.md` を先に読む（試験データの名前にシナリオIDを付ける・共有の設定は元に戻す・バッチの起動・店舗の読み替えなど）
- システムの外で済んでいること：スマレジの試験環境に接続できる。スマレジの試験環境の管理画面で会員のポイントを見られること。R2（スマレジへの連携に失敗する）の用意は試験環境の担当者に頼む（システムの外。UTS-14 の手順2と同じ扱い）
- バッチは毎日0:00に動く設計だが、時刻は待たずに手で起動する（2026-11-26 決定。起動のしかたは根拠の欄）。バッチは環境の中の対象の会員を全部処理する作りで、会員ごとに0.1秒の待ちを置く。合否はこの試験の会員の値（保有ポイント・履歴）で付け、ほかの会員の失効の件数は記録にする
- 用意するデータ（試験用の値。設計書の値ではない）
  - 会員：どれも本会員（UMB-01 の手順1〜7と UMB-02 の手順1〜2、USM-12 の手順で、この試験専用に作る。スマレジの会員が作られている）。代表 `usm19-t01@example.test`（お名前（名）「会員USM19」）、R2用に `usm19-r2@example.test`
  - 店舗チームの担当者：管理画面の会員管理（会員編集・ポイント管理）を使えるアカウント
  - ポイントの用意（会員ごと。USM-15 の代表の手順：会員編集の「ポイント管理・履歴一覧」＞「ポイント履歴追加（キャンペーン、特別対応）」。備考は「キャンペーン」）。バッチを起動する日を「実行日」と呼ぶ：
    - 付与1：増減量 300・ポイント発行日は実行日の200日前（有効期限＝発行日の183日後を過ぎている）
    - 付与2：増減量 500・ポイント発行日は実行日
    - 保有ポイントは 800。スマレジの会員のポイントも 800（USM-15 の連携で合う。スマレジの管理画面で確かめて控える。記録）
    - 発行日を過去にできないときは、そのエラーを記録し、試験で作った会員の履歴に限り、開発環境で発行日を書き換えて用意してよい（共通の決まり）
  - 失効額（期待値の計算）：失効額 ＝ 残高 − 期限内の付与の累計 ＝ 800 − 500 ＝ 300（0408 B08-02。付与1の300だけが期限切れ）
  - 手順の前に控える値：各会員の保有ポイント（800）、ポイント履歴の行数（2）、スマレジの会員のポイント（800。記録）、ジョブ一覧の先頭の行（番号）
- 画面の名前・文言は新実装の表示で書く。設計書の名前と違うときは「（設計書：…）」を添える

## L3で変わるところ（組み合わせ表は無い。1つずつ別のテストにする）

手順の番号は上の「操作の流れと期待値」。

| 行 | 条件 | 変わるところ |
|---|---|---|
| R1 | スマレジ会員IDが無い会員（対象外） | **実施不可（流せない）**：画面の操作で作る本会員にはスマレジの会員IDが必ず付く（USM-12）。スマレジの会員IDが無い本会員は画面から作れない。用意の手段（試験で作った会員に限り、開発環境でスマレジの会員IDを空にする）が決まったときの期待値：期限切れのポイントを持っていても、その会員は失効の対象にならない。手順3：保有ポイント・履歴は手順1のまま（失効の行は増えない）。手順4：マイページの現在のポイントも変わらない。手順6：スマレジの会員のポイントは変わらない（会員が無い）。代表の会員（`usm19-t01`）の失効が行われたのを見てから判定する（設計書 0408 B08-02 現行仕様「スマレジ会員IDが登録されていない会員は、有効期限を過ぎたポイントを持っていても対象に含めない」） |
| R2 | スマレジへの連携に失敗した会員（その会員の失効を行わず次へ） | 会員 `usm19-r2@example.test`（代表と同じポイントを用意する）を使う。手順2の前に、試験環境の担当者が、スマレジへの接続を失敗する状態にする（システムの外。共有の開発環境の設定は書き換えない。用意できないときは実施不可（流せない）として記録する。実行は設計書の読み取りまでになる）。期待値は設計書（0408 B08-02 エラーハンドリング「スマレジへのポイント増減API登録失敗…エラーが発生したユーザーのポイント失効処理(スマレジ・ユーザーポイント増減含め)は今回は行わず、次のユーザーの処理を行う／該当ユーザーのポイント失効処理は翌日以降に持ち越しとなる」）どおりに書く：手順3：この会員の保有ポイントは 800 のまま、履歴は2行のまま（失効の行は増えない）。ほかの会員の失効は進む。手順6：スマレジの会員のポイントは 800 のまま（記録）。接続を元に戻したあと、バッチをもう一度手で起動すると、手順3〜6のとおり失効する（翌日以降に持ち越された失効が行われる）。新実装は、保有ポイントの更新と失効の履歴の追加を確定してから、スマレジへの更新のジョブを投入する作りで、スマレジへの更新が失敗しても確定したEC側は戻らない見込み（設計書どおりに動かない）。手順3で失効の行ができて保有ポイントが 500 になったときは、不合格として記録し、手順5でジョブの失敗（ステータス「失敗」・エラーメッセージ）を記録して先へ進む |

## 記録（判断待ちではない。合否は設計書の期待値で付け、新実装の動きは記録する）

- 失効の行の日付：設計書は「有効期限:本日から183日間後の日時」「登録日時:本日の日時」と書き、新実装は失効の行の発行日に実行日の183日後を入れる（画面の「発行日」が未来の日付で出る見込み）。設計書の項目名と画面の項目名の対応が定かでないので、画面の値を記録するだけにし、合否は付けない（手順3）
- 失効の額の細部（付与と使用の組み合わせ・端数）は UPT-08 で確かめる
- スマレジへの連携に失敗した会員の扱い（R2）：シナリオ一覧が記録するとおり、新実装はEC側を先に確定するので設計書どおりに動かない見込み。失敗を起こす手段は試験環境の担当者が用意できたときだけ流す
- バッチの対象は環境の中の全会員。時間がかかるときは、完了の表示が出るまで待つ（会員ごとに0.1秒）
- スマレジの会員のポイントの見え方は外部サービスの見え方（記録だけ）

設計書との食い違い（起票しない）
- スマレジへの連携が失敗した会員のEC側の扱い：設計書は失効を行わない、新実装はEC側を確定してからジョブでスマレジへ送る（`scenario_list.md` の USM-19 の L3 欄に記録済み）
