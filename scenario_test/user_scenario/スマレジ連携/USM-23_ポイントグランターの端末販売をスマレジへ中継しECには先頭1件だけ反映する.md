# USM-23 ポイントグランターの端末販売を受け、スマレジへ中継し、ECには先頭1件だけポイントを付与する

| 項目 | 内容 |
|---|---|
| 利用者 | ポイントグランター（外部。端末）→ EC（API）→ スマレジ（試験環境。システムの外）→ 店舗チーム・会員（ポイント履歴で確かめる）→ 管理者（失敗の通知メール） |
| 目的 | ポイントグランターの端末が、端末販売の内容をECのAPIへ送ると、ECがスマレジへ中継し、連携内容の先頭要素の先頭行1件だけを会員の保有ポイントとポイント履歴に反映する（2行目以降・2要素目以降はECに反映しない）。付与ポイントが負なら保有ポイントが減る。増減が0でも、設計書（0517 E31・F38〜F39）は中継し、保有ポイントに0を足して履歴を1行残すと定める（新実装は中継せず履歴も作らない見込みで、省いたら食い違いとして記録する）。会員を特定できない・必須項目が欠けている・中継が失敗する・POST以外・接続情報が無効のときは、設計書の定めどおりに応答し、ECのポイントを変えない |
| 種類 | 正常（代表の1本＝T01）＋ 組み合わせ表の3行（T02〜T04）＋ 例外（E1〜E5） |
| マトリクスの行 | `matrix_USM-23/matrix.tsv` の T01（1行の連携内容。代表）・T02（複数行）・T03（付与ポイントが負）・T04（付与ポイントの増減が0）の4行。代表は T01。ほかの3行と例外5件（`exceptions.tsv` の E1〜E5。E3 は結果の違う2つに分けて E3a・E3b）は「L3で変わるところ」 |
| もとのシナリオ | なし（業務フローには無い）。設計書 0517 A17-03 による。参加ポイントの付与の通し（1行・正の付与）は UEV-06・UXB-15、受信の細部（取引の通知が戻っても1回分・結果が分からない失敗の通知）は UEX-13 が受け持つ。ここは連携内容の種類（行数・符号・0）と、受信そのものの失敗に絞る |

ポイントグランターの端末とスマレジの画面の見え方は外部サービスなので記録だけにし、合否は EC 側の値（会員の保有ポイント・ポイント履歴・マイページの現在のポイント・届いたメール）で付ける。APIの応答（状態コード・本文）は、設計書に定めのあるものは合否に使う（0517 の Excel 由来の欄の状態コード、現行仕様の節の本文。E2・E4）。定めの無いものは記録だけにする（UEV-06 の例外と同じ扱い）。設計書の定めと違うときは不合格として記録し、食い違いとして残す。

- 用意するデータ（試験用の値。設計書の値ではない）

  - 店舗チームの担当者：管理画面の会員管理（会員編集・ポイント管理）を使えるアカウント
  - 共有の設定を一時的に確かめる（E3b の行だけ）：追加システム設定の「スマレジ通信エラー通知メールアドレス」。**流す前に今の値を確かめて控える**。値が入っていれば変えない（もともと要る値。その宛先の受信箱で通知を読む。読めないときは E3b の「届く」を確かめられないので実施不可（流せない）として記録する）。空のときだけ、試験用の受信箱（`usm23-admin@example.test`）を入れて確かめ、**終わったら空に戻し、戻ったことを追加システム設定の画面で確かめる**（`../L4を流すときの共通の決まり.md`）
  - 手順の前に控える値：各会員の保有ポイントとポイント履歴の行数、スマレジの会員のポイント（記録）、マイページの現在のポイント
- 送る内容（行ごとに、スマレジの会員ID・付与ポイント・メモ・端末取引日時・ポイント属性を決める。取引区分は「ポイント加算（6）」。新実装が受け付けるのは 6（ポイント加算）か 7（ポイント減算）だけ。端末取引日時は、どの行も実行日の前日 12:00（日本時間）、ポイント属性は「付与型（1）」。設計書 0517 の入力例のポイント属性の値は 2 で、新実装のポイント種別の「付与型」は 1、2 は「購入型」。値は 1 を送る。違いは食い違いに記録）
- 画面の名前・文言は新実装の表示で書く。設計書の名前と違うときは「（設計書：…）」を添える

## 記録（判断待ちではない。合否は設計書の期待値で付け、新実装の動きは記録する）

- 要求の作り方（共通の決まり「外部のシステムから EC への要求」。2026-11-27 決定）：本物の試験環境が使えるときはそれで流し、使えないときは HTTP クライアントで代わりに送る。どちらで流したかを、行ごとに記録する
- 組み合わせ表の例外 E3 は、スマレジが拒否したとき（通知なし）と、結果が分からない失敗のとき（通知あり）で期待値が違うので、このファイルでは E3a・E3b に分けて書いた（`exceptions.tsv` は変えていない）
- T02：設計書は、2行目以降・2要素目以降もスマレジへ中継されると書く。新実装は先頭行だけをスマレジへ加算する作りに見え、中継の範囲が違う見込み（スマレジの画面の見え方は記録だけ）
- E2・E4：設計書の現行仕様が定める「本文は空の配列」と、新実装のエラーの内容を返す動き・POST以外を受け付けない動きは違う見込み。応答の本文・状態コードは外部との取り決めなので記録し、合否はECの値（保有ポイント・履歴が変わらないこと）と、設計書の本文の定め（空の配列）で付ける
- 端末の再送で同じ内容を再び送る（スマレジの加算は非冪等で二重付与になり得る）は、端末側の動作に依存する他層の論点で、外部連携 UEX-13 の R8 が確かめる（このシナリオでは行にしない。`matrix_USM-23/README.md` に記載のとおり）
- ポイント属性の種別は、管理画面・マイページのポイント履歴に出る項目が無く、ECの画面で確かめられない（UEX-13 と同じ。記録のみ）

設計書との食い違い（起票しない）
