# USM-05 スマレジの取引のWebhookが取りこぼされ、毎時の再連携で受注・ポイントが合う

| 項目 | 内容 |
|---|---|
| 利用者 | お客様（会員）→ 店舗チーム（スマレジのレジ。試験環境）→ スマレジ → 再連携のバッチ（システム）→ 店舗チーム・通販チーム（管理画面の受注一覧・会員のポイント）→ お客様（マイページのポイント） |
| 目的 | レジで取引が完了したのに、ECに取引の通知（Webhook。スマレジ側にリトライが無い）が届かなかったとき、毎時1分に動く再連携のバッチが、直近5時間の取引のうち、ECに未登録のもの・ポイントに不整合があるもの・返品などで更新があるもの（取引の更新日時に差異）を、受信処理と同じ処理で取り込み、受注・ポイントが USM-01・USM-02 と同じ状態になることを、EC側の値で確かめる |
| 種類 | 正常（代表の1本＝未登録の取引）＋ L3の5件（表外の具体例）＋例外1件 |
| マトリクスの行 | なし（組み合わせ表は無い。`scenario_list.md` のL3の欄にある、再連携の理由（未登録／ポイントの不整合／返品などの更新）・期間（直近5時間／手動で期間指定）・取引区分が通常でないもの・取り込みの失敗を、代表1本＋表外の具体例にした） |
| もとのシナリオ | なし（設計書 0405 B05-09「スマレジ取引連携エラー再連携」から組み立てた） |

在庫の変動を取り込む再連携は USM-04。このシナリオは受注・ポイントだけを確かめ、取引と同時に通知が止まったスマレジ在庫の変動は記録にする（在庫は USM-04 で確かめる）。

## 前提

- 共通の決まり：`../L4を流すときの共通の決まり.md` を先に読む（試験データの名前にシナリオIDを付ける・共有の設定は元に戻す・バッチの起動・店舗の読み替えなど）
- スマレジ側の操作は、スマレジの試験環境で行う（2026-11-24 決定）。スマレジの画面の見え方は記録だけにし、合否はEC側の値（受注・ポイント）で付ける
- 通知が届かない状態の作り方：USM-04 と同じ（スマレジ試験環境の通知の送り先を、試験の間だけ止めてからレジの操作をし、済んだら元に戻す。止めた時刻と戻した時刻を記録する。止められないときは「実施不可（流せない）」として記録する。判断待ち 1）。ECの設定は変えない
- バッチの流し方：毎時1分のバッチは、時刻を待たず手で起動する（起動のしかたと期間の指定のしかたは根拠の欄）。期間を指定しないときは、起動した時刻から5時間前までの取引が対象。このバッチは環境の中の取引を全部対象にするので、合否はこの試験の受注・会員の値で付け、再連携の件数は記録にする。完了の表示は「スマレジ取引再連携処理が完了しました。」（取得・再連携・内訳・スキップ・失敗の件数つき）
- システムの外で済んでいること：スマレジの試験環境に試験用の店舗とレジがそろっている。会員のお客様が、スマレジの会員番号を持つ（UMB-02）
- 用意するデータ（試験用の値。設計書の値ではない）
  - 会員：試験 太郎（本会員、メールアドレス `usm-05@example.test`、スマレジの会員番号あり）。保有ポイントは使用ポイント100を使えるだけ付与しておく
  - 商品：グッズ「シナリオ試験ショーケース品D USM-05」（商品コード `USM05-G01`、単価800円（税込））。グッズ商品CSV登録でスマレジ連携フラグ「連携する」・部門・スマレジ商品コードを書いて登録し、スマレジに商品ができたことを確かめてある（USM-08）。スマレジの管理画面とEC側のスマレジ在庫の両方に、在庫を10入れておく
  - 店舗：本店（店舗ID 1。画面によって「Hareruya」「トーナメントセンター 東京」と出る）。店舗は新しく作らない
  - 店舗チームの担当者：管理画面（受注管理・会員管理）と、スマレジのレジを使える
  - 手順の前に控える値：会員の保有ポイントとポイント履歴の行数
