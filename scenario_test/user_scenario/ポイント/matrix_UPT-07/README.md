# 注文の取り消し・返品で、ポイントの使用と付与が戻る（UPT-07）

IPA「高信頼化ソフトウェアのための開発手法ガイドブック」(2010) の表6-9〜6-11と同じ手順で作る（`通販/matrix/README.md` と同じ）。

1. 因子・水準表（FL表）: `fl_table.tsv`
2. 禁則表: `prohibitions.tsv`
3. マトリクス: `matrix.md` / `matrix.tsv`（`tools/build_matrix.py` が作る。1行が1本のシナリオ＝ポイントを使った／使わなかった通販の注文を通販チームが全部または一部取り消し、残高・履歴・スマレジが決まった値になるまで）
4. 例外の差し込み表: `exceptions.tsv`

## 範囲

- 通販の受注情報編集での取り消し。返金の方法（SPLINKSの請求キャンセル・振込・ポイント付与）は UTS-02・UTS-19、在庫・集計の戻りは UXB-02・UXB-03、店頭受取の取り消しは UOR-12、レジの返品は UPT-03・USM-02
- 取り消す前に、注文は UPT-05（使用）・UPT-01（付与）で作ったものを使う。ポイントの残高と履歴を、取り消す前に控える

## 期待値の決まり（行ごとに当てはめる）

| 取り消しの範囲（B）× 時点（C） | 使用ポイント | 付与ポイント | ポイント履歴 | スマレジ |
|---|---|---|---|---|
| B1 全部 × C1 出荷前 | 保有ポイントに戻る（残高は注文の前と同じ） | 付与予定は0 | 注文のポイント履歴がすべて消える | 使用分を戻す（キャンセルのポイント連携） |
| B1 全部 × C2 出荷後 | 同上 | 付与済みポイントを保有ポイントから差し引く。D2は判断待ち | 同上 | 差し引いた量をスマレジへ連携する（0のときは触れない） |
| B2 一部 × C1・C2 | 変動なし | 付与予定は再計算（付与済みは変動なし） | 変わらない | 触れない |

- 設計書の根拠：0203 受注情報編集 処理概要「キャンセル：…在庫・使用ポイント・付与ポイントを戻す。ポイント履歴を削除する」、現行仕様「削除したポイント履歴の変動量を合計する。合計が 0 でないときは、会員の保持ポイントから合計を差し引き、同じ量をスマレジへ連携する。合計が 0 のときは、会員の保持ポイントにもスマレジにも触れない」、M05-11-MSG-016「使用ポイント：変動なし／付与予定ポイント：再計算／付与済みポイント：変動なし」
- A3（全額ポイント）の B2：使用ポイントは変動しないので、減額した注文金額を使用ポイントが上回り得る。一部の返金は会員管理のポイント付与で返す（UTS-02・業務フロー16 9-8）
- D2（付与ポイントを使い切っている）× B2（一部の取り消し）：付与済みは変動なしなので、残高は変わらない（使い切っていても取り消せる。0203 M05-11-MSG-016）
- D2（付与ポイントを使い切っている）× B1 × C2：差し引くと残高がマイナスになり得る。設計書に定めが無く、新実装も差し引く前に残高を調べない（`src/Eccube/Service/PointService.php` 101〜134行）。管理画面のポイント付与は「ポイント残高を0未満にすることはできません。」と止める（M08-05-MSG-004）のに、取り消しは止めない。期待値は判断待ち（scenario_list.md）
- 完了の画面：全部取り消しは「全キャンセルが完了しました。」、一部は「一部キャンセルが完了しました」（M05-11-MSG-002・003）

## 実装で確かめたこと（2026-11-05）

- 受注情報編集のキャンセル：使用ポイントを戻す処理（`src/Eccube/Service/OrderStateMachine.php` 99〜100・136〜141行）のあとで、受注に紐づく履歴をすべて削除し合計を残高から引く（`src/Eccube/Service/PointService.php` 101〜134行、`src/Eccube/Controller/Admin/Order/EditController.php` 726〜731・917〜919行）
- 注意：使用ポイントを戻す処理が履歴の行を追加するのが、履歴を合計する処理より前で、間に保存（確定）の呼び出しが見当たらない。実装の読みでは、使用ポイントが二重に戻る（残高が注文前より増える）可能性がある。画面で、取り消し前後の残高と履歴を手で数えて確かめる（期待値は上の表のとおり注文前と同じ）
- 受注一覧の対応状況の一括変更（`src/Eccube/Controller/Admin/Order/OrderController.php` 516〜595行）は、使用ポイントを戻す処理だけを通り、履歴の削除と付与の取り消しを呼ばない（例外E1）

## まとめた水準

- 取り消す経路：受注情報編集の保存（全部）と、対応状況だけの更新（同画面の対応状況の変更）は、キャンセル日を新たに入れたときの処理が同じ（0203 現行仕様「対応状況だけの更新」「条件は受注全体の更新と同じ」）なので1つにまとめた。受注一覧の一括変更は処理が違うので例外E1に分けた
- 支払方法・配送方法：ポイントの戻しは支払方法に依らない（返金の違いはUTS-02・UTS-19）ため水準にしない
