# レジの取引の取消・打消しで、取引のポイントが元に戻る（UPT-10）

IPA「高信頼化ソフトウェアのための開発手法ガイドブック」(2010) の表6-9〜6-11と同じ手順で作る（`通販/matrix/README.md` と同じ）。

1. 因子・水準表（FL表）: `fl_table.tsv`
2. 禁則表: `prohibitions.tsv`
3. マトリクス: `matrix.md` / `matrix.tsv`（`tools/build_matrix.py` が作る。1行が1本のシナリオ＝完了済みの取引に対し、レジで取消・打消しが登録され、ECの残高・履歴が元に戻るまで）
4. 例外の差し込み表: `exceptions.tsv`

## 範囲

- 起点は取消・打消しの取引。元の取引の完了は UPT-03 で済ませておく（ポイントの履歴と残高を控える）
- 受注のキャンセル・在庫の戻りは USM-02・UOR-10。ここはポイントだけを見る

## 期待値の決まり（行ごとに当てはめる）

- 元の取引の付与・使用の履歴を削除し、その純増減を会員の保有ポイントから取り消す（残高は元の取引の前に戻る）。逆の履歴は残さない（逆の履歴を残すと、失効のバッチが取消済みの付与を有効ポイントとして数えるため）。0505 現行仕様「取消・打消しは逆に戻し、履歴を削除する」
- 付与・使用が0の取引は戻す履歴が無く、何もしない
- B4・B5（ポイント専用取引の取消・打消し）は設計書に処理が無い（判断待ち）。新実装は同じ方式で戻す

## 実装で確かめたこと（2026-11-05）

- 通常の取引：`src/Eccube/Service/Smaregi/Webhook/Transaction/SmaregiOrderPointReverter.php` 33〜125行（スマレジの取引に紐づく履歴だけを対象にし、EC注文時の履歴は巻き込まない）
- ポイント専用取引：`SmaregiPointAdjustmentReverter.php` 26〜60行（受注に紐づかない履歴を取引IDで探して削除し、純増減を残高から取り消す）

## まとめた水準

- 通常の取引の付与だけ・使用だけ・両方（B1〜B3）は戻し方が同じだが、純増減の値が違う（付与だけは＋、使用だけは−、両方は差）ので分ける
- 入口C2：店頭受取（本店・支店）・店頭PCの受注を持ち込む取引は、戻し方が同じなので1つにまとめた
