# レジ（スマレジ）で買い、スマレジが計算したポイントの付与・使用がECに合う（UPT-03）

IPA「高信頼化ソフトウェアのための開発手法ガイドブック」(2010) の表6-9〜6-11と同じ手順で作る（`通販/matrix/README.md` と同じ）。

1. 因子・水準表（FL表）: `fl_table.tsv`
2. 禁則表: `prohibitions.tsv`
3. マトリクス: `matrix.md` / `matrix.tsv`（`tools/build_matrix.py` が作る。1行が1本のシナリオ＝レジで取引が完了し、ECの会員の保有ポイント・ポイント履歴・マイページが取引と合うまで）
4. 例外の差し込み表: `exceptions.tsv`

## 範囲

- 取引の完了と、ポイント専用取引（取引区分6・7）の取り込み。完了済みの取引を取り消す・打消す経路は、取消・打消しを起点とする別の1本（UPT-10）
- 受注の作られ方（購入パターン1〜9）と在庫は USM-01 のマトリクス。ここは取引に載った付与・使用ポイントが、ECの残高・履歴・マイページにどう反映されるかだけを見る
- 付与・使用の額はスマレジが決める。ECは取引の値を受け取って写す（EC側の期待値は「取引の値と一致すること」）
- スムーズ店頭受取（取引は0円で、元の受注を出荷完了にする）は UPT-04

## 期待値の決まり（行ごとに当てはめる）

- A1：取引の付与ポイントだけ保有ポイントが増え、取引の使用ポイントだけ減る。ポイント履歴に付与（＋）と使用（−）が取引ごとに残る。マイページの履歴には注文番号の代わりにレシート番号が出る（0306 ポイント履歴。受注のある通常の取引だけ）。付与・使用が0のときは履歴を作らない
- A2・A3（判断待ち）：受注は作らず、会員のポイントだけが増減する。減算（A3）も付与ポイントに負の増減が入って届き（使用ポイントは0）、増減の合計が負なら残高を減らす。履歴の備考は加算が「店舗付与」、減算が「店舗使用」。増減が0の取引（B4）は残高も履歴も変えない。履歴は受注に紐づかないので、マイページのポイント履歴の番号欄は空になる。ポイント専用取引は、付与ポイントと使用ポイントの差（純増減）で増減を決める（使用ポイントが届く形にも備えている。SmaregiPointAdjustmentApplier.php 209〜222行）ので、使用だけ・使用と付与の両方の取引でも残高は純増減だけ動く。設計書に処理の定めが無いので、期待値は新実装の挙動
- マイページのレシート番号：受注のある履歴（A1）だけに出る（src/Eccube/Resource/template/default/Mypage/point_history.twig 99〜109行）
- 受注の状態：通常の取引から作る新規受注は「出荷完了」で作成され、持ち込んだ既存受注は「引き渡し済み」に更新される（SmaregiOrderFactory.php 324〜326行、Handler/Pattern/EccubeOtcPatternHandler.php 118〜120行）
- 使用ポイントの円換算：0505「ポイント値引き 使用ポイント * ポイント還元率 ※消費税含む」（1633行）。付与ポイント：「合計 * ポイント付与率」（1637行）

## 実装で確かめたこと（2026-11-05）

- 取引のポイントの反映：`src/Eccube/Service/Smaregi/Webhook/Transaction/SmaregiOrderPointApplier.php` 60〜200行（非会員は対象外・取消済みは付与しない・同一取引は再適用しない・付与も使用も0なら何もしない）
- ポイント専用取引：`SmaregiPointAdjustmentApplier.php` 33〜48行（受注を作らず区分6は加算・区分7は減算。会員に紐づく取引だけ。同一取引は再適用しない）

## まとめた水準

- 入口D2：店頭受取（本店・支店）と店頭PCの注文を持ち込む取引（購入パターン2〜7）と、複数受注の持ち込みは、ポイントの反映が同じ処理（取引の値を写す）ため1つにまとめた。購入パターンごとの違いは USM-01
- 取引の中のついで買いの有無：ポイントは取引全体に対して付くので分けない
