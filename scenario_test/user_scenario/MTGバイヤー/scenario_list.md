# MTGバイヤー：シナリオ一覧（L2）

MTGバイヤー（買取端末アプリ）と EC の連携は、店頭買取（UKA）とネット買取（UNK）のシナリオにばらばらに出てくる。ここでは業務フローの記述と設計書の MTGバイヤー向け処理を1行ずつ洗い出し（`## 連携の網羅`）、既存のシナリオで確かめられているものはそのIDを書き、足りないものだけを UMG のシナリオ（L2）として足した。

シナリオ1本は「起点の業務イベントから、業務として完了した状態になるまで」とする。担当者が替わっても切らない（買取担当者→買取端末→EC管理画面→経理・メール）。日をまたぎ、システムの状態が何かを待つもの（経理の振込、15時の自動入庫、お客様の承諾）は既存の UKA・UNK が扱う。前提データ（管理者・店舗・商品・部門などのマスタ）はシナリオから外す。カードの読み取り・身分証のコピー・印刷などの端末の物理操作は「システムの外」と書き、EC との間で送る・受ける値と、EC 側・端末側で見える結果を期待値にする。

行番号の書き方：`0601`・`0506`・`0507`・`0205`・`0206`・`0204`・`0209` は `excel_to_html/output/` の各HTMLの行。`O01-01`〜`O01-03` は `functions/pf-eccube3/` の機能設計書（O01-02・O01-03 は Excel の設計書が無く、現行ソース（買取端末アプリ）から起こしたもの）の行。業務フローは `scenario_test/markdown/` の行（R番号）。

| 階層 | 単位 | MTGバイヤーでの置き場所 |
|---|---|---|
| L1 業務領域 | シナリオのグループ | MTGバイヤー連携（店頭買取・ネット買取・入庫モード） |
| L2 シナリオ | 起点イベント→業務完了 | `## シナリオ一覧` の1行 |
| L3 バリエーション | 条件違い・例外 | `matrix_UMG-03/`・`matrix_UMG-04/`・`matrix_UMG-09/` と、各行の「L3」欄 |
| L4 ステップ | 画面操作と確認 | （まだ書かない） |

## 連携の網羅

方向は、端末→EC（端末が送る）、EC→端末（端末が取る）、両方向、なし。「シナリオ」は既存のID（`tools/check_refs.py` で実在を確かめた）か UMG。

### 判断待ち

- 買取成立の再送・15時のあとの再送・経理払い出し待ちの再送・メール送信失敗の扱い：設計書は「複数回押下しても最新の情報しか持たない」（0506:1283）と書くだけで、履歴・メール・入庫済みの扱いを定めない（見たもの：0506 A06-03、新実装の更新処理）
- 「トーナメントセンター 東京」の店舗名：開発環境の本店の店舗名と一致せず、ネット買取と入庫モードの列が期待どおりになるか決まらない（見たもの：開発環境の店舗情報、O01-02:14）
- 入庫モードのCSVの取り込み先、商品コードが空の行の生じ方（O01-03）
- 同じカード・カード詳細・言語・状態の組に商品規格が複数あるとき、応答に残る1件（0506:1698）
- 存在しないダブルチェック者のメンバーIDのときのエラー文言（0601:1115、0506 A06-16）

### 設計書との食い違い（設計書の不足。起票はしない）

- 査定中の受注を別の査定者が開くとき：0507:1377 は「更新前ステータスと指定ステータスが同じときは…正常終了（HTTP 200）」と明記し、新実装も同じ（UMG-04 E2 の期待値は成功・状態と履歴は不変）。一方、同じ文書の判定表（0507:1383）は「ともに査定中・査定再開」で担当者が違えばエラーとも読める。2人の担当者が同じ受注を同時に査定できてしまう

- 0601 は「機能No M06-01（正しくは O01-01）」。ネット買取（O01-02）・入庫モード（O01-03）の Excel 設計書が無い。0507 の機能No欄も A07-06・A07-07 の2シートが誤記
- 業務フロー14の2-5は「「査定前」のステータス」と書くが、ネット買取に査定前は無く、一覧に出るのは商品到着から（0507:1132）
- 0506 A06-12 は固定価格部門IDが無いとHTTP 500、A07-01 はまとめて買取商品IDが無いとHTTP 500相当。新実装は取得の応答で空の値を返して成功する
- 店頭買取の状態更新のエラー文言：設計書「この受注は「（査定担当者名）」が査定中です。」。新実装の店頭は括弧と句点が無い（ネットは設計書どおり）
- 0506 A06-02 の生年月日はISO8601の日時、新実装は日付のみ。所属店舗が定まらない管理者は設計書が「絞り込まない」、新実装は店舗なしなら空の一覧
- 設計書のAPIの宛先の形と、端末アプリが呼ぶ宛先の形が違う（バージョンの区切りの有無。詳細は物理名のため書かない）。刷新後の受け口が端末アプリの要求と合うか未確認
- 買取成立の再送・メール失敗・自動入庫後の再送の扱いが設計書に無い（判断待ち）
- 端末アプリのローカルのソースは古い可能性がある（設計書を優先した）
- 査定再開の受注の扱い（作業一覧2-8。店頭買取UTH-03の戻し事項）：0601 は、端末が査定再開（9）を送るのは「査定中断の受注を指定し、確認に『はい』と答えたとき」だけで、査定中断以外の受注を指定したときは査定中（6）を送ると書く（0601の「査定で使う状態ID」）。新実装は査定再開から査定中への更新を、直近の更新者本人にだけ許す（`src/Eccube/Service/App/MTGBuyer/V1/Admin/OtcBuyOrder/UpdateStatusAction.php:60〜95`）。そのため、再開した受注は、同じ査定を続けるあいだは査定再開のままで、再開の直後に査定中へ戻す送信は無い（通る状態の欄に反映した）。一方、査定再開の受注を一覧からもう一度選んだとき（査定中断以外の受注の指定）は、0601 により端末は査定中を送る。新実装は査定再開から査定中への更新を許す（`UpdateStatusAction.php:52〜55`）ので、同じ査定者なら査定中に戻り、別の査定者なら「この受注は{査定担当者名}が査定中です」のエラーになる（`UpdateStatusAction.php:95〜102`）。通しシナリオ UTH-03 の「査定再開のまま」は、再選択しない場合の記述として読む。作業一覧の「中断した後の状態」の言い方は、中断すれば査定中断になる（UMG-07）ので、そのままは採れない。判断待ちは無い

### 既存のシナリオへの影響（他の業務のファイルは書き換えていない）

- **店頭買取 UKA-01 E9**：「別の査定者が査定中または査定再開にしている受注を選ぶ」は、設計書の明記（同じ状態なら正常終了）と新実装では、査定再開のときだけエラーになり、査定中のときは同じ状態なので成功する（UMG-04 E2）。期待値の見直しが要る。E9 の文言も店頭は新実装と食い違う
- **店頭買取 UKA-01・UKA-03**：買取成立・キャンセルの EC 側の結果（端末取引ID・合計・実在庫・ダブルチェック者）は UMG-05 を区間として参照できる。UKA-01 の「買取店舗」因子は、ログイン者の所属店舗が一覧の絞り込みにも効く（UMG-02）
- **ネット買取 UNK-03**：査定の部分（L3 の中断・再開・まとめて買取・個別入力・サプライ）の細部は UMG-04 のマトリクスが担う。UNK-03 の備考に UMG-04 を足すと誤解がない。業務フロー14 R118 の「査定前」はネット買取に無い
- **ネット買取 UNK 一覧の食い違い「MTGバイヤーのネット買取の査定画面の設計書が無い」**：O01-02 が現行ソースから起こした機能設計書として存在する
- **商品登録・編集 UPR・スマレジ連携 USM-10**：部門の「MTGBuyer表示フラグ」が査定端末の選択肢に効くことは確かめていない（UMG-03 の前提とL3に入れた）
- **業務横断 UXB-10・11**：区間の買取の査定は UMG-04・UMG-05 を参照できる
- **業務周期**：MTGバイヤーに周期のバッチは無いので、周期の表への追加は不要
