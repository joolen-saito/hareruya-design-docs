端末の画面の見え方（メッセージ・画面の留まり）は外部システム（買取端末アプリ）の表示なので記録だけにし、合否は EC 側の値（買取詳細の明細・実在庫・金額・ステータス変更履歴、買取情報編集、経理チームのメール）で付ける（2026-11-24 決定）。端末が送った要求を、応答が届かなかったことにして再送する操作は、画面の操作で起こせないので、試験の担当者が用意する HTTP クライアントで EC に送る（共通の決まり「外部のシステムから EC への要求」と同じ。本物の機器・外部の試験環境が使えるときはそれで流し、どちらで流したかを記録に残す）。

  - 手順の前に控える値：受注の買取詳細のステータスとステータス変更履歴の行数・明細、商品P・Q・A・Mの在庫、経理チームの受け口の件数
- 画面の名前・文言は新実装の表示で書く

## L3で変わるところ（組み合わせ表は無い。1つずつ別のテストにする）

手順の番号は上の「操作の流れと期待値」。行ごとに別の受注を使い、流し始めの状態を控える。

| 行 | 条件 | 変わるところ |
|---|---|---|
| S1 | 保管先へのアップロードが失敗する（買取情報を更新しない） | 代表の手順2のとおり。買取成立・買取キャンセルでも同じ（保管してから更新する順序は共通）。（EC。合否）買取詳細は手順1の控えのまま。端末の確認「重要：査定中のデータが失われる可能性があります。…」は中断のときの確認で、この失敗では出ない（出るかは記録） |
| S2 | EC の更新が失敗する（UKA-01 E18・E19） | 保管先への保管が成功したあと、EC の更新だけを失敗させる方法が画面の操作に無い（ネットワークを外すと、先に保管が失敗して S1 になる）。この行の条件は作れないので実施不可（流せない）。端末の文言「サーバエラー：買取情報の登録に失敗しました。」「サーバエラー：経理払い出し待ちの登録に失敗しました。」は記録だけ。結合テストへは回さない |
| S3 | 応答が届かず、買取成立を再送する | 手順3の代わりに K1（UMG-05。端末取引IDを入れて買取成立）で登録し、手順4で同じ内容の買取成立の更新を HTTP クライアントで再送する。（EC。合否）明細（P×2・Q×3）・実在庫情報は全部消してから作り直すので二重にならず、最新の1組だけ。ステータスは「入庫待ち」。端末取引IDは同じ値のまま。ステータス変更履歴：買取成立は続けて入庫待ちに更新するため、再送のたびに「買取成立」「入庫待ち」の行が増える（設計書に定めが無い：記録だけ。2026-11-09 決着）。実在庫は P×2・Q×3 のまま。経理チームのメールは増えない |
| S4 | 経理払い出し待ちを再送する | 代表の手順4のとおり。メールは再送のたびに送られる（記録だけ）。ステータス履歴は増えない |
| S5 | 買取キャンセルを再送する | 手順3の代わりに UMG-05 の K3（買取キャンセル）、手順4で同じ内容の買取キャンセルの更新を再送する。（EC。合否）ステータス「買取キャンセル」のまま・履歴は増えない（状態が変わらないため）。明細（P×2・Q×3）は二重にならない。メールは送られない |
| S6 | 更新の確定後に、経理へのメール送信が失敗する | 新実装のコードの順序（更新を確定してからメールを送る）では、EC の買取は経理払い出し待ちに更新済みで、メールだけ届かない。端末は失敗を表示する。メール失敗時の扱いは設計書に無い。記録だけ（2026-11-09 決着）で、流さない（共有の追加システム設定を、メールが失敗する値に変える試験はしない） |
| S7 | 15時の自動入庫のあとに再送する | 設計書は更新前の状態による制限を課さないので、自動入庫（または入庫済みボタン）で入庫済みになった買取に買取成立を再送すると、状態が入庫待ちに戻り、再度入庫される恐れがある。記録だけ（2026-11-09 決着）で、流さない（入庫済みになった在庫を戻せないため） |
| S8 | ネットの査定完了の再送 | UMG-04 の例外E11のとおり：同じ査定完了の送信をもう一度送っても、明細は二重にならず、買取状況は「MTGBuyer査定完了」のまま、履歴は増えず、在庫は動かない（HTTP クライアントで送る：共通の決まり「外部のシステムから EC への要求」と同じ） |
| S9 | ネットの査定完了が通信エラーで失敗する | UMG-04 の例外E9のとおり：「サーバエラー：査定完了の登録に失敗しました。」が出て査定画面に留まり、EC の明細・状況・履歴は変わらない |
