# ネット買取の査定完了で査定金額が買取に入る（UMG-04）

IPA「高信頼化ソフトウェアのための開発手法ガイドブック」(2010) の表6-9〜6-11と同じ手順で作る。`fl_table.tsv`（因子・水準）→ `prohibitions.tsv`（禁則。今回は無い）→ `matrix.md`・`matrix.tsv`（`build_matrix.py` が作る）。エラーや中断は `exceptions.tsv` に1つずつ差し込む。

## 範囲

- 商品到着の買取を、店舗チームが MTGバイヤー（買取端末）で査定し、「査定完了」を押して、査定した金額・数量・状態が EC の買取情報に入り、買取の状況が MTGBuyer査定完了になるまで（業務フロー14の2-4〜2-6。R123「MTGバイヤーにて査定した査定金額が挿入される」）。通る状態：商品到着→査定中→（査定中断→査定再開）→MTGBuyer査定完了
- 査定のあとの査定内容連絡済み・承諾・振込は UNK-03・UNK-04 以降。この一覧は、UNK-03 の査定の部分を、MTGバイヤーと EC のやり取りで細かくしたもの（UNK-03 の L3「まとめて買取」「個別入力商品」「サプライ品」「中断・再開」を因子にした）
- カードの読み取り・カードの仕分け・端末の操作そのものはシステムの外。EC との間で送る値（状態・明細）と、EC 側（管理画面の買取情報編集・買取一覧）と端末側で見える結果を期待値にする
- 査定表に足す操作の細部（読み取り・検索・個別入力・金額指定）は UMG-03。実在庫は動かない（2026/4/30 変更。0507 A07-05）ので、査定完了で在庫は増えない

## 期待値（各テストに共通）

- EC の買取情報編集で、査定表の行（削除済みを除く）が明細になる。商品規格ID・商品名・言語・状態・フォイル区分・買取価格・買取カテゴリがすべて同じ行だけが枚数を合算して1明細になる（O01-02:148-150）。買取価格か買取カテゴリが違う行は分けて送られ、別の明細になる。査定金額合計は「単価×数量」の合計を10円単位で切り上げた額（0507 A07-05「合計額は10円単位で切り上げる」）。サプライ品（カード詳細IDが未設定の明細）は、単価が設定されていれば単価×数量が合計に入り、単価が未設定のものは加算されない（0507:1502）
- 買取の状況は MTGBuyer査定完了。状態の履歴は、状態が変わるので1件増える（0507 A07-05「ステータス履歴を登録するのは、更新前後でステータスが変わったときだけ」）
- 端末は「査定完了の登録が完了しました。お客様選択画面に移動します。」を出し、お客様選択画面（ネット買取）へ戻る。この受注は一覧から消える（一覧は商品到着・査定中・査定中断・査定再開だけ。0507 A07-02）。保管した査定途中のデータも消える
- マイページの買取履歴は、MTGBuyer査定完了のあいだ「受付を完了しました。20%」のまま（UNK-01・UNK-03。査定内容連絡済みで「査定が完了しました。50%」になる）

水準ごとの結果：A1＝同じ明細の査定価格が更新される／A2＝別の状態の明細ができ、同じ商品・言語・フォイルの申込時買取価格が状態ごとに引き継がれる／A3＝削除した行の明細が消え、残りの明細で合計が決まる／B2〜B4＝新しい明細が足される（G2は買取カテゴリが選んで買取の明細になる）（B3・B4は個別入力商品の一覧に入る）／C2＝まとめて買取の商品の固定の明細が消え、査定表で足した行が「まとめて買取」として入る／D2＝サプライ品は消えず合計に入る／D3＝サプライ品は消えないが、単価が未設定なので合計に入らない／E2＝中断前の査定表が復元されて同じ結果になる／F2＝合計の端数が切り上がる。
- 本人確認が必要な買取金額（10,000円）との比較に使われる金額は、ここで買取に入る査定金額合計（査定完了と、管理画面でのサプライ品の削除・保存で更新）。お客様の承諾の処理では更新されない（承諾後の金額とは別）。ただし承諾のあとに管理画面でサプライ品を削除すると、この合計は売却する明細だけの承諾金額で再計算されて上書きされる（PurchaseController.php:561〜567、DtbBuyOrder.php:729〜745）。新実装 `src/Eccube/Form/Type/Admin/Purchase/PurchaseDetailType.php:388〜393`・`src/Eccube/Service/App/MTGBuyer/V1/Admin/BuyOrder/UpdateBuyOrderAction.php:102〜105`（2026-11-05 作業一覧2-7）

## まとめた水準（2026-11-05 依頼者決定「種類別のフローや処理が変わらないならまとめて」）

| 因子 | まとめた水準 | 代表 | 根拠（変わらない理由） |
|---|---|---|---|
| B 査定中に足すカード | 金額指定の「1円」「2円」「5円」「10円」 | 1円 | 「買取価格は指定した金額。商品名は「{金額}円商品」。枚数は、追加するときに入力させた枚数」（O01-02「査定表の行の追加と買取価格」）。送る項目は商品規格ID0・商品名・枚数・価格・買取カテゴリで、金額が違うだけ |
| 申込のカードの状態 | NM・SP・MP・HP（A2の「申込と変えた状態」） | SP | 「状態（1=NM、2=SP、3=MP、4=HP）」。状態は明細の値で、状態ごとの申込時買取価格を引き継ぐ処理は同じ（0507 A07-05） |

分けたままにしたもの：B2（カードの追加）とB3（個別入力）。EC 側で、商品規格IDのある明細は買取代表カード、無い明細は個別入力商品に作られ、一覧も別になる（0507 A07-05・A07-06・A07-07）。

## 禁則が無い理由

7因子（A 申込のカードの査定の仕方・B 足すカード・C 申込のまとめて買取・D サプライ品・E 査定の経過・F 金額の端数・G 足した行の買取カテゴリ）は、担当者が査定の中で選ぶもの・受注から決まるもので、一方が他方を選べなくする記述は、0507・O01-02・0206 に見つからない。A3は「申込カードが複数あり1行だけ削除する」ので、ほかの明細が残る。査定表の行をすべて削除して空にした場合は、EC が「1つ以上の商品を選んでください。」を返して失敗するため（0507 A07-05 の入力検証）、正常な組には入れず例外E8で扱う。

## 実装と設計書で確かめたこと

- 新実装は、査定完了の処理で、商品規格IDが無い（または0の）明細を個別入力商品、それ以外を買取代表カードにし、既存と同条件なら更新、無ければ作る。送られなかった既存の買取代表カード・個別入力商品を削除し、サプライ・パックは保持して小計を加え、合計を10円単位に切り上げる。状態が変わったときだけ履歴を1件残す（0507 A07-05 と合う）
- ネット買取の状態更新は、更新前が商品到着・査定中・査定中断・査定再開のときだけ、査定中・査定中断・査定再開へ変えられる。同じ状態を指定すると何もせず成功する（0507:1377、新実装も同じ。例外E2）。同じ文書の判定表（0507:1383）との食い違いは `../scenario_list.md` に記録
- 設計書の状態更新のエラー文言は「この受注は「（査定担当者名）」が査定中です。」。新実装のネット買取は同じ文言。店頭買取の同じ処理は「この受注は{担当者名}が査定中です」で、括弧と句点が無い（`../scenario_list.md` の食い違い）
- 業務フロー14の2-5は「「査定前」のステータスの情報として登録されているので」と書くが、ネット買取の状態に「査定前」は無く、MTGバイヤーが一覧に出すのは商品到着からの4状態（0507 A07-02）
