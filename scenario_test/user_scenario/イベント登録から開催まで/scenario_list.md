# イベント登録から開催まで：シナリオ一覧（L2）

店舗チームがイベントを登録して公開し、お客様が見つけて申し込み、デッキを登録して、開催日に受付・実施し、参加ポイントがつくまでを、それだけで読んで流せる通しのシナリオにする。イベント管理（UEV）・デッキ登録（UDK）・スマレジ連携（USM）・会員管理（UMB）に分かれている区間を、1本につなぎ直したもの。各業務の一覧は書き換えず、区間ごとに既存のIDを参照する。この一覧の役割は、つなぎ目で値（イベント・日程・定員・参加費・申込状況・デッキ・ポイント）が正しく引き継がれ、お客様の画面・メール・店舗チームの画面に出るかを通しで確かめることで、例外の細部は既存のIDに任せて重ねない。

## シナリオの単位（切る場所と切らない場所）

シナリオ1本は「起点の業務イベントから、業務として完了した状態になるまで」。起点は「店舗チームがイベントを新規登録する」、終点は「参加ポイントが会員に付き、履歴に残る」とする。担当者が替わっても切らない（店舗チーム→お客様→決済の外部画面→店舗チーム→ポイントグランター→メール）。流れが変わるところ（参加費の有無・デッキ登録の時期・オンライン受付の有無）で分ける。

| 場所 | 扱い | 理由 |
|---|---|---|
| 受付期間・開催日を待つ | 切らない（日程の日時を実行日に合わせ、1日の中で通す） | 日をまたぐが、システムの状態は待たない。受付状況（予約受付中・予約終了など）・イベント終了は日時から表示が決まるだけで、日付の経過で状態を変える処理が無い（0307 イベント大会TOP 表1、0306 マイイベント・デッキ登録 機能仕様）。UEV一覧の「受付の状況は日時で変わるだけで、ここでは待たない」と同じ扱い |
| デッキを申込のあとで登録し直す | 別の1本（UEH-03） | 申込済みの会員が時間をおいて登録する。会員の操作を待つ状態があり、UEV-07・UDK-02の区間 |
| オンライン受付のあるなし | 分ける（UEH-01〜03とUEH-04） | オンライン受付が無いと、申込・決済・申込完了メール・申込リストが無く、当日の会員登録（業務フロー3-4・3-5）が入る |
| 参加費の有無 | 分ける（UEH-01とUEH-02） | 無料は、支払方法の欄・外部の決済画面・クレジット決済完了メールが無く、申込が最初から申込済み（0307 大会申込～完了） |
| キャンセル・返金・店舗都合の中止 | 範囲外（UEV-03・UEV-04・UEV-08） | キャンセルは、会員が決めるまで申込済みの状態が待つ別の1本 |
| 会員登録（仮会員→本会員） | UEH-04は参照（UMB-01・UMB-02）。細部は重ねない | メールの本登録を待つ状態は、会員管理の別の1本 |
| デッキの公開（18の2-2） | 範囲外（UDK-03） | 大会の開催後に顧客戦略チームが行う別の1本 |
| 受付・実施・照合・参加費の徴収 | システムの外として手順に書く | システムを触らない作業（業務フロー3-2・3-3） |
| スマレジへの売上登録 | スマレジ（外部システム）の操作として手順に書き、スマレジの売上で確かめる | 業務フロー3-8。ECには取り込まない（設計書に無い） |

### 設計書との食い違い（設計書の不足。起票はしない）

- 申込完了のメール（クレジット決済完了メール）を、決済の通常の戻りで送ることを書いた設計書が無い。0413は決済処理中チェックバッチが送ることだけを書き、0307 大会申込～完了の決済後の扱いにメールの記述が無い。件名・本文の項目・宛先（店舗の代表アドレスへの控え）も書かれていない。L4は新実装のテンプレートを参考に書き、期待値は「申込と一致する」ことだけにした
- 無料の申込に完了のメールを送るかの定めが設計書に無い（新実装は送らない）
- デッキ登録完了メールのテンプレートの選び方が設計書に無い（新実装は会員の都道府県が海外かで選ぶ）。申込完了メールは購入時のサイトの言語で選ぶので、英語のサイトで申し込んでデッキを登録する国内の会員は「申込完了は英語・デッキ登録完了は日本語」、日本語のサイトで申し込んだ海外の会員は逆になる
- マイイベント・デッキ登録の表示文言：設計書の識別ID 7は「デッキ登録状況」の列に「デッキ登録済み」「デッキ未登録」、新実装の画面は列の見出しが「デッキ登録」、値が「登録済み」「未登録」。L4は設計書の文言で期待値を書き、新実装の表示は記録欄に書いた。開催日時の書式も、設計書の現行仕様は「（年）年（月）月（日）日 （時）時（分）分」、新実装の画面は年/月/日 時:分（優先順位は Excel由来＞現行仕様のため、設計書の識別IDの文言を優先）
- 申込完了画面のデッキ登録ボタンが、まとめて申し込んだときどの日程のデッキ登録へ進むかが、設計書に無い
- デッキ登録ボタンの条件：設計書（0307 大会詳細 4）は申込と無関係に3条件だけ。現行仕様は申込のボタン領域を表示する状態のときだけ。新実装は設計書どおり（オンライン受付のないイベントの当日登録ができる）
- 支店のサイトでの申込・デッキ登録の可否が設計書に無い。新実装は本店だけ
- スマレジへの売上登録（3-8）をECへ取り込む処理が設計書に無い（UEV一覧の食い違いと同じ）。スマレジの売上にイベント金額が出ることは各L4で確かめるが、金額の内訳（オンライン決済済みの参加費を当日の金額に含めるか）は定めが無く、値は記録
- 申込一覧の申込状況の既定の絞り込みが設計書に無い（新実装は絞り込まないので、キャンセル済み・決済中の申込も載る）
- 業務フロー08の3-1「競技イベントの場合は、デッキ登録されたデッキを全員分PDFで出力する」は、オンライン受付のイベントの工程。オンライン受付のないイベントでの全員分の出力は業務フローに無い（UEH-04はルールの厳しさを因子にしなかった）
- 以前から記録のもの：キャンセル申込みの入口の条件・申込登録時に定員に達していたときの扱い・イベント規模の名称・コンビニ決済の名残・限定公開の出し分け・バナースライダーの条件・「PDFで出力」の読み替え・ポイント付与でプレイヤーを特定できないときの扱い（`イベント管理/scenario_list.md` の食い違い）

### 判断待ち

- サイトの言語と会員の登録住所が食い違うときの、申込完了メール・デッキ登録完了メールの言語：見たもの＝0405 購入完了手続き再処理（再送は会員の都道府県で決める）、0306 大会デッキ登録編集（言語の記述なし）、新実装のメール送信の処理（申込完了は購入時のサイトの言語、デッキ登録完了は会員の都道府県）。どれにも、どちらを正とするかの定めが無い。`matrix_UEH-01/` のE・Fの行と、`matrix_UEH-02/` のD・Eの行は、メールの言語を「記録」とし、合否は付けない
