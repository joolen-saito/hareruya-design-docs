IPA「高信頼化ソフトウェアのための開発手法ガイドブック」(2010) の表6-9〜6-11と同じ手順で作る。1行が1本のシナリオ（L3）。

2. 禁則表: `prohibitions.tsv`。ありえない組み合わせ
3. 組み合わせテストマトリクス: `matrix.md` / `matrix.tsv`。`build_matrix.py` が作る。1行が1本のシナリオになる
4. 例外の差し込み表: `exceptions.tsv`。エラーや中断（★の手順）は、正常な値と混ぜず、条件に合う行へ1つずつ差し込む

## 範囲

- 会員が申込のときにはデッキを登録せず、開催日の前に、マイページのマイイベント・デッキ登録の一覧から登録（登録済みなら編集）し、開催日に店舗チームが申込一覧とデッキ表示（登録デッキを全員分出す。印刷）で確認して受付・実施し、参加ポイントがつくところまで。UEV-07（後日のデッキ登録）と、UEV-06（開催日の受付〜ポイント付与）の「デッキを全員分出力する」を、イベントの登録・申込からつないだもの
- 各行の期待値：一覧の「デッキ登録」（登録済みなら「デッキ編集」）から登録すると、デッキ登録完了画面とデッキ登録完了メールが出て、一覧のデッキ登録状況が「デッキ登録済み」になる（ボタンは「デッキ編集」）。初回に提出したデッキは非公開で保存され、デッキ検索には出ない（0306 大会デッキ登録編集「公開設定(非公開)、デッキタイプ(イベント)を設定して保存する」）。登録済みデッキの編集は既存のデッキを上書きし、デッキの数は増えない。ルールが厳しい行は、開催日に申込一覧のデッキ登録を検索し、デッキ表示で全員分のデッキが印刷用に出て、会員が登録した内容と一致する
- 申込・デッキ登録は本店のサイトだけで使える（新実装は、この2つの画面を本店専用にし、支店のサイトからは開けない扱いにしている）。この通しは開催店舗を店舗Aとして、本店のサイトで通す（開催店舗が支店のイベントを本店のサイトから申し込む運用は、設計書に明記が無い。scenario_list.md の判断待ち）
- 同じ会員・同じ日程は二重に申し込めない。キャンセル済みは定員に数えない（開発環境の申込状況マスタ）ので、定員に数える設定が有効な申込状況（決済中・入金待ち・申込済み・入金期限切れ・支払番号が存在しない）が定員を使い、キャンセル済みだけが数えない
- 後日の登録は、受付期間・開催日を待つので、試験では日程の日時を実行日に合わせ、申込→（時間をおいて）一覧から登録→開催日の操作、の順に1日の中で通す。システムの状態は「申込済み」のまま変わらず、デッキの有無だけが変わる
- 因子に入れなかったもの：開催日当日に登録する（ルールが厳しくないときだけ成り立つ。開催日の全員分の出力より後になるので、UEH-04・UEV-06のD2で確かめる）、申込直後に登録する（UEH-01）、イベント規模・バナー・公開状態（UEH-01・UEV-01）

## 実装・設計書で確かめたこと（2026-11-05）

- マイイベント・デッキ登録の一覧には、申込したイベント（キャンセル済みを除く）とデッキを登録したイベントが、開催日時の降順で出る。デッキ登録済みの列の見出しは設計書が「デッキ登録状況」、新実装の画面は「デッキ登録」で、値は設計書が「デッキ登録済み」「デッキ未登録」、新実装の画面は「登録済み」「未登録」（scenario_list.md の食い違い）。L4では設計書の文言で期待値を書き、新実装の表示は記録欄に書く
- 後日の登録は、デッキ登録の条件（「デッキ登録あり」・「デッキ登録を終了する」にチェックなし・締切日時の前）だけで決まる（新実装のデッキ登録の判定）。受付期間が終わっていても登録できる
- 登録するデッキのフォーマットは、イベントに設定されたフォーマットのうちランキング表示またはメタ分布簡易化がオンのものから選ぶ（複数あるときだけ選択エリアが出る）。1つだけなら選択エリアは出ない
- デッキ登録完了メールは会員の都道府県が「海外」かで言語が決まる（UEH-01のREADME）
- デッキ表示（印刷）：メインのカード一覧を1ページ40枚で分け、サイドボードは先頭ページにだけ載せる（0214 デッキ表示 現行仕様）。DCIナンバー・Deck Check Rd・Status・Judgeは廃止（0214 デッキ表示 識別ID:5・9〜11）

## まとめた水準

なし（どの水準も処理が違う）。主な根拠：初回と編集は一覧のボタン名と、デッキの数が増えるか上書きかが違う。ルールが厳しいか否かは開催日のデッキ出力・確認の有無が違う。有料と無料は申込の決済・メールの有無が違う。日本語・英語は表示が違う。
