# UEH-01 有料イベントを登録し、会員が申し込み・決済してデッキを登録し、開催日に受付・実施して参加ポイントがつく

| 項目 | 内容 |
|---|---|
| 利用者 | 店舗チームの担当者（イベントと日程を登録する・開催日に申込一覧を出す）→ 会員のお客様（国内）→（外部：SPLINKSの決済画面）→ ポイントグランター（外部）→ メール |
| 目的 | 有料・オンライン受付ありの競技イベントを登録して公開し、会員が申し込み・決済し、デッキを登録して、開催日に申込一覧とデッキ表示で受付・確認し、実施して、参加ポイントが会員に付く。登録した値（イベント名・店舗・日時・定員・参加費・申込・デッキ・ポイント）が、つなぎ目の画面・メール・CSVで同じ値で引き継がれる |
| 種類 | 正常（通し） |
| マトリクスの行 | `matrix_UEH-01/matrix.md` のT07（1日程だけ申し込む・デッキ登録ありで申込完了画面から登録する・ルールが厳しい競技イベント・バナーを登録する・日本語のサイト・国内の住所） |
| もとのシナリオ | SCN-EVENT-001・003・006・011（イベント管理のUEV-01・UEV-02・UEV-06をつないだもの） |

既存の一覧の各区間は、`イベント管理/` のUEV-01（登録・公開）・UEV-02（申込・決済・デッキ登録）・UEV-06（開催日の受付〜ポイント付与）と `デッキ登録/` のUDK-02、`スマレジ連携/` のUSM-23にある。ここは、その区間のつなぎ目で値が引き継がれて、お客様の画面・メール・店舗チームの画面に出ることだけを通しで確かめる。例外の細部は既存のIDを参照する。

## 前提

- システムの外で済んでいること：イベント計画（スプレッドシート。業務フロー1-1）。参加者が使うクレジットカード（試験環境ではSPLINKSの試験決済画面で決済できるもの）。ポイントグランターの端末が、端末販売の内容をECのAPIへ送れる状態
- 日程の日時は、実行日の1日の中で通せるように決める（試験用）。日をまたぐ待ち（受付期間・開催日）はシステムの状態を待たず、受付状況・イベント終了は日時から表示が決まるだけなので、日時を実行時刻に合わせて前後にずらしてよい。順序だけは守る：オンライン受付の開始＜申込を行う時刻＜オンライン受付の終了＜日程の開始。デッキ登録締切は、デッキを登録する時刻より後
- 用意するデータ（試験用の値。設計書の値ではない）
  - 店舗チームの担当者（開催店舗「店舗A」の編集権限がある。メンバーのデフォルト表示の店舗が店舗A）
  - 会員：試験 花子（本会員、メールアドレス `ueh-01@example.test`、国内（東京都）の住所を登録済み、選手情報あり、スマレジの会員作成済み（USM-12）、保有ポイントは手順に入る前の値を控える）
  - イベント「シナリオ試験 スタンダード大会（有料）」（英語名 Scenario Test Standard Tournament）：店舗＝店舗A、フォーマット＝スタンダード（ランキング表示がオンのフォーマット）、ルール適用度＝競技（ルール適用度のマスターの値）、イベント規模＝定番イベント、公開状態＝公開、定員＝8、チーム戦＝オフ、支払方法＝クレジットカード決済、参加費＝1,000円
  - 日程1：開始＝実行日20:00、受付あり（受付時間 19:30〜19:50）、デッキ登録あり・デッキ登録締切＝実行日19:00、デッキ登録を終了するはオフ、オンライン受付あり（開始＝実行日0:00、終了＝実行日19:00）、定員8・参加費1,000円・公開状態は親イベントを引き継ぐ（申込時に登録しない行（デッキ登録の設定がB2）では、開催日の当日登録（業務フロー3-6）が実施（3-3）の後になるので、デッキ登録締切を実施の後（例：実行日23:00）に設定して登録する。設計書は、登録ボタンの条件を「現在日時が「デッキ登録締め切り」の日時より以前」とする）
  - デッキリスト：スタンダードに則したメインボード60枚・サイドボード15枚以内（試験用の内容）
- 申込のあるイベント・日程は削除できないので、試験が終わったあとにイベントを消す場合は申込・デッキ登録を片付けてから行う

## L3で変わるところ（マトリクスの他の行・例外）

- 申込む日程：別日程もまとめて申し込む行（T04・T05・T06）は、日程を2つ登録し、手順7で日程2にもチェックを入れる。申込確定画面は2件・合計2,000円、申込は2件、メールは日程ごとに2通（各メールのお支払い金額は日程ごとの1,000円）、残り予約数は日程ごとに7。開催日は、申込一覧が2件（日程ごと）で、受付・実施・登録デッキの照合は日程ごとに行う。参加ポイントを日程ごとに付与するかは設計書に定めが無い（記録。scenario_list.md の判断待ち）。デッキ登録は、デッキ登録の設定の水準で分かれる：
  - T04（デッキ登録ありで申込完了画面から登録する）：申込完了画面のデッキ登録ボタンは1つで、先頭の日程のデッキ登録へ進む（新実装の画面。記録）。もう一方の日程のデッキは、一覧から登録する（UEH-03）か、登録しない。デッキ表示には登録のある日程のデッキだけが載る
  - T05（申込完了画面では登録しない）：申込完了画面のデッキ登録ボタンは使わない。日程ごとに、開催日にイベント詳細から当日登録する
  - T06（デッキ登録なし）：デッキ登録のボタンも一覧からの登録も無い。デッキ関連の手順を通らない
- デッキ登録の設定
  - 申込完了画面では登録しない行（T02・T05・T08）：手順11・12・18を通らず、手順13の一覧は「デッキ未登録」・ボタン「デッキ登録」。開催日は、手順21の代わりに業務フロー3-6を通る。この行は日程のデッキ登録締切を実施の後に設定しておく（前提）。参加者が、イベント詳細（デッキ登録の条件を満たす間。締切前・終了にチェックなし）の「デッキ登録」から当日登録し、デッキ登録完了画面・デッキ登録完了メールが出て、一覧が「デッキ登録済み」になる。締切を過ぎる・終了にチェックが入っているとボタンが出ず、デッキ無しのまま実施・ポイント付与へ進む（例外EX9）。ルールが厳しい行（T02・T05）では、当日登録のデッキは開催前の全員分の出力（手順18）に載らない。当日登録後の確認の方法は業務フロー・設計書に定めが無い（記録）。後日に登録し直す通しはUEH-03
  - デッキ登録なしのイベントの行（T03・T06・T09）：日程の「デッキ登録あり」を入れずに登録し、イベント詳細・申込完了画面にデッキ登録のボタンが出ず、一覧にデッキ登録状況・ボタンも出ない。ルールが厳しい行（T03・T09）では、「デッキ登録を検索」が0件で、出力・確認するデッキが無い（業務フロー3-1・3-3の対象は「デッキ登録されたデッキ」）
- ルールの厳しさ：厳しくない行（T01・T04・T06・T08）は手順18のデッキ表示と手順20の照合を通らない
- バナー：バナーを登録しない行（T02・T04・T06・T08・T09）は手順3を通らず、TOPのバナースライダー・大会詳細の最上段のバナー画像が出ない
- 表示言語：英語のサイトの行（T02・T03・T04・T08）は、TOP・大会詳細・申込・デッキ登録の画面が英語で出る（大会詳細の事前予約欄は Pre-registration Information など、デッキ登録のボタンは登録済みでも Decklist）。クレジット決済完了メールが英語のテンプレート（件名「[店名] [Hareruya] Event registration is complete」）
