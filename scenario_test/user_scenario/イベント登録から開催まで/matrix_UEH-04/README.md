# イベント登録から開催までのオンライン受付でないイベント（UEH-04）

IPA「高信頼化ソフトウェアのための開発手法ガイドブック」(2010) の表6-9〜6-11と同じ手順で作る。1行が1本のシナリオ（L3）。

1. 因子・水準表（FL表）: `fl_table.tsv`。利用者が画面で選ぶもの・変わるものを因子にし、設計書の文を根拠に持つ
2. 禁則表: `prohibitions.tsv`。ありえない組み合わせ
3. 組み合わせテストマトリクス: `matrix.md` / `matrix.tsv`。`build_matrix.py` が作る。1行が1本のシナリオになる
4. 例外の差し込み表: `exceptions.tsv`。エラーや中断（★の手順）は、正常な値と混ぜず、条件に合う行へ1つずつ差し込む

## 範囲

- 店舗チームが、オンライン受付なし（日程の「オンライン受付あり」にチェックを入れない）のイベントと日程を登録して公開し、会員がフロントで見つけ（申込のボタンは出ない）、開催日に店頭で受付（参加費の徴収はシステムの外）・実施し、会員登録のない参加者は新規会員登録をして、デッキ登録ありのイベントではイベント詳細からデッキを登録し、参加ポイントがつくところまで（業務フロー 08 の1-1〜1-6、3-2〜3-8、2-1・2-2は通らない）
- 各行の期待値：イベント詳細に事前予約情報の区画（事前予約期間・残り予約数・参加費(事前予約)）が出ず、「イベント申込み」ボタンが出ない（0307 大会詳細 3-7〜3-10「オンライン受付ありの場合にオンライン受付情報を表示する。なしの場合はエリアごと表示しない」）。TOPには受付状況（予約受付中など）を出さない（0307 イベント大会TOP「予約が必要なイベントのみ…受付状況を表示する」）。当日、会員登録のない参加者は新規に会員登録し（UMB-01・UMB-02）、ログインしてデッキを登録すると、一覧に「デッキ登録済み」で載る。申込がなくデッキだけ登録したイベントの処理状態は「未登録」（0306 マイイベント・デッキ登録 (5)）。参加ポイントは会員の保有ポイントとポイント履歴に出る
- 申込・デッキ登録は本店のサイトだけで使える（新実装は、この2つの画面を本店専用にし、支店のサイトからは開けない扱いにしている）。この通しは開催店舗を店舗Aとして、本店のサイトで通す（開催店舗が支店のイベントを本店のサイトから申し込む運用は、設計書に明記が無い。scenario_list.md の判断待ち）
- 同じ会員・同じ日程は二重に申し込めない。キャンセル済みは定員に数えない（開発環境の申込状況マスタ）ので、定員に数える設定が有効な申込状況（決済中・入金待ち・申込済み・入金期限切れ・支払番号が存在しない）が定員を使い、キャンセル済みだけが数えない
- ルールの厳しさは因子に入れない：全員分のデッキの事前出力（3-1）はオンライン受付のイベントの工程で、当日に登録するデッキは出力の時点でまだ無い（UEV-06の禁則X4・X5）。出力と確認が要る競技イベントは、オンライン受付のUEH-01〜03で通す
- 参加費は店頭で徴収する（システムの外）。イベントの参加費は詳細・TOPに表示するだけで、ECの申込・決済は通らない
- 因子に入れなかったもの：イベント規模・バナー・公開状態（UEH-01・UEV-01）、参加費の有無（表示だけ）

## 実装・設計書で確かめたこと（2026-11-05）

- オンライン受付のない日程は、申込できる判定が偽になる（新実装 日程の申込可否の判定は「オンライン受付が開いている」ことが前提）ため、申込のボタンが出ない。デッキ登録のボタンは、申込と無関係にデッキ登録の条件だけで出る（新実装 イベント詳細のボタンの判定）。ログインしていない参加者が押すとログインへ進む
- 当日に新規会員登録した会員はスマレジ側の会員も作られ、ポイントグランターの端末で会員を特定してポイントを付与できる（会員のスマレジ連携はUSM-12）
- 参加者が会員登録を断ると、ポイントなどの受取拒否として終了する（業務フロー 3-4。例外EX1）

## まとめた水準

なし（どの水準も処理が違う）。主な根拠：会員登録済みと新規登録は会員登録の手順の有無が違う。デッキ登録あり・なしはイベント詳細のボタンとデッキ登録完了メールの有無が違う。日本語・英語は表示が違う。
