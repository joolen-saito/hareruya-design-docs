# ユーザー目線のシナリオ一覧の作り方（著者向け）

通販（`通販/`）で作った形を、ほかの業務にも同じ手順で作る。見本は `通販/scenario_list.md` と `通販/matrix/`。先に必ず両方を読むこと。

## ゴール

業務フロー（`scenario_test/markdown/NN_*.md`）の「業務フローパターン」の全パターンが、どれかのシナリオ（L2）に入っているか、理由つきで対象外になっていること。`tools/check_pattern_coverage.py <業務>` が OK を返すこと。

## シナリオの単位

- シナリオ1本（L2）は「起点の業務イベントから、業務として完了した状態になるまで」。目で確かめられる結果を終点に置く
- 担当者が替わっても切らない（お客様→店舗チーム→管理画面→外部システム→メール、までを1本にする）
- 日をまたぎ、システムの状態が何かを待つもの（入荷待ち、発売日まで保管、入金待ち、期限切れ、後日の処理）は別の1本にする
- ただし、日をまたぐのがシステムの外の作業だけで、システムの状態が何も待たないとき（翌朝の郵便局への持ち込み、前日のチェックシート作成など）は分けない
- 階層: L1 業務領域 → L2 シナリオ → L3 バリエーション（条件違い・例外）→ L4 ステップ（画面操作と確認）。今回作るのはL2の一覧とL3まで。L4（手順と期待値）はまだ書かない
- 前提データ（会員・商品・店舗などのマスタ）はシナリオから外す
- システムを触らない作業は「システムの外」と書く。システムを全く触らないパターンは対象外にしてよい（理由を書く）

### 1. `scenario_list.md`

通販と同じ節を同じ順で持つ。

1. 冒頭の説明（単位の決まり）と階層の表
2. `## シナリオ一覧`：列は `| ID | シナリオ | 利用者（担当の順） | 起点 | 終点（目で確かめる結果） | 通る状態 | L3 バリエーション | 優先度 | もとのシナリオ | 業務フロー |`。「通る状態」は、その業務の主な状態（受注ステータス、買取のステータス、在庫移動の状態など）の名前を正本どおりに書く
3. 表の下の注（※1など）
4. `## 業務フローパターンの網羅`：列は `| 業務フロー | # | パターン | シナリオ | 備考 |`。業務フローの番号（例 `12`）、パターンの番号、パターン名（業務フローの表からそのまま写す）、シナリオID（複数は「・」でつなぐ）か「対象外」、備考（対象外なら理由）。tobe版のパターンも1行ずつ入れる
5. `## 対象外`
6. `## 状態の遷移の網羅`：主な状態の遷移ごとに、通るシナリオを書く
7. `## 実装と設計書で確かめたこと`：論点・結論・根拠の表
8. `### 設計書との食い違い（設計書の不足。起票はしない）`
9. `## 今の成果物との関係`：今のシナリオ（SCN-*）とどう対応するか

優先度は、売上・お金への影響と発生頻度で P1〜P3 を付ける。

### 2. 組み合わせテストマトリクス（必要なL2だけ）

利用者が画面で選ぶもの・変わるもの（因子）が3つ以上あり、効き合うL2には、IPA「高信頼化ソフトウェアのための開発手法ガイドブック」(2010) の表6-9〜6-11と同じ手順でマトリクスを作る。L2ごとに `matrix_<シナリオID>/` を作り、次を置く（形は `通販/matrix/` と同じ）。

- `README.md`：1行目は `# <業務>の<シナリオ名>（<シナリオID>）`。範囲と、実装で確かめたこと
- `fl_table.tsv`（因子・水準表）：列 `因子ID 因子 水準ID 水準 設計書・シート 引用 扱い`。因子IDは英大文字1字、水準IDは因子ID＋数字（例 G1）
- `prohibitions.tsv`（禁則表）：列 `禁則ID 水準1 水準2 理由 根拠 扱い`
- `exceptions.tsv`（例外の差し込み表）：列 `例外ID 差し込む元の条件 差し込む手順 例外（★） 期待値 設計書・シート 引用 扱い`。エラーや中断は正常な値と組み合わせず、条件に合う行へ1つずつ差し込む
  - 差し込む元の条件には、例外が成り立つのに要る水準を全部書く（足りない条件を手順で補って回り道しない）。割り付けた行に条件に合う行が無いときは、`build_matrix.py` が条件を含む行を1行足す（テスト数に含め、matrix.md に「例外用の行を足した」と出る）。条件が禁則に当たるときは止まる（2026-11-05）
- 作り方：`nice python3 -I scenario_test/user_scenario/tools/build_matrix.py <フォルダ>` で `matrix.md`・`matrix.tsv` ができる（2因子間網羅率100%まで行を足す。禁則の重なりで成り立たない組は自動で分母から外す）

## 判断の決まり

- 捏造しない。起点・終点・状態名・バリエーションは、業務フロー・設計書・実装のどれかの文を根拠に持つ。根拠の引用は `実装と設計書で確かめたこと` やマトリクスの表に書く
- 決められないことは、まず設計書と実装（現行・新実装・開発環境の設定）を見て決める。それでも決まらないものだけ「判断待ち」とし、何を見たかを書く
- 業務フローと設計書・実装が食い違うときは、設計書を優先し、食い違いを記録する。依頼者の裁定があれば裁定に従う
- 設計書の不足や食い違いは記録するだけで、Backlogに起票しない
- 物理名（テーブル名・列名・内部の識別子）は成果物に書かない。画面名・画面の文言・業務の名前で書く。現行ソースの根拠は「現行ソース pf-eccube3 の〇〇の処理」のように書いてよい
- 文章は短く、結論を先に書く

## やってはいけないこと

- 自分の業務フォルダ（`scenario_test/user_scenario/<業務>/`）の外のファイルを書き換える（道具の不具合を見つけたら直さずに報告する）
- codex を動かす、git commit する、DBに接続する、Webを見る
- リポジトリ全体を検索する、巨大なHTMLを丸ごと読む（マシンの資源が少ない。重い処理は `nice` を付け、1本ずつ）

## 水準のまとめ方（2026-11-05 依頼者決定）

依頼者「種類別のフローや処理が変わらないならまとめて」。マトリクスの水準は、業務の流れ・システムの処理・画面の表示・期待値のどれかが変わるものだけを分ける。変わらない種類（例：本人確認書類の7種類が、どれも同じ画面で同じ処理なら）は代表の1つにまとめる。
- まとめるときは、まとめた種類の一覧と「流れ・処理が変わらない」根拠（設計書・実装の文）を、そのマトリクスの README の `## まとめた水準` に書く
- 種類によって設定やマスタの扱いが違う（例：開発環境のマスタで一部の種類が表示されない）なら、処理が違うので分ける。迷ったら分けたままにして理由を書く
- 例外の差し込みや禁則で、まとめた水準を参照していたら直す。直したら build_matrix.py を流し直す

決まり：
- 1フォルダに通しシナリオ1本。`scenario_list.md` に、利用者と目的、起点・終点、**区間の表**（区間ごとに今のL2のIDと、区間のつなぎ目で引き継ぐ値）、業務フローパターンの網羅、パターンの表、状態の遷移の網羅、確かめたこと、食い違い、判断待ち、まとめた水準を書く
- 通しシナリオは、待ちの状態（入金待ち・入荷待ち・日をまたぐ処理）があっても切らない。待ちは「区間の境目」として書き、そこで確かめる状態を期待値にする
- **パターン**：業務フローの分岐・利用者の選択・データの違いを因子にして `matrix_UTH-0x/` で組み合わせる（2因子間100%）。業務フローのパターンは全部、どれかの行か例外に割り当てる（割り当てられないものは対象外と理由）。パターンの行1つが「始まりから終わりまで通す1回の試験」になる
- **L4**：`UTH-0x_<題>.md` に、代表のパターンの手順と期待値（手順ごと）を書き、ほかのパターンは「パターンで変わるところ」（どの手順の何が変わるか）を表で書く。期待値は設計書の文言・画面項目・状態・新実装で言えるものだけ
- 区間の細部（例外・境界）は今のL2とそのマトリクスに任せ、通しシナリオでは「つなぎ目で値が正しく引き継がれ、利用者に見えるか」と「パターンで流れが変わるところ」を確かめる
