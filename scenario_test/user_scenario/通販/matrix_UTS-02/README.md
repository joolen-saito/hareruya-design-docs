# 通販の取り消し・返金（UTS-02）

IPA「高信頼化ソフトウェアのための開発手法ガイドブック」(2010) の表6-9〜6-11と同じ手順で作る（形は `../matrix/` と同じ）。`fl_table.tsv`（因子・水準）・`prohibitions.tsv`（禁則）・`exceptions.tsv`（例外の差し込み）から `matrix.md`・`matrix.tsv` を `build_matrix.py` が作る。2026-11-05 の裁定R13（支払方法は6種類）で、取り消しと返金が支払方法ごとに変わるので、マトリクスを作った。

## 範囲

- 出荷の前の取り消しと、一部の返金（注文金額の変更）。お客様が依頼する（UTS-02の起点）。出荷完了のあとの返品はUTS-19、入金が無いまま期限が来て通販チームが取り消すのはUTS-18
- 支払方法は `../matrix/` の水準S1〜S7（S1・S2のクレジットカード決済と登録済みクレジットカード決済は、ここではA1にまとめた。店頭支払は通販の配送方法に結び付かないので対象外）
- 受注の状態は、取り消す前の状態。入金待ちは銀行振込だけ（購入の直後）。注文受領は入金前（全額ポイント支払い・代金引換・郵便振替・コンビニ決済）。入金済みは入金確認またはカード決済の完了のあと。出荷指示は出荷指示リストを作ったあと（入金の前後がある。出荷準備は入金が無くても進める：業務フロー16 2-5の注）
- 返金の方法（振込による返金／ポイント付与による返金）は、お客様が選ぶ二択（業務フロー16 9-2）。入金済みの郵便振替・銀行振込・コンビニ決済の行は、**二つとも確かめる**（行の数は変えず、L3として二回行う）

## 期待値の決まり

| 支払方法 | 入金前（入金待ち・注文受領・入金前の出荷指示） | 入金済み（入金済み・入金済みの出荷指示） |
|---|---|---|
| クレジットカード決済・登録済みクレジットカード決済 | （無い。購入の直後に入金済み） | 全部：SPLINKSで請求キャンセル（8-2）。一部：SPLINKSで減額（8-2）。依頼者に報告（8-3）。減額できないときは報告だけで、返金は依頼元の部署へ（例外E1） |
| 全額ポイント支払い | 全部：使用ポイントが自動で戻る（0203）。一部：会員管理のポイント付与（注文金額変更によるご返金。9-8）。全額ポイントの返金はポイント付与以外では行わない（9-8の注） | （無い。入金済みにならない） |
| コンビニ決済・郵便振替・銀行振込 | 返金は無い（支払われていない）。コンビニ決済は、新実装の受注情報編集に、決済（支払い番号）を削除する操作がある（業務フロー・設計書に無い） | お客様に「振込による返金」か「ポイント付与による返金」かを確認（9-2）。振込：口座を確認して経理に依頼→経理が振込→お客様に完了報告→返金処理記録を更新（9-4〜9-7）。ポイント付与：会員管理のポイント付与→お客様に返信（9-8・9-9） |
| 代金引換 | 返金は無い（代金は配達時に受け取る） | （無い。出荷の前に入金済みにならない。判断待ち） |

受注・在庫・ポイントは支払方法によらず同じ（0203 受注情報編集）。

| 取り消しの範囲 | 受注の状態 | 在庫 | 使用ポイント | 付与ポイント |
|---|---|---|---|---|
| 全部（C1） | キャンセル（キャンセル日が入る。「全キャンセルが完了しました。」） | 注文数が戻る。在庫履歴に「キャンセル時の在庫戻し」。総原価は受注に保存した原価だけ戻る（業務横断 UXB-02） | ポイントを使った注文は戻る | 出荷前なのでまだ付与されていない（ポイント履歴があれば削除される） |
| 一部（C2） | 変わらない（「一部キャンセルが完了しました」） | キャンセル分だけ増える | 変動なし（確認ダイアログM05-11-MSG-016・017） | 付与予定ポイントを再計算する |

## 実装と設計書で確かめたこと（2026-11-05）

- 受注の状態の遷移：新実装は、画面（受注情報編集）からのキャンセルを、注文受領・入金待ち・入金済み・出荷指示・ピック中・ピック完了・店頭予約・出荷完了・引き渡し済みのどれからも許し、購入処理中・決済処理中からは許さない（`app/config/eccube/packages/order_state_machine.php` 200〜211行目）。キャンセルで在庫・使用ポイント・期間別販売数を戻す（`src/Eccube/Service/OrderStateMachine.php` 100行目）。受注情報編集の保存は、キャンセルでポイント履歴を削除し、保持ポイントを戻してスマレジへ連携する（`src/Eccube/Controller/Admin/Order/EditController.php` 730・918行目付近）
- 入金待ちになる支払方法：新実装は銀行振込だけ（`src/Eccube/Service/PurchaseFlow/Processor/OrderUpdateProcessor.php` 45行目）。設計書 0304 F04-04 は「注文受領または入金待ち」とだけ書く
- SPLINKSの操作：新実装のコンビニ決済・クレジットカード決済プラグインは、受注の一覧・編集の画面から決済の売上確定・取消（コンビニ決済は決済の削除）を実行できる（`app/Plugin/SlnPayment42/Controller/Admin/OrderController.php` 47行目〜）。業務フロー16の8は、SPLINKSの管理画面で処理するとする。設計書 0203 に決済の操作は無い
- 現行（pf-eccube3）は銀行振込と旧コンビニ決済を入金待ちにする（`app/Plugin/HareruyaEc/Service/ShoppingService.php` 530〜535行目）

## 判断待ち（何を見ても決まらなかったもの）

1. 代金引換の受注の入金（配達時の代金の回収を、台帳・受注に反映する手順）：業務フロー16・17、設計書 0203・0304、新実装に記述が無い。代金引換×入金済みの組は禁則（X9・X12）に入れ、判断待ちとして外した
2. 入金を確認した受注を入金済みにする担当者・時点：業務フロー16 の3は、発送管理台帳の入金日を更新するとだけ書く。設計書 0203 は、ステータス変更で「入金済み：入金日を登録」と定め、新実装はその遷移を持つ（UTS-16）

## まとめた水準

- クレジットカード決済（カード情報を入れた）と登録済みクレジットカード決済を、A1にまとめた。取り消しと返金はどちらもSPLINKSの請求キャンセル・減額で、受注の状態（購入の直後に入金済み）、在庫・ポイントの戻りも同じ（業務フロー16 8-1・8-2は決済の種類を分けない。0203 受注情報編集のキャンセルは支払方法で分岐しない）。違うのは購入のときのカード情報の入力だけで、それは `../matrix/` のS1・S2で確かめる
- 分けたまま：郵便振替・銀行振込・コンビニ決済（購入直後の状態、入金の確認の方法、決済の削除の有無が違う）、代金引換、全額ポイント支払い（返金がポイント付与だけ）。受注の状態5種類も、返金の要否・取り消せる元の状態が違うので分けたまま
