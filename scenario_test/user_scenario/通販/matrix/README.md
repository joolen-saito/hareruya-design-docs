# 通販の購入（UTS-01）

IPA「高信頼化ソフトウェアのための開発手法ガイドブック」(2010) の表6-9〜6-11と同じ手順で作る。

1. 因子・水準表（FL表）: `fl_table.tsv`。お客様が購入の画面で選ぶもの・変わるものを因子にし、設計書の文を根拠に持つ
2. 禁則表: `prohibitions.tsv`。ありえない組み合わせ
3. 組み合わせテストマトリクス: `matrix.md` / `matrix.tsv`。`build_matrix.py` が作る。1行が1本のシナリオになる
4. 例外の差し込み表: `exceptions.tsv`。エラーや中断（★の手順）は、マトリクスの行に1つずつ差し込んで別のシナリオにする（資料の6.3.2「シナリオを用いた効果的なピンポイントテスト」）

設計書に無い決まり（送料無料でゆうパケットが消える、海外で50,000円を超えるとSmall packetが消える、国内ではEMSが出ない、荷物の大きさで配送方法が絞られる）は、現行ソース（pf-eccube3）の配送方法の絞り込みと送料無料の判定で確かめ、扱い欄にそう書いた。

エラーになる値は、正常な値と混ぜて組み合わせない。混ぜると、先にエラーになった値に隠れてほかの値が確かめられないため。

## 範囲

- 本店のオンラインショップで、通常の購入グループの会員が買うところまで。非会員は買えない（2026-11-02 依頼者回答）
- 支払方法（2026-11-05 裁定R13でR0を改めた）：通販で選べるのは、クレジットカード決済・登録済みクレジットカード決済・全額ポイント支払い・コンビニ決済・郵便振替・銀行振込・代金引換の7水準。裁定の6種類のうち**店頭支払**は、新実装の開発環境でも現行（pf-eccube3）でも店頭受取の配送方法だけに結び付き、通販の配送方法（ゆうパック・ゆうパケット・EMS・Small packet・International TA-Q-BIN・同梱）では選べないので、通販のマトリクスに入れない（店頭受取受注管理で扱う。支店・店内アカウントの店頭支払もそちら）

### 設計書・実装の食い違い（起票しない）

1. 同梱の元の支払方法：設計書は銀行振込・郵便振替の受注だけ。新実装は支払方法の名前が店頭支払・代金引換・クレジットカード決済・コンビニ決済と完全に一致する受注だけを外すので、登録済みクレジットカード決済・クレジットカード決済（GMO）・全額ポイント支払いの受注も同梱の元になる（例外E13）
2. 同梱の件数：設計書は最大2件、新実装も2件だが、画面の案内は「最大3件」（`scenario_list.md` の食い違い）
3. 同梱と全額ポイント支払い：設計書の中で決まらない（禁則X41。判断待ち）
4. 代金引換の手数料の段階：開発環境には代金引換が5段階ある（330円・550円・880円・990円・1,430円。それぞれ30,000円ごとの利用条件）が、配送方法に結び付いているのは330円の1つだけで、30,000円以上の代金引換は選べない。設計書は手数料の値を定めない。段階の確認は判断待ち
5. コンビニ決済の購入直後の状態：設計書 0304 決済~購入完了は「注文受領または入金待ち」とだけ。新実装は注文受領、現行 pf-eccube3 の購入確定は銀行振込と旧コンビニ決済（ID 6）を入金待ちにする
6. 設計書の支払方法一覧に、登録済みクレジットカード決済・全額ポイント支払い（支払いなし）が無い（`../scenario_list.md` の食い違いに既出）

### 支払額の境界の確認（代金引換・コンビニ決済。例外E15・E16と、S7・S4の行の決まり）

- S7・S4の行は、お支払い額が上限以内になるよう用意する。商品金額の水準だけでは上限を超える行（K2〜K4）は、使用ポイントで下げて実行する。ポイントを使わない行（J1）で上限を超えるときは、その支払方法が選べないことの確認（E15・E16）になり、同じ行のほかの水準は選べる支払方法で続ける
- 境界（開発環境の値）：

| 支払方法 | 選べる | 選べない | 確かめること |
|---|---|---|---|
| 代金引換 | お支払い額（手数料込み）が29,999円 | 30,000円 | ゆうパックで、商品金額＋送料＋330円−使用ポイントを29,999円・30,000円にして選択肢を見る。ポイントを増やして30,000円から29,999円へ下げると選べる |
| コンビニ決済 | 299,999円 | 300,000円 | 同様。K4（30万円以上）でポイントを使わないと選べず、使うと選べる |
