# 通販：シナリオ一覧（L2）

シナリオ1本は「起点の業務イベントから、業務として完了した状態になるまで」とする。担当者が替わっても切らない（お客様→通販チーム→外部システム→メール）。日をまたぐもの（予約の入荷待ちなど）は別の1本にする。ただし、日をまたぐのがシステムの外の作業だけで、システムの状態が何も待たないとき（Small packetの翌朝の持ち込み、発売前日のチェックシート作成など）は分けない。条件違いはL3のバリエーションとして、組み合わせテストマトリクス（ペアワイズ）で絞る。

| 階層 | 単位 | 通販での置き場所 |
|---|---|---|
| L1 業務領域 | シナリオのグループ | 受注〜出荷（通販） |
| L2 シナリオ | 起点イベント→業務完了 | この表の1行 |
| L3 バリエーション | 条件違い・例外 | `matrix/`（UTS-01の購入部分）・`matrix_UTS-02/`（取り消し・返金）・`matrix_UTS-19/`（返品）と、各行の「L3」欄 |
| L4 ステップ | 画面操作と確認 | 各シナリオの「操作の流れと期待値」 |

### 判断待ち（何を見ても決まらなかったもの）

1. 代金引換の受け取り拒否・返送の扱い（受注の状態・在庫・送料）：業務フロー16・17、設計書0203・0304・0405、新実装に記述が無い
2. 代金引換の代金の回収（配送業者からの入金）を台帳・受注に反映する手順：同上に無い
3. 入金を確認した受注を入金済みにする担当者と時点（出荷準備のあと＝出荷指示の受注を入金済みに変えるかも含む。新実装は出荷指示から入金済みを許すが、設計書0203に定めは無い）：業務フロー16の3は台帳の入金日の更新まで。設計書0203と新実装は入金済みへの変更を持つ
4. 同梱と全額ポイント支払いの組み合わせ：設計書0304の同梱の規定（支払は郵便振替・銀行振込だけ）と全額ポイントの規定が衝突。新実装は同梱に全額ポイントも結び付ける
5. 代金引換の高額帯の手数料（550円〜1,430円）：開発環境で配送方法に結び付いておらず、30,000円以上の代金引換は選べない。設計書は値を定めない
6. 返品の物の流れ（返送・検品・在庫に戻す時点）：業務フローに無い
7. 未入金のキャンセル（UTS-18・20）の「1週間」の数え方と休業日の扱い：業務フロー16 R280・R281は「受注の5日後」「受注1週間後」とだけ書き、休業日・営業日・時刻の定めが無い。設計書 0203 の入金期限は「Ph2へ見送り」で（2863・2984行）、0304 にも期限の定めが無い。新実装の画面の案内（`messages.ja.yaml` 1364行）は「ご注文いただいた日から起算して7日後の15時まで。期限当日が金融機関の休業日に該当する場合は、その後の最初の営業日の15時」。休業日に当たる注文を1週間後にキャンセルすると案内した期限より前になる。キャンセルの日を営業日にずらすか、5日後の案内も営業日で数えるかは決まらない（UTS-20のL3に休業日の水準を置いた）
8. 受注一覧の対応状況の一括変更でキャンセルにしたときの付与の取り消しとポイント履歴の削除、受注情報編集のキャンセルでの使用ポイントの二重戻しの疑い（UTS-02・UTS-19・業務横断 UXB-02・UXB-03）：ポイントの UPT-07 の例外E1・README、判断待ち4・6。新実装の一括変更は履歴の削除と付与の取り消しを呼ばない（`src/Eccube/Controller/Admin/Order/OrderController.php` 516〜595行）。通常経路は受注情報編集のキャンセルで、期待値はUPT-07の表
9. 同梱と全額ポイント支払いの組み合わせ（X41。上の4）は、商品管理から注文確認メールまでの UPM-01 の判断待ちでも同じ論点で、そちらは同梱の購入の注文確認メールを範囲外（UTS-16）にしている。決まるまで同梱の購入の期待値はここ（UTS-01のマトリクス）で決めない
10. 外部委託できない受注の条件（UTS-08）：業務フロー16の12-2は「委託対応が不可の受注を抜き出しそれぞれ削除する」とだけ書く。見たもの：業務フロー16の12-1〜12-9、0203 の全シート（「委託」の語が無い）、通しシナリオ/UTH-05の判断待ち1。条件が決まるまで、UTS-08のL3は「委託できない受注を除く」とだけ置き、除く受注の水準は作らない
11. 外部委託の受注が出荷指示になる時点（UTS-09）：業務フロー16の12-5〜12-8は追跡番号の取り込みで出荷完了にすると書くが、取り込みの前に受注が出荷指示になる時点・担当は書かない（見たものは上と同じ）。期待値に時点を入れない
12. 受注マスターの保存検索「【通販】1.1 台帳用CSV」（業務フロー16 2-1）の検索条件：業務フロー16に名前しか無く、設計書0203に保存検索の条件の記述が見つからない。検索の使用と二つのCSVのダウンロードはUTS-01のL3に書いた。検索条件で絞られる受注の期待値は決めない
13. 注文者が会員でない受注の出荷実績の取り込み（エラーになる。0203 HTML 4240行付近）：通販で非会員は買えない（2026-11-02 依頼者回答）ので、取り込み前の非会員の受注を通販の画面操作で用意できない。非会員の受注を用意する経路が決まるまで手順を書かない
14. （解消）配送方法に海外区分の設定が無い受注：開発環境の配送方法の海外区分は必ず真か偽のどちらか（DBダンプの列定義 NOT NULL。新実装 DtbShippingStandbyRepository.php:240 の振り分け）で、区分が無い配送方法は作れないので、網羅マトリクスでは適用外にした
15. SPLINKS支払いなのに決済記録が無い受注（受注ステータスを処理中へ戻す。0304 HTML 2159行）：画面操作で決済記録の無い状態を作る手順が設計書にも業務フローにも無い
16. 購入完了の時点の受注のステータスが注文受領でも入金待ちでもない場合の購入処理異常（アラートメールと購入処理エラー画面。0304 HTML 2141行）：画面操作でその状態を作る手順が設計書にも業務フローにも無い

### 設計書との食い違い（設計書の不足。起票はしない）

- 0304 決済~購入完了の判定は「受注ステータスが注文受領または入金待ちか」で、入金済みが無い。新実装は「クレジットカード決済の入金済み」も購入完了を出す。開発環境の設定ではクレジットカード決済の直後は入金済みなので、設計書どおりだと購入完了が出ない
- 登録済みクレジットカード決済（現行・新実装・開発環境にある）が設計書の支払方法に無い。マトリクスには支払方法の因子として入れた
- 全額ポイント支払い（新実装の「支払いなし」）が設計書 0304 6-2 の選択肢に無い（業務ロジックの文にはある）
- 同梱：元の受注の支払方法の条件（設計書は銀行振込・郵便振替だけ、新実装は名前が店頭支払・代金引換・クレジットカード決済・コンビニ決済と一致するものだけを外す）、画面の案内の最大3件（設計書は2件）、全額ポイントとの衝突（`matrix/README.md`）
- 0304 決済~購入完了は購入直後の状態を「注文受領または入金待ち」とだけ書く。支払方法ごとの状態（銀行振込だけ入金待ち等）は新実装による
- 新実装のSPLINKSプラグインには、受注の画面から決済の売上確定・取消・コンビニ決済の結果照会・金額変更・削除を行う操作があるが、設計書 0203 に決済の操作が無く、業務フロー8はSPLINKSの管理画面で処理するとする
- 未入金の支払期限：画面の案内は「7日後の15時まで。期限当日が金融機関の休業日ならその後の最初の営業日の15時」（新実装）。業務フロー16 R281は「受注1週間後」で休業日の定めが無く、設計書 0203・0304 に期限の定めが無い（入金期限はPh2見送り）。休業日に当たるとキャンセルが案内より先になる
- 出荷完了のあとの返品の手順（誰がいつ・返金の方法）が業務フロー16・17に無い（業務横断 UXB-03 と同じ）。受け取り拒否の記述はどこにも無い
- 開発環境に International TA-Q-BIN (US Only)（海外向け）があり、お客様が選べる設定だが設計書に無い。マトリクスには配送方法の水準として入れた
- 欠品登録は「数量から欠品数を減算する」「減算した分に対して受注情報の再計算を行う」とだけあり、全部欠品（数量が0になる）のときの受注の扱いが設計書に無い
