2026-11-24 依頼者「わかりにくいね。人間にとっては。業務パターンを業務フローExcelから言語化して、それとマッピングするのはどうかね」→「よい」。業務フロー05（店頭受取受注管理）で試作し（`05_店頭受取受注管理.tsv`）、codex 3巡（`../review/dispositions_routes_R1〜R3.md`）で決まったこと。**書く前に、05 の TSV と R1〜R3 の採否を読む**。

## ファイル

- 1シート1ファイル：`routes/<業務フロー>.tsv`（例 `06_店頭買取.tsv`。「業務フロー」の列はファイル名＋`.md`）
- 列（タブ区切り・この順）：`業務フロー	道筋	パターン	業務パターン	分かれ目	業務条件の値	判定	通すシナリオ	前後のテスト	Excelとシナリオの違い	Excelの行	図の読み替え	飛ばす工程	対象外の区分	理由	決めた人	備考`
- 確かめ：`cd scenario_test/user_scenario && nice -n 10 python3 -I tools/build_route_table.py check 06 07`（シートの番号）。OK になるまで直す。止まる条件は `tools/build_route_table.py` の冒頭

## 正本（ここに無いことは書かない）

- 業務フローの文：`scenario_test/markdown/<業務フロー>`（Excel の書き起こし。行番号 R は Excel の行）。図の流れ（パターンの区間）は `python3 -I -c "import sys; sys.path.insert(0,'tools'); import verify_flow_coverage as vf; print(vf.sections_of('06'))"`
- 11/20 の照合（要素ごと）：`業務フローとの照合/02_パターン.tsv`・`03_工程.tsv`（工程ごとの扱い・通すシナリオ）・`04_分かれ道.tsv`（判断の矢印ごとの業務条件の値・通すシナリオ）・`05_条件の文.tsv`
- シナリオ：`<業務>/scenario_list.md`、テスト：`<業務>/matrix_<ID>/matrix.tsv`、業務条件の値：`網羅マトリクス/<業務>/factors.tsv`
- 対象外の決定：`業務フローとの照合/照合結果.md`「通していないものと依頼者の決定（2026-11-24）」、各 scenario_list.md の「対象外」、factors.tsv の備考、`tools/build_flow_proof.py` の DECIDER（決めた人の書き方）

## 書き方

1. **1行＝道筋1本**。パターンの区間の最初の工程から最後の工程まで。判断の矢印の行き先ごと、条件の文（「※支店のみ」「〜の場合は」「キャンセル後に来られた場合」など）の分かれごとに1本。
2. **道筋**：`<シート番号>-<区間の番号>-<A,B,…>`（例 `06-1-A`）。**パターン**：`<区間の番号> <区間の名前>`（sections_of の番号と名前。13 の 7〜13 のように図が対のシートにあるパターンは、図のあるシートの道筋が受け持つ）
3. **業務パターン**：Excel の文だけで書く（順番・状態の名前・日数・誰が何を確かめるか・自動か手動か・※の注記）。Excel に無いことを補うときは「業務フローに無く、<シナリオID> では…」と書いて出どころを示す。人の作業（ピッキングなど）も流れとして書く。2本目からは「（〜までは 06-1-A と同じ）→ …」と短くしてよいが、**Excelの行は最初の工程から全部**引く
4. **Excelの行**：通る順に `R23・R29・…`。工程の行（03_工程.tsv の R）と条件の文の行（05_条件の文.tsv の R）。見出しの行は引かなくてよい
5. **分かれ目**：その道筋に進む条件を短く
6. **業務条件の値**：分かれ目の値ID（`B1-1・B7-2`。04 の「業務条件の値」・05 の「引用する業務条件の値」から）。**1つの業務条件につき1つ**。前の道筋の続き（キャンセル後の来店など）は前の道筋の値も持つ。
   **判断の矢印のどれを通るかは、この値で決まる**（04 の矢印の値を持てば、その矢印を通る。行き先の工程があれば引く。行き先が範囲外の行ならよい）。
   判断の帯と行き先を引くのに値を持たないと止まる（本当に通らない判断なら「飛ばす工程」に `判断R57：理由`）。
   判断で終わる道筋（「拒否された場合は…終了する」）は、判断の帯を最後の工程にし、その帯の条件の文とその値を引く
7. **通すシナリオ**：業務の順に `UOR-01 → UOR-02 → UOR-09`。同じ道筋を別の目で見るシナリオは「、」のあと（`、UXB-09`）。03〜05 で、その工程・矢印・条件を通すシナリオと合わせる（合わないと止まる。照合の側が誤っていると思ったら直さずに報告する）
8. **前後のテスト**：分かれ目の値を持たないシナリオ（注文〜ピック、夜間の処理など）のテストを、マトリクスの列の値で選ぶ：`UOR-01：受取店舗=本店・配送方法=店頭受取／UOR-09：スマレジ商品削除の対象となる受注の状態=キャンセル／UXB-09`。値は頭が一致すると当たる（「店頭受取」は「スムーズ店頭受取」に当たらない）。列名に「・」があってもよい（列名を見て区切る）。例外は `UEV-06/EX1` と直に書く（matrix.tsv の No. か exceptions.tsv の例外ID）。マトリクスの無いシナリオは ID だけ（通販の UTS-01 は 通販/matrix/ を読む）。道筋のどのシナリオにもテストが付かないと止まる。**分かれ目の値で付くシナリオでも、前後のテストでそのシナリオを名指しすれば、名指ししたテストだけになる**（値で区別できないテストを外すとき：減額と請求キャンセルなど）
9. **Excelとシナリオの違い**：Excel の流れと、新しいシステム・シナリオ・テストの違い（状態の名前、テストの印刷のしかた・支払方法ごとの違い、依頼者の決定で変わった手順など）。根拠（シナリオID・文書・決定の日付）を書く。「／」で区切る
10. **図の読み替え**：図がその道筋のシステムと違うレーンで描いてあるとき（例：支店でも図は EC-CUBE（本店））だけ `EC-CUBE（本店）→EC-CUBE（支店）／根拠：R211「…」`
11. **飛ばす工程**：道具が見分けられないときだけ。「／」で区切り、理由には根拠の R 番号を入れる。**まず空で check し、止まったものだけ書く**。
    - `R275：理由`：引かない工程（図の矢印が無い・注記の書き誤りなど）。選ばなかった判断の側の工程と、前提の条件（工程の行そのものの条件の文と「〜のみ」の文）に当たらない工程は、道具が自分で分かるので書かない
    - `帯R52：理由`：1つの帯に別の工程の文と判断が入っていて、選ばなかった側の工程に見えるが引く
    - `判断R57：理由`：判断の帯と行き先を引くが、その判断は通らない
12. **対象外の道筋**：判定「対象外」、区分・理由・決めた人を全部書く。
    - システムを触らないパターン・分岐（11/24 依頼者「足さなくて良い」）：区分「システムを触らない」、決めた人「依頼者 2026-11-24「システムを触らないなら足さなくて良い」」
    - tobe のシートの現状の区間・刷新後に使わない運用（03_工程 の扱い「範囲外」など）：区分「刷新後に使わない運用」、決めた人「依頼者 2026-11-24「外したままで良い」」。範囲外の工程は通るの道筋に入れない（止まる）
    - フェーズ2見送り：区分「フェーズ2見送り」、決めた人「設計書のフェーズ2見送り・依頼者 2026-11-24「外したままで良い」」
    - 依頼者の決定で外した値：区分「依頼者の決定で外した値」、決めた人「依頼者（<日付>の決定）・2026-11-24「外したままで良い」」（日付は factors.tsv の備考・05 のメモから）
    - 理由には 03〜05 のメモ・scenario_list.md の対象外の表・factors.tsv の備考を引く。対象外の条件の文が別の分かれ（「EMS の場合は…」など）を表すときは、その分かれを対象外の道筋1本にする。説明・注記だけの条件の文（分かれ道でない）は、通るの道筋の文に入れて引く
13. 図の画面・データ、システムを触らない工程の列、通すテスト（分かれ目の値を持つテスト）は道具が足すので書かない。**システムの外の工程（ピッキングなど）も、通る道筋の Excel の行には引く**（道具はそれを「システムを触らない工程」の列に出す）
14. 区間：同じ番号の区間が2つあるとき（12 の「8 欠品対応」と「8 安価カード在庫補充作業」）は名前で引くので、パターンの列は区間の名前どおりに書く。区間の見出しの行が照合で工程（扱いが見出し以外）なら、それを最初の工程として引く。判断は、その道筋の区間の中のものだけを見る（同じ値が別の区間の判断に付いていても構わない）。図に流れが無いパターン（パターン一覧にだけある）は、Excel の行を空にした道筋で、パターン一覧のシナリオで通す
15. 道具が自分で分かること（書かなくてよい）：選ばなかった判断の側の工程、上へ戻る矢印（一部キャンセルで査定に戻る など）を選んだ道筋の2周目、判断で終わる道筋の判断より下、図形につながっていない矢印（全キャンセル）を選んだ道筋の終わりより下、範囲外の工程、前提の条件（工程の行そのものの条件の文と「〜のみ」。ただし同じ工程の中に同じ業務条件の別の値の条件の文があれば工程の中の分かれとみる）に当たらない工程、合流（前の工程から図の矢印で来る）
16. 順番：上から下へ。図の矢印が上へ戻るところは矢印の向きどおりに並べる（図の矢印の向きと逆に並べると止まる）
17. 図の矢印の行き先がずれているとき（図形が上の帯の最後の行にかかっている、矢印の先が図形につながっていないが行き先が文で分かる）は、`routes/arrow_fix.tsv` に根拠つきで書く（担当は書かずに報告する。まとめ役が足す）
18. **分かれ目の値を道筋から外して止まるのを避けない**（道具をだますことになる。判断の矢印の値は、その側の道筋が必ず持つ）。道具で表せないときは報告する

## してはいけないこと

- 自分の routes/<業務フロー>.tsv 以外を書き換えない（03〜05 の TSV・step_map・シナリオ・道具も）。照合や工程の対応表の誤りを見つけたら報告だけする
- 結合テスト（integration_test/・e2e/・項目表）に触れない
- 重い処理は `nice -n 10` で1本ずつ。リポジトリ全体の検索はしない（上の正本のファイルを名指しで読む）
