# 店頭受取受注管理の注文からピック完了まで（UOR-01）

IPA「高信頼化ソフトウェアのための開発手法ガイドブック」(2010) の表6-9〜6-11と同じ手順で作る（`通販/matrix/README.md` と同じ）。

1. 因子・水準表（FL表）: `fl_table.tsv`。会員が注文の画面で選ぶもの、店舗が選ぶ印刷の経路を因子にし、設計書の文を根拠に持つ
2. 禁則表: `prohibitions.tsv`
3. 組み合わせテストマトリクス: `matrix.md` / `matrix.tsv`。`tools/build_matrix.py` が作る。1行が1本のシナリオ（注文からピック完了まで）になる
4. 例外の差し込み表: `exceptions.tsv`。エラーや中断（★）は正常な値と混ぜず、条件に合う行へ1つずつ差し込む

## 範囲

- 本店または支店のオンラインショップで、通常の購入グループの会員が「店頭受取」または「スムーズ店頭受取」で注文し、店舗がスタック用紙を出してピックし、受注が「ピック完了」になるまで。非会員は買えない（通販と同じ。2026-11-02 依頼者回答）
- 店頭PC（店内アカウント）の注文は購入グループが違い、支払方法も店頭支払（店内PC）に決まるので、UOR-06 にする（因子が実質1つで、マトリクスにしない）
- 通販と同じ因子（商品の探し方・カートに入れる画面・お届け先・配送希望日・ポイント・国・金額・販売制限）は入れない。店頭受取・スムーズ店頭受取ではお届け先・配送方法の欄を出さない（0304「店頭受取、スムーズ店頭受取を選択した場合は配送方法エリアを非表示にする」）、配送希望日時は支店で非表示、備考欄は非表示（0304「店舗受取の場合は備考欄を非表示とする」）。ポイントは新実装の注文画面が「店頭受取・スムーズ店頭受取・支店」では使用欄を出さず、案内文言だけにする（新実装の注文画面の、ポイント使用欄を出すかどうかの判定）
- 予約商品は入れない（判断待ち。`scenario_list.md` の判断待ちを見る）

## 法令の表示の確認（SV-16。毎行で確かめる）

最終確認画面（ご注文方法指定）の特定商取引法の申込み段階の表示（消費者庁ガイドライン。分量・価格と支払総額・支払の時期と方法・引渡時期・撤回と解除の条件、有償の申込みになることの明確化、訂正の手段、離脱しても確定しないこと）は、因子にしない。マトリクスの全ての行と、例外の差し込みで、最終確認画面に着いたときに毎回確かめる。確認項目LO-01〜LO-13、支払・引渡しが店頭で行われる点を踏まえた当てはまりの判断、実行の決まりは `../legal_check.md`。水準で表示が変わるもの（受取店舗の支店の合計と内税のみの表示・ボタン「購入する」、配送方法、支払方法、端末、表示言語）は、行の水準で表示を確かめる。表の `fl_table.tsv`・`prohibitions.tsv`・`exceptions.tsv` は変えない。

## 実装で確かめたこと（2026-11-03）

- 配送方法と支払方法の結び付き（開発環境の設定。新実装リポジトリのDBダンプ 2026-09-07）：店頭受取＝店頭支払・支払いなし・店頭支払(店内PC)。スムーズ店頭受取＝支払いなし・クレジットカード決済・登録済みクレジットカード決済。店頭受取系の配送方法は、通常商品の販売グループに結び付く
- 通常会員グループが選べる支払方法に、店頭支払・支払いなし・クレジットカード決済・登録済みクレジットカード決済が入っている。店頭支払(店内PC)は店内アカウントだけ
- 「支払いなし」（全額ポイント支払い。水準C4）：開発環境の設定では店頭受取・スムーズ店頭受取の両方に結び付く。依頼者の裁定R13（2026-11-05）で残す。0304 は支店でポイントを表示しないと定め（X10）、本店ECでは「ポイント使用」を表示するので、本店の店頭受取・スムーズ店頭受取とも対象にする（R4指摘）。現行 pf-eccube3 は店頭受取だけ、新実装は店頭受取・スムーズ店頭受取の両方でポイント欄を非表示にするので、新実装で通るかは流して確かめる（通らなければ設計書との食い違い）。2026-11-05に水準C4の扱いを判断待ちに改めた（設計書では使える、新実装は店頭受取系でポイント欄を隠す。ポイントのUPT-04・UPT-06の判断待ち2と同じ論点。行は残し、期待値に「全額ポイント支払いが選べること」を置かない）
- 支店ごとの配送方法・支払方法の結び付きは、開発環境の設定に本店の行しか無い。支店は設計書（0304 6-2）の「店頭支払のみ」に従う
- 支払方法（2026-11-05 裁定R13）：通販の支払方法は6種類（コンビニ決済・クレジットカード決済・郵便振替・銀行振込・店頭支払・代金引換）で、支店は店頭支払のみ、店内アカウントは店頭支払（店頭PCのみ）。全額ポイント支払いと登録済みクレジットカード決済も残す。店頭受取・スムーズ店頭受取に結び付くのは、開発環境の設定で、店頭受取＝店頭支払・支払いなし・店頭支払(店内PC)、スムーズ店頭受取＝支払いなし・クレジットカード決済・登録済みクレジットカード決済だけ（通常商品の販売グループは店頭支払・支払いなし・クレジットカード決済・登録済みクレジットカード決済のすべてに結び付く）。コンビニ決済・郵便振替・銀行振込・代金引換は、店頭受取系の配送方法に結び付かず選べない。0304 (6-2) の6種類の選択肢は通販の配送方法の話として読む

## まとめた水準

なし（どの水準も処理が違う）。主な根拠：本店と支店は支払方法・ポイントの出る出ないが違い、店頭受取とスムーズ店頭受取は支払方法の選択肢が違う。カードの1つの状態・複数の状態・グッズ、数量の1点・複数・上限は購入画面の表示と入力の決まりが違う。PCとスマートフォンはナビゲーション、日本語と英語は氏名カナの入力欄が違う。
