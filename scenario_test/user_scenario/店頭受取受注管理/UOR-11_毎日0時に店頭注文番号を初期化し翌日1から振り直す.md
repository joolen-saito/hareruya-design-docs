# UOR-11 毎日0時に店頭注文番号を初期化し、翌日の番号が1から振り直される

| 項目 | 内容 |
|---|---|
| 利用者 | 店頭注文番号の初期化のバッチ（システム）。結果は店舗チーム（管理画面）と店内のお客様（店内PC）が確かめる |
| 目的 | 毎日0時にバッチが動き、本店・支店の店頭注文番号がすべて削除され、採番が1からやり直しになる。受注そのものは変わらず、翌日の店頭PCの注文に1番から振られる |
| 種類 | 正常（夜間バッチ） |
| マトリクスの行 | `matrix_UOR-11/matrix.md` のT01（毎日0時に初期化され、翌日1から振り直される） |
| もとのシナリオ | （SCN-ORDER は無い。0405 B05-03 店頭注文番号初期化） |

## 前提

- 共通の決まり：`../L4を流すときの共通の決まり.md` を先に読む（試験データの名前にシナリオIDを付ける・共有の設定は元に戻す・バッチの起動・店舗の読み替えなど）
- システムの外で済んでいること：店内のPCが使える。バッチは毎日0時に動く設定（試験では同じバッチを手で起動してよい）
- 用意するデータ（試験用の値。設計書の値ではない）
  - 前日の店頭PCの注文：本店の店内アカウントで3件注文済み。店頭注文番号（TC注文番号）は1・2・3。受注の対応状況は「注文受領」（注文番号と金額を控える）
  - 店舗チームの担当者：管理画面で本店の受注を見られる

## 操作の流れと期待値

| # | 操作する人と操作 | 期待値（画面で見えること） |
|---|---|---|
| 1 | 店舗チーム：初期化の前に、管理画面の受注情報検索で、店頭注文番号に「3」を入れて検索する。見つからないときは、前提で控えた3番目の注文の注文番号で検索して先へ進む | 店頭注文番号の検索で1件出る（前日の3番目の注文。見つからなければ不合格として記録する。下の「設計書との食い違い」）。この受注の注文番号・金額を控える |
| 2 | （システム）毎日0時にバッチが動く。または試験として同じバッチを起動する | エラーなく終わる。本店・支店の店頭注文番号がすべて削除され、採番が1からやり直しになる |
| 3 | 店舗チーム：受注情報検索で、店頭注文番号に「3」を入れて検索する。続けて手順1で控えた注文番号で検索する | 店頭注文番号「3」では見つからない（手順1で店頭注文番号の検索が見つかったときだけ合否を付ける。見つからなかったときは記録）。注文番号で検索すると受注は残っていて、対応状況・金額・明細は手順1と同じ（店頭注文番号が失われるだけで、受注は変わらず、金額の再計算も集計もされない） |
| 3a | （システム）手順4の注文の前に、同じバッチをもう一度起動する | エラーなく終わる。結果は手順2・3と同じ（店頭注文番号は無いまま。採番も初期化されたままで、次の注文は1番から）。受注は手順3と同じ |
| 4 | お客様（店内のPC）：翌日（初期化の後）、店内アカウントで1件注文を確定する | 購入完了画面のTC注文番号が、前日の続きの4ではなく1番から振られる（呼び出し番号の下4桁を4桁のゼロ埋めで表示するので「0001」）。この注文の店頭注文番号で受注情報検索すると、新しい注文が見つかる（見つからなければ不合格として記録する） |
| 5 | 店舗チーム：店頭注文番号札管理を開く | 登録済みの店頭注文番号札の一覧の扱いは、設計書に初期化の対象とは書かれていない（記録。店頭注文番号札は受注のデータと結び付いていない） |

| T02 | 対象が0件のときも実行できる | 前提：店頭注文番号が1件も無い状態（前日に店頭PCの注文が無い）。手順1：検索しても店頭注文番号が見つからない。手順2：エラーなく実行でき、削除と採番のやり直しが行われる（結果は「店頭注文番号が無い状態と、初期化済みの採番」だけ）。手順3：注文番号での再検索は行わない（控える受注が無い）。初期化がエラーなく終わったことは手順2で確かめる。手順3a：再実行もエラーなく終わる。手順4：翌日の注文が1番から振られる |
