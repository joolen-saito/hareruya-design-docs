# 業務フロー切り分け監査（物理作業 / 外部システム / EC-CUBE）

業務フローには、EC-CUBE 上の操作だけでなく、**物理作業**（ピッキング、梱包、郵送、バーコード貼付、
引渡しサイン）と**外部システム/ツール操作**（スマレジ、Backlog、スプレッドシート、メーラー）が混在する。
これらに EC-CUBE の機能Noを割り当てると、その画面では**観測できない期待結果**が生まれ、
システムテストとして実行不能になる。

**推測で埋めない。判定できないものは `要確認` として出す。**

## 切り分けの根拠

業務フロー Markdown のノード表（`| # | フェーズ | 実行主体(レーン) | 種別 | テキスト |`）を使う。
`20_凡例.md` が図形種別として `手作業` を定義しており、レーンには `EC-CUBE（本店）` / `スマレジ / システム` /
`店舗 / チーム` 等が入る。各ステップの `**[作業概要]**` をノードのテキストへ突き合わせて判定する。

| 判定 | 根拠 | 機能No | 観測点 |
|---|---|---|---|
| EC-CUBE操作 | 種別が `定義済み処理(サブフロー)` / `処理`、レーンが外部系でない | **必須** | 画面・DB・履歴 |
| 外部システム操作 | 種別が `手作業` かつ外部ツール語を含む | 付けない | 外部システム側の記録 |
| 物理作業 | 種別が `手作業` かつシステム操作の記述なし | 付けない | 現物・帳票・数量・サイン |
| 要確認 | 判定できない（後述） | 付けない | — |

## 現状（メインフロー 1,174 ステップ）

| 分類 | 延べ | 比率 |
|---|---:|---:|
| EC-CUBE機能No割当（根拠あり） | 392 | 33.4% |
| **要確認（推測せず保留）** | **404** | **34.4%** |
| 物理作業（機能No無し） | 261 | 22.2% |
| 外部システム（機能No無し） | 112 | 9.5% |
| 非EC-CUBE作業（メーラー等） | 5 | 0.4% |

機能Noを付けるのは、次のいずれかの**根拠がある場合だけ**である。

1. ノード表で EC-CUBE 工程と確認でき、かつ設計書名と本文が部分一致する
2. `EXPECTED_FUNCTIONS` のキーワード辞書（人が整備した対応表）が発火する

**根拠のない割当はしない。** 設計書名との類似度による割当は、ノード表で EC-CUBE 工程と
確認できた行に限る。ノード表と照合できない行（物理作業が紛れている）に類似度だけで画面を
結び付けるのは、元の誤割当と同じ推測である。

修正前は、**物理作業・外部作業を含む全ステップに EC-CUBE の機能Noが割り当てられていた**。
`assign_step_docs` が「類似度ゼロなら余っている設計書の先頭を割り当てる」フォールバックを持っていたためで、
次のような誤りが出ていた（いずれも修正済み）。

| 業務行動 | 修正前の割当 | 修正後 |
|---|---|---|
| 買取希望のカードを顧客が郵送する | ネット買取管理_買取検索一覧（M07-01） | 物理作業（機能No無し） |
| 商品の引き渡し、納品書にサインを頂く | API 受注管理 — 店頭注文番号取得（A05-03） | 外部システム（機能No無し） |
| バーコードを発行し商品に貼り付ける | 管理画面_商品管理_セール用価格変更CSV出力（M03-05） | 要確認（CSV操作を含む） |
| 注文商品をピッキングする | 管理画面_受注管理_店頭注文番号札管理（M05-27） | 物理作業（機能No無し） |

**解消は次のいずれか。**

- **EC-CUBE工程だが機能No未特定**（159件）: 対象の機能設計書を特定し、`EXPECTED_FUNCTIONS` のキーワード辞書に
  追補する。該当機能が存在しないなら、業務フロー側かシステム設計側の欠落なので設計に差し戻す。
- **手作業だがCSV/インポート等を含む**（104件）: 業務側で「EC-CUBE画面で行う」のか「Excel等の外部ツールで
  行う」のかを確定させる。前者なら機能Noを、後者なら外部システム扱いにする。

## 2. To-Be 対応方針は**ファイル名では判断できない**

`_tobe` の有無で As-Is / To-Be を判定してはならない。各業務フローの冒頭 `R3` に方針が明記されている。

| 業務フロー | R3 の注記 | 意味 |
|---|---|---|
| `06_店頭買取.md` | ※tobeではなく**こちらを新フローとして記載**しています。 | このファイルが To-Be |
| `12_在庫管理.md` | ※asis→tobeの形式ではなく、**新規に業務フローを起こしている** | このファイルが To-Be |
| `16_通販受注管理.md` | ※**すでにあるtobeで問題ないので変更なし** | 17_tobe が正 |
| `05_店頭受取受注管理.md` | ※…**業務フローの変更なし** | As-Is = To-Be |
| `09_商品登録・編集.md` | ※(tobe)シートに 4.6.7 の業務について在庫に関する tobe を記載 | 部分的に 10_tobe が正 |

As-Is 由来が実害になるのは、**To-Be で工程の新規追加・置換・廃止が明記されているのに、その対応が
管理されていない**場合に限る。例: `10_商品登録・編集_tobe.md` に「商品規格画面から在庫を操作できなくなり、
在庫編集を使う」という**置換**が明記されている。As-Is の手順が残っていれば実害になる。

## 3. 索引にあるのに本文が無いパターン（To-Be 新規業務の取りこぼし）

生成器が **WARNING** を出す。**シナリオが1件も作られていない**ため、放置すると未テストのまま気付けない。

| 業務フロー | # | パターン名 | 状態 |
|---|---|---|---|
| `17_通販受注管理_tobe.md` | 13 | **【新規追加】在庫移動準備業務** | **本文の作業行が無く、シナリオ0件。業務フロー側の補記が必要** |

To-Be で新規追加された業務が、索引には載っているのに本文の作業行を伴わないため、パーサが
パターンとして認識できずシナリオが生成されていない。業務フロー側に作業行を追記する必要がある。

## 4. 既知の未対応（次の課題）

- **複合ステップの分割**: 「商品の引き渡し、納品書にサインを頂く」は 物理（サイン）＋外部（スマレジ決済）＋
  EC-CUBE（対応状況の自動更新）の複合行。現在は `要確認` として保留しており、工程分割ができていない。
- **物理ステップの期待結果がテストオラクルになっていない**: 「注文商品をピッキングすること。」では、
  注文番号との一致・SKU・数量・欠品有無の照合基準がない。`確認対象` に現物・帳票を列挙しただけでは
  合否判定できない。
- **`要確認` 404件が strict validation を通過する**: 現状の strict は「未解決ラベルのホワイトリスト」で
  あり、出荷可否の判定にはならない。出荷判定用の strict（要確認0件必須）と、監査用の draft を
  分離すべき。
