# システムテスト網羅性レビュー

## 結論

現行シナリオは、形式検証としては `64件 / failed=0` で合格している。
ただし、業務フローとHTML/機能設計書に基づく「業務フロー成立に必要な機能の網羅性」としては、まだシステムテスト完了と判断できない。

主な理由は以下。

- 業務フロー番号としては64パターンがシナリオ化されているが、在庫管理で番号欠落/重複により追跡が曖昧な箇所がある。
- 正常系の手順が最大8行で切られており、長い業務フローでは後半工程がシナリオに入っていない。
- 期待機能番号のトレースが全シナリオで不足している。生成器側で関連機能を最大件数に丸めているため、必要機能を網羅する設計になっていない。
- エッジケースは存在するが、業務固有条件よりも汎用ケースに寄っている。
- 代替/異常系が分岐表にあるだけで、実行手順として操作・入力・期待結果まで落ちていない。

## 確認結果

| 観点 | 結果 | 補足 |
|---|---|---|
| 形式検証 | OK | `validate_scenarios.py --generated-only --strict` は `checked=64 failed=0` |
| 業務フローパターン数 | 64 | 生成器が抽出した canonical pattern 数とシナリオ数は一致 |
| 業務フロー番号の追跡 | NG | 在庫管理で番号10欠落、番号14重複の疑い |
| 正常系明細の網羅 | NG | 24パターンで業務フロー明細が9行以上あるが、生成器は先頭8行のみ採用 |
| 必要機能番号の網羅 | NG | 期待機能辞書に対し、全64シナリオでトレース不足を検出 |
| HTML設計書の網羅 | NG | 31シナリオで期待HTML設計書の一部が未参照 |
| エッジケース | NG | 共通ケース中心で、業務固有ケースが不足 |

## 重大指摘

### 1. 長い業務フローが途中で切れている

生成器の `step_rows()` は `pattern.rows[:8]` で正常系行を先頭8件に制限している。
そのため、店頭買取、ネット買取、発送準備、店頭受取、イベント受付、在庫移動など、9工程以上ある業務フローでは後半工程がシナリオ化されない。

例:

- `scenario_test/markdown/07_店頭買取_tobe.md` の店頭買取は22行相当の業務明細がある。
- `scenario_test/scenario/SCN-KAITORI-店頭買取本店支店とも-001_店頭買取（本店、支店ともに同じフロー）.md` は正常系が8行で終わり、後続の成立、在庫振分、CSV、Backlog、仕入れ連携まで十分に到達していない。

改善:

- 正常系は先頭8行ではなく、業務フローの完了条件に到達するまで出力する。
- 長すぎる場合は、業務上の節目でサブフローを分ける。
- 「正常完了ルート」と「キャンセル/返金/差戻しルート」を混在させない。

### 2. 正常系に代替/異常系が混入している

一部シナリオでは、正常系の途中にキャンセル、返金、期限超過などが入っている。
これは正常系としてテストするルートを曖昧にする。

例:

- `SCN-ORDER-店頭受取本店-001` は正常な受取完了ではなく、期限超過、キャンセル、商品戻し側に寄っている。
- `SCN-EVENT-イベント受付オンライ-002` はオンライン受付の正常系にキャンセル申込、返金依頼、返金処理が混入している。

改善:

- 正常系は「業務が予定どおり完了するルート」に限定する。
- キャンセル、返金、期限超過、差戻しは代替/異常系として独立した実行手順にする。

### 3. 必要機能番号の網羅性が不足している

生成器には業務ごとの期待機能辞書があるが、シナリオ側のトレーサビリティは最大件数で丸められている。
そのため、辞書上必要とされる機能番号が個別シナリオに出きっていない。

特に不足が大きい領域:

- 通販受注管理
- 在庫管理
- ネット買取
- イベント管理
- デッキ登録

改善:

- 個別シナリオに `主要機能No` と `補助機能No` を分けて出力する。
- `02_トレーサビリティ.md` に機能番号列を追加する。
- 期待機能番号が欠けている場合はバリデーションエラーにする。

### 4. エッジケースが業務固有になっていない

多くのシナリオで、エッジケースが「権限なし」「検索0件」「重複実行」「必須不備」などの共通ケースに寄っている。
共通ケースは必要だが、それだけでは業務固有リスクをテストできない。

例:

- バーコード貼替では、対象期間違い、CSV対象件数不一致、旧バーコード混在、ラベル再発行/重複貼付が必要。
- SPLINKS返金では、SPLINKS側取消失敗、売上確定前後の差、一部返金、二重返金が必要。
- 在庫0枚種類数集計では、公開/非公開、言語、Foil/NM、価格帯、集計先反映の条件確認が必要。

改善:

- 各シナリオで最低2件は業務フロー本文から業務固有エッジケースを抽出する。
- 分岐表だけでなく、`実行手順（代替/異常系）` として操作、入力、期待結果まで出力する。

### 5. 画面/機能割当が業務実態とずれている箇所がある

例:

- `SCN-TSUHAN-お客様対応メーラーで-006` は「メーラーでのみの対応」だが、実行手順がフロント注文画面中心になっている。
- メール受領、注文照会が必要な場合の管理画面確認、対応履歴、顧客返信を主軸にすべき。

改善:

- 業務フローの作業主体と利用システムを優先し、キーワード類似だけで画面を割り当てない。
- 「メーラーのみ」「手作業」「外部アプリ」などの非EC-CUBE作業は、画面なしの業務操作として表現する。

## Codex批判的レビュー要約

Codexサブレビューでも、以下の指摘が一致した。

- 形式検証は通っているが、システムテストとしての内容網羅性は不足。
- 在庫管理の業務10が欠け、番号14が重複している。
- 正常系が途中で切れているシナリオがある。
- エッジケースは列挙されているが、具体操作に展開されていない。
- 業務固有の確認対象ではなく、汎用的なステータス/履歴確認に寄っている。

## 次の改善方針

1. 業務フロー番号のキーを `出典ファイル + パターン番号 + 作業概要` に変更し、欠落/重複を検出する。
2. 正常系は8行制限を廃止し、完了条件到達まで出力する。
3. 正常系、代替系、異常系をルート単位に分離する。
4. 期待機能番号を `主要機能No` / `補助機能No` として全件出力する。
5. 業務固有エッジケースを最低2件以上、具体的な実行手順として出力する。
6. カバレッジ表は `○` だけでなく、未出力の業務行、未出力の機能番号、未手順化のエッジケース数を出す。
