# 観点抽出の共通指示

## 目的

公開資料（IPA ほか）から「シナリオテストで確認すべき観点」の候補を、原文の引用とページ付きで抜き出す。
抜き出した候補は、後で別の担当がまとめて体系化し、codex がレビューする。

## シナリオテストの定義（この作業での前提）

業務シナリオテスト。システムテスト〜受入テストの段階で、利用者（顧客・店舗スタッフ・管理部門の運用者）の視点から、
複数の機能・システムにまたがる一連の業務操作が、業務として期待どおり完遂できるかを、本番相当の環境で確かめるテスト。
正常系だけでなく、例外・取消・やり直し、日次/月次/年次などの周期業務、時刻・期間の境界、外部システムとの連携、
データの整合、業務の流れの中で現れる非機能（性能・可用性・セキュリティ・運用）も含む。

対象システムの想定: EC サイトの再構築。顧客向けの購入サイト、管理画面（受注・商品・会員・在庫など）、
決済・配送・在庫などの外部連携、バッチ処理、メール通知を持つ。EC パッケージをカスタマイズして作り、
現行システムを置き換える（現行の振る舞いを踏襲する部分と、変更する部分がある）。

## 守ること

1. 読むのは、割り当てられたテキストファイルだけ。**`/home/y-saito/Developments/` 配下のリポジトリやファイルは一切開かない。**
   依頼者の指示で、作成済みの社内ドキュメントを見ずに外部資料だけから集めることになっている。Web 検索・取得もしない。
2. 捏造しない。資料に書かれていないことを観点として書かない。資料の主張を一般化しすぎない。
3. **原文抜粋は、テキストファイルの連続した部分をそのままコピーする。** 20〜150 字。要約・言い換え・省略記号「…」の挿入は禁止。
   空白や改行の違いは後で無視して照合するので、空白はそのままでも詰めてもよい。PDF 由来で語順が少し乱れている箇所も、そのままコピーする。
4. ページは、テキストファイル中の `=====PAGE n=====` の n（PDF のページ番号）を書く。
5. シナリオテストに直接関係しないもの（単体テスト・コード品質・開発プロセス管理・契約など）は候補に入れない。
   迷ったものは「除外候補」に理由付きで入れる。

## 出力

指定された出力ファイルへ、UTF-8 の TSV で書く。1 行目は見出し。列は次の 8 列。タブと改行をセル内に入れない。

| 列 | 内容 |
| --- | --- |
| 区分 | `候補` または `除外候補` |
| 観点 | 短い名詞句（例: 時刻境界での連携可否） |
| 確認すること | シナリオテストで何を確かめるかを 1 文で。資料の範囲を超えない |
| 原文抜粋 | 規則 3 のとおり |
| ファイル | テキストファイル名（例: T13.txt） |
| PDFページ | 規則 4 のとおり |
| 資料内の位置 | 章・節・表番号など分かる範囲で（不明なら空） |
| 備考 | 除外候補の理由、他の観点との関係など（無ければ空） |

同じ観点を複数の箇所が支えるときは、行を分けてよい（後で束ねる）。
資料が観点の一覧・分類体系を持つとき（例: 大項目/中項目の表）は、体系そのものも候補として拾う。

最後に、出力ファイルの行数と、資料全体から見て拾い漏れがありそうな箇所（読み切れなかった章など）を短く報告する。
