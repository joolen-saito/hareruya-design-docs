### SV-20-01 本番相当の環境と、本番との差

テスト項目（STI）の準備手順は、ローカル環境（`http://localhost:8080`、`docker compose -f docker-compose.yml -f docker-compose.pgsql.yml -f docker-compose.dev.yml`）を前提にしている（179項目）。足すべき前提は次のとおり。

1. 実施する環境の名前（ローカル／ステージング）と、本番との差の一覧。ステージングの DB は設計（B16-10 ステージングデータベース保守バッチ、0416 1442行）で本番のスナップショットを毎月1日に作り直す。ローカルとは別物なので、どちらで実施するかを決める。
2. メールの受け先。STI は「試験受信箱」「試験用受信箱」と書くだけで、どこで受け取るかが無い（62項目）。ローカル構成ではメールは mailcatcher に届く（ec-cube-enterprise/docker-compose.yml の MAILER_DSN、リポジトリ外）。顧客メールの `scenario-NNN@example.test`（276項目）は届かないドメインなので、ステージングでは受け取れない。ステージングでマスクされない（受け取れる）アドレスは、スタッフ・ベンダーの5ドメインだけ（0416 1504行）。
3. 決済の接続先。STI は「決済検証環境」「SPLINKS検証環境の応答を指定の成功/不能に設定」と書く（16項目）が、接続先と、応答を成功/不能に切り替える手段が無い。設計は決済会社をソニーペイメントへ変える方針で、詳細は未定（0405 1636・1653行）。どの決済会社の検証環境で行うかも決まっていない。ローカルの設定ファイルでは、リンク型決済の接続先は環境変数から読む作りになっている（ec-cube-enterprise/app/config/eccube/packages/eccube.yaml、リポジトリ外）。
4. スマレジの接続先。ステージングでは、スマレジの設定を空にしたうえで、あらかじめ決めた83人だけにステージング用のスマレジIDを付ける（0416 1499・1543行）。ポイントのスマレジ連携（F04-04 の購入時、M05-26 の出荷時、M08-05 のポイント付与、STI-TSUHAN-018-005・019-005）を確かめる試験会員は、この83人から選ぶ必要がある。
5. 配送業者のテスト環境（「配送業者のテスト環境で発行された実番号」、900 の9項目）が実在するか。ラベル印字アプリ・海外発送管理アプリの試験用の環境が実在するか。
6. 定期起動のバッチ。0405 のバッチは Step Functions のスケジュール起動（毎分・10分おき・毎時10分・毎日4時など）で、ローカルでは動かない。B05 系を経路に入れる場合（VPR-TSUHAN-1904-01）は、手動で起動する手段を前提に書く。
7. 業務時計。STI は「テスト用の業務時計を指定時刻に固定」（24項目）と書くが、システムにその機能の定義が無い。

### SV-20-04 実データに近いデータと、例外を起こすデータ

全シナリオの顧客データは同じ型（試験 太郎／東京都新宿区試験町1-1／scenario-NNN@example.test／数量3／1,000円）だった。次のデータが無い。

- 海外住所（住所3）
- 外字・旧字体の氏名
- 長い住所（住所1・住所2 は全角を2・半角を1として90まで: 0304 1916行）
- 英語ページからの注文、同梱の複数受注、複数配送先

007 は、海外の工程（海外ラベル・海外チェックリスト・EMS後納表・smallpacket）を国内宅配便の受注1件で通している。ステージングDBは本番のマスク済みデータだが、保護対象以外の氏名は「ダミー」、住所は「東京都」「ダミー区」「0-0-0」、受注番号は「DUMMY-ORDER」に上書きされる（0416 1510〜1513行）。そのため、住所・氏名の多様さや受注番号での照合には使えず、件数・商品・金額の分布の確認にしか使えない。例外データは別に作る必要があり、そのための入力可能文字の定義（外字・機種依存文字を受け付けるか）も要る（SV-17-09 の根拠待ち部分と同じ不足）。

### SV-20-05 周期業務のテストデータ

通販には次の周期がある。

- 時刻: 8:30/13:00/15:00/18:00 の発送準備、15時以降の入金確認、16時のチェック、17時・18時の集荷、翌朝8:30 の smallpacket
- 日付: 発売一週間前から発売前日15時締めまで毎日、準キャンセル＝受注の5日後、キャンセル＝受注1週間後
- バッチ: 購入完了手続き再処理（毎分）、ポイント利用未反映チェック（毎時10分）、ポイント二重登録チェック（毎日4時）

既存項目は「業務時計を合わせ」で済ませている。足すべき前提は次の3点。

1. 結果から逆算した日付のデータを作る手順（例: 受注日を5日前・7日前へ補正した受注、発売日を翌日にした予約商品）
2. 補正の復元手順
3. 定期起動のバッチを試験時刻に動かす手段

月次（ステージングDBの毎月1日3時の作り直し）・年次の処理は、通販の経路では使わない。

## 5. 判断に迷った点

- SV-17-01 の判定。変える／変えないの区分そのものは設計書（カスタマイズ区分、★、「カスタマイズ要件に記載の内容以外は現行踏襲とする」）で決まっている。そのうえで、基盤変更で作りを変えたのに規則は変えない注文番号の採番を、「変わってしまう」かを確かめる具体例として項目にした。
- 「変えない個所が現行どおりか」の期待値は、設計書に埋め込まれた現行仕様（現行ソースのリバース）を使った。現行の実機の出力と比べる現新比較は SV-17-02 で根拠待ちとし、両者を分けた。
- SV-17-10 は判定基準の決まり（実施手順.md 37行、結合テストの裁定 2026-10-16・09-28）がある。それでも、シナリオ層で「業務フロー対設計書」の優先が無いことと、通販に未決の食い違いが残ることから根拠待ちにした。
- SV-19-01 は、経路全体の22項目が変える／変えない両方の機能を業務の順に通すため既存項目で確認済みにした。一方で、変更のたびに流し直す経路の選び方は決まっていない。
- SV-19-04 の経路は、業務フロー原典に無く、設計書（B05-02 の不具合への対策）だけを根拠にしている。親パターンは「お客様EC購入フロー」の派生に置く想定。
  - 工程1で「購入完了画面を表示する前はポイントが消費されない」ことを期待結果にする案は、F04-04 の現行仕様には合う。しかし不具合の状態を期待することになり、「現行踏襲の機能で現行の挙動が不具合のものはケースから外す」決まり（conflicts/README.md 16行）に反するため、外した。
- SV-17-09 の VP-TSUHAN-1709-02 は、結合テスト（IT-M05-21-028・031）と同じ関数を見る。それでも、ゼロ埋めの番号では数値と文字列の違いが出ないため、基盤変更の確認として足した。重複と見るかは取り込み側で判断してほしい。
- SV-17-08 と SV-17-09 の項目（海外の英語メール、文字コード）は、ほかの担当の観点（多言語、外部連携）と重なるかもしれない。
- SV-18 はすべて根拠待ちにした。通販の受注・会員・ポイントの移行の記述が無いため。移行の記述は商品管理（0204: タグの取捨選択、状態名のコピー）と会員管理（0207: メール配信フラグをオプトアウトで移行）にだけある。
