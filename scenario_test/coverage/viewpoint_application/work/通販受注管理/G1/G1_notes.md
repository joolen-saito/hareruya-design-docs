## 4. 誤りの原因（生成器・レジスタ）

- **トリアージの鍵の衝突**: 生成器は工程判定レジスタ（`scenario_test/scenario/` の 08 番のトリアージTSV）を (業務, R番号) を鍵に読む（`.codex/skills/hareruya-scenario-test-cases/scripts/generate_scenarios.py:612`）。通販受注管理は 16（as-is）と 17（tobe）が同じ業務名で、R番号が重なる。R72 は 2-2 出荷指示リスト作成（EXTERNAL、トリアージ #4）と 4-14 同梱出荷処理（TRACE-IN M05-14・M05-12・M05-15・M05-06、#20）、R32 は 1-2 商品をカートに入れる と 4-3 16時より（PHYSICAL、#8）。同じ鍵に2行あると後の行が勝ち（R72）、片方のファイルにしか行が無くても同じ R番号のもう片方の工程に当たる（R32）。その結果 003/004 工程2 に同梱出荷処理の機能No、001/002 工程2 に物理作業が付いた（同TSVの131・135・147行）。R36・R44・R60・R82 も両ファイルで重なっており、トリアージに当たる工程が増えると同じ誤りが起きる。
- **CUSTOMER 判定の表示**: `resolve_step_via_triage` は CUSTOMER を PHYSICAL と同じ「現場作業（物理作業。EC-CUBE操作なし）」に落とす（同 :1505）。トリアージ #3（同TSVの130行）は 1-3 注文処理を CUSTOMER（F04-02,F04-04）と判定しているのに、001/002 工程3 は物理作業になった。
- **担当の既定値**: レーンが取れない工程は業務の主アクター「通販チーム」（同 :32）になる。001/002 工程3・6、010 工程1・6、015 工程3・5、901 工程1 がこれで、原典ではお客様・依頼元部署・受託業者の作業。
- **メール受領の期待結果**: 既存契約 SC-062（`scenario_test/coverage/source_contracts.json`）が 5-2・6-2 のメール受領に「同じ受注番号の注文完了メールを顧客が受信すること」を当てている。原典で受け取るのは顧客への確認メール。
- **台帳の扱い**: 発送管理台帳・入金管理台帳の更新が、003/004/005/006/010/015 では物理作業（観測先: 現物・サイン）、901 では外部作業になっている。原典では台帳はその他レーンの帳票で、発送管理は Excel 台帳と書かれている（16:106 R239）。

## 6. 判断に迷った点

- **SV-01-02** は、SPLINKS 決済の注文を入金確認まで同じ受注で通す経路が無いが、EC-CUBE 側の「決済状況管理」が設計書に無く期待結果を決められないため、新規経路にせず「既存項目で確認済み」（901 と 006・011 の組合せ）とし、不足を理由欄に書いた。
- **SV-02-08** は、007-002（発送停止の受注を通常対応に戻す）を確認済みとみなす案もあったが、観点の「緊急のデータ修正」に当たる日付クリア・手修正の後の扱いが原典に無く、設計書からはポイント・メールの二重処理が導けてしまうため「根拠待ち」にした。
- **SV-01-08** は、通販受注管理に承認（決裁）が無いため「適用外」も考えたが、依頼→対応→報告の受け渡しは観点の「ワークフローステータスに抜けがないか」に当たると見て「既存項目で確認済み」とした。
- **VPR-TSUHAN-01-09-01（購入完了手続き再処理）** は設計書が GMO 決済前提の記述を含み、SPLINKS のクレジットカード決済で同じ抽出になるかは原典で確定していない。0304 の「SPLINKS決済のポイントは購入完了画面の表示時に消費」と整合するので経路にしたが、known_limits に残した。
- **30分のタイムアウト（VPR-TSUHAN-02-04-01）** は画面単位の機構とも読めるが、放置後に業務の状態（カート保持・注文1件）が崩れないかは業務の流れとして確かめるものと判断した。
- **同梱の経路（VPR-TSUHAN-02-03-01）** は、銀行振込で未入金の受注を出荷完了へ変更できるかが対応状況の遷移制約に依存する。遷移の一覧が設計書に無いため、拒否されたら合格にしない旨を known_limits に書いた。
- **台帳の工程を外部作業に変える範囲**: 台帳が Excel と明記されているのは 16:106 R239（発送管理）だけで、入金管理台帳は「台帳」とだけ書かれている。現物・サインの観測先は明らかに不適切なので外部作業にしたが、ツールの種類は書いていない。
- **012/018/019 工程1「返金依頼」** も物理作業の表示は不適切だが、通販チーム内の依頼をどこに記録するかが原典に無いため補正案を出していない。
- **G1-SF-33 と G1-SF-34** は同じ業務行動（お客様案内対応）で、012 は経路から外し、018・019 は外部作業にする。業務行動の完全一致で当てる仕組みでは区別できないため、012 は catalog_contracts.json の `route_changes`（`drop_steps`）の形で別にした。
- **G1-SF-44（901 工程1の担当）** は orders_contracts.json の `supplemental_steps` 由来の工程なので、`step_resolutions` の形の補正案では当たらない可能性がある。取込み側で supplemental_steps の actor を直す必要がある。
