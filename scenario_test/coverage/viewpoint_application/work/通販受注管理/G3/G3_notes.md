## 3. 判断に迷った点

- **SV-06-03 の非会員**: 非会員で受注を作れるという記述（0304:1749）も、非会員の行をエラーにする記述（0203:4756）も、埋め込みの現行仕様の節にある。本店ECで非会員購入を受け付けるか、非会員の行で全体を取り消すのを刷新後も踏襲するかは原典で決まっていない。0203 の CSV・納品書に「非会員」の表示（0203:1585, 2468）があるため非会員の受注は存在しうると判断し、項目にしたうえで known_limits に実施不可の条件を書いた。担当者の権限（0203:2810, 2811, 2827）は規則6どおり他層（ITA-19）とした。
- **SV-06-05 を「既存項目で確認済み」にしたこと**: 受け入れ基準の文書は無く、最終業務状態を受け入れ基準の代わりにした。受け入れ基準の文書を必須と読むなら「根拠待ち」になる。
- **SV-06-02・SV-07-01・SV-07-03 を「既存項目で確認済み」にしたこと**: 項目はあるが、2章の担当者の誤りや、マクロ・海外発送管理アプリの実原本が無いための実施保留がある。誤りを直すことを前提に確認済みとした。
- **SV-07-05 のつながり**: 出荷実績インポートが残す「エラーの印」（0203:4764）とスマレジEC受注連携エラー再連携の対象「スマレジ連携エラーフラグ」（0405:1727）を同じものと読んだ。受注情報編集の「スマレジ連携エラーの印」（0203:3505）と名前がそろうことが根拠で、直接の対応付けは無い。応答内容がポイント連携エラー欄に出ることも欄の名前とバッチ側の記述（0405:1734）からの読み取り。どちらも known_limits に書いた。再連携に成功してもエラー内容が残る記述（0405:1750）は、現行の副作用に当たる可能性があるため期待結果にしなかった。
- **SV-07-06 の送り状No.**: 出荷実績登録CSVフォーマットは送り状No.を数値(整数)（0203:4863、Excel由来）、埋め込みの現行仕様は英字・記号も文字列のまま保存（0203:4758）で食い違う。優先順位（Excel由来が上）で決めても、整数以外が来たときのふるまいはExcelに書かれていないため、項目にせず台帳に「設計の裁定待ち」と書いた。EMS などの追跡番号に英字が入るなら業務に響くが、追跡番号の形式は原典に無い。
- **SV-07-07 で外した2点**: 再取込で出荷完了メールやポイントを繰り返さないこと（0203:4718 の「更新された受注について」からの読み取り）と、受注を更新しない行でも配送先の発送日を更新すること（0203:4760、受注と配送先で日付が食い違う副作用の可能性）。
- **SV-10-02 の在庫1点**: 同じ瞬間の注文の排他は原典に無いため、会員Aの確定が終わってから会員Bが確定する順序にした。厳密な「同時」ではない。エラー時の画面名が Excel由来（システムエラーの画面、0304:2079）と表示メッセージの節（購入エラー画面、0304:2158）で違うため、画面名では判定しない。
- **SV-10-02 の出荷実績インポートの同時実行**: 再現のために担当者A側のCSVに出荷日が空の行（読み飛ばされる行、0203:4757）を5,000行入れて処理時間を延ばす。行数は原典の値ではなく、重ならなかったら再実施とした。現行仕様の節は「実行権を取る」とだけ書いている（MySQLの名前付きロックだったことは git の旧版の機能設計書にしか無いため根拠にしていない）。
- **SV-10-03 の購入完了手続き再処理**: 根拠の 0405:1225 は「ブラウザバックするとポイント減算されない不具合のため」という現行の不具合の記述。不具合そのもの（戻った直後に減算されていない状態）は期待結果にせず、バッチ後の最終状態（ポイント履歴が1件だけ・残高・メール・送信履歴・在庫履歴・スマレジ）だけを判定にした。バッチで在庫数を減らすかは Excel由来の本文の中で食い違う（0405:1239「履歴の登録のみ行う」と 0405:1261「在庫を減らす」）ため在庫数は判定に入れていない。0405:1240 の「GMOプラグイン」は旧決済の記述で、在庫履歴の登録を注文完了画面で行うという分担だけを根拠にした。
- **SV-10-03 の30分のタイムアウト**: 画面単位の遷移（シナリオの対象外）とも読めるが、注文が確定せずカートが残るという業務の結果があり、Excel由来の明記（0304:1715〜1716）があるため項目にした。結合テストに同じケースは見当たらなかった。
- **SV-07-08 を「根拠待ち」にしたこと**: スマレジのプラットフォームAPIへの切り替えは明記されているが、仕様は外部ドキュメントで、SP.LINKS は「仕様が決まり次第記載」。新方式で連携が成り立つこと自体は VP-TSUHAN-07-02-01・VPR-TSUHAN-07-05-01・VPR-TSUHAN-10-03-01 で通るので、観点の固有部分（新旧の比較・リハーサル）が根拠待ち、という整理にした。
- **バッチ・コマンドの書き方**: 手順にはバッチの論理名とスケジュール（毎分・5分ごと）だけを書き、起動コマンド名は書いていない。定期起動の無いローカル環境で手動起動する方法は known_limits に回した。
