## 2. 既存シナリオ・既存項目で見つけた誤り

1. **お客様のEC操作が現場作業・通販チームに分類されている**（SCN-TSUHAN-お客様EC購入フロー-001・002）。工程2「商品をカートに入れる」が「現場作業（物理作業。EC-CUBE操作なし）」、工程3「カート画面にて、購入処理を進める」は担当が通販チームで「現場作業（EC-CUBE操作なし）」。原典ではどちらもお客様のレーン（ノード#2 商品一覧・#3 カート）で、買い物かご（F04-01）・ご注文方法指定（F04-02）の操作。STI-TSUHAN-EC-001-003・004、EC-002-003・004 も同じ。工程6「決済手段による分岐」も担当が通販チーム（STI-TSUHAN-EC-001-007・EC-002-007・EC-002-010）だが、原典の判断図形#9「決済方法確認」はお客様のレーン。
2. **SCN-TSUHAN-購入入金国内出荷連鎖-901 の工程1（会員ログイン→カート→購入確定）の担当が通販チーム**（STI-TSUHAN-901-002）。お客様の操作。
3. **お客様対応（008・009）の最終業務状態が「同じ受注番号の注文完了メールを顧客が受信すること」**。工程が送るのはお客様対応のメール（原典ノード#126・#128「顧客への確認メール」）で注文完了メールではない。009 はEC-CUBEを使わない対応。STI-TSUHAN-ECCUB-008-001・003、STI-TSUHAN-009-001・003 が同じ文を判定にしている。
4. **008 のデータパターンの目的欄の引用違い**: DP-N003（一週間後のキャンセル）と DP-N004（予約入金完了の案内）が R277「準キャンセルは受注の5日後…」を引用している。正しくは 16_通販受注管理.md:130（キャンセルは受注1週間後…）と :131（予約入金は予約入金完了時にメール送付対応）。
5. **実行用テストデータの使い回し**: 22本中18本の実行用テストデータに「受注ステータス=対応中」、19本に「返金対象金額=1,000円」が同じ値で入っている（入金確認 005・006、発送 003・004・007・013・014・020、お客様対応 008・009 など返金と関係の無いシナリオを含む）。「対応中」は受注管理の対応状況の選択肢（0203:1203）に無い名称。入金確認の対象受注が「決済状態=売上確定済み」なのは未入金の確認という前提と矛盾する。
6. **STI-TSUHAN-014-002 の画面と判定**: 出荷指示の削除と再作成を「受注情報検索・一覧（M05-01）」で行う手順になっており、成功表示候補が M05-01 の「削除しました / 検索条件を削除しました」（受注・検索条件の削除）。実際の画面は出荷指示リスト編集（M05-20）と出荷指示リスト作成（M05-18）。期待結果は手順の言い換えで、合否を判定できない。VP-TSUHAN-04-03-01 で置き換える想定。

## 3. 設計書内で見つけた食い違い・不足（起票はしない）

- 購入完了手続き再処理（B05-02）の対象ステータス「新規」（0405:1230）が、受注管理の対応状況の選択肢（0203:1203、注文受領など）に無い。
- 出荷完了の状態名が、出荷実績インポートでは「発送済み」（0203:4715）、受注情報編集・検索では「出荷完了」（0203:2831、0203:1203）。
- 出荷指示リストの区分の判定が、Excel「受注商品名に「予約」を含む場合」（0203:4020）と現行仕様「先頭の明細の商品名」（0203:4056）で食い違う（SV-05-02 を根拠待ちにした理由）。
- 受注情報検索の画面項目 2-13・2-14 の名称が「出荷日」「キャンセル日」で 2-17・2-18 と重複している（0203:1213-1220）。現行仕様（0203:1307）では注文日・ピック中の期間・相対日数条件があり、名称の誤りとみられる。
- ご注文方法指定の現行仕様は「使用ポイントが支払うべき金額以上になったときは、お支払い方法の選択肢を「全額ポイント支払い」だけにする」（0304:1756）だが、Excel の支払方法の選択肢（0304:1650）にその選択肢は無く、結合テスト IT-F04-02-049 は「刷新仕様を採用」して通常の6種を期待している。SCN-TSUHAN-クレジットカード以外-019 の「全額ポイント使用」受注の作り方に影響する。
- 受注ステータスの遷移の許可規則（「%from% から %to% にはステータス変更できません」の対象）の一覧が設計書に無い（SV-04-02 の網羅部分が根拠待ちの理由）。
- 入金期限・受け取り期限の通知は Ph2 へ見送り（0203:3016-3018）で、準キャンセル・キャンセルの期限はシステムで制御されない。
- スマレジ商品削除（B05-05、店頭受取）は処理概要が「キャンセル」もしくは「引き渡し済み」、入力データ検索条件が「キャンセル」もしくは「出荷完了」と食い違う（0405:1492・1507。通販の範囲外の気づき）。

## 4. 判断に迷った点

- **SV-04-02 の判定**: 設計書に明記された無効な遷移（キャンセル・購入処理中は出荷指示にしない、出荷日登録済みは取込で再更新しない、再キャンセルで再度戻さない）は確かめられるが、状態とイベントの網羅は遷移規則の一覧が無く根拠待ち。業務の流れで起きる部分を新規経路で足すため「追加（新規経路）」にし、根拠待ちの部分を理由欄に書いた。
- **SV-03-10・SV-05-04 の条件**: 「同梱で出荷完了にした受注を取込に含める」「非会員の受注を取込に含める」は業務フローに書かれていない取り違え・混在の条件。期待結果は設計書の規則だけで決まるため項目にしたが、条件そのものは実行用の想定として known_limits に書いた。
- **SV-03-07 の待ち時間**: 「5分以上待つ」は処理対象「注文日時がバッチ起動時間の5分前から1分前まで」と毎分起動から導いた値で、原典に待ち時間は無い。対象ステータスの名称の不一致もあり、対象外になったときは値を証跡に残すようにした。B05-02 の結合テストは作り方未確定で全件除外されている。
- **SV-03-08 を既存で確認済みにしたこと**: 準キャンセル（5日後）・キャンセル（1週間後）は手作業の時期で、システムに期限の制御が無い。008-005・006 が起点日からの日数でこれを確かめているため既存で確認済みとし、同じ受注で続ける形は新規経路に入れた。008 の期待結果がシステムの結果（在庫・ポイントの戻し）を判定していない点は経路の工程4・5で補う。
- **SV-05-02 を根拠待ちにしたこと**: 購入グループが異なる場合の同時購入不可は IT-F04-01-021・022 が担当しているが、業務上の要点（予約と通常が混在した受注がどの出荷指示に入るか）が設計書内で食い違うため、項目を作らなかった。
- **SV-05-07 を根拠待ちにしたこと**: 006-007 は手作業の確認を行うが「高額」「決済エラー数」の閾値が無く合否を判定できないため、既存で確認済みとはしなかった。
- **SV-05-06 の購入種類数**: 数え方の定義が無いので、各商品1規格・各1点で購入し、商品数・規格数・明細数のどれで数えても150・149になるデータにした。
- **ee由来の機能設計書は根拠に使わなかった**: `functions/ec-cube-enterprise/` の m05-12・m05-14（標準機能、取消の確認ダイアログの文言など）は新実装から起こした資料で、期待結果の根拠にすると循環するため使っていない。
