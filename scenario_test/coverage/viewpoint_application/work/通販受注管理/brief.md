# 観点の当てはめ（通販受注管理・試行）共通指示

## 目的

シナリオテストを「観点の体系」に沿って作り直す試行として、通販受注管理の 22 シナリオに観点を当てはめる。
観点ごとに、既存のテスト項目で確認できているか、項目やシナリオを足す必要があるか、根拠が無くて作れないかを判定し、
足すものはテスト項目の材料（契約）を原典の引用付きで書く。後で別の担当がこの契約を生成スクリプトに取り込み、テスト項目を生成する。

## 守ること

1. 捏造しない。期待結果の値・状態・文言・判断規則は、業務フローか設計書に書かれているものだけを使う。書かれていなければ「根拠待ち」にして項目を作らない。
2. テストデータの具体値（論理ID `ST-...`、数量、金額など）は実行用の具体化として置いてよい。ただし業務ルールの閾値（期限の日数、上限数量、締め時刻など）は原典の値を使う。
3. 物理名を書かない。DB テーブル名（dtb_ など）・翻訳キー・ルート名を期待結果や手順に書かず、画面名・項目名・メッセージの表示文言で書く。画面名は設計書の名前を使う。
4. 曖昧語を使わない: 「設計どおり」「設計書に記載のとおり」「要確認」「適宜」「必要に応じ」「何らか」「UI標準」。
5. 既存の項目と重複させない。既存の項目で確認できているなら「既存項目で確認済み」とし、そのテストIDを挙げる。
6. 業務シナリオテストの範囲にとどめる。権限・必須/形式・重複実行・0件検索などの機構的な確認は、既存シナリオの「他層委譲（結合テスト）」に従い「他層で確認」とする。
7. `/home/y-saito/Developments/` 配下のファイルを書き換えない。出力は指定の作業ディレクトリにだけ書く。

## 判定（観点ごとに 1 つ。担当の分類の全観点について必ず 1 行書く）

| 判定 | 意味 |
| --- | --- |
| 既存項目で確認済み | 既存の STI 項目がこの観点を確かめている。テストIDを挙げる |
| 追加（既存シナリオ） | 既存シナリオに項目を足せば確かめられる。契約（kind=item）を書く |
| 追加（新規経路） | 既存シナリオのどれにも乗らず、新しい経路が要る。契約（kind=route）を書く |
| 他層で確認 | 機構的な確認で結合テストの担当（既存の他層委譲に沿う） |
| 根拠待ち | 当てはまるが、業務フロー・設計書に期待結果を決める記述が無い。何が足りないかを書く |
| 適用外 | 通販受注管理にこの観点が当てはまらない。理由を一言 |

## 出力（作業ディレクトリに 3 ファイル）

1. `<担当名>_ledger.tsv`（UTF-8、タブ区切り、1 行目見出し）
   列: `観点ID` / `判定` / `対象シナリオ` / `既存テストID` / `理由・確認すること` / `根拠`（file:line と要点。複数は ` / ` 区切り）
2. `<担当名>_contracts.jsonl`（1 行 1 契約）
   - 項目（kind=item）:
     `{"kind":"item","contract_id":"VP-TSUHAN-<観点IDの数字部>-<連番2桁>","viewpoint":"SV-xx-yy","scenario_id":"SCN-TSUHAN-...-NNN","function_id":"M05-11 または -","flow_type":"正常系|代替系|異常系","item_name":"<誰が><何をして><何を確かめるか>","precondition":"準備手順: … / 対象状態: …","input":"…","operation":"【準備確認】…\n【操作】…\n【操作後確認】…","expected_result":"…されること。など","observation":"確認場所: …","evidence":[{"file":"リポジトリ相対パス","line":行番号,"quote":"原典の連続した文字列"}],"known_limits":["実行用の具体値など、原典でないもの"]}`
   - 経路（kind=route）: 既存の補足経路の契約 `scenario_test/coverage/source_contracts.json` の `html_routes` と同じ形に寄せる。
     `{"kind":"route","contract_id":"VPR-TSUHAN-<観点IDの数字部>-<連番2桁>","viewpoint":["SV-xx-yy",…],"route_name":"…","route_kind":"正常代表|代替|異常","basis":"なぜこの経路が要るか（原典の根拠）","precondition":"…","seed":{…},"final_state":"…","steps":[{"no":1,"actor":"…","kind":"system|physical|external","screen":"…","function_ids":["…"],"operation":"…","expected_result":"…こと。","observation":"確認場所: …"}],"evidence":[…],"known_limits":[…]}`
   - 期待結果は「〜されること。」「〜されないこと。」「〜できること。」「〜であること。」のいずれかで終える。
   - 手順は他のファイルを開かずに実施できる具体さで書く（画面名・入力値・押すボタン）。
   - evidence は、期待結果と判定を支える原典の文を 1 件以上。行番号は grep -n の値。
3. `<担当名>_notes.md`: 判定の件数、既存シナリオ・既存項目で見つけた誤り（例: お客様の EC 操作が「現場作業（EC-CUBE 操作なし）」に分類されている）、判断に迷った点。
