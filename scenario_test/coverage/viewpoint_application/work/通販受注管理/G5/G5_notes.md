## 2. 既存シナリオ・既存項目で見つけた誤り

1. **SCN-TSUHAN-お客様EC購入フロー-001**
   - #2「商品をカートに入れる」はお客様のEC操作なのに「現場作業（物理作業。EC-CUBE操作なし）」に分類されている。
   - #3「カート画面にて、購入処理を進める」の担当が通販チームになっていて、分類も「現場作業」。実際はお客様が買い物かご・ご注文方法指定（F04-01・F04-02）で操作する。
   - #6「決済手段による分岐」の担当も通販チームになっているが、判断するのはお客様。
   - 代表データ DP-N001 の支払方法が「銀行振込」で、経路条件（クレジットカード・代金引換の場合に実線で購入完了へ進む）と合わない。銀行振込は 002 の経路。
2. **SCN-TSUHAN-予約受注対応シングル-014**
   - #1 は出荷指示の削除と再作成なのに、利用機能が「受注情報検索・一覧（M05-01）」になっている。削除は出荷指示リスト詳細（M05-20）、再作成は出荷指示リスト作成（M05-18）。
   - #2 の納品書・ラベル印刷の利用機能が「出荷指示リスト作成（M05-18）」になっている。印刷は出荷指示リスト編集のボタン（M05-22・M05-07）で行う。
   - #1 は業務フローの「※受注ステータスが『出荷指示』から『注文受領』に推移」をそのまま期待にしている。ところが出荷指示リスト詳細の現行仕様は「対応状況が出荷指示のまま出荷指示日だけが空になる」としており、この食い違いがシナリオに書かれていない。
   - データが受注1件だけで、作業単位「約60～70件」を使っていない（VP-TSUHAN-1105-01・02 で補う）。
3. **SCN-TSUHAN-既存業務発送業務-007**
   - #2「国内チェックリスト作成」の利用機能が受注情報検索・一覧（M05-01）になっている。原典では、ラベル印刷アプリからダウンロードした追跡情報でチェックリストを作る（外部ツールの作業）。
   - #11「早番退勤前を行う」では、原典4-15の中身（EMSは18時ごろ集荷、担当者がいれば当日、いなければ翌朝対応）が落ちている。
4. **STI-TSUHAN-003-003**（マクロで注文番号を生成する外部マクロの作業）の I/FID が M05-14・M05-12・M05-15・M05-06（受注ステータス変更・一括変更・メール）になっている。
5. **STI-TSUHAN-BOX-015-008・010**（出荷実績インポートのメール文面の変更と戻し）の I/FID が「-」。EC-CUBE の管理画面での設定変更なのに機能が割り当たっていない。どの画面で変えるかは設計書にも無い。
   **STI-TSUHAN-BOX-015-006**（発売日に、委託業者が発送完了と追跡番号を晴れる屋に共有する）は委託業者の作業なのに、I/FID が M05-18（出荷指示リスト作成）になっている。
6. 005・006・008・901 の「期待する主要機能No」に B05-08・B05-09 があるが、どの項目にも割り当たっていない（I/FID が B05 の STI は0件）。また B05-09（スマレジ取引連携エラー再連携）は店舗のレジ取引を扱うバッチで、通販の業務には当たらない。

## 3. 設計書の中の食い違い（作業中に見つけたもの。起票はしない）

- **出荷指示リストを削除した後の対応状況**: 業務フロー11-1は「出荷指示→注文受領」、M05-20 の現行仕様は「出荷指示のまま、出荷指示日だけが空」。
- **B05-02 購入完了手続き再処理と在庫**: 実行結果詳細には「在庫を減らす」とあり、処理概要には「在庫自体は注文確認の時点で減らされているため、ここでは履歴の登録のみ行う」とある。
- **B05-02 の対象状態の名前**: 「新規」「入金待ち」「ピック中」と書かれているが、受注管理の対応状況の選択肢（注文受領など）と名前が合わない。
- **B05-06 ポイント二重登録チェック**: 入力データ詳細は「ポイントが付与された履歴(ポイント増減量がマイナスの履歴)」で、付与と減算の言葉が食い違う。検索条件表は「0より小さい」。
- **B05-07 ポイント利用未反映チェック**: 概要は「GMO決済の受注」、カスタマイズはソニーペイメントへの変更で、参照方法は「現時点では詳細は未定」。一方、現行仕様にはソニーペイメントのプラグインの決済状態から読むと書かれている。
- **出荷実績インポート後の状態名**: 0203 は「発送済み」、受注編集は「出荷完了」（SCN-901 の分岐根拠に記録済み）。
- （店頭の業務・参考）B05-05 は、入力データ詳細では「キャンセル」もしくは「引き渡し済み」、検索条件表では「キャンセル」もしくは「出荷完了」。

## 4. 設計上のリスク（項目化する中で気づいたもの。期待値にはしていない）

- **B05-02 は取りこぼした注文を後から補えない**: 対象は「注文日時がバッチ起動時間の5分前から1分前まで」に限られる。バッチが5分を超えて止まると、その間に購入完了画面へ進まなかった注文は以後対象にならず、ポイント未消費・注文完了メール未送信のまま残る。期間を指定した再実行など、補う手段の記述が無い（SV-12-05 の根拠待ち部分）。B05-07（直近1時間）と B05-06（1日分）も同じ形。
- **B05-02 で在庫履歴が二重に登録されるおそれ**: 在庫履歴・販売数の更新を確定してから注文完了メールを送る。そのためメール送信で例外が起きると送信履歴が無いまま残り、次の回（5分の窓の中）で同じ受注が再び対象になって、在庫履歴・販売数が二重に登録されうる。SV-09-04（再実行後の重複）の担当へ引き渡す。
- **B05-08 は解消済みのエラーも表示し続ける**: 再連携に成功しても、受注情報編集にはポイント連携エラーの文言が残る。運用者は、受注情報編集だけでは解消済みかどうかを判別できない。
- **B08-06 の失敗は誰にも通知されない**: 購入時のスマレジ使用ポイント連携が失敗しても通知が無く、受注情報編集を開かないと気づけない。
- **B05-06 が前日付の重複を拾えないおそれ**: 管理画面のポイント付与では、ポイント発行日を年月日だけで手入力する。毎日4時・1日遡りの検索条件では、前日付で入れた重複を拾えない可能性がある（時刻の扱いは設計書に無い）。
- **バッチの異常の残り先**: B05-06・B05-07 の異常はコンソール出力にしか残らない。

## 5. 判断に迷った点

- **B05-02 を SV-12-04 に置いたこと**: 利用者の操作（決済後に購入完了画面へ進まない）で欠落した処理からの回復として SV-12-04 に置いた。ただし決済とブラウザの戻りの順序という点では SV-10-03 と重なりうる。
- **購入種類数150「大量」を SV-11-05 に置いたこと**: 1回の要求に含まれるデータ件数として置いたが、境界値・データパターンの観点と重なる。境界の149種類は含めていない。
- **擬似障害の起こし方**: スマレジとの連携を失敗させる方法（追加システム設定のスマレジアクセストークンを無効値にする）は原典に無い実行手段なので、known_limits に書いた。試験環境の他のスマレジ連携も止まる。
- **擬似障害の範囲**: 出荷実績インポートが残す「エラーの印」と B05-08 の対象フラグが同じものであることは、スマレジ連携の抜粋設計書のエラー処理表から読んだ。出荷完了メールがスマレジへの付与ポイント送信より先に送られることは、0203 の列挙順から読んだ。
- **SV-13-01 の判定**: 業務の時刻は既存項目が確かめているので「既存項目で確認済み」にした。ただしバッチとオンラインの両立は、オンラインを止める時間帯の定義が無く根拠待ちのまま。
- **使わなかった資料・扱わなかったバッチ**:
  - 0505 API（受注管理）の A05-01〜A05-04 は、店舗のプリンタ・店頭注文番号・スマレジ取引（レジ）の処理で、通販の業務フローに現れない。どの観点の根拠にも使わなかった（A05-04 の「秒間50回が上限」は SV-11-07 の理由欄で通販に当たらない旨だけ書いた）。
  - 店頭受取関連の B05-01・B05-03・B05-04・B05-05 と B05-09 は、通販の業務に当たらないとした。
  - 0416（インフラバッチ）の B16-12 データベースデッドロック感知（5分毎・管理者へメール）は、通販の業務フローに現れないため扱わなかった（SV-13-03 の基盤側の候補）。
  - 0209 に「購入処理エラー通知先メールアドレス」があるが、どの処理が使うかが書かれていない。
- **他の観点へ引き渡すもの**: 0304 の「受注データ作成後30分でタイムアウトしてカート画面へ戻る」は、注文の有効時間の業務規則としてタイミングの観点（SV-10）へ引き渡す。
- **検索の取りこぼし**: 作業中、シェルの grep（ugrep のラッパ）が実在する文字列を返さないことがあった（0203 の「閾値150」など）。キーワードの有無の判断は Python での全文照合でやり直した。
