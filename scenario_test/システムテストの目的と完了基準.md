# システムテストの目的とテストケースの完了基準

システムテストの目的は、システムが業務に必要な品質を満たし、担当者・画面・外部サービスをまたいで実際の業務が開始から完了まで回ることを、実測値と証跡から判断することである。この判断ができるテストケースを整えることを、今回の作業のゴールとする。

## 業務成立の判定

各経路は、最後の操作に成功しただけでは合格にしない。次の条件をすべて満たした場合に、その経路が成立したと判定する。

1. 開始条件、担当者・承認者、対象店舗、使用する案件・データパターンが確定している。
2. 同じ案件の実IDを引き継いで必要な工程を実施し、各工程の期待結果が指定された確認場所で観測できる。
3. 金額・数量・状態・宛先・CSV・帳票・通知等、当該経路が扱う値が、入力原本・処理結果・後続工程の参照値の間で一致する。変更が必要な値は、根拠のある変換規則と照合する。
4. 外部サービス・現場作業・別業務へ渡す工程では、受け渡した実データと受領後の業務結果を確認する。外部工程であることを理由に、その接点を未検証のまま完了扱いにしない。
5. 当該経路の最終業務状態を確認し、必須判定のすべてに合否・実測値・証跡が揃っている。

必須判定に不合格があれば経路不合格とする。未実施・保留・証跡不足が残る経路は合格にしない。別のデータパターンや排他的な分岐は、別案件で実施して判定する。

## テストケースを完成とする条件

- 業務フローの正常・主要代替・業務異常経路から、準備・操作・期待結果・確認場所・証跡まで追跡できる。
- 実施者が準備データと必要な環境を用意し、途中で仕様や手順を推測せずに操作できる。
- 合格・不合格を具体的に判定できる。資料の取得、保留の記録、画面への到達だけを業務上の合格条件にしない。
- 経路全体の判定と、工程・金額・数量・データ連鎖等の個別判定を対応付けている。経路全体の項目には、同じ実施で確認する必須判定を展開する。
- 結合テスト等へ分担した品質観点は、実在するケースと実施結果を追跡できる。参照IDが存在するだけで品質確認済みとは扱わない。
- 準備資料・判断基準・再現データの不足が業務成立の確認を妨げている場合、その経路のテスト設計は未完了として扱う。保留一覧を作成しただけでは作業完了としない。

業務フローやHTML設計書にない数値・外部様式・判断規則を作って不足を埋めない。既存資料・実装・実環境から確認できる部分は具体化し、そこで確定できない業務条件は、必要な原本または業務上の回答を特定して解消する。

## 品質を判断する範囲

本シナリオ群は、商品・価格・仕入れ・在庫・受注・買取・イベント・デッキの業務成立を確認する。権限、入力検証、重複処理等は機能・結合テストとの対応も含めて評価する。性能、同時実行、復旧等に受入要件がある場合は、その要件に対応するテストと結果も品質判定に含める。業務経路の合格だけで、別観点の品質まで確認済みとは扱わない。

テストケースの完成、実機テストの実施完了、システム品質の受入判断は、それぞれ別の完了状態として記録する。
