# B06-01 買取自動入庫バッチ（開発環境・2026-11-20）

## 結論（11/20 朝）：E2E では書かない → 11/20 依頼者決定で、自動の実行を待つ2回の形で書いた（下の「2回に分けて流す形」）

テストがまだ無い11件（015・016・017・022・023・025〜028・030・031）は、どれも手順1が「試験者が『買取自動入庫バッチ』を実行する」で、手順2が「バッチの実行一覧で、状態が『成功』になるまで待つ」。開発環境では、E2E からこのバッチを起動できない。

## 起動できない理由
- このバッチは、アプリのコンソールのコマンド（買取自動入庫バッチ）として作られている。管理画面にも API にも、起動する入口が無い。手順2の「バッチの実行一覧」の画面も無い。
- 開発環境では、バッチの EC2 が毎日 15:00（日本時間）に自動で流している。DB の在庫履歴で、履歴の元が「買取自動入庫バッチ」の行は、11/12〜11/19 の毎日 15:00 にできている。
- 流れると、入庫待ちの店頭買取とネット買取が全件入庫される。共有の DB にある、ほかの方の買取も対象になる（11/20 朝の時点で、入庫待ちの店頭買取は3件）。そのため、E2E から起動できたとしても、ほかの方の買取まで入庫してしまう。

## 流すとしたら（依頼者の判断が要る）
- 案1：E2E のシードで、入庫待ちの店頭買取を作っておく。毎日 15:00 の自動の実行のあとに、在庫・在庫履歴・買取詳細を確かめる。2回に分けて流す形（準備と確かめ）で、ハーネスにこの形を足す必要がある。手順1の「試験者が実行する」は、「15:00 の自動の実行を待つ」に読み替える（正本の外の補い）。
- 案2：流せない一覧（config/sheet_not_runnable.tsv）に載せて、項目表は「実施不可」にする。

## そのほか
- シード表の店舗「TC東京2F」は、11/13 の決まりで本店（店舗ID 1）か試験支店（1574）に読み替える必要がある。

## 2回に分けて流す形（2026-11-20 依頼者決定「B06-01・B08-04 は自動の実行を待つ形で書く」）

書いたケースは11件（015・016・017・022・023・025・026・027・028・030・031）。spec/b06/b06-01.spec.ts・seeds/b06-01.ts・db/b06_01.ts・pages/admin/b06_01_read.ts。

- バッチの実行の時刻は、DB の在庫履歴の登録元「買取自動入庫バッチ」の行の登録日時で見る。11/12〜11/19 は毎日 06:00 UTC（15:00 日本時間）。バッチの実行一覧の画面は無い。

### シードの作り（正本の外の補い）
- 店舗「TC東京2F」は試験支店に読み替える。
- 店頭買取は、試験支店のフロントの店頭買取査定申込（会員登録なし）で作る。申込者の姓に実行の印を付ける。シード表の会員は作らない。決め打ちの番号は使わない。
- 実在庫の明細（MTGBuyer の査定で付く行。管理画面に登録の手段が無い）と、ステータス（入庫待ち＝13・入庫済み＝11）・金額は、E2E の受注にだけ DB で書く。
- 商品はグッズ商品CSV登録で作る（商品コード・商品名に実行の印）。入庫先（試験支店）の EC-CUBE 在庫の在庫数・総原価は、E2E の商品の行にだけ DB で書く（シード表の「在庫履歴は0件」のため。画面の入庫は履歴を作る）。
- 「入庫待ちの買取はこの1件以外0件」「他の入庫待ちの買取情報は入庫済み等へ変えておく」は、しない（ほかの方の買取を書き換えることになる）。バッチは、ほかの方の入庫待ちも入庫する。ケースは E2E の商品・買取だけを見る。
- シード表のステータス「12: 入庫待ち」は、マスタでは 13 が「入庫待ち」（12 は「未登録在庫あり」）。名称に合わせた。

### 流せる・流せないもの

- 022〜031 のシード（S-B06-01-DP-…）は、作り方の文に「在庫履歴は0件にする」がある。そのため、消すシードとして開発環境で飛ばされる。コードは何も消さない（新しく作った商品の履歴は初めから0件）。
