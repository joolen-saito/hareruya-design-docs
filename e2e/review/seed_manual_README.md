# 手で試す人向け: シードの手順書・CSV・登録順

テスト用のデータ（マスタを含む）は、ダンプに入れない。渡すダンプはテスト用データの無いもの（09/07 のダンプ＋マイグレーション）で、
テストする人が、手順書とCSVを見ながら、画面から登録・取込する。マスタ（店舗・所属・管理者・権限・各種設定など）の新規登録もそのまま試せる。

## 置き場所（`e2e/seed_files/<機能ID>/`）
| ファイル | 中身 |
|---|---|
| `<シードID>.md` | そのシードの手順書。シード表の「状態・属性」「用途」「投入方法」の文をそのまま写してある（文にない操作は足していない） |
| `<シードID>/<正本のファイル名>` | 画面から取り込むCSV・TSV・テキスト・画像。ファイル名は設計書（シード表）が書く名前のまま。取り込む順は手順書に従う |
| `<シードID>/setup/` | 先に取り込む準備用CSV（グッズ商品CSV登録・商品CSV登録）。文にファイル名があればその名前（例 `M0330RB-001-base.csv`）、無ければ `setup1.csv`・`setup2.csv` …（備考に書いてある） |
| `_csv_index.tsv` | どのファイルが、正本のどのファイル名か。作り方（fixtures を写した／シード表の文から組んだ）と、担当が決めた値の理由 |
| `_order.md` | その機能の登録する順番 |

シード数は 2,640 件（手順書の数）。このうちパスワードを含む 255 件は `e2e/.runs/seed_files_private/<機能ID>/` にある（git に入れない）。同じ名前のシードが複数の機能の表に載っているものがあるため、固有のIDは約2,631件。


## 手順書の使い方
1. `_order.md` の順に、手順書を開く（先に登録するものが「先に登録するもの」の列に書いてある）。
2. 手順書の「投入方法」のとおりに画面から入力する。CSVで取り込むものは、同じフォルダのCSVを選んで取り込む。
3. 画面が振る番号（商品ID・カテゴリIDなど）は、登録した場所で控える。手順書に「控える呼び名」が書いてある。CSVの中の〔…〕（例 `〔商品ID-M0331-010〕`）は、その番号を控えた画面の値に置き換えてから取り込む。
4. 承認・削除・取込などで状態が変わるシードは、一度使うと元に戻らない。もう一度試すときは同じ内容で登録し直す（商品コードなどが重なるときは、前のものが残っていないか確かめる）。

## 登録順（`_order.md`）の読み方
依存の根拠は、(1) e2e/seeds の作り方の needs、(2) シード表の文に出てくる他のシードID。どちらも無いものは、区分からの目安の位置（環境・設定 → 店舗 → 所属 → 管理者 → 参照マスタ → 商品 → 在庫）に置く。区分からも決められないものは「順番不明」と書いてある。機能をまたぐ依存は「（他機能）」と付けてある。機能ごとの内訳は `review/seed_order_summary.tsv`。

同じ名前のシードが複数の機能の表に載っている場合: S-M03-30-QC-ENV・S-M03-30-QC-MASTERS・S-M03-30-QC-ADM は M03-30・M03-31・M03-32 の三つの表に載っているが同一のシード。手順書（.md）は各機能の置き場所にあるが、同じシード（M03-30 の表のもの）を一度登録すれば足りる。各機能の `_order.md` の冒頭にも同じ注意を書いてある。

## 設計書とアプリの食い違い（CSVの作り方）
商品コード: シード表の文は「任意」、アプリ（グッズCSV取込 `GoodsCsvController`）は「必須」。CSVは文のとおり商品コードを空にして作ってあり、取り込むとアプリ側で弾かれる可能性がある（試験で見える食い違い）。該当するCSVの備考にも同じ注記がある。

## 商品公開ステータスの値
設計書の値 2（公開）は、アプリでは 1 が公開（アプリの定義: 公開=1・非公開=2・廃止=3。支店の商品公開ステータスは公開=1・非公開=0）。2026-10-22 の依頼者決定で 1 を公開として扱う。シード表が「2（公開）」「公開を表す値」のどちらで書いていても、CSVにはアプリの値（公開=1）を入れ、手順書と `_csv_index.tsv` の備考にその旨を書いてある。「非公開」はアプリの 2。文が「2」とだけ書くもの（公開とも非公開とも書かない）は文のとおり 2 を入れ、備考で食い違いを知らせてある。

## 分類（`review/seed_split.tsv`）
マスタ（共有可）／ケースで登録（ケース専用・共有可でないもの。管理者・店舗を含む）。どちらも手順書がある。規則は `tools/seed_split.mjs` の冒頭。
内訳は、ケースで登録 2,392（ケース専用 2,353＋共有可のもの 39）、マスタ 248、要確認 0。

「共有可」と書かれたシード 287 件のうち 39 件が「ケースで登録」に分類されているのは、その区分の語（商品・商品規格・価格履歴・在庫移動・振替など）が、ケースごとに作り直す側の語だけでできている（または、ケース側の語が混ざる）ためである。マスタ側の語（店舗・業務マスタ・カードなど）が混ざるものも、丸ごとケースで登録する側に寄せた（依頼者決定 2026-10-23）。一覧と理由は `review/seed_split.tsv` の「共有」と「分類」「理由」の列。

## CSV
- CSV の出どころは「`e2e/fixtures` の検証済みファイルを写す」か「シード表の文から組む」の2つだけ（`tools/csv_make.py`）。作り方のコードを走らせて取り出したものは使っていない。環境の値（言語ID・サプライ・グッズのカテゴリID・購入グループ名など）は DB を読むだけ（SELECT）で引く。
- 画面が振る番号の所は、呼び名〔…〕をそのまま入れてある（値は作っていない）。シード表の文が値を決めていない列（「任意の金額」「有効な値」「正常値」など）は、e2e/seeds・fixtures の値、環境の有効な値（DB を読むだけで選ぶ）、機能IDの入った意図の分かる値の順に決め、手順書（.md）と `_csv_index.tsv` の備考に、決めた値と出どころを書いてある。
- 行数・サイズ・文字コード・改行・BOM・区切りの指定があるファイルは、指定を満たすように決定的に作り、`tools/csv_verify.py` で行数・改行数・バイト数・文字コード・改行・BOM・区切りを数えて確かめてある（結果: `review/csv_verify_result.txt`）。大きいファイル（5,009行・5MB±1バイトなど）も `seed_files/` に置いてある（10MBを超えるものは無い）。
- **サイズだけを指定するファイルの埋め方**: 文が中身を書いていれば、その行を入れる（M03-20 の 5MB は部門 20,000 行で、最終行の部門名の長さで調整）。大きさは、文が指定する不可視文字（先頭の BOM とゼロ幅スペース。どちらも除去後は文の内容そのまま）で合わせる。改行で埋めると行数の上限（M03-35・M03-38 は改行 5009）に触れて狙いが崩れるため使わない。3 で割れない端数は行末の LF を CRLF にして合わせる（備考に書いてある）。
- **5MB のファイルについて**: シード表の「5MB」は 5,242,880 バイト(1024×1024)として作った。アプリの CSV 取込の上限は Symfony の maxSize「5M」= 5,000,000 バイト(`src/Eccube/Form/Type/Admin/CsvImportType.php:84`、`eccube.yaml` の `eccube_csv_size: 5`)なので、5,000,001〜5,242,880 バイトのファイルはアプリに拒まれる見込みで、設計との差はテストで見える。該当のファイルの手順書の備考にも書いてある。
- 〔取込前の<列名>〕（M03-41 の更新・削除行）は、シード表の投入方法 (3) の指示どおりである（例 S-M03-41-CASE-005 の (3)「CSVの更新行に書く表示ランクなどの登録済みの値は、カテゴリ一覧のCSVダウンロードボタンで出力したCSVの当該カテゴリの行から写す」）。カテゴリ一覧の「CSVダウンロード」で出力したCSVの、そのカテゴリIDの行の同じ列の値に置き換えてから取り込む。M03-27 の更新系の「取込前の値」は、手順②で取り込む準備用CSV（`.<n>.csv` の base ファイル）の値をそのまま入れてある。
- 作れなかったもの（または一部だけ作れたもの）は、手順書の末尾に理由が書いてある。その部分は、シード表の文のとおりに手でCSVを作る。一覧は `review/csv_make_result.tsv`。
- 仕分け（アプリに触らず作れる／環境の値が要る／番号が要る）: `review/csv_seed_classes.tsv`。

## DBへ直接設定する部分（SQL）
画面でできない値（作成日・更新日、在庫数・総原価、価格履歴の削除、取込履歴の登録、規格の論理削除など）は、手順書に「DBへ直接設定する」と書かれている。その文ごとに、作れるものはSQLを作ってある。テストする人は、渡したダンプ（テスト用データ無し）から作ったDBに、手順書とCSVを見ながら画面でシードを登録し、DBへ直接設定する部分だけこのSQLを流す（依頼者決定 2026-10-23）。
- 置き場: `e2e/seed_files/<機能ID>/<シードID>/` の `db_before.sql`・`db.sql`・`db_<番号>.sql`。SQLの中に認証情報（パスワード・ハッシュ）を含むものは `e2e/.runs/seed_files_private/<機能ID>/<シードID>/` 側に置く決まり（今回、SQLの中に認証情報を含むものは無い）。シード表の文にパスワードを含むシードは、手順書（.md）だけが `e2e/.runs/seed_files_private/<機能ID>/<シードID>.md` にある（git に入れない）。そのシードのSQLファイルの先頭のコメントに、手順書の場所を書いてある。
- 流す時点: 各ファイルの先頭のコメント「-- 流す時点:」と、手順書の「DBへ直接設定する部分（SQL）」に同じ文で書いてある。投入方法の文の順から決めている（「投入方法の「…」を終えたあと、次の「…」より前」）。`db_before.sql` は画面で登録する前に流す（やり直しのときの後始末。前回の残りだけを消す。登録のあとに流すと作った行まで消えるので流さない）。ただし、状態・属性が「存在しない」と書く行（このシードが画面で作らない行。例: S-M03-13-PRIORITY-CODES の商品コード UNKNOWN-999 の規格）だけを消すものは、ファイルの先頭と手順書にそう書いてあり、登録のあとに流してもこのシードが作った行は消えない。`db_<番号>.sql` は、DBの文が画面操作の途中に何か所もあるときに時点ごとに分けたもの。状態・属性に書かれた文は、投入方法の画面の操作をひととおり終えたあとに流す。
- 決まり: どのファイルも 1つのトランザクション（BEGIN〜COMMIT）。消すのはそのシードの行だけ（商品コード・ファイル名・番号・棚卸名などで範囲を絞る）。**全件削除（表全体・取込種別全体を消すもの）は作っていない**。その状態にするには既存の行を消す必要がある文は、手順書に「渡したダンプの直後の件数」と「この状態にするには既存の行を消す必要がある（全件削除のため SQL は用意していない）」を書いた（件数は `tools/db_sql_run.py counts` が試し用DBから SELECT だけで取ったもの。`review/db_dump_counts.json`）。商品コード・店舗名・棚卸名・管理者名などで引く行と、呼び名の番号で指す行は、流す時点で1件に決まることを確かめ（`DO $$ … RAISE EXCEPTION`。止まったときのメッセージに実際の件数が出る）、決まらなければ止まる。更新（UPDATE）は、どれもその直前などに、同じ表・同じ条件で行の数を確かめる確認を置いた（番号や名前で1行を指すものは1件、文がN件と書くものはN件、文から数が決まらないものは1件以上。0件のまま黙って通らない）。確かめない更新は、意図して「あれば更新する」もの2つだけ（棚番号の後始末で消す棚番号を指す規格の棚番号を空にする更新／状態・属性が「在庫反映済みの棚卸詳細が0件」と書く計画の0件の更新。`tools/db_sql_lib.py` の `UPDATE_IF_PRESENT` に理由つきで載せた）。削除（DELETE）には置かない（消したあとに流し直すと消す行が0件になり、「消す行がある」確認は2回目で必ず止まるため。削除はどれも「あれば消す」形）。流し直しても壊れない形（同じ行があれば同じ値に揃える／このシードの行を消してから作り直す）にしてある。
- 取込種別の番号は、画面（コントローラ）が取込履歴を書き・一覧を引くときに使う定数（`src/Eccube/Entity/Master/MtbCsvImportType.php`）で決めた。マスタ（取込種別の表）の名前では決めない。番号5〜8はマスタの名前と画面が食い違う: 5=基準価格変更CSV（M03-30。マスタの名前は「セール用価格変更登録」）、6=セール用価格変更CSV（M03-31。「価格変更登録」）、7=高額商品価格変更CSV（M03-32。「セール用高額商品価格変更登録」）、8=セール用高額商品価格変更CSV（M03-33。「高額商品価格変更登録」）。手順書の「ダンプ直後の件数」もこの番号で数えた。番号9（在庫変更）・10（割引率変更）・12（略称タグ更新）・13（買取減額率変更）は、取込履歴を書く画面も一覧に出す画面も無い（略称タグCSVの画面には取込履歴の一覧が無く、取込でも履歴を書かない）。
- 店舗名で引くSQLのうち、同じ店舗名（例: 店舗A・店舗B）を複数の機能のシードがそれぞれ登録するものは、全部のシードを1つの環境に入れると「2件以上」で止まる。該当する手順書（M04-22・M04-31 など）に、避け方（機能ごとに環境を分ける、または控えた店舗IDで引く形に書き換えて流す）を書いた。シードの名前は正本のとおりで変えていない。
- 流す前に、SQLの中の〔…〕（画面で控えた番号の呼び名）を番号に書き換える。置き換えが要る呼び名は手順書に一覧がある（確認のメッセージの文字列の中の〔…〕は置き換えなくても動く）。
- 日時は日本時間（+09）として書いてある（DBの時刻は UTC）。文に無い値を決めたもの（例: 取込履歴の日時が「番号順に1分ずつ」とだけ書かれたもの、入荷通知依頼の会員の氏名、論理削除の規格の商品名）は、SQLの備考と手順書の備考に書いてある。
- 作っていない文・作れない部分: 全件削除でしか書けないもの、退避・復元の保管先が文に無いもの、行の中身（管理者・5009商品など）が文に無いもの、パスワードが要る管理者の登録など。手順書の末尾（「SQLを作っていない文と理由」「作れない部分」）に理由を書いた。現行のDBに設定先の表・列が無いもの（商品本体の削除済み・所属と店舗の関係）、番号が現行のDBの型の上限を超えるもの（所属ID・商品ID・取込履歴IDの桁）、取込種別のマスタの名前と画面が使う番号が食い違うもの（下）、取込履歴を書く画面・一覧の画面が無いもの（略称タグ更新CSVなど）、状態の値がアプリの状態の選択肢に無いもの（状態EX）は「設計と実装の差の候補」と区分を付けた（記録だけ。起票はしない）。一覧は `review/db_sql_result.tsv`（文ごと。結果は 作った／一部だけ作った／作れない、区分の列あり）、集計は `review/db_sql_summary.tsv`。
- 検査（SQLをDBに流さずに行う）: `tools/db_sql_check.py`（括弧・BEGIN/COMMIT、使った表と列が `tools/db_schema/`（information_schema の写し）にあるか、INSERT の NOT NULL 列と値の数、UPDATE の前に同じ表・同じ条件の行の数の確認があるか（`UPDATE_IF_PRESENT` の許可の一覧に当たるものを除く））。表がアプリの Entity／マイグレーションに出てくることの確認は `review/db_sql_entity_check.tsv`。表・列・外部キーの写しは `tools/db_schema_dump.sh`（SELECT だけ）で取り直せる。
- 試し用のDB（`eccubedb_sqltest`。渡すダンプから作ったもの）での確かめ: `tools/db_sql_run.py run`。データベース名は固定で、これ以外は受け付けず、毎回 `current_database()` を確かめて違えば止める（`eccubedb` には流さない）。どの確かめも1つのトランザクションの中で行い、最後に ROLLBACK する（SQLファイルの BEGIN/COMMIT は外して、外側のトランザクションの中で文を流す。試し用DBの行の中身は変えない。ただし連番（シーケンス）を進める文（nextval。番号を文に書かない取込履歴の登録など）があると、連番の値はロールバックしても戻らない）。ファイルごとに次を行い、結果を `review/db_sql_run_result.tsv` に書く。
  - A. 置き換えずに流す: 呼び名〔…〕を存在しない番号にして流す。止まったときは、どの確認で止まったか（メッセージと件数）を記録し、「0件（画面で作るデータが無い）」以外で止まったもの・エラーは想定外として数える。呼び名の有無はコメントと文字列を除いた本文で判定する。0件で止まったものでも、そのファイルが引く行を作るシードが無いもの（番号で引く管理者など。画面では番号を指定できず、どのシードのSQLも作らない）は「正しく登録しても止まる（作るシードが無い）」、別の機能のシードのSQLだけが作るもの（例: M03-27 の発送日目安736 は M03-04 の S-M03-04-RICH-002・S-M03-04-RICH-003 のSQLが作る）は「別の機能のシードを先に登録しないと止まる」と分けて数える。
  - B. 用意して流す: そのシードが画面で作るはずの最小の行を試し用に作ってから流す。用意する行の名前（商品コード・店舗名・棚卸名・ファイル名・呼び名）は、シード表の文と手順書の「画面で入れる値」から読む（`tools/db_sql_text.py`）。SQLの本文からは写さない（写すと、SQLが間違った名前を引いても用意した行に当たって通り、間違いを見逃すため）。管理者・部門などは、SQLが名前で引くもののうち、名前がシード表の文に完全な語として出てくるものだけ用意する。番号で引く行は、どれかのシードのSQLが作るときだけ用意する。文ごとに変わった行（更新前・更新後・消した行・入れた行）を記録し、変わったのが用意した行とこのSQLが入れた行だけか（ダンプにあった行を変えていないか）、`tools/db_sql_expect.py` に書いた期待（正しい行が正しい値になったか）を満たすか、もう一度流しても同じ状態か、を確かめる。期待は、敵対レビューで直した文（対象の規格・節・入荷通知依頼・取込履歴の日時と作業者・1件確認・規格の論理削除など）について書いてある。
  - C. シード全体: シード表の文から作った期待（`tools/db_sql_expect.py` の EXPECT_SEED。M04-30 のスマレジ商品IDと価格変更履歴の日時、M04-08 の節ごとの対象、M03-40 の論理削除など）と、「同名取込履歴0件」のシードの「文のファイル名・その機能の画面の取込種別の履歴が0件」は、そのシードの全ファイルを流す順（db_before → db.sql・db_N）に流して確かめる。期待はシード表の文から作り、SQLに値があるかどうかで足したり外したりしない。
  - 値の一つ一つを期待で確かめたのは一部のファイルだけ。ほかのファイルは「変わったのが用意した行（シード表の文から用意したもの）とこのSQLが入れた行だけ」「もう一度流しても同じ」までで、値そのものは確かめていない（手順書にもそう書いた）。
  - 値の照合（`tools/db_sql_check.py literals` → `review/db_sql_literal_check.tsv`）: 全SQLの WHERE で使う名前・コード・ファイル名の値が、シード表の文に完全な語として出てくるか（「3件とも本店」「と大阪支店」のような語の断片でないか）、手順書の「画面で入れる値」か、このSQLが自分で入れる値かを、機械的に確かめる。
  - 手順書の各SQLファイルの下に、そのファイルの確かめの結果を書いた（実際に行が変わったことを確かめたものだけ「変わったことを確かめた」と書く）。
- `tools/db_sql_run.py counts` は、渡すダンプ直後の件数（全件削除の案内用）を SELECT だけで取る。
- 洗い出し（SQLを作る前の一覧）: `tools/db_inventory.py` → `review/db_seed_inventory.tsv`。作り直し: `tools/db_sql.py`（SQL）→ `node tools/seed_split.mjs`（手順書）。

## 作り直し
`tools/seed_prepare.sh`（手順書・CSV・登録順の順に作る）。検査: `tools/csv_verify.py`（行数・サイズ・文字コードなどの指定）、`tools/setup_check.py`（準備用CSVの列数と必須列）、`tools/seed_order_check.py`（登録順の向き）。DBへ直接設定する箇所の洗い出し: `tools/db_inventory.py` → `review/db_seed_inventory.tsv`（SQLは `tools/db_sql.py` が作る。試し用DBでの確かめは `tools/db_sql_run.py run`）。数だけ見るなら `tools/seed_only.sh count`。
