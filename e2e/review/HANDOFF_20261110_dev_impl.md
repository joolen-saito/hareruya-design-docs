# 引き継ぎ: 開発環境での E2E テストコードの実装（2026-11-10）

別のセッションで、テストのまだ無い結合テストケースの E2E を実装し、開発環境で流して判定するための引き継ぎ。
同時に、もう1つのセッション（流し直しのセッション）が、テストのあるケースを開発環境で流し直している。

## 依頼者の決定（2026-11-10）
- E2E は手元の環境ではなく、**共有の開発環境**（https://replace-dev.hareruyamtg.com:8443）で流す。
- 対象は、共有ドライブの「結合試験項目表.xlsx」の「テストケース」シートのうち、実施者が空白か「E2E（Playwright）」の行。
- 結果は流し直しのセッションが項目表へ書き戻し（`e2e/tools/sheet_writeback.py`）、不合格を Backlog へ起票する（`e2e/tools/backlog_e2e_register.py`）。**このセッションでは書き戻しも起票もしない。** 判定と記録までを行う。
- 流せないケース（DB に直接入れる準備・外部の試験環境・メール通知の受信確認など）は、項目表で「実施不可」になる。理由を記録に書いておく。
- データを消すシードは、E2E が作ったデータだけを消すものなら流す。`config/shared_env_delete_ok.tsv` で「消してよい」と仕分けたものだけ、基盤が流す。ほかの方のデータも消しうるものは流さない。仕分けは流し直しのセッションが行っている。
- 「判断待ちはそのままで」。判断が要るものは記録に残して先へ進む。

## 開発環境で流す方法
```
cd /home/y-saito/Developments/hareruya-design-docs/e2e
set -a; . ./.env.dev; set +a
PW_SLOTS=2 tools/run_evidence.sh <機能ID> [番号…]
```
- `.env.dev` は git 管理外。接続先・管理者・DB の参照URL・メールの受け口が入っている。中身を表示したり、ほかへ書き写したりしない。
- DB は SSH のトンネル（127.0.0.1:15432 → 踏み台 replace-stg-bastion-01）を通る。接続は読み取り専用（`PGOPTIONS` で書き込みを拒否する）。
  - トンネルの見張りは `tools/dev_db_tunnel.sh`（30秒ごとに確かめ、切れていたら張り直す）。WSL やマシンを起こし直したあとは `nohup tools/dev_db_tunnel.sh >/dev/null 2>&1 &` で動かし直す（2つ動かしても害は無いが、1つでよい）。
- メールの受け口は開発環境のもの。試験会員はフロントの会員登録で作り、本登録のメールをここで読んでよい。

## DB への書き込み（2026-11-10 依頼者決定「E2E が作った行だけ書いてよい」）
- 画面で作れない状態（過去の日時・画面の入力チェックを通らない値・画面に無い項目・履歴の行など）は、画面で作った E2E の行に、`lib/db_write.ts` の `updateOwnRows`・`insertOwnRows`・`deleteOwnRows` で書き足す・書き換える。
- 書く相手は「持ち主の確かめ」（その行が E2E のものと分かる SELECT。実行の印・控えた番号）で示す。当たらない行が混ざれば、書かずに止まる。
- `.env.dev` の `E2E_DB_WRITE=1` で有効になる。書いたものは `.runs/db_writes.log` に残る。
- ほかの方のデータを消す・書き換えるシード（既存データの全件削除など）は、これまでどおり流さない。
- 呼び出しは `db/<機能>.ts` に業務の言葉の関数で包み、物理名を spec・記録に出さない。判定は、DB で書き足した値をケースが確かめるなら条件付き（正本の外の補い）、確かめないなら注記。
- スマレジの試験環境は「つながっていて、使ってよい」（依頼者 2026-11-10）。入り方は確認中。

## ぶつからないための決まり
1. **受け持ちの表 `e2e/review/WORK_CLAIMS.tsv` に、触る機能を先に書く。** すでに別の受け持ちがある機能は触らない。終わったら、その行の「内容」に「済み」を書き足す。
2. **流し終えた spec は直さない。** spec を直すと、同じファイルの全件が「要再実行」になり、もう一方の判定が古くなる。新しいケースは新しい spec（まだ無い名前、例 `spec/f04/f04-02-f.spec.ts`）とシードに書く。
3. **共通の部品（ほかの機能も使う pages・seeds・db）は、省略できる引数を足す程度にとどめる。** `e2e/lib/` を変えたいときは、変える前に依頼者に知らせる。
4. **git は自分が変えたファイルだけを `git add <パス>` でコミットする**（`git add -A` や `git add .` は使わない）。index.lock があれば少し待ってやり直す。プッシュは依頼者に言われたときだけ。
5. **Playwright は全体で3本まで。** PW_SLOTS=2 で流す。**PW_SLOTS=1 は「ほかの回と並べない単独の実行」なので使わない。** 基盤の枠は、セッションをまたいで本数を抑える。npx playwright を直接たたかない。
6. 判定は `tools/evidence_judgements.py` で書く。記録は `review/<機能ID>_progress_<日付>_dev.md`。合否の一覧への sync と一覧の作り直しは、流し直しのセッションがまとめて行う。

## 実装の決まり（いつもどおり）
- 手順の正本はスキル `/home/y-saito/Developments/hareruya-design-docs/.codex/skills/hareruya-e2e-case-evidence/SKILL.md` と、その `references/`（RULES.md・IMPLEMENTATION.md・RUN_AND_EVIDENCE.md・JUDGEMENT.md）。
- 基盤の使い方は `e2e/README.md`。経緯は `e2e/HANDOFF_codex.md` と、各機能の `review/<機能ID>_progress_*.md`。
- テストケースが正。正本（`integration_test/casegen/cases/`）・期待結果・アプリを変えない。ケースを足さない。
- テストデータは画面から作る。DB は参照だけ。決め打ちの値には実行の印（`lib/run_marker.ts` の `rc()`）を付ける。
- 開発環境のほかの方のデータを消したり、書き換えたりしない。共有の設定（目印「≪共有の設定≫」）は、基盤が1本だけで流して元へ戻す。
- 物理名をテスト名・注記・記録に書かない。資格情報をファイルに書かない。
- 待つループに `pgrep -f` を使わない。流しは前景で、終わるのを待ってから判定する。
- マシン資源を節約する（nice。リポジトリ全体の grep をしない）。
