## シードを作らない理由と、作らないときの形
- 使用シード（S-A15-15-FORMATS・CARDS・DECKS・MASTERS・CALLERS）は、どれも画面で作る形で、作り方はまだ無い（e2e/seeds に登録していない）。MASTERS は決め打ちのボード識別子 15301・15302 を「登録済み」とするので、画面では作れない。
- 送り先の経路が新アプリに無いので、どんなデータを作っても応答は同じ。そこで、事前準備の最初に送り先を確かめ、無いときだけシードを作らずに手順へ進む。確かめは、既存のフォーマット（DB を読むだけ）の番号で、新アプリの置き方の経路と設計の経路の両方へ送り、両方とも「404・本文が JSON でない」なら「無い」とする。
  - 設計は、フォーマットが無いときも 404 だが、本文は JSON（「format not found」）。経路が無い 404 とは、本文の種類で見分ける。
- 送り先が有るとき（アプリが直ったとき）は、ふつうどおりシードを作りに行く。作り方が無いので、事前準備で止まる。そのときは、シード表どおりの作り方を足す。
- シードを作らないときは、経路のフォーマット識別子に既存のフォーマットの番号を使う。アーキタイプ識別子（004・010）も、そのフォーマットの既存のアーキタイプの番号を読むだけで使う。カード識別子の突き合わせ（呼び名の番号との比較）はしない。HTTP ステータス・本文が JSON・集計が配列の確かめは、どのケースでも行う。

## 送り先の経路と条件
- 設計（機能一覧の経路・functions/endpoint-existence-check-report.md:368）は GET /deck/usage_card/{フォーマット識別子}。新アプリはデッキビルダーの API を /api/ の下に置く（デッキ情報参照 /api/deck/{id}・アーキタイプ検索 /api/archetypes/{id}）ので、同じ置き方の /api/deck/usage_card/{…} へ送る。確かめでは、設計の経路そのものにも送る。
- 条件の名前と応答の項目名は、現行（デッキの API の採用枚数。`deck-api/config/routes.yaml:53`・`deck-api/src/Controller/DeckController.php:326`）に合わせた（A15-15 は現行踏襲）。種別「土地以外」は、現行が「土地」以外の値をすべて土地以外として扱うので、土地でない値を送る（003 の補い）。
