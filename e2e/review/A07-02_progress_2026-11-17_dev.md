## 正本の外の補い（読み替え）
- **送り先と経路**：送り先は API サーバー（2026-11-17 依頼者に教わった。管理画面のホストではない）。正本の経路「/api/admin/buyOrders.json」は、開発環境の API サーバーでは HTTP 404 で、アプリの経路の設定で「/api/v1/admin/buyOrders.json」に置かれている。毎回、まず正本の経路へ送って 404 を記録し、/api/v1 の経路へ送り直した応答で確かめる（注記に両方が出る）。
- **開発者ツールの代わり**：テストのブラウザ（同じコンテキスト）から要求を送り、応答の HTTP ステータスと本文を読む。応答の一覧にはほかの方の試験データ（氏名・電話番号など）も入るので、エビデンスの画面にはケースが見る要素（控えた受注番号の要素）と件数だけを表で出す。
- **認証トークン**：正本の「署名シークレットを設定して HS256 のトークンを生成する」は、共有の開発環境では秘密の値を書き換えられないので、査定担当A・B のログインIDとパスワードで管理者ログインの API（POST /api/v1/admin/login.json）を呼んで受け取る。値は記録しない。要求ヘッダはアプリが読むもの（設計書は「リクエストヘッダで受け取る」とだけ定める）。
- **送信元IPの許可**：開発環境の設定のまま（書き換えない）。
- **査定担当A・B**：メンバー管理で登録し、実行をまたいで使い回す決まった印を名前・ログインIDに付けた（依頼者決定 2026-11-11）。所属店舗は試験支店（依頼者決定 2026-11-13）。002 の memberName は、印つきの名前「査定担当A-E2E」と比べる。
- **会員**：正本の「管理画面の会員登録」の代わりに、フロントの会員登録（依頼者決定 2026-10-31）。お名前・郵便番号・都道府県・住所・電話番号はシード表の値、メールアドレスはシード表の値の @ の前に実行の印を付けた。顧客IDは登録した会員のメールアドレスで DB を参照して控えた。
- **買取**：会員でフロントから既存の買取できる商品1点を数量1で申し込み、完了画面の買取番号を控えた。「商品到着」と管理者用メモは買取情報編集で保存した。
- **DB で書いた値**（E2E の買取にだけ。`lib/db_write.ts`・依頼者決定 2026-11-10）：査定申込日・ハイフン付きの電話番号と郵便番号・査定担当者（シード表が「画面で指定できないので DB」と定めたもの）・買取状況「振込完了」（007・008・016B）。011 は査定担当者の紐づけが無いことを確かめ、付いていれば外す。
- **マスタ**（S-A07-02-MASTERS）：DB へは書かず、買取状況（2・7・10・11・12）と都道府県「東京都」があることを参照で確かめた。
- **016 の「ほかの受注の状況を振込完了にする」**：ほかの方のデータなので行わない。期待結果（016A が含まれ 016B が含まれない）は、ほかの受注の有無に左右されない。
- **006**：2回の要求の間に、ほかの方の受注が変わると本文が違いうる（共有の開発環境）。違ったときは注記で分かる。

## 流した結果
- 2026-11-17 16:3x 002 を1件だけ流した（PW_SLOTS=2）: 1回目はシードで止まった（フロントの会員登録の直後はログイン済みの画面になり、申込みのためのログインの画面が出ない）。登録と申込みを別のブラウザで行うように直した。
- 2026-11-17 流し直し: **002 合格（条件付き）**。期待結果の11項目（受注番号・査定申込日・フリーコメント・査定担当者名・ステータスID・顧客の名・姓・電話番号・郵便番号・住所）はすべて期待どおり。
  - 条件: 正本の経路 /api/admin/buyOrders.json は API サーバーで 404 で、/api/v1/admin/buyOrders.json へ送り直した結果。設計書（0507 系の処理概要）の経路と、開発環境の経路が違う。アプリは経路の頭を設定で決める作り（`/%eccube_api_v1_route%/admin/…`）なので、設定の違いか実装の違いかは確かめていない。起票の担当へ「設計の確認」の材料として送った。
- 残りの 001・004・006・007・008・011・016 は昼の列に積んだ（a0702）。009 は消すシードなので基盤が飛ばす。
