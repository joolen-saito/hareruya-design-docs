## 前提（依頼者の決定であり、指摘対象外）

- **テストがパスしなくてもテストケース（正本の手順・期待結果）とシード表は直さない。** 正本の誤りや矛盾は、直さずに依頼者へ報告する。「正本を直せ」という修正案は出さない（正本の誤りの指摘そのものは歓迎する）。
- テストデータは画面から作る。SQL・フィクスチャで入れない。DB確認は参照だけ。
- 不合格8件（001・002・007・008・011・012・028・073）は結果として受け入れている。うち 012 は「管理者ID 1302」が画面登録では作れないこと、002・008 は実装に「会場」の項目が無いこと、028 は「デイリーイベント」が実装では「定番イベント」であることによる。
- 1巡目の指摘のうち見送ったもの（10 共有シードの完了状態・19 並列化・4 管理者ID 1302）は再提示しない。
- ワーカーは1つ。手元の環境は繰り返し実行でデータが増える（まっさらな専用DBが前提のケースがある）。
- 手順どおりに操作できないが期待結果は確かめられる場合（項目が無くて空にできない、ボタンが無効で押せない、メニューに削除が無い）は、不合格にせず「手順の注記」を残して続ける方針にしている。**この方針が期待結果の確かめを弱めている具体的なケースがあれば指摘せよ**（方針そのものへの一般論は不要）。

## 重点観点

1. **偽の合格**: 各ケースの `expected` の中の確かめが、正本の期待結果の全項目を覆っているか。覆っていない項目、正本より緩い条件（例: 「削除されること」を「ある でないこと」とだけ見ている、遷移先のアドレスの正規表現が別の画面にも合う、操作が実際には行われなくても成り立つ確かめ）を、テストIDと file:line で示せ。
2. **手順の実行**: `step(n)` の中身が正本の手順 n の操作になっているか。別の手順の操作を混ぜている、操作を省いている、開発者ツールの手順（要求の送信・トークンの改変・選択不可の解除）が実装の受け口（ルート・項目名・トークン名）と合っていない箇所。
3. **シードの作り方が正本どおりか**（`seeds/m13-02.ts`）: シード表の状態・属性・投入方法と食い違う値、入れるべき項目の入れ忘れ、「初期表示のまま」とされた項目を変えている箇所、控える番号の取り違え。
4. **画面操作の確かさ**: セレクタ・操作・待ち方が実装（twig・FormType・JS）の事実に合っているか。`force: true` を使っている3箇所（押せない状態のボタン・チェックボックスを押す）が、利用者の操作として妥当か。`expectSaved`・`EventForm.submit` が誤って成功／送信済みと判定しうる箇所。
5. **DB確認**（`db/*.ts`）: SQL が実装のテーブル・カラムの事実に合っているか。削除済みの扱い（論理削除か物理削除か）を取り違えていないか。
6. 1巡目の指摘の反映（`R1_disposition.md` で「反映」としたもの）が、実際にコードで成り立っているか。成り立っていないものだけ挙げよ。

```
### 指摘N（重要度: 高／中／低）

- 修正案: 結論を先に置いた1〜3文（ハーネス側の修正に限る）
```
