# A05-02 注文印刷_該当受注のステータスを印刷済みに変更（開発環境・2026-11-11）

対象: 実施不可でない9件（001・003〜007・010・015・018）と、仕分け直しの5件（002・008・009・016・017）。14件ともテストコードを書いた（流していない）。

## 実ソース（新アプリ）で確かめた作り
- 印刷結果の受信は `POST /api/order/print/direct/{店舗ID}` で、ConnectionType=SetResponse のときだけ ResponseFile（POST ボディ）の XML を読む。ConnectionType が無い・違う値なら 400 で何もしない。
- 印刷結果の printjobid の「_」より前を受注IDとして、ブラウザ印刷フラグが立っていればフラグを倒すだけ、立っていなければ対応状況をピック中・注文確定日を今の日時にする。受注の店舗との照合は無い。
- 外部へは送らない。認証は無い（秘密の値は要らない）。
- 設計書の `/order/prints/status/printed` に当たる経路は無い。

## テストの作り（spec/a05/a05-02.spec.ts・seeds/a05.ts・db/a05.ts・pages/api/a05_print.ts）
- 受注は E2E がその実行で作る: フロントの会員登録で本会員 → グッズ商品CSV登録の商品を本店・EC-CUBE に入庫・承認 → 会員がフロントで注文。
- 画面で指定できない状態だけ、E2E の受注の行に DB で書く（持ち主＝試験会員のメールアドレスを確かめる）: 対応状況「注文受領」・ブラウザ印刷フラグ・注文確定日を未設定・支店の受注（001B）は店舗ID 2・008 の金額1000・税100・付与ポイント50。
- 「開発者ツールから POST」は、同じブラウザの要求の機能で、手順のパス・値をそのまま送る。手順が ConnectionType・店舗IDを書かないケースは付けない。
- 送る printjobid は E2E の受注IDと未登録の 999999 だけ（999999 は DB で未登録を確かめる）。ほかの方の受注には当たらない。

## シードでの解釈
- S-A05-02-ENV: 店舗ID 1（本店）・2（支店）と対応状況「ピック中」があることを DB の参照で確かめる。店舗種別の登録・IP許可リスト（全員が使う設定）は書き換えない。
- 008: 受注ID 520006008・商品ID 205020008・在庫ID 305020008 は指定できないので、画面が振った番号で読み替えた（手順の printjobid も同じ番号）。在庫数7は入庫8・注文1で作る。シード表の「DB で同じ専用IDの受注・商品・在庫を削除」は行わない（印つきの新しい行なので消す相手が無い）。
- 支店の受注（001B）は、支店のフロントで注文する手段が無いので、本店で注文した受注の店舗を DB で店舗ID 2 にした。

## 流したときに出そうなこと（実ソースから。期待結果は変えていない）
- 001〜005・009（`/order/prints/status/printed`）: 経路が無いので更新されず、001〜005 は不合格、009 は状態が200にならない見込み。006・007・008・010 は「更新されない」の期待結果なので、経路が無くても合う見込み。
- 015〜018（`/api/order/print/direct/1`）: 手順に ConnectionType が無いので、アプリは 400 で何もしない見込み（不合格）。
- 002・017: アプリはブラウザ印刷フラグの立った受注のフラグを倒すだけで、対応状況を変えない。経路が合っても、対応状況がピック中にならない見込み。

## 流すときに要るもの
- E2E_DB_WRITE=1。1本だけで流すケースは無い。消すシードは無い（投入方法の「削除」は行わない）。
