# A15-04 他ユーザー情報参照（デッキビルダーの API）— 開発環境での実装の記録（2026-11-14〜）

正本: `integration_test/casegen/cases/A15-04_test_cases.tsv`・`A15-04_seed_data.tsv`。テスト: `spec/a15/a15-04.spec.ts`・`seeds/a15-04.ts`・`db/a15_04.ts`。

## 流せるようにした理由
- これまでは、流せない一覧（`config/sheet_not_runnable.tsv`）に「シードの投入方法が DB への直接の設定」の理由で入っていた（15件）。
- 11/10 の依頼者決定「E2E が作った行だけ DB に書いてよい」に当てはまる：選手（プレイヤー）は、フロントの新規会員登録で E2E が作る。DB に書くのは、その選手の行のニックネーム・プロフィール（005 はポイント残高・DCIナンバー、013 は更新日時）だけ。
- 書き込みは `lib/db_write.ts` を通す。持ち主の確かめは「選手の会員のメールアドレスが、今回登録した実行の印つきの試験会員（@example.test）であること」。
- ほかの方の行・全員が使うマスタには触れない。

## 正本の外の補い（読み替え）
- 会員のメールアドレスは、シード表の値の `@` の前に実行の印を付けた（前の実行の会員と重ならないように）。
- デッキユーザーID・プレイヤーID・顧客IDは、シード表の画面（マイページのマイデッキのリンク・管理画面のデッキ管理のプレイヤー検索・会員一覧）で控える代わりに、登録した会員のメールアドレスで DB を参照して控えた（同じ値）。
- 「デッキユーザーID 1504010Z・1504011Z・1504012Z に一致する選手は0件」は、0件であることを DB の参照で確かめるだけ（あれば止める。消さない）。
- 「ブラウザの開発者ツールで要求を送る」は、ブラウザでユーザー情報参照のアドレス（GET /api/user）を開いて送り、画面に出た応答本体と HTTP ステータスを読む形にした。認証トークンのヘッダが要るケースは、ブラウザに付けて送った。
- 007・015 の「有効な認証トークン」は、その会員のメールアドレスとパスワードでログインの API（POST /api/user/login）を呼んで受け取った（アプリの秘密の値は使わない。トークンの値は記録しない）。
- 005 の「メールアドレス a1504-005-a@example.test が応答に含まれない」は、実行の印つきのメールアドレスと、その前半「a1504-005-a」の両方で確かめた。

## 流す前から分かっていること
- 011 の失敗応答のメッセージは、アプリの英語の文言（`api.deck_builder.user.invalid_request`＝「Invalid request parameters」）。日本語の文言の定めは見当たらない。言語の切り替えで変わるかは、流して確かめる。

## 流した結果
- 2026-11-14 試しに 004 を1件だけ流した（PW_SLOTS=2）: 合格。シード（フロントの会員登録・選手の行へのニックネーム・プロフィールの書き込み）と API の要求が開発環境で通ることを確かめた。
- 残りの15件は昼の列に積んだ（db2）。判定は流したあとで書く。
