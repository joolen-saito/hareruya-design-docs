- **API の入口**：`/api/…` は `/api/v1/…` に読み替えた。
- **ステータスの渡し方**：ケースの文のとおり、URL のクエリパラメータ status で送る。
- **有効なトークン**：手順1の前に、管理者のログイン API で受け取る。
- **店舗**：店舗ID 1・「A06-05 AB試験店舗」は、試験店舗の使い回し（依頼者決定 2026-11-13）で作らず、試験支店に読み替えた。
- **受注の作り方**
  - 試験支店のフロントで、会員登録なしの店頭買取査定申込をして作る。申込者の姓には実行の印を付ける。
  - 現在ステータスは、シード表のとおり、査定担当の管理者（S-A06-05-ADM）でステータス変更画面から変える。
  - 「買取成立」と査定担当者だけは、シード表のとおり DB で書く。書くのは、印つきの E2E の受注の行だけ（db/a06_05.ts の 受注に書く。writeTestData・最大1行）。

## 流す前から分かっていること
アプリのソースを読んだ見立てで、まだ流して確かめていない。
- **ステータスの読み方**：アプリは、ステータスを要求の本文（フォームの値）から読む（`OtcBuyOrderController::updateStatus` の `$request->request->get('status')`）。
  - ケースの文のとおりクエリで送ると、有効なトークンでも「ステータスが不正です」（HTTP 400）になる見込み。ECCUBE_HARERUYA-4345 と同じ型。
  - 200 や状態の変化を期待するケース（001・002・006・029〜034）は、落ちる見込み。
  - 「書き換わらない」を確かめるケース（007・008・009・011・018・035〜038）は、成り立つ見込み。ただ、確かめたい遷移の判定まで進まないことを、判定で扱う必要がある。
- **成功のときの応答**：処理結果コード 200 だけの JSON（{"code":200}）。001 の「レスポンスデータがない」とは違う見込み。
