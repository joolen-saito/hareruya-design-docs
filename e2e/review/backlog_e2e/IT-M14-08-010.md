# 期待される挙動【必須】
- ケースの期待結果は次のとおり。どれも、設計書の現行仕様の節「保存の判定順序」（1 なりすまし対策の検証に失敗→保存せずアクセスを拒否、2 入力の検証に失敗→保存に失敗した旨のメッセージを表示して入力画面を再表示、収録カードは送信されたカードセットIDで取り直し、IDが無いときは空）を出典にしている。
  - 項目表 IT-M14-08-008（E2E のテストID IT-M14-08-010）: 送信したカードセットIDが無いため、収録カードが0件で再表示されること
  - 項目表 IT-M14-08-012（E2E のテストID IT-M14-08-016）: 送信したカードセットIDで収録カードが取り直され、「収録カードA」が表示されること
  - 項目表 IT-M14-08-046（E2E のテストID IT-M14-08-056）: アクセスが拒否され、保存に失敗した旨のメッセージを伴う入力画面の再表示にならないこと
- 一方、設計書の画面項目定義（Excel 由来）は、カードセット名日本語・英語・略称・リリース日を必須とし、「未入力で(21)登録を押下すると、動的に必須入力のエラーメッセージを表示する」と定める。画面で空のまま登録を押したときにブラウザ側で止まるのは設計書どおりで、優先順位（Excel 由来＞現行仕様の節）でもこちらが正。
- ケースの手順は画面の操作だけで、ブラウザの必須チェックを外す操作が無いため、判定順序 1・2 のサーバー側の処理まで要求が届かない。確認したいこと: ケースを次のどちらかに直してよいか。
  - A. 手順に「開発者ツールで必須の指定を外す」操作を足し、サーバー側の判定順序 1・2 を確かめる（IT-M14-08-046 はすでに開発者ツールでトークンを消す手順を持つ）。
  - B. 期待結果を「ブラウザの必須チェックが送信を止め、必須入力のエラーが表示されること」に改める。
