# 再現手順【必須】
1. 開発環境（https://replace-dev.hareruyamtg.com:8443）の管理画面で、商品管理＞売上分析登録/編集を開き、一覧の件数を12000件にして、既存の売上分析タグ（ケースでは「編集前売上分析タグ-033」・並び順10）の「編集」を押す
2. 名称を「トークン欠落更新タグ」に変更する
3. 開発者ツールで、保存用のなりすまし対策トークンの入力要素を削除する
4. 「登録」を押す
5. 保存の要求への応答（HTTPステータス）と、画面上部のメッセージ、名称の入力欄を確認する

# 期待される挙動【必須】
- 設計書の現行仕様の節 保存の判定順序 1「なりすまし対策トークンが有効か」は、無効のとき「アクセス拒否（HTTP 403）とする」と定める。ケースの期待結果（項目表 IT-M03-17-032）も「保存要求への応答がHTTP403となること」。同じ画面の削除の要求は、トークンが無効なら403を返し、項目表 IT-M03-17-034・035 は合格している。
- 保存の要求だけが、トークンが無効なとき403にならない。設計書どおりにするなら、保存の要求でもトークンの検証を入力欄の検証より先に行い、無効なら403にする。

# 現在の挙動【必須】
- 手順4 の保存の要求への応答は200。画面上部に「登録できませんでした。」が出て、見出し「編集」の入力欄に変更後の名称「トークン欠落更新タグ」が残った編集画面が描き直される。403のアクセス拒否にはならない。
- 名称は保存されない（項目表 IT-M03-17-033 は、DBの名称が「編集前売上分析タグ-033」のままで合格）。なりすまし対策としての防御は働いており、違うのは応答のステータスと、描き直される画面だけ。
- 原因は、保存の処理がトークンを入力欄の検証の一部（フォームの検証）として扱うため、トークンが無いと入力の検証の失敗と同じ経路（上の「登録できませんでした。」の画面描き直し）に入ること。削除の処理は、検証のメソッドを直接呼んで403にしている。

# 根拠
- 設計：
  - 現行仕様の節 保存の判定順序 1「なりすまし対策トークンが有効か」: 無効のときはアクセス拒否（HTTP 403）とする: `hareruya-design-docs/excel_to_html/output/0204_基本設計仕様書(商品管理).html:2967`
  - 現行仕様の節 削除の判定順序 1 も同じ（403）。Excel由来の部分・表示メッセージの節にトークン不正の扱いの記述は無い（食い違いは無い）
- ec-cube-enterprise：
  - 保存はトークンを入力欄の検証の一部として扱い、200で描き直す。削除は検証のメソッドで403: `ec-cube-enterprise/src/Eccube/Controller/Admin/Product/TagSalesAnalysisController.php:132-150`、`ec-cube-enterprise/src/Eccube/Controller/Admin/Product/TagSalesAnalysisController.php:225-228`
- ベース実装：
  - pf-eccube3 の保存は、入力欄の検証の前にトークンを確かめ、無効なら403: `pf-eccube3/app/Plugin/HareruyaEc/Controller/Admin/Product/TagSalesAnalysisController.php:52-58`、`pf-eccube3/app/Plugin/HareruyaEc/Controller/FormValidHelper.php:18-23`
  - 探した範囲: pf-eccube3 の売上分析タグのコントローラーと、入力欄の検証の補助（FormValidHelper）
