# 期待される挙動【必須】
- ケースの期待結果は、送信履歴が受注ごとに1件登録され、件名・受注ごとの本文・送信日時・使用したテンプレート・受注・注文者の会員が記録され、「作成者が設定されていないこと」。
- 設計書の業務ロジック「入出力: 永続化」（現行仕様の節）に、「1 通送信するたび。件名・本文・送信日時・使用したテンプレート・受注・注文者の会員を記録し、作成者は設定しない」とある。
- 作成者について書いてあるのはこの1文だけで、Excel 由来の画面項目定義・表示メッセージの節には作成者の記述が無い。設計書の中で食い違う記述は無い。

# 現在の挙動【必須】
- 送信履歴は受注ごとに1件登録され、件名・本文・送信日時・テンプレート（101）・受注・注文者の会員は期待どおりだった。ただし作成者に、操作した管理者のID（100009703）が両方の受注の履歴に記録された（E2E 2026-11-16 の開発環境。判定した15項目のうち不合格は作成者の2項目だけ）。
- アプリの履歴保存の処理は、作成者を自分では渡していない。一方、保存の直前に動く共通の処理（作成者を持つデータを保存するとき、ログイン中の管理者を作成者にする）が、送信履歴にも管理者を入れる。
- ベース実装（現行）も、一括送信の送信履歴は同じ共通の処理を通り、管理者のときに作成者へログイン中の管理者を入れる。つまり現行も作成者は記録される（コードの読みによる。現行の実機では確かめていない）。設計書の現行仕様の記述「作成者は設定しない」は、現行の動きと合っていない。
- 結論: アプリの動きはベース実装（現行踏襲）と同じで、設計書の現行仕様の1文だけが実態と違う見込み。直すのは設計書（「操作した管理者を作成者として記録する」へ）か、作成者を残さない仕様にするのかを決めてから、ケースの期待結果かアプリのどちらかを合わせる。
- 補足: 同じ設計書の会員管理機能にも「手動メールでは作成者の記録は持たない」「操作した管理者は記録しない」という同種の記述がある（0207_基本設計仕様書(会員管理機能).html:1366・2378・3005）。実装の挙動はこの起票では確かめていない。
