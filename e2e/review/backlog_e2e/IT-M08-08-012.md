# 期待される挙動【必須】
- 設計書の現行仕様の節 業務ロジック「送信できないとき」は「なりすまし対策トークンが一致しないときは送信せず、アクセスを拒否する扱い（403）とする」と定め、入出力の失敗時出力も「なりすまし対策トークン不一致は403」とする。ケースの期待結果（項目表 IT-M08-08-011。E2E のテストID IT-M08-08-012）も「応答がHTTP403となること」。
- トークンが不正な要求だけが、403にならない。設計書どおりにするなら、トークンの検証を入力欄の検証より先に行い、不正なら403にする。一方、同じ型の過去の課題は判断が割れている（下の関連）ので、設計書の現行仕様の403の記述を直すか、アプリを403にするかの判断を要する。

# 現在の挙動【必須】
- 手順4 の「確認」の要求への応答は200。確認画面へも403のアクセス拒否にも進まず、選んだテンプレートの件名・本文が入った入力画面が描き直される。画面上部にメッセージは何も出ない（開発モードの警告のみ）。送信は行われない（確認画面に進まないため）。
- 原因は、なりすまし対策トークンを入力欄の検証の一部（フォームの検証）として扱うため、トークンが不正だと入力の検証の失敗と同じ経路（送信せずに同じ画面を描き直す）に入ること。この画面のコントローラーはトークンの検証のメソッド（不正なら403にする）を呼んでいない。画面の入力欄ごとのエラー表示は有るが、フォーム全体のエラー（トークンの不一致はここに入る）を出す記述が無いので、利用者には失敗したことが示されない。
- ベース実装は、送信のたびに、入力欄の検証の前にトークンを確かめ、不正ならアクセス拒否の例外（403）にする。
