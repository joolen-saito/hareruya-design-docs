# 再現手順【必須】
1. （結合試験項目表・E2E とも IT-M03-13-021）開発環境（https://replace-dev.hareruyamtg.com:8443）の管理画面で、商品管理者としてログインし、規格コード TAG-A-001 と TAG-A-002 の商品（削除されておらず、どちらにも同じタグが付いている）を用意する。そのタグの編集画面（/admin/product/tag/<タグID>）を開く。タグには優先表示商品が別のコード1件だけ入っている
2. 「その他の設定」を開き、優先表示商品に、1行目「TAG-A-001」、2行目は空行、3行目「TAG-A-001」、4行目「TAG-A-002」と入力する
3. 登録ボタンを押す（「登録が完了しました。」が出る）
4. このタグの優先表示順（規格コードと順位）を DB で確認する

# 期待される挙動【必須】
- 優先表示順が TAG-A-001 = 2、TAG-A-002 = −1 の2件だけになる（結合試験項目表 IT-M03-13-021 の期待結果）
- 設計書 0204 の現行仕様の節「優先表示の順位」は、優先表示の順位を次のとおり定める。空の行と重複を除いたコードの件数を n、そのコードが入力テキストの何行目にあるか（0 始まり。空行・重複を数えた元の行）を i とすると、順位は n − i。本ケースでは n = 2。TAG-A-001 は 0 行目で 2 − 0 = 2、TAG-A-002 は 3 行目で 2 − 3 = −1

# 現在の挙動【必須】
- 登録は完了するが、優先表示順は TAG-A-001 = 2、TAG-A-002 = 1 の2件になる（1件目は期待どおり、2件目の順位が −1 でなく 1）。件数（2件）・コードの並び・重複と空行の除外は期待どおり。
- 原因は、空行と重複を除いたあとのコードの並びを連番に振り直してから順位を数えていること。TAG-A-002 の位置が元の4行目（i = 3）でなく、除いたあとの2番目（i = 1）になるため、n − i が 1 になる。
- 同じタグの中では、1行目に近いコードほど大きい順位になる関係は変わらない。違うのは順位の値だけ。
- 新アプリのこの処理は、完了済みの ECCUBE_HARERUYA-3817（優先表示商品の複数行が1つのコードになる件）の修正の中で、連番に振り直す形に変えられている（2026-11-05 のコミット「分割後のコード一覧を連番に戻」と、その単体テスト）。3817 には、本ケースが期待する「TAG-A-001 = 2、TAG-A-002 = −1」が記されている。

- 解析結果を「保留」にした理由: 現行（ベース実装）は元の行番号を使うので、空行・重複があると負の順位や欠番が出る。設計書の現行仕様の節はこの挙動をそのまま写した式で、新アプリは意図して連番に直している（連番のほうが妥当という判断かもしれない）。どちらを正とするかは、設計書か実装のどちらを直すかの確認が要る。順位の大小の関係は変わらないので、重要度は P3
- 同じ画面・近い項目の既存の課題（別の原因）: ECCUBE_HARERUYA-3817（完了。優先表示商品に複数行を入力すると1つのコードとして扱われる件。本ケースは、その修正のあとで順位の値だけが残った）／ECCUBE_HARERUYA-3819（未対応。優先表示商品の登録がエラーになったときに、保存前の優先表示順を残すか削除するかの件。取消時の作り直し）
