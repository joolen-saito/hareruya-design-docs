# 期待される挙動【必須】
- 設計書の現行仕様の節 保存の業務ロジックは「なりすまし対策トークンの検証に失敗したときはアクセスを拒否する（403）」と定め、入出力の失敗時出力も「トークン不正は403」とする。ケースの期待結果（項目表 IT-M03-22-018）も「アクセス拒否を示すHTTP 403画面が表示されること」。同じ画面の削除の要求は、トークンが無効なら403を返す（項目表 IT-M03-22-019。E2E のテストID IT-M03-22-023 は合格）。
- 更新の要求だけが、トークンが無効なとき403にならない。設計書どおりにするなら、更新の要求でもトークンの検証を入力欄の検証より先に行い、無効なら403にする。一方、同じ型の過去の課題は判断が割れている（下の関連）ので、設計書の現行仕様の403の記述を直すか、アプリを403にするかの判断を要する。

# 現在の挙動【必須】
- 手順4 の更新の要求への応答は200（登録の要求 200・移った画面 200）。画面上部にはメッセージが何も出ず（開発モードの警告のみ）、見出し「編集」の入力欄に変更後の名称（日）「トークン改ざん更新」が残った編集画面が描き直される。403のアクセス拒否にはならない。
- 原因は、更新の処理がトークンを入力欄の検証の一部（フォームの検証）として扱うため、トークンが不正だと入力の検証の失敗と同じ経路（保存せずに同じ画面を描き直す）に入ること。削除の処理は、検証のメソッドを直接呼んで403にしている。この更新の経路にはエラーメッセージを出す処理も無く、利用者には失敗したことが示されない。
- 保存されるかどうかは、今回の開発環境のケースではDBまで確かめていない（応答のステータスだけを確かめる）。コード上は入力の検証に通らないので保存の処理に入らず、手元の環境の前回（2026-10-20）では、名称（日）が「編集前購入グループ-022」のままだった。
