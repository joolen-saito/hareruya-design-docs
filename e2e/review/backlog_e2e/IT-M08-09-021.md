# 期待される挙動【必須】
- 設計書の画面項目定義は、識別ID 14「配送先住所1」・15「配送先住所2」を、全角・半角・必須・最大文字数90と定める。ケースの期待結果（項目表 IT-M08-09-013）は「入力した各項目が最大文字数の値で更新されること」で、住所1・住所2は全角90文字で更新されると読んでいる。
- ただし、設計書は最大「90」の数え方（文字数か、全角を2・半角を1とする幅か）を書いていない。現行のアプリ（pf-eccube3）は、住所1・住所2を全角2・半角1の幅（Shift-JIS のバイト数）で90までに制限する。このため、全角90文字を保存できるべきかは、設計書だけでは決まらない。設計書に数え方を定めるか、ケースの期待結果を「全角45文字（幅90）」に直すか、全角90文字を許すと決めるかの確認が要る。

# 現在の挙動【必須】
- 「登録」を押すと、配送先住所1・住所2の入力欄に赤いエラー「文字数制限を超えています」が出て、保存されない。配送先の登録内容は、配送先名称「編集前配送先-021」・氏名「配送 太郎」・住所1「千代田区千代田」・住所2「1-1」・会社名「編集前会社」などの更新前のまま変わらない（ほかの項目は入力欄には最大文字数のまま入っていたが、住所のエラーで全体が保存されなかった）。
- 新アプリは、住所1・住所2の長さを「全角を2・半角を1と数えた幅」で見て、上限を設定値の90にしている。全角45文字（幅90）までが通り、46文字目でエラーになる（ソースの読みによる。45文字・46文字そのものの試行は E2E では未実施）。
- ベース実装（pf-eccube3）も、配送先の編集で住所1・住所2を Shift-JIS に変換したバイト数で90（全角45文字）までと判定し、同じ文言「文字数制限を超えています」を出す。新アプリはこの現行の数え方を引き継いでいる。
- 同じ数え方は、フロントの注文の配送先新規登録・変更について ECCUBE_HARERUYA-2989（完了）で現行踏襲の要件として扱われ、影響範囲に管理画面の会員管理が含まれると確認されている。
