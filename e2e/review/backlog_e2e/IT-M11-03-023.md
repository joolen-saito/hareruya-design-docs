1. 開発環境（https://replace-dev.hareruyamtg.com:8443）の管理画面で、ケースの事前準備どおりに、商品登録・編集の画面（/product/product/new）と /product/edit だけを拒否URLに持つ権限を作り、その権限のメンバー（項目表 IT-M11-03-021 のシード S-M11-03-VIEW-ONLY-023。E2E のテストID IT-M11-03-023）を作る

# 期待される挙動【必須】
- ケースの期待結果（項目表 IT-M11-03-021）は「商品登録・編集権限を保持していなくても商品管理閲覧画面が表示されること」。出典は設計書の「権限制御」シートの機能仕様 1-2（拒否URLに登録された遷移先だけアクセス不可）と 2-3（編集権限が無くても、1-2 でアクセスできる画面は参照できる）。
- 設計書（Excel 由来・現行仕様の節とも）は、商品管理の閲覧画面のアドレスを「/product/list」と定めていない。権限URLマスターの例として書かれているのは「大カテゴリ：承認権限、権限名：承認権限、URL：/approval_authority」の1件だけ。「商品管理閲覧画面」という名前も設計書に無い。
- つまり「/product/list」は、ケースとシードの側が置いた値である。設計書の趣旨（編集権限の無いメンバーが、拒否されていない商品管理の画面を表示できる）を確かめるには、新しいアプリで実在する商品一覧のアドレス「/product」を使う（「/product/edit」も新しいアプリに無く、実在する編集画面は「/product/product/{id}/edit」）。
- 決めてほしいこと（ケース側の直し）。
  - ケース・シード表の「商品管理閲覧画面」のアドレスを /product に直す（あわせて、許可を「/product/list」と書いている部分は、拒否URL方式（拒否に登録されていなければアクセスできる）に合わせて「拒否に含めない」と書き直す）。拒否側の「/product/edit」も、実在する編集画面のアドレス（/product/product/{商品ID}/edit）に合わせて直す。
  - 同じアドレスを使う項目表 IT-M11-03-025（E2E の IT-M11-03-034）・IT-M11-03-026（IT-M11-03-035）も、「表示されない」が拒否によるのか画面が無いからなのか区別できない（両方とも条件付きで合格にしている）ので、同時に直す。

# 現在の挙動【必須】
- 手順3 で「/product/list」を開くと、「404 Page Not Found お探しのページが見つかりません。」が表示される（応答404）。ログイン画面へは移らず、ログインは成功している（手順2 のあとの画面は管理画面）。
- 期待した「応答が成功」にならないので、項目表のケースは不合格になった。拒否の設定の効き方（権限制御）の問題ではなく、開く先の画面がアプリに無いことによる。
- 新しいアプリの商品一覧のアドレスは「/product」。別のケース（E2E の IT-M11-03-034）で、拒否URLに「/product」だけを入れた権限のメンバーが「/product」を開くと403で拒否されることを参考に確かめている（実在の画面なので、拒否の効果として読める）。
- 新しいアプリにも、ベース実装（pf-eccube3）にも「/product/list」の画面・ルートは無い。新しいアプリの初期データ（baseline）の権限URLのマスターも「承認権限」の1件だけで、商品管理の閲覧画面を表す行は無い。

# 根拠
- 設計：
  - 機能仕様 1-2「画面遷移時に、権限判定データに登録されているURLを参照して、遷移先のURLが登録されている場合アクセス不可とする」・2-3「編集権限を保持していない場合でも、1-2の判定にてアクセス可能な場合、画面参照を可能とする」（商品管理の閲覧画面のアドレスは定めていない）: `hareruya-design-docs/excel_to_html/output/0201_基本設計仕様書(システム設定).html:1476`、`hareruya-design-docs/excel_to_html/output/0201_基本設計仕様書(システム設定).html:1482`
