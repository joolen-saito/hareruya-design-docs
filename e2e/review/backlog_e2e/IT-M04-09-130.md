# 期待される挙動【必須】
- ケースの期待結果（項目表 IT-M04-09-100。E2E のテストID IT-M04-09-130）は「入庫先に在庫移動(加算)の履歴が1件登録され、変更前在庫5から変更後在庫8、増減数+3、仕入総価格300、変更前総原価500から変更後総原価800、履歴登録元IDが在庫移動・振替ID、理由に『在庫移動による加算』『出庫元の店舗名から入庫先の店舗名』と在庫移動・振替IDが含まれること」。
- ケースのシード表（M04-09 の S-M04-09-APP-B）は、入庫担当者の用途を「入庫承認申請と入庫承認」とし、同じ入庫担当者が申請と承認の両方を行う前提で書かれている。ケース ① は「対象データの登録者ではない」と書くだけで、申請者が承認者と別であることは求めていない。
- 設計書の移動の入庫承認画面は、承認ボタンの押下で在庫・原価・履歴を更新すると定め、承認できる者を申請者以外に限る記述は無い（振替の承認には「ログインしているメンバーが在庫振替の登録者」ならエラーとする記述がある）。
- 一方、完了済みの ECCUBE_HARERUYA-3598 は「入庫承認申請をした本人が承認できてしまう」を不具合として起票し、期待を「承認権限が無いとして承認が行えない」とした。アプリはこの期待どおり、申請者本人の承認を拒む。
- したがって、このケースの期待は、シード表の前提（申請者＝承認者）か、3598 で決めた挙動のどちらかを直さなければ満たせない。どちらを正とするか決める（シード表を「入庫承認申請は別の管理者が行う」に直すか、設計書に申請者本人の承認の扱いを書く）。

# 現在の挙動【必須】
- 入庫承認画面で「承認」を押すと、画面上部に「承認権限がありません。」が出て入庫承認画面に戻り、ステータスは入庫承認待ちのまま（キャプチャ。実施は 2026-11-16、開発環境）。承認されないので、入庫先に在庫移動(加算)の履歴は付かず、在庫・総原価も変わらない（E2E の確認では入庫先の履歴の増えた件数が 0）。
- ステータス変更履歴の最後（入庫承認待ち）の更新者が、承認を押した入庫担当者本人である。
- 原因は、入庫承認の処理が、承認する管理者と更新者（入庫承認申請を行った管理者）が同一のとき、承認を拒むこと。承認の確認の段階（承認権限の確認）と処理の中の両方に同じ確認がある。承認が通れば、入庫先の履歴の理由は「在庫移動による加算 出庫元の店舗名から入庫先の店舗名 在庫移動振替ID：<ID>」で作られる（アプリの実装の確認。このケースでは承認が通らず確かめていない）。
- 比較：移動の出庫承認の拒否は、更新者でなく登録者（`getRegisteredMember()`）を基準にしている。入庫承認だけが更新者（申請者）を基準にしている。
