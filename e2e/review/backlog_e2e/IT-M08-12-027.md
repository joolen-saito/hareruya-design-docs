# 再現手順【必須】
1. 開発環境（https://replace-dev.hareruyamtg.com:8443）の管理画面で、会員管理の顧客グループ管理を開く
2. 登録の場合: 新規追加の状態で名称に「トークン不正追加」、ポイント還元率に10を入力する。更新の場合: 既存の顧客グループの編集状態を開き、名称を「トークン不正更新」に変える
3. 開発者ツールで、画面のなりすまし対策トークンの値を「invalid-token」に書き換える
4. 登録ボタンを押す
5. 登録（更新）要求への応答（HTTPステータス）と、戻ってきた画面の様子を確認する

# 期待される挙動【必須】
- 設計書の現行仕様の節 業務ロジック「登録・更新・削除の判定」は「登録・更新・削除 / なりすまし対策トークンの検証に失敗したとき / 保存も削除も行わず、アクセスを拒否する（403）」と定める。ケースの期待結果（項目表 IT-M08-12-020・IT-M08-12-022。E2E のテストID IT-M08-12-027・029）も「登録（更新）要求のHTTP応答ステータスが403となること」。
- 登録と更新だけが、トークン不正で403にならない（削除は403になる）。設計書どおりにするなら、登録・更新でもトークンの検証を入力欄の検証より先に行い、不正なら403にする。一方、同じ型の過去の課題は判断が割れている（下の関連）ので、設計書の現行仕様の403の記述を直すか、アプリを403にするかの判断を要する。

# 現在の挙動【必須】
- 手順4 の要求への応答は200。403のアクセス拒否にも保存にも進まず、顧客グループ管理画面（一覧つき）が描き直される。顧客グループは追加・更新されない（一覧に増えない）。画面上部には開発モードの警告のみで、失敗を示すメッセージは出ない。登録（027）・更新（029）とも同じ結果。
- 原因は、なりすまし対策トークンを入力欄の検証の一部（フォームの検証）として扱うため、トークンが不正だと入力の検証の失敗と同じ経路（保存せず同じ画面を描き直す）に入ること。この画面のコントローラーは、登録・更新でトークンの検証のメソッド（不正なら403にする）を呼ばない。削除だけは呼んでいる。画面にはフォーム全体のエラー（トークンの不一致はここに入る）を出す記述が無い。
- ベース実装は、登録・更新のたびに入力欄の検証の前にトークンを確かめ、不正ならアクセス拒否の例外（403）にする。

# 根拠
- 設計：
  - 現行仕様の節 業務ロジック「登録・更新・削除の判定」「登録・更新・削除 / なりすまし対策トークンの検証に失敗したとき / 保存も削除も行わず、アクセスを拒否する（403）」: `hareruya-design-docs/excel_to_html/output/0207_基本設計仕様書(会員管理機能).html:2817`
  - Excel 由来の部分（顧客グループ管理シート）・表示メッセージの節にトークン不正の扱いの記述は無い（食い違いは無い）
- ec-cube-enterprise：
  - 登録・更新はトークンを入力欄の検証の一部として扱い、不正でも200で描き直す: `ec-cube-enterprise/src/Eccube/Controller/Admin/Customer/CustomerGroupController.php:70-73`、`ec-cube-enterprise/src/Eccube/Controller/AbstractController.php:252-263`
- ベース実装：
  - pf-eccube3 は更新で入力欄の検証の前にトークンを確かめ403: `pf-eccube3/app/Plugin/HareruyaEc/Controller/Admin/CustomerGroupController.php:49-51`、`pf-eccube3/app/Plugin/HareruyaEc/Controller/FormValidHelper.php:10-14`
  - 探した範囲: pf-eccube3 の顧客グループ管理のコントローラーと、入力欄の検証の補助（FormValidHelper）。なお pf-eccube3 の更新は、登録・更新とも同じメソッドで扱われる
