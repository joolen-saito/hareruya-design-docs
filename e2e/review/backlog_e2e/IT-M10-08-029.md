# 再現手順【必須】
1. 開発環境（https://replace-dev.hareruyamtg.com:8443）の管理画面で、自動送信メール（基本情報設定）を開く
2. テンプレ選択で自動送信メールのテンプレート（「B自動テンプレート」）を選ぶ
3. 開発者ツールで、画面のなりすまし対策トークンの値を「invalid-token」に書き換える
4. 設定ボタンを押す
5. 要求への応答（HTTPステータス）と、戻ってきた画面の様子を確認する

# 期待される挙動【必須】
- 設計書の現行仕様の節 業務ロジック「保存の判定順序」は、順序1を「なりすまし対策トークン／不正なときは保存せず、アクセス拒否とする」と定める（入出力の失敗時出力にも「アクセス拒否」）。ケースの期待結果（項目表 IT-M10-08-027。E2E のテストID IT-M10-08-029）も「編集結果ではなく、アクセス拒否の応答が表示されること」（403）。
- 設計書どおりにするなら、トークンの検証を入力内容の検証より先に行い、不正なら403にする。一方、同じ型の過去の課題は判断が割れている（下の関連）ので、現行仕様の記述を直すか、アプリを403にするかの判断を要する。

# 現在の挙動【必須】
- 手順4 の要求への応答は200。403のアクセス拒否にも保存にも進まず、選んだテンプレートの編集画面が描き直される（最終更新日は更新前のまま）。画面上部には開発モードの警告のみで、失敗を示すメッセージは出ない。
- 原因は、なりすまし対策トークンを入力欄の検証の一部（フォームの検証）として扱うため、トークンが不正だと入力の検証の失敗と同じ経路（保存せず同じ画面を描き直す）に入ること。このコントローラーは、トークンの検証のメソッド（不正なら403にする）を呼ばない。画面にもフォーム全体のエラー（トークンの不一致はここに入る）を出す記述が無い。
- ベース実装は、保存のたびに入力欄の検証の前にトークンを確かめ、不正ならアクセス拒否の例外（403）にする。

ec-cube-enterprise 保存は入力欄の検証が通ったときだけ行い、通らなければ同じ画面を描き直す（トークンの検証のメソッドは呼ばない）: `ec-cube-enterprise/src/Eccube/Controller/Admin/Mall/MallAutoMailController.php:99-103`

# 根拠
- 設計：
  - 現行仕様の節 業務ロジック「保存の判定順序」「1 なりすまし対策トークン／不正なときは保存せず、アクセス拒否とする」: `hareruya-design-docs/excel_to_html/output/0209_基本設計仕様書(基本情報設定).html:1826`
  - Excel 由来の画面項目定義・表示メッセージの節にトークン不正の扱いの記述は無い（食い違いは無い）
- ec-cube-enterprise：
  - トークンを入力欄の検証の一部として扱い、不正でも200で描き直す: `ec-cube-enterprise/src/Eccube/Controller/Admin/Mall/MallAutoMailController.php:99-103`、`ec-cube-enterprise/src/Eccube/Controller/AbstractController.php:252-263`
- ベース実装：
  - pf-eccube3 は入力欄の検証の前にトークンを確かめ403: `pf-eccube3/app/Plugin/HareruyaEc/Controller/FormValidHelper.php:10-14`
  - 探した範囲: pf-eccube3 の自動送信メールのコントローラー（autoSendMail）と、入力欄の検証の補助（FormValidHelper）
