# A05-03 店頭注文番号取得（開発環境・2026-11-11）

対象: 実施不可でない3件（003・005・009）と、仕分け直しの10件。テストコードを書いたのは 003・005・009 の3件（流していない）。

## 実ソース（新アプリ）で確かめた作り
- 店頭注文番号の取得は `GET /waiting_api/get_waiting_number/{店舗ID}`（認証なし）。手順の `/waiting_api/get_waiting/…` に当たる経路は無い。
- 応答は、その店舗のピック済み受注の店頭注文番号と、店頭注文番号札管理で登録した番号札（登録の順）の JSON 配列。合計が画面表示最大件数（アプリの設定）を超えると、間の販売完了の番号も入れる。
- 店頭注文番号一覧ページ（/waiting_number）は、自分の店舗の店舗IDで要求する作り。

## シードでの解釈
- 試験店舗の登録の値はシード表どおり（会社名・店名・カナ・英語表記・支店URL・略称・郵便番号・住所・電話番号）。メールアドレス・表示順・公開・開店・売上集計の検索項目は店舗登録の部品の既定のまま。
- 003 の「CHAINA があれば削除ボタンで削除」: 前の実行でこの試験店舗に登録した番号札を、開始前に DB で消して0件に戻す（その店舗は E2E だけが使う。持ち主＝店名・会社名を確かめる）。
- S-A05-03-ADM: ログインID・名前に実行の印。権限はシステム管理者、所属店舗・既定の検索店舗・編集可能店舗は試験店舗（連鎖試験店）。
- S-A05-03-ENV（IP制限）: 全員が使う環境の設定なので書き換えない。

## 流したときに出そうなこと（実ソースから。期待結果は変えていない）
- 003・005: 手順の経路（/waiting_api/get_waiting/{店舗ID}）が無く、404 になる見込み（不合格）。
- 009: 404 の画面になり、注文番号の配列は含まれない見込み（期待結果どおり）。

## 流すときに要るもの
- E2E_DB_WRITE=1（003 の番号札の後始末）。消すシードの仕分けが要る: S-A05-03-CHAIN-003（その実行より前に E2E が試験店舗に登録した番号札だけを消す）。1本だけで流すケースは無い。
- 試験店舗が2店（決まった名前で1度だけ）増える。
