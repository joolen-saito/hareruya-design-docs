## 2. 守ること（依頼者の指示。例外なし）

- **テストがパスしなくても、テストケースを直さない。** 正本は `integration_test/casegen/cases/*_test_cases.tsv` と `*_seed_data.tsv`。直してよいのは `e2e/` の中（セレクタ・待ち方・シードの画面操作の実装）だけ。正本の誤りや矛盾は、直さずに報告する。
  - **例外（依頼者決定 2026-10-16）: 設計書が画面と合っていて、ケースの手順だけが誤っているときは、手順を直す。** 期待結果は直さない。設計書が操作の結果を定めず、画面と合っているとも言えないとき（M03-01 の031）や、設計書と画面が食い違うとき（M13-02 の045 など）は直さない。
  - 直し方は、`integration_test/casegen/datapattern/conflicts/rulings.tsv` に裁定の行（項目は `E01` から順に、根拠に設計書の行番号）を足して `python3 integration_test/casegen/datapattern/conflicts/apply_rulings.py` を流す。基線のケースは `precond/step_changes/` に「裁定訂正」として宣言される。そのあと `build_all_test_cases.py` と `precond/gate_precond.py --all` を流す。`cases/` を直接は書き換えない（流し直しで戻る）。
- **期待結果を弱めない。** 実装に合わせて確かめを緩めない。落ちたら、それが結果である。
- **手順が画面で実行できないとき**（項目が無い、ボタンが押せない など）の扱い：
  - 期待結果が DB などで確かめられるなら、手順に注記を残して続ける。
  - 期待結果が「遷移すること」など操作の結果を見るものなら、不合格にする。操作をせずに元の画面を見て合格にしない（2巡目のレビューで、この偽の合格を4件指摘された）。
- **テストデータは画面から作る。** SQL やフィクスチャで入れない。DB は確かめのための参照（SELECT）だけ。
- **資格情報・パスワードをコミットしない。** 開発環境の資格情報は環境変数で渡す。
- **コミット・プッシュは、依頼者の指示があるまで行わない。** `git add`・`git commit`・`git push` を自分の判断で実行しない。プッシュ済みの履歴を強制プッシュで書き換えない。
- **Playwright を2本同時に流さない。** `test-results` を取り合って結果が壊れる。調査用の実行も、前の実行が終わってから。
- **論理名の規約**：テスト・報告・コメントには業務上の名前を書く。物理名（テーブル名・カラム名・ルート名など）は、セレクタ・HTTP のパス・SQL の中にだけ書く（`.cursor/skills/logical-naming/SKILL.md`）。
- **開発環境（共有）では、依頼者の了承なしに流さない。** 他の人のデータを消すシードを持つケースは、共有環境では実行しない作りにしてある。

書き方の決まりは `e2e/README.md` にある。要点は次のとおり。

- テストIDで正本を引く。手順・期待結果の文はコードに写さない。
- 正本の手順を順にすべて実行し、そのあとで期待結果を確かめる。
- `caseTest("IT-…", 関数(…))` の形で、テストIDは必ずその場に文字列で書く。
- 期待結果に確かめる項目が複数あるときは `expect.soft` を使う。
- `npm run coverage` は、テストIDの二重定義・正本に無いID・中身が空の手順・確かめの無い期待結果を誤りとして止める。
