# 敵対レビュー規約

## 目的

設計書・テストケース・オラクルなど、根拠が実ソースにある成果物からハルシネーションを落とす。著者は自分の誤りを見つけられないため、独立したレビュアーに当てる。

## 担当

| 巡 | 担当 | 範囲 | 必須 |
| --- | --- | --- | --- |
| 1 巡目 | codex | 制限なし。10〜20本まとめて可 | 必須 |
| 2 巡目 | fable5 | **1回あたり 1〜3 本** | 推奨 |

**巡回数の上限は3巡。両レビュアーは並行で起動する**（2026-08-18 導入）。起動は
`scripts/run_review_round.sh <レビューディレクトリ> <走査ルート> [対象設計書...]` を使う。
上限に達したら、残る指摘は却下理由とともに carryover へ書いてレビューを閉じる。

著者とレビュアーは必ず別にする。著者が自分でレビューしたことにしない。

## 使い分けの根拠

2026-08-17 に受注管理機能の詳細設計 19 本で両方を回した実測。

**codex が強い**

- 参照の行番号ずれ、スコープ違反、断定の裏取り、網羅性の確認。
- 安定して完走する。M05-01 で 7 巡＋最終確認、17 本を 2 系統に分けた回、いずれも完走。
- 収束する。指摘 18→12→9→4→4→4→NONE。

**逐次で回し続けてはいけない（2026-08-18 実測）**

M05-01 検索結果で codex を10巡した結果、**合計233万トークン・1巡あたり約23万トークン**を使った。
指摘が1件だった R8 も 23.4万トークンかかっている。**コストは指摘数と無関係に一定**で、
巡ごとに走査をやり直すためである。指摘の推移は 7→9→4→4→4→4→4→1→2→2 で、
事実の誤りは R6 で尽き、R7 以降は再提示とスコープ論だけだった。fable5 は1本で17分かかった。

打ち切り条件は次のいずれか。ひとつでも満たしたら閉じる。

- 出力が `NONE`
- 3巡に達した
- その巡の指摘が、再提示・スコープ論・実装手段だけで、新規の事実指摘がゼロ

**codex が弱い**

- 巡ごとに指摘がぶれる。同じ箇所を「追記せよ」→「その追記は誤り」、「確認不能と書け」→「断定せよ」と反転した実績がある。
- 指摘量が多く、事実の欠落が半数近くを占める。記載方針との衝突は人が捌く必要がある。

**fable5 が強い**

- コードの層をまたぐ意味の取り違えを拾う。codex が 7 巡で一度も気づかなかった「注文者の電話番号とフリガナだけ入力値が変換され、配送先側は変換されない」という非対称を検出した。
- 1 回の指摘数は少ないが、当たりの密度が高い。

**fable5 が弱い**

- 範囲が広いと完走しない。17 本をまとめて渡したところ 10 分間応答が止まって停止した。だから 1〜3 本に絞る。

## 手順

### 1. レビュー観点をファイルに書く

正本（オラクル）の絶対パス、正本でないもの、成果物の制約、重点観点、出力形式を書く。両レビュアーへ同じファイルを渡すと突き合わせやすい。

出力形式は「指摘が無ければ `NONE` の 1 語」と決める。指摘ごとに `主張 / 実際（file:line）/ 判定 / 修正案` を書かせる。

**不機能仕様の台帳 `functions/dead-spec-register.tsv` のパスを観点ファイルに書き、「登録済みのものは意図的に書いていないので指摘対象外」と明記する。** これを書かないと、意図的な除外を毎回「事実の欠落」として指摘され続ける。

**同じ理由で、設計書に書かないと決めた種類も観点ファイルへ明記する。** 現時点の除外は次の2つ（`reverse-design/GRANULARITY.md` 3.6）。

- 乖離は I/O とふるまいに限る。通信方式・認可設定・受付先など実装手段の差は書かない。
- 結論を先に置く。接続詞で文を始めない／意図や目的を説明しない／一文に結論を複数積まない（`reverse-design/GRANULARITY.md` 3.8）。指摘の修正案もこの形で書かせる。
- 画面操作に依存する記述は書かない（同 0b）。押す・選ぶ・別タブ・描画順・スクロールの追加を求める指摘は出さない。
- ページャとセッション・Cookie の節は作らない（同 3.7b）。
- 永続化節はDBの永続化だけを書く。ログ出力とイベント・通知の発行は設計書に書かない（同 3.7）。これを書かないと「ログ出力が抜けている」と指摘され続ける（実例: M05-01 検索結果で R2・R3 の2巡）。
- 乖離節に Excel の画面項目に関する内容を書かない。
- Excel設計書だけに在るもの（現行に実装が無いもの）を書かない。

これを書かないと「Excel専用の仕様が抜けている」と毎巡指摘され、収束しない。実例: M05-01 検索結果で codex が R1・R9・R10 の3巡にわたり同じ追加を要求した。

### 2. codex を回す

```bash
codex exec --sandbox read-only --cd <走査したいルート> "$(cat prompt.md)" < /dev/null > out.txt 2>&1
```

- `< /dev/null` を必ず付ける。**stdin が開いたままだと codex が追加入力を待ち続けて止まる。**
  なお `Reading additional input from stdin...` は起動時に必ず出る行で、これ自体は異常ではない。完了したかどうかは出力末尾の `tokens used` の有無で判断する。
- `--cd` は正本リポジトリを含む親を指定する。設計書リポジトリの外に実ソースがある構成では必須。
- 複数系統を並行させてよい。ただし `pkill -f "codex exec"` は**自分の親シェルにもマッチして自滅する**ので使わない。止めるときは PID 指定。

### 3. fable5 を回す

Agent ツール（`subagent_type: "claude"`, `model: "fable"`）。観点ファイルのパスを渡して読ませる。**対象は 1〜3 本まで。**

### 4. 指摘を捌く

- **そのまま反映しない。** 1 件ずつ実ソースで確認してから直す。両レビュアーとも誤指摘を出す。
- 判定が「事実の誤り」「文言の捏造」「論理名の捏造」のものは、確認のうえ必ず直す。
- 判定が「事実の欠落」でも、**全部は直さない**。レビューを重ねるほど設計書が細かくなる原因がここにある（2026-08-18）。直すのは**この機能のI/Oかふるまいに直接効くもの**だけで、次は却下して carryover へ記録する。
  - 他機能の設計書が担当する処理内容（例: スタック用紙印刷の更新条件は M05-08、納品書の国内外の振り分けは M05-13/14）
  - 実装手段・内部配線（通信方式・認可設定・受付先・イベント発行・ログ出力・呼び出し順）
  - 基準機能が書いていない種類の内容。基準機能に無いものは、この設計書にも要らない
  - 不機能仕様の台帳に登録済みのもの
  実装を末端まで読むこと自体はやめない。読んだうえで、どこに書くかを決める。
- 欠落が出たら、指摘箇所だけ直して終わりにしない。**同じ機能の実装を末端まで読み直す。** レビュアーが見つけていない同種の欠落が残っている。2026-08-17 に、コントローラ層で読み止めたことが事実の誤り16件と欠落22件の共通原因だった。
- 反映後にもう一度回し、`NONE` になるまで繰り返す。

## 落とし穴

- **文言は翻訳キーのまま書かない。** キーを見て日本語を推測すると捏造になる。翻訳ファイルの値かコード上のリテラルで実在を確認する。2026-08-17 に 3 件の捏造を出した。
- **共用の文言に注意。** あるキーが別機能の文言を指していることがある。受注のCSV出力で「1つ以上のデッキを選択してください。」が出る実例がある。
- レビュー前の成果物を完成として報告しない。未レビューであることを明示する。
