# リバース詳細設計書 — 詳細ルール（参照用）

このファイルは Skill 本体を短く保つための補足。作成・レビュー時に必要なら開く。

## 守るべき原則

1. リバース設計であること — 既存実装のふるまい、状態、参照データ、判定境界、永続化、副作用を確認し、仕様の確からしさを把握することが目的。クラス名やメソッド名の列挙で代替しない。
2. HTTP 起点の明示 — 「利用者視点の入口」に HTTP メソッドとサイトルートからのパスパターンと期待されるふるまいを実装どおり書く。管理画面プレフィックスは `%eccube_admin_route%`・`{admin_route}` など設計書の前提に合わせ、`eccube.yaml`・`path.yml`・環境変数のどれ由来かが読み取れるように一文で書く。ルート bind 名や Symfony のルート name は本文で網羅せず grep 用なら「調査補助」へ隔離する。Controller クラス名やメソッド名を本文の主説明として列挙しない。
3. スコープの明示 — 「本書で扱うこと」「本書で扱わないこと」を冒頭で分ける。扱わないものは「実装または別機能の設計を正とする」と明記する。
4. 移行・現行値の分離 — 対象機能が移行対象のときは、「移行時に保証するふるまい」と「現行実装の確認値」を分ける。Cookie 名・セッションキー名・保存形式は仕様として固定せず確認値として書く（名称の照合はソースを見る旨を書く）。
5. 秘匿情報の禁止 — パスワード、なりすまし対策トークン、Cookie 値、セッション ID の完全値、Remember Me トークンの原値などを設計書本文やログ例に書かない。DB のパスワード列は「不可逆値として扱う」「原値を書かない」とだけ書く。
6. フレームワーク境界 — CSRF の生成・保管、パスワードハッシュ方式などはフレームワーク／インフラの管理範囲として「業務データとして扱わない」とできる。
7. 否定の明示 — 楽観／悲観ロックが無い、同時ログイン制御が対象外など、「ない」場合も節や箇条書きで明示する。
8. 装飾の抑止 — 本文・表セル・箇条書きで Markdown の太字（`**` や `__`）や HTML の strong を使わない。強調は章立てと表の粒度で示す。
9. 半角空白の抑制 — 和文では語と語のあいだに読みやすさ目的の半角空白を入れない。インラインコード・英数字・記号トークンの直後に続く助詞・助動詞の直前にも半角空白を入れない（詳細は [SKILL.md](SKILL.md) の表現ルール）。コードフェンス内・URL・パス・カンマ列挙など ASCII の構文に必要な空白は許容する。
10. 実装シンボルと論理名 — PHP のクラス・例外・Doctrine エンティティ短名（例: `AccessDeniedHttpException`、`MtbOption`、`Member`、`BaseInfo`）は、本文・表の主説明では業務上の論理名に置き換える。フレームワーク部品は「電話番号3分割用フォーム種別の送信後段」「CSRF 不正時のアクセス拒否」などと述べる。テーブル・列（`dtb_member`）、設定キー、フォームのキー文字列、Twig 変数名が仕様の境界そのもののときは照合用として残してよい。詳細は [SKILL.md](SKILL.md) の「表現ルール」を正とする。

## 章構成（必須 / 任意）

### 必須

| 章 | 書くこと | 書かないこと |
|----|----------|----------------|
| 概要 | 機能の目的、リバース設計であること、対象チャネル（例: ブラウザ管理画面）、管理画面プレフィックスの決まり方の一文、「利用者視点の入口」でパスを書く旨 | Controller メソッドの列挙による代替、本文での Markdown 太字・HTML strong |
| 本書で扱うこと | 箇条書きで範囲 | 実装手順のステップ番号だけの列挙 |
| 本書で扱わないこと | 別紙・実装正とする範囲 | 仕様を断定できないことの断定 |
| 用語 | 表形式「用語 / 説明」。定義文は論理名を先にし、PHP クラス短名は必要最小限または「調査補助」へ | 用語説明がクラス名・FQCN の一覧になっていること |
| 利用者視点の入口 | 表「入口 / URLエンドポイント / 期待されるふるまい」。ナビや操作の境界。各入口に HTTP メソッドとサイトルートからのパスパターン（管理画面は `%eccube_admin_route%` または設計対象に合わせ `{admin_route}`。ホスト・クエリ・資格情報を含む具体 URL は書かない）。処理フロー・画面遷移と実装照合のうえ整合させる | ルート bind 名だけの列挙、本節のみで網羅し処理フローと矛盾、ホスト付き URL |
| フロント挙動 | 表示要素、JS、CSS、モーダル、表示切替の有無。フォーム中心機能では入力項目を画面ラベルで列挙。textarea は種別を明記。ラジオ・トグルは設問ごとに選択肢と保存値を具体化 | CSS クラス名の全量転載 |
| 処理フロー | サブ見出し単位で番号付きフロー | クラスメソッド単位の疑似コード |
| 業務ルール・計算 | 対象データ、除外条件、集計単位、丸め、画面表示値との対応。入力フォームがある機能では `### 入力項目` に5列固定の表を置く（項目名は画面ラベルのみ、必須／任意、最大長、初期値、保存先・扱い）。フォームキー・論理キー・型名は保存先・扱い列に書く。体裁は `m10-06_admin_base_setting_setting_shop_delivery.md` の「### 入力項目」を正とする。最大長は文字数・桁数の具体値（例: 50 文字）を書き、根拠は `constant.yml.dist` 等の確認値とし環境上書きを注記。見出し直後は表のみ、補足は表の後。類似項目は束ねず行を分ける | ソースコードの式全文、`ルール・その他` 列や `入力種別` 列を別立てした6列以上の入力表、項目名列へのキー括弧付け |
| データ整合性 | 参照時点、一致を保証する範囲、保証しない範囲 | 推測した整合性保証 |
| API/バッチ結果 | API やバッチの入力、実行条件、成功結果、失敗結果、再実行時の扱い | 認証トークンや秘密値の具体例 |
| 入出力 | 表「種類 / 内容」（入力・成功・失敗・副作用） | リクエストボディのフィールド名だけの仕様書 |
| DBカラム | 当機能に直接関係する列のみ。型の細部はスキーマ参照と書く。束ね語にせず、画面項目と列の対応が追える粒度で書く | 全カラム転載、秘密値の例 |
| バリデーション | 項目ごとのルール、フレームワークとの境界（例: ログインが認証失敗として扱われる等）。メール・コード列など複数ある場合は項目名を揃えて個別行に分ける | バリデータクラス名の列挙のみ |
| 権限・認可 | 利用者状態 × リソース可否の表 | `@IsGranted` の列挙だけ |
| 画面遷移 | 表「条件 / 遷移先」（抽象的な遷移先でよい）。パスの細部は「利用者視点の入口」と分担 | 「利用者視点の入口」と同じパスの無意味な繰り返しだけで済ますこと |
| エラー処理 | 表「エラー内容 / 処理」 | スタックトレース例 |
| ログ・監査 | タイミングと記録内容の表、「ログに出してはいけないもの」サブ節 | トークンや Cookie の値 |

### 任意（機能に応じて）

| 章 | 使うとき |
|----|-----------|
| リニューアル移行時の扱い | Cookie・セッション・Remember Me 等、移行で名称が揺れるとき |
| 集計条件 | 件数・合計・一覧対象の抽出があり、条件や単位を独立して示したいとき |
| ○○時の判定順序 | 複数条件が順序依存するとき（認証・決済・同時実行など） |
| 表示メッセージ | ログイン・フォーム送信・一覧操作結果など、利用者向けの画面文言（正常・インラインエラー・フラッシュ）があるとき。判定順序の直後に置くと条件と対応しやすい |
| 試行制限 | レートリミット・ロックアウトがあるとき |
| セッション | セッションキーと用途・移行時の確認観点があるとき |
| Cookie | セッション Cookie・Remember Me の属性や環境変数由来の確認値があるとき |
| 排他制御・トランザクション | ロックや_tx境界がある／ないことを明示するとき |

判定順序がある機能では、認証系と同様に「画面上は失敗理由を区別しない／内部はログ・履歴で扱う」を検討する。

表示メッセージとエラー処理の分担 — 利用者が読む文言（日本語、英語ロケール対応がある機能では英語も併記）と表示条件は「表示メッセージ」節の表に集約する。エラー処理節はログイン画面に戻す、認証しない、例外として扱うなどの処理方針を書き、必要なら表示メッセージ節への参照列を足す。ロケールキーは調査補助に留める。体裁の参照例は `functions/ec-cube-enterprise/m01-01_admin_login_login.md` の「表示メッセージ」節。

## 書き方のコツ

- 半角空白を本文に挟まない — 設計書の本文・表・箇条書きでは、和文と助詞のあいだに読みやすさ目的の半角空白を入れず、英数字やインラインコードの直後に続く「を・の・で・と」などの直前にも入れない（SKILL の表現ルール・REFERENCE の原則 9）。コード・URL・パス・カンマ列挙に必要な空白だけ残す。
- 表を優先 — 順序、条件分岐、遷移、権限はすべて表にする。
- 入力項目の列挙粒度 — 「メール4種」「ラジオ系」のように実装グループだけを書かない。画面ラベル＝設計書の行を基本にする。類似項目は表で隣接させてよいが、列を統合して束ねない。
- textarea — 単なる「テキスト」一行に逃がさず、複数行入力（textarea）と明記し、必須／任意・最大長は `### 入力項目` の「最大長」列に文字数の具体値（`lltext_len` 既定等）と検証を書く。
- ラジオ・展開選択 — 設問の見出し（画面文言）ごとにブロックを分け、各選択肢の表示名と永続化される値（0/1、列名）を対応づける。`### 入力項目` の「初期値」列に DB 現行値とスキーマ既定を書き分ける。
- 入力項目表の列 — `### 入力項目` では列を5つに固定する（項目名、必須／任意、最大長、初期値、保存先・扱い）。見出し直後は表のみとし、説明は表の後に置く。項目名列は利用者向けラベルのみ。`mtb_option.option_key` に対する論理キー、Symfony のプロパティ名を項目名にバッククォート括弧付きで付けない。これらは保存先・扱いで `テーブル.列`（キー `...`）、`mtb_option.option_value`。論理キー `...`。のように示す。最大長は `constant.yml.dist` 等から読み取った具体文字数・桁数を書き、キー名のみの記載にしない（`stext_len` は補足として併記可）。Length が無い項目は「制約なし」「DB 上限」等を明示する。検証・保存経路は主に保存先・扱い列にまとめる。計算のみ・入力が無い機能では「本機能では入力項目に紐づく表を持たない」と明示してよい。
- 利用者入口で束ねる — 表示、リンク押下、送信、リダイレクト、同一画面更新を入口ごとにまとめる。「利用者視点の入口」では各行に `メソッド + パス` と期待されるふるまいを書く。実装単位の見出しに寄せすぎない。
- 境界条件を別表にする — 0件、NULL、重複、一意化、対象外ステータス、既存条件の上書きなどは「エッジケース」として本文から分離する。
- 括弧書きは最小限 — 補足や条件は括弧に逃がさず、前文・次文・別行・表の別セルへ展開する。略語や英字の対訳など、読みだけで済まない最小限のみ括弧やスラッシュを許容する。入力項目の項目名列ではフォームキーを括弧に入れない（保存先・扱いへ）。
- 太字は使わない — 強調やラベル付けに `**...**` や `<strong>` を置かず、見出し・表・箇条書きで情報の優先度を表す。
- 実装のフレーズは最小限 — `form_login` のように「なぜフォームの NotBlank と表示がズレるか」など、読者が実装を読むための手がかりに留める。
- クラス名は論理名へ — 例外・エンティティ・サービス短名を段落の主語にしない。サービス境界を示すときは「コアのメール送信サービス」「購入処理サービス」などとし、固有名が照合に必須なら括弧や「ソース照会」で補う。
- API 詳細設計は別物 — 「処理概要・シーケンス・HTTP ステータス中心」の別体裁は本スキルでは扱わない。ユーザが明示したときは別テンプレを検討する。

## レビュー時
