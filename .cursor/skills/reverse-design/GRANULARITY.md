# 情報粒度の基準 — 受注情報検索 一覧(検索入力)

全機能のHTML設計書は、この基準機能と**同じ作成手順・同じ情報粒度**で作る（2026-08-17 ユーザー指定）。

基準機能: `functions/pf-eccube3/m05-01_admin_order_order_search_list.md`
（Excel: `0203_基本設計仕様書(受注管理機能).html` / シート「受注情報検索 一覧(検索入力)」）

検査: `python3 .cursor/skills/reverse-design/scripts/doc_granularity_gate.py --function <機能No> --strict`

## 0. 節構成は基準機能に合わせる

節(H2)は基準機能が持つ2つだけとする。**「業務ロジック」と「入出力」**である（2026-08-18 ユーザー決定）。
処理の流れ・入口・フロント挙動は独立した節にせず、業務ロジックの小節として書く。

ゲートG3の必須節は固定値ではなく**基準機能から読む**。固定値にすると、基準機能自身が落ちる状態を作れてしまう。
実際 2026-08-18 まで「処理フロー」を必須節にしていたが、基準機能はこの節を持たない。19機能がこの幻の要求で落ちていた。

## 0b. 画面操作に依存しないことだけを書く

詳細設計書に書くのは**画面操作に依存しないI/O・ふるまい・業務ロジック**に限る（2026-08-18 ユーザー決定。ゲートG9が検査する）。
基準機能はこの形で書かれている。実測で、基準機能は本文106行のうち画面操作の語を含む散文が1行、
検索結果の初稿は84行のうち30行だった。

- 書く: 何を出すか、どの条件でどうなるか、何が更新されるか、どう算出するか。
- 書かない: どこを押すか、どのメニューから選ぶか、別タブで開くか、どの順に描画するか、スクロールするか。

表示メッセージ表は例外にする。文言と表示位置を逐語で載せる様式なので、「画面中央のダイアログ」の
ような語が入る。ゲートも表の行は数えない。

## 1. 粒度は分量ではなく密度で測る

分量で測ってはいけない。画面の大きさに比例するだけで、書き手の丁寧さを測れない。

実測（2026-08-17）: 同じ M05-01 の 検索入力 と 検索結果 は絶対量では 186行 対 84行 と倍以上違うが、
画面要素数（Excel画面項目定義の識別ID件数）で割ると次のとおりほぼ同等だった。

| | 画面要素 | 条件語 ÷ 画面要素 | 具体値 ÷ 画面要素 |
|---|---|---|---|
| 検索入力（基準） | 83 | 0.52 | 0.29 |
| 検索結果 | 23 | 0.57 | 0.30 |

体感の粒度差の実体は**画面の大きさ**であって書き方の差ではない。そこで粒度を2軸に分ける。

### 具体性（本文行あたり。画面の大きさに依存しない）

- **分岐密度** = (条件語の出現数 ＋ 表のデータ行数) ÷ 本文行数 ≧ **0.93**（ゲート）
- **具体値密度** = (バッククォート識別子 ＋「N件／N文字／N桁／N日 …」) の出現数 ÷ 本文行数 ≧ **0.23**（助言のみ）

具体値密度はゲートにしない。上限・既定値・変換規則といった定数を持たない機能が実在するからである
（M05-20 出荷指示リスト詳細編集/削除は備考1項目に最大長の制限も既定値も無く、実装から取れる定数が無い）。
必須にすると数値の水増しを強制して捏造を誘発する。基準未満は参考として集計するにとどめ、
「実装に定数があるのに書いていない」かどうかは人が判断する。

分岐は2通りの書き方で表される。散文の条件語（「〜のとき」）と、表の行（左列が条件・右列がふるまい）である。
条件語だけを数えると、条件を列見出しへ追い出す様式を不当に低く採点する（M05-13 は 74行中 条件語9 だが、
エッジケース表で7ケースを列挙しており実際は薄くない）。両方を分岐の担い手として数える。

### 記述量の充足（画面要素あたり）

- **記述量** = 本文行数 ÷ 画面要素数 ≧ **1.28**

分母は Excel の**画面項目定義**の表（`識別ID` と `ラベル` の両方を持つ表）から数える。
`識別ID / 項目名 / 備考` の3列表は CSV・帳票の出力項目一覧であって画面要素ではないので分母に入れない
（入れると CSV出力機能の分母が列数まで膨らみ、Excelを正とする規約 1b-1 どおり列を復唱していない
設計書を不当に低く採点する）。

具体性と充足はどちらか一方では足りない。具体性だけでは薄い設計書が通り、充足だけでは水増しが通る。
全390機能の実測では、不足の実体は具体性（379件）であって記述量（33件）ではない。
つまり大半の設計書に必要なのは長さではなく、具体値と分岐の書き込みである。

| 区分 | 正本 |

| 標準 | `ec-cube-enterprise` |

採番と対応させる。以下の「棚卸しは標準区分にしか使えない」は挙動・項目定義についての話であり、表示メッセージには適用しない。

`message_inventory/` の棚卸しは **ec-cube-enterprise 由来**。

## 3. 基準機能がやっていること（この形を踏襲する）

### 3.1 画面の要素を網羅列挙して表にする（散文にまとめない）

基準機能は検索条件27項目を「画面上の項目 → 検索条件」の2列表で1行ずつ書いている。
「各種日付で絞り込める」のようにまとめない。1項目1行で、その項目固有の照合規則まで書く。

    | 注文者のフリガナ | ひらがなを全角カタカナへ変換した入力値で、注文者のセイとメイを連結した文字列への部分一致 |
    | 配送先のフリガナ | 配送先のセイとメイを連結した文字列への部分一致。注文者側と違い、入力値の変換は行わない |

似た項目ほど差分を書く。上の2行は「注文者側は変換する／配送先側はしない」という実装差が要点である。

### 3.2 入力値の扱い・境界・エッジケースを書く

空文字の扱い、トリム対象（半角空白は除くが全角空白は除かない）、`0` と `"0"` の扱い、
ワイルドカード `%` `_` のエスケープ有無を**項目名を挙げて**書く。「適切に処理する」は書かない。

### 3.3 同時指定・上書きなど、実装に固有の落とし穴を書く

基準機能は「配送先の電話番号と郵便番号を同時に指定すると電話番号の条件にも郵便番号の値が使われる」
のような、仕様書からは読めないが実装にある挙動を表で列挙している。これが逆生成設計書の価値の中心である。

### 3.4 計算方法を式で書く

相対日数の境界日時の求め方、表示件数の決定順序、該当件数の数え方を、丸めと基準時刻まで書く。

### 3.5 表示メッセージを表で書く

列は「メッセージID／表示位置／画面上の文言／表示条件／後続処理」。**文言は区分によらず ec-cube-enterprise の逐語**とし、
IDは `message_inventory/MESSAGE_LIST.md` の当該機能の採番に対応させる（2026-08-19 ユーザー決定）。新たに採番しない。
IDを持たないメッセージは表に載せず、棚卸しの欠落として作業記録へ残す。ゲートG4が当該機能の全IDの被覆を検査する。

**表示メッセージ節は見出しの直後を表から始める**（2026-08-19 ユーザー決定。ゲートG10が検査する）。
正本・出典・採番規則・対になる設計書との分担といった前置きを書かない。どこから採ったかはこの規約の担当であって、
設計書の読者に要る情報ではない。メッセージを持たない機能だけは、その旨を一文で書いてよい。

### 3.6 Excel設計書との乖離を分離する

現行ソースにあって Excel に無い挙動は `[乖離]` を付け、末尾に「現行ソースのふるまい／Excel設計書の記載」の
2列表で対比する。**乖離が無い機能には書かない**（無理に書くと捏造になる）。

**乖離に書くのは I/O とふるまいに限る**（2026-08-18 ユーザー指示）。利用者から見た入出力と、
操作に対する挙動の差だけを書く。通信方式・認可設定・受付先の位置・内部の呼び出し順といった実装手段は、
現行と Excel で違っていても乖離に書かない。設計書本文で内部の呼び出し順を書かないのと同じ線引きである。

書く方向は**現行ソース起点の一方向だけ**である。次の2つも書かない（ゲートG5で検出する）。

- **Excel の画面項目に関する内容**。列の有無・ラベル・表示条件・項目の定義は Excel の画面項目定義が正であり、
  乖離節に持ち込むと規約 1b-1 の復唱になる。右列は「〜の記載が無い」まで書けばよく、
  「項目定義は〜だけを定めている」のように項目定義の中身を引かない。
- **Excel設計書だけに在るもの（現行ソースに実装が無いもの）の一覧**。逆生成設計書は現行から読み取れる
  ふるまいを書くものであって、これから作る仕様は対象外である。「Excel設計書の記載／現行ソースの状況」の
  ような Excel 起点の対比表を作らない。

外したい事実が惜しいときは設計書ではなく作業記録（`reverse_design_audit/<機能>/carryover.md` など）へ残す。
レビュアーが「Excel専用の仕様が抜けている」と指摘してきても、この方針にもとづき却下する。

### 3.7 永続化を操作×契機の表で書く

**永続化節に書くのは、DBへの登録・更新・削除と、キャッシュへの入出力だけである**（2026-08-19 ユーザー決定）。
読み取りは書かない。どの表をどう読むかは検索や表示の説明であって、永続化ではない。
何も書き込まない機能は「更新しない」の一文だけを置く。

書き込む機能は登録／更新／削除のどれをいつ行うかを書く。

DB限定にする理由は次のとおり（2026-08-18 ユーザー決定。ゲートG7が検査する）。
DB限定なら「この節は丸ごと ec-cube-enterprise を正とする」と機械的に言える（SKILL.md 1c）。
混在すると行ごとに正本が変わる（DB列は ee、ログ文言は現行ソース）。結合テストのDB直接参照の
判定にもこの節がそのまま候補リストとして使える。実測でも永続化節を持つ23本のうち21本は既にDB限定だった。

DB以外は捨てるのではなく、次へ移す。

| 内容 | 行き先 |
|---|---|
| セッション・Cookie | 業務ロジック。画面間で何を持ち越すかはふるまいそのものである |
| メール送信 | `出力: メール` |
| CSV・PDF・帳票 | `出力: CSVファイル` など出力ごとの節（CSV出力系の設計書が既にこの形） |
| ログ出力 | 書かない。監査要件がある機能だけ別節を立てる |
| イベント・通知の発行 | 書かない。内部配線であり、I/Oでもふるまいでもない |
| 読み取り（参照・取得・検索） | 書かない。何をどう読むかは業務ロジックの検索・表示の説明で足りる |

### 3.7b 設計書に置かない節

次の2つは節を作らない（2026-08-18 ユーザー決定。ゲートG8が検査する）。どちらも機能固有のふるまいではない。

| 置かない節 | 理由 |
|---|---|
| ページャ・ページング | 画面の共通部品であり、挙動は基本設計の画面項目定義が定める。書けば規約1b-1の復唱になる |
| セッション・Cookie・画面間で持ち越すもの | 内部の保持の仕組みであり、利用者から見た入出力でもふるまいでもない |

ふるまいの説明の途中でセッションに触れるのは差し支えない（「並び順はセッションへ保存されるが並びには反映されない」など、
利用者に見える結果を述べるための言及）。禁じるのは**保持そのものを主題にした節**である。

### 3.8 結論を端的に置く

**文の長さの問題ではない**（2026-08-18 ユーザー指示を受けた実測）。基準機能と検索結果の初稿は
平均36.3字 対 37.6字、60字超の文は 10% 対 6% で、むしろ検索結果のほうが短かった。
差が出たのは**結論をそのまま置いているか**であり、実測値は次のとおりだった。

| | 理由節を含む文 | 接続詞で始まる文 | 目的の説明 | 一文に結論が複数 |
|---|---|---|---|---|
| 検索入力（基準） | 8% | 0 | 0 | 0 |
| 検索結果（初稿） | 15% | 2 | 1 | 1 |

そこで次を守る。ゲートG6が基準機能の実測値を上限として検査する。

- **接続詞で文を始めない。** 「そのため」「また」「さらに」「なお」で始めると、その文だけを読む読者が前へ戻らされる。
- **意図や目的を説明しない。** 「〜するための補正である」ではなく「〜のとき、1つ前のページを表示する」と動作を書く。
  設計書が答えるのは「何が起きるか」であって「なぜそう作ったか」ではない。
- **一文に結論を複数積まない。** 「〜することも、〜することもある」は読み手がどちらが結論か決められない。文を分ける。
- **理由を書くときは結論を先に置き、機構は次の文へ出す。** 基準機能の「全角スペースは除かないため、
  全角スペースだけの入力でも条件が付く」のように理由節が短いものは残してよいが、割合は基準機能以下に収める。

    誤: 選択はページを移動すると失われるため、一括操作の対象にできるのは表示中のページの受注だけである。
    正: 一括操作の対象にできるのは表示中のページの受注だけである。選択はページを移動すると失われる。

**結論を削るのではなく、結論を先に出す。** 機構や理由を消せと言っているのではない。順序の問題である。

## 4b. レビューで細かくしすぎない

粒度ゲートは**下限**であって上限ではない。上限を機械で決めようとして、記述量（本文行数÷画面要素数）に
基準の2倍という天井を試したが、205本中142本が該当した。画面が小さいほど値が跳ねる指標で、
細かすぎることの指標にならない。上限は数値ではなく**担当の切り分け**で守る。

- 他機能の設計書が担当する処理内容は書かない。境界だけ書いて委ねる。
- 実装手段・内部配線は書かない（3.6・3.7・0b と同じ線引き）。
- 基準機能が書いていない種類の内容は書かない。

敵対レビューは3巡まで、指摘は5件／巡までとする。実測で、逐次10巡は1巡あたり約23万トークンかかり、
事実の誤りは6巡目で尽きた。詳細は `.cursor/skills/adversarial-review/SKILL.md`。

## 5. やってはいけないこと

- 密度を上げるために条件語や数値を water する。ゲートは近似指標であって目的ではない。
  指標を満たすために実装にない条件を書いたら捏造であり、`validate_messages.py` の捏造ゼロ検証と同じ基準で不可。
- Excel が持っている画面項目定義・CSV列一覧を設計書へ復唱する（1b-1 違反、かつ分母だけ増える）。
- 乖離の無い機能に「Excel設計書との乖離」節を作る。
- 現行踏襲・カスタマイズの機能に ee の文言・メッセージIDを持ち込む。
- 乖離節に Excel の画面項目に関する内容を書く（3.6）。
- 乖離に I/O・ふるまい以外（通信方式・認可設定・受付先など実装手段）の差を書く（3.6）。
- 接続詞で文を始める／意図や目的を説明する／一文に結論を複数積む（3.8）。
- 結論を機構の説明の後ろに置く（3.8）。順序を直すのであって、機構を消すのではない。
- 永続化節にログ・イベント発行・セッション・メール・ファイル出力を書く（3.7）。
- ページャ・セッション・Cookie の節を作る（3.7b）。
- Excel設計書だけに在るもの（現行に実装が無いもの）を設計書に列挙する（3.6）。
