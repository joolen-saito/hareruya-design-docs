# ソース↔設計書 網羅性照合チェックリスト

各ソース（現行リポ・ec-cube-enterprise・Excel基本設計）の内容と、リバース詳細設計書（Markdown正本）の内容が、**双方向に網羅できているか**を確認するためのチェックリスト。

- **目的**: 「ソースにあるが設計書に無い（漏れ）」「設計書にあるがソースに無い（無根拠・誤混入）」の両方を検出し、設計書が実装を網羅していることを担保する。
- **位置づけ**: [CHECKLIST.md](CHECKLIST.md)（出力前の品質・体裁チェック）の上位補完。reverse-design 手順10b（セルフレビュー）で本書を実施する。`doc-parity-check`（正本↔HTML一致）・`spec-consistency-check`（差分横断整合）とは目的が異なり相互補完。
- **正典ルール**: 参照ソースの選定・衝突解決は [SKILL.md](SKILL.md) 手順 1a / 1b-1 / 1c に従う。
- **使い方**: 機能1件ごとに A→E を上から確認する。各チェック項目は、確認した**ソース根拠を `ファイル:行` で残せる**ことを合格条件とする（根拠を書けない＝照合できていない）。
- **適用範囲の明示**: 該当しない観点（例: メール送信が無い機能のメール）は「本機能では扱わない」と明示すれば合格扱い。空欄のまま放置しない。

---

## A. 分類別ソース選定（前提）

- [ ] `functions/todo-list.md` の当該機能行で **カスタマイズ区分**（標準／現行踏襲／カスタマイズ／新規実装）を確認した。
- [ ] 区分に応じた参照ソースを正しく選んだ。
  - 標準: `ec-cube-enterprise`
  - 現行踏襲・カスタマイズ: 現行リポ（`ec-cube` / `pf-eccube3` / `pf-api` / `pf-article` のいずれか）＋ `ec-cube-enterprise`（移行後の扱い）＋ 該当Excel基本設計仕様書
  - 新規実装: Excel基本設計仕様書（正）＋ `ec-cube-enterprise`（補助）
- [ ] 当該機能の現行ソース所在（どのリポ・どのController/Service）を特定した。判別できない場合はユーザーに確認した。

## B. ソース → 設計書（実装網羅・漏れ検出）

各ソース要素が、設計書の対応する節に反映されているかを確認する。反映先の節名は [TEMPLATE.md](TEMPLATE.md) に対応する。

- [ ] **ルート/エンドポイント**（Controller の `#[Route]` / routing / firewall パターン）→「利用者視点の入口」に、入口ごとのHTTPメソッド・パスパターンが反映されている。
- [ ] **画面表示・フロント挙動**（Twig / JS / CSS / data属性 / モーダル・タブ・トースト）→「フロント挙動」に反映されている。
- [ ] **入力項目・バリデーション**（FormType の各フィールド、`Assert\*` 制約、`constant.yml` の桁数）→「入力項目」「バリデーション」に画面ラベル単位で反映されている。
- [ ] **判定・分岐・処理順**（Controller / Service / EventListener / Subscriber のロジック）→「処理フロー」「（主処理名）時の判定順序」に反映されている。
- [ ] **DB操作**（Repository のクエリ、Entity、`persist`/`flush`/直接 INSERT・UPDATE・DELETE）→「DBカラム」「DB操作」「データ整合性」に反映されている（**ec-cube-enterprise を正典 = 1c**）。
- [ ] **副作用**（認証・権限・Cookie・セッション・メール送信・キュー・ログ・履歴記録）→ 該当節（セッション／Cookie／ログ・監査／エラー処理 等）に反映されている。
- [ ] **メッセージ**（`messages.ja/en.yaml`、`validators.ja/en.yaml`、`addFlash`/`addError`、Twig の `trans`）→「表示メッセージ」に表示条件付きで反映されている。
- [ ] **設定値・閾値**（試行制限回数・期間、Cookie有効期限、最大長などの yaml / env / parameters）→ 該当記述に**具体値**で反映されている（キー名だけにしない）。
- [ ] **【網羅の最終確認】ソースにあって設計書に無い挙動・分岐・項目が無い**。検出したものは、設計書へ追記（標準・新規の補完範囲）するか、「本書で扱わないこと」「リニューアル移行時の扱い」へ分離する。

## C. 設計書 → ソース（無根拠・誤混入の排除）

- [ ] 設計書の各節の記述が、ソース（`ファイル:行`）で裏付けられる。裏付けられない記述は「本書では仕様確定しない」「別機能（機能No）を正とする」「実装で要確認」のいずれかに分類されている。
- [ ] **他機能の内容が誤混入していない**（節横断でトピックが一貫している。例: ログイン設計書にコンテンツ管理・帳票・別画面の項目仕様が紛れていない）。
- [ ] 推測でDBスキーマ・挙動を創作していない（ec-cube-enterprise に該当が無ければ「要確認」と残している）。

## D. 衝突解決の遵守

衝突時の優先順位（上が強い）:
0. **Excelが廃止を宣言した項目・画面・機能** … **Excel基本設計を正**とし、刷新後は実装しない仕様として扱う（1b-3 / 1d(0)）。ソースに実装が在ることを「Excelに記載が無い実装確認値」と読み替えてはならない。記述は消さず、廃止であることを明示して `functions/superseded_specs.json` へ登録する。
1. **DB操作・DB関連** … **ec-cube-enterprise が常に正典**（テーブル/列/型/桁/制約/関連、`### DB操作` の登録・更新・削除・検索、入力項目の「保存先・扱い」、データ整合性のDB部分、副作用のDB更新）。Excel基本設計や現行リポと食い違っても ec-cube-enterprise に合わせる（1c）。例外は「新規実装かつ ec-cube-enterprise に実装が無い」場合のみ Excel を正とする。
2. **DB以外の同一項目重複** … **Excel基本設計仕様書を正**とする（1b-1。画面項目・選択肢・件数・初期値・表示文言・業務条件・処理概要・CSV/帳票項目など）。

- [ ] **Excelが廃止を宣言した項目・画面・機能**を、ソースに実装が在ることを理由に現行仕様として書いていない（1b-3 / 1d(0)）。廃止は明示し、台帳へ登録している。
- [ ] **DB操作・DB関連は ec-cube-enterprise を正典**としている（Excel・現行リポと食い違う場合も enterprise に合わせ、差は「リニューアル移行時の扱い」に明記）。新規実装で enterprise 未実装の箇所のみ Excel を正としている。
- [ ] DB以外でExcel基本設計とソースが**同一項目で重複**する場合、**Excel基本設計仕様書を正**としている（1b-1）。Markdown側の食い違いはExcelに合わせるか、差分を「リニューアル移行時の扱い」「実装確認値」へ分離している。
- [ ] 現行値と移行後値（並び順キー、削除方式、数量・選択肢など）を取り違えていない。
