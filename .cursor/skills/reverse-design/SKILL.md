# リバース詳細設計書（機能単位）

実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むための詳細設計を Markdown で作成・レビューする。Markdown を一次成果物とし、HTML閲覧版は `function_spec_html_preview/` または Excel 由来HTMLへの統合ブロックとして Markdown から生成する派生成果物とする。HTML を直接編集しない。

機能の全体カタログは `functions/todo-list.md`（TODOリスト）を正典とする。設計書はこのリストのいずれかの機能に対応する。作成・更新したら同リストの該当行を更新する（手順12）。

## 正典

トーン・粒度・章立ては `functions/ec-cube-enterprise/m02-04_admin_home_home_shop_status.md` を第一正典にする。認証・Cookie・移行を扱う機能では `functions/ec-cube-enterprise/m01-01_admin_login_login.md` も参照する（表示メッセージの記載体裁は同書の「表示メッセージ」節を正とする）。テンプレ本文は複製しない。

## 手順

1. スコープ — 冒頭で「本書で扱うこと / 扱わないこと」を分け、別機能に委ねる範囲を明示する。一覧と詳細（登録・編集）など複数画面が同一Markdownを共有していて、対象シートに別画面の内容が出ている場合は、画面単位に Markdown を分割し、当該画面の挙動だけを残す。他画面の仕様は「別画面（機能No）を正とする」と委譲する。
1a. 参照リポの選択（カスタマイズ区分別） — 設計書の参照リポは、`functions/todo-list.md` の当該機能行の「カスタマイズ区分」列（標準／現行踏襲／カスタマイズ／新規実装。ユーザーが「分類」と呼ぶ列）で決める。これはMarkdown正本の作成・更新と、そこから生成するHTML閲覧版の双方の前提とする。
  - 標準: ec-cube-enterprise リポを参照する。リニューアル後の標準機能はそのまま ec-cube-enterprise の実装を正典とし、挙動もDBも ec-cube-enterprise に基づいて記述する。
  - 現行踏襲・カスタマイズ: まず現行リポ（`ec-cube` / `pf-eccube3` / `pf-api` / `pf-article` のいずれか。機能の所在に応じて選ぶ）で現行挙動を確認し、次に ec-cube-enterprise を参照してリニューアル移行後の扱いを確認する。記述は該当する基本設計仕様書に基づく。現行挙動は現行リポ、DBスキーマと移行後の扱いは ec-cube-enterprise（1c）、画面・機能の追加仕様は基本設計を根拠とし、現行と移行先の差は「リニューアル移行時の扱い」へ集約する。
  - 新規実装: 基本設計仕様書を正典とする。対応する現行実装が無いため、画面・項目・DBとも基本設計仕様書に基づいて記述する（ec-cube-enterprise に実装があれば補助参照してよいが、正は基本設計仕様書とする）。
  - カスタマイズ区分が空欄または判別できない場合、機能がどの現行リポにあるか不明な場合はユーザーに確認する。ユーザーが明示的に参照リポを指定した場合はその指定を最優先する。
1b. 基本設計との突き合わせ・リニューアル差分 — 基本設計（同シートの「機能仕様」等）の記述とリバース対象リポの実装が食い違う場合は、リバース対象リポの実装を正として現行挙動を断定で書く。基本設計が描く追加仕様（絞り込み・ソート・追加列など）がリバース対象リポに未実装のときは、実装済みとして書かず、「本書で扱わないこと」で対象外と明示し、差分は「リニューアル移行時の扱い」へ集約する。サイトリニューアル案件では基本設計＝リニューアル後（例: ec-cube-enterprise系）、リバース詳細設計＝現行（例: pf-eccube3）を指すことがあり、並び順キー（`rank` と `sort_no`）・削除方式（論理削除と物理削除）・絞り込みUIの有無などが現行と移行後で異なる。現行値と移行後仕様を取り違えない。どのリポを正とするかは 1a のカスタマイズ区分別ルールに従う（ユーザー明示指定があればそれを最優先する）。ただしDB関連の記述は 1c に従い ec-cube-enterprise を正とする。
1b-1. Excel基本設計とMarkdown正本の重複時優先 — `functions/**/*.md` と該当Excel基本設計仕様書に、同一機能・同一仕様（画面項目、選択肢、件数、初期値、表示文言、業務条件、処理概要、CSV/帳票項目など）に関する内容が重複して書かれている場合は、Excel基本設計仕様書を正とする。Markdown側の記述がExcelと食い違う場合は、HTML側でMarkdown記述を正として扱わず、Markdown正本をExcelに合わせて更新するか、差分を「リニューアル移行時の扱い」「実装確認値」として分離する。Excel基本設計に同一仕様の記載が無い実装確認値だけを、1a/1b/1cに従ってMarkdownへ残す。
1b-2. 数量・選択肢・配置名の突き合わせ — 「5枠」「4件」「上段中央」などの数値、個数、選択肢名、配置名、初期値、削除対象項目は、現行実装の値をそのまま用語・入力項目・業務ルールへ横展開しない。該当基本設計仕様書の「機能仕様」「画面項目定義」「画面部品の説明」に変更後の数量や選択肢がある場合は、リニューアル後の本文・用語・入力項目・バリデーション・フロント挙動をその値に合わせる。現行実装との差は「リニューアル移行時の扱い」に現行値と移行後値の対応表として残す。
1c. DB関連の記述の正典は ec-cube-enterprise — 永続化に関わる記述は、挙動の参照リポ（1b）にかかわらず ec-cube-enterprise リポの実装を正とする（カスタマイズ区分が「標準」「現行踏襲」「カスタマイズ」の場合）。各基本設計仕様書はリニューアル後システムの設計であり、確定すべきDBスキーマはリニューアル先（ec-cube-enterprise）のものとするためである。カスタマイズ区分が「新規実装」で ec-cube-enterprise に実装が無い場合は、DBも基本設計仕様書を正とする（1a）。対象は次のとおり。永続化先のテーブル名・列名・型・桁・制約・テーブル間の関連、DBカラム節、入力項目表の「保存先・扱い」列、データ整合性のうちDBに関わる部分、副作用節のDB更新（INSERT/UPDATE/DELETE）、用語・バリデーションのうちDB列・DB制約に言及する箇所。挙動・画面・処理フロー・メッセージ・UIバリデーションの動きは引き続き 1b の参照リポを正とする。現行リポとDBスキーマが食い違う場合（並び順キー `rank` と `sort_no`、論理削除と物理削除、補助テーブル `dtb_member_sub` の有無、列の分割・統合など）は、DB記述を ec-cube-enterprise に合わせ、現行との差分は「リニューアル移行時の扱い」に明記する。挙動説明の中でDB列に触れるときも、列名は ec-cube-enterprise の名称で書く。ec-cube-enterprise に該当テーブル・列が見当たらない場合は、推測でスキーマを作らず「ec-cube-enterprise 実装で要確認」と残す。
1d. 衝突時の優先順位（要約） — 1a〜1c を一文に整理する。生成者はこの順で正を決める。(1) DB関連（テーブル・列・型・桁・制約・関連、DB操作の登録/更新/削除/検索、保存先・扱い、副作用のDB更新）は **ec-cube-enterprise が常に正典**（新規実装で enterprise 未実装の箇所のみ Excel 基本設計を正）。(2) DB以外で Excel 基本設計とソースが同一仕様で重複する場合は **Excel 基本設計を正**（画面項目・選択肢・件数・初期値・表示文言・業務条件・処理概要・CSV/帳票項目など）。(3) Excel に記載が無い実装挙動・確認値のみ、1a の参照リポ実装を正とする。1b の「実装を正」は (3) の範囲（Excel に同一仕様の記載が無い実装確認値）に適用し、(2) の Excel 優先と取り違えない。
1e. DB操作の永続化モデル — DB操作節は ec-cube-enterprise の永続化を正典とする。**承認ワークフロー型（登録時に承認データを作成し、在庫は承認後または廃棄時のみ即時更新する方式）は在庫(stock)機能に固有**であり、Approval 系 Entity/Service は ec-cube-enterprise の `Admin/Stock` 配下にのみ存在する。在庫以外のドメイン（商品・受注・会員・設定・イベント・カード・デッキ・コンテンツ等）の書込は persist/flush による直接更新とする。各 DB操作行は 登録／更新／削除／検索 のいずれか1語で始め、当機能が実際に行わない操作を列挙しない。
2. 入口 — HTTP で届く機能では「利用者視点の入口」を唯一の入口節として書く。表は常に 3 列（入口・URLエンドポイント・期待されるふるまい）。ナビ・ボタン・XHR・タブ・ブックマーク・同一ページ内の操作など利用者がたどる境界ごとに行を分け、各 URLエンドポイントに HTTP メソッドとサイトルートからのパスパターン（実装確認値）を載せる。管理画面プレフィックスが環境依存なら、`eccube_admin_route`・`ADMIN_ROUTE`・`path.yml` のどれで決まるかと確認観点を概要または入口節の直前で一文にまとめる。ルート bind 名や Symfony のルート name の網羅は本文に置かず、grep 用なら「調査補助」へ隔離する。
3. フロント挙動 — Twig・JS・CSS・data 属性・モーダル・タブ・トースト・ローディング・表示／非表示切替を実装から拾う。フォーム中心の機能では、メール欄のように似た項目でも「〇種」に束ねず、画面ラベル単位で列挙する。textarea は入力種別を明記する。ラジオ・トグルは項目ごとに選択肢（例: 無効／有効）と保存値の対応まで具体化する。該当しない場合も「本機能では扱わない」と明示する。
4. 処理フロー — 表示、押下、送信、リダイレクト、同一画面更新などの入口ごとに番号付きで書き、利用者が結果まで追える形にする。
4b. 表示メッセージ — 利用者向けの画面文言がある機能では、「○○時の判定順序」の直後（無い場合は処理フローの後）に「表示メッセージ」節を置く。Twig（`trans` / `error` / `app.flashes`）、`messages.ja.yaml`、`validators.ja.yaml`、コントローラの `addError` / `addFlash` から調査する。英語ロケールに対応している機能（`messages.en.yaml` / `message.en.yml` / `validators.en.yaml` / `*.en.twig` などのロケールリソースが存在し、利用者が言語切替で英語表示へ到達できる場合）は、同一ロケールキー・同一テンプレートの英語文言も併せて調査し、表に「表示文言（英語）」列を加えて日本語と対応づけて出力する。英語リソースが見つからないキーは英語列を `-` とし、確認が必要なら備考に残す。日本語のみで英語ロケールリソースが存在しない機能では英語列を設けなくてよい。表は利用者が見る文言と表示条件を対応づける。列例: 表示文言（日本語）、表示文言（英語）、表示条件（利用者視点）、表示位置、備考。認証失敗で画面上理由を区別しない場合は備考に明記し、エラー処理節は処理方針、表示メッセージ節は文言の正とする。ロケールキー・Symfony メッセージ ID は調査補助または備考に留める。該当しない機能は節ごと削除するか「本機能では利用者向けの画面メッセージを扱わない」と1行で明示する。
5. 集計・判定・計算 — 対象データ、除外条件、集計単位、一意化、判定順序、丸め、画面表示値との対応を実装から抽出し、エッジケースも表で明示する。入力中心の画面では `### 入力項目` に5列固定の表を置く（項目名、必須／任意、最大長、初期値、保存先・扱い）。項目名列は画面ラベルのみとし、フォームフィールド名・オプション論理キー・DB 列と一致しない識別子は「保存先・扱い」に書く。「保存先・扱い」列のテーブル名・列名・制約は 1c に従い ec-cube-enterprise を正とする。文字数・桁数の具体値は ec-cube-enterprise の `constant.yml`／マイグレーション／エンティティ定義を優先し、無ければ現行リポの `src/Eccube/Resource/config/constant.yml.dist` 等を参照する。体裁は `m10-06_admin_base_setting_setting_shop_delivery.md` の「### 入力項目」を正とする。
6. データ整合性 — 一覧・詳細・外部連携・バッチ・同時更新・再表示で値が一致する範囲と保証しない範囲を分けて書く。DBに関わる整合（永続化先・列・関連）は 1c に従い ec-cube-enterprise を正とする。
7. API/バッチ結果 — API やバッチを呼ぶ機能では、入力、実行条件、成功結果、失敗結果、再実行時の扱いを記載する。該当しない場合は「本機能では扱わない」と明示する。
8. 副作用 — 認証・権限・状態遷移・DB・キャッシュ・キュー・ログ・セッション／Cookie の副作用をコードから追う。画面遷移時に検索条件・フラッシュメッセージ・セッション等を引き継ぐ場合は、遷移前の処理と遷移後の初期状態を分けて書く。
9. 下書き — [TEMPLATE.md](TEMPLATE.md) に沿う。「利用者視点の入口」で入口と実装パスが対応するように書く。無い章は削るか「本機能では扱わない」と一行。
10. セルフレビュー — [CHECKLIST.md](CHECKLIST.md) をすべて確認。
10b. ソース↔設計書 網羅性照合 — [SOURCE-COVERAGE-CHECKLIST.md](SOURCE-COVERAGE-CHECKLIST.md) の A〜E を実施し、各ソース（現行リポ・ec-cube-enterprise・Excel基本設計）の内容が設計書に双方向に網羅されていること（漏れ・無根拠・誤混入が無いこと）を確認する。各項目は確認したソース根拠を `ファイル:行` で残せること（残せない＝照合未了）を合格条件とし、必要に応じて同書の反映マトリクスを作成する。
11. 保存 — 既定は `functions/<参照リポ>/<機能No小文字>_<機能識別子>.md`。`<参照リポ>` は 1a のカスタマイズ区分別ルールに従い、標準・新規実装は原則 `ec-cube-enterprise`、現行踏襲・カスタマイズは現行リポ（`ec-cube` / `pf-eccube3` / `pf-api` / `pf-article`）とする。ファイル名は `functions/todo-list.md` の機能Noを小文字化した接頭辞（例: `F06-03` → `f06-03_`）で始める。ユーザー指定パスがあっても、機能No接頭辞が無い場合は原則として接頭辞付き basename に揃える。
12. TODOリスト連携 — `functions/todo-list.md` で対象機能の行を機能名・機能内容で特定する。TODOリストは全機能の正典のため、該当行が無い、または複数候補があるときはユーザーに確認し、原則リスト外の設計書は作らない。特定した行で次の2点を更新する。TODO列のチェックボックスを `- [ ]` から `- [x]` にする。8列目「詳細設計書」に Markdown と HTML 両方への相対リンクを記入する。書式は `[md](<参照リポ>/<機能No小文字>_<機能識別子>.md) / [html](../function_spec_html_preview/<参照リポ>/<機能No小文字>_<機能識別子>.html)` とする（パスは `functions/todo-list.md` からの相対）。MarkdownとHTMLの basename は一致させる。
13. HTML生成 — `python3 .cursor/skills/function-spec-html-render/scripts/convert_function_spec_html.py --source functions/<参照リポ>/<機能No小文字>_<機能識別子>.md --output function_spec_html_preview/<参照リポ>/<機能No小文字>_<機能識別子>.html` を実行する。Excel 由来HTMLへ統合する場合は `python3 .cursor/skills/function-spec-html-render/scripts/integrate_function_docs_into_excel_html.py` を実行する。生成物は編集せず、変更は元の Markdown と todo-list.md 側に行い、必ずスクリプトで再生成する。

## 表現ルール

- `〇〇され得る` のようなあいまい表現は避ける。
- 実装から確認できたふるまいは「する」「しない」「表示する」「保存する」のように断定する。
- 条件付きのふるまいは、条件を明示して「A の場合は B する」と書く。
- 実装から確定できない内容は、推測でぼかさず「本書では仕様確定しない」「別機能の設計を正とする」「実装を確認値とする」に分ける。
- リバース詳細設計書の本文・表（セル含む）・箇条書きでは、Markdown の太字（`**` や `__`）や HTML の strong を使わない。強調は見出し・表・箇条書きの構造で示す。
- 和文の本文・表（セル含む）・箇条書きでは、語と語のあいだに読みやすさ目的の半角空白を入れない。また、インラインコード・英字・数字・記号のみのトークンの直後に続く助詞・助動詞の直前にも半角空白を入れない（例:「CSVを」「HTTPエンドポイント」「eccube.yamlとする」「`dtb_csv`の列」「Symfonyの検証」「POSTで開く」）。英語の複合語として固定されている表記（例:「Remember Me」）や、コードフェンス内・URL・ファイルパス・カンマ区切り・HTTPヘッダ値など、ASCIIのみで書く構文に必要な空白はそのままとする。
- PHP のクラス名・例外クラス名・Doctrine エンティティの短名（例: `AccessDeniedHttpException`、`MtbOption`、`Member`）は本文・表では使わず、業務上の論理名で書く（例: アクセス拒否（HTTP 403）、オプションマスタ、管理者アカウント）。フレームワーク部品は「電話番号用フォーム種別の送信後処理」「URL 形式の検証」などと述べる。テーブル・列（`dtb_member`）、設定キー、フォーム項目のキー文字列、一般的な権限名（`ROLE_ADMIN`）は実装照合のためそのままよい。テーブル・列名は 1c に従い ec-cube-enterprise の名称を正とする。grep 専用の「調査補助」節が必要な場合も、主説明は論理名とし、パスは補助に留める。
- フォーム・設定画面では、メール欄など類似項目を「〇種」と束ねない。画面ラベルごとに、`### 入力項目` の行で業務ルール・バリデーション・DB 列を対応づける。textarea は表示要素と制約の両方で触れる。ラジオは設問見出し・各ラベル・永続化値を総称せず書く。
- `### 入力項目` の表 — 列は5つのみ（項目名、必須／任意、最大長、初期値、保存先・扱い）。見出し直後は空行のうえ表のみとし、補足は表の後（「### エッジケース」等の直前）に置く。項目名列には画面ラベルだけを書き、フォームキー・`mtb_option.option_key` に対応する論理キー・Symfony のプロパティ名などを括弧付きで付けない。これらは保存先・扱い列にまとめる（例: `dtb_help.law_company`（キー `law_company`）、`mtb_option.option_value`。論理キー `arrival_alert_max`。）。最大長は `constant.yml.dist` 等から読み取った具体文字数・桁数を書き、`stext_len` のようなキーだけにしない。環境で上書きされている場合は注記する。初期値は初回表示時にフォームへ載る値（多くは DB 現行値。新規行・列のスキーマ既定は補足）。検証・保存経路は主に保存先・扱い列に書く。
- 表示メッセージ — 本文・表の主説明は利用者向けの文言（日本語）とする。英語ロケール対応がある機能では「表示文言（英語）」列を併記し、同一ロケールキー・同一テンプレートの英語文言を日本語と対応づける。日本語と英語で内容や有無が食い違う場合は備考に明記する。複数行は改行を含め画面表示どおりに書く。ロケールキー・Symfony メッセージ ID は調査補助または備考列に留め、本文の主語にしない。
