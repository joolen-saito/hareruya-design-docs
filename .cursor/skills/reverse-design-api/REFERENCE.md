# リバース詳細設計書（API）— 詳細ルール（参照用）

このファイルは Skill 本体を短く保つための補足。作成・レビュー時に必要なら開く。リバース設計の共通原則は [reverse-design の REFERENCE.md](../reverse-design/REFERENCE.md) を正とし、ここでは API 固有の確認観点だけを足す。

## 守るべき原則（API 固有）

1. リバース設計であること — 既存実装のふるまい、参照・更新データ、判定境界、応答、副作用を確認する。コントローラ型名やメソッド名の列挙で代替しない。
2. HTTP 起点の明示 — 「利用者視点の入口」に HTTP メソッドとサイトルートからのパスパターンを実装どおり書く。呼び出し元クライアントを明示する。ルート name の網羅は本文に置かず grep 用なら「調査補助」へ。
3. 認証・認可を主題化 — API では認証・認可を必須節とする。方式・失敗時ステータス・照合先を確認値で書く。
4. 秘匿情報の禁止 — JWT トークン原値、署名シークレット（`auth_magic`）、パスワード、Cookie 値、セッションID完全値を書かない。
5. 否定の明示 — 副作用が無い・集計が無い・ロックが無い場合も明示する。

## ルーティング規約（確認値）

- 定義場所は `config/routes.yaml`（コントローラのアノテーションではない）。
- pf-api: `/admin/` プレフィックスの管理系 API があり、同一処理に `.json` 別名（例 `/admin/buyOrder/{id}.json` と `/admin/buyOrder/{id}`）が並ぶことがある。ルートIDは説明的な snake_case。
- deck-api: `.json` サフィックスは付けず、パスは短い（例 `/deck`、`/decks`、`/deck/usage_card/{formatId}`）。
- パスパラメータは型ヒント無しのことがある（`{id}`、`{productId}`、`{lang}` など）。
- 本文では「利用者視点の入口」に `メソッド + パスパターン` を書く。ルート name・コントローラ FQCN は調査補助に留める。

## レスポンス整形（確認値）

- 全コントローラは FOSRestBundle のビューハンドラ経由で JSON を返す（`config/packages/fos_rest.yaml`：`default_format: json`、`view_response_listener: 'force'`、`serialize_null: true`）。
- 返し方は2系統。
  - 配列・エンティティを直接 return（成功 200。JSON へ直列化）。
  - 明示的に応答を組み立てる場合はビュー生成 + ビューハンドラ（非200やメッセージ付き応答。deck-api には `createResponse(code, message)` のヘルパがある）。
- 命名は概ね camelCase（エンティティのプロパティ名がそのまま JSON キー）。DB 列は snake_case（Doctrine の命名戦略）。日時は ISO8601 文字列。
- 本文ではこれらを一文で要約し、フレームワーク部品は「JSON応答整形」などの論理名で述べる。

## 認証パターン（確認値）

- JWT 方式: カスタムヘッダ `jwt-token` を読み、HS256・シークレット `auth_magic` パラメータで検証し、ペイロード `aud`（利用者ID）で利用者を引く。
  - pf-api 管理系は管理者アカウントを引く（共通基底コントローラの認証処理）。
  - deck-api は会員・プレイヤーを引く（共通基底コントローラの認証処理、トークン生成は認証サービス）。
  - ヘッダ欠落・トークン不正・該当利用者なしは認証拒否（HTTP 401）。
- プロキシ型ログイン（pf-api 管理ログイン）: EC-CUBE 管理画面のログイン画面とログイン確認へ curl でアクセスし、セッション Cookie 経由で認証する。成功時はトークンを含む JSON を返し、失敗時は画面のエラー文言を抽出して認証拒否（HTTP 401）の JSON を返す。
- security.yaml はほぼ無効（`in_memory` の空プロバイダ）。認証はコントローラ層で行う。
- 本文ではトークン原値・`auth_magic`・パスワードを書かない。

## バリデーション（確認値）

- Symfony Form Type と Validator 制約（`Assert\*`）で行う。CSRF は API 用に無効化していることがある。
- カスタム制約の例: マスタ存在チェック（`MasterValue`、対象マスタ表を指定）。
- 検証エラーはメッセージ配列にまとめ、入力不正（HTTP 400）と `errors` 配列で返すことがある。
- 本文では項目ごとに「必須・形式・最大長・マスタ存在」などを書き、未充足時のステータスを示す。

## 入出力スキーマとサンプルレスポンス

「入出力」節では、リクエストとレスポンスのスキーマ情報、およびサンプルレスポンスを定義する。

- リクエストスキーマ — パラメータごとに、位置（パス／クエリ／ボディ）・型・必須／任意・説明を表で書く。位置と型はルート定義（`config/routes.yaml`）、コントローラでの取得方法（パス引数・`@QueryParam`・`$request->get()`・フォーム）、フォーム型や `Assert\*` から確認する。入力が無い参照系は「リクエストパラメータを持たない」と一行で明示し表を省く。
- レスポンススキーマ（成功）— 応答フィールドごとに型・説明を表で書く。型は、直接返すエンティティのプロパティ、`$app->json([...])` 等で組み立てる連想配列のキー、リポジトリの select 項目から確認する。配列・ネストは要素・子フィールドの型まで示す。命名は概ね camelCase。
- レスポンス（失敗）— 該当する HTTP ステータス（400／401／404／500）を、条件と本文の形で対応づける。本文の形は実装確認値（`{code, message}` または `{code, errors:[...]}` 等）。
- サンプルレスポンス — 成功時の応答例を JSON コードフェンスで1つ示す。実トラフィックの値ではなく、実装確認値に基づく代表値とする。トークン原値・パスワード・署名シークレットなどの秘匿値は必ずプレースホルダ（例: `"<jwtToken>"`）にし、実値・実ハッシュを書かない。個人情報は最小限の代表値に留める。

スキーマ・サンプルはあくまでリバース設計の補助であり、本文の主説明はふるまい（誰が・いつ・どの条件で・結果どうなるか）に置く。シーケンス図・ER 図中心の体裁（article-by-params-api.md）には寄せない。

## HTTP ステータスの目安（確認値）

| ステータス | 用途 |
|------------|------|
| 200 | 取得・登録・更新・削除の成功（POST 成功も 200 で本文を返すことがある） |
| 400 | 入力不正・検証失敗 |
| 401 | 認証ヘッダ欠落・トークン不正・認証失敗 |
| 404 | 該当リソースなし |
| 500 | 処理中の例外 |

## CLI/バッチ補足

- deck-api には `app:redis:save`（Redis のデッキ下書きを DB へ保存）がある。pf-api には専用コマンドは無い。
- API に付随する非同期・キャッシュ（Redis）副作用がある場合は「入出力」「データ整合性」で扱う。バッチ本体の設計は [reverse-design-batch](../reverse-design-batch/SKILL.md) を使う。

## 章構成（必須 / 任意）

| 章 | 区分 | 要点 |
|----|------|------|
| 概要 | 必須 | 目的・提供アプリ・呼び出し元・確認値の出所 |
| 本書で扱うこと / 扱わないこと | 必須 | 範囲。同種・旧版エンドポイントは別 API へ |
| 用語 | 任意 | ドメイン語彙 |
| 利用者視点の入口 | 必須 | メソッド+パス+ふるまい、呼び出し元 |
| 認証・認可 | 必須 | 方式・失敗時ステータス・照合先 |
| 処理フロー | 必須 | 入口ごとに番号付き |
| 集計条件 | 任意 | 一覧・検索・件数を返す API |
| 入出力 | 必須 | リクエストスキーマ・レスポンススキーマ（成功）・失敗（HTTP ステータス併記）・サンプルレスポンス・副作用・シリアライズ |
| バリデーション | 必須（入力がある場合） | 項目ごとのルール |
| データ整合性 | 必須 | 参照時点・一致範囲 |
| DBカラム | 必須 | 関係する列のみ |
| 権限・認可 | 必須 | 利用者状態 × API |
| エラー処理 | 必須 | エラー内容 / 処理（ステータス・本文） |
| ログ・監査 | 任意 | 記録内容、出してはいけないもの |
| ページネーション | 任意 | `per_page`・`total_count` を返す API |
| 排他制御・トランザクション | 必須 | ロック・_tx の有無 |
