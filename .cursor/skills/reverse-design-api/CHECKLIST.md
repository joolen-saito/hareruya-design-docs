# リバース詳細設計書（API）— 出力前チェックリスト

設計書を保存する直前に、以下をすべて確認する。

## スコープ・体裁

- [ ] リバース設計の目的が概要に書かれている（実装手順の代替になっていない）
- [ ] 本書で扱うこと / 扱わないことがある（扱わないものは実装または別APIの設計を正とする旨がある。同種・旧版エンドポイントを切り分けている）
- [ ] 「利用者視点の入口」があり、入口ごとに HTTP メソッドとサイトルートからのパスパターンが実装に基づき書かれている。呼び出し元クライアントが分かる
- [ ] Controller クラス名・メソッド名・ルート name を本文の主説明として列挙していない（grep の手がかりは「調査補助」に一行程度）
- [ ] `され得る` などのあいまい表現を避け、確認できたふるまいは断定し、未確定事項は対象外・確認値・別APIとして分けている
- [ ] 本文・表セル・箇条書きに Markdown 太字や HTML strong が無い
- [ ] 和文トークン同士、およびコード／英数字記号トークンと直後の助詞のあいだに不要な半角空白が無い（コードフェンス・URL・パス・カンマ列挙は除外）
- [ ] PHP クラス名・例外クラス名・エンティティ短名を主説明にしていない（論理名へ。テーブル・列・設定キー・ルート name・JWT クレーム名は除外）

## 認証・秘匿

- [ ] 認証・認可の節があり、認証方式（`jwt-token`ヘッダ・HS256・`aud`、またはプロキシログイン等）と認証失敗時の HTTP ステータス（多くは 401）が実装確認値で書かれている
- [ ] 照合先（会員・管理者・プレイヤー等）が分かる。参照系で認可を委ねる場合はその旨が一行ある
- [ ] JWT トークン原値・署名シークレット（`auth_magic`）・パスワード・Cookie 値・セッションID完全値が本文・表・ログ例に含まれていない

## 入出力・データ

- [ ] `functions/todo-list.md` のカスタマイズ区分（標準／現行踏襲／カスタマイズ／新規実装）に応じた参照リポで記述している。標準＝ec-cube-enterprise、現行踏襲・カスタマイズ＝現行APIリポ（pf-api／deck-api等）＋ec-cube-enterprise（移行後の扱い）＋該当基本設計仕様書、新規実装＝基本設計仕様書を正としている
- [ ] Markdown正本と該当Excel基本設計仕様書に同一API・同一仕様の内容が重複している場合、Excel基本設計仕様書を正としている。Markdown側の食い違いはExcelに合わせて更新するか、移行後の扱い・実装確認値として分離している
- [ ] ソース外の業務条件・項目・レスポンス要件は該当基本設計仕様書を正としてマージし、現行API実装との差分は移行後の扱いとして分離している（該当時のみ）
- [ ] DB関連の記述（テーブル名・列名・型・制約・関連、DB更新、副作用、DB列に由来するレスポンス項目）は ec-cube-enterprise リポの実装を正としている。新規実装で ec-cube-enterprise に実装が無い場合は基本設計仕様書を正とし、推測でスキーマ化していない
- [ ] 入出力にリクエストスキーマ（パラメータごとに 位置・型・必須／任意・説明）がある。入力が無い参照系は「リクエストパラメータを持たない」と明示している
- [ ] 入出力にレスポンススキーマ（成功）があり、応答フィールドごとに型・説明が書かれている（配列・ネストは子フィールドまで）。成功時の HTTP ステータスが分かる
- [ ] 失敗時のレスポンスがあり、該当する HTTP ステータス（400/401/404/500）と条件・本文の形（`{code, message}` または `{code, errors:[...]}` など）が実装確認値で対応づけられている
- [ ] サンプルレスポンス（成功例）が JSON コードフェンスで1つ示されている。トークン原値・パスワード・署名シークレット等の秘匿値はプレースホルダになっており、実値・実ハッシュが無い
- [ ] シリアライズ規約（JSON、`serialize_null`、camelCase、ISO8601 日時）が一文で添えられている
- [ ] 入力がある API では、バリデーション（必須・形式・最大長・マスタ存在チェック等）が項目ごとに整理され、未充足時のステータスが分かる
- [ ] 一覧・検索・件数を返す API では、集計条件（対象データ・結合・除外・一意化・並び順・ページング）が整理されている。該当しない参照系は集計なしと明示している
- [ ] ページングを返す API では、`per_page`・`total_count` 等の入出力が整理されている（該当 API のみ）
- [ ] DB カラムは当機能に直接関係する列に限定されている（全列転載していない）
- [ ] データ整合性として、参照時点、更新の有無、一覧と詳細の一致範囲が分かれている
- [ ] 副作用（DB 更新・キャッシュ・履歴・外部連携）が入出力で整理されている。参照のみの API は「副作用なし」を明示している
- [ ] 権限・認可が利用者状態（クライアント種別）とリソースの対応で表になっている

## ふるまいの明確さ

- [ ] 「利用者視点の入口」を起点に処理フローを番号付きで追える（入力受領→判定→取得・更新→応答）
- [ ] エラー処理が表で整理され、HTTP ステータスと本文の対応が分かる
- [ ] 排他制御・トランザクションについて、参照のみは「対象を持たない」、更新系は _tx の境界が書かれている

## 対象外・否定の明示

- [ ] 画面向けの章（フロント挙動・表示メッセージ・入力項目5列表・画面遷移・Cookie/セッション）を持ち込んでいない（認証で必要な範囲は認証・認可へ集約）
- [ ] 集計・ログ・ページネーションについて、該当しない場合は節を削除または「扱わない」と明示している

## 参考との整合

- [ ] 粒度・トーンが `functions/pf-api/a02-01_api_product_popup_product.md` と概ね揃っている（mermaid シーケンス図中心の article-by-params-api.md 体裁と混ざっていない）

## 5分類（章立て）

- [ ] 節は **処理フロー / 入出力 / 業務ロジック / 表示メッセージ / エラー処理** の5つだけである（[[output-exclusion-policy]] 2.5）。旧節（用語・概要・利用者視点の入口・権限・認可・ログ・監査 等）を新設していない。
- [ ] 5節すべてに記述がある。現行ソースに該当が無い節は「該当なし」と**理由・根拠**を書いた（空欄・節ごと省略にしない）。
- [ ] Excel基本設計に無い仕様（処理順・分岐、DB副作用、メッセージ文言、エラー時の挙動）を現行ソースから取り切った。
- [ ] 共通仕様（[[common-spec]]）と一致する横断内容は各機能に書かず、機能固有の差異だけを「業務ロジック」に書いた。
