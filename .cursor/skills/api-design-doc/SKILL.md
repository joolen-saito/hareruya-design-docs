# API設計スキル

## 前提

- 常に `.cursor/design/基本設計方針.md` を正とする。
- API契約の正本は原則として `.cursor/design/API/openapi.yaml` とする。
- 巨大化した場合はOpenAPIの `$ref` で内部分割する。機能別のAPI仕様書を別正本にしない。

## 記載対象

- エンドポイント
- HTTPメソッド
- リクエストパラメータ、リクエストボディ
- レスポンス
- 認証・認可条件
- エラー応答
- 共通スキーマ
- ページング、ソート、フィルタなどの共通仕様

## 作業手順

1. 関連する機能仕様書、画面項目定義書、共通仕様を確認する。
2. APIで扱う業務操作とデータ入出力を整理する。
3. OpenAPIにパス、スキーマ、レスポンス、エラー、認可条件を追加・更新する。
4. 既存スキーマの再利用可否を確認し、同じ概念を重複定義しない。
5. 画面項目定義や機能仕様に書くAPI情報は、API名・呼出目的・入出力概要までに留める。

## 注意

- DBカラムや内部実装の都合をAPI契約へ漏らさない。
- OpenAPIにないAPI仕様をMarkdownだけに書かない。
- HTML閲覧版は `swagger.html` で Swagger UI を提供する。正本 `openapi.yaml` と同内容のフォールバックを HTML 内に持ち、`file://` でも閲覧できるようにする。
- 画面項目定義 HTML の呼び出しAPIパスは、Swagger UI の該当 operation へディープリンクする。
- 認可条件、権限不足時の応答、バリデーションエラーの形式を共通仕様と整合させる。
- 未確定の仕様は `TODO` とし、推測で確定しない。
