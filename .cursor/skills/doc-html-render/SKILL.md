# 正本準拠HTML閲覧版生成スキル

## 目的

Markdown、YAML、CSVなどの正本を、人がブラウザで読みやすいHTML閲覧版へ変換する。仕様内容は正本に従い、HTML化の過程で要約、再構成、補足仕様、推測、図の自動追加を行わない。

このスキルは、読みやすいHTMLを作るためのスキルだが、仕様理解を助けるために内容を作り替えるスキルではない。HTMLは派生成果物であり、仕様の正本にしない。

## 使う場面

- Markdown正本からHTML閲覧版を作成・更新する。
- 既存HTML閲覧版のレイアウト、目次、アンカー、表表示を改善する。
- 長い設計書にサイド固定目次を追加する。
- Markdown正本とHTML閲覧版の内容差分を増やさず、閲覧性だけを上げる。

使わない場面:

- 要約、再構成、エグゼクティブサマリ、サマリカード、追加図解を作る。
- 正本に存在しない説明、判断、リスク、未確定事項をHTML側だけに追加する。
- HTMLを正本として仕様内容を編集する。ただしワイヤーフレームHTMLなど、HTML自体が正本の成果物は除く。

## 変換原則

- 正本の見出し順、本文順、表の列順、行順、箇条書き順を維持する。
- 正本にある文言、TODO、注記、制約、例外、リンク、コード、識別子を欠落させない。
- HTML側だけに仕様文、条件、例外、補足、推測を追加しない。
- 表示改善は、CSS、目次、アンカー、折りたたみ、表の横スクロール、対象要素ハイライトまでに留める。
- リンクは閲覧性のために `.md` から対応する `.html` へ向けてよい。ただし対応先が明確な場合に限る。
- 画面項目定義などでHTMLだけに画面イメージを埋め込む場合も、項目名、状態、バリデーション、アクション仕様は正本側の値を使う。

## 推奨レイアウト

長いHTML閲覧版は、本文の読みやすさを優先して次の構成にする。

1. タイトル。
2. 控えめな `details.doc-meta`。文書情報と改訂履歴を折りたたみで保持する。
3. レスポンシブな2カラムレイアウト。
4. 左側の `aside.sidebar` に、成果物マップとファイル内目次を置く。
5. 本文は正本の見出し順どおりに `main.doc-content` へ配置する。
6. モバイルでは目次を本文上部に移動し、固定表示を解除する。

スタイルの方向性:

- 参照ページのように、説明資料として読み進めやすい静かなトーンにする。
- 背景は白に近い暖色系、本文は高コントラスト、罫線は低彩度にする。
- サイドバーは「On this page」に相当する常時表示ナビとして扱い、成果物マップを上部に置く。成果物マップ全体は `<details class="artifact-map-root" open>` で折りたたみ可能とし、見出し `わりヨシ基本設計` は `<summary>` とする（初期状態は展開）。サイドバー自体は枠線・背景パネルを付けず、`max-height: calc(100vh - 40px)` と `overflow-y: auto` で右側本文とは独立してスクロールする。リンク表示名に `.html` は付けない。ファイル内目次見出し（`.sidebar-title`）は成果物マップ見出しと同じ字号・字間とし、色だけ `--text` で区別する。
- 成果物マップのセクション見出し（全体設計、機能仕様、画面設計、DB設計、API、外部IF、ログ管理、帳票設計）は `<p class="artifact-map-label">` として常時表示する。`<details>` で折りたたむのは、リンクが多数になる「個別機能仕様」「個別画面設計」「テーブル定義」「個別外部IF」「個別帳票設計」とする。現在ページが折りたたみ内にある場合は `open` を付ける。
- API（`Swagger UI（内部API）`）と外部IF（外部インターフェース仕様書・個別IF）は別セクションに分ける。
- 成果物マップの見た目は docs 系の「On this page」目次に合わせ、装飾を抑える。見出し `わりヨシ基本設計` は ON THIS PAGE 相当、セクション見出し（全体設計など）は Request path 相当とする。メニュー本体は `.artifact-map-rail` で左に1本の縦線を通し、各グループ内の個別縦線は使わない。折りたたみ見出しの展開アイコンは `clip-path` の三角とする。
- ページシェル（`.page` / `.sidebar` / `main.doc-content`）は `.cursor/tools/update_page_layout.py` の `doc-shell` ブロックで全HTML閲覧版を統一する。
- 成果物マップの追加・変更は `.cursor/tools/update_artifact_map.py` の `DOCS` を更新して一括反映する。
- 本文 `main.doc-content` も外枠の border / background パネルは付けず、背景に直接載せる。
- 画面設計など横長の表や画面イメージに合わせ、デスクトップでは外枠を幅広に取る。標準の `.page` は `max-width: 1800px` を基準にする。
- 現在ページのリンクは太字とアクセント色で示す。
- `details` は薄い枠と余白で、本文より控えめな補助要素として見せる。
- コード、ファイル名、識別子は薄い背景のインラインコードとして読みやすくする。
- 見出しの前後に十分な余白を取り、カードやチップを増やして本文を細切れにしない。

## 標準配色（2アクセント）

すべての設計成果物HTML閲覧版は、暖色ニュートラル基調 + 2アクセント（clay / olive）で統一する。緑や青の独自アクセント、見出し帯のグラデーションは使わない。`:root` に次のトークンを定義し、各ルールは変数経由で参照する。

```css
:root {
  --bg: #ffffff;          /* ページ背景（白） */
  --panel: #fffdf8;       /* パネル・表の地色 */
  --text: #2b2a26;        /* 本文（墨色） */
  --muted: #7a756a;       /* 補助テキスト */
  --line: #d6cdbd;        /* 罫線 */
  --line-soft: #ebe2d3;   /* 弱い罫線 */
  --band: #f3ede1;        /* 表ヘッダ・帯 */
  --clay: #c25a37;        /* 主アクセント（構造・現在地・強調） */
  --clay-soft: #f4e6dd;   /* clayの淡色背景 */
  --olive: #5f7048;       /* 副アクセント（対の分類） */
  --olive-soft: #e9ecdf;  /* oliveの淡色背景 */
  --accent: var(--clay);
  --accent-soft: var(--clay-soft);
}
```

配色ルール:

- 主アクセントは clay。現在ページリンク、見出しの目印、番号、フローなど構造表現に使う。
- 副アクセントは olive。入力/出力やロジック/例外のように対で区別したい場合にだけ使う。
- アクセントは2色まで。3色目を足したり、彩度の高い色面を広く敷いたりしない。
- バリデーションのエラー表示など、意味的に必要な `--danger` などの色は別途残してよい。デザインアクセントとは役割を分ける。
- 見出し帯や本文に `linear-gradient` の塗りは使わない。単色の `--band` などで表現する。色面の塗りつぶしは淡色トークンに留める。

目次の対象:

- 原則として `h2` と `h3`。
- 文書情報、改訂履歴などのメタ情報は本文目次へ含めない。
- 画面項目定義の番号ピン、表行、画面イメージ内の対象要素には、必要に応じてアンカーを付与する。

## HTML表現ルール

- `section`、`nav`、`aside`、`main`、`table` などの意味要素を使う。
- 表は `.table-wrap` で包み、横スクロールできるようにする。
- 真偽値列（`TRUE` / `FALSE`）は、HTML閲覧版では `TRUE` を `◯`、`FALSE` を空セルとして中央揃えで表示する。正本の文言は維持し、`aria-label` で元の値を残す。
- 画面項目定義のアクションイベント表など、`METHOD /path` 形式の呼び出しAPIは、HTML閲覧版でメソッドをチップ（`.api-method`）とパス（`.api-path`）に分けて表示する。`-` や未設定はそのまま表示する。GET は `--olive` 系、POST / PUT / PATCH / DELETE は `--clay` 系の淡色チップとする。
- 画面項目定義の画面イメージプレビュー（`.wireframe`）は、4px 枠線、角丸、控えめな `box-shadow` で文書本文から視覚的に分離する。ワイヤーフレーム内部の色・影はシンプルに保つ。
- DB ER図の HTML 閲覧版は `.cursor/design/er/schema.mmd` を正本とし、`データベース設計書.html` 内の `<pre class="mermaid">` で描画する。`.cursor/design/er/mermaid.min.js` と最大化用の `mermaid-viewer.*` を用いる。閲覧補助のための最小限の JavaScript を許容する。
- 内部 API の HTML 閲覧版は `API/swagger.html`（Swagger UI）とする。正本は `API/openapi.yaml` とする。`vendor/` 配下の Swagger UI と `file://` 向けフォールバック同梱を用いる。
- 長い表の列名、行数、No.は正本と一致させる。
- セクション見出しへの遷移時に、グラデーションや強いハイライトを付けない。
- 画面項目定義の表行や番号ピンのように、対象要素の識別が必要な場合だけ控えめにハイライトしてよい。
- 文書情報・改訂履歴は、本文見出しと同じ強さにしない。
- 正本にない内容を持つサマリカード、エグゼクティブサマリ、装飾チップ、ステータスバッジは追加しない。
- ただし正本の内容を増減させない範囲で、章や項目を読みやすく束ねる枠組み（セクションのカード化、入出力の2カラム化、箇条書きの定義リスト化、プロセスフローの番号ステップ化）は用いてよい。文言・順序・件数は正本に一致させる。
- 色は「標準配色（2アクセント）」のトークンに従う。淡い背景、低彩度の境界線、読みやすい本文色を基本にする。
- 外部CDNやJavaScriptは原則使わない。必要な場合は、依存理由を明記し、利用者に確認する。

## ワークフロー

1. 正本ファイルと出力HTMLファイルの対応を特定する。
2. 正本の見出し、本文、表、箇条書き、TODO、注記、リンクを抽出する。
3. 正本の順序を保ったままHTMLへ変換する。
4. タイトル直下に `details.doc-meta` を置く。
5. `h2` / `h3` からサイド固定目次を生成する。
6. 表、コード、リンク、アンカー、対象ハイライトを整える。
7. 変換後に `doc-parity-check` の観点で欠落・混入を確認する。

## 完了条件

- 正本にある見出し、本文、表、TODO、注記がHTMLに反映されている。
- HTMLに正本由来でない仕様内容がない。
- 目次リンクが対象見出しへ遷移する。
- 長い表が画面幅を壊さず読める。
- 文書情報と改訂履歴が保持され、本文より目立たない。
- `doc-parity-check` で欠落・混入・表不一致の観点を確認済みである。
