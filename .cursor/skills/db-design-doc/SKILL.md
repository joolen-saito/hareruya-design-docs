# DB設計スキル

## 前提

- 常に `.cursor/design/基本設計方針.md` を正とする。
- DB設計は機能別に分けず、DB設計領域で全体管理する。
- テーブル定義は `.cursor/db/tables/` 配下にテーブルごとに作成する。

## 出力先

- DB全体方針、ER、スキーマ: `.cursor/db/`
- テーブル定義: `.cursor/db/tables/{テーブル名}.md`

## テーブル定義の記載項目

- テーブル概要
- 関連機能
- カラム定義
- 主キー、外部キー
- 一意制約、インデックス
- リレーション
- データライフサイクル
- 論理削除、履歴、監査項目
- 移行・初期データ方針

## 作業手順

1. 関連する機能仕様書、画面項目定義書、API設計を確認する。
2. 業務概念として必要なエンティティ、状態、参照関係を整理する。
3. 既存テーブルで表現できるか、新規テーブルが必要かを判断する。
4. テーブル定義を作成・更新する。
5. ER、スキーマ、API、機能仕様、帳票への影響を確認する。

## 注意

- 機能ごとのDB定義ファイルは原則作らない。
- 機能仕様書には業務データの参照・作成・更新・削除までを書き、カラム詳細はテーブル定義へ寄せる。
- 実装都合だけのカラムにしない。業務上の意味、関連機能、ライフサイクルを明記する。
- 型、NULL可否、制約、インデックスは既存ルールと整合させる。
- HTML閲覧版の真偽値列（NULL、主キー、一意など）は `TRUE` を `◯`、`FALSE` を空セルとして表示する。正本の Markdown は `TRUE` / `FALSE` のまま維持する。
- ER図の正本は `.cursor/design/er/schema.mmd`（Mermaid `erDiagram`）とする。HTML閲覧版は `データベース設計書.html` 内に `<pre class="mermaid">` で同内容を埋め込み、`.cursor/design/er/mermaid.min.js` で描画する。単独の ER 図 HTML は作らない。
- 未確定事項は推測で埋めず `TODO` にする。
