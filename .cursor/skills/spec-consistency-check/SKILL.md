# 仕様整合性チェック

## 目的

要件定義、基本設計、詳細設計、または関連仕様の変更差分を起点に、プロジェクト内の関連ドキュメントを横断して確認し、矛盾、抜け漏れ、影響範囲、具体的な修正案を示す。

本スキルは文書間（要件・設計・画面・API・DB等）の横断整合を扱う。**ソースコードと設計書の双方向の網羅**（実装が設計書に漏れなく反映されているか、設計書の記述がソースで裏付くか）は `../reverse-design/SOURCE-COVERAGE-CHECKLIST.md` を用いる。

## 前提確認

最初に、対象プロジェクトの指示と正本となる参照資料を確認する。

- ルート階層のエージェント指示またはリポジトリ指示があれば確認する。
- ドキュメント固有の指示があれば確認する。
- 用語集、用語定義、ドメインルール、または同等の正本となる用語資料があれば確認する。
- 対象ファイルにより近い場所に具体的な指示があれば確認し、適用可能なものの中で最も具体的な指示を優先する。
- ユーザーが指定した対象ファイル、ディレクトリ、ブランチ、コミット、レビュー範囲を確認する。

## ワークフロー

1. 変更差分を特定する。
   - プロジェクトが Git 管理下にある場合は、変更ファイル名と差分を確認する。
   - ユーザーが対象ファイル、ディレクトリ、コミット、セクションを指定している場合は、その範囲を起点にする。
   - 差分が取得できない場合は、レビュー対象として明示されたファイルを起点にする。

2. 差分から確認軸を抽出する。
   - 追加、削除、変更された画面、API、データ項目、DB テーブル、業務イベント、状態、権限、バッチ、外部連携、通知、用語を拾う。
   - 変更された仕様が何を前提にしているか、上流または下流のどこに波及しそうかを短く仮説化する。

3. 関連ドキュメントを横断確認する。
   - 画面仕様と API 仕様の入力、出力、必須項目、エラー、権限、状態条件を照合する。
   - データ項目定義と DB 設計の型、必須、桁数、制約、enum、初期値、正規化方針を照合する。
   - 業務フローと機能仕様のトリガー、処理順、例外分岐、担当者、通知、取消、差戻しを照合する。
   - 状態遷移図、状態定義、API 更新条件、画面表示条件、バッチ処理条件を照合する。
   - プロジェクトに用語集や用語定義がある場合はそれを正本として扱い、同義語、表記揺れ、意味のズレを確認する。
   - 上流要件、下流設計、テスト、移行、認可、外部システム、運用手順への依存関係を確認する。

4. 問題を分類する。
   - `高`: 実装不能、仕様の衝突、データ不整合、業務フロー破綻、重大な要件欠落。
   - `中`: 実装判断が割れる、画面/API/DB/仕様の片側だけ更新されている、例外や状態条件が不足している。
   - `低`: 用語揺れ、参照漏れ、曖昧な表現、軽微な明確化で解消できる問題。

5. 修正案まで出す。
   - 単なる指摘で終えず、どのファイルのどのセクションをどう変更すべきかを具体化する。
   - 複数の修正案がある場合は、推奨案とその理由を示す。
   - 根拠が弱い場合は推測として明示し、必要に応じて不確実な点に回す。

## 確認観点

必ず以下を確認する。

- 画面仕様と API 仕様の不一致。
- データ項目定義と DB 設計の不一致。
- 業務フローと機能仕様の不整合。
- 状態遷移の矛盾。
- 命名や用語の揺れ。
- 関連仕様間の依存関係の破綻。

必要に応じて以下も確認する。

- 権限、ロール、認可条件。
- エラー、バリデーション、境界値。
- 通知、監査ログ、履歴。
- バッチ、非同期処理、外部連携。
- テスト仕様、受け入れ条件、移行手順。

## 出力形式

ユーザーが出力言語を指定している場合はその言語で出力する。指定がない場合は、ユーザーが使用している言語で出力する。網羅的に確認しつつ、不要に冗長にしない。推測は推測として明示する。

### 1. 検出した問題一覧

重要度順に並べる。各問題は次の形式にする。

- `[重要度] 問題名`
  - 場所: 対象ファイルパスとセクション。
  - 内容: 何が矛盾、欠落、曖昧なのか。
  - 根拠: 照合した関連仕様。
  - リスク: 放置した場合に起きること。

問題がない場合は「重大な不整合は見つかりませんでした」と明示し、確認済み範囲と残リスクを短く書く。

### 2. 影響範囲

変更が波及するファイル、セクション、仕様領域を列挙する。

- 直接影響: 差分が入った仕様と同じ対象を扱う箇所。
- 間接影響: 画面、API、DB、業務フロー、状態、テスト、運用などの上流または下流。
- 未確認だが影響し得る範囲: 影響する可能性はあるが根拠が弱い範囲。

### 3. 修正提案

問題ごとに具体的な直し方を示す。

- 修正対象ファイル。
- 修正対象セクション。
- 追加、変更、削除すべき内容。
- 推奨する整合方針。
- 必要に応じた代替案とトレードオフ。

### 4. 不確実な点

追加確認が必要な事項を列挙する。

- 仕様判断が必要な論点。
- 正本が不明な項目。
- 差分だけでは判断できない前提。
- 関係者確認が必要な業務ルール。

## 注意

- ユーザーが明示的に編集を依頼していない限り、レビュー結果の提示を優先し、仕様書本文は変更しない。
- ファイルやセクションへの言及は、できるだけ具体的に行う。
- プロジェクトに用語集や用語定義がある場合は、それを用語の正本として扱う。
- 依頼されていない限り、全面レビューに広げすぎない。変更差分から合理的に波及する範囲を優先する。
