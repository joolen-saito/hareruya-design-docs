# 機能仕様書作成スキル

## 前提

- リポジトリ内に基本設計方針ファイルがある場合は、その方針を正とする。存在しない場合は本スキルと `reverse-design` の分類別正典ルールを正とする。
- 機能仕様書は機能別に作成する。
- 画面項目、API契約、DB物理定義、帳票レイアウト、ログ保存設計の詳細は各設計書へ委ねる。
- 参照リポと正典は `functions/todo-list.md` のカスタマイズ区分で決める。標準は ec-cube-enterprise を正とする。現行踏襲・カスタマイズは現行リポ（`pf-eccube3` / `pf-api` / `ec-cube` 等）で現行挙動を確認し、ec-cube-enterprise で移行後の扱いを確認し、ソース外の画面・項目・業務条件は該当基本設計仕様書を正としてマージする。新規実装は基本設計仕様書を正とし、ec-cube-enterprise に実装がある場合だけ補助参照する。詳細は `reverse-design` 手順 1a / 1c を正とする。
- Markdown正本と該当Excel基本設計仕様書に同一機能・同一仕様の内容が重複して書かれている場合は、Excel基本設計仕様書を正とする。Markdown側の記述がExcelと食い違う場合は、Markdown正本をExcelに合わせて更新するか、Excelとの差分を移行後の扱い・実装確認値として分離する。詳細は `reverse-design` 手順 1b-1 を正とする。

## 出力先

- Markdown: `functions/<参照リポ>/<機能No小文字>_<機能識別子>.md`
- HTML閲覧版: `function_spec_html_preview/<参照リポ>/<機能No小文字>_<機能識別子>.html`

ファイル名は `functions/todo-list.md` の機能Noを接頭辞として必ず含める。例: `F06-03` は `f06-03_front_member_customer_login.md` のように小文字化して先頭に置く。既存ファイルに機能No接頭辞が無い場合は、MarkdownとHTMLの両方を同じ接頭辞付き basename に揃え、`todo-list.md` のリンクも同時に更新する。複数機能が同一Markdownを共有している場合だけ、無理にリネーム・分割せず、共有理由を確認してから扱う。

## 構成

1. 文書情報
2. 改訂履歴
3. TODO（未確定項目）
4. 機能章

各機能章は `1. 一覧・検索`、`2. 新規登録` のように連番と要件見出しでタイトルを付ける。

## 各機能章の記載項目

- 機能の目的と役割
- 入出力仕様
- 開始条件、終了条件
- 判定条件
- プロセスフロー
- ビジネスロジック
- 状態・データ更新
- 例外処理
- 関連設計への接続点

## 記載ルール

- ビジネスロジックと例外処理は `- **見出し**: 内容` の形式にする。
- 見出しは `アクセス制御`、`排他制御`、`メールアドレスの一意性` のように短く振る舞いが分かるものにする。
- 状態・データ更新には、業務データ単位で何を作成・更新・削除・参照するかを書く。
- テーブル名、カラム名、SQL、クラス名、関数名などの詳細実装へ踏み込まない。
- URLエンドポイントとDBカラムを記載・更新する場合は、`reverse-design` 手順 1a / 1c に従う。標準・現行踏襲・カスタマイズでは ec-cube-enterprise の実装を正とし、人間作成の設計書やリバース済み設計書に記載があっても、Controller のルート定義、Form/Service/Entity/Repository、Doctrine マッピング、Migration 等の実装で確認した値を優先する。新規実装で ec-cube-enterprise に実装が無い場合は、URLエンドポイントとDBカラムも基本設計仕様書を正とし、推測で補完しない。
- 実装で確認できない URLエンドポイントやDBカラムは推測で確定しない。「実装未確認」「実装を正とする」等として扱い、断定的なパス名・カラム名を書かない。
- 機能仕様書には `関連ドキュメント` セクションを設けない。必要な接続点は各機能章内に概要として書く。
- 文書情報には `機能ID` を記載しない。

## HTML閲覧版

- HTMLはMarkdown正本の閲覧版として扱う。
- HTMLだけに仕様内容を追加しない。文言、順序、件数は正本に一致させる。
- HTMLのレイアウト、目次、文書情報、表の表示、配色は `doc-html-render` の方針に従う。
- 配色は `doc-html-render` の「標準配色（2アクセント）」に従い、clay を主、olive を副として使う。

### 標準コンポーネント

各機能章は次の見せ方で構造化する。これは正本の内容を増減させず、見せ方だけを整える枠組みである。

- 機能章のカード化: 各機能章を `section.func` で囲み、見出しに連番の番号バッジ（clay）を付ける。`h2` の `id` は正本の見出しアンカーを維持する。
- 機能の目的と役割: 枠で囲まず、他の見出しと同じ `block-label` 見出し + 本文段落として置く。
- 入出力仕様: 「入力」と「出力」を2カラムのカードに分け、各項目を箇条書きで並べる。入力カードのアクセントは olive、出力カードは clay。正本の入力項目・出力項目の区切りと順序を保つ。
- プロセスフロー: 正本の文を文単位で番号付きステップ（縦並び）に分解して可視化する。語句の追加・要約・並べ替えはしない。
- ビジネスロジック: `- **見出し**: 内容` を「見出し列 + 説明列」の定義リストにする。アクセントは olive。
- 例外処理: ビジネスロジックと同形の定義リストにし、注意の意味でアクセントを clay にする。
- 見出しの目印（`block-label` の縦バー）は、ビジネスロジックは olive、それ以外は clay に合わせる。

### 禁止事項

- 上記の枠組みで正本にない説明、判断、ステータス、補足を足さない。
- 番号ステップ化のために文を作り変えない。フローは正本の文を分割するだけにする。
- アクセントは clay と olive の2色に留める。

## 確認観点

- 要件の判断条件が機能仕様の判定条件に落ちている。
- 要件の例外が例外処理に落ちている。
- 画面項目、API、DB、帳票、ログの詳細を機能仕様に混ぜていない。
- 未確定事項を推測で確定せずTODOに残している。
