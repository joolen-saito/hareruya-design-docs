# E2Eテストケース生成ハーネス（設計書・観点表 → Playwright）

HTML設計書（機能仕様）とテスト観点表・既存IT casesを入力に、**(1) E2Eテストケース表**（人がレビューできる中間成果物）を作り、**(2) ec-cube-enterprise の Playwright 規約に沿った Page Object＋spec** へ橋渡しする。

## ゴールと非ゴール
- ゴール: 設計書の画面・操作・分岐・観点を、ブラウザで観測・自動化できる E2E テストケースに落とし、Playwright（Page Object Model）コードの雛形まで生成する。
- ゴール（機能仕様書＝画面を伴わない仕様も対象）: **画面仕様書だけでなく、画面を伴わない機能仕様書（API・スマレジWebhook連携・バッチ処理・在庫差異修正等）もE2Eテストケースに書き起こす**。これらは「両レイヤ網羅」で扱う（後述）。
- 非ゴール（重要）: **本リポジトリでは Playwright を実行・検証しない**。`ec-cube-enterprise` の Playwright は実行不可で、**構造（ディレクトリ・命名・Page Object/fixture/spec の書き方）の参考のみ**に用いる。生成コードは「実機で実行する前提の雛形」とし、未検証セレクタは明示する。

## 機能仕様書（画面を伴わない）の扱い：両レイヤ網羅（必須）

API（`a*`）・バッチ（`b*`）・連携処理など**画面を伴わない機能仕様**は、次の2レイヤに分けて漏れなくE2Eテストケース化する。各観点は必ずどちらか（または手動/対象外）に分類する。

- **API/統合レイヤ（`E2E自動化(API/統合)`）**: Playwright の `request`（APIRequestContext）で、HTTPエンドポイント（例 `POST /smaregi/stocks`）への送信・Webhook受信・再連携APIの呼び出し・冪等性・バッチの起動（コンソール/トリガーAPI）を行い、**HTTPステータス・レスポンス本文・終了ステータス・出力ファイル・再連携の冪等性**を観測して判定する。ブラウザUIを介さない。
- **UIレイヤ（`E2E自動化(UI)`）**: その機能の**結果が管理画面に現れる範囲**（例: 在庫検索一覧の在庫数反映、在庫変動履歴一覧、在庫切れ/警告の対象一覧・入荷通知）をブラウザ操作で観測して判定する。

注意:
- バッチの起動口（コンソールコマンド／cron／トリガーAPI）が実機依存で本リポジトリから叩けない場合は、API/統合レイヤのケースは設計し spec では `test.fixme`（理由付き）で残す。結果のUI観測が可能ならUIレイヤで補完する。
- スマレジ実環境（外部POS）への実連携や、DB内部値のみ・ログのみで画面にもAPIレスポンスにも現れない観点は `手動`／`対象外`（理由付き）に分類する。
- 期待結果のオラクルは**API/統合レイヤでも設計書/観点表由来**とし、実装のレスポンス形・スマレジ実装挙動・HTTPライブラリ既定値を期待値に流用しない（オラクル独立性は両レイヤ共通）。

## 最重要原則：オラクル独立性（実装の不具合をテストに固定化しない）

テストの**合否判定（期待結果＝オラクル）は「仕様」から導く**。実装（ec-cube-enterprise の挙動・Twig・ソース）からは**セレクタ（機械的な位置情報）だけ**を取る。これを混同すると、実装にバグがあっても「実装どおり」を期待値にしてしまい、**バグごとテストに固定化されてバグを検出できない**。

- **期待結果（合否）の正典 = 設計書（正本md）＋テスト観点表＋基本設計（刷新後の要件）**。実装の現挙動を期待結果として写さない。
- **実装（Twig）から取るのはセレクタのみ**。設計書にセレクタが無いため位置情報だけ実装に依存する。挙動の正否は仕様で判定する。
- **仕様と実装が食い違う点は「不具合候補（仕様乖離）」として別表に出力する**。テストは仕様どおりに書き、実装が違えばテストが落ちて検出する（これがE2Eの価値）。
  - 例: 仕様がボタンA押下で画面Bへ遷移と定めるのに、実装が画面Cへ遷移 → テストは「画面Bへ遷移」を期待し、実装が違えば失敗＝バグ検出。
  - 例: 仕様が必須項目Xを要求するのに Twig に項目Xが無い → 「不具合候補」に記録し、テストは項目Xの存在/必須を期待値にする。
- 設計書自体が現行実装のリバースで書かれている場合、**基本設計（刷新後の要件）とテスト観点表をより上位のオラクル**とし、設計書と基本設計が食い違う箇所は不具合候補・要確認として明示する。
- セレクタが実装由来でも、**「その要素が仕様の要求する部品か」を設計書のUI部品記述で必ず確認**する。仕様に無い実装独自要素をテスト対象にしない（誤認識防止）。

## 入力（正典）
- HTML設計書: `excel_to_html/output/*.html`（基本設計グループ）／`function_spec_html_preview/<repo>/*.html`（機能詳細）。正本は `functions/<repo>/*.md`。**画面仕様書（`m*`）だけでなく、API（`a*`）・バッチ（`b*`）の機能仕様書も対象**（例 `a01-01_api_stock_smaregi_stock_sync`、`b01-02_batch_data_stock_shortage`）。在庫変動・スマレジ連携の業務ルール根拠として `excel_to_html/output/0202_…(在庫管理機能).html`（共通処理／別添資料_在庫変動時の履歴作成／在庫移動ステータス遷移）、`0501_…(API_在庫管理).html`、`0201_…(システム設定).html`（スマレジ用アカウント）も参照する。
- テスト観点表: `integration_test/integration-test-viewpoints.md`（IT-ID）。
- 既存IT cases: `integration_test/<機能No>_*_it_cases.md`（10列TSV）。E2E可能な観点の抽出元として参照する（`a*`/`b*` も同形式で存在する）。
- セレクタ源（位置情報のみ・**UIレイヤ**）: 刷新先 `ec-cube-enterprise` の Twig テンプレート（`src/Eccube/Resource/template/`）。**設計書にセレクタは無いため、必ずここから根拠付きで導出する**。
  - フォーム定義（`src/Eccube/Form/Type/`）は **フィールド名→DOMのid/name の対応（セレクタ）を確認する目的にのみ**使う。**必須・最大長・バリデーション等の制約をフォーム定義から期待結果に流用しない**（オラクル独立性の違反になる。必須/制約の正は設計書・観点表・基本設計）。
- エンドポイント／コマンド源（位置情報のみ・**API/統合レイヤ**）: `ec-cube-enterprise/src/Eccube` の **APIコントローラ（`Controller/**`）のルート（HTTPメソッド＋パス）**、**コンソールコマンド（`Command/**` の `AsCommand` 名）**、ルーティング定義。Webhookパス・認証方式（IP制限等）・コマンド名は**ここから `file:line` 根拠付きで導出**し、創作しない（設計書にパス記載があってもコードで突き合わせる）。確定できないものは `要実機確認`。**期待値（レスポンス形・ステータス意味）は設計書/観点表由来**で、コードの現挙動を流用しない。
- 構造参考: `ec-cube-enterprise/e2e-tests/`（`pages/`・`fixtures/`・`spec/`・`config/`）。**規約の参考のみ**。

## 出力
- E2Eテストケース表: `integration_test/e2e/<機能No小文字>_<機能識別子>_e2e_cases.md`。**テストケースTSVは顧客納品物であり、既存の結合試験テストケース（`<機能No>_*_it_cases.md`）と同一の 10 列 TSV 形式を厳守する**（機能名／テストID／I/FID／テスト観点／優先度／テスト項目名／前提条件／入力データ・リクエスト内容／操作手順・実行方法／期待結果・レスポンス。1行1判定・P1/P2/P3）。E2E固有情報（セレクタ・自動化区分・仕様根拠・シード・不具合候補）は **TSV に列を足さず、TSV後の付帯表**に置く（[TEMPLATE.md](TEMPLATE.md)）。
- Playwright 雛形（構造参考のもとで生成。実行はしない）:
  - Page Object: `ec-cube-enterprise/e2e-tests/pages/<area>/<module>/<screen>.page.ts`（既存があれば拡張）
  - spec: `ec-cube-enterprise/e2e-tests/spec/<area>/<module>/<screen>.spec.ts`
  - 既存 `fixtures/admin_login.fixture.ts`・`config/default.config.ts` を再利用する。

## ワークフロー
1. **スコープ確定**: 対象機能の設計書（正本md）と既存IT casesを読み、画面・操作・分岐・表示メッセージ・状態遷移を棚卸しする。
2. **E2E可否の分類（誤認識・抜け漏れ防止の要）**: 各観点/IT caseを次に分類する。[CHECKLIST.md](CHECKLIST.md) の基準に従う。
   - `E2E自動化(UI)`: ブラウザ操作で再現でき、画面/遷移/メッセージ/URL/Cookie等で観測できる。
   - `E2E自動化(API/統合)`: Playwright の `request`（APIRequestContext）でWebhook/APIへ送信・バッチ起動でき、HTTPステータス/レスポンス/終了ステータス/出力/冪等性で観測できる（画面を伴わない機能仕様の主レイヤ）。
   - `手動`: UI/APIはあるが自動化が高コスト/不安定（メール実受信、外部スマレジ実連携、時刻依存、帳票内容の厳密検査 等）。
   - `対象外`: ブラウザからもAPIレスポンスからも観測不能（DB内部値のみ、バッチ内部のログのみ、純粋なファイル内部構造 等）。**理由を必ず付す**。
   - DB副作用は、画面表示（例: 在庫検索一覧に反映、在庫変動履歴一覧）またはAPIレスポンスで観測できる範囲のみ E2E 化する。
   - **画面仕様書（`m*`）はUIレイヤが中心**だが、**機能仕様書（`a*`/`b*`）は両レイヤ（API/統合＋UI観測）で網羅**する。両者とも `手動`/`対象外` は理由付きで残し、無分類を作らない。
3. **E2Eテストケース表を書く（納品10列TSV）**: 既存IT casesと同一の 10 列 TSV（機能名/テストID/I/FID/テスト観点/優先度/テスト項目名/前提条件/入力データ/操作手順/期待結果）で書く。**期待結果は設計書/観点表（仕様）から導く**（オラクル独立性）。実装の現挙動を写さない。1行1判定。前提条件にはシードセットID（例 `SEED-M01-ADMIN`）を書く。E2E固有（セレクタ・E2E可否・仕様根拠・不具合候補・分類サマリ）は **TSV後の付帯表**に `テストID` で対応づける（[TEMPLATE.md](TEMPLATE.md)）。
4. **セレクタ導出（根拠必須・位置情報のみ）**: 操作対象のセレクタを Twig テンプレート（id/name/ボタン文言の trans キー）から導出し、表の「対象セレクタ」と Page Object に **Twig の file:line を根拠として残す**。テンプレートで確定できないものは `要実機確認` と明示し、創作しない。**セレクタはあくまで位置情報であり、合否は仕様で判定する**。
4b. **仕様乖離（不具合候補）の検出と出力**: 設計書(仕様)が要求する画面・項目・遷移・メッセージと、実装(Twig/ソース)の食い違いを洗い出し、`不具合候補（仕様乖離）` 表に出力する（[TEMPLATE.md](TEMPLATE.md)）。テストは仕様どおりに書き、当該ケースに「仕様乖離あり＝失敗で検出見込み」を注記する。乖離に合わせてテストの期待値を実装側へ書き換えない。
5. **Playwright 雛形生成**: 構造参考（既存 `e2e-tests`）に厳密に合わせて Page Object と spec を生成する。**機能仕様書（`a*`/`b*`）は両レイヤ分を生成する**（UIレイヤ＝Page Object＋spec、API/統合レイヤ＝`request` を使う spec とWebhookペイロード等のヘルパ）。API/統合レイヤの雛形は [TEMPLATE.md](TEMPLATE.md) の「API/統合レイヤ」節に従う。
   - Page Object: コンストラクタで Locator を定義（`#id` / `getByRole('button',{name})` 等）、操作メソッド（`goto`/`login`/`search...`/`fill...`/`see...`）を持つ。既存 `AdminAbstractPage` 継承または `login.page.ts` 形式に合わせる。
   - spec（管理画面）: `import {test, expect} from "<相対>/fixtures/admin_login.fixture"`、`test.describe('<和名> > <画面>', {tag:[...]}, () => { test('<シナリオ>', async ({loginPage, page}) => {...}) })`。`config/default.config.ts` の定数を使う。
   - spec（フロント）: ログイン不要な画面は `import {test, expect} from "@playwright/test"` を直接使う（管理fixtureを強制しない）。会員ログインが要る画面は対応するfixtureを使う。
   - Page Object: `expect` を使う場合は **必ず import する**（`import {expect} from "@playwright/test"` か、既存 `login.page.ts` のように fixture から import）。`AdminAbstractPage` を継承する形（`gotoViaMenu` 等を持つ）と、独立クラス形のどちらかを、対象画面の既存実装に合わせて選ぶ。
   - import の相対パスは、生成先ファイルの階層（`spec/<area>/<module>/...`）から `fixtures/`・`pages/`・`config/` までの実際の深さで算出する（`../` の数を機械的に合わせる）。
   - **spec に残すのは `E2E自動化`（実装済み）と、自動化予定だが未実装/`要実機確認` のケースのみ**。後者は `test.fixme`（理由コメント付き）で残す。**`手動`・`対象外` はケース表でのみ全量管理し、spec に大量の fixme を残さない**（実行結果のノイズ防止）。
5b. **シードデータ要件の集約**: 各ケースの前提（ログイン状態・必要レコード）を [TEMPLATE.md](TEMPLATE.md)「シードデータ要件」表に集約する。**個別に流し込めるシードセット**（独立・べき等・安定キー）として定義し、各セットの**データ源（synthetic／fixture／現行移行 migration）を明記**する。論理要件（必要レコードと値条件）は源非依存で書き、源を差し替え可能にする。**シード実装（実データ生成）は後工程**だが要件はここで確定する。共通ログインは `config/default_login_information.json` を流用する。
6. **セルフレビュー**: [CHECKLIST.md](CHECKLIST.md) をすべて確認。

## 規約（ec-cube-enterprise/e2e-tests から）
- testDir=`e2e-tests`、Page Object Model、`spec/<admin|front>/<module>/<screen>.spec.ts`、`pages/<admin|front>/<module>/<screen>.page.ts`。
- 認証は `fixtures/admin_login.fixture.ts`（`loginPage` fixture）。`ECCUBE_ADMIN_ROUTE/USER/PASS`・`E2E_BASE_URL` は `config/default.config.ts`。
- ロケールは ja-JP、Desktop Chrome、`acceptDownloads:true`。タグ（`@system` 等）で分類。
- セレクタは id 優先、無ければ `getByRole`/文言フィルタ。文言はTwigの trans キー由来であることを確認する。

## 重要原則（誤認識・抜け漏れ防止）
- **設計書網羅性（観点表だけでなく設計書本文を起点に網羅する）**。観点表の分類に加え、**設計書の各節を歩いて、テスト可能な挙動をすべて E2Eケース（自動化／手動／対象外＋理由）へ写像**する。最低限、次の節を起点に漏れを確認する: 利用者視点の入口（画面・URL）／フロント挙動（UI部品）／処理フロー／`判定順序`の各分岐／表示メッセージ（正常・エラー・フラッシュ）／画面遷移／エラー処理／バリデーション・入力項目（境界含む）／DB操作（登録・更新の間接確認）／試行制限／Cookie・セッション／権限・認可。各節→テストIDの **設計書網羅マトリクス**（付帯表）で照合し、未カバー0 を示す（[TEMPLATE.md](TEMPLATE.md)・[CHECKLIST.md](CHECKLIST.md)）。設計書にあって観点表に無い挙動も拾う。
- **ハッピーパスとエラーパスを必ず両方そろえる**。各ユーザーフロー/画面につき、最低1本の正常系（ハッピーパス）と、設計書が定める各エラー/分岐に対応する異常系（エラーパス）を漏れなくケース化する。
  - エラーパスの一次情報源は設計書の **「判定順序」「処理フロー」「表示メッセージ（エラー・警告）」「エラー処理」「バリデーション」** 節、および観点表の異常系行（「…エラーとなること」「失敗」「拒否」「取得/登録/更新されない」等）。
  - 設計書の判定順序に列挙された各失敗分岐（未入力・トークン不整合・試行制限・不存在・停止・不一致 等）を、それぞれ独立のエラーパス・ケースにする。
  - 正常系のみ・異常系のみで終わらせない。フロー単位で正常×異常の対が揃っているかを必ず確認する（[CHECKLIST.md](CHECKLIST.md)）。
- **観点表の該当全行を「E2E自動化／手動／対象外（理由付き）」のいずれかに必ず分類**し、無分類を残さない。ケース表に **分類サマリ（IT-ID別の件数：自動化/手動/対象外）を載せ、未分類0 を全量照合できる**ようにする（抜け漏れ防止）。
- **期待結果の根拠を明示**: 各ケースに「仕様根拠」（設計書のどの節・行、または観点表のIT-ID、基本設計）を記録し、期待結果が仕様由来であることをレビュー可能にする（オラクル独立性の担保）。
- **複合フロー（間接確認）の扱い**: 原則 1ケース1観測だが、ログイン履歴のように「操作した結果が別画面で観測される」副作用検証は、主観測（その画面の主目的）と副観測（間接確認）を分け、1ケース内で許容してよい。その場合も主観測を明確にする。
- **セレクタ／APIパス／コマンド名を創作しない**。Twig・APIコントローラ・コンソールコマンド由来の `file:line` 根拠が無いものは `要実機確認`。
- **観測不能なものを自動化したことにしない**（誤認識防止）。DB内部値のみ・バッチ内部ログのみ・メール実受信などは E2E 期待結果にしない。ただし**APIレスポンス／HTTPステータス／バッチ終了ステータス／出力ファイルで観測できるものは `E2E自動化(API/統合)` として扱う**（画面に出ないことだけを理由に対象外にしない）。
- 生成コードは未実行の雛形である旨を spec 冒頭コメントに記す。
