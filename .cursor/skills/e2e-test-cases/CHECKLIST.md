# E2Eテストケース・Playwright 出力前チェックリスト

E2Eテストケース表とPlaywright雛形を出力する直前に、すべて確認する。SKILL.md の「最重要原則：オラクル独立性」を満たすことを最優先する。

## API/参照系で頻出の落とし穴（生成時に最初から回避＝レビュー指摘の常連）

`a*`（API）・参照系GETで特に繰り返し指摘される。生成段階で必ず潰す:

- [ ] **レスポンス型契約を仕様の型で期待値化**する。正本mdが `price01/price02/stock/weeklySold` 等を **string（数値文字列）** と定義するなら期待結果に型を明記し、実装の `int` キャスト等の差異は**付帯表4の不具合候補**に出す（期待値を実装の int へ寄せない）。フィールド名・綴り（例 `strageCodeId`）も仕様契約として検証対象にする。
- [ ] **仕様に定義の無いステータス/挙動を固定しない**。型不正パスID→404、未知クエリ→200無視、タイムアウト/DB障害時の応答などは正典に無ければ**固定期待にせず `要実機確認`**（または対象外）。「該当なし404」など正典が明記したものだけを固定する。
- [ ] **認可方式が正典で未特定（「pf-api方針」等）なら、認可拒否ケースは `手動（要実機確認）`** に置き、自動化で「拒否応答」を固定しない。実体は付帯表4の要確認に。
- [ ] **値検証はシード期待値と照合**する。成功レスポンスケースは「フィールド存在・型」だけで終えず、**SEEDで投入した既知レコードの期待値と各フィールド値を突き合わせる**（値マッピング誤りを検出可能に）。付帯表3に既知期待値を明記。
- [ ] **送信先パスは実装の実効パスに統一**（TSV本体・付帯表で一致）。設計パスとの差異は付帯表4でのみ管理し、本体期待値に設計パスを混在させない。
- [ ] **エラー/フォールバック観点（決済代行・外部キャッシュ・転送再連携等）が本機能に非該当なら対象外で一貫**させ、**付帯表2の集計と付帯表2bの行単位分類を意味レベルで一致**させる（非該当観点をE2E自動化へ流用しない）。
- [ ] **区分値は4区分本体に統一**（`E2E自動化(UI)/E2E自動化(API/統合)/手動/対象外`）。`要実機確認`/`間接` は括弧の修飾子。`E2E自動化(API/統合)` と `自動化(API/統合)` のような表記揺れを作らない。
- [ ] **1行1判定**を徹底（真値/偽値/未指定、フィールド整合＋副作用なし、認可あり/なし等を1セルに詰めない）。
- [ ] **禁止語を残さない**（`設計どおり`/`設計書に記載のとおり`/`UI標準`）。リポ名 `pf-api` の綴りミス（`pf-apr` 等）も無いこと。

## バッチ（`b*`）で頻出の落とし穴（生成時に最初から回避）

- [ ] **付帯表2は母集合（既存IT cases の行数）で集計**する。E2Eケース件数で集計しない（付帯表2と付帯表2bの母集合を一致させ未分類0）。母集合外の補完ケースは別管理で明示。
- [ ] **終了コードの実値（0/非0）・処理件数のコンソール出力・出力形式を期待値化しない**。正常終了/異常終了の「扱い」で判定し、件数出力・メール通知など正本mdに規定の無い実装挙動は**付帯表4の実装差分**に留める。
- [ ] **DB内部値のみ（在庫数・履歴行の有無/件数・create_date・区分値の内部表現等）はE2E対象外**（IT層のDB副作用検証で担保）。**管理画面に表示される範囲のみUI観測**（在庫変動履歴・一覧等、Twig file:line根拠）。
- [ ] **観点表のファイル出力/受信検証/重複順序/外部取得 等を、該当処理の無いバッチへ読み替えて自動化に算入しない**。非該当は対象外（理由付き）。CSV出力系は正本mdがCSVを規定するなら**CSV列定義・件数・0件・出力失敗をオラクル**にし、刷新先がDB方式なら正本mdの移行表（刷新後要件）を精読して判断（DB方式が上位要件なら移行差異を付帯表4へ）。
- [ ] **バッチ起動口（コンソールコマンド名・cron・Step Functions）を `src/Eccube/Command` 等で grep 実在確認**し file:line 根拠を記す。実在しても**起動は実機依存のため spec は test.fixme 前提**。未実装/未特定は創作せず `要実機確認`。コマンド名不一致のような**フレームワーク層(起動前)エラーは本バッチ観測外＝対象外**。
- [ ] **正常×異常の対**（対象あり/対象0件 no-op/異常終了/出力失敗/不正入力）を揃える。**対象0件時に冒頭DELETE等で全削除し得る実装は付帯表4に重大乖離として明示**。
- [ ] **メール送信系**は送信操作・送信有無までを期待値にし、本文・件名・宛先・実受信は手動/別機能委譲。機微値をログに残さない観点は観測可能なら手動で。

## オラクル独立性（実装の不具合をテストに固定化しない）

- [ ] 各ケースの**期待結果（合否判定）が設計書/観点表（仕様）から導かれている**。実装の現挙動をそのまま期待値にしていない。
- [ ] セレクタ以外（遷移先・表示文言・状態・必須/エラー判定）を実装由来で確定していない。仕様で判定している。
- [ ] 実装（Twig/ソース）から取得したのは**セレクタ（位置情報）のみ**であり、合否の正は仕様である。
- [ ] **フォーム定義(Form/Type)は id/name のセレクタ確認にのみ使い、必須・最大長・制約・バリデーションを期待結果に流用していない**（制約の正は設計書・観点表・基本設計）。
- [ ] 各ケースに **`仕様根拠`（設計書の節・判定順序番号・観点ID・基本設計）が記載**され、期待結果が仕様由来であることをレビューできる。
- [ ] 設計書が現行実装のリバースに由来し、基本設計（刷新後要件）と食い違う箇所は、**基本設計/観点表を上位オラクル**として扱い、要確認を明示した。
- [ ] 仕様に存在しない実装独自要素をテスト対象にしていない（誤認識防止）。

## 不具合候補（仕様乖離）の検出

- [ ] 仕様（画面・項目・必須・遷移・メッセージ）と実装（Twig/ソース）を突き合わせ、食い違いを「不具合候補（仕様乖離）」表に列挙した。
- [ ] 乖離に合わせてテストの期待値を実装側へ書き換えていない（テストは仕様どおり＝落ちて検出する）。
- [ ] 各不具合候補に、関係するE2EケースIDと根拠（Twig/ソース file:line）を付した。
- [ ] 読み切れない箇所は `要確認`（実機確認待ち）として残し、創作で埋めていない。

## 納品TSV形式（既存IT casesと同一・厳守）

- [ ] テストケースTSVが **10列固定**（機能名／テストID／I/FID／テスト観点／優先度／テスト項目名／前提条件／入力データ・リクエスト内容／操作手順・実行方法／期待結果・レスポンス）で、既存 `<機能No>_*_it_cases.md` と同一形式である。**E2E固有の列を TSV に足していない**。
- [ ] `機能名` が全行同一（元設計の表示名）。`テストID` が一意（`E2E-<機能No>-NNN`）。優先度は `P1`/`P2`/`P3` のみ。
- [ ] **期待結果／レスポンスは1行1判定**。期待結果以外で複数項目はセル内 LF 改行。改行や `"` を含むセルはダブルクォートで囲む。
- [ ] E2E固有情報（セレクタ・E2E可否・仕様根拠・シード・不具合候補・分類サマリ）は **TSV後の付帯表**に置き、`テストID` で対応づけている。
- [ ] `I/FID`・`テスト観点` が観点表（`integration-test-viewpoints.md`）に一致している。

## 設計書網羅性・観点表反映（必須）

- [ ] **設計書の各節を起点に網羅**した。利用者視点の入口／フロント挙動／処理フロー／`判定順序`の各分岐／表示メッセージ（正常・エラー・フラッシュ）／画面遷移／エラー処理／バリデーション・入力項目（境界）／DB操作／試行制限／Cookie・セッション／権限・認可——のテスト可能な挙動が E2Eケースに写像されている。
- [ ] **設計書網羅マトリクス（節→テストID）** を作り、未カバーは理由（観測不能・別機能委譲等）付きで明示し、放置していない。
- [ ] **設計書にあって観点表に無い挙動**（例: 判定順序の特定分岐、固有メッセージ）も拾っている。
- [ ] **テスト観点表の反映**: 当該機能の既存IT casesが使う全関連ID（例 IT-15/20/22/23/25/26/03/13）が、E2E側で `自動化／手動／対象外` に分類され（分類サマリ・未分類0）、観点の取りこぼしが無い。
- [ ] `I/FID`・`テスト観点` 列が観点表の文言と一致している。

## ハッピーパス／エラーパスの網羅（必須）

- [ ] 各ユーザーフロー/画面に **正常系（ハッピーパス）が最低1本** ある。
- [ ] 設計書の **「判定順序」に列挙された各失敗分岐**（例: 未入力・トークン不整合・試行制限・不存在・停止・パスワード不一致 等）が、**それぞれ独立のエラーパス・ケース**になっている。漏れが無い。
- [ ] 設計書の **「表示メッセージ（エラー・警告）」「エラー処理」「バリデーション」** の各エラーが、対応するエラーパス・ケースに反映されている。
- [ ] 観点表の異常系行（「…エラーとなること」「失敗」「拒否」「取得/登録/更新されない」等）が、対応するエラーパス・ケースまたは `手動/対象外` に分類されている。
- [ ] **フロー単位で正常×異常の対が揃っている**（正常系のみ・異常系のみで終わっていない）。
- [ ] 境界値（最大長/最小長/＋1/−1 等、観点表 IT-22）が必要な入力項目について、正常（境界内）と異常（境界外）の両方がある。

## 両レイヤ網羅（機能仕様書 `a*`/`b*`＝画面を伴わない仕様。画面仕様書 `m*` は該当時のみ）

- [ ] 各観点を `E2E自動化(UI)` / `E2E自動化(API/統合)` / `手動` / `対象外` のいずれかに分類した（**画面に出ないことだけを理由に対象外にしていない**＝APIレスポンス/HTTPステータス/終了ステータス/出力で観測できるものは API/統合 に入れた）。
- [ ] **API/統合レイヤ**: Webhook/APIエンドポイント（HTTPメソッド＋パス・認証方式）・コンソールコマンド名を、APIコントローラ/Commandの **`file:line` 根拠**で記した（**創作禁止**・無ければ `要実機確認`）。
- [ ] **UIレイヤ**: その機能の結果が管理画面に現れる範囲（在庫数反映・在庫変動履歴・在庫切れ/警告一覧・入荷通知）を、観測可能ならUIケースとして拾った。
- [ ] **API/統合レイヤの期待値も設計書/観点表由来**（レスポンス形・スマレジ実装挙動・HTTPライブラリ既定値を期待値に流用していない）。
- [ ] Webhook/バッチの**正常×異常の対**がある（受信: 売上02/返品12正常 × 形式不正・重複・順序・部分失敗・スロットリング時ロールバック／バッチ: 対象あり・対象0件・異常終了）。
- [ ] **スマレジ実環境（外部POS）への実連携**・実メール・時刻依存は `手動`/`対象外`（理由付き）に置き、自動化したことにしていない。
- [ ] 起動口が実機依存のバッチ/Webhookは spec で `test.fixme`（理由付き）に留め、結果のUI観測が可能なら別途UIレイヤで補完した。
- [ ] 分類サマリ表に `自動化(UI)` と `自動化(API/統合)` を分けて集計し、合計が母集合と一致（未分類0）。

## 観点の網羅と分類（抜け漏れ防止）

- [ ] 該当するIT-IDを **分類サマリ表**（IT-ID別の自動化/手動/対象外の件数）に挙げ、**未分類0** を全量照合できる。
- [ ] 各行を `E2E自動化` / `手動` / `対象外` のいずれかに分類し、無分類が無い。
- [ ] 境界値は観点表 IT-22 に加え、**設計書の入力項目定義（最大長/最小長等）も一次情報源**として拾い、観点IDが別でも漏らさない。
- [ ] `手動`・`対象外` には理由（観測不能・外部依存・時刻依存・実メール等）を付した。
- [ ] DB副作用は、画面表示で観測できる範囲のみ E2E 化し、内部値のみの観点は `手動/間接` または `対象外` とした。
- [ ] 既存IT casesと突き合わせ、E2E化すべき主要シナリオ（正常・異常・境界・遷移）に漏れが無い。
- [ ] `元ITケースID`・`I/FID` でトレースできる。

## シードデータ要件（実装は後・要件は今）

- [ ] 各E2Eケースの「前提(ログイン/データ)」が宣言され、必要レコードと値条件が分かる。
- [ ] それらを **個別に流し込めるシードセット**（独立・べき等・安定キー）に集約した。一括投入を強制していない。
- [ ] 各シードセットに **データ源（synthetic／fixture／現行移行 migration）** を明記し、論理要件は源非依存で書いた（源を差し替え可能）。
- [ ] 共通ログインは `config/default_login_information.json` を流用し、不要な重複シードを作っていない。
- [ ] `migration`（現行pf-eccube3からの移行）を充てる場合、DB対応は ec-cube-enterprise 正典（reverse-design 1c）に従う旨を明記した。
- [ ] 生成データの後始末（撤去/使い捨て/識別接頭辞）を定義した。

## 論理名（物理名を書かない・[[logical-naming]]）

- [ ] ケース表・付帯表・Page Object/spec のコメントに、翻訳キー・セッションキー・フラッシュキー・ルート名・DB物理名（`dtb_`/`mtb_`/`plg_`）が無い（根拠としての併記も不可）。
- [ ] メッセージは `e2e/config/logical-names.tsv` のメッセージID＋画面上の文言で書いた（表に無いものは出典付きで行を足した／作れないものは `要確認` にして観測できる事実で判定した）。
- [ ] 翻訳キー未定義で生キーが表示される件は不具合候補に出し、生キー文字列を期待値にしていない。
- [ ] セレクタ・`file:line`・HTTPパス・コマンド名・SQL/シードは物理のまま残してよい範囲に収まっている（論理名化して実行不能にしていない）。
- [ ] `python3 .cursor/skills/logical-naming/scripts/audit_logical_naming.py --repo .` が `AUDIT OK` である。

## セレクタの根拠（創作禁止）

- [ ] すべての対象セレクタに Twig 由来の根拠（file:line、id/name/trans キー）がある、または `要実機確認` と明示している。
- [ ] ボタン・リンクの文言は Twig の trans キー由来であることを確認した（ハードコード和文を勝手に断定しない）。
- [ ] 仕様が要求するUI部品が Twig に見当たらない場合、テストを省略せず「不具合候補」に出して仕様どおりの期待値で書いた。

## Playwright 雛形の構造準拠（ec-cube-enterprise/e2e-tests は参考のみ）

- [ ] Page Object は `pages/<area>/<module>/<screen>.page.ts`、spec は `spec/<area>/<module>/<screen>.spec.ts` に置く命名・配置である。
- [ ] 認証は `fixtures/admin_login.fixture.ts` の `loginPage` を使い、定数は `config/default.config.ts`（`ECCUBE_ADMIN_ROUTE/USER/PASS`）を使う。
- [ ] Locator はコンストラクタで定義し、各 Locator に由来 Twig を **file:line** コメントで残した。
- [ ] Page Object で `expect` を使う場合、**`expect` を import している**（独立形は `@playwright/test`、fixture経由も可）。TypeScriptとして壊れていない。
- [ ] 管理画面spec は `admin_login.fixture`＋`loginPage`、**フロントspec は `@playwright/test` を直接使う**（管理fixtureを強制しない）。既存画面が `AdminAbstractPage` 継承なら踏襲する。
- [ ] import の相対パス（`../` の数）が生成先の階層に正しく合っている。
- [ ] spec に残すのは `E2E自動化(UI/API/統合)`（実装済み）と、自動化予定だが未実装/`要実機確認`（`test.fixme`）のみ。**`手動`・`対象外` はケース表で全量管理し、spec に大量の fixme を残していない**。
- [ ] spec 冒頭に「本リポジトリでは未実行の雛形。ec-cube-enterprise の Playwright は実行不可で構造参考のみ」と明記した。
- [ ] **機能仕様書（`a*`/`b*`）は両レイヤ分を出力**: API/統合 spec は `spec/api/<module>/<id>.api.spec.ts`（`request` 使用）、バッチ spec は `spec/batch/<module>/<id>.batch.spec.ts`、UIレイヤは `spec/admin/...`。ペイロード/ヘルパは `pages/api/<module>/<id>.api.ts`（TEMPLATE.md §4 準拠）。
- [ ] API/統合 spec の `request` 送信先・パスは `file:line` 根拠の実在エンドポイントで、認証(IP制限等)・前提は SEED/環境ガード(`test.skip`)で表現した。
