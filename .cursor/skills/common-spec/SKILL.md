# 共通仕様スキル

## 目的

機能設計書405本（`functions/<区分>/*.md`）に繰り返し書かれている定型の節を、`common_spec/共通仕様.md`
と `excel_to_html/output/0000_共通仕様.html` の1本へ集約する。各機能のHTMLからは同じ節を落とすが、
**落とすのは共通内容と一致すると判定された機能だけ**で、機能固有の内容を持つ機能では残す。

## 原則（捏造ゼロ）

- 共通仕様の本文は、実際の機能設計書に書かれている文字列を**そのまま**採録する。要約・言い換え・補筆をしない。
  採用した本文には出典（`path:line`）と同一本文の件数を必ず付ける。
- 共通か例外かの判定は決定的なルールだけで行う。判定できないものは**例外（＝各機能に残す）へ倒す**。
  取りこぼしは「まだ共通化できていない」だけで済むが、誤って共通化すると機能固有の仕様がHTMLから消える。
- Markdown正本は一切変更しない。除外はHTML生成時の措置で、正本を読めば内容は残っている。

## 対象節と判定ルール

| 節 | 適用範囲 | 判定 |
|---|---|---|
| 試行制限 | 全区分 | 本文クラスタ一致 or 非該当宣言 |
| Cookie | 全区分 | 同上 |
| 排他制御・トランザクション | 全区分 | 同上 |
| セッション | 全区分 | 同上 |
| 権限・認可 | **管理画面のみ** | 同上（フロント・APIは全件が機能固有のため対象外） |
| ログに出してはいけないもの | 全区分 | 箇条書きの項目集合が共通語彙に収まるか |

- **本文クラスタ一致**: 機能固有トークン（コードスパン・機能ID・`dtb_*`等のテーブル名・URL/パス・英数識別子・数字）を
  伏字化したうえで最大クラスタ（10本以上）と一致する。
- **非該当宣言**: 「扱わない／持たない／設けない／保存しない…」を含み、表も小見出しも持たず400字以下。
- **共通語彙**: 対象文書の50%以上に現れる項目。それ以外の項目を1つでも含む文書は例外。
- 「ログ・監査」節そのものは共通化しない（324本中321本が機能固有の記録内容を持つため）。禁止リストの小見出しだけを集約する。
  節の出力可否は別ルール（カスタマイズ区分が現行踏襲／カスタマイズの機能のみ出力）で、[[output-exclusion-policy]] を参照。

## ハーネス（実行）

```bash
S=.cursor/skills/common-spec/scripts/build_common_spec.py

python3 "$S" extract   # 全機能設計書を走査し common_spec/common_spec_data.json を作る
python3 "$S" build     # data JSON から 共通仕様.md と 0000_共通仕様.html を生成
python3 "$S" verify    # data JSON と生成物の同期・共通一致0本でないことを検査
```

- `common_spec/common_spec_data.json` が**判定台帳**。節ごとに `common_text`（採用本文）・`source`（出典）・
  `members`（共通化して各機能から落とす機能）・`exceptions`（残す機能と理由）を持つ。
- 各機能HTMLの除外は [[function-spec-html-render]] の `common_spec_titles()` がこの `members` を読んで行う。
  台帳が無い場合は何も落とさない（安全側）。
- Markdownや機能設計書を更新したら `extract` → `build` → `verify` の順で回す。`extract` を飛ばすと判定が古いままになる。

## 完了条件

- `common_spec/共通仕様.md` と `excel_to_html/output/0000_共通仕様.html` が data JSON と同期している（`verify` が OK）。
- 各節の `members` が0本でない。例外機能は理由付きで一覧できる。
- 各機能HTMLでは `members` の機能からのみ対象節が消え、例外機能では残っている
  （`cd excel_to_html && uv run python verify.py` の「出力除外セクション見出し: 0件」で機械確認）。
