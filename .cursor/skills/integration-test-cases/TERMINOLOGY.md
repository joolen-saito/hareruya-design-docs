# 結合試験テストケース用語

結合試験の Markdown／TSV では、ここに書いた語だけを使い、同じ意味を別の言い回しで書かない。

## ログイン完了後の管理画面

管理者としてログインし、必要なら二段階認証も済ませたあとに操作できる EC-CUBE の管理側の画面や機能を指す。リバース設計書の「保護された管理画面」「未ログインでは利用できない管理側の機能」と同じ範囲である。

### 使い分け

| 書き方 | 使う場面 |
|--------|----------|
| ログイン完了後の管理画面 | 画面そのものを指すときの総称 |
| ログイン完了後の管理画面の URL | アドレス欄に打ち込む URL を指すとき |
| ログイン完了後の管理画面のメニュー | メニューから別画面へ進む操作を書くとき。「別のログイン完了後の管理画面のメニュー」のように重ね書きしない |
| ホーム画面 | ログイン成功直後などに開く代表画面の名称。ログイン完了後の管理画面に含まれる |

### 使わない表現

次は書かない。意味がぶれるためである。

- 保護画面、保護 URL、保護メニュー、保護された管理画面、保護された管理機能
- 業務画面だけでの総称。本文で管理側の画面を指すときは「ログイン完了後の管理画面」に統一する
- 「管理ホーム」。ログイン後すぐ開く代表画面は「ホーム画面」と書く

### 二段階認証が途中のとき

ID とパスワードだけ通って追加認証がまだの状態では、ログイン完了後の管理画面はまだ利用できない。このときはその旨を文に明示する。

## 優先度（リスク基準）

テストケースの「優先度」列には **P1 / P2 / P3** のみを書く。限られた期間で効果を最大化するためのリスク基準であり、機能ごとに次の観点で振り分ける。

| 値 | 意味 |
|----|------|
| P1（最優先） | 金額・在庫・個人情報・権限に関わるフローに直結する。購入確定、受注ステータス遷移、在庫増減、ポイント、決済または外部連携、**管理権限および認証境界**など。 |
| P2（重要） | 運用頻度が高い処理、または UI 整合性として重要な領域。検索、CSV 入出力、メール通知、日次業務寄りの操作、ログイン周辺の再利用性の高い確認など。 |
| P3（通常） | 頻度が低い機能、周辺設定、表示のみ、環境依存が強い任意確認、詳細境界の補強など。 |

機能が管理認証のときは、未認証での保護資源アクセス、資格情報検証、セッション、二段階認証境界、監査・秘匿、試行制限などは原則 **P1** とする。

## 文体

テスト項目名・前提・操作手順・期待結果に「または」を書かない。別パターンは操作手順を番号で分け、期待は**観測・判定可能な一文**にまとめる。

## 期待結果とテスト項目名（1行1判定）

結合試験 TSV では、**期待結果／レスポンス列は1データ行につき1つの判定観点のみ**とする。一部OK・一部NGを記録しやすくするため、複数の期待を1セルに箇条書きや「・」で並べない。

### 行に分割する

次は**別データ行**に分ける。

| 種類 | 例 |
|------|-----|
| 画面とHTTP・DB・遷移など観測対象が異なる | 認証成功／ホーム遷移／履歴INSERT |
| 同一画面でも判定が独立 | ログインID欄表示、パスワード欄表示、送信ボタン操作可、CSRF hidden |
| 属性・キーごと | Cookie の HttpOnly／Secure／SameSite、POST の login_id／password |
| 「、」で並ぶ独立した結果 | 入力可・送信可・エラー表示可（ブラウザ試験） |

### 1行のままにする

次は**1データ行・1期待結果セル**のままよい。

| 種類 | 例 |
|------|-----|
| 1つの観測でまとめて判定 | ログインフォーム一式が操作可能であること |
| 名詞の並列のみ | 「ログインID・パスワード」の入力欄（項目名の説明） |
| 1つのDB行・1つのHTTP応答 | 成功区分の行が1件追加されること |

### テスト項目名

- **テスト項目名は当該行の判定が分かるよう具体化**する。分割した行で親シナリオ名をそのまま繰り返さない。
- よい例：`有効なログインID・パスワード送信で認証が成功すること`（期待が認証成功の行）
- 避ける例：分割後も「認証が成功しホームへ遷移すること」という複合名を全行にコピーする

### 繰り返してよい列

同一シナリオを分割した行では、**前提条件・入力データ・操作手順**は同じ内容を繰り返してよい。期待結果とテスト項目名だけ行ごとに変える。

## 期待結果に書かないこと

結合試験の前提・期待から次を避ける。設計書は試験の「入力・スコープ」の参照に留め、合格判定を設計書の有無に依存させない。

- 「設計書に記載のとおり」「設計書が定めるとおり」「設計どおり」「方式設計に従う」など、設計書を期待の根拠にする表現
- 特定の `.md` 設計ファイル名を期待結果の正とする記述（例：`m01-01_admin_login_login.md` と一致すること）

代わりに、画面・HTTP・DB・ログ・Redis などで確認する具体項目、試験計画または環境仕様で合意した値、既知の実装確認値を書く。

## 文字列長・境界（IT-41 等）

入力データ・前提・テスト項目名では、**「製品設定の上限」「アプリ共通の長さ制約」などの言い回しは使わない**。元設計の入力項目表に合わせ、**最大長**（および max+1 境界）として書く。

- よい例：`passwordを最大長ちょうどとし、login_idも正しく送信する`
- 避ける例：`password長を製品設定の上限ちょうどにする`

## 試行制限・レートリミット（ログイン試行など）

期待結果では **「同一窓」「誤爆」** のような通じにくい略語やインフラ寄りの語を使わない。**誰がどの単位でカウントされるか**をそのまま書く。

- よい例：`別のログインIDまたは別IPの試行が、意図しないキー単位へひもづいてまとめてカウントされないこと`
- 避ける例：`同一窓での誤爆や誤カウントがないこと`

「時間窓」が必要なら **試行制限期間**や **カウント対象とする期間** と書く。

## TSV 列とテスト観点.md の対応

結合試験 TSV の **1行目ヘッダ**（先頭列 `機能名`）は [TEMPLATE.md](TEMPLATE.md) 固定。**テストレベル列（IT1／IT2 等）は出力しない**（Gherkin エクスポートは `.cursor/test/stock/sheet_mapping.md` を参照）。特に次の2列を混同しない。

| TSV 列名 | テスト観点.md の列 | 例 | 使わない旧称・誤り |
|----------|-------------------|-----|-------------------|
| I/FID | 関連ID | `IT-04` | `IF-ADMIN-LOGIN-01`、`I/F ID` |
| テスト観点 | 観点 | `ログイン状態判定` | 列名 `観点`（旧TSV列名）、`I/F種別`、`画面→認証基盤`、旧ケース要約列 |

**テスト観点** 列の値は、テスト観点.md の当該行の **観点** 列からコピーする（**観点分類** 列ではない）。

機能ごとの連携先ラベル（`画面→認証基盤` など）は使わない。関連ID・観点が一覧に無い場合は、最も近い行を選び、対象外観点またはトレース表で理由を書く。
