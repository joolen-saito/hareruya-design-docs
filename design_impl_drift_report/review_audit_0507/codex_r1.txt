# Design Impl Drift Audit

## Purpose

Use this skill to audit functional differences between HTML design specifications and an implementation repository, with the design docs treated as authoritative. Produce or continue a report that lists concrete differences with design locations, implementation locations, confidence, severity, and impact.

## Repository Discovery

1. Find the design-doc directory and implementation directory from the user request. If omitted, infer from nearby names such as `*-design-docs` and application repos.
2. Look for an existing report before starting new work. Prefer directories named `design_impl_drift_report`, existing `findings.json`, per-function `findings/*.json`, and `index.html`.
3. Count total target specs and audited specs so the report clearly states scope and remaining work.
4. Preserve existing findings. Append or refine; do not overwrite unrelated prior work.

## Audit Workflow

For each target HTML spec:

1. Identify the feature ID, route/action name, UI template, CSV/batch/API behavior, and acceptance rules from the HTML design spec.
2. Extract a requirement inventory from the HTML spec before looking at code. This inventory must include not only route/screen names, but every concrete requirement in 処理概要, 図形・テキストボックス, 項目表, 表示メッセージ, 業務ルール・計算, 入力項目, エッジケース, データ整合性, API/バッチ結果, 入出力, DB操作, バリデーション, 権限・認可, 画面遷移, エラー処理, ログ・監査, セッション, Cookie, and 排他制御. Treat bullets such as "押下時", "場合", "登録/更新/保存", "遷移", "保持", "表示/非表示", "表示切り替え", "エリアを表示", "誘導", "エラー", "判定", "連携", time limits, thresholds, and retry/idempotency rules as auditable requirements. 秒後/分後, `画面を表示してから`, 自動遷移, タイマー, and store/kiosk/account-specific forced redirects are material requirements even if the route and template already exist.
3. For every extracted requirement, create or mentally maintain a `requirementTrace` row with: `requirementId`, `designRef`, `designRequirement`, `implementationSearchTerms`, `implementationRefs`, `implementationActual`, `traceVerdict` (`MATCHED|DRIFT|NOT_FOUND|UNCERTAIN|PHASE2_EXCLUDED`), and `traceReason`. A feature cannot be marked no-drift until all material requirements have a trace verdict other than `NOT_FOUND` or unresolved `UNCERTAIN`.
4. Search the implementation with `rg` across likely files: controllers, services, repositories, form types, entities, migrations, Twig/templates, commands/batches, route definitions, JavaScript, CSV exporters/importers, and PDF/print services. Search by business terms from the requirement, route names, translation keys, DB columns, state names, constants, statuses, time values, thresholds, and side-effect verbs. For timer or auto-navigation requirements, explicitly search client and server paths for `setTimeout`, `setInterval`, millisecond/second constants such as `60000` and `60 * 1000`, `location.href`, `location.assign`, `location.replace`, redirect routes, and the condition that limits the behavior. For a negative result, also search nearby implemented flows so the report can explain why they do not satisfy the design.
5. Compare behavior and user-facing text, not just names. Check input fields, validation, defaults, search conditions, session persistence, buttons/actions, labels, button text, messages, translation keys/locales, permissions, status transitions, CSV columns, sort/order rules, scheduled timing, timeouts/expiration, thresholds, client-side timers, forced auto-navigation, side effects, idempotency, external integrations, conditional display toggles, alternate UI areas, and error handling.
6. Do not treat "route/controller/template exists" as sufficient. Existence only satisfies the route/screen requirement. It does not satisfy individual rules inside the screen, such as timeout handling, cart retention, validation branches, status transitions, DB writes, logging prohibitions, conditional hide/show behavior, alternative contact/help areas, or external API retry behavior.
7. For conditional display requirements, audit each side of the condition separately. If the HTML says "Aの場合はXを非表示、Yを表示 / A以外はXを表示、Yを非表示", record trace rows for the condition detector, X visibility, Y visibility, and the inverse condition. A nearby notice or route is not enough unless the cited template/JS actually renders the required area under the required condition.
8. For labels, button text, messages, and translation keys, do a dedicated near-match pass. Extract user-visible Japanese text from the HTML item/message tables and compare it with implementation locale values and Twig/Form usage. Treat punctuation, okurigana, missing characters, long-vowel marks, wording changes such as `商品を追加` vs `商品の追加`, and business-term changes such as `返金` vs `送金` as audit targets.
9. A text drift finding is complete only when it cites both the translation/source value and the display path that uses it, such as `messages.ja.yaml` plus the `FormType` label or Twig `|trans` call. If the implementation value exists but no display path is verified, mark it `UNCERTAIN` instead of presenting it as confirmed.
10. Do not stamp all functions as if every standard aspect was fully checked. Separate "standard audit target aspects" from actual evidence. For each finding, list the aspects actually supported by evidence; for no-drift functions, include a requirement trace summary naming the concrete HTML requirements checked and implementation refs searched.
11. Record only actionable drift. If evidence is incomplete, mark the finding `UNCERTAIN` and explain what remains ambiguous.
12. For every drift finding, split the result into implementation-ready fields: `designExpectation`, `implementationActual`, `comparisonRows`, `comparisonSummary`, `mismatchReason`, `impact`, `fixTarget`, `requiredChange`, `implementationRefs`, and, when available, short design/implementation snippets from the cited lines. Do not rely on a generic prose paragraph alone.
13. Each `comparisonRows` entry must answer all four questions explicitly: comparison item, exact design value/requirement, exact implementation value/behavior, and why those two do not match. If any of those four cells would be vague, continue investigating before recording the finding.
14. Treat phase labels such as Ph2 as auxiliary context. They can be stored, but the main report must not use phase status as a substitute for concrete behavioral differences and exact implementation locations.
15. If the HTML design spec explicitly says the whole function or scoped subfeature is `フェーズ2で実装する`, `Ph2で対応`, or `Ph1では実装しない`, do not report absence of that planned Phase 2 work as drift or as a clear implementation gap. You may keep a secondary audit note that non-implementation was confirmed, but exclude it from finding counts and implementation-gap counts. Only keep a finding when there is a concrete non-phase mismatch, such as an implemented Phase 1 path behaving differently from the design or user-facing text differing.
16. When no drift is found, add the function to the audited set with an empty findings list only after the requirement trace gate passes. If material HTML requirements are untraced, do not mark `AUDITED_NO_DRIFT_FOUND`; mark the function as requiring review or add `UNCERTAIN` findings with the unresolved requirements.
17. Do not let one confirmed finding hide other requirements in the same function. A function with `AUDITED_WITH_FINDINGS` can still have untraced material requirements; keep those requirements visible in the trace gate until each one is converted to a confirmed finding, an uncertain finding, a matched trace row, or a documented phase/design non-implementation exclusion.
18. For explicitly registered critical requirements, the harness should carry a missing-finding template or an equivalent escalation rule. If the trace is not covered by an existing finding, promote it into findings automatically or fail the quality gate loudly. Do not rely on a hand-maintained `ADDITIONAL_FINDINGS` list as the only path for user-reported or high-risk missing behavior such as timeouts, cart retention, one-minute/30-minute limits, store-account auto redirects, conditional UI areas, status transitions, external calls, or destructive side effects.
19. The HTML report must not expose broad source-signal candidates as if they were implementation gaps. A requirement-level list in the main report must be limited to confirmed or explicitly uncertain actionable drift derived from findings, such as `NOT_FOUND` or `DRIFT` requirement traces and concrete comparison rows. If a source-signal scan is used for triage, keep it out of the main HTML report unless each row has been verified against implementation source and written as a concrete finding.
20. Do not hide time-based or automatic-navigation requirements merely because they are not confirmed findings yet. Requirements involving `画面を表示してから`, seconds/minutes after display, auto redirect/navigation, or timeout-to-cart/top behavior should appear in a separate focused untraced-requirement audit queue when they remain uncovered. This queue is not a confirmed defect count; it exists so these high-risk requirements are reviewed against Controller/Twig/JavaScript/Service source instead of being buried among broad requirement-trace failures.

## Function-Level Implementation Gap Audit

For every HTML spec sheet, maintain a function-level implementation audit even when no drift finding is confirmed yet.

- Extract implementation search terms from the HTML design: route names, URL paths, translation keys, class/controller/service names, batch/API/CSV names, and high-signal business terms from the sheet title and requirement text.
- Search implementation source by function across Controller, Form, Service, Repository, Entity, Migration, Twig, Command/Batch, CSV, PDF/print, API/webhook, locale/messages, JavaScript, and configuration files.
- Store a `functionImplementationAudit` object with `verdict`, `designDerivedTerms`, `candidateRefs`, `candidateCount`, `strongSignalCount`, `searchedAreas`, and `auditNote`.
- Use separate verdicts:
  - `CONFIRMED_IMPLEMENTATION_GAP`: a concrete drift finding already proves missing implementation.
  - `NO_IMPLEMENTATION_ENTRY_FOUND`: no entry candidate was found from design-derived terms; treat as an additional-review candidate, not an automatic confirmed defect.
  - `IMPLEMENTATION_ENTRY_FOUND`: strong source evidence such as route, class, translation key, or path was found.
  - `IMPLEMENTATION_CANDIDATE_FOUND`: weak business-term candidates were found but the entry point is not proven.
  - `PHASE2_NONIMPLEMENTATION_EXPECTED`: HTML design explicitly scopes non-implementation to Phase 2/Ph1 exclusion.
  - `DESIGN_NONIMPLEMENTATION_EXPECTED`: HTML design explicitly says the function or scoped behavior is not implemented by code, such as `実装しない`, `実装不要`, or infrastructure/external-service configuration replacing application code.
- Use `DESIGN_NONIMPLEMENTATION_EXPECTED` as the function-level verdict only when the non-implementation statement applies to the whole function or the implementation entry itself, for example an external WordPress server, Docker image cron, Aurora parameter group, or a bare whole-sheet `実装しない`. If the text only excludes a scoped subfeature, UI alert, HTML hint, logging detail, partial Phase 2 item, or internal job, keep the function's source-entry verdict and mention the scoped exclusion only in the trace/audit note.
- The report must show both confirmed implementation-gap findings and function-level no-entry candidates. Do not merge these counts: implementers need confirmed defects for fixing and no-entry candidates for review planning.
- A function-level candidate is not enough to mark the detailed requirements as implemented. Requirement trace still controls no-drift status.
- Do not set report metadata such as `auditComplete` or narrative notes to "complete" merely because every sheet has a function-level implementation audit. If any material requirement trace remains unresolved, state that all sheets have function-entry coverage but requirement-level audit is incomplete.
- For infrastructure-oriented sheets such as Step Functions, Lambda, WAF/S3 jobs, cron configured outside the application, or managed database settings, distinguish "not found in the requested implementation repository" from "not implemented anywhere". A confirmed implementation-gap finding may be scoped to the audited repository, but the report must say when external infrastructure repositories or cloud configuration were not checked.

## Requirement Trace Gate

Before marking a function no-drift, verify the following:

- Every material HTML requirement has a trace row. Material means it changes behavior, data, display, validation, permission, transition, side effect, external communication, schedule, retry/idempotency, logging/audit, CSV/API/PDF/batch I/O, or user-visible text.
- Each trace row includes exact design text or a tight paraphrase plus line/anchor reference, not only the sheet title.
- Each matched row cites the implementation path and line(s) that actually execute or render the behavior. A nearby class, route, or template is not enough unless the cited code contains the relevant condition/value/side effect.
- Each missing row is converted to a confirmed or uncertain finding. Use confirmed only after searching the direct path and nearby alternative implementations.
- Missing rows remain failures even if the function already has other findings. The gate is requirement-scoped, not function-scoped.
- If an explicit critical requirement has a configured missing-finding template, regenerate the report from the harness and verify the promoted finding appears in both JSON and HTML with design value, implementation behavior, mismatch reason, fix target, and search evidence.
- If a missing row does not yet have enough evidence for a confirmed or uncertain actionable finding, do not count it as an implementation gap and do not put it in the main HTML fix list. Keep the function in an incomplete requirement-trace state, and promote the row only after implementation source has been checked enough to state the exact design requirement, exact implementation behavior, and mismatch reason.
- A generic `auditEvidence` string is not a substitute for requirement traces.
- Negative searches must list the searched terms/areas and why nearby hits do not satisfy the design.

Use stable IDs and Japanese text when the existing report is Japanese. Keep dimensions consistent with existing findings when continuing a report.

## Severity Guidance

- `high`: missing feature/route, wrong critical business rule, destructive or externally visible behavior, missing required import/export/batch/PDF flow.
- `med`: partial implementation, wrong filtering/sorting/session behavior, missing non-critical columns or validation, incompatible screen behavior.
- `low`: copy/display/default-state differences, ambiguous design wording, minor workflow variance.

## Report Generation

If the project already has a report generator, use it. Otherwise copy or adapt `scripts/build_report.py` from this skill into the report directory, then run it from the repository root or pass paths as needed.

The HTML report must include:

- summary counts: total findings, severities, audited functions, functions with drift
- scope and remaining work
- per-function sections
- each finding with severity, confidence, dimension, audit aspects including label/message/translation-key differences when applicable, design reference, implementation reference, design expectation, implementation actual behavior, `comparisonRows`, mismatch reason, impact, fix target, required change, and evidence
- a comparison table with columns: 比較項目 / 設計書の値・要求 / 実装の値・挙動 / 乖離理由
- links or file paths precise enough for a developer to inspect
- short cited design and implementation snippets when available
- phase/Ph2 data only as hidden or secondary metadata, never as a report column or primary summary
- a function-level implementation audit section showing verdict counts, no-entry candidates, candidate source references, and the search terms that produced them
- a requirement-level difference list derived only from confirmed/uncertain findings, showing the exact design requirement, implementation behavior, mismatch reason, implementation refs, and a link back to the finding. Do not include broad unverified source-signal queues in the main HTML report.
- a focused untraced-requirement section for small, high-risk classes such as display-time timers, automatic redirects, and timeout navigation. Keep it separate from confirmed difference and implementation-gap counts, and include search terms/candidate refs so the next audit step is concrete.

After editing findings, validate JSON and regenerate HTML:


## Quality Bar

- Treat the HTML design spec as source of truth even when implementation looks intentional.
- Cite exact file paths and line numbers whenever available.
- Distinguish `不在` from “not found yet”; use `不在` only after searching likely implementation areas.
- Avoid broad claims such as “not implemented” without search evidence or contrasting nearby implemented features.
- Do not classify Phase 2 planned non-implementation as a defect. A missing route, CSV, batch, API, table, or screen is only a drift finding when the design expects it in the audited implementation phase.
- For label/message drift, prefer exact line evidence and a verified render path over fuzzy string similarity. Fuzzy or near-match scans are candidate generators; they are not findings until source and display usage are confirmed.
- When an external reviewer or another agent reports candidates, verify each candidate against the HTML design and implementation source before adding it. Keep rejected or ambiguous candidates out of confirmed counts, or mark them `UNCERTAIN` with the unresolved reason.
- For absent implementations, include the searched terms/areas, nearby implementation files with line numbers, and a concrete reason those nearby files do not satisfy the design. Do not leave `implRef` as only `不在` in the final report.
- Reject vague findings. A finding is not complete until it names the exact design value and exact implementation value that differ.
- Keep the report cumulative and resumable.

#[IsGranted('IS_AUTHENTICATED_FULLY')]
class BuyOrderController extends AbstractController
{
    public function __construct(
        private readonly DtbBuyOrderRepository $buyOrderRepository,
        private readonly MtbBuyOrderStatusRepository $buyOrderStatusRepository,
        private readonly UpdateFreeCommentAction $updateFreeCommentAction,
        private readonly UpdateStatusAction $updateStatusAction,
        private readonly UpdateBuyOrderAction $updateBuyOrderAction,
    ) {
    }

    /**
     * ネット買取受注一覧取得
     */
    #[Route('/%eccube_api_v1_route%/admin/buyOrders.json', name: 'api_admin_buy_orders_product_arrival', methods: ['GET'])]
    public function getProductArrivalBuyOrders(): JsonResponse
    {
        $buyOrders = $this->buyOrderRepository->findToAssessBuyOrders();

        $response = array_map(function (array $buyOrder): array {
            $address = implode(' ', array_filter([
                $buyOrder['prefName'],
                $buyOrder['addr01'],
                $buyOrder['addr02'],
            ]));

            return [
                'netBuyOrderId' => (string) $buyOrder['id'],
                'applyDate' => $buyOrder['orderDate']->format('Y/m/d H:i:s'),
                'freeComment' => $buyOrder['memo'] ?? '',
                'memberName' => $buyOrder['memberName'] ?? '',
                'netOrderStatusId' => (string) $buyOrder['buyOrderStatusId'],
                'customerInfo' => [
                    'firstName' => $buyOrder['firstName'],
                    'lastName' => $buyOrder['lastName'],
                    'telNo' => $buyOrder['telNo'] ?? '',
                    'zipcode' => $buyOrder['zipcode'],
                    'address' => $address,
                ],
            ];
        }, $buyOrders);

        return new JsonResponse($response);
    }

    /**
     * ネット買取受注コメント更新
     */
    #[Route('/%eccube_api_v1_route%/admin/buyOrder/{id}/freeComment.json', name: 'api_admin_buy_order_update_free_comment', methods: ['PUT'])]
    public function updateFreeComment(int $id, Request $request): JsonResponse
    {
        $raw = $request->request->get('free_comment');
        if ($raw === null) {
            throw new MissingRequiredParameterException('コメントを入力してください');
        }

        $BuyOrder = $this->buyOrderRepository->find($id);
        if (!$BuyOrder instanceof DtbBuyOrder) {
            throw new NotFoundException('買取情報が見つかりません');
        }

        $Member = $this->getUser();
        if (!$Member instanceof Member) {
            throw new UnauthenticatedException('認証エラー');
        }

        try {
            $input = new UpdateFreeCommentInput($BuyOrder, $Member, (string) $raw);
            $this->updateFreeCommentAction->handle($input);

            // システムエラーの場合は隠蔽して500エラーを返す
        } catch (\Throwable $e) {
            throw new InternalException('システムエラーが発生しました', $e);
        }

        return new JsonResponse(['code' => Response::HTTP_OK], Response::HTTP_OK);
    }

    /**
     * ネット買取受注ステータス更新
     */
    #[Route('/%eccube_api_v1_route%/admin/buyOrder/{id}/status.json', name: 'api_admin_buy_order_update_status', methods: ['PUT'])]
    public function updateStatus(int $id, Request $request): JsonResponse
    {
        $BuyOrder = $this->buyOrderRepository->find($id);
        if (!$BuyOrder instanceof DtbBuyOrder) {
            throw new NotFoundException('買取情報が見つかりません');
        }

        $statusId = $request->request->get('status');
        if ($statusId === null || $statusId === '' || !ctype_digit((string) $statusId)) {
            // 旧システム互換性目的：「店頭」ではないが、「店頭買取」という表現を使っている
            throw new MissingRequiredParameterException('正しい店頭買取ステータスIDを入力してください');
        }

        $BuyOrderStatus = $this->buyOrderStatusRepository->find((int) $statusId);
        if (!$BuyOrderStatus instanceof MtbBuyOrderStatus) {
            // 旧システム互換性目的：「店頭」ではないが、「店頭買取」という表現を使っている
            throw new InvalidParameterException('正しい店頭買取ステータスIDを入力してください');
        }

        $Member = $this->getUser();
        if (!$Member instanceof Member) {
            throw new UnauthenticatedException('認証エラー');
        }

        try {
            $input = new UpdateStatusInput($BuyOrder, $Member, $BuyOrderStatus);
            $this->updateStatusAction->handle($input);

            // カスタムエラーの場合はそのまま返す
        } catch (BaseApiException $e) {
            throw $e;
            // システムエラーの場合は隠蔽して500エラーを返す
        } catch (\Throwable $e) {
            throw new InternalException('システムエラーが発生しました', $e);
        }

        return new JsonResponse(['code' => Response::HTTP_OK], Response::HTTP_OK);
    }

    /**
     * ネット買取注文の査定終了処理
     * このAPIは、他のAPIとは異なりJSON形式のリクエストが前提となる
     */
    #[Route('/%eccube_api_v1_route%/admin/buyOrder/{id}.json', name: 'api_admin_buy_order_update', methods: ['PUT'])]
    public function updateBuyOrder(int $id, #[MapRequestPayload] UpdateBuyOrderDto $updateBuyOrderDto): JsonResponse
    {
        $BuyOrder = $this->buyOrderRepository->find($id);
        if (!$BuyOrder instanceof DtbBuyOrder) {
            throw new NotFoundException('買取情報が見つかりません');
        }

        $Member = $this->getUser();
        if (!$Member instanceof Member) {
            throw new UnauthenticatedException('認証エラー');
        }

        $BuyOrderStatus = $this->buyOrderStatusRepository->find($updateBuyOrderDto->orderStatusId);
        if (!$BuyOrderStatus instanceof MtbBuyOrderStatus) {
            throw new InvalidParameterException('正しい買取ステータスIDを入力してください');
        }

        try {
            $input = new UpdateBuyOrderInput(
                $BuyOrder,
                $Member,
                $BuyOrderStatus,
                $updateBuyOrderDto->orderDetails
            );

            $this->updateBuyOrderAction->handle($input);

            // カスタムエラーの場合はそのまま返す
        } catch (BaseApiException $e) {
            throw $e;
            // システムエラーの場合は隠蔽して500エラーを返す
        } catch (\Throwable $e) {
            throw new InternalException('システムエラーが発生しました', $e);
        }

        return new JsonResponse(['code' => Response::HTTP_OK], Response::HTTP_OK);
    }
}

#[IsGranted('IS_AUTHENTICATED_FULLY')]
class BuyMainCardController extends AbstractController
{
    public function __construct(
        private readonly DtbBuyMainCardRepository $buyMainCardRepository,
    ) {
    }

    /**
     * 複数ネット買取IDからネット買取受注の商品一覧を取得
     */
    #[Route('/%eccube_api_v1_route%/admin/buyMainCard.json', name: 'api_admin_buy_main_card', methods: ['POST'])]
    public function getByBuyOrderIds(Request $request): JsonResponse
    {
        $ids = $request->request->get('ids');

        // 旧システム互換目的：クライアントAppが空のリクエストを送信する可能性があり、400エラーで返すとハンドリングできないため空配列を返す
        if ($ids === null || $ids === '') {
            return new JsonResponse([]);
        }

        // カンマ区切りを配列に変換し、数字のみをフィルタリング
        $buyOrderIds = array_filter(
            explode(',', $ids),
            static fn (string $id) => preg_match('/^\d+$/', trim($id)) === 1
        );
        $buyOrderIds = array_map('intval', $buyOrderIds);

        // 有効なIDがない場合は空配列を返す
        if (empty($buyOrderIds)) {
            return new JsonResponse([]);
        }

        $BuyMainCards = $this->buyMainCardRepository->findByBuyOrderIdsWithApplicationPrices($buyOrderIds);

        $response = array_map(function (DtbBuyMainCard $BuyMainCard): array {
            // 状態（NM、SP等）をキーにした買取価格を整形
            $pricesByCondition = [];
            foreach ($BuyMainCard->getApplicationPrices() as $ApplicationPrice) {
                $conditionCode = $ApplicationPrice->getCardCondition()->getCode();
                $pricesByCondition[$conditionCode] = $ApplicationPrice->getApplicationPrice();
            }

            return [
                'buyMainCardId' => $BuyMainCard->getId(),
                'buyOrderId' => $BuyMainCard->getBuyOrder()->getId(),
                'productId' => $BuyMainCard->getProduct()->getId(),
                'languageId' => $BuyMainCard->getLanguage()?->getId(),
                'foilFlg' => $BuyMainCard->getFoilFlg(),
                'count' => $BuyMainCard->getCount(),
                'price' => $BuyMainCard->getPrice(),
                'cardConditionId' => $BuyMainCard->getCardCondition()?->getId(),
                'saleFlg' => $BuyMainCard->getSaleFlg(),
                'purchaseCategory' => $BuyMainCard->getPurchaseCategory(),
                'applicationPrice' => $pricesByCondition,
            ];
        }, $BuyMainCards);

        return new JsonResponse($response);
    }
}

    93	明細は1件ずつ処理する。商品規格IDが0の明細は個別入力商品として扱い、同名の既存があるときは更新し、無いときは新規に作る。それ以外の明細は商品規格から買取代表カードを特定し、同一条件の既存があるときは更新し、無いときは新規に作り、同一受注内で商品・言語・フォイル区分が一致するえらんで買取の既存買取代表カードから、状態ごとの申込時買取価格を引き継ぐ。既存の状態が未設定のカードはNM相当として突合する。
