## 要旨
設計は印刷情報の店頭注文番号欄を dtb_order_number.value（現行 waiting_number）から取得するとするが、実装は店頭注文番号欄にも注文番号(order_number)を出力している。

## 判定理由
設計DBカラム節(行1107)は店頭注文番号 dtb_order_number.value（現行は dtb_order_sub.waiting_number）を『印刷情報の店頭注文番号欄。受注IDで引く』と規定。実装 OrderDirectPrintAction.php では $orderNumber = order_number(行77) を、店頭注文番号欄(ラベル行94→値行97)と注文番号欄(ラベル行114→値行117)の双方に出力している。印刷対象取得クエリ getPrintOrderListMainShop / getDirectPrintOrderList はいずれも waiting_number / dtb_order_number.value を SELECT しておらず（rg で確認、print系クエリに waiting 列の選択なし）、店頭注文番号欄には待ち番号ではなく注文番号が印字される。

## 反証結果

反証を試みた結果、指摘は覆らなかった。反証を試みて逆に補強された。設計(HTML行1107)は店頭注文番号欄を dtb_order_number.value（現行 waiting_number）から受注IDで引くと規定。実装 OrderDirectPrintAction::getPrintData は order_number を htmlspecialchars して店頭注文番号欄(ラベル店頭注文番号→値)と注文番号欄の双方に同一出力。別ルート探索で Entity/DtbOrderNumber.php が実在し value 列(comment='店頭注文番号')を持つと確認したが、getPrintOrderListMainShop / getDirectPrintOrderList の SELECT はいずれも o.order_number のみで DtbOrderNumber.value も waiting 系も一切参照しない。つまり店頭注文番号テーブルは実装済みなのに印刷フローが無視し order_number を店頭注文番号欄に印字している。命名揺れ(value/waiting/store number)を横断しても代替実装なし。指摘は維持。
