# 不具合優先度 定義（業務基準 P1〜P3）

**版**: draft-3（2026-08-12）
**ゴール**: 不具合の改修優先度を定義する。
**判断基準**: 業務が回ること。`回らない > 迂回すれば回る > 回る` の順に優先する。
**位置づけ**: 既存の「優先度(実害基準) P1〜P4/D/R」および「実害(high/med/low)」を**統合して置き換える**、唯一の優先度定義。

> **draft-2 からの変更**: 実害(high/med/low)は業務語で定義されており、P1〜P3 の定義文と実質同一だった。
> 実害を入力に使うと優先度は実害の言い換えに退化するため、実害という判断層を廃止し、
> 優先度は**観測可能な3つの事実（現象・シナリオ被覆・回避策）**から導く構造に改めた。

---

## 1. 優先度の定義


| 優先度    | 業務の状態                                                          |
| ------ | -------------------------------------------------------------- |
| **P1** | **業務が回らない。** コア業務または準コア業務の遂行が止まる、または業務記録が壊れる。手作業でも代替できない       |
| **P2** | **迂回すれば回る。** 手作業・再実行・別経路で業務は完了できるが、コア業務の正しさ・効率を損なう。または周辺機能が止まる |
| **P3** | **業務は回る。** 業務の完了・記録・判断に影響しない                                   |


優先度は **軸1「業務停止性 B」**（§3）と **軸2「機能ランク C」**（§4）の合成で決まる（§5）。

---



## 2. 判定に使う3つの事実

優先度の判定に主観的な「重大度」を持ち込まない。1件の不具合について、次の3つを**事実として記録**する。

### 2.1 現象区分（X）— その機能が「どう壊れているか」

1機能の中だけで判定する。業務上の重さは語らない。


| 区分             | 定義                      | 例                                                      |
| -------------- | ----------------------- | ------------------------------------------------------ |
| `X1` **機能不成立** | 操作・処理が成立しない             | 設計にある機能が未実装で操作自体が存在しない／画面が表示されない／処理が異常終了する／外部連携が送信されない |
| `X2` **誤結果**   | 処理は通るが、値・状態・記録が誤る       | 集計値が誤る／保存先カラムが違う／ステータス遷移が設計と異なる／連携内容が欠落する              |
| `X3` **表示差**   | 文言・ラベル・整形の差。値・状態・記録は正しい | 見出し・ボタン文言・列名の相違／並び順・桁区切りの相違                            |


`X2` については **業務記録に不整合が残るか**（後続業務・帳票・外部システムに誤った状態が伝播し、放置すると訂正が困難になるか）を併記する。

### 2.2 シナリオ被覆（S）— その機能が「業務経路のどこに載るか」

正本は `scenario_test/scenario/02_トレーサビリティ.md`（158シナリオ／10業務／経路種別＝正常代表・主要代替・業務異常）。
不具合の発生機能（機能No）が、どの経路種別のシナリオに出現するかで決まる。`期待機能No` と `紐づけ機能No` の**和集合**を被覆とみなす。


| 区分   | 定義                                   |
| ---- | ------------------------------------ |
| `S1` | **正常代表**経路に出現する。＝その業務の標準手順そのものに載る    |
| `S2` | **主要代替／業務異常**経路にのみ出現する。＝条件が揃ったときだけ通る |
| `S3` | どのシナリオ経路にも出現しない                      |


> `S3` は「業務上重要でない」ではなく「**シナリオでは業務上の位置を測れない**」を意味する。
> シナリオは全機能を覆っていないため、`S3` をそのまま低優先として扱うと過小評価が起きる。§3 の補正ルールで打ち消す。



### 2.3 回避策（W）— 「迂回して業務が回るか」

**他画面・手作業・再実行によって、同じ業務結果に到達できるか。**


| 区分   | 判定                                                           |
| ---- | ------------------------------------------------------------ |
| `あり` | 代替手順を**具体的に記述できる**（どの画面・どの操作で同じ結果に到達するか）。かつ、その代替が別の業務を破綻させない |
| `なし` | 代替手順を記述できない／代替すると業務記録が別の形で壊れる／**未判定**                        |


未判定は `なし`（安全側）とする。「たぶん何とかなる」は `あり` にしない。

**効率の低下は** `あり` **を妨げない。** 同じ業務結果に到達できるなら、時間がかかっても `あり` とする。
効率低下そのものは優先度ではなく、後続の改修計画（工数・実施時期）で扱う。

## 3. 軸1: 業務停止性（B）

X・S・W から機械的に導く。判断の余地を残さないため、上から順に**最初に一致した行**を採る。


| 順   | 条件                                                     | B            |
| --- | ------------------------------------------------------ | ------------ |
| 1   | `X3`（表示差）                                              | `B3` 業務は回る   |
| 2   | `X2` かつ 業務記録に不整合が残る                                    | `B1` 業務が回らない |
| 3   | `X1`／`X2` かつ 回避策 `なし` かつ（`S1`／`S2` **または** 機能ランク `C1`） | `B1` 業務が回らない |
| 4   | 上記以外（`X1`／`X2`）                                        | `B2` 迂回すれば回る |


**3行目の** `C1` **条項が §2.2 の補正ルール**である。シナリオ未整備のためだけに `S3` となったコア機能が、
完全に壊れていても低優先に落ちることを防ぐ。

## 4. 軸2: 機能ランク（C）

「その機能が止まったとき何が止まるか」で機能を3段階に分ける。コア業務は **受注・買取・決済・出荷・外部連携・在庫・商品登録・価格管理**。


| ランク                    | 定義                                                                   | 
| ---------------------- | -------------------------------------------------------------------- | 
| `C1` **コア**            | 売上・仕入・在庫の発生／確定に直接関与する。止まるとその日の商売が止まる。決済・出荷・外部連携・法令要件（古物営業法の本人確認等）を含む |
| `C2` **準コア**           | 集客・顧客接点・イベント・コンテンツ・分析。止まってもその日の受注／買取は回るが、売上機会と顧客体験を失う |
| `C3` **周辺**            | 設定・管理補助・基盤。業務手順に直接現れない |
