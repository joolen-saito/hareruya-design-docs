# 工数圧縮案の批判的レビュー

`design_impl_drift_report/PLAN_OPTIMIZATION.md` は、EC-CUBE移行プロジェクトの改修工数を
工程別に整理し、「品質を下げずに工数と期間を下げる案」をまとめたもの。

あなたの仕事は**この案を疑い、誤りと抜けを指摘すること**である。追認は目的ではない。

## 前提（変更してはいけない）

- 工程順は 基本設計書 → 実装修正 → ユニットテスト → レビュー → レビューバック対応
- 結合テスト・シナリオテストは順守。削減対象にしない
- **楽観的にも悲観的にもならないこと。** 数字を大きく見せる方向・小さく見せる方向の
  どちらのバイアスも指摘対象である

## 見るべき点

### 1. 積み上げの正しさ
- 工程別の積み上げに二重計上・取りこぼしがないか
- 係数の当て方（工程1に特定50%、工程4-5を工程1+2に対して）が筋として通っているか
- 「見積不可147件」「結合テスト・シナリオテスト」を小計から外している扱いが妥当か

### 2. 圧縮案が本当に品質を下げないか
各施策について、**品質が下がる隠れた経路がないか**を探す。
- A1 重複を潰す → 別物を同一視して片方を直し漏れる危険はないか
- B1 機能×区分でまとめて直す → PRが大きくなりレビューで見落とす危険はないか
- B2 設計書をシート単位でまとめる → 文脈の取り違えが起きないか
- B3 画面表示を一括PR → 翻訳キーの衝突・意図しない他画面への波及はないか
- C1 設計書と実装を同一担当が連続 → レビューの独立性が落ちないか
- E1-E3 並列化・先行着手 → 統合時の手戻りが増えないか

### 3. 削減見込みの妥当性
- 「2件目以降が4割/5割で済む」という仮定は現実的か。
  実際のコードを見て、まとめて直せる例とまとめられない例を挙げて検証すること
- 慎重側・楽観側の置き方が偏っていないか

### 4. 抜けている施策・抜けているコスト
- 挙がっていない圧縮策はないか（品質を下げないもの）
- 逆に、案に含まれていないが実際には発生するコストはないか
  （環境構築、データ移行、リグレッション、既存テストの修正、リリース調整など）
