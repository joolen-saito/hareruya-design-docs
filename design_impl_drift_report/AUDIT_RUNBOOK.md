# ②不具合調査 手順書（第6段）

**この手順を通さない調査は行わない。**

対象は正本HTML設計書 45冊。第5段で再生成し `VERIFY OK` になった正本を読む。
正本が変われば判定は陳腐化するので、**第5段の完了が前提**である。

観点と判定値は [AUDIT_SCOPE.md](AUDIT_SCOPE.md) / [AUDIT_JUDGING_RULES.md](AUDIT_JUDGING_RULES.md)。
本書は**手順と、過剰指摘を止めるゲート**だけを書く。

## なぜゲートが要るか（2026-08-19〜22 の実測）

一度目の調査で指摘が **35件 → 161件** に膨らんだ。原因は2つとも仕組みの側にあった。

1. 折りたたみがバイト一致で、書き手が並列だとキーの文言が揺れて畳まれなかった（折込率 73% → 7%）。
2. 1つの実装欠陥が、要求の数だけ指摘に割れた。

さらに 2026-08-22 の点検で、母集合そのものが判定を誤らせる形をしていると分かった。

- 抽出の単位は **1行**。文単位でも仕様単位でもない。0214 では母集合1,254件のうち
  **79%が文末「。」で終わらない**（表のセル片・見出し）。
- Excel設計書は **1つの仕様を複数行に分けて書く**。カスタマイズの★は先頭行にしか付かず、
  後続行にも同じカスタマイズ要件が続く。
- Excel設計書は **同一行の別セルに備考を書く**。列の意味を知らないと備考を仕様と読み違える。
- Ph2・廃止の行が母集合に入る（0214 で46件）。規約では対象外だが、機械化されていなかった。

**判定の機会が増えるほど誤判定の機会も増える。** 規約で既に対象外と決まっているものは
エージェントに判定させず機械で落とす。これがゲート1・2の設計理由である。

## 母集合の作り（inventory）

```bash
python3 design_impl_drift_report/design_audit_harness.py inventory --doc <書番>
```

`design_audit/<書番>/requirements.tsv` に1行1要求で出る。列の意味:

| 列 | 意味 |
| --- | --- |
| `区分` | 処理概要／機能仕様／項目定義／現行仕様／刷新仕様／表示メッセージ／要件説明／本文／画像のみ |
| `ブロックID` | 同じ仕様のまとまり。★行・区分の変化・行番号の飛びで切れる |
| `ブロック見出し` | そのまとまりの先頭行（★行があればその文） |
| `カスタマイズ` | ★。**先頭行だけでなくブロック内の全行に付く**（★は先頭行にしか書かれないため） |
| `同ブロック` | 同じまとまりに属する他の要求ID。**判定前に必ず読む** |
| `表ヘッダ` | その行が属する表の見出し行。どのセルが備考かはこれで分かる |
| `要求文` | 行そのもの |

**単独で判定してよい行は少ない。** `同ブロック` と `表ヘッダ` を読まずに判定しない。

### 2. 判定

**シートをバッチへ束ねる。** シート単位で1エージェントにすると68体になり多すぎる。
1バッチ 150〜180要求・1〜4シートを目安にする。

**180要求を超えるシートは区画へ分ける。** 0202 には589要求のシートがあった。
分けるときは **`parts/<sheetId>__part<N>.tsv` と、区画ごとに別ファイルへ書かせる。**

> 1つのファイルへ並行に書かせてはいけない。後から書いた側が前の内容を消す。
> 2026-08-22 実測: 0202 の sheet-51 で144行が一度まるごと消え、**410件が未判定のまま残った**。
> 担当エージェントが「他担当の書き込みで自分の144行が消えた」と申告して発覚した。
> `merge` は `parts/*.tsv` を全部読むので、ファイル名が分かれていても結合には影響しない。

区画を担当させるときは、プロンプトへ次を書く。

- 担当する要求IDの範囲（`sheet-51-R145 〜 sheet-51-R288` のように明示）
- 書き出し先は自分の区画ファイルだけで、他の区画ファイルには触れないこと
- 自己検証は `audit_part.py check --doc <書> --sheet <区画名>`。
  区画では他範囲の判定漏れを見ないので、そのまま exit 0 を目指してよい

各エージェントに渡すもの:

- 担当シートの要求行（`同ブロック` `表ヘッダ` `ブロック見出し` `カスタマイズ` を含む全列）
- `design_audit/<書番>/sheets/<sheetId>.txt`（シート本文の全文）
- `design_audit/<書番>/images/<sheetId>_img*.png`（レイアウト図。**画像を見ずに「実装が無い」と判定しない**）
- ee 実装（`/home/y-saito/Developments/ec-cube-enterprise`）

各エージェントが返すもの: `VERDICT_COLUMNS` の全列を `parts/<sheetId>.tsv` へ。
**担当シートの全要求に判定を付ける**（判定漏れ0。取り込まないものも
OUT_OF_SCOPE / UNVERIFIABLE として理由付きで残す）。

自己検証は `audit_part.py check --doc <書> --sheet <シート>` で行う。
**exit 0 になるまで直させる。** ゲートに落ちたまま次へ進まない。

## ゲート

`build` は次に1つでも触れたら `RuntimeError` で落ちる。**閾値をいじって通さない。**

| # | ゲート | 何をするか |
| --- | --- | --- |
| 0 | 判定漏れ0 | 抽出した全要求に判定が付くまで build は成功しない |
| 0 | 捏造ゼロ | `設計根拠_引用` が該当シート本文に実在すること（空白を詰めた部分一致） |
| 0 | 実装参照の実在 | `実装参照` は ee 内に実在するファイル:行のみ。行数超過も落とす |
| 5 | **シート単位の対象外** | シートまるごと廃止／Ph2（`FUNCTION_SCOPE`）のシートと、標準機能のシートを機械で OUT_OF_SCOPE へ。実測14シート |
| 1 | **Ph2・廃止の自動対象外** | 行が宣言している／項目定義の識別IDが台帳と一致するものを機械で OUT_OF_SCOPE へ。**エージェントがDRIFTと書いても上書きする** |
| 2 | **非要求行の自動対象外** | `non_requirement_lines.tsv` の完全一致（表紙・目次・節見出し・表のヘッダ）とJSON構造記号を機械で OUT_OF_SCOPE へ |
| 3 | **類似・重複の折りたたみ** | 根本原因キーの完全一致で畳んだ後、`根本原因＋実装実態＋設計期待値` の類似度 0.86 以上を代表1件へ寄せる |
| 4 | **仕様でない引用からは指摘を出せない** | `設計根拠_引用` に述語が無ければ落とす。**文字数では見ない** |
| 旧1 | ★識別IDずれ | カスタマイズ説明の★識別IDずれは自動で対象外 |
| 旧2 | 実装手段の語 | `設計期待値` が通信方式・クラス名・join の種類などで書かれていたら落とす |
| 旧3 | I/Oかふるまいか | 指摘には `乖離種別` の明示が要る |
| 旧4 | 根本原因キー | 指摘には `根本原因` が要る（空なら落とす） |
| 7 | **レビュー結果の適用** | `reviews.tsv` の重複・過剰指摘を機械が指摘から取り下げる。**判定が割れたら重いほうを採る** |
| 6 | **根本原因キーの命名規約** | `<実装ファイル名>-<欠陥の短い英数説明>` でなければ落とす。日本語は不可。先頭は `実装参照` のファイル名と一致すること |

**ゲート1・2で落としたものは黙って消えない。** 判定根拠に `[gate1]` `[gate2]` と理由が残る。
**ゲート3で畳んだ要求IDは代表行に併記され、成果物にも必ず出る。**

### ゲートが捕まえられないもの

- **過小報告**（指摘を書かなければゲートは何も言わない）。抜き取りで人が見る。
- ゲート1が落とすのは「宣言している行」と「識別ID一致」だけ。target の部分一致では落とさない。
  機能はフェーズ1で項目だけがPh2という `ITEM_SCOPE` があり、target 語を含むフェーズ1の
  要求を巻き添えにするため。**残った曖昧なものはエージェントが判定する。**
- **「再編」は廃止ではない。** 台帳が `FUNCTION_SCOPE` でも、`replacement` / `renewalImpl` に
  置き換え先が書かれているものはシートごと落とさない。提供の形だけを変えてシートの仕様は
  生きている、という型があるためである（2026-08-23 実測: 0303-sheet-5 は
  「商品詳細検索画面（独立画面）は廃止し、商品一覧上のモーダルへ再編。これに伴い実装不要:
  **独立した詳細検索画面の表示とその画面遷移**」で、廃止されたのは画面遷移だけ。
  判定エージェントが見つけた DRIFT 2件がゲートで消えていた）。
- **ゲートが正しい指摘を消す向きの誤りを疑うこと。** 過剰指摘を止めるゲートを足すたびに、
  この向きの事故が起きている。実測3件: ゲート1が書番未照合で6件（0204）、ゲート6が拡張子を
  拒否して34件（0202）、ゲート5が再編を廃止と読んで2件（0303）。
  いずれもエージェントの申告か手戻りで発覚した。**機械が黙って落としたものを定期的に見ること。**
- **標準機能はそもそも母集合に入らない。** 標準28機能はExcel設計書のシートを持たない
  （20機能は台帳で `-/-` と明示、残る8機能も確定シートなし）。シート対応台帳
  `function-sheet-map.tsv` の確定行395件の区分はカスタマイズ213・現行踏襲139・新規実装43で、
  標準は0件である。ゲート5の標準経路は将来標準シートが現れたときの備えとして置いてある。
- **シート対応は `状態=確定` の行だけを使う。** 候補行はシート名が似ているだけで付くため、
  信じると「標準機能が同居している」と誤認してカスタマイズ機能のシートを巻き添えにする
  （2026-08-22 実測: 0201/sheet-6 は M11-03 カスタマイズが確定なのに M11-04 標準が
  スコア0.00の候補として並んでいた）。
- **引用が仕様かどうかは文字数で決めない。** 短くても仕様は仕様であり（実データ最短は16字
  「複製はリンクとして配置すること。」）、長くても項目名の羅列は仕様ではない。見るのは
  **述語があるか**＝何がどうなるかが書かれているか。当初は文字数の下限で近似したが基準として誤り
  （利用者指摘 2026-08-22）。表のセル末尾に挙動が書かれた行
  （`1 新規登録 ボタン - - - イベント登録画面へ遷移`）は通る。
  較正: 実データの仕様文9件・非仕様11件で誤り0件。0214母集合1,254件のうち76%が単独で引用可能、
  残り297件は同ブロックや説明セルを含めて引用させる。
- 非要求行の台帳は**確実なものだけ**を載せる。「なし」「機能」のように意味を持ちうる短い行は
  載せない。台帳に無いものはこれまでどおり判定する。

### 根本原因キーの書き方

**`<実装ファイル名>-<欠陥の短い英数説明>`** に固定する。
例 `ProductBulkUpdateBuyPriceStoreAction-no-smaregi-sync`。

- 先頭は欠陥のある実装ファイル名。`実装参照` のファイル名と一致すること。
  **拡張子は付けても付けなくてもよい**（`StockHistoryCsv` でも `StockHistoryCsv.php` でも通る）。
  当初は拡張子なしに固定したが、0202 でゲート6の違反34件が全部これだけだった。
  揺れを弾いても得るものが無く、**正しい指摘を機械が拒む**側の誤りだった
- 続く説明は英小文字・数字・ハイフンだけ。2〜5語
- 正規表現 `^[A-Za-z][A-Za-z0-9_.]*(?:-[a-z0-9]+)+$`（先頭はファイル名なので `.` を含みうる）

**接頭辞の照合は行ごとではなくグループ単位で行う。** 1つの欠陥が複数の実装ファイルに
またがるのは正常だからである（実測: 支店システムへの通知の未移植は
ProductClassUpdateAction / ProductClassDeleteAction / InventoryReflectService など
5ファイルに同じ形で出る）。行ごとに照合すると、この systemic な欠陥を1件に畳めなくなる。
接頭辞は**その欠陥の代表となる実装ファイル**であればよい。

理由: キーの表記が揺れると**同じ欠陥が別々の指摘として残る**。0204 の実測では
日本語48種・英数74種が混在し、同一欠陥が2つのキーに割れた組が5つあった。

| 割れていた組 | 件数 |
| --- | --- |
| `price-bulk-no-smaregi-sync` / `買取・基準価格一括編集がスマレジ未連携` | 8+5 |
| `section-csv-no-smaregi-sync` / `部門更新CSV登録がスマレジ未連携` | 3+2 |
| `branch-notify-missing` / `branch-notify-not-ported` | 4+3 |
| `csv-upload-confirm-modal-missing` / `商品公開CSVアップロードに確認の一段が無い` | 1+1 |
| `csv-import-history-total-count-missing` / `CSV取込履歴の総件数が画面に出ない` | 1+1 |

**ゲート3の類似折り畳みでは届かない。** 実測の類似度は0.50〜0.58で、閾値0.86に達しない。
書き手が並列である以上、文言の一致に頼るのは無理がある。ファイル名で固定すれば、
同じファイルの同じ欠陥は誰が書いても同じキーになる。

なお**同じファイルなら同じ欠陥、ではない**。0204 では次の3組が同じファイルを指しながら
別の欠陥だった。統合するかは実装実態で決める。

- `search-product-name-en-missing` / `search-card-name-en-missing`（参照テーブルが別）
- 商品規格の削除判定 / 期間別販売数の非表示（同じ twig の別の箇所）
- 高額行のエラー処理 / 削除済み規格の除外（同じリポジトリの別の条件）

## レビューと、その適用（ゲート7）

判定と反証だけでは、重複と過剰指摘が残る。**独立した2者にレビューさせ、結果を機械で適用する。**

| 巡 | 担当 | 位置づけ |
| --- | --- | --- |
| 反証ワークフロー | 本体と同じ系統 | 全指摘を7件ずつ分けて1件ずつ実装を開かせる。網羅的 |
| **codex** | **別系統。必須** | 1巡のみ。[[adversarial-review]] の規約に従う |

**codex を必須にする理由。** 同じ系統のレビューが「問題なし」と言っても、それは自分で自分を
確かめたにすぎない。0204 の実測では codex 固有の指摘は6件中1件だけだったが、
**両者が独立に「ハルシネーション0件」と判定した**ことのほうが重い。片方だけの
0件宣言は根拠にならない。1巡で打ち切ること（[[adversarial-review]]: 巡ごとに走査を
やり直すためコストは指摘数と無関係に一定。10巡で233万トークンを使った実績がある）。

結果は `design_audit/<書>/reviews.tsv` に置く。列は
`要求ID / レビュアー / 判定 / 畳む先 / 提案重要度 / 理由`。判定は
`OVER_REPORT`（過剰指摘＝指摘から取り下げ） / `DUPLICATE`（重複＝畳む先へ寄せる） /
`OVER_SEVERE`（重要度過大） / `WRONG_KIND` / `CONFIRMED`。

### レビュアーに書かせること

レビュアーの返す形が `reviews.tsv` の列と揃っていないと、**適用が黙って空振りする。**

- `OVER_SEVERE` と言うなら **`提案重要度` に「いくつが正か」を必ず書かせる。**
  0202 では22件のうち16件が空で、理由文にも書かれていなかった。
  空のまま build すると重要度は据え置かれるが「レビューを適用した」という記録だけ残る。
  いまは `[gate7] ★重要度が据え置き N件` として報せる。**この行が出たら埋めてから閉じる。**
- `DUPLICATE` と言うなら `畳む先` に要求IDを書かせる。畳む先が無ければ何もできない。
- 判定値は `OVER_REPORT / DUPLICATE / WRONG_KIND / OVER_SEVERE / CONFIRMED` の5つだけ。
  反証エージェントが `REFUTED` を返したことがある（＝指摘として成り立たない＝`OVER_REPORT`）。
  語彙を固定して渡すこと。

**反証エージェントは parts を直接直すことがある。** その場合レビュー結果は既に反映済みで、
`reviews.tsv` に載っていても build では「適用対象外」になる（判定が既に MATCHED 等）。
これは二重適用を避ける正しい振る舞いだが、**適用件数が少なく見える**ので驚かないこと。

### 判定が割れたら重いほうを採る

重さの順は **取り下げ > 重複 > 種別違い > 重要度過大 > 確認済**。
一番重いのは**指摘からの取り下げ**である（利用者決定 2026-08-22）。
独立した2者が見て片方だけが問題を挙げた場合、見落としの側に倒すより取り下げの側に倒す。

実例: `sheet-10-R005` は反証が「重複」、codex が「過剰指摘」と逆方向だった。
重い「過剰指摘」を採り、指摘から取り下げた。

### 重複の畳み方

**新しいキーを作らない。既存の根本原因キーへ寄せる。**
A→B と B→A の相互参照があるので、連結成分ごとに代表を1つ決め、
成分の中で最も要求IDが小さいものが持つキーへ揃える
（2026-08-22 実測: `__dup__<相手>` という固有キーを振ったところ、すでに同じキーで
 畳まれていた組がほどけ、件数が114→118へ**増えた**）。

## 台帳
