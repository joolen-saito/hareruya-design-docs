# 工程別工数の整理と、品質を下げない圧縮案

前提として次は変えない。

- 順序は **基本設計書 → 実装修正 → ユニットテスト → レビュー → レビューバック対応**
- **結合テスト・シナリオテストは順守**。削減対象にしない

## 2. 結合テスト・シナリオテストの規模（工数は未算定）

改修が触る機能とテスト資産の重なりは測れる。単価は実績がないと置けないので**あえて数字を作らない**。

| 項目 | 数 |
|---|---:|
| 改修が触る機能（実装＋設計書） | 253 |
| うち結合テスト対象機能に含まれるもの | 246 / 394 |
| シナリオテストの具体化済みケース | 261 （在庫のみ。全10モジュールで約1,067） |

**再テストの工数 = 対象機能数 × 1機能あたりの再実行・確認時間**。この単価は既存の結合テスト実績から出せるはずなので、そちらの数字を当ててほしい。仮に1機能0.5人日なら 123人日、1人日なら 246人日 になる。

## 3. 品質を下げずに圧縮できるところ

「品質を下げない」とは、**直すべきものを直さない・確認を省く、をやらない**という意味。以下は作業の重複を減らす案であり、対象や確認の範囲は変えない。

数値化していない施策として、B3（画面表示の一括PR）とC2（PR粒度の統一）がある。いずれも工程4-5のレビュー回数に効くが、**削減量を裏付ける実績がないため額を出していない**。B3には後述の重大な前提がある。

### B3（画面表示の一括PR）は前提を満たさないと採れない

当初「文言変更は影響が閉じている」としたが、これは実コードに反する。

翻訳キー `front.product.search__product_not_found` は8つのTwigから参照されており、商品検索(F03-01)と買取検索(F05-03)で**別々の文言**を要求する指摘が同時に存在する。一括で値を書き換えると、片方の要求を満たすともう片方の画面を壊す。

採るなら先に次が要る（いずれも未計上）。

1. 翻訳キー → 全参照箇所の逆引き表を作る
2. 要求が異なる画面は専用キーへ分離する
3. キー衝突の静的チェックと、画面別の表示確認を入れる

## 4. 期間を短くする（工数は減らない）

| # | 施策 | 効果 | 前提・副作用 |
|---|---|---|---|
| E1 | **区分別に並列化**。画面表示246件は他と独立性が高い | 期間短縮 | 同じ messages.ja.yaml に集中して衝突する。**共有キーは意味も共有する**ため、キー単位に担当を割っても衝突は消えない |
| E2 | **ドメイン別に分割**。上位は m04 110件、m13 74件、m03 60件 | 期間短縮 | スマレジ連携やM12-01の集計のようにドメイン・層を横断する改修は分割できない |
| E3 | **結合テストを機能単位で改修完了順に着手** | 期間短縮 | 後続改修で再テストになる機能が出る。依存が凍結するまでは予備確認として扱い、本番カウントは凍結後にする |
| E4 | **P1（実害high）64件を先行させる** | リスク低減 | 工数は減らない |

**並列化には統合コストが伴う**（rebase、競合解消、共有基盤の変更調整、依存変更による再テスト）。これらは上の表にも小計にも入っていない。共有基盤・DBスキーマ・共通APIを先行して凍結し、依存グラフで波を作るのが前提になる。

## 5. やらないこと（品質を下げる案）

- **結合テスト・シナリオテストの間引き** — 順守が前提。
- **ユニットテストの省略** — 工程3は325人日と大きいが、削ると回帰を検知できず結合テストで見つかって手戻りが増える。
- **レビューの省略・簡略化** — 工程4-5で370人日。既存挙動を変える改修が多く、レビューが最後の砦になる。
- **P4（実害low）の切り捨て** — 工数が小さく、切っても効果が薄いわりに不一致が残る。
- **見積不可の見切り発車** — 実装後に作り直しになる。

## 7. 進め方の順序

1. **見積不可153件を決裁**（開発工数外・並行可。論点別に束ねて一括処理する）
2. **重複82件を人が確認して確定**（A1の前提）
3. **Backlog255件の設計書更新要否を判定**（工程1の抜けを埋める）
4. **翻訳キーの逆引き表を作る**（B3・E1の前提）
5. **試行**：局所/横断、低/中/高工数、組サイズ、翻訳/移行で層化し、クラスター単位で5工程を通す。工程3-5の係数とPRサイズ別レビュー実績を採る
6. 共有基盤・スキーマを先行凍結し、依存グラフで波を作る
7. 設計書を書籍単位、実装をクラスター単位でまとめて直す
8. 改修完了した機能から結合テスト・シナリオテストへ

## 8. この案の弱いところ（codexレビュー反映後）

- **削減見込みの根拠は「2件目以降が4割/5割で済む」という仮定**であり実測ではない。同一機能×同一区分でも別作業が混在する組があり、上限側は届かない。
- **工程3-5は37%を占めるが係数で作った数字**。ここが実測でずれると、圧縮案の効果より係数の誤差のほうが大きい。
- **1,900人日はプロジェクト総工数ではない**。第6節のコストを積むまで総額は出せない。
- 施策の削減額は工程モデルの差分であり、施策どうしの重なり（B1とC2、B2とC1）を厳密には分離していない。単純合算はやや過大になる。
- B3・C2・E1のPR粒度方針は互いに矛盾しうる。基本単位を「機能×共有実装境界」に一本化し、locale変更は別PRに分けるのが穏当。
