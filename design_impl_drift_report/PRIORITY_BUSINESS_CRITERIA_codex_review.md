# 不具合改修優先度定義 draft-3 批判的レビュー

## 結論

draft-3 は、そのままでは優先度の正本にできない。主因は次の3点である。

1. `B2` を「迂回すれば回る」と定義しながら、導出表は `W=なし` から `B2` を生成する。軸1が自分の定義と矛盾している。
2. `B1` を「業務が回らない」と定義しながら、`B1×C3` を `P2` に落とす。軸1と合成表のどちらかが誤っている。
3. CSVの既定回避策には、更新対象や副作用が一致しない代替先が複数ある。誤った `W=あり` が再現可能な形で量産される。

「実害」という語は消えたが、`業務記録に不整合が残る`、`後続業務`、`訂正が困難`、`同じ業務結果`、`別の業務を破綻させない` に評価判断が移っただけで、観測事実への分解は完了していない。以下の13件を修正してから正式化すべきである。

## 指摘一覧

### F-01 [CRITICAL] `W=なし` なのに `B2=迂回すれば回る` になる

根拠:

- §2.3 は `W=なし` を「代替手順を記述できない」と定義する（`PRIORITY_BUSINESS_CRITERIA.md:60-65`）。
- §3 の3行目は `X1/X2, W=なし, S1/S2 または C1` だけを `B1` とし、4行目で残りを `B2` にする（同`:114-122`）。
- したがって `X1, S3, W=なし, C2` は `B2` になる。§5 の全経路表にも実際にこの行があり、最終結果は `P3` である（同`:190-195`）。

具体例: シナリオ未収載のC2機能が完全に異常終了し、代替手段も存在しない場合、現定義では「迂回すれば回る」と判定される。これは判定漏れではなく論理矛盾である。

修正案:

- §3から `S` と `C` をB導出条件から外し、Bを実際の業務完了状態だけで定義する。
- `X1/X2` で `W=あり（期限・処理量を満たすことを実証済み）` なら `B2`、`W=なし` かつ必要な業務結果を期限内に完了できないなら `B1`、必要な業務結果が影響を受けないなら `B3` とする。
- `S3` は重要度ではなく「経路を特定できない」状態なので、必要な業務結果を特定できるまで `R` とする。`B2` へフォールスルーさせない。

### F-02 [CRITICAL] 合成マトリクスがBの意味を破壊している

根拠:

- `B1` は「業務が回らない」と定義される一方、`B1×C3=P2` である（`PRIORITY_BUSINESS_CRITERIA.md:175-181`）。本当に業務が回らないなら、機能台帳上の静的なC3を理由にP2へ落としてはいけない。
- `B2` は「迂回すれば回る」であり、P2の定義そのものである（同`:18-20`）のに、`B2×C2=P3` としている（同`:179-181`）。準コア業務を迂回しなければ完了できない状態を「業務の完了・記録・判断に影響しない」とは言えない。

修正案: §5を次へ置換する。

|  | C1 | C2 | C3 |
|---|---:|---:|---:|
| B1: 期限内に必要業務を完了できない／未封じ込めの誤記録が伝播する | P1 | P1 | P1 |
| B2: 検証済み迂回・訂正で期限内に完了できる | P2 | P2 | P3 |
| B3: 業務結果・判断・記録に影響しない | P3 | P3 | P3 |

もし `B1×C3=P2` を維持したいなら、B1を「当該機能の通常経路が成立しない」という局所現象に改名し、「業務が回らない」という語を削る必要がある。その場合はP1定義とも別の軸になり、現行設計より複雑になるため推奨しない。

### F-04 [MAJOR] Xは相互排他的でも網羅的でもなく、観測値になっていない

`X1/X2/X3` は「機能不成立／誤結果／表示差」だけである（`PRIORITY_BUSINESS_CRITERIA.md:30-40`）。次が一意に分類できない。

- 一部レコードだけ失敗、一定確率で失敗、タイムアウトして締切に間に合わない。
- 権限不備で特定ロールだけ利用不能、バッチ遅延、二重実行、監査ログ欠落。
- 表示値は正しいが並び順のため誤判断する、ラベル誤りで反対の操作を選ぶ。
- 誤った値を表示するが保存は正しい、外部送信だけ欠落する。

特に「並び順」を無条件にX3へ入れ、X3を無条件B3とする規則（同`:38,116`）は危険である。ピッキング順、出荷順、優先処理順なら業務結果に影響する。

修正案: §2.1を次へ変更する。

- `X0 未判定` を追加し、X0は `R`。
- `X1 必要な結果が生成されない`、`X2 誤った結果・記録・外部副作用が生成される`、`X3 表現だけが異なり、同じ入力・判断・永続値・外部副作用になることを確認済み` とする。
- `全件/一部、常時/間欠、対象ロール、処理時間、影響レコード、永続化先、外部送信先` を別の必須観測列にする。
- X3の判定には「誤操作・誤判断を誘発しない」を必須条件とし、満たさなければX2にする。

### F-05 [MAJOR] Wが能力・期限を無視し、未判定と「存在しない」を混同している

「時間がかかっても `あり`」とする（`PRIORITY_BUSINESS_CRITERIA.md:67-68`）一方、例外では日次数千件・期限を認める（同`:105-106`）。この二つは矛盾する。「何件なら実運用上処理できないか」「期限はいつか」「何人を回避作業へ割けるか」が定義されず、判定者ごとに変わる。また未判定を `なし` に入れる（同`:63-65`）ため、情報不足と実在しないことが区別できない。

修正案: §2.3のWを3値にする。

| 値 | 定義 |
|---|---|
| W0 未確認 | 手順・権限・同値性・所要時間のいずれかが未検証。優先度は `R`。 |
| W1 実行可能 | 本番相当で手順が成功し、必要な履歴・通知・外部連携を含む同じ業務結果へ、対象件数を業務締切前に処理できる。 |
| W2 実行不能 | 手順が存在しない、結果が同値でない、必要権限を確保できない、または件数×1件時間が締切・要員能力を超える。 |

W1の証拠として実行者、画面/コマンド、前提権限、1件時間、対象件数、締切、検証日を必須化する。「効率低下は後続の改修計画だけで扱う」は削除する。締切に間に合うかは、まさに「業務が回るか」の入力である。

### F-06 [MAJOR] Sは「実際に経路に載る」事実ではなく、期待値を混ぜた推定である

§2.2は `期待機能No` と `紐づけ機能No` の和集合を被覆とする（`PRIORITY_BUSINESS_CRITERIA.md:42-54`）。しかしトレーサビリティでは、価格管理のM12-09/10は期待機能にある一方、紐づけ機能には無い（`scenario_test/scenario/02_トレーサビリティ.md:68-69`）。この和集合により「設計上は使うはずだが、経路証拠が無い」機能までS1になる。これは観測された被覆ではない。

修正案:

- `S1/S2` は `紐づけ機能No` に実在し、かつシナリオの具体的ステップへリンクできる場合だけ付与する。
- `期待機能No` にだけあるものは `S0=期待のみ・紐づけ未確認` とし、B判定前に `R` として調査する。
- `S3` は「シナリオ外」、`S0` は「カバレッジ欠落」と分ける。
- `02_トレーサビリティ.md` の行だけでなく、業務フロー本文の見出し/ステップIDをSの証拠列に保存する。

### F-07 [MAJOR] 「X2かつ業務記録に不整合」は主観的で、無条件B1は過大判定になる

`業務記録に不整合が残る` の説明は「後続へ伝播」「放置すると訂正が困難」（`PRIORITY_BUSINESS_CRITERIA.md:40`）であり、どの記録が正本か、何を伝播と数えるか、訂正困難の時間・費用・権限基準が無い。そのうえW・S・Cを無視して無条件B1にする（同`:116-119`）。これはP1の「手作業でも代替できない」（同`:18`）とも矛盾する。

具体例: 誤ステータスが保存されても、外部送信前に一覧から検知し、承認者が締切前に正しい状態へ戻せるならB2である。逆に少額でも会計・税・決済・在庫へ不可逆に伝播し、訂正不能ならB1になり得る。

修正案: `記録不整合` の真偽値を廃止し、`正本テーブル/外部系、誤記録件数、検知方法、伝播先、訂正手順、訂正期限、監査証跡保持、封じ込め済み` を記録する。§3の2行目は「誤記録が未封じ込めで、締切前の一括訂正・取消ができず、会計/決済/在庫/法令記録または後続処理へ伝播する」に限定する。検証済み訂正が間に合う場合はB2とする。

### F-08 [MAJOR] CをB導出とマトリクスの両方で使い、重要度を二重計上している

§3は `S3, W=なし` でもC1ならB1へ上げる（`PRIORITY_BUSINESS_CRITERIA.md:117-122`）。そのBを§5で再びCと合成する（同`:175-181`）。C1という静的評価がBとPの二段階で効き、X/S/WからBを導くという説明（同`:110-112`）にも反する。C1の範囲自体が広いため、この補正は「重要そうだからP1」に戻る迂回路である。

また§5の「全経路」は全経路ではない。

- `X1` に「記録不整合=なし」を置いているが、当該項目はX2だけに併記する定義である。
- `X2, 記録不整合=あり` はS/Wを `—` に畳み、検証済み回避・訂正が存在する組合せを表現できない。
- `X1/X2, S3, W=なし, C2/C3 -> B2` という意味上不可能な行を含む。
- X/S/Wの未判定、部分影響、複数機能のCが無い。

修正案: §3からC補正を削除する。S0/S3で業務位置が不明ならCで推測せずRへ送る。§5の全経路表は、修正後の列挙可能な値をスクリプトから生成し、未到達行をテストで検出する。

## 推奨する定義の最小再構成

13件を個別修正するだけでなく、判定順を次に固定すると再現性が上がる。

1. 不具合であること、発生条件、影響業務結果、対象件数を確認できなければ `R`。
2. セキュリティ・法令・会計・決済・個人情報の強制ゲートを判定する。
3. Xは「結果なし／誤結果／純表示」に分類し、部分率・頻度・対象を別列で記録する。
4. Sは紐づけ済み経路だけをS1/S2とし、期待のみはS0、未収載はS3とする。S0/S3で影響業務を特定できなければ `R`。
5. Wは同値性と期限内処理能力を実証したW1、不能なW2、未確認のW0に分ける。W0は `R`。
6. 業務結果が期限内に完了不能または誤記録が未封じ込めならB1、検証済み迂回/訂正で完了できるならB2、業務結果に影響しないならB3。
7. F-02の修正マトリクスでPを決める。複数業務にまたがる場合は最大Pを採る。
8. Cは静的な業務依存度に限定し、発生中の影響、繁忙期、件数、前提工程、シナリオ掲載だけで恒常的にC1へ上げない。

この順序なら、「実害」という総合主観を復活させず、観測証拠・業務締切・代替能力からPへ到達できる。
