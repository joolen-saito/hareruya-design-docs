# 実装乖離監査 判定規約（全設計書共通）

正本は `excel_to_html/output/*.html` から機械抽出した `design_audit/<doc>/sheets/<sheet-id>.txt` と
`design_audit/<doc>/images/<sheet-id>_imgN.png` だけ。実装は `../ec-cube-enterprise`（以下 ee）の HEAD。
**正本に書かれていないことは指摘にできない。実装を読まずに判定を書いてはいけない。**

## 判定値

| 判定 | 意味 |
| --- | --- |
| MATCHED | 設計どおり実装されている |
| DRIFT | 実装はあるが設計と違う |
| NOT_IMPLEMENTED | 設計の要求に対応する実装が無い |
| DESIGN_ISSUE | 正本内部で記述が矛盾し、どちらが正か決められない（設計裁定待ち） |
| UNVERIFIABLE | 実データ・実行時挙動に依存し静的解析では確定できない（理由必須） |
| OUT_OF_SCOPE | 実装対象の記述ではない（見出し・凡例・前置き・他機能の記述など。理由必須） |

## 機械ゲート（`audit_part.py check` が落とす。通らないものは成果物にできない）

1. DRIFT / NOT_IMPLEMENTED / DESIGN_ISSUE は `設計根拠_引用` が**当該シート本文に逐語で存在**すること
   （空白を詰めた部分一致で照合）。正本に無い要求は指摘にできない。
2. DRIFT / NOT_IMPLEMENTED は `実装参照` が ee 内に**実在するファイル:行**であること。行数超過も落ちる。
3. **MATCHED も実装の位置（`src/...php:123` 形式）を `判定根拠` か `実装参照` に最低1つ書くこと。**
   「設計どおり」と言う以上、どこを見たのかを示す。実在しない引用は落ちる。
4. DRIFT / NOT_IMPLEMENTED は `重要度`(P1/P2/P3)・`指摘区分`(未実装/実装違い)・`乖離種別`(IO/ふるまい)・
   `設計期待値`・`実装実態`・**`根本原因`** が必須。
5. 全行に `判定根拠` と `確信度`(high/med/low)。**そのシートの全要求に判定が要る（判定漏れ0）。**

## 過剰指摘を出さない（最重要・利用者指示 2026-08-21）

**1つの実装欠陥は1件として書く。** 設計書は同じ1つの欠陥を、項目表・機能仕様・現行仕様・入出力の
各所で繰り返し要求していることが多い。要求の数だけ指摘に割ると、実態より何倍も多い件数になる。

そのために `根本原因` 列がある。**同じ実装欠陥から出た指摘には、まったく同じ短いキーを書く。**
キーは設計書1冊の中で一意にする（シートをまたいで同じ欠陥なら同じキーにする）。
build はこのキーで1件に畳み、畳んだ要求IDは代表行に全件併記する（黙って落とさない）。

良い例:
- 振替明細に商品名・基準価格・在庫数・登録日・更新日・登録者・更新者が保存されない7件
  → すべて `根本原因 = 振替明細に振替当時の値を保存していない`
- 出庫日・入庫日が一覧でもCSVでも常に空になる7件
  → すべて `根本原因 = 出庫日時・入庫日時を書き込む処理が無い`
- 項目名の文言差が1画面に4件
  → すべて `根本原因 = 在庫一覧の項目名に商品管理側の共通文言を流用している`

キーは「実装のどこが1箇所直れば全部消えるか」で決める。**直す単位が別なら別のキーにする。**
迷ったら、その指摘を消すために触るファイルと行が同じかどうかで判断する。

**件数を稼がない。** 指摘の多さは成果ではない。同じことを言い換えて増やす、
影響の無い差を並べる、1つの原因を分割する——いずれも成果物の信頼を落とす。

## 指摘にしないもの（利用者指示・機械でも一部強制）

- **★書きの識別IDずれ**: カスタマイズ説明の「識別ID:N「X」を追加」が項目表とずれている件。
  追加すべき列は項目表側で決まり実装は追随済み。OUT_OF_SCOPE。
- **実装手段の差**: 通信方式・認可設定・受付先・内部配線・検証順序・トランザクション境界・
  セッションキー・ルート名・join の種類・クラス名/メソッド名など。`設計期待値` をこれらの語で書くと落ちる。
  結果・ふるまいの言葉で書けないなら、その指摘は取り下げる。
- **実装違いは I/O とふるまいに限る**: 応答にも画面にも現れない内部手順（読み込む設定値の内訳、
  ソルトの作り方など）は OUT_OF_SCOPE。
- **現行仕様に書かれた現行ソースの不具合・不用意な副作用**（0件でも見出し行だけのCSVを出す等）は
  踏襲対象ではない。ただし機能として定義された挙動（警告表示・並び順・据え置き時間等）は要求として扱う。
- **現行仕様と★カスタマイズ/リニューアル後の仕様が食い違うとき**は後者が優先。現行仕様側は OUT_OF_SCOPE。
  理由を「リニューアル後の仕様が優先するため踏襲対象ではない」と明記する。
- **見出し・表の見出し行・区分行・前置き・運用想定・背景説明**は OUT_OF_SCOPE。理由を書く。

## DESIGN_ISSUE にするもの

項目表・レイアウト図・機能仕様・現行仕様のあいだで記述が食い違い、**どちらが正か決められない**もの**だけ**。
実装と突き合わせる前に設計裁定が要る。`実装実態` は空にする（成果物には載らず、件数だけ残る）。

## 重要度（業務影響で決める。機能名で機械的に決めない）

- **P1**: 業務が回らず商売が止まる／データ整合性が壊れる／手作業でも代替できない。
  受注・買取・出荷・商品金額・金額相当（ポイント付与/失効）・決済・在庫・メール通知・
  外部連携（スマレジ/ユニサーチ/プリンター）・認証・認可・セキュリティ・法令要件、
  および登録フォームのバリデーション（そもそも登録できない）。
- **P2**: 迂回すれば回る（手作業・再実行・別経路）。CSV一括登録・イベント・デッキ・分析・コンテンツ。
- **P3**: 業務は回る。見出し・ボタン文言・列名の相違／並び順・桁区切りの相違。

例外は影響と迂回可否で判断する（受注管理でも文言差は P3、CSV一括登録でも取り込めない＝データ登録不能なら P1）。

## 画像を見ること

正本の文言はレイアウト図の画像に入っていることが多い。**画像を見ずに「実装が無い」と判定すると誤る。**
`design_audit/<doc>/images/<sheet-id>_imgN.png` を読み、根拠にしたときは `画像確認メモ` に書く。

## 手順

1. `design_audit/<doc>/sheets/<sheet-id>.txt` を全部読む。画像があれば全部見る。
2. `requirements.tsv` から当該シートの要求を全件取り出す。
3. ee の該当実装（コントローラ・フォーム・Twig・リポジトリ・サービス・locale）を読む。
   **grep の空振りを実在の否定に使わない**（同じ検索でも取りこぼすことがある。別の綴り・別の命名でも引く）。
4. `design_audit/<doc>/parts/<sheet-id>.tsv` に12列すべてを書く（TSV・ヘッダ付き）。
5. `python3 audit_part.py check --doc <doc> --sheet <sheet-id>` が OK になるまで直す。

## やってはいけないこと

- 実装を読まずに MATCHED を並べる（ゲート3で落ちるが、実在する無関係な行を引いて通すのは**捏造**）。
- 迷ったから OUT_OF_SCOPE にする（迷ったら UNVERIFIABLE か DESIGN_ISSUE。理由を書く）。
- 正本の文言を要約して `設計根拠_引用` に書く（**逐語**でないと落ちる）。

## 偽陽性率の抜き取り検査（設計書1冊ごと）

集約後の掲載予定の指摘から、P1・P2・P3 を各5件、決定的な手順（等間隔抽出。乱数を使わない）で選び、
**反証専任のエージェント**に1件1体で投げる。指示は「裏づけるな、壊しにかかれ。迷ったら取り下げ寄りに倒せ」。
潰す観点は5つ:

1. 設計根拠_引用が正本にそう書かれているか。文脈を切って意味を変えていないか。
   同じシートのリニューアル後の仕様・★カスタマイズがその要求を打ち消していないか。
2. 実装が本当に無いか／違うか。別ファイル・別命名・別階層を自分で探したか（grepは3回以上引く）。
3. 実装手段の差を指摘にしていないか。
4. 画面にも応答にも出ない内部挙動を指摘にしていないか。
5. 重要度が業務影響として妥当か。過大な重要度は過剰指摘と同じ害がある。

**取り下げ率が2割を超えたら、その設計書の判定は基準が緩い。規約を締めて判定からやり直す。**
1〜2件なら該当箇所を直して先へ進む。結果は AUDIT_PROGRESS.md に冊ごとに記録する。

スキーマの注意: 構造化出力のプロパティ名に日本語を使うと API が 400 を返す（`^[a-zA-Z0-9_.-]{1,64}$`）。
最上位のキーは ASCII にすること。
