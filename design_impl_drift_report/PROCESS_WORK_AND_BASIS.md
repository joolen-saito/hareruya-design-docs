# 各工程でやる作業と、工数の根拠

工程は **1 基本設計書 → 2 実装修正 → 3 ユニットテスト → 4 レビュー → 5 レビューバック対応**。
この順序と、結合テスト・シナリオテストを順守する前提は変えていない。
1人日 = 8時間。

この文書は「各工数がどの作業の時間で、その数字がどこから来たか」を工程ごとに書いたもの。**個別に見て積んだ数字と、係数で作った数字を分けて示す**。

## 0. 総括

| 工程 | 人日 | 割合 | 対象件数 | 根拠の等級 |
|---|---:|---:|---:|---|
| 1 基本設計書 | 122 | 6% | 513件 / 32冊 | 個別見積＋仮置き係数 |
| 2 実装修正 | 1084 | 57% | 1115件 | 個別見積＋仮置き係数 |
| 3 ユニットテスト | 325 | 17% | 同上 | **係数のみ** |
| 4 レビュー | 129 | 7% | 同上 | **係数のみ** |
| 5 レビューバック対応 | 241 | 13% | 同上 | **係数のみ** |
| **開発5工程 小計** | **1900** | | | |

この小計には **入っていないもの** が3つある。

1. **意思決定 153件**（何を作るか決まっていないもの）。開発工数ではないので別枠。第7節。
2. **結合テスト・シナリオテスト**。順守前提だが単価の実績がないため数字を作っていない。第8節。
3. **移行・環境・リリース・PR運用・並列化の統合コスト**。第9節に一覧。

素の個別見積は 設計書 70.4 ＋ 実装 722.4 = **792.8人日**。残る 1107人日 は「探索の上乗せ」「書籍固定費」「工程3-5の係数」で作った数字であり、**総額の 58% は仮置きの係数に依存している**。

## 1. 基本設計書（122人日）

### やる作業

- 既存テストが落ちるものを直す（fixture・期待値の更新を含む）
- 実行して通す

### 工数の作り方


## 4. レビュー（129人日）

### やる作業

- PRを出す（説明・関連指摘IDの記載を含む）
- レビュアーが読み、指摘する
- **設計書の変更もレビューする**（工程1のぶん）
- 書籍単位の設計レビュー（1冊まとまった時点で通しで見る）

### 工数の作り方

```
工程4 = (工程2 1084 + 工程1 122) × 10% + 32冊 × 0.25人日/冊
      = 121 + 8 = 129人日
```

**10%は実測ゼロの係数。**設計書にもレビューが発生するので、工程1を分母に含めている（含めないと設計レビューがゼロになってしまう）。

レビュー工数はPRの粒度で変わる。小さいPRを大量に出せば1件あたりは軽いが本数が増え、大きいPRにまとめれば本数は減るが1件が重くなる。**この係数はPR粒度を決めないまま置いた数字**なので、粒度方針を決めた時点で見直しが要る。

## 5. レビューバック対応（241人日）

### やる作業

- 指摘を直す
- 再度テストを通す
- 再レビューに出す（往復ぶん）

### 工数の作り方

```
工程5 = (工程2 1084 + 工程1 122) × 20% = 241人日
```

**20%は実測ゼロの係数。**レビュー時間（工程4）の2倍を置いている。「見る時間より直す時間のほうが長い」という一般則であって、このプロジェクトの実績ではない。

既存挙動を変える改修が多いため往復は増えやすい。一方で、指摘の多くは1ファイル内の局所修正なので往復は少ないという見方もできる。**どちらとも言えない。**

## 6. 係数をどう実測に置き換えるか

係数で作った金額は **1115人日（全体の59%）**。ここが動くと、圧縮案の効果より係数の誤差のほうが大きくなる。

| 係数 | 現在値 | 影響額 | 実測の取り方 |
|---|---:|---:|---|
| 工程2の特定・影響範囲 | 50% | 361人日 | 試行時に「探す時間」と「直す時間」を分けて記録する |
| 工程1の探索 | 50% | 35人日 | 1冊通してやり、シート特定の時間を測る |
| 工程3 UT比率 | 30% | 325人日 | 直近PRで、実装コミットとテストコミットの行数・時間の比を出す |
| 工程4 レビュー比率 | 10% | 121人日 | PR作成からapproveまでのレビュアー実作業時間 |
| 工程5 レビューバック比率 | 20% | 241人日 | 初回PRからマージまでの指摘対応コミットの時間 |
| 書籍固定費 | 0.75人日/冊 | 24人日 | 1冊通してやる |

**取り方**: 局所修正／横断修正、低／中／高工数、翻訳／移行 で層化して各区分から数件ずつ、5工程を通して実行する。数十件・数日の作業で、1900人日の数字の確度が決まる。

## 7. 開発工数に入れていない「意思決定」（153件）

**何を作るか決まっていないもの**。工数を積む対象ではなく、先に決める対象。

| 種類 | 件数 | 何を決めるのか |
|---|---:|---|
| 仕様確定待ち（乖離） | 72 | 設計と実装のどちらを正とするか |
| 設計判断待ち | 23 | 正本の中でテキストと画像が矛盾している。どちらが正か |
| 要再調査 | 19 | 判断材料が足りず、指摘自体の妥当性が確定していない |
| 設計書側の作業を判断できず | 6 | 設計書を触る必要があるか判定不能 |
| 仕様確定待ち（Backlog） | 33 | 同上 |
| **計** | **153** | |

**これを1人日/件で積むのは誤り**（前の版ではそう計上していた）。決裁会・確認・正本更新・受入条件確定・再見積が要り、論点別に束ねれば1件あたりは軽くなる。まとめ方次第で総額が変わるので、**開発工数とは別枠で管理するのが正しい**。

決まった後は工程1から通常どおり流れる。つまり **153件ぶんの開発工数は上の1900人日に未計上** である。

## 8. 結合テスト・シナリオテスト（順守／工数未算定）

順守が前提なので削減対象にしていない。規模だけ測れる。

| 項目 | 数 |
|---|---:|
| 改修が触る機能（実装＋設計書） | 253 |
| うち結合テスト対象機能に含まれるもの | 246 / 394 |
| シナリオテストの具体化済みケース | 全10モジュールで約1,067 |

### やる作業

- 改修で挙動が変わる機能のテストケース（期待値）を直す
- テストデータ・環境を用意する
- 実行する
- 失敗を解析し、実装かテストのどちらが悪いか切り分ける
- 再実行する

**工数 = 対象機能数 × 1機能あたりの再実行・確認時間**。単価は既存の結合テスト実績から出せるはずなのでそちらを当ててほしい。仮に1機能0.5人日なら 123人日、1人日なら 246人日。

**単価に実績がないため、ここで数字を作ることはしない。**
