# 処理単位 → 機能 の割り当て（担当者向けの指示書）

## 目的

ec-cube-enterprise（以下 ee）の規模をファンクションポイント（FP）で測った。FP の処理単位（基本機能プロセス）は
「コントローラのアクション1つ＝1件」（ルート）と、業務バッチのコンソールコマンド1本＝1件（バッチコマンド）。
これを機能一覧の機能（機能ID）に割り当て、**機能ごとのFP**を出し、結合テストのケース数が FP から見て妥当かを調べる。
割り当てを間違えると、ある機能のFPが膨らみ、別の機能が「ケースが多すぎる」と誤って判定される。推測で埋めず、根拠を残すこと。

## 入力（すべて読み取り専用）

| ファイル | 中身 |
| --- | --- |
| `fp_scale/per_function/work/transactions.tsv` | 処理単位 819件。ID・種類・コントローラアクション・ルート名・パス・HTTPメソッド・領域・FP種別・手がかり3列 |
| `fp_scale/per_function/work/functions.tsv` | 機能一覧 412件。機能ID・区分・分類・機能名・カスタマイズ区分・説明・設計書md・ケース数・状態 |
| `/home/y-saito/Developments/ec-cube-enterprise` | ee のソース（コントローラ `src/Eccube/Controller/`、テンプレート `src/Eccube/Resource/template/`、コマンド `src/Eccube/Command/`、`app/Plugin/`） |
| 各機能の設計書 md | functions.tsv の「設計書md」列（リポジトリ直下からの相対パス）。画面名・処理・URL の記述がある |
| `excel_to_html/output/*.html` | 正本のHTML設計書（画面ごとのシート）。必要なときだけ該当シートを grep で引く |

手がかり列は**ヒントであって正解ではない**:
- 手がかり_既存推定: 以前ファイル名の近さで当てた推定。外れが多い。
- 手がかり_ケース内URL: そのパスが結合テストケースの本文に出てくる機能と回数。強い手がかりだが、別機能のケースが遷移元として書いているだけのこともある。
- 手がかり_現行画面名: 現行システム（pf）の画面名。バッチコマンドでは ee のコマンドの説明。

## やること

担当範囲（依頼文で指定する ID の集合）の**全件**について、1件ずつ次を決める。

1. **機能ID**: functions.tsv の機能IDを1つ。次の場合だけ例外にする。
   - 1つのアクションを複数の機能が本当に共有している（例: 同じコントローラアクションが本店TOPと支店TOPを描く、一覧と検索が同じアクション）→ カンマ区切りで複数。FP は等分する。安易に複数にしない。
   - どの機能にも当たらない → `対象外` とし、理由区分を付ける:
     `機能一覧に無い`（利用者機能だがどの機能IDにも当たらない。パッケージ標準の画面など） /
     `開発・運用用`（インストーラ、開発用、テスト用、ヘルスチェック） /
     `画面の部品`（Block 描画・AJAX の補助など、それ単体では利用者機能でないが、特定の機能の画面に属するなら機能IDを付けてよい）
   - 状態が「標準（ケース不要）」「フェーズ2見送り・実装しない」「ケースなし（その他）」の機能にも、当たるなら**その機能IDを付ける**（ケースが無い機能にFPがあることも調査結果になる）。
2. **FP種別**: ルートは transactions.tsv の値をそのまま写す。ただし、明らかに誤り（例: 検索なのに EI、CSV取込なのに EO）なら直してよく、直したら根拠に書く。バッチコマンドは EI（データを更新する）/ EO（加工して出す: メール送信・ファイル出力・外部送信）/ EQ（参照だけ）を判定する。
3. **確度**: 高（設計書の画面・URL とソースが一致）/ 中（名前と処理内容から判断）/ 低（推測が混じる）。
4. **根拠**: ソースや設計書の位置（`ファイル:行`）と、決め手を一文で。例: `src/Eccube/Controller/Admin/Stock/StockMoveController.php:120 の edit が在庫移動・振替登録画面を描く（functions/…/m04-09_….md の画面名と一致）`。

## 出力

`fp_scale/per_function/work/assign_<担当名>.tsv`（タブ区切り、UTF-8、見出しあり）。列は次の順:

```
ID	機能ID	対象外の理由	FP種別	確度	根拠
```

- 担当範囲の ID を**1件も落とさず・重複させず**に書く。
- 機能IDは functions.tsv に実在するものだけ（大文字、例 `M04-09`）。
- 書き終えたら、件数（担当範囲の件数と一致すること）・機能ごとの件数の上位・対象外の件数を最後の報告に書く。迷った件は報告に挙げる。

## 守ること

- ee・設計書・ケースは**読むだけ**。書いてよいのは自分の出力ファイルだけ。git 操作・docker・DB には触らない。
- マシンの資源が少ない。重いコマンドは `nice` を付けて1本ずつ。リポジトリ全体や `/home` 全体への grep・find はしない（`src/Eccube/Controller/Admin/Stock` のように範囲を絞る）。`node_modules`・`vendor`・`var` は見ない。
- 機能IDの割り当てに、テストケースの件数（多い・少ない）を考慮しない。ソースと設計書だけで決める（結論を先取りしないため）。
