## この巡について

1巡目の指摘8件は `fp_scale/per_function/review/r1_dispositions.tsv` のとおり反映済み（割り当てファイルの根拠欄に「codex R1 で付け替え」とある）。反映済みのものを再提示しない。`review/targets.md` は反映後の集計で作り直してある。1巡目で見ていない箇所、とくに targets.md の A・B・C の機能について、割り当て漏れ・抱え込みを重点的に見ること。

## 背景

ec-cube-enterprise（ee）の規模を概算FP法（IFPUG未調整・平均複雑度）で測りました。処理単位は「コントローラのアクション1つ＝1件」（ルート785件）と「業務バッチのコンソールコマンド1本＝1件」（34件）です。
これを別の担当者が機能一覧の機能IDへ割り当て、機能ごとのFPから結合テストのケース数の目安（IPA 全開発種別 668.8〜3,450.8 件/KFP）を出して、実際のケース数と比べました。
**割り当てを誤ると、機能のFPが増減して「ケースが少ない／多い」の判定が誤ります。** その誤りを見つけるのがこのレビューです。

## 見てほしいこと（targets.md の A〜E）

1. **A（少ない）・C（多い）**: その機能に割り当てた処理単位が正しいか。特に、**本来その機能に属する処理単位が別の機能や対象外に割り当てられていないか**（C は割り当て漏れで FP が過小になっている疑い）、逆に **別の機能の処理単位まで抱えていないか**（A は抱え込みで FP が過大になっている疑い）。
2. **B（FPが0）**: その機能を実装しているルートやコマンドが ee にあるのに、別の機能か対象外へ割り当てられていないか。ee にルートもコマンドも本当に無い（JavaScript だけ・外部の仕組み・別リポジトリ）なら、それで正しい。
3. **D（ケース0件でFPあり）**: 割り当てが正しいか（誤ってこの機能に付いていないか）。
4. **E（確度「低」）**: 割り当て先が妥当か。より適切な機能IDがあれば示す。
5. **FP種別**: 担当者が直した FP種別（根拠欄に「EI→EQ」などと書いてある）が明らかに誤っていれば指摘する。EI・EQ はどちらも重み4なので、EO（重み5）との取り違えだけ指摘すればよい。

## 指摘しないこと

- テストケースの中身や件数の多寡そのもの（このレビューは割り当てだけを見る）。
- FP の数え方の規則（1アクション＝1件、1テーブル＝1ILF、平均複雑度）そのものへの異論。
- 根拠欄の書き方（行番号が無い等）だけの指摘。割り当て先が変わらないなら不要。
- 対象外にした インストーラ（Install）・オーナーズストア（Admin/Store）・Messenger ダッシュボードが対象外であること。

## 出力形式

指摘が無ければ `NONE` の1語だけを出す。
指摘があれば1件ずつ次の形で書く。**割り当て先が変わる指摘だけ**を出す。

```
### <処理単位ID または 機能ID>
- 主張: 今の割り当て（例: TX-0123 → M04-09）
- 実際: ソース・設計書で確かめた事実（ファイル:行）
- 判定: 誤り / 疑い
- 修正案: TX-0123 → M04-10（など）
```
