# ee の結合テストはどれくらいの規模になるか

> **適用範囲:** 本資料の10,163件は、パッケージ標準を含むee全量5,702 FPへ
> 密度を適用した値。パッケージ標準から増えた約4,000 FPを母数にする差分見積は
> [PACKAGE_STANDARD_DELTA.md](PACKAGE_STANDARD_DELTA.md)を参照。

ee リポジトリ全体をファンクションポイント（FP）で測り、IPA の統計値から
**結合テストのテストケース数と検出バグ数の目安**を出したもの。

| | |
| --- | --- |
| 測定対象 | `ec-cube-enterprise` リビジョン `e62127094f`（2026-08-27） |
| 算定日 | 2026-08-31 |
| スコープ | **ee 全体**（EC-CUBE本体＋ハレルヤ独自）。結合テスト対象377機能に対応する全機能 |
| 手法 | **概算FP法**（IFPUG未調整FP・全項目を平均複雑度）＋ **バックファイア法**による検算 |
| 含まないもの | 実績値との突合。**基準値からの見積のみ**を出している |
| 再現手順 | [README.md](README.md)。数値はすべて `out/*.tsv` から生成 |

---

## 1. 答え

> **ee の規模は 5,702 FP。IPA の中央値を当てると、結合テストは約 10,200 件・
> そこで見つかるバグは約 520 件。**

| 出したい数字 | 中央値 | ありうる幅（P25〜P75） |
| --- | ---: | --- |
| **未調整FP（規模そのもの）** | **5,702 FP** | 4,182 〜 8,494 FP ※複雑度前提を振った幅 |
| **結合テストケース数** | **10,163 件** | 3,813 〜 19,676 件 |
| **結合テストの検出バグ数（現象）** | **520 件** | 234 〜 936 件 |
| 総合テストケース数（参考） | 3,175 件 | 1,439 〜 8,553 件 |
| 総合テストの検出バグ数（参考） | 172 件 | 60 〜 456 件 |

**1機能あたりに落とすと** — 結合テスト対象377機能で割って
**15.1 FP／機能、テストケース 27 件／機能**（中央値）。機能別に計画を立てるときの単位になる。

### この数字の読み方

IPA が公表しているのは**点ではなく四分位**（P25／中央／P75）。
つまり「10,163件が正解」ではなく、**業界の実績はこの幅に散らばっている**という意味。
中央値を「あるべき数」として扱わず、**幅のどこに自分たちを置くかを決めるための材料**として使う。

幅は狭くない。結合テストケース数の P25〜P75 は **5.2倍**開く。
これは測り方が雑だからではなく、この工程の実績が業界内でそれだけ散らばっているということ。

## 2. どうやって出したか

```
  ┌─ ① 数えたもの（すべて ee の実体から機械抽出）
  │
  │   Symfony ルータの実出力 ........ 902 ルート
  │     └ フレームワーク内部を除く ... 887 ルート
  │        └ コントローラアクション単位に集約
  │                                    782 基本機能プロセス
  │                                    （EI 482 / EO 112 / EQ 188）
  │   Doctrine Entity のテーブル ..... 242 → ILF
  │   外部連携システム（出典付き） ...   6 → EIF
  │
  ├─ ② IFPUG の重みを掛ける（平均複雑度）
  │       EI×4  EO×5  EQ×4  ILF×10  EIF×7
  │                                → 未調整FP 5,702
  │
  ├─ ③ 別の道で検算（バックファイア法）
  │       PHP 220,633 行 ÷ 49〜53
  │                                → 4,163〜4,503 FP（同オーダー ✓）
  │
  └─ ④ IPA『ソフトウェア開発分析データ集2022』の基準値を掛ける
          結合テストケース  1,782.3 件/KFP（中央値）
          結合テスト検出バグ   91.2 件/KFP（中央値）
                                   → 10,163 件 / 520 件
```

## 3. 規模（FP）の内訳

### 3.1 何が FP を押し上げているか

| FP種別 | 意味 | 件数 | 重み | FP | 構成比 |
| --- | --- | ---: | ---: | ---: | ---: |
| **ILF** | ee が持つデータ（テーブル） | 242 | 10 | 2,420 | 42.4% |
| **EI** | データを更新する処理（登録・編集・削除・CSV取込） | 482 | 4 | 1,928 | 33.8% |
| **EQ** | データを見るだけの処理（一覧・検索・詳細） | 188 | 4 | 752 | 13.2% |
| **EO** | 加工して出す処理（CSV出力・帳票・ダウンロード） | 112 | 5 | 560 | 9.8% |
| **EIF** | 外部システムのデータを参照する口 | 6 | 7 | 42 | 0.7% |
| | **合計（未調整FP）** | | | **5,702** | 100% |

**FP の4割は「テーブルの数」から来ている。** ここが後述の限界2に直結する。

### 3.2 どこに集中しているか

| 領域 | EI | EO | EQ | 基本機能プロセス | FP |
| --- | ---: | ---: | ---: | ---: | ---: |
| **管理画面** | 392 | 110 | 81 | **583** | **2,442** |
| フロント | 74 | 1 | 84 | 159 | 637 |
| API | 9 | 1 | 19 | 29 | 117 |
| インストーラ | 7 | 0 | 4 | 11 | 44 |

トランザクション由来FP 3,240 のうち **75% が管理画面**。
**結合テストの物量も同じ偏りになる**と見ておけばよい。

### 3.3 検算（バックファイア法）

コード行数から逆算して、FP の値が妥当かを別の道で確かめる。

| 層 | NCLOC | 代用言語 | SLOC/FP | バックファイアFP |
| --- | ---: | --- | ---: | ---: |
| ロジック層（PHP） | 220,633 | J2EE / Java | 49〜53 | **4,163 〜 4,503** |
| 表現層（Twig） | 263,060 | HTML / ASP | 40〜54 | 4,871 〜 6,576 |
| クライアント層（JS） | 5,673 | JavaScript | 53 | 107 |
| 合計（表現層を含む） | 489,366 | ― | ― | 9,141 〜 11,186 |

- ✅ **ロジック層のみ 4,163〜4,503 FP は、概算FP 5,702 と同オーダー**（乖離 1.27〜1.37倍）。
  数え方の違う2つの手法が近い値を出しているので、5,702 という値は信用してよい。
- ⚠️ **表現層を含めた合計 9,141〜11,186 FP は使わない。** OSSパッケージのフォークを
  バックファイアすると必ず起きる過大評価で、Twig 26万行は機能量ではなく
  「1つの機能を多数の画面パーツで表現した行数」を数えているため。上限側の目安まで。
- `app/DoctrineMigrations` の 61,662 行はマスタデータのINSERTが大半で機能量に対応しないため、
  主計測から外している。

## 4. IPA 基準値を当てた結果（全量）

採用FP **5,702** に、IPA『ソフトウェア開発分析データ集2022』表5-2-1〜5-2-4 を適用。
**■ が採用値。**

### 4.1 結合テスト

| ■ | **全開発種別** | **テストケース数** | 42 | **3,813** | **10,163** | **19,676** |
| ■ | **全開発種別** | **検出バグ数（現象）** | 41 | **234** | **520** | **936** |
| ■ | 全開発種別 | 検出バグ数（原因） | 27 | 262 | 536 | 773 |

| | 改良開発 | テストケース数 | 17 | 5,417 | 10,308 | 50,828 |
| | 改良開発 | 検出バグ数（現象） | 17 | 209 | 485 | 786 |
| | 再開発 | テストケース数 | 5 | ― | 20,264 | ― |
| | 再開発 | 検出バグ数（現象） | 5 | ― | 762 | ― |

**なぜ「全開発種別」を採ったか。**
本案件は pf(EC-CUBE3) の現行仕様を ee へ移す**再開発**の性格を持つ。
しかし IPA の「再開発」層は **N=5 で四分位が公表されておらず中央値しか無い**ため、
単独の根拠には使えない。参考として併記するにとどめた。

**ただし再開発中央値は見ておく必要がある。**
採るとテストケース 20,264件・検出バグ 762件で、**全開発種別中央値のちょうど約2倍**。
改良開発の P75 が 50,828件まで伸びていることと合わせて、
**上振れ側のリスクは実在する**と考えたほうがよい。

### 4.3 密度の定義（このプロジェクトで使う値）

| 指標 | 定義 | 採用値（IPA中央値） |
| --- | --- | ---: |
| **結合テスト密度** | 結合テストケース数 ÷ FP規模 | **1,782.3 件/KFP** |
| **結合テスト検出バグ密度（現象）** | 検出バグ現象数 ÷ FP規模 | **91.2 件/KFP** |
| 結合テスト検出バグ密度（原因） | 検出バグ原因数 ÷ FP規模 | 94.0 件/KFP |
| 参考: SLOC基準の結合テスト密度 | 件 ÷ KSLOC | 51.7 件/KSLOC |
| 参考: SLOC基準の検出バグ密度（現象） | 件 ÷ KSLOC | 1.111 件/KSLOC |

> **「現象」と「原因」を足したり比べたりしないこと。**
> IPA は両者を別々に集計しており、**両方を提出したプロジェクト群の重なりが少ないため
> 数だけでは比較できない**（データ集2022 5章冒頭の注記）。どちらか一方を選んで使う。

### 4.4 FP 前提を振ったときの感度

概算FP法の複雑度前提を変えると、結合テストケース数はこう動く（全開発種別・中央値 1,782.3 件/KFP）。

| 複雑度前提 | 未調整FP | 結合テストケース数 |
| --- | ---: | ---: |
| 全単純 | 4,182 | 7,454 |
| **全平均（採用）** | **5,702** | **10,163** |
| 全複雑 | 8,494 | 15,139 |

## 5. この数字の限界

数字を使う側が知っておく必要がある、誤差の**向き**と**大きさ**。

| # | 限界 | 向きと大きさ |
| :-: | --- | --- |
| 1 | **EI と EQ の切り分けは信用できない** | ee の管理画面は検索フォームを POST で送るため、IFPUG 上は EQ に当たる一覧検索が EI へ寄っている（EQ 188件は実態より少ない）。**ただし平均複雑度では EI も EQ も重み4のため、FP合計には影響しない。** |
| 2 | **1テーブル＝1ILF は過大側** | IFPUG の ILF は利用者から見た論理グループで、親子テーブルは本来1ILFに束ねる。実測242テーブルをそのまま数えたため、FPの42%を占める ILF 分は上限側。**仮に ILF を半数に束ねると 4,492 FP（−21%）、結合テストケース中央値は約8,000件になる。** ここが最大の振れ幅。 |
| 3 | **基本機能プロセスの粒度は両方向にずれる** | AJAX 用のヘルパールートも1件として数えており、利用者が認識する単位より細かいものが混じる。一方で1画面内に複数ある基本機能プロセスは取りこぼす。**誤差は過大・過小の両方向**で、打ち消し合う可能性もある。 |
| 4 | **IPA 基準値の母数が小さい** | FP規模の結合テストケース数は **N=42**、検出バグ数は **N=41**。SLOC規模（N=665／507）に比べて桁違いに少なく、P25〜P75 の幅も5.2倍と広い。**中央値を「あるべき数」として扱わないこと。** |
| 5 | **VAF（調整係数）は掛けていない** | IPA 基準値の層別定義が `5001_FP実績値(調整前)` のため、調整前FPで揃えている。意図的な省略。 |

## 6. 用語

| 用語 | 意味 |
| --- | --- |
| **FP（ファンクションポイント）** | 実装量ではなく、利用者から見た**機能の量**で規模を測る単位。言語や実装方針に左右されない |
| **未調整FP** | 複雑度の調整係数（VAF）を掛ける前のFP。IPA 統計はこちらで集計されている |
| **概算FP法** | 個々の機能の複雑度を判定せず、全項目を「平均」複雑度とみなして数える簡易法 |
| **EI / EO / EQ** | トランザクション型ファンクション。順に 入力（更新）／出力（加工して出す）／照会（見るだけ） |
| **ILF / EIF** | データ型ファンクション。順に 自分が持つデータ／外部システムが持つデータ |
| **基本機能プロセス** | 利用者にとって意味のある処理のひとまとまり。FP はこの単位で数える |
| **P25 / 中央 / P75** | 四分位。P25＝下位25%の位置、P75＝上位25%の位置。**P25〜P75 に実績の半数が入る** |
| **NCLOC** | 空行とコメント行を除いたコード行数 |
| **バックファイア法** | コード行数を言語ごとの換算値（SLOC/FP）で割ってFPを逆算する検算手法 |
