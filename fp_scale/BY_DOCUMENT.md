# HTML設計書ファイルごとの分解

[FP_AND_TEST_SCALE.md](FP_AND_TEST_SCALE.md) の全体規模を、正本HTML設計書のファイル単位（書）に割ったもの。

- 生成: `python3 fp_scale/build_by_doc.py` → `out/by_document.tsv`
- 対象: 正本HTML設計書 **45冊 / 要求 40,178件**

---

## 1. 何ができて、何ができないか

| 指標 | 書別に出せるか | 根拠 |
| --- | --- | --- |
| 要求数（規模の代理） | ✅ **45冊すべて** | 正本HTMLからの機械抽出。欠測ゼロ |
| 指摘件数・重要度 | ✅ **41冊** | `design_audit/<書>/verdicts.tsv` と `AUDIT_<書>.tsv` |
| **指摘率（要求あたり）** | ✅ **41冊** | 上記2つの割り算。按分を使わない実測 |
| ITケース数 | △ **31冊** | 機能に紐づくものだけ。14冊はケース0 |
| **FP（件/KFP のバグ密度）** | ❌ **出せない** | 下記の通り |

### FP を書別に割れない理由

FP のうち **EI/EO/EQ（57%）は「どのルートがどの設計書に属するか」が確定していないと割れない**。
現状の帰属状況:

| | 数 | 割合 |
| --- | ---: | ---: |
| 書に紐づいた機能 | 381 | ― |
| うち実装ルートまで帰属済み | **173** | **45%** |
| ルート帰属がゼロの書 | **14冊** | 45冊中 |
| 到達できたルート | 500 | 902ルート中 55% |

ルート帰属ゼロの14冊には **0517（1,088要求）・0416・0405・0404・0302** など要求数の大きい書が含まれる。
残る55%を推定で埋めれば書別FPは作れるが、**それは実測ではなく按分**になり、
その按分値で割ったバグ密度は按分の仮定を測っているだけになる。**だから出していない。**

**FP を書別に割りたい場合に必要な作業**は1つだけ:
902ルート ↔ 394機能 の帰属を全数で作ること。作れば `build_by_doc.py` に列を足すだけで
「件/KFP」の書別バグ密度が出る。

## 2. 代わりに使う分母 — 要求数

正本HTMLから抽出した**要求数**を規模の代理に使う。45冊で欠測がなく、按分も推定も挟まない。

```
指摘率 = 掲載指摘件数 ÷ 対象要求数
         （対象要求数 = 判定済要求数 − OUT_OF_SCOPE）
```

**全体の水準: 23,128 対象要求に対し掲載指摘 855件 = 37.0 件/千要求（3.70%）**

これが書別の比較の基準線になる。

## 4. 読みどころ

### 4.1 指摘率が高い書（対象要求200件以上）

| 書 | 指摘率 | 対象要求 | 指摘 | P1 |
| --- | ---: | ---: | ---: | ---: |
| 0307 | 69.1 | 376 | 26 | 1 |
| 0209 | 67.9 | 501 | 34 | 0 |
| 0306 | 54.5 | 1,449 | 79 | 3 |
| 0505 | 54.2 | 277 | 15 | 0 |
| 0515 | 46.6 | 472 | 22 | 0 |
| 0202 | 43.0 | 3,441 | 148 | 4 |

全体平均 37.0 の **1.5〜1.9倍**。**0306 と 0202 は率も件数も大きく、P1 も出ている**ため、
結合テストの重点配分先としては最優先。

### 4.2 指摘率が低い書

| 書 | 指摘率 | 対象要求 | 指摘 |
| --- | ---: | ---: | ---: |
| 0308 | 8.0 | 251 | 2 |
| 0408 | 14.7 | 339 | 5 |
| 0507 | 17.2 | 232 | 4 |
| 0514 | 17.2 | 233 | 4 |
| 0517 | 20.5 | 586 | 12 |

**低い＝品質が良い、とは限らない。** 0517 と 0514 は次項のとおりITケースも薄く、
「見ていないから出ていない」可能性を切り分けられていない。

### 4.3 テストが薄い書（要求300件以上・ケース/要求が低い順）

| 書 | ケース/要求 | 要求数 | ITケース |
| --- | ---: | ---: | ---: |
| 0000 / 0211_詳細設計 / 0416 / 0515 | 0.0 | 865 / 759 / 382 / 745 | **0** |
| 0514 | 0.2 | 661 | 114 |
| 0517 | 0.2 | 1,088 | 190 |
| 0301 | 0.4 | 849 | 309 |
| 0502 | 0.4 | 547 | 192 |

一方で 0203・0204・0209・0213 は 1.4〜2.0 件/要求。**同じ1要求に対するテストの厚みが10倍違う。**
この偏りは規模ではなく整備状況の差なので、**書別に見る最大の価値はここ**にある。

### 4.4 P1 の分布

P1 は全体で 23件。**0204(5) / 0202(4) / 0306(3) / 0517(2) / 0501(2)** に集中している。
0517 は指摘率が低い（20.5）のに P1 が2件出ており、**率だけで優先度を決めないこと。**

## 5. この数字を IPA 基準と直接比べてはいけない

**掲載指摘855件は「設計書と実装の静的突合で見つけた乖離」であって、「結合テストで検出したバグ」ではない。**

| | 本監査の指摘 | IPA の結合テスト検出バグ |
| --- | --- | --- |
| 検出手段 | 設計書の記述と実装ソースの読み比べ | テストの実行 |
| 検出できるもの | 設計と実装の食い違い | 実行して初めて出る不整合、結合面の不具合 |
| 工程 | テスト実行前 | 結合テスト工程 |

参考までに全体を FP で割ると 855件 ÷ 5.702 KFP = **150 件/KFP** で、
IPA の結合テスト検出バグ密度の中央値 91.2 件/KFP と同じ桁に収まる。
だが**上表のとおり測っているものが違うので、この一致に意味を読み取らないこと。**
IPA 基準と比較できるのは、結合テストを実行して検出したバグを数えたときだけ。
