## §1. 全ケース共通前提
- **入口/認証**: MTGバイヤー（外部アプリ）が pf-api の A06系APIを `jwt-token` ヘッダのJWTで認証して呼び出す（L323,L363,L366）。本書はEC-CUBE側APIを利用者視点の入口として扱う（L324）。管理画面URL・MTGバイヤー本体画面は対象外（§0）。
- **対象API**: ログイン `POST /admin/login.json`、査定対象一覧 `GET /admin/otcBuyOrders.json`、査定結果確定（詳細更新）`PUT /admin/otcBuyOrder/{id}.json`、ステータス更新 `PUT /admin/otcBuyOrder/{id}/status.json`、フリーコメント更新 `PUT /admin/otcBuyOrder/{id}/free_comment.json`、本人確認更新 `PUT /admin/otcBuyOrder/{id}/identification.json`（L323）。
- **副作用テーブル**（L357）: `dtb_otc_buy_order` / `dtb_otc_buy_order_detail` / `dtb_otc_buy_order_indivisual_input_product` / `dtb_otc_buy_order_stock` / `dtb_otc_buy_order_stock_history` / `dtb_otc_buy_order_status_history`（参照: `mtb_otc_buy_order_status`）。DB永続化の正はec-cube-enterprise、承認ワークフローを介さず persist/flush で直接確定（L359）。
- **トランザクション/ロック**: 詳細更新は「既存明細・在庫の削除→明細・在庫・履歴の登録→受注更新→ステータス履歴登録」を一連の保存処理として扱い、例外時は未確定更新をロールバックする（L389）。専用の楽観/悲観ロック・ロックファイルは持たず、同時更新は後勝ち（L344,L347,L389）。
- **応答形式**: JSON（L324,L350,L353）。更新API成功時は対象データを保存し成功コード/更新結果を返す。失敗（認証不可/該当なし/入力不正/保存例外）は各API設計のHTTPステータス・本文形式に従う（L350,L372）＝契約細部はCONTRACT委譲（§5）。
- **オラクル独立性**: 期待は詳細設計HTML由来で実装から独立。実装との差は付帯表4で乖離＝バグ候補として扱う。
