# 戦略: 25,561件を「実行・判定できる具体オラクル」に仕上げる

> 2026-07-22 ／ 立案: fable5（戦略立案）／ 次: codex 敵対レビュー → M0スパイク着手
> 前提: `MILESTONE_STATUS.md`（母集合設計・実行区分は確定／ケースオラクルは未達＝本戦略の対象）

## 0. 診断（調査で確定）
汎用期待値の震源は生成器 `generate_it_cases.py` の `expected_result()`（観点ラベル＋定型句しか返さず、
HTML由来cueは観点と無関係にラウンドロビン割当）。台帳の期待列は構造的に実値を持てない。
一方、**オラクル素材の中間資産が既に存在**する:
- 手本: `integration_test/e2e/a02_01_..._e2e_cases.md`（付帯表3-1 SEED固定値＋等値照合型）
- `item_definition_audit/item_definition_audit_scoped.tsv`（683項目・pf/ee両実装値・file:line）
- `message_inventory/MESSAGE_LIST.tsv`（1,158メッセージID・根拠付き）
- `e2e/seed/manifest.json`（SEED帯・envVars契約・apply/teardown実装済み）
- `_poc2_*`（期待=正本verbatim・根拠file:line付き、入力実値なし）

→ 本フェーズは「ゼロから書く」でなく **「既存資産を1本の結合キーで繋ぐ」** 問題。

## 1. アーキテクチャ: 台帳凍結＋3コンパニオン層
検証済み整合（trace一意・差分0）を壊さないため台帳（all_it_cases/trace/execution_assignment）は凍結。
- **L1 `integration_test/oracle/<fid>_oracle.tsv`**: 機能別オラクル表。1行=1オラクル単位。
  列: オラクルID/種別/対象/期待実値/値種別(実値|定数名|委譲|TBD)/根拠(file:line)/オラクル源。
- **L2 `integration_test/oracle/oracle_binding.tsv`**: テストID→オラクル行→SEEDキー→期待式。
  binding不成立=オラクル欠落として自動計上（=未実装計器G8オラクル被覆率の実現）。
- **L3 `integration_test/exec/<fid>_it_exec.md`**: L1+L2から機械レンダリングする実行ワークブック
  （a02-01型: 付帯表3-1 SEED固定値＋DDT表＋ケース。既存e2e/*_e2e_cases.mdと別ディレクトリ）。
圧縮見込み: 25,561件のbindingに対しL1オラクル行は1/5〜1/10。

## 3. SEED固定値（正は manifest.json 一本）
- **M0で帯拡張**（現1,000個中150消費・380機能で枯渇）: モジュール別サブ帯へ桁上げ・既存割当は動かさず上積み。
- 合成値は捏造でないが**制約適合性は設計書由来**（桁数内・型適合・状態コードは定義域から）→ゲートO4で検査。
- 境界値入力はSEEDに置かず決定的生成関数（`boundary(max=50)`参照・Nの根拠はL1）。
- **`e2e/helpers/db.ts` 新設**（DBアサーション。現在e2eに存在せず）: 「Playwright+手動確認7,126件」の大半を
  Playwright単独へ落とす最大の工数レバー（区分根拠が「期待値がGUIに出ない=DB確認要」だったため）。

## 4. スケール手段（実行方法区分別パイプライン・`integration_test/tools/`）
- **Phase A 決定的抽出(LLM不使用)** `oracle_extract.py`: mdの構造化表をパーサ抽出→L1。audit/MESSAGE_LIST変換取込。
- **Phase B LLM補完(散文のみ)**: 表にない実値をLLM抽出・**逐語引用必須**・機械ゲートで逐語存在照合。量産判定はfable5並列可。
- **Phase C binding生成**: 台帳×L1を観点タイプ経由で結合・曖昧はLLM第2パス（文字列突合2度破綻の教訓）。未結合=欠落レポート。
- **Phase D レンダリング(区分別)**: Playwright=DDT spec機械生成（既存POM 364再利用）／Playwright+手動確認=db.ts昇格＋残は観測SQL手順書／非UI=API request・バッチrunner新設／手動301=紙で完結。

## 5. 捏造ゼロ担保 `oracle_gate.py`（ハードゲート exit1）
- O1 根拠実在（file:line） / O2 逐語一致（数値・文言、散文は引用照合） / O3 3類型明示（実値欄に推測値なし）
  / O4 SEED制約適合 / O5 実装値混入スキャン（「Excelを正」正当・「実ソースを正」違反）/ O6 被覆率双方向(=G8)。
- 敵対レビューは **codex単独**（fable5は抽出・判定の量産バッチのみ）。**新規実装35機能は全件codex較正**
  （薄Excel過剰具体化は機械で捕まらない実証）。**カナリア**（故意欠陥1件混入で検出率計測）。

## 7. 落とし穴と対策
1. 文字列突合2度破綻→機械照合は逐語存在(O2)限定・意味結合はLLM第2パス。
2. pf/ee意味論差→桁数オラクルは単位=文字数明記・Form層とDB層の両観測層保持。
3. 「制約が無い」は証明不能→否定形オラクル生成禁止・沈黙は要判定。
4. 設計書情報不足→3類型＋TBD正直伝播・HUMAN_DECISION_LIST 32機能は業務回答まで除外。
5. 新規実装の過剰具体化→codex外部較正無条件必須。
6. 帯枯渇→M0で拡張（後追いはenv契約破壊）。
7. 台帳再生成事故→本フェーズは台帳を触らずcompanion層のみ追加（--overwrite地雷・権限ゲート回避）。
8. 実行時データ汚染→ワークブック単位にteardown/reseed機械組込。
9. 旧設計書陳腐化（GMO残存25の前例）→決済抽出はSPLINKS系allowlist。
