## §1. 全ケース共通前提
- **入口/認証**: 呼び出し元は買取アプリ（MTGバイヤー）。ルートは `PUT /admin/buyOrder/{id}.json`（正本 L316）。`jwt-token` ヘッダのJWT（HS256）を検証し、ペイロードの利用者IDから管理者会員を引く（正本 L320）。ヘッダ欠落・署名不正・該当管理者会員なしのいずれも認証拒否 HTTP 401（正本 L320,L339）。認証方式はExcel `0507:L1660`（トークン）と一致。
- **判定順序**（正本 L325）: ①認証（失敗401）→②受注ID特定（なし404）→③入力検証（失敗400・更新しない）→④明細処理・合計額算出→⑤既存カード整理（まとめ買取／サプライ保持）→⑥受注更新・不要データ削除→⑦ステータス変化時のみ履歴登録→⑧1トランザクションで確定（例外はロールバックし500）→⑨成功時 code 200。
- **トランザクション**（正本 L381）: 明細の取得・登録・削除、受注更新、履歴登録までを1トランザクション。例外時はロールバックし HTTP 500。楽観／悲観ロックは持たず、同一受注への同時更新は後勝ち（正本 L363,L381）。
- **副作用**（Excel `0507:L1692-1694` 優先／正本 L353-355 補完）: 受注のステータス・合計額・更新担当者・更新日時を更新。送られた明細から買取代表カード・個別入力商品を登録／更新し、保持しない既存分と紐づく申込時買取価格を削除。まとめ買取商品（オプションマスタのまとめ買取商品ID）は既存明細＝買取代表カードを削除し、紐づく申込時買取価格も削除する（Excel `0507:L1692`「まとめて買取の商品ID（固定の商品ID、固定の金額）の明細を削除する」が正。詳細設計正本 L355「申込時買取価格のみ削除」はExcelと食い違いのため付帯表4#3にポインタ列挙・期待には用いない）。ステータス変更時のみステータス履歴を1件登録。
- **応答整形**（正本 L356）: JSON応答。プロパティは camelCase、日時は ISO8601、`serialize_null` 有効。
- **オラクル独立性**: 期待はオラクル（Excel優先・沈黙部は詳細設計HTML）由来で実装から独立。実装との差は付帯表4で乖離＝バグ候補として扱う。
