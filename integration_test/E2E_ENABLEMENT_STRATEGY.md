## 1. 目的と非目的

### 1.1 「実行可能」の定義（本戦略の到達点）

あるテストケースが**実行可能**であるとは、次の3条件を同時に満たすこと:

1. **具体オラクル**: 実施者（人またはspec）が**そのケース単体で**入力実値・照合実値を持ち、
   合否を判定できる。期待値は一次資料由来（捏造ゼロ）で、`source_class` と根拠(file:line)を持つ
   （ORACLE_STRATEGY L1/L2の定義に従う。汎用文言「標準のページ設定ブロック構成で描画」等は不合格）。
2. **再現可能な前提**: 前提状態がSEEDセットID（`e2e/seed/manifest.json` 契約）で機械再現でき、
   べき等（apply.sh 再実行で収束）・teardown可能である。
3. **判定手段の実装**: 区分に応じた判定手段（spec自動assert／キャプチャ+目視判定基準／
   API・DB検証／手動手順書）が存在し、結果が記録先（e2e_cases.md 結果列）に残る。

### 1.2 非目的（本戦略でやらないこと）

- **母集合25,549件の削減・再設計はしない**。台帳3本（all_it_cases/trace/execution_assignment）は
  凍結（ORACLE_STRATEGY §1）。実行可能化はcompanion層（oracle/・exec/・e2e/）の追加のみで行う。
- **手動301件の自動化はしない**（ユーザー指示: そのまま進める）。障害注入・機密実挙動・
  外部代行（決済/GMO等）・聖域は自動化対象外のまま手動管理する。
- **全件Pass達成は目的でない**。仕様乖離で落ちるのは検出成功（a02-01付帯表4の思想）。
  目的は「全件が合否判定できる状態」であり「全件が合格する状態」ではない。
- **業務未確定事項の勝手な確定はしない**（超売りNo.518・未確定オラクル33件等は§6で隔離管理）。

どの区分も「L1/L2で具体オラクルを得る→区分別の判定手段に落とす」の順で、区分は判定手段だけが違う。

### 2.0 全区分共通の絶対規約: テストデータの外部化（spec直書き禁止）

**シードデータ・CSVインポートデータ・SEED固定値（具体オラクルの入力実値）は、
spec/pageファイル内にハードコードせず、必ず外部ファイルへ切り出して保存する。**
既存基盤が既にこの型であり、これを全4トラック共通の絶対規約に格上げする:

| データ種別 | 置き場所（唯一の正） | spec からの参照経路 |
|---|---|---|
| DB前提状態（SEED） | `e2e/seed/sets/<module>/SEED-*.sql`（＋`.down.sql` 撤去対） | `manifest.json` の `envVars` 契約 → `seed-env.sh` → `process.env`（`config/*.config.ts` 経由） |
| CSV取込などファイル入力 | `e2e/fixtures/csv/`（揮発物は `gen-volatile.sh` 生成・gitignore） | fixture パス参照（パス自体も config/env で解決） |
| SEED固定値（fixtureの入力実値） | e2e_cases.md 付帯表3-1（人間可読の契約表）＋ `manifest.json`（**fixture値・再現手段としての正**） | シードID→環境変数契約。specは env/config 経由でのみ値を得る |
| 境界値入力（max/max+1等） | SEEDに置かず決定的生成関数（§2.5.3。Nの根拠はL1） | ヘルパー関数（`boundary(...)`）＋パラメータはL1オラクルID参照 |

- **【最重要・codex Blocker是正】manifest.json は「fixture値・再現手段」の正であって、
  期待値の正ではない**。期待値の正は常に**L1オラクルID**である。SEEDは入力値の出所であり、
  仕様値・DB列・変換規則の根拠に使えない（ORACLE_STRATEGY codex較正②。manifestを期待値の正に
  すると、実装都合のseed値を期待値へロンダリングできてしまう）。
  - 等値照合（「入力した値がそのまま出る」型）のアサートは**三段参照**で組む:
    `L1恒等写像claim（passthrough_basis が非SEEDの一次資料claimを指す）
    → fixture_version（SEEDセットID@manifest_sha1） → 実値`。
  - **manifest単独参照のアサート（L1 claimを経由せず env値と実値を直接比較）はゲートで機械拒否**
    （§3.2ゲート(2)を拡張: 期待側の参照はL1オラクルID必須・L1がseed_equivalence型の場合は
    passthrough_basis検証済みであること）。**拒否能力はカナリアC6**（manifest単独参照の期待値を
    故意に混入→D9三段参照ゲートが落とすことをCIで検証）と**カナリアC7**（manifestを経由しない
    fixtureファイル値の期待側直参照→D8 lintが落とす。§3.2(3)）で常時実証する
    （ORACLE_M0_PLAN §4。いずれも実行前提はD5 exit0）。
  - **三段参照形式の具体レイアウト**（e2e_cases.md 期待結果セル・L3レンダリング出力の記法）:
    `期待実値（人間可読） [L1:<oracle_id>; fixture:<SEEDセットID>@<manifest_sha1短縮>]`
    の対で書く。等値照合型は `<oracle_id>` が seed_equivalence claim（passthrough_basis検証済み）を
    指し、fixture値は「入力の再現手段」としてのみ現れる。L1参照タグの無い期待実値・
    fixture参照だけの期待実値は、抽出時（union）と生成時（spec）の両方でゲート拒否。
  - **現行a02-01（`a02_01_..._e2e_cases.md`）は旧形式**（SEED固定値を期待値に直書き・

### 2.2 トラックB: Playwright+手動確認（7,114件）— Playwright操作＋Chrome in Claudeキャプチャで目視判定を担保

この区分の定義は「自動操作はできるが**判定の一部が目視必須**（帳票見た目/PDF/印刷/CSS数値/
外部連携の実結果）」。ユーザー指示により **Chrome in Claude**（Claudeによるブラウザ実操作＋
スクリーンショット取得）を判定担保の手段として設計する。

**設計原則: キャプチャは証拠であり、オラクルではない。** 目視判定にも一次資料由来の
判定基準（何が写っていれば合格か）を必ず先に文書化する。基準なきキャプチャは判定不能＝実行可能でない。

#### 運用フロー（1機能単位）

1. **判定点の分解**: 各ケースを「自動判定可能な部分」と「目視必須の部分」に分解し、
   e2e_cases.md に**付帯表6「目視判定点表」**を新設する。列:
   `判定点ID（VP-<機能>-<連番>） / 対象ケースID / キャプチャ対象（画面・帳票・状態） /
   キャプチャ手順（URL・操作・タイミング） / 目視判定基準（一次資料由来・source_class・根拠file:line） /
   判定不能条件（何が写らなければ再取得か）`。
   判定基準の例: 「納品書PDFにExcel帳票設計<根拠>記載の8項目（宛名・受注番号…）が配置されている」。
   基準が一次資料に無い場合は**TBDとして未確定オラクル台帳へ**（捏造して基準を作らない）。
2. **自動部分の先行実行**: 操作・到達・データ整合など機械判定できる部分は通常specで先に自動実行する
   （トラックAと同じ）。目視部分だけを残す。

#### 2.5.1 オラクル決定の規約（プロジェクト既存方針・厳守）

1. **項目定義の正典はee（EC-CUBE Enterprise）**。現行pf基準で突合すると偽陽性を量産する
   （監査実績: ee固有値194 対 pf固有値1）。任意/必須・最大長の期待値は
   **三値比較（設計書HTML／pf実装／ee実装）**で決定し、設計書とeeが一致する値を第一候補、

   ee実装値をそのまま期待値にしない（source_class規約: ee-enterprise由来は標準28機能のみ
   `standard-src` として可・他は設計書正本へ遡って確定＝オラクル独立性）。
2. **最大文字数の意味論差（pf=MySQL/ee=PostgreSQL）**: pfはバイト長・eeは文字長で境界が変わる。
   よって最大文字数のL1オラクルは **unit（文字/バイト）必須**（L1スキーマの`unit`列）で、テストは
   **Form層とDB層の両方**を対象に、境界値（max/max+1/マルチバイト混在）をケース化する。
   境界値入力の生成は§2.5.3の決定的生成規約に従う（SEEDに置かない・「max相当」等の曖昧語を使わない）。
3. **「制約が無い」は断定しない**: 委譲型（Form制約がEntity/DBへ委譲されている等）では
   「制約なし」は証明不能。否定形オラクル（「エラーにならないこと」の無制限版）は生成禁止で、
   設計書が沈黙する項目の上限はTBD（未確定オラクル台帳へ）。
4. **メッセージの一次資料はロケール別のyaml対**（§2.7 locale軸と連動）:
   ja＝`messages.ja.yaml`/`validators.ja.yaml`、en＝**`messages.en.yaml`/`validators.en.yaml`**

   baseline-manifest（§0.1）でSHA固定する。実装Twig/Controllerの現文言を期待値に流用しない。

#### 2.5.3 文字数境界値の決定的生成規約（codex Blocker是正・「max相当」等の曖昧語禁止）

境界値入力はL1の `unit` ごとに**決定的生成アルゴリズム**で作り、生成パラメータを
データ契約（L1オラクルID参照）として固定する。M0で以下を規約ファイル化する:

- **unit=文字（ee/PostgreSQL系）**: `charFill(n, repertoire)` ＝ 指定文字集合から決定的順序で
  n文字を生成。repertoire は最低3種を規定: `ascii`（1byte/字）・`multibyte`（3byte/字の
  CJK固定文字、例「あ」）・`mixed`（ascii と multibyte の決定的交互）。
  期待: max受理（Form通過＋DB保存成功）／max+1拒否。**拒否の観測層（Form validatorメッセージ／
  HTML5属性ブロック／DB制約エラー）は既定を置かず、L1 claimごとに一次資料由来で必須指定**
  （codex R2是正: 「max+1=Form層」は常に成り立たない。観測層未指定の文字数系claimはゲート拒否
  ＝ORACLE_M0_PLAN D11）。
- **unit=バイト（pf現行回帰系）**: `byteFill(nBytes, repertoire)` ＝ UTF-8バイト数がちょうど
  nBytes になる決定的文字列（端数はasciiで充填。不可能な組は生成せず契約エラー）。
  期待: nBytes受理／nBytes+1拒否。**同一文字数でもバイト長が変わることをrepertoire別に検証**
  （文字制約とバイト制約の判別がこのサブトラックの主目的）。
- **Unicode正規化**: 生成値はNFC固定と明記（結合文字による長さ揺れを排除）。NFD等の正規化差を
  試す観点は別claim（適用可否は設計書記載がある場合のみ）。
- **観測方法の契約**: Form層＝該当validatorメッセージ（§2.5.1-4のロケール別yaml由来）または
  HTML5属性ブロック（どちらの層かはL1 claimに明記）。DB層＝`db.ts` で保存後の列値
  （文字数/バイト長を両方測定）と列定義。**Form層通過→DB保存失敗**が起きた場合は
  ×（仕様乖離候補）でなくまず**トリアージ分類（§2.6.2）の「fixture/隔離」「SUT乖離候補」を
  証跡付きで判別**し、確定時は「層間不整合」として付帯表4へ記録する分類を設ける。
- max/max+1 の N は必ずL1オラクルID（unit付き）から取得（生成関数にリテラルNを渡す呼び出しは
  外部化lintの検査対象）。

#### 2.5.4 規模とパイプラインへの影響

- 粒度が「ケース」から「項目×制約種別×層×境界値」のアサーションへ細分化されるため、

- 概算規模（計画用・確定値にしない）: 再生成固定後のスコープ項目（現行実測682・§2.5.2の
  再生成で確定）×（必須1＋文字数上限がある項目のみForm境界×repertoire＋DB層＋メッセージ×locale）で

#### 2.6.1 テストケースが正＝オラクル不可侵

**期待値どおりにならなくても、テストの期待値（Playwrightアサーション含む）も、ee実装（SUT）も、
絶対に変更しない。** 不一致は「不具合・仕様乖離の検出＝テストの成功」であり、
通すために期待値やSUTを直す対象ではない（a02-01付帯表4の思想を全トラックA/B/C/Dの鉄則に格上げ）。

- 検出した乖離は **何も変えずに ×（仕様乖離）として記録**し、当該機能の付帯表4
  （不具合候補/要確認）＋`BUG_CANDIDATE_REGISTER.md` 系へ登録する。
- 期待値の変更が許されるのは唯一、**L1オラクル自体の是正**（根拠の読み誤り・設計書改訂）が
  ゲート（O1-O6）とcodexレビューを通った場合のみ。specから直接期待値を書き換える経路は存在しない
  （§3.2の生成拒否ゲートで機械遮断）。
- ee実装の修正は本プロジェクトのスコープ外（不具合候補として報告するまで）。

#### 2.6.2 唯一の例外＝ハーネス修正（失敗トリアージの5分類・codex Blocker是正）

失敗はすべて次の**5分類**でトリアージしてから記録する（全トラックの運用フローに組み込む）。
HTTPステータス不一致・タイムアウト等の症状は、URL誤り・認証・seed・待機・外部依存でも生じるため、
**症状だけでSUT乖離へ分類しない**（既存実績の実例: 画面遷移済みなのにナビ待機30秒タイムアウト、
HTML5バリデーションをサーバ側メッセージとして観測し損ね）。

| 分類 | 定義 | 対応 |
|---|---|---|
| **(1) SUT乖離候補** | ハーネス・fixture・環境の健全性を証跡で確認済みで、SUT実挙動が期待値（L1オラクル）と異なる疑い | 下記の**×確定プロトコル**を経て初めて「仕様乖離」×を確定→付帯表4/不具合候補登録。期待値・SUTは変更しない |
| **(2) ハーネス** | セレクタ誤り・待機不足・遷移ハンドリング・観測層の取り違え等、Playwright実装のバグ | **page/specの操作・観測ロジックのみ修正**して再実行。期待値・オラクルID参照は変更禁止 |
| **(3) fixture/隔離** | seed不足・fixture値の誤り・前ケースの残存状態・データ衝突 | SEED/teardown/隔離契約（§2.6.4）の是正として扱い、fixture変更は変更管理（§2.6.5）経由で再実行 |
| **(4) 環境・外部依存** | 環境未起動・外部サービス未接続・サンドボックス・Toolbar遮蔽等 | ×にせず「未実施（理由コード）」。環境是正後に再実行 |
| **(5) 判定不能** | 証跡不足でいずれとも確定できない | ×にも〇にもしない。「判定不能（要証跡）」として残し、証跡を追加して再トリアージ |

- **×（仕様乖離）確定プロトコル**: **1回の実行だけで確定させない**。確定には次の証跡を必須とする:
  ①再現手順（決定的に再現すること） ②実行ログ・Playwright trace・SUT応答（HTTP/DOM/DB）の記録
  ③fixture hash（fixture_version@manifest_sha1＝どのデータ状態か） ④**独立観測**（別経路での確認:
  手動再現・APIレベル確認・DB直接参照のいずれか）。証跡が揃わない間は (5)判定不能 に留める。
- **証跡テンプレート（M0=D16で様式化・必須フィールド）**: 症状／分類コード／再現手順／
  実行ログ・trace参照パス／SUT応答（HTTP・DOM・DB のうち該当）／fixture hash
  （fixture_version@manifest_sha1）／独立観測の種別と結果／判定者・判定時刻。
  欠落フィールドのある×確定はゲート拒否。
- **独立観測の選択条件（観測層別の対応表）**: UI観測の失敗→API直叩きまたはDB直接参照で確認／
  API観測の失敗→DB直接参照または手動再現／DB観測の失敗→別接続からの再クエリ＋手動再現／
  バッチ観測の失敗→DB＋実行ログ。同一経路の再実行は独立観測と認めない。
- **判定不能(5)の滞留期限**: 起票から**5営業日またはフェーズ末の早い方**。期限超過は棚卸しで
  裁定（担当再割当・証跡取得計画の明示）。期限超過を理由に自動で×や〇へ倒すことは禁止。
- ハーネス修正のdiffは「操作・観測ロジックのみ」であることをレビューで確認する
  （期待値リテラルの変更が混ざったらリジェクト。§2.0の外部化lintが期待値直書き自体を防ぐ）。
- **失敗理由の記録語彙**は既存運用（`e2e/reports/standard-e2e-execution-todo.md`）の症状語彙
  （セレクタ不一致・タイムアウト・HTTPステータス不一致・Toolbar遮蔽・シード不足・外部未接続等）を
  **症状**として残しつつ、必ず上記5分類の**分類コード**を併記する（症状→分類の自動対応付けはしない）。

#### 2.6.3 結果記録の二重化（md⇔TSVの同期規約)

テストは何度も回すため、合否の記録は次の2層で持ち、機械同期する:

1. **正（single source of truth）＝各 `integration_test/e2e/<機能>_e2e_cases.md` 内の
   14列ケース表（実施者・実施日・結果・失敗理由の実施管理欄）**。実行のたびにここへ追記更新する
   （結果 `〇`/`×`＋失敗理由は上記語彙。fixme/skipは〇にしない＝既存運用ルール踏襲）。
2. **導出＝統合具体TSV（§3.5）／レポート**: 一枚の実行用テストケースTSV
   `all_e2e_cases_concrete.tsv` と `e2e/reports/*-execution-todo.md`（実行履歴・コマンドライン・
   passed/failed内訳）は、mdのケース表から**機械union/抽出で生成**する（手で二重入力しない）。
   統合具体TSVは導出ビューであり**手編集しない**（結果もmd側に書き、再生成で反映する）。
   **同期検証は「再生成して差分0」だけでは保証にならない**（codex Major是正: 壊れた抽出器は
   壊れた出力を再現して差分0になる）。次をM0で契約化する:
   ①**入力manifest**（union対象mdの確定リスト。384ファイルの列挙＋各mdのsha256）
   ②**抽出器の固定版**（TSVブロック抽出規則: コードフェンス・複数表・改行セル・引用符の扱いを
   仕様化し、抽出器自体のバージョン/ハッシュを統合TSVヘッダに記録）
   ③**行単位source hash**（統合TSV各行に source md・行位置・内容hash＝§3.5.1の行メタ）
   ④**独立した逆検証**（統合TSV→全md行集合へ戻す逆変換で、欠落・余剰・列数不正をexit1。
   順方向とは別実装で検査する）。mdとTSVが食い違ったら**mdが正**、TSVを再生成する。
   `format_tsv --check` 通過は必要条件（十分条件ではない）。
3. 複数回実行の履歴は reports 側（実行履歴表）に時系列で残し、mdの結果列は**最新実行の判定**を持つ
   （過去×→今回〇の場合も履歴はreportsに残るため監査遡及可能）。

#### 2.6.4 冪等性と隔離・復元契約（codex Blocker是正: 2連続同一判定は必要条件であって十分条件でない）

- **前提の冪等**: SEEDは既存規約（固定ID＋`ON CONFLICT DO UPDATE`＋`seed_resync`。apply.sh 2回で
  収束＝検証済み）を全モジュール拡張でも厳守。撤去は `.down.sql`（子→親・帯ID＋マーカー）。
- **状態は DB だけではない — 5系統の隔離・復元契約**をケース（最低限ワークブック）単位で定義する。
  同じ誤った残存状態で2回通れば「同一判定」になり得るため、系統ごとに初期化・検証・撤去を持つ:

  | 状態系統 | 既知の実態（一次資料） | 初期化・検証・撤去の契約 |
  |---|---|---|
  | DB | seed契約で管理済み | 帯内スナップショット（seed前後の対象テーブル差分0検証）＋.down |
  | cache/RateLimiter | **RateLimiter状態はSQL seedで生成不可**（seed README明記: 実行時に連続失敗or専用setupで生成） | 実行前の状態リセット手順（cacheクリア/保存先初期化）を機能契約に明記。ロック系ケースはsetupで状態生成→teardownで消去 |
  | queue/非同期ジョブ | バッチ・messenger系 | 実行前キュー空検証・実行後の残ジョブ検査 |
  | mail | mailcatcher(:1025/:1080)へ隔離済み | ケース前にmailcatcher受信箱クリア・検証後クリア |
  | 外部スタブ/連携 | 外部API・決済スタブ | スタブ状態の初期化とリセットをスタブ契約に含める（未整備なら当該ケースは未実施(理由コード)） |

- **実行中の汚染防止**: 破壊的更新系（保存・削除・ステータス変更・CSV取込）は
  **使い捨て専用SEEDに限定**し、spec の afterEach（またはワークブック単位のteardown/reseed）で
  初期値へ復元する。一覧の「先頭受注」等、共有データへの書込みは禁止
  （m05-13 specに実在する既知の穴。E2で是正し、以後の量産では生成時点で禁止）。
  各機能の対象データと復元方法は **e2e_cases.md 付帯表3** に定義し、SEED実装はその契約に従う
  （付帯表3→manifest.json→sets/*.sql の順で具体化）。
- **並行実行の隔離**: 並行実行・障害注入を要する行（§2.7マトリクスの属性）は共有環境での
  同時実行を禁止し、**serial実行または専用コンテナ/namespace**を必須化する（M0で要否を機能別に判定）。
- **契約テンプレートの必須フィールド（M0=D12で様式化）**: 5系統それぞれについて
  初期化コマンド（実コマンド行）／対象（テーブル・キャッシュ保存先・キュー・受信箱・スタブ）／
  スナップショット範囲（帯内テーブルと抽出条件）／namespace・serial実行の割当規則。
  フィールド欠落の契約は使用不可。
- **スナップショット検証の定義**（「seed前後差分0」の曖昧さを是正）:
  (i) **apply→再apply収束**＝帯内件数・内容が不変（べき等）。
  (ii) **teardown後の帯内差分0**＝seedが投入した帯内レコードが撤去済み（seed投入自体は
  差分を作るのが正常。検証対象は「撤去の完全性」と「再適用の収束」）。
- **完了ゲート（機能単位）**: ①フレッシュDBからの再構築→seed→実行で結果再現
  ②上記スナップショット検証（(i)(ii)）通過 ③**独立した2回のfixture適用**（apply→teardown→apply）で
  同一状態に収束 ④同一シード状態からの2連続実行で同一判定（flaky検出）。
  ④単独では汚染ゼロを証明しないため、①〜③と併せて初めて完了とする。
- 非べき等操作（`eccube:install` 等の初回構築）はSEEDと明確に分離し、フレッシュDB再構築手順として
  別文書化する（§5-1）。

#### 2.6.5 変更管理（期待値改変の抜け道封鎖・codex Major是正）

specリテラルの直書き禁止（§2.0）だけでは、**manifest・fixture・helper・L1参照先・期待値生成関数を
変えることで期待実値を変えられる**。よって実行期間中は次を変更管理対象とする:
**L1台帳・L2 binding・manifest.json・seed SQL/fixture・期待値生成関数（boundary等）・抽出器/union生成器**。
- 変更には ①変更理由（L1是正/ハーネス起因のfixture是正/シード拡充 の別） ②根拠差分（一次資料）
  ③承認 ④影響test_id列挙 ⑤影響ケースの再実行 を必須とする。
- **承認主体の規定**: L1是正・オラクル系変更＝codexレビュー必須／要件・スコープに触れる変更
  （en要件・対象外化・baseline更新）＝発注者決裁必須／ハーネス起因fixture是正＝機械検査
  （影響test_idの再実行green）＋事後codexサンプリング。**承認が得られない変更はゲートが拒否**
  （未承認エントリを参照する実行結果は無効）。
- **変更台帳はappend-only**とし、各エントリに前エントリのhashを持たせる（hashチェーン断絶＝
  改竄検知でexit1。ORACLE_M0_PLAN D13）。
- **baseline更新の順序強制**: baseline-manifest更新 → 全ゲート再実行 → 旧baselineに紐づく
  過去結果の無効化範囲を明示、の順のみ許可（更新前結果を新baselineの実績に流用しない）。
- 「L1是正」と「ハーネス修正に伴うfixture変更」を機械的に区別できるよう、変更記録に
  種別コードを持たせ、L1の期待値に触る変更はO1-O6再通過を必須にする。

### 2.7 多軸実行マトリクス（実行・完了の正）＋ロケール軸 ja/en

#### 2.7.1 実行マトリクスの定義（codex Blocker是正: 4トラック一軸では多軸契約が消える）

上流の `execution-schema.md`（確定済みデータ契約）は、実行属性を**独立列**として要求する:
実行チャネル（UI/API/DB/batch・複数可）・必須観測層（Form/DB/外部/通知・複数可）・
実環境依存（実決済/スタブ/契約試験/障害注入/なし）・人手承認・並行実行・障害注入・
VRT初回承認・**聖域（全数実行必須・代表/サンプリング禁止）**・未解決。

**事実（codex R2確定）: 現物 `execution_assignment.tsv` は10列のみで、
人手承認・並行実行・未解決 列が存在しない＝「全属性join」の入力は現在存在しない**
（execution-schema.md の「多軸化はP2で全件適用」は未適用が実態）。
よって本戦略は次の**入力契約**を定め、その充足をM0成果物（ORACLE_M0_PLAN **D14**）とする:

  **未付与を表す明示値**（空文字でなく `未付与` を予約値とし、正規値と機械区別）・
  **付与規則**（`case_viewpoint_trace.tsv` を唯一の入力とする決定的規則。ケース側(IT-ID,小項目)
  逆引き禁止＝schema §0）・**再計算hash**（規則+入力から出力hashが再現）を定義する。
- **成果物**: 全25,549行（baseline）へ属性を再付与した固定台帳 `execution_assignment_v2.tsv`
  （SHA固定・baseline-manifestへ追加）。
- **受入基準（codex R3是正: v2ファイル自体の受入検査。いずれか1件でも即exit1）**:
  (a) 全必須属性が非空・非`未付与`（未付与1件でもv2受入失敗＝「聖域/完了判定時のみ失敗」は撤回）
  (b) traceの全キーと一対一対応（欠落0・余剰0）
  (c) キー重複0
  (d) 値域外の値0（execution-schema.md §2の型・値域で全セル検査）

  以降の全joinはそのSHAのv2のみを入力とする。v2受入合格まで、§7の③実行済・聖域被覆は

- **完了判定は属性ごと**: 各行について、要求属性（例: 必須観測層=DB＋通知・障害注入=1）が
  すべて実施証跡（spec実行結果・db.tsアサート・キャプチャmanifest・手動記録）を持つか、
  未実施理由コードを持つ状態を「会計済み」とする。**通常Playwright実行の成功だけでは
  障害注入・並行実行・外部観測を要する行は完了にならない**。
- **聖域全数ゲート**: 聖域=1（現baseline 2,014件）は代表・サンプリング禁止＝全行が属性充足で

#### 2.7.2 ロケール軸 locale∈{ja,en}（ユーザー要件: UI確認もen必須）

- **locale を一級の実行軸**として実行マトリクスに追加する。ja/en の両方で実行・判定し、
  **UI（画面）確認も en が必須**。フロントの切替口は既存の `ECCUBE_FRONT_LOCALE`
  （`e2e/config/default.config.ts:10,24`・既定ja。**フロント用設定であり管理画面の切替を
  証明しない**）。**M0 Go条件（ORACLE_M0_PLAN D15）＝「管理画面を含む対象UIで en 到達・
  画面取得に成功」の実機PoC**。不能な場合は「対象外」ではなく、**要件変更の明示決裁（発注者）
  または実現手段確立まで実装停止**とする（手動移管・対象外承認でen要件を満たしたことにしない）。
- **locale_sensitive はL1 claimの属性**とし、**決定表で機械分類**する（codex R2是正:
  例示だけでは「全部sensitiveで倍化」も「全部非sensitiveでenを消す」も阻止できない）。
  分類キーは `claim_type × 観測対象 × ユーザー可視性`:

  | claim_type | 観測対象 | ユーザー可視 | locale_sensitive |
  |---|---|---|---|
  | message / validation_rule（エラー文言側） | UI文言・validatorメッセージ | 可視 | **1**（yaml対がja/enで別値） |
  | display_field | 画面表示値のうち翻訳対象（ラベル・列名・帳票文言・日付/通貨書式） | 可視 | **1** |
  | display_field | 画面表示値のうち非翻訳データ（ID・数値・コード値そのもの） | 可視 | **0**（理由コード `data-passthrough`） |
  | http_status / db_effect / status_transition / calculation | HTTP・DB列・状態値・計算結果 | 不可視 | **0**（理由コード `non-ui-observable`） |
  | auth_rule | 到達可否・リダイレクト先 | 可視（URL） | **0**（`non-translated`）。ただし拒否時の**表示文言**を観測するassertionは別claimで**1** |
  | external_contract | 電文・API入出力 | 不可視 | **0**（`contract-fixed`）。ただし言語コードが入力パラメータのAPI（a02-01のlang等）は**1**（`lang-as-input`） |
  | seed_equivalence | 入力→出力の恒等写像 | — | 対象fieldが翻訳対象なら1・それ以外0 |

  - **default規則**: 決定表のどの行にも適合しない/判定に迷うclaimは **`locale_sensitive=1` を既定**

#### 3.5.3 系譜ゲート（機械仕様・codex Blocker是正）＋O6会計

系譜の正はL2 binding（主キー `(test_id, assertion_ordinal)`）。統合具体TSVの系譜メタ列（§3.5.1）に
対し、**系譜ゲート `lineage_gate`**（M0=D7で実装・exit1）を定義する。
**検査の主式はtest_id集合ではなくassertion単位**（codex R2是正: bound親に1具体行があるだけでは
他assertionの宙吊りを通してしまう）:

1. **assertion単位の双方向差分=exit1**:
   - 順差分: `L2 bound assertion集合 {(test_id, assertion_ordinal)} − 具体行mapping集合 ＝ ∅`
     （boundなのに具体行を持たないassertionの検出。1件でもexit1）。
   - 逆差分: `具体行mapping集合 − L2 bound assertion集合 ＝ ∅`
     （L2に存在しない(test_id, ordinal)を指す具体行＝宙吊り/誤結合の検出）。
   - test_idレベルの三者会計（baseline母集合 −（bound ∪ excluded ∪ approved-TBD）＝空）は
     このassertion検査の**前段**として維持する（O6①会計）。
2. **多重度の許可検査（期待多重度）**: 同一 `(test_id, assertion_ordinal)` に複数の具体行が
   対応することは、**閉じた理由コード**（`obs:form+db`＝観測層多重／`locale:ja+en`＝ロケール多重／
   `retry:independent`＝独立観測 等の管理語彙）と、L2側に宣言した**期待多重度
   （expected_multiplicity: 理由コードから機械算出、例 locale:ja+en なら2）**が一致する場合のみ許可。
   理由コード無しの重複・宣言多重度との不一致（過小=欠落/過大=二重計上）はexit1。
3. **正規化**: 親test_id配列は `;` 区切り固定・前後空白除去・`IT-`形式検証・配列内重複禁止。
   正規化不能な値（自由記述・別形式ID）はexit1。
4. **補完行の隔離**: `補完理由コード` を持つ行は親test_id配列が空であることを検査し、
   O6・被覆のいかなる分子にも入れず別集計する（a02-01前例の「母集合外・設計書補完」を機械化）。
5. 各行の `source_md/source_line/row_sha256` により、統合TSV→md原本行への遡及を機械検証
   （§2.6.3の逆検証と同一基盤。row_sha256の定義と更新規則は§3.5.5）。
6. **M0実測**: 既存384mdに対してlineage_gate v0を走らせ、欠落・重複・補完・locale多重度の
   現状を実測レポート化する（D7の受入条件）。

#### 3.5.5 row_sha256の定義と更新規則（行位置変動への対応）

- **行の同一性キーは `(test_id, assertion_ordinal, locale, multiplicity_reason, occurrence)`**
  （codex R3是正: 旧2要素キー〔テストID＋locale〕は撤回。同一test_idの複数assertion_ordinal・観測層多重を
  区別できないため）。`occurrence` は同一 `(test_id, assertion_ordinal, locale, multiplicity_reason)`
  内の連番（1..expected_multiplicity）。**このキーでの重複は不可（exit1）**とし、
  各キー群の行数が expected_multiplicity（§3.5.3-2）と一致することを機械検査する。
  `source_line`（md内の行位置）は参考情報でありキーにしない（md編集で行番号は変わる）。
- `row_sha256` ＝ 14列を正規化（タブ結合・改行/引用符の正規形化）した行内容のsha256。
  **結果・失敗理由列を含む**ため、結果記入のたびに変わるのは仕様（＝「どの版の行を根拠に
  集計したか」の監査キー）。
- 更新規則: md編集（結果記入・オラクル是正）→ union再生成 → `source_line`・`row_sha256` を
  再計算し統合TSVを更新。同期ゲートは「mdから再計算した値と統合TSVの記載値の差分0」を検査
  （mdが常に正）。row_sha256が変わったのに変更管理記録（§2.6.5）が無い期待値系列の変化は
  exit1（結果列のみの変化は変更管理不要）。

- **O6被覆会計の分母は従来どおり baseline版母集合 `cut -f2 all_it_cases.tsv`**（§0.1でSHA固定）。
  統合具体TSVの行数は分母にしない（補完行・1ケース複数具体行があるため）。

#### 3.5.4 「具体手順はテストケースに載る」要件の充足

具体化済みの手順・実値は**テストケースそのもの（機能別14列具体TSVとその統合ビュー）に載る**。
母集合tsvが汎用文言のままなのは欠陥ではなく「設計台帳」という役割分担であり（§1.2非目的）、
実施者が見るテストケースは常に統合具体TSV（または機能別md）の側である。
