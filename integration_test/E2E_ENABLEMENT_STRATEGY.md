## 1. 目的と非目的

### 1.1 「実行可能」の定義（本戦略の到達点）

あるテストケースが**実行可能**であるとは、次の3条件を同時に満たすこと:

1. **具体オラクル**: 実施者（人またはspec）が**そのケース単体で**入力実値・照合実値を持ち、
   合否を判定できる。期待値は一次資料由来（捏造ゼロ）で、`source_class` と根拠(file:line)を持つ
   （ORACLE_STRATEGY L1/L2の定義に従う。汎用文言「標準のページ設定ブロック構成で描画」等は不合格）。
2. **再現可能な前提**: 前提状態がSEEDセットID（`e2e/seed/manifest.json` 契約）で機械再現でき、
   べき等（apply.sh 再実行で収束）・teardown可能である。
3. **判定手段の実装**: 区分に応じた判定手段（spec自動assert／キャプチャ+目視判定基準／
   API・DB検証／手動手順書）が存在し、結果が記録先（e2e_cases.md 結果列）に残る。

### 1.2 非目的（本戦略でやらないこと）

- **母集合25,549件の削減・再設計はしない**。台帳3本（all_it_cases/trace/execution_assignment）は
  凍結（ORACLE_STRATEGY §1）。実行可能化はcompanion層（oracle/・exec/・e2e/）の追加のみで行う。
- **手動301件の自動化はしない**（ユーザー指示: そのまま進める）。障害注入・機密実挙動・
  外部代行（決済/GMO等）・聖域は自動化対象外のまま手動管理する。
- **全件Pass達成は目的でない**。仕様乖離で落ちるのは検出成功（a02-01付帯表4の思想）。
  目的は「全件が合否判定できる状態」であり「全件が合格する状態」ではない。
- **業務未確定事項の勝手な確定はしない**（超売りNo.518・未確定オラクル33件等は§6で隔離管理）。

## 2. 4区分別トラック設計

4トラックは独立に進行できるが、**トラック共通の上流はオラクル具体化パイプライン（§3）**である。
どの区分も「L1/L2で具体オラクルを得る→区分別の判定手段に落とす」の順で、区分は判定手段だけが違う。

### 2.0 全区分共通の絶対規約: テストデータの外部化（spec直書き禁止）

**シードデータ・CSVインポートデータ・SEED固定値（具体オラクルの入力実値）は、
spec/pageファイル内にハードコードせず、必ず外部ファイルへ切り出して保存する。**
既存基盤が既にこの型であり、これを全4トラック共通の絶対規約に格上げする:

| データ種別 | 置き場所（唯一の正） | spec からの参照経路 |
|---|---|---|
| DB前提状態（SEED） | `e2e/seed/sets/<module>/SEED-*.sql`（＋`.down.sql` 撤去対） | `manifest.json` の `envVars` 契約 → `seed-env.sh` → `process.env`（`config/*.config.ts` 経由） |
| CSV取込などファイル入力 | `e2e/fixtures/csv/`（揮発物は `gen-volatile.sh` 生成・gitignore） | fixture パス参照（パス自体も config/env で解決） |
| SEED固定値（等値照合の期待実値） | e2e_cases.md 付帯表3-1（人間可読の契約表）＋ `manifest.json`（機械可読の正） | シードID→環境変数契約。specは env/config 経由でのみ値を得る |
| 境界値入力（max/max+1等） | SEEDに置かず決定的生成関数（ORACLE_STRATEGY §3。Nの根拠はL1） | ヘルパー関数（`boundary(max=N)`）＋NはL1オラクルID参照 |

- **manifest.json が唯一の正**。同じ値が spec と manifest に二重に存在する状態を作らない
  （既存specの `VALID_TN` 等のリテラル定数直書きは、L1整備時に env/config 参照へ移行する）。
- 要件は「外部化・単一の正(manifest)・べき等(apply収束)・.down撤去・監査遡及
  （値→シードID→manifest→根拠file:line）」の5点セット。**全トラックの成果物チェックリスト**（§7）に含める。
- 機械ゲート化: spec生成/レビュー時に「アサート期待値・入力値のリテラル直書き」を検査する
  lintを設ける（§3.2の「spec直書き遮断」ゲートと同一。例外は根拠コメント付きの仕様定数のみ）。

### 2.1 トラックA: Playwright（12,762件）— 既存パイプラインで全自動

- **入力**: L1/L2確定済みオラクル＋既存 `integration_test/e2e/<機能>_e2e_cases.md`（無い機能は新規）。
- **処理**: 成熟済みパイプラインをそのまま使う:
  `e2e_cases.md`（E2E自動化区分＋具体オラクル＋元ITケースID紐付け）→ `e2e/spec/**/<機能>.spec.ts` ＋
  `e2e/pages/**/<機能>.page.ts` → SEED適用 → 実行。
  実行手順（固定）: `e2e/seed/lib/apply.sh` → `eval "$(e2e/seed/lib/seed-env.sh)"` →
  `cd e2e && npx playwright test <path>`。前提: web `localhost:8080`(admin/password)・
  PostgreSQL `:15432`・mailcatcher `:1025`。
- **既存specの扱い**: 395本の大半は未実行雛形（test.fixme/skip）。「specがある＝実行可能」ではない。
  fixme/skipの解消条件は必ず理由別に分類する（(a)シード未整備→SEED追加で解禁、
  (b)オラクル汎用文言→L1具体化待ち、(c)破壊的更新→専用SEED+teardown待ち、(d)本来は他区分→区分整合の確認）。
- **成果物**: fixme/skipが解消されたspec＋実行結果（e2e_cases.md 結果列 〇/×＋失敗理由）。
- **検証**: spec内アサートの期待値がL1のオラクルIDへ遡れること（実装現挙動の書き写し禁止＝
  オラクル独立性。m05_13 spec の様式: 期待文言は messages.ja.yaml/validators.ja.yaml 由来をコメントで根拠明記）。
- **画面項目の網羅検証**: 画面を持つ機能は§2.5の「項目×制約種別」個別アサーション方針を必須で適用する
  （任意/必須・最大文字数・メッセージを項目ごとに1アサーションずつ）。

### 2.2 トラックB: Playwright+手動確認（7,114件）— Playwright操作＋Chrome in Claudeキャプチャで目視判定を担保

この区分の定義は「自動操作はできるが**判定の一部が目視必須**（帳票見た目/PDF/印刷/CSS数値/
外部連携の実結果）」。ユーザー指示により **Chrome in Claude**（Claudeによるブラウザ実操作＋
スクリーンショット取得）を判定担保の手段として設計する。

**設計原則: キャプチャは証拠であり、オラクルではない。** 目視判定にも一次資料由来の
判定基準（何が写っていれば合格か）を必ず先に文書化する。基準なきキャプチャは判定不能＝実行可能でない。

#### 運用フロー（1機能単位）

1. **判定点の分解**: 各ケースを「自動判定可能な部分」と「目視必須の部分」に分解し、
   e2e_cases.md に**付帯表6「目視判定点表」**を新設する。列:
   `判定点ID（VP-<機能>-<連番>） / 対象ケースID / キャプチャ対象（画面・帳票・状態） /
   キャプチャ手順（URL・操作・タイミング） / 目視判定基準（一次資料由来・source_class・根拠file:line） /
   判定不能条件（何が写らなければ再取得か）`。
   判定基準の例: 「納品書PDFにExcel帳票設計<根拠>記載の8項目（宛名・受注番号…）が配置されている」。
   基準が一次資料に無い場合は**TBDとして未確定オラクル台帳へ**（捏造して基準を作らない）。
2. **自動部分の先行実行**: 操作・到達・データ整合など機械判定できる部分は通常specで先に自動実行する
   （トラックAと同じ）。目視部分だけを残す。
3. **Chrome in Claudeキャプチャセッション**: シード適用済み環境（localhost:8080）に対し、
   Chrome in Claude で付帯表6のキャプチャ手順どおりに操作し、判定点ごとにスクリーンショットを取得する。
   - 保存先: `e2e/reports/captures/<機能>/<テストID>/<判定点ID>_<取得日時>.png`（命名固定・追記式）。
   - 1セッション=1機能を原則とし、セッション冒頭でSEEDセットIDと適用結果を記録する
     （どのデータ状態のキャプチャかを紐付ける＝再現性）。
   - PDF/帳票は当該ファイルもダウンロード保存する（画面キャプチャだけに頼らない）。
4. **判定と記録**: キャプチャを付帯表6の判定基準と突合して合否判定し、e2e_cases.md の
   結果列（〇/×）・失敗理由列に記録する。判定記録には**必ず判定点IDとキャプチャファイルパスを残す**
   （後日の監査・codexレビューで証拠へ遡れる）。判定基準に写っていない・判定不能なら「再取得」
   であり〇にしない（standard-e2e-execution-todo.md の運用ルール「fixme/skipを〇にしない」と同思想）。
5. **判定の検証**: 判定結果のサンプル（機能ごとに最低3件＋全×件）をcodex敵対レビューにかけ、
   「基準に無いものを合格にした／基準を実装現挙動に寄せた」逸脱を検査する。

#### 区分降格（Playwright+手動確認→Playwright）の扱い

ORACLE_STRATEGY §3のとおり、この区分の主因が「期待値がGUIに出ない＝DB確認要」だったケースは、
`e2e/helpers/db.ts`（DBアサーション・未実装）の新設で**Playwright単独へ降格できる可能性がある**。
ただしcodex較正済みの条件（★反映事項）に従い、降格は「DBアサート成功」だけでは許可せず、
**観測層・実環境依存・隔離・teardown・実走成功**を満たした場合のみ。降格候補の実測はM1で行い、
**7,114件の何割が真に目視必須か（＝Chrome in Claudeキャプチャの実対象数）をM1で確定**する。
それまで本トラックの規模見積りを確定値にしない。

- **成果物**: 付帯表6（目視判定点表）／キャプチャ資産（captures/配下）／判定済み結果列／
  降格判定リスト（db.ts昇格可否）。
- **注意**: 本区分はP1が6,532件（91.8%）に偏る。優先度上は最重要トラックだが、
  キャプチャ判定は人手律速のため、§4のフェーズで「自動部分の先行実行→目視部分の後追い」を徹底する。

### 2.4 トラックD: 手動（301件）— 自動化せず「そのまま進める」

ユーザー指示どおり既存方針を踏襲。自動化しない。実行可能化の作業は次の2点のみ:

1. **手動手順書化**: 各ケースの前提SEED・操作手順・具体オラクル（L1由来）・判定基準を
   e2e_cases.md（または機能に手動しか無い場合は専用手順書）へ具体化する。
   汎用文言のままでは手動でも判定できないため、**オラクル具体化の対象からは除外しない**
   （L2で excluded にしない＝ORACLE_M0_PLAN §2「手動301はexcludedにしない」を踏襲）。
2. **実施管理**: 14列TSVの実施管理欄（実施者・実施日・結果・失敗理由）で管理。
   障害注入・決済実挙動など環境準備が必要なものは前提条件欄に準備手順を明記。

分布は3件/機能程度で全機能に薄く広がる（最多でも機能あたり3件）ため、専任フェーズは設けず、
各機能のオラクル具体化時に同梱で手順書化する。

### 2.5 横断サブトラック: 画面項目の網羅検証（任意/必須・最大文字数・メッセージ）

ユーザー要件により、画面を持つ機能（トラックA、およびトラックBの自動部分）では、
**各画面項目について (a)任意/必須 (b)最大文字数 (c)バリデーションメッセージ を、
項目ごとに個別のPlaywrightアサーションで検証する**。ケース粒度は「項目×制約種別」へ細分化される。

#### オラクル決定の規約（プロジェクト既存方針・厳守）

1. **項目定義の正典はee（EC-CUBE Enterprise）**。現行pf基準で突合すると偽陽性を量産する
   （監査実績: ee固有値194 対 pf固有値1）。任意/必須・最大長の期待値は
   **三値比較（設計書HTML／pf実装／ee実装）**で決定し、設計書とeeが一致する値を第一候補、
   食い違いは `oracle_conflicts.tsv`（ORACLE_M0_PLAN §6-2）へ全件記録して裁定する。
   ee実装値をそのまま期待値にしない（source_class規約: ee-enterprise由来は標準28機能のみ
   `standard-src` として可・他は設計書正本へ遡って確定＝オラクル独立性）。
2. **最大文字数の意味論差（pf=MySQL/ee=PostgreSQL）**: pfはバイト長・eeは文字長で境界が変わる。
   よって最大文字数のL1オラクルは **unit（文字/バイト）必須**（L1スキーマの`unit`列）で、テストは:
   - **Form層**: max受理／max+1拒否（拒否時メッセージは(c)と同一アサーションに統合可）
   - **DB層**: `db.ts` で保存後の列値・列定義を検証（Form層通過がDB制約超過で落ちる系の検出）
   - **境界値3種**: max（半角）／max+1／**マルチバイト混在でmax相当**（文字長とバイト長の差が出る値）
   の両層×3値を項目ごとにケース化する。境界値入力は§2.0のとおり決定的生成関数で作る（SEEDに置かない）。
3. **「制約が無い」は断定しない**: 委譲型（Form制約がEntity/DBへ委譲されている等）では
   「制約なし」は証明不能。否定形オラクル（「エラーにならないこと」の無制限版）は生成禁止で、
   設計書が沈黙する項目の上限はTBD（未確定オラクル台帳へ）。
4. **メッセージの一次資料は `messages.ja.yaml`/`validators.ja.yaml`**。実装Twig/Controllerの
   現文言を期待値に流用しない。プレースホルダ（`%name%`等）は原文保持し、実行時値の解決根拠をL1に持つ。

#### 既存資産への接続（実測確認済み・いずれも「発見/照合補助」であり値根拠ではない）

- **`item_definition_audit/item_definition_audit_scoped.tsv`（683項目）**: 列に
  設計書HTML値（必須○/最大文字数）＋ `pf_Form上限/ee_Form上限`（出典file:line付き）＋
  `pf_必須(NotBlank)/ee_必須(NotBlank)` ＋ `pf_DB列長/ee_DB列長` ＋ 判定列
  （例 `B_リニューアル変更(HTML=ee≠pf)`）を持つ。**三値比較の突合結果が既に683項目分ある**ため、
  §2.5の第一波はこの683項目を核にL1化する（ケース設計をゼロから始めない）。
  ただしcodex較正①のとおり監査由来ラベルのまま値根拠にせず、採る値は元の設計書（判定列が
  設計書一致を示す場合）または三値裁定を経て source_class を確定する。
  全量版 `item_definition_audit.tsv`（4,655行）は683のスコープ外項目の発見リストとして使う。
- **`message_inventory/MESSAGE_LIST.tsv`（1,180行）**: 列に メッセージID／機能ID／種別／
  **表示位置／画面上の文言／表示条件／後続処理／根拠(file:line＝yaml行含む)** を持つ。
  「項目×メッセージ」紐付けの足場に**使える**: 表示条件列（例「削除指定した規格が使用中で…」）と
  機能ID列で、どの項目のどの制約違反がどのメッセージを出すかの候補結合（Phase C binding）に使い、
  期待文言そのものは根拠列のyaml行へ遡って確定する（棚卸しは発見・結合補助、値はyaml由来）。
- **DB層の列長根拠**: ee側は `ec-cube-enterprise/src/Eccube/Entity/**`（Doctrine属性）が
  スキーマ正典（e2e/seed/README.md記載）。標準機能では `standard-src` として直接根拠に可、
  それ以外は設計書DBカラム表を正としEntityは照合補助。

#### 規模とパイプラインへの影響

- 粒度が「ケース」から「項目×制約種別×層×境界値」のアサーションへ細分化されるため、
  **台帳は増やさない**方針で吸収する: 凍結台帳のtest_id（バリデーション系約2,240件）に対し
  L2の `assertion_ordinal` で多対多に項目別アサーションを束ねる（ORACLE_STRATEGY codex較正③の
  設計そのまま。1 test_id＝1画面項目群の検証に複数assertionが正規形）。
  台帳に対応行が無い項目×制約はa02-01前例の「母集合外・設計書補完」として別管理し台帳を汚さない。
- 概算規模（計画用・確定値にしない）: 683スコープ項目×（必須1＋文字数上限がある項目のみ
  Form境界3＋DB層1＋メッセージ1）で**数千アサーション規模**。DDT化（項目リストを外部データに持ち
  specはループ1本）で spec本数は増やさない。**実測係数（項目あたりアサーション数・工数）はE1の
  m11-02（バリ重量級パイロット）で取る**。M2（バリデーション波・E3）の主内容がこのサブトラック。
- Form層エラーの観測は標準28機能の実行実績から2系統ある: `.text-danger` 型（サーバ側バリ）と
  **HTML5 required/maxlength による送信前ブロック**（m01-01の010/011で実証）。項目ごとに
  どちらの層で観測するかをL1のclaimに含める（観測層の取り違えが既知の失敗パターン）。

### 2.6 実行規律／不変条件（全トラック共通の鉄則）

#### 2.6.1 テストケースが正＝オラクル不可侵

**期待値どおりにならなくても、テストの期待値（Playwrightアサーション含む）も、ee実装（SUT）も、
絶対に変更しない。** 不一致は「不具合・仕様乖離の検出＝テストの成功」であり、
通すために期待値やSUTを直す対象ではない（a02-01付帯表4の思想を全トラックA/B/C/Dの鉄則に格上げ）。

- 検出した乖離は **何も変えずに ×（仕様乖離）として記録**し、当該機能の付帯表4
  （不具合候補/要確認）＋`BUG_CANDIDATE_REGISTER.md` 系へ登録する。
- 期待値の変更が許されるのは唯一、**L1オラクル自体の是正**（根拠の読み誤り・設計書改訂）が
  ゲート（O1-O6）とcodexレビューを通った場合のみ。specから直接期待値を書き換える経路は存在しない
  （§3.2の生成拒否ゲートで機械遮断）。
- ee実装の修正は本プロジェクトのスコープ外（不具合候補として報告するまで）。

#### 2.6.2 唯一の例外＝ハーネス修正（失敗トリアージの二分類）

失敗はすべて次の二分類でトリアージしてから記録する（全トラックの運用フローに組み込む）:

| 分類 | 定義 | 対応 |
|---|---|---|
| **(i) 実挙動の乖離を検出** | ハーネスは正しく観測しており、SUTの実挙動が期待値（L1オラクル）と異なる | **何も変えず** ×＋失敗理由「仕様乖離」で記録→付帯表4/不具合候補登録。再実行不要 |
| **(ii) ハーネス不良** | セレクタ誤り・待機不足・遷移ハンドリング等、**Playwright実装（テストハーネス）自体のバグ**で正しく観測できていない | **Playwrightコード（page/spec の操作・観測ロジック）のみ修正**して再実行。期待値・オラクルID参照は変更禁止 |

- 切り分けの証拠: Playwright trace/screenshot・必要なら手動再現。判断根拠を失敗理由列に残す
  （例「030: `#loading` 非表示待ちタイムアウト＝ハーネス起因か実挙動か trace で確認済み」）。
- ハーネス修正のdiffは「操作・観測ロジックのみ」であることをレビューで確認する
  （期待値リテラルの変更が混ざったらリジェクト。§2.0の外部化lintが期待値直書き自体を防ぐ）。
- **失敗理由の記録語彙**は `e2e/reports/standard-e2e-execution-todo.md` の既存運用に倣い統一する:
  `セレクタ不一致`／`タイムアウト`／`HTTPステータス不一致`／`Web Debug Toolbar遮蔽`／`シード不足`／
  `外部サービス未接続`／`仕様乖離（実挙動が期待と異なる）`／`環境起因（サンドボックス等）`。
  うち (ii)ハーネス系＝セレクタ不一致・タイムアウト（観測待機起因）・Toolbar遮蔽、
  (i)検出系＝仕様乖離・HTTPステータス不一致（実挙動）、
  前提系＝シード不足・外部未接続・環境起因（×でなく「未実施(理由コード)」として記録）。

#### 2.6.3 結果記録の二重化（md⇔TSVの同期規約)

テストは何度も回すため、合否の記録は次の2層で持ち、機械同期する:

1. **正（single source of truth）＝各 `integration_test/e2e/<機能>_e2e_cases.md` 内の
   14列ケース表（実施者・実施日・結果・失敗理由の実施管理欄）**。実行のたびにここへ追記更新する
   （結果 `〇`/`×`＋失敗理由は上記語彙。fixme/skipは〇にしない＝既存運用ルール踏襲）。
2. **導出＝統合具体TSV（§3.5）／レポート**: 一枚の実行用テストケースTSV
   `all_e2e_cases_concrete.tsv` と `e2e/reports/*-execution-todo.md`（実行履歴・コマンドライン・
   passed/failed内訳）は、mdのケース表から**機械union/抽出で生成**する（手で二重入力しない）。
   統合具体TSVは導出ビューであり**手編集しない**（結果もmd側に書き、再生成で反映する）。
   同期検証: md→統合具体TSV を再生成し差分0を確認するゲートを実行後に必ず回す
   （`format_tsv --check` 通過を含む）。mdとTSVが食い違ったら**mdが正**、TSVを再生成する。
3. 複数回実行の履歴は reports 側（実行履歴表）に時系列で残し、mdの結果列は**最新実行の判定**を持つ
   （過去×→今回〇の場合も履歴はreportsに残るため監査遡及可能）。

#### 2.6.4 冪等性の絶対担保（何度回しても同一前提・同一結果）

- **前提の冪等**: SEEDは既存規約（固定ID＋`ON CONFLICT DO UPDATE`＋`seed_resync`。apply.sh 2回で
  収束＝検証済み）を全モジュール拡張でも厳守。撤去は `.down.sql`（子→親・帯ID＋マーカー）。
- **実行中の汚染防止**: 破壊的更新系（保存・削除・ステータス変更・CSV取込）は
  **使い捨て専用SEEDに限定**し、spec の afterEach（またはワークブック単位のteardown/reseed）で
  初期値へ復元する。一覧の「先頭受注」等、共有データへの書込みは禁止
  （m05-13 specに実在する既知の穴。E2で是正し、以後の量産では生成時点で禁止）。
  各機能の対象データと復元方法は **e2e_cases.md 付帯表3（シードデータ要件: 独立性・べき等・後始末列）**
  に定義し、SEED実装はその契約に従う（付帯表3→manifest.json→sets/*.sql の順で具体化）。
- **結果の冪等の検証**: 同一シード状態からの**2連続実行で同一判定**になることを機能完了の条件とする
  （不一致＝flaky。原因をトリアージ二分類にかけ、ハーネス起因なら修正・データ起因ならSEED/復元の穴として是正）。
- 非べき等操作（`eccube:install` 等の初回構築）はSEEDと明確に分離し、フレッシュDB再構築手順として
  別文書化する（§5-1）。

### 3.5 テストケースTSVの二層構造と生成の向き（母集合＝設計台帳／統合具体TSV＝実行ビュー）

#### 3.5.1 成果物「統合具体TSV」の新設

- **生成先**: `integration_test/e2e/all_e2e_cases_concrete.tsv`（機械生成物・手編集禁止。
  先頭コメント行に生成元・生成日時・union元ファイル数を記録）。
- **列定義**: a02-01の実列に合わせた**14列**
  （機能名／テストID／I/FID／テスト観点／優先度／テスト項目名／前提条件／
  入力データ・リクエスト内容／操作手順・実行方法／期待結果・レスポンス／
  実施者／実施日／結果／失敗理由）＋**派生列15列目 `元ITケースID`**
  （各mdの付帯表1から機械結合。複数対応は`;`区切り・母集合外補完行は`(補完)`マーク）。
- **union元**: 全 `integration_test/e2e/<機能>_e2e_cases.md` 内の14列具体TSVブロック（現在384ファイル）。
- **役割**: これが実行・入力実値/照合実値の確認・結果記録の
  **「テストケースTSV（実行の正本の集約ビュー）」**。実施者は原則この一枚（または機能別md）だけで
  合否判定に必要な全情報（具体手順・SEED固定値参照・具体期待値）を得る。
- 実行方法区分・聖域・優先度別の集計は、`元ITケースID` で母集合／`execution_assignment.tsv` と
  joinして付す（統合具体TSVに属性を二重保持しない）。

#### 3.5.2 生成の向きは一方向（母集合へ書き戻さない）

```
母集合 all_it_cases.tsv（凍結） → trace台帳＋オラクル具体化(L1/L2＋SEED固定値)
  → 機能別 e2e_cases.md 14列具体TSV → 統合具体TSV（派生・再生成対象）
```

- **母集合 `all_it_cases.tsv` へは書き戻さない**。母集合は「どの機能にどの観点を何件」の
  設計台帳であり、物理整合（trace一意・差分0）検証済みの凍結資産。
- **注意（混同禁止）**: `generate_it_cases.py` の再実行は母集合を**汎用文言で上書き再生成する
  だけ**であり、具体手順・具体期待値は入らない（生成器は観点×HTML表セルの粗い組合せしか
  出力しない＝MILESTONE_STATUS診断済みの構造的制約）。「母集合の再生成」と
  「統合具体TSVの再生成（mdからのunion）」は別物であり、実行可能性を更新するのは後者のみ。
- **凍結解除（母集合への具体値書き戻し）は不採用**。理由: trace物理整合・監査再現性を
  作り直すことになる／生成器がオラクル（下流成果物）に依存する循環が生じる。二層分離が正。

#### 3.5.3 系譜連結とO6会計

- 全具体行は原則、母集合のtest_idに `元ITケースID` で連結される（母集合を書き換えずに
  トレーサビリティを保持。機械joinの正はL2 binding＝test_id×assertion_ordinal）。
- a02-01前例の「母集合外・設計書補完」行は例外として明示マークし別管理（母集合集計に算入しない）。
- **O6被覆会計の分母は従来どおり母集合 `cut -f2 all_it_cases.tsv`**。統合具体TSVの行数は
  分母にしない（補完行・1ケース複数具体行があるため）。

#### 3.5.4 「具体手順はテストケースに載る」要件の充足

具体化済みの手順・実値は**テストケースそのもの（機能別14列具体TSVとその統合ビュー）に載る**。
母集合tsvが汎用文言のままなのは欠陥ではなく「設計台帳」という役割分担であり（§1.2非目的）、
実施者が見るテストケースは常に統合具体TSV（または機能別md）の側である。
