## §1. 全ケース共通前提
- **入口/認証**: 認証済み管理者が管理画面で利用（正本 L360「管理画面のログイン要件に従う／コントローラ単位の追加ロール注釈は無い」）。対象はブラウザ経由の管理画面に限定（L308）。ルートは3本（L316,L393）:
  - `GET,POST /{admin_route}/standby/{id}/edit`（`admin_shipping_standby_edit`・詳細表示。POSTでも表示のみで保存しない＝L325）
  - `POST /{admin_route}/standby/{id}/update`（`admin_shipping_standby_update`・備考保存）
  - `DELETE /{admin_route}/standby/{id}/delete`（`admin_shipping_standby_delete`・リスト削除）
- **CSRF**: 更新フォームは標準トークン、DELETE は共通のトークン名とヘッダ／パラメタ検証（L357）。DELETE の CSRF 無効は HTTP 403（アクセス拒否）（L329,L368）。削除リンクはフレームワークのメソッド偽装で DELETE となるマークアップ（L319）。
- **参照/更新の別**: 詳細表示（GET）は読み取りのみ。更新・削除はサービス層でトランザクション開始・コミット、例外時ロールバックし例外再送出（コントローラでは主に捕捉しない）（L327,L329,L368,L388）。楽観ロック Version 列は持たない（L342,L388）。
- **404 前提**: 表示・更新・削除いずれも対象 `{id}` が無ければ HTTP 404（L323,L327,L329,L339,L368）。詳細表示は受注・受注明細まで内部結合で読むため、受注が無い/明細が無いリストは結合でヒットせず 404 になりうる（L323,L335,L339）。
- **オラクル独立性**: 期待は詳細設計HTML由来で実装から独立。実装との差は付帯表4で乖離＝バグ候補として扱う。

## §7. gen(90) からの是正（オラクル差し替え）
- gen の期待verbatimは詳細設計HTMLの総称文（「詳細を表示する（GET admin_shipping_standby_edit）」等）や表全体のベタ貼りで、具体オラクルになっていなかった。→ 全行を「id別・アクション別（GET表示/POST更新/DELETE削除）」の具体挙動へ差し替え、前提SEEDをアクション別に分離（ゲート規則3）。
- gen が「検索条件」を24行量産していたが、本機能に検索フォームは無い。ただし「検索を扱わない」明示的否定文が正本に無いため OUT にはせず §5 で `要判定`（偽OUT回避＝ゲート規則2）。
- gen の「必須バリデーション」等を、実在する入力項目（備考のみ）の最大長境界 DDT（§3）へ畳み込み。文字種/数値/相関は入力項目不在＋否定文なしで `要判定`。
- CSRF を DELETE=403（L329,L368）／更新フォーム=標準トークン検証失敗→編集リダイレクト（L327,L357）に分けて実施化。
