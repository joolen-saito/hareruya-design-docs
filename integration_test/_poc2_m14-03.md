## §1. 全ケース共通前提
- **入口/認証**: 認証済み管理者（管理画面にログインし当メニューに到達できる運用者）がブラウザ経由の管理画面で利用する。対象はブラウザ経由の管理画面に限定（L308）。ルートは `m14-03_admin_card_card_bulk_delete`＝`POST /{admin_route}/card/delete`（L397）。管理画面のロール・IP 制限は共通ルールに従う（L363）。
- **送信形態**: カード検索一覧と同一 HTML フォームから送信する。フォーム既定 `action` は検索用 `POST /{admin_route}/card/search/1` であり、「一括削除」ボタンが `formaction` で当ルートへ差し替えて送信する（L318）。
- **CSRF**: 検索フォーム本体は CSRF 無効の型で生成されるが、一括削除ボタン内に `name=_token` の隠し項目を置き、コア既定のトークン名で検証する（L322）。無効なら HTTP 403（L326 手順2・L334 順序1・L371）。成功時は同プロバイダでトークンを更新する（L326 手順2）。
- **入力**: POST ボディは `cardIds[]` と `_token` のみを参照する（L350）。カード ID の選択状態はセッションに持たず POST のみで渡す（L385）。
- **更新系**: 本機能は削除（更新系）であり、副作用は `mtb_card` 周辺の物理削除（ORM）、`dtb_product_sub` の NULL 更新、支店通知、ログ、支店エラー表の追記（L350）。確定は persist/flush による即時反映で承認ワークフローを介さない（L356）。
- **DB関連の読み替え**: 削除対象の `mtb_card`・`mtb_card_detail`・`dtb_deck_card` は現行と移行先で同一テーブル名。商品との紐付け先と削除可否判定に用いる商品の削除方式のみ L313 の表に従い読み替える（L312,L313）。
- **オラクル独立性**: 期待は詳細設計HTML（Excel該当なし）由来で実装から独立。実装との差は付帯表4で乖離＝バグ候補として扱う。

## §7. gen(74) からの是正（オラクル差し替え）
- gen の期待は正本の**表まるごとverbatim**（例 RG-m14-03-015〜020 が同一の画面遷移表を6行反復）と総称文（「一括削除を実行する（POST …）」を16行反復＝RG-042〜057）で、**期待が具体オラクルになっていない**。→ 全行を L305〜L397 の具体挙動（判定順序6段・403/404/302・フラッシュキー・支店通知・NULL切り離し）へ差し替えた。
- gen が CSRF を `DELEG-STATIC`（RG-001）、未認証を `EXEC-UI`（RG-002）としつつ**両者に同一の権限表 L363 を根拠**に当てていたのは誤配線。→ CSRF は L322/L326手順2/L334順序1 に固有の具体挙動があるため `EXEC`（RG-002,003）へ、未認証は L363「本書では詳細を確定しない」により `DELEG-STATIC`（RG-047）へ是正。
- gen が「数値バリデーション」を `EXEC-UI:DDT` で8行に増幅（RG-026〜033・全行が同一の入力項目表 L339 を引用）していたが、正本の入力は `cardIds` と `_token` の2項目のみ。→ 固定オラクルのある `cardIds` の空/不在/型不正/負値/ゼロのみ DDT 実施（DV-01〜07）とし、トークン長境界は要実機確認（件数外）へ縮退。
- gen が「登録内容」を P1 で12行（RG-063〜074）に増幅していたが、本機能は削除であり登録は行わない。→ 副作用（L350）・DBカラム（L354）・DB操作（L356,357）に基づく実削除・NULL切り離し・再帰削除（RG-015〜019,044）へ置換。
