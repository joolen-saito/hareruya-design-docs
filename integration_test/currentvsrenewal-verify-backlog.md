# 現行/移行先 記述に関する所見（重要な訂正）

## 結論（m03-11 等の深掛け検証から）

当初、「現行(pf-eccube3)設計書が ece(移行先) の Controller/挙動を引用しているのは取り違え（混入）」と疑い、64件をバックログ化した。しかし代表機能 **m03-11 商品カテゴリ登録/編集** を深掛けした結果、**多くは混入ではなく、reverse-design ルール上の意図的な記述**と判明した。

- reverse-design SKILL 1a/1b: カスタマイズ/現行踏襲は「挙動は現行リポを正」だが、**画面・機能の追加仕様は基本設計（＝刷新後＝ece相当）を根拠**とし、**DBは ece 正典(1c)**。現行と移行先の差は「リニューアル移行時の扱い」へ集約する。
- m03-11 は既に「リニューアル移行時の扱い」で 補助表分離 / `rank`↔`sort_no` / 階層キー / 追加列(画像・html・search_parameters) を**現行↔移行先で整理済み**。本文修正は不要だった。

→ すなわち「ece挙動を記述している」こと自体は誤りではない。**64件のバックログは error ではなく、せいぜい「現行/移行後の差分整理が十分かの任意レビュー」**である。

## 本当に直すべきもの（限定的）

深掛けで確度高く是正したのは次の狭い類型のみ:
1. **処理機構の誤記**: 現行が使わない仕組みを現行挙動として断定（例 m05-11 の PurchaseFlow/prepare-commit）。横断スキャン済み＝該当は m05-11 のみ（修正済み）。
2. **事実誤り**: フラッシュキー誤記（m05-14）、挙動の事実誤り（m05-26 出荷日空スキップ）。
3. **現行/移行後の差分注記の不足**: 現行に無い刷新機能を移行表に補う（例 m05-06 確認画面）。

## 申し送り（任意レビュー対象、errorではない）

64件の ece-Controller 引用 doc は、必要に応じて「リニューアル移行時の扱い」の差分整理が十分かを確認する。優先する場合は Write/編集系から。ただし m03-11 のように既に整理済みのものが多く、**機械的な本文書き換えは行わない**（基本設計ベースの意図を損なうため）。
