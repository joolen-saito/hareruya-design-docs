## §1. 全ケース共通前提
- **入口**: デッキビルダーアプリからの `POST /user/login`（L237）。応答形式はJSON、呼び出し元はデッキビルダーアプリ（L238）。ブラウザ向け画面を持たないため、入力＝リクエストボディのフォーム値、期待＝処理結果・副作用・レスポンスで検証する（L219）。
- **本APIの認証**: トークン取得の入口であり `jwt-token` ヘッダを要求しない。未認証のクライアントが呼び出せる（L241）。認証ヘッダは不要で、フォームはCSRF検証を行わず、定義外の追加項目を許容する（L254）。
- **判定順序**: リクエストボディから `id`（メールアドレス）と `password` を受け取り→フォーム検証（失敗＝HTTP 400）→メールアドレス・有効状態（本会員）・未削除で会員を引く（該当なし＝HTTP 401）→ソルトでハッシュ化し保存パスワードと突合（不一致＝HTTP 401）→一致でアクセストークン発行→Cookie設定・セッション開始→200のJSON（L246）。検証は会員照合の前に行う（L274）。
- **失敗応答の形**: 400／401 とも `{code, message}`（L259）。400の message は `Required fields have not been filled in. Or the input format is incorrect`、401の message は `ID or password does not match`（L259,L293）。500 は deck-apiの共通例外処理に委ね、本API独自のフォールバック文言は設けない（L259,L293）。
- **秘匿**: トークン原値・署名シークレット・パスワードは本書に記載しない（L242）。ログにはパスワード・アクセストークンの原値・署名シークレット（`auth_magic`）・Cookie値/セッションIDの完全値を出してはならない（L297）。よって検証は「値の存在・形式・突合結果」で行い、原値そのものを記録しない。
- **オラクル独立性**: 期待はオラクル（Excel該当なしのため詳細設計HTML）由来で実装から独立。実装との差は付帯表4で乖離＝バグ候補として扱い、正本に無い挙動は「要実機確認」とする。
