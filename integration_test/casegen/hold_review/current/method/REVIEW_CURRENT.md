# 敵対レビュー依頼: 保留論点の現行ソース調査（__BATCHES__）

これは**レビューの依頼**である。調査をやり直すのではなく、誤りを指摘すること。

結合テストで保留のまま残った論点について、別の著者が現行ソースに答えがあるかを調べた。
その結果に誤りが無いかを、**現行ソースを実際に読んで**確かめてほしい。

| もの | 場所 |
| --- | --- |
| 著者に渡した調査規約（**判定基準**） | `S/current/CURRENT_RULES.md` |
| 調べた論点 | `S/current/batch/<cNN>.tsv` |
| 著者の調査結果 | `S/current/out/<cNN>.tsv` |

対象バッチ: __BATCHES__

**ec-cube-enterprise は現行ソースではない（構築中の新実装）。** そこを根拠にした答えは誤り。

機械検査（`S/current/gate_current.py`）で、根拠の file:line にそのコードが実在することは確認済み。そこは見なくてよい。
**見てほしいのは、そのコードから本当にその答えが出るか**である。

## 重点（上ほど重い）

1. **答えの誤り（「現行で確定」「現行で一部」）。** 引いたコードが別の画面・別の条件・別の分岐のもので、論点の答えになっていない。
   Controller だけ見て Service・Repository・テンプレート・設定値の上書きを見落としている。値が設定ファイルや DB で上書きされる。
   答えの具体値（上限・文言・遷移先・ステータス）がコードと違う
2. **「現行で確定」の過大評価。** 論点の未定義事項の一部しか答えていないのに「確定」にしている
3. **「使えるか」の誤り。** 刷新の指示（`S/src/<機能ID>.txt` のカスタマイズ説明・機能仕様）がその点を変えているのに「可」にしている。
   現行踏襲の機能なのに「参考のみ」にしている。分類が矛盾の論点を「可」にしている
4. **「現行に無し」の見落とし。** 現行ソースに答えがあるのに無しとしている。指摘するときは file:line とコードを逐語で示す
5. **参照先の誤り。** ec-cube-enterprise や、リポジトリ内の設計書 md を現行として使っている
6. **front-application（MTGバイヤー）の版ズレ。** このアプリは刷新後の新APIに合わせた改修が入り始めている（APIパスが `api/v1/...` で現行 pf-api の `api/...` と違う、直近コミットで設計書のエンドポイント名に合わせた、など）。
   刷新後に向けて書き換わった箇所を「現行」の答えにしていないか。該当すれば `git log`・`git blame` で時期を示して指摘する

## 指摘しないもの

- 答えの言い回し
- 機械検査で見ている file:line の実在
- 現行の実装の良し悪し（バグだと思っても、現行の挙動として正しく書かれていれば指摘しない）

## 出力形式

指摘が1件も無ければ `NONE` の1語だけを出力する。指摘があれば、1件ごとに次の形で書く。

```
### <論点ID>
主張: <著者の判定・答え・使えるかのどれが、どうなっているか>
実際: <現行ソースの記述（逐語）と repo/path:line>
判定: 答えの誤り / 確定の過大評価 / 使えるかの誤り / 無しの見落とし / 参照先の誤り
修正案: <どう直すか>
```
