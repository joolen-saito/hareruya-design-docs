設計書に書かれていない値・挙動が、現行の実装で決まっていることが多い。それを file:line で拾う。

## 論点ごとの参照先

`S/current/batch/cNN.tsv` の各行に、帰属台帳（`functions/source-attribution-all.tsv`）の `区分` と `参照元` を付けてある。

- 参照元のリポジトリを主に調べる
- 外部連携の論点は、相手側のリポジトリも調べる（MTGバイヤー→`front-application`、デッキビルダーアプリ→`deck-builder`、記事サイト→`pf-article`）
- 区分が「新規実装」の機能は現行ソースを持たない。相手側のリポジトリで答えが出る外部連携の論点だけ調べ、それ以外は `現行に無し（新規実装）` とする

## 調べ方

1. 論点の文と、`S/out/hold_rejudge.tsv` の該当ケース（`説明`）、元の保留理由（`S/batch/*.tsv` の `期待結果`）を読んで、何が未定義かをつかむ
2. 参照先のリポジトリで、画面名・URL・ルート名・翻訳の日本語文言・テーブル名・メッセージ文言などで検索し、該当の処理を**末端まで**読む（Controller で止めず、Service・Repository・テンプレート・設定値まで）
3. **検索が0件でも、1回で「無い」と結論しない。** `rg` は同じ入力でも時々0件を返す。`grep -rn` でも引き直し、語を変えて2通り以上探す
4. 答えの根拠は、実ソースの file:line と、その行のコードを**そのまま**写したもの

## 判定（1論点に1つ）

| 現行の判定 | 意味 |
| --- | --- |
| 現行で確定 | 現行ソースで、論点の未定義事項が**全部**決まっている |
| 現行で一部 | 一部だけ決まる。決まらない部分を `補足` に書く |
| 現行に無し | 探したが該当する処理・値が無い（機能自体が現行に無い場合を含む） |
| 現行に無し（新規実装） | 区分が新規実装で、相手側でも答えが出ない |

## 期待結果に使えるか（現行で確定・一部のときだけ付ける）

| 使えるか | 条件 |
| --- | --- |
| 可 | 区分が「現行踏襲」。または「カスタマイズ」で、刷新の指示がこの点を変えていない |
| 参考のみ | 刷新の指示がこの点を変えている／変える可能性がある。論点の分類が「矛盾」で、刷新の指示どうしが食い違っている（現行は判断材料にとどまり、決めるのは設計者） |
| 不可 | 現行の値が刷新の指示と明らかに食い違う（刷新を採る） |

- 「カスタマイズ」で可とするときは、刷新の指示（設計書のカスタマイズ説明・機能仕様）がその点に触れていないことを `S/src/<機能ID>.txt` で確かめ、`補足` に書く
- 分類が「異常の作り方」（テスト側）の論点は、現行でその異常がどこで・どの条件で起きるかを答えとする（例: どの例外がどの入力で出るか）。使えるかは「参考のみ」

## 出力

`S/current/out/cNN.tsv`（ヘッダーあり、UTF-8、LF）。入力の論点を**全件・入力と同じ順**で1行ずつ。

```
論点ID	機能ID	現行の判定	現行での答え	根拠	使えるか	補足
```

- `現行での答え`: 未定義事項への答えを具体値・具体挙動で1〜3文（例: 「上限は10MB（10485760バイト）。超過時は『ファイルサイズが大きすぎます』を表示し一覧に戻る」）。現行に無しなら `—`
- `根拠`: `<リポジトリ>/<パス>:<行> 「<その行のコード>」` を ` || ` で区切って並べる。コードはその行の一部を逐語で（前後の空白は落としてよい）。現行に無しなら、探した語と場所を書く（例: `探索: pf-eccube3 で "csv_upload" "ファイルサイズ" を rg/grep、0件`）
- `使えるか`: 可／参考のみ／不可。現行に無しなら `—`
- `補足`: 判断の理由、一部しか決まらない部分、刷新の指示との関係。セル内にタブ・改行を入れない

書き終えたら `python3 S/current/gate_current.py S cNN` を通すこと（根拠の file:line に、書いたコードが実在するかを機械検査する）。
