## 判定の基準

| 使えるか | 条件 |
| --- | --- |
| 可 | 区分が現行踏襲。またはカスタマイズで、刷新の指示がこの点を変えていない（設計書で確かめた旨を補足に記載） |
| 参考のみ | 刷新の指示がこの点を変える／変えうる。分類が「矛盾」または「異常の作り方」。現行の挙動が明らかな実装不備 |
| 不可 | 現行の値が刷新の指示と明らかに食い違う（刷新を採る） |

「現行で確定」にしないもの（「現行で一部」に下げたもの）:

- 値が、リポジトリに無い実環境の設定ファイル（`app/config/eccube/*.yml`、`api.yml`、`.env.local` など）や、管理画面で変えられるDB値で上書きされうる
- 答えの中核が vendor（Symfony・Doctrine・Silex など）の既定の挙動に依る。**どのリポジトリにも vendor が同梱されていない**ため file:line で確かめられない
- 画面の文言が debug 設定に依る（エラー画面。本店ECではプラグインのハンドラがコアより先に応答する）

参照したリポジトリと版: pf-eccube3 `9cde293346`、pf-api `90719e19`、deck-api `a146a162`、deck-builder `c7b49a45`、pf-article `95c6331`、ec-cube `52cad77a`、front-application `27dffb8`（ただし根拠は2026年以前の行か、刷新前のリリース `f60bb01` の版に限った）。ec-cube-enterprise（構築中の新実装）は読んでいない。

**3巡目でも答えの誤りが39件見つかり、レビューは収束していない。** 規約の上限の3巡で閉じたので、

結合テストの実行（現行環境での確認）または設計者の確認で裏を取るのがよい。誤りの型は

## 作業中に分かったこと

- **front-application（MTGバイヤー）は刷新に向けた改修が2026年から入っている**（APIパスの新形式、jwt-token の付与など）。現行の根拠にはできない。刷新前の最終リリースは 2025-04 の `f60bb01`
- **本店ECのエラー画面はプラグインのハンドラが先に応答する**（`HareruyaEcServiceProvider.php:337-367`、優先度 -7）。404・400 の文言はコアと違う。403 は例外メッセージを画面に出さない
- **`event.yml` に同じイベントキーの重複定義がある**（`shopping_confirm`・`shopping_shipping`）。symfony/yaml 2.x の扱いでは先の定義が残るため、支店店内注文の制限ハンドラがご注文内容確認・お届け先一覧の2画面に登録されていない可能性が高い
- 設計書の前提が現行と大きく違う例: 祝日管理（M16-03）は外部APIでなくライブラリで計算、在庫リコメンドCSV（B02-07）はバッチがDB更新だけで出力は別画面、デッキ登録のレギュレーション違反は登録を拒否せずフラグを立てるだけ

## 持ち越し（方針の確認が要るもの）

1. **現行踏襲なのに現行の挙動が実装不備のもの**を「参考のみ」にした（例: Q-M16-03-03 は404を返すつもりがクラス未定義エラー、Q-M09-10-05 はタグIDでなく配列キーを使う）。規約の文面では「可」になる。現行の不具合を期待結果に写さないための判断
2. **連鎖ID を含む論点**（13件）は、連鎖IDがテスト設計側の概念で現行ソースに答えが無いため「現行で一部」にした。論点から連鎖IDを外せば「確定」に上がるものがある
3. debug 依存でエラー画面を「一部」にした行は、本番の入口が debug を有効にしないので実害は小さい。保守的に倒してある
