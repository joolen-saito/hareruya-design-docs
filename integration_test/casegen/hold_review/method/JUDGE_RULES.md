# 保留ケースの判定し直し（手順1・2）

結合テストケースのうち実行区分が「保留」のケースを、**最新のHTML設計書**で判定し直す。
あわせて、保留の理由を「決める人」と「論点」で整理する。
**答えを作る作業ではない。** 設計書に無い値・挙動を補ってはならない。

## 前提

- 保留ケースは、ケース生成時（2026-09-03〜04）に「設計書に期待結果を決めるだけの記述が無い」と判断されたもの。
  `期待結果` 列に、何が未定義かが書いてある
- 生成後の 2026-09-11 に、Excel更新を反映してHTML設計書を再生成した。記述が増えた機能がある

## 置き場所（S = このファイルのあるディレクトリ）

| もの | 場所 |
| --- | --- |
| 判定する保留ケース | `S/batch/bNN.tsv`（11列。1行1ケース） |
| 機能ごとの最新の設計書テキスト | `S/src/<機能ID>.txt`（HTML設計書の該当シートと、埋め込まれた機能設計書。ケース生成時と同じ範囲） |
| 生成後に変わった行 | `S/src/<機能ID>.diff.txt`（追加された行／消えた行） |
| ケースの出典が挙げる、その機能以外のシート | `S/src/<機能ID>.ref.txt`（別添資料・隣接画面など。ある機能だけ）。ここも設計書として判定に使い、引用してよい |
| 原本のHTML設計書 | `/home/y-saito/Developments/hareruya-design-docs/excel_to_html/output/<書番>_*.html` |
| 結合テストの範囲 | `/home/y-saito/Developments/hareruya-design-docs/integration_test/SCOPE.md` |

`src/<機能ID>.txt` はHTMLのタグを改行に置き換えたもの。表のセルは1行ずつに分かれている。
表の行の対応が分からないときは原本のHTMLを開いて確かめてよい。

## 判定（1ケースに1つ）

| 判定 | 意味 | 根拠引用 |
| --- | --- | --- |
| 維持 | 最新の設計書にも、期待結果を決めるだけの記述が無い | 分類が「矛盾」なら食い違う両方の記述。それ以外は空でよい |
| 解消 | 生成後に**追加・変更された記述**（`diff.txt` の追加行）で、期待結果が決まるようになった | 必須。追加された行からの逐語引用 |
| 保留誤り | 生成時点から設計書に記述があり、期待結果が決まっていた | 必須。設計書からの逐語引用 |
| 対象外 | 結合テストのケースにしない。`SCOPE.md` で単体・e2e・性能の担当になるもの、または設計書が「刷新後は実装不要」「フェーズ1では実装不要」と明示しているもの | 必須。SCOPE.mdの該当行、または設計書の明示箇所 |

### 判定の縛り

1. **「期待結果が決まる」とは、実行者が画面またはDBで合否を付けられる値・状態まで設計書が書いていること。**
   近い記述・関連する記述があるだけでは決まらない。保留の理由に挙がった未定義事項が**全部**埋まったときだけ「解消」「保留誤り」にする。一部だけ埋まったものは「維持」にし、`説明` に埋まった部分を書く
2. **他機能の設計書・一般常識・実装コードから補わない。** 例: ある機能が「該当が無いときは画面を表示しない」としか書いていなければ、他機能にHTTP404とあっても404は決まっていない
3. **現行仕様（埋め込まれた機能設計書）と刷新の指示（Excel基本設計の本文）が食い違うときは刷新を採る**（`SCOPE.md`）。これは矛盾ではない。刷新の指示で決まるなら「保留誤り」または「解消」
4. 根拠引用は `src/<機能ID>.txt` の文字列を**そのまま**写す。要約・言い換え・補完をしない。
   複数箇所を引くときは ` || ` で区切る。矛盾の片側が他機能のシートにあるときは、その機能の `src/<機能ID>.txt` から引いてよい（`説明` にどの機能か書く）。1つの引用は `src` の1行の中に収める（セルをまたがない）
5. 「解消」は、引用した行が `diff.txt` の「追加された行」にあること。追加行に無いなら「保留誤り」か「維持」

## 分類（判定が「維持」のときだけ付ける。それ以外は空）

| 分類 | 意味 | 決める人 |
| --- | --- | --- |
| 矛盾 | 設計書の中で記述が食い違い、どちらを採るか決まらない（刷新と現行の食い違いは除く） | 設計者 |
| 仕様値 | 値・上限・範囲・書式・型・並び順・対象範囲・時刻などが書かれていない | 設計者 |
| 結果 | 操作後に見えるもの（遷移先・画面表示・HTTP応答・DB更新の有無・出力内容）が書かれていない | 設計者 |
| 異常の作り方 | 期待結果（画面・応答・DB）は設計書に書かれているが、その異常・状態を試験環境で作る方法が書かれていない | テスト側 |
| 外部連携 | 外部システム・他機能の側の条件やふるまいが書かれていない | 設計者 |

- 結果も作り方も書かれていないものは「結果」にする（設計者が決めないと進まないため）
- 「異常の作り方」は、**期待結果が設計書に書いてあることを確かめてから**付ける。期待結果の記述を根拠引用に入れる

## 論点（「維持」のときだけ書く）

保留の原因となっている**未定義の事項を1文**で書く。設計者に質問としてそのまま渡せる粒度にする。

- 形: `<設計書の箇所>の<何>が未定義` 。箇所は `<シート名> 識別ID n` や `<シート名> 業務ロジック <節名>` のように人がHTMLで探せる形
- 同じ機能で同じ未定義事項から出た保留には、**一字一句同じ論点**を書く（あとで機械的にまとめるため）
- 1ケースが複数の未定義事項を抱えるときは、主たるもの1つを論点にし、残りは `説明` に書く

## 出力

`S/judge/bNN.tsv` に次の9列のTSVを書く（ヘッダー行あり、UTF-8、LF）。
入力の保留ケースを**全件・1件1行・入力と同じ順**で出す。

```
テストID	機能ID	判定	分類	決める人	論点	根拠引用	生成後の変化	説明
```

- `決める人`: 維持なら分類の表に従う（設計者／テスト側）。解消・保留誤り・対象外は `—`
- `生成後の変化`: そのケースに関わる行が `diff.txt` にあれば `あり`、無ければ `なし`
- `説明`: 判定の理由を1〜2文。セル内にタブ・改行を入れない

書き終えたら、次を実行して機械検査を通すこと。通るまで直す。

```
python3 S/gate.py S bNN
```
