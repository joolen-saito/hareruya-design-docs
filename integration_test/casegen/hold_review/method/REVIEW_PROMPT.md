結合テストケースのうち実行区分が「保留」のケースを、別の著者が最新のHTML設計書で判定し直した。
その判定に誤りが無いかを、**設計書を実際に読んで**確かめてほしい。

## 重点（上ほど重い）

1. **「解消」「保留誤り」の誤り。** 引用した記述だけで、保留の理由に挙がった未定義事項が**全部**決まるか。
   関連するだけの記述、一部しか埋まらない記述、他機能や一般常識で補わないと決まらないものを「解消」「保留誤り」にしていたら指摘する。
   ここを誤ると、根拠の無い期待結果でテストが作られる。最も重い
2. **「維持」の見落とし。** 設計書に期待結果を決める記述があるのに「維持」にしているもの。
   指摘するときは、その記述を `src/<機能ID>.txt` から**逐語で**引き、行番号を付けること
3. **「対象外」の誤り。** `SCOPE.md` の該当行や設計書の「実装不要」の明示が、本当にそのケースに当てはまるか
4. **分類・決める人の誤り。** 特に「異常の作り方」（テスト側が決める）は、期待結果が設計書に書かれている場合だけ付けてよい。
   期待結果が書かれていないのに「異常の作り方」にしていたら指摘する（設計者に聞くべきものがテスト側に流れる）
5. **「矛盾」の誤り。** 現行仕様と刷新の指示の食い違いは矛盾ではない（刷新を採る）。それを「矛盾」にしていたら指摘する
6. **引用の制約で分類を寄せたもの。** 途中まで、矛盾の片側が他機能のシートにあると引用できない制約があった。
   そのため本来「矛盾」のものを「仕様値」「外部連携」「結果」に寄せた判定がある（`説明` に他シート・別添との食い違いが書かれているもの）。見つけたら分類の誤りとして指摘する
7. **論点の誤り。** 論点が保留の原因を正しく言い当てていない、設計書の箇所（シート名・識別ID・節名）が違う、
   同じ機能で同じ未定義事項なのに論点の文言が違う（まとめられない）もの

## 指摘しないもの

- 設計書に無い値を「こうすべき」と提案すること。このレビューは答えを作らない
- 実装コードに基づく指摘。期待結果の根拠は設計書に限る
- 説明文の言い回し・文体
- 機械検査で見ている形式・逐語性

## 出力形式

指摘が1件も無ければ `NONE` の1語だけを出力する。
指摘があれば、1件ごとに次の形で書く。

```
### <テストID>
主張: <著者の判定・分類・論点のどれが、どうなっているか>
実際: <設計書の記述（逐語）と file:line>
判定: 解消の誤り / 保留誤りの誤り / 維持の見落とし / 対象外の誤り / 分類の誤り / 矛盾の誤り / 論点の誤り
修正案: <判定・分類・論点をどう直すか>
```
