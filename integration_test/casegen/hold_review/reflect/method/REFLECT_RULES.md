# 現行ソースで決まった答えを、正本（機能設計書）とテストケースへ反映する

保留だった結合テストの論点のうち、**現行ソースで答えが決まり、期待結果に使えると判定したもの**（「現行で確定」かつ「使えるか=可」）を反映する。
答えは3巡の敵対レビューを経ているが、誤りが残っている前提で、**書く前に根拠のコードを自分で読んで確かめる**こと。

R = /home/y-saito/Developments/hareruya-design-docs（リポジトリ）
S = /tmp/claude-1000/-home-y-saito-Developments-hareruya-design-docs/5d95a25c-a317-4d35-b601-d34efcc2a313/scratchpad/hold

## 入力（担当バッチ `S/reflect/batch/rNN.tsv`）

1行1論点。列: 論点ID・機能ID・区分・論点・現行での答え・根拠（file:line と逐語コード）・補足・テストID（カンマ区切り）・機能設計書（md のパス。1機能に md が複数あるときは `;` 区切りで、論点のシートに合う方へ書く）。

あわせて読むもの:
- 保留ケースの元の行: `R/integration_test/casegen/cases/<機能ID>_test_cases.tsv`（`期待結果` 列に何が未定義だったかが書いてある）
- 設計書（HTMLの該当シートを文字にしたもの）: `S/src/<機能ID>.txt`、`.ref.txt`
- 現行ソース: `/home/y-saito/Developments/` の pf-eccube3, pf-api, pf-article, deck-api, deck-builder, front-application, ec-cube（**ec-cube-enterprise は読まない**）

## 作業1: 機能設計書（md）へ書く

HTML設計書の「現行仕様」は `R/functions/<dir>/<機能>_*.md` から埋め込まれている。ここへ書けば正本HTMLに載る（埋め込み直しは別の作業者が行う）。

1. 根拠のコードを開いて答えを確かめる。答えが誤っていたら書かず、`作業記録` に「答えの誤り」として理由を書く（その論点のケースも直さない）
2. **答えが「どうやって起こすか」（呼出元の画面・操作・起動のしかた・試験データの作り方）だけのときは md に書かない。** 画面操作は設計書に書かない規約（0b）であり、手順は期待結果と違って設計書を根拠にしなくてよい。作業2の `手順`・`事前準備` にだけ使い、`結果` は「ケースのみ」とする
3. md に既に同じことが書いてあるか探す。書いてあれば新たに書かず、既存の文を使う
4. 書く場所: 既存の `## 業務ロジック` の `###` 小見出し、`## 入出力`、`## 表示メッセージ` の表のどれか。論点の中身に合う既存の小見出しに足す。合うものが無ければ `## 業務ロジック` の下に `###` を新設する。**`##` を新設しない**（HTMLに出るのは 処理フロー／入出力／業務ロジック／表示メッセージ／エラー処理 だけで、それ以外の `##` は本文ごと黙って消える）
5. 書き方（`R/.cursor/skills/reverse-design/GRANULARITY.md` の 0b・3.8・5 に従う）
   - 答えの中身だけを書く。**根拠のコードで確かめた範囲を超えて書かない**（推測・一般論・他機能からの補い禁止）
   - 画面操作（どこを押すか・どの順に描画するか）を書かない。何が起きるか・何が出るか・何が更新されるかを書く
   - 結論を先に置く。接続詞（そのため／また／なお／さらに）で文を始めない。意図や目的を書かない。一文に結論を1つ
   - **物理名を書かない**（`R/.cursor/skills/logical-naming/SKILL.md`）。テーブル名・カラム名・翻訳キー・ルート名・セッションキーは業務名に直す（例: `dtb_tag_sort.rank` → タグ優先表示順の順位）。HTTPパス・HTTPメソッド・コマンド名・環境変数名・具体値は物理のままでよい
   - 表示メッセージを足すときは既存の表の形（メッセージID・表示位置・画面上の文言・表示条件・後続処理）に合わせ、文言は現行ソースの逐語。新しいメッセージIDは振らず、既存IDに当たらないものは `業務ロジック` の本文に「〜と表示する」と書く
   - 現行の挙動が明らかな実装不備（効かない判定、到達しない分岐など）は書かない（不機能仕様の規約）
6. md 末尾の `## 出典` 表に、書いた小見出しと根拠を1行ずつ足す。形は既存行と同じ `<リポジトリ>:<パス>:<行>`、重要度は既存の同じ小見出しの行に合わせる（無ければ P2）
7. md の編集で粒度ゲートのフックが動く。出力のうち**自分が足した文が原因のもの**（接続詞で始まる文・目的の説明など）だけ直す。元からある違反には触れない

## 作業2: 保留ケースを実行できるケースに直す

論点に紐づくテストIDの行（実行区分=保留）を、書いた現行仕様を根拠に、実行できるケースへ書き換える。**テストID・要求ID・観点ID・優先度は変えない。**

- 規約は `R/integration_test/casegen/GEN_PROMPT_TEMPLATE.md` の「縛り」と `R/integration_test/casegen/STEP_PATTERNS.md`、判定基準は `R/integration_test/SCOPE.md`
- `実行区分`: ブラウザのみ／ブラウザ+DB確認。DB確認は画面・ファイル・ログなど外から観測できない副作用があるときだけ
- `連鎖ID`: 連鎖IDは論点から外した（依頼者決定）。空にする
- `使用シード`: 既存のシードID（`R/integration_test/casegen/cases/<機能ID>_seed_data.tsv`）を使う。足りなければ同じファイルへ行を足す（列は既存と同じ `シードID / 区分 / 論理名 / 状態・属性 / 用途 / 投入方法`、「同上」禁止）
- `事前準備`・`手順`: 共通の前提（ログイン・シード投入）は書かない。固有の前提が無ければ `—`。禁止語: 失敗させる／該当する操作を行う／同上／いくつか／別の画面
- `期待結果`: 実行者が画面またはDBで合否を付けられる形で1つ。**作業1で書いた文（または既存の文）から言えることだけ**。画面表示文言の逐語照合は結合テストの担当外（SCOPE.md）なので、文言そのものの一致を期待結果にしない
- `出典`: `<書番> <シート名> / 現行仕様 <節名> <小見出し>` の形（例: `0204 タグ登録 / 現行仕様 業務ロジック 優先表示の順位`）。ケースのみの論点では、期待結果の根拠にした設計書の箇所を書く（現行仕様でなくてよい）
- 物理名を書かない（作業1と同じ）
- 1つの論点に複数のテストIDが紐づくときは、それぞれ元の保留理由に合わせて書く。元の保留理由の一部が答えで埋まらないケースは書き換えず、`作業記録` に残す

## 出力

1. 書き換えた md（`R/functions/...`）と cases・seed（`R/integration_test/casegen/cases/...`）。担当の機能以外は触らない
2. 作業記録 `S/reflect/out/rNN.tsv`（ヘッダーあり、担当の論点を全件・入力順に1行ずつ）

```
論点ID	機能ID	結果	md小見出し	mdに書いた文	テストID	補足
```

- `結果`: 反映／既存の記述で反映（md は書かず、既存の文を根拠にケースを直した）／ケースのみ（答えが起こし方だけで md に書かず、手順に使った）／見送り（答えの誤り・ケースに届かない等。理由を補足へ）
- `md小見出し`: `業務ロジック > <小見出し>` のように。ケースのみ・見送りは `—`
- `mdに書いた文`: md に足した文を**逐語で**（複数なら ` || ` 区切り）。既存の記述を使った場合はその既存の文を逐語で。ケースのみ・見送りは `—`
- `テストID`: 書き換えたテストID（カンマ区切り）。書き換えなかったものは補足へ

最後に `python3 S/reflect/gate_reflect.py S rNN` を通すこと。
