# 商品登録画面で商品を作るシードの書き直し（2026-10-19〜）

依頼者決定（2026-10-19「商品登録画面で商品を作るシードも直して」）。

刷新後は商品の新規登録が禁止されている（M03-02 L0075〜L0077「商品新規登録のアクセスを禁止する」、URL は404）。E2E の実機でも、商品登録画面はどの権限でも開けない（403、`../../../e2e/HANDOFF_codex.md`）。それなのに、多くのシードが商品登録画面で商品を作る書き方になっていた。商品を作る部分を、グッズ商品CSV登録（M03-27）で作る書き方に直す。先に直した2件（`../datapattern/conflicts/rulings.tsv` の E03・K03）と同じ型。

## 書き直しの決まり（`PROMPT.md`）

- 直すのは商品を新しく作る部分だけ。ほかの部分（会員・店舗・注文・在庫の操作、DB への直接設定、控える番号）は変えない。ケースも変えない。
- 商品は、カード商品も含めてグッズ商品CSV登録で作る。カード商品は、取り込んだあと商品登録編集画面（既存の商品の編集。刷新後も使える）の「カード指定 >」（M03-02 L0092）でカードを付け、商品カテゴリと割引率を入れて「商品を登録」を押す（IT-M03-02-006 と同じ操作）。
- カード商品CSV登録（M03-26）は使わない。選んだ割引率に登録されたカードの状態ごとに規格を作り、価格も状態ごとの率で計算し直すので（M03-26 L0150・L0165、現行 pf-eccube3 の `ProductCardImportHandler`）、元のシードの規格の数と価格を再現できない。
- 規格は元のシードのとおりに作る。CSV が作るニアミントの規格は直して使い、ほかの規格は商品規格一覧の「新規作成」（M03-08 L0059）から商品規格登録編集画面（M03-09）で足す。
- グッズ商品CSVの商品カテゴリはサプライ・グッズ等の配下だけ（M03-27 L0123）。ほかのカテゴリが要るときは、取り込んだあと編集画面で付け替える（カテゴリの木は動かさない）。
- 編集画面は割引率・販売制限などが空だと登録できない（`functions/pf-eccube3/m03-02_admin_product_product_edit.md` 17行目）。グッズ商品CSVには割引率の列が無いので、編集するときは割引率を選ぶ。

## 試行（F06-15・F02-02・A07-06・M03-03）

- 最初はカード商品をカード商品CSVで作る型にしたが、試行でどの状態の規格が作られるか決まらないと分かり、上の決まりに変えた。
- 商品登録編集画面の登録ボタンも「商品を登録」（M03-02 識別ID 35）なので、ボタン名では新規登録かどうかを判定しない。
- codex の確認（`review/P1`）の指摘は2件（M03-03 の PAGING-011・012。編集で割引率を選んでいない）。採用して直し、同じ型を gate の G8 で拾うようにした。

決まり（担当の途中で分かり、`PROMPT.md`・`gate.py` に足したもの）:

- 価格は税込みで登録する（ee の ProductClass「晴れる屋仕様では価格は『税込み』で登録される」）。税込みの額は1.1で割らない。
- 新しく作る規格はセールフラグ無効で、販売価格は基準価格と同じになる（M03-09 L0086〜L0087、ee の取り込み）→ G9。
- 規格の画面に在庫数・在庫無制限の欄は無い（M03-09 L0095・L0097）。在庫は在庫変更CSV登録（M04-21）で入庫し、登録者と別の承認権限を持つメンバーが承認一覧（M04-32 L0108・L0110）で承認する → G10・G11。
- 支店の商品公開ステータスの ee の初期値は公開（Product.php `is_branch_published`）。元が指定していない行は1にそろえた（`work/fix_branch.py`、190行）。
- 規格の公開ステータスの ee の初期値は公開（ProductClass.php `visible`）。

ケースに影響があると理由の欄に書いた「直す」の行は98件。51件は F10-03 の固定の商品ID（元のシードとケースの欠陥）。残りの多くは、CSV が作るニアミントの規格が余る、または論理削除で残るもの（規格の数・一覧の行を見るケースでは影響があり得る）。

### 2巡目の直し（2026-10-19、`fix_stock.py`）

2巡目の指摘は、書き直しで新しく書いた入庫・承認の文の型の抜けだった。指摘された行だけでなく、同じ型の430件（18機能）を `fix_stock.py` で直した（何度流しても同じ。記録は `work/fix_stock_log.tsv`、直す前と後の対照は `review/L_diff.tsv`）。元のシードにもともとあった入庫・承認の文は直していない（`work/notes.md` の「別の論点」に件数）。

- 在庫変更CSV登録の承認通知先は、所属選択とメンバー選択のどちらも必須（M04-21 L0131・L0132）。在庫編集（M04-02）はメンバー選択だけが必須
- 1つの規格で100以上の増減があるときは、「一括登録を実行」のあと確認モーダルで「OK」を押す（M04-21 L0056〜L0058）
- 承認一覧で「承認する」を押したあと、確認画面で「OK」を押す（M04-32 L0218・L0301）
- M05-10 の29件は「CSVを取り込む」とだけ書いていたので型で書き直した。入庫の店舗は元のシードの作り分けどおり（STORES-001 の支店用商品と SORTBRANCH-026 は支店、ほかは本店）
- 入庫の店舗の取り違え: F04-04 INSTORE の4件（TC東京）、F04-02 STORE-CARTS-020（本店カートの商品は本店）・SMAREGI-051（支店）。同じ型を機械で突き合わせ、M05-23 の17件（受注店舗=本店なのに TC東京へ入庫）も本店に直した
- A06-03 AB-PRODUCT: 承認者に名指しした S-A06-03-ADM は AB試験店舗の承認権限が無く、ケースも使っていない。AB試験店舗の承認権限を持つメンバーをこのシードの中で作る形にした
- 検査 G12（新しく書いた在庫変更CSV登録の必須の操作）・G13（承認のあとの確認画面の「OK」）を足した。直す前の out にはどちらも数百件当たる
- `apply.py` は、前に自分が当てた文（`work/applied.tsv` に文のハッシュを控える）も置き換えてよい文とみなすようにした。`seed_screen/apply.py` が書き直し前へ戻さないシード（M12-03 の4件）に前回の書き直しが残り、「上流で変わった」と止まったため
直したあと `seed_screen/apply.py` から流し直し、2,418件が書き直しと一致すること、`gate_precond.py --all`・`gate_dp.py` の合格、ケース数 11,713件のままを確かめた。実機では未実行。
