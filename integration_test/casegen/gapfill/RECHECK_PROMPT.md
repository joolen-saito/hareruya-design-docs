# 依頼: {FID} に足した結合テストケースが、抜けを実際に埋めているかの再監査

リポジトリ `/home/y-saito/Developments/hareruya-design-docs/`。出力は日本語。これは監査であり、ケースも設計書も直さない。
あなたは著者でもレビュアーでもない第三者である。事実は自分でファイルを読んで確かめ、推測で「埋まった」としない。

## 背景

HTML設計書の監査で「設計書に定めがあるのに確かめる結合テストケースが無い」抜けが見つかり、著者がケースを足した。
足したケースが、その抜けを本当に確かめているかを1件ずつ判定する。

## 読むもの（`integration_test/casegen/` 配下）

| 何 | パス |
| --- | --- |
| 抜けの一覧（指摘ID／単位／行／記述／理由＝何が確かめられていなかったか） | `gapfill/targets/{FID}_gaps.tsv` |
| 著者の仕分け（指摘ID → 扱い・テストID） | `gapfill/cases/{FID}_gf_dispositions.tsv` |
| 足したケース（13列。末尾は指摘ID）と足したシード | `gapfill/cases/{FID}_gf_test_cases.tsv`・`{FID}_gf_seed_data.tsv` |
| 既存ケースを含む全ケースとシード（「既存ケースで確認済み」の確認、共有シードの中身） | `cases/{FID}_test_cases.tsv`・`{FID}_seed_data.tsv` |
| 設計書（行頭 L0001 が行番号） | `coverage_audit/units/<単位>/sheet.txt` |

対象は、仕分けの扱いが「ケース化」「既存ケースで確認済み」の抜けだけ（「ケースにしない」は対象外で、出力に書かない）。
`gapfill/review/` と `gapfill/recheck/` の他のファイル、他機能のファイルは読まない。
書くのは下の出力1つだけ。git の変更操作（add・commit など）をしない。

## 判定（抜け1件につき1行）

設計書の該当行を読み、抜けの「理由」が言う未確認の点を、挙げられたケースの**事前準備・手順・期待結果**が実際に確かめているかで決める。

| 判定 | 意味 |
| --- | --- |
| 埋まった | 挙げられたケースを実行すれば、その定めが守られていない実装は不合格になる |
| 一部 | 定めの一部しか確かめていない（別の枝・逆側の条件・別の項目・境界が残る）。何が残るかを書く |
| 埋まっていない | ケースが別のことを確かめている／期待結果がその定めの成否で変わらない／事前準備と手順からその定めの場面に到達しない／期待結果が設計書の定めと食い違う。理由を書く |

- 期待結果がその定めと無関係に常に成り立つもの（例: 画面が表示されること、だけ）は「埋まっていない」。
- 設計書が定めていない値を期待していても、定め自体を確かめていれば「埋まった」でよい（その場合は理由欄に「余分な期待: …」と書く）。
- 判定IDの当て方、書式、シードの作り方が未確定であること、は判定に使わない。

## 出力

`integration_test/casegen/gapfill/recheck/{FID}.tsv`（ヘッダつきタブ区切り・セル内に改行とタブを入れない）

```
指摘ID	判定	テストID	理由
```

テストIDは判定に使ったケース。理由は「一部」「埋まっていない」で必須（設計書の行番号を引く）。

書いたら `python3 integration_test/casegen/gapfill/gate_recheck.py {FID}` を実行し、不合格が無くなるまで直す。
返答は、判定ごとの件数と、「一部」「埋まっていない」の指摘IDを1行ずつ。
