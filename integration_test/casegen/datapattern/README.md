# データパターンの結合テストケース（2026-10-15）

依頼者（2026-10-15）: 「データパターンを網羅したい。例えば数量1と複数。データの組合せによって挙動が異なるケース、データ有無によって挙動が異なるケース。
他にもあれば提案して、データパターンによるテストケースも追加して」

調べた結果: ケースは設計書の定め1件ごとに作られていて、同じ定めをデータを変えて通す確認が無い。
注文のあとに在庫を確かめるケースは7件（IT-F04-04-020・021・040・041 ほか）すべて1商品・数量3で、数量1・2商品を1回で注文・在庫ちょうどの注文は無い。

依頼者決定（2026-10-15）:
- パターンは7種。依頼の3つ（数量・件数の1と複数、組合せ、有無）と、提案した4つ（混在、状態・区分ごと、端数・ちょうどの値、同じデータの重ね）
- 範囲は全機能（ケースのある349機能）。1機能ずつ監査して、抜けだけ足す。進め方は被覆監査（`../coverage_audit/`・`../gapfill/`）と同じ

## やり方

| 段 | 何をしたか | 道具 |
| --- | --- | --- |
| 単位を作る | 機能ごとに、いまのHTML設計書の対応シートを文字に起こし（行番号つき）、数量・件数・条件の語を含む行（keylines）と、テストから外したケースを添える。M01-01・M05-14・M11-05 は対応シートが無く、機能設計書の md を使った | `build_units.py` → `units/<機能ID>/design.txt`・`keylines.tsv`・`excluded.tsv`、`units/_common/`、`units.tsv` |
| 監査 | 1機能1エージェント（sonnet）。データで結果が変わる定めごとに試すデータを挙げ、ケースあり／抜け／除外済み／対象外を付ける。keylines の全行にも扱いを付ける | `AUDIT_PROMPT.md`・`mk_prompt.py` → `audit/<機能ID>.tsv`・`_keylines.tsv` |
| 検査 | 形式、連番、根拠の行の実在、テストIDの実在、keylines の全行に扱いがあること | `gate_dp.py` |
| 反証 | 抜けを約50件ずつ codex に渡し、反証できないかを1件ずつ判定させる（3回に分けて流した: V・W・X） | `mk_verify.py`・`verify.sh` → `verify/*_out.txt`、`collect_verify.py` → `verified.tsv` |
| 束ねる | 反証で「妥当」の抜けだけを機能ごとに束ね、開始番号（既存の続き）を決める。標準機能（M01-01・M05-14・M11-05）は結合テストケースを作らない決定（2026-10-06）なので外す | `build_targets.py` → `targets.tsv`・`targets/<機能ID>_gaps.tsv`、外したものは `dropped.tsv` |
| 著者 | 1機能ずつ（sonnet。小さい機能は1本で2〜4機能を順に）。抜け1件ごとに ケース化／既存ケースで確認済み／ケースにしない を決める。既存ケースは変えない | `GEN_PROMPT.md`・`mk_gen.py` → `cases/<機能ID>_dp_test_cases.tsv`（13列。末尾は項目ID）・`_dp_seed_data.tsv`（足したシードだけ）・`_dp_dispositions.tsv` |

裁定は `../sheetmap/FIX_R1_BRIEF.md`（A〜L、C'）・`FIX_R2_BRIEF.md`（M〜O）をそのまま使った。

## 直すときの手順

1. `datapattern/cases/<機能ID>_dp_*.tsv` を直す
2. `python3 datapattern/verify_dp.py`
3. `python3 datapattern/merge_dp.py`
4. `python3 seed_screen/apply.py`（画面で作る形への書き直しを当て直す。merge は ../cases/ を書き直し前へ戻すため）
4b. `python3 datapattern/conflicts/apply_rulings.py`（食い違いの裁定を当て直す。seed_screen/apply.py の後）
5. `python3 exclude_open.py`（テストできない・作り方が未確定のケースを外し直す。precond/README.md）
5b. `python3 exclude_scope.py`（フェーズ2見送り・実装しない機能のケースを外す。2026-10-16）
6. `python3 build_all_test_cases.py` と `python3 precond/gate_precond.py --all`

`sheetmap/`・`nosheet/`・`ga/`・`gapfill/` の `merge_into_cases.py` は該当機能のケースファイルを作り直すので、流したら 3 から流し直す。

## 読むときの注意

- 2巡目の指摘を反映した後の版は codex に掛けていない（レビューは2巡まで）。2巡目でも44件の指摘が出ており、ゼロに収束したわけではない。
- 足したケースが抜けを実際に埋めたかの再監査（gapfill で行った `RECHECK`）はしていない。
- 実機では1件も流していない。投入方法が「未確定」のシードを使うケースは合流時に外れた（21件）。
- 期待結果のうち、著者が設計書から読み取った解釈に頼るものがある（例: M12-05 の「別会員2人なら件数2」、M15-04 は機能設計書の md の記述、M16-03 の祝日 2026-02-23 は一般知識）。レビューは事実確認だけで、解釈の当否までは裁定していない。
- F10-03 の追加シードに、著者が設計書に無い対応づけ（「PL」＝モデレトリープレイド）を推測で書いていた。依頼元が「PL」の語を外し、設計書の選択肢の名前だけにした。
- F01-02 の追加ケースは、Foil の選び方を設計書の「あり」で書いた。管理画面の選択肢は「なし・通常・特殊」で、「あり」がどれに当たるかは設計書から決まらない。
- M03-32 の既存ケース・シード（今回足した分を含む）は商品登録画面で商品を作る書き方だが、M03-02 L0075・L0076 では商品新規登録は404。足したケースのうち M03-26・F10-03・M03-11 の分はCSV登録で作る形に直した。
- 物理名: 足したケースには、設計書か既存ケースにすでに書かれている名前（APIの項目名、CSVのファイル名、`/admin/...` の画面のパスなど）が残る。設計書に書かれた名前は使ってよい決まり（GEN_PROMPT）に従った。
- 1巡目の前提条件の検査の明細（`review/<機能ID>_r1_gate.txt`）は、`gate_dry.sh` の古いファイルの削除が `*_r1_gate.txt` まで消したため失われた。いまのファイルは目印だけ。直した内容は各機能の `_r1_dispositions.tsv` にある。削除の処理は直した。
- 著者・レビュアーは、ほかの機能の設計書（units/ の design.txt）を参照のために読んだことがある。ほかの機能の datapattern/cases の成果物は読んでいない（報告による）。
