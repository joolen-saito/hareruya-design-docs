# 既存ケースと設計書の食い違いの裁定（2026-10-16）

データパターンのケースを足す作業（`../README.md`）の途中で、監査・著者・レビューのエージェントが報告した「既存ケースと設計書の食い違い」「設計書の中の食い違い」52件（`../existing_case_conflicts.txt`）を、原文で照合して裁定し、ケースへ当てた。

## 依頼者の決定（2026-10-16）

設計書（HTML）は Excel 由来の本文と、末尾に埋め込んだ機能設計書（リバースの現行仕様）の2層でできている。埋め込みのうち「表示メッセージ」の節だけは、2026-08-19 の決定でリニューアル後の仕様（HTML では「リニューアル後の仕様」の見出しの下）。層の間で記述が食い違うときの優先順位を決めた。

| 規則 | 内容 |
| --- | --- |
| 規則1 | Excel由来の本文 ＞ 埋め込みの現行仕様の節。★の無い行（現行踏襲の要約）も含め Excel を採る（既存ケースを生成した GEN_PROMPT の規則と同じ） |
| 規則2 | 埋め込みの表示メッセージの節 ＞ 同じ埋め込みの現行仕様の節 |
| 規則3 | Excel由来の本文 ＞ 埋め込みの表示メッセージの節 |
| 未決の扱い | 規則で決まらない食い違い（Excel どうし、Excel の文言どうし）は、両方に共通する部分だけを期待結果に書き直す。共通部分が無いケースは保留として外し、設計者に聞く |

既存の決まりもそのまま当てた。同じ出所の中では改訂日つき・「変更／削除／修正／廃止」の記述が改訂前に優先する（表では「改訂後」）。現行踏襲の機能で現行の挙動が不具合のものはケースから外す（2026-09-28 決定。表では「現行の不具合」）。
Excel が触れていない条件を埋め込みが足しているだけのもの（例: Excel「無効でもNMは表示」と埋め込み「高額商品コードの規格は表示しない」）は食い違いではなく、両方を当てる。

## 進め方

1. `prov.py` で、設計書の写し（`../units/<機能ID>/design.txt`）の各行に出所（Excel／埋め込みの md）を付けた（`prov/`。design.txt と1行ずつ一致することを確かめてある）
2. 照合: sonnet 8本が項目を分担し、原文・出所・改訂の記述・ケースの今の記述を突き合わせて分類と裁定案を出した（`BRIEF.md`・`verify/G1〜G8.tsv`、まとめ `merged.tsv`）。BRIEF.md の置き場の記述は作業時の一時ディレクトリのもの
3. codex の反証 1巡（`review/V1〜V3`）。指摘33件。最大の論点は表示メッセージの節の扱い（照合者は現行仕様として扱っていた）で、上の規則2・3として依頼者が決めた
4. 依頼者の決定を当てて項目ごとに裁定し（`decisions.tsv`）、ケースへ当てた
5. codex の確認 1巡（`review/W1・W2`）。指摘10件のうち8件を採った（外し漏れ M03-27-066・M09-07-033、M09-07-029・031 のファイル名の操作、M04-23-055 の事前準備・シード、M04-18-011 の0件の作り方、M15-06-029 の裁定理由、A17-04-018 の出典、問い QD-M04-23-01）。採らなかった2件（M05-09-006・M05-22-003）は理由を `decisions.tsv` の C34・C35 に書いた。確認の後の直しは codex に掛けていない（レビューは事実確認の2巡まで）

## 直すときの手順

`rulings.tsv` を直してから、次の順に流す（`apply_rulings.py` は何度流しても同じ）。

1. merge（sheetmap・nosheet・ga・gapfill の `merge_into_cases.py`、`../merge_dp.py`）
2. `python3 seed_screen/apply.py`
3. `python3 datapattern/conflicts/apply_rulings.py`（seed_screen/apply.py が cases/ と oracle_changes/ を書き直すので、必ずその後。最後に `product_csv/apply.py`〔商品登録画面で商品を作るシードの書き直し、2026-10-19〕と `runnable/apply.py`〔書かれたとおりに実行できるようにする直し、2026-10-19〕も呼ぶ。後段が当てた文は `runnable/work/applied.tsv` で見分け、裁定は済みとみなす）
4. `python3 exclude_open.py`、続けて `python3 exclude_scope.py`（フェーズ2見送り・実装しない機能の除外。2026-10-16）
5. `python3 build_all_test_cases.py` と `python3 precond/gate_precond.py --all`、`python3 datapattern/gate_dp.py`

前提条件の検査（`../../precond/gate_precond.py`）は、手順の変更の種別に「裁定訂正」を認めるようにした。基線にあるケースの期待結果・手順・出典の変更は、`precond/oracle_changes/`・`step_changes/`・`source_changes/` に裁定（承認欄「2026-10-16 依頼者裁定」）として宣言してある。
データパターンの監査の検査（`../gate_dp.py`）は、監査が「ケースあり」で挙げた既存ケースが今回保留へ外れたもの（12件）を通し、件数を参考として出す。前提条件の検査の G6 は、足したケース（added_cases.tsv）が保留へ外れた分も差し引いて照合する（M03-27-066 は被覆監査で足したケース）。
