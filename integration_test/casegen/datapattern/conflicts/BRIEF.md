# 照合の依頼：既存の結合テストケースと設計書の食い違い

データパターンのケースを足す作業の途中で、監査・著者・レビューのエージェントが「既存ケースと設計書の食い違い」「設計書の中の食い違い」を報告した。
これは報告のままで、誰も原文を照合していない。あなたは担当の項目ごとに原文を照合し、事実と裁定案を出す。**ファイルは一切変更しない**（下の出力ファイルを書くことだけ許す）。rg は使わない（取りこぼしがある）。grep・sed・awk・python で読む。出力は日本語。

## 項目ごとにやること

1. 報告が挙げたテストIDのケースが今どこにあるか（`cases/` にある／excluded_open／excluded_hold／無い）。あれば事前準備・手順・期待結果の要点と出典を引く。seed_screen/cases や oracle_changes に行があればそれも書く
2. 報告が挙げた設計書の行を prov で読み、**原文をそのまま引く**（行番号・出所）。前後の行も読み、報告の読みが正しいか確かめる。改訂の記述（「2026/7/21修正」「変更」「削除」「刷新」など）、条件の範囲（どの画面から来た場合か等）を落とさない。必要なら HTML の表や画像も見る
3. 報告に無い関連記述（同じ機能の他の行、同じ冊子の別シート）で食い違いが解けるか、または強まるかを探す
4. 次のどれかに分類し、裁定案を出す

| 分類 | 意味 | 裁定案の書き方 |
| --- | --- | --- |
| ケース誤り | 設計書が一意に定めており、ケースがそれと違う | ケースを設計書に合わせる。新しい期待結果（必要なら事前準備・手順）の文案を書く |
| 規則で決まる | 設計書の中で食い違うが、次の規則で一方に決まる。(R1) 埋め込み（現行仕様）と Excel 由来（刷新の指示）が食い違うときは Excel 由来を採る。(R2) 同じ出所の中で、改訂日の付いた記述・「〜に変更／削除／修正」と書かれた記述が、改訂前の記述と食い違うときは改訂後を採る | どの規則でどちらを採るかを書き、ケースの直し方（文案）を書く。ケースが既に採るべき側なら「直し不要」 |
| 設計裁定 | 設計書の中で食い違い、R1・R2 で決まらない（Excel 由来どうし、埋め込みどうし、項目定義とメッセージ定義など） | 両方の原文を並べ、設計者に聞く問いを1文で書く。両方に共通する部分だけで期待結果を書けるならその文案、書けないなら「共通部分なし」 |
| 報告誤り | 原文を読むと食い違いは無い（読み違い、条件の取り違え、別の行が既に解いている） | 根拠を書く。何もしない |
| その他 | 食い違いでない報告（標準機能・フェーズ2の確認、抜けの重複の注意、手順・作り方の不備など） | 事実を確かめ、取るべき処置を書く |

推測で埋めない。設計書に無い期待値を文案に入れない。期待結果の根拠は設計書だけで、実装（`/home/y-saito/Developments/ec-cube-enterprise` など）は手順・作り方の実行可能性を見るためにだけ読んでよい。実装と設計書の違いは分類に使わない。
1件の報告に複数の論点があれば、論点ごとに行を分ける（項目に -1, -2 を付ける）。報告が挙げたテストIDの他に、同じ食い違いを抱える既存ケースを見つけたら「同型のケース」に挙げる。

書き終えたら、最後の返答に、項目ごとの分類を1行ずつ（`C01 ケース誤り` の形）と、迷ったもの・確信の持てないものを書く。
