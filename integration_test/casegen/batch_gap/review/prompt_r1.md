# 敵対レビュー: バッチから画面への連携の設計確認の論点（1巡目）

これは成果物のレビューである。著者（別のAI）を信用せず、事実は自分で設計書を読んで確認せよ。褒める必要はない。ファイルは変更するな（読み取りのみ）。
パスはすべて `/home/y-saito/Developments/hareruya-design-docs/` からの相対である。

## 背景

結合テストで、バッチが更新したデータを画面で確かめる連携ケース（判定 IT-0334）を作ったとき、下流の候補の多くが「その画面がこのデータを使うと設計書に書かれていない」として外された。
依頼者の決定（2026-10-16）: バッチから画面への連携のうち、設計書に連携先が書かれていないものを、設計確認の論点として設計者へ起票する。
著者はバッチ20本の設計書を読み、論点を16件にまとめた。起票は Backlog に、カテゴリ「設計要確認」、課題名を疑問形にして行う予定である。

## 成果物（`integration_test/casegen/batch_gap/`）

- 論点: `questions.tsv`（論点ID・バッチ・区分 A/B/C・更新先のデータ・関係する画面・設計書の記述・足りない記述・設計者への問い・選択肢・前の作業の報告）
- 著者の報告: `report.md`（論点にしなかったバッチと理由を含む）
- 著者への依頼文: `PROMPT.md`（区分の意味、論点にしないもの、確かめ方が規則の正）


## 正本・照合先

- 機能設計書 `functions/*/<機能IDの小文字>_*.md`（`_archive` は読まない）、HTML設計書 `excel_to_html/output/<ブック>_*.html`、機能とシートの対応 `functions/function-sheet-map.tsv`
- 既にある論点: `integration_test/casegen/hold_review/current/issues.tsv`、`integration_test/casegen/precond/open_preconditions.tsv`
- 既に起票した設計確認: `integration_test/casegen/batch_gap/work/existing_design_issues.tsv`（Backlog のカテゴリ「設計要確認」90件の件名と本文の冒頭）
- 前の作業の報告: `integration_test/casegen/link/gen_<バッチ>/report.md`

## 検証してほしいこと

1. **事実の誤り（最重点）**: 「設計書の記述（根拠）」の箇所を開き、書かれている内容が正しいか。「〜に記述なし」「画面が無い」とした主張が本当か（そのデータの業務名で設計書を検索し、表示・利用すると書いた画面が実はあれば挙げよ）。
2. **論点として成り立つか**: 設計者に答えてもらう必要がある欠落か。
   - 内部の制御用の印（再連携の要否を決めるフラグなど）で、設計上も画面に出さないことが読み取れるなら、「どの画面で表示しますか」と問うのは不適切。その場合は削除か、問いの書き直し（「画面には表示しない内部の値でよいですか」など）を提案せよ。
   - 区分C は、本当に設計書の中で食い違っているか（片方が古い記述で、改訂後の記述や刷新の指示で決まるなら食い違いではない。`integration_test/SCOPE.md` と、設計書内の食い違いの優先順位: Excel由来＞表示メッセージ節＞現行仕様節・改訂後優先）。
3. **重複**: 論点どうしで同じ問い（例: BG-004 と BG-007）、既にある論点（`hold_review/current/issues.tsv`・`open_preconditions.tsv`）や既に起票した設計確認（`existing_design_issues.tsv`）と同じ問いがあれば挙げよ。
4. **問いの書き方**: 設計者が設計書だけを見て答えられるか。推測や仕様の提案を混ぜていないか。選択肢が設計書の記述どおりか（著者が案を作っていないか）。物理名を書いていないか。
5. **取りこぼし**: 著者が「論点にしなかった」バッチ・組（`report.md`）のうち、実は連携先が書かれていないのに外したもの。

## 指摘対象外

- 起票すること自体の是非。結合テストのケースの中身。
- 試験環境の作り方（バッチの起動方法・外部サービスの試験環境）。

## 出力形式

指摘が無ければ `NONE` の1語だけを出力せよ。指摘は1件ごとに次の形で書け。結論を先に置け。

```
### 指摘N（重大度: Major / Minor）対象: <論点ID または バッチ>
主張: （著者の記述）
実際: （確認した事実。file:line を付ける）
判定: 事実の誤り / 論点として不成立 / 重複 / 問いの不備 / 取りこぼし
修正案: （書き直した問い、削除、統合、追加すべき論点の骨子）
```
