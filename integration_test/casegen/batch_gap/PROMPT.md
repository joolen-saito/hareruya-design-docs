# 依頼: バッチから画面への連携で、設計書に連携先が書かれていないものを、設計確認の論点にまとめる

これは**調査と下書きの依頼**である。あなたがバッチごとに設計書を読み、設計者へ確かめるべき論点の一覧を作ってファイルへ保存する。
**設計書に書いていないことを推測で補わない。** 論点は「設計書のどこに何が無いか」という事実と、それを埋めるための問いだけにする。仕様の提案はしない。

ケースを足す前に、設計書に連携先（どの画面がそのデータを表示・利用するか）を書いてもらうためである。

## 論点にするもの（区分）

| 区分 | 意味 |
| --- | --- |
| A 連携先が無い | バッチの更新先（登録・更新・削除するデータ）を、表示・検索・利用すると書いた画面が、設計書に1つも無い。刷新後の更新先そのものが機能設計書に書かれていない場合を含む |
| B 対応が書かれていない | 下流の画面に似た項目（名称・内容が近い）はあるが、バッチが更新するデータと同じだと言える記述（取得元、名称の対応）が無い |
| C 連携に関わる食い違い | バッチ側と画面側、または同じ冊子の中で、連携するデータの記述が食い違い、どちらを正とするか決まらない |

論点にしないもの:
- 試験環境の作り方が決まっていない話（バッチの起動方法、外部サービスの試験環境、時計の固定など）。これは `open_preconditions.tsv` の範囲で、設計書の連携先の話ではない。一覧には載せず、報告の「範囲外」に1行で書く。
- 連携と関係の無い設計書の不備（画面の文言の誤字、識別IDの重複など）。
- 既に連携ケースがあり、いまも残っている組（B02-06・B08-01・B08-05 の残っているケース）。
- 既にある論点（`hold_review/current/issues.tsv` の論点、`open_preconditions.tsv` の行）と同じ問い。重なるときは一覧に載せず、報告に「既存の論点 <ID> と同じ」と書く。

## 確かめ方

1. バッチの機能設計書と HTML設計書から、刷新後にバッチが登録・更新・削除するデータ（業務名）を書き出す。
2. 下流の候補（`link_targets.tsv` の行、前の作業の報告で検討した画面）のうち、そのデータを扱いそうな画面の画面項目定義・機能仕様を読む。候補に無い画面でも、そのデータの業務名で設計書を検索して見つけたら読む。
3. 「そのデータを表示・検索・利用する」と書いた画面があれば、区分Aにはしない（連携先がある）。項目はあるが同じデータと言えないなら区分B、食い違いなら区分C。
4. 1つの論点は、1本のバッチ × 1つの更新先データ（同じ問いになるなら複数の画面をまとめてよい）。

タブ区切り・1行目はヘッダ・セル内のタブと改行なし。

```
論点ID	バッチ	区分	更新先のデータ	関係する画面	設計書の記述（根拠）	足りない記述	設計者への問い	選択肢	前の作業の報告
```

- `論点ID`: `BG-001` からの連番
- `バッチ`: 機能IDと機能名（例 `B02-03 期間別入庫数集計`）
- `区分`: A／B／C
- `更新先のデータ`: 業務名（物理名を書かない）
- `関係する画面`: 機能IDと画面名。区分Aで候補が無ければ `—`
- `設計書の記述（根拠）`: バッチ側と画面側の該当箇所（`<ブック> <シート名> / 識別ID または節名`、機能設計書なら `ファイル:行`）。読んだが記述が無かった箇所も「〜に記述なし」と書く
- `足りない記述`: 何が書かれていないか（1文）
- `設計者への問い`: 疑問形の1文（例「期間別入庫数集計バッチが登録する期間別入庫数は、どの画面で表示・利用しますか？」）
- `選択肢`: 区分Cなら食い違う記述をそれぞれ。A・B は、設計書の中に候補の画面が書かれていればそれを並べ、無ければ `—`（自分で案を作らない）
- `前の作業の報告`: `link/gen_<バッチ>/report.md` の該当箇所（節名）。無ければ `—`
