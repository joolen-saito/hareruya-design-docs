# 依頼: {FID} の画面への書き直しで出た、前提条件の検査の不合格を直す

リポジトリ `/home/y-saito/Developments/hareruya-design-docs/`。出力は日本語。直すのは `integration_test/casegen/seed_screen/out/{FID}.tsv` と `seed_screen/cases/{FID}.tsv` の2つだけ。ほかのファイルは変更しない。**git の変更操作（add・commit・push など）を絶対にしない。** スクリプトやコマンドは下に挙げたもの以外実行しない。

## 背景

`python3 integration_test/casegen/seed_screen/mk.py {FID}` の出力が、この書き直しの依頼文である（決まりはそこにある）。
あなたの前の担当が書いた out・cases を全機能まとめてケースへ当てたところ、前提条件の検査（識別子の一意性）で {FID} に不合格が出た。
不合格の一覧: `integration_test/casegen/seed_screen/gatefix/{FID}.txt`

## 検査の決まり（G5）

- ケース専用シードの「状態・属性」に書いた識別子（英数字・ハイフン・下線・ピリオド・@ の4文字以上の連なりで、英字と数字の両方を含むもの。例 `A205`、`TAG-A-001`、`M0505`）は、**ほかのケースの事前準備・手順・期待結果にも、ほかのケース専用シード（全機能）にも現れてはならない**。
- 〔…〕で囲んだ「控えた番号」の呼び名は識別子として数えない。
- 「他ケースの専用データ X（S-…）を使っている」= そのケースの文に、別のケース専用シードの識別子 X が出ている。
- 「識別子 X が他のケース専用シードと重なる」= 複数のケース専用シードの状態・属性に同じ X がある。

## よくある原因と直し方

- 書き直しで、状態・属性に機能を表す短い記号（`{FIDC}` など）や連番だけの名前を新しく書き足した → その記号を〔…〕の呼び名の中に入れるか、機能とケース番号を含む一意の名前にする（例 `{FIDC}-012-A`）。
- 呼び名を〔…〕で囲まずに書いた → 〔…〕で囲む。
- 複数のケースが同じデータを使っている → そのデータは共有可のシードのものなので、ケース専用シードの状態・属性に書かない（共有シード側にあれば足りる）。
- 元（書き直し前）から固定値で一意だった識別子を、書き直しで別の値に変えてしまった → 元の値に戻す（`integration_test/casegen/seed_screen/in/{FID}.tsv` に元の状態・属性がある。試験者が入力する名称・コードは変えない決まり）。
- 他機能のシードと重なった → {FID} 側の識別子に機能とケース番号を足す（cases の文も同じ値に揃える）。ただし元からの固定値はケースが名指ししているので、変えるときは cases にそのケースの行を足して事前準備・手順・期待結果も同じ値に揃える。

G7（「step_changes の新手順とケースの手順が違う」）の行は依頼元が直すので無視してよい。

## 確かめ方

1. `python3 integration_test/casegen/seed_screen/gate.py {FID}` が「不合格 0」。
2. gatefix の各行について、原因の識別子が、直したあとの out（状態・属性）と cases（3つの欄）で重ならなくなったことを `grep -F` で確かめる。ほかの機能との重なりは `grep -rF '<識別子>' integration_test/casegen/cases/ integration_test/casegen/seed_screen/out/` で確かめる。

返答は、不合格ごとの原因と直し方を1行ずつ。
