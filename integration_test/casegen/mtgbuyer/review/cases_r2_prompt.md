## 重点観点

1. 期待結果が設計書の記述から出るか。設計書に無い値・挙動を期待していないか。事前準備の値から期待結果の値が一意に決まるか。現行ソースで実際にそうなるかも確かめよ（特に: 受注を指定したときに送る状態ID、査定完了で送るJSONの各項目とまとめ方、買取価格の決まり方、まとめて買取の判定、CSVの列・囲み・商品名の形・出力しない行、ファイル名、失敗時にとどまるか進むか）。
2. 事前準備の状態から手順を実行して期待結果に到達できるか。現行ソースの画面遷移・ボタンの有無・モードごとの違いに照らして、実行できない手順（そのモードに無い操作、存在しない画面部品）、成立しない前提を挙げよ。事前準備が手順の結果を先取りしていないか。各ケースが単独で成立するか。
3. 判定IDの当て方が判定単位の文に合うか。
4. 確認方法が実行できるか（中継の記録で観測できないものを中継で見ようとしていないか。ECCUBEの管理画面に無い表示を見ようとしていないか。DBを直接見ているケースは、管理画面や中継で代えられないか）。
5. 設計書の表の行（条件・項目・ケース・エラー）のうち、結合テストの範囲に入るのにケースが無いもの。report.md の「書かなかった理由」が妥当か。逆に、結合テストの範囲でない（アプリ内で完結する）ケース。
6. 同じことを確かめている重複ケース。1ケースに期待結果が複数入っているもの。物理名（テーブル名・カラム名・クラス名・設定キー）の混入。

