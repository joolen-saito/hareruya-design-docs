## 判定単位（どれか1つに1ケースが対応する）

`integration_test/viewpoint_canonical/viewpoints_canonical.tsv` の次の行から選ぶ。文は必ず原文を読み、当てはまるものだけに使え。観点IDは判定IDに対応する観点ID列の値をそのまま書く。

| 判定ID | 使いどころ |
| --- | --- |
| IT-0215 | 正常応答のHTTPステータス、応答の形（JSON配列）、要素の項目名と値の型 |
| IT-0011 / IT-0010 | 指定したIDに紐づく個別入力商品だけが、取得元と同じ値で返る（該当分だけ返す、指定していない受注の分は返さない、値の再計算・丸めをしない、未設定の値の扱い） |
| IT-0216 / IT-0217 | 該当0件のときのHTTPステータスと0件表現（空配列） |
| IT-0224 | 認証トークンが欠落・不正・該当する管理者が無いときに、処理を行わず定められたHTTPステータスを返す |
| IT-0214 | 必須のリクエスト項目が欠落したときの扱い（根拠に定めがある場合だけ） |
| IT-0080 | 参照だけのAPIで、実行前後にデータが更新されない |

- 根拠の表の1行（項目1つ、条件1つ）ごとに当たる判定単位があるかを決め、あればケースにする。取りこぼさない。
- 返す順序は「定めていない」ので、順序を期待結果にしない。
- 許可IPによる制限など、根拠に「ある」とだけ書かれ、拒否時のふるまい（ステータスなど）が書かれていないものは、ケースにせず報告書に挙げる。

## ケースの書き方

- 1ケース1期待結果。期待結果は合否が一意に決まる具体値で書く。値は事前準備に書いた値から決まること。
- APIのパス・リクエスト項目名・レスポンス項目名（`ids`、`buyOrderIndivisualInputProductId`、`buyOrderId`、`name`、`price`、`count`、`saleFlg` など）は、根拠の表記のままバッククォートで囲んで書いてよい。それ以外で物理名（テーブル名・カラム名・クラス名）を書かない。
- 実行区分は `ブラウザのみ`（DBを直接見ない）か `ブラウザ+DB確認`。優先度は、値の一致・該当分だけ返す・認証を P1、型・0件・非更新を P2。
- 連鎖IDは空欄。

## 前提条件の規約（`integration_test/casegen/precond/README.md` の P1〜P13 を読め。要点）

- 各ケースは単独で成立する。状態を変えるデータはケース専用シード（シードID `S-A07-07-<名前>-<ケース番号3桁>`）、参照だけのマスタ・API試験条件・管理者は共有可。このAPIは参照だけなので、ケースごとのデータも「そのケースだけが使う」ならケース専用にする（各ケースはケース専用シードを1件以上使うこと）。
- ケース専用データの識別子（ネット買取受注ID、個別入力商品ID、商品名）は全機能で一意にする。機能IDとケース番号を織り込む（例: 受注ID `970707003`、商品名「個別A0707-003-A」）。英数字とハイフンの連なり1つ1つに機能とケース番号を入れる。共通のパスワード・共通の名称をケース専用シードに書かない（共有シードに置く）。`grep -r` で `integration_test/casegen/cases/` と重ならないことを確かめよ。
- 事前準備は必須。使用シードすべてについて状態を値付きで書き、シードIDを括弧で添える（「① …（S-…）／② …（S-…）」の形）。投入方法は何を使ってどう作るかを書く。
