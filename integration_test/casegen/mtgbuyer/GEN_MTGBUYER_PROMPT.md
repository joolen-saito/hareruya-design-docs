# MTGバイヤー（ネット買取・入庫モード）の結合テストケース作成（著者への依頼）

リポジトリ: `/home/y-saito/Developments/hareruya-design-docs/`。出力はすべて日本語で書く。
あなたは渡された機能ID（O01-02／O01-03 のどちらか1つ）のケースを書く著者である。レビューは別の担当が行う。

## 背景（依頼者決定 2026-10-06）

MTGバイヤーは店舗の買取端末で動くアプリ（Windows）で、ECCUBEとはAPIでつながる外部システムである。
「ネット買取」（O01-02）と「入庫モード」（O01-03）は現行踏襲で、Excelの基本設計にシートが無かったため結合テストケースが0件だった。
現行アプリのソースから機能設計書を起こしたので、それを根拠に、結合テスト観点に照らしてケースを書く。

- テスト対象は「現行のままのアプリ」と「刷新後のECCUBE」の間の連携である。期待値の正は現行アプリのふるまい（＝機能設計書）。
- ECCUBE側のAPI単体の検証（必須項目・認証・応答形式・DB更新の詳細）は A06・A07 の既存ケースが持っている。同じものを書かない。書くのは、アプリの操作を起点にして、アプリとECCUBE（またはアプリが出力するファイル）の間で値・状態が設計どおり受け渡されることである。
- アプリの中だけで完結する確認（並べ替え、ページ送り、絞り込み、小計の計算、カメラでのカード認識、色・見た目）は単体テストの範囲なので書かない（`integration_test/SCOPE.md` を読め）。

## ケースの書き方

- 1ケース1期待結果。期待結果は合否が一意に決まる具体値で書く（「正しいこと」「設計どおり」は不可）。値は事前準備に書いた値から決まること。
- 操作はMTGバイヤーの画面で行う。画面名・操作名は機能設計書の表記（業務選択画面、お客様選択画面（ネット買取）、査定画面、「査定完了」「査定を中断する」「お客様切り替え」「コメント更新」「CSV形式で出力する」など）をそのまま使う。
- カードを査定表・一覧へ足す操作は、カード名での検索を使う（カメラでの読み取りは使わない）。
- 確認方法は次のどれかにする。どれで確かめるかを手順の最後に書く。
  - アプリの画面に表示された値（一覧・査定表・メッセージ）
  - ECCUBEの管理画面（ネット買取の買取検索/一覧・買取情報編集）に表示された値。画面名は既存ケースの表記に合わせる
  - 通信の中継の記録（アプリとECCUBEの間に置き、要求と応答を記録する。送信内容＝メソッド・パス・項目・値・回数を確かめるとき、または「送らないこと」を確かめるとき）。中継は試験基盤として `S-<機能ID>-RELAY` の共有シードにし、事前準備に書く
  - 出力されたファイルの内容（文字コード・見出し行・列・値・行数）とファイル名、端末の査定途中・作業途中のデータの有無
- ECCUBEを止めた状態・エラー応答を返させる状態が要るケースは、中継で「該当の要求にHTTP 500を返す」「応答を返さない」のように、何をどうするかを事前準備に値付きで書く。
- APIのパスと送信項目名（`status`、`free_comment`、`order_status`、`order_details`、`product_class_id`、`ids` など）は連携の取り決めそのものなので、機能設計書の表記のままバッククォートで囲んで書いてよい。それ以外で物理名（テーブル名・カラム名・クラス名・関数名・設定キー）を書かない。ファイル名（`n{受注ID}.csv` など）もバッククォートで囲む。
- 画面文言の逐語照合だけを目的にしたケースは書かない。メッセージは、分岐（成功／失敗、続行／とどまる）を見分ける手がかりとして期待結果に使ってよい。そのとき文言は機能設計書の表示メッセージ表のとおりに書く。
- 金額・枚数は「事前準備で用意した値から決まる値」にする（例: 申込カードの枚数2・申込時買取価格300 → 査定表の枚数2・買取価格300）。設計書の外の計算規則を持ち込まない。
- 実行区分は `ブラウザのみ`（DBを直接見ない）か `ブラウザ+DB確認`（DBを直接見る）。この列はDBを直接見るかどうかの区分であり、アプリを操作するケースも同じ値を使う。DBを直接見るのは、管理画面でも中継の記録でも確かめられないときだけにする。
- 優先度は、状態の更新・査定完了の登録内容・出力ファイルの値と件数・利用できる店舗を P1、0件・失敗時の代替動作・ファイル名・削除の契機を P2 とする。
- 要求ID・連鎖IDは空欄にする（この機能群はExcel由来の要求表を持たない）。
- 出典は「<機能ID> 機能設計書 / <機能設計書の小見出し>」の形。小見出し（`###` の見出し、または `業務ロジック` `入出力` `表示メッセージ`）は実在するものだけ。複数のときは「、」で区切る。

## 前提条件の規約（`integration_test/casegen/precond/README.md` の P1〜P13 を読め。要点）

- 各ケースは単独で成立する。他のケースの結果に依存しない。
- 状態を変えるデータ（ネット買取の受注、査定途中のデータ、作業途中のデータ）はケース専用シードにする。シードIDは `S-<機能ID>-<名前>-<ケース番号3桁>`。共有できるのは参照だけのマスタ・環境設定・中継・ログイン利用者（状態を変えない場合）。
- ケース専用データの識別子（ネット買取受注ID、会員、商品ID、商品規格ID、商品コード、商品名、利用者のメンバーID）は全機能で一意にする。機能IDとケース番号を織り込む（例: 受注ID `90102003`、商品コード `O0102-003-A`、商品名「カードO0102-003-A」）。英数字とハイフンの連なり1つ1つに機能とケース番号を入れる（「O0102商品003」のように機能だけで切れる綴りは全ケースで重なる）。既存と重ならないことを `grep -r` で `integration_test/casegen/cases/` に対して確かめよ。
- 事前準備は必須。使用シードすべてについて、状態を値付きで書き、シードIDを括弧で添える（「① …（S-…）／② …（S-…）」の形）。
- 事前準備は手順より前に完結する。手順で決まる値（出力日時など）を期待結果で使うときは、手順の中で控える。
- 投入方法は、何を使ってどう作るか（ECCUBE管理画面のどの画面か／DB投入／ファイル保管先へ置く／端末の所定の場所へファイルを置く）を書く。
- 作り方が設計書から決まらない前提（中継、ファイル保管先の中身の確認方法、端末の査定途中データの置き場所、アプリの接続先の切り替え）は、シード表の投入方法に分かる範囲で書いたうえで、報告書の「試験環境に要るもの」に挙げる。

## 出力（この3ファイルだけを作る。ほかの既存ファイルは変更しない）

1. `integration_test/casegen/mtgbuyer/cases/<機能ID>_mb_test_cases.tsv`
   タブ区切り・12列: `テストID	判定ID	要求ID	連鎖ID	観点ID	優先度	実行区分	使用シード	事前準備	手順	期待結果	出典`
   テストIDは `IT-<機能ID>-001` からの連番で欠番なし。手順は「1. …／2. …」の形。セル内に改行・タブを入れない。
2. `integration_test/casegen/mtgbuyer/cases/<機能ID>_mb_seed_data.tsv`
   タブ区切り・7列: `シードID	区分	論理名	状態・属性	用途	投入方法	共有`（共有は `共有可` か `ケース専用`）
3. `integration_test/casegen/mtgbuyer/gen_<機能ID>/report.md`（70行以内）
   - 機能設計書の小見出し・表の行 → テストID の対応表（取りこぼしが無いことを示す）
   - 書かなかったものと理由（単体テストの範囲、判定単位が無い、設計書から期待値が決まらない、など）
   - 試験環境に要るもの

最後に `python3 integration_test/casegen/mtgbuyer/verify_mtgbuyer.py <機能ID>` を実行し、合格するまで直せ。
