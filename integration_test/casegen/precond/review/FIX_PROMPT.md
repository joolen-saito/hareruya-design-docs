## やること（指摘1件ごと）

1. **裏取り**: 指摘の「実際」に挙がった file:line を自分で読み、主張が正しいか確かめる。レビュアーも誤る。
   根拠は HTML設計書（`../../excel_to_html/output/`、機能↔シートは `../../functions/function-sheet-map.tsv`）、機能設計書（`../../functions/*/<機能ID小文字>_*.md`）、
   ee実装 `/home/y-saito/Developments/ec-cube-enterprise`（データの作り方の根拠。オラクルではない）
2. **扱いを決める**: `反映`（直す）／`却下`（指摘が誤り。理由を書く）／`未確定化`（作り方が設計書にも ee にも無い → 未確定の前提へ）
3. **直す**: 同じ種類の問題が同じ機能の他のケースにもあれば、それも直す（指摘箇所だけで終えない）

## 直してよいファイル（担当機能の分だけ）

- `cases/<機能ID>_test_cases.tsv` の **使用シード・事前準備・手順** 列
- `cases/<機能ID>_seed_data.tsv`（列: シードID/区分/論理名/状態・属性/用途/投入方法/共有）
- `precond/renames/<機能ID>.tsv`、`precond/step_changes/<機能ID>.tsv`（テストID/種別/新手順/理由）、`precond/readonly_cases/<機能ID>.tsv`
- 未確定の前提は `precond/open_add/<機能ID>.tsv` に書く（列: 対象/未確定の内容/影響ケース/手がかり）。**`precond/open_preconditions.tsv` は触らない**
- 扱いの記録は `precond/review/disposition/<機能ID>.tsv`（列: 指摘ID/扱い/理由/対応内容）

**TSV は Python の csv モジュール（delimiter='\t'）で読み書きする。** 手で置換してタブや改行を壊さない。

## 縛り

- **期待結果・要求ID・連鎖ID・観点ID・優先度・実行区分・出典は変えない。** 保留ケースは1文字も変えない
- 手順を変えたら step_changes に種別（準備移動/改名/発番値控え/データ指示/中継置換）と理由を書く。改名なら renames にも書く
- 手順で入力する値（登録する名称・コード）は改名しない（P13）
- 物理名（テーブル名・カラム名・環境変数・ルート名・翻訳キー）を書かない。画面名・業務名で書く
- 設計書に無い振る舞いを書かない。書くのはデータの状態と作り方だけ
- 一覧・検索・集計で「この N 件だけ」を期待するケースは、他ケースのデータが混ざっても成立する前提にする（検索条件をケース固有の値にする、または事前準備で対象外データが無い状態にする）。どうしても成立しないなら未確定化
- 他の機能のファイルは触らない
- **非同期処理（Webhook・バッチ・メッセージ処理）の完了を待つ手順が要る場合**、その種別はまだ承認されていない。既存の種別（中継置換など）を流用して手順を足さず、`precond/open_add/<機能ID>.tsv` に「非同期完了待ちが要る」と書いて未確定化する
- **1件しかない設定・レコード**（基本設定など）は共有可にし、使う各ケースの事前準備に「開始時に◯◯を△△に設定する」と値付きで書く
- **数値の改名**は、同じ数字が並び順・数量・価格として期待結果に出ていないか、ID順を期待するケースで改名後も大小が保たれるかを確かめる。改名は `precond/gate_precond.py` の `apply()` で機械的に当たる（「ID100」「F6102」の形も置き換わる）

## 終わりに

担当機能ごとに次を実行し、両方が OK になるまで直す。
```
python3 precond/gate_precond.py <機能ID>
python3 verify_cases.py <機能ID>
```
（G5 で他機能との識別子の重なりが出たら、自分の機能の側の名前を変えて解消する）

最後に、機能ごとに「指摘数・反映・却下・未確定化・同種で追加で直した件数・ゲート結果」を短く報告せよ。
