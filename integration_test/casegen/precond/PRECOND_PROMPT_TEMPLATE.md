# 依頼: {FID} の結合テストケースの前提条件を書き直す

これはレビューではなく**作成の依頼**である。あなたが書く。

## なぜ

いまのケースは上から順に実行すると成立しないものが多い。前提（どのデータがどういう状態か）がケースに書かれておらず、
状態を書き換えるデータを複数ケースで共有しているからである。例: あるケースが商品を2個販売すると、
同じ商品で「在庫10から8」を期待する次のケースが成立しない。
**各ケースを、他のケースを実行したかどうかに関係なく単独で成立させる。** そのためにケースごとに専用データを持たせる。

## 縛り

1. **期待結果は書かない。** 出力に期待結果の列は無い。期待結果は基線に改名を当てて機械で作る
1b. **シードの名前を変えただけでは専用にならない。** DB投入するレコードのID（例「ID 20の店舗」）もケースごとに別の値にする。あるケースが ID 20 を更新するなら、ID 20 を前提にする他のケースは順序次第で壊れる
1c. **1件しかない設定（基本設定など）や、ケースごとに分けられないデータ**は `共有可` にし、用途に「各ケースが開始時に必要な値を自分で設定する」と書く。そのうえで、使う各ケースの事前準備に「開始時に◯◯を△△に設定する」と値付きで書く。一覧画面の件数・並び順を期待するケースは、他ケースのデータが混ざっても判定できるよう、自ケースのデータだけで判定できる事前準備にする（混ざると判定できないなら未確定として報告）
2. **改名は識別子から識別子へだけ。** 商品ID・商品コード・会員メール・CSVファイル名・注文番号など、テストが用意するデータの名前に限る。
   新しい名前は `<旧>-<ケース番号3桁>` を基本にし、`ident_registry.tsv` の既存と重ねない
2b. **手順で入力する値（新規登録する名称・コード・英字名など）は改名しない。** 境界値や文字種の検査が壊れる。重複を避けるには事前準備に「その値のデータが無い状態にする（あれば削除する）」と書く。改名してよいのはシードが用意するデータの名前だけ
3. **手順は原則そのまま。** 変えてよいのは P8 の5種別だけ（準備移動／改名／発番値控え／データ指示／中継置換）。変えたら種別と理由を書く
3b. **期待結果を変えてよいのは類型 T1（外部発番値）だけ。** そのときは `新期待結果` 列に全文を書く。それ以外で期待結果を変えたくなったら、変えずに報告する
4. **事前準備は手順より前に完結させる。** 手順の結果（発番ID・返された値）を事前準備に書かない。「手順N」と書かない
5. **事前準備には使用シードのIDを全部書き、値を具体的に書く。** 期待結果の「AからB」「Aのまま」の A は事前準備に書く
6. **保留以外の各ケースはケース専用シードを1件以上使う**（読み取りだけのケースは出力5で宣言）。**状態を変えるデータは `ケース専用`。** 参照だけのマスタ、ロックさせない管理者アカウント、環境設定だけ `共有可`。
   ログイン失敗・ロックを試すケースの管理者アカウントは `ケース専用`
7. **設計書に無い振る舞いを書かない。** 書くのはデータの状態と作り方だけ。作り方は設計書に無ければ ee 実装から引いてよい。
   **物理名（テーブル名・カラム名・環境変数・ルート名・翻訳キー）は書かない。** 画面名・業務名で書く
8. **作り方がどちらにも無いときは推測で埋めない。** 未確定として報告する
9. **保留ケースは出力しない**（1文字も変えない）
10. 禁止語: 失敗させる／該当する操作を行う／同上／いくつか／別の画面

## 出力

コードブロックを5つ、この順で出す。TSV（タブ区切り）で、1行目は見出し。

1. `シード表` — 列 `シードID / 区分 / 論理名 / 状態・属性 / 用途 / 投入方法 / 共有`。基線のシードを置き換える全量を出す。ケース専用のシードIDは末尾をケース番号3桁にする
2. `ケース表` — 列 `テストID / 使用シード / 事前準備 / 新手順 / 手順変更種別 / 手順変更理由 / 新期待結果 / 期待結果変更理由`。保留以外の全ケース。`新手順` は手順を変えたときだけ全文を書き、変えないときは空。`新期待結果` は T1 のときだけ書く。事前準備は `① … ／② …` の形
3. `改名表` — 列 `テストID / 旧 / 新`。無ければ見出しだけ
4. `未確定の前提` — 列 `対象 / 未確定の内容 / 影響ケース / 手がかり`。無ければ見出しだけ
5. `読み取り専用ケース` — 列 `テストID / 理由`。どのデータの状態も変えず、ケース専用シードを使わないケースだけ。無ければ見出しだけ

最後に1行: `単独で成立しないまま残ったケース: <テストIDと理由、無ければ「なし」>`

- 一般論・方法論は書かない
- 基線の手順・期待結果が前提にしている状態を1つずつ洗い出してから書け。暗黙の前提（店舗、在庫場所、連携設定、既存の受注や取引、ステータス、日付、権限）を落とすな
