## 検証してほしいこと

### 1. 判定単位に合っているか（最重点）

判定単位の文は次のとおりである。ケースがこの文の範囲に収まっているかを1件ずつ判定せよ。

- IT-0334: 設計書でバッチの更新先と画面の取得元に対応付けられたデータが、バッチ更新後に**参照画面**へ設計どおり受け渡されること。
- IT-0335: **マスタ**を登録または更新した場合、参照側機能の**選択肢**に、対象の追加または変更が設計どおり反映されること。
- IT-0336: **マスタ**を削除した場合、参照側機能の**選択肢**から対象が設計どおり除外されること。
- IT-0337: **設定値**を変更した場合、その設定を参照する別機能の**挙動**が、変更後の設定値に応じて設計どおり切り替わること。

著者が判定単位を広げて使っている疑いがある。次を判定し、範囲外のケースはテストIDを挙げて「削除」または「別の判定IDへ付け替え」を示せ。

- 下流が画面でなくCSV出力・CSV取込・メール・別バッチであるケース（例: B06-02 の CSV、M03-14 の3組、M03-16、M03-20、M03-02 の L001・L002、M03-35 の L003）。
  CSVに出る値が取得元と同値であることは既存の IT-0071・IT-0083 が担う。
- 上流がマスタでも設定でもなく、商品・在庫などの個別データの編集であるケース（例: M03-02 商品編集、M03-38 商品公開CSV登録、M03-36 買取減額率変更CSV登録、M03-29・M03-35 の紐づけ更新）。
  商品1件の属性を「設定値」と呼んで IT-0337 を当ててよいか。
- 「選択肢」でなく、削除可否の判定や一覧の表示に当てているケース（例: M03-29、M03-35 の削除拒否）。

範囲外だが結合テストとして価値があり、判定単位の文を少し広げれば受けられるものがあれば、
どの判定単位をどう書き換えれば受けられるかを別枠で提案せよ（判定単位の変更は依頼者が決める）。

### 2. 期待結果の捏造・推測による接続

各ケースの期待結果の値・項目・挙動が上流と下流の設計書の記述から出るか。`gen_<機能ID>/report.md` の対応表の行番号を開いて確かめよ。
特に次を見よ。

- M03-36: 著者は「買取減額率の値の書式（パーセントか小数か）が設計書に無い」「取込ボタンの名称が設計書に無い」と報告しながら「70%」などと書いた。
- M03-29・M03-35: 期待結果にメッセージの文言が入っている。文言の逐語照合（e2eの担当）になっていないか。
- M03-17 は M03-02（商品編集）を下流に採用し、M03-29 の著者は M03-02 を「廃止（0204 識別ID 26）」として外した。どちらが正しいか。
- B06-01: 総原価10900・原価単価991などの具体値は別添資料の例と計算式から出したとある。設計書の記述どおりか。
- B13-01、B05-09、B08-02、B08-05、B08-03、B08-01、B08-06、B05-02 の各ケース。

### 3. 0件の機能の取りこぼし

0件にした機能（B05-03・B05-04・B05-05・B05-06・B13-02・M02-01・M03-34・M04-03）について、設計書の両側に記述があるのに落としている連携があれば挙げよ。件数を増やすための指摘はするな。

### 4. 手順が最後まで通るか／重複

上流の操作から下流の確認まで、入力値の検証・業務上の拒否条件・必須項目・関連データ・非同期の完了待ちに不足が無いか。
`integration_test/casegen/all_test_cases.tsv` の既存ケース、および `link/cases/` の他の連携ケースと同じ「上流操作→下流確認」の判定が無いか
（M03-14・M03-16・M03-37 は互いに近い。M03-18・M03-20・M03-35 も互いに近い）。

### 5. 依頼文の型と台帳

マスタ・設定の残り43機能と画面遷移の50機能へ広げる前に、`GEN_LINK_PROMPT_TEMPLATE.md`・`AGENT_BRIEF.md`・
台帳 `link_targets.tsv`（作成は `build_link_targets.py`）に直すべき点があれば挙げよ。
台帳は「mtb_ で始まる表を更新する管理画面機能」をマスタ・設定の上流として機械的に拾っており、
マスタでも設定でもない機能（M02-01、M04-03、M03-02 など）が混じっている。
