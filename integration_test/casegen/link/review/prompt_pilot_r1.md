## 検証してほしいこと

### 1. 期待結果の捏造（最重点）

10件それぞれについて、期待結果の値・項目・挙動が上流と下流の設計書の記述から出るかを確認せよ。
出典欄が指す箇所を実際に開き、そこに書いてあるかを見よ。設計書に無い項目・値・並び・件数を足していれば挙げよ。

### 2. 上流と下流を推測でつないでいないか

上流が登録・更新するデータと、下流が表示・選択肢化するデータが同じものだと設計書から言えるか。
特に次を判定せよ。

- IT-F06-01-L005: 著者は「お届け先」という語の一致で対応づけ、設計者の確認が要ると書いている。残すべきか外すべきか。
- IT-M14-10-L001・L005: 上流の「並び順」と下流の「表示順」を同じ項目と判断している。根拠は足りるか。
- IT-M14-10-L002・L003: 「商品検索条件に表示」を著者は実装に合わせて「チェックを付ける／外す」と書いた。設計書は「単一選択」としている。手順は設計書に従うべきである。どう書くべきか。

### 3. 既存ケースとの重複

著者は IT-M14-10-L001〜L003 が既存の IT-F03-03-015・016 と判定が重なると報告している。
既存ケースは下流の前提をシードで直接置いている。今回のケースは上流の操作を手順で実際に行う。
この違いがあっても同じ判定と言えるか。10件それぞれについて、上流・下流の既存ケースに
「上流の操作を手順で行い、下流で確かめる」ものが既にあれば、そのテストIDを挙げよ。

### 4. 0件の2機能は本当に0件か

- B05-01: 著者は「刷新後はバッチの役割がスマレジ用商品コードの採番と連携に変わり、それを参照する画面の記述が無い」として0件にした。
  設計書（`functions/*/b05-01_*.md` と 0405 のHTML設計書）で確認し、ケースにできる連携を見落としていないか判定せよ。
- F02-01: 著者は「商品一覧側に、引き継いだカードセットと検索語が検索条件のどの項目に設定されるかの記述が無い」として0件にした。
  `functions/*/f03-01_*.md` と 0303 のHTML設計書で確認せよ。

### 5. 採用した2機能の取りこぼし

F06-01 と M14-10 について、著者が「作らなかった候補」とした理由が正しいか。
設計書の両側に記述があるのにケースにしていない連携があれば挙げよ。件数を増やすための指摘はするな。

### 6. 前提条件と手順

各ケースが単独で成立するか。事前準備に無い状態を手順や期待結果が前提にしていないか。
手順が実行者に再現できる具体さか。物理名（テーブル名・カラム名・ルート名）が混じっていないか。
