## ケースにしなかったもの

| 記述 | 理由 |
| --- | --- |
| 出力 デッキユーザーID「未設定のときはnull」 | この分岐はデッキユーザーIDで検索するため、未設定（null）のプレイヤーは到達できず、確認手段が無い |
| 入力 デッキユーザーID「この分岐では必須」 | 未指定時の必須エラー応答は書かれていない。未指定は別分岐（A15-03）で結果が決まるため015でケース化した |
| 「呼び出せるのはデッキビルダーアプリだけ」 | アプリを識別する方法・拒否時の応答が書かれていない |
| 「金額・税・ポイント・在庫数量の再計算と丸めを行わない」 | この機能の出力に該当する値が無く、判定の対象が無い |
| 失敗時出力の処理結果コード | 記述が食い違うため011では確認しない（下記） |
| 削除済みプレイヤー、デッキユーザーIDの大文字小文字・前方一致 | 設計書に扱いが書かれておらず期待結果が決まらない |

## 設計書の不備として報告すべきもの

- A15-04 にエンドポイント（GET /user）、デッキユーザーIDのクエリ名、応答のキー名が書かれていない。エンドポイントは A15-01「以降の認可」、項目の存在は A15-03「入出力」から補った。キー名（code・user_name・profile・deck_user_id）は A15-03「出力: フィールド」に書かれているが、A15-04 の節には無く、検査（verify_nosheet.py）が自機能の節に無い名前を物理名として拒む（user_name・deck_user_id で不合格を確認）。このため004は項目の対応とスネークケースまでを期待結果にした。検査が他機能の節の項目名を許すなら、正確なキー名へ直せる。
- 要求表に行が無い記述: なし（sheet.txt の記述はすべて R001〜R017 に対応）。
- 記述の食い違い（裁定J）: 業務ロジックのエラー時の扱いは「メッセージ『Invalid request parameters』だけを返す」、入出力の失敗時出力は「処理結果コードとメッセージ『Invalid request parameters』」で、失敗応答に処理結果コードが含まれるか否かが一致しない。011は両方に共通するメッセージだけを確認する。
- 裁定待ち: 上記の食い違い。

## 試験環境に要るもの

- ee 実装のデッキユーザーIDは8文字以内のため、シードのIDは8文字にした。
- 007 はテスト用認証データ作成機構で顧客ID 15040072 の有効な認証トークンが要る（A15-13 と同じ方式）。009 の署名不正トークンは任意の文字列でよい。
- 013 のDB確認はプレイヤーの更新日時を直接参照できるDB接続が要る。
