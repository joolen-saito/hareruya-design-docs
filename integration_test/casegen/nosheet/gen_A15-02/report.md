## 判定単位の選び方

- IT-0182 は「HTTPステータスが応答されること」だけを受けるので、001 は HTTP 200 の確認に絞った。結果コード・結果メッセージ（002）、Cookie を空にする（003）、業務データを更新しない（008）は、受ける判定単位が観点表に無いので IT-0156 を使った。
- IT-0225（参照のみの機能は Cookie・セッションを更新しない）はログアウトが Cookie を空にするため矛盾し、使わなかった。
- 欠落・署名不正・署名方式違い・プレイヤー無しは、前提が欠落・不正なときの応答を受ける IT-0224 に当て、「ログアウトせず」を Cookie が空にされないことで確かめる（同一判定単位内）。
- IT-0218（未認証の利用者）は 004 のヘッダ欠落と同じ操作になるため別ケースにしなかった。

## ケースにしなかったもの

| 記述 | 理由（何が書かれていないから決まらないか） |
| --- | --- |
| 「すでに無効な状態に対する要求のふるまいは、既存の認証エラーまたは冪等な成功応答の実装に従う」（R011） | 認証エラーと成功応答のどちらかが決まらない |
| ログアウト後の旧トークン再利用（IT-0226） | 設計書は「トークンのCookieを空にする」とだけ書き、ヘッダのトークン自体を無効にするとは書いていない。R011 が無効状態への要求を実装に委ねており、旧トークンで保護対象APIを呼んだ結果が設計書から決まらない。IT-0226 の文を適用するには「ログアウトでトークンが失効する」という定めが要るが、この設計書には無い（レビュー指摘3は却下） |
| 「処理中の例外はデッキビルダーAPIの共通例外処理に委ねる」（R014 後半） | 中身が書かれていない |
| 失敗時（401）の結果コードの値 | ログアウトの設計書に値が無い。ケースは結果コードが含まれることだけを期待結果にした |
| リクエストボディに追加項目を付けた場合（IT-0183） | 結果が書かれていない |

## 設計書の不備として報告すること

- 失敗時の結果コードの値、トークンのCookie名、Cookieを「空にする」が値を空にするのか削除なのかが書かれていない（003 はトークン値が残らないことだけを確かめる）。
- ログアウト後に、ヘッダで渡したトークンが引き続き使えるのかが書かれていない（上記 IT-0226 の理由）。
- 要求表に行が無い記述は無い（R001〜R017 で足りた）。

## 試験環境に要るもの

- 試験用署名鍵「A15-02-JWT-KEY」の設定とセッション保存先（S-A15-02-ENV）。
- 署名方式と利用者IDを指定して署名済みアクセストークンを作る手段（S-A15-02-WRONGALG-006 の HS384 トークン、S-A15-02-NOPLAYER-007・S-A15-02-BADSIGNOPLAYER-009・S-A15-02-NOCHANGENOPLAYER-012 のプレイヤー無し会員のトークン。投入方法「未確定」）。現行のログインAPIはプレイヤーが無い会員を認証拒否するため、007 のトークンはログインで得られない。
- 受注とポイント残高を直接投入するフィクスチャ（S-A15-02-NOCHANGE-008・NOCHANGENOTOKEN-010・NOCHANGEBADSIG-011・NOCHANGENOPLAYER-012。投入方法「未確定」）。
