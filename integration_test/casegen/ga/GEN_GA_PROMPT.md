リポジトリ: `/home/y-saito/Developments/hareruya-design-docs/`。出力はすべて日本語で書く。
あなたは渡された機能ID（F10-01／F10-02／F10-03 のどれか1つ）のケースを書く著者である。レビューは別の担当が行う。

## 背景（依頼者決定 2026-10-06）

現行システムはアクセス解析（Googleアナリティクス）へ値を連携している。刷新後へ移植するので、結合テストで確かめる。

- 期待値の正は現行どおり。現行の挙動は機能設計書に起こしてある（下の「根拠」）。
- 連携は、画面がページ内の受け渡し領域（`dataLayer`）へ値を積み、タグの管理サービスがそれを読んでアクセス解析へ送る、の2段である。今回書くのは前段（受け渡し領域へ積むところまで）のケースである。後段（アクセス解析の受信）はタグの管理サービスの設定が手元に無く期待値を決められないので、今回は書かない。

## 根拠（これ以外を根拠にしない）

| 機能ID | 機能設計書 | HTML設計書での見出し（出典に書く名前） |
| --- | --- | --- |
| F10-01 | `functions/pf-eccube3/f10-01_front_analytics_customer_id.md` | 0310 フロント アクセス解析 / 会員IDの連携 |
| F10-02 | `functions/pf-eccube3/f10-02_front_analytics_purchase.md` | 0310 フロント アクセス解析 / 購入完了の売上連携 |
| F10-03 | `functions/pf-eccube3/f10-03_front_analytics_retargeting.md` | 0310 フロント アクセス解析 / 閲覧商品の連携 |

- 期待結果は、上の機能設計書の `## 業務ロジック` `## 入出力` に書いてあることだけから出す。`## 出典` 節（現行ソースの所在）は読まなくてよく、現行ソースを読んで期待値を足してはならない。
- 設計書に書いていないことは書かない。期待結果が設計書から出ないケースは作らない（保留ケースは作らない）。作れなかったものは報告書に理由を書く。
- 画面を開くまでの操作（ログイン、かごへ入れる、注文する）の手順と画面名は、その画面の機能の既存ケースに倣う。`integration_test/casegen/cases/` の次のファイルを見よ。買い物かご＝`F04-01`、ご注文方法指定〜購入完了＝`F04-04`、商品詳細・商品一覧＝`F03-*`、ログイン＝`F06-*`。画面名・ボタン名は既存ケースと同じ表記にする。

`integration_test/viewpoint_canonical/viewpoints_canonical.tsv` の次の5行。文は必ず原文を読め。

| 判定ID | 観点ID | 見るもの |

## ケースの書き方

- 1ケース1期待結果。期待結果は合否が一意に決まる具体値で書く（「正しいこと」「設計どおり」は不可）。値は事前準備に書いた値から決まること。
- 確認方法: 手順の最後を「ブラウザの開発者ツールのコンソールで受け渡し領域（`dataLayer`）の内容を表示する」とし、期待結果は「受け渡し領域に、項目名 `…` が値 … の要素が1件あること」のように、要素の項目名と値と件数で書く。タグの管理サービス自身が積む要素は対象にしないので、「項目名 `…` を持つ要素」で数える。
- 型の確認（IT-0341）は「値が文字列の `"00012345"` であること」「値が数値の 0 であること」のように、値と型を一緒に書く。
- 受け渡し領域の項目名（`uid`、`transactionId`、`gtm_cart_ids` など）は連携の取り決めそのものなので、設計書の表記のまま バッククォートで囲んで書く。それ以外で物理名（テーブル名・カラム名・ルート名・クラス名・翻訳キー）を書かない。
- 画面文言の逐語照合、見た目の確認はしない。
- 金額などは「事前準備で用意した値から計算できる値」にする（例: 単価500の商品を数量3 → 商品小計1500）。税や送料の計算規則を設計書の外から持ち込まない。必要な金額（商品小計、送料合計、かごの合計金額）は、事前準備で「受注の商品小計は1500、送料合計は600である」のように状態として直接書く。
- 実行区分は `ブラウザのみ`。優先度は、値の一致・積む条件・重複を P1、型・構造・0件・英語サイトを P2 とする。
- 要求ID・連鎖IDは空欄にする（この機能群はExcel由来の要求表を持たない）。
- 出典は「0310 フロント アクセス解析 / <機能名> / <機能設計書の小見出し>」の形。小見出しは実在するものだけ。

## 前提条件の規約（`integration_test/casegen/precond/README.md` の P1〜P13 を読め。要点）

- 各ケースは単独で成立する。他のケースの結果に依存しない。
- 状態を変えるデータ（会員のかご、受注）はケース専用シードにする。シードIDは `S-<機能ID>-<名前>-<ケース番号3桁>`。共有できるのは参照だけのマスタ・環境設定。
- ケース専用データの識別子（会員ID、メールアドレス、受注ID、商品ID、商品コード、商品名）は全機能で一意にする。機能IDとケース番号を織り込む（例: 商品コード `F1002-A-003`、メール `f1002-003@example.test`、会員ID・受注ID・商品IDは 9桁で `91002003` のように機能とケース番号を含める）。既存と重ならないことを `grep` で確かめよ。
- 事前準備は必須。使用シードすべてについて、状態を値付きで書き、シードIDを括弧で添える（「① …（S-…）／② …（S-…）」の形）。
- 事前準備は手順より前に完結する。手順で発番される値（受注IDなど）を期待結果で使うときは、手順の中で「購入完了画面に表示された受注番号を控える」のように控え、期待結果は「手順Nで控えた受注番号を8桁になるよう左を0で埋めた文字列」と照合する。ただし、購入処理中の受注を事前準備でID指定して用意する既存ケース（F04-04）の書き方に倣えるなら、固定値で書く方がよい。
- 投入方法は、何を使ってどう作るか（管理画面のどの画面か／DB投入）を書く。

## 出力（この3ファイルだけを作る。ほかの既存ファイルは変更しない）

1. `integration_test/casegen/ga/cases/<機能ID>_ga_test_cases.tsv`
   タブ区切り・12列: `テストID	判定ID	要求ID	連鎖ID	観点ID	優先度	実行区分	使用シード	事前準備	手順	期待結果	出典`
   テストIDは `IT-<機能ID>-001` からの連番で欠番なし。観点IDは判定IDの観点ID1つ。手順は「1. …／2. …」の形。セル内に改行・タブを入れない。
2. `integration_test/casegen/ga/cases/<機能ID>_ga_seed_data.tsv`
   タブ区切り・7列: `シードID	区分	論理名	状態・属性	用途	投入方法	共有`（共有は `共有可` か `ケース専用`）
3. `integration_test/casegen/ga/gen_<機能ID>/report.md`（60行以内）
   - 設計書の表の行 → テストID の対応表（取りこぼしが無いことを示す）
   - 書かなかったものと理由
   - 試験環境に要るもの（英語サイトの切り替え方法など、設計書からは作り方が決まらない前提）

最後に `python3 integration_test/casegen/ga/verify_ga.py <機能ID>` を実行し、合格するまで直せ。
