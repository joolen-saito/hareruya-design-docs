# レビュー指摘の反映（著者への依頼・R2）

`integration_test/casegen/ga/review/cases_r1_dispositions.md` の末尾2節（「R2」と「前提条件ゲートで出た分」）のうち、あなたの機能IDに当たるものをすべて反映せよ。指摘の原文は `review/cases_r2_findings.md`。

- 識別子の規則（全機能共通・重要）: シード表と事前準備に書く名称・コード・メールなどの値は、英数字・ハイフン・下線・ピリオド・@ の連なり1つ1つが、機能とケース番号を含むこと。日本語を挟むと連なりが切れる。「F1002商品001」は「F1002」と「001」に切れて全ケースで重なるので不可。「F1002-001-A」「商品F1003-038-X」のように書く。数字だけのID（会員ID・商品ID・受注IDなど）も、機能とケース番号を含む桁にして全シードで重ならないこと。
- 期待結果に「〜のまま」「AからB」を書かない（事前準備の値からの変化として機械検査される）。件数は「1件であること」と書く。1ケース1期待結果は守る。
- 直した結果、設計書から期待結果が出ない・前提を作る方法が既存ケースにも設計書にも無いと分かったものは、推測で埋めず、シードの投入方法に「未整備」と書かずにケースを削除して report.md に理由を残す。試験環境の用意が要るだけのもの（検索基盤へのデータ投入、撮影用画像、保存先、メール設定）は、共有可の環境シードとして状態と用意の仕方を書く。
- 削除・追加の後、テストIDを 001 からの連番に振り直し、ケース専用シードのID末尾と事前準備の参照も合わせる。
- 触ってよいのは、あなたの機能IDの `ga/cases/` の2ファイルと `ga/gen_<機能ID>/report.md` だけ。
- 最後に `python3 integration_test/casegen/ga/verify_ga.py <機能ID>` が合格するまで直す。

返答は3行以内: 件数、判定IDごとの内訳、削除・追加した件数、verify の結果。
