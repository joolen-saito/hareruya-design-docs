# 作り方が未確定で外したケースを、環境で戻せるか判定して書く（担当 {BATCH}: {NAMES}）

あなたは結合テストのシード（テストデータの作り方）を確定させる担当です。作業ディレクトリは `/home/y-saito/Developments/hareruya-design-docs`。

## 背景

作り方が決まっていないデータを使うケース 1,939件を、結合テストのケース一覧から外してある（2026-10-14。`integration_test/casegen/precond/README.md`「テストできない・作り方が未確定のケースの除外」）。外した理由は、シードの投入方法にある「未確定」「未整備」と、`integration_test/casegen/precond/open_preconditions.tsv`（未確定の前提）の行。

依頼者決定（2026-10-19）: **次の3つは試験環境で用意できる。**

| 用意できる | 中身 |
| --- | --- |
| バッチ | 試験環境でバッチを起動して実行させ、終わるのを待つ手段。バッチの実行設定（参照先・定期起動の設定など）を試験用に変えられる |
| 外部の試験環境 | スマレジなど外部システムの試験用の環境・アカウント。その管理画面や API でデータを作り、ECCUBE からの接続先にする。外部システムは本物のふるまいをする（こちらで応答を作り変えたり、止めたり、遅らせたりはできない） |
| メール | 試験環境が送るメールを受け取り、宛先・件名・本文を見られる受信箱 |

**次は用意しない**（同じ日の依頼者決定）: 中継・模擬応答（通信の記録・保留・転送、外部の応答の差し替え、エラー応答を返す仕組み）、時刻の固定、障害を起こす手段（DB の停止、タイムアウトなど）。

ほかの理由（値を指定してデータを入れる手段が無い、設計書に定めが無い・食い違う、他のケースのデータと分けられない、など）も、この決定では解消しない。

## 入力

- `integration_test/casegen/runnable/env/in/<名前>.tsv`: 外したケースを止めている項目。列は `種別	対象ID	列	今の文	状態・属性	止めているケース	手がかり`。
  - 種別「シード」: 投入方法に未確定・未整備があるシード。今の文はその投入方法。
  - 種別「前提」: 未確定の前提の行。今の文は「未確定の内容」、手がかりにその行の対象・手がかり・状態。
- `integration_test/casegen/runnable/env/in/<機能ID>_cases.tsv`: その機能の外したケースと、止めている項目の対象ID（ケースは止めている項目が**全部**解消したときだけ戻る）。
- 外したケースの中身: `integration_test/casegen/excluded_open_cases.tsv`（「元_」の列）。外したシードの全体: `integration_test/casegen/excluded_open_seeds.tsv`。
- 「未確定（未確定の前提を参照）」とだけ書いたシードは、同じ機能の前提の行（このファイルか `precond/open_preconditions.tsv`）に中身がある。
- 設計書の写し: `integration_test/casegen/datapattern/units/<機能ID>/design.txt`。無い機能は `integration_test/casegen/coverage_audit/units.tsv` で機能から書番・シートIDを引き、`coverage_audit/units/<書番>_<シートID>/sheet.txt`。
- 実装: `/home/y-saito/Developments/ec-cube-enterprise`（読むだけ）。
- 確定済みのシードの書き方の例: 「試験環境のメール配送設定で受信箱を指定する」「試験環境のバッチ設定、実行コンソール設定およびアプリケーション設定で行う」「試験環境の配備設定でスマレジ試験環境の接続先、契約情報および認証情報を設定する」。

## 判定

項目ごとに決める。

| 判定 | いつ |
| --- | --- |
| 環境で解消 | その項目の未確定・未整備の**すべて**が、上の3つ（バッチ・外部の試験環境・メール）を用意すれば決まる |
| 解消しない | 1つでも、用意しないもの（中継・模擬、時刻、障害）か、ほかの理由が残る |

区分の欄には、その項目の未確定の中身をすべて、次の語から選んで「・」でつなぐ: バッチ／外部の試験環境／メール／中継・模擬／時刻／障害／作り方／設計／分離／その他。
- 作り方: 値を指定してデータを入れる手段・画面が無い、実装上その状態を作れない、など
- 設計: 設計書に定めが無い・食い違う、期待結果が決まらない
- 分離: 他のケースのデータと分けられない、専用DB・初期化の手段が要る

迷うときの決め方:
- 外部システムに、正常な取引・商品・会員などのデータを作るだけなら「外部の試験環境」。外部にエラーを返させる、応答を止める・遅らせる、通信を記録して中身を確かめる、こちらから外部のふりをして送る、は「中継・模擬」。
- バッチの実行の手段・起動経路・接続先が決まっていないだけなら「バッチ」。バッチの対象になる「本番」「ステージング」の環境・クラウドの資源そのものを試験用に作る必要があるなら「その他」（用意できるのはバッチを動かす手段であって、本番相当の基盤ではない）。
- メールが届いたこと・本文を見るだけなら「メール」。送信の失敗を起こすのは「障害」。

## 環境で解消のときに書くこと

- シード: 新しい投入方法に、**未確定・未整備を残さない全文**を書く。どの環境の、どの画面・操作で、何の値を入れるかまで書く（「試験環境の〇〇で〇〇を設定する」「スマレジ試験環境の管理画面で、商品コード〇〇の商品を在庫10で登録する」「試験環境の受信箱で、宛先〇〇のメールを消してから始める」）。元の投入方法のうち未確定に関係しない部分は一字も変えない。状態・属性を変える必要があれば新しい状態・属性に全文を書く（要らなければ空）。
  - 商品を新しく作るなら、商品登録画面（新規）は使えない。`integration_test/casegen/product_csv/PROMPT.md` の決まりでグッズ商品CSV登録で作る（確認モーダルの確定、割引率、規格・在庫の作り方）。
  - ネット買取の申込みをするなら「ネット買取規約同意」にチェックし、モーダルの「申込み」を押す（F05-06 L0060・L0062〜L0066・L0108）。
  - バッチの書き方は用語の規約に従う（`integration_test/casegen/precond/README.md`「用語の置き換え」。バッチと書き、AWS の製品名や「非同期処理ダッシュボード」と書かない）。
  - 物理名（テーブル名・列名など）は書かない（`.cursor/skills/logical-naming/SKILL.md`）。呼び名〔…〕は消さない。
- 前提: 新しい投入方法の欄に「解消の書き方」を1〜2文で書く（何を用意すれば、その前提がどう満たされるか）。同じ中身のシードの行があれば、そのシードの書き方と食い違わないようにする。
- 根拠: 確かめた設計書の行・実装の箇所。

## 解消しないとき

新しい投入方法・新しい状態・属性は空。理由の欄に、残る未確定を具体的に書く（例「スマレジにエラー応答を返させる手段が要る（中継・模擬は用意しない）」）。

## 出力

`integration_test/casegen/runnable/env/out/<名前>.tsv`。タブ区切り・見出し付き・UTF-8。入力の項目を1行ずつ、漏れなく同じ順で。

`種別	対象ID	判定	区分	新しい投入方法	新しい状態・属性	根拠	理由`

- セルの中にタブと改行を入れない。書くときは Python で `"\t".join(...)` を使う（csv.writer は使わない）。

## 守ること

- 書いてよいのは `integration_test/casegen/runnable/env/out/` の担当のファイルと、作業用フォルダ `integration_test/casegen/runnable/work/{BATCH}/` だけ。ほかのファイルは読むだけ。
- **git の変更操作（add・commit・push・checkout・stash など）は一切しない。** 外部サービスへの書き込みもしない。
- 推測で「環境で解消」にしない。設計書と実装で、その状態が試験環境の操作で本当に作れることを確かめる。決めきれないものは「解消しない」にして理由を書く。
- 書き終えたら `python3 integration_test/casegen/runnable/gate.py env {NAMES}` を流し、不合格が無くなるまで直す。検査を通すためだけの文を足さない。検査が誤っていると思うときは、直さずに返答で知らせる。
- 返答は3行以内: ファイルごとの 環境で解消／解消しない の件数、gate の結果、知らせたいこと。
