# 書かれたとおりに実行できるようにする直し（担当 {BATCH}: {NAMES}）

あなたは結合テストのケースとシード（テストデータの作り方）を直す担当です。作業ディレクトリは `/home/y-saito/Developments/hareruya-design-docs`。

## 背景

結合テストケースの中に、書かれたとおりには実行できないものが残っている。人が実行するなら当然補う操作（決まった番号の読み替え、必須のチェック、確認モーダルの確定）や、画面では作れない状態を、ケースとシードに書き足す。

- 依頼者決定（2026-10-19「おすすめで進めて」）: 人が補って実行できるものはケースに書き足す。画面で作れない状態は、理由を添えて DB へ直接入れる書き方にしてよい（2026-10-09 の決まり。`integration_test/casegen/seed_screen/README.md`）。
- 刷新後は商品の新規登録が禁止（`integration_test/casegen/datapattern/units/M03-02/design.txt` L0075〜L0077）。商品はグッズ商品CSV登録（M03-27）で作る。決まりは `integration_test/casegen/product_csv/PROMPT.md` にすべて書いてある。項目「商品」の行を直す前に必ず読むこと。
- 画面が自動で振る番号（商品ID・管理者IDなど）は指定できない。登録したときに控えた番号を呼び名〔…〕で使う（類型T4。`integration_test/casegen/seed_screen/README.md` の「控えた番号の書き方」）。

## 入力

`integration_test/casegen/runnable/kept/in/<名前>.tsv`。列は `項目	種別	対象ID	列	今の文	使うケース	手がかり`。
- 種別がシードなら対象IDはシードID、列は「投入方法」か「状態・属性」。種別がケースなら対象IDはテストID、列は「事前準備」「手順」「期待結果」。
- 項目は、何を直すか（複数あればカンマ区切り）。機械で広めに拾ったので、直す必要の無い行も混ざっている。
- ケースとシードの全体: `integration_test/casegen/cases/<機能ID>_test_cases.tsv`・`<機能ID>_seed_data.tsv`。
- 設計書の写し: `integration_test/casegen/datapattern/units/<機能ID>/design.txt`（行頭の L0001 が行番号）。無い機能は `integration_test/casegen/coverage_audit/units.tsv` で機能から書番・シートIDを引き、`coverage_audit/units/<書番>_<シートID>/sheet.txt`。
- 実装: `/home/y-saito/Developments/ec-cube-enterprise`（読むだけ）。

## 項目ごとの直し方

### 商品（シードの投入方法）

商品登録画面（新規）で商品を作っているシード。`product_csv/PROMPT.md` の決まりで、グッズ商品CSV登録で作る書き方に直す。
手がかりに「product_csv で直せないとした理由」があるシードは、CSV と画面だけでは作れない状態がある。そこは画面で作れる部分を画面で作り、残りだけを DB へ直接設定する（「画面+DB」）。理由を投入方法の中に書く（例「（規格の販売種別を変える入力欄が無いため）」）。

- 販売種別: グッズ商品CSVの取り込みが規格に付ける販売種別を ee の実装で確かめる。シードが要る販売種別（「先頭の商品種別」「宅配便とゆうパックの両方が選べる販売種別」など）と同じなら CSV だけでよい（根拠に実装の箇所を書く）。違えば、取り込んだあと DB で規格の販売種別を直す。
- 規格が0件の商品: グッズ商品CSVで作ったあと、取り込みが作った規格と、それに付く行（在庫・価格の履歴など。ee の実装で何が作られるかを確かめる）を DB で消し、規格0件にする。
- 在庫を管理しない・在庫無制限の規格: CSV で作ったあと、DB で規格の在庫無制限・在庫の値を直す。
- 画面の入力チェックが通さない値（販売価格0円で買取価格1円など）: 通る値で作ったあと、DB で値を直す。
- 送料・手数料から価格を逆算する: シードとケースが使う配送方法・支払方法を確かめ、その送料・手数料の値をシード表か設定のシードから読んで販売価格を決める。値がどこにも無ければ「配送方法設定・支払方法設定の画面で〇〇の送料と〇〇の手数料を確かめ、合計が〇〇円になる販売価格（税込み）にする」と書く。
- 手がかりに理由が無い行（「商品の新規登録の操作が残っている」）: product_csv が「直さない」とした書き方（既存の商品の編集、すでに CSV で作っている）なら「直さない」にして理由を書く。

DB への直接設定は、業務名で書く（「DBで、この商品の規格の在庫無制限を有効にする」）。テーブル名・列名などの物理名は書かない（論理名規約 `.cursor/skills/logical-naming/SKILL.md`）。

### 控えた番号（F10-03・M13-02）

- シードの状態・属性: 固定の番号を消し、「<番号の名前>は登録時に画面が振る（控える。以下〔<番号の名前>-<機能IDのハイフン無し>-<ケース番号><枝>〕）」と書く。共有シードの呼び名は末尾を「共有」にする（例〔管理者ID-M1302-共有〕）。
- シードの投入方法: 登録したあと、どの画面のどこに表示された番号を控えるかを書き足す（設計書で画面と項目を確かめる。商品IDは商品マスター(検索結果)の行の商品ID、管理者IDはメンバー管理の一覧など）。
- ケース: 事前準備・手順・期待結果の固定の番号を呼び名に置き換える。**期待結果は番号を呼び名に置き換えるだけ**で、ほかの文は変えない。
- F10-03: 固定の商品ID（9100…）を、そのケースのシードが CSV で作る商品の呼び名に置き換える。期待結果が番号の大小・桁数・並び順そのものを確かめているなど、控えた番号では成り立たないケースは「直せない」にして理由を書く。
- M13-02: 管理者ID 1302 は画面のメンバー登録で指定できない（E2E で確かめた。`e2e/HANDOFF_codex.md` 4章の1）。S-M13-02-ADM で控える呼び名〔管理者ID-M1302-共有〕に置き換える。ログインIDなど、画面で入力する値は変えない。

### 割引率（シードの投入方法）

既存の商品を商品登録編集画面で編集して「商品を登録」を押すのに、割引率を選んでいない。編集では割引率が必須（`functions/pf-eccube3/m03-02_admin_product_product_edit.md` 17行目。グッズ商品CSVに割引率の列が無い）。「商品を登録」の前に「割引率を販売割引率に登録済みのものから選び」を書き足す。元のシードが割引率を指定していればその値。商品を編集していない（「商品を登録」が別の意味）なら「直さない」。

### 規約同意（シードの投入方法）

フロントのネット買取の申込み（F05-06）で、「ネット買取規約同意」のチェックと、申込みボタンで開くモーダルの「申込み」ボタンを書いていない（F05-06 L0060・L0062〜L0066・L0108。チェックが無いと画面遷移せずエラー）。お手本は `integration_test/casegen/datapattern/conflicts/rulings.tsv` の K03 の2つ目の置換:
「適格請求発行事業者の確認に「いいえ」を入れて「申込み」ボタンを押す。」⇒「適格請求発行事業者の確認に「いいえ」を入れ、「ネット買取規約同意」にチェックを入れて「申込み」ボタンを押し、表示されたモーダルの「申込み」ボタンを押す。」
ネット買取の申込みでないもの（店頭買取、イベントの申込み、DB で買取の受注を入れるだけ など）は「直さない」。

### 確認モーダル（シードの投入方法）

グッズ商品CSV登録の「CSVファイルのアップロード」は、押下後に確認モーダルを表示する（M03-27 L0092）。アップロードを押す操作のあとに「表示された確認モーダルでアップロードを確定する」を書き足す（この語句のとおりに書く）。グッズ商品CSV以外の CSV（カテゴリ登録CSVなど）は、その画面の設計書に確認モーダルがあるときだけ足す。

## 共通の決まり

- 直すのは、項目の部分だけ。ほかの文は一字も変えない（割引率・規約同意・確認モーダルは書き足しだけ）。
- 呼び名〔…〕を消さない・変えない（控えた番号の項目で新しく定義するものを除く）。
- 設計書に無い画面・項目・ボタン名を作らない。確かめた設計書の行（例 M03-27 L0092）か実装の箇所を根拠の欄に書く。
- ケースの期待結果を変えてよいのは、控えた番号の置き換えだけ。
- 元の文のほかの誤りに気づいても直さない。理由の欄に書く。

## 出力

`integration_test/casegen/runnable/kept/out/<名前>.tsv`。タブ区切り・見出し付き・UTF-8。入力の行を1行ずつ、漏れなく同じ順で。

`種別	対象ID	列	判定	新しい文	根拠	理由`

- 判定: 直す／直さない／直せない。
- 新しい文: 「直す」のときだけ、その列の**全文**（今の文を直したもの）。「直さない」「直せない」は空。
- 根拠: 確かめた設計書の行・実装の箇所。
- 理由: 直さない・直せないの理由、気づいた誤り。直さない・直せないのときは必須。
- セルの中にタブと改行を入れない。書くときは Python で `"\t".join(...)` を使う（csv.writer は使わない）。

## 守ること

- 書いてよいのは `integration_test/casegen/runnable/kept/out/` の担当のファイルと、作業用フォルダ `integration_test/casegen/runnable/work/{BATCH}/` だけ。ほかのファイルは読むだけ。
- **git の変更操作（add・commit・push・checkout・stash など）は一切しない。** 外部サービスへの書き込みもしない。
- 書き終えたら `python3 integration_test/casegen/runnable/gate.py kept {NAMES}` を流し、不合格が無くなるまで直す。検査を通すためだけの文を足さない。検査が誤っていると思うときは、直さずに返答で知らせる。
- 返答は3行以内: ファイルごとの 直す／直さない／直せない の件数、gate の結果、知らせたいこと。
