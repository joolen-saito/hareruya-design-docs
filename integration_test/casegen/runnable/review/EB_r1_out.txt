## 判定

項目ごとに決める。

| 判定 | いつ |
| --- | --- |
| 環境で解消 | その項目の未確定・未整備の**すべて**が、上の3つ（バッチ・外部の試験環境・メール）を用意すれば決まる |
| 解消しない | 1つでも、用意しないもの（中継・模擬、時刻、障害）か、ほかの理由が残る |

区分の欄には、その項目の未確定の中身をすべて、次の語から選んで「・」でつなぐ: バッチ／外部の試験環境／メール／中継・模擬／時刻／障害／作り方／設計／分離／その他。
- 作り方: 値を指定してデータを入れる手段・画面が無い、実装上その状態を作れない、など
- 設計: 設計書に定めが無い・食い違う、期待結果が決まらない
- 分離: 他のケースのデータと分けられない、専用DB・初期化の手段が要る

迷うときの決め方:
- 外部システムに、正常な取引・商品・会員などのデータを作るだけなら「外部の試験環境」。外部にエラーを返させる、応答を止める・遅らせる、通信を記録して中身を確かめる、こちらから外部のふりをして送る、は「中継・模擬」。
- バッチの実行の手段・起動経路・接続先が決まっていないだけなら「バッチ」。バッチの対象になる「本番」「ステージング」の環境・クラウドの資源そのものを試験用に作る必要があるなら「その他」（用意できるのはバッチを動かす手段であって、本番相当の基盤ではない）。
- メールが届いたこと・本文を見るだけなら「メール」。送信の失敗を起こすのは「障害」。

## 環境で解消のときに書くこと

- シード: 新しい投入方法に、**未確定・未整備を残さない全文**を書く。どの環境の、どの画面・操作で、何の値を入れるかまで書く（「試験環境の〇〇で〇〇を設定する」「スマレジ試験環境の管理画面で、商品コード〇〇の商品を在庫10で登録する」「試験環境の受信箱で、宛先〇〇のメールを消してから始める」）。元の投入方法のうち未確定に関係しない部分は一字も変えない。状態・属性を変える必要があれば新しい状態・属性に全文を書く（要らなければ空）。
  - 商品を新しく作るなら、商品登録画面（新規）は使えない。`integration_test/casegen/product_csv/PROMPT.md` の決まりでグッズ商品CSV登録で作る（確認モーダルの確定、割引率、規格・在庫の作り方）。
  - ネット買取の申込みをするなら「ネット買取規約同意」にチェックし、モーダルの「申込み」を押す（F05-06 L0060・L0062〜L0066・L0108）。
  - バッチの書き方は用語の規約に従う（`integration_test/casegen/precond/README.md`「用語の置き換え」。バッチと書き、AWS の製品名や「非同期処理ダッシュボード」と書かない）。
  - 物理名（テーブル名・列名など）は書かない（`.cursor/skills/logical-naming/SKILL.md`）。呼び名〔…〕は消さない。
- 前提: 新しい投入方法の欄に「解消の書き方」を1〜2文で書く（何を用意すれば、その前提がどう満たされるか）。同じ中身のシードの行があれば、そのシードの書き方と食い違わないようにする。
- 根拠: 確かめた設計書の行・実装の箇所。

## 解消しないとき

新しい投入方法・新しい状態・属性は空。理由の欄に、残る未確定を具体的に書く（例「スマレジにエラー応答を返させる手段が要る（中継・模擬は用意しない）」）。

## 出力

- セルの中にタブと改行を入れない。書くときは Python で `"\t".join(...)` を使う（csv.writer は使わない）。

## 守ること

- 書いてよいのは `integration_test/casegen/runnable/env/out/` の担当のファイルと、作業用フォルダ `integration_test/casegen/runnable/work/{BATCH}/` だけ。ほかのファイルは読むだけ。

# Agent Instructions

# 開発環境

- アプリの起動: `docker compose -f docker-compose.yml -f docker-compose.pgsql.yml -f docker-compose.dev.yml up -d --wait`
- ユーザーフロントURL: http://localhost:8080/ja
- 管理画面ログインURL: http://localhost:8080/admin/login
- 管理画面クレデンシャル: ID=admin PW=password
- データ投入: `docker compose exec ec-cube bin/console eccube:seed:card` && `docker compose exec ec-cube bin/console eccube:seed:product`
  - 商品シードはカードシード未投入だと外部キー制約違反になるため、上記の順で実行する。
- データベース接続: `docker compose -f docker-compose.yml -f docker-compose.pgsql.yml -f docker-compose.dev.yml exec -T -e PGPASSWORD=secret postgres_primary psql -U dbuser -d eccubedb`（サービス名指定で実行可能）。
- APP_DEBUG=1 のため管理画面には Symfony Web Debug Toolbar が表示される。
- Doctrineマイグレーションは、起動後に `docker compose -f docker-compose.yml -f docker-compose.pgsql.yml -f docker-compose.dev.yml exec -T ec-cube bin/console doctrine:migrations:migrate --no-interaction` で適用できる。
- Docker起動時にホスト側の`composer.json`および`composer.lock`がプラグイン設定により変更される場合がある。タスクと無関係な差分は検証後に`git checkout -- composer.json composer.lock`で戻してから差分確認する。

## フロントJS（イベント関連）

ハレルヤのフロント JS は TAM からビルド済みで納品されるが、**イベント関連
（`hareruya-event.js`）のみビルド前ソースを当リポジトリで管理している**。

- ソースとビルド設定: `frontend/hareruya/`
- ビルド: `cd frontend/hareruya && npm ci && npm run build`
  - 出力先は `html/template/default/assets/hareruya/js/hareruya-event.js`
  - **成果物はコミット対象**。ソースを変更したらビルドして一緒にコミットする
- 型検査: `cd frontend/hareruya && npm run typecheck`
- Node 22.12 以上が必須（rspack の要件）。`.nvmrc` / volta で 22.18.0 を固定している

リポジトリ直下の `gulpfile.js` / `webpack.config.js`（出力 `html/bundle`）は
EC-CUBE 本体のビルドであり、これとは無関係。Node のバージョン要件も異なるため
意図的に分離している。混ぜないこと。

`data-*` 属性と CSS クラス名は TAM のマークアップとの契約のため、変更せず追加のみとする。
詳細は `frontend/hareruya/README.md` を参照。

# コーディング規約
## Action クラス

- `src/Eccube/Service/**/*Action.php` の public メソッドは `handle()` のみとする（`__construct` を除く）。
- 複数の public メソッドを持たせない。Action は単一のユースケース入口であり、共通クラス化しない。
- 一覧の QueryBuilder 取得なども `handle()` の戻り値で表現する（例: `StockListSearchAction`）。
- 共通化が必要なロジックは Util・Repository・専用クラス等に切り出す。

# テスト実装と実行

- PHPUnit実行ファイルは `bin/phpunit` ではなくコンテナ内の `vendor/bin/phpunit`。例: `docker compose -f docker-compose.yml -f docker-compose.pgsql.yml -f docker-compose.dev.yml exec -T ec-cube vendor/bin/phpunit tests/Eccube/Tests/Web/Admin/Product/ProductControllerTest.php --filter 'testRoutingAdminProductProductNewGet|testProductRegistrationButtonTranslation'`
- 全てのユニットテストはクラスか各関数のいずれかに `@group HARERUYA` もしくは `#[Group(name: 'HARERUYA')]` アノテーションが必要。
- このチェックアウトではホストにPHPおよび`vendor/`が存在しないため、PHP構文確認・PHPUnit・PHP CS Fixerは`ec-cube`コンテナ内で実行する。起動後の公開ポートは管理画面を含むApacheが`8080`、Caddyが`8000`である。
- FormTypeのテストは、項目ごとにテストケースを分けるとsetUp実行によるテスト時間の増加に繋がりやすいため、`tests/Eccube/Tests/Form/Type/Admin/SearchProductTypeTest.php#L160` を参考にデータ駆動形式で検証する。
- テストの層は「変更したファイルの位置」ではなく「責務の所在」で決める。`src/Eccube/Service/**/*Action.php` のロジックは `tests/Eccube/Tests/Service/**` で検証し、Controller経由のリクエストで間接的に確認しない。
- Controller IT はカーネル起動・フィクスチャ投入・HTTP往復を伴い最も実行コストが高いため、ルーティング・権限・リダイレクト・Form→Actionの受け渡しなど、Controller自身の責務を検証する場合に限る。
- assert の根拠は変更差分ではなく仕様から取る。
- 各テストメソッドには、実装を読まなくても意図が分かるよう、次のフォーマットで PHPDoc コメントを記載すること。1行目は「対象 - 正常系/異常系」、2行目は期待する振る舞いを「〜こと」で書く。例: `tests/Eccube/Tests/Entity/DtbEventDetailHasFinishedTest.php`
```php
/**
 * hasFinished - 正常系
 * 開催日当日は開始時刻を過ぎても終了扱いにならないこと
 */
```

## 自動テストを追加するかの判断

「この変更が将来壊れたとき、振る舞いが変わるか、表示だけが変わるか」で決める。振る舞いが変わるなら自動テストを追加し、表示だけなら目視で確認して自動テストは追加しない。

| 変更の性質 | 検証手段 |
| --- | --- |
| 条件分岐・計算・状態遷移・クエリ条件・バリデーションのルール・権限・永続化 | 自動テストを追加する |
| CSV の列順・列数・キーとの対応、API 応答のキー構成 | 自動テストを追加する |
| twig 内の `{% if %}` / `{% for %}` などの分岐・計算 | 自動テストを追加する（可能な限り Action / Service 側で検証し、Controller IT にしない） |
| 表示文言のみ（`messages.*.yaml` の値、twig の静的文字列、ラベル・プレースホルダ・バリデーションメッセージの文面） | 自動テストを追加せず、目視で確認する |
| PHP 内の文言のみ（CSV 見出し文字列・メール件名・API のラベル文字列など、値の並びや対応は変えないもの） | 自動テストを追加せず、目視で確認する |
| CSS・レイアウトのみ | 自動テストを追加せず、目視で確認する |

自動テストを追加しない場合は、確認した画面（URL または操作）と確認結果を作業報告に書く。

### やらないこと

- 画面表示の文言確認を目的とした Controller IT の新規追加・拡張（「Controller IT は Controller 自身の責務を検証する場合に限る」の具体例）
- 既存テストの PHPDoc を書き換えて別目的の検証を相乗りさせること。既存テストの意図は変えない。同じクラスに新しいテストメソッドを追加するのは可

### 既存テストの維持

- 文言を変更したら `tests/` 配下を旧文言で grep し、fail する既存テストを洗い出す。
- fail する既存テストの修正は「テストの追加」ではなく必須の維持作業として行う。
- 修正は期待値の更新で行い、assert の削除はしない。削除してよいのは、その assert が検証していた文言自体が無くなった場合のみ。

## テスト粒度

以下の基準で選択すること：
- UT：ロジックが単体で完結しており、外部依存がない場合
- IT：DB・フレームワーク・外部依存が関わる場合
原則としてUTを優先するが、無理にモックを増やすことは禁止であり、その場合はITを選択すること

## テストの独立性

前提としてDBがクリーンな状態でテストされるようになっている。
ただし、シーケンスなどは継続されている。

## 保守性

実装変更に強く、過剰に内部実装に依存しないように実装すること。
