## なぜ見直すか

要因表は全機能で作り、codex の反証と直しまで済んでいる。担当によって扱いが割れた型が3つあり、依頼者が次のとおり決めた（2026-10-20）。
今の要因表を、この決定に合わせてそろえる。決定に関わらない所は変えない。

| 決定 | 中身 |
| --- | --- |
| 1 打ち切り側は1回でよい | その値（または値の組）になると処理がそこで打ち切られ、ほかの要因の値が結果に効かないとき（非公開で出さない、エラーで元の画面へ戻る、廃止済みで何も変えない、トークンが無効で拒否、0件で行を出さない など）、その条件を constraints.tsv に種別 `打ち切り` で書く。機械はその条件を1回だけ通し、ほかの要因との組は埋めない |
| 2 列ごとに独立して決まる値は組にしない | 出力の列・表示項目ごとに独立して決まる値（CSV の列が「値が無ければ空欄」、日付の書式、区分の文言への変換 など）は要因にしない。ほかの要因と効き合う（その値で、ほかの要因の結果や、行を出す・出さないが変わる）ときだけ残す |
| 3 結果が同じ値はまとめる | 設計書が別々の条件として書いていても、結果が同じ値は1つにまとめる（例: 仮会員と退会済み会員がどちらも対象外なら「仮会員または退会済み」）。条件を1つずつ通すのは 10/15 のデータパターンのケースの持ち分 |

## やること（機能ごと）

1. 直す前に `python3 integration_test/casegen/combination/gate_factors.py <機能ID>` を1回流し、行の数（前）を控える。
2. 決定1: 打ち切りに当たる値を探し、constraints.tsv に `処理ID	組	打ち切り	根拠	理由` で書く。根拠は打ち切りを定める設計書の行。
   - 打ち切られても一部の要因の値がまだ結果に効くとき（例: エラーの文言が言語で変わる）は、その要因の値も組に入れて値ごとに書く（`F01=非公開&F03=英語`）。
   - 打ち切りを表すために今までしていた回避は外す: 全行に値が要るために足した値（「呼ばない」「確認が出ない」など、ほかの要因で決まってしまう値）、打ち切りの値とほかの要因の組を全部並べた「作れない」制約。
   - 打ち切りの値を含む「効き合う」の判定は、そのままでよい（打ち切りの値の組は機械が埋めない）。ただし、打ち切りを理由に3つ以上をまとめた効き合うは、2要因の行に分けられるなら分ける。
3. 決定2: 列・表示項目ごとに独立して決まるだけの要因を外す。外して要因が1つになった処理は処理ごと外す（要因が1つだけの処理は挙げない）。外した要因・処理に関わる interactions・constraints・existing の行も外す。
4. 決定3: 結果が同じ値を1つにまとめる。値を変えたら constraints・existing の値も合わせる。
5. gate が合格するまで直す。**まだケースを書いていない機能なので、要因ID・値の振り直しはしてよい**。
6. 処置を `integration_test/casegen/combination/review/<機能ID>_factors_s_dispositions.tsv` に書く（タブ区切り・4列・見出し行あり: `決定	処置	理由	直した所`。決定は 1・2・3、処置は `直し`／`直しなし`）。3つとも当たる所が無ければ `-	直しなし	当たる所なし	` の1行。

書いてよいのは受け持ちの機能の `factors/<機能ID>_*.tsv` とその `_factors_s_dispositions.tsv`、スクラッチパッド（`/tmp/claude-1000/-home-y-saito-Developments-hareruya-design-docs/7ac77140-f212-4eb4-b04c-5cbd0cc6fcfa/scratchpad/` の下、名前に機能IDを入れる）だけ。`combos/` は gate が作り直す。`units/` は書き換えない。
