## 検証してほしいこと

1. **判定の誤り（最重点）**: 連鎖ごとの判定が設計書と既存ケースに照らして正しいか。
   - 「既存で確認済み」: 挙げた既存ケースが、本当にその契機を手順で起こし、遷移先の画面を期待結果で確かめているか。データの登録有無だけを見ているものを確認済みにしていないか。
   - 「連鎖ではない」: 出典の行を開き、別の機能の画面への遷移が本当に書かれていないか。遷移先の機能の取り違えで捨てていないか。
   - 「作れない」: 設計書か実装に、契機を試験で起こせる条件（関連データ、状態、入力値など）が書かれているのに作れないとしていないか。逆に「作成」で、起こす方法を著者が考え出していないか。
2. **期待結果の捏造・推測**: 遷移先の画面、メッセージの種類、引継データ（検索条件・ページ番号・表示件数、イベント詳細IDなど）が、出典と遷移元・遷移先の設計書に書かれているか。著者が補っていないか。出典の識別ID・節名を開いて確かめよ。
3. **重複**: 同じ契機を起こして同じ遷移先を確かめる既存ケースが、遷移元・遷移先の機能のケースにあれば、テストIDを挙げよ。
4. **手順が最後まで通るか**: 入力値の検証、業務上の拒否条件（権限、状態、関連データ）、画面を開く前提（管理者の権限、公開側の会員のログイン・店舗・言語）。事前準備に無い状態を手順や期待結果が前提にしていないか。刷新後に画面が無い（404）機能の画面でシードを作っていないか。
5. **規約**: ケースを置く機能の番号（遷移元、標準なら遷移先）、観点ID（ITA-20／エラー・入力不備は ITA-14,ITA-20／引継データも見るなら ITA-05,ITA-20）、各ケースが単独で成立するか、ケース専用データ、事前準備の値、シードを画面から作っているか、物理名（URLのパスを含む）を書いていないか、画面表示文言を逐語で照合していないか。
