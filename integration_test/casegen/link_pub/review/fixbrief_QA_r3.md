# レビュー3巡目の指摘の反映（群 QA）

codex の3巡目のレビュー指摘が `integration_test/casegen/link_pub/review/QA_r3_findings.md` にある。
3巡目は、2巡目の反映・合流前の置き換え（`fix_idents_log.tsv`）・手直しだけを見たレビューで、依頼文は `review/prompt_QA_r3.md`。
パスはすべて `/home/y-saito/Developments/hareruya-design-docs/` からの相対である。

1. **指摘を鵜呑みにしない。** 1件ずつ、指摘が挙げた file:line と、関係する設計書（機能設計書 `functions/*/<機能IDの小文字>_*.md`、HTML設計書 `excel_to_html/output/<ブック>_*.html`）を自分で開いて確かめ、採用／一部採用／却下を決める。
   レビュアーの修正案に書かれた語・値もそのまま採らず、設計書の表現で書く。レビュアーも誤る（存在しない記述を引く、範囲を取り違える）。
   期待結果の正否は設計書で決める。データの作り方（シードの投入方法）に限り、設計書に無い手順を実装（`/home/y-saito/Developments/ec-cube-enterprise` ほか）で確かめて書いてよい。そのときは report.md に「実装由来」と書く。
2. 採用した指摘はケース表 `cases/QA_test_cases.tsv`・シード表 `cases/QA_seed_data.tsv`・`gen_QA/report.md` を直す。直せない（設計書に根拠が無い）ケースは削除する。
3. **このケースは機能ごとのケースファイルへ合流済みである。番号を振り直すな。**
   - テストIDとケース専用シードIDの番号は変えない。ケースを削除したら、その番号は空けたままにする（詰めない）。削除したケースだけが使っていたシードも削除する。
   - ケースを足すのは、この群で既にレビューを通ったケースと同じ型（同じ上流の画面操作と同じ準備の作り方、同じ下流の画面の確かめ方の組合せ）に当てはめられるときだけ。足すケースの番号は、その機能のこの群の最大の番号（削除した番号を含む）の次。新しい型になるものは足さず、report.md に「作らなかった候補」として理由つきで書く。
   - 合流先（`integration_test/casegen/cases/`）は触るな。依頼元が `sync_pub.py` で当て直す。
4. **前提条件の検査 G5（ケース専用データの識別子が全機能で一意）を壊すな。** 検査の字句は `[A-Za-z0-9][A-Za-z0-9_.@\-]{3,}`。
   新しく書く名前・コード・メールアドレス・パスワードなどの英数字の語は、この群で既に使っている形（機能番号を含む形。例「M0326QB001」「qh0805-001@example.test」「Passw0rd-M0805QH」）にそろえる。パスワードに「!」を使わない。群の番号だけの語（例「QB001」「A002」）を単独で置かない。合流前の置き換えを元に戻さない。
5. 裁定を `integration_test/casegen/link_pub/review/QA_r3_dispositions.tsv` に書く。タブ区切り・ヘッダ付き:
   `指摘	裁定	確認した根拠	直したこと`（指摘は「指摘1」など。裁定は 採用／一部採用／却下。根拠は file:line。却下の理由は根拠の列に書く。直したことは、変えたテストID・シードID・削除・追加）
6. `gen_QA/report.md` の末尾に「レビュー3巡目の反映」の節を足す（件数の増減、削除・追加したケース、作らなかった候補）。報告書の表の記載漏れを指摘されたときは、その表を直す。
7. `python3 integration_test/casegen/link_pub/verify_pub.py QA` を合格させる。

触ってよいのは上の4ファイル（ケース表・シード表・report.md・裁定ファイル）と gen_QA/ の作業用ファイルだけ。他の群のファイルは読むだけにする。git の変更操作はしない。
ファイルの書き込みを拒否されたときは、回避せず、書くはずだった本文を返答に載せる（依頼元が保存する）。

返答は3行以内: 採用・一部採用・却下の件数、ケース数の増減（削除・追加したテストID）、verify の結果。
