## 検証してほしいこと

1. **期待結果の捏造・推測による接続（最重点）**: 上流側の設計書に、その操作が登録・更新する記述があるか。下流側の設計書に、その画面がその値を表示する（表示しない条件がある）記述があるか。両者が同じデータを指すと設計書から言えるか。著者が項目の対応・桁区切り・連結・初期値などを補っていないか。出典の識別ID・節名を開いて確かめよ。
2. **重複**: 同じ上流操作をして同じ下流画面を確かめる既存ケースが `all_test_cases.tsv` にあれば、テストIDを挙げよ。群の中での重複（項目違いで同じ判定を増やしている）も挙げよ。
3. **手順が最後まで通るか**: 入力値の検証、業務上の拒否条件（購入制限、ブラックリスト、状態、権限、期限）、公開側の前提（ログイン、店舗と言語、公開状態、カート）、反映に要る途中の処理（承認、検索の索引の更新、非同期処理・バッチ）と完了待ち、支払方法の前提。事前準備に無い状態を手順や期待結果が前提にしていないか。
4. **範囲**: 判定IDが範囲表に合っているか（IT-0150 に設定値の挙動切替〔IT-0337〕やマスタの選択肢〔IT-0335・0336〕を混ぜていないか、IT-0355 が別の実体を見ているか、下流が画面か）。IT-0150 の期待結果が操作の前後で表示が変わることを示しているか。ケースを置く機能の番号（上流、標準なら下流）。
5. **取りこぼし**: 著者が「作らなかった候補」とした組のうち、設計書の両側に記述があり既存ケースも無いのに落としたもの。手がかりに挙げた主な連携（群の依頼文の「手がかり」）が理由なく落ちていないか。
6. **前提条件の規約**: 各ケースが単独で成立するか、ケース専用データ、事前準備の値、シードを画面から作っているか（画面が振る番号を固定値にしていないか）、物理名を書いていないか。
