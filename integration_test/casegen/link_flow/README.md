# APIから画面・管理画面どうしの連携ケース（2026-10-16）

依頼者の指摘（2026-10-16）: 結合テストでは機能をまたぐ連鎖のケースが重要。分布として足りているか。

調べた結果（全11,654件）: 機能をまたぐケースは576件（4.9%）。画面遷移の連鎖（`../chains.tsv`）は機能をまたぐ遷移208本のうち186本（89%）にケースがあり足りていた。
足りないのは機能間のデータの受け渡しで、とくに次の2つは連携の候補台帳（`../link/link_targets.tsv`）の方向に入っていなかった。
- 外部の仕組み（店頭買取アプリ・スマレジ・デッキビルダー・PointGranter）から呼ばれる**APIが書き込んだデータを画面で見る**経路。ケース0件（A系のケースはAPIの応答かDBで止まる）。
- **管理画面どうしの業務データの受け渡し**（受注→出荷指示、在庫の承認→在庫履歴、買取のステータス変更→買取商品履歴、ポイント付与→ポイント履歴など）。観点表の IT-0340 はあったがケースは22件だけ。

依頼者決定（2026-10-16）: この2方向を足してケースを作る（「1から進めて」）。

観点表の変更（`../../viewpoint_canonical/build_canonical.py` の `ADD_LINK_API`）: IT-0364「API-画面 / 更新反映」（ITA-05）と IT-0365「API-画面 / 削除反映」（ITA-11）を末尾に足した。
既存の判定IDは動かしていない。codex で3巡レビューした（`../../viewpoint_canonical/review/prompt_link_flow_r1〜r3.md`、指摘の抜粋 `link_flow_r*_findings.md`、裁定 `link_flow_r*_dispositions.tsv`）。
- R1: 「責務の異なる画面」では範囲が決まらない → 更新先と取得元の対応で決める。削除は表示・非表示の出し分けなので IT-0365 に分けた。
- R2: 更新のたびに明細を削除して登録し直すAPI（店頭買取情報更新）がある → 更新の中の削除・再登録を IT-0365 から除いた。
- R3: 要求に含めなかった明細は削除されたままになる → 除くのは「同じ対象が最終的に登録し直される場合の途中の削除」だけにした。

管理画面どうしは既存の IT-0340 で受けた（観点表は変えていない）。

| ファイル | 内容 |
| --- | --- |
| `groups.tsv` | 著者に割り振る群（A*: API→画面 5群、R*: 管理画面→別の参照画面 10群）。上流機能は群の間で重ならない |
| `PROMPT_TEMPLATE.md`／`make_prompts.py` | 著者への依頼文。`gen_<群>/prompt.md` を作る（`../link_pub/` の型を元に、判定IDの範囲・APIの呼び出し方を書き換えた） |
| `cases/<群>_test_cases.tsv`・`_seed_data.tsv` | 著者の成果物（14列。判定ID・上流機能・下流機能の列あり） |
| `gen_<群>/report.md` | 著者の報告（組ごとの評価、対応表、重複の確認、到達可能性、作らなかった候補、設計書の不備）と、レビューの反映の節 |
| `verify_flow.py` | 機械検査（`../link_pub/verify_pub.py` を元に、方向の検査だけを替えた） |
| `REVIEW_TEMPLATE.md`／`make_review.py`／`review.sh`／`extract_findings.py`／`FIX_BRIEF.md` | codex レビューの依頼文・実行・指摘の取り出し・反映の依頼文。出力は `review/` |
| `merge_flow.py`／`merged_map.tsv` | 機能ごとのケースファイル（`../cases/`）への合流と、旧テストID→新テストIDの対応（判定ID・上流・下流つき） |

- テストIDは合流前が `IT-<機能ID>-<群><3桁>`、合流後は機能ごとの連番の続き。ケースを置く機能は上流機能（上流が標準機能のときは下流機能）。
- 著者は sonnet（1群1本）、レビューは codex。報告書を書き込めなかった著者の分は、返答の本文を依頼元が保存した（報告書の末尾に注記）。

## 結果（2026-10-16）

- 15群の著者（sonnet）→ codex レビュー3巡（1巡目＝全体、2巡目＝反映と追加、3巡目＝2巡目の反映・追加と合流前の置き換えだけ）。裁定は `review/<群>_r<巡>_dispositions.tsv`、反映は各 `gen_<群>/report.md` の末尾。
  2巡目以降に足せるのは既にレビューを通った型だけにし、直し切れない前提を抱えるケースは削除した。
- 合流前に `fix_idents.py` で、前提条件の検査 G5（ケース専用データの識別子の一意性）に掛かる書き方を機械的に直した（パスワード「Passw0rd!X」→「Passw0rd-X」、共有データの名前の「機能番号＋群」の語を機能IDの形に分ける、群 AC の商品名「…03/04/05」→「…甲/乙/丙」）。
  手で直したもの: 群 AB の会員のパスワードを末尾にシードの番号を付けた形に、群 AE のフォーマット名(英)を半角の別名に、群 RF の申込者の姓を空白の無い名前に。記録は `fix_idents_log.tsv`。
- 合流（`merge_flow.py --apply`）: **123件・53機能**（上流×下流の組105）。IT-0364 27件、IT-0340 96件。新設したケースファイルは M04-29。全体は 11,654件 → **11,777件・347機能**。
  - API→画面: AA 4（スマレジ連携→在庫）、AB 10（店頭買取アプリ→店頭買取の管理画面・マイページ）、AC 9（ネット買取→ネット買取の管理画面・マイページ）、AD 0、AE 4（デッキ更新→大会デッキ登録・デッキ編集）
  - 管理画面どうし: RA 11・RB 10（商品→価格履歴・在庫・受注・買取）、RC 15・RD 17（在庫の承認・棚卸・移動・分割→在庫履歴・在庫一覧・商品規格一覧）、RE 8（受注→受注一覧・在庫履歴・ポイント・メール履歴）、RF 5・RG 5（買取→在庫・買取商品履歴・集計）、RH 8（会員→ポイント履歴・メール履歴・買取・イベント）、RI 9（イベント→申込）、RJ 8（カード・デッキ→商品・アーキタイプ）
- 合流のあと `../seed_screen/apply.py` → `../datapattern/conflicts/apply_rulings.py` → `../exclude_open.py` → `../exclude_scope.py` → `../build_all_test_cases.py` → `../precond/gate_precond.py --all` 合格。足したケースは除外に掛かっていない。
- 0件・削除が多かった群: AD（注文印刷）は、刷新後に商品の新規登録画面が無く（404）、受注に使う商品を画面から作れないため0件。AA のスマレジ受信（A05-04）5件は Webhook 受信の認証情報が未確定（`../precond/open_preconditions.tsv`）なので削除。AE のデッキの新規登録・インポート登録は、APIが登録するデッキの種別が設計書に無いので0件。
- 実機では1件も流していない。設計書の不備として著者が報告したもの（用語の不一致、別添資料と画面の食い違い、ステータス表示名の食い違いなど）は各 `gen_<群>/report.md` の「設計書の不備」。
