## 検証してほしいこと

1. **期待結果の捏造・推測による接続（最重点）**: 上流側の設計書に、その操作（APIの呼び出し・管理画面の操作）が登録・更新・削除する記述があるか。下流側の設計書に、その画面がその値を表示する（表示しない条件がある）記述があるか。両者が同じデータを指すと設計書から言えるか。著者が項目の対応・桁区切り・連結・初期値などを補っていないか。出典の識別ID・節名を開いて確かめよ。
2. **重複**: 同じ上流操作をして同じ下流画面を確かめる既存ケースが `all_test_cases.tsv` にあれば、テストIDを挙げよ。群の中での重複（項目違いで同じ判定を増やしている）も挙げよ。
3. **手順が最後まで通るか**: 入力値の検証、業務上の拒否条件（権限、状態、ブラックリスト、在庫不足、期限）、下流の画面を開く前提（管理者の権限、検索条件、店舗）、反映に要る途中の処理（承認、確定、非同期処理・バッチ・キャッシュ）と完了待ち。IT-0364 はAPIの呼び出し方が、そのAPIの既存ケース（`cases/<APIの機能ID>_test_cases.tsv`）の形に合っているか、認証の前提が満たされているか。事前準備に無い状態を手順や期待結果が前提にしていないか。
4. **範囲**: 判定IDが依頼文の範囲表に合っているか。IT-0340 に同じ機能群の編集画面と一覧画面の間の再表示、公開側・バッチ・マスタの選択肢・設定値の挙動・画面遷移の引継ぎを混ぜていないか。IT-0364 でAPIの応答や、APIを呼び出した仕組みの側の画面（店頭買取アプリ、デッキビルダー）を下流にしていないか。下流が画面か。期待結果が操作の前後で表示が変わることを示しているか。ケースを置く機能の番号（上流、標準なら下流）。
5. **取りこぼし**: 著者が「作らなかった候補」とした組のうち、設計書の両側に記述があり既存ケースも無いのに落としたもの。手がかりに挙げた主な連携（群の依頼文の「手がかり」）が理由なく落ちていないか。
6. **前提条件の規約**: 各ケースが単独で成立するか、ケース専用データ、事前準備の値、シードを画面から作っているか（画面が振る番号を固定値にしていないか）、物理名を書いていないか。
