## 背景

結合テストケースのシード表には、テストデータの状態と「投入方法（何を使ってどう作るか）」が書いてある。
{FID} のシードのうち、投入方法に「未確定」「未整備」と書かれたもの（作り方が設計書から分からなかったもの）を、実装を読んで確定させる。

依頼者の前提: **テストデータは、実際には画面から入力して作る。** だから、画面（管理画面・フロント画面）で作れるものは画面操作で書く。画面で作れないものだけ、ほかの手段にする。

## 1件ずつ、未確定の内容を調べて次のどれかに決める

| 判定 | いつ | 新しい投入方法に書くもの |
| --- | --- | --- |
| 確定 | 作り方が、設計書または実装を読んで事実として分かった | 試験者がそのまま実行できる作り方。画面で作れる部分は「<画面名>で<項目>に<値>を入れて<ボタン>を押す」の粒度。画面で作れない部分だけ、その手段（下の優先順）を書く。「未確定」「未整備」の語を含めない |
| 環境の決定待ち | 作り方が実装に無く、試験環境をどう作るかを決めないと定まらない（時刻の固定、外部システムの模擬・中継、障害の起こし方、バッチの起動経路、本番・ステージングの代わりの接続先 など） | 分かった部分は確定の粒度で書き、決まっていない部分を「未確定: <誰が何を決めれば確定するか>」と1つずつ書く |
| 作れない | 実装を読むと、その状態は作りようがない（その項目・機能が実装に無い、制約で登録できない） | 「未確定: <なぜ作れないか>」。ケース側の見直しが要る旨を備考に書く |

手段の優先順（上が優先）:
1. 管理画面・フロント画面の操作（その画面と入力項目が実装に実在することを確かめる）
2. 画面からのCSV取込・ファイルアップロード
3. 実装に用意されているコマンド・管理用の機能（キャッシュの消去、バッチの手動実行 など。実在を確かめる）
4. DBへの直接投入（画面では作れない値のときだけ。過去の日時、内部のID、画面に入力欄が無い項目、不整合な状態、大量データ など。**なぜ画面で作れないかを必ず添える**）
5. 試験用のストレージ・メール受信箱・外部システムの試験環境の管理画面

決まり:
- 推測で埋めない。「確定」にするのは、根拠（設計書の単位と行、または実装の file:line）を示せるものだけ。
- 新しい投入方法には物理名（テーブル名・カラム名・クラス名・ルート名・翻訳キー・環境変数名・キャッシュのキー名）を書かない。画面名・項目名・ボタン名・設計書に出てくる名前で書く。コマンドは「キャッシュを消去する管理コマンド」のように役割で書き、実際の名前は根拠欄に書く。
- 秘密情報（パスワード・鍵・トークンの実値）を書かない。
- 状態・属性（どんなデータか）は変えない。変えないと作れないときは「作れない」とし、備考に書く。
- 同じ未確定事項を複数のシードが持つときも、1シード1行で全部書く（投入方法はシードごとに完結させる。「同上」「共有シードの未確定に従う」と書かない）。

## 出力

`integration_test/casegen/seed_resolve/out/{FID}.tsv`（ヘッダつきタブ区切り・セル内に改行とタブを入れない・対象の全シードを1行ずつ）

```
シードID	判定	新しい投入方法	根拠	備考
```

- 根拠: 設計書の単位と行、実装の file:line（物理名はここに書いてよい）。
- 備考: 環境の決定待ちなら「決める人の候補と、決める内容の選択肢」。作れないならケース側の見直し案。無ければ空欄。

返答は、判定ごとの件数と、環境の決定待ちの内容を種類ごとに1行ずつ。
