# 結合テスト実行方針の決定（26,188件／4人／3か月）

> 作成: 2026-07-21 ／ 根拠: codex 反復レビュー＋台帳実測（trace接続後の確定値）＋適用述語パイロット
> 位置づけ: **実行方法の決定は確定**（§2〜§4）。要員・期間の充足は発注者判断が要る（§5）。

## 決定サマリ（先に）

1. **母数26,188件は削らない**（網羅台帳）。圧縮は「実行方法」で行う。
2. **各ケースの実行方法を機械確定した**（下表・全26,188件に付与済み・`all_it_cases.tsv`の`実行方法`列）。
3. **手段は自動生成優先**（台帳→spec機械生成）。手書きは破綻する。
4. **4人3か月では、全数を品質維持で完了できない**（§4）。不足は要員・期間・スコープの
   契約判断で埋める。**2週間の較正スパイクで実測し、事前合意した閾値で自動発動**する（§5）。

## 1. 実行方法の確定内訳（全26,188件・trace接続済み）

区分の基準は「駆動できるか」でなく**期待値をGUI上で観測して合否判定できるか**（GUI観測モデル）。

| 実行方法 | 件数 | 割合 | 意味 |
|---|---:|---:|---|
| **Playwright** | 12,283 | 46.9% | GUIで駆動・GUIで判定。完全自動 |
| **Playwright+手動確認** | 7,098 | 27.1% | GUIで駆動、判定にDB等を併用（pf/ee桁数・暗号化・履歴はGUIに出ない） |
| **非UI（API/バッチ）** | 5,550 | 21.2% | 入り口がGUIでない。API駆動・CLIで自動化 |
| **手動** | 1,257 | 4.8% | 実決済3DS・並行競合・帳票目視。GUIで再現/観測できない |

- **Playwright系（GUI駆動）= 19,381件（74%）／純手動 = 1,257件（4.8%）／非UI = 5,550件（21.2%）**
- 付与は生成器由来の trace（ケースID×観点No、一意）を唯一の入力とする。逆引きは使わない
  （187キー中55衝突・67%該当・行順で反転するため）。多軸台帳は `execution_assignment.tsv`。

### 「自動化可能」と「今すぐ自動実行できる」は別
上表の実行方法は**到達目標**であって現状の実行可能性ではない。以下は現時点で人手・準備が要る：
- 実決済サンドボックス依存: 409件（決済連携観点）
- VRT初回ベースライン承認: 1,787件相当（人が視覚基準を承認）
- 障害注入が要る: 1,179件（外部連携・並行・タイムアウト）
- 必須観測層が GUI+DB の両層アサート: 6,819件（pf/ee差ゆえForm層だけでは不合格を検出できない）

## 2. 聖域（全数実行必須・サンプリング禁止）＝3,115件

**優先度で聖域を決めない。** 実測で聖域3,115件のうち**P3が321件**（ロールバック256含む）。
「P3は後回し」を機械適用すると原子性の中核が黙って落ちる。聖域の定義キーは
「原子性/競合のIT-ID（IT-06/07/08/33）∪ 上位ドメイン（決済・在庫・注文・買取・認証・状態遷移・
外部連携・ポイント・金額計算・通知）∪ RISK観点No.517-528」。**P1/P2/P3を問わず全数**。

## 3. 手段（4本柱）

- **L1 台帳→spec機械生成（最重要）**: 手書きPlaywrightは1件0.5–2hで24,931件＝300人日超で破綻。
  既存生成器資産を使い台帳から機械生成（行単位assert・シードバンド割当）。これが不成立なら全体が不成立。
- **L2 データ駆動**: ユニーク観点174・構造反復が支配的。共有fixture・並列化で圧縮。
  **行単位のassert・行単位のレポートは維持**（スイート単位pass/failは観測力喪失で不可）。
- **L3 下層functional検証**: DB/バリデーションはWebTestCaseで高速・低flaky。GUI+DB両層6,819件は両層アサート必須。
- **L4 リスク層別**: 聖域3,115は全数。非聖域P2は同値＋ペアワイズ代表、失敗時は同値クラス全数へ自動昇格。

## 4. 工数（作業パッケージ別・人日／ケース数の足し算はしない）

4人×3か月＝約240人日。工数はケース数でなく**作業パッケージの人時**で見積る（codex指摘）。

| 作業パッケージ | 内容 | 概算人日 | 性質 |
|---|---|---:|---|
| WP1 自動生成基盤 | 台帳→spec生成・シード/フレッシュDB/専用アカウント・外部I/F仮想化 | 50–70 | 一括（初期） |
| WP2 自動実行運用 | CI実行・flaky triage・失敗一次切分け・再実行・証跡レビュー（自動24,931件） | 40–70 | 日次（期間全体） |
| WP3 手動実行 | 純手動1,257＋VRT初回承認＋実決済サンドボックス確認 | 55–80 | 期間全体。決済のリード時間が律速 |
| WP4 聖域承認・証跡 | 聖域3,115件（P1/P2/P3全数）の結果承認・エビデンス保全 | 25–40 | 期間全体 |
| WP5 不具合再テスト | 不良率5–10%での修正確認・回帰 | 20–35 | 期間全体 |
| **合計** | | **190–295** | vs 予算 **240** |

**結論: 楽観側（190人日）なら240以内、保守側（295人日）で約55人日超過。** 律速は
WP1の完成時期（遅れると聖域が全数手動へ流れ10倍化）と決済サンドボックスのリード時間。
**単一の確定値は出せない**。範囲で提示し、スパイクで収束させる。

## 5. 要決定（発注者・§4の振れ幅を埋める）

**2週間の較正スパイク（4人＝約40人日、WP1の先行着手）**を実施し、次を実測する:
自動化到達率／1ケール当たりauthoring時間／flaky率／決済サンドボックスの調達リードタイム。

スパイク完了時（Day10）に、**事前合意した閾値で自動的に**以下を発動:

| 実測結果 | 発動する決定 |
|---|---|
| 残工数 ≤ 残予算（約200人日）に収まる | 現体制で続行 |
| 超過 15人日以内 | **(B) +2〜3週の期間延長** |
| 超過 15〜50人日 | **(A) +1名 投入** |
| 超過 50人日超 | **(A)+1名 かつ (C) 非聖域P2代表のスコープ縮小を発注者と合意**（聖域は縮小不可） |

**(C)の品質定義**: 非聖域P2のみ同値クラス＋ペアワイズで代表選定。サンプル内失敗は
当該同値クラス全数へ自動昇格。聖域3,115・純手動の決済・在庫競合は縮小対象外。

## 6. 品質の担保（不可侵・完了扱いにできない領域）

削ってはいけない／代表画面の成功で「合格」にしてはいけない:
- 決済金額・請求・返金・取消の整合、二重課金/二重返金防止、失敗時ロールバック
- 在庫の競合・負在庫（1点物の超売り）、引当の解放漏れ
- 注文・買取の状態遷移（不正遷移拒否）、外部I/Fの重複・順序逆転・再送・部分失敗
- **認証・セッション・CSRF・権限昇格防止**、店舗/顧客間のデータ分離（認可境界だけでは不足）
- **個人情報・決済情報・トークンのログ/通知/CSVへの漏えい抑止**
- 税・端数・割引・ポイント・返金の金額整合、監査証跡・履歴の完全性、失敗時の可観測性
- CSV/バッチの部分成功・再実行・冪等性・リカバリ、DB更新と通知の原子性（Outbox）
- ブラウザ差・モバイル・アクセシビリティをVRTだけで代替しない

**未仕様の重要リスクは、仕様決定または明示的なリリース受容が完了するまで「完了」扱いにしない。**
特に No.518（超売り）は仕様未確定の13機能・後勝ち懸念の5機能について合格オラクルが未定義であり、
`ESCALATION_oversell_risk.md` の業務判断が済むまで No.518 は全数実行と呼んでも合否不能。
