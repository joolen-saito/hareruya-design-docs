# 【業務エスカレーション】在庫の同時競合（超売り）に関する設計の空白

> 作成: 2026-07-21 ／ 起点: 結合テスト観点 No.518（在庫の同時競合）の設計書証拠判定
> 分類: **テスト設計より上位の業務仕様判断**（テストを整えても仕様が空白なら守れない）

## 1. これは何か

トレカECは**在庫1点（同一カードの特定コンディション）の商品が大半**である。
複数の経路（フロント購入・管理画面の在庫編集・POS〈スマレジ〉同期）が同一在庫を
**同時に**更新したとき、確定引当が二重成立して**在庫が負値になる＝同じ現物カードが
二重販売される（超売り）**リスクがある。

結合テスト観点 No.518 で全機能を設計書証拠で判定した結果、**このリスクに対する
仕様が「決まっていない」機能が実在**することが分かった。これはテスト不足ではなく、
**設計の空白**である。実装がどう振る舞っても「仕様違反」と言えないため、
テストの合否基準すら定義できない。

## 2. 実測（在庫を更新する23機能の内訳）

| 状態 | 機能数 | 意味 |
|---|---:|---|
| 競合仕様が明記 | 10 | 挙動が決まっている＝テストで検証できる |
| **競合仕様が沈黙** | **13** | **挙動が未定義＝超売りが起きても仕様違反と言えない** |

| M04-22 | 新規実装 | 在庫移動・振替 CSV登録 |

| M04-32 | 新規実装 | 承認一覧 |

### 2-2. 競合仕様が「後勝ち／ロックなし」と明記されている機能（別種の要確認）

競合仕様は書かれているが、その内容が**在庫に対して後勝ち（last-write-wins）を許容**
しているもの。受注フィールドの後勝ちは許容可能でも、**在庫数に後勝ちが波及すると
超売りになる**ため、意図の確認が要る：

| 機能 | 区分 | 設計書の記述（実抜粋） |
|---|---|---|
| F04-04 | 現行踏襲 | 「楽観ロック・悲観ロックの対象は持たないが、受注ステータスを完了確定の前提条件として用いる」 |
| M05-14 | 標準 | 「本操作に固有の悲観ロック取得は持たず、受注ステータス遷移に伴う在庫処理側のロックは購入フローの設計を正とする」 |
| A06-03 | カスタマイズ | 「楽観ロック・悲観ロックの対象は持たず、同一受注への同時更新は後勝ちとなる」 |
| M07-03 | カスタマイズ | 「同時編集は後勝ちに近い通常ORM更新となる」 |
| O01-01 | カスタマイズ | 「同一受注を複数の利用者・APIが同時に更新した場合、後から保存された内容が残る」 |

**特に F04-04（フロント購入完了）** はロックを持たず、在庫確保を「受注ステータスを
前提条件として用いる」に留めている。この経路が M04-02/M04-03（管理画面の在庫編集）や
A01-01（POS同期）と**同時**に走ったとき、在庫が負にならない保証が設計書にない。

### 2-3. 競合仕様がきちんと定義されている機能（参考・テスト対象）

排他制御を明示しており、そのまま結合テストで検証できる：

- M04-02 在庫編集「廃棄は登録時点で在庫をロック（即時減算）」
- M04-21 在庫変更CSV登録「商品コードから規格を更新ロックして取得」
- M04-31 棚卸計画「棚卸計画の排他ロック取得に失敗（＝ロックを取る設計）」
- B05-02 購入完了再処理「二重実行を避けるためロックを取得」

## 3. 想定される事故シナリオ（在庫1点の現物カード）

1. 顧客Aがフロントで残1のカードを購入（F04-04、在庫ロックなし）
2. ほぼ同時に、店舗スタッフが管理画面で同カードの在庫を編集（M04-03）
   ／またはPOS販売がスマレジ同期で在庫を減算（A01-01）
3. 双方が「在庫1」を前提に確定 → 在庫が0または負に、**同じ現物が二重に売れる**
4. 一方の顧客に商品が渡せず、返金・謝罪・信用毀損。トレカは代替在庫が無い（1点物）

## 4. 業務側にお願いしたい判断

テスト設計では埋められない。以下を**仕様として確定**いただきたい：

1. **在庫更新の同時実行ポリシー**を決める
   - 悲観ロック（`SELECT FOR UPDATE`）で直列化するか
   - 在庫の負値をDB制約で禁止し、超過時はエラーにするか
   - 「後勝ち」を許容する範囲（受注メタは可・在庫数は不可、等）を明示するか
2. 上記を**2-1の13機能・2-2の5機能に反映**する（特に新規実装6件は先に）
3. 決定後、No.518は「根拠付きの並行テスト（決定論的な同時購入シナリオ）」として
   結合テスト母集合に投入可能になる（PostgreSQLのSELECT FOR UPDATE／直列化異常を
   突く形で自動化できる）
