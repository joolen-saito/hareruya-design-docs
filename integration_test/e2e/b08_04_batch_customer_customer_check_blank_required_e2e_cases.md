種別: batch（`dtb_customer` から必須項目が空欄の会員を抽出し、該当が1件以上あれば管理者の通知先へアラートメールを送信するコンソールバッチ。画面を伴わない機能仕様）。期待結果はバッチ終了ステータス・標準出力（開始/完了・エラー）・通知メールの送信有無など、API/統合レイヤ（コマンド起動）および手動（メール実送信観測）で観測できる結果で判定する。**期待結果は仕様（正本md・観点表）由来**とし、実装の現挙動・終了コード実値・出力メッセージ文言・抽出SQLの対象列・メール本文/件名/宛先の編集内容をオラクル化しない（オラクル独立性）。pf-eccube3リバース＝基本設計・観点表を上位オラクルとし、乖離は付帯表4に出す。TSV は既存IT casesの10列に実施管理欄（実施者・実施日・結果・失敗理由）を加えた14列固定。E2E固有情報（コマンド/根拠・自動化区分・仕様根拠・シード・不具合候補）は TSV 後の付帯表に `テストID` で対応づける。Playwright は本リポジトリでは実行しない（構造参考のみ）。未確定の判定・閾値・内部挙動は `要実機確認`。

## 起動口（コンソールコマンド）の特定状況：実装済み（コマンド実在）

本機能の起動口は刷新先 `ec-cube-enterprise` に実装済みであることを `#[AsCommand]` の grep で確認した。

- コマンド名（刷新先・実在）: `eccube:customer:check-blank-required-item`（`src/Eccube/Command/CheckBlankRequiredItemCustomerCommand.php:25`、`#[AsCommand(name: 'eccube:customer:check-blank-required-item', description: '必須項目空欄会員通知バッチ')]`）。引数は取らない。
- 処理本体: `Eccube\Service\Admin\Customer\CheckBlankRequiredItemCustomerAction::handle()`（`src/Eccube/Service/Admin/Customer/CheckBlankRequiredItemCustomerAction.php:31`）。`CustomerRepository::getBlankRequiredItemCustomers()`（`src/Eccube/Repository/CustomerRepository.php:640`）で空欄会員を抽出し、`MailService::sendBlankRequiredItemCustomerAlertMail()`（`src/Eccube/Service/MailService.php:1264`）で管理者へ通知する。
- なお正本md（現行 pf-eccube3 リバース）はコマンド名を `customer:batch checkBlankRequiredItemCustomer` と記すが、刷新先の実在コマンド名は `eccube:customer:check-blank-required-item` で異なる（移行差異・付帯表4-1）。E2Eの起動コマンド名は刷新先の実在根拠で確定し、終了コード実値・出力文言は期待値にしない。
- Playwright の `request` ではコンソールバッチを直接起動できない（起動口は実機/シェル依存）。区分は `E2E自動化(API/統合)` とし、コマンド名は実在根拠で確定する一方、spec では `bin/console` 実行が実機依存のため `test.fixme`（理由付き）で残す前提とする。
- アラートメールの**送信有無**は正本mdが規定する観測対象だが、実送信は外部SMTP経由で本リポジトリから観測できないため `手動`（要実機確認・mailcatcher等）に分類する。メールの**本文・件名・宛先・ヘッダ**は正本md「本書で扱わないこと」によりメール設定・テンプレート管理を正とする＝別機能委譲で `対象外`。
