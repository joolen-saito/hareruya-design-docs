### 自動化区分と spec 実行実態の対応（網羅マトリクスの「カバー」の内訳）

本表・付帯表1の「E2E自動化」は**自動化区分（計画）**であり、spec での実行可否とは別概念である。破壊的（DB登録/更新/削除）・要実機確認のケースは `spec` で `test.fixme`（未実行＝計画）として保持し、誤った成功を避ける。両者の対応は以下。

- spec で実行（非破壊・資格情報/シードがあれば実走）: **001, 002, 011, 020, 022, 030, 033, 040**
- spec で `test.fixme`（破壊的/要実機＝未実行・計画）: **010, 012, 013, 014, 021, 023, 031, 032**
- 手動のみ（ケース表で全量管理・spec には残さない＝規約）: **050（CSRFネガティブ送信）, 060（同時更新・2セッション）**

したがってマトリクスの「カバー」のうち 010/012/013/014/021/023/031/032 は「自動化計画済み・未実行」、050/060 は「手動（spec化しない）」を意味し、実行済みの保証ではない。本監査で追加した 033（削除キャンセル）は非破壊のため実行ケースとして spec に実装した。
