種別: batch（ポイント履歴から二重登録されているものを検知し、該当があれば対象の注文番号を添えて管理者へ通知メールを送信するコンソールバッチ。画面を伴わない機能仕様）。期待結果はバッチ終了ステータス・標準出力（開始/完了・エラーメッセージ）・通知メール送信有無など、API/統合レイヤ（コマンド起動）で観測できる結果で判定する。**期待結果は仕様（正本md・観点表）由来**とし、実装の現挙動・終了コード実値・出力メッセージ文言・重複判定SQLの内部条件・メール本文/宛先をオラクル化しない（オラクル独立性）。pf-eccube3リバース＝基本設計・観点表を上位オラクルとし、乖離は付帯表4に出す。TSV は既存IT casesの10列に実施管理欄（実施者・実施日・結果・失敗理由）を加えた14列固定。E2E固有情報（コマンド/根拠・自動化区分・仕様根拠・シード・不具合候補）は TSV 後の付帯表に `テストID` で対応づける。Playwright は本リポジトリでは実行しない（構造参考のみ）。未確定の判定・閾値・内部挙動は `要実機確認`。

## 起動口（コンソールコマンド）の特定状況：正典コマンド名で確定（実装は別名で実在・乖離）

本機能の起動口は **正典（正本md）が定義するコマンド名 `order:batch checkDuplicatePoint`（正本md L63／L71）** を期待の基準とする。これと対応する実装は刷新先 `ec-cube-enterprise` に存在することを `#[AsCommand]` の grep で確認したが、実装のコマンド名は正典と異なる（乖離は付帯表4-6に明示）。

- **正典のコマンド名（期待の基準）**: `order:batch checkDuplicatePoint`（正本md「利用者視点の入口」L63／処理フロー見出し L71）。引数は取らない。期待値・操作手順はこの正典名を基準とする。
- 対応する実装（正典差分・実装名を「正しい」と断定しない）: `eccube:check-duplicate-point`（`src/Eccube/Command/CheckDuplicatePointCommand.php:34`、`#[AsCommand(name: 'eccube:check-duplicate-point', description: 'ポイント二重登録チェックバッチ')]`、docブロックに「ポイント二重登録チェックバッチ（B05-06）」と明記）。実装が実在することは根拠であるが、コマンド名が正典 `order:batch checkDuplicatePoint` と乖離する点は付帯表4-6で要確認とし、実装名を期待値の「正しいコマンド名」とはしない。
- 検知・通知本体: `Eccube\Service\Admin\Order\CheckDuplicatePointAction::handle()`（`src/Eccube/Service/Admin/Order/CheckDuplicatePointAction.php:37`）。`DtbPointHistoryRepository::findDuplicatePoint()`（同Repository.php:219）で二重登録の受注IDを取得し、`OrderUtil::getOrderNumbers()`（`src/Eccube/Util/OrderUtil.php:33`）で注文番号を特定、`MailService::sendOrderDuplicateNotificationMail()`（`src/Eccube/Service/MailService.php:2231`）で管理者へ通知する。
- ただし Playwright の `request` ではコンソールバッチを直接起動できない（起動口は実機/シェル依存）。区分は `E2E自動化(API/統合)` とし、期待値・操作手順のコマンド名は正典 `order:batch checkDuplicatePoint` を基準とする一方（実装名 `eccube:check-duplicate-point` との乖離は付帯表4-6）、spec では `bin/console` 実行が実機依存のため `test.fixme`（理由付き）で残す前提とする（コマンド未特定ではなく起動手段依存）。
- 通知メールの本文・件名・宛先・実受信は、本機能の正本md「本書で扱わないこと」（メール設定・テンプレート管理を正とする）により**別機能委譲**であり、実メール送信の成否・内容は `手動`／`対象外`（理由付き）に分類する。
