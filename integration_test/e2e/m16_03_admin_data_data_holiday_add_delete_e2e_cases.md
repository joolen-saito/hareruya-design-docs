**実行対象と期待値の切り分け（オラクル独立性の明確化／codexレビュー反映）**: 本設計書は現行 pf-eccube3（HareruyaEc プラグイン）のリバースだが、E2E が実際に走行する唯一の対象は刷新先 ec-cube-enterprise（コア提供）である。両者は**ルートパス（仕様 `/{admin_route}/holiday`・`/holiday/add`・`/holiday/{id}/delete` ↔ 実装 `/{admin}/data/holiday`・追加は一覧ルート統合・削除は HTTP DELETE）／メッセージ鍵（仕様 `hareruyaec.holiday.overlap`・`admin.delete.complete` ↔ 実装 `admin.data.holiday.overlap`・`admin.common.delete_complete`）／フォーム名（仕様 `hareruyaec_holiday_add` ↔ 実装 getBlockPrefix `holiday_add`）／トグル要素・タイトル**に構造乖離がある。これらは**不具合候補（仕様乖離）として付帯表4に `要確認` で全件分離**する。期待値の方針は次のとおり: (a) 観測する**表示テキスト**（重複「入力した日付が…重複しています。」等）と**ふるまい**（保存しない・一覧へリダイレクト・403 等）は仕様由来のため、メッセージ鍵が乖離していても文言が一致する限りオラクルとして妥当。(b) URLアサーション・トグルDOM id・フォーム名は**走行対象（ec-cube-enterprise）に存在する値**を用いる。仕様パス（`/holiday` 等）は走行対象に存在せず、これを期待値にすると全ケースが到達不能で落ちるため採らない。仕様パスとの不一致は走行ではなく**付帯表4の照合（要確認）で検出**する。テストを実装の挙動（Form制約値・Cookie名）へ寄せて固定することはしない。
