# A17-01（記事単一検索） E2Eテストケース

元設計md（正本一次）: `functions/pf-api/a17-01_api_other_article_search_single.md`
機能詳細HTML: `function_spec_html_preview/pf-api/a17-01_api_other_article_search_single.html`

テスト観点: `integration_test/integration-test-viewpoints.md` ／ 既存IT: `integration_test/a17_01_api_other_article_search_single_it_cases.md`（母集合 計38観点行）

本機能は画面を伴わない機能仕様（WP投稿ID（`wpPostId`）に一致する記事情報を1件返すJSON API・GET参照系）であり、**両レイヤで網羅**する。本APIはブラウザ向け画面を持たず（正本md「対象はJSON APIエンドポイントであり、ブラウザ向けの画面を持たない」）、結果が管理画面に現れる範囲も無いため、**UIレイヤ＝0、API/統合レイヤ中心**で分類する。API/統合レイヤ＝Playwright `request`（APIRequestContext）でエンドポイントへGET送信し、HTTPステータス・レスポンスのフィールド構成／型契約・データ整合・該当なし時の404で判定する。

**期待結果は仕様（設計書・観点表・基本設計）由来**とし、実装のレスポンス形・型・キー綴り・HTTPライブラリ既定値を期待値に流用しない（オラクル独立性）。pf-apiの正本mdは現行（旧システム）のリバース設計であり、刷新先 ec-cube-enterprise との乖離（エンドポイントパス・404本文形・応答フィールド名のケース〔camelCase⇔snake_case〕・論理削除除外・認可方式）は**設計書/観点表を上位オラクル**として扱い、付帯表4（不具合候補／要確認）に出す。実装からは位置情報（APIパス・メソッド・認可属性・404発火位置）のみを `file:line` 根拠で取得し、取れないものは `要実機確認`。送信先パスは実装の実効パス `GET /article.json`（`ArticleController.php:45`／App配下はprefixなし `routes.yaml:5-7`）に統一し（テストが実在経路へ届くため）、合否は設計書の意味（正常取得＝記事情報JSON＋200／該当なし＝404／不正・特殊文字 `wpPostId` は正しい記事が取得されない＝正常取得200とならない）で判定する。仕様で固定される404は該当なし時のみであり、必須欠落・型不正・特殊文字時の具体ステータス（400/404等）は要実機確認とする。設計⇔実装のパス・本文・フィールド名の差異は付帯表4でのみ一元管理し、TSV期待値に実装の現挙動を固定しない。TSV は既存IT casesの10列に実施管理欄（実施者・実施日・結果・失敗理由）を加えた14列固定。Playwright は本リポジトリでは実行しない（構造参考のみ）。
