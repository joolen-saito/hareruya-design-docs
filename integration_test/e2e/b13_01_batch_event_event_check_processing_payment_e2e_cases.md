種別: batch（申込みステータスが設定時間以上「決済中」のイベント申込を抽出し、決済サービスへ取引照会して、結果に応じてステータス更新・記録除去（論理削除）・申込履歴記録を行い、想定外エラーは管理者へ通知するコンソールバッチ。画面を伴わない機能仕様）。期待結果はバッチ終了ステータス（正常終了／異常終了の扱い）・実行結果（処理の扱い）・申込みステータス整合の扱い・管理者通知の有無など、API/統合レイヤ（コマンド起動）で観測できる結果で判定する。**期待結果は仕様（正本md・観点表）由来**とし、実装の現挙動・終了コード実値・件数出力文言・申込ステータスの内部値・SP.LINKS実装挙動・HTTPライブラリ既定値をオラクル化しない（オラクル独立性）。pf-eccube3リバース＝基本設計・観点表を上位オラクルとし、乖離は付帯表4に出す。TSV は既存IT casesの10列に実施管理欄（実施者・実施日・結果・失敗理由）を加えた14列固定。E2E固有情報（コマンド/根拠・自動化区分・仕様根拠・シード・不具合候補）は TSV 後の付帯表に `テストID` で対応づける。Playwright は本リポジトリでは実行しない（構造参考のみ）。未確定の判定・閾値・内部挙動・SP.LINKS照会結果は `要実機確認`。

## 起動口（コンソールコマンド）の特定状況：実装済み（コマンド実在）

本機能の起動口は刷新先 `ec-cube-enterprise` に実装済みであることを `#[AsCommand]` の grep で確認した。

- コマンド名: `eccube:payment-status-check`（`src/Eccube/Command/PaymentStatusCheckCommand.php:35`、`#[AsCommand(name: 'eccube:payment-status-check', description: '決済処理中チェックバッチ')]`、docブロックに「決済処理中チェックバッチ」「bin/console eccube:payment-status-check」と明記）。引数は取らない。
- 処理本体: `Eccube\Service\Admin\Payment\PaymentStatusCheckAction::handle()`（`src/Eccube/Service/Admin/Payment/PaymentStatusCheckAction.php:65`）。抽出は `DtbEventEntryRepository::getBeforeMinutesEntry(30)`（`src/Eccube/Repository/DtbEventEntryRepository.php:261`、決済処理中＝`PROCESSING_PAYMENT`・`payment_no IS NOT NULL`・未削除・指定分前以前）。
- ただし Playwright の `request` ではコンソールバッチを直接起動できない（起動口は実機/シェル依存）。区分は `E2E自動化(API/統合)` とし、コマンド名は実在根拠で確定する一方、spec では `bin/console` 実行が実機依存のため `test.fixme`（理由付き）で残す前提とする（コマンド未特定ではなく起動手段依存）。
- 取引照会（`PaymentStatusCheckAction::getApiResponse()`：`PaymentStatusCheckAction.php:191`）は SP.LINKS取引照会API未実装で現状 `LogicException` を送出する。OK→更新／取引不在→論理削除の正常経路は現状到達不能のため照会結果のスタブは `要実機確認`（付帯表4-5）。期待値は仕様（正本md処理フロー）由来のままとする。
- 結果のUI観測（イベント申込一覧画面での申込ステータス反映・論理削除の非表示）は、本機能の正本mdが「イベント申込そのものの入力・確定はイベント申込機能を正とする」と明記するため**別機能委譲**＝`手動`（要実機確認）に分類する。
