種別: batch（コンビニ決済で入金待ちのイベント申込を抽出し、決済サービスへ取引照会して申込ステータスを整合〔入金確認＝申込済みへ更新・申込履歴記録／取引不在＝記録の論理削除〕させ、想定外エラーは管理者へ通知するコンソールバッチ。画面を伴わない機能仕様）。期待結果はバッチ終了ステータス（正常終了／異常終了の扱い）・実行結果（処理結果の内訳・エラー出力）・DB副作用（申込ステータス・申込履歴・論理削除）など、API/統合レイヤ（コマンド起動）で観測できる結果で判定する。**期待結果は仕様（正本md・観点表）由来**とし、実装の現挙動・終了コード実値・処理件数の出力文言・メール本文/宛先をオラクル化しない（オラクル独立性）。pf-eccube3リバース＝基本設計・観点表を上位オラクルとし、乖離は付帯表4に出す。TSV は既存IT casesと同一の 10 列固定。E2E固有情報（コマンド/根拠・自動化区分・仕様根拠・シード・不具合候補）は TSV 後の付帯表に `テストID` で対応づける。Playwright は本リポジトリでは実行しない（構造参考のみ）。未確定の判定・閾値・内部挙動は `要実機確認`。

## 起動口（コンソールコマンド）の特定状況：実装済み（コマンド実在・名称は移行表の予想と相違）

本機能の起動口は刷新先 `ec-cube-enterprise` に実装済みであることを `#[AsCommand]` の grep で確認した。

- コマンド名: `eccube:payment-status-check`（`src/Eccube/Command/PaymentStatusCheckCommand.php:35`、`#[AsCommand(name: 'eccube:payment-status-check', description: '決済処理中チェックバッチ')]`、docブロックに「決済処理中チェックバッチ」「`bin/console eccube:payment-status-check`」と明記）。引数は取らない。**正本md移行表 L50 の現行コマンド `entry:batch checkCvsPayment`／「移行先で要確認」とは名称・実体が相違**（付帯表4-1）。
- 処理本体: `Eccube\Service\Admin\Payment\PaymentStatusCheckAction::handle()`（`src/Eccube/Service/Admin/Payment/PaymentStatusCheckAction.php:65`）。抽出は `DtbEventEntryRepository::getBeforeMinutesEntry(30)`（`src/Eccube/Repository/DtbEventEntryRepository.php:261`）。照会は `getApiResponse()`（同Action:191）。
- Playwright の `request` ではコンソールバッチを直接起動できない（起動口は実機/シェル依存）。区分は `E2E自動化(API/統合)` とし、コマンド名は実在根拠で確定する一方、spec では `bin/console` 実行が実機依存のため `test.fixme`（理由付き）で残す前提とする（コマンド未特定ではなく起動手段依存）。
- 結果のUI観測（イベント申込のステータス／履歴表示）は、イベント申込管理（別機能）の設計を正とするため、UI観測は別機能委譲＝`手動`（要実機確認）に分類する。本機能のDB副作用は API/統合レイヤ（バッチ実行後のDB状態照会）で観測する。
- 重要: 決済照会API `getApiResponse()` は **現状未実装で例外（`LogicException`）を投げる**（同Action:191-196「後続PRで実装予定」）。期待結果は仕様（入金確認＝更新／取引不在＝記録除去）のままとし、実装の現挙動を期待値にしない（付帯表4-6＝重大乖離）。
