# 【業務意思決定シート②】在庫の同時競合（超売り）ポリシー

> 2026-07-22 ／ 対象: 業務側・設計オーナー ／ 分析根拠: `ESCALATION_oversell_risk.md`
> 位置づけ: **仕様が未定義のため、どのテストパイプラインでも合否判定できない。** テスト以前の業務決定。
> トレカECは在庫1点物が大半 → 超売り＝同じ現物カードの二重販売＝事業毀損。

## 決める理由
No.518（在庫の同時競合）を証拠判定した結果、**在庫を更新する23機能のうち13機能が「同時実行時の挙動が設計書に沈黙」**。
実装が超売りしても「仕様違反」と言えない＝**合否オラクルが定義できない**。ここを業務が決めるまで、
No.518は「全数実行」と呼んでも合否不能（`MILESTONE_STATUS.md`・`TEST_EXECUTION_DECISION.md §6`）。

## 決定項目（記入してください）

### 決定1: 在庫更新の同時実行ポリシー（1つ選択）
- [ ] **A. 悲観ロック**（`SELECT FOR UPDATE`）で在庫更新を直列化する
- [ ] **B. 負在庫をDB制約で禁止**し、超過時はエラー（アプリで捕捉）
- [ ] **C. 後勝ち許容**（ただし在庫数には不可・受注メタのみ等、許容範囲を明記）
- [ ] D. その他（　　　　　　　　　　　）
→ 決定内容が No.518 の**合否オラクル**になる（例: Aなら「同時2確定で一方のみ成功・在庫非負」）。

### 決定3: 「後勝ち／ロックなし」を明記している5機能の意図確認
在庫に後勝ちが波及すると超売り。以下が意図通りか確認：
| 機能 | 設計書の記述（実抜粋） | 意図通りか（記入） |
|---|---|---|
| F04-04 | 「楽観ロック・悲観ロックの対象は持たない…受注ステータスを完了確定の前提条件として用いる」 | |
| M05-14 | 「本操作に固有の悲観ロック取得は持たず…購入フローの設計を正とする」 | |
| A06-03 | 「同一受注への同時更新は後勝ちとなる」 | |
| M07-03 | 「同時編集は後勝ちに近い通常ORM更新となる」 | |
| O01-01 | 「後から保存された内容が残る」 | |
→ **特に F04-04（フロント購入完了）はロックを持たず、在庫確保をステータス前提条件に留めている。**
この経路が管理画面在庫編集(M04-03)やPOS同期(A01-01)と同時に走ると、在庫非負の保証が設計書に無い。

## 決定後の効果
- No.518 が「根拠付きの並行テスト（決定論的な同時購入シナリオ）」として結合テスト母集合に投入可能になる
  （PostgreSQLの SELECT FOR UPDATE／直列化異常を突く形で自動化できる）。
- 決定が無いまま「全数実行」しても合否不能。**仕様決定 or 明示的なリリース受容が完了するまで No.518 は完了扱いにしない**。

## 想定事故シナリオ（決定の重要性）
1. 顧客Aがフロントで残1のカードを購入（F04-04・在庫ロックなし）
2. ほぼ同時に店舗スタッフが管理画面で在庫編集（M04-03）／POS販売がスマレジ同期で在庫減算（A01-01）
3. 双方が「在庫1」を前提に確定 → 在庫0/負・**同じ現物が二重に売れる**
4. 一方の顧客に商品が渡せず返金・信用毀損。トレカは1点物で代替在庫なし。
