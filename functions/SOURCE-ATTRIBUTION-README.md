## 参照元は一意

**両方のリポジトリに実装がある場合は本店(`pf-eccube3`)を採る**（2026-08-18 ユーザー指示）。
したがって **`参照元` が pf-eccube3 であることは「ec-cube に同等機能が無い」ことを意味しない。**
根拠欄が ec-cube 側の実装に触れていない行でも、不在の証明ではない。
不在を主張している行は根拠欄にその旨を明記してある。

## 判定で守るルール（レビューで確立）

1. **EC-CUBE のコア語彙は帰属の証拠にしない。** `admin.common.save_error` のような共有メッセージキーは
   ec-cube(支店) と ec-cube-enterprise(移行先) が同じ EC-CUBE4 系で共有するため、設計書mdが移行先の語彙で
   書かれているだけで ec-cube に誤一致する。
2. **ただしルート定義・メソッドは実装存在の証拠として残す。** `admin_order_export_order` のようなルートは
   語彙ではなくその機能そのものである。1 と混同しない。
3. **「無い」ことの証明に、語彙・ディレクトリ名・ファイル名の不在を使わない。** 同じ機能が別の名前で実装されている。
   レビューで実際に3回やらかした型:
   - **語彙**: 納品書＝`order_print`、受注一括メール＝`admin_order_mail_notice`
   - **ディレクトリ**: 「ec-cube に `Deck/` が無い」→ pf-eccube3 側も該当画面は `Mypage/deckentry.twig` で描画していた
   - **ファイル名**: 「`auto_mail` が無い」→ 両コアに汎用のメールテンプレート編集画面がある
   不在を主張するときは、**その機能を実行するルート定義とテンプレートが無いこと**を示す。
   逆に、設定項目やエンティティ定義だけが一致していても機能の存在にはならない
   （例: ec-cube の `picking_list_threshold` はピッキングリスト分割閾値の設定で、印刷処理ではない）。
   **片方の命名で検索して他方を判定しない。** 同じ機能が別名で実装されている
   （M16-04 MTGマスターデータ編集: pf-eccube3 は `HareruyaMasterdata`、ec-cube は `MtgMasterdata`。
   ec-cube の名前で pf を検索して「pf に無い」と誤判定した）。
4. **Excel が名指しする現行の実装挙動で決める。** パスや機能名の字面で決めない
   （A05-03 は URL が pf-eccube3 に前方一致するが、Excel の「※支店側の実装を移植」と店舗絞り込みの実装で ec-cube）。

## 計測の罠（必読）

**`rg` は同一入力でも約10回に1回 0件を返す。** 実測: 同じコマンドを20回叩いて {2件:19, 0件:1}。
取りこぼしは常に**過小側**で、過大側には振れない。

Stage 0 で使っていた「2回連続で同じ結果が出るまで引き直す」方式では防げない
（0が2回続く確率が約1/100あり、識別子400個なら数件がすり抜ける。実際 M15-10 で発生した）。

**N回走査して最大値を採ること。** 見つかったヒットは本物、0はフレークの可能性がある、という非対称性に基づく。
5回で取りこぼし確率は 10^-5。

この罠はスキャンに依拠した判定すべてに及ぶ。実装のルート・テンプレートを直接読んで判定したものには影響しない。

## 走査範囲の注意

`pf-article` は WordPress である。`wp-content` だけを走査すると `wp-admin`・`wp-includes` の
コア資産を見落とす（M12-05 の `sort_key` が `wp-admin/js/customize-nav-menus.js` に実在した）。
**唯一性（「〜にのみ実在」）を主張するときは、各リポジトリを全体で走査すること。**
証拠として採用する側は従来どおりカスタマイズ領域に限ってよい。
