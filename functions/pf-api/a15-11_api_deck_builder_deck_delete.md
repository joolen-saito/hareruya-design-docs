# API デッキビルダー — デッキ情報削除

## 概要

デッキビルダーアプリの利用者（プレイヤー）が、自身が所有する既存デッキを削除するためのAPIである。deck-api（デッキビルダー用のAPIアプリケーション）が提供するJSON APIで、デッキIDで対象を特定し、論理削除（削除日時の設定）とRedis一時保存の削除を行う。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。確認値はdeck-apiのデッキ削除処理、ルート定義（`config/routes.yaml`）、デッキ削除処理（デッキ保存サービス）、デッキを扱うエンティティ、共通の認証処理を正とする。

本機能のカスタマイズ区分は現行踏襲とする。挙動はdeck-api（デッキビルダー用APIアプリケーション）の実装を確認値とし、DB関連の記述（テーブル名・列名・永続化先）はec-cube-enterpriseの実装を正とする。

対象はJSON APIエンドポイントであり、ブラウザ向けの画面を持たない。本文ではフレームワークのコントローラ型名やメソッド名を主説明としない。「利用者視点の入口」にHTTPメソッドとパスパターンを書く。

---

## 本書で扱うこと

- 認証したプレイヤーによる自身のデッキの削除と所有者チェック
- 論理削除（削除日時の設定）とRedis一時保存の削除
- 認証失敗・対象なし・他人デッキ・処理失敗時の応答

---

## 本書で扱わないこと

以下は本書では仕様確定せず、実装または別APIの設計を正とする。

- デッキの新規登録・更新・参照（デッキ情報登録・デッキ情報更新・デッキ情報参照の各APIの設計を正とする）
- 採用カード・関連テーブルの物理削除（本APIはデッキ本体の論理削除のみを行う）
- トークンの発行（デッキビルダー用ログインの設計を正とする）

## リニューアル移行時の扱い

デッキビルダー関連テーブルは、現行（deck-api）と移行先（ec-cube-enterprise）で同一スキーマであり、テーブル名も一致する（デッキは`dtb_deck`）。本機能で更新するのは次のとおり。

| 項目 | 現行（deck-api） | 移行先（ec-cube-enterprise） | 差分・注意 |
|------|------------------|------------------------------|-----------|
| デッキ本体 | `dtb_deck` | `dtb_deck` | 同一テーブル名。 |
| 論理削除 | 削除日時（`deleted_at`）の設定 | 削除日時（`deleted_at`）の設定 | 同一列。物理削除は行わない。 |
| 所有者 | プレイヤー（`player_id`） | プレイヤー（`player_id`）。会員（`member_id`）列も持つ | 移行先はプレイヤーに加え会員列を持つ。所有者チェックの正は実装を確認値とする。 |

採用カード等の関連テーブルは本機能では物理削除せず、現行・移行先で扱いに差はない。

| 用語 | 説明 |
|------|------|
| デッキ | プレイヤーが作成するカードの組み合わせ。デッキIDで一意に特定する。 |
| 論理削除 | デッキ本体に削除日時を設定し、検索・参照の対象から外すこと。物理削除ではない。 |
| 下書き保存 | 更新内容をRedisに一時保存したもの。削除時にあわせて削除する。 |

## 利用者視点の入口

| 入口 | URLエンドポイント | 期待されるふるまい |
|------|--------------------|--------------------|
| デッキ情報の削除 | `DELETE /deck/{id}` | 認証したプレイヤーが所有するデッキIDのデッキを論理削除し、Redis一時保存を削除する。成功時はコード200のJSONを返す。 |

応答形式はJSON。呼び出し元はデッキビルダーアプリ。

---

## 認証・認可

| 観点 | 内容 |
|------|------|
| 認証方式 | `jwt-token`ヘッダのJWTを検証し、ペイロード`aud`の顧客IDからプレイヤーを引く。署名方式はHS256。 |
| 認証失敗時 | ヘッダ欠落・署名不正・該当するプレイヤーなしのいずれも認証拒否（HTTP 401）とし、`{code, message}`を返す。 |
| 認可 | 認証したプレイヤーが対象デッキの所有者である場合のみ削除できる。所有者でない場合は認証拒否（HTTP 401）とする。呼び出し可能なクライアントはデッキビルダーアプリ。 |

トークン原値・署名シークレットは本書に記載しない。

---

## 処理フロー

### デッキ情報を削除する（DELETE `/deck/{id}`）

1. `jwt-token`ヘッダのトークンを検証し、プレイヤーを特定する。検証できない場合は認証拒否（HTTP 401）とする。
2. パスのデッキIDで対象デッキを1件取得する。該当が無い場合は該当なし（HTTP 404、「The deck does not exist」）とする。
3. 対象デッキの所有者が認証したプレイヤーと一致しない場合は認証拒否（HTTP 401、「Authentication failed」）とする。
4. 対象デッキに削除日時を設定して論理削除し、当該デッキのRedis一時保存があれば削除する。一連の処理は1件のトランザクションで行い、例外時はロールバックして処理失敗（HTTP 500）とする。
5. 成功時はコード200・メッセージ（「Deck delete success」）を返す。

## 入出力

### リクエスト

| パラメータ | 位置 | 型 | 必須／任意 | 説明 |
|------------|------|----|-----------|------|
| `id` | パス | integer | 必須 | 削除対象のデッキID。 |
| `jwt-token` | ヘッダ | string | 必須 | 認証用のJWTトークン。 |

ボディパラメータは持たない。

### レスポンス（成功）

HTTP 200。

| フィールド | 型 | 説明 |
|------------|----|------|
| `code` | integer | 処理結果コード。成功時は200。 |
| `message` | string | 処理結果メッセージ。成功時は「Deck delete success」。 |

### レスポンス（失敗）

| HTTPステータス | 条件 | 本文の形 |
|----------------|------|----------|
| 401 | トークン欠落・署名不正・該当するプレイヤーなし、または対象デッキの所有者でない | `{code, message}`（messageは「Access Token is incorrect」「Authentication failed」） |
| 404 | デッキIDに該当するデッキが無い | `{code, message}`（messageは「The deck does not exist」） |
| 500 | 削除処理中の例外 | `{code, message}`（messageは例外メッセージ） |

### サンプルレスポンス

成功時の応答例。

```json
{
  "code": 200,
  "message": "Deck delete success"
}
```

### 副作用

対象デッキに削除日時を設定して論理削除する（DB更新）。当該デッキのRedis一時保存があれば削除する。採用カード等の関連テーブルは物理削除しない。参照のみではない。

応答はJSON応答整形を経て返す。プロパティはJSONキーに準じ、`serialize_null`は有効とする。

## バリデーション

本APIはボディの入力パラメータを持たない。パスのデッキIDで対象を特定し、該当が無い場合は該当なし（HTTP 404）とする。

## データ整合性

| 観点 | 内容 |
|------|------|
| 参照時点 | 削除時点で存在し、認証プレイヤーが所有するデッキを対象に削除する。 |
| 削除方式 | 削除日時の設定による論理削除とする。物理削除は行わない。 |
| 下書きの整合 | 当該デッキのRedis一時保存を削除し、削除後に下書きが残らないようにする。 |

## DBカラム

機能に直接関係する列のみ記載する。型や一覧の細部はスキーマを参照する。

| テーブル | 列 | メモ |
|----------|-----|------|
| デッキ（`dtb_deck`） | デッキID（`id`） | 対象の特定と所有者チェックに用いる。 |
| デッキ（`dtb_deck`） | プレイヤー（`player_id`） | 所有者チェックに用いる。 |
| デッキ（`dtb_deck`） | 削除日時（`deleted_at`） | 論理削除のため現在日時を設定する。 |

### DB操作

永続化の正は ec-cube-enterprise（テーブル名・操作は ec-cube-enterprise を正典）。当ドメインは承認ワークフローを介さず persist/flush で直接確定する（承認ワークフローは在庫機能固有）。

| 操作種別 | 対象テーブル | 契機・条件 |
|---------|--------------|------------|
| 登録/更新 | dtb_deck | 当機能が行う登録・更新で対象テーブルを直接保存する（不要な削除は含まない）。確定は persist/flush による即時反映。DB=ec-cube-enterprise を正典とする。 |

## 権限・認可

| 利用者状態 | デッキ情報削除 |
|------------|----------------|
| 認証済みかつ対象デッキの所有者 | 自身のデッキを削除できる。 |
| 認証済みだが他人のデッキ | 認証拒否（HTTP 401、「Authentication failed」）となり、削除できない。 |
| 未認証・トークン不正 | 認証拒否（HTTP 401）となり、削除できない。 |

---

## エラー処理

| エラー内容 | 処理 |
|------------|------|
| 認証不可 | 認証拒否（HTTP 401）とし、`{code, message}`を返す。 |
| デッキが存在しない | 該当なし（HTTP 404、「The deck does not exist」）とする。 |
| 他人のデッキ | 認証拒否（HTTP 401、「Authentication failed」）とする。 |
| 削除処理中の例外 | 処理失敗（HTTP 500）とし、`{code, message}`を返す。 |

## ログ・監査

### ログに出してはいけないもの

- JWTトークンの原値
- 署名シークレット（`auth_magic`）
- Cookie値・セッションIDの完全値

---

## 排他制御・トランザクション

本APIは論理削除とRedis一時保存の削除を1件のトランザクションで行い、例外時はロールバックする。楽観ロック・悲観ロックの対象は持たず、同一デッキへの同時操作は後勝ちとなる。
