# API デッキビルダー — デッキ情報更新

## 概要

デッキビルダーアプリの利用者（プレイヤー）が、自身が所有する既存デッキの情報を更新するためのAPIである。deck-api（デッキビルダー用のAPIアプリケーション）が提供するJSON APIで、デッキIDで対象を特定し、即時保存フラグの有無に応じてデータベースへ確定保存するか、Redisへ一時保存（下書き保存）する。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。確認値はdeck-apiのデッキ更新処理、ルート定義（`config/routes.yaml`）、デッキ保存処理（デッキ保存サービス・Redis一時保存）、デッキを扱うエンティティ、共通の認証処理を正とする。本機能のカスタマイズ区分は現行踏襲であり、挙動はデッキビルダーAPI（deck-api）の実装を参照し、DB関連の記述はec-cube-enterpriseを正とする。

対象はJSON APIエンドポイントであり、ブラウザ向けの画面を持たない。本文ではフレームワークのコントローラ型名やメソッド名を主説明としない。「利用者視点の入口」にHTTPメソッドとパスパターンを書く。

---

## 本書で扱うこと

- 認証したプレイヤーによる自身のデッキの更新と所有者チェック
- 即時保存フラグに応じたデータベース確定保存とRedis一時保存（下書き保存）の切り替え
- 更新時のレギュレーション違反判定と入力検証
- 限定公開デッキの閲覧用トークンの応答
- 認証失敗・対象なし・他人デッキ・入力不正・処理失敗時の応答

## 本書で扱わないこと

以下は本書では仕様確定せず、実装または別APIの設計を正とする。

- デッキの新規登録・削除・参照（デッキ情報登録・デッキ情報削除・デッキ情報参照の各APIの設計を正とする）
- デッキリスト文字列からのインポート更新（デッキインポートAPIの設計を正とする）
- Redisに保存した下書きをデータベースへ反映するバッチ（Redis保存コマンドの設計を正とする）
- トークンの発行（デッキビルダー用ログインの設計を正とする）

## リニューアル移行時の扱い

DB関連の記述はec-cube-enterpriseを正とする。挙動の参照元であるデッキビルダーAPI（deck-api）は提供リポジトリに含まれないため、現行deck-apiと移行先ec-cube-enterpriseでスキーマが異なる場合はec-cube-enterpriseを正とし、確認できない差異はec-cube-enterprise実装で要確認とする。確定保存はデッキ本体（`dtb_deck`）と採用カード（`dtb_deck_card`／`dtb_maybe_card`／`dtb_attraction_card`／`dtb_sticker_card`）を更新する。下書き保存はRedisへのJSON一時保存でありデータベースは更新しないため、Redis一時保存はec-cube-enterpriseのDBスキーマの対象外とする。

| 観点 | 現行（deck-api） | 移行先（ec-cube-enterprise） |
|------|------------------|------------------------------|
| デッキ本体テーブル | deck-api実装で要確認 | デッキ（`dtb_deck`） |
| 採用カードテーブル | deck-api実装で要確認 | 採用カード（`dtb_deck_card`）。即時保存時に初期化して保存しなおす |
| 下書き保存先 | Redis（JSON、既定1800秒） | データベース対象外。Redis一時保存のまま |
| 公開範囲の保持 | リクエスト`scope_id`（公開1・非公開2・限定公開3） | デッキリスト非公開フラグ（`private_flg`）と限定公開トークン（`display_token`）で表現。`scope_id`列の有無はec-cube-enterprise実装で要確認 |

## 用語

| 用語 | 説明 |
|------|------|
| デッキ | プレイヤーが作成するカードの組み合わせ。デッキIDで一意に特定する。 |
| 即時保存フラグ | 更新内容を即時にデータベースへ確定するか、下書きとして一時保存するかを切り替える指定。 |
| 下書き保存 | 更新内容をRedisにJSON形式で一時保存すること。確定保存ではない。 |
| 限定公開トークン | 限定公開デッキを閲覧するための識別子。 |

## 利用者視点の入口

| 入口 | URLエンドポイント | 期待されるふるまい |
|------|--------------------|--------------------|
| デッキ情報の更新 | `PUT /deck/{id}` | 認証したプレイヤーが所有するデッキIDのデッキを、即時保存フラグに応じてデータベース確定保存またはRedis一時保存し、成功時はコード200のJSONを返す。 |

応答形式はJSON。呼び出し元はデッキビルダーアプリ。

## 認証・認可

| 観点 | 内容 |
|------|------|
| 認証方式 | `jwt-token`ヘッダのJWTを検証し、ペイロード`aud`の顧客IDからプレイヤーを引く。署名方式はHS256。 |
| 認証失敗時 | ヘッダ欠落・署名不正・該当するプレイヤーなしのいずれも認証拒否（HTTP 401）とし、`{code, message}`を返す。 |
| 認可 | 認証したプレイヤーが対象デッキの所有者である場合のみ更新できる。所有者でない場合は認証拒否（HTTP 401）とする。呼び出し可能なクライアントはデッキビルダーアプリ。 |

トークン原値・署名シークレットは本書に記載しない。

## 処理フロー

### デッキ情報を更新する（PUT `/deck/{id}`）

1. `jwt-token`ヘッダのトークンを検証し、プレイヤーを特定する。検証できない場合は認証拒否（HTTP 401）とする。
2. パスのデッキIDで対象デッキを1件取得する。該当が無い場合は該当なし（HTTP 404、「The deck does not exist」）とする。
3. 対象デッキの所有者が認証したプレイヤーと一致しない場合は認証拒否（HTTP 401、「Authentication failed」）とする。
4. リクエストボディの全パラメータを受領する。即時保存フラグが立つ場合は、整合性を検証したうえでデータベースへ確定保存し、当該デッキのRedis一時保存を削除する。即時保存フラグが立たない場合は、整合性を検証したうえで内容をRedisへ一時保存（下書き保存）する。
5. 成功時はコード200・メッセージを返す。公開範囲が限定公開の場合は閲覧用トークンも返す。

## 業務ルール・計算

| 項目 | 内容 |
|------|------|
| 更新対象 | リクエストで指定されたID・入力値に対応する業務データを対象にする。対象特定、入力不正、認証・認可の判定順序は処理フローとバリデーションの各節を正とする。 |
| 更新方法 | 入力値を対象データへ上書きまたは追加登録する。履歴登録や関連データ更新がある場合は入出力の副作用およびDBカラムの節を正とする。 |
| 計算処理 | 本APIでは金額・税・ポイント・在庫数量の再計算や丸めを行わない。ステータスやコメント等の更新は、実装で定義された遷移・存在確認・担当者判定に従う。 |
| 応答値 | 成功時は処理結果コードまたは更新後に取得した値を返す。レスポンス値は本API内で独自集計せず、保存結果または取得結果をJSON応答へ整形する。 |

## 入出力

### リクエスト

リクエストボディはフォーム送信形式で受け取り、全キーをそのまま参照する。デッキ本体・採用カードのキーは登録APIと共通とする。

| パラメータ | 位置 | 型 | 必須／任意 | 説明 |
|------------|------|----|-----------|------|
| `id` | パス | integer | 必須 | 更新対象のデッキID。 |
| `jwt-token` | ヘッダ | string | 必須 | 認証用のJWTトークン。 |
| `instant_save_flag` | ボディ | boolean | 任意 | 真の場合はデータベースへ確定保存する。偽または未指定の場合はRedisへ一時保存（下書き保存）する。 |
| `deck_name` | ボディ | string | 任意 | デッキ名。 |
| `format_id` | ボディ | integer | 任意 | フォーマットの識別子。レギュレーション判定に用いる。 |
| `archetype_id` | ボディ | integer | 任意 | アーキタイプの識別子。 |
| `scope_id` | ボディ | integer | 必須 | 公開範囲。公開（1）・非公開（2）・限定公開（3）。応答の限定公開トークン出力可否の判定に用いる。 |
| `image_card_id` | ボディ | integer | 任意 | 代表カード画像に用いるカードID。 |
| `campaign_tag_ids` | ボディ | integer または array | 任意 | キャンペーンタグの識別子。単一値・配列のいずれも受け付ける。 |
| `cards` | ボディ | array | 任意 | 採用カードの配列。各要素は`card_id`・`board_id`・`count`を持つ。 |

### レスポンス（成功）

HTTP 200。

| フィールド | 型 | 説明 |
|------------|----|------|
| `code` | integer | 処理結果コード。成功時は200。 |
| `message` | string | 処理結果メッセージ。成功時は「Deck update success」。 |
| `display_token` | string | 限定公開デッキの閲覧用トークン。公開範囲が限定公開（3）のときのみ含める。 |

### レスポンス（失敗）

| HTTPステータス | 条件 | 本文の形 |
|----------------|------|----------|
| 401 | トークン欠落・署名不正・該当するプレイヤーなし、または対象デッキの所有者でない | `{code, message}`（messageは「Access Token is incorrect」「Authentication failed」） |
| 404 | デッキIDに該当するデッキが無い | `{code, message}`（messageは「The deck does not exist」） |
| 400 | 採用カードまたはデッキ本体の整合性検証に失敗 | `{code, message}`（messageは検証エラー内容） |
| 500 | 保存処理中の例外 | `{code, message}`（messageは例外メッセージ） |

### サンプルレスポンス

成功時の応答例（公開範囲が限定公開の場合）。

```json
{
  "code": 200,
  "message": "Deck update success",
  "display_token": "<displayToken>"
}
```

### 副作用

即時保存フラグが立つ場合は、デッキ本体と採用カード（メイビー・アトラクション・ステッカーを含む）を確定保存し（DB更新）、確定前に既存の採用カードを初期化したうえで保存しなおす。あわせて当該デッキのRedis一時保存を削除する。即時保存フラグが立たない場合は、更新内容をRedisにJSON形式で一時保存する（有効期間あり。既定1800秒）。データベースのデッキ本体は更新しない。

応答はJSON応答整形を経て返す。プロパティはJSONキーに準じ、`serialize_null`は有効とする。

## バリデーション

| 項目 | 内容 |
|------|------|
| 採用カード | ボード区分ごとに採用カード・メイビー・アトラクション・ステッカーとして組み立て、各エンティティの制約を検証する。未充足時は入力不正（HTTP 400）とする。 |
| デッキ本体 | フォーマット・公開範囲・採用カードを設定したうえでデッキ本体の制約を検証する。未充足時は入力不正（HTTP 400）とし、エラーメッセージを返す。 |
| 検証のタイミング | 即時保存・一時保存のいずれの場合も同一の整合性検証を行う。一時保存ではデータベースへ書き込まず検証のみ行ってからRedisに保存する。 |
| レギュレーション違反 | 即時保存時、フォーマットの枚数範囲・禁止制限・4枚制限・フォーマット適合・統率領域の伝説条件を判定し、フラグとして保存する。違反は更新自体を妨げない。 |

## データ整合性

| 観点 | 内容 |
|------|------|
| 参照時点 | 更新時点で存在し、認証プレイヤーが所有するデッキを対象に更新する。 |
| 確定保存と下書き | 即時保存はデータベースへ確定する。下書き保存はRedisにのみ反映し、データベースは更新しない。 |
| 採用カードの一致 | 即時保存では既存の採用カードを一旦削除して保存しなおすため、応答時点のデッキ内容と採用カードが一致する。 |

## DBカラム

機能に直接関係する列のみ記載する。型や一覧の細部はスキーマを参照する。

テーブル名・列名はec-cube-enterpriseの定義を正とする。

| テーブル | 列 | メモ |
|----------|-----|------|
| デッキ（`dtb_deck`） | デッキID（`deck_id`） | 対象の特定と所有者チェックに用いる。 |
| デッキ（`dtb_deck`） | デッキ名（`deck_name`）・フォーマット（`format_id`）・アーキタイプ（`archetype_id`）・代表カード画像（`card_image_id`） | 即時保存時の更新対象。公開範囲は非公開フラグ（`private_flg`）と限定公開トークン（`display_token`）で表現する。 |
| デッキ（`dtb_deck`） | プレイヤー（`player_id`）・プレイヤー名（`player_name`） | 認証プレイヤーを設定する。 |
| デッキ（`dtb_deck`） | レギュレーション違反フラグ（`regulation_violation_flg`） | 即時保存時に判定して保存する。 |
| デッキ（`dtb_deck`） | 更新日時（`update_date`） | 即時保存時に現在日時を設定する。 |
| 採用カード（`dtb_deck_card`）・メイビーカード（`dtb_maybe_card`）・アトラクションカード（`dtb_attraction_card`）・ステッカーカード（`dtb_sticker_card`） | デッキ・カード・ボード・枚数 | 即時保存時に初期化して保存しなおす。 |

### DB操作

永続化の正は ec-cube-enterprise（テーブル名・操作は ec-cube-enterprise を正典）。当ドメインは承認ワークフローを介さず persist/flush で直接確定する（承認ワークフローは在庫機能固有）。

| 操作種別 | 対象テーブル | 契機・条件 |
|---------|--------------|------------|
| 登録/更新 | dtb_attraction_card / dtb_deck / dtb_deck_card / dtb_maybe_card / dtb_sticker_card | 当機能が行う登録・更新で対象テーブルを直接保存する（不要な削除は含まない）。確定は persist/flush による即時反映。DB=ec-cube-enterprise を正典とする。 |

## 権限・認可

| 利用者状態 | デッキ情報更新 |
|------------|----------------|
| 認証済みかつ対象デッキの所有者 | 自身のデッキを更新できる。 |
| 認証済みだが他人のデッキ | 認証拒否（HTTP 401、「Authentication failed」）となり、更新できない。 |
| 未認証・トークン不正 | 認証拒否（HTTP 401）となり、更新できない。 |

## エラー処理

| エラー内容 | 処理 |
|------------|------|
| 認証不可 | 認証拒否（HTTP 401）とし、`{code, message}`を返す。 |
| デッキが存在しない | 該当なし（HTTP 404、「The deck does not exist」）とする。 |
| 他人のデッキ | 認証拒否（HTTP 401、「Authentication failed」）とする。 |
| 採用カード・デッキ本体の検証失敗 | 入力不正（HTTP 400）とし、`{code, message}`を返す。 |
| 保存処理中の例外 | 処理失敗（HTTP 500）とし、`{code, message}`を返す。 |

## ログ・監査

### ログに出してはいけないもの

- JWTトークンの原値
- 署名シークレット（`auth_magic`）
- 限定公開トークンの原値
- Cookie値・セッションIDの完全値

## 排他制御・トランザクション

即時保存はデッキ本体と採用カードの確定保存を1件のトランザクションで行い、例外時はロールバックする。一時保存はRedisへの書き込みのみで、データベースのトランザクションは持たない。楽観ロック・悲観ロックの対象は持たず、同一デッキへの同時更新は後勝ちとなる。
