# API デッキビルダー — ユーザー情報変更

## 概要

デッキビルダーアプリが、ログイン中の自分のユーザー情報（ニックネーム・プロフィール）を変更するためのAPIである。deck-api（デッキビルダー用のAPIアプリケーション）が提供するJSON APIで、`jwt-token`ヘッダのトークンから特定したプレイヤーのニックネームとプロフィールを保存する。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。確認値はdeck-apiのユーザー情報更新処理、ルート定義（`config/routes.yaml`）、プレイヤーを扱うエンティティ、共通の認証処理を正とする。本機能のカスタマイズ区分は現行踏襲であり、挙動はデッキビルダーAPI（deck-api）の実装を参照し、DB関連の記述はec-cube-enterpriseを正とする。

対象はJSON APIエンドポイントであり、ブラウザ向けの画面を持たない。本文ではフレームワークのコントローラ型名やメソッド名を主説明としない。「利用者視点の入口」にHTTPメソッドとパスパターンを書く。

---

## 本書で扱うこと

- 認証したプレイヤー自身のニックネーム・プロフィールの更新
- 認証、入力不正、更新失敗時の応答
- 更新対象とする列の範囲

---

## 本書で扱わないこと

以下は本書では仕様確定せず、実装または別APIの設計を正とする。

- ユーザー情報の参照（ユーザー情報参照・他ユーザー情報参照APIの設計を正とする）
- デッキユーザーID・本名・メールアドレス・ポイント等、本APIで更新しない項目の変更
- トークンの発行（デッキビルダー用ログインの設計を正とする）

---

## リニューアル移行時の扱い

DB関連の記述はec-cube-enterpriseを正とする。挙動の参照元であるデッキビルダーAPI（deck-api）は提供リポジトリに含まれないため、現行deck-apiと移行先ec-cube-enterpriseでスキーマが異なる場合はec-cube-enterpriseを正とし、確認できない差異はec-cube-enterprise実装で要確認とする。

| 観点 | 現行（deck-api） | 移行先（ec-cube-enterprise） |
|------|------------------|------------------------------|
| 更新対象テーブル | プレイヤー（deck-api実装で要確認） | プレイヤー（`dtb_player`） |
| ニックネーム列 | deck-api実装で要確認 | `nickname`（255桁、null許容） |
| プロフィール列 | deck-api実装で要確認 | `profile`（255桁、null許容） |
| 対象特定キー | `aud`の顧客ID | `customer_id`（顧客IDで照合） |

## 用語

| 用語 | 説明 |
|------|------|
| プレイヤー | デッキビルダーの利用者。会員（顧客）に紐づき、`aud`の顧客IDで特定する。 |
| ニックネーム | プレイヤーの表示名。本APIで更新するユーザー名。 |
| プロフィール | プレイヤーの自己紹介文。本APIで更新する。 |

---

## 利用者視点の入口

| 入口 | URLエンドポイント | 期待されるふるまい |
|------|--------------------|--------------------|
| 自分のユーザー情報変更 | `PUT /user` | `jwt-token`ヘッダから特定したプレイヤーのニックネームとプロフィールを保存し、成功時はコード200のJSONを返す。 |

応答形式はJSON。呼び出し元はデッキビルダーアプリ。

---

## 認証・認可

| 観点 | 内容 |
|------|------|
| 認証方式 | `jwt-token`ヘッダのJWTを検証し、ペイロードの`aud`の顧客IDから顧客IDに対応するプレイヤーを引く。署名方式はHS256。 |
| 認証失敗時 | ヘッダ欠落・署名不正・該当するプレイヤーなしのいずれも認証拒否（HTTP 401）とする。本文は`{code, message}`で返す。 |
| 認可 | 認証したプレイヤー自身の情報のみを更新する。他プレイヤーの情報は更新できない。呼び出し可能なクライアントはデッキビルダーアプリ。 |

トークン原値・署名シークレットは本書に記載しない。

---

## 処理フロー

### 自分のユーザー情報を更新する（PUT `/user`）

1. `jwt-token`ヘッダのトークンを検証し、`aud`の顧客IDからプレイヤーを特定する。検証できない、または該当するプレイヤーがない場合は認証拒否（HTTP 401）とし、`{code, message}`を返す。
2. リクエストからユーザー名（`user_name`）とプロフィール（`profile`）を受領する。ユーザー名が未指定（null）の場合は入力不正（HTTP 400）とし、`{code, message}`（メッセージは「Invalid request parameters」）を返す。
3. トランザクションを開始し、プレイヤーのニックネームをユーザー名で、プロフィールを指定値で更新して保存し、コミットする。更新中に例外が発生した場合はロールバックし、処理失敗（HTTP 500）として例外メッセージを返す。
4. 成功時はコード200とメッセージ「Update user information」のJSONを返す。

## 業務ルール・計算

| 項目 | 内容 |
|------|------|
| 更新対象 | リクエストで指定されたID・入力値に対応する業務データを対象にする。対象特定、入力不正、認証・認可の判定順序は処理フローとバリデーションの各節を正とする。 |
| 更新方法 | 入力値を対象データへ上書きまたは追加登録する。履歴登録や関連データ更新がある場合は入出力の副作用およびDBカラムの節を正とする。 |
| 計算処理 | 本APIでは金額・税・ポイント・在庫数量の再計算や丸めを行わない。ステータスやコメント等の更新は、実装で定義された遷移・存在確認・担当者判定に従う。 |
| 応答値 | 成功時は処理結果コードまたは更新後に取得した値を返す。レスポンス値は本API内で独自集計せず、保存結果または取得結果をJSON応答へ整形する。 |

---

## 入出力

### リクエスト

| パラメータ | 位置 | 型 | 必須／任意 | 説明 |
|------------|------|----|-----------|------|
| `jwt-token` | ヘッダ | string | 必須 | 認証用のJWTトークン。検証して`aud`の顧客IDからプレイヤーを引く。 |
| `user_name` | ボディ | string | 必須 | 設定するニックネーム。未指定（null）の場合は入力不正（HTTP 400）となる。 |
| `profile` | ボディ | string | 任意 | 設定するプロフィール。未指定の場合はnullとして保存する。 |

### レスポンス（成功）

HTTP 200。応答本体はラッパオブジェクトで、JSONキーはsnake_caseで組み立てる。

| フィールド | 型 | 説明 |
|------------|----|------|
| `code` | integer | 処理結果コード。成功時は200。 |
| `message` | string | 結果メッセージ。成功時は「Update user information」。 |

### レスポンス（失敗）

| HTTPステータス | 条件 | 本文の形 |
|----------------|------|----------|
| 401 | `jwt-token`ヘッダ欠落・署名不正・`aud`に該当するプレイヤーなし | `{code, message}`（`message`は「Access Token is incorrect」または「Authentication failed」） |
| 400 | ユーザー名（`user_name`）が未指定（null） | `{code, message}`（`message`は「Invalid request parameters」） |
| 500 | 更新中に例外が発生（保存失敗） | `{code, message}`（`message`は例外メッセージ。ロールバックする） |

### サンプルレスポンス

成功時の応答例（実装確認値に基づく代表値）。

```json
{
  "code": 200,
  "message": "Update user information"
}
```

### 副作用

プレイヤーのニックネームとプロフィールを更新する（DB更新）。参照のみではない。更新はトランザクション内で行い、例外時はロールバックする。

応答はJSON応答整形を経て返す。本APIは連想配列を組み立てて返すため、JSONキーは実装で記述したsnake_case（`code`・`message`）となり、エンティティのプロパティ名（camelCase）はそのままは現れない。`serialize_null`は有効とする。

## バリデーション

| 項目 | 内容 |
|------|------|
| `user_name` | 必須。未指定（null）の場合は入力不正（HTTP 400）とし、「Invalid request parameters」を返す。空文字や最大長（ニックネームは255桁）の上限はdeck-api側のコントローラでは判定せず、DB保存時の制約に委ねる。 |
| `profile` | 任意。未指定の場合はnullとして保存する。最大長（255桁）の上限はコントローラでは判定しない。 |
| `jwt-token` | 必須。ヘッダ欠落・署名不正・該当プレイヤーなしのいずれも認証拒否（HTTP 401）とする。 |

---

## データ整合性

| 観点 | 内容 |
|------|------|
| 参照時点 | 認証時点で特定したプレイヤーを対象に更新する。 |
| 更新範囲 | ニックネームとプロフィールのみを更新する。デッキユーザーID・本名・メールアドレス・ポイント等の他項目は本APIでは変更しない。 |
| 同時更新 | 同一プレイヤーへの同時更新に対する排他制御は本APIでは持たない。 |

---

## DBカラム

機能に直接関係する列のみ記載する。型や一覧の細部はスキーマを参照する。

列名はec-cube-enterpriseのプレイヤー（`dtb_player`）の定義を正とする。

| テーブル | 列 | メモ |
|----------|-----|------|
| プレイヤー（`dtb_player`） | 顧客ID（`customer_id`） | `aud`の顧客IDでプレイヤーを特定する。 |
| プレイヤー（`dtb_player`） | ニックネーム（`nickname`） | 更新対象。`user_name`の指定値で上書きする。最大255桁。 |
| プレイヤー（`dtb_player`） | プロフィール（`profile`） | 更新対象。`profile`の指定値（未指定時はnull）で上書きする。最大255桁。 |

### DB操作

永続化の正は ec-cube-enterprise（テーブル名・操作は ec-cube-enterprise を正典）。当ドメインは承認ワークフローを介さず persist/flush で直接確定する（承認ワークフローは在庫機能固有）。

| 操作種別 | 対象テーブル | 契機・条件 |
|---------|--------------|------------|
| 登録/更新 | dtb_player | 当機能が行う登録・更新で対象テーブルを直接保存する（不要な削除は含まない）。確定は persist/flush による即時反映。DB=ec-cube-enterprise を正典とする。 |

## 権限・認可

| 利用者状態 | ユーザー情報変更 |
|------------|------------------|
| 認証済みのプレイヤー | 自分のニックネームとプロフィールを更新できる。 |
| 未認証・トークン不正 | 認証拒否（HTTP 401）となり、更新できない。 |

## エラー処理

| エラー内容 | 処理 |
|------------|------|
| 認証不可 | 認証拒否（HTTP 401）とし、`{code, message}`を返す。 |
| ユーザー名未指定 | 入力不正（HTTP 400）とし、「Invalid request parameters」を返す。 |
| 更新中の例外 | ロールバックし、処理失敗（HTTP 500）として例外メッセージを返す。 |

---

## ログ・監査

### ログに出してはいけないもの

- JWTトークンの原値
- 署名シークレット（`auth_magic`）
- パスワード
- Cookie値・セッションIDの完全値

---

## 排他制御・トランザクション

本APIはニックネームとプロフィールの更新を1つのトランザクション内で行い、例外時はロールバックする。楽観ロック・悲観ロックの対象は持たず、同一プレイヤーへの同時更新は後勝ちとなる。
