# API デッキビルダー — デッキ更新インポート

## 概要

デッキビルダーアプリが、デッキリストのテキスト（カードリスト）を貼り付けて既存デッキを上書き更新するためのAPIである。deck-api（デッキビルダー用のAPIアプリケーション）が提供するJSON APIで、`jwt-token`ヘッダから特定したプレイヤーが所有する既存デッキを対象に、カードリストを解読してデッキ内容を更新し保存する。本書は更新（パスにデッキ識別子を持つPUT）を対象とする。

本機能のカスタマイズ区分は現行踏襲であり、挙動は現行実装（deck-api）を参照し、DB関連はec-cube-enterpriseを正とする。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。確認値はdeck-apiのデッキインポート処理、ルート定義（`config/routes.yaml`）、デッキ保存サービス・カードリスト解読処理、共通の認証処理を正とする。

対象はJSON APIエンドポイントであり、ブラウザ向けの画面を持たない。本文ではフレームワークのコントローラ型名やメソッド名を主説明としない。「利用者視点の入口」にHTTPメソッドとパスパターンを書く。

---

## 本書で扱うこと

- パスのデッキ識別子による既存デッキの特定と所有者照合
- カードリストテキストの解読と既存デッキの上書き更新
- 解読できなかった行（カード名未一致）の扱いと部分成功（HTTP 206）
- 非公開・限定公開時の表示用トークンの扱い

---

## 本書で扱わないこと

以下は本書では仕様確定せず、実装または別APIの設計を正とする。

- デッキの新規登録インポート（デッキ登録インポートAPI `POST /deck/import`の設計を正とする）
- カードリストを用いない通常のデッキ更新（`PUT /deck/{id}`の設計を正とする）
- デッキの参照・検索・削除（各デッキAPIの設計を正とする）
- トークンの発行（デッキビルダー用ログインの設計を正とする）

## リニューアル移行時の扱い

現行（deck-api）と移行先（ec-cube-enterprise）でデッキ永続化のスキーマに差がある。DB関連の記述は移行先を正とし、確認できた差を以下に記録する。

| 項目 | 現行（deck-api） | 移行先（ec-cube-enterprise） |
|------|------------------|------------------------------|
| 公開区分 | 公開区分（`scope_id`、公開・非公開・限定公開の3値） | 非公開フラグ（`dtb_deck.private_flg`、真偽）と閲覧用トークン（`dtb_deck.display_token`）に分けて保持する。3値の公開区分の移行可否はec-cube-enterprise実装で要確認。 |
| 所有者照合 | 認証したプレイヤーとデッキ所有者の一致 | `dtb_deck.player_id`（プレイヤー `dtb_player`）で照合する。あわせて会員参照 `member_id` を持つ。 |
| デッキ本文 | メイン・サイド・統率者の本文 | `dtb_deck.text_main`・`text_side`・`text_command`（テキスト列）にメイン・サイド・統率を保持し、カード明細を `dtb_deck_card`（`board_id` で区分）に保持する。 |
| ボード外区分 | メイビー・アトラクション・ステッカー | 別表 `dtb_maybe_card`・`dtb_attraction_card`・`dtb_sticker_card`（いずれも `deck_id`・`card_id`・`count`）。更新時はこれらを初期化してから作り直す。 |
| 削除方式 | 実装で要確認 | `dtb_deck.deleted_at` による論理削除。 |

## 用語

| 用語 | 説明 |
|------|------|
| プレイヤー | デッキビルダーの利用者。会員（顧客）に紐づき、`aud`の顧客IDで特定する。 |
| カードリスト | デッキ内容を表すテキスト（枚数とカード名の行を並べた形式）。`card_list`として受け取る。 |
| ボード | メインボード・サイドボード・統率者などデッキ内の区分。カードリストの区切り文字列で切り替える。 |

## 利用者視点の入口

| 入口 | URLエンドポイント | 期待されるふるまい |
|------|--------------------|--------------------|
| デッキ更新インポート | `PUT /deck/import/{id}` | `jwt-token`ヘッダから特定したプレイヤーが所有する、パスの`id`のデッキを対象に、`card_list`を解読して内容を上書き更新し、デッキ識別子をコード200のJSONで返す。解読できない行があるときはコード206を返す。 |

応答形式はJSON。呼び出し元はデッキビルダーアプリ。新規登録（`POST /deck/import`）と同一の処理を共有し、本書はパスにデッキ識別子を持つPUT（更新）のみを扱う。

## 認証・認可

| 観点 | 内容 |
|------|------|
| 認証方式 | `jwt-token`ヘッダのJWTを検証し、ペイロードの`aud`の顧客IDから顧客IDに対応するプレイヤーを引く。署名方式はHS256。 |
| 認証失敗時 | ヘッダ欠落・署名不正・該当するプレイヤーなしのいずれも認証拒否（HTTP 401）とし、本文は`{code, message}`で返す。 |
| 認可 | パスのデッキの所有プレイヤーが認証したプレイヤーと一致する場合のみ更新できる。一致しない場合は認証拒否（HTTP 401）とする。呼び出し可能なクライアントはデッキビルダーアプリ。 |

トークン原値・署名シークレットは本書に記載しない。

## 処理フロー

### デッキを更新する（PUT `/deck/import/{id}`）

1. `jwt-token`ヘッダのトークンを検証し、プレイヤーを特定する。検証できない、または該当するプレイヤーがない場合は認証拒否（HTTP 401）とし、`{code, message}`を返す。
2. メソッドがPUTでパスの`id`が指定されているため、`id`に一致する既存デッキを取得する。該当が無い場合は該当なし（HTTP 404）とし、「The deck does not exist」を返す。
3. 取得したデッキの所有プレイヤーが認証したプレイヤーと一致しない場合は認証拒否（HTTP 401）とし、「Authentication failed」を返す。
4. ボディの`format_id`からフォーマットを取得し、`card_list`をフォーマットの統率者使用設定に応じて解読する。解読結果のカード配列を`cards`としてリクエストに組み込む。
5. 既存デッキ配下の旧カード（デッキカード・メイビー・アトラクション・ステッカー）を初期化したうえで、解読したカードと`deck_name`・`scope_id`・`archetype_id`等で内容を組み立て直し、検証を通過したらデータベースに保存する。あわせて当該デッキのRedis上の下書きを削除する。検証エラーは入力不正（HTTP 400）とし、その他の例外は処理失敗（HTTP 500）とする。
6. デッキ識別子（`deck_id`）を含むコード200のJSONを返す。公開区分が限定公開のときは表示用トークン（`display_token`）も返す。
7. カードリストに解読できない行（カード名未一致）がある場合は、コードを206に切り替え、該当行の行番号を`errors`として返す。

### 新規登録との分岐

同一処理を新規登録（POST）と共有し、パスのデッキ識別子の有無で動作を分ける。

| 条件 | 動作 |
|------|------|
| メソッドがPUTかつパスの`id`が非null | `id`の既存デッキを取得し、該当なしは404、所有者不一致は401とする。取得できた場合は既存デッキを上書き更新する。 |
| メソッドがPOST（パスにデッキ識別子なし） | 既存デッキの取得・所有者照合を行わず、新規デッキとして登録する（デッキ登録インポートAPIで扱う）。 |

更新時のメッセージは「Deck update success by import」、新規登録時は「Deck registration success by import」となる。

| 項目 | 内容 |
|------|------|
| 更新対象 | リクエストで指定されたID・入力値に対応する業務データを対象にする。対象特定、入力不正、認証・認可の判定順序は処理フローとバリデーションの各節を正とする。 |
| 更新方法 | 入力値を対象データへ上書きまたは追加登録する。履歴登録や関連データ更新がある場合は入出力の副作用およびDBカラムの節を正とする。 |
| 計算処理 | 本APIでは金額・税・ポイント・在庫数量の再計算や丸めを行わない。ステータスやコメント等の更新は、実装で定義された遷移・存在確認・担当者判定に従う。 |
| 応答値 | 成功時は処理結果コードまたは更新後に取得した値を返す。レスポンス値は本API内で独自集計せず、保存結果または取得結果をJSON応答へ整形する。 |

## 入出力

### リクエスト

| パラメータ | 位置 | 型 | 必須／任意 | 説明 |
|------------|------|----|-----------|------|
| `id` | パス | integer | 必須 | 更新対象のデッキ識別子。該当が無い場合は該当なし（HTTP 404）、所有者が一致しない場合は認証拒否（HTTP 401）となる。 |
| `jwt-token` | ヘッダ | string | 必須 | 認証用のJWTトークン。検証して`aud`の顧客IDからプレイヤーを引く。 |
| `format_id` | ボディ（フォーム値） | integer | 必須 | デッキのフォーマット識別子。カードリスト解読時の統率者使用設定の判定に用いる。 |
| `card_list` | ボディ（フォーム値） | string | 任意 | デッキ内容のテキスト。枚数とカード名の行を並べた形式。未指定・空のときは空のカード配列として扱う。 |
| `deck_name` | ボディ（フォーム値） | string | 任意 | デッキ名。 |
| `scope_id` | ボディ（フォーム値） | integer | 任意 | 公開区分（公開・非公開・限定公開）。限定公開のとき応答に表示用トークンを含める。 |
| `archetype_id` | ボディ（フォーム値） | integer | 任意 | アーキタイプ識別子。 |
| `image_card_id` | ボディ（フォーム値） | integer | 任意 | デッキ画像に用いるカード識別子。 |
| `campaign_tag_ids` | ボディ（フォーム値） | integer または array | 任意 | 紐づけるキャンペーンタグ識別子。 |

カードリストの行数の上限は500行で、超過時は入力不正（HTTP 400）となる。

### レスポンス（成功）

HTTP 200（解読できない行がある場合はHTTP 206）。応答本体はラッパオブジェクトで、JSONキーはsnake_caseで組み立てる。

| フィールド | 型 | 説明 |
|------------|----|------|
| `code` | integer | 処理結果コード。全行解読できたときは200、解読できない行があるときは206。 |
| `message` | string | 処理結果メッセージ。更新時は「Deck update success by import」。 |
| `deck_id` | integer | 更新したデッキの識別子。 |
| `display_token` | string | 限定公開のときのみ含まれる表示用トークン。 |
| `errors` | array | 解読できない行がある場合のみ含まれる、該当行の行番号（0始まりのインデックス）の配列。 |

### レスポンス（失敗）

| HTTPステータス | 条件 | 本文の形 |
|----------------|------|----------|
| 401 | `jwt-token`ヘッダ欠落・署名不正・`aud`に該当するプレイヤーなし、またはデッキの所有者が認証したプレイヤーと不一致 | `{code, message}`（`message`は「Access Token is incorrect」「Authentication failed」） |
| 404 | パスの`id`に一致するデッキが無い | `{code, message}`（`message`は「The deck does not exist」） |
| 400 | 検証失敗（必須項目不足・不正値）、またはカードリストが上限行数超過 | `{code, message}`（`message`は検証エラーメッセージ） |
| 500 | 保存処理中のその他の例外 | `{code, message}`（`message`は例外メッセージ） |

### サンプルレスポンス

更新の成功例（実装確認値に基づく代表値）。

```json
{
  "code": 200,
  "message": "Deck update success by import",
  "deck_id": 12345
}
```

解読できない行がある場合の例（限定公開）。

```json
{
  "code": 206,
  "message": "Deck update success by import",
  "deck_id": 12345,
  "display_token": "<displayToken>",
  "errors": [3, 7]
}
```

### 副作用

既存デッキ配下のカード（デッキカード・メイビー・アトラクション・ステッカー）を初期化したうえで、デッキ内容とカードをデータベースに上書き更新する（DB更新）。あわせて当該デッキのRedis上の下書きを削除する。保存は単一のトランザクション内で行い、例外時はロールバックする。

応答はJSON応答整形を経て返す。本APIは連想配列を組み立てて返すため、JSONキーは実装で記述したsnake_case（`code`・`message`・`deck_id`・`display_token`・`errors`）となる。`serialize_null`は有効とする。

| 項目 | 内容 |
|------|------|
| `id` | パス必須。該当するデッキが無い場合は該当なし（HTTP 404）、所有者が一致しない場合は認証拒否（HTTP 401）とする。 |

## データ整合性

| 観点 | 内容 |
|------|------|
| 更新の有無 | 既存デッキ配下のカードを初期化してから、解読したカードで作り直して保存する。デッキ本体は同一識別子のまま内容を上書きする。 |
| トランザクション | カードの初期化・デッキ本体・カードの保存を1つのトランザクションで行い、検証エラー・例外時はロールバックする。 |
| 下書きとの整合 | 保存後に当該デッキのRedis上の下書きを削除し、保存済みデータと下書きの不整合を解消する。 |

## DBカラム

機能に直接関係する列のみ記載する。型や一覧の細部はスキーマを参照する。

テーブル名・列名はec-cube-enterpriseを正とし、現行（deck-api）と呼称が異なる箇所は括弧で補う。

| テーブル | 列 | メモ |
|----------|-----|------|
| デッキ（`dtb_deck`） | 識別子（`id`）・デッキ名（`deck_name`）・フォーマット（`format_id`）・アーキタイプ（`archetype_id`）・非公開フラグ（`private_flg`、現行の公開区分 `scope_id` に対応）・所有プレイヤー（`player_id`）・閲覧用トークン（`display_token`）・本文（`text_main`・`text_side`・`text_command`）・更新日時（`update_date`）・削除日時（`deleted_at`） | 更新の対象。所有プレイヤーの一致を更新可否の判定に用いる。 |
| デッキカード（`dtb_deck_card`） | デッキ（`deck_id`）・カード（`card_id`）・ボード（`board_id`）・枚数（`count`） | 初期化後にカードリスト解読結果で作り直す。 |
| メイビー／アトラクション／ステッカー（`dtb_maybe_card`／`dtb_attraction_card`／`dtb_sticker_card`） | デッキ（`deck_id`）・カード（`card_id`）・枚数（`count`） | 更新時は初期化してから作り直す。 |
| フォーマットマスタ（`mtb_format`） | 識別子・統率者使用設定 | カードリスト解読の挙動判定に用いる。 |

### DB操作

永続化の正は ec-cube-enterprise（テーブル名・操作は ec-cube-enterprise を正典）。当ドメインは承認ワークフローを介さず persist/flush で直接確定する（承認ワークフローは在庫機能固有）。

| 操作種別 | 対象テーブル | 契機・条件 |
|---------|--------------|------------|
| 登録/更新 | dtb_attraction_card / dtb_deck / dtb_deck_card / dtb_maybe_card / dtb_sticker_card / mtb_format | 当機能が行う登録・更新で対象テーブルを直接保存する（不要な削除は含まない）。確定は persist/flush による即時反映。DB=ec-cube-enterprise を正典とする。 |

## エラー処理

| エラー内容 | 処理 |

- JWTトークンの原値
- 署名シークレット（`auth_magic`）
- パスワード
- Cookie値・セッションIDの完全値

## 排他制御・トランザクション

本APIは既存デッキのカード初期化とデッキ・カードの上書き更新を1つのトランザクションで行う。検証エラー・例外時はロールバックする。同一デッキへの同時更新に対する楽観ロック・悲観ロックは持たない。
