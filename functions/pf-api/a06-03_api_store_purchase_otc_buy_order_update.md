# API 店頭買取管理 — 店頭買取受注詳細更新

## 概要

買取アプリ（MTGバイヤー）が店頭買取受注の査定明細を確定し、受注全体を更新するためのAPIである。pf-api（買取連携用のAPIアプリケーション）が提供するJSON APIで、受注IDで対象を特定し、送られた明細で既存の明細・個別入力商品・在庫・在庫履歴を作り直し、受注のステータス・買取合計金額・査定担当者・更新日時などを保存する。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。確認値はpf-apiの店頭買取受注詳細更新処理、ルート定義（`config/routes.yaml`）、店頭買取受注・店頭買取受注明細・個別入力商品・在庫・在庫履歴・ステータス変更履歴を扱うエンティティ、店頭買取ステータスマスタ、入力検証用のエンティティと制約、共通の認証処理を正とする。

本機能のカスタマイズ区分はカスタマイズで、挙動の参照リポはpf-apiとする。DB関連の記述（テーブル名・列名・永続化先）はec-cube-enterpriseを正とする。

対象はJSON APIエンドポイントであり、ブラウザ向けの画面を持たない。本文ではフレームワークのコントローラ型名やメソッド名を主説明としない。「利用者視点の入口」にHTTPメソッドとパスパターンを書く。

## 本書で扱うこと

- 受注IDによる店頭買取受注の特定
- 送られた明細による明細・個別入力商品・在庫・在庫履歴の作り直し
- 受注のステータス・買取合計金額・査定担当者・更新日時・成立日時／キャンセル日時・適格請求書発行事業者の確認済みフラグの更新
- ステータス変更履歴の登録
- 入力検証（ステータス必須・マスタ存在、明細必須、明細各項目の形式）と認証・対象なし時の応答

## 本書で扱わないこと

以下は本書では仕様確定せず、実装または別APIの設計を正とする。

- 店頭買取受注のステータス単独更新（店頭買取受注ステータス更新APIの設計を正とする）
- 店頭買取受注のフリーコメント更新・本人確認情報更新（各店頭買取APIの設計を正とする）
- 店頭買取受注一覧の取得（店頭買取受注一覧取得APIの設計を正とする）
- 査定明細の業務上の意味づけや画面表示・部門や商品規格の選び方（買取アプリの設計を正とする）
- トークンの発行（買取アプリ用ログインの設計を正とする）

## リニューアル移行時の扱い

明細の全置換・在庫集計・買取合計金額の10円切り上げ・ステータス変更履歴登録の挙動は現行（pf-api）を正とし、永続化に関わるテーブル・列名は移行先（ec-cube-enterprise）を正とする。店頭買取受注に関わる各表は現行・移行先で同名である。

| 区分 | 現行（pf-api） | 移行先（ec-cube-enterprise） |
|------|----------------|------------------------------|
| 店頭買取受注 | dtb_otc_buy_order | 同一スキーマ（dtb_otc_buy_order） |
| 店頭買取受注明細 | dtb_otc_buy_order_detail | 同一スキーマ（dtb_otc_buy_order_detail） |
| 個別入力商品 | dtb_otc_buy_order_indivisual_input_product | 同一スキーマ（dtb_otc_buy_order_indivisual_input_product） |
| 在庫・在庫履歴 | dtb_otc_buy_order_stock・dtb_otc_buy_order_stock_history | 同一スキーマ（同名テーブル） |
| ステータス変更履歴 | dtb_otc_buy_order_status_history | 同一スキーマ（dtb_otc_buy_order_status_history） |
| 店頭買取ステータス・部門・商品規格 | mtb_otc_buy_order_status・mtb_section・商品規格 | 同一スキーマ（mtb_otc_buy_order_status・mtb_section・商品規格） |
| 査定担当者 | dtb_member（member_id） | dtb_member（id）。会員の主キー名がidになる |

検証メッセージ・成立／キャンセル日時の振り分け・確認済みフラグの更新条件はリニューアル後も同じ前提とするが、査定担当者として記録する会員の主キー名が現行のmember_idから移行先のidへ変わる。受注が持つ店舗列は、現行のshop_id（mtb_shop）から移行先のbase_info_id（dtb_base_info）へ変わるが、本APIでは更新しない。

## 認証・認可

| 観点 | 内容 |
|------|------|
| 認証方式 | `jwt-token`ヘッダのJWTを検証し、ペイロードの利用者IDから管理者会員を引く。署名方式はHS256。 |
| 認証失敗時 | ヘッダ欠落・署名不正・該当する管理者会員なしのいずれも認証拒否（HTTP 401）とする。 |
| 認可 | 認証した管理者会員が査定担当者として記録される。呼び出し可能なクライアントは買取アプリ。受注の現在のステータスや担当者による更新制限は本APIでは課さない。 |

トークン原値・署名シークレットは本書に記載しない。

## 処理フロー

### 店頭買取受注の詳細を更新する（PUT `/admin/otcBuyOrder/{id}.json`）

1. `jwt-token`ヘッダのトークンを検証し、管理者会員を特定する。検証できない場合は認証拒否（HTTP 401）とする。
2. パスの受注IDで店頭買取受注を1件取得する。該当が無い場合は該当なし（HTTP 404）とする。
3. リクエストのステータス（`order_status`）・明細配列（`order_details`）・適格請求書発行事業者の確認済みフラグ（`qualified_invoice_issuer_confirmation_flg`）を受け取り、ステータス・明細の入力検証と、明細1件ごとの入力検証を行う。検証エラーが1件以上あれば、入力不正（HTTP 400）とし全エラーメッセージを`errors`配列で返す。
4. 受注に紐づく既存の明細・個別入力商品・在庫・在庫履歴を削除する。
5. 送られた明細を1件ずつ処理する。商品規格IDが空の明細は個別入力商品として登録し、商品規格IDがある明細は明細として登録する。いずれも部門IDがあり該当部門が存在すれば部門を設定する。明細の単価×数量を合算し、買取合計金額を10円単位へ切り上げる。商品規格に紐づく明細は商品規格ごとに数量を集計し、在庫と在庫履歴を作る。
6. 受注にステータス・買取合計金額・明細・個別入力商品・在庫を設定し、査定担当者に認証した管理者会員を、更新日時に現在日時を設定する。指定ステータスが成立（1）の場合は成立日時を、それ以外の場合はキャンセル日時を現在日時に設定する。受注が適格請求書発行事業者に該当する場合は確認済みフラグを指定値で更新する。
7. 更新前と指定ステータスが異なる場合は、ステータス変更履歴を1件登録する。
8. 一連の保存を行い、コード200のJSONを返す。

## 集計条件

| 指標 | 集計の要点 |
|------|------------|
| 買取合計金額 | 送られた明細の単価×数量の総和を求め、10円単位へ切り上げる。 |
| 在庫数量 | 商品規格に紐づく明細を商品規格ごとに集計し、同一商品規格の数量を合算する。個別入力商品（商品規格IDなし）は在庫集計に含めない。 |

## 入出力

### リクエスト

| パラメータ | 位置 | 型 | 必須／任意 | 説明 |
|------------|------|----|-----------|------|
| `id` | パス | integer | 必須 | 更新対象の店頭買取受注ID。 |
| `order_status` | ボディ（フォーム値） | integer | 必須 | 更新後の店頭買取ステータスID。店頭買取ステータスマスタに存在する値であること。 |
| `order_details` | ボディ（フォーム値） | array | 必須 | 査定明細の配列。1件以上であること。各要素は明細1件分のオブジェクト。 |
| `order_details[].product_class_id` | ボディ（フォーム値） | integer | 任意 | 商品規格ID。空のときは個別入力商品として扱う。整数のみ。 |
| `order_details[].name` | ボディ（フォーム値） | string | 必須 | 商品名。最大65535文字。 |
| `order_details[].quantity` | ボディ（フォーム値） | integer | 任意 | 数量。整数のみ。 |
| `order_details[].price` | ボディ（フォーム値） | integer | 任意 | 単価。整数のみ。 |
| `order_details[].sell_price` | ボディ（フォーム値） | integer | 任意 | 販売価格。整数のみ。 |
| `order_details[].section_id` | ボディ（フォーム値） | integer | 任意 | 部門ID。整数のみ。該当部門が存在する場合のみ設定する。 |
| `qualified_invoice_issuer_confirmation_flg` | ボディ（フォーム値） | boolean | 任意 | 適格請求書発行事業者の確認済みフラグ。受注が適格請求書発行事業者に該当する場合のみ反映する。 |
| `jwt-token` | ヘッダ | string | 必須 | 認証用のJWTトークン。 |

ボディの項目はフォーム値として受け取り、明細各項目のキーはスネークケースで指定する。

### レスポンス（成功）

HTTP 200。

| フィールド | 型 | 説明 |
|------------|----|------|
| `code` | integer | 処理結果コード。成功時は200。 |

### レスポンス（失敗）

| HTTPステータス | 条件 | 本文の形 |
|----------------|------|----------|
| 401 | トークン欠落・署名不正・該当する管理者会員なし | 認証拒否（本文を持たない） |
| 404 | 受注IDに該当する店頭買取受注が無い | 該当なし（本文を持たない） |
| 400 | ステータス未指定 | `{code, errors}`（`errors`に「ステータスを選択してください。」を含む） |
| 400 | ステータスIDが店頭買取ステータスマスタに存在しない | `{code, errors}`（`errors`に「MtbOtcBuyOrderStatusに{指定ID}が見つかりません。」を含む） |
| 400 | 明細が未指定または空 | `{code, errors}`（`errors`に「1つ以上の商品を選んでください。」を含む） |
| 400 | 明細の商品名が未入力 | `{code, errors}`（`errors`に商品名必須の検証メッセージを含む） |
| 400 | 明細の商品名が最大長超過 | `{code, errors}`（`errors`に「商品名は、 65535 以下で入力してください。」を含む） |
| 400 | 明細の商品規格ID・数量・単価・販売価格・部門IDが整数でない | `{code, errors}`（`errors`に該当項目の整数形式メッセージを含む） |
| 500 | 削除・登録・保存処理中の例外 | 共通例外処理に委ねる |

検証エラーは複数件をまとめ、`errors`は文字列の配列とする。受注全体の検証と明細各件の検証を合算した全メッセージを返す。

### サンプルレスポンス

成功時の応答例。

```json
{
  "code": 200
}
```

入力不正時の応答例。

```json
{
  "code": 400,
  "errors": [
    "1つ以上の商品を選んでください。"
  ]
}
```

### 副作用

受注に紐づく既存の明細・個別入力商品・在庫・在庫履歴を削除し、送られた明細で作り直す（DB削除・登録）。受注のステータス・買取合計金額・査定担当者・更新日時を更新し、指定ステータスが成立のときは成立日時を、それ以外のときはキャンセル日時を更新する（DB更新）。受注が適格請求書発行事業者に該当する場合は確認済みフラグを更新する。更新前と指定ステータスが異なる場合は、ステータス変更履歴を1件登録する。履歴には受注ID・更新後ステータスID・更新担当者ID・登録日時を記録する。在庫履歴には更新後数量・登録者・登録日時を記録する。参照のみではない。

応答はJSON応答整形を経て返す。プロパティはcamelCase、日時はISO8601、`serialize_null`は有効とする。

## 業務ルール・計算

- 更新対象はリクエストで指定されたIDと認証・権限条件で特定できる既存レコードに限定する。
- 入力値は既存バリデーション、状態遷移可否、店舗・支店条件を満たす場合のみ保存する。
- 金額・ポイント・数量など派生値が関係する場合は既存サービスの計算結果を正とし、API層で独自の丸め・補正を行わない。
- 検証エラー、対象なし、権限不足、状態不整合では保存せず、既存のエラー形式で返す。

## データ整合性

| 観点 | 内容 |
|------|------|
| 参照時点 | 更新時点で存在する店頭買取受注・店頭買取ステータスマスタ・商品規格・部門マスタを対象に判定・更新する。 |

| 同時更新 | 同一受注への同時更新に対する排他制御は本APIでは持たない。 |

| 部門マスタ | 部門ID | 明細・個別入力商品の部門設定に用いる。 |
| 商品規格 | 商品規格ID | 明細・在庫の商品規格特定に用いる。 |
| 店頭買取ステータス変更履歴 | 受注ID・ステータスID・更新担当者ID・登録日時 | ステータス変更時に1件追加する。 |

---

## 権限・認可

| 利用者状態 | 店頭買取受注詳細更新 |
|------------|----------------------|
| 認証済みの管理者会員 | 受注の明細・ステータス・買取合計金額・査定担当者などを更新できる。 |
| 未認証・トークン不正 | 認証拒否（HTTP 401）となり、更新できない。 |

---

## エラー処理

| エラー内容 | 処理 |
|------------|------|
| 認証不可 | 認証拒否（HTTP 401）とする。 |
| 受注が存在しない | 該当なし（HTTP 404）とする。 |
| 入力検証エラー | 入力不正（HTTP 400）とし、全メッセージを`errors`配列で返す。削除・登録・保存は行わない。 |
| 削除・登録・保存処理中の例外 | 共通例外処理に委ねる（HTTP 500相当）。 |

---

## ログ・監査

ステータス変更時はステータス変更履歴を、在庫登録時は在庫履歴をDB上の業務履歴として永続化する。アプリケーションログとは別である。

### ログに出してはいけないもの

- JWTトークンの原値
- 署名シークレット（`auth_magic`）
- Cookie値・セッションIDの完全値

---

## 排他制御・トランザクション

本APIは明細・個別入力商品・在庫・在庫履歴の削除と再登録、受注更新、ステータス変更履歴の登録を行う。楽観ロック・悲観ロックの対象は持たず、同一受注への同時更新は後勝ちとなる。
