# API デッキビルダー — ログアウト

<!-- リバース詳細設計書（API・機能単位）。deck-api が提供する会員ログアウトAPI。 -->

## 概要

デッキビルダーアプリの利用者がログアウトし、クライアントが保持するアクセストークンのCookieを無効化するためのAPIである。deck-api（デッキビルダー用のAPIアプリケーション）が提供するJSON APIで、`jwt-token`ヘッダのトークンを検証して会員に紐づくプレイヤーを引き、認証できた場合にトークンCookieを空に設定して成功応答を返す。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。既存実装のふるまい、参照するデータ、判定境界、副作用を確認し、仕様の確からしさを把握することを目的とする。確認値はdeck-apiのログアウト処理、共通基底のトークン認証処理、ルート定義（`config/routes.yaml`）、照合先のプレイヤーデータを正とする。

本機能のカスタマイズ区分は現行踏襲であり、挙動はデッキビルダー用APIの現行実装（deck-api）を、DB関連はec-cube-enterpriseの実装を正とする。

対象はJSON APIエンドポイントであり、ブラウザ向けの画面を持たない。本文ではフレームワークのコントローラ型名やメソッド名を主説明としない。「利用者視点の入口」にHTTPメソッドとパスパターンを書く。

## リニューアル移行時の扱い

DB関連の記述はec-cube-enterpriseの実装を正とする。挙動は現行のデッキビルダー用API（deck-api）を正とする。現行と移行先でプレイヤーテーブルの主キー列名が異なる。

| 観点 | 現行（deck-api） | 移行先（ec-cube-enterprise） |
|------|------------------|------------------------------|
| プレイヤーテーブル | `dtb_player` | `dtb_player` |
| プレイヤーの主キー列 | `player_id` | `id` |
| 会員ID列 | `customer_id`（現行は`dtb_customer.customer_id`を参照） | `customer_id`（移行先は`dtb_customer.id`を参照） |

トークン認証・Cookie操作の挙動は現行と移行先で同じだが、プレイヤーテーブルの主キー列名（現行`player_id`、移行先`id`）と会員参照先の主キー列名が異なる。移行に伴うトークン仕様の変更は本書では確定しない。

## 用語

| 用語 | 説明 |
|------|------|
| デッキビルダーアプリ | デッキ作成・共有で利用するクライアント。本APIの呼び出し元。 |
| アクセストークン | ログイン時に発行する署名付きトークン。`jwt-token`ヘッダで送信する。 |
| プレイヤー | 会員に紐づくデッキビルダー上の利用者。トークンの`aud`（会員ID）から引く対象。 |

## 利用者視点の入口

| 入口 | URLエンドポイント | 期待されるふるまい |
|------|--------------------|--------------------|
| デッキビルダーアプリからのログアウト | `POST /user/logout` | `jwt-token`ヘッダのトークンを検証し、認証できた場合はトークンCookieを空に設定して成功（HTTP 200）のJSONを返す。ヘッダ欠落・トークン不正・該当プレイヤーなしは認証拒否（HTTP 401）のJSONを返す。 |

応答形式はJSON。呼び出し元はデッキビルダーアプリ。

---

## 認証・認可

| 観点 | 内容 |
|------|------|
| 認証方式 | `jwt-token`ヘッダのJWTを検証する。署名方式はHS256。ペイロードの`aud`（会員ID）でプレイヤーを引く。 |
| 照合先 | `aud`に対応する会員IDでプレイヤーを引く。プレイヤーが取得できた場合に認証成功とする。 |
| 認証失敗時 | `jwt-token`ヘッダが欠落、またはトークンの署名が不正な場合は認証拒否（HTTP 401）とし、メッセージ`Access Token is incorrect`を返す。該当プレイヤーが無い場合も認証拒否（HTTP 401）とし、メッセージ`Authentication failed`を返す。 |
| 認可 | ログイン済みのクライアント（有効なトークンを持つ会員）のみがログアウトできる。 |

トークン原値・署名シークレット・パスワードは本書に記載しない。

---

## 処理フロー

### 会員ログアウトを行う（POST `/user/logout`）

1. `jwt-token`ヘッダのトークンを検証する。ヘッダが欠落、または署名が不正な場合は認証拒否（HTTP 401）のJSONを返す。
2. トークンの`aud`（会員ID）でプレイヤーを引く。該当が無い場合は認証拒否（HTTP 401）のJSONを返す。
3. 認証できた場合、トークンCookieを空値に設定する。
4. コード200・メッセージ`Logout success`のJSONを返す。

## 入出力

### リクエスト

本APIはリクエストボディのパラメータを持たない。認証ヘッダのみを要求する。

| パラメータ | 位置 | 型 | 必須／任意 | 説明 |
|------------|------|----|-----------|------|
| `jwt-token` | ヘッダ | string | 必須 | ログイン時に取得したアクセストークン。検証して会員に紐づくプレイヤーを引く。 |

### レスポンス（成功）

HTTP 200。

| フィールド | 型 | 説明 |
|------------|----|------|
| `code` | integer | 結果コード。成功時は200。 |
| `message` | string | 結果メッセージ。成功時は`Logout success`。 |

### レスポンス（失敗）

| HTTPステータス | 条件 | 本文の形 |
|----------------|------|----------|
| 401 | `jwt-token`ヘッダの欠落、またはトークンの署名が不正 | `{code, message}`（`message`は`Access Token is incorrect`） |
| 401 | `aud`に対応するプレイヤーが存在しない | `{code, message}`（`message`は`Authentication failed`） |
| 500 | 処理中の例外 | deck-apiの共通例外処理に委ねる |

### サンプルレスポンス

成功時の応答例。

```json
{
  "code": 200,
  "message": "Logout success"
}
```

### 副作用

トークンCookieを空値に設定する（クライアント側のトークン保持を解除する）。サーバ側ではトークンの失効・ブラックリスト登録は行わず、業務データも更新しない。発行済みトークン自体は有効期限まで署名上有効なままである。

応答はJSON応答整形を経て返す。プロパティはcamelCase、日時はISO8601、`serialize_null`は有効とする。

## バリデーション

本APIはリクエストボディの入力検証を行わない。認証は`jwt-token`ヘッダの検証で行い、未充足時は認証拒否（HTTP 401）となる。

## 業務ルール・計算

- ログアウトは現在のセッションまたはトークンの無効化のみを行い、会員・注文・ポイント等の業務データは更新しない。
- 既に無効なセッションに対する要求は既存の認証エラーまたは冪等な成功応答の実装に従う。
- 金額・ポイント・在庫などの業務値は計算しない。

| 観点 | 内容 |
|------|------|
| 参照時点 | 照合するプレイヤーデータはログアウト呼び出し時点の値である。 |

## 権限・認可

| 利用者状態 | ログアウト |
|------------|------------|
| 有効なトークンを持つ会員 | ログアウトできる。トークンCookieを空に設定し成功応答を返す。 |
