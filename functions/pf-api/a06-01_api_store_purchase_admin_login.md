# API 店頭買取管理 — 買取アプリ用ログイン

## 概要

買取アプリ（MTGバイヤー）が利用者の資格情報で管理者ログインを行い、以降のAPI呼び出しに使うトークンを取得するためのAPIである。pf-api（買取連携用のAPIアプリケーション）が提供するJSON APIで、受け取ったログインIDとパスワードをEC-CUBE管理画面の買取アプリ用ログインへ中継し、認証成功時に会員情報とJWTトークンを返す。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。確認値はpf-apiのログイン中継処理、ルート定義（`config/routes.yaml`）、中継先であるEC-CUBE側（pf-eccube3 HareruyaEc）の買取アプリ用ログインAPIとそのファイアウォール設定を正とする。

本機能のカスタマイズ区分は現行踏襲で、挙動の参照リポはpf-api（中継先はpf-eccube3 HareruyaEc）とする。DB関連の記述（テーブル名・列名・永続化先）はec-cube-enterpriseを正とする。

対象はJSON APIエンドポイントであり、ブラウザ向けの画面を持たない。本文ではフレームワークのコントローラ型名やメソッド名を主説明としない。「利用者視点の入口」にHTTPメソッドとパスパターンを書く。

---

## 本書で扱うこと

- ログインIDとパスワードによる買取アプリ用ログインの中継
- 認証成功時に返す会員情報とJWTトークン、およびトークンの以降の用途
- 認証失敗時の応答

---

## 本書で扱わないこと

以下は本書では仕様確定せず、実装または別機能の設計を正とする。

- EC-CUBE管理ログイン本体の認証判定・二段階認証・試行制限（管理ログイン機能を正とする）
- 発行したトークンを用いる各買取APIの認可（各APIの設計を正とする）
- 中継先が参照する管理者会員・会員サブ・店舗の登録・編集（各管理機能を正とする）

## リニューアル移行時の扱い

挙動（ログイン中継・トークン発行）は現行（pf-api／中継先pf-eccube3）を正とし、応答を組み立てる際に参照する会員・店舗の永続化先は移行先（ec-cube-enterprise）を正とする。会員・店舗の参照モデルが現行と移行先で異なる。

| 区分 | 現行（pf-api／pf-eccube3） | 移行先（ec-cube-enterprise） |
|------|---------------------------|------------------------------|
| 管理者会員 | dtb_member（会員ID＝member_id、氏名） | dtb_member（id、氏名）。会員IDの主キー名がidになる点に注意 |
| 会員と店舗の関連 | 会員サブ（dtb_member_sub）のshop_idで所属店舗を引く | 会員サブ（dtb_member_sub）は廃止。会員（dtb_member）のbase_info_idが所属店舗、編集可能店舗はmember_base_info（dtb_member_base_info）で管理する |
| 店舗 | 店舗マスタ（mtb_shop）。店舗名・住所を保持 | 店舗＝BaseInfo（dtb_base_info）。店舗名・住所はBaseInfoの列を参照する |

応答フィールド（memberName・memberId・shopName・shopAddr・jwtToken）の構造と、トークンのペイロード（発行者・利用者ID＝管理者会員のID）はリニューアル後も同じ前提とするが、店舗名・店舗住所の取得元が店舗マスタ（mtb_shop）からBaseInfo（dtb_base_info）へ変わる。移行先での店舗紐付け（base_info_id）の取り回しはec-cube-enterprise実装で要確認とする。

## 用語

| 用語 | 説明 |
|------|------|
| 買取アプリ | 店頭買取で利用するクライアント（MTGバイヤー）。本APIの呼び出し元。 |
| JWTトークン | 認証成功時に発行する署名付きトークン。以降のpf-api買取系APIの認証に用いる。 |
| 買取アプリ用ログインAPI | 中継先となるEC-CUBE側のログイン用エンドポイント。認証済みの管理者会員情報とトークンをJSONで返す。 |

## 利用者視点の入口

| 入口 | URLエンドポイント | 期待されるふるまい |
|------|--------------------|--------------------|
| 買取アプリからのログイン | `POST /admin/login.json` | ログインIDとパスワードを中継して認証し、成功時は会員情報とJWTトークンのJSONを返す。失敗時は認証拒否（HTTP 401）のJSONを返す。 |
| 同上（拡張子なし別名） | `POST /admin/login` | 上と同一処理。 |

応答形式はJSON。呼び出し元は買取アプリ（MTGバイヤー）。

## 認証・認可

| 観点 | 内容 |
|------|------|
| 本APIの認証 | 本APIはトークン取得の入口であり、`jwt-token`ヘッダを要求しない。受け取ったログインID・パスワードを中継先の認証に委ねる。 |
| 認証の中継 | EC-CUBEの買取アプリ用ログイン画面へアクセスしてセッションを確立し、ログインID・パスワードをログイン確認へ送信して認証する。 |
| トークン発行 | 認証成功時、中継先が署名付きJWTトークンを発行して返す。トークンのペイロードは発行者と利用者ID（管理者会員のID）を持つ。署名方式はHS256。 |
| 以降の認可 | 呼び出し元は受け取ったトークンを以降のpf-api買取系APIの`jwt-token`ヘッダに付与する。各APIはトークンの利用者IDから管理者会員を引いて認可する（各APIの設計を正とする）。 |
| 認証失敗時 | 中継先が認証情報を返さない場合は認証拒否（HTTP 401）とする。 |

トークン原値・署名シークレット・パスワードは本書に記載しない。

## 処理フロー

### 買取アプリ用ログインを行う（POST `/admin/login.json`）

1. リクエストからログインIDとパスワードを受け取る。
2. 中継先のログイン画面へアクセスし、セッション確立用のCookieを一時ファイルに保存する。一時ファイル名はログインID別とする。
3. ログインIDとパスワードを、保存したCookieとともに中継先のログイン確認へ送信する。リダイレクトを追従し、認証成功時はEC-CUBE側の買取アプリ用ログインAPIに到達する。
4. 一時Cookieファイルを削除する。
5. 応答本文をJSONとして解釈する。
6. 解釈結果が空の場合は認証失敗とみなし、応答に含まれるエラー文言を抽出し、コード401とメッセージのJSONを返す。
7. 解釈できた場合は、中継先が返したJSON（会員名・会員ID・店舗名・店舗住所・JWTトークン）をそのまま返す。

## 業務ルール・計算

| 項目 | 内容 |
|------|------|
| 更新対象 | リクエストで指定されたID・入力値に対応する業務データを対象にする。対象特定、入力不正、認証・認可の判定順序は処理フローとバリデーションの各節を正とする。 |
| 更新方法 | 入力値を対象データへ上書きまたは追加登録する。履歴登録や関連データ更新がある場合は入出力の副作用およびDBカラムの節を正とする。 |
| 計算処理 | 本APIでは金額・税・ポイント・在庫数量の再計算や丸めを行わない。ステータスやコメント等の更新は、実装で定義された遷移・存在確認・担当者判定に従う。 |
| 応答値 | 成功時は処理結果コードまたは更新後に取得した値を返す。レスポンス値は本API内で独自集計せず、保存結果または取得結果をJSON応答へ整形する。 |

## 入出力

### リクエスト

| パラメータ | 位置 | 型 | 必須／任意 | 説明 |
|------------|------|----|-----------|------|
| `login_id` | ボディ（フォーム値） | string | 必須 | 管理者のログインID。中継先の認証に用いる。pf-api側では形式検証しない。 |
| `password` | ボディ（フォーム値） | string | 必須 | 管理者のパスワード。中継先の認証に用いる。pf-api側では形式検証しない。 |

### レスポンス（成功）

HTTP 200。

| フィールド | 型 | 説明 |
|------------|----|------|
| `memberName` | string | 認証した管理者会員の氏名。 |
| `memberId` | integer | 認証した管理者会員のID。発行するトークンの利用者IDにも対応する。 |
| `shopName` | string | 会員に紐づく店舗名。店舗が紐づかない場合は空文字。 |
| `shopAddr` | string | 会員に紐づく店舗住所。店舗が紐づかない場合は空文字。 |
| `jwtToken` | string | 発行したJWTトークン。以降のpf-api買取系APIの`jwt-token`ヘッダに用いる。 |

### レスポンス（失敗）

| HTTPステータス | 条件 | 本文の形 |
|----------------|------|----------|
| 401 | 中継先が認証情報を返さない（資格情報の誤り等による認証失敗） | `{code, message}`（`message`は中継先の画面エラー文言から改行表記を除いたもの） |
| 500 | 中継先への到達不可・処理中の例外 | pf-apiの共通例外処理に委ねる |

### サンプルレスポンス

成功時の応答例（秘匿値はプレースホルダ）。

```json
{
  "memberName": "山田太郎",
  "memberId": 12,
  "shopName": "晴れる屋テスト店",
  "shopAddr": "東京都千代田区0-0-0",
  "jwtToken": "<jwtToken>"
}
```

### 副作用

ログインID別の一時Cookieファイルの作成と削除。中継先でのログインセッション確立は中継先（管理ログイン）の範囲。pf-api自身は業務データを更新しない。

応答はJSON応答整形を経て返す。プロパティはcamelCase、日時はISO8601、`serialize_null`は有効とする。

## データ整合性

| 観点 | 内容 |
|------|------|
| 参照時点 | 返す会員情報・店舗情報は認証成功時点で中継先が保持する値である。 |

## DBカラム

本APIはpf-api自身では業務テーブルを参照しない。中継先が認証済みの管理者会員・会員サブ・店舗を参照して応答を組み立てる。直接関係する範囲のみを以下に示す。型や一覧の細部はスキーマを参照する。

| テーブル | 列 | メモ |
|----------|-----|------|
| 管理者会員（dtb_member） | 氏名・会員ID（移行先はid） | 応答の会員名・会員IDに用いる。トークンの利用者IDにも用いる。 |
| 店舗紐付け | 所属店舗 | 会員に紐づく店舗の特定に用いる。現行は会員サブ（dtb_member_sub）のshop_id、移行先は会員（dtb_member）のbase_info_idおよびmember_base_info。 |
| 店舗（移行先はBaseInfo＝dtb_base_info、現行はmtb_shop） | 店舗名・住所 | 応答の店舗名・店舗住所に用いる。 |

### DB操作

永続化の正は ec-cube-enterprise（テーブル名・操作は ec-cube-enterprise を正典）。当ドメインは承認ワークフローを介さず persist/flush で直接確定する（承認ワークフローは在庫機能固有）。

| 操作種別 | 対象テーブル | 契機・条件 |
|---------|--------------|------------|
| 登録/更新 | dtb_base_info / dtb_member / dtb_member_sub | 当機能が行う登録・更新で対象テーブルを直接保存する（不要な削除は含まない）。確定は persist/flush による即時反映。DB=ec-cube-enterprise を正典とする。 |

## 権限・認可

| 利用者状態 | 買取アプリ用ログイン |
|------------|----------------------|
| 未認証のクライアント | ログインのために呼び出せる。資格情報が正しい場合のみトークンを取得できる。 |

## エラー処理

| エラー内容 | 処理 |
|------------|------|
| 認証情報が返らない（認証失敗） | 応答からエラー文言を抽出し、コード401・メッセージのJSONを返す。画面上の理由文言をそのまま用い、pf-api独自の文言は設けない。 |
| 中継先への到達不可・処理中の例外 | pf-apiの共通例外処理に委ねる。本API独自のフォールバック文言は設けない。 |

---

## ログ・監査

### ログに出してはいけないもの

- パスワード
- JWTトークンの原値
- 署名シークレット（`auth_magic`）
- 一時Cookieファイルの中身・Cookie値
- セッションIDの完全値

---

## 排他制御・トランザクション

本APIは認証の中継と応答整形のみであり、業務トランザクションを張ってデータを更新しない。楽観ロック・悲観ロックの対象は持たない。中継時の一時CookieファイルはログインID別の名前で作成し、処理後に削除する。
