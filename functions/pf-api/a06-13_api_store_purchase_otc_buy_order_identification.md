# API 店頭買取管理 — 本人確認更新

## 概要

買取アプリ（MTGバイヤー）が店頭買取受注の本人確認情報（提示された証明書の種別）を更新するためのAPIである。pf-api（買取連携用のAPIアプリケーション）が提供するJSON APIで、受注IDで対象を特定し、本人確認証明書マスタに存在する証明書を設定して、更新担当者・更新日時とともに保存する。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。確認値はpf-apiの本人確認更新処理、ルート定義（`config/routes.yaml`）、店頭買取受注を扱うエンティティ、本人確認証明書マスタ、共通の認証処理を正とする。

カスタマイズ区分は現行踏襲。挙動の参照リポは現行の買取連携API（pf-api）とし、DB関連はec-cube-enterpriseを正とする。現行と移行先で異なる点は「リニューアル移行時の扱い」に集約する。

対象はJSON APIエンドポイントであり、ブラウザ向けの画面を持たない。本文ではフレームワークのコントローラ型名やメソッド名を主説明としない。「利用者視点の入口」にHTTPメソッドとパスパターンを書く。

---

## 本書で扱うこと

- 受注IDによる店頭買取受注の特定と、本人確認証明書・更新担当者・更新日時の保存
- 証明書IDの妥当性確認（本人確認証明書マスタの存在確認）
- 認証、対象なし、証明書ID不正時の応答

---

## 本書で扱わないこと

以下は本書では仕様確定せず、実装または別APIの設計を正とする。

- 店頭買取受注そのものの登録・査定・ステータス更新（各店頭買取APIの設計を正とする）
- 本人確認証明書マスタの登録・編集（マスタ管理の設計を正とする）
- オンライン本人確認の判定ロジック（本人確認機能の設計を正とする）
- トークンの発行（買取アプリ用ログインの設計を正とする）

## リニューアル移行時の扱い

現行（pf-api）と移行先（ec-cube-enterprise）でエンドポイントと認証方式、DB列の確認値が異なる。挙動は現行を正とし、DB関連は移行先を正とする。

| 観点 | 現行（pf-api） | 移行先（ec-cube-enterprise） |
|------|----------------|------------------------------|
| エンドポイント | `PUT /admin/otcBuyOrder/{id}/identification`（拡張子あり別名あり） | `PUT /{api_v1_route}/admin/otcBuyOrder/{id}/identification.json`（API版数プレフィックス付き） |
| 認証 | `jwt-token`ヘッダのJWT（HS256） | 共通の管理者認証。方式の差異はec-cube-enterprise実装で要確認 |
| 本人確認証明書の保存列 | 本人確認証明書（現行スキーマで要確認） | `dtb_otc_buy_order.identification_id`（`mtb_identification`への参照） |
| 更新担当者の保存列 | 更新担当者（現行スキーマで要確認） | `dtb_otc_buy_order.member_id`（`dtb_member`への参照） |
| 更新日時の保存列 | 更新日時（現行スキーマで要確認） | `dtb_otc_buy_order.update_date` |
| 本人確認証明書マスタ | 本人確認証明書マスタ（現行スキーマで要確認） | `mtb_identification`（`id`・`name`） |

ec-cube-enterprise実装では本人確認証明書（`identification_id`）・更新担当者（`member_id`）・更新日時（`update_date`）の3列のみを更新する。

## 利用者視点の入口

| 入口 | URLエンドポイント | 期待されるふるまい |
|------|--------------------|--------------------|
| 店頭買取受注の本人確認更新 | `PUT /admin/otcBuyOrder/{id}/identification` | 受注IDの店頭買取受注に本人確認証明書を設定し、更新担当者・更新日時とともに保存して、成功時はコード200のJSONを返す。 |
| 同上（拡張子あり別名） | `PUT /admin/otcBuyOrder/{id}/identification.json` | 上と同一処理。 |

## 認証・認可

| 観点 | 内容 |
|------|------|
| 認証方式 | `jwt-token`ヘッダのJWTを検証し、ペイロードの利用者IDから管理者会員を引く。署名方式はHS256。 |
| 認証失敗時 | ヘッダ欠落・署名不正・該当する管理者会員なしのいずれも認証拒否（HTTP 401）とする。 |
| 認可 | 認証した管理者会員が更新担当者として記録される。呼び出し可能なクライアントは買取アプリ。 |

トークン原値・署名シークレットは本書に記載しない。

---

## 処理フロー

### 店頭買取受注の本人確認を更新する（PUT `/admin/otcBuyOrder/{id}/identification`）

1. `jwt-token`ヘッダのトークンを検証し、管理者会員を特定する。検証できない場合は認証拒否（HTTP 401）とする。
2. パスの受注IDで店頭買取受注を1件取得する。該当が無い場合は該当なし（HTTP 404）とする。
3. リクエストの証明書IDで本人確認証明書マスタを引く。該当が無い場合は入力不正（HTTP 400）とし、エラーメッセージを返す。
4. 店頭買取受注に本人確認証明書を設定し、更新担当者に認証した管理者会員を、更新日時に現在時刻を設定して保存する。
5. コード200のJSONを返す。

## 業務ルール・計算

| 項目 | 内容 |
|------|------|
| 更新対象 | リクエストで指定されたID・入力値に対応する業務データを対象にする。対象特定、入力不正、認証・認可の判定順序は処理フローとバリデーションの各節を正とする。 |
| 更新方法 | 入力値を対象データへ上書きまたは追加登録する。履歴登録や関連データ更新がある場合は入出力の副作用およびDBカラムの節を正とする。 |
| 計算処理 | 本APIでは金額・税・ポイント・在庫数量の再計算や丸めを行わない。ステータスやコメント等の更新は、実装で定義された遷移・存在確認・担当者判定に従う。 |
| 応答値 | 成功時は処理結果コードまたは更新後に取得した値を返す。レスポンス値は本API内で独自集計せず、保存結果または取得結果をJSON応答へ整形する。 |

## 入出力

### リクエスト

| パラメータ | 位置 | 型 | 必須／任意 | 説明 |
|------------|------|----|-----------|------|
| `id` | パス | integer | 必須 | 更新対象の店頭買取受注ID。 |
| `identification` | ボディ（フォーム値） | integer | 必須 | 設定する本人確認証明書のID。本人確認証明書マスタに存在しない値の場合は入力不正（HTTP 400）となる。 |
| `jwt-token` | ヘッダ | string | 必須 | 認証用のJWTトークン。 |

### レスポンス（成功）

HTTP 200。

| フィールド | 型 | 説明 |
|------------|----|------|
| `code` | integer | 処理結果コード。成功時は200。 |

### レスポンス（失敗）

| HTTPステータス | 条件 | 本文の形 |
|----------------|------|----------|
| 401 | トークン欠落・署名不正・該当する管理者会員なし | 認証拒否（本文を持たない） |
| 404 | 受注IDに該当する店頭買取受注が無い | 該当なし（本文を持たない） |
| 400 | 証明書IDが本人確認証明書マスタに存在しない（未指定を含む） | `{code, errors}`（`errors`は「正しい証明書IDを入力してください」） |

### サンプルレスポンス

成功時の応答例。

```json
{
  "code": 200
}
```

### 副作用

店頭買取受注の本人確認証明書・更新担当者・更新日時を更新する（DB更新）。参照のみではない。

応答はJSON応答整形を経て返す。プロパティはcamelCase、日時はISO8601とする。

## バリデーション

| 項目 | 内容 |
|------|------|
| `identification` | 必須。本人確認証明書マスタに存在するIDのみ受け付ける。未指定・存在しないIDの場合は入力不正（HTTP 400）とし、「正しい証明書IDを入力してください」を返す。 |
| `id` | パスの受注ID。該当する店頭買取受注が無い場合は該当なし（HTTP 404）とする。 |

## データ整合性

| 観点 | 内容 |
|------|------|
| 参照時点 | 更新時点で存在する店頭買取受注を対象に更新する。 |
| 更新範囲 | 本人確認証明書・更新担当者・更新日時のみを更新する。受注の他項目・ステータスは本APIでは変更しない。 |
| 同時更新 | 同一受注への同時更新に対する排他制御は本APIでは持たない。 |

## DBカラム

機能に直接関係する列のみ記載する。DB関連の記述はec-cube-enterpriseの実装を正とする。型や一覧の細部はスキーマを参照する。

| テーブル | 列 | メモ |
|----------|-----|------|
| 店頭買取受注（`dtb_otc_buy_order`） | `id`（受注ID） | 受注の特定に用いる。 |
| 店頭買取受注（`dtb_otc_buy_order`） | `identification_id`（本人確認証明書） | 更新対象。証明書IDに対応する`mtb_identification`を設定する。 |
| 店頭買取受注（`dtb_otc_buy_order`） | `member_id`（更新担当者） | 認証した管理者会員を記録する。 |
| 店頭買取受注（`dtb_otc_buy_order`） | `update_date`（更新日時） | 更新時の現在時刻を記録する。 |
| 本人確認証明書マスタ（`mtb_identification`） | `id` | 指定された証明書IDの存在確認に用いる。 |

### DB操作

永続化の正は ec-cube-enterprise（テーブル名・操作は ec-cube-enterprise を正典）。当ドメインは承認ワークフローを介さず persist/flush で直接確定する（承認ワークフローは在庫機能固有）。

| 操作種別 | 対象テーブル | 契機・条件 |
|---------|--------------|------------|
| 登録/更新 | dtb_otc_buy_order / mtb_identification | 当機能が行う登録・更新で対象テーブルを直接保存する（不要な削除は含まない）。確定は persist/flush による即時反映。DB=ec-cube-enterprise を正典とする。 |

## 権限・認可

| 利用者状態 | 本人確認更新 |
|------------|--------------|
| 認証済みの管理者会員 | 本人確認証明書・更新担当者・更新日時を更新できる。 |
| 未認証・トークン不正 | 認証拒否（HTTP 401）となり、更新できない。 |

## エラー処理

| エラー内容 | 処理 |
|------------|------|
| 認証不可 | 認証拒否（HTTP 401）とする。 |
| 受注が存在しない | 該当なし（HTTP 404）とする。 |
| 証明書IDが不正 | 入力不正（HTTP 400）とし、「正しい証明書IDを入力してください」を返す。 |

## ログ・監査

### ログに出してはいけないもの

- JWTトークンの原値
- 署名シークレット（`auth_magic`）
- Cookie値・セッションIDの完全値
- 本人確認に関わる個人情報の具体値

## 排他制御・トランザクション

本APIは本人確認証明書・更新担当者・更新日時の更新を行う。楽観ロック・悲観ロックの対象は持たず、同一受注への同時更新は後勝ちとなる。
