# API デッキビルダー — デッキ情報登録

## 概要

デッキビルダーアプリの利用者（プレイヤー）が、自身のデッキ情報を新規登録するためのAPIである。deck-api（デッキビルダー用のAPIアプリケーション）が提供するJSON APIで、デッキ名・フォーマット・公開範囲・採用カードなどを受け取り、デッキ本体と採用カードをデータベースへ保存する。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。確認値はdeck-apiのデッキ登録処理、ルート定義（`config/routes.yaml`）、デッキ保存処理（デッキ保存サービス）、デッキを扱うエンティティ、共通の認証処理を正とする。本機能のカスタマイズ区分は現行踏襲であり、挙動はデッキビルダーAPI（deck-api）の実装を参照し、DB関連の記述はec-cube-enterpriseを正とする。

対象はJSON APIエンドポイントであり、ブラウザ向けの画面を持たない。本文ではフレームワークのコントローラ型名やメソッド名を主説明としない。「利用者視点の入口」にHTTPメソッドとパスパターンを書く。

---

## 本書で扱うこと

- 認証したプレイヤーによるデッキ情報の新規登録と、採用カードの保存
- 登録時のレギュレーション違反判定と入力検証
- 限定公開デッキの閲覧用トークン発行
- 認証失敗・入力不正・処理失敗時の応答

---

## 本書で扱わないこと

以下は本書では仕様確定せず、実装または別APIの設計を正とする。

- 既存デッキの更新・削除・参照（デッキ情報更新・デッキ情報削除・デッキ情報参照の各APIの設計を正とする）
- デッキリスト文字列からのインポート登録（デッキインポートAPIの設計を正とする）
- カードマスタ・フォーマットマスタ・アーキタイプ等のマスタ管理
- トークンの発行（デッキビルダー用ログインの設計を正とする）

## リニューアル移行時の扱い

DB関連の記述はec-cube-enterpriseを正とする。挙動の参照元であるデッキビルダーAPI（deck-api）は提供リポジトリに含まれないため、現行deck-apiと移行先ec-cube-enterpriseでスキーマが異なる場合はec-cube-enterpriseを正とし、確認できない差異はec-cube-enterprise実装で要確認とする。ec-cube-enterpriseでは、デッキ本体（`dtb_deck`）が識別子（`deck_id`）・デッキ名（`deck_name`）・フォーマット（`format_id`）・アーキタイプ（`archetype_id`）・代表カード画像（`card_image_id`）・プレイヤー（`player_id`）・プレイヤー名（`player_name`）・限定公開トークン（`display_token`）・レギュレーション違反フラグ（`regulation_violation_flg`）・作成日時（`create_date`）・更新日時（`update_date`）を持ち、採用カードは採用カード（`dtb_deck_card`）の`deck_id`・`card_id`・`board_id`・`count`で保存する。メイビー・アトラクション・ステッカーは`dtb_maybe_card`・`dtb_attraction_card`・`dtb_sticker_card`に分かれる。

| 観点 | 現行（deck-api） | 移行先（ec-cube-enterprise） |
|------|------------------|------------------------------|
| デッキ本体テーブル | deck-api実装で要確認 | デッキ（`dtb_deck`） |
| 採用カードテーブル | deck-api実装で要確認 | 採用カード（`dtb_deck_card`）。ボード区分は`board_id`、枚数は`count` |
| メイビー・アトラクション・ステッカー | 各区分のカード | `dtb_maybe_card`・`dtb_attraction_card`・`dtb_sticker_card` |
| 公開範囲の保持 | リクエスト`scope_id`（公開1・非公開2・限定公開3） | デッキリスト非公開フラグ（`private_flg`）と限定公開トークン（`display_token`）で表現。`scope_id`列の有無はec-cube-enterprise実装で要確認 |

## 用語

| 用語 | 説明 |
|------|------|
| デッキ | プレイヤーが作成するカードの組み合わせ。デッキIDで一意に特定する。 |
| プレイヤー | デッキビルダーの利用者。トークンから特定する会員。 |
| ボード | カードの配置区分。メインボード・サイドボード・統率領域・メイビー・アトラクション・ステッカーがある。 |
| 公開範囲 | デッキの公開区分。公開・非公開・限定公開がある。 |
| 限定公開トークン | 限定公開デッキを閲覧するための識別子。登録時に発行する。 |
| レギュレーション違反 | フォーマットの枚数範囲・禁止制限・統率領域条件などに反する状態。 |

## 利用者視点の入口

| 入口 | URLエンドポイント | 期待されるふるまい |
|------|--------------------|--------------------|
| デッキ情報の新規登録 | `POST /deck` | 認証したプレイヤーのデッキ本体と採用カードを保存し、成功時はコード200と発番したデッキIDのJSONを返す。 |

応答形式はJSON。呼び出し元はデッキビルダーアプリ。

## 認証・認可

| 観点 | 内容 |
|------|------|
| 認証方式 | `jwt-token`ヘッダのJWTを検証し、ペイロード`aud`の顧客IDからプレイヤーを引く。署名方式はHS256。 |
| 認証失敗時 | ヘッダ欠落・署名不正・該当するプレイヤーなしのいずれも認証拒否（HTTP 401）とし、`{code, message}`を返す。 |
| 認可 | 認証したプレイヤーが登録デッキの所有者となる。呼び出し可能なクライアントはデッキビルダーアプリ。 |

トークン原値・署名シークレットは本書に記載しない。

## 処理フロー

### デッキ情報を新規登録する（POST `/deck`）

1. `jwt-token`ヘッダのトークンを検証し、プレイヤーを特定する。検証できない場合は認証拒否（HTTP 401）とし、`{code, message}`を返す。
2. リクエストボディの全パラメータを受領し、新規デッキを生成する。
3. 採用カードを受け取り、ボード区分ごとに採用カード・メイビー・アトラクション・ステッカーとして組み立てる。各カードの整合性を検証し、不正な場合は入力不正（HTTP 400）とする。
4. フォーマット・アーキタイプ・公開範囲・代表カード画像・キャンペーンタグを解決し、デッキ本体に設定する。設定済み内容からレギュレーション違反を判定する。
5. デッキ本体の整合性を検証し、不正な場合は入力不正（HTTP 400）とする。
6. デッキ本体と採用カードを保存する。限定公開トークン未設定の場合は、発番したデッキIDから閲覧用トークンを生成して保存する。一連の保存は1件のトランザクションで行い、例外時はロールバックする。
7. 成功時はコード200・メッセージ・デッキIDを返す。公開範囲が限定公開の場合は閲覧用トークンも返す。

## 業務ルール・計算

| 項目 | 内容 |
|------|------|
| 更新対象 | リクエストで指定されたID・入力値に対応する業務データを対象にする。対象特定、入力不正、認証・認可の判定順序は処理フローとバリデーションの各節を正とする。 |
| 更新方法 | 入力値を対象データへ上書きまたは追加登録する。履歴登録や関連データ更新がある場合は入出力の副作用およびDBカラムの節を正とする。 |
| 計算処理 | 本APIでは金額・税・ポイント・在庫数量の再計算や丸めを行わない。ステータスやコメント等の更新は、実装で定義された遷移・存在確認・担当者判定に従う。 |
| 応答値 | 成功時は処理結果コードまたは更新後に取得した値を返す。レスポンス値は本API内で独自集計せず、保存結果または取得結果をJSON応答へ整形する。 |

## 入出力

### リクエスト

リクエストボディはフォーム送信形式で受け取り、全キーをそのまま参照する。位置はいずれもボディ。

| パラメータ | 位置 | 型 | 必須／任意 | 説明 |
|------------|------|----|-----------|------|
| `jwt-token` | ヘッダ | string | 必須 | 認証用のJWTトークン。 |
| `deck_name` | ボディ | string | 任意 | デッキ名。未指定時はnullで保存する。 |
| `format_id` | ボディ | integer | 任意 | フォーマットの識別子。空でない場合にフォーマットを解決する。レギュレーション判定に用いる。 |
| `archetype_id` | ボディ | integer | 任意 | アーキタイプの識別子。空でない場合に解決する。 |
| `scope_id` | ボディ | integer | 任意 | 公開範囲。公開（1）・非公開（2）・限定公開（3）。限定公開時はトークンを応答に含める。 |
| `image_card_id` | ボディ | integer | 任意 | 代表カード画像に用いるカードID。未指定時はアーキタイプの画像などで補完する。 |
| `campaign_tag_ids` | ボディ | integer または array | 任意 | キャンペーンタグの識別子。単一値・配列のいずれも受け付ける。 |
| `cards` | ボディ | array | 任意 | 採用カードの配列。各要素は子フィールドを持つ。 |
| `cards[].card_id` | ボディ | integer | 任意 | 採用カードのカードID。 |
| `cards[].board_id` | ボディ | integer | 必須（cards指定時） | 配置ボード。メイン（1）・サイド（2）・統率領域（3）・メイビー（4）・アトラクション（5）・ステッカー（6）。 |
| `cards[].count` | ボディ | integer | 必須（cards指定時） | 採用枚数。 |

### レスポンス（成功）

HTTP 200。

| フィールド | 型 | 説明 |
|------------|----|------|
| `code` | integer | 処理結果コード。成功時は200。 |
| `message` | string | 処理結果メッセージ。成功時は「Deck register success」。 |
| `deck_id` | integer | 発番したデッキの識別子。 |
| `display_token` | string | 限定公開デッキの閲覧用トークン。公開範囲が限定公開（3）のときのみ含める。 |

### レスポンス（失敗）

| HTTPステータス | 条件 | 本文の形 |
|----------------|------|----------|
| 401 | トークン欠落・署名不正・該当するプレイヤーなし | `{code, message}`（messageは「Access Token is incorrect」または「Authentication failed」） |
| 400 | 採用カードまたはデッキ本体の整合性検証に失敗 | `{code, message}`（messageは検証エラー内容） |
| 500 | 保存処理中の例外 | `{code, message}`（messageは例外メッセージ） |

### サンプルレスポンス

成功時の応答例（公開範囲が限定公開の場合）。

```json
{
  "code": 200,
  "message": "Deck register success",
  "deck_id": 12345,
  "display_token": "<displayToken>"
}
```

### 副作用

デッキ本体・採用カード・メイビーカード・アトラクションカード・ステッカーカードを新規保存する（DB更新）。限定公開トークンを生成して保存する。本登録APIはRedis一時保存を行わない。参照のみではない。

応答はJSON応答整形を経て返す。プロパティはJSONキーに準じ、`serialize_null`は有効とする。

## バリデーション

| 項目 | 内容 |
|------|------|
| 採用カード | ボード区分ごとに採用カード・メイビー・アトラクション・ステッカーとして組み立て、各エンティティの制約を検証する。未充足時は入力不正（HTTP 400）とする。 |
| デッキ本体 | フォーマット・公開範囲・採用カードを設定したうえでデッキ本体の制約を検証する。未充足時は入力不正（HTTP 400）とし、エラーメッセージを返す。 |
| レギュレーション違反 | フォーマットの統率領域・メインボード・サイドボードの枚数範囲、禁止制限カード、4枚制限、フォーマット適合、統率領域の伝説条件を判定する。違反はフラグとして保存し、登録自体は妨げない。 |

## データ整合性

| 観点 | 内容 |
|------|------|
| 参照時点 | 登録時点のマスタ（フォーマット・カード・アーキタイプ等）を解決して保存する。 |
| 更新範囲 | デッキ本体と採用カードを新規に作成する。所有者は認証したプレイヤーで固定する。 |
| 限定公開トークン | デッキID発番後に生成して保存するため、登録完了時点で確定する。 |

## DBカラム

機能に直接関係する列のみ記載する。型や一覧の細部はスキーマを参照する。

テーブル名・列名はec-cube-enterpriseの定義を正とする。

| テーブル | 列 | メモ |
|----------|-----|------|
| デッキ（`dtb_deck`） | デッキID（`deck_id`） | 保存時に発番する。 |
| デッキ（`dtb_deck`） | デッキ名（`deck_name`）・フォーマット（`format_id`）・アーキタイプ（`archetype_id`）・代表カード画像（`card_image_id`）・プレイヤー（`player_id`）・プレイヤー名（`player_name`） | 登録対象。公開範囲は非公開フラグ（`private_flg`）と限定公開トークン（`display_token`）で表現する。 |
| デッキ（`dtb_deck`） | 限定公開トークン（`display_token`） | デッキID発番後に生成して保存する。 |
| デッキ（`dtb_deck`） | レギュレーション違反フラグ（`regulation_violation_flg`） | 設定内容から判定して保存する。 |
| デッキ（`dtb_deck`） | 作成日時（`create_date`）・更新日時（`update_date`） | 登録時に現在日時を設定する。 |
| 採用カード（`dtb_deck_card`） | デッキ（`deck_id`）・カード（`card_id`）・ボード（`board_id`）・枚数（`count`） | 採用カードごとに保存する。 |
| メイビーカード（`dtb_maybe_card`）・アトラクションカード（`dtb_attraction_card`）・ステッカーカード（`dtb_sticker_card`） | デッキ・カード・枚数 | 対応ボードのカードを保存する。 |

### DB操作

永続化の正は ec-cube-enterprise（テーブル名・操作は ec-cube-enterprise を正典）。当ドメインは承認ワークフローを介さず persist/flush で直接確定する（承認ワークフローは在庫機能固有）。

| 操作種別 | 対象テーブル | 契機・条件 |
|---------|--------------|------------|
| 登録/更新 | dtb_attraction_card / dtb_deck / dtb_deck_card / dtb_maybe_card / dtb_sticker_card | 当機能が行う登録・更新で対象テーブルを直接保存する（不要な削除は含まない）。確定は persist/flush による即時反映。DB=ec-cube-enterprise を正典とする。 |

## ログ・監査

### ログに出してはいけないもの

- JWTトークンの原値
- 署名シークレット（`auth_magic`）
- 限定公開トークンの原値
- Cookie値・セッションIDの完全値

---

## 排他制御・トランザクション

本APIはデッキ本体と採用カードの保存を1件のトランザクションで行い、例外時はロールバックする。新規登録のため既存デッキとの競合は持たず、楽観ロック・悲観ロックの対象は持たない。
