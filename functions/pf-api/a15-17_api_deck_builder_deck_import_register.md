# API デッキビルダー — デッキ登録インポート

## 概要

デッキビルダーアプリが、デッキリストのテキスト（カードリスト）を貼り付けてデッキを新規登録するためのAPIである。deck-api（デッキビルダー用のAPIアプリケーション）が提供するJSON APIで、`jwt-token`ヘッダから特定したプレイヤーを所有者として、カードリストを解読してデッキを作成し保存する。本書は新規登録（パスにデッキ識別子を持たないPOST）を対象とする。

本機能のカスタマイズ区分は現行踏襲であり、挙動は現行実装（deck-api）を参照し、DB関連はec-cube-enterpriseを正とする。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。確認値はdeck-apiのデッキインポート処理、ルート定義（`config/routes.yaml`）、デッキ保存サービス・カードリスト解読処理、共通の認証処理を正とする。

対象はJSON APIエンドポイントであり、ブラウザ向けの画面を持たない。本文ではフレームワークのコントローラ型名やメソッド名を主説明としない。「利用者視点の入口」にHTTPメソッドとパスパターンを書く。

---

## 本書で扱うこと

- カードリストテキストの解読とデッキの新規登録
- 認証したプレイヤーを所有者として保存すること
- 解読できなかった行（カード名未一致）の扱いと部分成功（HTTP 206）
- 非公開・限定公開時の表示用トークンの扱い

---

## 本書で扱わないこと

以下は本書では仕様確定せず、実装または別APIの設計を正とする。

- 既存デッキの更新インポート（デッキ更新インポートAPI `PUT /deck/import/{id}`の設計を正とする）
- カードリストを用いない通常のデッキ新規登録（`POST /deck`の設計を正とする）
- デッキの参照・検索・削除（各デッキAPIの設計を正とする）
- トークンの発行（デッキビルダー用ログインの設計を正とする）

## リニューアル移行時の扱い

現行（deck-api）と移行先（ec-cube-enterprise）でデッキ永続化のスキーマに差がある。DB関連の記述は移行先を正とし、確認できた差を以下に記録する。

| 項目 | 現行（deck-api） | 移行先（ec-cube-enterprise） |
|------|------------------|------------------------------|
| 公開区分 | 公開区分（`scope_id`、公開・非公開・限定公開の3値） | 非公開フラグ（`dtb_deck.private_flg`、真偽）と閲覧用トークン（`dtb_deck.display_token`）に分けて保持する。3値の公開区分の移行可否はec-cube-enterprise実装で要確認。 |
| 所有者 | 認証したプレイヤーを所有者とする | `dtb_deck.player_id`（プレイヤー `dtb_player`）。あわせて会員参照 `member_id` を持つ。 |
| デッキ本文 | メイン・サイド・統率者の本文 | `dtb_deck.text_main`・`text_side`・`text_command`（テキスト列）にメイン・サイド・統率を保持し、カード明細を `dtb_deck_card`（`board_id` で区分）に保持する。 |
| ボード外区分 | メイビー・アトラクション・ステッカー | 別表 `dtb_maybe_card`・`dtb_attraction_card`・`dtb_sticker_card`（いずれも `deck_id`・`card_id`・`count`）。 |
| 削除方式 | 実装で要確認 | `dtb_deck.deleted_at` による論理削除。 |

## 用語

| 用語 | 説明 |
|------|------|
| プレイヤー | デッキビルダーの利用者。会員（顧客）に紐づき、`aud`の顧客IDで特定する。 |
| カードリスト | デッキ内容を表すテキスト（枚数とカード名の行を並べた形式）。`card_list`として受け取る。 |
| ボード | メインボード・サイドボード・統率者などデッキ内の区分。カードリストの区切り文字列で切り替える。 |
| 表示用トークン | 限定公開デッキを参照するための識別子。`display_token`として返す。 |

## 利用者視点の入口

| 入口 | URLエンドポイント | 期待されるふるまい |
|------|--------------------|--------------------|
| デッキ登録インポート | `POST /deck/import` | `jwt-token`ヘッダから特定したプレイヤーを所有者として、`card_list`を解読してデッキを新規登録し、新規デッキ識別子をコード200のJSONで返す。解読できない行があるときはコード206を返す。 |

応答形式はJSON。呼び出し元はデッキビルダーアプリ。同一の処理がパスにデッキ識別子を持つPUTでも呼ばれ、その場合は更新となる（本書では新規登録のPOSTのみを扱う）。

## 認証・認可

| 観点 | 内容 |
|------|------|
| 認証方式 | `jwt-token`ヘッダのJWTを検証し、ペイロードの`aud`の顧客IDから顧客IDに対応するプレイヤーを引く。署名方式はHS256。 |
| 認証失敗時 | ヘッダ欠落・署名不正・該当するプレイヤーなしのいずれも認証拒否（HTTP 401）とし、本文は`{code, message}`で返す。 |
| 認可 | 認証したプレイヤーを新規デッキの所有者として登録する。呼び出し可能なクライアントはデッキビルダーアプリ。 |

トークン原値・署名シークレットは本書に記載しない。

## 処理フロー

### デッキを新規登録する（POST `/deck/import`）

1. `jwt-token`ヘッダのトークンを検証し、プレイヤーを特定する。検証できない、または該当するプレイヤーがない場合は認証拒否（HTTP 401）とし、`{code, message}`を返す。
2. パスにデッキ識別子を持たないPOSTのため、新規デッキを対象とする（既存デッキの取得・所有者照合は行わない）。
3. ボディの`format_id`からフォーマットを取得し、`card_list`をフォーマットの統率者使用設定に応じて解読する。解読結果のカード配列を`cards`としてリクエストに組み込む。
4. 解読したカードと`deck_name`・`scope_id`・`archetype_id`等を用いてデッキを組み立て、検証を通過したらデータベースに保存する。あわせて当該デッキのRedis上の下書きを削除する。検証エラーは入力不正（HTTP 400）とし、その他の例外は処理失敗（HTTP 500）とする。
5. 新規デッキ識別子（`deck_id`）を含むコード200のJSONを返す。公開区分が限定公開のときは表示用トークン（`display_token`）も返す。
6. カードリストに解読できない行（カード名未一致）がある場合は、コードを206に切り替え、該当行の行番号を`errors`として返す。

## 業務ルール・計算

| 項目 | 内容 |
|------|------|
| 更新対象 | リクエストで指定されたID・入力値に対応する業務データを対象にする。対象特定、入力不正、認証・認可の判定順序は処理フローとバリデーションの各節を正とする。 |
| 更新方法 | 入力値を対象データへ上書きまたは追加登録する。履歴登録や関連データ更新がある場合は入出力の副作用およびDBカラムの節を正とする。 |
| 計算処理 | 本APIでは金額・税・ポイント・在庫数量の再計算や丸めを行わない。ステータスやコメント等の更新は、実装で定義された遷移・存在確認・担当者判定に従う。 |
| 応答値 | 成功時は処理結果コードまたは更新後に取得した値を返す。レスポンス値は本API内で独自集計せず、保存結果または取得結果をJSON応答へ整形する。 |

## 入出力

### リクエスト

| パラメータ | 位置 | 型 | 必須／任意 | 説明 |
|------------|------|----|-----------|------|
| `jwt-token` | ヘッダ | string | 必須 | 認証用のJWTトークン。検証して`aud`の顧客IDからプレイヤーを引く。 |
| `format_id` | ボディ（フォーム値） | integer | 必須 | デッキのフォーマット識別子。カードリスト解読時の統率者使用設定の判定に用いる。 |
| `card_list` | ボディ（フォーム値） | string | 任意 | デッキ内容のテキスト。枚数とカード名の行を並べた形式。未指定・空のときは空のカード配列として扱う。 |
| `deck_name` | ボディ（フォーム値） | string | 任意 | デッキ名。 |
| `scope_id` | ボディ（フォーム値） | integer | 任意 | 公開区分（公開・非公開・限定公開）。限定公開のとき応答に表示用トークンを含める。 |
| `archetype_id` | ボディ（フォーム値） | integer | 任意 | アーキタイプ識別子。 |
| `image_card_id` | ボディ（フォーム値） | integer | 任意 | デッキ画像に用いるカード識別子。 |
| `campaign_tag_ids` | ボディ（フォーム値） | integer または array | 任意 | 紐づけるキャンペーンタグ識別子。 |

カードリストの行数の上限は500行で、超過時は入力不正（HTTP 400）となる。

### レスポンス（成功）

HTTP 200（解読できない行がある場合はHTTP 206）。応答本体はラッパオブジェクトで、JSONキーはsnake_caseで組み立てる。

| フィールド | 型 | 説明 |
|------------|----|------|
| `code` | integer | 処理結果コード。全行解読できたときは200、解読できない行があるときは206。 |
| `message` | string | 処理結果メッセージ。新規登録時は「Deck registration success by import」。 |
| `deck_id` | integer | 登録したデッキの識別子。 |
| `display_token` | string | 限定公開のときのみ含まれる表示用トークン。 |
| `errors` | array | 解読できない行がある場合のみ含まれる、該当行の行番号（0始まりのインデックス）の配列。 |

### レスポンス（失敗）

| HTTPステータス | 条件 | 本文の形 |
|----------------|------|----------|
| 401 | `jwt-token`ヘッダ欠落・署名不正・`aud`に該当するプレイヤーなし | `{code, message}`（`message`は「Access Token is incorrect」または「Authentication failed」） |
| 400 | 検証失敗（必須項目不足・不正値）、またはカードリストが上限行数超過 | `{code, message}`（`message`は検証エラーメッセージ） |
| 500 | 保存処理中のその他の例外 | `{code, message}`（`message`は例外メッセージ） |

### サンプルレスポンス

新規登録の成功例（実装確認値に基づく代表値）。

```json
{
  "code": 200,
  "message": "Deck registration success by import",
  "deck_id": 12345
}
```

解読できない行がある場合の例（限定公開）。

```json
{
  "code": 206,
  "message": "Deck registration success by import",
  "deck_id": 12345,
  "display_token": "<displayToken>",
  "errors": [3, 7]
}
```

### 副作用

デッキ・デッキカード（メイン・サイド・統率者・メイビー・アトラクション・ステッカー）をデータベースに新規登録する（DB更新）。あわせて当該デッキのRedis上の下書きを削除する。保存は単一のトランザクション内で行い、例外時はロールバックする。

応答はJSON応答整形を経て返す。本APIは連想配列を組み立てて返すため、JSONキーは実装で記述したsnake_case（`code`・`message`・`deck_id`・`display_token`・`errors`）となる。`serialize_null`は有効とする。

## バリデーション

| 項目 | 内容 |
|------|------|
| `jwt-token` | 必須。ヘッダ欠落・署名不正・該当プレイヤーなしのいずれも認証拒否（HTTP 401）とする。 |
| `card_list` | 任意。500行を超える場合は入力不正（HTTP 400）とし、上限超過のメッセージを返す。解読できない行は登録を中断せず、行番号を`errors`に記録してコード206とする。 |
| デッキ内容 | デッキ・デッキカードは保存サービスの検証を通す。必須項目不足・不正値など検証エラーは入力不正（HTTP 400）とし、検証エラーメッセージを返す。 |
| `format_id` | デッキ組み立て・カードリスト解読に用いる。 |

## データ整合性

| 観点 | 内容 |
|------|------|
| 更新の有無 | 新規デッキとそのカードをデータベースに登録する。登録前に当該デッキ配下のカードを初期化する処理は新規時には対象が無いため作用しない。 |
| トランザクション | デッキ本体・カードの保存を1つのトランザクションで行い、検証エラー・例外時はロールバックする。 |
| 下書きとの整合 | 保存後に当該デッキのRedis上の下書きを削除し、保存済みデータと下書きの不整合を解消する。 |

## DBカラム

機能に直接関係する列のみ記載する。型や一覧の細部はスキーマを参照する。

テーブル名・列名はec-cube-enterpriseを正とし、現行（deck-api）と呼称が異なる箇所は括弧で補う。

| テーブル | 列 | メモ |
|----------|-----|------|
| デッキ（`dtb_deck`） | 識別子（`id`）・デッキ名（`deck_name`）・フォーマット（`format_id`）・アーキタイプ（`archetype_id`）・非公開フラグ（`private_flg`、現行の公開区分 `scope_id` に対応）・所有プレイヤー（`player_id`）・閲覧用トークン（`display_token`）・本文（`text_main`・`text_side`・`text_command`）・作成日時（`create_date`）・更新日時（`update_date`）・削除日時（`deleted_at`） | 新規登録の対象。所有プレイヤーには認証したプレイヤーを設定する。 |
| デッキカード（`dtb_deck_card`） | デッキ（`deck_id`）・カード（`card_id`）・ボード（`board_id`）・枚数（`count`） | メイン・サイド・統率のカード明細を登録する。 |
| メイビー／アトラクション／ステッカー（`dtb_maybe_card`／`dtb_attraction_card`／`dtb_sticker_card`） | デッキ（`deck_id`）・カード（`card_id`）・枚数（`count`） | ボード外区分のカードを別表で登録する。 |
| フォーマットマスタ（`mtb_format`） | 識別子・統率者使用設定 | カードリスト解読の挙動判定に用いる。 |

### DB操作

永続化の正は ec-cube-enterprise（テーブル名・操作は ec-cube-enterprise を正典）。当ドメインは承認ワークフローを介さず persist/flush で直接確定する（承認ワークフローは在庫機能固有）。

| 操作種別 | 対象テーブル | 契機・条件 |
|---------|--------------|------------|
| 登録/更新 | dtb_attraction_card / dtb_deck / dtb_deck_card / dtb_maybe_card / dtb_sticker_card / mtb_format | 当機能が行う登録・更新で対象テーブルを直接保存する（不要な削除は含まない）。確定は persist/flush による即時反映。DB=ec-cube-enterprise を正典とする。 |

## 権限・認可

| 利用者状態 | デッキ登録インポート |
|------------|----------------------|
| 認証済みのプレイヤー | 自分を所有者としてデッキを新規登録できる。 |

## エラー処理

| エラー内容 | 処理 |
|------------|------|
| 認証不可 | 認証拒否（HTTP 401）とし、`{code, message}`を返す。 |
| 検証失敗・行数超過 | 入力不正（HTTP 400）とし、`{code, message}`を返す。 |
| 解読できない行あり | 登録は完了させ、コード206として該当行番号を`errors`に含める。 |
| 保存処理中のその他の例外 | 処理失敗（HTTP 500）とし、`{code, message}`を返す。 |

## ログ・監査

### ログに出してはいけないもの

- JWTトークンの原値
- 署名シークレット（`auth_magic`）
- パスワード
- Cookie値・セッションIDの完全値

## 排他制御・トランザクション

本APIはデッキ本体とカードの新規登録を1つのトランザクションで行う。検証エラー・例外時はロールバックする。楽観ロック・悲観ロックは持たない。
