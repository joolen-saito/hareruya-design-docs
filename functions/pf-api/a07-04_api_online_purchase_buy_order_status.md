# API ネット買取管理 — ネット買取受注ステータス更新

## 概要

買取アプリ（MTGバイヤー）がネット買取受注のステータスを更新するためのAPIである。pf-api（買取連携用のAPIアプリケーション）が提供するJSON APIで、受注IDで対象を特定し、指定したステータスへ更新するとともに更新担当者とステータス変更履歴を保存する。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。確認値はpf-apiのステータス更新処理、ルート定義（`config/routes.yaml`）、ネット買取受注・買取ステータスマスタ・買取ステータス履歴を扱うエンティティ、共通の認証処理を正とする。

本機能のカスタマイズ区分は現行踏襲であり、挙動の参照リポはpf-api、DB関連（テーブル名・列名・永続化先）の記述はec-cube-enterpriseを正とする。

対象はJSON APIエンドポイントであり、ブラウザ向けの画面を持たない。本文ではフレームワークのコントローラ型名やメソッド名を主説明としない。「利用者視点の入口」にHTTPメソッドとパスパターンを書く。

## 本書で扱うこと

- 受注IDによるネット買取受注の特定と、ステータス・更新担当者・更新日時の保存
- ステータス変更履歴の登録
- 認証、対象なし、無効なステータス、査定終了後・査定中の更新可否判定と応答

| エンドポイントの配置 | サイトルート直下 `/admin/buyOrder/{id}/status.json`。 | APIバージョンのルートプレフィックス（設定キー `eccube_api_v1_route`）配下に配置される。パス末尾 `admin/buyOrder/{id}/status.json` は同じ。 |

## 認証・認可

| 観点 | 内容 |
|------|------|
| 認証方式 | `jwt-token`ヘッダのJWTを検証し、ペイロードの利用者IDから管理者会員を引く。署名方式はHS256。 |
| 認証失敗時 | ヘッダ欠落・署名不正・該当する管理者会員なしのいずれも認証拒否（HTTP 401）とする。 |
| 認可 | 認証した管理者会員が更新担当者として記録される。査定中・査定再開の受注を査定開始できるのは、その受注を査定中の担当者本人に限る。呼び出し可能なクライアントは買取アプリ。 |

トークン原値・署名シークレットは本書に記載しない。

## 処理フロー

### ネット買取受注のステータスを更新する（PUT `/admin/buyOrder/{id}/status.json`）

1. `jwt-token`ヘッダのトークンを検証し、管理者会員を特定する。検証できない場合は認証拒否（HTTP 401）とする。
2. パスの受注IDでネット買取受注を1件取得する。該当が無い場合は該当なし（HTTP 404）とする。
3. 更新前のステータスIDを保持する。
4. リクエストのステータスID（`status`）で買取ステータスマスタを引く。該当が無い場合は入力不正（HTTP 400）とし「正しい店頭買取ステータスIDを入力してください」を返す。
5. 更新前ステータスが査定終了に該当する場合は更新不可とし、入力不正（HTTP 400）を返す。指定ステータスが査定中・査定再開のときは「この査定はすでに終了しているため開くことができません。」、それ以外は「この査定はすでに終了しているためステータスの更新に失敗しました。」を返す。
6. 更新前ステータスが査定中・査定再開で、かつ指定ステータスも査定中・査定再開で、その受注の査定担当者が認証した管理者会員と異なる場合は、入力不正（HTTP 400）とし「この受注は「（査定担当者名）」が査定中です。」を返す。
7. 更新前ステータスと指定ステータスが異なる場合のみ、受注のステータス・更新担当者・更新日時を更新し、ステータス変更履歴を1件登録する。保存はトランザクション内で行う。更新前後が同じステータスのときは更新も履歴登録も行わない。
8. コード200のJSONを返す。

| 項目 | 内容 |
|------|------|

## 入出力

### リクエスト

| パラメータ | 位置 | 型 | 必須／任意 | 説明 |
|------------|------|----|-----------|------|
| `id` | パス | integer | 必須 | 更新対象のネット買取受注ID。 |
| `status` | ボディ（フォーム値） | integer | 必須 | 設定する買取ステータスID。買取ステータスマスタに存在する値であること。 |
| `jwt-token` | ヘッダ | string | 必須 | 認証用のJWTトークン。 |

買取ステータスマスタに登録されているステータスIDは、受注（1）・商品到着（2）・完了（3）・査定同意（4）・書留発送（5）・振込依頼（6）・振込完了（7）・振込失敗（8）・キャンセル（9）・査定中（10）・保留（11）・査定再開（12）・連絡済み（13）である。これらに存在しないIDを指定した場合は入力不正（HTTP 400）となる。

### レスポンス（成功）

HTTP 200。

| フィールド | 型 | 説明 |
|------------|----|------|
| `code` | integer | 処理結果コード。成功時は200。更新前後が同じステータスでも200を返す。 |

### レスポンス（失敗）

| HTTPステータス | 条件 | 本文の形 |
|----------------|------|----------|
| 401 | トークン欠落・署名不正・該当する管理者会員なし | 認証拒否（本文を持たない） |
| 404 | 受注IDに該当するネット買取受注が無い | 該当なし（本文を持たない） |
| 400 | 指定ステータスIDが買取ステータスマスタに存在しない | `{code, errors}`（`errors`は「正しい店頭買取ステータスIDを入力してください」） |
| 400 | 更新前ステータスが査定終了で、指定ステータスが査定中・査定再開 | `{code, errors}`（`errors`は「この査定はすでに終了しているため開くことができません。」） |
| 400 | 更新前ステータスが査定終了で、指定ステータスがそれ以外 | `{code, errors}`（`errors`は「この査定はすでに終了しているためステータスの更新に失敗しました。」） |
| 400 | 査定中・査定再開の受注を、査定担当者本人以外が査定中・査定再開へ更新 | `{code, errors}`（`errors`は「この受注は「（査定担当者名）」が査定中です。」） |
| 500 | 保存処理中の例外 | `{code, errors}`（`errors`は例外メッセージ。トランザクションはロールバックする） |

### サンプルレスポンス

成功時の応答例。

```json
{
  "code": 200
}
```

### 副作用

更新前後でステータスが異なる場合に、ネット買取受注のステータス・更新担当者・更新日時を更新し（DB更新）、ステータス変更履歴を1件登録する。履歴には受注ID・更新後ステータスID・更新担当者ID・登録日時を記録する。参照のみではない。更新はトランザクション内で確定し、例外時はロールバックする。更新前後が同じステータスのときは更新も履歴登録も行わない。

応答はJSON応答整形を経て返す。プロパティはcamelCase、日時はISO8601、`serialize_null`は有効とする。

## バリデーション

| 項目 | 内容 |
|------|------|
| `status` | 必須。買取ステータスマスタに存在するIDであること。存在しない場合は入力不正（HTTP 400）とし、「正しい店頭買取ステータスIDを入力してください」を返す。 |
| ステータス遷移（査定終了） | 更新前が査定終了に該当する場合は更新できない。入力不正（HTTP 400）とし、指定先が査定中・査定再開かどうかでメッセージを切り替える。 |
| ステータス遷移（査定中の占有） | 更新前と指定先がいずれも査定中・査定再開で、査定担当者が認証会員と異なる場合は更新できない。入力不正（HTTP 400）とし、査定担当者名を含むメッセージを返す。 |
| `id` | パスの受注ID。該当するネット買取受注が無い場合は該当なし（HTTP 404）とする。 |

## DBカラム

機能に直接関係する列のみ記載する。型や一覧の細部はスキーマを参照する。

列名はec-cube-enterpriseを正とし、現行（pf-api）と異なるものは括弧で添える。

| テーブル | 列 | メモ |
|----------|-----|------|
| ネット買取受注 `dtb_buy_order` | 受注ID `id`（現行 `buy_order_id`） | 受注の特定に用いる。 |
| ネット買取受注 `dtb_buy_order` | 買取ステータスID `buy_order_status_id` | 更新対象。指定したステータスIDで上書きする。 |
| ネット買取受注 `dtb_buy_order` | 更新担当者 `member_id` | 認証した管理者会員（`dtb_member`）を記録する。 |
| ネット買取受注 `dtb_buy_order` | 更新日時 `update_date` | 更新時点の日時を記録する。 |
| 買取ステータスマスタ `mtb_buy_order_status` | ステータスID `id` | 指定ステータスの存在確認に用いる。 |
| 買取ステータス履歴 `dtb_buy_order_status_histry`（現行 `dtb_buy_order_status_history`） | 受注ID `buy_order_id`・買取ステータスID `buy_order_status_id`・更新担当者 `member_id`・登録日時 `create_date` | ステータス変更時に1件追加する。 |

### DB操作

永続化の正は ec-cube-enterprise（テーブル名・操作は ec-cube-enterprise を正典）。当ドメインは承認ワークフローを介さず persist/flush で直接確定する（承認ワークフローは在庫機能固有）。

| 操作種別 | 対象テーブル | 契機・条件 |
|---------|--------------|------------|
| 登録/更新 | dtb_buy_order / dtb_buy_order_status_history / dtb_buy_order_status_histry / dtb_member / mtb_buy_order_status | 当機能が行う登録・更新で対象テーブルを直接保存する（不要な削除は含まない）。確定は persist/flush による即時反映。DB=ec-cube-enterprise を正典とする。 |

## エラー処理

| エラー内容 | 処理 |
|------------|------|
| 認証不可 | 認証拒否（HTTP 401）とする。 |
| 受注が存在しない | 該当なし（HTTP 404）とする。 |

## ログ・監査

ステータス変更の履歴は買取ステータス履歴として永続化する（受注ID・更新後ステータスID・更新担当者ID・登録日時）。アプリケーションログとは別のDB上の業務履歴である。

### ログに出してはいけないもの

- JWTトークンの原値
- 署名シークレット（`auth_magic`）
- Cookie値・セッションIDの完全値

## 排他制御・トランザクション

本APIはステータス更新と履歴登録を1つのトランザクション内で行い、例外時はロールバックする。楽観ロック・悲観ロックの対象は持たず、同一受注への同時更新は後勝ちとなる。査定中・査定再開の占有は担当者比較による業務判定であり、DBレベルのロックではない。
