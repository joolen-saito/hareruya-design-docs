# 店舗設定 — 受注対応状況設定

管理画面の「店舗設定」から辿れる「受注対応状況設定」であり、画面のサブタイトルは日本語ロケールでは翻訳キー `admin.setting.basic_info` により「基本情報設定」となる（口語の「店舗設定の基本設定」と混同しうるが、表示文言はこのキーに従う）。`mtb_order_status` と同一キーで紐付くマスタの表示名・色・受注管理画面でのステータス別件数表示の有無をまとめて編集して保存する。

## 概要

管理者が、`mtb_order_status` と同一キーで紐付くマイページ向け名称・受注管理向け見た目の色を画面から更新し、`display_order_count` により受注一覧の検索エリアでのステータス別件数表示のオンオフを切り替える。行の追加削除や並び順の変更はこの画面では行わず、一覧に並ぶステータスの集合は事前に用意されたマスタ行に固定される。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。既存実装のふるまい、参照するデータ、判定境界、副作用を確認し、仕様の確からしさを把握することを目的とする。

カスタマイズ区分は標準であり、挙動・DB関連ともにec-cube-enterpriseの実装を正典とする。DB関連の記述（テーブル名・列名・型・制約、保存先・扱い、副作用のDB更新）もec-cube-enterpriseを正とする。

対象はブラウザ経由の管理画面であり、REST API 経由での同旨の編集やマスタデータの新規インポートは別機能とする。

本書では Symfony の route 名、URL パス、Controller 構成は扱わない。

## 処理フロー

### 画面表示（GET）

1. 利用者が受注対応状況設定画面にGETで到達する。
2. システムは`OrderStatus`を`sort_no`昇順で列挙する。
3. `CollectionType`で各`OrderStatus`を1行分の子フォームに割り当て、`OrderStatusSettingType`の`POST_SET_DATA`で、同じIDの`OrderStatusColor`と`CustomerOrderStatus`が存在すれば色・名称(マイページ)の初期表示値をそこから埋める。名称(受注管理)は`OrderStatus`自身の`name`から来る。
4. テンプレートでテーブル行を描画する。ID列は子フォームのデータ実体から`id`を表示し、編集不可とする。

### 登録送信（POST・成功）

1. 利用者が登録を押下し、同一画面向けにPOSTする。
2. CSRFトークンが無効なら管理共通の扱いに従い拒否される。
3. 各子フォームについてバリデーションが通ると、紐付く`OrderStatus`に名称(受注管理)と件数表示がマッピングされ、永続化対象として積まれる。
4. 同じIDの`CustomerOrderStatus`が存在すれば名称(マイページ)を上書きし永続化指示する。存在しなければ名称(マイページ)は保存されない。
5. 同じIDの`OrderStatusColor`が存在すれば色文字列を上書きし永続化指示する。存在しなければ色は保存されない。
6. 一度`flush`し、`addSuccess`でキー`admin.common.save_complete`を管理フラッシュドメインに積む（日本語ロケールの確認値は「保存しました」）。続けて同一画面の一覧表示へGETするリダイレクト応答を返す。
7. リダイレクト後のGETで、更新後のマスタを読み直して再表示する。

### 登録送信（POST・バリデーション失敗）

1. 手順は成功時と同様にPOSTを受け取るところまで進む。
2. いずれかの子フィールドが`NotBlank`または`Length`最大超過に該当すると、フォーム全体は無効となり`flush`は行われない。
3. HTTP 200で同一画面を再描画し、該当フィールド下にエラーを表示する。PHPUnitの実装確認では日本語ロケールで未入力に対し「入力されていません。」が画面テキストに含まれる。

## 業務ルール・計算

| 項目 | 内容 |
|------|------|
| 並び順 | 画面上の行順は保存時にも変更しない。一覧の並びは`sort_no`の昇順のみ。 |
| 識別子 | ステータスの`id`は編集しない。画面上は参照表示のみ。 |
| クロスエンティティ更新 | `OrderStatus`の`name`と`display_order_count`はフォームから直接セットする。マイページ名と色はマッピングされない独自フィールドから読み、`CustomerOrderStatus`と`OrderStatusColor`側へコピーする。 |

### 入力項目

短文系の最大長は設定キー`eccube_stext_len`であり、既定の確認値は255（`app/config/eccube/packages/eccube.yaml`）。

| 項目名 | 必須／任意 | 最大長 | 初期値 | 保存先・扱い |
|--------|------------|--------|--------|--------------|
| 名称(受注管理) | 必須 | 255 | GET時点の`mtb_order_status.name` | `mtb_order_status.name`へ上書き。未入力および最大長超過は送信無効。 |
| 名称(マイページ) | 必須 | 255 | GET時点で対応する`mtb_customer_order_status.name`があればその値 | `mtb_customer_order_status.name`へ上書き。対応行が無いときは当機能のループでは`persist`しない。未入力および最大長超過は送信無効。 |
| 色 | 必須 | 255 | GET時点で対応する`mtb_order_status_color.name`があればその値 | `mtb_order_status_color.name`へ上書き。対応行が無いときは当機能のループでは`persist`しない。未入力および最大長超過は送信無効。カラー型はブラウザが返す文字列形式に従う。 |
| 件数表示 | 任意 | （文字列長制約は専用でかけない） | GET時点の`mtb_order_status.display_order_count` | `mtb_order_status.display_order_count`へ上書き。チェック型のためオフ時は偽、オン時は真として解釈される。 |

### エッジケース

| ケース | 扱い |
|--------|------|
| ステータス行が0件 | 通常の初期データでは起こりにくい。起きた場合は空コレクションのフォームとなり送信しても実質更新無しとなる。 |
| `CustomerOrderStatus`または`OrderStatusColor`の行だけ欠けている | 欠け側は初期表示では当該列が値未セットのままとなる。送信時、当該子フォームについて未入力ならば`NotBlank`で送信は無効となる。入力を埋めて検証が通れば`OrderStatus`側の項目は保存される一方、関連行が存在しないテーブルにはコントローラが`persist`しないため、その列で入力した内容はそのテーブルに反映されず失われる。運用上は両テーブルを`OrderStatus`と同じ主キーで揃える。 |
| 同時編集 | 楽観ロックは持たない。後勝ちで`flush`した内容が残る。 |
| 送信途中の検証のみ失敗 | `flush`前に停止し、DBは不変。 |

### DB操作

永続化の正は ec-cube-enterprise（テーブル名・操作は ec-cube-enterprise を正典）。当ドメインは承認ワークフローを介さず persist/flush で直接確定する（承認ワークフローは在庫機能固有）。

| 操作種別 | 対象テーブル | 契機・条件 |
|---------|--------------|------------|
| 登録/更新 | mtb_customer_order_status / mtb_order_status / mtb_order_status_color | 当機能が行う登録・更新で対象テーブルを直接保存する（不要な削除は含まない）。確定は persist/flush による即時反映。DB=ec-cube-enterprise を正典とする。 |

## 権限・認可

| 利用者状態 | 受注対応状況設定画面 |
|------------|---------------------|
| 未認証 | 利用不可。管理画面のログイン要件に従う。 |
| システム管理者・モール系管理者など、店舗設定配下への拒否パターンが紐付いていない権種 | 画面表示および登録送信が評価上許可される。 |
| 店舗側の権種（`Authority`のロールキー確認値として`tenant_owner`および`tenant_operator`。`mtb_authority.id`の確認値はそれぞれ4および5） | 初期データでは`dtb_authority_role`に、管理パス先頭`/setting/shop`と前方一致する`deny_url`が紐付く。評価は共通の権限コンポーネントがリクエストパスと照合して拒否を返す。PHPUnitの`Enterprise_Mall`系テストでは、`tenantOnlyAllowedTest`によりテナントへ`Authority::TENANT_OWNER`でログインしたうえで本画面へのGETがHTTP 403となることを確認する。`TENANT_OPERATOR`単体の成否は同一テストクラスでは明示していない。 |
| メンバー単位で追加された権限パターン | 運用上、管理画面のアクセス許可設定で許可リストとブロックリストが変われば結果も変わる。 |

本機能が`dtb_authority_role`を書き換える処理はない。拒否リストの参照のみ行う。

認可評価の詳細アルゴリズムは共通セキュリティコンポーネントの実装を正とする。

## 画面遷移

| 条件 | 遷移先 |
|------|--------|
| 送信が検証と永続化に成功した | フラッシュ設定後、この画面へのリダイレクトによりGETで一覧を組み立て直す。 |
| 検証失敗 | 同一画面へ200で応答し、入力値とエラーを再表示する。 |
| 認可失敗 | 管理共通のエラー応答。 |

### 遷移時に引き継ぐ状態

| 起点 | 遷移前の処理 | 遷移後の初期状態 |
|------|--------------|------------------|
| 登録成功後の再表示 | 成功フラッシュに`admin.common.save_complete`キーを積む | 管理画面共通の成功フラッシュ領域に、日本語ロケール確認値として「保存しました」が載る。送信ボタンラベルは引き続き「登録」である。入力欄は更新後マスタ値で組み替えられる |

検索条件セッションなどは本機能では更新しない。

## エラー処理

| エラー内容 | 処理 |
|------------|------|
| 入力必須違反・最大長超過 | 送信を無効化しフィールド単位エラーをHTMLに載せる。 |
| CSRF検証失敗 | 共通の拒否処理。 |
| 権限評価拒否 | 403系の共通応答。 |
| DB障害や`flush`例外 | アプリケーション共通の例外処理に委ねる。本機能だけのユーザー向け補足メッセージは書かない。 |

## 試行制限

本機能では試行制限を扱わない。

## ログ・監査

| タイミング | 記録内容 |
|------------|----------|
| 画面表示および保存処理 | 本機能専用の業務監査ログ項目は増やしていない。 |
| アクセス拒否 | 管理共通のログ方針に従う。 |

### ログに出してはいけないもの

- CSRF対策トークンの原値
- パスワードやCookie値
- セッションIDの完全値

---

## セッション

本機能では、画面のためだけに検索条件セッションなど新たなサーバ状態を増やさない。

### セッションへ保存しない情報

フラッシュバッグの用途以外に、入力下書きだけをサーバ側に保持する処理はしない。

---

## Cookie

この画面が独自にCookieを増やすことはない。セッション維持は管理画面全体の認証に従う。

---

## 排他制御・トランザクション

本機能はエンティティマネージャの既定トランザクション境界で`flush`するだけであり、行バージョン列や楽観ロックを持たない。同時保存は最後に成功した`flush`が残る。
