# システム設定 — マスタデータ管理

管理画面の「設定」（システム設定）に属するマスタデータの選択と、ID・名称・表示順の一覧編集・保存。

## 概要

本画面は、Doctrine 上マスタとして定義されたエンティティのうち、共通形状（識別子・名称・並び順）を持つものをプルダウンで選び、テーブル形式で各行の ID・名称を編集したうえで一括保存する。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。
既存実装のふるまい、参照するデータ、検証境界、副作用、拡張イベントによる差し替え可能性を確認し、仕様の確からしさを把握することを目的とする。

本機能のカスタマイズ区分は標準であり、挙動・DB関連ともにリニューアル後（ec-cube-enterprise）の標準実装を正とする。

対象はブラウザ経由の管理画面におけるマスタデータ管理である。
メニュー上の「システム情報」（サーバ環境などの参照専用表示）は別画面・別機能とする。

本書では Symfony の route 名、URL パス、Controller クラス名は扱わない。

## 本書で扱うこと

- マスタ候補の構築条件（Doctrine メタデータ）と、プルダウンから除外されるエンティティクラス
- マスタ選択送信後の再表示、編集フォームの表示条件、保存成功・失敗時のフラッシュと再遷移
- ID・名称フィールドのバリデーション、重複 ID 検証、削除相当（行クリア）の判定
- 保存時の永続化（新規・更新・削除、`sort_no` の振り直し方）
- 店舗系権種によるアクセス拒否の確認値（PHPUnit）
- 本体が dispatch する拡張イベントのタイミングと、レスポンス差し替えが起き得る地点

## 本書で扱わないこと

以下は本書では仕様確定せず、実装または別機能の設計を正とする。

- 管理画面ログイン、二段階認証、権限マスタ編集 UI の詳細
- 権限評価アルゴリズムの全分岐（共通セキュリティコンポーネントの実装を正とする）
- 各マスタテーブルを参照する業務画面・API・バッチの個別仕様
- 具象マスタに `AbstractMasterEntity` 以外の列がある場合の業務的意味（例: 受注ステータスの一覧件数表示フラグ）
- 外部キー制約違反時の DB エラーコードや例外型の列挙
- MTG 専用の別マスタ管理画面（データメニュー配下）の仕様

## リニューアル移行時の扱い

- 本機能のカスタマイズ区分は標準であり、リニューアル後（ec-cube-enterprise）の標準実装を挙動・DBともに正とする。
- 編集対象は ec-cube-enterprise の共通マスタ基底（識別子・名称・並び順を持つマスタエンティティ）に対応するテーブルであり、保存処理は各テーブルの `id`・`name`・`sort_no` のみを更新する。並び順キーは `sort_no` で、保存時に画面の行順へ 0 起算で振り直す標準仕様とする。
- プルダウン候補から除外するマスタ、重複 ID 不可・空 ID で削除といった判定は ec-cube-enterprise の標準実装に従う。
- 現行（pf-eccube3／EC-CUBE3系）の相当画面との構成差がある場合は、移行時に ec-cube-enterprise の標準スキーマ・標準挙動へ揃える。現行との具体差は ec-cube-enterprise 実装を正として移行設計で確認する。

## 用語

| 用語 | 説明 |
|------|------|
| マスタ候補 | Doctrine のメタデータ走査で得られる、画面のプルダウンに載り得るエンティティ一覧。 |
| マスタキー | プルダウンおよび hidden 項目に用いる、FQCN をハイフン区切りにした識別子（例: `Eccube-Entity-Master-Sex`）。保存時にバックスラッシュへ戻してクラス名とする。 |
| 編集コレクション | 保存用フォームの `data` 配列。1要素が1行に対応し、`id` と `name` を持つ。 |
| 行キー | 編集コレクションの配列キー。一覧初期表示ではおおむねエンティティの主キーと一致するが、新規追加行は末尾採番となる。削除相当の処理ではこのキーで `find` する。 |
| 除外クラス | プルダウン候補から明示的に除くエンティティ。`OrderStatus`、`OrderStatusColor`、`CustomerOrderStatus`、`MtbColorSequence`、`Country` の各定義クラス名がコード上で列挙される。 |

| 入口 | URLエンドポイント | 期待されるふるまい |

| マスタデータ管理を開く（マスタ未選択） | `GET /%eccube_admin_route%/setting/system/masterdata` | マスタ選択フォームとツールチップ付き見出しが表示される。編集テーブルは表示されない。 |

| 編集のみの入口へ GET | `GET /%eccube_admin_route%/setting/system/masterdata/edit` | 200 で応答する。編集対象データが無ければ編集テーブルは出ない。 |

| 店舗側権種で許可されたログイン状態（確認テスト） | `GET /%eccube_admin_route%/setting/system/masterdata` | マスタデータ管理への GET が HTTP 403 となる確認がある。 |

## 処理フロー

### マスタ選択フォーム組み立て（マスタ管理画面の初期表示および再入）

1. マスタ選択用フォームビルダを生成する。
2. 拡張イベントを dispatch し、リスナーがビルダを変更し得る。
3. マスタ選択が POST され検証に成功した場合、完了イベントを dispatch する。リスナーがレスポンスを設定した場合はそれを返し終了する。
4. リスナーがレスポンスを返さなければ、一覧表示用の入口へリダイレクトする。リダイレクト先のパス引数には、3の直前に送信されたマスタキーが載る。
5. 入口にマスタキーのパス引数があり、かつマスタ選択フォーム上そのキーが有効なら、当該エンティティのリポジトリで `sort_no` 昇順の `findBy` を実行する。
6. 各行について、配列データに主キー・名称を格納する。主キーは行キーにも用いる。
7. 配列末尾に、ID・名称が空の1行を追加する。
8. メタデータ解釈に失敗した場合（マッピング例外）は、6のデータ読込を行わず、編集テーブル用データを空に近い状態にする。
9. 編集用フォームビルダを、7または8で得たデータを初期値として生成する。
10. 別の拡張イベントで編集フォームビルダを改変し得る。
11. 2つのフォームのビューを返し、テンプレートを描画する。

### 保存（編集テーブル送信）

1. 編集用フォームのみリクエストから組み立て、拡張イベントで初期化し得る。
2. POST なら `handleRequest` 後、検証する。
3. 検証失敗なら、マスタ選択フォームを別イベントで初期化し、リクエストボディと編集フォーム内 hidden のマスタ名を merge した値でマスタ選択フォームを submit し、2つのフォームビューを返す（同一画面でエラー再表示）。
4. 検証成功なら、隠しフィールドのマスタキーからクラス名を復元する。
5. 送信データの各行について、非 null の ID と非 null の名称が両方ある行は、主キーで既存を検索し、無ければ新規インスタンスを生成する。`setId`・`setName` のあと、ループの 0 始まり連番で `setSortNo` する。`persist` する。
6. ID と名称が両方そろわない行のうち、行キーが「他行で使われている ID 一覧」に含まれないものは削除候補とし、行キーを主キーとして `find` した結果があれば `remove` する。
7. `flush` を試みる。成功時は保存完了イベントを dispatch し、成功フラッシュに `admin.common.save_complete` を積む。失敗時（コメント上は外部キー制約など）は例外を握り潰し、エラーフラッシュに `admin.common.save_error` を積む。
8. 選択中マスタの一覧表示入口へリダイレクトする。

### 編集入口への GET のみ

1. 編集用フォームを空のデフォルトで生成し、初期化イベントを dispatch する。
2. マスタ選択フォームを生成し、別イベントで初期化したあと、リクエストの POST パラメータ全体と、編集フォーム hidden のマスタ名を merge して submit する。GET では POST パラメータは空に近い。
3. 2つのフォームビューを返す。編集データが空ならテンプレートは編集テーブルを出さない。

## 業務ルール・計算

| 項目 | 内容 |
|------|------|
| マスタ候補 | 具象クラス（抽象クラス除外）、ルートエンティティ名に `Master` を含み、`id`・`name`・`sort_no` フィールドを持つメタデータを候補とする。除外クラスは候補から外す。 |
| 表示順 | 一覧読込は `sort_no` 昇順。保存時は送信された行の並び順で `sort_no` を 0 から連番で付け直す。 |
| 新規行 | 既存に無い主キーが送られれば新規 `persist` する。 |
| 更新行 | 主キーが一致する既存行があれば、そのエンティティへ名称と `sort_no` を上書きする。 |
| 削除行 | 行の ID と名称が両方 null で、かつその行キーが「送信中の非空 ID 一覧」に含まれない場合、行キーを主キーとして `find` し、存在すれば削除する。 |
| 説明文 | 日本語ロケールの確認値として、重複 ID 不可・空 ID は削除・設定誤りでサイトが動かなくなり得る旨がカード内に表示される。 |

### 入力項目

| 項目名 | 必須／任意 | 最大長 | 初期値 | 保存先・扱い |
|--------|------------|--------|--------|--------------|
| マスタ選択 | 必須（NotBlank） | 選択肢に依存 | 未選択 | 選択後のリダイレクト先のパス引数および編集 hidden に引き継ぐ。 |
| 行 ID | 任意 | `eccube_int_len`（確認値 9）、正規表現は非負整数の十進表記 | 既存行は DB の主キー。末尾行は空。 | エンティティの主キー。空または未送信の行は削除判定に回り得る。 |
| 行名称 | 条件付き | フォーム上は長さ制約なし | 既存行は DB の名称。末尾行は空。 | `name` 列。行に ID が入力されている場合、名称が空文字相当だと検証エラーとする。 |

### エッジケース

| ケース | 扱い |
|--------|------|
| 同一送信内で同じ ID が複数行 | 各行の ID フィールドに重複エラーが付く。翻訳キーは `admin.setting.system.master_data.duplicate_id`。 |
| 主キーとして 0 を使う | 自動テスト上、名称を伴う 0 の保存や、ID 0 行の削除が確認されている。整数解釈および DB 制約に従う。 |
| `flush` が例外 | エラーフラッシュを積み、リダイレクトは同様に行う。トランザクションの扱いは永続化層の既定に従う。 |
| 無効なマスタキーでパス引数だけ開く | マッピング例外を握り潰し、編集表が出ない状態に寄せ得る。 |
| プルダウンでは選べない除外マスタ | 保存処理は hidden のマスタキー文字列を解釈するため、リクエストを構築できれば当該クラスを対象に保存し得る。画面導線では選べない旨と、管理画面認可内の運用を前提とする。 |
| 具象マスタの追加列 | 本画面の保存処理は `id`・`name`・`sort_no` のみをセットする。その他の列は変更しない。新規行の追加列は DB デフォルト・Doctrine の初期状態に従う。 |

## データ整合性

| 観点 | 内容 |
|------|------|
| 一覧と DB | 一覧表示は `flush` 直後のリダイレクト先で再クエリするため、成功時は保存結果と一致する。 |
| 参照整合性 | 削除は `remove` と `flush` に依存し、参照先が残ると例外となりエラーフラッシュに落ちる。 |
| 同時更新 | 行バージョンや楽観ロックは持たない。同時編集は後勝ちになる。 |
| キャッシュ | 一部マスタエンティティに ORM キャッシュ指定がある。キャッシュ整合の詳細は Doctrine とエンティティ定義を正とする。 |

## DBカラム

保存処理が集合的に触り得る列は、画面で選択中のマスタに対応するテーブルのうち次の列である。具象マスタが持つその他の列は本画面の保存ループでは更新しない。

| テーブル | 列 | メモ |
|---------|-----|------|
| 選択中のマスタに対応するテーブル | id | 主キー。`AbstractMasterEntity` 系では `GeneratedValue` は無く、画面指定または行キーに基づく。 |
| 選択中のマスタに対応するテーブル | name | 名称。 |
| 選択中のマスタに対応するテーブル | sort_no | 保存完了時に画面上の行順へ 0 起算で振り直す。 |

## バリデーション

| 項目 | 入力種別 | ルール・扱い |
|------|----------|--------------|
| マスタ選択 | select | `NotBlank`。 |
| 行 ID | text | 任意。`Length` 最大 `eccube_int_len`。`Regex` で十進の非負整数のみ。 |

| 利用者状態 | マスタデータ管理 |

## 画面遷移

| 条件 | 遷移先 |
|------|--------|
| マスタ選択の POST が成功 | 一覧付きの同機能内の別入口へリダイレクト。 |

検索条件セッションは本機能では更新しない。

| エラー内容 | 処理 |
|------------|------|
| マスタ未選択、ID 形式不正、名称ブランク、ID 重複 | 送信を完了させずフィールドエラーを表示する。 |
| CSRF 検証失敗 | 共通の拒否処理。 |
| 権限拒否 | 403 等の共通応答。 |
| `flush` 時の例外 | エラーフラッシュを積み、リダイレクトする。 |

---

## 試行制限

本機能では試行制限を扱わない。

---

## ログ・監査

| タイミング | 記録内容 |
|------------|----------|
| 画面表示および保存処理 | 本機能専用の業務監査ログ項目を増やす処理はない。 |
| アクセス拒否 | 管理共通のログ方針に従う。 |

### ログに出してはいけないもの

- CSRF 対策トークンの原値
- パスワードや Cookie 値
- セッション ID の完全値

---

## セッション

本機能は検索条件セッションなど新たなサーバ状態を専用に増やさない。フラッシュバッグはSymfony 共通の仕組みに従う。

---

## Cookie

本画面が独自に Cookie を増やさない。セッション維持は管理画面全体の認証に従う。

---

## 排他制御・トランザクション

本機能はエンティティマネージャの既定境界で `flush` するだけであり、行バージョン列や楽観ロックを持たない。同時保存は最後に成功した `flush` が残る。

---

## 拡張イベント（確認値）

以下の識別子がコントローラから dispatch される。リスナーがビルダやフォームへフィールドを足す、完了時にレスポンスを差し替える、といった拡張が想定される。

- マスタ選択フォーム生成直前
- マスタ選択 POST 検証成功直後（ここでレスポンスが返ればリダイレクトに代わる）
- 編集フォーム生成直前（一覧表示フロー）
- 編集初期化時（保存アクション）
- 保存 `flush` 成功直後

イベント識別子の定数表記はソースのイベント定義クラスを正とする。本書では route 名と同様、Symfony サービス名やリスナークラス名は列挙しない。
