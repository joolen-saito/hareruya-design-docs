# m05-12_admin_order_order_bulk_status_change（管理画面_受注管理_対応状況一括変更）

受注一覧画面でチェックした複数の出荷を対象に、変更先の対応状況をプルダウンで選び、一括で対応状況を変更する機能。

## 概要

対応状況一括変更は、受注管理担当者が受注一覧画面で複数の出荷行を選択し、選んだ対応状況へまとめて変更するための機能である。一覧上部の対応状況プルダウンと決定ボタンから確認モーダルを開き、選択した出荷を1件ずつ順番に変更処理へ送り、進捗バーで処理状況を示す。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。既存実装のふるまい、参照するデータ、判定境界、副作用、拡張による差し替え可能性を確認し、仕様の確からしさを把握することを目的とする。

対象はブラウザ経由の管理画面の受注一覧画面における対応状況の一括変更操作である。一括変更は専用のサーバ処理を1回呼ぶのではなく、出荷ごとの対応状況更新エンドポイントを画面側から順番に呼び出す方式で成り立つ。

管理画面プレフィックスは環境変数ECCUBE_ADMIN_ROUTEで決まり、既定値はadminである。設定はeccube.yamlのeccube_admin_routeに展開され、ルートのパスでは%eccube_admin_route%として解決される。本書のURLエンドポイントはこのプレースホルダで示す。

本書ではルートのbind名やSymfonyのルートnameの網羅は扱わない。URLエンドポイントは利用者視点の入口に限り、実装確認値として記載する。

本機能のカスタマイズ区分は標準であり、挙動・DB関連ともにec-cube-enterpriseの実装を正とする。

## 本書で扱うこと

- 受注一覧画面で出荷行のチェックボックスを選択し、対応状況プルダウンで変更先を選んで決定したときのふるまい
- 一括変更が、出荷単位の対応状況更新エンドポイントへの順次呼び出しで構成されること
- 変更対象が受注ではなく出荷（チェックボックスの値）単位で選択され、各出荷から受注をたどって対応状況を変更すること
- 変更先と現在の対応状況が同一の場合、変更できない遷移の場合、変更が成立した場合それぞれの応答と画面表示
- 対応状況が配送完了の場合の出荷日設定と、受注配下の全出荷が出荷済みのときのみ受注ステータスを進める条件
- 対応中またはキャンセルへ変更したときの在庫の戻し・引き当てに伴う商品情報の更新
- 一括変更では出荷お知らせメールを送らないこと（メール送信は別機能）
- 進捗モーダルの表示、成功・スキップ・遷移不可・システムエラー時の画面表示

## 用語

| 用語 | 説明 |
|------|------|
| 対応状況 | 受注の進行状態を表す区分。新規受付・入金済み・対応中・発送済み・キャンセル・返品・購入処理中・決済処理中などがあり、画面では受注ステータスとして表示する。テーブルはmtb_order_status、受注側の保持はdtb_order.order_status_id。 |
| 出荷 | 受注配下の発送単位。受注一覧の各行は出荷単位で表示し、チェックボックスの値は出荷のIDである。テーブルはdtb_shipping。 |
| 対応状況プルダウン | 一覧上部の変更先選択セレクト。選択肢は登録済みの対応状況の一覧で、未選択時は「対応状況の変更」の見出し行が選ばれている。 |
| 状態遷移ルール | ある対応状況から別の対応状況へ変更できる組み合わせの定義。ワークフロー設定order_state_machineで定義する。 |
| 確認モーダル | 決定ボタン押下後に表示され、進捗バーと結果一覧を出すダイアログ。出荷済にする確認モーダルと同一の領域を再利用する。 |
| 一括対象 | チェックを入れた出荷行の集合。変更は1件ずつ順番に送信される。 |

## 利用者視点の入口

受注一覧画面の表示自体は受注一覧機能の入口であり、本機能はその画面内の操作と、出荷ごとの対応状況更新エンドポイントへの順次呼び出しで成り立つ。

| 入口 | URLエンドポイント | 期待されるふるまい |
|------|--------------------|--------------------|
| 受注一覧画面を開く | `GET /%eccube_admin_route%/order` | 出荷行ごとのチェックボックス、対応状況プルダウン、決定ボタンを含む一覧を表示する。1件以上チェックすると一括操作の領域が表示される。 |
| 対応状況プルダウンで変更先を選び決定ボタンを押す | 画面内操作（直接のHTTP送信はしない） | 変更先が未選択なら警告を出して中断する。選択済みなら確認モーダルを開き、チェックした出荷を1件ずつ更新エンドポイントへ送る。 |
| 一括変更の各出荷の更新（画面側からの順次呼び出し） | `PUT /%eccube_admin_route%/shipping/{id}/order_status` | 出荷IDごとに、変更先の対応状況IDを送信する。XHRかつなりすまし対策トークンが正しいときのみ処理し、結果をJSONで返す。 |
| 変更完了後に閉じるボタンを押す | `GET /%eccube_admin_route%/order?resume=1` | 受注一覧へ戻り、検索条件をセッションから復旧して再表示する。 |
| 非管理者・未認証 | `GET /%eccube_admin_route%/order` ほか管理側URL | 受注一覧画面へ到達できないため、本操作も利用できない。 |

各更新エンドポイントのパスのidは出荷のIDである。受注のIDではない。

| 観点 | 内容 |

| JS 挙動（選択） | チェックボックスが1件以上選択されたとき一括操作領域を表示し、0件のとき隠す。全選択チェックボックスのオンで全行を選択、オフで全解除する。個別チェックの変更時は全選択チェックを外す。 |
| JS 挙動（決定） | 決定ボタン押下時、対応状況プルダウンが未選択なら「対応状況を選択してください」の警告を出して中断する。選択済みなら確認モーダルを開き、本文を処理中表示にし、操作ボタン群とメール送信オプションを隠して進捗バーを表示する。 |
| JS 挙動（順次送信） | チェックした出荷を対象に、出荷ごとの更新エンドポイントへPUTを1件ずつ送る。1件の応答が返ってから次の1件を送る逐次処理とする。各応答ごとに進捗バーを進め、応答にメッセージがあれば結果一覧へ注意として追記する。 |
| JS 挙動（完了） | 全件の送信が終わると進捗バーを隠し、本文を完了表示にして閉じるボタンを表示する。閉じるボタンで受注一覧へ戻る。 |
| メール送信欄 | 一括の対応状況変更ではメール送信のチェックは表示せず、送信もしない。メール送信欄は出荷済にする個別変更・メール送信機能で用いる。 |
| CSS・レイアウト | 一括操作領域は選択件数に応じて表示・非表示を切り替える共通クラスで制御する。確認モーダルは出荷済にする確認モーダルの領域を共用する。 |
| モーダル・ポップアップ | 確認モーダルを表示する。進捗バー、結果の注意・エラー一覧、完了文言、閉じるボタンを順に切り替える。ブラウザ標準のアラートは変更先未選択時に用いる。 |
| 入力項目 | フォーム送信値としての文字入力は持たない。変更先はプルダウン選択、対象は出荷行のチェックボックスで指定する。 |

## 処理フロー

### 出荷の選択と決定

1. 利用者が受注一覧画面で、変更したい出荷行のチェックボックスを選択する。1件以上選択すると一括操作領域が表示される。
2. 対応状況プルダウンで変更先を選ぶ。
3. 決定ボタンを押す。変更先が未選択のときは警告を出し、ここで中断する。
4. 変更先が選択済みのとき確認モーダルを開き、対象件数を選択済みのチェックボックス数として確定する。

### 一括の順次更新

1. 画面側は、チェックした各出荷について更新エンドポイントのURLと送信データを組み立てる。送信データは変更先の対応状況IDのみとする。
2. 先頭の出荷から1件ずつ、出荷ごとの更新エンドポイントへPUTで送る。1件の応答が返ってから次の1件を送る。
3. 各応答ごとに進捗バーを進め、応答にメッセージが含まれるとき結果一覧へ注意として表示する。
4. 全件の送信が終わると本文を完了表示にし、閉じるボタンを表示する。
5. 閉じるボタンで受注一覧へ戻り、検索条件をセッションから復旧して再表示する。

### サーバ側の1出荷あたりの処理

1. リクエストがXHRであり、かつなりすまし対策トークンが正しいことを確認する。いずれかを満たさないときは異常応答（HTTP400）を返す。
2. パスの出荷IDから出荷を取得し、その出荷が属する受注を得る。
3. 送信された対応状況IDから変更先の対応状況を取得する。存在しないときは異常応答（HTTP400）を返す。
4. 受注の現在の対応状況と変更先が同一のとき、変更を行わずスキップのメッセージを応答に含める。
5. 同一でないとき、状態遷移ルールで変更先へ遷移できるか判定する。遷移できないとき、変更できない旨のメッセージを応答に含める。
6. 遷移できるとき、変更先が配送完了かどうかで分岐して対応状況を適用する。詳細は「配送完了への変更時の判定順序」を参照する。
7. 変更先が対応中またはキャンセルのとき、在庫の戻し・引き当てが伴うため対象の商品規格・在庫情報を更新する。
8. 受注と出荷を保存する。受注に会員がひもづくとき、会員の購入回数・購入金額などの集計を更新する。
9. 正常終了時はステータスOKと、スキップや遷移不可のメッセージがあればそれを合わせてJSONで返す。処理中に想定外の例外が起きたときはシステムエラー応答（HTTP500）を返す。

一括変更では送信データに出荷お知らせメールの送信指定を含めない。このためサーバ側ではメール送信を行わず、メール送信日も更新しない。

## 配送完了への変更時の判定順序

| 順序 | 判定 | 結果 |
|------|------|------|
| 1 | 受注の現在の対応状況が変更先と同一か | 同一ならスキップのメッセージを返し、変更しない。 |
| 2 | 状態遷移ルールで変更先へ遷移できるか | 遷移できないなら変更不可のメッセージを返し、変更しない。 |
| 3 | 変更先が配送完了か | 配送完了でなければ、受注へ変更先の対応状況を適用する。 |
| 4 | 配送完了で、当該出荷がまだ出荷済みでないか | 出荷済みでなければ、当該出荷に出荷日として現在日時を設定する。 |
| 5 | 配送完了で、受注配下の全出荷が出荷済みか | 全出荷が出荷済みのときのみ、受注へ配送完了を適用する。1件でも未出荷の出荷が残るときは受注の対応状況を配送完了に進めない。 |

配送完了の一括変更では、複数出荷を持つ受注に対し、選択した出荷の出荷日を順次設定していく。全出荷が出荷済みになった時点の出荷で受注ステータスが配送完了へ進む。状態遷移ルール上、配送完了へは新規受付・入金済み・対応中から遷移でき、それ以外の対応状況からは遷移できない。

### フラッシュ・トースト

本機能は一括変更の結果としてフラッシュメッセージを生成しない。結果はモーダル内の進捗・一覧で示す。閉じるボタンで戻る受注一覧の再表示時に、本機能由来のフラッシュは表示しない。

### 表示しないが関連する遷移

| 事象 | 画面でのメッセージ |
|------|-------------------|
| 全件が正常に変更できた | 個別の成功メッセージは出さず、本文を完了しました。に切り替える。 |
| 一部の出荷だけがスキップ・遷移不可だった | 当該出荷について注意行を結果一覧へ追記する。他の出荷の変更は続行する。 |

## 業務ルール・計算

| 項目 | 内容 |
|------|------|
| 変更対象の単位 | チェックボックスの値である出荷を対象とし、各出荷から受注をたどって対応状況を変更する。受注に複数出荷がある場合、選択した出荷ごとに処理が走る。 |
| 変更先の指定 | 一括変更では全対象に同一の変更先を適用する。変更先は対応状況プルダウンの選択値とする。 |
| 同一ステータスのスキップ | 受注の現在の対応状況が変更先と同一のとき、変更を行わずスキップする。 |
| 遷移可否 | 状態遷移ルールで許可された組み合わせのみ変更する。許可されない組み合わせは変更しない。遷移の定義はワークフロー設定を確認値とする。 |
| 配送完了の特例 | 変更先が配送完了のとき、未出荷の当該出荷に出荷日を設定し、受注配下の全出荷が出荷済みのときのみ受注を配送完了へ進める。 |
| 在庫・ポイントの調整 | 状態遷移に伴い在庫の戻し・引き当て、ポイントの調整がワークフローの遷移処理で行われる。変更先が対応中またはキャンセルのとき、商品規格・在庫情報を更新する。 |
| 会員集計の更新 | 受注に会員がひもづくとき、変更後に会員の購入回数・購入金額などの集計を更新する。 |
| メール送信 | 一括の対応状況変更ではメールを送らない。メール送信は別機能とする。 |
| 計算の有無 | 件数・金額の集計表示は本機能では行わない。進捗の割合は処理済み件数を対象件数で割って算出する。 |

### エッジケース

| ケース | 扱い |
|--------|------|
| チェックを1件も入れずに決定ボタンを押す | 一括操作領域はチェック0件のとき隠れる。変更先未選択であれば警告で中断する。 |
| 変更先プルダウンが未選択 | 警告を出し、サーバへ送信せず中断する。 |
| 変更先が現在の対応状況と同一 | 当該出荷をスキップし、注意メッセージを結果一覧へ表示する。他の出荷の処理は続行する。 |
| 遷移できない組み合わせ | 当該出荷を変更せず、変更できない旨のメッセージを結果一覧へ表示する。他の出荷の処理は続行する。 |
| 変更先の対応状況IDが存在しない | 当該出荷の更新は異常応答（HTTP400）となり、結果一覧へシステムエラーを表示する。 |
| 配送完了へ変更するが受注の他出荷が未出荷 | 当該出荷の出荷日は設定するが、受注の対応状況は配送完了へ進めない。 |
| 同一受注の複数出荷を同時に選択して配送完了へ変更 | 1件ずつ順番に出荷日を設定し、全出荷が出荷済みになった時点の出荷で受注が配送完了へ進む。 |
| XHR以外のリクエスト、またはトークン不正 | 当該出荷の更新は異常応答（HTTP400）となる。 |
| 処理中に想定外の例外 | 当該出荷の更新はシステムエラー応答（HTTP500）となり、結果一覧へエラーを表示する。 |

---

## データ整合性

| 観点 | 内容 |
|------|------|
| 参照時点 | 各出荷の更新は呼び出し時点の受注・出荷・在庫を読み、その時点の状態で遷移可否を判定する。一覧画面表示時点の値と更新時点の値が異なる場合、更新時点を正とする。 |
| 逐次処理 | 一括変更は1件ずつ順番に送る。1件の更新が確定してから次を送るため、同一受注の複数出荷でも在庫・ポイントの加算減算の整合を保つ。 |
| 一覧との整合性 | 一括変更後、画面の一覧は閉じるボタンで戻った再表示時に最新の対応状況を反映する。送信中の進捗表示は処理済み件数の割合であり、各受注の最終状態は再表示で確認する。 |
| 会員集計との整合性 | 受注に会員がひもづくとき、変更後に会員の購入回数・購入金額の集計を更新する。集計の再計算条件は受注集計の共通処理を正とする。 |
| 部分的失敗 | 一部の出荷がスキップ・遷移不可・エラーでも、他の出荷の変更は確定する。一括全体を一つのトランザクションでまとめてロールバックはしない。 |

---

## API/バッチ結果

| 種類 | 内容 |
|------|------|
| API | 一括変更は専用のサーバ集約処理を呼ばない。出荷ごとの対応状況更新エンドポイントを画面側から順次呼び出す。入力は出荷IDと変更先の対応状況ID。成功時はステータスOKのJSONを返す。スキップ・遷移不可時はOKに加えてメッセージを返す。トークン不正・XHR以外・変更先不存在は異常応答（HTTP400）、想定外例外はシステムエラー応答（HTTP500）を返す。 |
| バッチ | 本機能ではバッチを起動しない。 |
| 再実行 | 同一の出荷を再度同じ変更先で送ると、現在の対応状況が変更先と同一になっているためスキップとして扱われる。 |

---

## 入出力

| 種類 | 内容 |
|------|------|
| 入力 | チェックした出荷の集合と、対応状況プルダウンの変更先。各更新リクエストでは出荷IDと変更先の対応状況IDを送る。なりすまし対策トークンとXHRであることを伴う。 |
| 成功時出力 | 各出荷についてステータスOKのJSON。スキップ・遷移不可のときはOKに加えてメッセージを含む。画面では進捗バーと完了文言を表示する。 |
| 失敗時出力 | トークン不正・XHR以外・変更先不存在はHTTP400、想定外例外はHTTP500のJSON。画面では結果一覧へシステムエラーを表示する。 |
| 副作用 | 受注の対応状況更新、配送完了時の出荷日設定、在庫・ポイントの調整、会員集計の更新。一括変更ではメール送信日を更新しない。 |

## DBカラム

当機能に直接関係する列のみを以下に列挙する。型や一覧の細部はスキーマを参照する。

| テーブル | 列 | メモ |
|----------|-----|------|
| dtb_shipping | id | チェックボックスの値であり、更新エンドポイントのパスのidに対応する。 |
| dtb_shipping | shipping_date | 配送完了への変更時、未出荷の出荷に現在日時を設定する。 |
| dtb_shipping | mail_send_date | 一括の対応状況変更では更新しない。メール送信機能の対象。 |
| dtb_order | id | 出荷からたどる受注のキー。 |
| dtb_order | order_status_id | 受注の対応状況。状態遷移により更新される。 |

| mtb_order_status | id | 対応状況の識別子。プルダウン選択値・送信値に対応する。 |

| mtb_order_status | sort_no | プルダウンの並び順に用いる。 |

### DB操作

永続化の正は ec-cube-enterprise（テーブル名・操作は ec-cube-enterprise を正典）。当ドメインは承認ワークフローを介さず persist/flush で直接確定する（承認ワークフローは在庫機能固有）。

| 操作種別 | 対象テーブル | 契機・条件 |
|---------|--------------|------------|
| 登録/更新 | dtb_order / dtb_shipping / mtb_order_status | 当機能が行う登録・更新で対象テーブルを直接保存する（不要な削除は含まない）。確定は persist/flush による即時反映。DB=ec-cube-enterprise を正典とする。 |

## バリデーション

| 項目 | 内容 |
|------|------|
| 変更先の選択 | 変更先プルダウンが未選択のまま決定したときは画面側で中断する。変更先の対応状況IDが存在しないときはサーバ側で異常応答とする。 |
| 対象の選択 | チェック0件のとき一括操作領域は表示されない。 |
| リクエストの正当性 | 各更新リクエストはXHRであること、なりすまし対策トークンが正しいことを要件とする。満たさないときは異常応答とする。 |
| 遷移の妥当性 | 状態遷移ルールに反する変更は行わず、変更できない旨のメッセージを返す。 |

## 権限・認可

| 利用者状態 | 受注一覧画面と対応状況一括変更 |
|------------|--------------------------------|
| 未認証 | 利用不可。管理領域の認証要件によりログイン等へ誘導される。管理側URLは%eccube_admin_route%配下として認証配下に置かれる。 |
| 管理者として認証済み | 受注一覧画面を表示でき、出荷を選択して対応状況を一括変更できる。 |
| 更新エンドポイントの直接呼び出し | XHRでない、またはトークン不正のときは異常応答となり処理されない。 |

機能ごとの細かなロール制御の有無は管理画面の権限設計を正とする。本書では受注一覧画面に到達できる管理者が一括変更を実行できることを確認値とする。

## 画面遷移

| 条件 | 遷移先 |
|------|--------|
| 受注一覧画面で出荷を選択し決定 | 同一画面上に確認モーダルを表示し、画面遷移はせず順次更新する。 |
| 変更完了後に閉じるボタンを押す | 受注一覧。検索条件をセッションから復旧して再表示する。 |
| 変更先未選択で決定 | 遷移せず、警告のみ表示する。 |

### 遷移時に引き継ぐ状態

| 起点 | 遷移前の処理 | 遷移後の初期状態 |
|------|--------------|------------------|
| 確認モーダルの閉じるボタン | 一括変更を順次確定する。 | 受注一覧を、保持済みの検索条件・ページ番号で再表示し、各受注の最新の対応状況を反映する。 |

## エラー処理

利用者が読む文言は表示メッセージ節を正とする。本節は処理方針を示す。

| エラー内容 | 処理 |
|------------|------|
| 変更先プルダウンが未選択 | 画面側で警告を出し、送信せず中断する。 |
| XHR以外、またはトークン不正 | 当該出荷の更新を異常応答（HTTP400）とし、結果一覧へシステムエラーを表示する。 |
| 変更先の対応状況IDが存在しない | 当該出荷の更新を異常応答（HTTP400）とする。 |
| 現在の対応状況と変更先が同一 | スキップとして扱い、注意メッセージを結果一覧へ表示する。 |
| 遷移できない組み合わせ | 変更せず、変更できない旨のメッセージを結果一覧へ表示する。 |
| 処理中の想定外の例外 | システムエラー応答（HTTP500）とし、ログへ記録する。結果一覧へエラーを表示する。 |

## ログ・監査

| タイミング | 記録内容 |
|------------|----------|
| 同一ステータスでスキップ | 対応状況一括変更スキップの旨を記録する。 |
| 遷移を含む1出荷の処理完了 | 対応状況一括変更処理完了の旨と受注のIDを記録する。 |
| 処理中の想定外の例外 | 予期しないエラーの旨と例外メッセージを記録する。 |

### ログに出してはいけないもの

- なりすまし対策トークンの原値
- Cookie値
- セッションIDの完全値
- 会員・受注の個人情報本文を結果説明として書くこと

## 排他制御・トランザクション

一括変更は出荷を1件ずつ順番に確定する逐次処理であり、複数出荷をまとめた単一トランザクションでのロールバックは行わない。各出荷の更新は受注・出荷・在庫・会員集計の保存を含むが、悲観ロック・楽観ロックの取得は本機能では行わない。在庫・ポイントの整合は逐次処理によって保つ。同時に別の管理者が同一受注を更新した場合の競合は、更新時点の状態を読んで遷移可否を判定することで扱う。
