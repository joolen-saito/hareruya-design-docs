# コンテンツ管理 — CSS管理

管理画面のコンテンツ管理配下で、店舗フロント向けのカスタマイズ用CSSを1ファイル単位で編集・保存し、保存後にファイルストレージへ反映する機能である。

## 概要

CSS管理は、管理者がブラウザ経由で店舗フロントに適用するカスタマイズCSSを画面上のコードエディタで編集し、保存することで店舗フロントの見た目を上書きできるようにする機能である。編集対象は単一ファイル`customize.css`であり、フォーム送信のたびに全文を上書き保存する。

本機能のカスタマイズ区分は標準であり、挙動・DB関連ともに ec-cube-enterprise の実装を正とする。本機能は永続化先がサーバ上のCSSファイルとファイルストレージであり、データベースへは保存しないため、DBスキーマを持たない。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。既存実装のふるまい、参照するファイル、保存先、画面表示、副作用を確認し、仕様の確からしさを把握することを目的とする。

対象はブラウザ経由の管理画面のCSS管理画面に限定する。店舗フロント側でこのCSSがどの読み込み順で適用されるかは、適用経路として確認値の範囲で触れる。

管理画面プレフィックスは環境変数由来の設定値で決まる。本書では`%eccube_admin_route%`をプレースホルダとして用い、ホスト名・クエリ・資格情報を含む具体URLは書かない。本文ではルート名の網羅やコントローラ実装の手順は扱わず、入口はHTTPメソッドとサイトルートからのパスパターンで示す。

## リニューアル移行時の扱い

本機能はカスタマイズ区分が標準であり、挙動・DB関連ともに ec-cube-enterprise の実装を正とする。

| 観点 | 現行（pf-eccube3） | 移行先（ec-cube-enterprise） |
|------|--------------------|------------------------------|
| 永続化先 | サーバ上のカスタマイズCSSファイルとファイルストレージ。DB列を持たない。 | 同一。DB列を持たない。保存先は `html/user_data/assets/css/customize.css` とファイルストレージ。 |
| DBスキーマ | 該当テーブル・列なし | 該当テーブル・列なし（永続化はファイルのみのため、現行と移行先でDB差分は無い） |
| 機能区分 | 店舗フロント向けカスタマイズCSSの編集 | 標準機能として ec-cube-enterprise が実装を保持する |

本機能はデータベースへ保存しないため、テーブル名・列名の差分、論理削除・物理削除の差、補助表の有無といった移行差は発生しない。

## フロント挙動

| 観点 | 内容 |
|------|------|
| 表示要素 | カード見出し「CSS設定」。カード内に項目見出し「コード」、必須バッジ、ツールチップ（「カスタマイズ用CSSファイルを編集します。CSSで記述します。」）、高さ約480pxのコード入力領域。下部に戻り導線「CSS管理」と「登録」ボタン。 |
| コードエディタ | コード入力領域はAceエディタとして初期化し、CSSモード、配色テーマ`tomorrow`を適用する。初期値はフォームのCSS値を流し込む。基本補完・スニペット・ライブ補完・不可視文字表示を有効化する。領域はリサイズ可能で、リサイズ時にエディタを追従させる。 |
| JS挙動（保存ボタン制御） | エディタの注釈変更時に、エラー種別の注釈が1件でもあれば「登録」ボタンを非活性にし、無ければ活性にする。注釈が空のときも活性にする。エラーの有無はクライアント側のCSS解析に基づくものであり、サーバー側のCSS構文検証ではない。 |
| JS挙動（送信直前の同期） | フォーム送信時に、隠しテキストエリアへエディタの現在値を書き戻してから送信する。これにより画面のエディタ内容が送信値になる。 |
| CSS・レイアウト | 管理画面標準のカード・行レイアウト。エディタ右下のリサイズハンドルの位置を微調整するスタイルを当画面で定義する。 |
| モーダル・ポップアップ | 当画面はモーダル、確認ダイアログ、トーストを持たない。メッセージはフラッシュ表示と項目エラー表示で示す。 |
| 入力項目 | コードを入力する複数行テキスト入力（textarea）が1つ。エディタ表示は前面のAce、実際の送信値は背面の隠しtextareaが担う。 |

### フロントエンド側ビジネスロジック

| 起点 | 参照する値 | 判定順序 | 更新する表示値・送信値 | サーバ側再検証 |
|------|------------|----------|--------------------------|----------------|
| エディタ注釈変更 | Aceエディタの注釈一覧 | 注釈にエラー種別が1件以上あれば登録ボタンを非活性にする。エラー種別が無い、または注釈が空なら活性にする。 | 登録ボタンのdisabled状態を切り替える。CSS本文の送信値はこの時点では更新しない。 | サーバ側ではCSS構文の妥当性を検証しない。ファイル保存可否を判定する。 |
| フォーム送信 | Aceエディタの現在値、非表示textarea | 送信直前にエディタ内容を非表示textareaへ書き戻す。 | 非表示textareaの値が保存対象CSSになる。 | 保存先ファイルへの書き込み可否とファイル反映可否をサーバ側で処理する。 |
| エディタリサイズ | エディタ領域サイズ | リサイズ操作に応じてエディタを再描画する。 | 表示領域だけを更新する。送信値は変更しない。 | 再検証なし。 |

## 処理フロー

### CSS管理画面を開く（GET）

1. 管理画面の認証・権限の各ルールを通過する。ファイルアップロード制限が有効で当URLが制限対象なら、この時点でアクセス拒否（HTTP403）となり以降へ進まない。
2. ファイルアップロード制限に関する案内メッセージを、情報フラッシュとして一度だけ積む。
3. CSS用のフォーム（コード入力1項目、任意）を組み立てる。
4. `customize.css`の絶対パスを組み立て、ファイルが存在し、かつ書き込み可能であれば、その内容をフォームのコード値へセットする。存在しない、または書き込み不可の場合はセットしない。
5. テンプレートを描画する。Aceエディタにフォームのコード値を初期表示する。

### 「登録」押下（POST、保存成功）

1. フォームをリクエストで処理する。送信直前にエディタ値が隠しtextareaへ同期されているため、送信値はエディタ内容となる。
2. フォームが送信済みかつ検証成功であれば保存処理へ進む。
3. `customize.css`へフォームのコード値を全文書き込みする（ファイルが無ければ作成、あれば上書き）。
4. 管理画面向け成功メッセージ（「保存しました」）を積む。
5. 既定のファイルストレージアダプタを取得し、書き込んだローカルファイルを配信用パス`/html/user_data/assets/css/`に`customize.css`としてアップロードする。
6. 同一のCSS管理画面へリダイレクトする。

### 「登録」押下（POST、書き込み失敗）

1. フォームをリクエストで処理し、検証成功で保存処理へ進む。
2. ファイル書き込みで入出力例外が発生した場合、保存に失敗したと判断する。
3. 管理画面向けエラーメッセージ（「保存に失敗しました」）を画面に表示する。
4. 失敗の詳細（対象パスと例外）をアプリケーションログへ記録する。
5. リダイレクトせず、同一画面のフォームビューを再描画する。

### 「登録」押下（POST、検証不成立）

1. フォームが送信済みでも検証が成立しない場合は保存処理へ進まない。
2. 同一画面のフォームビューを再描画する。コード項目は任意のため、空でも検証自体は妨げない実装である。

## 業務ルール・計算

本機能では金額計算・集計・丸めなどの業務計算を行わない。保存対象は単一のCSSファイルであり、入力されたコードを解釈・整形せず全文をそのまま保存する。

| 項目 | 内容 |
|------|------|
| 保存対象 | 単一ファイル`customize.css`のみ。複数ファイルや差分保存は行わない。 |
| 保存方式 | フォームのコード値でファイル全文を上書きする。既存内容とのマージは行わない。 |
| 初期表示の条件 | 対象ファイルが存在し、かつ書き込み可能なときに限り、現行内容をエディタへ初期表示する。書き込み不可・不存在のときは空表示。 |
| ストレージ反映 | ローカルへ書き込み後、既定のファイルストレージへ同名でアップロードする。アップロードは書き込み成功後にのみ行う。 |
| 構文検証 | サーバー側でCSS構文の妥当性検証は行わない。クライアント側エディタのエラー注釈は「登録」ボタンの活性制御にのみ用いる。 |

### 入力項目

| 項目名 | 必須／任意 | 最大長 | 初期値 | 保存先・扱い |
|--------|------------|--------|--------|----------------|
| コード | 任意 | Symfony Length制約なし（複数行テキスト入力。サーバー側の文字数上限を課さない） | 対象ファイルが存在し書き込み可能なら現行内容、そうでなければ空 | ファイル`html/user_data/assets/css/customize.css`（フォーム項目キー `css`、`TextareaType`、`required`は偽）。検証成功時に全文上書き保存し、続けて既定ファイルストレージへ`/html/user_data/assets/css/customize.css`として同名アップロードする。 |

コードは画面ではAceエディタとして表示されるが、送信値は背面の複数行テキスト入力（textarea）が保持する。サーバー側ではフォーム制約として文字数上限を課しておらず、CSS内容の構文検証も行わない。フォーム項目自体は任意であるが、画面上は必須バッジを表示する。

### エッジケース

| ケース | 扱い |
|--------|------|
| 対象ファイルが存在しない | 初期表示はせず空のエディタとなる。「登録」時は新規作成として書き込みする。 |
| 対象ファイルが存在するが書き込み不可 | 初期表示で現行内容を読み込まない（空表示）。「登録」時の書き込みに失敗すればエラーメッセージとログ記録となる。 |
| コードを空のまま登録 | 項目は任意のため検証は妨げない。空内容でファイルを上書きし、空のCSSが保存・反映される。 |
| ファイル書き込みで入出力例外 | 保存失敗メッセージを表示し、ログへ対象パスと例外を記録し、同一画面へ留まる。ストレージアップロードは行わない。 |
| ファイルアップロード制限が有効 | 当URLは到達前にアクセス拒否（HTTP403）となる。GET・POSTのいずれも遮断される。 |

## データ整合性

| 観点 | 内容 |
|------|------|
| 画面とローカルファイル | 保存成功後にリダイレクトで再表示するため、エディタには直前に保存したローカルファイル内容が再度初期表示される。 |
| ローカルとストレージ | ローカルファイルへの書き込みが成功した後にストレージへアップロードする。書き込みは成功したがアップロードで例外が出た場合の挙動は、フレームワークの例外処理に委ねる。 |
| 店舗フロントとの整合 | 店舗フロントが参照するのはストレージ配信またはローカルの同パスファイルである。配信キャッシュ・CDNの反映タイミングは配信側の設定に依存し、本機能は保存・アップロードの時点までを担う。 |
| 同時編集 | 複数の管理者が同時に保存した場合、最後に書き込まれた内容が残る。版管理・楽観ロックは行わない。 |

## ログ・監査

| タイミング | 記録内容 |
|------------|----------|
| 保存成功時 | 管理画面向け成功フラッシュを積む。アプリケーションログ専用の追加記録は当機能のコア実装からは読み取らない。 |
| ファイル書き込み失敗時 | エラーメッセージとともに、対象ファイルパスと発生した例外をアプリケーションログへ記録する。 |

### ログに出してはいけないもの

- パスワード
- なりすまし対策トークン
- Cookie値
- セッションIDの完全値

CSS本文は機能上の入力であるが、秘匿情報を含めない運用を前提とする。

---

## 適用経路（店舗フロントでの反映）

保存したカスタマイズCSSは、店舗フロントのテンプレート（既定テーマのフレーム）で、ヘッダ末尾付近に`user_data`配下の`assets/css/customize.css`への読み込みとして出力される。読み込み位置が他のスタイルシートより後段にあるため、既定スタイルを上書きする用途として機能する。読み込み元の配信（ストレージ／CDN）の細部は配信側設定を正とする。

## セッション

### 本機能におけるセッション

| 観点 | 内容 |
|------|------|
| 案内・成功・失敗メッセージ | 画面表示や保存後の再表示で一度表示するため、フラッシュバッグへ格納する。 |

### セッションへ保存しない情報

CSS本文やフォームの下書きをセッションへ保持する処理は当機能では行わない。

---

## Cookie

本機能単体で特有のCookieは定義しない。セッションCookieは管理画面全体の実装を正とする。

---

## 排他制御・トランザクション

当機能はファイル書き込みとストレージアップロードを行い、データベーストランザクションや楽観・悲観ロックは持たない。複数管理者が同時に保存した場合は、最後に書き込まれた内容が残る。
