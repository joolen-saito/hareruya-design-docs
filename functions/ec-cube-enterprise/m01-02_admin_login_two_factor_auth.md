# 管理画面ログイン — 二段階認証

管理画面における二段階認証。

## 概要

管理画面二段階認証は、管理者としての ID・パスワード認証が成功したあと、登録済みの TOTP 方式のワンタイムトークンで再度本人確認を行い、認証済み状態をブラウザに紐付けて保持する機能である。

本機能のカスタマイズ区分は標準であり、挙動・DB関連ともec-cube-enterpriseを正とする。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。
既存実装のふるまい、状態、参照するデータ、判定境界、永続化、副作用を確認し、仕様の確からしさを把握することを目的とする。

対象はブラウザ経由の管理画面であり、二段階認証の有効化、初回設定、追加認証、本人による再設定を含む。

本書では Symfony の route 名、URL パス、Controller 構成は扱わない。
利用者がたどる境界として、「利用者視点の入口」に HTTP メソッドとサイトルートからのパスパターン（実装確認値）を記載する。

---

## 本書で扱うこと

- システム全体および個別管理者における二段階認証の有効／無効の扱い
- パスワード認証後、保護された管理画面へ進む前の追加認証としての TOTP 検証
- 二段階認証が有効な管理者の、秘密鍵未設定時の初回設定。QR の表示およびトークンによる登録
- 本人による秘密鍵の再設定および既存デバイスへの影響
- 認証済み状態を表す HTTPOnly Cookie の付与・検証・有効期限
- メンバー管理画面での「2 段階認証」スイッチおよび一覧での設定完了／未完了の表示
- 各画面に表示される正常・警告・エラーメッセージの文言と表示条件

## 本書で扱わないこと

以下は本書では仕様確定せず、実装または別機能の設計を正とする。

- Symfony の route 名、URL パス、Controller 構成
- 管理画面ログインにおけるログイン ID・パスワードの検証、試行制限、ログイン履歴
- API ログインおよび API 経由の認証
- TOTP ライブラリの内部アルゴリズム、時刻許容ウィンドウの数値。実装依存のため許容ウィンドウの有無に触れるに留める
- パスワードハッシュ方式、CSRF・セッション Cookie の詳細
- Cookie 名・属性の現行互換保証
- 同一管理者の複数ブラウザ同時利用時の競合排除としての排他ロック

## リニューアル移行時の扱い

二段階認証用 Cookie 名、保存 JSON の構造、パラメータ名は現行実装の確認値として記録し、機能仕様として固定しない。

移行時に保証する対象は、名称ではなく次のふるまいである。

- システムで二段階認証が無効な場合、追加認証を要求しない。
- 二段階認証が有効な管理者は、パスワード認証後、トークン検証および初回秘密鍵登録のいずれかを完了するまで保護された管理画面を利用できない。
- トークン検証または秘密鍵登録が成功したあと、一定期間は同一ブラウザで追加認証を省略できる。その範囲は認証済み Cookie が有効な期間による。
- 管理者の 2 段階認証を OFF にした場合、当該管理者に対する追加認証要求は発生しない。当該管理者の秘密鍵が DB に残るかどうかは実装に従う。

次の項目は現行実装の確認値として記録する。名称一致を確認する場合は、設計書ではなくソースコードまたは環境変数定義を確認する。

- 二段階認証用 Cookie 名。既定は環境変数 `ECCUBE_2FA_COOKIE_NAME` 由来の値となる
- 認証済み状態の有効日数。環境変数 `ECCUBE_2FA_EXPIRE` 由来。0 のときはブラウザセッションに近い扱いとなる
- Cookie の Path、Secure、SameSite。いずれも SSL 強制設定と連動する
- Cookie 値、TOTP 秘密鍵、6 桁トークンの原値

## 用語

| 用語 | 説明 |
|------|------|
| 管理者 | 管理メンバー。本機能では Symfony Security 上で管理者としてログイン済みの主体を指す。 |
| システム 2FA | アプリ設定により、二段階認証機能全体を有効にするスイッチ。無効時は追加認証や画面誘導を行わない。 |
| 個別 2FA 有効 | メンバーごとの `two_factor_auth_enabled`。有効時のみ追加認証の対象となる。 |
| TOTP 用秘密鍵 | 認証アプリとサーバが共有する秘密。DB に保持し、設計書やログに原値を書かない。 |
| デバイス トークン | 認証アプリが表示する 6 桁のワンタイムコードとして入力される値。 |
| 追加認証 | パスワード成功後、6 桁トークンを検証する画面・処理。 |
| 初回設定 | 個別 2FA が ON だが秘密鍵が未設定のときに、QR 等を用いて秘密鍵を登録する画面・処理。 |
| 認証済み Cookie | トークン検証または秘密鍵登録成功後に付与され、一定期間追加認証を省略する HTTPOnly Cookie。 |
| 本人の再設定 | 既に秘密鍵がある状態で、新しい秘密鍵に付け替える操作。認証済み Cookie があるときにのみ当該画面を利用できる。 |

## 利用者視点の入口

| 入口 | URLエンドポイント | 期待されるふるまい |
|------|--------------------|--------------------|
| 保護された管理画面 | `GET /%eccube_admin_route%/…`（業務 URL。未完了時は次項へ誘導） | システム 2FA と個別 2FA がともに ON、かつ認証済み Cookie が無効なとき、業務画面の代わりに追加認証画面または初回設定画面へ誘導する。 |
| 追加認証画面 | `GET /%eccube_admin_route%/two_factor_auth/auth`、`POST /%eccube_admin_route%/two_factor_auth/auth` | 6 桁トークンを入力し、成功するとホーム画面相当へ遷移し、認証済み Cookie が付与される。失敗時は同一画面で再入力を促す。 |
| 初回設定画面 | `GET /%eccube_admin_route%/two_factor_auth/set`、`POST /%eccube_admin_route%/two_factor_auth/set` | QR コードを表示し、6 桁トークンで秘密鍵を確定する。成功すると秘密鍵が保存され、認証済み Cookie が付与され、ホーム画面相当へ遷移する。 |
| 本人の再設定画面 | `GET /%eccube_admin_route%/setting/system/two_factor_auth/edit`、`POST /%eccube_admin_route%/setting/system/two_factor_auth/edit` | ヘッダー等から開く想定であり、認証済み Cookie があるユーザーにのみ到達しやすい。新しい秘密鍵の登録用 QR と 6 桁検証を行う。 |
| メンバー編集 | `GET /%eccube_admin_route%/setting/system/member/{id}/edit` 等（メンバー管理の編集経路） | 別の管理者による他メンバー編集。個別 2FA の ON/OFF を切り替え可能。ON だが秘密鍵未登録の場合は一覧で未完了が示される。 |

## 処理フロー

### 保護画面へのアクセス時・入口ガード

1. リクエストが管理画面であること、かつシステム 2FA が有効であることを確認する。いずれかで無ければ何もしない。
2. 追加認証画面そのものへのリクエストは、ガードによるリダイレクトの対象外とする。
3. 初回設定画面へのリクエストは、当該管理者の秘密鍵が未設定のときのみガードの対象外とする。秘密鍵が既にある場合は対象とし、これにより初回設定ルートへの安易な迂回を防ぐ。
4. 現在利用者が管理者であり、個別 2FA が ON であり、認証済み Cookie が有効でない場合、秘密鍵の有無に応じて追加認証画面または初回設定画面へリダイレクトする。それ以外はそのまま後続処理へ進む。

### 追加認証・秘密鍵が既に設定済みの場合

1. システム 2FA が無効、または認証済み Cookie が既に有効なら、ホーム画面相当へ送る。
2. 秘密鍵が未設定なら、初回設定画面へ誘導する。
3. POST で 6 桁トークンを受け取り、フォーム妥当性のうえで秘密鍵と照合する。
4. 成功時はホーム画面相当へリダイレクトし、認証済み Cookie を付与する。
5. 失敗時またはフォーム不正時は、同画面に留まり、再入力を促す文言を表示する。

### 初回設定・個別 2FA ON かつ秘密鍵未設定の場合

1. システム 2FA が無効、または認証済み Cookie が既に有効なら、ホーム画面相当へ送る。
2. 既に秘密鍵が設定済みなら、追加認証画面へ送る。未認証状態での秘密鍵の再設定を防ぐためである。
3. GET 時は新規秘密鍵候補を生成し、フォームの隠し項目に渡し、QR コード用データとして画面に出す。
4. POST 時は隠し項目の秘密鍵と入力 6 桁を照合し、成功時に DB に保存し、フラッシュ成功メッセージと認証済み Cookie を付与してホーム画面相当へ送る。
5. 失敗時はエラーメッセージを表示する。GET 時に既に秘密鍵が DB 上ある場合は警告を出し、再設定に相当することを伝える。

### 本人による再設定・秘密鍵の付け替え

1. 認証済み Cookie が無効な場合、ホーム画面相当へ送る。以降のガードにより追加認証へ誘導される想定である。
2. 初回設定と同様に GET で秘密鍵候補と QR を出し、POST で検証する。画面上の遷移およびレイアウトは管理画面標準フレームを用いる。
3. 成功時の DB 更新により、従来のデバイスから発行されたトークンは無効化される。新秘密鍵で認証アプリを再登録する必要がある。

## 管理画面アクセス時の判定順序

| 順序 | 判定 | 結果 |
|------|------|------|
| 1 | 管理画面リクエストでない、またはシステム 2FA が無効 | 追加認証の誘導を行わない。 |
| 2 | 追加認証画面へのリクエスト | 後続処理を実行する。 |
| 3 | 初回設定画面へのリクエストかつ秘密鍵未設定 | 後続処理を実行する。 |
| 4 | 初回設定画面へのリクエストかつ秘密鍵あり | 通常のガード対象とし、追加認証へ誘導する。 |
| 5 | 利用者が管理者でない、または個別 2FA が OFF | 追加認証の誘導を行わない。 |
| 6 | 認証済み Cookie が有効 | 追加認証の誘導を行わない。 |
| 7 | 秘密鍵あり | 追加認証画面へ誘導する。 |
| 8 | 秘密鍵なし | 初回設定画面へ誘導する。 |

## 業務ルール・計算

| 項目 | 内容 |
|------|------|
| 追加認証の対象 | システム 2FA が有効、個別 2FA が ON、認証済み Cookie が無効な管理者を対象にする。秘密鍵がある場合は追加認証、秘密鍵が無い場合は初回設定へ誘導する。 |
| TOTP 検証 | 入力された 6 桁トークンを、管理者の秘密鍵または POST された秘密鍵候補と照合する。許容ウィンドウなど TOTP ライブラリ内部の詳細は本書では仕様固定しない。 |
| 初回設定 | 個別 2FA が ON で秘密鍵が未設定の場合、秘密鍵候補と 6 桁トークンが一致したときに秘密鍵を DB に保存し、認証済み Cookie を付与する。 |
| 本人の再設定 | 認証済み Cookie が有効な利用者だけが秘密鍵を付け替える。更新後は旧秘密鍵に基づく認証アプリのトークンを使えない。 |
| 認証済み状態 | トークン検証または秘密鍵登録に成功した後、認証済み Cookie を付与し、有効期間内は追加認証を省略する。 |
| メンバー管理 | 個別 2FA の ON/OFF は管理者レコードに保存する。OFF の管理者には追加認証を要求しない。 |

### 入力項目

| 項目名 | 必須／任意 | 最大長 | 初期値 | 保存先・扱い |
|--------|------------|--------|--------|--------------|
| デバイス トークン（6 桁） | 必須 | 6 桁数字として検証（表記ゆれ・桁不足は失敗） | 空 | TOTP 照合のみ。永続化しない。 |
| 秘密鍵候補（hidden） | 初回設定・本人再設定の POST で必須 | — | GET で生成した値をフォームに埋め込み | 検証成功時に `dtb_member.two_factor_auth_key` へ保存する値の元。ログに原値を出さない。 |
| 個別 2FA の ON/OFF（メンバー管理） | 画面により必須／任意はフォーム定義に従う | — | 現行の `two_factor_auth_enabled` | `dtb_member.two_factor_auth_enabled` を更新する。 |
| CSRF / なりすまし対策トークン | 必須 | — | フォーム埋め込み | フレームワークの検証に従う。 |

### エッジケース

| ケース | 扱い |
|--------|------|
| システム 2FA が無効 | 個別 2FA や秘密鍵の状態にかかわらず追加認証を要求しない。 |
| 個別 2FA が OFF | システム 2FA が有効でも当該管理者には追加認証を要求しない。 |
| 個別 2FA が ON で秘密鍵が未設定 | 初回設定画面へ誘導し、秘密鍵登録完了まで保護された管理画面を利用できない。 |
| 初回設定画面へ秘密鍵設定済み管理者がアクセス | 追加認証画面へ送る。未認証状態での秘密鍵再設定を防ぐ。 |
| 本人再設定時に認証済み Cookie が無効 | ホーム画面相当へ送られ、その後ガードにより追加認証または初回設定へ誘導される。 |
| Cookie 有効期間が切れた | 次回の保護画面アクセス時に追加認証または初回設定が必要になる。 |
| 同一管理者が複数ブラウザを使う | 認証済み状態はブラウザの Cookie と管理者の秘密鍵に依存する。複数ブラウザ同時利用を排他する要件は持たない。 |

## データ整合性

| 観点 | 内容 |
|------|------|
| 秘密鍵と Cookie | 認証済み Cookie は管理者 ID と秘密鍵から検証される。秘密鍵を更新した場合、旧秘密鍵に基づく Cookie や認証アプリのトークンは有効な認証材料として扱われない。 |
| DB 更新とレスポンス | 初回設定または本人再設定では、秘密鍵保存と認証済み Cookie 付与が成功時の副作用になる。保存失敗時の扱いはフレームワークおよび永続化層の例外処理に委ねる。 |
| メンバー管理との整合性 | 個別 2FA の ON/OFF はメンバー管理で変更される。変更後の追加認証要求は、次回以降の管理画面アクセス時の判定に従う。 |
| 時刻との整合性 | TOTP 検証はサーバ時刻とライブラリの許容範囲に依存する。本書では許容ウィンドウの数値を仕様固定しないが、実装確認値は前後 2 ステップ（`TwoFactorAuthService::verifyCode` が `verifyCode($authKey, $token, 2)` を呼ぶ）。 |
| 外部連携との整合性 | 本機能は外部認証サービスや通知 API を呼び出さない。TOTP 秘密鍵と認証済み Cookie の範囲で判定する。 |

## API/バッチ結果

| 種類 | 内容 |
|------|------|
| API | 本機能はブラウザ経由の管理画面フォームとして動作し、二段階認証のための専用公開 API は扱わない。 |
| バッチ | 本機能はバッチを起動しない。秘密鍵や個別 2FA 設定が別処理で変更済みの場合、次回の管理画面アクセス時にその時点の永続化済みデータを読む。 |
| 成功時 | 追加認証成功、初回設定成功、本人再設定成功のいずれも、認証済み Cookie の付与または秘密鍵更新を伴い、ホーム画面相当へ遷移する。 |
| 失敗時 | トークン不一致、フォーム不正、秘密鍵保存失敗などは画面メッセージまたは共通例外処理に委ねる。本機能専用の JSON エラー応答は扱わない。 |

## Cookie

### 二段階認証済み Cookie

以下は現行実装での確認事項である。移行時は「ブラウザが管理画面パス配下で一定期間追加認証を省略できる」ことが成立するかを確認する。

| 項目 | 内容 |
|------|------|
| 名称 | 環境変数 `ECCUBE_2FA_COOKIE_NAME` を経由して決まるパラメータ。既定の確認はコード定数および `eccube.yaml` で行う。実装確認値は `eccube_2fa`。 |
| 値の意味 | JSON 形式で複数管理者 ID 分のエントリを保持しうる。各エントリに検証用ハッシュと更新時刻を含む。 |
| 検証 | エントリのハッシュが当該管理者の ID と秘密鍵から導かれる期待値と一致し、かつ有効期限設定を満たすこと。 |
| 有効期限 | 環境変数 `ECCUBE_2FA_EXPIRE` の日数。実装確認値は 14 日（付与時刻＋14×24×60×60 秒）。0 のときは Cookie の expires がセッション扱いに近い。 |
| Path | アプリケーションのベースパスと管理画面ルートセグメントに連動。 |
| HttpOnly | true |
| Secure | SSL 強制設定が有効なとき true。 |
| SameSite | SSL 強制設定が有効なとき、`None` が使われる実装がある。 |

アプリログに Cookie 値やハッシュ原値を載せない。

## 排他制御・トランザクション

二段階認証は注文や在庫更新のような業務データ更新を主目的としない。
秘密鍵更新とレスポンス Cookie 付与は実装に従い、楽観・悲観ロックによる排他は本機能の要件としては扱わない。
