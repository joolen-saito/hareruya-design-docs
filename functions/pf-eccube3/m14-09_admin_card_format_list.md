# カード管理 — フォーマット一覧

## 概要

HareruyaEc プラグインが管理画面の「カード管理」メニューから提供する、フォーマットマスタ（`mtb_format`）の全件一覧表示である。表示順はランクの昇順、同一ランク内は ID の昇順とする。各行から編集画面へのリンクと、操作メニュー経由の削除要求（別 HTTP メソッド）に接続する。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。pf-eccube3 に配置された HareruyaEc プラグインのソースを確認値とする。

本機能のカスタマイズ区分は現行踏襲である。挙動は現行リポ（pf-eccube3 の HareruyaEc プラグイン）を参照し、DB関連は ec-cube-enterprise を正とする。

対象はブラウザ経由の管理画面に限定する。フォーマットの新規登録・更新フォームの項目定義や禁止・制限カードの保存手順の細部は本書の主題としない。

本文ではフレームワークのコントローラ型名やメソッド名を主説明としない。本文ではルートbind名やSymfonyのルートnameの網羅は主説明としない。「利用者視点の入口」にHTTPメソッドとサイトルートからのパスパターンを書く。コード探索でbind名が必要なときだけ「調査補助」へ書く。

---

## リニューアル移行時の扱い

- ec-cube-enterprise にフォーマットマスタが実装されており、本機能の参照先は移行先に存在する。
- フォーマットマスタ（`mtb_format`）は、主キー `id` と列（`name_jp`、`name_en`、`code`、`certification_id`、`rank`、`deleted_at` ほか）が現行 pf-eccube3 と同一スキーマである。
- 並びの第一キーは現行・移行先とも `rank`（予約語のためバッククォート付き）であり、`sort_no` への改称はない。第二キーは `id`。
- 論理削除列 `deleted_at` を現行・移行先とも持ち、一覧取得は論理削除済み行を除外する。
- 認定参照（`certification_id`）は認定マスタへの外部キーで、現行・移行先とも同じ関連である。
- 移行先 `mtb_format` には現行に無い列（イベント表示フラグ `is_shown_in_event` 等）が追加されているが、一覧表示では参照しない。

## 利用者視点の入口

| 入口 | URLエンドポイント | 期待されるふるまい |
|------|--------------------|---------------------|
| ナビ「カード管理」→「フォーマット管理」 | `GET /{admin_route}/format` | フォーマットが表形式で並ぶ。件数に上限を設けたページ送りはない。 |
| サブタイトル右の「新規登録」 | `GET /{admin_route}/format/new` | 登録フォーム画面へ遷移する。 |
| 表のフォーマット名（和／英）リンク | `GET /{admin_route}/format/{formatId}/edit` | 該当 ID の編集画面へ遷移する。 |
| 行末メニュー「編集」 | `GET /{admin_route}/format/{formatId}/edit` | 同上。 |
| 行末メニュー「削除」 | `DELETE /{admin_route}/format/{formatId}/delete` | CSRF 付きアンカーとして送信され、削除処理が走る。条件により失敗し Referer に戻る。 |

## フロント挙動

| 観点 | 内容 |
|------|------|
| 表示要素 | ページタイトルは「フォーマット管理」。サブタイトルは「フォーマット一覧」と、右寄せの「新規登録」ボタン（通常の `input type="button"` を `a` で包んだ形状）。表の列は「フォーマット名」「略称」「認定」、および操作列。フォーマット名セルは「和名 / 英名」のテキストを編集 URL へのリンクとする。認定は `certificationId` が非 NULL のときのみ、認定マスタの和名／英名を同様に「 / 」区切りで出す。NULL のときは当該セルは空。操作列は Bootstrap のドロップダウンで「編集」「削除」。 |
| JS 挙動 | 一覧テンプレートには `javascript` ブロックがなく、一覧表示専用のスクリプトは読み込まない。削除アンカーは他画面と同様、Method Override（`data-method="delete"`）と確認メッセージ用 `data-message`、および `csrf_token_for_anchor()` によるトークン付与に依存する（共通管理画面 JS の挙動に委ねる）。 |
| CSS・レイアウト | `admin/assets/css/format.css` を読み込み。「新規登録」ボタンのパディングと、表セルの縦位置（middle）を揃える程度のルールのみ。 |
| モーダル・ポップアップ | 本一覧テンプレート単体ではモーダルを定義しない。削除確認はアンカーの data 属性に基づく共通処理に従う。 |

## 処理フロー

### 一覧を表示する（GET `m14-09_admin_card_format_list`）

1. 管理画面の認証・共通制約を通過する。
2. フォーマット向けリポジトリで、ソフト削除拡張がマッピング上で有効な通常稼働では、論理削除済み行を除いた集合に対し、空の検索条件、並び `rank` 昇順、`id` 昇順でDoctrine の `findBy` 相当が実行される。
3. 得られた配列をそのまま Twig に渡し、テーブル行をループで描画する。
4. 0 件の場合も表ヘッダは表示され、データ行は出力されない（空の tbody）。

### 一覧の行メニューから削除する（DELETE `admin_format_delete`）

1. 管理画面の認証・共通制約および CSRF 検証を通過する。
2. パスの ID に対応するフォーマットが存在しなければ HTTP 404 とする。
3. 当該フォーマットに紐づくイベント、デッキ、アーキタイプのいずれかのコレクションが空でない場合、エラーメッセージキー `admin.format.error.delete.event` をフラッシュに積み、`Referer` へ HTTP リダイレクトする。削除は行わない。
4. 上記がすべて成立する場合、当該フォーマットに紐づくカード別制限行（カードとフォーマットと制限の交差）をすべて削除し、その後フォーマット行を削除し、成功メッセージを積んで `m14-09_admin_card_format_list` へリダイレクトする。

## データ整合性

| 観点 | 内容 |
|------|------|
| 一覧と DB | 一覧は当該 GET リクエスト処理中に読み取ったフォーマット集合の反映である。他セッションでの更新とは楽観的競合制御を行わない。 |
| 論理削除 | マッピング上、フォーマットは `deleted_at` によるソフト削除可能な定義である。一覧取得は通常フィルタ下では論理削除済み行を含めない（Doctrine／Gedmo の運用を確認値とする）。 |
| 認定表示 | 認定 ID が NULL の行は画面では認定列を空とし、外部キー行が欠落していても Twig 側は単に空表示に留まる。 |

## DBカラム

一覧の表示に直接関係する列のみ記載する。型の詳細はスキーマ・マッピングを参照する。

| テーブル | 列 | メモ |
|----------|-----|------|
| `mtb_format` | `id` | 行リンク・削除 URL に使用。 |
| `mtb_format` | `name_jp`, `name_en` | フォーマット名列。 |
| `mtb_format` | `code` | 略称列。 |
| `mtb_format` | `certification_id` | NULL なら認定列は空。 |
| `mtb_format` | `rank` | 並びの第一キー。 |
| `mtb_format` | `deleted_at` | 論理削除。通常一覧では非表示扱い。 |

認定列の文字列は、関連エンティティがロードされていればその和名・英名マッピングに依存する。列名はマッピング上のコメントに合わせ「フォーマット名(日／英)」「認定ID」等がベースである。

### DB操作

本機能は参照系（検索）であり、DBへの登録・更新・削除は行わない。テーブル名は ec-cube-enterprise を正典とする。

| 操作種別 | 対象テーブル | 契機・条件 |
|---------|--------------|------------|
| 検索 | mtb_format | 検索条件に合致するレコードを抽出する。 |

一覧表示処理単体では利用者入力を受け付けないため、入力バリデーションは行わない。削除の可否は「関連イベント・デッキ・アーキタイプの有無」によるサーバ側判定に従う。

## 権限・認可

| 利用者状態 | 一覧表示（GET `/format`） | 削除（DELETE `/format/{id}/delete`） |
|------------|---------------------------|--------------------------------------|
| 管理画面の認証を通過した運用者 | 他の HareruyaEc 管理ルートと同様に到達し得る実装である。個別のルート単位のロール制限は Format 専用プロバイダでは追加していない。 | 同上。CSRF トークンが無効な場合は共通の CSRF 失敗経路に従う。 |
| 未認証 | 管理画面共通のログイン要求に帰着する（本書では詳細を確定しない）。 | 同上。 |

## 画面遷移

| 条件 | 遷移先 |
|------|--------|
| 「新規登録」押下 | `GET /{admin_route}/format/new` |
| フォーマット名リンクまたは「編集」 | `GET /{admin_route}/format/{formatId}/edit` |
| 削除が関連データにより拒否された | `Referer`（多くは一覧または編集の URL） |
| 削除が成功した | `GET /{admin_route}/format`（一覧再表示） |

### 遷移時に引き継ぐ状態

一覧 GET では検索条件用セッションを独自に読み書きしない。削除失敗時はフラッシュにエラーが積まれ、`Referer` 先の画面で表示され得る。削除成功時は成功フラッシュが積まれ一覧へ戻る。

---

## エラー処理

| エラー内容 | 処理 |
|------------|------|
| 削除対象フォーマットが DB に存在しない | HTTP 404。 |
| イベント・デッキ・アーキタイプのいずれかが紐づく状態で削除要求 | メッセージ `admin.format.error.delete.event` をフラッシュし、`Referer` へリダイレクト。 |
| CSRF 検証失敗 | 管理画面共通の CSRF エラー処理（本書ではメッセージ文言を確定しない）。 |

本機能ではログイン試行回数のような独自のレート制限を扱わない。

## ログ・監査

一覧 GET に特化した追加のアプリケーション情報ログはソース上は置かれていない。削除や他管理操作の共通ログ方針はコア・プラグイン全体に従う。

### ログに出してはいけないもの

- パスワード
- なりすまし対策トークン
- Cookie 値
- セッション ID の完全値
- Remember Me トークンの原値

## セッション

本機能の一覧 GET はセッションに検索状態を保存しない。削除以外の本画面の操作は基本的に GET による画面遷移である。

### セッションへ保存しない情報

一覧表示のための利用者入力やクエリ条件はセッションに載せない。

---

## Cookie

本機能は管理画面のセッション Cookie に依存するにとどまり、フォーマット一覧専用の Cookie を新たに設定しない。

---

## 排他制御・トランザクション

一覧表示は読み取りのみである。削除処理は実装が単一リクエスト内で `flush` する形であり、本書では行ロックの有無を業務要件として切り分けない。
