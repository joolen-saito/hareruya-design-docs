# デッキ管理 — デッキ登録 CSV（取込）

## 概要

HareruyaEc プラグインが管理画面に提供する「デッキ登録 CSV, TSV」画面である。利用者がアップロードしたファイルの 1 行目を論理キーとして解釈し、イベント系デッキ（`dtb_deck`）および表示条件が満たされる場合はデッキ明細（`dtb_deck_card`）まで登録または更新する。区切りは拡張子が `tsv` のときタブ文字、それ以外はコア設定の CSV 区切り文字および囲み文字を使う。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。本機能のカスタマイズ区分はカスタマイズであり、挙動は現行リポ pf-eccube3 配下の HareruyaEc プラグイン実装を確認値とし、DB関連は ec-cube-enterprise を正とする。

対象はブラウザ経由の管理画面に限定する。

コントローラのメソッド名は本文の主題としない。本文ではルートbind名やSymfonyのルートnameの網羅は主説明としない。「利用者視点の入口」にHTTPメソッドとサイトルートからのパスパターンを書く。コード探索でbind名が必要なときだけ「調査補助」へ書く。

## リニューアル移行時の扱い

現行（pf-eccube3 の HareruyaEc プラグイン）が持つデッキ系テーブルは、移行先（ec-cube-enterprise）ではコア標準のエンティティとして取り込まれている。DB関連の記述は移行先を正とする。

| 観点 | 現行（pf-eccube3） | 移行先（ec-cube-enterprise） |
|------|---------------------|-------------------------------|
| デッキ本体テーブル | `dtb_deck`。主キー列は `deck_id` | `dtb_deck`。主キー列は `id`。CSV 論理キー `deck_id` の対応先は移行先では `id` 列となる |
| デッキ明細テーブル | `dtb_deck_card`（`deck_id`・`card_id`・`board_id`・`count`） | 同名・同構成。`dtb_deck_card`（`deck_id`・`card_id`・`board_id`・`count`） |
| 表示状態 | 表示マスタ ID（`disp_id`）への写像 | 同じく `disp_id`（公開状態マスタへの外部キー） |
| デッキ種別 | デッキ種別 ID | `deck_type_id`（デッキ種別マスタへの外部キー）。未セット時のイベント種補給は移行先でも同様に要確認 |
| デッキタグ中間表 | デッキタグの多対多中間表 | `dtb_deck_deck_tag`（`deck_id`・`deck_tag_id`） |

CSV 論理キーの並び・画面表示・取込処理の判定順序は現行 pf-eccube3 実装を正とする。再取込時の `dtb_deck_card` 明細削除の有無など挙動面の差は本書の処理フロー・エッジケースを正とし、移行先で同挙動かは ec-cube-enterprise 実装で要確認とする。

## 処理フロー

### 取込フォーム画面を開く（GET `admin_deck_csv`）

1. 管理画面の認証と共通処理を通過する。
2. フォーム型 `admin_csv_import` に、ラベル翻訳キー `form.deck.strict` のチェック項目 `strict`（未必須）を結合ビルダで追加したフォームを生成し `handleRequest` する。
3. コントローラ内連想配列 `getCsvHeader` の論理キー一覧と説明をテンプレートへ渡して描画する。

### ファイルを取り込む（POST `m15-06_admin_deck_deck_csv_import`）

1. 管理画面の認証および共通処理を通過する。
2. POST 側でもフォーム構成は GET と同様に `handleRequest` する。
3. 共有サービスの `DeckCsv` インスタンスを生成するとき、想定論理キー一覧と「必須論理キー」連想配列、`sessionKey` 文字列はプレフィクス論理名としてのみ渡される（当機能の処理フローでセッションに検索状態を読み書きする実装は無い）。
4. `$deckCsv->setIsStrict` にチェック `strict` の値を渡し、その後共通「フォーム有効」のヘルパで CSRF と Symfony バリデーションを評価する。CSRF が不正なときは共通ヘルパがアクセス拒否（HTTP 403）種別へ至るコードパスとなる。
5. `checkFormValid` は Symfony 評価が不合格であれば各エラーを管理画面エラー用フラッシュへ積みつつ、このクラス共通の終了処理用リダイレクト応答オブジェクトまで組み立てる。その戻り値をデッキ用インポートコントローラは変数代入も早期 return もしておらず、ソースだけを見ると直後へ処理が進み続けるコード順序になる。この時点での副作用はフラッシュと CSRF の更新に留まって応答転送しない可能性があることを、共通実装順序とセットで読むべきギャップとする。
6. アップロードファイル参照は `import_file` から読み込み、共通 `getFormFile` はソース上サイズがゼロのときの処理本文が欠けた状態のうえ単に値を返すだけである。コンテローラはこの周辺のみ `LogicException` を明示キャッチするが、共通実装だけを見ればこの種の例外送出はしない構造にある。
7. 情報ログ「デッキCSV登録開始」を出す。
8. 共通取込サービスにより一時ファイル名を乱数ベースで採り、`csv_temp_realdir` へファイルを書き換え移設する。その後読み込み、Windows とその他環境での文字コード方針、改行統一、`removeWhite` によるゼロ幅や BOM の除去、`CsvImportService` へ第一行ヘッダを食わせて反復できる集合体を準備する。区切りは拡張子が文字列一致で `tsv` のときタブ、その他では `csv_import_delimiter` と `csv_import_enclosure` が使われる。この途中でコンストラクタが拒否すると `false` が返り、リダイレクト応答で終える。
9. アップロード後の論理ヘッダ配列が想定側の論理キー配列・任意除外セットを除いた両者の並びまで一致しない場合、`admin.csv.error.format.header` がメッセージ本文のランタイム例外が投げられ、共通の catch でロールバックとエラー返却になる（翻訳はこの時点では当てずの経路となる）。
10. データ集合の件数が 0 だとランタイム例外 `admin.csv.error.data.empty`。トランザクションはまだ開始前なので、この例外のみロールバック対象にならず取込共通の応答のみになる。
11. ORM の SQL ロガーを無効にし、`beginTransaction` する。
12. データ行ごとに次を順番に評価し、異常終了するとロールバックとエラー用フラッシュ、リダイレクトとなる。

    - 当行の値の個数がヘッダ個数と等しいこと（翻訳付きランタイム例外）
    - 必須論理キーに相当する説明連想配列への一致ルールでの空文字禁止。ただし `main_list` についてはリスト非公開に相当する `private_flg` のとき空文字許容となる分岐のみが共通必須ロジックを上書きする（コメントにより非公開フラグの検証順序との食い違いリスクがコード上に明示されている）。
    - フォーマット英名でのレギュレーション存在（翻訳付きランタイム例外）
    - アーキタイプの日本語名または英名とフォーマット ID の両方での一致がいずれかで成立すること（無ければ翻訳付きランタイム例外）
    - イベント詳細 ID が空でなければ該当行がイベント詳細に存在すること（翻訳付きランタイム例外）
    - イベント開催日が機械解釈可能な日時文字列になること、`strtotime` 失敗は翻訳付きランタイム例外、`DateTime` へ昇格される
    - 表示フラグが `dtb_deck` 側の公開・非公開定数それぞれの文字列表現と完全一致すること、以外はフォーマット系翻訳
    - デッキリスト非公開フラグも同様に二値定数との文字列完全一致
    - 統率者は当該フォーマットが統率を使うマスタフラグがあるときのみ必須。空でなければ「行頭に枚数として 1 と空白を前置したリスト解釈」でカード名が解けること、および解けた名前が有効カードとなること。
    - 旧デッキ ID が空でなければ半角英数とアンダースコア想定で最大 16 文字の事前正規表現に合致しつつ、`dtb_deck` 上での重複が無いこと
    - リスト検証経路に入る場合は、` // ` をスラッシュ一つへ正規化してからリスト解釈、統率者有無に応じたメインボード側の統率者カード重複削除とテキスト再生成、リスト形式異常および不明名検出、アーキタイプ横断チェックおよび禁止制限チェック結果を読み、そのうちチェックフラグオンなら許容しないエラーへ昇格
    - 同じくリスト検証経路かつフラグオンならフォーマットマスタ由来の最小・最大枚数との比較

13. `deck_id` 列値により Doctrine 側の単行取得規約へ従って既存本体を読み、`insertFlg` で新規オブジェクト作成と継続的 `persist` を切り替える。
14. 本体セッター群で名前・イベント・カウント類・フラグ類・リスト原文・調整済統率テキスト・旧サイト向け連番・代表画像のいずれかを設定する。表示マスタへの ID はプラグイン側 `Disp::CSV_TO_DISPID` が `dtb_deck` 由来の公開・非公開二値 CSV 値から EC-CUBE マスタ側の整数へ写像する連想で変換される。ログイン済み運用アカウントから `member_id` が必ずセットされる。
15. 「デッキ種別が未セットならイベント種」のデフォルト補給がある。
16. リスト検証経路でのみ共通 `CardUtil` によりボード単位へ `dtb_deck_card` 新規オブジェクトが積まれる経路となる。統率者はフラグオン形式で入力が済んでいれば常に統率者ボード側へ別途書き込む。
17. 行番号ベースおよび新規フラグでの `flush` とキャッシュクリアを間引きし、全行処理後にもう一度フラッシュおよび `commit`。成功時フラッシュ鍵は `admin.register.complete` と情報ログ「デッキCSV登録完了」。
18. 成功および失敗のいずれも `DeckCsv.render` が一時ファイル名が残っていれば削除を試み、GET `admin_deck_csv` へ応答ヘッダ付きリダイレクトを組み立てる。

## 取込処理時の判定順序（一覧）

| 順序 | 判定 | 結果 |
|------|------|------|
| 1 | multipart 入力とチェックフラグおよび CSRF、ファイル制約が Symfony 評価および CSRF プロバイダ側で許容されるか | 許容のみ後続進行 |
| 2 | 一時読込と区切り判定が成立するか | 失敗はリダイレクトのみ |
| 3 | ヘッダ論理順が期待と一致するか、データが 1 行以上あるか | ヘッダ空振りおよび空データは異常応答またはロールバック不要の例外のみ |
| 4 | DB 側トランザクション開始後は行順にヘッダ列長、必須空欄からマスタ照合およびリスト検証（条件付き）へ進む | 最初の異常時点で rollback とエラー用フラッシュ、リダイレクト応答となる |
| 5 | 「厳密」オフならリスト内の複数種エラー状態は昇格しないまま処理が継続し得て、オンなら昇格順を `switch` が固定する |

### エッジケース

| ケース | 扱い |
|--------|------|
| 表示はするがリストを非公開にしたい | メインリスト空欄を必須解釈から外す特例が適用される。リスト検証経路にも入らないため本文・明細チェックおよび `dtb_deck_card` 反映はしない。統率者有無の評価はフォーマットの統率使用フラグに従ってもリスト検証外で早期に例外になり得る。 |
| 「厳密」オンとオフ | オンなら禁止・制限超過などに対応する翻訳付き異常種別すべてが昇格される。オフなら昇格しないまま許容または黙読する状態が並ぶ運用モデルとなる。 |
| CSV 側 `deck_id` に既存有効 ID を書いて再取込 | コード上明示的な `dtb_deck_card` 既存削除は無い。そのためリスト検証経路を通すたび `CardUtil#setDeckCards` は新オブジェクトのみ `persist` し、`flush` と commit で既存複製が残り得る。DB 側一意制約が無いときの重複行はサイト表示仕様側でどう読むかに依存するため、一覧整合は保証しない。 |
| アップロード後にヘッダ不一致 | メッセージが翻訳キーそのまま管理画面フラッシュになり得る。 |
| Symfony 側でファイル必須違反などフォーム検証無効のみが成立したとき | `checkFormValid` はエラーをフラッシュしつつリダイレクト応答オブジェクトへまとめるが、この呼び出しの戻り値をコンテローラ側が評価して早期 return しておらず、ソース上そのまま続行コードパスにある。環境での実害（例えば `import_file` 未取得状態で後続処理が致命的エラーへ至る）は実装側の運用確認を要するギャップである。 |

## データ整合性

| 観点 | 内容 |
|------|------|

| 種類 | 内容 |
|------|------|

## DBカラム

当機能経路での主な更新および参照は次のようなテーブル列に張り付く。型や残りすべての項目はDoctrine定義および DB 実体へ照らすこと。

| テーブル | 列または関係論理名 | メモ |
|---------|---------------------|------|
| `dtb_deck` | 主キー `id`（現行 `deck_id`）。プレイヤー名・各種カウント・名前・フラグ類・リスト原文（`text_main`・`text_side`・`text_command`）・代表画像外部キー・旧サイト向け一意文字列ほか一式 | INSERT および UPDATE が列値から直接更新されるコードパス。CSV 論理キー `deck_id` の対応先は移行先 `dtb_deck.id`。 |
| EC-CUBE 共通表示マスタ | `disp_id` | CSV 側二値フラグ経由の写像のみでセットされ、プラグイン定数での写像未定義状態はソース上未考慮。 |
| `dtb_deck_card` | デッキ ID・カード・ボード・枚数ほかの明細項目 | INSERT のみ並ぶ処理が並び、ソース上削除とクリアはしない。 |

### DB操作

永続化の正は ec-cube-enterprise（テーブル名・操作は ec-cube-enterprise を正典）。当ドメインは承認ワークフローを介さず persist/flush で直接確定する（承認ワークフローは在庫機能固有）。

| 操作種別 | 対象テーブル | 契機・条件 |
|---------|--------------|------------|
| 登録/更新 | dtb_deck / dtb_deck_card | 当機能が行う登録・更新で対象テーブルを直接保存する（不要な削除は含まない）。確定は persist/flush による即時反映。DB=ec-cube-enterprise を正典とする。 |

### ログに出してはいけないもの

- アップロード済みリスト本文に混入し得る利用者入力の一覧は開発者向けにマスクしない設計にあるため運用側で一覧を取らない前提とするログ方針を別途持つことを推奨とするのみ本書には書かず、ソースの網羅的マスク有無についてはログポリシー別紙へ委ねる（秘密値の転記はしない）。

一般的なログ禁止例（資格情報、Cookie の原値すべて、セッション完全値）は管理画面共通方針に従う。

## 排他制御・楽観制御・トランザクション

Doctrine の単一レイヤでの `beginTransaction`〜`commit`／`rollback` を取込コンテキストで使うモデルとなる。ソース上ロック句や明示バージョン列は並ばず、同一 `deck_id` の競合同時取込耐性はソースからは保証されないコードパスのみとなる。

## 排他制御・トランザクション

| 観点 | 内容 |
|------|------|
| トランザクション境界 | 明示的なトランザクション境界が実装にある場合は処理フローの保存処理を正とする。明示境界が無い更新はフォーム処理またはCSV取込後の永続化処理と`flush`単位で確定する。 |
| ロック | 行ロック・悲観ロック・楽観ロック・ロックファイルを使用しない。競合時は後から確定した更新が残る。 |
| 例外時 | 検証エラーまたは保存前の例外では対象更新を確定しない。保存処理中の例外はエラー処理の節を正とし、未確定の永続化対象はロールバックまたは未flushのまま確定しない。 |
