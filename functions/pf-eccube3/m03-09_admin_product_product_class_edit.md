# M03-09（商品規格登録/編集）

## 概要

商品規格登録/編集機能は、管理画面の商品管理で、ある商品に属する1規格（言語・状態の組み合わせ単位）の価格・在庫・コード・画像・販売制限数などを登録・更新する機能である。新規登録（規格の追加）と既存規格の編集は同一の更新処理を共有する。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。既存実装のふるまい、参照するデータ、判定境界、永続化、副作用を確認し、仕様の確からしさを把握することを目的とする。

本機能のカスタマイズ区分はカスタマイズである。画面・処理の挙動は現行リポ（pf-eccube3）の実装を参照し、DB関連（テーブル名・列名・保存先・副作用のDB更新）は ec-cube-enterprise を正とする。

対象はブラウザ経由の管理画面の商品規格の登録・編集画面と更新処理である。商品本体の基本情報の編集はM03-02を正とする。規格一覧の表示、在庫・価格の一括更新、規格削除は概要に留め、価格変更CSV取込はM03-31を正とする。

管理画面プレフィックスは設定キー`admin_route`で決まる。ルート定義は`/'.$app['config']['admin_route'].'/...`の形でパスを組み立てるため、本書ではパスを`{admin_route}`で表す。コントローラのメソッド名・ルートbind名は本文の主説明としない。

## 本書で扱うこと

- 規格の新規登録画面と編集画面の表示時のふるまい（言語・状態欄の入力可否の違いを含む）
- 規格更新時の入力項目、必須・任意、保存先
- 更新送信時の処理順序（在庫履歴・価格履歴の記録、入荷通知メール、支店連携、成功時の遷移）
- 在庫数の変動時の在庫変動区分・理由の記録と、入荷区分時の在庫予約数の加算
- 規格削除が最後の1件では行えないこと

## 本書で扱わないこと

以下は本書では仕様確定せず、実装または別機能の設計を正とする。

- 商品本体の基本情報の編集（M03-02を正とする）
- 規格一覧画面（M03-09の一覧側。本書は登録・編集の詳細を扱う）の表示仕様の全量
- 在庫一括更新・価格一括更新・買取価格一括更新の画面と処理
- セール用価格変更CSV取込（M03-31を正とする）、その他の価格・在庫CSV
- 買取価格の割引計算式・買取価格表の構造（CSV取込側で扱う計算はM03-31を正とする）
- 入荷通知メールの送信内容・宛先抽出ロジック
- 支店システム連携APIの通信仕様・失敗時リトライ

## リニューアル移行時の扱い

挙動（入力項目・処理順序・履歴記録・入荷通知）は現行 pf-eccube3 を参照するが、永続化先のスキーマは移行先 ec-cube-enterprise で大きく変わる。

| 観点 | 現行（pf-eccube3） | 移行先（ec-cube-enterprise） |
|------|--------------------|------------------------------|
| 規格属性の保持先 | 補助表 `dtb_product_sub_class`（言語・状態・買取価格・帯URL・セールフラグ・高額商品コード・下代・備考・部門・棚番号など） | `dtb_product_class` に統合。`language_id`・`card_condition_id`・`buy_price`・`belt_url`・`sale_flg`・`high_price_code`・`wholesale_price`・`memo`・`section_id`・`shelf_number_id` を実在確認。補助表は廃止 |
| 規格の削除方式 | `dtb_product_class.del_flg` による論理削除 | `dtb_product_class` に `del_flg` 列が無く物理削除。移行先 ec-cube-enterprise の削除挙動で要確認 |
| 在庫予約数 | 補助表 `dtb_product_sub_class` の `stock_up_quantity01`・`stock_up_quantity03`〜`stock_up_quantity10` | 別表 `dtb_stock_up_quantity` に `stock_up_quantity_01`〜（アンダースコア区切り）で保持 |
| 在庫の反映先 | `dtb_product_stock.stock` | 同一 |

基本設計が描く本機能固有の追加仕様は無い。挙動説明中の論理削除は現行の確認値であり、移行先の物理削除との差は本節に集約する。

## 用語

| 用語 | 説明 |
|------|------|
| 商品規格 | 1商品の中の、言語と状態（カード状態）の組み合わせ単位の販売明細。価格・在庫・コード・画像などを持つ。 |
| 言語 | 規格を識別する言語区分。新規登録時は選択でき、編集時は変更しない読み取り表示になる。 |
| 状態 | カードの状態区分。新規登録時は選択でき、編集時は変更しない読み取り表示になる。 |
| 在庫変動区分 | 在庫数を変更した理由の区分。在庫数が変わったときに在庫履歴へ記録する。 |
| 在庫予約数 | 段階的な在庫の予約数量。入荷区分・マスタ更新区分での在庫増加時に増分を各予約数へ加算する。 |
| 代表画像 | 規格に紐づける商品画像。商品本体に登録済みの画像から選択する。 |
| 高額商品 | 価格変更CSVの取込対象外となる高額商品。本画面では高額商品コード欄で扱う。 |

## 利用者視点の入口

| 入口 | URLエンドポイント | 期待されるふるまい |
|------|--------------------|--------------------|
| 規格一覧を開く | `GET /{admin_route}/product/product/{id}/class/list` | 登録済みの規格一覧を表示する。商品が存在しなければ見つからない（HTTP404）。 |
| 規格の新規登録画面 | `GET /{admin_route}/product/product/{id}/class/new` | 既定値を載せた新規規格フォームを表示する。言語・状態は選択欄として表示する。 |
| 規格の編集画面 | `GET /{admin_route}/product/product/{id}/class/{classId}/edit` | 指定規格の現行値をフォームに載せて表示する。言語・状態は読み取り表示にする。 |
| 規格の新規登録送信 | `POST /{admin_route}/product/product/{id}/class/new/create` | 入力値を検証し、合格時に規格を保存して編集画面へ戻す。 |
| 規格の更新送信 | `POST /{admin_route}/product/product/{id}/class/{classId}/edit/update` | 入力値を検証し、合格時に規格・在庫・履歴を保存して編集画面へ戻す。 |
| 規格の削除 | `DELETE /{admin_route}/product/product/{id}/class/{classId}/edit/delete` | 削除可能なら規格を論理削除し、規格一覧へ戻す。最後の1件は削除できない。 |

新規登録送信と更新送信は同一の更新処理が受け、`classId`の有無で新規・編集を判別する。

## 処理フロー

### 規格の登録・編集画面を表示する

1. 利用者が新規登録画面または編集画面を開く。
2. 商品IDから商品付加情報を読み込み、見つからなければ見つからない（HTTP404）とする。
3. 編集（`classId`あり）では指定規格を読み込み、見つからなければ見つからない（HTTP404）とする。新規（`classId`なし）では既定値（在庫0、在庫無制限なし、通常種別など）を持つ空の規格を用意する。
4. 編集フォームを生成し、代表画像の選択肢と現行の代表画像を初期値として設定する。
5. 編集時かつ規格が削除可能な場合は削除ボタンを表示する。

### 規格を更新する

1. 利用者が商品規格を登録ボタンを押下する。
2. 入力値を受け取り、検証する。
3. 検証に失敗した場合は「登録できませんでした。」のエラーを設定し、同じ画面を再表示する。
4. 検証に合格した場合、規格を永続化対象にする。
5. 既存の規格・画像関連を削除し、送信された代表画像と並び順で画像関連を作り直す。
6. 在庫レコードへ在庫数を反映する。
7. 在庫数が変更されている場合、在庫変動区分・理由をもとに在庫履歴を記録し、支店側へ在庫更新を通知する。入荷区分またはマスタ更新区分で在庫が増加した場合は、増分を各段階の在庫予約数へ加算する。
8. 販売価格または買取価格が変更されている場合、価格履歴を記録する。
9. 在庫が0から正数へ増えた場合、当該規格について入荷通知メールを送る。
10. 規格の更新日時を現在時刻にし、永続化を確定する。
11. 支店システムへ当該商品の更新を通知する。
12. 「登録が完了しました。」の成功フラッシュを設定し、同じ規格の編集画面へリダイレクトする。

### 規格を削除する

1. 削除可能でない（最後の1件）場合は不正要求（HTTP400）とする。
2. 規格を論理削除し、永続化を確定する。
3. 支店システムへ当該商品の更新を通知し、規格一覧へリダイレクトする。

## 主処理時の判定順序（更新）

| 順序 | 判定 | 結果 |
|------|------|------|
| 1 | フォーム検証 | 不備なら「登録できませんでした。」を設定し同一画面を再表示。 |
| 2 | 在庫数が変更されたか | 変更時は在庫履歴を記録し支店へ在庫更新を通知。 |
| 3 | 在庫変動区分が入荷またはマスタ更新で在庫が増加したか | 増分を各段階の在庫予約数へ加算。 |
| 4 | 販売価格または買取価格が変更されたか | 変更時は価格履歴を記録。 |
| 5 | 在庫が0から正数へ増えたか | 入荷通知メールを送信。 |

## 業務ルール・計算

| 項目 | 内容 |
|------|------|
| 言語・状態の固定 | 編集では言語・状態を変更せず読み取り表示する。新規登録でのみ選択する。 |
| 在庫履歴 | 在庫数が変わったときのみ、在庫変動区分・理由を伴って記録する。 |
| 在庫予約数の加算 | 在庫変動区分が入荷またはマスタ更新で在庫が増加したとき、増分を在庫予約数01・03〜10へ加算する。 |
| 価格履歴 | 販売価格または買取価格が変わったときのみ記録する。 |
| 入荷通知 | 在庫数が0から正数へ増えたときのみ、当該規格について入荷通知メールを送る。 |
| 削除可否 | 規格が最後の1件のときは削除しない。 |

### 入力項目

| 項目名 | 必須／任意 | 最大長 | 初期値 | 保存先・扱い |
|--------|------------|--------|--------|----------------|
| 言語 | 必須（新規のみ選択） | 単一選択 | 新規は未選択、編集は現行の言語 | `dtb_product_class`（現行は補助表 `dtb_product_sub_class`）の言語参照。フォームキー`productSubClass[language]`。編集時は読み取り表示し隠しフィールドで保持。 |
| 状態 | 必須（新規のみ選択） | 単一選択 | 新規は未選択、編集は現行の状態 | `dtb_product_class`（現行は補助表 `dtb_product_sub_class`）の状態参照。フォームキー`productSubClass[cardCondition]`。編集時は読み取り表示し隠しフィールドで保持。 |
| 商品コード | 任意 | フォーム上限なし（DB依存） | 新規は空、編集はDBの商品コード | `dtb_product_class`の商品コード。フォームキー`productClass[code]`。 |
| 在庫数 | 任意（在庫数か在庫無制限のいずれか必須） | 数値（正の整数。`Regex`数値） | 新規は0、編集はDBの在庫数 | `dtb_product_class`の在庫数。フォームキー`productClass[stock]`。在庫数も在庫無制限も未設定なら「在庫数を入力、もしくは在庫無制限を設定してください。」を表示。 |
| 販売制限数 | 任意 | 10桁、1以上（`Length max 10`・`GreaterThanOrEqual 1`・`Regex`数値） | 新規は空、編集はDBの販売制限数 | `dtb_product_class`の販売制限数。フォームキー`productClass[sale_limit]`。 |
| 在庫変動区分 | 必須 | 単一選択 | 既定の区分 | 在庫履歴記録に用いる。フォームキー`stock_change_type_id`。 |
| 在庫変動理由 | 任意 | フォーム上限なし（DB依存） | 空 | 在庫履歴のメモ。フォームキー`stock_change_memo`。 |
| 販売価格 | 必須 | 10桁（`NotBlank`・`Length max 10`・`Regex`数値） | 新規は空、編集はDBの販売価格 | `dtb_product_class`の販売価格（`price02`）。フォームキー`productClass[price02]`。 |
| 買取価格 | 必須 | 9桁（`NotBlank`・`Length max 9`・`Regex`数値。桁区切り入力欄） | 新規は空、編集はDBの買取価格 | `dtb_product_class`（現行は補助表 `dtb_product_sub_class`）の買取価格。フォームキー`productSubClass[buyPrice]`。 |
| 代表画像 | 必須 | 複数選択 | 編集時は現行の代表画像 | 規格と商品画像の関連。フォームキー`productSubClass[productSubClassImages]`（`mapped`偽）。送信内容で関連を作り直す。 |
| 帯URL | 任意 | フォーム上限なし（DB依存） | DBの帯URL | `dtb_product_class`（現行は補助表 `dtb_product_sub_class`）の帯URL。フォームキー`productSubClass[beltUrl]`。 |
| セールフラグ | 任意 | チェック（論理値） | DBのセールフラグ | `dtb_product_class`（現行は補助表 `dtb_product_sub_class`）のセールフラグ。フォームキー`productSubClass[saleFlg]`。 |
| 高額商品コード | 任意 | フォーム上限なし（DB依存） | DBの高額商品コード | `dtb_product_class`（現行は補助表 `dtb_product_sub_class`）の高額商品コード。フォームキー`productSubClass[highPriceCode]`。 |
| 下代 | 任意 | 9桁（`Length max 9`・`Regex`数値。桁区切り入力欄） | DBの下代 | `dtb_product_class`（現行は補助表 `dtb_product_sub_class`）の下代（卸価格）。フォームキー`productSubClass[wholesalePrice]`。 |
| 備考 | 任意 | フォーム上限なし（DB依存） | DBの備考 | `dtb_product_class`（現行は補助表 `dtb_product_sub_class`）の備考。フォームキー`productSubClass[memo]`。 |
| 部門 | 必須 | 単一選択（未選択の選択肢あり） | DBの部門 | `dtb_product_class`（現行は補助表 `dtb_product_sub_class`）の部門参照。フォームキー`productSubClass[section]`。 |
| 棚番号 | 必須 | 単一選択（未選択の選択肢あり） | DBの棚番号 | `dtb_product_class`（現行は補助表 `dtb_product_sub_class`）の棚番号参照。フォームキー`productSubClass[shelfNumber]`。 |

買取価格・下代の最大桁はプラグイン設定（`product_sub_class.length.buy_price` 確認値9）に従う。販売価格・販売制限数の桁はコア規格フォームの`Length max 10`を確認値とする。文字列項目はフォームに`Length`を持たないため、上限はDBのカラム型に依存する。

## データ整合性

| 観点 | 内容 |
|------|------|
| 参照時点 | 編集画面表示時にDBから読み取った規格の現行値を初期表示する。 |
| 在庫レコードとの整合性 | 更新時に規格の在庫数を在庫レコードへ反映する。 |
| 履歴との整合性 | 在庫・価格の変更があった場合のみ各履歴を記録する。変更なしでは履歴を作らない。 |
| 代表画像との整合性 | 既存の画像関連を削除してから送信内容で作り直す。送信に含まれない画像は関連から外れる。 |
| 支店連携との整合性 | 更新確定後に支店へ在庫・商品更新を通知する。反映タイミングは支店連携機能の設計を正とする。 |
| CSVとの整合性 | 価格変更CSV取込（M03-31）による更新と本画面の更新は別経路であり、最後に確定した内容が現行値となる。 |

## DBカラム

本機能の登録・編集画面が直接扱う代表的な列のみを記載する。型の細部はスキーマを参照する。

| テーブル | 列 | メモ |
|---------|-----|------|

### DB操作

永続化の正は ec-cube-enterprise。商品系は承認ワークフローを介さず persist/flush で直接確定する（在庫の承認ワークフローとは別系統。`ProductController`・各CSVサービスで確認）。

| 操作種別 | 対象テーブル | 契機・条件 |
|---------|--------------|------------|
| 登録/更新 | dtb_product_class / dtb_product_stock / dtb_product_sub_class / dtb_stock_up_quantity | 当機能が行う登録・更新で対象テーブルを直接保存する（不要な削除は含まない）。確定は persist/flush による即時反映。DB=ec-cube-enterprise を正典とする。 |

## セッション

本機能では検索条件等の一覧状態を更新しない。成功・エラーフラッシュは管理画面共通の仕組みに依存する。

管理画面のセッションCookieのみを正とし、本機能用の追加Cookieは定義しない。

## 排他制御・トランザクション

更新処理は規格・在庫・履歴の保存を同一更新処理内でflush・commitする。画面側に楽観ロックの版情報は持たない。在庫変更時の支店連携は更新確定の流れの中で通知する。
