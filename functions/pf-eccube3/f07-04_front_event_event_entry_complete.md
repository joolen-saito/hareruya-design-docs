# F07-04（大会申込～完了）

ログイン会員が、イベント詳細を申込対象に選び、別日程の同イベントを追加し、支払方法を選び、確認のうえ申込を登録し、無料時または決済完了後に申込完了画面に至るまでの、複数段階のイベント申込機能である。

## 概要

大会申込～完了は、ログイン会員が選択したイベント詳細について、申込対象の選択（別日程の同イベントの追加を含む）、支払方法・チームメンバー席次とメールアドレスの入力、申込内容の確認、申込の登録、決済への遷移、申込完了画面の表示までを扱う機能である。申込登録は1トランザクションで申込・申込選手・申込履歴を作成し、チーム戦ではメンバー招待メールを送る。参加費が0円なら申込状況をエントリー済みにして完了画面へ進み、有料なら申込状況を決済中にして外部決済へ遷移し、決済完了後に完了画面へ至る。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。確認値はpf-eccube3（EC-CUBE3系）のHareruyaEcプラグインのイベント申込・支払方法選択・申込確認・申込登録・決済完了・決済キャンセル処理、申込フォーム種別（`event_registration`）、テンプレート（`Event/entry.twig`・`Event/select_payment.twig`・`Event/entry_confirm.twig`・`Event/payment_complete.twig`・`Block/js/event_payment.twig`）、申込状況マスタを正とする。

本機能のカスタマイズ区分はカスタマイズであり、挙動の参照リポはpf-eccube3、DB関連はec-cube-enterpriseを正とする。

対象はブラウザ経由のフロントに限定する。フロントのルートはロケールを先頭に持つ`/{_locale}`配下にあり、イベントは`/{_locale}/events`配下にまとまる。

本文ではフレームワークのコントローラ型名やメソッド名を主説明としない。本文ではルートbind名の網羅は主説明とせず、「利用者視点の入口」にHTTPメソッドとサイトルートからのパスパターンを書く。コード探索でbind名が必要なときだけ「調査補助」へ書く。

| 用語 | 説明 |

## 処理フロー

### 申込対象を選ぶ（GET `/{_locale}/events/{eventDetailId}/entry`）

1. イベント詳細を取得する。無ければページが見つからない（HTTP404）として扱う。
2. 受付期間外、またはログイン会員が申込済みなら、イベント詳細（F07-03）へリダイレクトする。
3. ログイン会員の選手情報で、申込可能な別日程の同イベントを取得し、申込可能なものに絞る。
4. 申込可能な別日程が無ければ、支払方法選択処理へ進む。あれば申込対象選択画面を表示する。

### 支払方法選択を開く（GET `/{_locale}/events/{eventDetailId}/select_payment`）

1. 一括遷移（主IDが0）の場合、追加対象の先頭を主対象に繰り上げる。
2. 主対象を取得する。無ければページが見つからない（HTTP404）として扱う。
3. 受付期間外、または申込済みなら、イベント詳細へリダイレクトする。
4. 追加対象を取得し、すべて同一イベントであること・すべて参加可能であることを確認する。満たさなければ不正要求（HTTP400）として扱う。
5. 合計参加費を計算する。0円なら支払方法を提示せず、有料ならイベントの支払方法を提示する。
6. 申込対象・合計・支払方法・チーム入力欄を表示する。前段の検証エラーがあれば各欄に表示する。

### 申込内容を確認する（POST `/{_locale}/events/confirm`）

1. なりすまし対策トークンを検証する。
2. 主対象を取得する。無ければHTTP404。受付期間外・申込済みならイベント詳細へリダイレクトする。
3. 追加対象を取得し、同一イベント・参加可能を確認する。満たさなければHTTP400。
4. チーム戦（チーム人数が1より大きい）なら、メンバーメールと席次を検証する。重複メール・席次不正・ログイン会員と同一メールはエラーとし、支払方法選択へエラー付きで戻す。
5. 検証を通過したら、申込確認画面を表示する。支払方法があれば確認後の送信をPOST、無料時はGETとする。

### 申込を登録する（POST `/{_locale}/events/registration`・非同期）

1. 非同期要求でなければ不正要求（HTTP400）として扱う。
2. 申込フォームを検証する。検証不正ならエラーログを記録し不正要求（HTTP400）。
3. 申込対象（主対象＋追加対象）を取得し、トランザクションを開始する。
4. 同一イベント・参加可能（定員ロックつき再判定）を満たさなければ不正要求（HTTP400）。
5. 合計参加費が0円なら申込状況をエントリー済み、正しい支払方法があれば決済中、いずれでもなければ不正要求（HTTP400）とする。
6. チーム戦なら、メンバーメール数・重複・席次を再検証し、不正なら支払方法選択へエラー付きで戻す。検証通過後、メンバーのメールのみの仮選手を作成する。
7. 申込対象ごとに、申込・申込選手（ログイン会員と仮選手）を作成し、チーム戦のメンバーには未承認・席次を設定する。チーム戦ではメンバー招待メールを送る。
8. 先頭申込から支払番号（`EV`＋作成日時＋申込ID）を生成し、申込群に設定する。
9. 申込履歴を登録する。
10. トランザクションをコミットする。例外時はロールバックして再送出する。
11. 無料なら完了画面用パラメータ（対象詳細ID）を、有料なら決済用パラメータ（支払番号・金額）をJSONで返す。

### 決済後に戻る（GET `/{_locale}/events/payment_finish`）

1. 外部決済の結果を復号して取得する。
2. 結果コードが正常でなければ、決済ログにエラーを記録し、決済キャンセルへリダイレクトする。
3. 正常なら、支払番号で申込を取得し、決済確認処理で申込状況を確定する。確定に失敗すれば決済ログにエラーを記録する。
4. 申込完了画面へリダイレクトする。

### 申込完了を表示する（GET `/{_locale}/events/payment_complete`）

1. 対象詳細IDで詳細を取得する。
2. 完了文言と、デッキ登録可能なときのデッキ登録導線、大会一覧への導線を表示する。

### 決済キャンセル（GET/POST `/{_locale}/events/payment_cancel`）

1. 支払番号で申込を取得する。
2. 決済確認処理で申込を取消側に整える。
3. 決済キャンセル画面を表示する。

## 集計条件

| 指標 | 集計の要点 |
|------|------------|
| 合計参加費 | 申込対象（主対象＋追加対象）の参加費を合算する。0円なら支払方法を提示しない。 |
| 別日程の同イベント | 同一イベントで、事前予約開始日時以降・事前予約終了日時以前・表示区分が表示・事前予約フラグが真・申込済みでない、主対象以外の日程を開催日昇順で抽出する。 |
| 申込済み人数（定員判定） | 当該イベント詳細の集計対象ステータスの申込件数に、チーム人数を掛けた人数。定員未満かどうかの判定に用いる。 |

## `申込登録` 時の判定順序

| 順序 | 判定 | 結果 |
|------|------|------|
| 1 | 非同期要求か | 非同期でなければ不正要求（HTTP400） |
| 2 | 申込フォームが妥当か | 不正ならエラーログを記録し不正要求（HTTP400） |
| 3 | 全対象が同一イベントかつ参加可能（定員ロックつき）か | 満たさなければ不正要求（HTTP400） |
| 4 | 合計が0円か、正しい支払方法があるか | 0円はエントリー済み、支払方法ありは決済中、いずれでもなければ不正要求（HTTP400） |
| 5 | チーム戦のメンバー数・重複・席次が妥当か | 不正なら支払方法選択へエラー付きで戻す |
| 6 | 上記を通過 | 申込・申込選手・申込履歴を作成、チーム戦は招待メール送信、支払番号を採番してコミット |

申込可否は受付期間（事前予約開始・終了日時）・定員・重複申込で判定する。定員判定は申込登録時に悲観ロックつきで再評価する。

## 業務ルール・計算

| 項目 | 内容 |
|------|------|
| 申込対象の同一性 | 主対象と追加対象はすべて同一イベントの日程に限る。違反は不正要求（HTTP400）。 |
| 受付期間 | 事前予約開始日時以降・事前予約終了日時以前であること。各段階で再判定する。 |
| 定員 | 申込済み人数（チーム人数換算）が定員未満であること。申込登録時は悲観ロックつきで再判定する。 |
| 重複申込 | ログイン会員の選手情報が当該イベント詳細に申込済みでないこと。 |
| 合計参加費 | 申込対象の参加費合計。0円は無料申込、1円以上は支払方法必須。 |
| 申込状況 | 無料はエントリー済み、有料は決済中で作成する。決済完了で確定、キャンセルで取消側へ。 |
| 支払番号 | 申込群共通。`EV`＋先頭申込の作成日時（`Ymdhi`）＋10桁ゼロ詰めの申込ID。 |
| チーム戦 | チーム人数が1より大きいとき、ログイン会員以外の人数分のメンバーメールと席次が必要。メンバーは席次つき未承認の申込選手として登録し、招待メールを送る。 |

### 入力項目

| 項目名 | 必須／任意 | 最大長 | 初期値 | 保存先・扱い |
|--------|------------|--------|--------|----------------|
| 別日程の同イベント選択 | 任意 | — | 主対象のみ選択 | 追加対象のイベント詳細ID（`details[]`）。同一イベント・参加可能を検証し合計参加費に加える。 |
| 支払い方法 | 有料時必須 | — | イベントの支払方法の先頭 | フォームキー`payment`（支払方法ID）。正しい支払方法でなければ申込登録で不正要求。無料時は提示しない。 |
| 席次 | チーム戦時必須 | 1～2桁の数値 | ログイン会員は先頭席、他は未選択 | `team_members[i][seat]`。数値・チーム人数以内・重複なしを検証し、申込選手の席次に保存する。 |
| チームメンバーメールアドレス | チーム戦時必須 | 半角表示可能文字 | 空 | `team_members[i][address]`。メール形式・半角・重複なし・ログイン会員と非同一を検証し、メールのみの仮選手として保存する。 |
| 申込確定チェック | 支払方法選択で必須 | — | 未チェック | チェックボックス（永続化しない）。チェックしないと「支払いへ進む」を送信できない。 |

席次・メールはログイン会員以外のメンバー人数分を入力する。ログイン会員自身はメール入力欄を持たず席次のみ選ぶ。

### エッジケース

| ケース | 扱い |
|--------|------|
| イベント詳細が存在しない | ページが見つからない（HTTP404）として扱う。 |
| 受付期間外・申込済みで各段階に到達 | イベント詳細（F07-03）へリダイレクトする。 |
| 申込対象が異イベントを含む | 不正要求（HTTP400）として扱う。 |
| 定員に達している | 参加可能でないため不正要求（HTTP400）。登録時は悲観ロックで再判定する。 |
| 合計0円 | 支払方法を提示せず、申込状況をエントリー済みで登録し完了画面用パラメータを返す。 |
| 有料で支払方法が不正・空 | 申込登録で不正要求（HTTP400）。 |
| チームメンバーメール重複・席次不正 | 支払方法選択へエラー付きで戻す。 |
| 非同期でない申込登録 | 不正要求（HTTP400）として扱う。 |
| 決済結果が異常 | 決済キャンセルへリダイレクトする。 |
| 登録途中で例外 | トランザクションをロールバックし例外を再送出する。 |

## データ整合性

| 観点 | 内容 |
|------|------|
| 申込の原子性 | 申込・申込選手・申込履歴の作成と支払番号採番は1トランザクションで確定し、例外時はロールバックする。 |
| 申込と管理画面 | 確定した申込は管理画面側のイベント申込として現れる。本書では管理側の編集は扱わない。 |
| 申込状況と決済 | 無料はエントリー済み、有料は決済中で作成し、決済完了で確定、キャンセルで取消側に整える。決済完了の確定処理は決済確認処理を正とする。 |
| 定員 | 詳細表示時点の残り予約数は概算で、申込登録時に悲観ロックで再判定する。表示と確定の差は登録側を正とする。 |
| メール送信 | チーム戦の招待メールは申込登録の中で送る。個別の送信失敗時の扱いは実装を確認値とする。 |

## API/バッチ結果

| 種類 | 内容 |
|------|------|
| API | 申込登録は非同期で、無料は完了画面用パラメータ、有料は決済用パラメータをJSONで返す。決済URL取得は非同期で外部リンク決済の遷移用フォームHTMLをJSONで返す。決済後の戻りで外部決済結果を復号して判定する。 |
| バッチ | 本機能ではバッチを実行しない。 |

決済の暗号化・URL生成・結果判定の内部仕様は外部決済プラグインを正とする。招待メール送信・申込履歴登録の個別失敗時の再実行は本書では仕様確定せず実装を確認値とする。

## DBカラム

機能に直接関係する列のみ記載する。型や一覧の細部はスキーマを参照する。

テーブル名・列名はec-cube-enterpriseを正とし、現行（pf-eccube3）と異なる場合は括弧で添える。

| テーブル | 列 | メモ |
|---------|-----|------|
| `dtb_event_detail` | `event_id`／`online_entry_start_date`／`online_entry_end_date`／`entry_flg`／`capacity`／`entry_fee` | 同一性・受付期間・定員・参加費の判定に用いる。 |
| `dtb_event` | `is_team_battle`（現行は`team_member_count`）／支払方法参照 | チーム戦判定・支払方法の提示に用いる。移行先は`is_team_battle`（チーム戦フラグ）を持つ。チーム人数の取得元はec-cube-enterprise実装で要確認。 |
| `dtb_event_entry` | 申込・申込ステータス（`entry_status_id`）・支払方法（`payment_id`）・価格（`price`）・支払会員（`paying_customer_id`）・支払番号（`payment_no`） | 申込本体。状況・支払番号・参加費を保持する。 |
| `dtb_entry_player` | 申込（`event_entry_id`）・選手（`player_id`）・席次（`seat_order`）・承認フラグ（`confirm_flg`） | 申込選手。チーム戦のメンバーは未承認・席次つきで作成する。 |
| `dtb_player` | メール（`email`）・会員参照（`customer_id`） | チーム戦のメンバーはメールのみの仮選手として作成する。 |
| `dtb_entry_history` | 申込履歴（`event_entry_id`／`entry_status_id`／`member_id`） | 申込登録時に作成する。 |
| `mtb_entry_status` | 申込状況・集計対象フラグ | エントリー済み・決済中・取消の判定、定員集計の対象判定に用いる。 |

### DB操作

永続化の正は ec-cube-enterprise（テーブル名・操作は ec-cube-enterprise を正典）。当ドメインは承認ワークフローを介さず persist/flush で直接確定する（承認ワークフローは在庫機能固有）。

| 操作種別 | 対象テーブル | 契機・条件 |
|---------|--------------|------------|
| 登録/更新 | dtb_entry_history / dtb_entry_player / dtb_event / dtb_event_detail / dtb_event_entry / dtb_player 等 | 当機能が行う登録・更新で対象テーブルを直接保存する（不要な削除は含まない）。確定は persist/flush による即時反映。DB=ec-cube-enterprise を正典とする。 |

## バリデーション

| 項目 | 内容 |
|------|------|
| 申込対象 | 主対象・追加対象がすべて同一イベントかつ参加可能であること。違反は不正要求（HTTP400）。 |
| 支払方法 | 有料時はイベントに紐づく正しい支払方法であること。不正・空は不正要求（HTTP400）。 |
| チームメンバーメール | 必須・メール形式・半角表示可能文字・重複なし・ログイン会員と非同一。違反は支払方法選択へエラー付きで戻す。 |
| 席次 | チーム人数分・数値・1～2桁・チーム人数以内・重複なし。違反は支払方法選択へエラー付きで戻す。 |
| 非同期要求 | 申込登録は非同期要求であること。違反は不正要求（HTTP400）。 |
| なりすまし対策 | 申込確認はトークン検証を行う。検証はフレームワークの範囲とする。 |

## 権限・認可

| 利用者状態 | 申込各段階 |
|------------|------------|
| 未ログイン | 申込・支払方法選択・申込登録はログイン会員の選手情報を前提とするため利用できない。会員ログインへの誘導は会員ログイン機能を正とする。 |
| ログイン済み会員 | 自身の選手情報で申込できる。申込済み・受付期間外はイベント詳細へ戻る。 |

申込・支払方法選択・申込確認・申込登録はログイン会員を前提とする。完了・決済戻りは申込群の支払番号・対象詳細で扱う。

## 画面遷移

| 条件 | 遷移先 |
|------|--------|
| 申込対象選択で別日程あり | 申込対象選択画面 |
| 申込対象選択で別日程なし | 支払方法選択画面 |
| 支払方法選択の確定 | 申込確認画面（`POST /events/confirm`） |
| 申込確認の申込する | 申込登録（非同期）→ 無料は完了画面、有料は外部決済 |
| 外部決済の正常終了 | 申込完了画面（`/events/payment_complete`） |
| 外部決済の異常 | 決済キャンセル画面（`/events/payment_cancel`） |
| 受付期間外・申込済み | イベント詳細（F07-03） |
| 同一性・参加可能・支払方法の違反 | 不正要求（HTTP400） |
| イベント詳細なし | ページが見つからない（HTTP404） |
| 完了画面のデッキ登録／大会一覧 | デッキ登録機能／イベント大会TOP |

### 遷移時に引き継ぐ状態

| 起点 | 遷移前の処理 | 遷移後の初期状態 |
|------|--------------|------------------|
| 支払方法選択 | 申込対象ID・支払方法・チーム入力をフォームへ載せる。 | 申込確認画面で確定内容を表示する。検証エラー時は支払方法選択へエラー付きで戻る。 |
| 申込確認の申込する | 申込を登録し、無料は対象詳細ID、有料は支払番号・金額を返す。 | 無料は完了画面、有料は決済URL取得を経て外部決済へ。 |
| 外部決済の戻り | 決済結果を判定し申込状況を確定または取消側へ整える。 | 完了画面、または決済キャンセル画面。 |

検索条件のようなセッション引き継ぎは行わず、申込対象・入力はリクエストパラメータで段階間を引き渡す。

## エラー処理

| エラー内容 | 処理 |
|------------|------|
| イベント詳細が存在しない | ページが見つからない（HTTP404）として扱う。 |
| 受付期間外・申込済み | イベント詳細（F07-03）へリダイレクトする。 |
| 申込対象が異イベント・参加不可 | 不正要求（HTTP400）として扱う。 |
| 支払方法が不正・空（有料） | 不正要求（HTTP400）として扱う。 |
| チームメンバーメール・席次の不正 | 支払方法選択へエラー付きで戻す。 |
| 非同期でない申込登録 | 不正要求（HTTP400）として扱う。 |
| 登録途中の例外 | トランザクションをロールバックし例外を再送出する。 |
| 決済結果が異常 | 決済ログにエラーを記録し、決済キャンセルへリダイレクトする。 |

表示文言は表示メッセージ節を正とする。

## ログ・監査

| タイミング | 記録内容 |
|------------|----------|
| 申込登録の検証不正 | 支払い前イベント登録エラーとフォームエラーの情報を記録する。 |
| 決済結果が異常 | 決済ログに結果コードのエラーを記録する。 |
| 決済確認の確定失敗 | 決済ログに確認エラーを記録する。 |

### ログに出してはいけないもの

- 決済の機微情報・暗号化値の原値
- なりすまし対策トークン
- Cookie値
- セッションIDの完全値

## 排他制御・トランザクション

申込登録は申込・申込選手・申込履歴の作成と支払番号採番を1トランザクションで確定し、例外時はロールバックする。定員判定は申込登録時に悲観ロックつきで再評価し、定員超過の同時申込を防ぐ。
