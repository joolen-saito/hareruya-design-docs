# M12-05（入荷通知依頼 一覧表示）

## 概要

分析・集計メニューの入荷通知依頼は、会員が登録した入荷通知（再入荷お知らせ）依頼を、依頼日・購入日・販売金額・購入状況・売上分析タグなどの条件で検索し、商品規格・会員・購入実績とともに一覧表示する機能である。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。確認値はpf-eccube3（EC-CUBE3系）のHareruyaEcプラグインの入荷通知依頼の検索処理、入荷通知依頼の検索用リポジトリ、検索フォーム種別、一覧テンプレートを正とする。本機能のカスタマイズ区分はカスタマイズであり、挙動は現行リポpf-eccube3を参照し、DB関連の記述はec-cube-enterpriseを正とする。現行と移行先でテーブル名・列の所在が異なる箇所は「リニューアル移行時の扱い」に集約する。

対象はブラウザ経由の管理画面に限定する。本文ではフレームワークのコントローラ型名やメソッド名を主説明としない。管理画面プレフィックスは環境により変わる（`admin_route`）。「利用者視点の入口」にHTTPメソッドとサイトルートからのパスパターンを書く。

CSVダウンロードはM12-06で扱う。本書は一覧の表示までを扱う。

---

## 本書で扱うこと

- 入荷通知依頼の初期表示時に設定される検索条件の既定値
- 検索条件（依頼日・販売金額・購入日・購入状況・並べ替え・表示件数・売上分析タグ）の指定による一覧の表示
- 抽出の対象データ・結合・除外条件・集計単位の取り扱い
- 一覧に表示する列と行ごとの操作メニュー

---

## 本書で扱わないこと

以下は本書では仕様確定せず、実装または別機能の設計を正とする。

- 検索結果のCSVダウンロード（M12-06を正とする）
- 入荷通知依頼の削除・規格編集など行操作の遷移先機能（各機能を正とする）
- フロントの入荷通知依頼の登録（フロント機能を正とする）
- 管理画面へのアクセス制御・ログイン・権限設定の詳細

## リニューアル移行時の扱い

挙動は現行リポpf-eccube3を正とし、DB関連はec-cube-enterpriseを正とする。現行（pf-eccube3）と移行先（ec-cube-enterprise）でスキーマが異なる箇所を記録する。

| 観点 | 現行（pf-eccube3） | 移行先（ec-cube-enterprise） |
|------|--------------------|------------------------------|
| 入荷通知依頼テーブル | `dtb_product_request`（`create_date`・`deleted_at`・`product_class_id`） | `dtb_product_request`（`create_date`・`deleted_at`・`product_class_id` は同名） |
| 依頼者の結合 | 会員（`dtb_customer`）への結合 | プレイヤー（`dtb_player`）への結合（`dtb_product_request.player_id`）。会員名に相当する表示はプレイヤー名となる。 |
| 商品規格テーブルのコード列 | `dtb_product_class.code` | `dtb_product_class.product_code` |
| 言語・状態の保持 | 規格サブ（`dtb_product_class_sub` 系の言語・状態・英名） | `dtb_product_class` の `language_id`（言語）・`card_condition_id`／`card_condition_name`（状態）に統合。規格サブは移行先に存在しない。 |
| 会員名（表示・絞り込み） | `dtb_customer.name01`・`name02` | `dtb_player.last_name_jp`・`first_name_jp`（英名は `last_name_en`・`first_name_en`） |
| 購入日の判定列 | `dtb_order.order_date` | `dtb_order.order_date`（同名） |

DB列に言及する箇所は移行先（ec-cube-enterprise）の名称を主とし、現行名を括弧で添える。移行先に該当が見当たらない箇所は推測でスキーマ化せず「ec-cube-enterprise 実装で要確認」と残す。

## 処理フロー

### 検索画面初期表示（`/{admin_route}/analysis/request`）

1. 管理画面の認証・権限を通過する。
2. 検索条件セッションを破棄する。
3. 依頼日Fromに当月初日、依頼日Toに当月末日、並び順に昇順を設定する。
4. 検索フォームを表示する。一覧は無しとする。

### 検索・一覧表示（`/{admin_route}/analysis/request/result`）

1. 検索フォームへ送信値を取り込む。
2. 検索条件を検索条件セッションへ保存する。
3. 論理削除フィルタを無効化する。これにより通知設定が削除済み（論理削除済み）の依頼も抽出対象とする。
4. 入荷通知依頼の検索用リポジトリへ検索条件を渡し、結果を取得する。
5. 一覧を同一画面に表示する。

## 集計条件

| 指標 | 集計の要点 |
|------|------------|
| 対象データ | 入荷通知依頼を起点に、会員・商品規格・商品・規格サブ（言語・状態）を結合する。一覧は依頼単位（依頼IDでグループ化）で表示する。 |
| 結合 | 言語・状態は規格サブの参照（左結合）で取得する。購入実績は当該会員・当該規格の注文明細・注文を左結合し、依頼の通知設定削除日より後の注文日を持つ注文を購入とみなす。 |
| 除外条件 | 論理削除フィルタを無効化して抽出する。通知済み（通知設定削除済み）の依頼も対象に含める。 |
| 期間 | 依頼日From・To、購入日From・Toで絞り込む。Toは翌日初日未満まで含める。 |
| 購入状況 | 購入状況が購入済みのみのときは購入注文日が存在する依頼、未購入のみのときは購入注文日が存在しない依頼に絞り込む。両方選択時は絞り込まない。 |
| 売上分析タグ | 売上分析タグを指定した場合、商品サブに紐づくタグで絞り込む。 |
| 並べ替え | 並べ替えで商品名・会員名・販売金額のいずれかを選んだ場合、その列で昇順/降順に並べる。 |

購入日の列は、依頼後に該当会員が該当規格を購入した注文のうち最も早い注文日を`%Y/%m/%d %H:%i`で表示する。

## 業務ルール・計算

| 項目 | 内容 |
|------|------|
| 依頼単位 | 一覧は依頼IDでグループ化し、依頼1件を1行として表示する。 |
| 購入の判定 | 依頼後（通知設定削除日より後の注文日）の同会員・同規格の注文を購入とみなす。 |
| 通知日/通知設定削除日 | 依頼の論理削除日時を、通知日または通知設定削除日として`Y/m/d H:i`で表示する。未設定のときは空。 |
| 会員名 | 会員の姓と名を全角空白で連結して表示する。 |
| 表示件数 | 一覧は表示件数の上限で打ち切る。 |

### 入力項目

| 項目名 | 必須／任意 | 最大長 | 初期値 | 保存先・扱い |
|--------|------------|--------|--------|----------------|
| 商品名（日/英）・会員名 | 任意 | フォーム上限なし | 空 | フォームキー `multi`。商品ID・商品名・規格サブ英名・規格コード・会員姓名の部分一致絞り込み。検索条件セッションへ保存。 |
| 依頼日From | 任意 | 日付 | 当月初日 | フォームキー `create_date_from`。依頼の登録日下限。 |
| 依頼日To | 任意 | 日付 | 当月末日 | フォームキー `create_date_to`。依頼の登録日上限（翌日未満）。 |
| 販売金額From・To | 任意 | 数値 | 空 | フォームキー `price_from`・`price_to`。規格の販売金額（`price02`）で絞り込む。上限は規格サブの販売金額桁数による。 |
| 購入日From | 任意 | 日付 | 空 | フォームキー `order_date_from`。購入注文日の下限。 |
| 購入日To | 任意 | 日付 | 空 | フォームキー `order_date_to`。購入注文日の上限（翌日未満）。 |
| 購入状況 | 任意 | — | 未選択 | フォームキー `bought`。購入済（1）/未購入（0）の複数選択。 |
| 並べ替え | 任意 | — | 指定なし | フォームキー `sort_key`。商品名/会員名/販売金額。 |
| 昇順/降順 | 必須 | — | 昇順 | フォームキー `asc_desc`。`asc`/`desc`。 |
| 表示件数 | 必須 | — | ページ表示件数マスタの値 | フォームキー `limit`。一覧の最大件数。 |
| 売上分析タグ | 任意 | — | 未選択 | フォームキー `tagSalesAnalyses`。複数選択。商品サブのタグで絞り込む。 |

本フォームはなりすまし対策トークンを使わない（`csrf_protection`を無効化）。

### エッジケース

| ケース | 扱い |
|--------|------|
| 検索結果が0件 | 該当データが無い旨の見出しを表示する。 |
| 通知設定が削除済みの依頼 | 論理削除フィルタを無効化するため抽出対象に含める。 |
| 購入実績が無い依頼 | 購入日列は空となる。未購入のみ選択時に抽出される。 |
| 通知設定削除日が未設定 | 通知日/通知設定削除日列は空。行操作に削除を表示する。 |

## データ整合性

| 観点 | 内容 |
|------|------|
| 参照時点 | 一覧は検索実行時にデータベースから読み取った値である。表示後の更新は自動反映しない。 |
| 論理削除フィルタ | 検索時に論理削除フィルタを無効化する。同一リクエスト内のその後の処理での扱いは共通機能の設計を正とする。 |
| CSVとの整合性 | 検索実行で検索条件をセッションへ保存する。CSVダウンロードは同じセッションの検索条件で再抽出する。 |
| 更新との整合性 | 本機能は参照のみで台帳を更新しない。削除・規格編集は遷移先機能の範囲とする。 |

## DBカラム

機能に直接関係する列のみ記載する。型や一覧の細部はスキーマを参照する。テーブル名・列名はec-cube-enterpriseを正とし、現行（pf-eccube3）と異なる場合は現行名を括弧で添える。

| テーブル | 列 | メモ |
|---------|-----|------|
| dtb_product_request | create_date | 依頼日の絞り込み・表示。 |
| dtb_product_request | deleted_at | 通知日/通知設定削除日の表示・購入判定。 |
| dtb_product_request | product_class_id | 規格との結合キー。 |
| dtb_product_request | player_id | 依頼者（プレイヤー）との結合キー。現行は会員（dtb_customer）への結合。 |
| dtb_product_class | product_code（現行 code）, price02, stock | 商品コード・販売金額・在庫数の表示・絞り込み。 |
| dtb_product_class | language_id, card_condition_id, card_condition_name | 言語・状態の表示。現行は規格サブで保持する。 |
| dtb_order | order_date | 購入日の判定・表示・絞り込み。 |
| dtb_player（現行 dtb_customer） | last_name_jp, first_name_jp（現行 name01, name02） | 会員名（プレイヤー名）の表示・絞り込み。 |

### DB操作

本機能は参照系（検索）であり、DBへの登録・更新・削除は行わない。テーブル名は ec-cube-enterprise を正典とする。

| 操作種別 | 対象テーブル | 契機・条件 |
|---------|--------------|------------|
| 検索 | dtb_customer / dtb_order / dtb_player / dtb_product_class / dtb_product_request | 検索条件に合致するレコードを抽出する。 |
