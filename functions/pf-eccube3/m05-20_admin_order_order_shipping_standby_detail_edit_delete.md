# m05-20_admin_order_order_shipping_standby_detail_edit_delete（管理画面_受注管理_出荷指示リスト詳細_備考編集・リスト削除）

## 概要

管理画面「受注管理」の「出荷指示」メニューから遷移する出荷指示リストのうち、一覧で選んだ 1 件について、備考（メモ）を保存するほか、当該リスト自体を削除する機能である。詳細画面上部のカードで備考を編集し、同一画面では紐付く受注の一覧・一括操作ボタンも表示されるが、本書が主に追うのは備考の更新 POST とリスト削除 DELETE である。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。ec-cube-enterprise のコア実装を確認値とする。

対象はブラウザ経由の管理画面に限定する。

コントローラのメソッド名は本文の主題としない。本文ではルートbind名やSymfonyのルートnameの網羅は主説明としない。「利用者視点の入口」にHTTPメソッドとサイトルートからのパスパターンを書く。コード探索でbind名が必要なときだけ「調査補助」へ書く。

本機能のカスタマイズ区分は現行踏襲であり、出荷指示機能は現行リポ（pf-eccube3 の HareruyaEc プラグイン）と移行先（ec-cube-enterprise コア）の双方に同名で実装される。挙動は現行リポの実装を踏襲し、DB（永続化先のテーブル・列）は ec-cube-enterprise の実装を正とする。

---

## リニューアル移行時の扱い

出荷指示リスト詳細の備考編集・リスト削除は、現行は pf-eccube3 の HareruyaEc プラグインに、移行先は ec-cube-enterprise コアに同名で実装される。永続化先の出荷指示リスト（`dtb_shipping_standby`）・出荷指示と受注の中間表（`dtb_order_shipping_standby`）・受注（`dtb_order`）は、両者で同一スキーマである。備考の保存先 `dtb_shipping_standby.comment`（ec-cube-enterprise ではテキスト型）・最終更新者 `dtb_shipping_standby.member_id`、リスト削除時に NULL 一括更新される `dtb_order.commit_date`、中間表の列（`standby_id`・`order_id`）は ec-cube-enterprise の定義を正とする。現行と移行先で差異が判明した場合は、DB記述は ec-cube-enterprise 実装を正とする。

## 処理フロー

### 詳細を表示する（GET `admin_shipping_standby_edit`）

1. 管理画面の認証・共通制約を通過する。
2. パス `{id}` でリポジトリがリスト行を受注・受注明細まで内部結合で読み込む。該当が無い、または結合条件により行が得られない場合は空配列扱いとなり HTTP 404 を返す。
3. 最終更新者は `member_id` から管理者アカウントを検索し、表示用配列に足す。
4. 紐付く各受注の ID から注文番号文字列を解決し、テンプレートへ渡す。
5. 備考は専用フォーム種別で、初期データは現行の `comment` のみとする。
6. `ShippingStandby/edit.twig` を描画する。

### POST が `admin_shipping_standby_edit` に届いた場合

1. 上記と同様に表示処理のみが走り、備考の保存は行わない。運用上はフォームの `action` が更新用ルートに向くため、この経路は通常使われない。

### 備考を保存する（POST `admin_shipping_standby_update`）

1. 管理画面の認証・共通制約を通過する。
2. `id` で出荷指示リスト行を主キー検索する。無ければ HTTP 404。
3. フォームにエンティティを載せてリクエストを取り込む。
4. 未送信または検証失敗のとき、管理画面の汎用保存エラーメッセージをフラッシュし、`admin_shipping_standby_edit` へリダイレクトする。
5. 成功時、トランザクション内で当該行の備考と最終更新者 ID を更新し、コミットする。失敗時はロールバックのうえ例外を再送出する（コントローラでは捕捉しない経路が主である）。
6. 業務アクション内で引数不正として無効論理引数例外が送出された場合、メッセージをエラーフラッシュし、編集画面へ戻す分岐がある（現行の更新アクション実装本体からこの例外が直接送出される箇所は無い。呼び出し先差し替えを想定した経路として残っている可能性がある）。
7. 成功時、汎用保存完了メッセージをフラッシュし、`admin_shipping_standby_edit` へリダイレクトする。

### リストを削除する（DELETE `admin_shipping_standby_delete`）

1. 管理画面の認証・共通制約を通過する。
2. CSRF トークンをリクエスト本文または専用ヘッダから検証する。無効ならアクセス拒否（HTTP 403）となる実装である。
3. `id` でリスト行を主キー検索する。無ければ HTTP 404。
4. トランザクション内で、紐付く受注配列に対して出荷指示日を NULL に一括更新してから、リスト行を削除しフラッシュしてコミットする。
5. 無効論理引数例外を捕捉する分岐があるが、現行の削除アクション実装から直接この例外が送出される箇所は無い。
6. 成功時、汎用削除完了をフラッシュする。
7. セッションキー `admin.shipping_standby.search.page_no` にページ番号が入っていれば、ルート名 `admin_shipping_standby_search` へ `page_no` 付きでリダイレクトし、無ければ `admin_shipping_standby` へリダイレクトする。リポジトリ／trait 側の一覧は `eccube.admin.shipping_standby.search.page_no` にページを保存しており、キー名が一致しないため、現行コードのみを見ると削除後は多くの場合 `admin_shipping_standby` 側に落ちる。また `admin_shipping_standby_search` という名前のルート定義は本リポジトリのルート一覧上は見当たらない（セッションに値が残っていた場合は未定義ルート参照になりうる）。

## 業務ルール・計算

| 項目 | 内容 |
|------|------|
| 備考更新 | 検証通過後、当該リスト行の備考列と最終更新者 ID 列だけを上書きする。更新日時列を明示的に進める処理はこのアクション内には無い。 |
