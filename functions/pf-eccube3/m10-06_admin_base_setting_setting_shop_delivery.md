# 店舗設定 — 配送業者・配送料・お届け時間（配送方法管理）

## 概要

管理画面の「店舗設定」配下において、配送方法（配送業者）マスタの一覧表示・並び順変更・論理削除、および配送方法ごとの編集（基本属性、利用可能な支払方法、都道府県別送料、お届け時間帯の文言、ショップ内向けメモ）を扱う機能である。ナビゲーション上は「配送方法管理」と関連付けられ、一覧の見出しも「配送方法一覧」である。編集画面のサブタイトル文言は「配送先管理」となっている。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。pf-eccube3 コア実装を確認値とする。プラグインにより管理画面テンプレートやハンドラ実装が差し替えられる場合は、その環境の実装を正とする。

対象はブラウザ経由の管理画面に限定する。

本機能のカスタマイズ区分は現行踏襲であり、画面・処理の挙動は現行リポ（pf-eccube3）の実装を確認値とし、DB関連（テーブル名・列名・型・保存先）は ec-cube-enterprise を正とする。

本書の本文ではルート名の網羅やコントローラ実装の手順は扱わない。ただし「利用者視点の入口」には、HTTP メソッドとサイトルートからの相対パスを `{admin_route}` を含む形で記載する（ホスト名・絶対 URL は書かない）。

---

## 本書で扱うこと

- 配送方法一覧の抽出条件、表示内容、ドラッグ並び替え（Ajax）による表示順の更新
- 配送方法の新規作成時の既定値（商品種別、表示順、削除フラグ）
- 編集画面の入力項目と保存先（配送エンティティ、都道府県別配送料、お届け時間、支払方法との中間エンティティ）
- 検証ルール（Symfonyフォーム制約および送信後の支払方法チェック）
- 登録成功時・削除成功時・削除対象不存在時のフラッシュメッセージと画面遷移
- 論理削除時の削除フラグ・ランクの更新および残存レコードのランク詰め直し
- お届け時間スロットを画面では最大16件まで扱う実装
- 「全国一律送料」入力欄とクライアントスクリプトによる各都道府県送料欄への一括反映（永続化は各都道府県の送料列のみ）
- Doctrineの保存時イベントにより作成日時・更新日時・作成者が自動設定される範囲
- 一覧表示後・編集フォーム組み立て後・編集保存後・削除後にイベントがディスパッチされ、プラグイン等が差し込めること

## 本書で扱わないこと

以下は本書では仕様確定せず、実装または別機能の設計を正とする。

- 管理画面ログイン、セッション、CSRFの仕様の詳細（名称や値の環境依存を含む）。削除操作におけるトークン検証は行う実装であるが、トークン値そのものは本書では扱わない。
- フロントのカート・購入フローにおける配送方法の絞り込み（商品種別・選択済み支払方法との突き合わせ）、送料の確定計算、複数配送設定との組み合わせの詳細
- 支払方法マスタ自体の登録・編集（当機能では既存の支払方法からチェックボックスで選択するのみ）
- 商品種別マスタの定義・並び順変更（当機能ではドロップダウンで選択するのみ）
- 都道府県マスタの件数・ID割り当ての業務的意味（当機能ではマスタの全件について送料行を用意する実装である）
- プラグイン差し替え後の画面項目・検証・保存処理の差分の完全列挙

## リニューアル移行時の扱い

現行（pf-eccube3）の挙動を踏襲しつつ、永続化先は移行先（ec-cube-enterprise）の配送関連テーブルに合わせる。テーブル名は同一だが、主キー名・並び順キー・削除方式・外部キー名に差がある。当書の各列名は移行先の名称を主とし、現行名を括弧で添える。

| テーブル | 観点 | 現行（pf-eccube3） | 移行先（ec-cube-enterprise） |
|---------|------|--------------------|------------------------------|
| dtb_delivery | 主キー | `delivery_id` | `id` |
| dtb_delivery | 並び順 | `rank` | `sort_no` |
| dtb_delivery | 削除方式 | `del_flg`（論理削除） | `visible`（boolean。表示制御） |
| dtb_delivery | 商品種別外部キー | `product_type_id`（商品種別） | `sale_type_id`（販売種別マスタへの外部キー） |
| dtb_delivery | 英語名・属性 | 無し | `service_name_en`・`max_size`・`lead_time`・`is_abroad` 等が追加 |
| dtb_delivery_fee | 主キー | `fee_id` | `id` |
| dtb_delivery_fee | 都道府県外部キー | `pref` | `pref_id` |
| dtb_delivery_fee | 送料 | `fee`（decimal） | `fee`（decimal(12,2)・unsigned）。`size`・`weight` 列が追加 |
| dtb_delivery_time | 主キー | `time_id` | `id` |
| dtb_delivery_time | 並び順・表示 | 無し | `sort_no`・`visible` が追加 |
| dtb_payment_option | 構成 | `delivery_id`＋`payment_id` の複合主キー | 同一。`base_info_id` 列が追加 |

現行の論理削除（`del_flg`）は移行先では表示フラグ（`visible`）に置き換わる点、商品種別（`product_type_id`）が販売種別（`sale_type_id`）へ改称される点が主な差分である。入力項目・DBカラム節の現行列名は現行挙動の確認用に残し、移行先の永続化先は本節および「DBカラム」節の移行先名を正とする。

## 用語

| 用語 | 説明 |
|------|------|
| 配送方法 | 画面上・ナビ上の呼称。データモデル上は配送業者（配送サービス）に相当し、`dtb_delivery` の1行として保持される。 |
| 都道府県別配送料 | 配送方法×都道府県ごとの送料。`dtb_delivery_fee` に保持される。 |
| お届け時間 | 購入者が選択する時間帯文言の候補。`dtb_delivery_time` に保持され、配送方法に紐づく。 |
| 管理者 | 管理画面にログイン可能な `Member`。配送方法の編集には管理画面の認可が前提となる。 |
| 論理削除 | `dtb_delivery.del_flg` を削除済み値に更新し、一覧や通常取得から除外する削除方式。物理削除は当機能では行わない。 |

## 利用者視点の入口

| 入口 | URLエンドポイント | 期待されるふるまい |
|------|--------------------|---------------------|
| ナビから配送方法一覧を開く | `GET /{admin_route}/setting/shop/delivery` | 削除フラグが「未削除」の配送方法だけが表示順のルールに従って並ぶ。各行に配送業者名・名称（サービス名）、編集・削除の導線がある。データが0件なら空表示になる。 |
| 一覧で行をドラッグして並べ替える | `POST /{admin_route}/setting/shop/delivery/rank/move`（本文に並べ替え対象IDとランク。実装を正とする） | 並べ替え操作中はモーダルBackdropで画面が覆われ、Ajax送信後にBackdropが外れる。サーバー側で各行の表示順（ランク）が更新される。 |
| 「配送方法・配送料を新規入力」ボタン（文言は設定により前半のみの場合あり） | `GET /{admin_route}/setting/shop/delivery/new` | 新規用の編集画面が開く。商品種別にはマスタ上の先頭（ランク昇順で最初）が既定選択になる場合がある。 |
| 一覧から編集へ進む | `GET /{admin_route}/setting/shop/delivery/{id}/edit` | 既存の配送方法が読み込まれ、全ての都道府県について送料行がフォームに並ぶ。お届け時間は最大16件分の入力枠が並ぶ。既に紐づく支払方法はチェック済みで表示される。 |
| 「登録」を押す（編集画面） | `POST /{admin_route}/setting/shop/delivery/new` または `POST /{admin_route}/setting/shop/delivery/{id}/edit` | 検証に成功すれば保存され、成功フラッシュが積まれたうえで一覧へ遷移する。失敗すれば同一編集画面に留まり、項目エラーが表示される。 |
| 一覧から削除を実行する | `DELETE /{admin_route}/setting/shop/delivery/{id}/delete` | CSRFトークンが伴う削除リクエストが送信される。対象が存在すれば論理削除され、成功フラッシュが積まれ一覧へ戻る。対象が存在しなければ警告フラッシュが積まれ一覧へ戻る。 |
| 未ログインまたは権限・IP制限で拒否される利用者 | 上記パス（到達前） | 管理画面の共通ルールに従いアクセスできない（詳細は管理画面認証・認可の実装を正とする）。 |

## 処理フロー

### 一覧を開く（GET）

1. 管理画面の認証・権限・IP制限の各ルールを通過する。
2. 削除フラグが「未削除」の配送方法を、表示順の降順で取得する。
3. 一覧表示完了後にイベントをディスパッチする（プラグイン等が一覧データを参照できる）。
4. テンプレートを描画する。

### 一覧上で並び順を変更した直後（Ajax POST）

1. リクエストがAjaxであると判定された場合のみ処理する。それ以外は処理しない。
2. リクエストボディに含まれる「配送方法ID → 新ランク」の対応を繰り返し、該当エンティティのランクを更新して永続化する。
3. レスポンスボディは実質的に真値のみで、一覧画面の再読込は行わない。

### 新規編集画面を開く（識別子が新規）

1. 既存最大ランクを参照し、その値に1を加えた値を新規配送方法のランクとする。既存が無ければ1とする。
2. 削除フラグを「未削除」にし、商品種別をマスタから取得した先頭（ランク昇順で最初の1件）に設定した新規エンティティを組み立てる。
3. 全ての都道府県について配送料エンティティを検索し、無ければ作成する。配送料金額が空に相当するものだけを配送方法に関連付けとして追加する（既存読込時はDBから既に関連付いている行が主となる）。
4. 関連付け済み配送料を都道府県ID昇順で並べ替え直し、コレクションへ再登録する。
5. お届け時間コレクションの件数が16未満である間、空のお届け時間エンティティを追加し続け合計16件相当になるまで埋める。
6. フォームビルダーを生成し、編集初期化イベントをディスパッチする。
7. フォームを構築し、お届け時間・支払方法フィールドに現在のコレクション状態を明示的にセットする。
8. POSTでなければテンプレートを描画する。

### 既存編集画面を開く（識別子が既存）

1. 識別子で配送方法を取得する。取得できなければその後の処理は実装の分岐に従う（新規相当の扱いにはならない）。
2. 全ての都道府県について配送料を検索または作成し、金額が空に相当する行のみを関連付けに追加する。
3. 以降は「新規編集画面を開く」の手順4〜8と同様。

### 「登録」押下（POST、検証成功）

1. フォームをリクエストで処理する。
2. 検証成功時、フォームデータとして配送方法実体を取得する。
3. お届け時間について、文言がnullの要素を配送方法から外し、データストアから削除する。文言がnullでない要素は残る（空文字のみの行はこの判定では削除されない）。
4. 当該配送方法に紐づく「配送—支払」中間レコードをすべて検索し、エンティティから外して削除する。
5. 配送方法を永続化してフラッシュする（新規ならこの時点で識別子が採番される）。
6. フォームで選択された支払方法ごとに中間エンティティを新規作成し、配送方法と支払方法の双方に関連付けて永続化する。
7. 再度永続化処理とフラッシュを行う。
8. 編集保存完了イベントをディスパッチする。
9. 管理画面向け成功メッセージを積む。
10. 一覧へリダイレクトする。

### 「登録」押下（POST、検証失敗）

1. フォームをリクエストで処理する。
2. 検証失敗時、同一編集テンプレートを再描画する。成功メッセージは積まない。

### 削除実行

1. CSRFトークン検証を行い、失敗時はHTTPアクセス拒否例外となる。
2. 識別子で配送方法を取得する。無ければフラッシュをクリアしてから警告メッセージを積み、一覧へリダイレクトして終了する。
3. 削除フラグを「削除済み」にし、ランクを0に更新する。
4. 削除フラグが「未削除」の配送方法を表示順の昇順で取得する。
5. 削除対象以外について、表示順を1から順に振り直して永続化する。
6. フラッシュする。
7. 削除完了イベントをディスパッチする。
8. 成功メッセージを積み、一覧へリダイレクトする。

## 「登録」時の判定順序（フォーム検証）

| 順序 | 判定 | 結果 |
|------|------|------|
| 1 | フィールド個別のSymfony制約（必須・URL形式・金額の下限・桁など） | 違反時は該当項目にエラー。処理は進まない。 |
| 2 | 送信後イベントで支払方法が1件も選択されていないか | 違反時は支払方法フィールドにエラー文言を付与する。処理は進まない。 |

画面上のメッセージ文言はメッセージカタログのキーに依存する（具体文言は翻訳リソースを正とする）。

## 業務ルール・計算

| 項目 | 内容 |
|------|------|
| 一覧の対象 | 削除フラグが「未削除」の配送方法のみ。 |
| 一覧の並び | 表示順の降順（数値が大きいほど一覧の先頭側に来やすい実装である）。 |
| 新規の表示順 | 既存の配送方法のうち最大の表示順に1を加えた値。既存が無ければ1。 |
| 論理削除後の表示順 | 「未削除」のみを昇順に読み、一覧に現れる行へ先頭から1,2,3,…と割り当て直す。削除対象はランク0・削除済みフラグのまま。 |
| お届け時間の枠数 | 編集画面では常に16件分の入力行が並ぶように空行を充填する。 |
| 全国一律送料 | フォーム上は金額ウィジェットとして表示されるがエンティティにはマップされない。反映ボタンで各都道府県の送料入力へ値を複製するのみ。 |
| 送料の数値 | 金額フィールドは整数・通貨は実装上日本円相当のオプションが既定。0以上かつ設定ファイル由来の最大桁制約を課す。 |

### 入力項目

| 項目名 | 必須／任意 | 最大長 | 初期値 | 保存先・扱い |
|--------|------------|--------|--------|----------------|
| 配送業者名 | 必須 | Symfony Length制約は無し（DBはtext型） | 既存値または空 | `dtb_delivery.name` |
| 名称 | 必須 | 同上 | 既存値または空 | `dtb_delivery.service_name` |
| 伝票No.URL | 任意 | 同上 | 既存値または空 | `dtb_delivery.confirm_url`。入力がある場合はURL形式制約。 |
| 商品種別 | 必須 | — | 新規はマスタ先頭、既存はDB値 | `dtb_delivery.sale_type_id`（現行 `product_type_id`。販売種別マスタへの外部キー） |
| 支払方法（複数） | 実質必須（1件以上） | — | 既存の関連する支払方法がチェック済み | `dtb_payment_option` に配送方法識別子と支払方法識別子の組で保存。保存時に旧行は全削除のうえ再作成する。 |
| お届け時間（最大16行） | 各行任意 | text項目として桁制約は無し（DBはtext型） | 既存の時間帯文言または空 | `dtb_delivery_time.delivery_time`。nullの行は保存直前に削除。 |
| 全国一律送料 | 任意 | 金額ウィジェット既定（桁は設定の `price_len` 確認値が8） | 空 | 永続化しない。反映ボタンで各行送料入力へコピーするだけ。 |
| 都道府県別送料（全県分） | 必須（各行） | 同上 | 既存値または未設定 | `dtb_delivery_fee.fee`。配送方法と都道府県の組で1行。 |
| ショップ用メモ欄 | 任意 | 同上 | 既存値または空 | `dtb_delivery.description` |

最大長の数値はコア付属の `src/Eccube/Resource/config/constant.yml.dist` における `price_len`（確認値8）を記載する。運用環境で上書きされている場合はその環境の値が正とする。

### エッジケース

| ケース | 扱い |
|--------|------|
| 削除対象の識別子が存在しない | 警告フラッシュを積み一覧へリダイレクトする。 |
| お届け時間の文言がnull | 保存直前にその行エンティティを削除する。 |
| お届え時間の文言が空文字のみ | null削除の対象外。保存され得る。 |
| 支払方法が0件 | 送信後検証でエラーとなり保存しない。 |
| 新規作成でまだ識別子が無い状態の支払関連の読込 | 識別子0で中間テーブルを検索するため、ヒットは通常無い。その後の保存で識別子が採番され、中間行が作成される。 |

## データ整合性

| 観点 | 内容 |
|------|------|
| 一覧と編集 | 一覧は削除フラグが「未削除」のみ。編集は識別子指定で取得した行を基本とする（削除済み行の編集抑止はコア単体の実装では明示していない）。 |
| 支払方法の関連 | 保存のたびに当該配送方法の中間行を全削除し、フォーム選択で再作成する。途中失敗時の整合はトランザクション境界の実装を正とする。 |
| 並び順Ajaxと一覧 | Ajax成功後もブラウザは同一HTMLのままである。他セッションでの変更とは同期しない。 |
| 作成日時・更新日時・作成者 | 永続化直前のDoctrineイベントで、作成日時・更新日時が設定される。管理者ログイン下での新規作成時は作成者がログインユーザに設定される実装である。更新時は更新日時が上書きされる。 |

## 排他制御・トランザクション

当機能のコア実装はDoctrineの典型パターンによる永続化であり、配送方法を楽観ロックで版本管理する実装は持たない。複数管理者が同一配送方法を同時編集した場合の結果は最後にflushされた内容が残る。
