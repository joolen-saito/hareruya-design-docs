# 店舗設定 — 税率設定（共通税率・商品別税率オプション）

## 概要

管理画面の「店舗設定」配下において、店舗全体の共通税率（税率・課税規則・適用開始日時）を複数件保持し、画面上で一覧・新規登録・編集・論理削除する機能である。また、画面ブロック「個別税率設定」から、商品ごとに個別の税率ルールを設定できるモード（実装上は店舗基本情報のオプション項目）を切り替える。画面ブロックタイトルは「基本情報設定」、サブタイトルは「税率設定」である。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。pf-eccube3コア実装を確認値とする。プラグインがコントローラ・テンプレート・イベントを差し替えている環境では、その環境の実装を正とする。

カスタマイズ区分は現行踏襲であり、挙動の参照リポはpf-eccube3とする。DB関連の記述（テーブル名・列名・型・制約、保存先・扱い、副作用のDB更新）はec-cube-enterpriseを正とする。現行と移行先でスキーマが異なる箇所は「リニューアル移行時の扱い」に集約する。

対象はブラウザ経由の管理画面に限定する。

本書の本文ではルート名の網羅やコントローラ実装の手順は扱わない。ただし「利用者視点の入口」には、HTTP メソッドとサイトルートからの相対パスを `{admin_route}` を含む形で記載する（ホスト名・絶対 URL は書かない）。

## 本書で扱うこと

- 税率設定画面のブロック構成（個別税率設定・共通税率設定・税率一覧）と、同一HTMLフォーム内に2系統の送信先があること
- 共通税率の入力検証、同一適用日時の重複チェック、保存・削除・適用不能・不存在時のリダイレクトとフラッシュメッセージ
- `tax_rule_id` が既定の基本税率（ID固定値1）のときのフォーム差し替え（適用日時フィールド非表示・変更対象外）
- 税率一覧の抽出条件（商品・規格に紐付かない共通税率のみ）と並び（適用日時の降順）
- 店舗基本情報への「商品別税率機能」フラグの保存経路（上部「登録」ボタン専用）
- 新規共通税率行の既定（課税規則マスタID1、税端数調整0、論理削除フラグ0）と、永続化時に付与される作成者・日時
- イベントディスパッチによるフォーム初期化・保存完了・削除完了・パラメータ保存完了への差し込み点
- 購入・表示側で税率を解決するときの優先キー設定（設定ファイルの確認値）およびリポジトリ内キャッシュの存在（画面保存とは別経路の確認値として記載）

- 課税規則マスタ（`mtb_taxrule`）の名称・件数の運用変更手順
- 導入プラグインによる差分の完全列挙

## リニューアル移行時の扱い

現行（pf-eccube3）と移行先（ec-cube-enterprise）で、共通税率の永続化に関するスキーマが異なる。挙動説明は現行を確認値とするが、DB記述は移行先を主とし、現行名を括弧で添える。

| 観点 | 現行（pf-eccube3） | 移行先（ec-cube-enterprise） |
|------|--------------------|------------------------------|
| 主キー列 | `tax_rule_id` | `id`（`dtb_tax_rule.id`） |
| 削除方式 | `del_flg` による論理削除。一覧取得では除外しない | `del_flg` 列が無く物理削除。論理削除の概念自体が無い |
| 課税規則（端数処理）の参照 | `calc_rule`（参照先マスタ `mtb_taxrule`） | `rounding_type_id`（参照先マスタ `mtb_rounding_type`、丸め種別マスタ） |
| 税率・税端数・適用日時・作成更新・作成者・地域商品キー | `tax_rate`／`tax_adjust`／`apply_date`／`create_date`／`update_date`／`creator_id`／`country_id`／`pref_id`／`product_id`／`product_class_id` | 同名（`dtb_tax_rule` 上で一致） |
| 商品別税率機能フラグ | `dtb_base_info.option_product_tax_rule` | 同名（移行先では真偽型、既定偽） |

移行先で論理削除が無いため、現行の「一覧取得が論理削除行を除外しない」という挙動は移行先には引き継がれない。削除済み行が一覧に残る現象は現行固有の確認値であり、移行先では物理削除により行自体が消える。

## 用語

| 用語 | 説明 |
|------|------|
| 共通税率 | `dtb_tax_rule` のうち、`product_id` と `product_class_id` がともにNULL相当の行。本画面の一覧と編集対象はこの集合に限られる。 |
| 基本税率設定 | `tax_rule_id` がコア定数で定められた既定値（1）の共通税率行。一覧では適用日時列に固定文言「基本税率設定」と表示し、適用日時入力は出さない。 |
| 商品別税率機能 | 店舗基本情報 `dtb_base_info.option_product_tax_rule`。有効時のみ課税解決で商品・規格を考慮する実装分岐がある（詳細はリポジトリ・サービス実装を正とする）。画面ラベルは「商品別税率機能」。 |
| 課税規則 | `dtb_tax_rule.calc_rule` が参照するマスタ `mtb_taxrule` の1件。税額計算時の端数処理種別（四捨五入・切り捨て・切り上げ）に対応するIDがマスタに保持される。 |
| 適用日時 | 共通税率が「いつから有効か」の起点として比較される日時。基本税率行では画面上から変更しない。 |
| 論理削除 | `del_flg` を削除済み値へ更新する。本画面の一覧取得では論理削除を除外しないため、一覧に残りうる（実装確認値）。 |

## 利用者視点の入口

| 入口 | URLエンドポイント | 期待されるふるまい |
|------|--------------------|---------------------|
| ナビから税率設定を開く（一覧の既定入口） | `GET /{admin_route}/setting/shop/tax` | 「個別税率設定」「共通税率設定」「税率一覧」が縦に並ぶ。共通税率の入力フォームは新規行用の初期状態で載り、`商品別税率機能`は現在の店舗基本情報の値が選択状態になる。一覧は共通税率のみが適用日時の新しい順で並ぶ。 |
| 一覧から「編集」を選ぶ | `GET /{admin_route}/setting/shop/tax/{id}/edit` | 当該行がフォームに載る。基本税率行なら適用日時欄は出ない。それ以外なら適用日時欄と日時ピッカーが出る。 |
| 共通税率で下部「登録」を押す | `POST /{admin_route}/setting/shop/tax` または `POST /{admin_route}/setting/shop/tax/{id}/edit`（編集文脈に応じる） | 検証に通れば当該行が保存され、成功メッセージのあと税率設定画面に戻る。失敗なら同画面でフィールドエラーが付く。 |
| 「個別税率設定」ブロックの「登録」を押す | `POST /{admin_route}/setting/shop/tax/edit_param` | フォームの送信先だけが切り替わり、`商品別税率機能`の選択だけが店舗基本情報へ保存される想定の経路になる。成功時は成功メッセージのあと税率設定画面に戻る。検証に失敗した選択値は保存されず、その場合も同様に画面へ戻る。 |
| 一覧から「削除」（論理削除）を実行する | `DELETE /{admin_route}/setting/shop/tax/{id}/delete` | CSRF付きの削除要求。基本税率行は削除処理を呼ばず一覧へ戻るのみ。それ以外で対象が存在すれば論理削除し成功メッセージ。存在しなければ警告メッセージに差し替えられたうえで一覧へ戻る。 |
| 編集対象IDが存在しない | `GET /{admin_route}/setting/shop/tax/{id}/edit`（不存在の `{id}`） | 例外によりエラー画面系の応答となる（フレームワークのエラーハンドリングに従う）。 |
| 未ログインまたは権限・IP制限で拒否される利用者 | 上記パス（到達前） | 管理画面の共通ルールに従いアクセスできない（詳細は管理画面認証・認可の実装を正とする）。 |

## 処理フロー

### 一覧画面を開く（GET、一覧用エンドポイント）

1. 管理画面の認証・権限・IP制限の各ルールを通過する。
2. 編集対象として新規の共通税率エンティティを組み立てる（課税規則はマスタID1を既定割り当て、税端数調整0、論理削除フラグ0）。
3. 店舗基本情報を取得し、フォームの「商品別税率機能」に現在値を明示的にセットする（フォーム項目自体はエンティティにマップしない）。
4. 編集対象が基本税率ならフォームから適用日時項目を取り除く。
5. イベントでフォームビルダに対する初期化フックを実行する。
6. 共通税率一覧を取得しテンプレートへ渡す。
7. テンプレートを描画する。

### 一覧画面を開く（GET、既存行の編集エンドポイント）

1. 管理画面の認証・権限・IP制限の各ルールを通過する。
2. パスに含まれるIDで共通税率を取得する。無ければ例外。
3. 以降は「一覧を開く」と同様に、店舗基本情報との合成フォームを組み立て、基本税率なら適用日時を除外し、イベント初期化、一覧取得、描画する。

### 共通税率を保存する（POST、一覧または編集エンドポイント）

1. フォームをリクエストで処理する。
2. フォーム全体が有効であり、かつ同一適用日時の別行が存在しないことを確認する（基本税率は適用日時がフォームに無いため、この重複検索は実質ほかの行の適用日時との突き合わせのみになる）。
3. 対象の共通税率エンティティを永続化しフラッシュする。イベントで完了フックを実行する。
4. 管理画面向け成功メッセージを積み、税率設定画面（一覧表示）へリダイレクトする。
5. 検証に失敗した場合は同一テンプレートを再描画し、成功メッセージは積まない。

### 商品別税率機能だけを保存する（POST、パラメータ用エンドポイント）

1. `tax_rule` 名前のフォームビルダをデータ無しで用意し、イベントで初期化フックを実行する。
2. POSTならリクエストで処理する。
3. 「商品別税率機能」子フォームだけが有効な場合に限り、店舗基本情報の同一項目を更新しフラッシュする。完了イベントを実行し、成功メッセージを積む。
4. GETでもPOSTでも最終的に税率設定画面（一覧表示）へリダイレクトする。子フォームが無効な場合は店舗基本情報を更新しない。

### 共通税率を論理削除する（DELETE）

1. CSRFトークン検証を行う。
2. 対象IDで行を取得する。無ければフラッシュをクリアし警告メッセージだけ残して一覧へリダイレクトする。
3. 基本税率行でなければ論理削除フラグを更新してフラッシュし、完了イベントと成功メッセージを積む。
4. 基本税率行なら何も更新せず一覧へリダイレクトする。
5. 一覧へリダイレクトする。

## 課税解決時の優先順序（参照のみ）

購入処理など別機能が税率を解決するとき、共通／地域／商品／規格の優先は設定キー `tax_rule_priority` の並びに基づきランク付けしたうえで、適用日時とランクの組でソートして先頭を選ぶ実装である。既定の確認値は `product_id,product_class_id,pref_id,country_id` の順である。同一リクエスト内のリポジトリキャッシュにより、キャッシュクリアまで再問い合わせ結果が再利用される。

本節は税率設定画面の保存処理そのものではなく、保存結果が参照される側の実装概要のメモである。

## 業務ルール・計算

### 入力項目

| 項目名 | 必須／任意 | 最大長 | 初期値 | 保存先・扱い |
|--------|------------|--------|--------|----------------|
| 商品別税率機能 | 必須 | —（展開ラジオ） | 店舗基本情報の現行値 | フォーム上はエンティティにマップしない。上部「登録」経由のPOSTでのみ `dtb_base_info.option_product_tax_rule` が更新される。下部「登録」だけでは更新しない。選択肢「有効」は1、「無効」は0として保存される型分岐がある。不正な選択値は子フォーム検証で却下され店舗基本情報は変わらない。 |
| 消費税率 | 必須 | 整数 0〜100（フォーム検証・`int_len` 桁上限は `constant.yml.dist` を確認値とする） | 編集対象行のDB現行値／新規ならスキーマ既定に準ずる | `dtb_tax_rule.tax_rate`。0 以上 100 以下・数値書式パターンの併用。 |
| 課税規則 | 必須 | —（マスタ選択） | 編集対象行のDB現行値／新規ならマスタID1 | `dtb_tax_rule.rounding_type_id`（現行`calc_rule`）。移行先は丸め種別マスタ `mtb_rounding_type` を参照。 |
| 適用日時 | 条件付き必須 | 日時入力（単一行テキストとピッカー） | 編集対象行のDB現行値 | `dtb_tax_rule.apply_date`。基本税率行では項目自体が無い。それ以外では必須。 |
| 税端数調整 | — | — | 新規組み立て時のみ実装上 0 をセット | `dtb_tax_rule.tax_adjust`。当画面フォームには無い。 |
| 作成日時・更新日時 | — | — | 新規は保存直前に現在時刻、更新は更新側のみ自動 | `dtb_tax_rule.create_date`／`update_date`。共通サブスクライバにより設定。 |
| 作成者 | — | — | 新規かつ管理画面管理者トークンがあるときログインメンバー | `dtb_tax_rule.creator_id`。 |

### エッジケース

| ケース | 扱い |
|--------|------|
| 基本税率行の削除を試みる | リクエストは受理されるが論理削除処理は呼ばれず、リダイレクトのみ。 |
| 同一適用日時の別行が既に存在する（基本税率以外の編集・新規） | フォームエラー文言「既に同じ適用日時で登録されています。」を付与し保存しない。 |

| 論理削除済みIDへの削除要求 | 対象無し扱いで警告メッセージに差し替え。 |

## データ整合性

| 観点 | 内容 |
|------|------|
| 一覧と編集フォーム | 一覧は共通税率の全件を論理削除で除外せず返すため、一覧に残った論理削除行を編集画面へ入れることは技術的に可能である。 |
| 商品別税率機能とフォームの上下ボタン | 画面上は同一フォームだが、店舗基本情報への反映は上部ボタン経路のみ。下部ボタン経路では値を読み取って保存しない。 |
| 課税計算側との整合 | 税率設定保存時にリポジトリのメモリキャッシュを自動クリアする処理は当コントローラには無い。別機能が参照する税率はキャッシュ・クエリ条件の実装次第である。 |

## セキュリティ観点メモ

POSTおよび論理削除ではCSRFトークンを伴う。削除はブラウザ側でDELETEメソッドに変換される実装パターンを前提とするアンカー属性がある。

## 排他制御・トランザクション

| 観点 | 内容 |
|------|------|
| トランザクション境界 | 共通税率保存・論理削除・商品別税率機能保存は各リクエスト内の永続化処理と`flush`単位で確定する。画面表示だけのGETではDB更新しない。 |
| ロック | 税率行、店舗基本情報に対する行ロック・悲観ロック・楽観ロック・ロックファイルは使用しない。同一税率行や商品別税率機能を同時更新した場合は後から確定した内容が残る。 |
| 例外時 | 検証エラーでは保存しない。flush前の例外では未確定、flush後の例外では確定済みの税率・店舗基本情報更新は戻らない。 |
