# デッキ管理 — デッキタグ一覧（カスタム管理画面）

## 概要

HareruyaEc プラグインが管理画面に提供する「デッキ管理」の下にある、デッキタグマスタ（実装上はテーブル `mtb_deck_tag`）を一覧し、並び順の切り替え・ページ単位の表示・モーダルからの新規登録・更新・一覧上からの削除を行う機能である。一覧は Doctrine で全件読み込みしたうえで、Twig 側でページ番号により行を間引いて表示する。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。本機能のカスタマイズ区分は現行踏襲であり、挙動は現行リポ pf-eccube3 に配置された HareruyaEc プラグイン実装を確認値とし、DB関連は ec-cube-enterprise を正とする。コア単体では当ルートは存在しない。

対象はブラウザ経由の管理画面に限定する。側メニュー項目の名前は「デッキタグ一覧」だが、メニューが参照しているルート bind と、本書が主題とする `deckTag.twig` を返すエンドポイントはソース上ずれがある（後述および「本書で扱わないこと」参照）。

コントローラの公開メソッド名は本文の主題としない。本文ではルートbind名やSymfonyのルートnameの網羅は主説明としない。「利用者視点の入口」にHTTPメソッドとサイトルートからのパスパターンを書く。コード探索でbind名が必要なときだけ「調査補助」へ書く。

## リニューアル移行時の扱い

デッキタグマスタは移行先（ec-cube-enterprise）でもコア標準のエンティティとして取り込まれている。DB関連の記述は移行先を正とする。並び順キーの列名が現行と移行先で異なる。

| 観点 | 現行（pf-eccube3） | 移行先（ec-cube-enterprise） |
|------|---------------------|-------------------------------|
| テーブル名 | `mtb_deck_tag` | 同名 `mtb_deck_tag` |
| 並び順列 | `rank`（表示順） | `sort_no`（表示順）。並び順キーの列名が現行 `rank` から移行先 `sort_no` へ変わる |
| 日本語名・英語名 | `name_jp`・`name_en`（各最大 32 文字） | 同名・同桁。`name_jp`・`name_en`（各最大 32 文字） |
| 主キー | `id` | 同じく `id` |
| デッキ／アーキタイプとの中間表 | デッキ用・アーキタイプ用の多対多中間表 | `dtb_deck_deck_tag`（`deck_id`・`deck_tag_id`）、`dtb_archetype_deck_tag`（`archetype_id`・`deck_tag_id`） |

一覧の並び替えキー値・ページ間引き・モーダル編集・削除可否判定などの挙動面は現行 pf-eccube3 実装を正とする。リクエスト引数 `sortKey` の値（`default`・`nameJp`・`nameEn`・`rank`）自体は画面上の論理キーであり、移行先では並び替えに用いる DB 列が `sort_no` になる。

## 処理フロー

### 一覧を表示する（GET `admin_decktag_list_disabled` または `admin_decktag_sort`）

1. 管理画面の認証・共通制約を通過する。
2. フォーム名 `admin_deck_tag` のビルダを生成し、そのビューをテンプレートに渡す（一覧表示時は未入力の新規状態に近いが、一覧描画のみで入力値検証はしない）。
3. リクエストまたはルート既定に従い `pageCount`・`pageNo`・`sortKey` を確定する。
4. `sortKey` がリポジトリの対応表に無い場合は並び順句を追加しない実装となる。既定キーでは `default` と `rank` が同じ列並び昇順となるマッピングが定義されている。
5. `mtb_deck_tag` 向けクエリビルダで昇順のみの `ORDER BY` を適用した結果をすべて取得してテンプレートへ渡す。セッション保存はしない。

### モーダル送信で新規登録または更新する（POST `admin_decktag_update`）

1. 管理画面の認証・共通制約を通過する。
2. 送信ボディについて、フォーム名に紐づく CSRF 検証が先に実行され、異常時は共通の拒否処理となる。
3. フォームのバリデータが問題なければ、`id` 有無で既存検索または新規エンティティを準備する。識別子は存在するが行が無いときは HTTP 404 とする。
4. フォーム配列データを共通トレイトの配列セットでエンティティへ反映する。関連コレクション名は対象から除外しているので多対多は更新しない。
5. Doctrine の永続・フラッシュの後、更新成功フラッシュ（管理共通メッセージ鍵を使用）を積み、`admin_decktag_sort` へ送信元と同一のページ変数へリダイレクトする。
6. バリデータが問題ある場合は一覧と同構成の Twig を再レンダして返し、画面上は JS がバリダーメッセージ検知によりモーダルを再び開く構成になる。

### 削除する（DELETE `admin_decktag_delete`）

1. 管理画面の認証・共通制約を通過する。
2. アンカー用 CSRF が無効なら共通の CSRF 失敗となる。
3. 対象行が無い場合は HTTP 404 となる。
4. 関連するデッキの個数が 0 でないとき、プラグインメッセージ（デッキ利用中）はエラーフラッシュのみし、`admin_decktag_list` の URL でリダイレクトする（パス実体は側メニューと同様のマスタデータ向け）。
5. アーキタイプ初期値側の関連が 0 でないときも同様にエラーフラッシュのみし、同じ `admin_decktag_list` でリダイレクトする。
6. 上記両方とも 0 のときのみエンティティを remove したうえで flush し、削除成功フラッシュを積み、同様に `admin_decktag_list` でリダイレクトする。

## 集計条件

| 指標 | 集計の要点 |
|------|-------------|
| 一覧の総件数 | リポジトリが返す結果配列長と一致する。追加のクエリ集約カウントはしない。 |
| 表示行 |  Twig のループ位置が `(pageNo-1)*pageCount` より後かつ `pageNo*pageCount` までの半開区間にある行のみ表に載る。この間引きはクライアントが受け取る HTML が既に絞られたものになる。 |

## 一覧取得時の並び順

| sortKey の値として解釈されるもの | ORDER BY に使う論理項目 | 昇降 |
|------------------------------|---------------------------|------|
| `default`（初期） | 表示順列 `sort_no`（現行 `rank`） | ASC |
| `nameJp` | 日本語名列 `name_jp` | ASC |
| `nameEn` | 英語名列 `name_en` | ASC |
| `rank` | 表示順列 `sort_no`（現行 `rank`） | ASC |

上記辞書に無い値が経路により渡される場合でも、並び順句自体は追加されない実装となる。ルート assert は英字のみのため、通常運用経路での未定義入力は限定される。

## 業務ルール・計算

本機能に税額・価格のような関数計算はない。並び順の重複だけが業務規則に近い制約となる。

### 入力項目（モーダル）

プラグイン定数 `deck_tag.length.name` は 32。`deck_tag.max.rank` は 999999。Twig とメッセージは翻訳リソース環境により文言が異なりうる。

| 項目名 | 必須／任意 | 最大長 | 初期値 | 保存先・扱い |
|--------|------------|--------|--------|----------------|
| 日本語名 | 必須 | 入力 32 文字（Symfony Length と HTML maxlength、設定ファイルの名前長定数による） | 編集開始時は行の現在値または空 | `mtb_deck_tag.name_jp`。空白不可。フォーム種別は一行テキスト。 |
| 英語名 | 必須 | 同上 | 同上 | `mtb_deck_tag.name_en`。同上。 |
| 表示順 | 必須 | 整数。上限 999999（LessThanOrEqual と HTML max）、下限 1 より大きい（Symfony GreaterThan と HTML min）の両方により 1〜999999 | 編集開始時は行の現在順位。新規時は画面上「現リストの順位最大 +1」（データが無いとき基準順位からの加算となる Twig 側の単純規則） | `mtb_deck_tag.sort_no`（現行 `rank`）。既存または新規とも、自分以外で同一順位があるとカスタム制約によりエラーとなる。別メッセージキーにより「表示順が他と重複」旨を文言化。 |
| 識別子（非画面） | 任意 | hidden | 新規では空または未設定相当 | DB 自動採番主キー。更新時のみ既存検索キーとなる。送信時のみ意味を持ち、一覧表示のみの GET には含まれない。 |

### エッジケース

| ケース | 扱い |
|--------|------|
| 表示順が他行と競合 | フォーム送信は成功せず一覧再描画。モーダル再表示により翻訳メッセージを見せる構成。 |
| 削除対象デッキタグがデッキに利用中 | 削除はしない。プラグインメッセージ（デッキ利用中）はエラー表示し、`admin_decktag_list` へリダイレクト。 |
| アーキタイプ初期値側にのみ残っている | 同上、アーキタイプ向け文言でエラー。 |
| 更新で存在しない ID | 一覧とは別経路として HTTP 404。 |
| GET の sortKey が辞書外 | ORDER BY が付かない可能性があるため、並び順は不定に近くなる経路がある（通常はルート制約により英字のみ）。 |

## データ整合性

| 観点 | 内容 |
|------|------|
| 一覧と送信後の並び・ページ | 一覧は送信直前にも全件クエリであり、フラッシュのみ跨いでも DB 状態は送信完了後値で次回 GET に反映される。更新後リダイレクト URL は入力と同じ `pageNo` と `pageCount` を維持する。よって並び順変更により当該ページが空白になる経路がある。 |
| マスタデータ画面との二重運用 | 同一テーブルへ別経路でも書けるが、両画面間のロックや整合前提はソース上ここには書かれていない。この設計書は一方の経路のみを細述する。 |
| 側メニューからの削除後ゴール画面 | DELETE 処理は `deckTag.twig` と異なる Twig となるリダイレクトパスでもよいソースになっているため、画面上のコンテキストは一覧独自画面と異なる状態へ切り替わりうる。 |

## 画面遷移

| 条件 | 遷移先 |
|------|--------|

## 調査補助（ソース位置の索引）

読者がソースを検索するときの手掛かりとして、プラグインディレクトリ配下における確認しやすい相対経路のみ列挙する。

- HareruyaEc / 管理側ルート定義：`app/Plugin/HareruyaEc/ServiceProvider/Admin/DeckServiceProvider.php`、`HareruyaMasterdataServiceProvider.php`
- HareruyaEc / 一覧・送信・削除：`app/Plugin/HareruyaEc/Controller/Admin/DeckTagController.php`
- HareruyaEc / Twig と JS：`app/Plugin/HareruyaEc/Resource/template/admin/DeckTag/deckTag.twig`、`.../assets/js/deck-tag.js`
- HareruyaEc / 並び一覧と順位検査：`app/Plugin/HareruyaEc/Repository/MtbDeckTagRepository.php`
- HareruyaEc / フォーム：`app/Plugin/HareruyaEc/Form/Type/Admin/DeckTag/` 一式
- HareruyaEc / 設定定数：`app/Plugin/HareruyaEc/config.yml` の `const.deck_tag`
- HareruyaEc / 側メニュー：`app/Plugin/HareruyaEc/ServiceProvider/Admin/SidebarProvider.php`


### HTTPルート名とパス（コード探索用・旧入口節より退避）

- `admin_decktag_list_disabled` … `GET` … `/{admin_route}/deckTag`（一覧の初期表示。コントローラの既定引数により `pageCount=100`、`pageNo=1`、`sortKey=default` と同値の状態でテンプレートを描画する。）
- `admin_decktag_sort` … `GET` … `/{admin_route}/deckTag/{pageCount}/{pageNo}/{sortKey}`（`pageCount`・`pageNo` はともに 1 以上の整数（ルートの assert）、`sortKey` は英字のみ（ルートの assert）。一覧のページ送り、表示件数変更、並び順変更後の表示。）
- `admin_decktag_update` … `POST` … `/{admin_route}/deckTag/{pageCount}/{pageNo}/{sortKey}`（モーダル内フォームによる新規作成または更新の送信先。同上のパス変数パターンを満たす必要がある。）
- `admin_decktag_delete` … `DELETE` … `/{admin_route}/deckTag/{id}`（`{id}` は 1 以上の整数（assert）。一覧の削除ボタンから、CSRF 付きのアンカー経由で送る想定ルートである。）
