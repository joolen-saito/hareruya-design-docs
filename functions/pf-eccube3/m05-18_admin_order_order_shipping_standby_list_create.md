# 受注管理 — 出荷指示リスト作成

## 概要

管理画面「受注管理」配下の「出荷指示」画面から、注文番号レンジと受注日時レンジで条件を付け、条件に合う受注を抽出し、区分（通常・予約・大量）ごとに出荷指示リストを新規登録する。登録と同時に、対象受注へ出荷指示日時を記録し、対応状況を「出荷指示」（マスタID 9）へ一括更新する。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。確認対象はec-cube-enterpriseの現行実装とする。

対象はブラウザ経由の管理画面に限定する。出荷指示一覧の検索表示・ページング、リストの編集・削除・CSV・印刷・送り状出力、受注一覧・受注編集の個別操作の詳細は別範囲とする。

コントローラのメソッド名単位の解剖は本文の主題としない。本文ではルートbind名やSymfonyのルートnameの網羅は主説明としない。「利用者視点の入口」にHTTPメソッドとサイトルートからのパスパターンを書く。コード探索でbind名が必要なときだけ「調査補助」へ書く。

本機能のカスタマイズ区分は現行踏襲であり、出荷指示機能は現行リポ（pf-eccube3 の HareruyaEc プラグイン）と移行先（ec-cube-enterprise コア）の双方に同名で実装される。挙動は現行リポの実装を踏襲し、DB（永続化先のテーブル・列）は ec-cube-enterprise の実装を正とする。

## リニューアル移行時の扱い

出荷指示機能は、現行は pf-eccube3 の HareruyaEc プラグイン（`app/Plugin/HareruyaEc`）に、移行先は ec-cube-enterprise コア（`src/Eccube`）に同名で実装される。永続化先の出荷指示リスト（`dtb_shipping_standby`）・出荷指示と受注の中間表（`dtb_order_shipping_standby`）・受注（`dtb_order`）・受注タイプマスタ（`mtb_order_type`）は、両者で同一スキーマである。`dtb_shipping_standby` の列構成（`id`・`member_id`・`order_type_id`・`create_date`・`update_date`・`comment`）と中間表の列（`standby_id`・`order_id`）は ec-cube-enterprise の定義を正とする。対応状況「出荷指示」（ID 9）への更新先 `dtb_order.order_status_id`、出荷指示日の `dtb_order.commit_date` も両者同一である。現行と移行先で差異が判明した場合は、DB記述は ec-cube-enterprise 実装を正とする。

## 処理フロー

### 出荷指示リストを作成する（POST `admin_order_generate_standby_list`）

1. 管理画面の認証・共通制約を通過する。
2. 生成専用フォーム種別をリクエストにバインドする。ブロックプレフィックスは`admin_generate_shipping_standby`。
3. 未送信または検証失敗の場合、管理向けエラーフラッシュ（キー`admin.common.save_error`）を積み、`admin_shipping_standby`へリダイレクトする。
4. 検証成功時、フォーム配列を条件として、出荷指示リスト除外が偽の配送方法エンティティ一覧を取得し、受注リポジトリの待機対象抽出に渡す。
5. 戻りが空配列なら、`admin.common.save_error`を積み同ルートへリダイレクトする（永続化処理は呼ばない）。
6. 空でない場合、区分別の受注配列と操作者の管理者アカウントを引数に、リスト生成用アクションを呼ぶ。
7. アクションはトランザクション開始後、区分IDごとに次を繰り返す。
   - `mtb_order_type`を区分IDで取得する。行がなければ引数例外を投げる。
   - 出荷指示リスト行を新規作成し、当該区分の受注コレクション・操作者の会員ID・区分参照を設定して永続化する（ORMの`persist`と`flush`）。
   - 続けて受注リポジトリの一括更新を呼び、当該受注すべての対応状況を「出荷指示」（ID 9）にし、`commit_date`を処理実行時刻（日時を`Y-m-d H:i:s`形式の文字列としてバルク更新）にする。
8. 全区分処理後にコミットする。途中で例外が出ればロールバックし例外を再送出する。
9. コントローラは引数例外だけを捕捉し、そのメッセージをフラッシュに載せ`admin_shipping_standby`へリダイレクトする。
10. 成功時は成功フラッシュ（`admin.common.save_complete`）を積み`admin_shipping_standby`へリダイレクトする。

## 集計条件

| 指標 | 集計の要点 |
|------|------------|
| 抽出対象受注 | 受注エンティティを起点に、対応状況が「購入処理中」（ID 8）および「注文取消し」（ID 3）以外であること。いずれかの配送が、配送方法の`is_shipping_standby_list_exclusion`が偽であるものに紐づくこと。`commit_date`がNULLであること。オプションで`order_no`の上下限（フォームの注文番号始端・終端に対応）および`order_date`の始端（以上）・終端（未満）を付与する |

## 区分振り分けの判定順序

抽出後の各受注は、次の順でちょうど一つの区分キー（`mtb_order_type`のID）に入る。

| 順序 | 判定 | 結果 |
|------|------|------|
| 1 | 受注明細コレクションの先頭行の商品名に、マスタ定数で定義された文字列 `予約` が部分一致する | 区分キーは予約（ID 2） |
| 2 | 上記以外で、受注明細件数（受注の明細件数カウント）が 150 以上 | 区分キーは大量（ID 3） |
| 3 | 上記以外 | 区分キーは通常（ID 1） |

画面上の区分表示名は`mtb_order_type.name`のデータに依存する。

## 業務ルール・計算

| 項目 | 内容 |
|------|------|
| 作成されるリスト行数 | 抽出結果に受注が現れる区分ごとに1行。3区分すべてに受注があれば、同一トランザクションで3行作成される |
| 対象外の配送 | 配送方法の「出荷指示リストから除外」が真のものだけを使う配送は、結合条件から外れる |
| 受注の更新 | 各リスト行の`flush`の直後に、その行に紐づく受注へ対応状況と出荷指示日を一括適用する。区分ループのたびに呼ばれる |

### 入力項目

| 項目名 | 必須／任意 | 最大長 | 初期値 | 保存先・扱い |
|--------|------------|--------|--------|----------------|
| 注文番号 | 任意 | 整数種別。PHPが扱える整数範囲。参照列`dtb_order.order_no`は最大255文字の文字列で、条件では数値パラメータとの比較演算が用いられる | 空欄 | キー`order_id_from`。入力時のみ`order_no >= パラメータ` |
| ～ | 任意 | 同上 | 空欄 | キー`order_id_to`。ラベルはフォーム定義上「～」。入力時のみ`order_no <= パラメータ` |
| 注文日時 | 任意 | 単一行日時（`DateTimeType`、`input`はdatetime、`widget`は`single_text`） | 空欄 | キー`order_date_from`。入力時のみ`order_date`が`Y-m-d H:i:s`に整形した値以上 |
| ～ | 任意 | 同上 | 空欄 | キー`order_date_to`。ラベルはフォーム定義上「～」。入力時のみ`order_date`が同形式の値未満（終端は未満比較） |

### エッジケース

| ケース | 扱い |
|--------|------|
| 全条件未入力 | 配送・対応状況・出荷指示日・除外フラグの条件のみで抽出する（集合は広くなりうる） |
| 区分ごとの受注0件 | 当該区分キーは結果連想配列にキーが現れず、当該区分のリスト行は作られない |
| 全区分で0件 | コントローラが配列空と判断し、永続化前にエラーフラッシュで終了する |
| 受注明細が0件の受注 | 区分判定で先頭明細参照があり、実装上エラーになりうる |
| `mtb_order_type`に期待IDがない | 引数例外となり、コントローラがその文言をフラッシュして一覧へ戻す |
| 配送に結合する複数行 | SQL上は受注が重複行になりうる。ORMの結果配列に同一受注が複数回含まれると、永続化処理へ重複が渡りうる |

## DBカラム

| テーブル | 列 | メモ |
|---------|-----|------|
| `dtb_shipping_standby` | `id` | 連番。画面では出荷指示番号として扱われる |
| `dtb_shipping_standby` | `member_id` | 作成時の操作者（`dtb_member`）のID |

| `dtb_shipping_standby` | `create_date`, `update_date` | 作成処理の当該アクションではエンティティ上セットしない（NULLのままとなりうる。テスト固めでは別経路で明示セットあり） |
| `dtb_order_shipping_standby` | `standby_id`, `order_id` | 中間テーブル |
| `dtb_order` | `order_status_id` | 出荷指示（9）へ更新 |
| `dtb_order` | `commit_date` | 処理日時を一括設定 |

### DB操作

永続化の正は ec-cube-enterprise（テーブル名・操作は ec-cube-enterprise を正典）。当ドメインは承認ワークフローを介さず persist/flush で直接確定する（承認ワークフローは在庫機能固有）。

| 操作種別 | 対象テーブル | 契機・条件 |
|---------|--------------|------------|
| 登録/更新 | dtb_member / dtb_order / dtb_order_shipping_standby / dtb_shipping_standby / mtb_order_type | 当機能が行う登録・更新で対象テーブルを直接保存する（不要な削除は含まない）。確定は persist/flush による即時反映。DB=ec-cube-enterprise を正典とする。 |
