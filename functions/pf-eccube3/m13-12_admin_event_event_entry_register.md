# イベント管理 — イベント新規申込登録

## 概要

イベント管理において、管理者がイベント日程を指定し、参加プレイヤー・支払金額を入力して新規のイベント申込を1件登録する機能である。申込状況・支払方法は管理側申込として固定値で登録する。詳細・編集と同一テンプレートを用いるが、本書は新規登録の表示（`GET …/entry/{eventDetailId}/new`）と登録送信（`POST …/entry/{eventDetailId}/create`）に範囲を限定する。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。確認値はpf-eccube3（EC-CUBE3系）のHareruyaEcプラグインのイベント申込新規登録処理、申込詳細フォーム、申込・申込プレイヤー・申込履歴の永続化を正とする。本機能のカスタマイズ区分はカスタマイズであり、挙動の確認はpf-eccube3を参照し、永続化先のテーブル・列名などDB関連の記述はec-cube-enterpriseを正とする。

対象はブラウザ経由の管理画面に限定する。

本文ではフレームワークのコントローラ型名やメソッド名を主説明としない。管理画面プレフィックスは環境により変わり、プラグイン設定の`admin_route`で決まる。「利用者視点の入口」にHTTPメソッドとサイトルートからのパスパターンを書く。

---

## 本書で扱うこと

- イベント日程を指定した新規申込の入力画面表示
- 参加プレイヤー・支払金額の入力と申込の新規登録
- 管理側申込としての申込状況・支払方法の固定設定
- 支払会員の自動決定、申込履歴の記録
- 登録先イベント日程の選択導線

---

## 本書で扱わないこと

以下は本書では仕様確定せず、実装または別機能の設計を正とする。

- 既存申込の詳細・編集（M13-10を正とする）
- イベント申込一覧・検索（イベント申込一覧機能を正とする）
- CSV出力・一括登録（M13-09・M13-13を正とする）
- イベント・日程そのものの登録（イベント新規登録・日程登録を正とする）
- プレイヤー・会員マスタの編集

## 処理フロー

### 新規申込フォームを表示する（`GET …/entry/{eventDetailId}/new`）

1. 会員のソフトデリートを除外対象にし、プレイヤーのソフトデリートを無効化して読み込む。
2. 新規の申込を用意し、指定イベント詳細を紐づける。日程が無ければ404とする。
3. チーム人数の行数で参加者行を空で用意し、空のプレイヤー情報リスト（JSON）をフォームへ設定する。
4. 支払金額にイベントの参加費、申込状況に参加（固定）、支払方法に管理者（固定）を初期設定する。
5. 席順アルファベット一覧が参加者数より少ない場合は404とする。
6. 詳細テンプレートを返す。

### 新規申込を登録する（`POST …/entry/{eventDetailId}/create`）

1. 申込詳細フォームを送信として処理する。未送信のときは登録失敗を表示し、新規画面へリダイレクトする。
2. 検証NGのとき、支払金額が不正なら金額メッセージ、それ以外は申込重複メッセージを表示し、新規画面へリダイレクトする。
3. 検証OKのとき、新規申込を作り、フォーム値を反映する（申込状況・支払方法・支払会員などは除外したうえで個別設定する）。
4. 申込にイベント詳細を紐づけ、支払会員に参加者1行目の会員を設定する。申込状況は参加（固定）、支払方法は管理者（固定）を設定する。
5. 申込IDを確定するため先に申込を登録する。
6. 申込履歴を1件記録する。
7. プレイヤー情報リストの各要素を申込プレイヤーとして登録する（プレイヤーID・確認フラグ・席順）。
8. 成功を表示し、登録した申込の編集画面へリダイレクトする。

## 業務ルール・計算

| 項目 | 内容 |
|------|------|
| 申込状況 | 新規登録時は参加（固定値）で登録する。画面のセレクトは無効化表示。 |
| 支払方法 | 新規登録時は管理者（固定値）で登録する。 |
| 支払金額 | 初期値はイベントの参加費。半角数字のみ。 |
| 支払会員 | 参加者1行目のプレイヤーの会員を採用する。 |
| 参加プレイヤー | 隠しフィールドのプレイヤー情報リスト（JSON、要素はプレイヤーID・確認フラグ・席順）で管理し、登録時に申込プレイヤーへ展開する。 |
| 申込履歴 | 登録成功時に申込履歴を1件記録する。 |

### 入力項目

| 項目名 | 必須／任意 | 最大長 | 初期値 | 保存先・扱い |
|--------|------------|--------|--------|----------------|
| 申込状況 | 必須（新規はフォーム無効化、固定登録） | 選択（申込状況マスタの単一選択） | 参加（固定） | `dtb_event_entry.entry_status_id`。フォームキー`entryStatus`。登録時に参加で固定設定する。 |
| 支払方法 | 必須（フォーム無効化、固定登録） | 選択（クレジット・コンビニ・管理者の単一選択） | 管理者（固定） | `dtb_event_entry.payment_id`。フォームキー`payment`。登録時に管理者で固定設定する。 |
| 支払金額 | 必須 | 半角数字のみ（通貨JPY・小数なし） | イベントの参加費 | `dtb_event_entry.price`。フォームキー`price`。半角数字以外は検証エラー。 |
| 参加プレイヤー情報 | 必須 | JSON文字列（プレイヤーID・確認フラグ・席順の配列） | 空（参加者行は空で用意） | `dtb_entry_player`の`player_id`・`confirm_flg`・`seat_order`へ展開。フォームキー`entryPlayerList`。重複検証あり。1行目の会員を支払会員にする。 |
| プレイヤー検索語 | 任意 | テキスト（検索用、保存しない） | 空 | フォームキー`search`。モーダル検索の入力。永続化しない。 |

イベント名・店舗・会場・フォーマット・支払会員は表示専用であり、入力項目ではない。最大長の数値は申込詳細フォームの実装確認値とする。

## データ整合性

| 観点 | 内容 |
|------|------|
| 申込と申込プレイヤー | 申込IDを得るため申込を先に登録し、続けて申込プレイヤーを登録する。両者は同一リクエストで反映する。 |
| 支払会員 | 参加者1行目の会員を採用する。1行目のプレイヤー・会員が解決できることを前提とする。 |
| 申込状況・支払方法 | 画面入力に依らず固定値で登録する。 |

## DBカラム

機能に直接関係する列のみ記載する。型や一覧の細部はスキーマを参照する。

| テーブル | 列 | メモ |
|---------|-----|------|
| `dtb_event_entry` | `event_detail_id` | 指定イベント日程を紐づける。 |
| `dtb_event_entry` | `entry_status_id` | 参加（固定）で登録。 |

| `dtb_entry_player` | `event_entry_id`、`player_id`、`confirm_flg`、`seat_order` | 参加者を新規登録。 |
| `dtb_entry_history`（申込履歴） | 申込ID・登録内容 | 登録成功時に1件追加。 |

### DB操作

永続化の正は ec-cube-enterprise（テーブル名・操作は ec-cube-enterprise を正典）。当ドメインは承認ワークフローを介さず persist/flush で直接確定する（承認ワークフローは在庫機能固有）。

| 操作種別 | 対象テーブル | 契機・条件 |
|---------|--------------|------------|
| 登録/更新 | dtb_entry_history / dtb_entry_player / dtb_event_entry | 当機能が行う登録・更新で対象テーブルを直接保存する（不要な削除は含まない）。確定は persist/flush による即時反映。DB=ec-cube-enterprise を正典とする。 |
