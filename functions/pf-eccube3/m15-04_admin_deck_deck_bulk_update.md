# デッキ管理 — 検索一覧からの一括編集

## 概要

HareruyaEc プラグインの管理画面「デッキ管理」において、検索結果一覧でチェックした複数デッキに対し、チェックボックスで選択した項目だけを共通値でまとめて更新する機能である。一覧・検索・詳細編集・CSV 入出力とは別ルートで POST され、`change_flgs[項目名]` でサーバに「どの列を上書きするか」が伝わる。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。カスタマイズ区分は「カスタマイズ」。画面・挙動は pf-eccube3 に配置された HareruyaEc プラグインのソースを確認値とし、DB関連（テーブル・列・型・制約・関連）は ec-cube-enterprise の実装を正とする。

対象はブラウザ経由の管理画面に限定する。

コントローラのメソッド単位の解剖は本文の主題としない。本文ではルートbind名やSymfonyのルートnameの網羅は主説明としない。「利用者視点の入口」にHTTPメソッドとサイトルートからのパスパターンを書く。コード探索でbind名が必要なときだけ「調査補助」へ書く。

---

## リニューアル移行時の扱い

- 画面・挙動は現行（pf-eccube3 の HareruyaEc プラグイン）の確認値、DBスキーマは移行先（ec-cube-enterprise）を正とする。
- 一括編集の対象データはデッキ（`dtb_deck`）および関連するデッキカード（`dtb_deck_card`）である。これらは移行先 ec-cube-enterprise にも存在する。`change_flgs[項目名]` で指定された列のみを共通値で更新する点は実装挙動であり、移行先での列名・型は ec-cube-enterprise の `DtbDeck`／`DtbDeckCard` を正とする。
- デッキ管理一括編集の管理画面（コントローラ）が ec-cube-enterprise に移植済みかは未確認のため、移植有無と差分は ec-cube-enterprise 実装で要確認とする。現行と移行先でデッキ系テーブルのスキーマ差が判明した場合は本節とDB節を更新する。

## 利用者視点の入口

| 入口 | URLエンドポイント | 期待されるふるまい |
|------|--------------------|---------------------|
| ナビなどからデッキ一覧の初期画面を開く（検索結果ゼロ） | `GET /{admin_route}/deck` | 一括編集フォームは検索結果ボックス内にあり、結果が無いときはパネルごと描画されないため、この入口からは一括編集を実行できない。 |
| 検索を実行し結果が 1 件以上ある | `POST /{admin_route}/deck/search/{page_no}`（検索フォーム） | 一覧・チェックボックス・一括編集パネルが表示される。 |
| 「一括編集」ボタンでパネルを開き、項目チェック・入力後「一括編集実行」 | `POST /{admin_route}/deck/bulk_update` | CSRF とフォーム検証を通過すれば選択デッキが更新され、成功フラッシュが積まれたうえで直前一覧へ戻る。 |

一覧まわりのフォームは `bulk_update_form` の `action` が `m15-04_admin_deck_deck_bulk_update` に固定されている。CSV 出力・一括削除は同一フォーム内の別ボタンで `formaction` が差し替わる（本書の範囲外）。

## フロント挙動

| 観点 | 内容 |
|------|------|
| 表示要素 | 検索結果が 1 件以上のときのみ、一覧ヘッダ付近に CSV 出力・旧サイト向け出力・一括削除・「一括編集」アコーディオン・ページ件数・ソートがある。テーブル左端は `deckId[]` のチェックボックス、表頭 `#allCheck` で `[deckId]` 属性を持つ行チェックを一括オンオフする。一括編集パネル内は項目ごとに「変更フラグ用チェック」と入力ウィジェットを組み合わせる。初期状態では入力ブロックは `display: none`。 |
| JS 挙動（一覧共通） | Select2 を検索条件のフォーマット・アーキタイプ・タグ、および一括編集のアーキタイプ・フォーマット・デッキタグに適用する。検索側のアーキタイプはフォーマット・カラー選択で選択肢がフィルタされる。 |
| JS 挙動（一括編集） | 変更フラグのチェックで対応する `#bulk_update_form_*` を表示切替し、チェック時に子要素の `.required` に HTML5 `required` を付与する（チェックオフで除去）。ページ読込時は一括編集の入力から `required` を剥がし、変更フラグはすべてオフにする。イベント開催日は moment 日本語ロケール付き datetimepicker（`YYYY-MM-DD HH:mm`）。「一括編集実行」押下時、変更フラグが 1 つも無ければアラート「変更されている項目がありません。」で送信中止。チェック済みデッキが 0 件なら「一括編集するデッキをひとつ以上選択してください。」で中止。通過後、フォームの `submit` イベントに確認「一括編集の内容を送信しますか？」を紐付ける（送信のたびにハンドラが追加され、同一セッションで複数回実行すると確認が複数回積み上がり得る実装である）。 |
| CSS・レイアウト | 管理画面共通の Bootstrap 系。一括編集アコーディオンは `accordion` / `toggle` / `accpanel` 構造で、管理テンプレートの `function.js` によるスライド開閉が前提。 |
| モーダル・ポップアップ | 専用モーダルは使わない。確認は `alert` / `confirm` のみ。 |

## 処理フロー

### 一括編集を実行する（POST `m15-04_admin_deck_deck_bulk_update`）

1. 管理画面の認証・共通制約を通過する。
2. フォーム名 `m15-04_admin_deck_deck_bulk_update` でリクエストを処理し、CSRF を検証する。失敗時はアクセス拒否（HTTP 403）の扱いになる（共通ヘルパの実装に従う）。
3. フォーム検証に失敗した場合、エラーメッセージをフラッシュに積み、`Referer` ヘッダの URL へ HTTP リダイレクトする。
4. 検証成功時、フォーム項目名とエンティティ更新用セッター名の対応表に従い、各 `change_flgs[項目名]` が存在する項目だけについて、フォームの値をセッターに渡して各デッキ行を更新する。`change_flgs` に無い項目は既存値を保持する。
5. リクエストの `deckId` を配列として取得し、各要素が非空かつ半角数字のみであることを検査する。1 つでも不一致なら HTTP 404 で打ち切る。
6. デッキ ID 集合に対応する行をリポジトリから取得する（取得方法は「エッジケース」参照）。
7. 取得した各行について手順 4 の更新を適用し、最終更新者として操作者の管理者 ID を `member_id` に記録する。永続化コンテキストへ登録する。
8. まとめて flush する。
9. 成功メッセージキー `admin.register.complete` をフラッシュに積み、`Referer` へリダイレクトする。

### 一覧に一括編集フォームを載せる（表示時）

1. デッキ検索一覧用のコントローラが `bulkUpdateForm` として空の `m15-04_admin_deck_deck_bulk_update` フォームビューをテンプレートへ渡す（トークンのみ実体化し、入力は未送信状態）。

## 一括更新時の判定順序

| 順序 | 判定 | 結果 |
|------|------|------|
| 1 | CSRF トークン | 無効ならアクセス拒否。 |
| 2 | 送信フォームの検証（全項目。変更フラグは検証対象の絞り込みに使わない） | 失敗ならエラーフラッシュと Referer へリダイレクト。 |
| 3 | 各 `deckId` が半角数字のみか | 1 件でも不正なら HTTP 404。 |
| 4 | 各行について各列 | `change_flgs` にキーがある列だけ、フォーム値で上書きする。 |

## 業務ルール・計算

| 項目 | 内容 |
|------|------|
| 変更対象列 | `format`, `archetype`, `disp`, `privateFlg`, `eventNameJp`, `eventNameEn`, `eventDate`, `ranking`, `result`, `winCount`, `lossCount`, `drawCount`, `dciNo`, `playerName`, `deckTags`, `sourceUrl` のいずれかについて、対応する変更フラグが POST に含まれるときだけ、その列の現在のフォーム値を全対象デッキに適用する。 |
| フォーマット | 空の選択（プレースホルダ相当）で上書きすると、永続化層では外部参照なしとして解釈され得る（未選択時の解釈はフォーム送信値に従う）。 |
| アーキタイプ | エンティティの「アーキタイプと代表カード画像を同時設定」用の更新経路を使う。アーキタイプに代表カード画像が無い場合は画像参照の更新は行われない実装である。 |
| デッキタグ | 多値選択。変更フラグが付いた場合の値で既存のタグ紐付けが置き換わる（空選択は空コレクションとして解釈され得る）。 |
| 編集者 | 各対象デッキの `member_id` は操作した管理者アカウント ID に更新される。 |

本機能では売上・順位計算などの業務計算は行わない。

### 入力項目

| 項目名 | 必須／任意 | 最大長 | 初期値 | 保存先・扱い |
|--------|------------|--------|--------|----------------|
| フォーマット | 任意 | — | 未選択表示 | `dtb_deck` のフォーマット外部参照。変更フラグ `format` が付いたときのみ更新。変更フラグがオフのときは検証だけ受け、値の上書きは行わない。 |
| アーキタイプ | 任意 | — | 未選択表示 | `dtb_deck` のアーキタイプ外部参照と代表カード画像の更新。変更フラグ `archetype`。 |
| 公開状態 | 必須 | — | マスタの展開ラジオの先頭選択 | `dtb_deck` の表示マスタ参照。変更フラグ `disp`。フォーム定義上は常に必須。 |
| デッキリスト公開状態 | 必須 | — | 「公開」側 | `dtb_deck.private_flg`。真偽。変更フラグ `privateFlg`。 |
| イベント名（日） | 任意 | 50 文字（コア設定 `stext_len` の実値。環境で上書きされ得る） | 空 | `dtb_deck.event_name_jp`。変更フラグ `eventNameJp`。DB 列は 255 文字まで持つため、フォーム上限と DB 上限は一致しない。 |
| イベント名（英） | 任意 | 同上 | 空 | `dtb_deck.event_name_en`。変更フラグ `eventNameEn`。 |
| イベント開催日 | 任意 | — | 空 | `dtb_deck.event_date`。単一行テキスト＋datetimepicker。設定 `HareruyaEc.const.format.datetime` の形式。変更フラグ `eventDate`。 |
| 順位 | 任意 | 数値検証のみ（1 超 99999999 以下） | 空 | `dtb_deck.ranking`。変更フラグ `ranking`。空欄時の扱いは整数項目としての変換結果に従う。チェックを付けたうえで不整数は検証エラー。 |
| 成績 | 任意 | フォームに Length 制約なし | 空 | `dtb_deck.result`（スキーマ上 32 文字）。変更フラグ `result`。長大文字列は DB または永続化層の制限に依存する。 |
| 勝利数 | 任意 | 0 以上 99999999 以下 | 空 | `dtb_deck.win_count`。変更フラグ `winCount`。 |
| 敗北数 | 任意 | 同上 | 空 | `dtb_deck.loss_count`。変更フラグ `lossCount`。 |
| 引き分け数 | 任意 | 同上 | 空 | `dtb_deck.draw_count`。変更フラグ `drawCount`。 |
| DCIナンバー | 任意 | 50 文字かつ数字のみ（正規表現） | 空 | `dtb_deck.dci_no`（スキーマ上 16 文字）。変更フラグ `dciNo`。フォーム上限と DB 上限は一致しない。 |
| プレイヤー名 | 任意 | 50 文字 | 空 | `dtb_deck.player_name`（スキーマ上 64 文字）。変更フラグ `playerName`。 |
| タグ | 任意 | — | 未選択 | `dtb_deck` のデッキタグ多対多。変更フラグ `deckTags`。 |
| 引用元URL | 任意 | 50 文字 | 空 | `dtb_deck.source_url`（スキーマ上 2048 文字）。変更フラグ `sourceUrl`。一括編集フォームのみ 50 文字制約が掛かり、詳細画面と上限が異なる。 |

数値上限 99999999 は `HareruyaEc.const.deck.max.number` の確認値である。

### エッジケース

| ケース | 扱い |
|--------|------|
| POST された `deckId` の一部が DB に存在しない | 取得できたデッキ行だけを更新する。存在しない ID についてエラーにはしない。 |
| サーバ実装でのリポジトリ呼び出し | コントローラ側の取得メソッド呼び出し名と、リポジトリに定義された複数 ID 取得メソッド名が一致しないソースがあり得る。その場合は未定義メソッド呼び出しとなる（調査補助でファイルとメソッド名を照合すること）。 |
| 変更フラグを 1 つも付けずに送信 | クライアントの「一括編集実行」でブロックされる。サーバ側は変更フラグが無くても検証が通れば flush だけ行い、実質データ変化はセッターが呼ばれない。 |
| `deckId` を付けずに POST | クライアントではブロックされない経路があり得る。サーバでは `deckId` を `foreach` しており、PHP の版によっては致命的エラーまたは警告となり得る。 |
| Referer が無い | リダイレクト先が空や不正 URL になり得る。ブラウザとクライアント実装に依存する。 |

## データ整合性

| 観点 | 内容 |
|------|------|
| 一覧との一致 | 更新直後は Referer で戻った検索一覧の内容は、検索条件が同じでも再検索タイミング・他操作の有無に依存する。 |
| 詳細画面 | 一括編集はデッキ本文（カードリスト）や `latest_flg` 等を変更しない。詳細画面で見える項目の一部のみが対象。 |
| 同時更新 | 楽観ロックは用いない。後勝ちで上書きされる。 |

## DBカラム

当機能が直接書き換え得る主な列（型・制約の詳細は Doctrine マッピングを参照）。

| テーブル | 列 | メモ |
|---------|-----|------|

### DB操作

永続化の正は ec-cube-enterprise（テーブル名・操作は ec-cube-enterprise を正典）。当ドメインは承認ワークフローを介さず persist/flush で直接確定する（承認ワークフローは在庫機能固有）。

| 操作種別 | 対象テーブル | 契機・条件 |
|---------|--------------|------------|
| 登録/更新 | dtb_deck | 当機能が行う登録・更新で対象テーブルを直接保存する（不要な削除は含まない）。確定は persist/flush による即時反映。DB=ec-cube-enterprise を正典とする。 |

## ログ・監査

明示的な監査ログ出力は本処理内に限定しては定義されていない（管理画面共通のリクエストログの有無は基盤実装を正とする）。

### ログに出してはいけないもの

- パスワード
- なりすまし対策トークン
- Cookie 値
- セッション ID の完全値
- Remember Me トークンの原値

---

## セッション

検索条件・ページ番号はデッキ一覧のセッションキー `admin.deck.search` 系で保持されるが、一括編集処理本体はそれを書き換えない。フラッシュメッセージはセッションを用いる。

### セッションへ保存しない情報

フォームに入力された一括編集の各値を、処理成功後にセッションへ永続化する実装にはなっていない（次回表示は初期空フォーム）。

---

## Cookie

本機能単体で新たに Cookie を設定しない。管理画面セッション用 Cookie は環境依存（管理画面ログイン設計を正とする）。

---

## 排他制御・トランザクション

明示的なトランザクション境界や楽観ロック Version 列の更新は行わない。複数デッキに対する persist は 1 回の flush でまとめて送信される。
