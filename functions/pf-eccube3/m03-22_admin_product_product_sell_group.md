# 商品管理 — 購入グループ管理

## 概要

管理画面「商品管理」配下から到達できる、`mtb_sell_group`（購入グループ）および関連するmany-to-many（支払方法・配送方法）を維持する機能である。同一テンプレート上に入力フォーム（新規または編集中の一行）と、論理削除対象外の一覧表を並べ表示し、新規作成・更新・論理削除を行う。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。ソースは eccube-enterprise コア（Symfony の管理画面ルート・アプリケーション層およびテンプレート）を確認値とする。

本機能のカスタマイズ区分は現行踏襲である。挙動の参照は現行リポ pf-eccube3 の HareruyaEc プラグイン実装を正とし、DB関連は ec-cube-enterprise を正とする。現行と移行先のスキーマ差は「リニューアル移行時の扱い」へ集約する。

対象はブラウザ経由の管理画面に限定する。

本文ではSymfonyのコントローラ型やメソッド名を主題としない。本文ではルートbind名やSymfonyのルートnameの網羅は主説明としない。「利用者視点の入口」にHTTPメソッドとサイトルートからのパスパターンを書く。コード探索でbind名が必要なときだけ「調査補助」へ書く。

## リニューアル移行時の扱い

DB関連の正典は ec-cube-enterprise とする。挙動は現行リポ pf-eccube3 の HareruyaEc プラグインを正とし、移行先との差は本節へ集約する。

| 観点 | 現行（pf-eccube3） | 移行先（ec-cube-enterprise） |
|------|--------------------|------------------------------|
| 予約商品フラグ | `mtb_sell_group` に `reservation_flg` 列が無い。 | `mtb_sell_group.reservation_flg`（小整数、既定 0、符号なし）が加わる。本書の予約商品フラグは移行先の列を正とする。 |
| メモの桁 | `mtb_sell_group.memo` は文字列 1024 桁、null 許容。 | `memo` はテキスト型（`TEXT`、null 許容）で上限が拡大する。本書の入力項目はメモを移行先の列定義を正として記述する。 |
| 名称の NULL 許容 | `name`／`name_en` は null 許容（既定空文字）。 | `name`／`name_en` は非 NULL（255）。本書の必須扱いは移行先の制約と整合する。 |
| 中間表の参照列 | `dtb_sell_group_payment`／`dtb_sell_group_delivery` は支払・配送の主キー `payment_id`／`delivery_id` を参照する。 | 同中間表で支払・配送の主キー `id` を参照する（参照先マスタの主キー名が `id` へ変更）。中間表名・`sell_group_id` 列名は同じ。 |
| 論理削除 | `deleted_at` による論理削除。一覧は `deleted_at` が null の行のみ。 | 同左（`deleted_at` を現在時刻に更新する論理削除。物理削除ではない）。両者で同じ。 |
| 更新者・日時列 | `member_id`／`create_date`／`update_date`。 | 同一の列名。同一スキーマである。 |

`mtb_sell_group` の `id`／`name`／`name_en`／`memo`／`create_date`／`update_date`／`deleted_at`／`member_id`、中間表 `dtb_sell_group_payment`／`dtb_sell_group_delivery` の `sell_group_id` 列は現行と移行先で同名である（上表の差分を除く）。

## 処理フロー

### 一覧と新規フォームを表示する（GET `m03-22_admin_product_product_sell_group`）

1. 管理画面の認証状態を経てルートへ到達する。
2. 削除日時が null の購入グループを主キー昇順で読み込む。
3. 入力対象となる空の業務モデルへフォーム型をバインドし、画面へ渡す。編集フラグは偽で、編集中の対象参照は渡さない。
4. Twig で上部フォーム送信先は `create` ルートとなる。

### 新規作成する（POST `m03-22_admin_product_product_sell_group_create`）

1. 新規モデルへ同型フォームを生成し、`handleRequest` で束ねる。
2. SymfonyのフォームCSRFおよび各フィールド制約により妥当性評価を行う。
3. 妥当なら現在日時を作成・更新両日時へ入れ、ログイン管理者が運用アカウント種別として解釈される場合は、その参照を更新者へ記録して永続レイヤへ保存対象として登録し単一トランザクションへ flush する。成功フラッシュ鍵は `admin.common.save_complete`。一覧 GET へリダイレクトする。
4. 妥当でなければ一覧再取得およびエラー状態のフォーム表示で応答コード 200 とする。

### 編集表示する（GET `m03-22_admin_product_product_sell_group_edit`）

1. `{id}` に該当する永続モデルをパラメータ解決により取得できなければ、フレームワークが 404 とする。
2. モデルの削除日時が非 null の場合は、「対象が見つからない」趣旨の翻訳メッセージをエラースロットへ積み、一覧へリダイレクトする。
3. そうでなければモデル結合済みフォームを生成する。一覧は再読込し、現在 ID が編集中であるフラグおよび参照オブジェクトを渡す。送信先 URL は `update` となる。

### 更新する（POST `m03-22_admin_product_product_sell_group_update`）

1. `{id}` 解決失敗時は 404 とする。
2. 削除日時が非 null のモデルへの送信は一覧へリダイレクトし変更はしない。
3. フォーム処理は新規作成と同型。妥当時は作成日時は触らず更新日時のみ現在時刻、更新者はログイン状態に準じ記録され、flush 後成功フラッシュと一覧リダイレクト。
4. 失敗時は編集フラグ維持で同一テンプレ再表示。

### 論理削除する（DELETE `m03-22_admin_product_product_sell_group_delete`）

1. アンカー送信に付随するCSRF確認を親抽象で行い、失敗時アクセス拒否（HTTP 403）。
2. 削除日時が既に設定済みなら削除エラークラスのフラッシュを積んで一覧へ戻す。
3. モデルから商品側一方参照の集合が空でなければ、名称埋め込みの翻訳メッセージでエラー表示し一覧へ戻す。
4. ここまで通れば情報ログに削除開始メッセージと主キーを残し、`deleted_at` を現在時刻で flush、完了ログ、削除完了フラッシュ、一覧へリダイレクトする。

## フォーム送信・削除時の判定順序（POST と DELETE に共通する範囲を含む）

| 順序 | 判定 | 結果 |
|------|------|------|
| 1（DELETE のみ最初） | 共通CSRF名のトークンが有効か | 無効なら403。 |
| 2（GET 編集・更新） | 対象モデルが論理削除済みか | GET編集およびPOST更新とも削除済みなら一覧リダイレクト（編集開始時は特定のエラーメッセージ、更新時は名称等を変えず）。 |
| 3（POST） | Symfonyフォームと宣言制約により妥当か | 否なら同一画面レイアウトと検証結果表示。 |
| 4（POST 成功時） | 日時および更新者の付与、`persist` と `flush` の実行後リダイレクト | はい。 |
| 5（DELETE） | 商品コレクション空か | 否ならエラーと一覧へ。 |
| 6（DELETE 成功時） | 論理削除日時のセットとログ | はい、一覧へ。 |

## 業務ルール・計算

| 項目 | 内容 |
|------|------|
| 支払方法の選択肢 | 表示フラグが真である支払のみ。並びキーが大きいものから順に並べ替えクエリにより取得し、チェックボックス一覧にする。未選択許容。送信時選択集合が中間表へ反映される。 |
| 配送方法の選択肢 | 同上で配送側のマスタであり、並び順定義および表示フラグ条件はそれぞれのマスタ側の並び項目で降順になるようクエリ側で並べる。未選択許容。 |
| 予約商品フラグ | UIは単一チェック。永続モデル側は整数0または1。フォーム側でモデル変換により双方向へマッピングする。 |

本機能では金額丸めや集約集計などの別種の業務計算は行わない。

### エッジケース

| ケース | 扱い |
|--------|------|
| 商品が一つでも紐づく購入グループへの削除要求 | flush しない。フラッシュへ埋め込み名称付きエラー文案を載せ一覧へリダイレクト。 |
| 既に論理削除されたIDを編集URLで開く | 一覧へリダイレクトし、対象未取得のエラーメッセージをフラッシュへ積む。404にはせずパラメータ変換結果の実体読込は起こり得る。 |
| POST 送信で検証失敗 | 一覧表は送信処理内でも再クエリ済みであり、画面上は常に削除されていない全集を伴う編集状態または新規状態で検証結果を見せる。 |
| 一覧に行が無いとき | 表はヘッダのみの空データ相当で描画される。フォームだけで新規登録は継続可能。 |

### DB操作

永続化の正は ec-cube-enterprise。商品系は承認ワークフローを介さず persist/flush で直接確定する（在庫の承認ワークフローとは別系統。`ProductController`・各CSVサービスで確認）。

| 操作種別 | 対象テーブル | 契機・条件 |
|---------|--------------|------------|
| 登録/更新 | dtb_sell_group_delivery / dtb_sell_group_payment / mtb_sell_group | 当機能が行う登録・更新で対象テーブルを直接保存する（不要な削除は含まない）。確定は persist/flush による即時反映。DB=ec-cube-enterprise を正典とする。 |

### 遷移時に引き継ぐ状態

| 起点 | 遷移前の処理 | 遷移後の初期状態 |
|------|--------------|------------------|
| 成功保存や削除後302 | フラッシュメッセージに成功またはエラー文言種を積む | 一覧再描画および新規向けフォーム初期表示。一覧は削除除外後の結果。編集フラグ初期は新規状態。 |

本機能では購入グループ一覧用に独立した名前付き検索オブジェクトセッションを新設しない。

---

## エラー処理

| エラー内容 | 処理 |
|------------|------|
| フォーム入力不正 | 一覧付きページをHTTP 200で返しSymfonyがフィールド側エラーを出す。永続モデルへの flush は行わない。 |
| 削除共通CSRF失敗 | 403。フラッシュ一覧は前提としない業務異常応答として扱う。 |
| 論理削除済みモデルでの編集表示や更新送信 | GET編集開始はエラー付きフラッシュ後に一覧へ、POST更新も一覧へ戻してデータは不変とする。 |
| 商品利用中削除 | メッセージキーにより名称込み説明フラッシュのみ。 |
| DB整合性または予期しない例外 | ここまでのソース範囲では個別キャッチしない。共通例外ハンドリングに準拠。 |

---

## 試行制限

本機能では試行制限を別途設けず、管理上のログインレートリミット等は該当ファイアウォール共通に従う。

---

## ログ・監査

| タイミング | 記録内容 |
|------------|----------|
| 削除が実際に flush される直前および成功直後の情報ログ | メッセージ本文に処理区分文字列および配列での主キー参照を含める。ユーザー表示名称や備考長文自体はログ要求に載せない。 |

### ログに出してはいけないもの

- パスワード
- なりすまし対策トークン
- Cookie 値
- セッション ID の完全値
- Remember Me トークンの原値

---

## セッション

本機能は購入グループ一覧の検索条件やページング状態をセッションに保持しない。

### 本機能におけるセッション

| 観点 | 内容 |
|------|------|
| フラッシュメッセージ | 一覧リダイレクト後一回限りユーザーへ表示される以外の機能上の状態は増やさない。 |

---

## Cookie

認証状態を表すものは管理者向け共通のセッションクッキーに従い、本機能専用のCookieを新規に発行しないこととする詳細なCookie名一覧は共通ログイン設計を正とする。

---

## 排他制御・トランザクション

モデル側に論理ロック用の版管理列が無く、画面上の競合検知や再読込比較は行わない。保存時はDoctrineの単一ユニットオブワーク向け処理としてトランザクション境界に包含される運用となる。
