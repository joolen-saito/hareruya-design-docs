# メンバー管理（システム情報設定／設定）

## 概要

管理画面の「システム情報設定」配下において、管理ログイン用の管理者アカウント（メンバー）を新規登録・編集する機能である。ページタイトルブロックは「システム設定」、サブタイトルは「メンバー管理」、登録・編集ボックスの見出しは「メンバー登録・編集」として表示される。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。対象は pf-eccube3 のメンバー登録・編集（new／edit）とその保存処理とする。一覧表示・削除・表示順の入れ替えは「メンバー管理一覧」（M11-01）を正とする。

挙動・画面・処理フローの参照ソースツリーは pf-eccube3 を正とする。メンバー登録・編集は現行では HareruyaEcプラグインがコア実装を上書きしており、保存時に補助テーブル `dtb_member_sub`（所属店舗・スマレジ用アカウント）を併せて更新する。ただしDB関連の記述（テーブル名・列名・型・制約・関連・永続化先、入力項目の保存先、DBカラム節、データ整合性のDB部分、副作用のDB更新）は、リニューアル後システムである ec-cube-enterprise の実装を正とする。ec-cube-enterprise では所属店舗・スマレジ用アカウント・メールアドレス等は `dtb_member` 本体の列、編集可能店舗は結合表 `dtb_member_base_info` に保持し、現行プラグインの補助表 `dtb_member_sub` は持たない。現行と移行先のスキーマ差は「リニューアル移行時の扱い」に明記する。URLエンドポイントは管理画面コントローラのルート定義（`AdminControllerProvider`）で確認した利用者視点の入口として記載する。管理画面プレフィックスは `ADMIN_ROUTE`（`path.yml` の `admin_route`）で決まる。

---

## 本書で扱うこと

- メンバー新規登録・編集フォームの表示項目、検証、保存
- 編集時のパスワード・ソルトの扱い（未変更時の既存ハッシュ維持、変更時のソルト生成と再ハッシュ）
- 所属店舗とスマレジ用アカウントの保存（DB保存先は ec-cube-enterprise を正とし `dtb_member.base_info_id` / `dtb_member.smaregi_member_flg`。現行は HareruyaEcプラグインが補助表 `dtb_member_sub` の `shop_id` / `smaregi_member_flg` に保存）
- スマレジ用アカウントの一意制約（自身以外に有効な行が存在する場合のエラー）
- 保存成功・失敗時の結果メッセージと遷移先（プラグインは編集画面へ戻す）
- 編集画面表示時のセキュリティトークン上のユーザー復元
- 表示初期化・編集完了イベントによるプラグイン拡張点（名称はコード内の `EccubeEvents` 定数を参照）

---

## 本書で扱わないこと

以下は本書では仕様確定せず、実装または別機能の設計を正とする。

- メンバー一覧の表示・並び順、削除、上へ・下へ（「メンバー管理一覧」M11-01 を正とする）
- 管理画面へのログイン、セッション、CSRF の名称形式、Remember Me、パスワードポリシー全般の詳細
- 権限マスタ（`mtb_authority`）の各行が拒否するパスの対応関係（「権限管理」M11-03 を正とする）
- スマレジ連携そのものの処理（連携バッチ・APIを正とする）。本書はスマレジ用アカウントの指定保存のみ扱う
- 本機能以外が `dtb_member` を更新する経路（バッチ、他画面、直接SQL）の一覧
- 基本設計の機能仕様にある項目のうち、現行 pf-eccube3 の登録・編集画面には表示されない項目（メールアドレス、デフォルト検索表示店舗、編集可能店舗、二段階認証、自動ログアウト設定など）の画面挙動。これらは移行先 ec-cube-enterprise の `dtb_member` 等に列としては存在するが、現行画面の挙動としては扱わない。差分は「リニューアル移行時の扱い」を参照する

---

## リニューアル移行時の扱い

- 画面挙動・処理フローは現行（pf-eccube3）の確認値、DBスキーマは移行先（ec-cube-enterprise）を正とする。実装済み・未実装を取り違えず、現行と移行先を対比で示す。
- 永続化モデルの差: 現行は所属店舗・スマレジ用アカウントを補助表 `dtb_member_sub`（`shop_id` / `smaregi_member_flg`、メンバーと1対1）へ手動保存する。移行先は補助表を持たず、これらを `dtb_member` 本体の列（`base_info_id` / `smaregi_member_flg`）に保存する。本書のDB記述は移行先（`dtb_member` 本体）を正とする。
- 列対応（現行 → 移行先）:
  - 所属: `dtb_member.department`（テキスト） → `dtb_member.department_id`（`mtb_department` 参照のマスタFK）
  - 所属店舗: `dtb_member_sub.shop_id`（`mtb_shop` 参照） → `dtb_member.base_info_id`（`dtb_base_info` 参照）
  - スマレジ用アカウント: `dtb_member_sub.smaregi_member_flg` → `dtb_member.smaregi_member_flg`
  - 表示順: `dtb_member.rank` → `dtb_member.sort_no`（一覧 M11-01 と共通）
  - 主キー: `dtb_member.member_id` → `dtb_member.id`
- 移行先のみに存在する列・表: メールアドレス（`dtb_member.email`、非NULL）、デフォルト検索表示店舗（`dtb_member.default_search_base_info_id`）、二段階認証（`dtb_member.two_factor_auth_enabled` / `two_factor_auth_key`）、自動ログアウト設定（`dtb_member.is_auto_logout`）、編集可能店舗（結合表 `dtb_member_base_info` の `member_id` / `base_info_id`）。現行画面にはこれらの入力項目がなく、現行 `dtb_member` にも相当列がない。基本設計の機能仕様の追加項目はこれらに対応する。
- 所属店舗のマスタ差: 現行は専用マスタ `mtb_shop`、移行先は店舗（拠点）マスタ `dtb_base_info`。移行時はマスタ対応と、単一選択（所属店舗）と複数選択（編集可能店舗）の保持先の差を移行設計で吸収する。
- 保存成功時の遷移先は、コアでは一覧、現行の HareruyaEcプラグイン適用後は編集画面である。現行挙動は編集画面への遷移を正とする。

| 用語 | 説明 |
|------|------|
| メンバー | 管理画面へログインするアカウント。`dtb_member` に保存される。フロントの会員（顧客）とは別物である。 |
| 補助メンバー情報 | 現行 pf-eccube3 で所属店舗・スマレジ用アカウントを保持する補助表 `dtb_member_sub`（メンバーと1対1）。移行先 ec-cube-enterprise には存在せず、相当値は `dtb_member` 本体の列が持つ。 |
| 所属 | フォーム上のラベルは「所属」。保存先は `dtb_member.department_id`（`mtb_department` 参照のマスタFK）を正とする（現行 pf-eccube3 は `department` テキスト列）。 |
| 所属店舗 | 基本設計の「所属店舗」に対応する。保存先は `dtb_member.base_info_id`（`dtb_base_info` 参照）を正とする（現行 pf-eccube3 はプラグインの `dtb_member_sub.shop_id`、`mtb_shop` 参照）。 |
| 権限 | `mtb_authority` のマスタ項目。登録・編集ではドロップダウンで単一選択する。拒否パスの制御は権限管理を正とする。 |
| 稼働 | `mtb_work` のマスタ項目。登録・編集ではラジオで選択する。 |

| プレースホルダパスワード | 編集画面表示時にパスワード欄へ載せる設定値（`default_password`）。これと同じ値のまま送信された場合はパスワード未変更とみなす。 |

## 利用者視点の入口

| 入口 | URLエンドポイント | 期待されるふるまい |
|------|--------------------|---------------------|
| 新規登録を開く | `GET /%admin_route%/setting/system/member/new` | 空のメンバー登録・編集フォームが表示され、登録ボタンと一覧へ戻るリンクがある。 |
| 既存メンバーの編集を開く | `GET /%admin_route%/setting/system/member/{id}/edit` | 選択したメンバーの各項目がフォームに表示される。パスワード欄にはプレースホルダ文字列が入った状態で表示される。所属店舗・スマレジ用アカウントは補助メンバー情報の現行値で初期化する。 |
| 登録ボタンで新規登録を送信する | `POST /%admin_route%/setting/system/member/new` | 検証に成功すれば新規メンバーと補助メンバー情報を保存し、成功メッセージののち当該メンバーの編集画面へ遷移する。 |
| 登録ボタンで編集を送信する | `POST /%admin_route%/setting/system/member/{id}/edit` | 検証に成功すれば更新し、成功メッセージののち同じ編集画面へ遷移する。失敗時はエラーメッセージを表示し同一画面を再表示する。 |
| 存在しないIDで編集を開く | `GET /%admin_route%/setting/system/member/{id}/edit` | 404 応答となる。補助メンバー情報が見つからない場合も同様に 404 とする。 |
| 戻るリンク | —（一覧へのリンク） | メンバー一覧（M11-01）へ遷移する。 |

## 処理フロー

### 新規登録・編集を開く（GET）

1. 管理画面の認証・認可・ネットワーク制限などの前置処理を通過する（詳細は管理画面基盤の実装を正とする）。
2. 編集で ID 指定がある場合、該当メンバーと補助メンバー情報を取得する。どちらも無ければ 404 とする。あれば退避用に暗号化済みパスワードを保持し、エンティティのパスワードにプレースホルダ値を代入してフォーム表示用にする。新規の場合は空のメンバーと空の補助メンバー情報を生成する。
3. ログイン中メンバーをクローンし、永続化コンテキストから切り離す（セッション上のユーザー実体と編集対象の混在を避けるための確認値）。
4. 管理者メンバー用フォームをメンバーに紐づけて生成し、編集向け初期化イベントをディスパッチする。フォームには標準項目に加え、所属店舗とスマレジ用アカウントをプラグイン拡張で表示する。
5. フォームを描画する前に、セキュリティトークンのユーザーへクローンしたログイン中メンバーを戻す。
6. テンプレートにフォームビュー、メンバー、補助メンバー情報を渡して描画する。所属店舗・スマレジ用アカウントの初期表示は補助メンバー情報の現行値を用いる。

### 登録ボタン押下（POST、検証成功）

1. フォームをリクエストで処理する。
2. 検証成功時、編集かつ入力パスワードがプレースホルダのままなら退避していた暗号化パスワードを戻す。それ以外はソルト未設定ならランダムソルト（5文字）を生成し、エンコーダでパスワードをハッシュ化してセットする。
3. メンバーを保存する。
4. 保存に成功した場合、フォームの所属店舗が選択されていれば所属店舗を設定し、未選択なら空にする（現行は補助メンバー情報の `shop_id` へ保存。移行先は `dtb_member.base_info_id` を正とする）。
5. スマレジ用アカウントが有効で、かつ自身以外に有効なスマレジ用アカウントが存在する場合は、エラーメッセージを積み、編集画面へ遷移する（スマレジ用フラグは反映しない）。
6. 競合がなければ、スマレジ用フラグを設定して保存する（現行は補助メンバー情報の `smaregi_member_flg`、移行先は `dtb_member.smaregi_member_flg` を正とする）。
7. 編集完了イベントをディスパッチし、成功メッセージを積み、登録時は作成したメンバーの編集画面へ、編集時は同じ編集画面へ遷移する。
8. メンバー保存が失敗した場合はエラーメッセージを積み、同一画面を再表示する。

### 登録ボタン押下（POST、検証失敗）

1. フォームをリクエストで処理する。
2. 同一の登録・編集テンプレートを再表示し、項目エラーを表示する。成功メッセージは積まない。
3. 描画前にセキュリティトークンのユーザーをクローンしたログイン中メンバーへ戻す。

## 集計条件

## 保存時の判定順序

| 順序 | 判定 | 結果 |
|------|------|------|
| 1 | フォーム検証に成功したか | 失敗なら同一画面を再表示し、以降を実行しない。 |
| 2 | 編集かつパスワードがプレースホルダのままか | そのままなら退避した暗号化パスワードを戻す。異なる場合はソルト未設定なら生成し、再ハッシュする。 |
| 3 | メンバー保存に成功したか | 失敗ならエラーメッセージを積み同一画面を再表示する。 |
| 4 | スマレジ用アカウントが有効で、自身以外に有効な行が存在するか | 存在するならエラーメッセージを積み編集画面へ戻す。スマレジ用フラグは反映しない。 |
| 5 | 上記を満たすか | 補助メンバー情報を保存し、成功メッセージを積み編集画面へ遷移する。 |

## 業務ルール・計算

本機能では金額計算や税率計算は行わない。

### 入力項目

| 項目名 | 必須／任意 | 最大長 | 初期値 | 保存先・扱い |
|--------|------------|--------|--------|----------------|
| 名前 | 必須 | 50 文字 | 新規は空、編集はDB現行値 | `dtb_member.name`。空白不可・長さ検証あり。 |
| 所属 | 必須相当 | 50 文字 | 新規は空、編集はDB現行値 | 保存先は `dtb_member.department_id`（`mtb_department` 参照のマスタFK）を正とする。現行 pf-eccube3 はテキスト項目で `department` 列に保存し、フォーム定義上は任意だが空白不可の検証を持つため実質必須として扱う。 |
| ログインID | 必須 | 4〜50 文字 | 新規は空、編集はDB現行値 | `dtb_member.login_id`。空白不可・長さ・印字可能文字＋空白の正規表現検証あり。列の一意制約により重複時はエラー（メッセージは実装の翻訳メッセージを正とする）。 |
| パスワード | 必須 | 4〜50 文字（確認欄も同条件） | 新規は空、編集はプレースホルダ表示 | `dtb_member.password`。平文は永続化せず、保存前にソルト付きハッシュへ変換し `dtb_member.salt` を用いる。編集で入力がプレースホルダのままなら既存ハッシュを維持する。 |
| 権限 | 必須 | （マスタに依存） | 新規は先頭、編集はDB現行値 | フォーム項目 `Authority`。`dtb_member.authority_id`。権限マスタからドロップダウンで単一選択する。 |
| 所属店舗 | 任意 | （店舗マスタに依存） | 新規は空、編集は現行値 | 保存先は `dtb_member.base_info_id`（`dtb_base_info` 参照）を正とする。現行 pf-eccube3 はプラグインの `dtb_member_sub.shop_id`（`mtb_shop` 参照、フォーム `Shop` は `mapped: false`）に保存する。 |
| 稼働 | 必須 | （マスタに依存） | フォームバインド時のエンティティ初期状態 | フォーム項目 `Work`。`dtb_member.work_id`。ラジオで選択する。 |
| スマレジ用アカウント | 任意 | — | 新規は無効、編集は現行値 | 保存先は `dtb_member.smaregi_member_flg` を正とする。現行 pf-eccube3 はプラグインの `dtb_member_sub.smaregi_member_flg`（フォーム `smaregiMemberFlg` は `mapped: false`）に保存する。有効化は自身以外に有効な行が無い場合のみ可能とする。 |

長さの数値はコア付属の `src/Eccube/Resource/config/constant.yml.dist` の既定（`stext_len` 50、`id_min_len` 4、`id_max_len` 50）を確認値とする。運用環境で上書きされている場合はその環境の値が正とする。`default_password` は編集画面のプレースホルダおよび「パスワード未変更」判定に使われる文字列であり、環境設定で与えられる。

### エッジケース

| ケース | 扱い |
|--------|------|
| 編集でパスワードをプレースホルダのまま送信 | 退避した暗号化パスワードをそのまま保存する。ソルトの新規生成と再ハッシュは行わない。 |
| 新規でログインIDが既存と重複 | 一意制約によりエラーとなり保存が成立しない。 |
| スマレジ用アカウントを有効化したが他に有効な行がある | メンバー自体は保存済みのまま、エラーメッセージを積み編集画面へ戻す。スマレジ用フラグは反映しない。 |
| 所属店舗を未選択で保存 | 現行は所属店舗を空にできる（補助表 `dtb_member_sub.shop_id` を空）。移行先の `dtb_member.base_info_id` は非NULLのため、移行時は所属店舗の必須化を要検討。 |
| 編集対象が存在しない | 404 応答となる（現行は補助メンバー情報が無い場合も 404）。 |

## データ整合性

| 観点 | 内容 |
|------|------|
| 編集画面とDB | 編集GETではパスワード列をプレースホルダで上書きしたあとフォームに載せるため、画面上のパスワード欄はDBの暗号文と一致しない。 |
| 所属店舗・スマレジ等の保存先 | 移行先は所属店舗（`base_info_id`）・スマレジ用アカウント（`smaregi_member_flg`）を `dtb_member` 本体に保存する（本書のDB記述はこれを正とする）。現行 pf-eccube3 はメンバー保存に成功した後、補助表 `dtb_member_sub` に保存する。 |
| スマレジ用アカウントの一意性 | 有効なスマレジ用アカウントは全メンバーで1件までとする。重複時はメンバー保存後にエラーで差し戻し、スマレジ用フラグの反映を見送る。 |
| 認証情報との関係 | ログイン中トークンのユーザー実体は編集画面描画前に元のログインメンバーへ戻すため、編集対象の一時エンティティがトークンに残らない。 |
| 一覧との関係 | 保存後の表示は一覧（M11-01）に反映される。一覧の並び・削除は M11-01 を正とする。 |

本機能では外部HTTP API 呼び出しやバッチ実行を扱わない。スマレジ連携の実処理は連携バッチ・APIを正とし、本機能はスマレジ用アカウントの指定保存のみを扱う。

### DB操作

永続化の正は ec-cube-enterprise（テーブル名・操作は ec-cube-enterprise を正典）。当ドメインは承認ワークフローを介さず persist/flush で直接確定する（承認ワークフローは在庫機能固有）。

| 操作種別 | 対象テーブル | 契機・条件 |
|---------|--------------|------------|
| 登録/更新 | dtb_base_info / dtb_member / dtb_member_base_info / dtb_member_sub / mtb_authority / mtb_department 等 | 当機能が行う登録・更新で対象テーブルを直接保存する（不要な削除は含まない）。確定は persist/flush による即時反映。DB=ec-cube-enterprise を正典とする。 |

## 画面遷移

| 条件 | 遷移先 |
|------|--------|
| 一覧から新規登録リンク | メンバー登録・編集画面（新規）。 |
| 一覧から編集リンク | メンバー登録・編集画面（既存）。 |
| 登録成功 | 作成したメンバーの編集画面。 |
| 編集成功 | 同一メンバーの編集画面。 |
| メンバー保存失敗 | 同一の登録・編集画面（再表示）。 |
| スマレジ用アカウント重複 | 同一メンバーの編集画面（エラーメッセージ付き）。 |
| 検証失敗 | 同一の登録・編集画面。 |
| 戻るリンク | メンバー一覧（M11-01）。 |
| 編集で ID 非存在 | エラー画面（404）。 |

### 遷移時に引き継ぐ状態

| 起点 | 遷移前の処理 | 遷移後の初期状態 |
|------|--------------|------------------|
| 保存成功 | 成功フラッシュを積む | 編集画面が再読込されメッセージが表示される。 |
| スマレジ重複 | エラーフラッシュを積む | 編集画面が再読込されエラーが表示される。 |
| 登録・編集画面を描画 | セキュリティトークンのユーザーをログイン中メンバーへ戻す | 以降の画面は通常のログインコンテキストである。 |

## エラー処理

| エラー内容 | 処理 |
|------------|------|

## 排他制御・トランザクション

メンバー保存はリポジトリ処理で行い、補助メンバー情報は永続化マネージャで保存・flushする。行レベルの楽観ロック列は持たない。スマレジ用アカウントの一意性は保存時の検索で担保し、同時更新の競合保証は本書では切らない。
