# o01-01_other_mtg_buyer_mtg_buyer_store_purchase（その他_MTGバイヤー_店頭買取）

## 概要

MTGバイヤーで店頭買取の査定を行う業務を、EC-CUBE側の店頭買取データ、管理画面、pf-api連携から見たリバース詳細設計である。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。確認値は`../pf-eccube3`のHareruyaEcプラグインにある店頭買取業務資料、店頭買取フロント・管理画面、店頭買取API設計を正とする。本機能のカスタマイズ区分はカスタマイズであり、挙動はpf-eccube3（HareruyaEcプラグイン）の実装を参照し、DB関連（テーブル・列）の記述はec-cube-enterpriseを正とする。

MTGバイヤー本体は本リポジトリ内に実装が無い外部アプリである。本書では外部アプリ内部の画面・UI・ローカル保存仕様は確定せず、EC-CUBE側で確認できる入口、API、DB更新、副作用を扱う。

---

## 本書で扱うこと

- 店頭買取の受付後、MTGバイヤーで査定を開始・入力・確定する業務境界
- MTGバイヤーが利用する店頭買取APIの役割
- 査定結果がEC-CUBE側の店頭買取受注、明細、在庫、履歴、ステータスへ反映される範囲
- リポジトリ内で確認できる管理画面・CSV・集計との整合

---

## 本書で扱わないこと

以下は本書では仕様確定せず、外部アプリまたは別機能の設計を正とする。

- MTGバイヤー本体の画面項目、ローカルDB、オフライン動作、バーコード読取、印刷の内部仕様
- Backlog、Excelマクロ、スマレジ、店舗作業などリポジトリ外の運用
- 店頭買取申込フォームの詳細（F08-01〜F08-03を正とする）
- 店頭買取管理画面の検索・編集・CSV出力の詳細（M06系の各設計を正とする）
- pf-api各エンドポイントのリクエスト・レスポンス詳細（A06系の各API設計を正とする）

## 処理フロー

### 店頭買取を受付する

1. フロントの店頭買取申込で、会員または非会員が申込情報を入力する。
2. 申込確定時に店頭買取受注を作成し、査定番号を採番する。
3. 店頭買取ステータスは査定前として登録される。
4. 受付時の本人確認、買取品の預かり、身分証コピーなどの実作業は運用で行う。

### MTGバイヤーで査定を開始する

1. MTGバイヤーはログインAPIで認証し、認証トークンを取得する。
2. 店頭買取受注一覧取得APIで査定対象の受注を取得する。
3. 店舗に紐づく管理者で認証している場合は、当該店舗の受注だけが一覧に含まれる。
4. 査定開始時はステータス更新APIにより査定中へ更新する。
5. EC-CUBE側は受注のステータス、査定担当者、更新日時、ステータス変更履歴を保存する。

### MTGバイヤーで査定結果を確定する

1. MTGバイヤーは商品検索・商品取得APIを使い、査定対象の商品情報を取得する。
2. 査定明細として商品規格ID、商品名、数量、買取単価、販売価格、部門などを送信する。
3. EC-CUBE側は受注IDで店頭買取受注を特定する。該当が無い場合は該当なしとして返す。
4. ステータス、明細配列、明細各項目を検証する。検証エラーがあれば保存せず入力不正を返す。
5. 既存の受注明細、個別入力商品、在庫、在庫履歴を削除し、送信明細で作り直す。
6. 商品規格に紐づく明細は商品規格単位で数量を集計し、在庫と在庫履歴を作る。
7. 明細の買取単価×数量を合計し、買取合計金額を10円単位へ切り上げる。
8. ステータス、買取合計金額、査定担当者、更新日時、成立日時またはキャンセル日時を保存する。
9. ステータスが変わった場合はステータス変更履歴を登録する。

### 査定後の店頭買取業務へ進む

1. 査定結果を顧客と確認する。
2. 買取キャンセルの場合はステータスを買取キャンセルへ更新する。
3. 買取成立の場合はステータスを買取成立へ更新する。
4. EC-CUBE管理画面では、買取一覧、買取詳細、買取商品履歴、買取集計、古物台帳用CSV、在庫登録用CSVなどで確定済みデータを参照・出力する。
5. バーコード印刷、Backlog起票、スマレジ、仕入れ作業などはリポジトリ外の運用を正とする。

## 業務ルール・計算

| 項目 | 内容 |
|------|------|
| 査定対象の抽出 | 店頭買取受注一覧取得APIは、商品到着、査定中、振込前、保留、査定再開の状態にある受注を対象にする。成立、キャンセル、ダブルチェック済、データ出力済などは査定対象一覧から外れる。 |
| 店舗絞り込み | 認証した管理者に所属店舗がある場合は、その店舗に一致する店頭買取受注だけを返す。所属店舗が無い場合は店舗で絞り込まない。 |
| 明細の全置換 | 査定結果確定APIは、既存の明細・個別入力商品・在庫・在庫履歴を削除して、送信された明細で作り直す。送信されなかった既存明細は残らない。 |
| 個別入力商品の扱い | 商品規格IDが空の明細は個別入力商品として登録する。商品規格に紐づかないため、商品規格単位の在庫集計には含めない。 |
| 買取合計金額 | 送信明細の買取単価×数量を合算し、10円単位へ切り上げる。MTGバイヤー側の表示値ではなく、EC-CUBE側保存処理で再計算した値を保存する。 |
| 在庫数量 | 商品規格に紐づく明細を商品規格ごとに集計し、同一商品規格の数量を合算して店頭買取受注在庫と在庫履歴を作成する。 |
| ステータス変更履歴 | 更新前後でステータスが異なる場合に履歴を登録する。同じステータスへの詳細更新では明細・在庫は作り直すが、ステータス変更履歴は追加しない。 |
| 外部運用 | 査定表印刷、本人確認の実作業、出金、バーコード印刷、Backlog、スマレジ、仕入れ統合作業はEC-CUBE側で確認できる範囲外の運用を正とする。 |

### 入力項目

| 項目名 | 必須／任意 | 最大長 | 初期値 | 保存先・扱い |
|--------|------------|--------|--------|----------------|
| 認証トークン | 必須 | API認証仕様に従う | ログインAPIの成功結果 | 各APIの`jwt-token`ヘッダ。原値は本書に記載しない。 |

| 査定明細 | 必須 | 配列。商品名はAPI設計の上限に従う | MTGバイヤーで入力 | 商品規格ID、商品名、数量、買取単価、販売価格、部門を受け取り、明細・個別入力商品・在庫へ反映する。 |

| 本人確認情報 | 任意 | API設計の上限に従う | 既存値 | 店頭買取受注に紐づく本人確認状態を更新する。 |

### エッジケース

| ケース | 扱い |
|--------|------|
| 認証不可 | APIは認証拒否とし、店頭買取データを返さず更新しない。 |
| 査定対象が0件 | 店頭買取受注一覧取得APIは空配列を返す。 |
| 受注IDが存在しない | 詳細更新、ステータス更新、コメント更新、本人確認更新は該当なしとして扱う。 |
| 明細が空 | 詳細更新APIは入力不正とし、既存明細・在庫を削除しない。 |
| 同じステータスで詳細更新 | 明細・個別入力商品・在庫・在庫履歴は送信内容で作り直す。ステータス変更履歴は追加しない。 |
| 同時更新 | 専用の楽観ロック・悲観ロックは持たない。後から確定した更新が残る。 |

## データ整合性

| 観点 | 内容 |
|------|------|
| 参照時点 | MTGバイヤーの一覧取得、商品情報取得、管理画面の一覧・詳細・CSVは、それぞれ実行時点で永続化済みのデータを参照する。 |
| 査定結果と管理画面 | MTGバイヤーで確定した受注明細、個別入力商品、在庫、在庫履歴、ステータス、査定担当者、更新日時は、保存成功後に管理画面の店頭買取詳細・履歴・CSVの参照元になる。 |
| 在庫と履歴 | 詳細更新時に商品規格ごとの数量で店頭買取受注在庫を作り直し、対応する在庫履歴を登録する。既存在庫・履歴は削除後に再作成される。 |
| ステータスと集計 | 買取成立、ダブルチェック済、データ出力済など集計対象のステータスへ変わると、店頭買取集計やCSV出力の対象になる。集計処理の詳細はM06系およびバッチ設計を正とする。 |
| 外部運用との整合 | Backlog、スマレジ、Excelマクロ、バーコード印刷は本リポジトリ内で直接整合を保証しない。EC-CUBE側で出力したCSVや確定済みデータを運用で利用する。 |
| 同時更新 | DB行ロックを使った査定占有は確認できない。同一受注を複数の利用者・APIが同時に更新した場合、後から保存された内容が残る。 |

## API/バッチ結果

| 種類 | 内容 |
|------|------|
| API | MTGバイヤーはpf-apiのA06系APIを利用する。ログイン、店頭買取受注一覧取得、詳細更新、コメント更新、ステータス更新、本人確認更新、商品検索・商品取得が主な接続点である。 |
| 成功結果 | 参照APIはJSONで対象データを返す。更新APIは対象データを保存し、成功コードまたは更新結果を返す。 |
| 失敗結果 | 認証不可、対象なし、入力不正、保存例外は各API設計のHTTPステータスと本文形式に従う。 |
| バッチ | 店頭買取集計は`otcBuyOrder:batch updateSummary`で実行される。MTGバイヤー本体が直接バッチを起動する仕様は確認できない。 |
| 再実行時 | 参照APIは実行時点の最新データを返す。詳細更新APIは明細・在庫を全置換するため、同じ受注に再送すると送信内容で上書きされる。 |

### DB操作

永続化の正は ec-cube-enterprise（テーブル名・操作は ec-cube-enterprise を正典）。当ドメインは承認ワークフローを介さず persist/flush で直接確定する（承認ワークフローは在庫機能固有）。

| 操作種別 | 対象テーブル | 契機・条件 |
|---------|--------------|------------|
| 登録/更新 | dtb_otc_buy_order / dtb_otc_buy_order_detail / dtb_otc_buy_order_indivisual_input_product / dtb_otc_buy_order_status_history / dtb_otc_buy_order_stock / dtb_otc_buy_order_stock_history 等 | 当機能が行う登録・更新で対象テーブルを直接保存する（不要な削除は含まない）。確定は persist/flush による即時反映。DB=ec-cube-enterprise を正典とする。 |

## バリデーション

| 項目 | 内容 |
|------|------|
| 認証 | `jwt-token`ヘッダのJWTを検証し、管理者会員を特定する。失敗時は処理を行わない。 |
| 店頭買取受注ID | 対象受注が存在すること。存在しない場合は該当なし。 |
| ステータス | 店頭買取ステータスマスタに存在すること。存在しない場合は入力不正。 |
| 査定明細 | 1件以上であること。商品名、数量、価格、部門、商品規格IDなどの形式は店頭買取受注詳細更新APIの検証に従う。 |
| 商品・部門 | 商品規格IDや部門IDが送信された場合、存在するデータだけを関連付ける。存在しない場合の扱いはAPI設計を正とする。 |

## 権限・認可

| 利用者状態 | 店頭買取査定 |
|------------|--------------|
| 認証済みの管理者会員 | MTGバイヤーからA06系APIを呼び出せる。査定結果確定時は査定担当者として記録される。 |
| 店舗に紐づく管理者会員 | 店頭買取受注一覧取得では所属店舗の受注に絞り込まれる。 |
| 店舗に紐づかない管理者会員 | 店頭買取受注一覧取得では店舗による絞り込みを行わない。 |
| 未認証・トークン不正 | APIは認証拒否となり、参照・更新できない。 |

## 画面遷移

| 条件 | 遷移先 |
|------|--------|
| MTGバイヤーでログイン成功 | MTGバイヤー側の査定対象一覧へ進む想定。外部アプリ内遷移は本書では仕様確定しない。 |
| 査定対象を選択 | MTGバイヤー側の査定入力へ進む想定。EC-CUBE側では対象受注の詳細更新APIを受け付ける。 |
| 査定結果確定成功 | MTGバイヤー側の完了または一覧へ戻る想定。EC-CUBE側ではDB更新が確定し、管理画面・CSV・集計の参照元になる。 |
| 入力不正・認証不可 | MTGバイヤー側でエラー表示する想定。EC-CUBE側はAPIエラー応答を返す。 |

## エラー処理

| エラー内容 | 処理 |
|------------|------|
| 認証不可 | APIは認証拒否を返し、店頭買取データを返さず更新しない。 |
| 受注が存在しない | 該当なしとして返し、更新しない。 |
| ステータス不正 | 入力不正として返し、更新しない。 |
| 明細不正 | 入力不正として返し、既存明細・在庫を削除しない。 |
| 保存処理中の例外 | APIの共通例外処理に従う。トランザクション内の未確定更新はロールバックする。 |
| 外部運用の失敗 | Backlog、スマレジ、Excelマクロ、バーコード印刷などは本書では処理結果を保証しない。各運用を正とする。 |

## ログ・監査

| タイミング | 記録内容 |
|------------|----------|
| ステータス変更 | 店頭買取ステータス変更履歴に受注ID、更新後ステータス、更新担当者、登録日時を記録する。 |
| 詳細更新 | 店頭買取在庫履歴に更新後数量、登録者、登録日時を記録する。 |
| APIエラー | アプリケーションの共通ログ方針に従う。 |

### ログに出してはいけないもの

- JWTトークンの原値
- 署名シークレット
- パスワード
- Cookie値
- セッションIDの完全値
- 本人確認画像や個人情報の不要な全文

## セッション

MTGバイヤー連携APIはJWTヘッダで認証する。EC-CUBE管理画面やフロント店頭買取申込のセッションは各画面設計を正とし、本書ではMTGバイヤー本体のセッション保存仕様を扱わない。

---

## Cookie

MTGバイヤー本体のCookie仕様は本書では扱わない。pf-api連携では`jwt-token`ヘッダを認証に使い、Cookie値の原値は設計書に記載しない。

## 排他制御・トランザクション

| 観点 | 内容 |
|------|------|
| トランザクション境界 | 店頭買取受注詳細更新APIは、既存明細・在庫の削除、明細・在庫・履歴の登録、受注更新、ステータス履歴登録を一連の保存処理として扱う。保存処理中の例外では未確定更新をロールバックする。 |
| ロック | 査定対象受注に対する行ロック・悲観ロック・楽観ロック・ロックファイルは確認できない。査定中などのステータスは業務上の状態であり、DBレベルの占有ロックではない。 |
| 例外時 | 検証エラーでは削除・登録・更新を開始しない。保存処理中の例外ではトランザクション内の未確定更新をロールバックする。 |
| 同時更新 | 同一受注を複数のMTGバイヤーまたは管理画面から同時更新した場合、後から確定した保存内容が残る。 |
