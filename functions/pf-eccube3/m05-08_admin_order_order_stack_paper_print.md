# 受注管理 — スタック用紙印刷

## 概要

管理画面の「受注管理」一覧から選択した配送行に対し、別ウィンドウを開いたうえで非同期処理を走らせ、スタック用紙向けに必要な印刷予約フラグおよび条件に応じた受注ステータス・確定日を更新する機能である。呼び出し成功時にはJSONで確認メッセージを返し、アラート表示後に子ウィンドウを閉じる。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。確認値とするソースは `src/Eccube/Controller/Admin/Order/OrderController.php` の該当ルート、`src/Eccube/Resource/template/admin/Order/index.twig`、`src/Eccube/Resource/template/admin/Order/print_stack_window.twig`、`src/Eccube/Repository/OrderRepository.php` の印字リスト取得処理、`src/Eccube/Service/Admin/Order/UpdateStackListAction.php`、`src/Eccube/Entity/Master/MtbOption.php` とする。

対象はブラウザ経由の管理画面に限定する。店舗別の基本情報画面上の「スタック用紙高額商品しきい値価格」（`dtb_base_info.stack_paper_threshold`）の入力・同期は別画面の設計とし、一覧からのスタック用紙印字クエリそのものでは参照しない点に注意する。

本機能のカスタマイズ区分は現行踏襲である。現行挙動は pf-eccube3 のHareruyaEcプラグイン実装を参照し、リニューアル移行後の挙動とDBは ec-cube-enterprise を確認値とする。DB関連の記述は ec-cube-enterprise を正とする。

コントローラの公開関数一覧は本文の主題としない。本文ではルートbind名やSymfonyのルートnameの網羅は主説明としない。「利用者視点の入口」にHTTPメソッドとサイトルートからのパスパターンを書く。コード探索でbind名が必要なときだけ「調査補助」へ書く。

## リニューアル移行時の扱い

スタック用紙印刷は現行 pf-eccube3 では HareruyaEc プラグインで実装する。ブラウザ印刷フラグ・確定日時・担当者は、現行では補助テーブル `dtb_order_sub` に分割保持するが、移行先 ec-cube-enterprise では `dtb_order` に統合される。DB関連は ec-cube-enterprise を正とし、本書のテーブル・列名は移行先名で記す。

| 項目 | 現行 pf-eccube3（HareruyaEc） | 移行先 ec-cube-enterprise |
|------|-------------------------------|----------------------------|
| ブラウザ印刷フラグ | `dtb_order_sub.browser_print_flg` | `dtb_order.browser_print_flg` |
| 確定日時 | `dtb_order_sub.confirm_date` | `dtb_order.confirm_date` |
| 担当者会員 | `dtb_order_sub.operator_id` | `dtb_order.member_id` |
| 受注ステータス | `dtb_order.order_status_id` | `dtb_order.order_status_id`（同一） |
| 高額判定・閾値オプション | `mtb_option`（`option_key`/`option_value`） | `mtb_option`（同一。`stack_paper_judgment_price`, `stack_paper_threshold_price`） |

本書のDBカラム節・副作用節のDB更新記述は移行先 ec-cube-enterprise の名称に合わせている。現行の補助テーブル列は上表で対応づける。

## 処理フロー

### 子ウィンドウを開いてHTMLを表示する（`admin_order_print_stack_window`）

1. 管理画面の認証・共通制約を通過する。
2. リクエストパラメータ `ids` をそのままテンプレート変数に渡す（配列でも単一値でもテンプレート側でJSON化する）。
3. `print_stack_window.twig` を返す。ルート処理内に `_token` の検証コードは無い。

### 印刷予約を記録する（`admin_order_print_stack`）

1. 管理画面の認証・共通制約を通過する。
2. リクエストボディの `_token` について共通の検証関数で照合し、失敗時は管理向けエラーメッセージを積み、HTTP400でJSON「不正なリクエストです。」を返す。
3. `ids` が空ならHTTP404でJSON「対象の注文が指定されていません。」を返す。配列でなければ長さ1の配列に包む。
4. `mtb_option` から `stack_paper_judgment_price` と `stack_paper_threshold_price` を取得し、連想配列にする。
5. `getPrintOrderList` に配送ID配列と当該オプション値を渡し、注文ごとの印字行を得る。SQLの `ORDER BY` は `dtb_order.id` 昇順。
6. 各行について `order_no` が空ならHTTP400でJSON「注文番号が未採番の注文があります。」を返し、以降の更新は行わない。
7. 各行について更新パラメータを組み立てる。配列には印刷フラグを真にする意図のキーを含めるが、保存処理側は現行コードではそれ以外のビジネス用キーを解釈しない。ステータスが新規受付（数値IDが1）の行だけピックへ進めるフラグを真にする。
8. `src/Eccube/Service/Admin/Order/UpdateStackListAction.php` が提供するハンドラをトランザクション内で実行する。各注文に対し `browser_print_flg` を真にし、手順7でピック遷移フラグが真になった行だけ受注ステータスをピック中（数値IDが10）にし `confirm_date` を現在日時で上書きする。操作者会員が解決できれば `dtb_order` の担当者をその会員に差し替える。
9. 例外が出た場合はハンドラでロールバックしたうえで再送出される。コントローラ側は単一種類の標準例外だけをHTTP400のJSONへ写し替える分岐がある。印刷フラグ更新ハンドラの処理本文だけを読む限り、その型での終了は定義されていない。その他はそのまま外へ伝播しうる。
10. 正常終了時はHTTP200でJSON「印刷予約を受け付けました。」を返す。

## 集計条件

本機能は一覧の件数集計や合計金額の再計算を行わない。

| 指標 | 集計の要点 |
|------|------------|
| 印字行の単位 | 選択された `dtb_shipping.id` に紐づく `dtb_order.id` ごとに1行。同一注文の複数配送を同時に選んでも注文は1行にまとまる |

## スタック用紙印字データ組み立て時の判定

| 順序 | 判定 | 結果 |
|------|------|------|
| 1 | `stack_paper_judgment_price` の文字列が `"0"` か | `"0"` なら明細価格の最大を使うサブクエリを採用。それ以外なら商品規格の買取価格の最大を使うサブクエリを採用 |
| 2 | 閾値 `(int) stack_paper_threshold_price` と `op.price` を比較する | 現行の `CASE` 式では閾値以上・未満にかかわらず印字列 `expensive` は同じ空欄装飾文字（実装では「□」）になる |

## 業務ルール・計算

| 項目 | 内容 |
|------|------|
| 閾値 | `mtb_option.stack_paper_threshold_price` を整数化してSQLパラメータに渡す。店舗マスタ `dtb_base_info.stack_paper_threshold` は当クエリでは使わない |
| 高額印字区分 | 前表のとおり分岐はあるが、返却列の文字は両分岐で同一のため、現行実装単体では印字データ上の差は出ない |
| 新規受付時の追加更新 | ステータスIDが1の注文だけピック中（ID10）へ遷移し、`confirmDate` をサーバ現在日時でセットする。それ以外のステータスではステータスと確定日は変えない |

本機能ではフォーム入力の保存・更新画面を持たないため、`### 入力項目` の5列表は置かない。

## データ整合性

| 観点 | 内容 |
|------|------|
| 一覧との対応 | チェックボックスの値は配送ID。印字と更新の対象はその配送が属する注文 |
| オプションと店舗マスタ | 印字SQLは全体オプションの閾値のみ参照し、行ごとの店舗しきい値とは自動一致しない |
| 同時操作 | 更新は悲観的ロックの追加取得なしで行う。他画面と同一注文を同時に更新した場合の結果は最終書き込み優先 |
| 子画面と親画面 | 親の検索条件セッションは本導線では書き換えない |
| 配送ID欠損時 | SQLに現れなかった配送IDだけは更新対象に含まれず、リストに載った注文だけがコミットされる |

## DBカラム

当機能の更新で直接触れる主な列は次のとおり。型の細部はスキーマ定義を参照する。

| テーブル | 列 | メモ |
|---------|-----|------|
| `dtb_order` | `browser_print_flg` | 真に更新する |
| `dtb_order` | `order_status_id` | 新規受付からピック中への遷移時のみ変更 |
| `dtb_order` | `confirm_date` | 上記遷移時に現在日時をセット |
| `dtb_order` | `member_id` | 操作者会員が存在するときにセット |

### DB操作

本機能は参照系（検索・出力）であり、DBへの登録・更新・削除は行わない。テーブル名は ec-cube-enterprise を正典とする。

| 操作種別 | 対象テーブル | 契機・条件 |
|---------|--------------|------------|
| 検索 | dtb_order | 検索条件に合致するレコードを抽出する。抽出結果を所定フォーマットでファイル出力する。 |

## 画面遷移

| 条件 | 遷移先 |
|------|--------|
| 一覧で印刷ボタン押下（正常） | 子ウィンドウが開き、同セッション内でAJAX後に子が閉じる。親URLは変わらない |
| CSRF失敗・対象なし・未採番 | 子ウィンドウ内でアラート後に閉じる。親はそのまま |

### 遷移時に引き継ぐ状態

| 起点 | 遷移前の処理 | 遷移後の初期状態 |
|------|--------------|------------------|
| 一覧→子ウィンドウ | 一括フォームに埋めた `ids[]` と `_token` をPOST | 子は同じ `ids` をJSONでAJAXに載せ替え、新しいページ生成時点の `_token` を付与する |

## エラー処理

| エラー内容 | 処理 |
|------------|------|
| CSRF不正 | HTTP400、JSONで固定メッセージ。管理向けフラッシュにCSRF関連キー |
| `ids` 空 | HTTP404、JSONで対象未指定メッセージ |
| 注文番号未採番 | HTTP400、JSONで未採番メッセージ。DB更新は行わない |
| AJAX応答がJSONでない等 | 子ウィンドウで固定のシステムエラー文を表示して閉じる |
| 更新処理の例外（HTTP400へ写し替えられない種類） | 子ウィンドウ側では汎用エラー表示に落ちうる。サーバは伝播させうる |

## 調査補助（grep用）

実装位置の手がかりとして、ルート名 `admin_order_print_stack_window`・`admin_order_print_stack`、テンプレート `print_stack_window.twig`、リポジトリメソッド `getPrintOrderList`、サービス `UpdateStackListAction` を検索する。

### HTTPルート名とパス（コード探索用・旧入口節より退避）

- `admin_order_print_stack_window` … `POST` … `/{admin_route}/order/print/stack/window`（子ウィンドウ用の薄いページをHTMLで返す。`ids[]` と `_token` を一覧の一括フォームからPOSTする前提）
- `admin_order_print_stack` … `POST` … `/{admin_route}/order/print/stack`（AJAXによる印刷予約処理。`_token` を検証し、配送ID群から受注を解決してDB更新し、JSONで結果メッセージを返す）
