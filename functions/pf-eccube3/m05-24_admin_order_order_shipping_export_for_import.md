# 受注管理 — 出荷実績入力用CSV出力

## 概要

「出荷実績インポート登録」で取り込むCSVと同一の日本語ヘッダ列を持つファイルを、管理画面からダウンロード応答で返す機能である。画面ラベルは翻訳キー`admin.order.shipping_export_for_import`で「出荷実績入力用CSVダウンロード」となる。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。ソース上の確認値はSymfonyルート、`src/Eccube/Controller/Admin/Order/OrderCsvController.php`の送信先処理、`src/Eccube/Service/Csv/OrderCsv.php`、`src/Eccube/Repository/OrderRepository.php`の出荷実績用CSV検索、`src/Eccube/Resource/template/admin/ShippingStandby/edit.twig`のボタンとフォーム送信とする。

対象はブラウザ経由の管理画面に限定する。

本機能のカスタマイズ区分は現行踏襲であり、画面挙動と処理フローは現行リポ pf-eccube3 の実装を確認値とし、永続化に関わるテーブル・列の記述は ec-cube-enterprise を正とする。

コントローラの公開関数一覧は本文の主題としない。本文ではルートbind名やSymfonyのルートnameの網羅は主説明としない。「利用者視点の入口」にHTTPメソッドとサイトルートからのパスパターンを書く。コード探索でbind名が必要なときだけ「調査補助」へ書く。

## リニューアル移行時の扱い

DB関連の記述は ec-cube-enterprise を正とする。CSV生成が参照する永続化先のうち、注文の郵便番号の保持方式に現行と移行先で差がある。

| 観点 | 現行（pf-eccube3） | 移行先（ec-cube-enterprise） |
|------|--------------------|------------------------------|
| 受注本体 | `dtb_order` | 同一テーブル。郵便番号列の構成のみ後述のとおり異なる。 |
| 注文の郵便番号 | `dtb_order` が `zip01`（3桁）・`zip02`（4桁）の2列で保持 | `dtb_order.postal_code`（単一列、最大8桁）に統合。先頭3桁・残り4桁への分割はエンティティの取得補助で行う。CSVヘッダは引き続き2列分を出力する。 |
| 配送 | `dtb_shipping`（INNER JOIN のため配送が無い注文は出力対象外） | 同一スキーマ。 |
| 配送先FAX | 専用列なし。CSVでは空文字で補完 | 同一。移行先にも配送先FAX列は無く、空文字補完の前提は変わらない。 |

CSVのヘッダ列順・日時書式（`Y/m/d H:i:s`）・エンコーディング設定は永続化スキーマではなく出力仕様であり、本節の差分管理対象としない。

## 処理フロー

### CSVをダウンロードする（`admin_order_export_for_input`、`exportForInput`）

1. 管理画面の認証・共通制約を通過する。
2. `set_time_limit(0)`でPHPの実行時間制限を無効にする。
3. Doctrineの設定からSQLログ出力を無効にする確認値となる。
4. `order_ids`を配列として取得する。PHP配列でない、または空のときフラッシュへ`admin.common.select`を載せ、`Referer`が空で無ければそこへ、空ならルート名`admin_order`へリダイレクトする。
5. キー一覧を整数IDの並びとして解釈し、出荷実績用CSV生成関数へ渡す。
6. 返却データが論理偽となるとき実行時論外メッセージを投げる。そのメッセージは翻訳キー`admin.csv.error.export.not_registered`であり、標準ロケール下の日本語文言は文言上カード領域向けであり受注一覧からは転用読みとなる（実装確認値）。
7. 論外を捕まえた場合はフラッシュへメッセージを載せ、同様に`Referer`または`admin_order`へリダイレクトする。
8. 成功経路では`StreamedResponse`を返す。コールバック内で`CsvExportService`を開く。
9. ヘッダ行として、ヘッダ定数の連想キー配列について`array_keys`の順で1行書く。
10. クエリ結果の各行について、そのまま`fputcsv`へ渡す。 DoctrineのDateTime項目はクエリ関数内で事前に`'Y/m/d H:i:s'`形式へ書式化済みとなる。
11. ストリームを閉じる。
12. ファイル名は接頭辞`order_`、`YmdHis`桁そろえ日時、拡張子`.csv`を連結する実装関数を用いる（受注一覧向け自動命名と接頭辞と形式が字面で同一規則である確認値）。
13. 応答ヘッダに`Content-Type: text/csv;charset=<出力エンコーディング>`と`Content-Disposition: attachment; filename=…`を付与する。`<出力エンコーディング>`は設定`eccube_csv_export_encoding`がSJIS系と判定される場合のラベルを`windows-31j`に寄せたりそうでない場合そのまま読む処理である。
14. ストリーム返却の手前で情報ログに「CSV出力ファイル名」とファイル名を記録する。

## 集計条件

本機能は金額集計をしない。結果行数および列値は検索関数の結合規則に従う。

| 指標 | 集計の要点 |
|------|-------------|
| 出力対象受注集合 | POSTで送られた内部IDのみ。セッションの受注検索条件とは無関係である。 |
| 受注単位での最大行数 | 受注に対し配送（`dtb_shipping`に相当するORM結合対象）と配送時間の組が複数ありうるとき、`GROUP BY`句に配送側の識別に足りない列が並ばない構造のため、同一受注で複数配送があるケースでもSQLエンジン実装およびデータの状態によって複数結果行が並ぶ結果になりうる。完全な一意性の保証はクエリのみからは断定しない。 |
| DBから結果ゼロ | 関数が空とみなされる配列または偽値を返したとき、このコントローラ経路では上記論外となる。すべての指定IDが顧客未紐付け・配送無しなどでクエリ結果に現れなかった場合に該当しうる。 |

## 業務ルール・計算

| 項目 | 内容 |
|------|------|
| ヘッダ列順 | アップロード側と整合する連想キー並び順（日本語項目名）はルータファイル側のヘッダ定数に固定される。 |
| 日時フォーマット | Doctrine結果に含まれる日時項目は関数内書式化により`OrderRepository::CSV_DATE_FORMAT`の確認値`'Y/m/d H:i:s'`へそろえる。 |
| 顧客郵便番号 | DBは単一桁列の確認値であり、関数内で先頭3桁・残り4桁に`SUBSTRING`分割して2列出力する実装である。 |
| 配送先FAX | DB列が無い確認値であり、関数内では空文字3列として埋める。 |
| 文字コード | `CsvExportService`のコールバックで、セルごとに`eccube_csv_export_encoding`へ向けて`mb_convert_encoding`する。UTF-8系と判定されるときのみ先頭BOMを付与するfopen処理である。 |
| 区切り・囲み | `eccube_csv_export_separator`、`fputcsv`のエスケープはバックスラッシュ、囲みは二重引用符が確認値である。 |

本機能では画面フォーム入力をサーバへ永続化しないため、`### 入力項目`の表は置かない。

### エッジケース

| ケース | 扱い |
|--------|------|
| 選択IDリストが論理欠損または空 | フラッシュ`admin.common.select`相当を載せ、`Referer`または`admin_order`へリダイレクト。 |
| クエリ関数が論理偽のデータ集合を返す | 転用読みとなる翻訳メッセージを載せて実行時論外となり、その後フラッシュ処理とリダイレクト。 |
| GETで`/order/export/order`へ入るが本ルート名では無いとき | Symfonyのマッチは受注dtb_csv系CSVが優先される（GETのみのルートが選ばれた確認環境がある）。セッション検索状態に応じて受注明細粒度の項目定義ファイルが生成される。この取得経路によるファイルは受注一覧用の出力であり、固定ヘッダの出荷実績入力用CSVではない。 |
| 画面上の一覧フォームがCSRF用hidden無しであること | Twig断片のみでは共通トークンを確認できなかった。送信が拒否されるかはSymfony全体の構成に従う。 |

## データ整合性

| 観点 | 内容 |
|------|------|
| 一覧との一致 | 受注一覧の検索状態や並び順とは無関係に、`order_ids`に含まれたIDのみをSQLへ渡す。 |
| アップロード形式との対応 | ヘッダ定数および列順はインポート実装側のチェック関数と共通のソース定数であり、両者は同一ソースで更新されることが前提となる。一方でSQLが返す列セットはDoctrineの結果キー並びであり、クエリ側の並び変更で列ズレするリスクがあるため、両ファイルの並び確認が運用上の論点となる。 |
| DBの更新 | 読み取りのみ。インポート登録とは別機能。 |

## DBカラム

当機能はリポジトリの選択子一覧に応じ、`dtb_order`を中心とし会員情報・決済情報・状態マスタ・配送・都道府県・配送時間帯など多数のJOINに触れる。

| テーブル | 列または関係のメモ |
|---------|---------------------|
| `dtb_order` | 注文番号、計上金額系、関連日時、送り状番号内部保持列など結果に露出する項目がある。詳細な列リストは関数の選択子およびスキーマを正とする。 |
| 会員系 | INNER JOINとなるため結果に現れず、関数が空になりうる。 |
| 配送系（`dtb_shipping`相当） | INNER JOINとなるため無い注文は出力から落ちうることをリバース側で押さえる価値がある。 |

### DB操作

本機能は参照系（検索・出力）であり、DBへの登録・更新・削除は行わない。テーブル名は ec-cube-enterprise を正典とする。

| 操作種別 | 対象テーブル | 契機・条件 |
|---------|--------------|------------|
| 検索 | dtb_order / dtb_shipping | 検索条件に合致するレコードを抽出する。抽出結果を所定フォーマットでファイル出力する。 |
