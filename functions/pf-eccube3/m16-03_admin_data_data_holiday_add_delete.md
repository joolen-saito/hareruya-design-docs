# データ管理 — 祝日の追加・削除

## 概要

HareruyaEc プラグインが管理画面「データ管理」配下に提供する「祝日管理」画面において、`mtb_holiday` に祝日を1件追加したり、一覧から1件削除したりする機能である。同一画面には日本の祝日カレンダーライブラリから期間指定でまとめて登録する処理もあるが、本書では手入力による新規追加と削除を主題とし、一括読込の詳細フローは対象外とする。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。カスタマイズ区分は「現行踏襲」。画面・挙動は pf-eccube3 配下の HareruyaEc プラグインのソースを確認値とし、DB関連（テーブル・列・型・制約・関連）は ec-cube-enterprise の実装を正とする。

対象はブラウザ経由の管理画面に限定する。

本文ではコントローラのメソッド単位の解剖を主題としない。本文ではルートbind名やSymfonyのルートnameの網羅は主説明としない。「利用者視点の入口」にHTTPメソッドとサイトルートからのパスパターンを書く。コード探索でbind名が必要なときだけ「調査補助」へ書く。

## リニューアル移行時の扱い

- 本機能の DB は現行（pf-eccube3 の HareruyaEc プラグイン）と移行先（ec-cube-enterprise コア）で同一スキーマである。`mtb_holiday`（`id` / `date` / `name`(VARCHAR(64), NULL可)）のテーブル名・列名・型は一致するため、DB記述はそのまま移行先の正とする。
- 祝日と催事の関連は、両リポとも `mtb_holiday` から催事テーブルへの直接FKは持たず、`dtb_event_detail.holiday_flg`（BOOLEAN）で表す。本機能の追加・削除時に同日の催事明細の `holiday_flg` を更新する副作用も移行先で同等。
- 画面・挙動は現行（pf-eccube3）の確認値。移行先では祝日管理がコア（管理画面「データ」配下）に存在する。現行はプラグイン提供、移行先はコア提供である。
- 現行と移行先でスキーマ差は確認されていない。差が生じた場合のみ本節に追記する。

## 利用者視点の入口

| 入口 | URLエンドポイント | 期待されるふるまい |

| 追加フォームで「追加」を押す | `POST /{admin_route}/holiday/add` | フォーム名に紐づく CSRF と入力検証を通過し、同一日付の既存行が無ければ insert され成功メッセージの後に一覧へ GET リダイレクトされる。検証失敗時は失敗メッセージのみで一覧へリダイレクトされ、フィールドエラー再表示はしない。同一日付が既登録なら重複エラーメッセージで一覧へリダイレクトされる。 |

| CSRF が無効な追加送信 | `POST /{admin_route}/holiday/add` | アクセス拒否（HTTP 403）が投げられる共通実装である。 |
| CSRF が無効な削除送信 | `POST /{admin_route}/holiday/{id}/delete` | 同上。 |
| 期間内の公的祝日を一括登録する（本書では詳細を扱わない）。 | `POST /{admin_route}/holiday/load` | 期間内の公的祝日を一括登録する（本書では詳細を扱わない）。 |

## 処理フロー

### 一覧を表示する（GET `admin_holiday_list`）

1. 管理画面の認証・共通制約を通過する。
2. 追加用フォームビルダと一括読込用フォームビルダを名前だけから生成しビューを用意する（一覧描画時点ではリクエストをバインドしない）。
3. 祝日マスタを日付昇順で全件取得する。
4. Twig で一覧・両フォームを描画する。

### 手入力で祝日を追加する（POST `admin_holiday_add`）

1. 管理画面の認証・共通制約を通過する。
2. 追加フォームを生成しリクエストでバインドする。
3. 共通トレイトにより、フォーム名に対応する CSRF トークンを検証する。成功時はトークンを更新する。
4. Symfony の検証が失敗した場合、管理画面向けエラー鍵 `admin.register.failed` を積み、一覧ルートへ HTTP リダイレクトする（同一レスポンス内でのフィールドエラー表示はしない）。
5. 送信された日付と同一の日付を持つ行を検索し、1件でもあればプラグイン定義メッセージ鍵 `hareruyaec.holiday.overlap` を積み、一覧へリダイレクトする。保存はしない。
6. 重複が無ければ新規行を組み立て、日付・名称をセットして永続化し、成功鍵 `admin.register.complete` を積む。
7. その日の開始時刻がイベント詳細の開始日時と同日スパンに入る全行について、祝日フラグをオンに更新し、行ごとに永続化処理を呼ぶ実装である。
8. 一覧ルートへ HTTP リダイレクトする。

### 一覧から祝日を削除する（POST `admin_holiday_delete`）

1. 管理画面の認証・共通制約を通過する。
2. フォーム無しの経路で共通 CSRF トークンを検証する（フォーム名ではなくアプリケーション共通のトークン鍵）。成功時はトークンを更新する。
3. URL の数値 ID に対応する行を取得する。無ければアプリケーションエラー応答となる記述がある。
4. 行を削除してフラッシュし、成功鍵 `admin.delete.complete` を積む。
5. 削除した行の日付について、イベント詳細リポジトリが「その暦日に開始する詳細」を検索する条件で該当行を取得し、各行の祝日フラグをオフにして永続化する実装である（詳細は複数回フラッシュされる）。
6. 一覧ルートへ HTTP リダイレクトする。

## 業務ルール・計算

本機能では金額計算や複合スコアリングを行わない。

### 入力項目（手入力による追加のみ）

追加フォームは初期表示では DOM 上非表示でも、一覧 GET 時にトークン付きで生成される。

| 項目名 | 必須／任意 | 最大長 | 初期値 | 保存先・扱い |
|--------|------------|--------|--------|----------------|
| 祝日名 | 必須 | 64 文字（ウィジェット `maxlength` および Symfony Length max と一致） | 空（プレースホルダ「名称」） | `mtb_holiday.name`。NotBlank、最大 64。 |
| 日付 | 必須 | 単一行日付入力、`yyyy-MM-dd` | 空の単一行フィールド | `mtb_holiday.date`。Symfony の date 型、`datetime` 入力、`single_text`。フォームに Symfony の Length は無いが DB は date 型列である。 |

補足: 日付が同一の行が既に存在する場合、追加は拒否されプラグインの重複メッセージが表示される。

### エッジケース

| ケース | 扱い |
|--------|------|
| 同一日付が既に登録済み | 新規追加は保存せず重複エラーで一覧へリダイレクトする。 |
| 追加フォームの検証エラー（名称未入力、長さ超過など） | `admin.register.failed` で一覧へリダイレクトする。入力値の再提示はしない。 |
| 削除対象 ID が存在しない | ソース上は一覧更新前にエラー応答となる分岐がある。 |
| 同日にイベント詳細が無い | 祝日フラグ追随ループは対象ゼロであり、イベント詳細テーブルへの書き込みは発生しない。 |

## データ整合性

| 観点 | 内容 |
|------|------|
| 一覧とマスタ | 一覧は常に `mtb_holiday` の現在状態を日付昇順で読む。追加・削除の直後はリダイレクト GET で再読込される。 |
| 祝日マスタとイベント詳細フラグ | 追加時は同日開始のイベント詳細へ祝日フラグオンを書き込む。削除時はオフにする。イベント開始日時が別日へ変更済みであれば、その変更結果とフラグの整合は別機能の保存処理に依存する。 |
| トランザクション | 祝日の flush とイベント詳細の複数 flush が別単位である。途中失敗時の原子性はフレームワーク既定と DB 設定に依存し、本書では個別トランザクション境界までを確認値とする。 |

## DBカラム

| テーブル | 列 | メモ |
|---------|-----|------|
| `mtb_holiday` | `id` | 自動採番主キー。 |
| `mtb_holiday` | `date` | 必須。date 型。 |
| `mtb_holiday` | `name` | 可変長 64、スキーマ上は nullable だが追加フォームでは必須検証により空は通さない。 |
| `dtb_event_detail` | `holiday_flg` | 祝日追加・削除の副作用で更新されうる。 |

### DB操作

永続化の正は ec-cube-enterprise（テーブル名・操作は ec-cube-enterprise を正典）。当ドメインは承認ワークフローを介さず persist/flush で直接確定する（承認ワークフローは在庫機能固有）。

| 操作種別 | 対象テーブル | 契機・条件 |
|---------|--------------|------------|
| 登録/更新 | dtb_event_detail / mtb_holiday | 当機能が行う登録・更新で対象テーブルを直接保存する（不要な削除は含まない）。確定は persist/flush による即時反映。DB=ec-cube-enterprise を正典とする。 |

### HTTPルート名とパス（コード探索用・旧入口節より退避）

- `admin_holiday_list` … `GET` … `/{admin_route}/holiday`（祝日一覧・新規追加フォーム（初期非表示）・期間指定の一括読込フォーム・各行の削除リンクを表示する。）
- `admin_holiday_add` … `POST` … `/{admin_route}/holiday/add`（手入力による祝日1件の追加。検証・重複チェック後に永続化し一覧へリダイレクトする。）
- `admin_holiday_delete` … `POST（削除リンク経由）` … `/{admin_route}/holiday/{id}/delete`（指定 ID の祝日行を削除し、関連イベント詳細の祝日フラグをオフにして一覧へリダイレクトする。アンカーに付与された疑似 DELETE はフロント共通処理で POST に変換される想定である。）
- `admin_holiday_load` … `POST` … `/{admin_route}/holiday/load`（期間内の公的祝日を一括登録する（本書では詳細を扱わない）。）
