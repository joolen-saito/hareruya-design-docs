# データ管理 — 買取価格対応表（編集）

## 概要

HareruyaEc プラグインが管理画面「データ管理」配下で提供する、`mtb_buy_price_list` の一行を主キーで指定し、買取価格（円）のみを更新する編集機能である。利用者は一覧の金額セルから遷移し、識別情報（NM価格・カード状態・Foil／プロモ可否）は表示のみとし、入力・送信できるのは買取価格のみ。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。カスタマイズ区分は「現行踏襲」。画面・挙動は pf-eccube3 配下の HareruyaEc プラグインのソースを確認値とし、DB関連（テーブル・列・型・制約・関連）は ec-cube-enterprise の実装を正とする。本機能のマスタ `mtb_buy_price_list` は両リポで同一スキーマである。

一覧マトリクスの表示・並び・セル欠けは別紙「データ管理 — 買取価格対応表」（`m16-06_admin_data_data_buy_price_list.md`）を正とする。本書は `GET /{admin_route}/buy_price_list/{id}` と `POST /{admin_route}/buy_price_list/{id}` のふるまいに限定する。

対象はブラウザ経由の管理画面に限定する。

---

## リニューアル移行時の扱い

- 本機能の DB は現行（pf-eccube3 の HareruyaEc プラグイン）と移行先（ec-cube-enterprise コア）で同一スキーマである。`mtb_buy_price_list` のテーブル名・列名・型は一致し、編集対象列は買取価格（`price`）。DB記述はそのまま移行先の正とする。
- 画面・挙動は現行（pf-eccube3）の確認値。1行の買取価格のみを更新する編集機能は移行先でも同等で、現行はプラグイン提供、移行先はコア提供である。
- 現行と移行先でスキーマ差・挙動差は確認されていない。差が生じた場合のみ本節に追記する。

本文ではコントローラのメソッド単位の解剖を主題としない。本文ではルートbind名やSymfonyのルートnameの網羅は主説明としない。「利用者視点の入口」にHTTPメソッドとサイトルートからのパスパターンを書く。コード探索でbind名が必要なときだけ「調査補助」へ書く。

## 利用者視点の入口

| 入口 | URLエンドポイント | 期待されるふるまい |
|------|--------------------|--------------------|
| 一覧の金額セルを押す | `GET /{admin_route}/buy_price_list/{id}` | 当該行の識別情報が表で示され、買取価格が入力可能になる。「更新」「戻る」が表示される。 |
| 「更新」を押す | `POST /{admin_route}/buy_price_list/{id}` | 検証成功時は保存され成功メッセージの後に一覧へ移る。失敗時は同一編集画面が再表示される。 |
| 「戻る」を押す | `GET /{admin_route}/buy_price_list`（ボタンは `type="button"` のクライアント遷移） | 保存されない。一覧へ戻る。 |
| 存在しない `id` | `GET` または `POST …/buy_price_list/{id}` | 404。 |
| CSRF が無効な更新 | `POST …/buy_price_list/{id}` | アクセス拒否（HTTP 403）。 |

## フロント挙動

| 観点 | 内容 |
|------|------|
| 表示要素 | 画面タイトルは「買取価格対応表」、サブタイトルは「編集」。メニューは `menus = ['data_menu', 'buy_price_list']`。識別用に 1 行の表（列: NM価格、カード状態、Foil or Promotion Card?）。その下に Symfony の `form_row(form.price)` による買取価格欄。右カラムに「更新」（`type=submit`）と「戻る」（`type=button`）。 |

## 処理フロー

### 編集画面を表示する（GET `admin_buy_price_list_edit`）

1. 管理画面の認証・共通制約を通過する。
2. パス `id` が欠ける、または主キーに一致する行が無ければ 404 応答とする。
3. 当該行エンティティをデータとし、フォーム種別名 `admin_buy_price_list` でフォームを生成する（マッピングされるのは `price` のみである）。
4. `conditions` にカード状態マスタの `findAllCode` 結果（識別子昇順で構築された `id => code`）を渡す。
5. Twig でフォームを描画する。`form` の `action` は `admin_buy_price_list_update` に `id` を渡した URL である。

### 買取価格を保存する（POST `admin_buy_price_list_update`）

1. 管理画面の認証・共通制約を通過する。
2. パス `id` が欠ける、または主キーに一致する行が無ければ 404 応答とする。
3. 同一行エンティティでフォームを生成し、`handleRequest` で POST を束ねる。
4. 共通トレイトにより、フォーム名に紐づく CSRF トークンを検証する。成功時はトークンを更新する。失敗時はアクセス拒否（HTTP 403）となる。
5. フォームが妥当でなければ、同一編集テンプレートを再表示する（`conditions` を再取得して渡す）。成功時のフラッシュは積まない。
6. 妥当なら ORM で `persist` と `flush` を行う（単一行）。業務上の再計算や他表の連鎖更新は行わない。
7. 成功メッセージ鍵 `admin.register.complete` を積む（日本語環境の確認値は「登録が完了しました。」）。
8. `GET /{admin_route}/buy_price_list` へ HTTP リダイレクトする。

---

## フォーム送信時の判定順序

| 順序 | 判定 | 結果 |
|------|------|------|
| 1 | 主キー `id` に行が存在するか | 無ければ 404。 |
| 2 | CSRF トークンが有効か | 無効なら HTTP 403。 |
| 3 | フォーム（必須の数値項目など）が妥当か | 否なら編集 HTML を 200 で返す。 |
| 4 | 上記をすべて満たす | DB を更新し、成功フラッシュを積んで一覧へリダイレクト。 |

## 業務ルール・計算

利用者が送信した `price` を、そのまま `mtb_buy_price_list.price` に書き込む。NM価格帯や割合による自動再計算は行わない。`nm_price`、`card_condition_id`、`special_flg` は本画面では更新対象に含めない（フォームにも出さないため POST で上書きされない）。

### 入力項目

| 項目名 | 必須／任意 | 最大長 | 初期値 | 保存先・扱い |
|--------|------------|--------|--------|----------------|
| 買取価格(円) | 必須 | フォームに Symfony `Length` 等の桁上限は無い。DB は `mtb_buy_price_list.price` の符号なし整数（実装を確認値とする）。プラグイン `config.yml` の商品規格 `buy_price` 桁数 9 は運用上の目安であり、本フォームに直結した制約ではない。 | 当該行の現行 `price` | `mtb_buy_price_list.price`。ウィジェット種別は `number`。`admin_buy_price_list[price]` として POST される。 |

### エッジケース

| ケース | 扱い |
|--------|------|
| 二つの利用者が同一 `id` を編集 | 楽観ロックは無い。後に `flush` した更新が残る。 |
| ブラウザの戻るで古いフォームを再送信 | 同一主キーに対する通常の POST 更新として処理される（重複送信の抑止は本機能固有には無い）。 |

## DBカラム

編集で変更し得る列と、表示のみの列は次のとおり。

| テーブル | 列 | メモ |
|---------|-----|------|
| `mtb_buy_price_list` | `price` | POST 成功時に更新する。 |
| `mtb_buy_price_list` | `id` | URL で指定。更新対象の特定にのみ用いる。 |
| `mtb_buy_price_list` | `nm_price` | 編集画面では表示のみ。 |
| `mtb_buy_price_list` | `card_condition_id` | 編集画面では `conditions` 経由の表示のみ。 |
| `mtb_buy_price_list` | `special_flg` | 編集画面では YES/NO 表示のみ。 |

### DB操作

永続化の正は ec-cube-enterprise（テーブル名・操作は ec-cube-enterprise を正典）。当ドメインは承認ワークフローを介さず persist/flush で直接確定する（承認ワークフローは在庫機能固有）。

| 操作種別 | 対象テーブル | 契機・条件 |
|---------|--------------|------------|
| 登録/更新 | mtb_buy_price_list | 当機能が行う登録・更新で対象テーブルを直接保存する（不要な削除は含まない）。確定は persist/flush による即時反映。DB=ec-cube-enterprise を正典とする。 |
