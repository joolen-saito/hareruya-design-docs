# m05-27_admin_order_order_waiting_tag（管理画面_受注管理_店頭注文番号札管理）

## 概要

管理画面の「受注管理」配下で、店頭向けモニター等に掲出する英字の「注文番号札」を店舗単位で登録・一覧表示・削除する機能である。ナビゲーションの翻訳キー `admin.order.waiting_tag` では「店頭注文番号札管理」と表示される。一覧に載る整理番号（数字）やフロントの呼び出しAPIとは別テーブルである。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。ec-cube-enterprise のコア実装を確認値とする。

本機能のカスタマイズ区分はカスタマイズであり、画面挙動は現行（pf-eccube3）を踏襲しつつ、本書の挙動確認値および永続化に関わるテーブル・列の記述は ec-cube-enterprise を正とする。

対象はブラウザ経由の管理画面に限定する。

コントローラのメソッド名は本文の主題としない。本文ではルートbind名やSymfonyのルートnameの網羅は主説明としない。「利用者視点の入口」にHTTPメソッドとサイトルートからのパスパターンを書く。コード探索でbind名が必要なときだけ「調査補助」へ書く。

## 処理フロー

### 一覧・フォームを表示する（GET `m05-27_admin_order_order_waiting_tag`）

1. 管理画面の認証・共通制約を通過する。
2. 新規用の `dtb_waiting_tag` 行を組み立て、ログイン管理者の店舗を `base_info_id` にセットする。
3. 店頭注文番号札用のフォーム種別でフォームを生成する。
4. `dtb_waiting_tag` を `BaseInfo` がフォームの店舗になっている行だけ昇順ソート指定なしで取得し、テンプレートへ渡す（実装は `findBy(['BaseInfo' => $BaseInfo])`。順序は実装依存）。
5. `BaseInfo` は常にログイン店舗としてテンプレートへ渡す（削除ボタン表示の比較用）。

### 店名だけを切り替える（POST `m05-27_admin_order_order_waiting_tag`）

1. フォームにリクエストを bind する。
2. bind 後のエンティティから店舗を読み、一覧の検索キーに使う。
3. コメントどおり検証エラー表示を避けるため、同一エンティティを載せた新しいフォームインスタンスを生成し、画面へ渡す（この時点では `handleRequest` しない）。
4. 一覧・ログイン店舗の渡し方は GET と同型である。

### 新規登録する（POST `m05-27_admin_order_order_waiting_tag_store`）

1. 店頭注文番号札用のフォーム種別でデータ無しからフォームを作り、リクエストを処理する。
2. 未送信または検証失敗のとき、翻訳キー `admin.register.failed` をエラーフラッシュに積み、同一テンプレートを応答本文付きで描画する（リダイレクトしない）。
3. 検証成功のとき、登録処理をトランザクション内で実行する。
4. 登録処理は次を行う。既に同一 `waiting_tag` 文字列の行が任意の店舗について存在する場合、翻訳キー `admin.order.waiting_tag.already_exists` のメッセージを例外として投げる（クエリは `waiting_tag` のみで絞り、`base_info_id` は条件に含めない。ソースコメントは同一店舗と書くが、実装は店舗横断で一意に近い挙動である）。
5. 問題なければ `persist` と `flush`、コミットする。
6. 例外時はロールバックし、例外メッセージをエラーフラッシュに積み、手順 2 と同様にテンプレートを描画する。
7. 成功時は翻訳キー `admin.register.complete` を成功フラッシュに積み、`m05-27_admin_order_order_waiting_tag` へリダイレクトする。

### 削除する（DELETE `m05-27_admin_order_order_waiting_tag_delete`）

1. CSRF 検証を行う（親クラスのトークン検証）。
2. パス変数の ID で `dtb_waiting_tag` を解決する（該当なしはフレームワークの扱いに従う）。
3. 削除処理をトランザクション内で実行する。
4. 削除処理は次を行う。`waiting_tag` 文字列が一致する行が見つからない場合、翻訳キー `admin.order.waiting_tag.not_found` を例外として投げる（こちらも `base_info_id` は条件に含めない）。
5. リポジトリの `delete` と `flush`、コミットする。
6. 例外時はロールバックし、翻訳キー `admin.common.delete_error` をエラーフラッシュに積む。
7. 成否にかかわらず `m05-27_admin_order_order_waiting_tag` へリダイレクトする。成功専用フラッシュはない。

## 業務ルール・計算

| 項目 | 内容 |
|------|------|
| 登録可否 | `waiting_tag` 文字列について `dtb_waiting_tag` を店舗条件なしで検索し、1 件でもあれば登録拒否する（メッセージキー `admin.order.waiting_tag.already_exists`）。コメントは同一店舗と読めるが、クエリは `waiting_tag` のみである。 |
| 削除前確認 | 削除処理も `waiting_tag` のみで存在確認し、無ければ `admin.order.waiting_tag.not_found` で失敗する。 |
| 売上・件数集計 | 行わない。 |

### 入力項目

| 項目名 | 必須／任意 | 最大長 | 初期値 | 保存先・扱い |
|--------|------------|--------|--------|----------------|
| 店名 | 必須 | — | 一覧の対象店（GET 時はログイン店舗に紐づく新規エンティティの店） | `dtb_waiting_tag.base_info_id`（店舗エンティティ関連）。プルダウンは店舗一覧から単一選択、`choice_label` は店舗名。 |
| 店頭注文番号札 | 必須 | 10 文字 | 空に近い状態から入力 | `dtb_waiting_tag.waiting_tag`。正規表現は `/^[a-zA-Z]+$/` のみ（数字不可）。違反時メッセージキー `admin.order.waiting_tag.regex_error`。長さ上限はフォーム種別内の数値と DB 列長 10 が一致する。`constant.yml.dist` の長さ定義とは連動しない。 |

### エッジケース

| ケース | 扱い |
|--------|------|
| 英字以外・数字のみ・記号混入 | 検証エラー。メッセージは正規表現違反または長さ。 |
| 11 文字以上 | `Length` で不正。 |
| 既に別店舗が同じ `waiting_tag` を保持 | 登録処理が `admin.order.waiting_tag.already_exists` で失敗し、同一画面にエラーフラッシュ。 |
| 削除対象 ID が存在しない | ルート解決段階でエラーになりうる（フレームワークの確認値）。 |
| ログイン店舗以外の店を一覧で見ている | 行は表示されるが、「削除」と「登録」ボタンはログイン店舗選択時のみ活性に見える実装である（テンプレートの `BaseInfo.id` 比較）。DELETE はコントローラ側でログイン店舗との一致を強制しないため、到達可能性は権限設計に依存する。 |

## 排他制御・トランザクション

| 観点 | 内容 |
|------|------|
| トランザクション境界 | 明示的なトランザクション境界が実装にある場合は処理フローの保存処理を正とする。明示境界が無い更新はフォーム処理またはCSV取込後の永続化処理と`flush`単位で確定する。 |
| ロック | 行ロック・悲観ロック・楽観ロック・ロックファイルを使用しない。競合時は後から確定した更新が残る。 |
| 例外時 | 検証エラーまたは保存前の例外では対象更新を確定しない。保存処理中の例外はエラー処理の節を正とし、未確定の永続化対象はロールバックまたは未flushのまま確定しない。 |
