# m07-02_admin_online_purchase_purchase_online_old_goods_ledger_csv_export（管理画面_ネット買取管理_古物台帳入力用CSV出力）

## 概要

管理画面の「ネット買取管理」買取一覧または買取詳細（編集）から、選択した買取注文IDを対象に、古物台帳入力用として固定レイアウトのCSVファイルをダウンロード応答として返す機能である。一覧のドロップダウン項目の翻訳キーは`admin.purchase.online.btn.csvexport`であり、文言は「古物台帳入力用CSV」と表示される。店頭買取向けの同名ラベル（別ルート・別クエリ）とはデータ源が異なる。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。テンプレート注釈で示された移植元はpf-eccube3プラグインであるが、本書の確認値はec-cube-enterpriseのコア実装とする。

本機能のカスタマイズ区分はカスタマイズである。現行挙動は現行リポ（pf-eccube3のHareruyaEcプラグイン）を出自とし、リニューアル後はec-cube-enterpriseのコア実装へ移載される。挙動の確認値はec-cube-enterpriseのコア実装とし、DB関連の記述（テーブル名・列名・整合）はec-cube-enterpriseを正とする。本機能はCSV出力のみでDB更新を行わない。

対象はブラウザ経由の管理画面に限定する。

コントローラのメソッド名は本文の主題としない。本文ではルートbind名やSymfonyのルートnameの網羅は主説明としない。「利用者視点の入口」にHTTPメソッドとサイトルートからのパスパターンを書く。コード探索でbind名が必要なときだけ「調査補助」へ書く。

## 処理フロー

### CSVをダウンロードする（POST `admin_purchase_csv_export`）

1. 管理画面の認証・共通制約を通過する。
2. PHPの実行時間制限を無効にする（`set_time_limit(0)`）。
3. リクエストボディから`buyOrderIds`をすべて取得し、各要素を`intval`したうえで`array_filter`により0を除き、配列として扱う。
4. 手順3の配列が空である場合、翻訳キー`admin.purchase.online.csv_export.no_selection`のエラーをフラッシュに積み、セッションキー`eccube.admin.purchase.search.page_no`（無ければ実装上は1扱い）へ相当する買取一覧ページへHTTPリダイレクトする。
5. 買取注文リポジトリで、IDが手順3の集合に含まれる買取注文を取得し、`id`昇順で並べる。
6. 手順5の結果が空配列である場合、`RuntimeException`としメッセージは`admin.purchase.online.csv_export.not_registered_buy_order_id`のキー文字列とする。コントローラはこれを翻訳してフラッシュに積み、手順4と同様に買取一覧へリダイレクトする。
7. 手順3で渡されたIDのうちDBに存在しないIDは手順5の結果に現れない。少なくとも1件でも存在すれば手順6には至らない（存在しないIDは黙ってスキップされる）。
8. 同じリポジトリで、点数と前回利用日を買取注文ID単位に取得する。別クエリで、出力対象の買取注文に含まれる会員について、利用回数などの行を取得する（会員はプレイヤー経由で本人確認ステータスと結合される）。
9. サービス層で行配列を組み立てる。ヘッダはコード内の連想配列`CSV_HEADER`の値（日本語ラベル）をキー順に出力する。データ行は内部キー順にヘッダと揃える。
10. `StreamedResponse`のコールバック内で共通のCSVエクスポートサービスを開く。UTF-8設定のときはBOMを書く。各行を`mb_convert_encoding`により設定`eccube_csv_export_encoding`へ変換し、`eccube_csv_export_separator`と二重引用符・エスケープ規則で`fputcsv`相当の書き込みを行い、閉じる。
11. ファイル名は接頭辞`purchase_`と、リクエストに含まれた買取注文IDの最小値を7桁ゼロ埋めした番号と、アンダースコア、日時`YmdHis`、拡張子`.csv`を連結したものとする。
12. 応答の`Content-Type`は`application/octet-stream`とし、`Content-Disposition`は`attachment`で上記ファイル名を付与する。
13. ストリーム送信の完了扱いで情報ログに「古物台帳入力用CSV出力完了」とファイル名を記録する。

### 部分一致するIDのみが存在するとき

1. 手順7どおり、存在する買取注文だけが行になる。依頼したID本数とCSV行数は一致しない。

## POSTパラメータ（エクスポート要求）

本機能はブラウザフォームからのPOSTを受け取るが、店舗設定のCSV型定義（`dtb_csv`）で列を増減する方式ではない。よって「入力項目」表（5列）は置かず、送信パラメータのみ整理する。

| パラメータ | 必須 | 内容 |
|------------|------|------|
| `buyOrderIds` または `buyOrderIds[]` | 実質必須 | 整数配列。空またはすべてが0に正規化後に失われるとエラーフラッシュして一覧へ戻る。 |

詳細画面では編集フォームの他フィールドも同じPOSTに含まれる。エクスポート処理が読むのは`buyOrderIds`のみである。

## 集計条件

### 点数（列「点数」）

- `dtb_buy_main_card`に紐づく当該買取注文の`count`合計に、`dtb_buy_order_indivisual_input_product`の`quantity`合計を加える。
- いずれの明細もない買取注文は0となる。

### 前回利用日（列「前回利用日」）

- 同一会員・同一`dtb_buy_order`について、`order_date`が当該行より厳密に早い買取注文のうち、最大の`order_date`を取る。
- 該当が無いときは空（サービス層ではNULL相当が空文字に落ちる）。
- 書式は`Y/m/d`の文字列。

### 利用回数（列「利用回数」）

- リポジトリは、出力対象の買取注文IDに含まれる会員に限定しつつ、その会員に紐づく買取注文をカウントする（対象IDに限った件数ではなく、会員の累計件数）。
- 会員にプレイヤーがおらず結合できない場合、当該顧客キーは集計結果に現れず、CSV上は0となる。

## 出力列とデータの対応

ヘッダ行の並びは`CSV_HEADER`のキー定義順と同じである。データ行の内部キーは次の対応となる。固定文字列列はコード定数どおり出力する。

| CSV列名（ヘッダ） | データの由来・規則 |
|-------------------|---------------------|
| 日付 | 買取注文の`order_date`を`Y/m/d`とする。無い場合は空。 |
| 受注番号 | 買取注文の整数`id`。 |
| 氏名 | `last_name`と`first_name`を連結（間にスペースは入れない）。 |
| 住所 | 都道府県名・`addr01`・`addr02`をそれぞれ1つの半角スペースで区切り連結し、`addr03`が非NULLかつ非空なら末尾にそのまま連結する（`addr02`と`addr03`のあいだに余分なスペースは入れない）。 |
| 年齢 | 生年月日があれば、`date('Y')`の年と生年の差の整数。サーバの現在日付基準であり、申込日時点の年齢ではない。生年月日が無い場合は空。 |
| 職業 | 職業マスタの名称。無ければ空。 |
| 電話番号 | 買取注文の`tel_no`。無ければ空。 |
| 身分証 | 身分証種別マスタの名称。無ければ空。 |
| 点数 | 上記「点数」集計。 |
| 金額 | 査定合計など`totalPrice`を文字列化。NULLは空文字。 |
| 区別 | 固定文字列「買受」。 |
| 品目 | 固定文字列「トレーディングカード」。 |
| 特徴 | 固定文字列「マジック・ザ・ギャザリング」。 |
| 利用回数 | 上記「利用回数」集計。 |
| 前回利用日 | 上記「前回利用日」。値があるときは`Y/m/d`文字列。無いときは空。 |

内部キー名`identificaion`はソース上の綴りとする。CSVヘッダの日本語は「身分証」である。

## 業務ルール・計算

- 出力対象は画面・APIで確定した検索条件、権限、店舗・支店条件に一致するレコードに限定する。
- 金額・数量・日時・ステータスは参照時点の永続化済み値をそのまま出力し、CSV生成時に再計算・補正しない。
- 文字コード、列順、ヘッダ、空値表現は既存CSV仕様を正とし、該当値がない項目は空欄として扱う。
- 件数上限やページングの有無は呼び出し元の検索条件・既存実装に従い、出力途中で対象データが更新されても再読込による整合補正は行わない。

## データ整合性

- 一覧・詳細に表示される利用回数は、検索処理が同系のリポジトリメソッドで組み立てた値と一致し得るが、CSVは出力時点のDB状態で再計算する。
- 「金額」列は画面の「申込時買取金額合計」とは別フィールド（`totalPrice`系）をソースとする。画面表示の金額文字列と完全一致を保証しない（単位・フォーマット・揃えるフィールドが異なる）。

## リニューアル移行時の扱い

本機能固有のCookieやRemember Meは扱わない。セッションキー`eccube.admin.purchase.search.page_no`は実装の確認値である。

現行はpf-eccube3のHareruyaEcプラグインが買取関連テーブルとCSV組み立てを保持し、リニューアル後はec-cube-enterpriseのコアへ移載される。DB関連の記述はec-cube-enterpriseを正とする。

- 集計に用いる明細テーブルは、ec-cube-enterprise実装では選んで買取・まとめて買取が`dtb_buy_main_card`、個別入力が単数形`dtb_buy_order_indivisual_input_product`である。本書はこの名称で記す。
- 出力対象・列順・空値表現は既存CSV仕様を踏襲する。CSV出力はDBを更新しないため、移行に伴う論理削除/物理削除の差は本機能では生じない。
- 上記以外の買取関連テーブル・列について、現行プラグインと移行先コアの個別の差異は本書では網羅照合していない。差異が疑われる箇所はec-cube-enterprise実装を確認値とする。
