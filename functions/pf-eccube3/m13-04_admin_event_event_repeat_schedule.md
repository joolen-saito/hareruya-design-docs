# イベント管理 — 繰り返し日程登録

## 概要

管理画面で、登録済みのイベントに繰り返しの日程をまとめて登録する機能である。期間と曜日等を指定し、該当する日について日程を一括作成する。申込受付を有効にする場合は、イベントに支払い方法が設定されていることを前提とする。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。確認値はpf-eccube3（EC-CUBE3系）のHareruyaEcプラグインの管理画面繰り返し日程処理、繰り返し日程フォーム、イベント・日程を扱うリポジトリ、テンプレート（`Schedule/repeatschedule.twig`）、エラー文言を正とする。

カスタマイズ区分は現行踏襲であり、挙動の参照リポはpf-eccube3、DB関連の記述はec-cube-enterpriseを正とする。

対象はブラウザ経由の管理画面に限定する。

本文ではフレームワークのコントローラ型名やメソッド名を主説明としない。管理画面プレフィックスは環境により変わる（`admin_route`）。「利用者視点の入口」にHTTPメソッドとサイトルートからのパスパターンを書く。

- 期間・曜日指定に基づく日程の生成

## リニューアル移行時の扱い

現行（pf-eccube3）と移行先（ec-cube-enterprise）の差を記録する。DB関連はec-cube-enterpriseを正とする。繰り返し日程登録の挙動は現行（pf-eccube3）を正とする。

| 観点 | 現行（pf-eccube3） | 移行先（ec-cube-enterprise） |
|------|--------------------|------------------------------|
| 保存先テーブル | イベント詳細（`dtb_event_detail`） | 同名のテーブルを持つ。主キーは`id`（現行は`event_detail_id`）。一括作成は複数行を作成する。 |
| 申込受付フラグ | 日程の申込フラグ（`entry_flg`） | 同名の`entry_flg`（申込フラグ）。同一。 |
| 支払い方法の関連 | イベントの支払い方法（中間表`dtb_event_payment`） | 同名の中間表`dtb_event_payment`（`event_id`・`payment_id`）。申込受付有効化の前提確認に用いる。同一。 |
| 削除方式 | `deleted_at`による論理削除 | `deleted_at`による論理削除。双方とも論理削除で同一。 |

## 処理フロー

### 繰り返し日程を登録する（POST `/{admin_route}/event/repeatschedule/{eventId}/create`）

1. 管理画面の認証・権限を通過する。
2. パスのイベントIDでイベントを取得する。存在しない場合はページが見つからない扱い（404）とする。
3. 繰り返し日程フォームを検証する。検証に失敗した場合はエラーメッセージを表示して入力画面を再表示する。
4. 申込受付を有効にする指定で、当該イベントに支払い方法が設定されていない場合は、申込受付不可のエラーメッセージを表示して入力画面を再表示する。
5. チェックされた曜日を取得し、指定期間内の該当日について日程を一括作成する。

## 表示メッセージ

| 表示文言 | 表示条件 | 備考 |
|----------|----------|------|
| 保存失敗メッセージ（ロケールキー`admin.schedule.save.failed`） | 検証失敗時、または申込受付有効で支払い方法未設定のとき | 入力画面を再表示する |
| 支払い方法未設定の旨（ロケールキー`admin.schedule.error.payment.not.exists`） | 申込受付有効で支払い方法が未設定のとき | 申込受付不可 |
| M13-04-MSG-001 | 管理画面上部 | 不正なリクエストです。 |
| M13-04-MSG-002 | 管理画面上部 | 保存しました |
| M13-04-MSG-003 | 管理画面上部 | 保存に失敗しました |
| M13-04-MSG-004 | 入力項目直下/フォーム上部 | オンライン受付ありかつ参加費が有料の場合は、イベント編集画面で支払方法を設定してください。 |

## データ整合性

| 観点 | 内容 |
|------|------|
| 更新単位 | 登録・編集・削除の対象データは、フォーム送信またはCSV取込で検証を通過した単位で更新する。保存対象と副作用は処理フロー、入出力、DBカラムの各節を正とする。 |
| 再表示 | 保存成功後はDBに確定した値を次回表示・検索・出力の基準にする。検証エラーまたは例外時に確定しない入力値は再表示画面のフォーム値に留まる。 |
| 同時更新 | 明示的な楽観ロック・悲観ロックを持たない場合、同一データを複数管理者が同時に更新すると後から保存された内容が残る。 |

## DBカラム

機能に直接関係する列のみ記載する。型や一覧の細部はスキーマを参照する。

| テーブル | 列 | メモ |
|---------|-----|------|
| `dtb_event_detail` | `id`（現行: `event_detail_id`）、`event_id`、`start_date`、`entry_flg` | イベント詳細（日程）として該当日について一括作成する。`entry_flg`は申込受付状態。 |
| `dtb_event_payment` | `event_id`、`payment_id` | イベントに設定された支払い方法。申込受付有効化の前提確認に使用する。 |

### DB操作

永続化の正は ec-cube-enterprise（テーブル名・操作は ec-cube-enterprise を正典）。当ドメインは承認ワークフローを介さず persist/flush で直接確定する（承認ワークフローは在庫機能固有）。

| 操作種別 | 対象テーブル | 契機・条件 |
|---------|--------------|------------|
| 登録/更新 | dtb_event_detail / dtb_event_payment | 当機能が行う登録・更新で対象テーブルを直接保存する（不要な削除は含まない）。確定は persist/flush による即時反映。DB=ec-cube-enterprise を正典とする。 |

| エラー内容 | 処理 |
|------------|------|

| 申込受付有効で支払い方法未設定 | 申込受付不可のメッセージを表示し入力画面を再表示する。 |
