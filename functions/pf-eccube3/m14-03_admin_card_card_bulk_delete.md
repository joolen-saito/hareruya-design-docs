# カード管理 — 一括削除

## 概要

HareruyaEc プラグインが管理画面の「カード管理」検索一覧から、チェックボックスで選んだカードをまとめて削除する機能である。単一カードの削除（別ルートの DELETE）とは送信方法・ CSRF の載せ方が異なるが、削除可否の判定・関連商品規格の紐付け解除・子データの再帰削除・支店連携通知の流れは同一の処理本体を通る。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。pf-eccube3 に配置された HareruyaEc プラグインのソースを確認値とする。

本機能のカスタマイズ区分は現行踏襲である。現行挙動は pf-eccube3 の HareruyaEc プラグインを参照し、永続化に関わるテーブル名・列名などのDB関連は ec-cube-enterprise を正とする。

対象はブラウザ経由の管理画面に限定する。

コントローラのメソッド名は本文の主題としない。本文ではルートbind名やSymfonyのルートnameの網羅は主説明としない。「利用者視点の入口」にHTTPメソッドとサイトルートからのパスパターンを書く。コード探索でbind名が必要なときだけ「調査補助」へ書く。

## リニューアル移行時の扱い

DB関連の記述は ec-cube-enterprise の実装を正とする。削除対象のカードマスタ・カード詳細・デッキ採用行は現行と移行先で同一のテーブル名（`mtb_card`、`mtb_card_detail`、`dtb_deck_card`）だが、商品との紐付け先と削除可否判定に用いる商品の削除方式が異なる。

| 観点 | 現行（pf-eccube3） | 移行先（ec-cube-enterprise） |
|------|---------------------|-------------------------------|
| カード詳細と商品の紐付け列 | `dtb_product_sub.card_detail_id`（補助表 `dtb_product_sub` 経由） | `dtb_product.card_detail_id`（商品本体 `dtb_product` の列。補助表 `dtb_product_sub` は移行先に存在しない）。削除前の `NULL` 切り離しは移行先では `dtb_product.card_detail_id` を対象とする。 |
| 削除可否の商品判定 | 論理未削除（`dtb_product.del_flg = 0`）の商品がカード詳細経由で存在するか | 移行先の `dtb_product` は `del_flg` を持たず物理削除のため、紐付く商品行の存在有無で判定する（論理削除→物理削除）。 |
| デッキ採用判定 | `dtb_deck_card` | 同一スキーマ（`dtb_deck_card`）。 |
| カード本体・子の削除 | `mtb_card` ほか ORM 再帰削除 | 同一スキーマ。 |

削除のフロー・CSRF・支店通知の挙動は現行（pf-eccube3）を参照する。`dtb_product_sub` 経由の切り離しと `del_flg` 判定は移行先で上表のとおり読み替える。

## 利用者視点の入口

| 入口 | URLエンドポイント | 期待されるふるまい |
|------|--------------------|---------------------|
| 検索結果が 1 件以上あり、一覧でカードにチェックを入れ、「一括削除」を押して確認で OK | `POST /{admin_route}/card/delete` | 選択 ID 分の削除が順に試みられ、すべて通れば成功メッセージが付いたうえで検索一覧（またはカード一覧）へ戻る。 |
| 検索結果エリアが無い・件数ゼロ | （一括削除ボタンは描画されない） | 一覧のチェックボックスと一括削除ボタンが無いため、この入口からは実行できない。 |
| 検索結果はあるがチェックを付けずに「一括削除」を押す | `POST /{admin_route}/card/delete` | フラッシュ無しで一覧へリダイレクトする（ページ番号は後述のセッションキーがあればそのページ）。 |

同一 HTML フォームの既定 `action` は検索用の `POST /{admin_route}/card/search/1` であるが、「一括削除」ボタンは `formaction` で `m14-03_admin_card_card_bulk_delete` に差し替えて送信する。

| 観点 | 内容 |

## 処理フロー

### 一括削除を実行する（POST `m14-03_admin_card_card_bulk_delete`）

1. 管理画面の認証・共通制約を通過する。
2. リクエストボディの `_token` を、コア既定 ID（実装では `Constant::TOKEN_NAME` と一致する文字列）として CSRF プロバイダで検証する。無効ならアクセス拒否（HTTP 403）となる例外を投げる。成功時は同プロバイダでトークンを更新する。
3. セッションキー `admin.card.search.page_no` を読む（互換の別画面パスでは空のときがある）。
4. ルートパラメータで ID が無い一括経路では、ボディの `cardIds` を ID 群とみなす。`cardIds` がリクエストに存在しない（`null`）とき、フラッシュは付けず、`admin.card.search.page_no` が空でなければ `m14-01_admin_card_card_search` の当該ページへ、空なら `admin_card_list` へリダイレクトして終了する。
5. `cardIds` を先頭から順に走査する。要素が空文字相当、またはカードマスタが取得できないとき、HTTP 404 で打ち切る。
6. 各 ID について、デッキ採用行（`deckCards` の件数）が 1 件でもある、または「論理未削除の商品がカード詳細経由で存在する」ネイティブ問い合わせの件数が 1 以上のとき、削除ブロックとみなす。翻訳キー `admin.card.delete.failed` にカードの合成名を埋め込んだエラーメッセージをフラッシュし、この時点までに削除完了した ID だけを支店通知へ渡してから `Referer` へリダイレクトする。
7. ブロックされなければ、カード用レポジトリのネイティブ更新で、当該カードにぶら下がるカード詳細に結び付いていた商品規格の `card_detail_id` を NULL に切り離す（販売商品の親子構造は維持し、印刷版参照だけ外す）。
8. 汎用ヘルパの再帰削除で、Doctrine 上 oneToMany として子側へマッピングされたコレクションを深さ優先で `remove` し、最後に当該カードマスタを `remove` して `flush` する（ manyToMany はこの再帰の対象外。親エンティティ削除時の ORM の扱いはマッピングに従う）。
9. ループ内で `commit` を呼ぶ実装になっている（トランザクション境界は実装を確認値とする）。
10. すべての ID が成功したら再度 `commit` を呼び、翻訳キー `admin.delete.complete` を成功フラッシュする。
11. 支店連携サービスに、リクエストで受け取った ID 配列（文字列のまま混在し得る）を渡して更新通知を送る。通知結果はログに残し、失敗時は支店連携エラーテーブルへ追記して `flush` する。
12. `admin.card.search.page_no` が空でなければ `m14-01_admin_card_card_search` の当該ページへ、空なら `admin_card_list` へリダイレクトする。

### 論理未削除商品の有無判定（削除ブロックの内訳）

実装の SQL は `mtb_card`・`mtb_card_detail`・`dtb_product_sub`・`dtb_product` を結合し、`dtb_product.del_flg = 0` の行が 1 件でもあれば「削除不可の商品が残っている」と数える。買取系テーブルはこの問い合わせに含まれない（ソース上のコメントと SQL の対応は実装を確認値とする）。

本機能では売上集計や件数集計は行わない。削除可否の集計はカード単位で、上記 SQL とデッキ採用件数のみである。

## 一括削除時の判定順序

| 順序 | 判定 | 結果 |
|------|------|------|
| 1 | CSRF トークン | 無効なら HTTP 403（アクセス拒否）。 |
| 2 | ボディに `cardIds` キーが存在するか | 無ければリダイレクトのみ（メッセージなし）。 |
| 3 | 各 ID が非空かつ DB にカードが存在するか | 満たさなければ HTTP 404。 |
| 4 | デッキ採用があるか | あればエラーフラッシュ・部分通知・Referer へ。 |
| 5 | 論理未削除商品がカード詳細経由で存在するか | あれば同上。 |
| 6 | 上記を通り抜けた各 ID | 規格紐付け解除・ORM 削除・flush。 |

## 業務ルール・計算

本機能では数量計算や料金計算は行わない。削除の順序は POST の `cardIds` 配列の反復順に依存する。

### 入力項目

| 項目名 | 必須／任意 | 最大長 | 初期値 | 保存先・扱い |
|--------|------------|--------|--------|----------------|
| 行チェック（一覧） | 任意（未選択なら送信されない） | カード ID の整数表現に準ずる | 未チェック | ボディキー `cardIds`（配列フィールド名 `cardIds[]`）。未送信時は `null` 扱いでリダイレクトのみ。 |
| CSRF トークン（隠し） | 必須 | 実装のトークン長 | サーバが発行した現行値 | ボディキー `_token`。コアの既定トークン ID で検証。成功後にプロバイダが更新。 |

### エッジケース

| ケース | 扱い |
|--------|------|
| `cardIds` が空配列として送られる | ループが 0 回になり、成功フラッシュと支店通知（空配列に近いパラメータ組み立て）に至り得る。実装を確認値とする。 |
| 複数 ID のうち途中でブロック | その時点までに flush 済みの削除は残る。フラッシュは 1 件分のエラーのみ。支店には削除済み ID のみ通知。 |
| 支店 API 失敗 | 画面は成功メッセージのままリダイレクトし得る。失敗内容はログと支店連携エラーテーブル側に残る。 |

## データ整合性

| 観点 | 内容 |
|------|------|
| 一覧との関係 | 削除直後はリダイレクトで一覧を再取得する。別タブの古い一覧とは一致しない場合がある。 |
| 商品マスタ | カード削除前に `dtb_product_sub.card_detail_id` が NULL に更新されるため、商品行は残りカード参照だけ失われる。 |
| 支店 | 通知は HTTP クライアントで非同期に近い呼び出しであり、支店側反映と管理 DB 削除の厳密な同一トランザクションは保証しない。 |

## API/バッチ結果

本機能は画面 POST の一次処理であり、画面からバッチを起動しない。支店更新通知は内部で HTTP POST を行う。失敗時も画面フローは成功リダイレクトし得るため、利用者は支店連携エラー画面やログではなくフラッシュだけでは判別できない場合がある。

## DBカラム

当機能が直接触れる主な列は以下。型の細部はスキーマを参照する。

| テーブル | 列 | メモ |
|---------|-----|------|
| `mtb_card` | 主キー | 行ごと削除。移行先（ec-cube-enterprise）も同一スキーマ。 |
| `mtb_card_detail` | `card_id` ほか | 親カード削除に伴い ORM で子から削除される。移行先も同一スキーマ。 |
| `dtb_product.card_detail_id`（現行は `dtb_product_sub.card_detail_id`） | `card_detail_id` | 削除前に NULL 更新で切り離す。移行先 ec-cube-enterprise では商品本体 `dtb_product` の列で、補助表 `dtb_product_sub` は存在しない。 |
| `dtb_product` | （現行のみ `del_flg`） | 削除可否判定にのみ参照（更新しない）。移行先 ec-cube-enterprise の `dtb_product` は `del_flg` を持たず物理削除のため、紐付く商品行の存在有無で判定する。 |

### DB操作

永続化の正は ec-cube-enterprise（テーブル名・操作は ec-cube-enterprise を正典）。当ドメインは承認ワークフローを介さず persist/flush で直接確定する（承認ワークフローは在庫機能固有）。

| 操作種別 | 対象テーブル | 契機・条件 |
|---------|--------------|------------|
| 登録/更新 | dtb_product / dtb_product_sub / mtb_card / mtb_card_detail | 当機能が行う登録・更新で対象テーブルを直接保存する（不要な削除は含まない）。確定は persist/flush による即時反映。DB=ec-cube-enterprise を正典とする。 |
