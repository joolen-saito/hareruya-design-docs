# データ管理 — MTGマスターデータ編集

## 概要

HareruyaEc プラグインが管理画面の「データ管理」配下から到達できる、プラグイン内の複数種マスタテーブル（カード属性・店舗・言語など）を一画面で一覧し、選択した種別に応じて全行を表形式で表示・一括送信で登録・更新・削除処理を試みる機能である。Doctrine の単純フィールドのみを対象とし、表示列はメタデータ上のフィールド名を先頭大文字だけ変換した見出しで並べる。コアの「マスターデータ管理」（`/setting/system/masterdata`）とは別ルートであり、選択肢一覧もプラグイン専用の定義のみを使う。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。カスタマイズ区分は「カスタマイズ」。画面・挙動は pf-eccube3 に配置された HareruyaEc プラグインのソースを確認値とし、DB関連（テーブル・列・型・制約）は ec-cube-enterprise の実装を正とする。ただし本機能が編集対象とするマスタはMTG固有でありプラグイン定義のため、移行先での扱いに注意が要る（下記「リニューアル移行時の扱い」）。

対象はブラウザ経由の管理画面に限定する。

実装レイヤーのメソッド名は本文の主題としない。本文ではルートbind名やSymfonyのルートnameの網羅は主説明としない。「利用者視点の入口」にHTTPメソッドとサイトルートからのパスパターンを書く。コード探索でbind名が必要なときだけ「調査補助」へ書く。

## リニューアル移行時の扱い

- 機能の枠組み（マスタ種別を選び、全行を表形式で一括編集する汎用エディタ）は移行先 ec-cube-enterprise にも存在するが、ルート位置が異なる。現行はプラグインの「データ管理」配下（`/{admin_route}/masterdata`）、移行先はコアの「システム設定」配下（`/{admin_route}/setting/system/masterdata`）である。移行先はイベントディスパッチで全マスタ（コア＋プラグイン）を対象にできる。
- 本機能が編集対象とする 23 種は MTG 固有マスタ（カード属性・レアリティ・色・デッキタグ・キャンペーンタグ等）で、HareruyaEc プラグインが定義する。ec-cube-enterprise コアにはこれら固有テーブルの定義は無く、移行先でも当該プラグイン相当の定義に依存する。固有テーブルの列は移行先のプラグイン実装を確認のうえ確定する（要確認）。
- 列の表示はDoctrineメタデータのフィールドからI動的生成する点は両者同等。移行先の汎用エディタは既定で `sort_no` 昇順、現行は先頭の `id` 含みフィールド順という並びの差がある。
- 画面・挙動は現行（pf-eccube3）の確認値。MTG固有マスタの移行先スキーマが確定したら、本節と「DBカラム」節を移行先に合わせて更新する。

## 処理フロー

### 一覧を表示または種別を確定する（`admin_hareruya_masterdata`、`admin_hareruya_masterdata_view`、および `admin_decktag_list` に振られた POST での同一処理）

1. PHP の `memory_limit` を無制限に設定する。
2. 種別選択用フォームを生成し、`GET` であれば入力は未送信扱い、POST であれば `handleRequest` 後に検証する。
3. POST かつ検証成功のときのみ、送信された種別文字列が `$entity` として確定する。それ以外かつ `$entity` 引数があるときはクエリまたはルート値で補われるパスにより種別が渡りうる（同一コントローラの index 処理）。
4. `$entity` が null でないとき、その文字列から `\` に戻した完全修飾名を Doctrine メタデータで解決し、フィールド名配列・昇順並びキー・表示用の列名を求める。ソート順は、`id` を部分一致で含む最初のフィールド名を昇順ソート対象として採用する単純な規則である。
5. リポジトリの `findBy` で対象種別を全件取得して配列データに写し込む。このとき `\DateTime` 型フィールドかつ Doctrine のプロパティ名変換後の見出し文字列が `ViewStartDate` または `ViewEndDate` である列は、`Y-m-d H:i:s` 形式へ文字列化する。真偽値が PHP の false のセルについては画面上は数値の 0 とする。
6. 行キーとして先頭 Doctrine フィールドの値（エンティティの配列参照で getter を叩く経路で取得される）で連想を切る。そのうえで最後に空オブジェクト構造による「空行」を 1 行追加する。
7. 種別側に `IS_VIEW_ONLY` 定数が真で定義されている場合は「登録」ボタンを無効にするフラグが立ちうる。現時点でプラグイン内マスタ種別へは当該定数の定義は無く、フラグは偽となる（実装追加時はフラグのみが変わる）。
8. 種別側に `FIXED_FORM_NUM` が定義されていれば読み込み、その整数が編集ロック境界に使われる。
9. 編集フォームビルダに上記データを渡し Twig をレンダする。

### 一覧を送信して永続化する（POST `admin_hareruya_masterdata_edit`）

1. PHP の `memory_limit` を無制限に設定する。
2. 編集用フォームを生成し、`handleRequest` する。
3. フォーム検証が通らない場合、HTTP 404 で終了する（同一画面でのエラー再表示などは行わない）。
4. 隠しフィールドから `{entity}` 文字列とコレクション行の配列を取り出し、`{entity}` から Doctrine メタデータを解決する。リポジトリ検索が異常でも 404 とする経路がある。
5. コレクション各行について次を繰り返す。行キーを 50 で割った余りが 0 のタイミングで `flush` を挟み、その後にもう一度末尾 `flush` する。
   - `prm0`（主キー相当の隠し値）があり、すべての削除判定用フラグが真のとき: 当該主キーを `findOneById` 系経路で読み込み、アイデンティティマネージャから除去する。この削除判定関数は、`prm1` 以降のキーごとに「値が null でない」のものがひとつも無いときのみ真となる。Symfony のテキスト型で送られた典型的な「空入力」が空文字のまま結合されると null とはみなされないため、この経路のみに依存すると削除が成立しない行が送信されうる実装となる（実装矛盾は「エッジケース」を正とする）。
   - `prm0` が送られ、`prm1` 以降に入力があると判定されるとき（上記削除でないとき）: 既存エンティティを読み、主キー以外の Doctrine 単純フィールドに対応する入力をセッターで上書きする。日時列は空でないことのチェックがあり、不合格なときは運用共通のキャンペーンタグ想定文言キー経由でエラーを積み、`Referer` へ HTTP 302 応答となる。入力が空許容となる列への未設定はプロパティ側では空文字の代入となる PHP の記法で処理される。
   - `prm0` が空であり、それ以外いずれかに値があると判定されるとき: 新規インスタンスを構築し、主キー以外の Doctrine 単純フィールドに対してのみセッターを順に適用して永続キューへ追加する。
6. Doctrine のフラッシュ処理が済んだら、`admin.register.complete` メッセージ種別で成功フラッシュを積み、`admin_hareruya_masterdata_view` へ送信した種別パラメータを付けてリダイレクトする。

| 指標 | 集計の要点 |
|------|------------|
| 並び順 | メタデータ上のフィールド名のうち、文字列として `id` を部分包含するものを最初に見つけた列を昇順キーとして `findBy` に渡す。ヒットしない場合は空の順序指示であり、Doctrine の規定順に依存する。 |

### エッジケース

| ケース | 扱い |
|--------|------|
| 編集送信フォーム検証エラー | HTTP 404 応答のみ。フラッシュでの利用者への具体的メッセージはこの分岐には無い実装となる。 |
| 日時列を空または空白のみ送信し更新または新規 | 翻訳キー `admin.campaign_tag.require` と同一キーでのエラー積載と、`Referer` HTTP 302。 |
| 既存主鍵があり、画面上で空欄化したのみの送信 | 「すべて null」の削除経路は Symfony のテキスト送信では空文字のままになり、null とはみなされにくく、削除より更新分岐になりうる。画面の削除説明文と完全一致しない場合があることを実装を正として記載する。 |
| `prm0` 無しかつ入力なし送信 | Doctrine の永続化対象とはならずスキップされる。 |
| メタデータ上の並び順に `id` を含む列が無い | ソート句が空になり、並び順は DB 側の未定義許容状態に依存する。 |
| 真偽列で DB が false を返している | 一覧では数値「0」と表示される。送信時には「0」を文字または数値として解釈しセッターに渡すので、Doctrine の型および PHP の弱い変換規則に従って再保存される動きとなる。 |

## DBカラム

画面は Doctrine がメタデータに持つ複数種のテーブルへアクセスする。機能では「Doctrine の単純列」のみ読み書き対象となる。細部は各エンティティのマッピングとスキーマを正とする。Doctrine メタデータ上の複合キーや関連付けのみの列がある種別については、この画面だけでは一覧に含まれず、一覧に出た列のみが入力対象となる。

## 画面遷移
