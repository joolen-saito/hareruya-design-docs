# カスタムCSV出力項目設定（店舗設定／システム設定）

## 概要

管理画面の「店舗設定」配下（サイドメニューでは `HareruyaEc` の差込により追加）から開く画面で、商品CSV・受注CSV・配送CSVそれぞれについて、標準の `dtb_csv.enable_flg` とは独立した「カスタムCSV定義（名前付きプリセット）」を複数保存し、出力する列とその順序を確定する機能である。画面見出しは「カスタムCSV出力項目設定」となる。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。対象はブラウザ経由の管理画面に限定する。

本書では Symfony のルート名、URL パス、コントローラクラス名は扱わない。

カスタマイズ区分はカスタマイズであり、挙動・画面・処理フローの参照は現行リポ pf-eccube3 を正とし、DB関連（テーブル名・列名・型・制約・関連、DBカラム節、入力項目の保存先、データ整合性のDB部分、副作用のDB更新）はリニューアル後システムである ec-cube-enterprise を正とする。

## 本書で扱うこと

- カスタムCSV定義の表示・切替・新規・保存・削除の利用者視点のふるまい
- 二段リスト（出力しない項目／出力する項目）と送信時に全行を選択するクライアント挙動
- 保存先（`dtb_csv_extension` と `dtb_csv_csv_extension`）と、更新時の既存紐付けの削除・再登録
- カスタムCSVの実ファイル出力が参照する検索条件（セッション）とエクスポートサービスとの関係の要点
- CSV種別として選択肢に載る範囲（商品・受注・配送）

## 本書で扱わないこと

以下は本書では仕様確定せず、実装または別機能の設計を正とする。

- 管理画面ログイン、セッション、CSRF の共通ポリシー全般（本機能の更新アクションがフォーム検証経由でない点を含め、ミドルウェアやSilex設定での補完の有無は環境を正とする）
- `dtb_csv` マスタ自体の追加・変更（マイグレーションや他画面での項目定義）
- 標準の「CSV出力項目設定」（`enable_flg` と `rank` を直接更新するコア実装）の詳細。カスタム定義は `dtb_csv` 行を選択するだけで当該列を書き換えない
- カスタムCSV以外のダウンロード経路（標準の商品CSV・受注CSV等）の出力仕様の全体
- `findById` 等、同梱ソース上は基底リポジトリに見えないメソッド呼び出しが実行時に成功するかどうか（デプロイ先のオートローダ・Doctrineメタデータ・リポジトリ差し替えを正とする）

## リニューアル移行時の扱い

- 挙動・画面・処理フローは現行（pf-eccube3）の確認値、DBスキーマは移行先（ec-cube-enterprise）を正とする。実装済み・未実装を取り違えず、現行と移行先を対比で示す。
- 出力項目マスタ（dtb_csv）の列対応（現行 → 移行先）:
  - 主キー: `csv_id` → `id`
  - 並び順: `rank` → `sort_no`（移行先は SMALLINT。本書のDB記述は `sort_no` を正とする）
  - 有効フラグ: `enable_flg` → `enabled`（移行先は真偽値）
  - CSV種別外部キー: `csv_type` → `csv_type_id`
- カスタム定義（dtb_csv_extension）の列対応（現行 → 移行先）:
  - 主キー: `csv_extension_id` → `id`
  - 名称 `name` の桁: 現行 64 → 移行先 255（移行先も NULL 可）
  - 移行先は `base_info_id`（店舗参照 `dtb_base_info`）と `create_date` を持つ。現行にこれらは無い。
  - ソフトデリート列 `deleted_at` は現行・移行先とも持つ。
- 紐付け表（dtb_csv_csv_extension）の並び順列は、移行先でも `rank` のままである（dtb_csv の `sort_no` とは異なる）。`csv_extension_id` と `csv_id` は移行先の各主キー列 `id` を参照する。
- 移行時は、現行と移行先のスキーマ差（主キー名・並び順キー名・有効フラグ名・CSV種別FK名・追加列）を移行設計で吸収する。

## 処理フロー

### 画面を開く（GET）

1. 管理画面の認証・権限・IP制限の各ルールを通過する（詳細は管理画面共通を正とする）。
2. リクエストで指定されたCSV種別識別子が `mtb_csv_type` に存在しない場合、該当HTTPエラーとなる。
3. カスタム定義識別子が指定されており、かつ該当する `dtb_csv_extension` 行が無い場合、該当HTTPエラーとなる。未指定の場合は新規エンティティとして扱う。
4. フォームビルダに、CSV種別・既存定義セレクト・名称・左右リストの選択肢がバインドされる。右リストは、当該定義に既に紐づく `dtb_csv` 行を種別と結合条件で取得した結果である。左リストは、同じCSV種別の `dtb_csv` のうち、右に出ている主キーを除いた集合を `sort_no`・`id` 順（現行 pf-eccube3 は `rank`・`csv_id` 順）で並べた結果である。
5. テンプレートを描画する。

### 「設定」押下（POST）

1. リクエストボディから `admin_custom_csv` 連想配列を読む。Symfonyフォームの`isValid`を呼ぶ処理は無い。
2. 名称文字列をカスタム定義に格納し、CSV種別を関連付け、ログイン中の管理者の主キーを `member_id` に格納する。Doctrineへ永続化しフラッシュする。
3. 既存定義の更新である場合、同一のカスタム定義主キーを持つ `dtb_csv_csv_extension` 行を生SQLで一括削除する。
4. 新規の場合は直前のフラッシュで採番されたカスタム定義主キーを取得する。
5. リクエスト内の `csv_output`（`dtb_csv` 主キーの配列）を、配列の添字を0始まりの順序番号として解釈し、行ごとに `dtb_csv_csv_extension` の複合主キーと `rank` を保存する。配列内の各IDについて `dtb_csv` 行を取得し、結合エンティティにセットして永続化する。
6. 管理画面向け成功メッセージを積み、当機能のGETへリダイレクトする（パラメータはCSV種別と保存したカスタム定義主キー）。

### 「削除」実行（DELETE相当）

1. CSRFトークンをフォーム名無しの既定トークン名で検証する。無効ならアクセス拒否例外となる。
2. カスタム定義主キーが欠ける、または該当エンティティが無い場合、該当HTTPエラーとなる。
3. カスタム定義の関連コレクションを空にしてflushした後、エンティティを`remove`し再flushする。
4. 当機能トップ相当へリダイレクトする。

### カスタムCSVファイルの出力（別コントローラ、GETストリーム）

1. カスタム定義主キーで `dtb_csv_extension` を取得できなければ該当HTTPエラーとなる。
2. `dtb_csv_csv_extension` から `rank` 順に `dtb_csv` 行を再取得し、エクスポートサービスへ渡す。
3. タイムアウト制限を無効化し、SQLロガーを無効化する。
4. CSV種別に応じて、商品は管理画面の商品検索セッション、受注・配送は受注検索セッションから検索フォームを復元し、当システムが拡張したクエリビルダで一覧対象を取得する。
5. ヘッダ行に、選択された各 `dtb_csv` の表示名を並べ、データ行は種別ごとのエクスポーターで埋める。文字コードや区切り文字はアプリケーション設定に従う。

## 業務ルール・計算

| 項目 | 内容 |
|------|------|
| 対象CSV種別 | フォームの「CSV出力項目」は、内部クエリで商品・受注・配送の3種に限定する。会員CSV・カテゴリCSVは選択肢に出さない。 |
| 左リストの構成要素 | 指定CSV種別の `dtb_csv` のうち、現在編集中のカスタム定義の右リストに含まれる主キー以外。標準画面のように有効フラグ `enabled`（現行 pf-eccube3 は `enable_flg`）で左右を分けない。 |
| 名称 | 必須。空白のみはフォーム制約上は不可だが、POST処理はフォーム検証を経由しないため、運用上はリクエスト改ざんに注意（表示・保存値の整合は実装を確認値とする）。 |
| 保存単位 | 1回の「設定」で1件の `dtb_csv_extension` と、それに紐づく `dtb_csv_csv_extension` の全置換を行う。 |
| 更新者 | 保存のたびに、当該リクエストのログイン中管理者主キーを `member_id` に上書きする。 |

### 入力項目

| 項目名 | 必須／任意 | 最大長 | 初期値 | 保存先・扱い |
|--------|------------|--------|--------|----------------|
| CSV出力項目 | 必須 | —（セレクト） | 現在のCSV種別 | 画面切替のみ。保存時は `customUpdate` がリクエストの名称等と合わせて読む対象であり、種別変更後に未保存の左右リストを送った場合の整合は利用者操作に依存する。 |
| カスタムCSV | 条件付き必須 | —（セレクト） | 既存なら該当行、新規なら空 | 表示切替。コアのNotBlank制約が付くがPOSTは生パラメータ経路のため、実効性は環境・改ざん耐性の観点で別途確認。 |
| 出力名 | 必須 | 255 文字（移行先 dtb_csv_extension.name の桁。現行 pf-eccube3 は 64） | 既存定義の名称または空 | `dtb_csv_extension.name`（NULL 可）。 |
| CSV出力しない項目 | 任意 | —（複数選択） | CSV種別に属する未割当行 | 送信時は補助的。保存ロジックは右側 `csv_output` のみを解釈し、左に残した主キーは紐付け行を作らない。 |
| CSV出力する項目 | 任意 | —（複数選択） | 既存定義に紐づく行 | `dtb_csv_csv_extension` に順序付きで保存。空にすると、紐付け行はすべて削除された状態に近いが、定義本体は残る。 |

### エッジケース

| ケース | 扱い |
|--------|------|
| 新規定義で右リストが空 | `dtb_csv_csv_extension` 行は作成されない。エクスポートはヘッダのみ等、サービス実装次第。 |
| 既存定義の更新で、削除用の前置き分岐が真 | 旧紐付けを生SQL DELETEしてから再挿入する。 |
| ソフトデリート可能なエンティティを物理削除 | 削除処理は `remove` による削除。ソフトデリート設定との整合はORM設定を正とする。 |

## データ整合性

| 観点 | 内容 |
|------|------|
| 標準CSV設定との関係 | `dtb_csv.enabled`（現行 pf-eccube3 は `enable_flg`）は本機能で更新しない。フロントの標準CSVダウンロードが参照する有効列集合と、カスタム定義が参照する列集合は一致しない。 |
| カスタム定義間 | 同一CSV種別に複数の `dtb_csv_extension` が共存する。それぞれ独立に `dtb_csv_csv_extension` を持つ。 |

### DB操作

永続化の正は ec-cube-enterprise（テーブル名・操作は ec-cube-enterprise を正典）。当ドメインは承認ワークフローを介さず persist/flush で直接確定する（承認ワークフローは在庫機能固有）。

| 操作種別 | 対象テーブル | 契機・条件 |
|---------|--------------|------------|
| 登録/更新 | dtb_base_info / dtb_csv / dtb_csv_csv_extension / dtb_csv_extension / dtb_member / mtb_csv_type | 当機能が行う登録・更新で対象テーブルを直接保存する（不要な削除は含まない）。確定は persist/flush による即時反映。DB=ec-cube-enterprise を正典とする。 |
