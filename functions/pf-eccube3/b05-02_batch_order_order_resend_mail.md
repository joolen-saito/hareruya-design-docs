# バッチ 受注管理 — 購入完了手続き再処理

## 概要

購入完了処理が完了しきらず注文完了メールが未送信となった受注について、ポイント処理・在庫更新・注文完了メールの再送信をやり直すバッチである。コマンドライン（コンソールコマンド）から実行する。二重実行を避けるためロックを取得し、受注ごとにトランザクションで処理する。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。確認値はpf-eccube3（EC-CUBE3系）のHareruyaEcプラグインの受注バッチ（購入完了手続き再処理）、受注・受注サブ・ポイント履歴・受注番号を扱うリポジトリ、在庫更新・メール再送信・スマレジポイント連携処理を正とする。カスタマイズ区分は現行踏襲であり、挙動の参照リポはpf-eccube3、DB関連はec-cube-enterpriseを正とする。

対象はコンソールコマンドであり、ブラウザ経由の画面を持たない。

本文ではフレームワークのコマンド型名やサービス型名を主説明としない。実行はコンソールのバッチコマンドで行う。

- 二重実行を避けるロックの取得

- スマレジポイント連携の別プロセス実行
- 受注ごとのトランザクションと失敗時の扱い

## リニューアル移行時の扱い

現行（pf-eccube3）の挙動と移行先（ec-cube-enterprise）の差を記録する。挙動は現行リポを正とし、DB関連はec-cube-enterpriseを正とする。

| 観点 | 現行（pf-eccube3） | 移行先（ec-cube-enterprise） |
|------|--------------------|------------------------------|
| 消費ポイントの列 | 受注サブテーブル`dtb_order_sub`の消費ポイント列で判定する。 | 補助表`dtb_order_sub`を持たず、消費ポイントを受注`dtb_order`の`spended_points`列へ統合している。 |
| ポイント履歴テーブル | プラグインのポイント履歴で冪等判定する。 | `dtb_point_history`（`customer_id`・`order_id`・`point_change`・`point_type_id`等）が正。`order_id`で受注に紐づく。 |
| 在庫履歴テーブル | 在庫履歴と販売数を更新する。 | 在庫履歴は`dtb_stock_history`（`product_stock_id`で関連）、販売数は`dtb_product_class`が正。 |
| 注文番号 | 受注番号（8桁）を取得して使用する。 | 受注`dtb_order`の`order_number`（文字列・桁11）が正。桁・型が現行と異なる（要確認）。 |

| 入口 | 実行方法 | 期待されるふるまい |
|------|----------|--------------------|
| コンソールのバッチコマンド | `order:batch resendMail` | メール未送信の受注について、ポイント・在庫を整え、注文完了メールを再送信する。 |

## 処理フロー

### 購入完了手続き再処理を実行する（`order:batch resendMail`）

1. 同名バッチが実行中の場合は、未完了の旨を出力して終了する。
2. メール送信用の経路を準備する。
3. ロックを取得する。取得に失敗した場合は異常として終了する。
4. メール未送信の受注を取得する。
5. 受注ごとにトランザクションを開始し、次を行う。
   - 受注サブに消費ポイントがあり、かつポイント履歴が無い場合はポイント処理を行う。
   - 消費ポイントがある場合はスマレジポイント連携を別プロセスで実行する。
   - 受注番号（8桁）を取得する。
   - 在庫履歴と販売数を更新する。
   - トランザクションを確定する。
   - 注文完了メールを再送信する（宛先言語は会員の都道府県が海外なら英語、それ以外は日本語）。
6. 受注の処理で例外が発生した場合は、当該受注のトランザクションを巻き戻し、エラーメッセージを出力して次の受注へ進む。

## 業務ルール・計算

| 項目 | 内容 |
|------|------|
| 二重実行防止 | 実行中なら未完了の旨を出力して終了し、開始時にロックを取得する。 |
| ポイントの冪等性 | 消費ポイントがあってもポイント履歴が既にある場合はポイント処理を重複して行わない。 |
| 言語判定 | 会員の都道府県が海外の場合は英語、それ以外は日本語でメールを再送する。 |
| 受注単位の独立性 | 受注ごとにトランザクションを分け、1件の失敗を他に波及させない。 |

## DBカラム

機能に直接関係する列のみ記載する。型や一覧の細部はスキーマを参照する。

テーブル・列名はec-cube-enterpriseを正とする。現行（pf-eccube3）と異なる場合は移行先名を主とし現行名を括弧で添える。

| テーブル | 列 | メモ |
|---------|-----|------|
| `dtb_order` | メール送信状態 | メール未送信受注の抽出に使用する。 |
| `dtb_order`（現行は`dtb_order_sub`） | `spended_points` | ポイント処理・スマレジ連携の判定に使用する消費ポイント。 |
| `dtb_point_history` | `order_id`・`point_change`・`point_type_id`・`customer_id` | ポイント処理の冪等判定と登録に使用する。 |
| `dtb_order`（現行は`dtb_order_sub`） | `order_number` | 在庫更新・メールに使用する注文番号（移行先は文字列・桁11）。 |
| `dtb_stock_history` | `product_stock_id`・`stock` | 在庫履歴を更新する。 |
| `dtb_product_class` | 在庫・販売数 | 販売数を更新する。 |

### DB操作

永続化の正は ec-cube-enterprise（テーブル名・操作は ec-cube-enterprise を正典）。当ドメインは承認ワークフローを介さず persist/flush で直接確定する（承認ワークフローは在庫機能固有）。

| 操作種別 | 対象テーブル | 契機・条件 |
|---------|--------------|------------|
| 登録/更新 | dtb_order / dtb_order_sub / dtb_point_history / dtb_product_class / dtb_stock_history | 当機能が行う登録・更新で対象テーブルを直接保存する（不要な削除は含まない）。確定は persist/flush による即時反映。DB=ec-cube-enterprise を正典とする。 |

## エラー処理

| エラー内容 | 処理 |
|------------|------|
| 実行中（ロック未取得相当） | 未完了の旨を出力して終了する。 |
| ロック取得失敗 | 異常として終了する。 |
| 受注処理での例外 | 当該受注を巻き戻し、エラーメッセージを出力して次の受注へ進む。 |

## ログ・監査

| タイミング | 記録内容 |
|------------|----------|
| 実行中検知 | 未完了の旨のコンソール出力。 |
| 受注処理失敗 | エラーメッセージのコンソール出力。 |

### ログに出してはいけないもの

- 会員のメールアドレス等の機微値
- スマレジ・メールの認証情報

---

## 排他制御・トランザクション

開始時にロックを取得して二重実行を避ける。受注ごとにトランザクションを開始・確定し、失敗時は当該受注のみ巻き戻す。
