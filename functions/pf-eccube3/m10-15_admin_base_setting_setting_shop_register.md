# 店舗基本設定の店舗登録（SHOPマスター保存）

## 概要

管理画面の「店舗設定」配下にある「基本情報設定」（画面見出し。サブタイトルは SHOPマスター）において、フォームに入力した店舗基本情報を「登録」ボタンで `dtb_base_info` に保存する機能である。複数店舗レコードを新規作成して登録する機能ではなく、識別子既定で取得した1行を更新する保存処理を指す。

本書は実装手順ではなく、誰が・いつ・どの条件で・結果どうなるかを読むためのリバース詳細設計とする。対象コードベースは pf-eccube3 のコア実装とする。

対象はブラウザ経由の管理画面に限定する。

本書では Symfony のルート名、URL パス、コントローラクラス名は扱わない。

カスタマイズ区分はカスタマイズであり、挙動・画面・処理フローの参照は現行リポ pf-eccube3 を正とし、DB関連（テーブル名・列名・型・制約・関連、DBカラム節、入力項目の保存先、データ整合性のDB部分、副作用のDB更新）はリニューアル後システムである ec-cube-enterprise を正とする。

## リニューアル移行時の扱い

- 挙動・画面・処理フローは現行（pf-eccube3）の確認値、DBスキーマは移行先（ec-cube-enterprise）を正とする。実装済み・未実装を取り違えず、現行と移行先を対比で示す。
- 永続化先は現行・移行先とも `dtb_base_info` の単一行更新だが、列構成が次のとおり異なる。本書のDB記述は移行先を正とする。
  - 郵便番号: 現行は `zip01` と `zip02` の2列、移行先は `postal_code` の1列（長さ8）。
  - 電話番号: 現行は `tel01` / `tel02` / `tel03` の3列、移行先は `phone_number` の1列（長さ14）。
  - FAX番号: 現行は `fax01` / `fax02` / `fax03` の3列、移行先は `fax_number` の1列（長さ14）。
  - 都道府県: 現行は `pref`、移行先は `pref_id`（`mtb_pref` 参照の外部キー）。
  - 在庫切れ非表示: 現行は `nostock_hidden`、移行先は `option_nostock_hidden`（真偽値）。
- 緯度 `latitude`・経度 `longitude` は、移行先 `dtb_base_info` に相当列が見当たらない（ec-cube-enterprise 実装で要確認）。現行 pf-eccube3 にのみ存在する入力・列として扱い、移行時の保持要否は移行設計で確定する。
- 移行時は、複数列を1列へ統合する郵便番号・電話・FAXの分割統合、都道府県のテキスト→マスタFK化、緯度経度列の有無を移行設計で吸収する。

## 処理フロー

### 画面を開く（GET）

1. 管理画面の認証・IP 制限・権限拒否の各ルールを通過する。
2. リポジトリの `get` で店舗基本情報を既定 ID で取得する（Doctrine のクエリ結果キャッシュを使用）。
3. 取得済み実体の複製を作成し `detach` したうえで、Twig グローバルの店舗基本情報へ載せる。編集にバインドする実体とは別参照とする。
4. `shop_master` フォームビルダを実体に対して作成する。
5. ディスパッチャに表示初期化用イベントを渡す。イベント引数にフォームビルダと店舗基本情報が含まれる。
6. フォームを組み立て、`handleRequest` で GET の場合は送信済みとみなされない。
7. テンプレートを描画する。

### 「登録」押下（POST、検証成功）

1. `handleRequest` が送信済みとして処理する。
2. フォーム検証が成功すると、同一マネージド実体に入力値が載った状態になる。
3. `persist` と `flush` で変更を DB に反映する。更新日時は永続化直前のライフサイクルで現在時刻が自動設定される（後述）。
4. 検証成功後ディスパッチャに完了イベントを渡す。イベント引数にフォームと店舗基本情報が含まれる。
5. 管理画面向け成功フラッシュにメッセージキー `admin.shop.save.complete` を積む。文言はロケールで「基本情報を保存しました。」（確認値）。
6. 基本情報設定画面自体へリダイレクトする（GET で再表示）。

### 「登録」押下（POST、検証失敗）

1. `handleRequest` は送信済みとして処理するが、`isValid` が false となる。
2. 同一テンプレートを再描画し、項目エラーを表示する。成功フラッシュは積まない。`persist`・`flush` は実行されない。
3. Twig グローバルの店舗基本情報はリクエスト開始時点で複製・detach したスナップショットのままである。フォームに載った送信値・エラー表示と、ヘッダ等でグローバルを参照する表示が一致しない場合がある。

## 登録処理における判定順序

| 順序 | 判定 | 結果 |
|------|------|------|
| 1 | 管理画面へのアクセスが許可されるか | 否なら保存処理に到達しない。 |
| 2 | CSRF を含むフォーム送信として妥当か | 否ならフレームワークのエラー扱い（詳細はセキュリティ設定を正とする）。 |
| 3 | `isSubmitted` か | POST で true。 |
| 4 | `isValid` か | true なら永続化フローへ。false ならエラー再描画のみ。 |
| 5 | 設定で結果キャッシュクリアが有効かつ、店舗基本情報の更新が検知されたか | postUpdate 等で結果キャッシュ全削除が走る場合がある。 |

### エッジケース

| ケース | 扱い |
|--------|------|
| メール4項目のいずれかが空 | NotBlank でエラー。保存しない。 |
| 電話の一部欄だけ入力 | `form.tel.empty_value` でエラー。保存しない。 |

| `dtb_base_info` に既定 ID の行が無い | `getSingleResult` が例外となる。通常インストール済み DB を前提とする。 |

## データ整合性

| 観点 | 内容 |
|------|------|
| 同一レコードの更新 | 楽観ロックは無い。後から flush した更新が残る。 |
| 結果キャッシュ | 店舗基本情報の取得は結果キャッシュを使用する。設定でクリアが有効なら更新後にキャッシュ全削除が走る。無効なら TTL 内は古いスナップショットが読まれる可能性がある。 |
| 郵便番号の保存列 | 現行 pf-eccube3 はフォームを `zip01`・`zip02` にマップし、結合列 `zipcode` は当フォームに無く送信だけでは変更セットに載らない（既存値が保持される）。移行先 ec-cube-enterprise は `postal_code` の1列で保持し、結合列は持たない（差は「リニューアル移行時の扱い」を参照）。 |
| 保存後の再表示 | リダイレクト後の GET で再度 `get` するため、キャッシュが無効化されていれば保存値が読み込まれる。 |

### DB操作

永続化の正は ec-cube-enterprise（テーブル名・操作は ec-cube-enterprise を正典）。当ドメインは承認ワークフローを介さず persist/flush で直接確定する（承認ワークフローは在庫機能固有）。

| 操作種別 | 対象テーブル | 契機・条件 |
|---------|--------------|------------|
| 登録/更新 | dtb_base_info / mtb_pref | 当機能が行う登録・更新で対象テーブルを直接保存する（不要な削除は含まない）。確定は persist/flush による即時反映。DB=ec-cube-enterprise を正典とする。 |

## 排他制御・トランザクション

- 楽観ロックは無い。複数管理者が連続保存した場合は最後の保存が残る。
- コントローラは明示トランザクションを張らず `flush` を1回呼ぶ。途中失敗時の部分反映は ORM・DB の挙動に従う。
- `preUpdate` で `setUpdateDate` が呼ばれ、`flush` の単位で更新日時が進む。

---

## 永続化時の自動処理（確認値）

Doctrine の保存イベント購読が `prePersist`／`preUpdate` に応答し、更新日時 setter を持つエンティティへ現在時刻を設定する。店舗基本情報は更新保存が主であり、`preUpdate` が該当する。

結果キャッシュ全削除のイベント購読は設定 `doctrine_cache.result_cache.clear_cache` が真のときのみ `postPersist`／`postUpdate`／`postRemove` を購読し、店舗基本情報など特定エンティティの変更時に結果キャッシュ実装へ対して `deleteAll` を呼ぶ。

---

## プラグイン向けフック（確認値）

表示初期化時および保存検証成功後にイベントディスパッチャへイベントが渡る。イベント引数にフォームビルダまたはフォーム、および店舗基本情報が含まれる。具体的なフック名と追加処理はプラグイン実装およびイベント定義を正とする。
