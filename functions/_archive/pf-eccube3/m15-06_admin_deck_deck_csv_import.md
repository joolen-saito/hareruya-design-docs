#### エッジケース
| ケース | 扱い |
|--------|------|
| 表示はするがリストを非公開にしたい | メインリスト空欄を必須解釈から外す特例が適用される。リスト検証経路にも入らないため本文・明細チェックおよび `dtb_deck_card` 反映はしない。統率者有無の評価はフォーマットの統率使用フラグに従ってもリスト検証外で早期に例外になり得る。 |
| 「厳密」オンとオフ | オンなら禁止・制限超過などに対応する翻訳付き異常種別すべてが昇格される。オフなら昇格しないまま許容または黙読する状態が並ぶ運用モデルとなる。 |
| CSV 側 `deck_id` に既存有効 ID を書いて再取込 | コード上明示的な `dtb_deck_card` 既存削除は無い。そのためリスト検証経路を通すたび `CardUtil#setDeckCards` は新オブジェクトのみ `persist` し、`flush` と commit で既存複製が残り得る。DB 側一意制約が無いときの重複行はサイト表示仕様側でどう読むかに依存するため、一覧整合は保証しない。 |
| アップロード後にヘッダ不一致 | メッセージが翻訳キーそのまま管理画面フラッシュになり得る。 |
| Symfony 側でファイル必須違反などフォーム検証無効のみが成立したとき | `checkFormValid` はエラーをフラッシュしつつリダイレクト応答オブジェクトへまとめるが、この呼び出しの戻り値をコンテローラ側が評価して早期 return しておらず、ソース上そのまま続行コードパスにある。環境での実害（例えば `import_file` 未取得状態で後続処理が致命的エラーへ至る）は実装側の運用確認を要するギャップである。 |

#### ログに出してはいけないもの
- アップロード済みリスト本文に混入し得る利用者入力の一覧は開発者向けにマスクしない設計にあるため運用側で一覧を取らない前提とするログ方針を別途持つことを推奨とするのみ本書には書かず、ソースの網羅的マスク有無についてはログポリシー別紙へ委ねる（秘密値の転記はしない）。
一般的なログ禁止例（資格情報、Cookie の原値すべて、セッション完全値）は管理画面共通方針に従う。
