#### エッジケース
| ケース | 扱い |
|--------|------|
| `deckId` が空配列として送られる（実装環境により稀） | ループが 0 回となり、その後でも成功フラッシュに至り得る。 |
| 複数 ID のうち途中で「記事中」に当たった | それまで削除済みの分は確定済み。エラーは 1 メッセージのみ。Referer が無いときの結果はフレームワーク側の規約に委ねる。 |
| CSV 側と同様の「未選択で送信抑止」をクライアントが行わない | 送信されればサーバ側の `null` 分岐または空配列入力の結果に応じて遷移する。 |
---
### データ整合性
| 観点 | 内容 |
|------|------|
| 一覧との関係 | 成功時は一覧へリダイレクトし再クエリされる。処理中断時は Referer により直前一覧の再表示に戻り、一部削除のみ完了している状態があり得る。 |
| デッキ内カード | 親デッキの `remove` 前に子行を順に除去する実装であり、親削除時に子だけ残り続ける状態にはしない設計になっている（ORM の flush 順序は Doctrine に従う）。 |
| many-to-many 付随テーブル | `dtb_deck_deck_tag` のような関連は、親デッキのライフサイクルに任せ、`remove` とマッピングに従い付随関係も整理されることを期待する運用となる。細部は ORM とスキーマを参照する。 |
| 支店連携など外部通知 | 当ルート単体には、カード一括削除のような支店 API 送信ブロックが無い。 |

## 0203に無い定型節（設計書からは削除・2026-08-19）

### ログ・監査
当ルート処理本体は、フラッシュとリダイレクトが主なユーザー向け帰結であり、このメソッド内だけを見ても支店サービス級の送信や専用の監査テーブル追記があるとは限らない。一般的なウェブ／アクセスログはインフラ設定に依存する。
#### ログに出してはいけないもの
- パスワード
- なりすまし対策トークン
- Cookie 値
- セッション ID の完全値
- Remember Me トークンの原値

| 管理外の主体 | 管理画面の認可に阻まれる（詳細は本書では確定しない）。 |

### 排他制御・トランザクション
楽観ロックやユーザー単位の明示排他キーは当メソッド内に無い。配列順に順次 `flush` するため、他セッションが同一デッキを同時編集していた場合は、取得・削除競合により 404、制約エラー、その他 Doctrine エラーになり得る。境界の詳細は再現ログを正とする。
