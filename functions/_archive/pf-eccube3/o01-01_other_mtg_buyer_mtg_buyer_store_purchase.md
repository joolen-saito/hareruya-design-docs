## 用語

| 用語 | 説明 |
|------|------|
| MTGバイヤー | 店頭買取・ネット買取の査定作業に使う外部アプリ。EC-CUBEとはpf-api経由で連携する。 |
| 店頭買取受注 | 店頭で受け付けた買取申込。EC-CUBE側では`dtb_otc_buy_order`を中心に管理する。 |
| 査定対象 | 店頭買取ステータスが商品到着、査定中、振込前、保留、査定再開など、MTGバイヤーで扱う対象となる受注。 |
| 査定明細 | MTGバイヤーで入力・確定する商品、数量、買取単価、販売価格、部門などの明細。商品規格に紐づく明細と個別入力商品に分かれる。 |
| 店頭買取ステータス | 店頭買取の進行状態。査定前、査定中、買取成立、買取キャンセル、ダブルチェック済、データ出力済などを持つ。 |

## 0203に無い定型節（設計書からは削除・2026-08-19）

#### エッジケース
| ケース | 扱い |
|--------|------|
| 認証不可 | APIは認証拒否とし、店頭買取データを返さず更新しない。 |
| 査定対象が0件 | 店頭買取受注一覧取得APIは空配列を返す。 |
| 受注IDが存在しない | 詳細更新、ステータス更新、コメント更新、本人確認更新は該当なしとして扱う。 |
| 明細が空 | 詳細更新APIは入力不正とし、既存明細・在庫を削除しない。 |
| 同じステータスで詳細更新 | 明細・個別入力商品・在庫・在庫履歴は送信内容で作り直す。ステータス変更履歴は追加しない。 |
| 同時更新 | 専用の楽観ロック・悲観ロックは持たない。後から確定した更新が残る。 |

### データ整合性
| 観点 | 内容 |
|------|------|
| 参照時点 | MTGバイヤーの一覧取得、商品情報取得、管理画面の一覧・詳細・CSVは、それぞれ実行時点で永続化済みのデータを参照する。 |
| 査定結果と管理画面 | MTGバイヤーで確定した受注明細、個別入力商品、在庫、在庫履歴、ステータス、査定担当者、更新日時は、保存成功後に管理画面の店頭買取詳細・履歴・CSVの参照元になる。 |
| 在庫と履歴 | 詳細更新時に商品規格ごとの数量で店頭買取受注在庫を作り直し、対応する在庫履歴を登録する。既存在庫・履歴は削除後に再作成される。 |
| ステータスと集計 | 買取成立、ダブルチェック済、データ出力済など集計対象のステータスへ変わると、店頭買取集計やCSV出力の対象になる。集計処理の詳細はM06系およびバッチ設計を正とする。 |
| 外部運用との整合 | Backlog、スマレジ、Excelマクロ、バーコード印刷は本リポジトリ内で直接整合を保証しない。EC-CUBE側で出力したCSVや確定済みデータを運用で利用する。 |
| 同時更新 | DB行ロックを使った査定占有は確認できない。同一受注を複数の利用者・APIが同時に更新した場合、後から保存された内容が残る。 |

### 試行制限
本機能固有の試行制限は本書では仕様確定しない。API認証の失敗扱い、ログイン制限、外部アプリ側のリトライ制御は各APIおよびMTGバイヤー側を正とする。
---
### 排他制御・トランザクション
| 観点 | 内容 |
|------|------|
| トランザクション境界 | 店頭買取受注詳細更新APIは、既存明細・在庫の削除、明細・在庫・履歴の登録、受注更新、ステータス履歴登録を一連の保存処理として扱う。保存処理中の例外では未確定更新をロールバックする。 |
| ロック | 査定対象受注に対する行ロック・悲観ロック・楽観ロック・ロックファイルは確認できない。査定中などのステータスは業務上の状態であり、DBレベルの占有ロックではない。 |
| 例外時 | 検証エラーでは削除・登録・更新を開始しない。保存処理中の例外ではトランザクション内の未確定更新をロールバックする。 |
| 同時更新 | 同一受注を複数のMTGバイヤーまたは管理画面から同時更新した場合、後から確定した保存内容が残る。 |
