## 副作用（設計書からは削除・2026-08-19）

| 副作用 | 永続化層では、各行について`OrderStatus`を`persist`し、同一IDの`CustomerOrderStatus`・`OrderStatusColor`が存在するときだけそれぞれ名称・色を更新して`persist`する。最後に`flush`する。受注ヘッダの`order_status_id`そのものや履歴テーブルは本機能では変更しない。セッションは管理画面共通の認証に従い、本機能は検索条件セッションを追加しない。成功時のみフラッシュバッグに完了メッセージを積む。 |

#### エッジケース
| ケース | 扱い |
|--------|------|
| ステータス行が0件 | 通常の初期データでは起こりにくい。起きた場合は空コレクションのフォームとなり送信しても実質更新無しとなる。 |
| `CustomerOrderStatus`または`OrderStatusColor`の行だけ欠けている | 欠け側は初期表示では当該列が値未セットのままとなる。送信時、当該子フォームについて未入力ならば`NotBlank`で送信は無効となる。入力を埋めて検証が通れば`OrderStatus`側の項目は保存される一方、関連行が存在しないテーブルにはコントローラが`persist`しないため、その列で入力した内容はそのテーブルに反映されず失われる。運用上は両テーブルを`OrderStatus`と同じ主キーで揃える。 |
| 同時編集 | 楽観ロックは持たない。後勝ちで`flush`した内容が残る。 |
| 送信途中の検証のみ失敗 | `flush`前に停止し、DBは不変。 |

### 権限・認可
| 利用者状態 | 受注対応状況設定画面 |
|------------|---------------------|
| 未認証 | 利用不可。管理画面のログイン要件に従う。 |
| システム管理者・モール系管理者など、店舗設定配下への拒否パターンが紐付いていない権種 | 画面表示および登録送信が評価上許可される。 |
| 店舗側の権種（`Authority`のロールキー確認値として`tenant_owner`および`tenant_operator`。`mtb_authority.id`の確認値はそれぞれ4および5） | 初期データでは`dtb_authority_role`に、管理パス先頭`/setting/shop`と前方一致する`deny_url`が紐付く。評価は共通の権限コンポーネントがリクエストパスと照合して拒否を返す。PHPUnitの`Enterprise_Mall`系テストでは、`tenantOnlyAllowedTest`によりテナントへ`Authority::TENANT_OWNER`でログインしたうえで本画面へのGETがHTTP 403となることを確認する。`TENANT_OPERATOR`単体の成否は同一テストクラスでは明示していない。 |
| メンバー単位で追加された権限パターン | 運用上、管理画面のアクセス許可設定で許可リストとブロックリストが変われば結果も変わる。 |
本機能が`dtb_authority_role`を書き換える処理はない。拒否リストの参照のみ行う。
認可評価の詳細アルゴリズムは共通セキュリティコンポーネントの実装を正とする。
