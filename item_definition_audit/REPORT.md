## 0. 結論（先に読む3点）

### ① ご依頼の前提が成立していなかった

**「HTML設計書は現行システム(pf-eccube3)のソースが元になっている」という前提は、実データで成立しない。**
画面項目定義の制約値は**リニューアル後(ec-cube-enterprise)に整合**しており、現行ソースと突き合わせる限り
「乖離」は構造的に大量の偽陽性になる。

決定的証拠（HTMLの数値制約411件を両システムの定数辞書へ機械マッチ）:

| HTMLの値の一致先 | 件数 |
|---|---|
| **ee固有の定数値（pfに存在しない）** | **194** |
| 両方に存在（判別不能） | 176 |
| どちらにも無い（DB型由来など） | 40 |
| **pf固有の定数値（eeに存在しない）** | **1** |

`stext_len` は pf=**50** / ee=**255**。HTMLは255を**88箇所**で使い、255はpfの定数辞書に一つも無い。
0201メンバー管理の「2段階認証」「自動ログアウト設定」「デフォルト検索表示店舗」「編集可能店舗」は
pf `MemberType.php`（6項目のみ）に**存在せず**、ee `MemberType.php:138-171` にのみ存在する。

→ したがって本調査は**三値比較 (HTML, pf, ee)** に切り替えた。

### ② 既存レポートは汚染されている

`functions/item_definition_drift.tsv`（881行）は **HTML vs 機能設計書markdown** の突合であり、
自身のdocstringに「**本スクリプトは config.yml もソースコードも読まない**」と明記されている。

- 「最大文字数の不一致 12件」のうち **7件が 255 vs 50** ＝ EC-CUBE3→4 の `stext_len` 変更そのもの（偽陽性）
- 「確定乖離 56件」のうち **32件がカスタマイズ区分＝カスタマイズの機能**上にある（差異は設計意図）

## 1. 前提: pf=MySQL / ee=PostgreSQL で意味論が変わる

| | pf (現行/MySQL) | ee (新/PostgreSQL) |
|---|---|---|
| DB定義の所在 | `src/Eccube/Resource/doctrine/*.dcm.yml`(42) ＋ `app/Plugin/*/Resource/doctrine/` | `src/Eccube/Entity/*.php` の `#[ORM\Column]` |
| 文字列列の実態 | ほぼ全て `type: text`（length指定なし）＝**65,535バイト** | `type: string, length: N`＝**N文字** |
| 上限超過時 | strict=ERROR / 非strict=**切り捨て**（サイレント破損） | **ERROR**（切り捨てなし）→ 登録/更新不能 |
| 列事実(実測) | 1,028列 / text 245・string 201 | 1,518列 / string 484・text 86 |

**バイトと文字を混同してはいけない。** ee定数にも換算の痕跡がある:
```
eccube_product_stock_change_reason_max_len: 16384 # 65535byte制限を4バイト文字の文字数制限で指定
```
HTMLの `65535`（12件）はMySQLのバイト上限由来で、Postgresには対応概念が無い。
pf `CustomerAddrValidator.php:18` は **Shift-JISバイト長**90 を検査し、ee の90は**文字数** — 同じ数字で意味が違う。

### 判定の原則

**画面項目定義の「最大文字数」＝その画面で入力できる最大長＝FormType の `Assert\Length`。**
DB列長は「その数字がどこから来たか」の説明にはなるが、画面仕様としての正しさは保証しない。
（`password` のDB列255は**ハッシュの保存領域**であり、平文パスワードの入力上限ではない）
`max_length` / `maxlength` は**表示属性**でありサーバ側検証ではない（クライアントで回避可能）。

## 7. 捏造ゼロの担保方法

**LLMは値を生成しない。値はパーサだけが出す。**

1. **決定的パーサ**が `file:line` 付きで値を抽出（`factbase.py` / `dbfacts.py`）
2. **エージェント**は「どのFormType/Entityのどの項目か」の**対応付けのみ**を担当し、
   全主張に**実ファイルの逐語引用**を添える
3. **機械ゲート**（`gate.py`）が実ファイルを読み直し、①ファイル実在 ②引用が該当行に literal に存在
   ③主張値が引用内に literal に存在 ④定数経由なら定数定義の引用も必須 — を検証。**1つでも落ちれば値を採用しない**
4. ゲートは**自己テスト済み**（真の主張3件を通過、捏造3件＝存在しない値・存在しないファイル・行番号違いを全棄却）
5. DB層では**エージェントの値を一切採用せず**、対応付けだけを使ってパーサから値を引き直した
   （実際にエージェントが `pf memo は length:65535` と誤報したが、実ファイルは `type: text` で length 無し → 破棄）

**実績**: 解決器の全主張のうちゲート棄却は最終2件。棄却理由は全て「値が引用内に無い（定数引用の欠落）」で、
**「ファイルに引用が存在しない」＝捏造は0件**。

**「判定漏れ0」と「捏造ゼロ」は両立しない。** 全4,655行に無理やり判定を付けることが捏造の発生源であるため、
**確定不能を正当な分類として計上**した（文字数50 / 数値82 / 必須4,106）。
