# 機能設計書Markdown 書き直し指示（0203の型へ）

あなたは機能設計書Markdownを1本ずつ書き直す。**新しい事実を作らない**ことが最優先である。

## 手順

1. 対象ファイルを読む。
2. 下記の型と禁止事項に従って書き直す。
3. **Writeツールで同じパスへ上書きする。**

## 出力する型（H2はこの3つだけ・この順）

```
# <元のH1をそのまま>

## 業務ロジック

### <内容固有の小見出し>

（本文）

## 入出力

| 種類 | 内容 |
|------|------|
| 入力 | … |
| 成功時出力 | … |
| 失敗時出力 | … |

### 入出力: 永続化

（更新するものがある場合だけ置く。無い機能ではこの節ごと書かない）

| 操作 | 契機 |
| --- | --- |
| 追加 | … |

## 表示メッセージ

| メッセージID | 表示位置 | 画面上の文言 | 表示条件 | 後続処理 |
| --- | --- | --- | --- | --- |
```

- 元が「処理フロー」に書いていた手順は、業務ロジックの**内容固有のH3**へ畳む。
  「一覧を開く（GET）」のようなHTTPメソッド見出しは作らない。
  良い見出し例: 検索条件 / 初期表示 / 並び順 / 在庫数の更新 / 出力する列 / 値の取り方 /
  保存の判定順序 / 他機能との境界 / エラー時の扱い
- 元が「エラー処理」に書いていた表は、業務ロジックの末尾に `### エラー時の扱い` として置く。
- 汎用ラッパー見出し（業務ルール・計算 / 集計・判定・計算 / エッジケース / データ整合性 /
  入力項目 / 副作用）は**作らない**。内容は親節の本文へ流す。
- 定型節（ログ・監査 / 権限・認可 / セッション / Cookie / 排他制御・トランザクション /
  試行制限 / ログに出してはいけないもの）は**書かない**。

## 3分類の外でも必ず残すもの（2026-08-21 追加・落とすと台帳検証がNGになる）

次の2つは3分類に属さないが、**H1直下の `###` 節としてそのまま残す**（内容も削らない）。

```
### Excel基本設計により廃止された仕様（刷新後は実装不要）

- <元の記述をそのまま>

### フェーズ2対応（フェーズ1では実装しない）

- <元の記述をそのまま>
```

元ファイルに「により廃止」「はフェーズ2対応」を含む行があれば、それは廃止台帳・Ph2台帳が
参照している記述である。文言を短くしたり要約したりせず、原文のまま移すこと。

## 絶対禁止

1. **元ファイルに無い事実を書かない。** 推測で補わない。不明なことは書かない。
2. **メッセージ表の行を落とさない。** メッセージIDと「画面上の文言」は**原文のまま逐語で**転記する。
   言い換え・敬体化・要約・実行時値への差し替え（`%maxRecord%` → `5010`）は違反。
   列構成が違う表が複数あっても、5列（メッセージID/表示位置/画面上の文言/表示条件/後続処理）に
   統合して**全行**残す。メッセージIDが無い行は `—` とする。
3. **実装手段を書かない。** クラス名・メソッド名・ファイル名・イベント名・フォーム型名・
   セッションキー・翻訳キー・設定キー・定数名・`Repository`/`Controller`/`Twig`/`Doctrine`/
   `Symfony`/`handleRequest`/`dispatch`/`flush`/`persist` などを残さない。
4. **DB物理名を書かない。** `dtb_*` `mtb_*` `plg_*` は業務名へ言い換える
   （例: `dtb_product_class.product_code` → 規格コード、`dtb_member` → 管理者アカウント）。
   ただし現行と移行先で**物理名の差そのものが仕様内容**の箇所（例: 移行先に `del_flg` が無い）は
   その事実として残してよい。

## 文章

- 結論を先に置く。1事実1文。接続詞で文を始めない。意図や目的を説明しない。
- 手順の番号書き（1. 2. 3.）は、順序自体が仕様のとき（判定順序など）だけ表で残す。
  それ以外は業務の記述に直す。
- 分量は元の 1/2〜1/3 が目安。内容を削るのではなく、実装手段と重複を落とした結果としてそうなる。
