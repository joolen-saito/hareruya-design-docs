# 機能設計書Markdown 書き直し規準（0203 を型とする）

0203_基本設計仕様書(受注管理機能) に埋め込まれている22本の正本Markdownから機械抽出した型。
書き直しはこの型に合わせる。**内容の出どころは変えない**（現行ソース・Excel正本のまま）。

## 1. 節構成（H2 は3つだけ・この順）

```
## 業務ロジック
## 入出力
## 表示メッセージ
```

- 22本すべてがこの3節のみを持つ。処理フロー・エラー処理の節は無い。
- 旧「処理フロー」の内容は、業務ロジックの**内容固有のH3**へ畳む（「一覧を開く（GET）」のような
  HTTPメソッド見出しは作らない）。
- 旧「エラー処理」の内容は、業務ロジック（判定・分岐として書けるもの）か表示メッセージ
  （利用者に見えるもの）へ振り分ける。

## 2. 小見出し（H3）は内容固有の名前にする

0203 の実例: 検索条件 / 入力値の扱い / 複数条件を同時に指定したときの上書き /
フリーワードの分割と検索 / 日付の検索対象 / 検索の成立条件 / 初期表示 / 保存済み検索条件 /
計算方法 / 出力対象の受注 / 出力する列 / 値の取り方 / 行の作り方 / 明細の並び / 改ページ /
印刷対象 / 納品書の組み立て / 差出人・届け先の表示 / 金額の表示 / 受注の更新

- 汎用ラッパー（業務ルール・計算 / データ整合性 / エッジケース / 入力項目）は作らない。
- 定型節（ログ・監査 / 権限・認可 / セッション / Cookie / 排他制御・トランザクション /
  試行制限 / ログに出してはいけないもの）は書かない（共通仕様と粒度規約で非出力）。

## 3. 「入出力: 永続化」は更新するものがある機能にだけ置く

論理名で書く。物理テーブル名・列名は書かない。**更新対象の表を持たず「更新しない」だけの節は書かない**
（2026-08-19 ユーザー決定。`sync_markdown_exclusions.py drop` が機械的に落とす）。

```
### 入出力: 永続化

保存済み検索条件は検索パターンテーブルに保持する。項目はID・パターン名・検索パターン・画面キーである。

| 操作 | 契機 |
| --- | --- |
| 登録・更新 | 検索条件保存 |
| 削除 | 検索条件削除 |

受注側のデータは更新しない。
```

## 4. 表示メッセージは5列の表1枚

```
| メッセージID | 表示位置 | 画面上の文言 | 表示条件 | 後続処理 |
```

- フラッシュ・トースト / フォームバリデーション / 確認ダイアログ のような表示区分ごとの
  小見出し分割はしない。
- 翻訳キー（`admin.common.save_complete` 等）は書かない。文言は画面上の文言をそのまま書く。

## 5. 文章

- 結論を先に置く。接続詞で文を始めない。意図や目的を説明しない。
- 実装手段（クラス名・メソッド名・ファイル名・イベント名・Doctrine/flush 等）を書かない。
- DB物理名を書かない（論理名対応表 `e2e/config/logical-names.tsv` の論理名を使う）。
  物理名の差そのものが仕様内容の箇所だけ `e2e/config/logical-names-keep.tsv` に登録して残す。
